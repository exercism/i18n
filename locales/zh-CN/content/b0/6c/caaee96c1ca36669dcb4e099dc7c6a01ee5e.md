# 简介

一条指令看起来可能是一个不可分割的动作，实际却完全不是这么回事。以给内存中的某个值加上 5 为例：

```x86asm
add qword [rel counter], 5
```

在底层，处理器并没有直接对内存做加法的办法。它会把这一条指令拆成三个更小的步骤，称为**微操作**：

1. 从内存**读取**当前的值；
2. 在寄存器中**修改**这个值，给它加上 5；
3. 把结果**写回**。

```x86asm
mov rax, qword [rel counter] ; 1. load the current value
add rax, 5                   ; 2. add five
mov qword [rel counter], rax ; 3. store the result back
```

这是一个常见的模式，叫做**读取-修改-写入（RMW）**。

注意，读取（或加载）和写入（或存储）是两件独立的事情，它们之间有一段时间窗口。我们通常察觉不到，因为在单个核心上，每条指令都保证会在下一条指令之前完整地产生效果。因此这个窗口是不可见的，`add`表现得就像一个整体。

然而，现代的 CPU 很少是单核的，应用程序常常同时运行在多个核心上，彼此之间没有先后顺序。当多个核心在同一瞬间运行时，另一个核心可能在这个窗口内读写`counter`，也就是在本核心加载之后、存储之前。两个线程各自加载同一个旧值，各自加 5，再各自存回结果。两次加法都发生了，但值只增加了 5。有一次更新被悄无声息地丢掉了。

这就是**数据竞争**，是多线程代码中常见的问题。

并不是每个值都会这样暴露在外。每个线程都有自己的寄存器和自己的栈，所以保存在寄存器里的值，或者线程栈上的局部变量，都只属于该线程，不会发生竞争。只有线程共享的内存，比如上面的`counter`，才需要保护。

x86-64 提供了一组指令来解决这个问题，办法是让指令变得不可分割。它不仅对处理它的那个核心表现为一个整体，对其它所有核心也是如此。这种保持完整、其它核心无法拆开的操作，称为**原子操作**。

~~~~exercism/note
人们常把运行在多个核心上的应用程序称为多线程。
然而，**线程**和核心并不是一回事。
两个线程可能在同一核心上并发运行、彼此交错，也可能在不同核心上并行运行。

如果一个读取-修改-写入被拆成了多条指令，交错的线程之间就已经可能发生竞争，因为操作系统可以在任意两条指令之间切换线程。
不过，_单条_指令内部的那个窗口，只有真正并行的代码才会暴露出来。
因为操作系统只在指令之间切换线程，从不在一条指令内部切换，所以单条指令在单个核心上天生就是安全的。

下面这些指令所提供的，正是跨_多个_核心的真正原子性。
~~~~

## 原子交换

`xchg`指令交换两个操作数。目的操作数变成源操作数原来的值，而源操作数变成目的操作数原来的值。从概念上讲，可以把它看作两条`mov`指令同时发生。

和通常一样，它既可以用于两个寄存器操作数，也可以用于一个内存操作数和一个寄存器操作数：

```x86asm
mov  eax, 1
xchg dword [rdi], eax ; [rdi] = 1, eax = the old value of [rdi]
mov ecx, 2
mov edx, 3
xchg edx, ecx         ; edx = 2, ecx = 3
```

当用于内存操作数时，`xchg`_始终_是原子的。

~~~~exercism/caution
当其中一个操作数是内存位置时，`xchg`自动就是原子的。
这也意味着在这种情况下，该操作会慢很多。

如果你不需要原子性，不妨改用普通的`mov`指令，通过一个空闲寄存器来完成交换。
~~~~

## lock 前缀

在 x86-64 中，让一条指令变得原子，最常见的方式就是加上`lock`前缀。它把读取、修改和写入融合成一个不可分割的步骤。这意味着在整个过程中，这个核心独占该内存，其它核心无法在中途读写这个位置。

```x86asm
lock add qword [rel counter], 5 ; the read, the modify, and the write are one step
```

`lock`只在目的操作数是内存时才有效，而且只适用于对那块内存做读取-修改-写入的指令：

1. 算术运算，例如`add`、`sub`、`inc`、`dec`、`neg`；
2. 位运算，例如`and`、`or`、`xor`、`not`；
3. 位操作`bts`、`btr`、`btc`；
4. 一些其它专用指令，例如下面要介绍的`xadd`和`cmpxchg`。

~~~~exercism/caution
独占一个内存位置、把所有其它核心挡在外面，并不是没有代价的。
带`lock`前缀的操作明显比它的普通形式慢，当多个核心争用同一个位置时还会更慢。

这个前缀应当只用在预期会被多个线程修改的内存上。
如果内存并不共享，或者只被读取，就不要使用它。
~~~~

## 交换并相加

单纯的`lock add`会更新内存，却把旧值丢掉。而旧值常常正是你想要的，比如给每个线程分配一个不同的票号。

`xadd`指令（`x`代表 exchange，也就是交换）在相加的同时返回之前的值。它把和写入目的操作数，并把目的操作数原来的值留在源寄存器中。

```x86asm
mov  rax, 1
lock xadd qword [rdi], rax ; [rdi] = [rdi] + rax = [rdi] + 1
                           ; rax = the old value of [rdi]
```

加上`lock`前缀后，这就是一个原子的**取回并相加**。当许多线程对同一个计数器执行它时，每次调用都会返回一个不同的旧值。

和`lock add`一样，计数器最终正好等于调用的次数。不过，与`lock add`不同的是，每一个中间值也会被返回，一个调用者得到一个。

## 比较并交换

`xadd`做加法，`xchg`做覆盖，但两者都无法让新值取决于当前值，并且只在底层没有发生变化时才应用它。这种有条件的更新，正是`cmpxchg`（比较并交换）所提供的，也是这些原语中最通用的一种。

`cmpxchg dest, src`把`rax`当作隐式的累加器，拿它和`dest`比较：

- 如果`dest == rax`，那么`dest = src`，且`ZF = 1`。
- 如果`dest != rax`，那么`rax = dest`，且`ZF = 0`。

注意，只有当`dest`等于之前加载到`rax`中的预期值时，它才会被更新。这个相等关系保证了`dest`仍然保存着用来计算新值的那个值，因此基于过期读取的更新永远不会被应用。这使`cmpxchg`成为原子更新的基本构件，也称为**比较并交换（CAS）**：

```x86asm
    mov rax, qword [rdi]          ; rax = the value we expect to find
.retry:
    lea rcx, [rax + 10]           ; rcx = the new value we want to install
    lock cmpxchg qword [rdi], rcx ; if [rdi] still equals rax, store rcx and set ZF
                                  ; otherwise reload rax with the current value, clear ZF
    jnz  .retry                   ; ZF is cleared, so another thread won the race. Recompute and retry
```

这个**重试循环**是无锁更新的核心。读取与比较并交换之间的窗口，正是另一个线程可能插手的时机，而`cmpxchg`通过拒绝存储基于过期读取算出的值，把这种情况捕获下来。

## 内存排序

到目前为止，每个操作都只涉及一个内存位置。当线程通过多个位置进行协调时，就会出现一个新问题：一个线程的写入以什么顺序对另一个线程可见。回答这个问题的规则，就是处理器的**内存排序**。

无分支代码那个概念已经介绍过一个想法：现代核心不会一条一条地慢吞吞执行指令。它同时让许多指令在运行中，并在可能的地方提前执行。这意味着，一次写入对其它核心可见的时间，可能比程序所暗示的更晚，而它后面的指令却已经先行执行了。

x86-64 在普通的加载和存储之间保持**强内存排序**，因此在每个核心上：

1. 加载永远不会被重排到后面的加载之后；
2. 存储永远不会被重排到后面的存储之后；
3. 加载永远不会被重排到后面的存储之后。

唯一可能出现的重排，是一次存储看起来在随后对_不同_地址的加载之后才完成。

带`lock`前缀的指令，或者带内存操作数的`xchg`，是一道完整的屏障：任何东西看起来都无法从任一方向越过它。这就是为什么在大多数情况下，它们足以保证完整的顺序。

## 自旋与`pause`

在设置某个标志位的同时返回它之前状态的指令，称为**测试并设置**。它们可以用来构成**自旋锁**，确保某个核心对某段代码拥有独占访问权。

整体算法如下，用`xchg`指令配合一个二值标志：

1. 标志初始为`0`。
2. 要获取锁，核心把标志中的值和`1`交换。
3. 如果返回的值是`1`，说明锁正被另一个核心_持有_。当前核心于是等待，并再次尝试获取锁。
4. 如果返回的值是`0`，说明锁原本是空闲的。此时`xchg`已把它设为`1`，其它核心会一直等到这个核心释放它。
5. 当前核心完成工作后，把标志更新为`0`即释放锁。

```x86asm
acquire:
    mov  eax, 1
    xchg dword [rdi], eax ; try to take the lock; eax = its old value
    test eax, eax
    jnz  .held            ; old value was 1: someone else holds it
    ret                   ; old value was 0: the lock is ours
.held:
    pause                 ; wait before trying again
    jmp  acquire
```

等待循环里的`pause`指令并不改变代码算出的结果。它是在提示处理器：这是一次自旋等待。CPU 就能降低等待线程的功耗，并把执行机会让给共享同一核心的兄弟线程。没有`pause`的自旋循环依然正确，只是白费力气。

线程完成工作后，可以用`mov`做一个普通的`0`存储来释放锁。除了`mov`之外什么都不需要，因为在 x86-64 上，加载和存储永远不会被重排到后面的存储之后。如果一个存储永远不会越过它之前的访问，就说它具有**释放排序**，而在 x86 上，每个普通存储都带有这种排序。

~~~~exercism/note
任何能原子地测试并设置某个内存位置的指令，都可以用来实现自旋锁。
例如，可以用`lock bts`代替`xchg`，在设置某一位的同时检查它是否已被设置。

注意，标志位（例如被`bts`修改的`CF`）是寄存器`rflags`的一部分。
这意味着它们为每个线程所独有。
~~~~

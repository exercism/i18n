# 为 C Track 做贡献

感谢你有兴趣为 Exercism C 语言 track 做贡献！
我们欢迎一切贡献，无论是新增练习、修改工具或文档、提出问题，还是仅仅在现有 issue 或 PR 下留个评论。
本文件提供了一些信息，帮助你起步。

首先，请读一读 [Exercism 文档][Exercism docs]，特别是关于[为语言 track 做贡献][contributing to a language track]的内容，这些文档涵盖了大量的基础知识。

其次请注意，本代码仓库还有一些特有的事项，下面会加以说明。

我们鼓励提交对现有练习的错误修复和改进。
请注意，本 track 的练习必须符合 [problem-specifications][] 代码仓库所确定的标准。
对通用练习的测试或文档所做的改动，往往需要先在该代码仓库中提交一个 pull request，之后才能被纳入本 track 的练习。
如果你不确定，就尽管开一个 GitHub [issue][]，我们一起来讨论这个改动。

## 行为准则

帮助我们让 Exercism 保持友好包容。
请阅读并遵守[行为准则][Code of Conduct]。

## Git 工作流

1. Fork 并 clone。
2. 把这个代码仓库添加为你 clone 的一个新远程：`git remote add upstream https://github.com/exercism/c.git`
3. 新建一个分支：`git checkout -b name-of-branch`
4. 照常在你的新分支上 commit 并 push
5. 当你准备好提交 pull request 时，把你的分支 rebase 到上游 main 上，这样就能解决冲突：`git fetch upstream && git rebase upstream/main` 解决冲突后，你可能需要用 `--force` push 到你的分支。
6. 一切准备就绪后，push 到你的分支，并按下面的说明创建 pull request。

## Issues

我们在代码仓库里用 GitHub [issues][] 来跟踪 bug、功能改进和支持请求。

关于整个项目更高层面的讨论，请查看 [discussions][] 代码仓库中的 issues。

### 适合新手的第一个补丁

如果某个 issue 我们认为不需要太多 Exercism 代码库或功能方面的背景知识就能解决，就会尽量给它打上“good first patch”标签。想找到它们，可以搜索 [good-first-patch][]。

## Pull Requests

如果在创建 PR 时能遵循这些简单的 [pull request 指南][pull request guidelines]，那就太好了，不过这并不是必须的。

Pull request 应该聚焦于单个 issue 或改动。
我们欢迎对代码风格和措辞的修改，但如果可能，请为这些改动另开一个 PR。
如果要创建会显著（破坏性地）改变现有练习、或跨多个练习进行改动的 PR，请先开一个 issue。最好在动手之前先讨论这些改动。

如果你的改动针对某个练习，你可以在提交 pull request 之前运行 CI 脚本，它们也会在之后自动运行，详见[持续集成][Continuous Integration]。

提交 pull request 时，我们有时会请你先做些修改，然后再接受这个补丁。

请不要关掉第一个 pull request，再另开一个带着这些改动的新 PR。
如果你向已经开过 pull request 的分支再 push 更多 commit，pull request 会自动更新。

如果你想创建一个改动尚未完全准备好合并到 main 的 PR（比如你想讨论某个具体条目），可以照常创建 PR，然后用 GitHub 网站界面[把 PR 转换为草稿][convert the PR to a draft]，这样维护者就知道它还没准备好被合并。

和添加更多 commit 一样，如果你修改了历史（rebase、squash、amend），并用 git push --force 更新你 fork 上的分支，你不需要关闭 pull request 再开一个新的。
Pull request 指向的是那个分支，而不是具体的 commit。

## 代码风格

代码改动贡献所期望的代码风格在[风格指南][style guide]中有说明。

练习代码会在 [CI][Continuous Integration] 期间检查是否符合空格与缩进风格规则。
该检查使用[`clang-format`][clang-format]命令行工具。
当你新增或修改一个练习时，可以在提交前先在本地运行这个工具，检查你的改动是否符合这些规则。

在 Linux 上，`clang-format` 应该可以通过你的发行版包管理器安装。
在 Mac 上，你可以用 [Homebrew][] 安装 `clang-format` 包。

clang-format 可以通过执行 `format.sh` 对所有文件运行。
要手动对单个文件运行，可以执行以下命令：

```bash
clang-format -i $(file)
```

## 练习结构

每个练习都应放在目录 `c/exercises/practice/{exercise-name}` 中。
关于如何实现一个符合规范的练习，深入细节参见[按规范实现练习][implement-an-exercise-from-specification]。

一个练习目录的结构如下（注意目录名和文件名分别使用连字符和下划线）：

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - 本文件包含该练习的所有测试。  
`test-framework` - 存放来自 [ThrowTheSwitch][] 的测试框架 [Unity][] 的目录。  
  ThrowTheSwitch 有一份不错的 [Unity 入门][getting started with Unity]指南，如果你想看教程的话。  
  所用的 Unity 版本在[版本][versions]中注明。测试文件的布局在[风格指南][test-file-layout]中说明。  
  测试应该按照 [problem-specifications][] 代码仓库中该练习的 `canonical-data.json` 文件来编写。  
`{exercise-name}.c` / `{exercise-name}.h` - 该练习的源文件。  
  请在你的头文件中使用 [include guards][]。
  练习测试可以用 `make test` 从代码仓库根目录运行。
* `makefile` - 是练习的 makefile，用于按需构建。  
需要两条规则，  
test：编译 test_{exercise-name}.c 并运行它。
memcheck：用 -fsanitize=address、-fno-common、-fno-omit-frame-pointer 标志编译 test_{exercise-name} 并运行它。
不同练习之间的 Makefile 变化应该很小，所以从一个练习复制到另一个练习应该很容易。

**别忘了**把练习加入 track 的 `config.json`。为此，你需要在所有其他 track 练习的顺序中确定添加该练习的最佳位置。你还需要生成一个 UUID 加到这里。这两件事你都可以用 [configlet][] 工具来做，做完这些改动后，这个工具甚至会帮你 lint 并格式化 `config.json`！

顺便提一句，要获取 configlet 工具的安装包，请看 [configlet 发布页面][configlet releases page]。

## 持续集成

本代码仓库使用 GitHub 工作流在每个 pull request 的每次 commit 上运行一些工具。
在你自己的贡献上运行这些工作流最简单的方法，是在本代码仓库上开一个带改动的 PR，把 PR 设为草稿，然后让本代码仓库的 CI 设置自动帮你处理一切。

### CI 环境

GitHub 在它称为 [托管运行器][hosted runners] 的虚拟机上运行 CI。
工作流可以配置它们希望运行所在运行器的一些方面。

本代码仓库中的工作流只指定它们各自都应在 Ubuntu 24.04 上运行。这些工作流固定到具体版本，而不是引用 `latest`，因为所使用的一些工具在不同版本上可能有不同的表现。

### 在自己的 fork 上运行 CI

如果你愿意，也可以在自己的 fork 上运行 CI，只需像平常一样在 GitHub 上克隆这个代码仓库。
位于 [`./.github/workflows/`][workflows] 的 YAML 文件应该同样能正常工作。
如果你希望 [`/format`][format-workflow] 自动化 Action 能正常工作，需要给你的克隆代码仓库添加一个部署密钥。

### 工作流

* `checks.yml` 对工具脚本运行 `shellcheck`，随后运行以下这些工具：
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * [Lychee 链接检查器][lychee] Action
* `configlet.yml` 获取最新版本的 configlet，然后对本 track 运行 `lint` 命令
* `format-code.yml` 检查 PR 的任何评论中是否出现字符串 `/format`，如果找到，就对练习运行 `format.sh`，并提交由此产生的任何改动。要让这次 commit 能够重新触发 CI，需要一个部署密钥。该部署密钥由 Exercism 直接管理。
* `test.yml` 在代码仓库根目录运行 `make`，以测试所有练习

### 工具

从[工作流][workflows]可以看出，GitHub 被指示从 [`./bin`][bin] 目录运行工具。
这个目录中工具所做的工作描述如下：

* `check-unitybegin` 确保每个测试文件都在其 `main()` 函数开头正确添加 `UNITY_BEGIN()` 行。
* `fetch-configlet` 从它的[代码仓库][configlet]获取 `configlet` 工具。
* `verify-unity-version` 检查每个练习所用 Unity 测试框架的版本。此文件应检查的版本在 [`./docs/VERSIONS.md`][versions] 中指定。
* `check-include-guards` 检查每个练习的桩文件和示例头文件中所用的 include guard 是否使用了正确的格式，如下所示：

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` 从它的[代码仓库][configlet]获取 `configlet` 工具。

### 在本地运行工具

你也可以在提交前在自己的机器上运行单个工具。
首先确保你已经安装了必要的应用程序（例如 `clang-format`、[`git`][git]、[`sed`][sed]、[`make`][make] 和一个 C 编译器），然后从代码仓库根目录运行所需的工具。例如：

```bash
~/git/c$ make
```

如果你只想运行部分测试来检查你的工作，可以把它们指定为 make 的目标。

```bash
~/git/c$ make acronym all-your-base allergies
```

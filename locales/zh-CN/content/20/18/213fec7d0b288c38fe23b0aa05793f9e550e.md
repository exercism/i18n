# 简介

`GenServer`（通用服务器）是一种[行为][concept-behaviours]，它抽象了 Elixir 进程之间常见的客户端与服务器交互。

还记得我们学习[进程][concept-processes]时讲过的接收循环吗？`GenServer`行为提供了抽象，方便你实现这类循环，也方便你与运行这类循环的进程交换消息。它让保存状态和执行异步代码变得更容易。

~~~~exercism/note
请注意，`GenServer`这个名字含义很多。它也用来指_使用_`GenServer`行为的_模块_，以及从使用`GenServer`行为的模块启动的_进程_。
~~~~

`GenServer`行为定义了一个必需的回调`init/1`，以及几个值得一提的可选回调：`handle_call/3`、`handle_cast/2` 和 `handle_info/3`。使用`GenServer`的_客户端_不应该直接调用这些回调。相反，`GenServer`模块提供了一些函数，客户端可以用它们与`GenServer`进程通信。

通常，一个模块既定义了_客户端 API_，也就是 Elixir 应用的其他部分可以用来与这个`GenServer`进程通信的一组函数，也定义了_服务器回调实现_，其中包含这个`GenServer`的逻辑。

我们先看一个简单的`GenServer`示例，然后再了解每个回调的含义。

## 示例

这是一个示例服务器，它能回应漫长的公路旅行中烦人乘客没完没了的追问，更准确地说，是这个问题：“我们到了吗？”它会记录这个问题被问了多少次，并给出越来越不耐烦的回复。

```elixir
defmodule AnnoyingPassengerAutoresponder do
  use GenServer
  # Client API

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg)
  end

  def are_we_there_yet?(pid) do
    GenServer.call(pid, :are_we_there_yet?)
  end

  # Server callbacks

  @impl GenServer
  def init(_init_arg) do
    # the initial count of questions asked is always 0
    state = 0
    {:ok, state}
  end

  @impl GenServer
  def handle_call(:are_we_there_yet?, _from, state) do
    reply =
      cond do
        state <= 3 -> "No."
        state <= 10 -> "I told you #{state} times already. No."
        true -> "..."
      end

    # increase the count of questions asked
    new_state = state + 1
    # reply to the caller
    {:reply, reply, new_state}
  end
end
```

## 回调

### `init/1`

可以通过调用`GenServer.start/3`或`GenServer.start_link/3`来启动服务器。我们在[链接][concept-links]概念中了解过这两个函数的区别。

这两个函数：

- 第一个参数接受一个实现了`GenServer`行为的模块。
- 第二个参数叫`init_arg`，可以是任何值。顾名思义，这个参数会传给`init/1`回调。
- 第三个参数是可选的，包含运行进程的高级选项，这里不展开。

通过调用`GenServer.start/3`或`GenServer.start_link/3`启动服务器时，会以阻塞的方式调用`init/1`回调。`init/1`的返回值决定了服务器能否成功启动。

`init/1`回调通常返回以下值之一：

- `{:ok, state}`。服务器会用`state`作为初始状态，开始它的接收循环。`state`可以是任何类型。
- `{:stop, reason}`。`reason`可以是任何类型。服务器不会开始接收循环。进程会以给定的原因退出。

还有一些更高级的用法，这里不展开。

如果服务器的接收循环启动了，`GenServer.start/3`和`GenServer.start_link/3`会返回`{:ok, pid}`元组。否则返回`{:error, reason}`。

### `handle_call/3`

需要回复的消息可以用`GenServer.call/2`发送给服务器进程。这个函数的第一个参数是正在运行的服务器进程的`pid`，第二个参数是消息。消息可以是任何类型。

`handle_call/3`回调负责处理并响应同步消息。它接收三个参数：

1. `message`：传给`GenServer.call/2`的第二个参数的值。
2. `from`：调用`GenServer.call/2`的进程的`pid`。大多数情况下这个参数可以忽略。
3. `state`：服务器的当前状态。记住，它的初始值是在`init/1`回调中设置的。

`handle_call/3`回调通常返回一个三元组`{:reply, reply, state}`。这表示元组中的第二个元素`reply`（可以是任何类型）会被发送回调用方。元组中的第三个元素`state`是服务器处理这条消息之后的新状态。

还有一些更高级的用法，这里不展开。

~~~~exercism/note
想通过名字记住这个回调的作用，
可以把它想象成给某人“打电话”。

如果对方有空，你会立刻收到回复（同步地）。
~~~~

### `handle_cast/2`

不需要回复的消息可以用`GenServer.cast/2`发送给服务器进程。它的参数与`GenServer.call/2`的参数完全相同。

`handle_cast/2`回调负责处理这些消息。它接收两个参数，`message`和`state`，与`handle_call/3`回调中的参数相同（除了没有`from`）。

`handle_cast/2`回调通常返回一个二元组`{:noreply, state}`。

还有一些更高级的用法，这里不展开。

~~~~exercism/note
想通过名字记住这个回调的作用，
记住“cast”也有“扔”的意思。

如果你把一条消息装进瓶子扔进海里，
就别指望立刻收到回复，甚至可能永远收不到。
~~~~

### 该用`call`还是`cast`？

即使你的客户端代码不需要服务器的回复，也几乎总是应该用`call`。

使用`call`会等待回复，这起到背压机制的作用（防止客户端一次发送太多消息）。收到服务器的回复，也是唯一能确定服务器已收到并处理了客户端消息的方法。

### `handle_info/2`

消息也可能通过调用`GenServer.call/2`或`GenServer.cast/2`之外的方式进入服务器的信箱，例如调用普通的`send/2`函数。

要处理这类消息，使用`handle_info/2`回调。这个回调的工作方式与`handle_cast/2`完全相同。

`GenServer`行为提供了一个`handle_info/2`的兜底实现，它会记录关于意外消息的错误。如果你覆盖了这个默认实现，一定要保留你自己的兜底实现。如果忘了，服务器在收到意外消息时会崩溃。

## 超时

上面介绍的四个回调，其返回值都可以再增加一个元组元素，即超时。例如，`init/1`不返回`{:ok, state}`，而是返回`{:ok, state, timeout}`。

超时可以用来检测信箱在某段时间内没有收到消息。如果服务器从某个回调中返回了超时值，并且在指定的毫秒数内没有消息到达，就会以`:timeout`作为第一个参数调用`handle_info/2`。

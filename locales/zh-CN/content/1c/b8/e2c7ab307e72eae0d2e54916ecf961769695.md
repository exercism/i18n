# 简介

## 原子操作

一条指令看起来可能是一个不可分割的动作，而实际上根本不是。以给内存中的某个值加上 5 为例：

```x86asm
add qword [rel counter], 5
```

在底层，处理器并不能直接对内存做加法。
它把这一条指令拆成三个更小的步骤，称为**微操作**：

1. **读取**内存中的当前值；
2. 在寄存器中**修改**这个值，把它加上 5；
3. 把结果**写回**。

```x86asm
mov rax, qword [rel counter] ; 1. load the current value
add rax, 5                   ; 2. add five
mov qword [rel counter], rax ; 3. store the result back
```

这是一种常见的模式，称为**读取-修改-写入（RMW）**。

注意，读取（加载）和写入（存储）是两个独立的事件，因此它们之间存在一个时间窗口。
我们通常不会注意到这一点，因为在单核上，每条指令都保证在开始下一条之前完整地产生效果。
因此这个窗口是看不见的，`add`表现得就像一个整体。

然而，现代 CPU 很少是单核的，应用程序常常同时运行在多个核心上，它们之间没有任何先后顺序。
当多个核心在同一瞬间运行时，另一个核心可以在那个窗口内读取或写入`counter`，也就是在本核心加载之后、存储之前。
两个线程各自加载相同的旧值，各自加上 5，再各自存储自己的结果。
发生了两次加法，但值却只增加了 5。
有一次更新悄无声息地丢失了。

这就是**数据竞争**，多线程代码中的常见问题。

并不是每个值都会以这种方式被暴露出来。
每个线程都有自己的寄存器和自己的栈，因此保存在寄存器中的值，或者线程栈上的局部变量，都是该线程独有的，不会发生竞争。
只有线程共享的内存，比如上面的`counter`，才需要保护。

x86-64 提供了一组指令来解决这个问题，方法是让一条指令不可分割。
它不仅对处理它的核心表现为一个整体，对其他所有核心也是如此。
这种始终作为一个整体、其他核心无法拆分的操作，称为**原子操作**。

~~~~exercism/note
人们常把运行在多个核心上的应用程序称为多线程。
然而，**线程**并不等同于核心。
两个线程可以在同一个核心上并发运行，相互交错，也可以在不同核心上并行运行。

如果一次读取-修改-写入被拆成多条指令，交错运行的线程本身就可能产生竞争，因为操作系统可以在任意两条指令之间切换线程。
不过，_单条_指令内部的窗口只有真正的并行代码才会暴露出来。
因为操作系统只在指令之间切换线程，从不在指令内部切换，所以单条指令在单核上本身是安全的。

下面这些指令提供的，正是跨_多个_核心的真正原子性。
~~~~

### 原子交换

`xchg`指令交换两个操作数。
目标操作数会变为源操作数之前的值，而源操作数会变为目标操作数之前的值。
从概念上讲，可以把它看成两条`mov`指令同时发生。

和往常一样，它既可以用两个寄存器操作数，也可以用一个内存操作数加一个寄存器操作数：

```x86asm
mov  eax, 1
xchg dword [rdi], eax ; [rdi] = 1, eax = the old value of [rdi]
mov ecx, 2
mov edx, 3
xchg edx, ecx         ; edx = 2, ecx = 3
```

当与内存操作数一起使用时，`xchg`_总是_原子的。

~~~~exercism/caution
当其中一个操作数是内存位置时，`xchg`会自动具备原子性。
这也意味着在这种情况下，该操作要慢得多。

如果你不需要原子性，就改用普通的`mov`指令，通过一个空闲寄存器来完成交换。
~~~~

### lock 前缀

在 x86-64 中，让一条指令具备原子性最常见的方式，就是加上`lock`前缀。
它把读取、修改和写入融合成一个不可分割的步骤。
这意味着核心在整个过程中独占该内存，因此其他核心无法在这期间读取或写入那个位置。

```x86asm
lock add qword [rel counter], 5 ; the read, the modify, and the write are one step
```

`lock`只在目标是内存时才有效，而且只适用于对该内存执行读取-修改-写入的指令：

1. 算术运算，例如`add`、`sub`、`inc`、`dec`、`neg`；
2. 位运算，例如`and`、`or`、`xor`、`not`；
3. 位操作`bts`、`btr`、`btc`；
4. 其他一些专用指令，例如下面会介绍的`xadd`和`cmpxchg`。

~~~~exercism/caution
独占一个位置，并把其他所有核心挡在外面，是有代价的。
带`lock`前缀的操作明显比它的普通形式慢，当多个核心争用同一个位置时就更是如此。

这个前缀应该留给预期会被多个线程修改的内存。
如果内存不是共享的，或者只会被读取，就避免使用它。
~~~~

### 交换并相加

普通的`lock add`会更新内存，但会把旧值丢掉。
很多时候，旧值恰恰是想要的东西，比如给每个线程分配一个不同的号码。

`xadd`指令（`x`表示 exchange）在相加的同时返回之前的值。
它把和写入目标，并把目标原来的值留在源寄存器中。

```x86asm
mov  rax, 1
lock xadd qword [rdi], rax ; [rdi] = [rdi] + rax = [rdi] + 1
                           ; rax = the old value of [rdi]
```

加上`lock`前缀，这就是原子的**获取并相加**。
当多个线程在同一个计数器上运行时，每次调用都会返回一个不同的旧值。

和`lock add`一样，计数器最终会正好等于调用的次数。
不过，与`lock add`不同的是，每一个中间值也都会被返回，分别交给各个调用者。

### 比较并交换

`xadd`做加法，`xchg`做覆盖，但两者都无法让新值依赖于当前值，并且只在底层没有发生变化时才应用它。
`cmpxchg`（比较并交换）提供的正是这种条件更新，它是这些原语中最通用的一个。

`cmpxchg dest, src`以`rax`作为隐式累加器，并将它与`dest`比较：

- 如果`dest == rax`，则`dest = src`，并且`ZF = 1`。
- 如果`dest != rax`，则`rax = dest`，并且`ZF = 0`。

注意，只有当`dest`等于之前加载到`rax`中的预期值时，才会更新`dest`。
这种相等性确保`dest`仍然保存着新值所依据的那个值，因此基于过期读取的更新永远不会被应用。
这使得`cmpxchg`成为原子更新的基础构件，也称为**比较并交换（CAS）**：

```x86asm
    mov rax, qword [rdi]          ; rax = the value we expect to find
.retry:
    lea rcx, [rax + 10]           ; rcx = the new value we want to install
    lock cmpxchg qword [rdi], rcx ; if [rdi] still equals rax, store rcx and set ZF
                                  ; otherwise reload rax with the current value, clear ZF
    jnz  .retry                   ; ZF is cleared, so another thread won the race. Recompute and retry
```

这个**重试循环**是无锁更新的核心。
读取与比较并交换之间的那个窗口，正是另一个线程可能插进来的时机，而`cmpxchg`通过拒绝存储基于过期读取算出的值来抓住这一点。

### 内存排序

到目前为止，每个操作都只涉及一个位置。
当线程通过多个位置进行协调时，就出现了一个新问题：一个线程的写入以什么顺序对另一个线程可见。
回答这个问题的规则，就是处理器的**内存排序**。

无分支代码的概念提到过这样一个想法：现代核心不会一次一条地慢慢执行指令。
它会同时让许多指令处于执行中，并在可能的地方提前运行。
这意味着一次写入变得对其他核心可见的时间，可能比程序所暗示的更晚，而它之后的指令却已经提前执行了。

x86-64 在普通的加载和存储之间保持**强内存排序**，因此在每个核心上：

1. 加载永远不会被重排到更晚的加载之后；
2. 存储永远不会被重排到更晚的存储之后；
3. 加载永远不会被重排到更晚的存储之后。

唯一可能的重排是：一次存储看起来在针对_不同_地址的后续加载之后才完成。

带`lock`前缀的指令，或者带内存操作数的`xchg`，是一道完整的屏障：没有任何东西看起来能跨越它向任一方向移动。
这就是为什么在大多数情况下，它们足以保证完整的顺序。

### 自旋与`pause`

这类在设置标志的同时返回它先前状态的指令，称为**测试并设置**。
它们可以作为**自旋锁**的基础，确保某个核心对代码的某一部分拥有独占访问权。

下面是用`xchg`指令配合一个二值标志的完整算法：

1. 标志一开始是`0`。
2. 为了获取锁，核心把标志中的值与`1`交换。
3. 如果返回的值是`1`，说明锁已被另一个核心_持有_。
   当前核心于是等待，并再次尝试获取锁。
4. 如果返回的值是`0`，说明锁是空闲的。
   `xchg`现在已把它设为`1`，其他核心会一直等到这个核心释放它。
5. 当前核心完成工作后，把标志更新为`0`就释放了锁。

```x86asm
acquire:
    mov  eax, 1
    xchg dword [rdi], eax ; try to take the lock; eax = its old value
    test eax, eax
    jnz  .held            ; old value was 1: someone else holds it
    ret                   ; old value was 0: the lock is ours
.held:
    pause                 ; wait before trying again
    jmp  acquire
```

等待循环中的`pause`指令不会改变代码计算出的结果。
它向处理器提示这是一次自旋等待。
CPU 于是可以降低等待线程的功耗，并让位给共享同一核心的兄弟线程。
没有`pause`的自旋循环依然是正确的，只是浪费。

线程完成工作后，可以用`mov`以普通的存储写入`0`来释放锁。
需要的不过是一条`mov`而已，因为在 x86-64 上，加载和存储永远不会被重排到更晚的存储之后。
一次存储如果从不越过它之前的访问，就说它具有**释放排序**；在 x86 上，每条普通存储都具备这一点。

~~~~exercism/note
任何以原子方式测试并设置某个内存位置的指令，都可以用来实现自旋锁。
例如，可以用`lock bts`代替`xchg`，在设置某个特定位的同时检查它是否已经被设置。

注意，像被`bts`修改的`CF`这样的标志，是寄存器`rflags`的一部分。
这意味着它们对每个线程都是独有的。
~~~~

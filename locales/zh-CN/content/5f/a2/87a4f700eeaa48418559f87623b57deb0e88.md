# Markdown 规范

以下是 Exercism 中所有 Markdown 文件应当遵循的结构方式。

本文档中的部分规则尚未在整个 Exercism 中落实。
我们欢迎大家提交 PR 来修复。
所有规则都在逐步加入我们的 CI 和代码检查工具，新的改动都应当遵守。

## 标题

- 所有文件都必须以一级标题（`# Some heading text`）开头。
- 一级标题纯粹是为了在 GitHub 或同类平台上展示。
- 如果文件由 Exercism 渲染（例如显示在网站上，或通过 CLI 渲染），这个标题会被移除，并插入一个与上下文相关的标题。
- 标题最多只能比上一级低一级（例如 `##` 后面只能接 `###`，不能接 `####`）。
- 除了唯一的一级（`#`）标题外，只能使用二级（`##`）、三级（`###`）和四级（`####`）标题。

## 链接

请使用[引用式链接][reference-links]。这类链接在 Markdown 文件底部定义，映射到一个引用 slug，并在正文中通过该 slug 引用。

这种方式让维护更容易，因为链接只需在一个地方更新。

示例：

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

链接应当始终带有锚文本，而不是把 URL 本身放进正文。例如，下面这个就没有使用锚文本，也更难阅读。

```
If you want some more information, please visit https://google.com.
```

使用锚文本并对其加链接，更容易理解，也更容易看出语境。

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

渲染出来是：“如果你想了解更多信息，[Google][google-link] 是一个有用的资源。”

## 代码

凡是提到代码元素（例如函数或关键字）时，都应当用反引号把代码括起来：

```
- The `printf()` function writes to the console.
```

渲染结果如下：

- `printf()` 函数会写入控制台。

更复杂的代码（例如多行代码）应当用三个反引号括起来。为了启用语法高亮，应当在起始的三个反引号后面指定一个[语言标识符][language-identifier]：

````python
```python
# Define a variable
album = "Abbey Road"
```
````

在可能的情况下，以最贴合代码所处环境的方式来格式化代码。如果有的话，请参考你所使用语言的文档。

例如，Python 有 REPL（读取-求值-打印循环），它允许程序员直接在终端里输入代码。如果用户正在调试某段代码，或者在本地运行一个函数来测试、观察它的行为，他们更可能用 REPL 来做这件事，因为在里面交互式地输入更方便。在这种情况下，我们更倾向于把示例代码格式化成像是输入到 REPL 里的样子，并在前面加上 `>>>`：

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

在另一些情况下，把代码格式化成像是放在 `.py` 文件里的样子更合理。这样，学生看到的内容就跟他们自己写代码的方式相似，对他们更有帮助。

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

当分不清该用哪种方式时，有一个快速判断的方法：如果这是学生能在终端里运行的代码，就按那种方式格式化。如果是 Exercism 可能会运行的代码（在测试里、学生将要编写的库代码里等），就默认把它格式化成可运行的代码。

## 特殊块（有时称为 admonition）

我们支持几种特殊类型的块，可以把不适合放在正文里的说明单独提取出来，加到文档中。

<img width="500" alt="Markdown 提示块" src="https://user-images.githubusercontent.com/20866761/139531109-0c0f3ea5-b589-44ff-93ab-d901a45edc56.png">

<img width="500" alt="Markdown 警告块" src="https://user-images.githubusercontent.com/20866761/139531234-9b58b9ab-524b-44fd-bbcb-4e10f2927d27.png">

<img width="500" alt="Markdown 进阶块" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

我们支持三种类型的块：

- **exercism/note：** 用来提取一些额外特殊信息的块
- **exercism/caution：** 人们应当了解或谨慎对待的事项
- **exercism/advanced：** 只对那些想更深入钻研某样东西、或者本应具备更进阶知识的人才有用的信息。

所有块都用 4 个波浪号（~）书写，格式如下：

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

（注意：在特殊情况下，你也可以使用反引号或其他数量的波浪号）

## 布局

### 每行一句

段落应当按每行一句来排列。[Ascii Doctor 文档][asciidoctor] 清楚地解释了这个逻辑。

例如，一个段落的排版应当如下：

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## 列表

无序列表使用连字符（`-`）作为项目符号。

## 注释

- 优先使用 Markdown 注释，而不是 HTML 注释（例如使用 `[comment]: # (Actual comment...)`，而不是 `<!-- Actual comment -->`）

你可以在 [babelmark3] 上查看注释经 commonmark 渲染后的效果，以此测试你的 Markdown 注释是否会被移除。

## 内联 HTML

- 允许使用内联 HTML，但应当谨慎使用
- 如果有原生 Markdown 的替代写法，就始终使用它（例如使用 `# ...`，而不是 `<h1>...</h1>`）

## 图片

由于网站支持浅色和深色主题，社区提交的图片必须在两种主题下都能良好显示。
解决办法是给图片名称加上后缀（加在文件扩展名之前）：

1. 让图片名称以 `-invertible` 结尾（例如 `graph-invertible.svg`）。在深色主题下显示时，图片会被自动反色（通过 `filter: invert(100%)`）。
1. 让图片名称以 `-light` 结尾（例如 `graph-light.png`），同时再创建一个兼容深色主题、以 `-dark` 结尾的版本（也就是 `graph-dark.png`）。我们会根据用户使用的主题自动渲染正确的图片。

两个后缀都不带的图片，会在两种主题下原样使用。
这意味着如果你想制作灰度图片，通常可以让它在浅色主题下看起来不错，然后把它设为可反色。
但如果你用的图片颜色很多，也许就想做两个版本。

在渲染图片的地方，应当把完整的图片名称（包括 `-invertible`）写进 Markdown。
对于浅色/深色版本，**只**加入 `-light` 版本。
这套逻辑适用于所有 Markdown 文档。

## 代码检查工具

你可以用各种规则来配置代码检查工具，使其符合本规范：

- [MD001][md001]：启用
- [MD002][md002]：启用
- [MD003][md003]：使用 `atx` 风格
- [MD004][md004]：使用 `dash` 风格
- [MD013][md013]：停用
- [MD033][md033]：停用

## 自动格式化

有些代码仓库使用 [prettier][prettier] 来确保所有 Markdown 的格式保持一致。这会带来以下好处：

- 无需为格式争论。
- 出色的编辑器/IDE 集成，文件可以在保存时自动格式化。
- 很容易为格式添加 CI 检查。
- 很容易用脚本自动格式化文件。

以上这些都能大大减少评审过程中的频繁变动，这种变动对评审者和被评审者来说都很折磨人。

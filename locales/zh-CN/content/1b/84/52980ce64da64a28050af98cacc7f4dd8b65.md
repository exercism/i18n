# 关于

[调用栈][stack]（简称**栈**）是一种特殊的数据结构，它从内存的最高地址开始，向下增长。

## push 与 pop

栈至少支持两种操作，每种操作都有同名的指令：

| 指令 | 执行的操作 |
| ----------- | --------------------------------------------------- |
| `push`      | 向栈中添加一个元素 |
| `pop`       | 移除并返回最近添加的那个元素 |

这意味着栈是一种**后进先出（LIFO）**的数据结构。

为了跟踪栈的当前位置，也就是最新元素所在之处，我们会用到`rsp`寄存器。

所以，一条 [push][push] 指令接收一个操作数，并把这个操作数的内容存入栈中。
由于栈向下增长，`rsp`中的值会减去所存入值的大小。

类似地，一条 [pop][pop] 指令接收一个操作数，并把栈中最新的值（也就是`rsp`指向的那个值）存入这个操作数。
随后，`rsp`中的值会增加，增加量等于取出的值的大小。

## 局部变量

也可以直接修改`rsp`的值。
这通常用于为函数创建局部变量。

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

注意，在栈中预留出空间的那一刻，这块空间里存储的值是_未定义_的。

~~~~exercism/note
无论`pop`还是直接修改`rsp`，都不会真正清除内存中存储的内容。
栈的“移除”只是通过`rsp`中的新地址抽象出来的。

在某些场景中，这可能会把内部的值暴露给外部来源，从而引发安全问题。
应对办法之一，是把函数用到的所有栈空间的内容清零。
~~~~

## call 与 ret

栈的主要作用是跟踪被调用函数的返回地址。

正如之前的一个概念中提到的，有一个特殊的寄存器`rip`，它指向下一条要执行的指令。
这个寄存器用于控制程序的流程，`jmp`和`call`之类的指令会修改它。

每当使用一条`call`指令时，`rip`中的当前值会被隐式地压入栈中。
随后，该指令的操作数被移入`rip`，执行便在被调用的函数中继续。

一条`ret`指令执行相反的操作。
它从栈中弹出值存入`rip`，于是执行返回到调用它的函数。

在进入函数时，`rsp`指向要返回的那个地址。
这正是`ret`必须从栈中弹出的地址。

所以，函数内部对`rsp`值的任何改动，无论是直接修改还是通过`push`修改，都必须在函数返回前撤销。

## 被调用者保存寄存器和调用者保存寄存器

除了`rsp`，还有其他一些寄存器必须在函数调用前后保持不变：`rbp`、`rbx`、`r12`、`r13`、`r14`和`r15`。
一般来说，调用函数希望自己在使用这些寄存器时，它们不会被被调用的函数改动。

这意味着_被调用_的函数在使用这些寄存器之前，必须先保存其中的值，并在返回前把它们恢复为原来的值。
这就是它们被称为**被调用者保存寄存器**的原因。

其他通用寄存器则可以直接供被调用的函数使用。

这意味着_调用_函数在调用任何函数之前，必须先保存这些寄存器中的值，以防它们被被调用的函数修改。
这就是它们被称为**调用者保存寄存器**的原因。

_保存寄存器内容最常见的方法，就是把它存入栈中。_

## 序言和尾声

在某些情况下，栈可能被大量使用，函数返回前会出现很多改动。
这样一来，要跟踪所有这些改动再逐一撤销，可能会很复杂。

在这些情况下，一种常见的做法是把`rsp`的值保存在另一个寄存器中，并让这个寄存器在函数内部保持原样。
然后在函数返回之前，用一条简单的`mov`指令就能恢复`rsp`的值。

虽然任何寄存器都可以用于这个目的，但按照惯例，我们会用`rbp`作为基址指针。
由于`rbp`本身就是被调用者保存寄存器，所以这之前通常会先执行一条`push rbp`。
这个序列通常称为**序言**。

在最后，用`mov rsp, rbp`恢复`rsp`，然后再用一条`pop`指令从栈中恢复`rbp`。
这个序列通常称为**尾声**。

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

~~~~exercism/note
序言和尾声序列的主要作用，是帮助程序员跟踪`rsp`的变化。
当然，对编译器来说这要容易得多。

所以，许多编译器都会启用一项优化，尽可能省略帧指针，去掉序言和尾声。
~~~~

## 用栈传递实参

在 [System V ABI][SystemV] 调用约定中，实参通常通过寄存器传给函数。
但是，当实参太多，或者它们需要的空间超过一个寄存器的大小时，就可能用到栈。

在这些情况下，值会以相反的顺序加入栈中，这样第一个实参就离`rsp`更近。
由于在进入函数时，`rsp`指向返回地址（在 x86-64 中这是一个 8 字节的值），所以栈上的第一个实参（如果有的话）可以通过`rsp + 8`访问：

```x86asm
mov rdi, 4   ; first argument
mov rsi, 8   ; second argument
mov rdx, 15  ; third argument
mov rcx, 16  ; fourth argument
mov r8, 23   ; fifth argument
mov r9, 42   ; sixth argument

; any remaining integer argument goes on the stack in reversed order
sub rsp, 16
mov qword [rsp], 100      ; seventh argument
mov qword [rsp + 8], 300  ; eighth argument

call many_arguments_fn ; call implicitly pushes `rip` to the stack
; so, at point of entry, 'many_arguments_fn' finds the first six integer arguments in the usual registers
; the seventh argument is found in rsp + 8
; and the eighth argument is found in rsp + 16
```

## 栈对齐

System V ABI 规定，在`call`指令执行之前，栈必须立即按 16 字节对齐。
由于`call`会把`rip`压入栈中，所以在进入被调用函数时，它的栈**并不**是 16 字节对齐的。

这意味着，一个函数如果要调用另一个函数（尤其是外部函数），就需要在使用`call`之前对齐栈。

做法是从`rsp`中减去一个合适的值。
在进入函数时，这个值必须是 16 的倍数再加 8：8、24、40 等等。
由于`push`指令会减小`rsp`，所以用奇数个`push`也能达到同样的效果：

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

## 红区

System V ABI 在`rsp`正下方保留了一块 128 字节的空间，使用它时不需要对`rsp`做任何调整。
这块空间叫做[红区][red-zone]：

```x86asm
fn:
    mov [rsp - 8], rax ; this is safe to use because it is in the red zone
    ret                ; no need to restore rsp
```

只有叶子函数（也就是不调用其他函数的函数）才能安全地使用红区。

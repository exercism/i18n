# 排序

```sather
   numbers.sort;                                  -- the natural order
   words.insertion_sort_by(bind(before(_, _)));   -- an order you supply
```

## sort 需要什么

`sort`要求元素类型带有`is_lt`。`INT`、`STR`、`CHAR`、`FLTD`和`INTI`都具备。你自己写的类则没有，除非你为它写一个。

`insertion_sort_by`对元素类型没有任何要求：它需要知道的一切都在你交给它的那个例程里。

## 一个比较必须满足什么

例程必须定义一个一致的顺序，否则结果就是未定义的：

- 如果`before(a, b)`为 true，那么`before(b, a)`必须为 false；
- 如果`a`排在`b`前面，`b`排在`c`前面，那么`a`就排在`c`前面；
- `before(a, a)`必须为 false。

最后一条最容易让人出错。写`<=`而不是`<`，就等于说某个东西排在它自己前面，而拿这样的比较去排序，什么结果都可能出来。

## 并列

`sort`和`insertion_sort_by`都**不稳定**：比较判定为相等的元素可能以任意顺序出现，而在这个库里，它们通常会被反过来。

所以，那种排两次序的做法（先按名称排，再按积分排，指望积分相同的队伍仍然保持字母顺序）在这里行不通。同样，也不能指望输入顺序能保证什么。

如果并列的顺序有影响，就要**在比较里**把它们的先后定下来。把它做成一个全序，让任何两个不同的元素都不会被判为相等：

```sather
   shorter(a, b : STR) : BOOL is
      if a.size /= b.size then return a.size < b.size; end;
      return a < b;                  -- same length: alphabetical
   end;
```

即使你认为不可能出现并列，这样做也值得。一个比较如果在正反两个方向上都返回 false，结果就是不确定的，而这个 bug 会表现为顺序毫无来由地发生变化。

## 其他方法

| 调用 | 作用 |
| --- | --- |
| `a.sort` | 原地排序，自然顺序，不稳定 |
| `a.insertion_sort_by(lt)` | 原地排序，用你给的顺序，稳定 |
| `a.is_sorted` | 检查 |
| `a.is_sorted_by(lt)` | 按你给的顺序检查 |
| `a.binary_search(e)` | 在已排序的数组中查找 |
| `a.binary_search_by(e, lt)` | 按你给的顺序查找 |

在未排序的数组上使用`binary_search`不会报错，只会给出毫无意义的结果。它的前置条件已经说明了这一点，而前置条件是不做检查的，除非给编译器加上`-chk`。

## 开销

插入排序的工作量与长度的平方成正比，对十几个队伍的小榜单来说没问题，对一万条记录就不合适了。`ARR_SORT_ALG::sort_by`是同一思路的快速排序版本，适合数组很大、而稳定性无所谓的时候。

# 关于

## 为错误添加上下文

我们已经在[错误概念][concept-errors]中探讨过 Go 的基本错误处理。
如你在那里学到的，默认情况下错误并不携带堆栈跟踪。
因此，确保错误本身包含足以定位问题的信息就至关重要。

如果只用我们已经掌握的工具给现有的错误补充信息，可以这样写，创建一个新错误，把原错误的文本和附加信息拼接起来：

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

幸运的是，标准库中的`fmt`包为此提供了一个简写形式，也就是`Errorf`函数。
有了它，你就能轻松地为错误补上它发生时的上下文信息。

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

除非你能确定错误本身已经包含足够的信息，否则应该养成习惯：在从函数中返回错误之前，先为它添加上下文。
也就是说，标准的错误处理模式应该像这样：

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

如示例所示，惯例是用冒号把错误和补充的信息分隔开。
与原错误的信息一样，上下文信息也不应大写首字母，末尾也不要加句号。

~~~~exercism/note
给错误添加上下文时，很容易想让它以 “failed to ...” 或类似的说法开头。
不过，错误沿着函数调用链向上传递时会累积大量额外的上下文，这会让最终被记录或展示给用户的信息变得难以阅读，或者充满重复。

下面用个例子来说明：

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

所以，写上下文信息时要想着最终的效果，不要再去说明“某件事没有按预期进行”。
这一点通常从上下文（比如日志级别 “ERROR”）和原始错误信息中就能看出来。
~~~~

这种给错误补充信息的方式通常已经够用，但有些情况下，你希望错误的调用方能检查或取出原始的那个底层错误。
在 Go 中，以这种允许检查底层错误的方式添加上下文叫做“包装错误”。

## 包装错误与检查哨兵错误

只要对上文代码做一处很小的改动，就能实现错误包装。
要包装一个错误，需要用格式化动词`%w`而不是`%v`。
在背后，这会确保生成的错误实现`Unwrap`方法，返回原始错误。
正因如此，才能用`errors.Is`检查某个特定的哨兵错误是否出现在“错误链”的某处。
它的做法是反复悄悄调用`Unwrap`，直到找到目标错误或者链条结束。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

如果用常见的`%v`格式化动词，就无法用`errors.Is`检查原始错误。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

因此，好的做法是默认使用`%v`，只有当你明确希望让调用方访问底层错误时才使用`%w`（[Google Go 风格指南][google-go-styleguide]）。

如果你需要检查哨兵错误，却明确不想解包，可以用`==`代替`errors.Is`。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

相反，如果错误被包装过，`==`就无法识别它。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

默认使用`errors.Is`没问题，但要始终意识到，这意味着整条错误链都会被搜索。

## 检查（自定义）错误类型

有一个与`errors.Is`对应的函数，可以检查并取出错误链中某个特定类型的错误。
这个函数就是`errors.As`，和`errors.Is`一样，它会沿着整条链搜索给定的错误类型。
`errors.As`只有在找到匹配类型的错误时才把它提取出来，以便你进一步处理，比如取出其中的具体字段。

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
注意上面涉及指针的语法。
只有当`customError`具有实现错误接口的确切类型时，代码才能正常工作并正确编译。
在我们的例子里，这个类型是`*MyCustomError`（指向`MyCustomError`的[指针][concept-pointers]），而不是`MyCustomError`本身。

此外，第二个实参必须是指向错误变量的指针。
由于我们的错误本身已经是指针，传给`errors.As`的其实是一个指向指针（指向 MyCustomError）的指针。
只有设置正确，Go 才能把找到的错误填入这个变量。
~~~~

和前面一样，如果调用`Errorf`时用的是`%v`，`errors.As`就找不到这个错误类型。

如果出于某种原因不想解包，可以改用类型断言（相当于上面的`==`）。

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

如果错误被包装过，类型断言就无法识别出这个错误类型。

## 让自定义类型的错误可以被解包

有时，仅用一段额外的文字包装错误是不够的。
你可以改为创建一个自定义错误类型，用来保存原始错误以及你想添加的结构化数据。
如果想让自己的错误类型支持解包，唯一要做的就是手动添加一个`Unwrap() error`方法，从而满足`Unwrap`接口。

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## 合并多个错误

Go 1.20 在内置的`errors`包中新增了`Join`函数。
`Join`可以把多个错误合并在一起，同时仍然支持解包，也就是沿着链检查特定的错误或错误类型。
这样一来，错误链实际上可能是一棵错误树。
更多信息可以查看[发行说明][release-notes]和[文档][doc-join]。

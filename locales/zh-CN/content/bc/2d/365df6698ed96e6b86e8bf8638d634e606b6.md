# 关于

`MACRO:`声明定义的是一个词，它的*主体*在编译期运行。主体从编译期栈上取走字面量实参，并且必须在栈上留下一个引用。编译器随后用这个引用替换宏调用，因此运行时的程序根本看不到宏，只看到它生成的代码。

```factor
USING: kernel macros sequences ;

MACRO: twice ( quot -- compound )
    dup append ;
```

如果调用方写下`[ 1 + ] twice`，编译器就会在栈上有`[ 1 + ]`的情况下运行主体，得到`[ 1 + 1 + ]`，再把它拼接进去。没有运行时的额外开销，宏所替代的循环或组合子已经消失了。

## 输入必须是字面量

因为主体在编译期运行，所以每个输入在调用处都必须是*字面量*：一个`[ … ]`引用、一个数字、一个数组、一个字符串。传入非字面量的值（只有在运行时才知道的值）是编译期错误。

```factor
! works: [ 1 + ] is a literal quotation
: inc-twice ( x -- y ) [ 1 + ] twice ;

! refused: f is a literal, but the macro can't run with a non-quotation
! input where the body expects to call `append` on it
```

## 结构化输入产生结构化输出

有意思的宏接受一个*结构*（一个数组、一个字面量的对序列），并生成形状取决于该结构的代码。本练习中的`each-literal`接受一个字面量序列和一个引用，并为每个元素生成一份柯里化并内联的引用副本。运行时的程序是直线式代码，没有`each`，也没有逐元素分派，序列的迭代完全发生在编译期。

## 为什么没有卫生问题

Lisp 宏要应付*卫生*问题：引入局部名字的宏可能与调用处的名字冲突，因而需要`gensym`或一套卫生系统。Factor 没有这个问题，因为引用是*已解析的词引用*序列：每个词都在解析期查找，而不是在展开期按符号查找。宏构建的引用里的`dup`永远是`kernel:dup`，不管调用处存在哪些名字。

代价是：Factor 宏不能像`defmacro`那样引入新的绑定。它们只能用解析器已经见过的词来构建代码。对大多数元编程来说，这已经够了。

## 相邻的形式（本练习不涉及）

- `MACRO::`是`MACRO:`的局部变量形式，就像`::`是`:`的局部变量形式一样。当主体不止一次引用自己的输入时很有用。
- `<< … >>`是解析期求值块。它在编译期运行普通的 Factor 代码，但没有返回引用的约定。用于计算一个必须在解析期就存在的值，例如由环境查询得到的`CONSTANT:`。
- `SYNTAX:`是*解析词*。它是另一类东西：作用于解析器的记号流，而不是值，并且运行在更早的阶段。它用来定义新的字面量语法（`T{ }`、`H{ }`）。超出了本概念的范围。
- `functor:`是声明式模板，能从一份声明生成一组相关的词。它建立在宏机制之上，属于库作者的地盘。

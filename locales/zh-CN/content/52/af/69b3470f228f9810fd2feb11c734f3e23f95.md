## 工具

`bin/`里有一些 bash 脚本形式的工具。
`rust-tooling/`里还有更多，
任何稍复杂的工作都应优先使用那里的工具。

另外还有一份 [`mise`](https://mise.jdx.dev/)配置，
里面有几个与代码仓库交互的实用命令。
欢迎自行扩充。

如果想在本地运行 CI 测试，`mise run test`能帮你完成大部分工作。

## 排除测试与添加自定义测试

在创建或更新练习时，你可能想排除某些测试，不让它们被生成。
可以在 `.meta/tests.toml`中设置 `include = false`。
请附上一条注释，说明排除它的原因。

如果你想添加额外的、本 track 专属的测试，可以写在 `.meta/additional-tests.json`文件里。
只有在有充分理由不把这些测试上游化时才这样做。
附加测试里的注释应当回答这些问题：
- 为什么这个测试没有上游到 `problem-specifications`，也就是为什么它对其他语言没有普遍价值？
- 为什么这个测试对 Rust track 仍然有价值？

## 创建新练习

请先熟悉 [Exercism 关于练习的文档][Exercism documentation about practice exercises]。

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

运行 `mise run add-exercise`，系统会提示你输入生成练习骨架所需的最少信息。
之后进入生成的练习，把里面的占位符都补上。
最主要的工作包括：

- 在 `src/lib.rs`中编写练习骨架
- 在 `.meta/example.rs`中添加示例解答
- 调整 `.meta/test_template.tera`

测试用模板引擎 [Tera] 生成。
模板的输入是来自 [`problem-specifications`]的规范数据。

关于编写 tera 模板的一些技巧见[这里](#tera-templates)。

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

一个练习实现得是否正确，有很多方面会在 CI 中检查。
与其花大量时间研究并撰写关于这个流程的文档，我建议你_直接动手做_。
如果哪里出了问题，就修好它，再加一个测试或自动化检查，让它不会再发生。

如果你要从零创建一个练习，而它并不在 `problem-specifications`中，
那就得手动编写测试。
测试应当按复杂度递增的顺序排列，
这样学生可以逐个取消忽略，用 TDD 的方式完成练习。
关于如何写好测试，[Exercism 文档](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)里有更多思考。

除非有特殊情况，
骨架文件应当能在 `cargo test --no-run`下编译通过。
这样我们就能检查骨架文件里的函数签名
是否与测试期望的签名一致。
为此，请把每个函数体写成 `todo!()`。
如果有正当理由做不到这一点，
请在练习的 `.meta/config.json`中加入一个 `.custom."allowed-to-not-compile"`键，
把原因写进去。

## 更新练习

很多练习都源自 [`problem-specifications`]，
包括它们的测试套件和面向用户的文档。
在这里提出改动之前，
先确认这些改动是不是应该直接提到 `problem-specifications`。

运行 `mise run update-exercise`可以更新练习。
它把大部分工作交给 `configlet sync --update`，
并重新运行测试生成器。

更新一个还没有 tera 模板的练习时，
系统会为你生成一个新模板。
你多半还得对它做一些调整。

关于编写 tera 模板的一些技巧见[下一节](#tera-templates)。

## Tera 模板

tera 模板的完整文档在[这里][tera-docs]。
下面是一些在我们的具体需求下行之有效的方法。

你大概会想看看练习的 `canonical-data.json`，了解输入数据长什么样。
你可以用 `bin/symlink_problem_specifications.sh`把这份数据
以符号链接的形式放进真正的练习目录。很方便！

每个练习的输入属性名都不一样。
默认模板大概长这样：

```txt
let input = {{ test.input | json_encode() }};
```

你需要补上这个练习具体的输入字段，比如：

```txt
let input = {{ test.input.integers | json_encode() }};
```

有些练习的返回值可能是错误。
你可以根据数据的结构，用 if-else 渲染出不同的内容：

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

有些练习有多个函数需要学生实现，因此也需要测试。
这种情况下，规范数据里会有一个 `property`字段。
你可以基于 `test.property`构造 if-else 链，据此渲染出不同的函数。

有些练习的测试用例被组织成_测试分组_。
你的模板必须处理好这一点。
很多时候，你可以直接把结构展平。（示例：[`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera)）
但不同分组里的测试有时会有相同的描述，展平结构后就会造成命名冲突。
这种情况下，你可以用分组描述把测试组织到模块里。（示例：[`forth`](/exercises/practice/forth/.meta/test_template.tera)）

[`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs)里有一些自定义的 tera 过滤器。
下面这份列表希望是最新的：
- `to_hex`把整数格式化为十六进制
- `make_ident`把任意字符串变成像样的 Rust 标识符。
   在根据测试描述生成函数名时最有用。
- `fmt_num`格式化数字字面量（每三位插入一个 `_`）

欢迎你在 `rust-tooling`这个 crate 里添加自己的过滤器。
也希望你记得顺手更新这里的列表。🙂

想看一个相当复杂的例子，可以看看 `triangle`的测试模板。
它把测试用例组织到模块里，并动态判断哪些测试该放到 feature gate 后面。
那个练习还在 `additional-tests.json`里重新实现了上游的一些测试用例，为的是给它们补充生成好测试所必需的信息。

[tera-docs]: https://keats.github.io/tera/docs/#templates

## 教学大纲

教学大纲目前因为质量太低已停用。
关于这个决定的背景，见[这个论坛帖子](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)。

做一个更好的教学大纲会很有价值，
但这工作量很大，还需要良好的沟通与协调。
如果你有什么计划，一定要先在论坛上和
有教学大纲构建经验的人讨论。

# 简介

## 为错误添加上下文

我们在[错误概念][concept-errors]中探讨了 Go 的基本错误处理。正如你在那里了解到的，默认情况下，错误不携带堆栈跟踪信息。因此，确保错误本身包含足以定位问题的信息就至关重要。

如果我们想用已经掌握的工具为现有错误添加信息，可以这样写，创建一个新错误，其文本由原错误和附加信息组合而成：

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

幸运的是，标准库中的`fmt`包以`Errorf`函数的形式为此提供了一个简写版本。
这样一来，你就可以轻松地添加错误发生时所处上下文的信息。

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

通常，用这种方式为错误添加信息已经足够了，但有些情况下，你希望错误的使用方能够检查或获取原始的底层错误。
在 Go 中，以允许这种做法的方式添加上下文称为“包装错误”。

## 包装错误与检查哨兵错误

只需对上面看到的代码做很小的改动，就能实现错误包装。
要包装一个错误，你需要使用格式化动词`%w`而不是`%v`。
在幕后，这会确保生成的错误实现了一个`Unwrap`方法，该方法返回原始错误。
因此，就可以用`errors.Is`来检查某个特定的哨兵错误是否出现在“错误链”的某处。
它通过暗中反复调用`Unwrap`来实现这一点，直到找到目标错误或错误链结束。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

默认情况下使用`%v`、只有在明确希望允许使用方访问底层错误时才使用`%w`，这是很好的做法（[Google Go 风格指南][google-go-styleguide]）。

如果你遇到想检查哨兵错误、但明确不想解包的情况，可以用`==`代替`errors.Is`。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

默认使用`errors.Is`没问题，但你始终要意识到，这意味着整条错误链都会被搜索。

## 检查（自定义）错误类型

`errors.Is`有一个对应的函数，可以从错误链中检查并取出特定类型的错误。
这个函数就是`errors.As`，和`errors.Is`一样，它会沿着整条链查找给定的错误类型。
只有找到符合该类型的错误时，`errors.As`才会把它提取出来，供你进一步操作，例如取出特定的字段。

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
注意上面与指针相关的语法。
只有当`customError`的类型恰好是实现 error 接口的那个类型时，代码才能正常工作并正确编译。
在我们的例子里，这个类型是`*MyCustomError`（一个指向 MyCustomError 的[指针][concept-pointers]），而不是`MyCustomError`本身。

除此之外，第二个参数必须是指向错误变量的指针。
由于我们的错误本身已经是指针，所以我们传给`errors.As`的是一个指向指针的指针（指向 MyCustomError）。
只有正确设置这一点，Go 才能把找到的错误填入这个变量。
~~~~

和之前一样，如果在调用`Errorf`时使用的是`%v`，`errors.As`就无法找到该错误类型。

如果出于某种原因不想解包，可以改用类型断言（相当于上面的`==`）。

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

如果错误被包装过，类型断言就无法识别出错误类型。

## 允许解包自定义类型的错误

有时仅用一些附加文本包装错误还不够。
你可以改为创建一个自定义错误类型，用它保存原始错误以及你想要添加的结构化数据。
如果你想让自己定义的错误类型支持解包，唯一要做的就是手动添加一个`Unwrap() error`方法，从而满足`Unwrap`接口的要求。

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

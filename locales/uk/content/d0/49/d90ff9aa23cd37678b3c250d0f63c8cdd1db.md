# About

Програмісти зазвичай намагаються писати бездоганне програмне забезпечення і зазвичай зазнають невдачі.

Щось несподівано йде не так, і ми маємо вміти з цим давати раду.

Деякі розробники мов уважають, що передусім треба якнайшвидше виявити помилку, а тоді перервати виконання з інформативним повідомленням, яке допоможе під час налагодження.

Мови для науки про дані зазвичай обирають виваженіший підхід.
Деякі помилки настільки серйозні, що потрібне негайне переривання, але часто краще позначити проблему як таку, з якою розберемося пізніше, і продовжити виконання.

Ми бачили в концепції [Порожнеча][nothingness], що Julia надає кілька заповнювачів для проблемних значень: [`missing`][nothing], [`NaN`][NaN] і `Inf`.
Чи кращий такий підхід у конкретній ситуації за переривання програми, має вирішувати сам програміст.

_Одне уточнення щодо термінології_, перш ніж заглибимося в деталі: документація Julia вважає слова «помилка» і «виняток» здебільшого взаємозамінними.
Виклад нижче може бути так само непослідовним.

## Стандартні типи помилок

На цьому етапі силабусу ми вже неодмінно бачили чимало повідомлень про помилки від Julia.
Наприклад:

```julia-repl
julia> Int(3.14)
ERROR: InexactError: Int64(3.14)
```

Спроба перетворити число з плаваючою комою на ціле число призводить до втрати точності, тож ми отримуємо `InexactError`.

`InexactError` - це тип, один із кількох (наразі 25), вбудованих у Julia як стандартні.
Усі вони є підтипами `Exception`:

```julia-repl
julia> supertype(InexactError)
Exception
```

## `throw()`

Деякі зі стандартних типів помилок може бути корисно створювати у власному коді.

Як і всі конкретні типи, помилки мають конструктори.
Вони приймають найрізноманітніші аргументи, тож варто зазирнути в [документацію][errors], щоб обрати потрібний.

```julia-repl
julia> DomainError(42, "out of range")
DomainError(42, "out of range")
```

Щоб скористатися помилкою, обгорнімо конструктор у функцію [`throw()`][throw]:

```julia-repl
julia> throw(DomainError(42, "out of range"))
ERROR: DomainError with 42:
out of range
```

## `error()`

Коли треба швидко й просто, у пригоді стане функція [`error()`][error].
Вона приймає як аргумент рядок тексту (англ. string) або його складові:

```julia-repl
julia> happy = false;
julia> happy || error("😞 something went wrong")
ERROR: 😞 something went wrong
```

## Власні помилки

Створювати нові типи помилок загалом дуже просто.
Достатньо додати ще один підтип `Exception`:

```julia-repl
julia> struct MyError <: Exception end

julia> throw(MyError)
ERROR: MyError
```

Однак у наведеному прикладі немає полів, а конструктор не приймає аргументів, тож ми не маємо контролю над повідомленням про помилку.
Можна додати поле для повідомлення:

```julia-repl
julia> struct AnotherError <: Exception
           msg::String
       end

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError("Wrong!")
```

Просто вивести конструктор - ще не зовсім те, що потрібно.
Порівняймо з попереднім прикладом, де ми викинули `DomainError`.

Щоб власну помилку було оброблено так само, як вбудовані, потрібно додати метод [`showerror()`][showerror]:

```julia-repl
julia> Base.showerror(io::IO, e::AnotherError) =
           print(io, "AnotherError: ", e.msg)

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError: Wrong!
```

Ця доволі погано задокументована можливість по суті вбудовує наш власний тип помилки в стандартну систему обробки помилок Julia.

## Твердження

Основна ідея твердження: «це твердження має бути правдою, тож гучно скаржмося, якщо воно неправда».
Цінність цього полягає переважно в налагодженні, бо код у продакшені ніколи не повинен провалити твердження.

Ми бачили в концепції [Типи][types], що можна додавати твердження про типи, наприклад, щоб перевірити тип поверненого значення функції.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Загальніше, макрос [`@assert`][assert] дає змогу перевірити будь-який вираз, який обчислюється в булеве значення (англ. Boolean):

```julia-repl
julia> n = 22;
julia> @assert isodd(n) "n must be odd"
ERROR: AssertionError: n must be odd
```

## `try`...`catch`

Деякі помилки неминуче фатальні, але часто ми очікуємо, що програма коректно відновиться.

Типово помилка негайно завершує поточну функцію, і ця помилка (разом з інформативним повідомленням) передається функції, яка її викликала.

Так триває вгору стеком викликів, доки код верхнього рівня не завершиться з повідомленням про помилку.

На будь-якому етапі помилку можна перехопити блоком [`try...catch`][try-catch], який намагається її обробити.

```julia-repl
julia> n = -1;
julia> try
           log_n = log(n)
       catch problem
           if problem isa DomainError # number out of range
               # See next section for more on @warn and @info
               @warn "you may have supplied a negative real number: $n"
               @info "trying with complex argument"
               log_n = log(Complex(n))  # fallback calculation

           elseif problem isa MethodError # no idea what n is
               @error "please supply a valid argument"
 
           else
              rethrow() # the error could be anything else
           end
      end
┌ Warning: you may have supplied a negative real number: -1
└ @ Main REPL[3]:5
[ Info: trying with complex argument
0.0 + 3.141592653589793im  # success
```

У наведеному прикладі `log(n)` потребує, щоб `n` було або додатним дійсним значенням, або будь-яким комплексним значенням.
Конструкція `try ... catch` перехоплює проблеми з відʼємними дійсними значеннями, повертаючи правильну комплексну відповідь `iπ` у математичному записі.

Якщо передати, наприклад, аргумент-рядок тексту, відновитися не вдасться: доведеться попросити користувача його виправити.

Наостанок, як універсальний перехоплювач, ми додали [`rethrow()`][rethrow] для всього, що не є ані `DomainError`, ані `MethodError`.

Є також кілька необовʼязкових частин:

- [`else`][else], яка виконується, якщо частина `try` успішна;
- [`finally`][finally], яку можна використати для звільнення зовнішніх ресурсів незалежно від того, успішна частина `try` чи ні: закрити файли, розірвати зʼєднання з базою даних...

***Примітка:*** Іноді `try...catch` - саме те, що потрібно, але краще не зловживати ним.
Якщо натомість можна обійтися блоком `if...else`, він буде значно продуктивнішим за перехоплення винятків.

## Журналювання

Зауважмо, що функцію `error()`, про яку йшлося вище, не слід плутати з макросом [`@error`][error_macro].

Функція породжує виняток, який передаватиметься вгору стеком викликів, якщо його не перехоплять.

Макрос [`@error`][error_macro] разом зі своїми побратимами [`@debug`][debug_macro], [`@info`][info_macro] і [`@warn`][warn_macro] належить до модуля [`Logging`][logging] і призначений створювати інформативні повідомлення, які не змінюють хід виконання програми.

Типово виведення йде в термінал (із кольоровим кодуванням за рівнем важливості), хоча в справжньому застосунку можливостей значно більше.

```julia-repl
julia> @warn "Something looks not quite right"
┌ Warning: Something looks not quite right
└ @ Main REPL[55]:1

julia> @error "Panic!"
┌ Error: Panic!
└ @ Main REPL[56]:1
```

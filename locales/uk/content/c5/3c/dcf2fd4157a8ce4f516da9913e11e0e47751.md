# Про нуллабельність

В ідеальному світі ми могли б розраховувати на те, що все гарно визначено, з конкретними значеннями і без прогалин.

Це суперечить нашому повсякденному досвіду, тому багато мов програмування мають спосіб позначити відсутність значення: null або NULL, nil, None, nothing...

Це було легко запровадити (ще 1965 року), але невдовзі призвело до жалю. Згодом винахідник назвав це своєю [«помилкою на мільярд доларів»][web-mistake].

За останні десятиліття творці мов дослідили чимало способів зробити null доступним, але (переважно) безпечним.

У Kotlin є кілька [загальних принципів][ref-null-safety], які [суттєво відрізняються від Java][ref-java2kotlin]. _Ці відмінності означають, що Kotlin має спеціальні можливості для взаємодії з Java, хоча деталі виходять за межі цієї концепції._

- У Kotlin є спеціальне значення `null`.
- Усі типи _типово_ є ненуллабельними (тобто не можуть бути `null`).
- Усі типи можуть бути _нуллабельними_, але це потрібно вказати явно.
- Функції, які можуть завершитися винятком, імовірно мають варіант із нуллабельним поверненим значенням.
- Спеціальний, дуже лаконічний синтаксис покликаний зробити перевірку на null і реакцію на нього якомога простішими.

## Створення нуллабельних змінних

Тип можна зробити [нуллабельним][ref-nullable-type], додавши суфікс `?` (наприклад, `String?` замість `String`).

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Корисні оператори та функції

### [Оператор безпечного виклику][ref-safe-call] `?.`

Для ненуллабельного `String` ми можемо отримати властивість `.length`.

Нуллабельний `String?` із тим самим синтаксисом спричинить помилку, але використання `?.length` допускає можливість `null`.
Тип поверненого значення - `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Як ми бачили в останньому рядку вище, `?.` також працює з ненуллабельними типами.

### [Оператор Елвіса][ref-elvis] `?:`

Розвиваючи ідею оператора безпечного виклику, [оператор Елвіса][wiki-elvis] дає змогу вказати типове значення замість `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### [Оператор ствердження ненульовості][ref-not-null] `!!`

Цей оператор змушує трактувати нуллабельний тип як ненуллабельний, коли програміст у цьому впевнений.
Можливо, іноді ми розуміємо логіку програми краще за надто обережний компілятор?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Тепер відповідальність на нас: якщо `b` усе ще `null`, ми отримаємо `NullPointerException`.

### [Функція `let`][ref-let] `?.let`

Якщо ми передаємо нуллабельний елемент у блок коду, можна зробити окремі перевірки на `null`: `if (item != null) { do something }`.

Простіше й ідіоматичніше використати `item?.let { do something }`.
`do something` виконається лише тоді, коли `item` не є null.

### Функції виду `somethingOrNone()`

Деякі функції можуть зазнавати невдачі, наприклад, коли ми запитуємо недійсний індекс у рядку тексту (англ. string) чи масиві.

Замість того щоб викидати виняток, ми можемо скористатися [варіантом функції `...OrNull`][ref-elem-at-or-null], щоб отримати (у цьому випадку) повернене значення типу `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

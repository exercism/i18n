# Вступ

Функція називається **рекурсивною**, коли вона викликає саму себе.

Одна з ключових відмінностей між викликом функції та циклом полягає в тому, що виклик функції кладе в стек адресу, на яку потім треба повернутися.
Це означає, що рекурсивна функція зазвичай потребує більше місця в стеку, ніж еквівалентний цикл.

Як наслідок, функція, яка продовжує викликати саму себе, може зрештою вичерпати весь простір стеку.
Це називається **переповненням стеку**.

Саме тому кожна рекурсивна функція повинна мати принаймні один базовий випадок, тобто ситуацію, коли функція повертає результат, не викликаючи себе.
Будь-який рекурсивний виклик зрештою має досягти базового випадку.

Наприклад, функцію факторіала `n! = n * (n - 1) * ... * 1` можна визначити рекурсивно, узявши `1` за базовий випадок:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Зауважмо, що `factorial` має виконати `push rdi` перед рекурсією та `pop rdi` після неї.
Це тому, що після повернення з рекурсивного виклику їй усе ще потрібне `n`, щоб обчислити `n * (n-1)!`.

Зауважмо також, що використання регістра, який зберігає викликана функція, не розвʼязало б цієї проблеми.

Хоча рекурсивна функція потенційно викликає саму себе, вона водночас сама є викликаною функцією для якоїсь іншої функції.
Це означає, що функція також має зберігати регістри, які зберігає викликана функція, перш ніж ними скористатися, і відновлювати їхні значення після використання.
Зазвичай це робиться послідовністю `push`/`pop`, як ми бачили в попередньому концепті.

Оскільки кожен кадр рекурсивної функції, крім базового випадку, теж є викликачем, якому потрібно зберегти власні локальні змінні, цю послідовність `push`/`pop` доводиться повторювати для кожного кадру.
Навіть якщо зберігати змінну безпосередньо в стеку, не використовуючи регістрів, це все одно коштуватиме ті самі `8` байтів на кадр.

Це означає, що кожен рекурсивний виклик додає до стеку `8` байтів на адресу повернення, яку кладе `call`, плюс `8` байтів на кожну локальну змінну, яку потрібно зберегти.
Функція додаватиме ці байти до стеку з кожним кадром, доки не досягне базового випадку.
Лише тоді вона починає розгортатися у зворотному порядку: кожен рекурсивний виклик виконує стільки `pop`, скільки потрібно, а потім `ret`.

Наприклад, якби `factorial` викликали з аргументом `10`, вона викликала б себе девʼять разів, перш ніж досягти базового випадку `1`.
У цей момент `144` байти було б витрачено на збереження `n` (`8` байтів) і адреси повернення (`8` байтів) для кожного попереднього кадру.

## Хвостовий виклик

У деяких ситуаціях функція не виконує жодної роботи після виклику іншої функції й до повернення.

Розгляньмо, наприклад:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

Функція `triple_of_square`:

- множить переданий аргумент (у `rdi`) сам на себе, отримуючи його квадрат;
- потім викликає `times_three`, яка повертає переданий аргумент, помножений на три.

У результаті `triple_of_square` повертає `3*x²`, де `x` позначає її аргумент, переданий у `rdi`.

Зауважмо, що після виклику `times_three` у `triple_of_square` не виконується жодної роботи, функція просто повертає результат.
У такій ситуації замість `call` функція може скористатися `jmp` і передати керування викликаній функції:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

Це називається **хвостовим викликом**.

Головна перевага хвостового виклику в тому, що він дає змогу уникнути додаткових витрат на `call`.
`call` кладе адресу повернення в стек, і щоб керування повернулося до того місця, має бути відповідний `ret`.

Хвостовий виклик пропускає і те, і те: немає адреси повернення, яку треба покласти в стек, і немає зайвого `ret`, з яким її треба було б поєднати, є лише власний `ret` викликаної функції.

## Хвостова рекурсія

Хвостовий виклик особливо корисний для рекурсивних функцій, які можуть викликати себе багато разів, перш ніж повернути результат.

Однак не кожен рекурсивний виклик можна безпосередньо перетворити на хвостовий.
Оскільки `jmp` передає керування викликаній функції, викликач не може виконати жодної роботи після хвостового виклику.

Наприклад, розглянута раніше функція `factorial` **не** є хвостово-рекурсивною.
Після рекурсивного виклику їй усе ще потрібно помножити результат на поточне `n` за допомогою `imul rax, rdi`.

У таких ситуаціях іноді можна скористатися акумулятором, який збиратиме проміжні результати обчислень і буде повернутий наприкінці.
Наприклад, ми можемо визначити `factorial_helper`, яка виконує більшу частину роботи, а потім `factorial` задає акумулятор і передає керування `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Оскільки після рекурсивного виклику більше не виконується жодної роботи, нам також більше не потрібно зберігати `rdi`.
Тут немає ні `call`, ні `push rdi`, тож кожна рекурсивна ітерація додає до стеку `0` байтів: додатковий простір стеку не використовується.
Ця версія може обробляти як завгодно великі `n`, не переповнюючи стек.
Вона і ефективніша, і безпечніша.

У деяких випадках, змінивши порядок функцій, можна уникнути навіть `jmp` до допоміжної функції.
Наприклад, `factorial` і `triple_of_square` можна переписати так:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

У наведеному фрагменті виконання `factorial` просто переходить до `factorial_helper`.
Те саме відбувається з `triple_of_square` і `times_three`.
В обох випадках виконання продовжується послідовно, і здається, що хвостова функція - це просто локальна мітка всередині «головної» функції.

Насправді жодної істотної різниці між локальною міткою та функцією немає.
Ассемблер x86-64 не робить винятку ні для чого з них, усе це просто адреси в секції з виконуваним кодом, наприклад `section .text`.

Отже, хвостово-рекурсивну функцію можна розглядати по суті як цикл, у якому рекурсивний виклик повертається на початок, а базовий випадок - це умова, яка завершує цикл.

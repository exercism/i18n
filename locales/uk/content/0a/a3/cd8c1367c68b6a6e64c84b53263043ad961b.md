# Докладніше

## Помилки в `jq`

`jq` повідомляє про дві великі категорії помилок:

1. **Помилки під час компіляції**: сама програма недійсна, тобто має синтаксичні помилки, посилається на невизначені функції чи змінні тощо.
   `jq` взагалі відмовляється запускати таку програму.

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **Помилки під час виконання**: програма коректна, але щось іде не так під час обробки значення, наприклад індексування числа рядком тексту (англ. string), розбір некоректного тексту JSON за допомогою `fromjson`, виклик функції з аргументами неправильного типу тощо.

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

Ідеться тут про **помилки під час виконання**: як їх генерувати, як перехоплювати і як зупиняти програму.

Неперехоплена помилка під час виконання змушує `jq` надрукувати повідомлення в _стандартний потік помилок_ і завершити роботу зі статусом `5`.

## Генерування помилок: `error` і `error(message)`

Фільтр [`error`][man-error] генерує помилку.

- `error` генерує помилку, значенням якої є **вхідні дані**.
- `error(message)` генерує помилку, значенням якої є результат `message`.

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
Значенням помилки може бути _будь-яке_ значення JSON, а не лише рядок тексту.
Генерування структурованих помилок дає змогу обробнику `catch` ухвалювати рішення на основі вмісту помилки.

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

Якщо значення помилки не є рядком тексту і його не перехопили, `jq` друкує його як JSON із позначкою `(not a string)`.

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## Перехоплення помилок: `try` і `catch`

Помилки можна перехопити за допомогою [`try EXP catch HANDLER`][man-try-catch].
Спочатку виконується перший вираз; якщо він генерує помилку, виконується вираз `HANDLER`, **причому його вхідними даними стає значення помилки**.
Вихідні дані обробника виводяться так, ніби це вихідні дані виразу під `try`.

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

Коротша форма `try EXP` рівносильна `try EXP catch empty`: помилку відкидають, і нічого не виводиться.

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
Помилка **обриває решту потоку** всередині `try`.
Уже отримані значення зберігаються, але нічого після помилки не обчислюється.

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

Обробник може згенерувати нову помилку або повторно згенерувати початкову простим `error`: оскільки значення помилки є вхідними даними обробника, воно передається далі без змін.

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## Пригнічення помилок: оператор `?`

[Оператор `?`][man-question-mark], записаний як `EXP?`, є скороченням для `try EXP`.
Він перетворює вираз, що завершується помилкою, на такий, що просто нічого не виводить.

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

Його часто можна побачити поруч з операторами індексування:

- `.foo?` - це `.["foo"]?`
- `.[]?` виконує перебір, лише якщо вхідні дані є масивом або обʼєктом, а інакше нічого не дає

~~~~exercism/caution
`?` пригнічує **кожну** помилку, зокрема ті, яких ми не передбачили.
`user.name?` мовчки нічого не дає, коли `user` не є обʼєктом, а це може приховати проблеми з даними або одруківки в нашій програмі.
Краще використовувати `try ... catch`, коли нам потрібно знати, _що_ щось не вдалося, або явно перевіряти вхідні дані.
~~~~

## Альтернативний оператор `//`

Програмісти іноді очікують, що `a // b` дасть `b`, коли `a` зазнає невдачі.
Так було в давніших версіях `jq`, але не від `jq` 1.6.
Оператор `//` не пригнічує помилки.
Він підставляє `b`, лише коли `a` не дає значення, дає `false` або `null`; помилки в `a` все одно поширюються далі.

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

Використовуймо `try a catch b`, якщо нам потрібен запасний варіант на випадок помилок.

## Альтернативний оператор деструктуризації `?//`

[Оператор `?//`][man-question-mark-slash-slash] поєднує деструктуризацію з обробкою помилок.
Він по черзі пробує кожен шаблон привʼязування, доки якийсь не спрацює, а змінні, привʼязані невдалими варіантами, отримують значення `null`.

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

Тут перший шаблон припускає, що `c` - це _обʼєкт_ із ключами `d` і `e`, а другий припускає, що `c` - це _масив_, який містить такий обʼєкт.
Перший елемент вхідних даних привʼязується першим шаблоном; другий елемент не відповідає цьому шаблону, тож замість нього пробують другий шаблон.

Це дає змогу одній програмі деструктурувати вхідні дані, які можуть мати одну з кількох форм, не пишучи явних ланцюжків `if type == ...`.

## Зупинка програми: `halt` і `halt_error`

Іноді правильна реакція на помилку - припинити обробку взагалі.

- [`halt`][man-halt] негайно зупиняє програму `jq`, не виводячи більше нічого; статус завершення - `0`.
- [`halt_error`][man-halt-error] зупиняє програму, друкує її **вхідні дані** в _стандартний потік помилок_ як необроблений текст (без оформлення і навіть без символу нового рядка) і завершується з указаним статусом, що типово дорівнює `5`.

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

Зауважмо, що ці фільтри зупиняють програму негайно, навіть якщо ще залишилося прочитати інші вхідні дані.

### Статуси завершення

Для довідки, `jq` використовує такі статуси завершення:

| Статус | Значення                                         |
| :----: | ------------------------------------------------ |
| `0`    | успіх                                            |
| `2`    | помилка використання (неправильні параметри командного рядка) |
| `3`    | помилка компіляції                               |
| `5`    | помилка під час виконання (або `halt_error` без аргументу) |

З параметром `--exit-status` / `-e` статус натомість відображає останнє виведене значення: `0` для `true` або чисел, `1` для `false` або `null`, `4`, якщо виводу немає.

## Допоміжні засоби для налагодження

Коли треба зʼясувати, звідки береться помилка, стають у пригоді такі фільтри:

- [`debug`][man-debug] пропускає свої вхідні дані без змін, але друкує `["DEBUG:", <input>]` у стандартний потік помилок.
  `debug(msgs)` також друкує `msgs` як повідомлення налагодження.
- [`stderr`][man-stderr] друкує свої вхідні дані необробленими й компактними в стандартний потік помилок.
- [`input_line_number`][man-input-line-number] виводить номер рядка вхідних даних, які зараз обробляються. Це безцінно, коли файл містить багато текстів JSON і один із них зіпсований.
- [`$__loc__`][man-loc] виводить обʼєкт із ключами `file` і `line`, які описують, де саме в програмі він трапляється; цей обʼєкт можна вбудувати в повідомлення про помилки.

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

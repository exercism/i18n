# Вступ

Досі силабус не дуже розповідав про типи, але вони, очевидно, існують у Julia:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

Ми жодного разу не вказали типи, але Julia все одно їх присвоїла.

1. У Julia є `types`, і вони відіграють центральну роль у її архітектурі.
2. Julia зазвичай може «вгадати» тип, використовуючи `Type Inference`.

JIT-компілятор перегляне (увесь) код, побачить, як використовується змінна, і _виведе_ придатний типовий тип, сумісний із цим використанням.

## Підвищення типів

У попередніх концепціях було багато прикладів, де числові типи зводяться до єдиного вигляду, починаючи з найпростішої арифметики.

```julia-repl
julia> 2 + 1.3
3.3
```

Ми додали ціле число (Int64) і число з плаваючою комою (Float64) та отримали результат типу Float64.
Так само:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

У наведеному вище випадку кортеж зберіг тип кожного елемента, але перетворення на вектор змінило їх усі на однорідний Float64.

Компілятор Julia розуміє, які перетворення типів можливі: перетворити ціле число на число з плаваючою комою не проблема, а перетворення числа з плаваючою комою на ціле втрачає точність, тож виникає `InexactError`.
Підвищення типів перетворює всі значення у виразі на спільний тип, достатньо універсальний, щоб бути сумісним з усіма вхідними даними.

## Присвоєння типу

Покладатися на виведення типів цілком нормально, коли ми розвʼязуємо прості навчальні вправи, але для більших програм, імовірно, знадобиться точніший контроль.

На більшості сучасних процесорів ціле число типово представлене як `Int64`.
У концепції [`Numbers`][numbers] ми бачили, що значення можна перетворити на конкретний нетиповий тип.

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

Однак змінній `x` усе ще можна присвоїти інший тип:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

Це `type instability`, і вона:

- Дуже зручна в невеликих скриптах.
- Погано впливає на продуктивність і надійність у більших програмах.

Натомість ми можемо задати тип `x` за допомогою оператора `::`:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

Тепер `y` має тип `Int16` і завжди матиме його.
Отже, компілятор знає, скільки байтів зарезервувати для неї, і може оптимізувати решту коду, розраховуючи на стабільний тип.
У цьому змінна більш-менш схожа на змінні зі статично типізованої мови, як-от C.

## Твердження типу

Присвоєння типу, описане вище, використовують у лівій частині присвоєння змінній, щоб обмежити тип цієї змінної.

Використання оператора `::` зі значенням або з чимось, що обчислюється до значення, зазвичай є _твердженням_, що значення має бути саме цього типу, інакше має виникнути помилка.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Часто це застосовують до поверненого значення функції як просту останню перевірку, що функція поводилася так, як очікувалося.

## Ієрархія типів

`Int64`, `Int16`, `String`, `Char`: звідки ж _«беруться»_ ці типи?

У багатьох обʼєктно-орієнтованих (ООП) мовах кожен тип - це клас, успадкування підкласів шикує їх в ієрархію класів, а методи класів визначають поведінку.

Java і Ruby - очевидні приклади цього підходу, але навіть Python усередині влаштований подібно.

***У Julia немає класів.***

Задокументована причина в тому, що можливості ООП заважають JIT-компілятору та шкодять продуктивності під час виконання.

І все ж погляньмо на цей код:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

Додамо трохи деталей:

- `Int16` - це тип, і ми можемо створювати змінні цього типу.
- `Int16` - підтип `Signed`, і функція `supertype()` показує нам це.
- Існує ієрархія типів, яка піднімається через `Integer`, `Real` і `Number` до `Any` на вершині, а `subtypes()` перелічить для нас цю гілку ієрархії.

Усі гілки закінчуються на `Any`, який унікальний тим, що є власним надтипом.

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

Отже, у Julia немає ієрархії `class`, але ієрархія `type` у неї _таки_ існує.

Зрештою, ми спробуємо розібратися, як це працює, але спершу нам належить дослідити ще багато чого.

## Перевірка типів

Ми можемо використовувати `typeof()`, щоб перевіряти рівність звичайним способом.

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

Рівність типів має бути точною, адже таке порівняння нічого не знає про ієрархію типів.

Гнучкіше: `isa` повідомить нам, чи має значення той самий тип, що й значення для порівняння, або його підтип.
Його можна використовувати як у функціональній, так і в інфіксній формі.

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

Зауважмо, що `isa` приймає ліворуч `value`, а не `type`.

Спроба порівняти в такий спосіб два _типи_ дасть несподівані результати.
Правильний оператор - `<:`, і ми побачимо його набагато частіше в наступних концепціях.

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## Абстрактні та конкретні типи

Ми бачили, що ієрархія типів утворює деревоподібну структуру (у сенсі інформатики, з коренем на вершині).

Кожен елемент дерева - це `node`, і їх можна поділити на категорії:

1. Вузли, що мають підтипи, називаються `abstract`.
2. Листкові вузли, без підтипів, називаються `concrete`.

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

Це важлива відмінність, адже лише конкретні типи можна `instantiated` як змінні.


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

Зауважмо, що спроба використати абстрактний тип не дає повідомлення про помилку (у цьому випадку), але компілятор створює відповідний конкретний тип: `Int64` замість `Integer`.
Принаймні це заважає присвоїти змінній щось нецілочисельне:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

Отже, присвоєння типу з абстрактним типом накладає _обмеження_ на тип змінної: він має бути будь-яким підтипом (у наведеному вище випадку) `Integer`.
Це дещо незвичне у світі мов програмування: слабше за присвоєння типу в C, сильніше за підказку типу в недавніх версіях Python.

Функції `isabstracttype()` і `isconcretetype()` дають змогу перевіряти.
Зауважмо, що вони не просто заперечують одна одну: у пізнішій концепції ми побачимо, що деякі типи не є ні абстрактними, ні конкретними.


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

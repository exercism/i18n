# Докладніше

Навряд чи нам трапиться багато робочого коду, який не використовує простори імен.

Ось приклад синтаксису:

```csharp
namespace MyNameSpace
{
    public class MyClass {}

    public class OtherClass {}
}
```

Простори імен дають змогу групувати повʼязаний код і уникати збігів назв.

Згідно з [офіційною документацією][namespaces], простори імен мають дві головні ролі:

- По-перше, .NET використовує простори імен, щоб упорядкувати свої численні класи
- По-друге, оголошення власних просторів імен допомагає контролювати область видимості назв класів і методів у великих проєктах.

Базова бібліотека класів (BCL) широко використовує простори імен, щоб упорядкувати свою функціональність.

## Посилання на типи з просторів імен

До типів, укладених у простори імен, звертаються ззовні простору імен, додаючи перед назвою типу крапковий синтаксис. Або ж, і так буває частіше, можна розмістити директиву `using` на початку файлу (чи всередині простору імен), і будь-який тип з імпортованого простору імен можна використовувати без префікса. У межах одного простору імен уточнювати назви типів не потрібно.

```csharp
namespace MySpace
{
    public class MyClass {}

    public class Foo
    {
        public void Bar()
        {
            var baz = new MyClass();
        }
    }
}

public class Qux
{
    public void Box()
    {
        var nux = new MySpace.MyClass();
    }
}

namespace OtherSpace
{
    using MySpace;

    public class Tix
    {
        public void Jeg()
        {
            var lor = new MyClass();
        }
    }
}
```

Ця [стаття][using] докладно пояснює, як можна використовувати директиву `using`:

- `using`: позбавляє необхідності уточнювати типи простором імен
- `using static`: позбавляє необхідності уточнювати члени типів (гарний приклад: `Math.Max()`).
- `using MyAlias = YourNamespace;`: замінює назву простору імен на зручнішу для читання.

## Збіг просторів імен

.NET розвʼязує проблему двох просторів імен з однаковою назвою в різних збірках, де стався б збіг повністю кваліфікованих назв ідентифікаторів (можливо, у сценарії, коли завантажено кілька версій однієї збірки). Цю проблему розвʼязують за допомогою [кваліфікатора псевдоніма простору імен][namespace-alias-qualifier] та [зовнішнього псевдоніма][extern-alias].

Цю доволі вузьку тему варто згадати хоча б через [оператор `::`][dot-dot-operator], який у ній використовується. Ми часто бачимо, як кваліфікатор `global::` стоїть перед просторами імен, особливо у згенерованому коді. Мета тут полягає в тому, щоб уникнути можливого збігу з якимось вкладеним простором імен чи назвою класу. Додаючи `global::` перед простором імен, ми гарантуємо, що буде вибрано простір імен верхнього рівня.

## Зауваження для розробників Java

Порівнюючи з `import` `packages` у Java, варто відзначити кілька відмінностей і подібностей:

- У C# немає відповідника імпорту конкретних типів.
- `using static` та `import static` рівнозначні.
- У Java назви пакетів впливають на доступність між jar-файлами. У C# головну роль відіграють збірки, і належність до того самого простору імен не впливає на рівень доступу.
- Звʼязок між шляхами у файловій системі та повністю кваліфікованими назвами класів у Java не відображено в просторах імен C#, хоча, де це можливо, варто давати файлу ту саму назву, що й головний клас, який він містить.

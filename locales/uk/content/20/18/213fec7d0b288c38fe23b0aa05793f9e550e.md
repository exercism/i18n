# Вступ

`GenServer` (загальний сервер) - це [поведінка][concept-behaviours], яка абстрагує типові взаємодії клієнт-сервер між процесами Elixir.

Пригадаймо цикл отримання, коли ми вивчали [процеси][concept-processes]? Поведінка `GenServer` надає абстракції для реалізації таких циклів і для обміну повідомленнями з процесом, який виконує такий цикл. Вона полегшує збереження стану та виконання асинхронного коду.

~~~~exercism/note
Зауважмо, що назва `GenServer` має кілька значень. Нею також описують _модуль_, який _використовує_ поведінку `GenServer`, а також _процес_, запущений з модуля, який _використовує_ поведінку `GenServer`.
~~~~

Поведінка `GenServer` визначає один обовʼязковий колбек `init/1` і кілька цікавих необовʼязкових колбеків: `handle_call/3`, `handle_cast/2` та `handle_info/3`. _Клієнти_, які використовують `GenServer`, не повинні викликати ці колбеки напряму. Замість цього модуль `GenServer` надає функції, які клієнти можуть використовувати для звʼязку з процесом `GenServer`.

Часто один модуль визначає і _клієнтський API_ (набір функцій, які інші частини нашого Elixir-застосунку можуть викликати для звʼязку з цим процесом `GenServer`), і _реалізації серверних колбеків_, які містять логіку цього `GenServer`.

Розглянемо спочатку простий приклад `GenServer`, а потім дізнаймося, що означає кожен колбек.

## Приклад

Це приклад сервера, який може відповідати на повторювані розпитування набридливих пасажирів під час довгої автомобільної подорожі, а точніше на запитання: «Ми вже приїхали?». Він відстежує, скільки разів це запитання було задано, і повертає дедалі роздратованіші відповіді.

```elixir
defmodule AnnoyingPassengerAutoresponder do
  use GenServer
  # Client API

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg)
  end

  def are_we_there_yet?(pid) do
    GenServer.call(pid, :are_we_there_yet?)
  end

  # Server callbacks

  @impl GenServer
  def init(_init_arg) do
    # the initial count of questions asked is always 0
    state = 0
    {:ok, state}
  end

  @impl GenServer
  def handle_call(:are_we_there_yet?, _from, state) do
    reply =
      cond do
        state <= 3 -> "No."
        state <= 10 -> "I told you #{state} times already. No."
        true -> "..."
      end

    # increase the count of questions asked
    new_state = state + 1
    # reply to the caller
    {:reply, reply, new_state}
  end
end
```

## Колбеки

### `init/1`

Сервер можна запустити, викликавши `GenServer.start/3` або `GenServer.start_link/3`. Про різницю між цими функціями ми дізналися в [концепції посилань][concept-links].

Ці дві функції:

- Приймають модуль, який реалізує поведінку `GenServer`, як перший аргумент.
- Приймають будь-що як другий аргумент під назвою `init_arg`. Як випливає з назви, цей аргумент передається в колбек `init/1`.
- Приймають необовʼязковий третій аргумент із додатковими параметрами для запуску процесу, які ми зараз не розглядаємо.

Запуск сервера викликом `GenServer.start/3` або `GenServer.start_link/3` викличе колбек `init/1` у блокуючий спосіб. Повернене значення `init/1` визначає, чи сервер може запуститися успішно.

Колбек `init/1` зазвичай повертає одне з таких значень:

- `{:ok, state}`. Сервер запустить свій цикл отримання, використовуючи `state` як початковий стан. `state` може бути будь-якого типу.
- `{:stop, reason}`. `reason` може бути будь-якого типу. Сервер не запустить свій цикл отримання. Процес завершиться із заданої причини.

Існують також складніші можливості, які ми зараз не розглядаємо.

Якщо цикл отримання сервера запускається, функції `GenServer.start/3` і `GenServer.start_link/3` повертають кортеж `{:ok, pid}`. Інакше вони повертають `{:error, reason}`

### `handle_call/3`

Повідомлення, яке потребує відповіді, можна надіслати процесу сервера за допомогою `GenServer.call/2`. Ця функція приймає `pid` запущеного процесу сервера як перший аргумент і повідомлення як другий аргумент. Повідомлення може бути будь-якого типу.

Колбек `handle_call/3` відповідає за обробку та відповідь на синхронні повідомлення. Він приймає три аргументи:

1. `message` - значення, передане як другий аргумент до `GenServer.call/2`.
2. `from` - `pid` процесу, який викликає `GenServer.call/2`. Найчастіше цей аргумент можна ігнорувати.
3. `state` - поточний стан сервера. Памʼятаймо, що його початкове значення було встановлено в колбеку `init/1`.

Колбек `handle_call/3` зазвичай повертає кортеж із 3 елементів `{:reply, reply, state}`. Це означає, що другий елемент кортежу, `reply`, який може бути будь-якого типу, буде надіслано назад викликачу. Третій елемент кортежу, `state`, це новий стан сервера після обробки цього повідомлення.

Існують також складніші можливості, які ми зараз не розглядаємо.

~~~~exercism/note
Щоб запамʼятати, що робить цей колбек, за його назвою,
уявімо це як «дзвінок» комусь по телефону.

Якщо ця людина доступна, ми отримаємо відповідь негайно (синхронно).
~~~~

### `handle_cast/2`

Повідомлення, яке не потребує відповіді, можна надіслати процесу сервера за допомогою `GenServer.cast/2`. Його аргументи ідентичні аргументам `GenServer.call/2`.

Колбек `handle_cast/2` відповідає за обробку цих повідомлень. Він приймає два аргументи, `message` і `state`, які є тими самими аргументами, що й у колбеку `handle_call/3` (крім `from`).

Колбек `handle_cast/2` зазвичай повертає кортеж із 2 елементів `{:noreply, state}`.

Існують також складніші можливості, які ми зараз не розглядаємо.

~~~~exercism/note
Щоб запамʼятати, що робить цей колбек, за його назвою,
памʼятаймо, що «to cast» також означає «кидати».

Якщо ми кидаємо пляшку з повідомленням у море,
ми не очікуємо отримати відповідь негайно,
а можливо, й ніколи.
~~~~

### Що використовувати: `call` чи `cast`?

Майже завжди використовуймо `call`, навіть якщо нашому клієнтському коду не потрібна відповідь від сервера.

Використання `call` очікує на відповідь, що слугує механізмом зворотного тиску (щоб клієнти не надсилали занадто багато повідомлень одночасно). Отримання відповіді від сервера також є єдиним способом переконатися, що сервер отримав і обробив повідомлення клієнта.

### `handle_info/2`

Повідомлення також можуть потрапляти до поштової скриньки сервера іншими способами, ніж виклик `GenServer.call/2` або `GenServer.cast/2`, наприклад, викликом звичайної функції `send/2`.

Щоб обробляти такі повідомлення, використовуймо колбек `handle_info/2`. Цей колбек працює точно так само, як `handle_cast/2`.

Поведінка `GenServer` надає універсальну реалізацію `handle_info/2`, яка записує в журнал помилки про неочікувані повідомлення. Якщо ми перекриваємо цю типову реалізацію, обовʼязково завжди додаваймо власну універсальну реалізацію. Якщо ми забудемо, сервер аварійно завершиться, якщо отримає неочікуване повідомлення.

## Тайм-аути

Повернене значення кожного з чотирьох описаних вище колбеків можна розширити ще одним елементом кортежу, тайм-аутом. Наприклад, замість повернення `{:ok, state}` з `init/1` повертаємо `{:ok, state, timeout}`.

Тайм-аут можна використовувати, щоб виявити відсутність повідомлень у поштовій скриньці протягом певного періоду. Якщо сервер повертає тайм-аут з одного зі своїх колбеків, і вказана кількість мілісекунд минула, а повідомлення не надійшло, викликається `handle_info/2` з `:timeout` як першим аргументом.

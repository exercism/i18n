# Специфікація Markdown

Нижче описано, як мають бути структуровані всі файли Markdown у межах Exercism.

Деякі правила з цього документа ще не впроваджені в усьому Exercism.
Ми вітаємо PR, які їх виправляють.
Усі правила додаються до наших інструментів CI та лінтерів, і їх слід дотримуватися в нових змінах.

## Заголовки

- Усі файли мають починатися із заголовка першого рівня (`# Some heading text`).
- Заголовки першого рівня існують виключно для перегляду на GitHub чи аналогічних платформах.
- Якщо файл відображає Exercism (наприклад, показує на сайті чи рендерить через CLI), цей заголовок буде прибрано, а на його місце вставлено контекстний заголовок.
- Жоден заголовок не може опускатися більш ніж на один рівень нижче попереднього (наприклад, після `##` може йти лише `###`, а не `####`).
- Окрім єдиного заголовка першого рівня (`#`), можна використовувати лише заголовки другого (`##`), третього (`###`) і четвертого (`####`) рівнів.

## Посилання

Використовуйте [референсні посилання][reference-links], які визначаються внизу файлу Markdown, зіставляються з референсним слагом, і на які в тексті посилаються за цим слагом.

Такий підхід полегшує супровід, адже посилання потрібно оновлювати лише в одному місці.

Приклад:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

Посилання завжди повинні мати якірний текст, а не містити саму URL-адресу в тексті. Наприклад, наведене нижче посилання не використовує якірного тексту, і його важче читати.

```
If you want some more information, please visit https://google.com.
```

Коли є якірний текст і посилання на нього, це легше зрозуміти й осмислити в контексті.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

Що відображається так: «Якщо потрібно більше інформації, [Google][google-link] - корисний ресурс.»

## Код

Коли ми згадуємо елементи коду (наприклад, функції чи ключові слова), код слід брати у зворотні лапки:

```
- The `printf()` function writes to the console.
```

Що відображається так:

- The `printf()` function writes to the console.

Складніший код (наприклад, багаторядковий) слід брати в потрійні зворотні лапки. Після відкривних потрійних зворотних лапок слід указати [ідентифікатор мови][language-identifier], щоб увімкнути підсвічування синтаксису:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

Коли можливо, форматуйте код так, як найдоречніше для середовища, у якому його подано. Якщо вона доступна, звертайтеся до документації для відповідної мови.

Наприклад, у Python є REPL (read-eval-print loop, тобто цикл «читання - обчислення - виведення»), який дозволяє програмісту вводити код безпосередньо в терміналі. Якщо користувач налагоджує код або запускає функцію локально, щоб перевірити чи побачити, як вона працює, він радше скористається для цього REPL, бо там зручніше вводити код інтерактивно. У такій ситуації ми віддаємо перевагу форматуванню прикладу коду так, ніби його вводять у REPL, з провідним `>>>`:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

В інших випадках доцільніше залишити код відформатованим так, ніби він у файлі `.py`. Тут учень виграє від того, що бачить код, схожий на той, який він написав би сам.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

Швидкий спосіб розрізнити ці два випадки, коли незрозуміло: якщо це код, який учень може запустити в терміналі, форматуйте його саме так. Якщо це код, який може запускати Exercism (у тестах, коді бібліотеки, який напише учень, тощо), типово оформлюйте його як код, готовий до запуску.

## Особливі блоки (іноді їх називають admonitions)

Ми підтримуємо особливі типи блоків, які можна додавати до документів, щоб виокремити коментарі, які не вписуються в основний текст.

<img width="500" alt="Блок примітки Markdown" src="https://user-images.githubusercontent.com/20866761/139531109-0c0f3ea5-b589-44ff-93ab-d901a45edc56.png">

<img width="500" alt="Блок застереження Markdown" src="https://user-images.githubusercontent.com/20866761/139531234-9b58b9ab-524b-44fd-bbcb-4e10f2927d27.png">

<img width="500" alt="Блок advanced Markdown" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

Ми підтримуємо три типи блоків:

- **exercism/note:** блоки, які виокремлюють додаткову особливу інформацію
- **exercism/caution:** те, що людям варто знати або з чим слід поводитися обережно
- **exercism/advanced:** інформація, доречна лише для тих, хто хоче глибше зануритися в тему або від кого очікують ґрунтовніших знань.

Усі блоки записуються за допомогою 4 тильд у такому вигляді:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(Примітка: за виняткових обставин можна також використовувати зворотні лапки або іншу кількість тильд)

## Компонування

### Одне речення на рядок

Абзаци слід розкладати так, щоб кожне речення було на окремому рядку. У [документації Ascii Doctor][asciidoctor] логіку цього пояснено чітко.

Наприклад, один абзац має бути викладений так:

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## Списки

Використовуйте символ дефіса (`-`) як маркер списку для невпорядкованих списків.

## Коментарі

- Надавайте перевагу коментарям Markdown замість коментарів HTML (наприклад, використовуйте `[comment]: # (Actual comment...)` замість `<!-- Actual comment -->`)

Можна перевірити, що коментар Markdown прибирається, подивившись, який вигляд він має після рендерингу через commonmark на [babelmark3].

## Вбудований HTML

- Вбудований HTML дозволено, але вживати його слід ощадливо
- Завжди використовуйте нативні альтернативи Markdown, якщо вони є (наприклад, `# ...` замість `<h1>...</h1>`)

## Зображення

Оскільки сайт підтримує світлу й темну теми, зображення, подані спільнотою, мають добре відображатися в обох темах.
Розвʼязання полягає в тому, щоб додати суфікс до назви зображення (перед розширенням файлу):

1. Нехай назва зображення закінчується на `-invertible` (наприклад, `graph-invertible.svg`). Зображення автоматично інвертується, коли його показують у темній темі (через `filter: invert(100%)`).
1. Нехай назва зображення закінчується на `-light` (наприклад, `graph-light.png`), і додатково створіть сумісну з темною темою версію із суфіксом `-dark` (тобто `graph-dark.png`). Ми автоматично відображатимемо потрібне зображення залежно від теми користувача.

Зображення без жодного із суфіксів використовуються без змін в обох темах.
Це означає, що якщо є потреба створити зображення у відтінках сірого, зазвичай можна зробити так, щоб вони мали гарний вигляд у світлій темі, а потім зробити їх інвертованими.
Але якщо використовується зображення з безліччю кольорів, можливо, варто зробити два варіанти.

Повну назву зображення (разом із `-invertible`) слід додати в Markdown там, де зображення відображається.
Для світлих/темних варіантів додавайте **ЛИШЕ** варіант `-light`.
Цю логіку застосовують в усіх документах Markdown.

## Автоформатування

Деякі репозиторії використовують [prettier][prettier], щоб увесь Markdown був відформатований однаково. Це може дати такі переваги:

- Жодних суперечок про форматування.
- Чудова інтеграція з редакторами/IDE, тож файли можна форматувати під час збереження.
- Легко додавати перевірки форматування в CI.
- Легко автоматично форматувати файли за допомогою скрипту.

Усе це може значною мірою зменшити обсяг зайвих змін під час рецензування, що дратує і того, хто рецензує, і того, кого рецензують.

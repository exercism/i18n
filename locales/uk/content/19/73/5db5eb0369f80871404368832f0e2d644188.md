# Про мову

На цьому етапі силабусу ми вже бачили чимало визначень функцій.
Зазвичай їх подавали без особливих пояснень щодо того, що виводить REPL:

```julia-repl
julia> f(x) = x^2
f (generic function with 1 method)
```

Чому саме _generic function with 1 method_?

Припустімо, ми хочемо точніше вказати типи аргументів.

```julia-repl
julia> f(x::Integer) = x^2
f (generic function with 2 methods)

julia> f(x::Real) = x^2
f (generic function with 3 methods)
```

Або можемо змінити кількість аргументів:

```julia-repl
julia> f(x, y) = x * y
f (generic function with 4 methods)
```

Виходить, що нові визначення тієї самої функції називаються «методами».
Методи додаються до списку, а не перезаписують старе визначення.

Ми легко можемо перелічити методи:

```julia-repl
julia> methods(f)  # output edited for brevity
# 4 methods for generic function "f" from Main:
 [1] f(x, y)
 [2] f(x::Integer)
 [3] f(x::Real)
 [4] f(x)
 ```

Коли ми викликаємо функцію `f`, Julia якимось чином знає, який метод використати:

```julia-repl
julia> f(2.5)  # Float64
6.25

julia> f(2)  # Int64
4

julia> f(2, 3)  # Int64, Int64
6
```

## Що таке функція?

Згідно з [посібником][function], функція - це обʼєкт, який відображає кортеж аргументів у повернене значення.
Це близько до визначення, яким користуються математики.

Ми зазвичай уявляємо аргументи функції в `f(2, 3)` як два окремі елементи, але компілятор бачить їх як один [кортеж][tuple].
Це так навіть для одного аргументу (щоправда, щоб це стало очевиднішим, треба додати кому):

```julia-repl
julia> typeof( (2, 3) )
Tuple{Int64, Int64}

julia> typeof( (2,) )
Tuple{Int64}
```

Якщо розглядати функцію як чорну скриньку, можна сказати, що всередину потрапляє кортеж, а назовні виходить повернене значення.
Формальніше кажучи, кортеж _відображається_ у повернене значення.

## Як функції працюють з різною кількістю та типами аргументів?

Зазвичай це називають [«поліморфізмом»][polymorphism].

Протягом кількох десятиліть це була одна з головних тем в інформатиці, і тут застосовували різні підходи.

Підхід Julia незвичний, хоч і не унікальний.

- Функції є [«узагальненими»][generic], тобто до них можна прикріпити кілька методів.
- Функції - це лише імена, доки до них не прикріплено методи.
- Методи можна додавати за потреби, і їх може бути дуже багато (оператор `+` наразі має 161 метод).
- Коли функцію викликають, Julia аналізує сигнатуру виклику: кількість аргументів і поточний тип кожного з них.
- Обирається метод, що найточніше відповідає сигнатурі виклику.
  - Загалом кількість аргументів має збігатися точно (хоча оператор [splat/slurp][splat] `...` може частково це обійти).
  - Перевагу віддають методам, типи яких точно збігаються із сигнатурою виклику.
  - За потреби Julia переглядає супертипи кожного аргументу в сигнатурі виклику, щоб знайти найточніший збіг, найконкретніший метод.
- Обраний метод [`dispatched`][dispatch] із заданими аргументами й повертає результат.
- Якщо відповідного методу не знайдено, виникає [`MethodError`][methoderror].

Зауважмо, що Julia має динамічну типізацію, тому диспетчеризація методів відбувається під _час виконання_.

## Множинна диспетчеризація: приклад

У попередньому розділі було багато слів, тож втілімо ці ідеї в код.
Для простоти функції нижче мають лише один аргумент, але функції з десятками аргументів не рідкість (наприклад, у пакетах для побудови графіків чи в машинному навчанні).

Почнімо з визначення кількох власних типів, які представлятимуть геометричні фігури.

```julia-repl
julia> abstract type Shape end

julia> struct Circle <: Shape
           radius::Float64
       end

julia> struct Square <: Shape
           side::Float64
       end

julia> struct Rectangle <: Shape
           length::Float64
           width::Float64
       end
```

Далі можемо визначити методи для обчислення площі кожної фігури.
Кожен із них приймає один аргумент, і в кожному випадку це конкретний тип, визначений користувачем.

```julia-repl
julia> area(c::Circle) = π * c.radius^2
area (generic function with 1 method)

julia> area(s::Square) = s.side^2
area (generic function with 2 methods)

julia> area(r::Rectangle) = r.length * r.width
area (generic function with 3 methods)
```

Тепер можемо створити кілька фігур і обчислити їхні площі, покладаючись на механізм диспетчеризації Julia, який застосує правильну формулу для кожної.

```julia-repl
julia> circle = Circle(2.3)
Circle(2.3)

julia> area(circle)  # call signature Tuple{Circle}
16.619025137490002

julia> square = Square(1.6)
Square(1.6)

julia> area(square)  # call signature Tuple{Square}
2.5600000000000005

julia> rectangle = Rectangle(1.4, 2.1)
Rectangle(1.4, 2.1)

julia> area(rectangle)  # call signature Tuple{Rectangle}
2.94
```

## [Параметричні методи][parametric]

Сигнатури методів можуть приймати фіктивні значення типів, приблизно так само, як параметричні типи.

Синтаксис тут особливий: потрібна конструкція `where`:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T} = true
same_type (generic function with 1 method)

julia> same_type([1, 2], 3)
true

julia> same_type([1, 2], "three")
ERROR: MethodError: no method matching same_type(::Vector{Int64}, ::String)
```

У наведеному прикладі обидва аргументи мають бути одного типу `T`, яким би він не був.

Можна зробити вимогу точнішою, наклавши обмеження на `T`:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T<:Number} = true
same_type (generic function with 2 methods)
```

Із цим методом `true` повертають лише однакові числові типи.

Можливі й кілька фіктивних змінних, розділених комами в конструкції `where`.
Наступні два методи схожі між собою:

```julia-repl
julia> func(v::Vector{Number}, x::Number) = true
func (generic function with 1 method)

julia> func(v::Vector{S}, x::T) where {S<:Number, T<:Number} = true
func (generic function with 2 methods)
```

Одна з відмінностей у тому, що значення типів `S` і `T` можна використовувати в тілі функції другого методу.
Це той прийом, який ми, можливо, не будемо використовувати часто, але в деяких ситуаціях він може врятувати від багатьох проблем.

Наприклад, у наведеному нижче визначенні параметричного типу поля мають бути одного типу `T`, обмеженого тим, що він є підтипом `Real`:
```julia
struct Point{T<:Real}
    x::T
    y::T
end
```
Це визначення `Point` приймає `x` і `y` однакового типу, або ж може приймати `x` і `y` різних типів, але тоді потрібно явно вказати тип перетворення.
```julia-repl
julia> Point(4, 5)
 Point{Int64}(4, 5)

julia> Point(3.5, 2)
 MethodError: no method matching Point(::Float64, ::Int64)    # Output truncated for brevity

julia> Point{Float32}(3.5, 2)
 Point{Float32}(3.5f0, 2.0f0)

julia> Point{Int64}(3.5, 2) 
 InexactError: Int64(3.5)      # Output truncated for brevity
```
Хоч такий рівень контролю над типами може бути бажаним, іноді корисно додати трохи абстракції.
```julia
Point(x::T, y::S) where {T<:Real, S<:Real} = Point{promote_type(T,  S)}(x, y)
```
Цей зовнішній конструктор дає змогу `Point` приймати `x` і `y` різнорідних типів без явного зазначення типу перетворення.
Значення типів `T` і `S` використовуються в тілі функції в `promote_type(T, S)`, щоб задати явний тип перетворення для початкового визначення.
```julia-repl
julia> Point(3.5, 2)
 Point{Float64}(3.5, 2.0)
```

## Порівняння з іншими мовами

Оскільки під час вибору методу Julia аналізує всі аргументи, це називають [`multiple dispatch`][multiple-dispatch].

Кілька інших мов теж підтримують множинну диспетчеризацію, наприклад Common Lisp, але вона рідко буває настільки ж центральною для дизайну мови, як у Julia.

Натомість в обʼєктно-орієнтованій (ООП) мові (наприклад, Ruby) методи зазвичай викликають на [екземплярі][instance].
Тепер визначення надає перевагу першому аргументу (з іменем на кшталт `self` або `this` у визначенні), а імʼя методу приєднують до екземпляра через крапку, щоб його викликати:

```ruby
irb(main):004:0> "abc".sub("b", "*")
=> "a*c"
```

Це називають [`single dispatch`][single-dispatch], оскільки для вибору методу використовується лише клас екземпляра (рядка "abc" у наведеному вище прикладі).

Деякі статично типізовані обʼєктно-орієнтовані мови підтримують поліморфізм методів, який дещо нагадує множинну диспетчеризацію.
Головна відмінність у тому, що вибір методу відбувається лише під _час компіляції_.

Функціональні мови зазвичай мають лише одне визначення функції, а різні можливості обробляють якимось виразом на кшталт Select/Case/Match.
Ми пишемо власну логіку, зазвичай завдяки лаконічному синтаксису зіставлення зі зразком, якого в Julia немає.
Звісно, Julia теж певною мірою виконує зіставлення зі зразком, але під час диспетчеризації, а не в тілі функції.

## Висновок

Множинна диспетчеризація в Julia дуже гнучка й високопродуктивна, тому її широко застосовують.

Як показує приклад зі 161 методом для `+`, програмісти Julia прагнуть визначати методи з вузько заданими типами. 
На рівні байт-коду додавання двох цілих чисел дуже відрізняється від додавання двох чисел з плаваючою комою, а додавання цілого числа до числа з плаваючою комою додає ще одну складність: підвищення типу.

Чим конкретніший тип, тим більше оптимізацій може зробити компілятор: це майже не має значення в простій навчальній вправі на Exercism, але критично важливо для швидкодії у великих чисельних симуляціях, для яких і створено Julia.

_Якщо ми знаємо, які вхідні дані отримає метод, повідоммо про це компілятору!_

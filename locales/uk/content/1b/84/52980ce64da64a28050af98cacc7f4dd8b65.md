# Про стек

[Стек викликів][stack], або просто **стек**, - це особлива структура даних, яка починається в найвищій точці памʼяті й росте вниз.

## Операції push і pop

Стек підтримує щонайменше дві операції, для яких існують інструкції з такими самими назвами:

| Інструкція | Виконувана операція                                |
| ----------- | --------------------------------------------------- |
| `push`      | додає елемент до стека                              |
| `pop`       | вилучає й повертає останній доданий елемент         |

Це означає, що стек є структурою даних **«останній прийшов, першим пішов» (LIFO)**.

Щоб відстежувати поточну точку стека, де міститься останній доданий елемент, використовують регістр `rsp`.

Отже, інструкція [push][push] приймає один операнд і зберігає вміст цього операнда в стеку.
Оскільки стек росте вниз, значення в `rsp` зменшується на розмір збереженого значення.

Так само інструкція [pop][pop] приймає один операнд і записує в нього останнє значення зі стека (те, на яке вказує `rsp`).
Потім значення в `rsp` збільшується на розмір вилученого значення.

## Локальні змінні

Також можна змінювати значення `rsp` безпосередньо.
Так часто створюють локальні змінні для функції.

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

Зауважимо, що в момент, коли в стеку виділяють місце, значення, збережене в цьому місці, є _невизначеним_.

~~~~exercism/note
Ані `pop`, ані безпосередня зміна `rsp` насправді не видаляють вміст, збережений у памʼяті.
«Видалення» зі стека існує лише як абстракція щодо нової адреси в `rsp`.

У деяких випадках це може викликати проблеми безпеки, розкриваючи внутрішні значення зовнішнім джерелам.
Один зі способів зарадити цьому: занулити вміст усього простору стека, який використовує функція.
~~~~

## Операції call і ret

Головне призначення стека - відстежувати адресу повернення для викликаних функцій.

Як згадувалося в попередньому концепті, є особливий регістр `rip`, який указує на наступну інструкцію для виконання.
Цей регістр використовують, щоб керувати потоком виконання програми; його змінюють такі інструкції, як `jmp` і `call`.

Щоразу, коли використовують інструкцію `call`, поточне значення `rip` неявно додають до стека.
Далі операнд цієї інструкції переміщують у `rip`, щоб виконання продовжилося у викликаній функції.

Інструкція `ret` виконує протилежну дію.
Вона вилучає значення зі стека й записує його в `rip`, тож виконання повертається до функції-викликача.

У точці входу `rsp` указує на адресу, на яку треба повернутися.
Саме цю адресу `ret` має вилучити зі стека.

Тож будь-яку зміну значення `rsp` усередині функції, пряму чи через `push`, треба скасувати, перш ніж функція поверне керування.

## Регістри, які зберігає викликана функція, і регістри, які зберігає викликач

Крім `rsp`, є й інші регістри, які треба зберігати між викликами функцій: `rbp`, `rbx`, `r12`, `r13`, `r14` і `r15`.
Загалом функція-викликач розраховує, що зможе користуватися цими регістрами, і викликана функція їх не змінить.

Це означає, що _викликана_ функція має зберегти значення цих регістрів, перш ніж ними скористатися, і відновити їхні початкові значення перед поверненням.
Саме тому їх називають **регістрами, які зберігає викликана функція**.

Інші регістри загального призначення викликана функція може використовувати безпосередньо.

Це означає, що функція-_викликач_ має зберегти значення цих регістрів перед викликом будь-якої функції, адже викликана функція може їх змінити.
Саме тому їх називають **регістрами, які зберігає викликач**.

_Найпоширеніший спосіб зберегти вміст регістра - записати його в стек._

## Пролог і епілог

У деяких випадках стек може використовуватися дуже інтенсивно, із багатьма змінами до повернення з функції.
Тож відстежувати всі ці зміни, щоб їх скасувати, може бути складно.

У таких випадках поширена стратегія - зберегти адресу `rsp` в іншому регістрі, який усередині функції більше ніяк не змінюється.
А потім значення `rsp` можна відновити простою інструкцією `mov` наприкінці, перед поверненням з функції.

Хоча для цього можна використати будь-який регістр, заведено брати `rbp` як покажчик бази.
Оскільки `rbp` сам є регістром, який зберігає викликана функція, перед цим часто виконують `push rbp`.
Цю послідовність зазвичай називають **прологом**.

Наприкінці `rsp` відновлюють інструкцією `mov rsp, rbp`, а потім відновлюють і `rbp`, вилучивши його зі стека інструкцією `pop`.
Цю послідовність зазвичай називають **епілогом**.

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

~~~~exercism/note
Головне призначення послідовностей прологу й епілогу - допомогти програмісту відстежувати зміни `rsp`.
Компілятору це, звісно, робити набагато легше.

Саме тому багато компіляторів застосовують оптимізацію, яка за можливості відмовляється від покажчика кадру й прибирає прологи та епілоги.
~~~~

## Передавання аргументів через стек

Згідно з угодою про виклики [System V ABI][SystemV] аргументи зазвичай передають функціям у регістрах.
Однак коли аргументів забагато або вони не вміщуються в розмір одного регістра, можна скористатися стеком.

У таких випадках значення додають до стека у зворотному порядку, щоб перший аргумент був ближче до `rsp`.
Оскільки в точці входу `rsp` указує на адресу повернення, а це 8-байтове значення в x86-64, до першого аргументу в стеку, якщо він є, можна звернутися через `rsp + 8`:

```x86asm
mov rdi, 4   ; first argument
mov rsi, 8   ; second argument
mov rdx, 15  ; third argument
mov rcx, 16  ; fourth argument
mov r8, 23   ; fifth argument
mov r9, 42   ; sixth argument

; any remaining integer argument goes on the stack in reversed order
sub rsp, 16
mov qword [rsp], 100      ; seventh argument
mov qword [rsp + 8], 300  ; eighth argument

call many_arguments_fn ; call implicitly pushes `rip` to the stack
; so, at point of entry, 'many_arguments_fn' finds the first six integer arguments in the usual registers
; the seventh argument is found in rsp + 8
; and the eighth argument is found in rsp + 16
```

## Вирівнювання стека

System V ABI вимагає, щоб стек був вирівняний на 16 байтів безпосередньо _перед_ виконанням інструкції `call`.
Оскільки `call` додає `rip` до стека, у точці входу стек викликаної функції **не** вирівняний на 16 байтів.

Це означає, що функція, яка викликає іншу (особливо зовнішню), має вирівняти стек перед використанням `call`.

Це можна зробити, віднявши від `rsp` відповідне значення.
У точці входу це значення має бути на 8 більшим за число, кратне 16: 8, 24, 40 тощо.
Оскільки інструкція `push` віднімає від `rsp`, того самого результату можна досягти непарною кількістю `push`:

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

## Червона зона

System V ABI резервує 128-байтовий простір одразу під `rsp`, яким можна користуватися без будь-якого коригування `rsp`.
Цей простір називають [червоною зоною][red-zone]:

```x86asm
fn:
    mov [rsp - 8], rax ; this is safe to use because it is in the red zone
    ret                ; no need to restore rsp
```

Червоною зоною безпечно користуватися лише в листовій функції, тобто в такій, яка не викликає інших.

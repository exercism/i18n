# Як зробити внесок у трек C

Дякуємо за інтерес до треку мови C на Exercism!
Ми раді будь-якому внеску: новій вправі, зміні в інструментарії чи документації, створеному issue або навіть просто коментарю до наявного issue чи PR.
Цей файл допоможе зробити перші кроки.

Спершу радимо прочитати [документацію Exercism][Exercism docs], зокрема розділ про [внесок у трек мови][contributing to a language track], адже ці документи охоплюють більшість базової інформації.

Далі зауважмо, що кілька речей, специфічних саме для цього репозиторію, пояснено нижче.

Ми заохочуємо внески, які виправляють і покращують наявні вправи.
Зауважте, що вправи цього треку мають відповідати стандартам, визначеним у репозиторії [problem-specifications][].
Зміни в тестах чи документації спільної вправи зазвичай потребують pull request у тому репозиторії, перш ніж їх можна буде додати до вправ цього треку.
Якщо є сумніви, просто відкрийте [issue][issue] на GitHub, і ми обговоримо зміну.

## Кодекс поведінки

Допоможімо зберегти Exercism привітним для всіх.
Будь ласка, прочитайте й дотримуйтеся [Кодексу поведінки][Code of Conduct].

## Робочий процес Git

1. Зробіть форк і клонуйте.
2. Додайте цей репозиторій як новий remote до свого клону: `git remote add upstream https://github.com/exercism/c.git`
3. Створіть нову гілку: `git checkout -b name-of-branch`
4. Робіть коміти й надсилайте їх як зазвичай у своїй новій гілці
5. Коли все буде готово надіслати pull request, зробіть rebase своєї гілки на upstream main, щоб розвʼязати можливі конфлікти: `git fetch upstream && git rebase upstream/main` Після розвʼязання конфліктів може знадобитися надіслати зміни у свою гілку з `--force`.
6. Коли все готово, надішліть зміни у свою гілку й створіть pull request, як описано нижче.

## Issues

Ми відстежуємо баги, покращення та запити на підтримку в репозиторії за допомогою [issues][issues] на GitHub.

Для загальніших обговорень проєкту загалом зазирніть до issues у репозиторії [discussions][discussions].

### Гарний перший патч

Ми намагаємося позначати issues тегом «good first patch», якщо вважаємо, що їх можна розвʼязати без глибокого контексту про кодову базу чи функціональність Exercism. Щоб знайти їх, виконайте пошук за [good-first-patch][good-first-patch].

## Pull Requests

Було б чудово дотримуватися цих простих [настанов щодо pull request][pull request guidelines] під час створення PR, але це не обовʼязково.

Pull request має бути присвячений одному issue або одній зміні.
Ми вітаємо зміни в стилі коду й формулюваннях, але для таких змін, якщо можливо, відкривайте окремий PR.
Відкрийте issue, перш ніж створювати PR зі значними (breaking) змінами в наявній вправі або зі змінами в багатьох вправах. Краще обговорити ці зміни до початку роботи.

Якщо зміна стосується вправи, можна запустити скрипти CI перед надсиланням pull request, або вони запустяться автоматично після, як описано в розділі [Continuous Integration][Continuous Integration].

Під час надсилання pull request ми іноді просимо внести зміни, перш ніж прийняти патч.

Не закривайте перший pull request і не відкривайте другий із цими змінами.
Якщо надіслати більше комітів у гілку, для якої відкрито pull request, він оновиться автоматично.

Якщо потрібно створити PR зі змінами, які ще не готові до злиття в main (наприклад, щоб обговорити якийсь конкретний пункт), створіть PR як зазвичай, але скористайтеся вебінтерфейсом GitHub, щоб [перетворити PR на чернетку][convert the PR to a draft], аби супровідники знали, що він ще не готовий до злиття.

Як і з додаванням комітів, не потрібно закривати pull request і відкривати новий, якщо змінюється історія (rebase, squash, amend), а для оновлення гілки у своєму форку достатньо git push --force.
Pull request указує на цю гілку, а не на конкретні коміти.

## Стиль коду

Очікуваний стиль коду для внесків зі змінами в коді описано в [настановах зі стилю][style guide].

Код вправ перевіряється під час [CI][Continuous Integration] на відповідність правилам стилю щодо пробілів і відступів.
Перевірка використовує інструмент командного рядка [`clang-format`][clang-format].
Додаючи вправу чи змінюючи її, можна перевірити відповідність зміни цим правилам, запустивши інструмент локально перед комітом.

У Linux `clang-format` має бути доступний для встановлення через пакетний менеджер вашого дистрибутива.
На Mac пакет `clang-format` можна встановити за допомогою [Homebrew][].

`clang-format` можна запустити для всіх файлів, виконавши `format.sh`.
Щоб запустити його вручну для одного файлу, виконайте таке:

```bash
clang-format -i $(file)
```

## Будова вправи

Кожна вправа має міститися в каталозі `c/exercises/practice/{exercise-name}`.
Докладніше про реалізацію вправи, що відповідає специфікації, дивіться в [implement-an-exercise-from-specification][implement-an-exercise-from-specification]

Структура каталогу вправи така (зверніть увагу: для назв каталогів використовується дефіс, а для назв файлів - підкреслення):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - Цей файл містить усі тести для вправи.  
`test-framework` - каталог із тестовим середовищем [Unity][] від [ThrowTheSwitch][].  
  У ThrowTheSwitch є непоганий посібник із [початку роботи з Unity][getting started with unity], якщо потрібен туторіал.  
  Використовувану версію Unity зазначено в [versions][]. Структуру тестового файлу описано в [настановах зі стилю][test-file-layout].  
  Тести слід писати так, щоб вони задовольняли файл `canonical-data.json` для вправи в репозиторії [problem-specifications][]  
`{exercise-name}.c` / `{exercise-name}.h` - Вихідні файли вправи.  
  Використовуйте [include guards][] у заголовних файлах.
  Тести вправи можна запустити командою `make test` з кореня репозиторію.
* `makefile` - це makefile вправи в тому вигляді, як він має збиратися.  
Потрібні два правила:
test: скомпілювати test_{exercise-name}.c і запустити його.
memcheck: скомпілювати test_{exercise-name} з флагами -fsanitize=address, -fno-common, -fno-omit-frame-pointer і запустити його
Очікується, що файли makefile майже не змінюються від вправи до вправи, тож скопіювати такий файл з іншої вправи має бути легко.

**Не забудьте** додати вправу до `config.json` треку. Для цього потрібно визначити найкраще місце для вправи серед порядку всіх інших вправ треку. Також потрібно згенерувати UUID, щоб додати його сюди. Для обох цих завдань можна скористатися інструментом [configlet][]; він навіть виконає перевірку лінтером і відформатує `config.json` після внесення цих змін!

До відома: щоб отримати інсталяційний артефакт для інструмента configlet, перегляньте [сторінку релізів configlet][configlet releases page].

## Безперервна інтеграція

Цей репозиторій використовує GitHub workflows, щоб запускати деякі інструменти на кожен коміт у pull request.
Найпростіший спосіб запустити ці workflows для власного внеску - відкрити PR у цьому репозиторії зі своїми змінами, позначити PR як чернетку й дозволити CI цього репозиторію автоматично подбати про все.

### Середовище CI

GitHub запускає CI на віртуальних машинах, які називає [hosted runners][].
Workflows можуть налаштовувати деякі аспекти ранерів, на яких хотіли б запускатися.

Workflows у цьому репозиторії вказують лише те, що кожен із них має запускатися на Ubuntu 24.04. Workflows привʼязані до конкретних версій, а не посилаються на `latest`, оскільки деякі використовувані інструменти можуть поводитися по-різному на різних версіях.

### Запуск CI у власному форку

За бажанням CI можна також запустити у власному форку: просто клонуйте цей репозиторій на GitHub як зазвичай.
YAML-файли в [`./.github/workflows/`][workflows] мають працювати так само.
Щоб автоматична дія [`/format`][format-workflow] працювала правильно, потрібно додати deploy key до свого клонованого репозиторію.

### Перелік workflows

* `checks.yml` запускає `shellcheck` для скриптів інструментів, а потім запускає такі з цих інструментів:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * дія [перевірки посилань Lychee][lychee]
* `configlet.yml` завантажує останню версію configlet, а потім запускає команду `lint` для треку
* `format-code.yml` шукає рядок `/format` у будь-якому коментарі до PR; якщо його знайдено, для вправ запускається `format.sh` і всі отримані зміни комітяться. Щоб коміт міг повторно запустити CI, потрібен deploy key. Deploy key адмініструє безпосередньо Exercism.
* `test.yml` запускає `make` у корені репозиторію, щоб протестувати всі вправи

### Інструменти

З [workflows][workflows] видно, що GitHub отримує вказівку запускати інструменти з каталогу [`./bin`][bin].
Робота, яку виконують інструменти в цьому каталозі, описана так:

* `check-unitybegin` перевіряє, що кожен тестовий файл правильно додає рядок `UNITY_BEGIN()` на початку своєї функції `main()`.
* `fetch-configlet` завантажує інструмент `configlet` з його [репозиторію][configlet].
* `verify-unity-version` перевіряє версію тестового фреймворку Unity, яку використовує кожна вправа. Версію, яку має перевіряти цей файл, зазначено в [`./docs/VERSIONS.md`][versions]
* `check-include-guards` перевіряє, що include guards у заголовних файлах заготовки та прикладу кожної вправи мають правильний формат, а саме:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` завантажує інструмент `configlet` з його [репозиторію][configlet].

### Запуск інструментів локально

Окремі інструменти можна також запускати на власній машині перед комітом.
Спершу переконайтеся, що потрібні програми встановлено (як-от `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] і компілятор C), а потім запустіть потрібний інструмент з кореня репозиторію. Наприклад:

```bash
~/git/c$ make
```

Якщо потрібно запустити лише частину тестів, щоб перевірити свою роботу, їх можна вказати як цілі для make.

```bash
~/git/c$ make acronym all-your-base allergies
```

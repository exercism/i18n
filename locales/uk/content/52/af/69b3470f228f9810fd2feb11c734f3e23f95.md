# Як долучитися до треку Rust на Exercism

Issue та pull request зараз закриваються автоматично.
Опублікуйте повідомлення на [форумі Exercism][the Exercism forum], щоб запропонувати зміни.
Ми дуже раді внескам, якщо їх узгоджено на форумі.

[the Exercism forum]: https://forum.exercism.org/

## Загальні правила

- [Кодекс поведінки](https://exercism.org/code-of-conduct)
- [Правила Exercism щодо pull request](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## Інструментарій

Частина інструментарію лежить у вигляді bash-скриптів у `bin/`.
А набагато більше міститься в `rust-tooling/`, і саме йому варто віддавати перевагу для всього нетривіального.

Також є конфігурація [`mise`](https://mise.jdx.dev/)
з кількома корисними командами для взаємодії з репозиторієм.
Можна сміливо її розширювати.

Якщо ми хочемо запустити тести CI локально, `mise run test` допоможе нам чимало.

## Виключення тестів і додавання власних

Створюючи або оновлюючи вправу, ми можемо вирішити виключити частину тестів із генерації.
Це робиться за допомогою `include = false` у `.meta/tests.toml`.
Будь ласка, додайте коментар із причиною виключення.

Якщо ми хочемо додати додаткові тести, специфічні для треку, це можна зробити у файлі `.meta/additional-tests.json`.
Робімо це лише тоді, коли є вагома причина не передавати ці тести в upstream.
Коментар у додатковому тесті має відповідати на такі запитання:
- Чому тест не передано в `problem-specifications`, тобто чому він не є загально цінним для інших мов?
- Чому цей тест усе одно цінний для треку Rust?

## Створення нової вправи

Ознайомтеся з [документацією Exercism про практичні вправи][Exercism documentation about practice exercises].

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

Запустіть `mise run add-exercise`, і вона попросить мінімальну
інформацію, потрібну для генерації заготовки вправи.
Після цього візьміться за згенеровану вправу й заповніть усі місця-заповнювачі, які знайдете.
Зокрема:

- написання заготовки вправи у `src/lib.rs`
- додавання прикладу рішення у `.meta/example.rs`
- коригування `.meta/test_template.tera`

Тести генеруються за допомогою рушія шаблонів [Tera].
На вхід шаблону подаються канонічні дані з [`problem-specifications`].

Поради щодо написання шаблонів Tera шукайте [тут](#tera-templates).

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

Багато аспектів правильно реалізованої вправи перевіряються в CI.
Замість того щоб витрачати купу часу на вивчення й написання
документації про цей процес, радимо _просто взятися до справи_.
Якщо щось ламається, виправмо це й додаймо тест або автоматизацію,
щоб це більше не повторилося.

Якщо ми створюємо практичну вправу з нуля,
якої немає в `problem-specifications`,
тести доведеться писати вручну.
Тести варто впорядковувати за зростанням складності,
щоб студенти могли по одному прибирати з них ігнорування й розвʼязувати вправу з TDD.
Докладніше про написання якісних тестів читайте в [документації Exercism](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md).

За винятком надзвичайних обставин,
файл заготовки має компілюватися командою `cargo test --no-run`.
Це дає нам змогу перевірити, що сигнатури у файлі заготовки
збігаються із сигнатурами, які потрібні тестам.
Щоб цього досягти, використовуйте `todo!()` як тіло кожної функції.
Якщо є обґрунтована причина, чому це неможливо,
додайте ключ `.custom."allowed-to-not-compile"`
у `.meta/config.json` цієї вправи із зазначенням причини.

## Оновлення вправи

Багато вправ походять із [`problem-specifications`].
Це стосується і їхнього набору тестів, і документації для користувачів.
Перш ніж пропонувати зміни тут,
перевірмо, чи не варто зробити їх у `problem-specifications`.

Щоб оновити вправу, запустіть `mise run update-exercise`.
Більшість роботи тут виконує `configlet sync --update`,
а потім знову запускається генератор тестів.

Коли ми оновлюємо вправу, яка ще не має шаблону tera,
для неї згенерується новий.
Імовірно, його доведеться певною мірою доопрацювати.

Поради щодо написання шаблонів Tera шукайте [в наступному розділі](#tera-templates).

## Шаблони Tera

Повна документація щодо шаблонів Tera [тут][tera-docs].
Далі наведено кілька підходів, які спрацювали для наших конкретних потреб.

Ймовірно, нам захочеться зазирнути у `canonical-data.json` цієї вправи, щоб побачити, як виглядають вхідні дані.
Можна скористатися `bin/symlink_problem_specifications.sh`, щоб створити символьне посилання на ці дані
в каталозі самої вправи. Зручно!

Назва вхідної властивості відрізняється від вправи до вправи.
Типовий шаблон матиме такий вигляд:

```txt
let input = {{ test.input | json_encode() }};
```

Доведеться додати конкретне поле вхідних даних для цієї вправи, наприклад:

```txt
let input = {{ test.input.integers | json_encode() }};
```

Деякі вправи можуть мати значення, що повертаються у разі помилки.
Можна скористатися конструкцією if-else, щоб згенерувати щось інше
залежно від структури даних:

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

Деякі вправи мають кілька функцій, які студент має реалізувати,
а отже, і протестувати.
У такому разі канонічні дані містять поле `property`.
Можна побудувати ланцюжки if-else на основі `test.property` і залежно від цього згенерувати різні функції.

У деяких вправах тестові випадки згруповано в _групи тестів_.
Шаблон має це враховувати.
Часто структуру можна просто вирівняти. (приклад: [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
Однак іноді тести мають однаковий опис у різних групах, що призводить до конфліктів імен, якщо структуру вирівняти.
У такому разі можна скористатися описом групи, щоб упорядкувати тести в модулі. (приклад: [`forth`](/exercises/practice/forth/.meta/test_template.tera))

У [`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs) є кілька власних фільтрів Tera.
Ось, сподіваємося, актуальний список:
- `to_hex` форматує цілі числа у шістнадцятковому вигляді
- `make_ident` перетворює довільний рядок тексту (англ. string) на пристойний ідентифікатор Rust.
   Найкорисніший для генерації назв функцій з описів тестів.
- `fmt_num` форматує числові літерали (вставляє `_` кожні три цифри)

Створюйте власні фільтри в крейті `rust-tooling`.
Сподіваємося, ми не забудемо оновити й цей список. 🙂

Щоб побачити досить складний приклад, зазирнімо в тестовий шаблон `triangle`.
Він упорядковує тестові випадки в модулі й динамічно визначає, які тести сховати за feature gates.
У цій вправі також перереалізовано частину тестових випадків з upstream у `additional-tests.json`, щоб додати до них більше інформації, потрібної для генерації якісних тестів.

[tera-docs]: https://keats.github.io/tera/docs/#templates

з людьми, які мають досвід побудови силабусів.

# Вступ

У мові асемблера будь-які дані - це послідовність байтів.
Це означає, що будь-які дані можна розглядати як **масив** цих базових байтів.

## Доступ до елементів масиву

Щоб отримати доступ до будь-якого значення в памʼяті, потрібно обчислити його **ефективну адресу**.
Ефективна адреса - це вираз, який може складатися з:

- _базової адреси_, наприклад тієї, на яку вказує мітка змінної.
- одного _регістра індексу_, можливо, масштабованого на `1`, `2`, `4` або `8`.
- знакового 32-бітного _зміщення_, тобто числа, яке додають до базової адреси (або віднімають від неї).

Зауважмо, що ця адресація _починається з нуля_, тому базова адреса без будь-якого зсуву вказує на перший байт змінної.
Саме тому розіменування памʼяті за допомогою самої лише мітки, без жодного зсуву, як ми робили в попередніх концепціях, дає значення, що починається з її першого байта:

```x86asm
section .data
    example dq 10 ; example is a 8-byte variable
                  ; so it can be viewed as an array of those 8 bytes
                  ; which can be accessed from index 0 to index 7

section .text
fn:
    mov al, byte [example] ; this accesses the first byte
    mov r8b, byte [example + 2] ; this accesses the third byte
    mov edx, dword [example + 1] ; this accesses 4 bytes starting at the second
```

~~~~exercism/note
x86-64 використовує [little endian][endianness].
Це означає, що найменш значущий байт багатобайтового значення зберігається за найменшою адресою памʼяті.

Отже, коли ми звертаємося до окремих байтів багатобайтового значення, до базової адреси потрібно додати додатне зміщення, щоб дістатися старших байтів.

[endianness]: https://en.wikipedia.org/wiki/Endianness
~~~~

Ініціалізована змінна, оголошена зі списком значень, утворює масив цих значень, де кожен елемент має вказаний розмір.
Однак зсуви завжди вимірюються в **байтах**, навіть коли кожен елемент масиву має більший розмір:

```x86asm
section .data
    arr dq 4, 8, 15, 23, 42 ; this defines an array of 5 qwords (8-byte elements)
                            ; the first qword has value 4 and can be accessed at [arr] (offset 0)
                            ; any subsequent qword can be accessed at offsets increasing by the size in bytes of each element (8)

section .text
fn:
    mov rdx, 2
    lea rcx, [rel arr]
    mov rax, qword [rcx + 8*rdx + 8]  ; rdx is an index register scaled by 8
                                      ; 8 is a signed 32-bit displacement
                                      ; rax now holds 8-bytes stored in 'arr' starting at offset:
                                      ; 8*rdx(2) + 8 = 16 + 8 = 24
                                      ; this is the fourth element of the array, i.e., the element 23
```

Зауважмо, що оскільки адреси вимірюються в байтах, ми можемо звернутися безпосередньо до окремого байта будь-якого елемента масиву:

```x86asm
section .data
    arr dq 4, 8, 15, 16   ; this defines an array of 4 qwords (8-byte elements)

section .text
fn:
    mov r8, 3
    lea r9, [rel arr]
    mov r10b, byte [r9 + 2*r8 + 1] ; this accesses the byte in 'arr' at offset: 2*r8(3) + 1 = 7
                                   ; this byte is part of the first qword and has value 0 (the fist byte is the least significant one)
```

З тієї ж причини в одній інструкції можна звернутися до обсягу, більшого за розмір одного елемента:

```x86asm
section .data
    arr db 1, 2, 3, 4 ; this defines an array of 4 bytes

section .text
fn:
    mov r11d, dword [rel arr] ; this accesses all bytes in arr as a 32-bit value with bytes
                              ; the least significant byte is 1, the next is 2 and so on
                              ; the resulting number is 0x04030201 or 67305985 in decimal
```

~~~~exercism/caution
Асемблер не перевіряє межі під час доступу до масивів.
Індекс за межами масиву читає або записує памʼять поза ним.
Це може призвести до непомітно неправильних результатів, до пошкодження інших даних, а якщо памʼять, до якої ми звертаємося, не відображена, то й до збою під час виконання.
Програміст відповідає за те, щоб кожна ефективна адреса залишалася в межах масиву.
~~~~

## Обчислення розміру ініціалізованого масиву

NASM (The Netwide Assembler, асемблер, який використовує цей трек) має спеціальний символ (`$`), що вказує на поточне місце в памʼяті.
Цей символ дає зручний спосіб обчислити загальний обсяг памʼяті, який займає масив:

```x86asm
section .data
    example dd 4, 5, 6
    example_length dq $ - example  ; this is a qword variable with the size of the array, in bytes
```

Якщо використати `$` одразу після `example`, він має адресу памʼяті кінця масиву.
Це означає, що `$ - example` - це різниця між цією адресою і адресою, на яку вказує мітка `example`.
Це саме загальний розмір у байтах, який займає масив, позначений `example`.

Отже, визначивши `example_length` з цим значенням, ми створили 8-байтову змінну, яка зберігає розмір, або довжину, масиву в байтах.

## Секція .bss

Неініціалізовані дані оголошуються в **секції .bss**.
На більшості платформ операційна система заповнює ці дані нулями на початку виконання програми.

У NASM неініціалізована змінна має імʼя, директиву, яка вказує розмір даних, і кількість елементів, які потрібно зарезервувати.
Кожна з них відокремлюється від інших пробілом.

Основні директиви та відповідні їм розміри даних:

| директива | розмір  |
| :-------: | :------ |
|   resb    | 1 байт  |
|   resw    | 2 байти |
|   resd    | 4 байти |
|   resq    | 8 байтів |

Наприклад, так резервується неініціалізований простір на `3` байти у змінній з іменем `example`:

```x86asm
section .bss
    example resb 3
```

А так резервується неініціалізований простір на `10` разів по `8` байтів (тобто `80` байтів) у змінній з іменем `arr`:

```x86asm
section .bss
    arr resq 10
```

Змінні в `section .bss` можна змінювати, тобто вони доступні для читання й запису.

До неініціалізованих даних можна звертатися так само, як до ініціалізованих, використовуючи їхню ефективну адресу.
Так само вони мають статичний час зберігання і доступні з будь-якої функції в тому самому вихідному файлі (а якщо оголошені `global`, то й в інших вихідних файлах).

## Доступ до адрес масиву за допомогою інструкції lea

Як ми вже зʼясували в попередній концепції, інструкція `lea` обчислює ефективну адресу памʼяті.
Її можна використати, щоб обчислити адресу будь-якого елемента масиву, за тією самою семантикою.

Зауважмо, що за відносної адресації часто потрібно спершу завантажити адресу змінної в регістр, а вже потім формувати складнішу адресу:

```x86asm
lea rax, [rel arr]
lea rdx, [rax + 8*r10 - 20] ; accessing 'arr' directly instead of loading it into rax first may yield an error
```

~~~~exercism/note
Одна з переваг `lea` полягає в тому, що вона використовує арифметику обчислення адрес, щоб отримати значення, фактично не звертаючись до памʼяті за цією адресою.
Завдяки цьому її зручно використовувати для арифметичних обчислень, навіть коли жоден з регістрів не містить адреси памʼяті:

```x86asm
mov rcx, 3
mov rdx, 5
lea rax, [rcx + 8*rdx + 10] ; rax = rcx(3) + 8*rdx(5) + 10 = 3 + 40 + 10 = 53
```
~~~~

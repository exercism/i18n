# Вступ

У багатьох обʼєктно-орієнтованих мовах прийнято розширювати поведінку, [створюючи підкласи][wiki-subclass] батьківського класу: ми успадковуємо методи від батька і додаємо до них нові.
Так ми отримуємо ієрархію обʼєктів.

У Julia _немає класів_, а тому й _немає підкласів_.
Як же нам успадковувати наявну поведінку й розширювати її?

У попередніх концепціях ми бачили, як створити ієрархію типів, а також дізналися, як Julia використовує [множинну диспетчеризацію][concept-multiple-dispatch], щоб обирати методи за типами аргументів.

У Julia також є кілька неформальних інтерфейсів, які дають нашим власним типам змогу долучатися до поведінки, уже визначеної для стандартних типів.

Найпростіше це показати на прикладі інтерфейсу Iterator.

## Ітератори

Раніше в силабусі ми бачили кілька способів, якими Julia може працювати з кожним елементом колекції.

- [Цикли][concept-loops], наприклад `for item in items...`
- [Трансляція][concept-vector-operations]: `[1, 2, 3] .- 0.5`
- [Функції вищого порядку][concept-hof]: `map(√, [1, 4, 9])`
- [Включення][concept-comprehensions]: `[x * y for x in 1:3 for y in 4:6 if isodd(x * y)]`
- [Генератори][concept-comprehensions]: `(x^2 for x in 1:1e6)`, які обчислюються ліниво.

Очевидно, Julia вміє перебирати стандартні колекції елемент за елементом: вектори й діапазони в наведених прикладах, а також Set, Dict тощо.

Як же нам надати цю можливість нашим власним колекціям, особливо якщо їх можна перебирати ліниво, як генератор?

### Мінімальні вимоги

Щоб створити послідовність для ітерації, нам потрібні (принаймні) дві речі:

1. Спосіб отримати _перший_ елемент.
2. Спосіб отримати _наступний_ елемент із поточного стану.

Julia виконує ці завдання методами функції `Base.iterate()` за такими кроками:

1. Спочатку автоматично викликається `Base.iterate(iter)`.
    - Якщо перебирати нічого, повертається `nothing`.
    - Інакше повертається `Tuple` з першого повернутого елемента та першого стану: `(firstitem, firststate)`.
2. `Base.iterate(iter, state)` викликається автоматично, якщо на попередній ітерації було повернуто елемент, і приймає `firststate` як свій аргумент `state`.
    - Якщо ітерація завершується, повертається `nothing`.
    - Інакше повертається `Tuple` з наступного елемента та наступного стану: `(nextitem, nextstate)`.
3. Повторюється крок 2, доки ітерація не завершиться.

Усі ці кроки відбуваються «під капотом»: виклики методів і стан керуються всередині протоколом ітерації (а сам стан залишається непрозорим), а назовні видно лише елемент, зокрема для високорівневих конструкцій на кшталт циклів.
Інакше кажучи, нам завжди видно лише `item`, а все інше залишається в чорній скриньці.

[Множинна диспетчеризація][concept-multiple-dispatch] тут відіграє центральну роль.
Тип `iter` визначає, які методи викликаються, а кількість аргументів визначає, повертається перший чи наступний елемент.

Методи для стандартних типів уже визначено: `Vector`, `Range`, `Set` тощо ([наразі][ref-iterations-collections] загалом 14 типів).

Щоб наш власний `MyType` мав таку саму поведінку, спершу потрібно визначити:
- `Base.iterate(iter::MyType)`
- `Base.iterate(iter::MyType, state)`

Усе це, ймовірно, звучить заплутано в теорії, але насправді може бути досить просто.
Для прикладу уявімо, що нам потрібен тип, який дає степені заданого цілого числа `n` до певної максимальної кількості.

Спершу визначимо власний тип:

```julia
struct Powers
    n::Int      # base number to raise to a power
    count::Int  # maximum length of the sequence
end
```

Тепер ми можемо визначити методи `iterate` для цього типу, але що таке перший елемент і перший стан?

Щоб отримати перший елемент, деяким ітераторам потрібне складне налаштування, але в цьому іграшковому випадку можна помітити, що перший повернутий елемент - це просто основа, тож достатньо перевірити, чи значення `count` більше або дорівнює одиниці.

Тепер розглянемо перший стан, який несе інформацію, потрібну для наступної ітерації.
Вирішувати нам, яку інформацію потрібно відстежувати для цього, і вона може бути будь-якого типу.

У цьому випадку ми могли б просто відстежувати «індекс», до якого підносити `n`, або знайти продуктивніший варіант, використавши найновіший степінь `n` (тобто повернутий елемент) і наступний «індекс» у послідовності.
Ці два числа можна загорнути в `Tuple` і повернути як `state`.

```julia
function Base.iterate(p::Powers)
    # if iteration should continue
    if 1 ≤ p.count
        # return (firstitem, firststate)
        return (p.n, (p.n, 2)) 
    end
    # else terminate iteration
    return nothing
end
```

У цьому прикладі перший елемент (`p.n`) повертається в цикл, а перший стан `(p.n, 2)` передається методу `iterate(P::Powers, state)`.
Там ми можемо обробити стан, щоб отримати наступний елемент, помноживши поточний елемент на основу, і тим самим збільшивши його степінь на `1`.

```julia
function Base.iterate(p::Powers, state)
    # unpack the state
    curr, index = state

    # create next item                 
    next = curr * p.n

    # if iteration should continue
    if index ≤ p.count
        # return (nextitem, nextstate)
        return (next, (next, index + 1))
    end
    # else terminate iteration
    return nothing
end
```

Якщо значення індексу все ще в межах `count`, повертається `Tuple` з елементом `next` і збільшеним `Tuple` стану.
Коли значення `index` перевищує `count`, тоді натомість повертається `nothing`, щоб показати, що ітерація завершилася.

Можливо, ми помітили, що методи `iterate(p::Powers)` і `iterate(p::Powers, state)` мають досить схожі тіла функцій.
Насправді, якщо ми кмітливі, ця схожість дає змогу спростити реалізацію, використавши лише версію з двома аргументами та типовим значенням для стану: `Base.iterate(p::Powers, state=(1, 1))`
Завдяки цьому нам не знадобилася б окрема версія з одним аргументом `iterate(p::Powers)`.
Так часто роблять на практиці, коли це можливо.

Поки що ми вже маємо корисну функціональність: для перших 4 степенів числа 3 ми можемо пройтися циклом по результатах, перевірити, чи задане число є серед результатів, і застосувати агрегувальні функції, як-от `sum()`.

```julia-repl
julia> for p in Powers(3, 4)
            println(p)
       end
3
9
27
81

julia> 9 ∈ Powers(3, 4) # ∈ is a synonym for in
true

julia> sum(Powers(3, 4))
120
```

### Додаткові методи

Попри цей добрий початок, працює ще не все.

```julia-repl
julia> [p for p in Powers(3, 4)]
ERROR: MethodError: no method matching length(::Powers) (from the documentation][ref-interfaces])
The function `length` exists, but no method is defined for this combination of argument types.
You may need to implement the `length` method or define `IteratorSize` for this type to be `SizeUnknown`.
```

І справді, `length(Powers(3, 4))` видає точно те саме повідомлення про помилку.

Це легко виправити, адже довжина є частиною конструктора типу: у цьому випадку 4.
Нам лише потрібно визначити `Base.length()` для цього типу, і тоді ми зможемо використовувати включення та `collect()` для цієї послідовності.

```julia-repl
julia> Base.length(P::Powers) = P.count

julia> length(Powers(3, 4))
4

julia> [p for p in Powers(3, 4)]
4-element Vector{Int64}:
  3
  9
 27
 81

julia> collect(Powers(3, 4))
4-element Vector{Any}:
  3
  9
 27
 81

julia> Set(Powers(3, 4))
Set{Int64} with 4 elements:
  81
  27
  9
  3
```

Задля ефективності краще також визначити `Base.eltype()`: тип елементів результату.
Це дає змогу таким функціям, як `collect()`, заздалегідь виділити місце під вихідний `Vector{Int}`, а не раз за разом робити `push!()` у `Vector{Any}`.

Звернімо увагу на синтаксис, якого ми, можливо, раніше не бачили: цей метод визначається для _типу_, а не для _екземпляра_ типу.

```julia-repl
julia> Base.eltype(::Type{Powers}) = Int
```

Ітератори не _зобовʼязані_ мати скінченну довжину.
Використання «нескінченних» послідовностей обмеженіше, але прохід циклом по них може бути корисним, доки існує спосіб вийти з циклу за допомогою `break`.
Наприклад, ми могли б визначити варіант `Powers`, який генерує значення, менші за певну межу (можливо, `typemax(Int)`, щоб уникнути переповнення цілих чисел).

## Підсумок

Інтерфейси досить заплутано пояснювати, бо підхід Julia настільки відрізняється від більшості інших мов.
Зокрема, назва інтерфейсу може взагалі не згадуватися в реалізації, що зовсім не схоже на [створення підкласів][wiki-subclass] чи [міксини][wiki-mixins].

Однак на практиці вони напрочуд прості:

1. Визначити відповідний тип.
2. Зʼясувати, які методи потрібні.
3. Реалізувати ці методи для свого власного типу; зазвичай це лише кілька методів, досить коротких і простих.
4. Дозволити [множинній диспетчеризації][concept-multiple-dispatch] автоматично подбати про решту.

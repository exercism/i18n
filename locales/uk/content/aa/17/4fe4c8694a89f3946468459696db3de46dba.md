# Докладніше

## Додавання контексту до помилок

Ми розглянули базову обробку помилок у Go в [концепції помилок][concept-errors].
Як ми там дізналися, типово помилки не несуть із собою трасування стека.
Тому так важливо, щоб сама помилка містила достатньо інформації, аби визначити проблему.

Якби ми хотіли додати інформацію до наявної помилки тими засобами, які вже знаємо, то могли б написати щось таке, щоб створити нову помилку з обʼєднаним текстом початкової помилки та додаткової інформації:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

На щастя, пакет `fmt` зі стандартної бібліотеки містить коротший варіант для цього у вигляді функції `Errorf`.
Це дає змогу, наприклад, легко додати інформацію про контекст, у якому сталася помилка.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Якщо ми не впевнені, що помилка вже містить достатньо інформації, варто взяти за звичку завжди додавати контекст до помилки, перш ніж повертати її з функції.
Тобто типовий шаблон обробки помилок має мати такий вигляд:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Як видно з прикладів, за домовленістю додане повідомлення відокремлюють від помилки двокрапкою.
Як і повідомлення початкової помилки, контекстне повідомлення не повинно починатися з великої літери, і в кінці не ставлять крапку.

~~~~exercism/note
Додаючи контекст до помилки, так і хочеться почати повідомлення з «не вдалося ...» чи чогось подібного.
Однак, оскільки помилка, піднімаючись ланцюжком функцій, може накопичити багато додаткового контексту, остаточне повідомлення, яке потрапить у журнал або яке побачить користувач, стає важче читати й рясніє повтореннями.

Ось приклад для ілюстрації:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Тож тримаймо цей кінцевий результат у голові, пишучи контекстні повідомлення, і утримаймося від тексту про те, що щось пішло не так, як очікувалося.
Зазвичай це зрозуміло з контексту (наприклад, рівня логування «ERROR») і з повідомлення початкової помилки.
~~~~

Часто такого способу додавання інформації до помилки цілком достатньо, але бувають випадки, коли треба дозволити тому, хто отримав помилку, перевірити початкову помилку чи дістатися до неї.
Додавання контексту в такий спосіб у Go називають «обгортанням помилки».

## Обгортання помилок і перевірка сторожових помилок

Обгортання помилки потребує лише невеликої зміни в коді, який ми бачили вище.
Щоб обгорнути помилку, треба використати дієслово форматування `%w` замість `%v`.
Під капотом це гарантує, що отримана помилка реалізує метод `Unwrap`, який повертає початкову помилку.
Завдяки цьому `errors.Is` можна використати, щоб перевірити, чи трапляється конкретна сторожова помилка десь у «ланцюжку помилок».
Він робить це, нишком викликаючи `Unwrap` знову й знову, доки потрібну помилку не знайдено або доки ланцюжок не закінчиться.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Перевірка початкової помилки через `errors.Is` не працювала б зі звичайним дієсловом форматування `%v`.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Отже, добра практика - типово використовувати `%v` і вдаватися до `%w` лише тоді, коли ми явно хочемо дозволити тому, хто отримав помилку, дістатися до вкладеної помилки ([Google Go Styleguide][google-go-styleguide]).

Якщо ми опинилися в ситуації, коли треба перевірити сторожову помилку, але явно не хочемо її розкривати, можна використати `==` замість `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Натомість `==` не розпізнав би помилку, якби її було обгорнуто.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Цілком нормально типово працювати з `errors.Is`, але варто завжди памʼятати, що це означає пошук по всьому ланцюжку помилок.

## Перевірка (власних) типів помилок

Існує аналог `errors.Is`, який дає змогу перевірити й дістати з ланцюжка помилок помилку конкретного типу.
Функція для цього - `errors.As`, і, як і `errors.Is`, вона шукатиме заданий тип помилки по всьому ланцюжку.
`errors.As` лише тоді вилучає знайдену помилку відповідного типу, щоб з нею можна було працювати далі, наприклад дістати конкретні поля.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Звернімо увагу на синтаксис щодо вказівників вище.
Код працюватиме й скомпілюється правильно лише тоді, коли `customError` має саме той тип, який реалізує інтерфейс помилки.
У нашому випадку це `*MyCustomError` ([вказівник][concept-pointers] на `MyCustomError`), а не сам `MyCustomError`.

До того ж другий аргумент має бути вказівником на змінну з помилкою.
Оскільки наша помилка вже є вказівником, у `errors.As` ми передаємо вказівник на вказівник (на MyCustomError).
Лише за такого правильно налаштованого коду Go зможе заповнити змінну знайденою помилкою.
~~~~

Як і раніше, `errors.As` не знайшов би тип помилки, якби під час виклику `Errorf` використали `%v`.

Якщо з якоїсь причини не хочемо розкривати помилку, замість цього можна скористатися перевіркою типу (аналогічно до `==` вище).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

Перевірка типу не зможе визначити тип помилки, якби помилку було обгорнуто.

## Як дозволити розкривати помилки власних типів

Іноді самого лише обгортання помилки з додатковим текстом недостатньо.
Натомість можна створити власний тип помилки, який зберігає початкову помилку та додаткові структуровані дані, які ми хочемо додати.
Щоб дозволити розкриття для свого типу помилки, треба лише вручну додати метод `Unwrap() error`, щоб задовольнити інтерфейс `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Поєднання кількох помилок

У Go 1.20 до вбудованого пакета `errors` додали нову функцію `Join`.
`Join` дає змогу поєднати кілька помилок так, що розкриття все ще працює, тобто можна перевірити конкретну помилку чи тип помилки в ланцюжку.
Завдяки цьому ланцюжок помилок насправді може виявитися деревом помилок.
Більше інформації можна знайти в [нотатках до випуску][release-notes] та в [документації][doc-join].

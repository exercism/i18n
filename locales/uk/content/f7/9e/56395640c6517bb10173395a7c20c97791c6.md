# Робочі процеси

GitHub Actions використовує концепцію _робочих процесів_, тобто скриптів, які запускаються автоматично, коли відбувається певна подія (наприклад, надсилання коміту).

Кожен робочий процес GitHub Actions визначається у файлі `.yml` у каталозі `.github/workflows`.
Щоб дізнатися більше про робочі процеси, звернімося до таких документів:

- [Синтаксис робочого процесу](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions)
- [Як вибрати, коли запускається робочий процес](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow)
- [Як вибрати, де запускається робочий процес](https://docs.github.com/en/actions/writing-workflows/choosing-where-your-workflow-runs)
- [Як вибрати, що робить робочий процес](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does)
- [Написання робочих процесів](https://docs.github.com/en/actions/writing-workflows)
- [Найкращі практики](/docs/building/github/gha-best-practices)

## Спільні робочі процеси

Деякі робочі процеси використовуються спільно кількома репозиторіями.

```exercism/caution
Спільні робочі процеси синхронізуються автоматично (з [репозиторію org-wide-files](https://github.com/exercism/org-wide-files/)).
Тому не варто змінювати їхній вміст вручну.
```

### Загальні робочі процеси

- [Синхронізація міток](/docs/building/tracks/ci/workflows/sync-labels): синхронізує мітки репозиторію з файлу

### Робочі процеси для конкретного треку

- [configlet](/docs/building/tracks/ci/workflows/configlet): перевіряє, чи правильно структуровані файли (конфігурації) треку, як синтаксично, так і семантично
- [Жоден важливий файл не змінився](/docs/building/tracks/ci/workflows/no-important-files-changed): коментує pull request-и, які призвели б до повторного тестування наявних рішень
- [Тест](/docs/building/tracks/new/setup-continuous-integration#h-test-workflow): перевіряє вправи треку

### Робочі процеси для інструментарію

- [Розгортання](/docs/building/tracks/ci/workflows/deploy): розгортає Docker-образ інструментарію треку в Docker Hub та ECR

### Необовʼязкові робочі процеси

Є також робочі процеси, які треки можуть підключати за бажанням:

- [Призупинення внесків спільноти](/docs/building/tracks/ci/workflows/pause-community-contributions): автоматично коментує нові issue та PR, створені користувачами, які не є членами GitHub-організації Exercism

## Власні робочі процеси

Супровідники можуть вільно додавати власні робочі процеси до своїх репозиторіїв.
Прикладами таких робочих процесів можуть бути:

- [Лінтування shell-скриптів](https://github.com/exercism/configlet/blob/3baa09608c8ac327315c887608c13a68ae8ac359/.github/workflows/shellcheck.yml)
- [Автоматичне коментування pull request-ів](https://github.com/exercism/elixir/blob/b737f80cc93fcfdec6c53acb7361819834782470/.github/workflows/pr-comment.yml)
- І так далі.

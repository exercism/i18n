# Генератори тестів

Генератори тестів дають трекам змогу генерувати тести автоматично, без потреби писати їх вручну. Кожен генератор тестів читає `canonical data` вправи, де визначено назву тесту, його вхідні та вихідні дані. Докладніше про підхід Exercism до наборів тестів можна прочитати [тут](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Автоматичне генерування тестів позбавляє від будь-яких помилок користувача під час створення тестів. Ми хочемо, щоб тести точно відповідали канонічним даним. Генерування тестів також значно полегшує підтримання тестів в актуальному стані. Коли канонічні дані змінюються, тести автоматично оновлюються під час запуску генератора для відповідного тесту.

Приклад файлу з канонічними даними можна знайти [тут](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)

## Загальні терміни

Переглядаючи канонічні дані та код генераторів, ми натрапляємо на чимало спільних термінів. Сподіваємося, цей список пояснить, що вони означають.

* Канонічні дані - це весь набір тестів.
* Випадок канонічних даних - це представлення одного тестового випадку.
* Опис - назва тесту.
* Властивість - метод, який викликається під час запуску тесту.
* Вхідні дані - те, що подається на вхід тестового випадку.
* Очікуване значення - значення, яке ми очікуємо отримати, запустивши тестовий випадок.

## Як додати простий генератор

Додати генератор тестів нескладно. Достатньо додати до файлу `Generators.fs` у теці `generators` клас із назвою вправи (у PascalCase) й успадкувати його від абстрактного класу `GeneratorExercise`.

Прикладом простого генератора може бути вправа Bob. Її код наведено нижче, але його також можна подивитися в репозиторії [тут](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174).

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

Це цілком робочий генератор, більше нічого писати не потрібно. Щоправда, така простота випливає з того, що і набір тестів, і сама програма досить прості.

## Як додати складний генератор

Для багатьох генераторів достатньо типової поведінки класу `GeneratorExercise`. Однак для складніших генераторів можна перевизначити один або кілька його віртуальних методів:

### Метод: RenderInput

Формує вхідні дані тестового методу.

#### Приклад

Генератор `Gigasecond` формує вхідне значення як значення `DateTime` у дужках:

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

Зауважимо, що поле `key` дає змогу налаштувати вихідні дані лише для конкретних вхідних полів. Так робить генератор `Yacht`:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Метод: RenderExpected

Формує очікуване значення тестового методу.

#### Приклад

Генератор `Connect` формує очікуване значення як значення `Option<T>`:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Метод: RenderSut

Формує систему, що тестується (System Under Test, SUT). Це фактичне значення, яке звіряють з очікуваним.

#### Приклад

У генератора `RunLengthEncoding` є тестовий випадок, який перевіряє, що кодування, а потім декодування вхідних даних дає те саме значення. Метод `RenderSut` перевизначено, щоб перетворити те, що було б одним викликом неіснуючої функції `consistency`, на ланцюжок викликів `encode |> decode`:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Метод: RenderArrange

Формує частину підготовки тестового методу. Саме тут створюється SUT.

Зазвичай типової поведінки цілком достатньо. Змінювати її варто лише за дуже особливих обставин.

Зауваження: цей метод повертає `string list`, де кожен `string` відповідає одному сформованому рядку у файлі тестів.

### Метод: RenderAssert

Формує частину з твердженням тестового методу. Саме тут виконується твердження, яке звіряє SUT з очікуваним значенням.

Зазвичай типової поведінки цілком достатньо. Змінювати її варто лише за дуже особливих обставин.

Зауваження: цей метод повертає `string list`, де кожен `string` відповідає одному сформованому рядку у файлі тестів.

### Метод: RenderSetup

Формує будь-які додаткові допоміжні чи підготовчі методи. Це дає змогу визначити допоміжні методи, які можна використовувати в тестових методах.

Код підготовки додається _перед_ тестовими методами, щоб методи підготовки можна було використовувати в тестових методах.

Зауваження: цей метод повертає `string list`, де кожен `string` відповідає одному сформованому рядку у файлі тестів.

#### Приклад

Генератор `Zipper` додає два допоміжні методи, які використовуються в тестових методах, щоб позбутися частини нудного шаблонного коду:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Метод: RenderValue

Формує одне значення (яке використовується для формування вхідних параметрів, очікуваного значення та SUT).

### Приклад

Генератор `ComplexNumbers` формує різні значення залежно від типу значення:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Метод: MapCanonicalDataCase

Зіставляє випадок канонічних даних. Це може стати в пригоді, якщо потрібно додати або вилучити властивості.

Зазвичай типової поведінки цілком достатньо. Змінювати її варто лише за дуже особливих обставин.

#### Приклад

Генератор `ScaleGenerator` використовує зіставлення випадку канонічних даних, щоб додати відсутню властивість зі значенням `null` (це полегшує подальше опрацювання):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Метод: PropertiesUsedAsSutParameter

Визначає, які властивості слід використовувати як параметри SUT.

Зазвичай типової поведінки цілком достатньо. Змінювати її варто лише за дуже особливих обставин.

#### Приклад

Генератор `RailFenceCipher` явно визначає властивості, які використовуються як параметри SUT, щоб змінити порядок їх передавання:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Метод: PropertiesWithIdentifier

Визначає, яким властивостям слід присвоїти ідентифікатор. Якщо властивість є в цьому списку, їй буде присвоєно значення в окремому рядку, під власним ідентифікатором.

#### Приклад

Генератор `Transpose` вирішив використовувати ідентифікатори для всіх властивостей:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Метод: IdentifierTypeAnnotation

У деяких випадках потрібно, щоб ідентифікатор мав явний тип. Поширений випадок - коли значення є порожнім масивом. Тоді FsUnit потребує анотації типу, щоб успішно виконати твердження.

#### Приклад

Генератор `Minesweeper` додає анотацію типу `string list` для порожніх значень:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Метод: AdditionalNamespaces

Повертає масив додаткових просторів імен, які потрібно відкрити у файлі тестів.

#### Приклад

Генератор `Gigasecond` працює з примірниками `DateTime`, тому додає його простір імен до масиву додаткових просторів імен:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Метод: AssertTemplate

Шаблон твердження, який слід використовувати. Повний список шаблонів тверджень можна знайти в `generators/Templates/_Assert*.liquid`

#### Приклад

Генератор `RationalNumbers` використовує шаблон `"AssertEqualWithin"`, щоб перевіряти числа з плаваючою комою на рівність із заданою точністю:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Метод: TestFileFormat

Формат файлу тестів: модуль або клас.

Типової поведінки майже завжди цілком достатньо. Змінювати її варто лише в надзвичайно рідкісних випадках.

#### Приклад

Генератор `Grep` оголошує себе тестовим класом, щоб можна було використовувати методи підготовки та завершення:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Метод: TestMethodName

Визначає назву тестового методу.

Зазвичай типової поведінки цілком достатньо. Змінювати її варто лише за дуже особливих обставин.

#### Приклад

Генератор `Zipper` трохи чистить назви тестових методів:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Метод: UseFullMethodName

Указує, чи має назва тестового методу використовувати повний шлях: для вкладених тестових випадків перед назвою методу додаватиметься опис батьківського випадку (або випадків).

Зазвичай типової поведінки цілком достатньо. Змінювати її варто лише тоді, коли інакше було б кілька тестових методів з однаковою назвою.

#### Метод: Signature

Генератор `KindergartenGarden` використовує повні назви методів, щоб уникнути збігу назв тестових методів:

```fsharp
override __.UseFullMethodName _ = true
```

### Метод: SkipTestMethod

Указує, чи слід позначати тестовий метод властивістю `Skip = true`.

Типової поведінки майже завжди цілком достатньо. Змінювати її варто лише в надзвичайно рідкісних випадках.

#### Метод: Signature

Вправа `Markdown` - це вправа з рефакторингу, тож усі її тести вже мають бути в належному стані. Тому вона не додає властивість `Skip` до жодного зі своїх тестових методів:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Оновлення наявних файлів

Можливо, наявна вправа не відповідає канонічним даним. Цілком нормально оновити заготовку вправи та (або) приклад вправи, щоб вони відповідали канонічним даним!

Крім того, якщо ми виявимо проблему в одному з наявних генераторів чи наборів тестів, достатньо відкрити генератор, який хочемо оновити, внести зміни й запустити генератори.

## Запуск генераторів

Цей репозиторій написано під [.NET Core 2.x](https://www.microsoft.com/net/core). Щоб запустити генератори, достатньо виконати таку команду в теці generators:

`dotnet run`

Ця команда бере всі визначені генератори вправ і генерує всі тестові випадки для кожної вправи. Ми використовуємо рефлексію, щоб отримати всі вправи, тож якщо ми додаємо новий тест, він автоматично потрапить до генерації під час запуску генератора.

Якщо потрібно запустити лише один генератор, це можна зробити такою командою:

`dotnet run -e <exercise>`

Після запуску генератора результат генерації можна подивитися, перейшовши до файлу тестів для цієї вправи. Наприклад, набір тестів для вправи Bob лежить тут:

`exercises/bob/BobTests.fs`

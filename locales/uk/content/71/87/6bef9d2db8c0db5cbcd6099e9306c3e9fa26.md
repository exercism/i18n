# Про

## Складені типи даних

Часто буває корисно визначати у своїх програмах власні типи.

Створювати нові примітивні типи можна, але роблять це рідко.
Вбудовані [примітивні типи][primitive] - не довільний вибір: вони добре узгоджуються зі стандартними типами в компіляторі LLVM, який Julia використовує для JIT-компіляції.

Куди кориснішою є можливість визначати [складені типи даних][composite-types] з іменованими полями.

В інших мовах є щось подібне, їх називають `structs` або `records`.
Документація Julia називає їх `composite types`, хоча (з невеликою розбіжністю) синтаксис мови визначає їх ключовим словом `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

У наведеному прикладі варто зауважити кілька моментів:

- Для `id` не вказано тип, тож компілятор інтерпретує це як `id::Any`.
  - **Примітка:** на практиці краще допомогти компілятору, вказавши для поля конкретний тип.
  - У [майбутній концепції][parametric] ми побачимо, що ще одним варіантом є використання параметрів.
- Назву типу використовують як конструктор, наприклад `Person(id, name, age)`, щоб отримати екземпляр типу `Person`.
- До окремих полів можна звертатися через точкову нотацію, так само як до [іменованих кортежів][named-tuple].

Екземпляри типу `Person` незмінні, тому оновлювати їх не можна.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Якщо змінюваність потрібна, додамо `mutable` до визначення.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Конструктор типово вимагає, щоб поля йшли в тому самому порядку, що й у визначенні, а це стає незручним для складніших типів.

Використання макросу `@kwdef` дає дві нові можливості:

- Конструктор використовує ключові слова, а не позиції.
- Поля можуть мати типові значення, і за бажанням їх можна не передавати в конструктор.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Ієрархії складених типів даних

Досі ми створювали лише конкретні складені типи даних.
Якщо перевірити, усі вони є підтипами `Any`.

Коли ми створюємо кілька споріднених типів, доцільніше визначити для них ієрархію.
Зробити це зовсім не складно.

Спершу створимо абстрактний тип:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Далі додамо оператор `<:` до визначення типу, щоб показати це відношення.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Повторюємо за потреби, памʼятаючи, що створювати підтипи конкретних типів не можна.

Для складнішої ієрархії створимо абстрактні підтипи за потреби.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

Цінність такої ієрархії стане зрозумілішою, коли ми дійдемо до концепції `Multiple Dispatch` і побачимо, як функції працюють із типами аргументів.


## Внутрішні конструктори

На початку цієї концепції ми бачили, що назву типу використовують як конструктор, щоб створювати екземпляри цього типу:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

Тут `Person()` відомий як `outer constructor`.
Типи полів перевіряють на сумісність із визначенням типу, і якщо треба, виникає помилка.

А якщо нам потрібні обмеження на _значення_, які передають, а не лише на _типи_?

Тоді ми можемо додати `inner constructor` у визначення типу, щоб виконати відповідні перевірки.

Наприклад, у нас є абстрактний тип `AbstractPoint`, призначений для координат `(x, y)`, але ми хочемо підтип з обмеженням `y > x`.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

Функцію `new()` можна використовувати _лише_ у внутрішніх конструкторах; вона повертає потрібний екземпляр, якщо вхідні дані визнано придатними.

У разі некоректних вхідних даних ми могли б зупинитися з повідомленням про помилку, як у прикладі.
Або ж замість цього можна використати заповнювач, наприклад `nothing` або `missing`.
Докладніше про це йдеться в концепції [`Nothingness`][nothingness].

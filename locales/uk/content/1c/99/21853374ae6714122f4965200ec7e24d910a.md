# Докладніше

`interfaces` - це основний засіб [відокремлення][wiki-loose-coupling] використання класу від його реалізації. Таке відокремлення дає гнучкість під час супроводу реалізації та допомагає забезпечити типобезпечну узагальнену поведінку.

Синтаксис інтерфейсу подібний до синтаксису класу чи структури, але методи й властивості подаються лише як сигнатури, без тіла.

```csharp
public interface ILanguage
{
    string Speak();
}

public interface IItalianLanguage : ILanguage
{
    string Speak();
    string SpeakItalian();
}

public interface IScriptConverter
{
    string Version { get; set; }
    string ConvertCyrillicToLatin(string cyrillic);
}
```

Клас або структура, що реалізує інтерфейс, повинні реалізувати всі операції, визначені в інтерфейсі.

Зазвичай інтерфейси роблять одне або кілька з такого:

- дають змогу коду, який їх використовує, працювати з багатьма різними класами узагальнено. У цьому разі інтерфейси відіграють ту саму роль, що й базовий клас
- відкривають підмножину функціональності для якоїсь конкретної мети (наприклад, [`IComparable<T>`][icomparable]) або
- відкривають публічний API класу, щоб кілька реалізацій могли співіснувати. Один з прикладів - [тестовий дубль][wiki-test-double]

```csharp
public class ItalianTraveller : IItalianLanguage
{
    public string Speak()
    {
        return "Ciao mondo";
    }

    public string SpeakItalian()
    {
        return Speak();
    }
}

public class ItalianTravellerV2 : IItalianLanguage
{
    public string Speak()
    {
        return "migliorata - Ciao mondo";
    }

    public string SpeakItalian()
    {
        return Speak();
    }
}

public class FrenchTraveller : ILanguage
{
    public string Speak()
    {
        return "Ça va?";
    }
}

public class RussianTraveller : ILanguage, IScriptConverter
{
    public string Version { get; set; } = "1.0";

    public string Speak()
    {
        return "Привет мир";
    }

    public string ConvertCyrillicToLatin(string cyrillic)
    {
        throw new NotImplementedException();
    }
}

public class DocumentTranslator : IScriptConverter
{
    public string Version { get; set; } = "1.0";

    public string Translate(string russian)
    {
        throw new NotImplementedException();
    }

    public string ConvertCyrillicToLatin(string cyrillic)
    {
        throw new NotImplementedException();
    }
}
```

Код, який використовує наведені вище інтерфейси та класи, може:

- однаково працювати з усіма, хто вміє «говорити», незалежно від мови.
- давати змогу якійсь підсистемі, що займається перетворенням системи письма, працювати, не переймаючись тим, з якими саме типами вона має справу.
- залишатися необізнаним про зміни в італійському мовці, що зручно, коли код класу й код користувача супроводжують різні команди

Інтерфейси широко використовують для підтримки тестування, адже вони уможливлюють просте [мокування][so-mocking-interfaces].

Докладніше про те, які типи членів можна включати в інтерфейс, розповідає ця [стаття][dt-interfaces].

Інтерфейси можуть успадковуватися від інших інтерфейсів.

Члени інтерфейсу типово є публічними.

Інтерфейси можуть містити вкладені типи, як-от літерали `const`, `enums`, `delegates`, `classes` і `structs`. Тут інтерфейси відіграють роль [просторів імен][wiki-namespaces] так само, як класи й структури, а поведінка та синтаксис ідентичні.

За задумом C# не підтримує множинне успадкування, але дає змогу отримати його різновид через інтерфейси.

Крім того, механізм інтерфейсів ґрунтується на тому, що [поліморфізм можна реалізувати через інтерфейси][interface-polymorphism].

## Явна реалізація інтерфейсу

Іноді назви методів і сигнатури можуть збігатися в двох різних інтерфейсах.
Щоб мати окрему реалізацію таких методів, C# пропонує [явну реалізацію інтерфейсів][explicit-implementation]. Зауважмо: щоб скористатися конкретною реалізацією інтерфейсу, потрібно привести вираз, який посилається на обʼєкт, до цього інтерфейсу. Це можна зробити присвоєнням, приведенням типу або передаванням як параметра.

```csharp
public interface IFoo
{
    void X();
}

public interface IBar
{
    void X();
}

public class Census : IFoo, IBar
{
    void IFoo.X()
    {
        Console.Write("This is from Foo");
    }

    void IBar.X()
    {
        Console.Write("This is from Bar");
    }
}

public class User
{
    public void Use()
    {
        IFoo foo = new Census();
        IBar bar = new Census();
        foo.X();
        // => "This is from Foo"
        bar.X();
        // => "This is from Bar"
    }
}
```

Є кілька випадків використання:

- Конфлікт доменів (як у прикладі вище), коли методи мають однакові сигнатури.
- Методи з однаковою назвою, але різними типами повернення: у власних класах-колекціях може виявитися потрібним явний інтерфейс для застарілого `IEnumerable.GetEnumerator()` поряд з `IEnumerable<T>.GetEnuerator()`. Можливо, такий інтерфейс ніколи не буде використано, але компілятор може наполягати на ньому.
- Методи, назви яких не конфліктують між інтерфейсами, але класу-реалізації бажано використати цю назву для іншої, спорідненої мети: `IFormattable` має метод `ToString()`, який приймає параметр _типу формату_, а також параметр типу `IFormatProvider`. Такий клас, як `FormattableString` з базової бібліотеки класів (BCL), має цей інтерфейс, щоб його могли використовувати процедури, які приймають `IFormattable`, але для його основної версії `ToString(IFormatProvider)` виразніше було б опустити параметр _типу формату_, бо в реалізації він не використовується й лише заплутав би користувачів API.

## Типова реалізація

Версія 8 мови C# розвʼязує дошкульну проблему з API. Якщо додати методи до інтерфейсу, щоб розширити функціональність для нових реалізацій, доведеться змінити всі наявні реалізації цього інтерфейсу, щоб вони відповідали контракту API, навіть якщо жодної специфічної для них поведінки не потребують. Тепер C# дозволяє надати _типовий метод_ як частину інтерфейсу (розробникам Java це знайомо). Раніше в разі такої зміни поряд з початковим інтерфейсом існувала його _версія 2_.

Ця [стаття][dt-interfaces] - чудовий вступ до інтерфейсів; вона зосереджується на _типовій реалізації_ та інших допоміжних нововведеннях, як-от члени `static`, `private` і `virtual`.

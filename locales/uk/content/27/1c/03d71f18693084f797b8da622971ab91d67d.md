## Використання скрипта

Для генерації тестів потрібна локальна копія репозиторію [problem-specifications][problem-specifications]. Скрипт потрібно запускати з кореневої директорії `python`, щоб коректно отримати доступ до вправ.

Щоб дізнатися, як користуватися скриптом, запустіть `bin/generate_tests.py --help`.

## Шаблони тестів

Шаблони тестів підтримують синтаксис [Jinja2] і мають такі контекстні змінні з канонічних даних:
- `exercise`: назва вправи через дефіс (напр.: `two-fer`)
- `version`: версія канонічних даних (напр.: `1.2.0`)
- `cases`: список обʼєктів випадків або список списків `cases`. Щоб дізнатися точну структуру для вправи, над якою ми працюємо, зверніться до `canonical-data.json`
- `has_error_case`: указує, чи передбачає якийсь тестовий випадок викидання помилки (напр.: `False`)
- `additional_cases`: подібна до `cases` структура, але заповнюється з файлу `.meta/additional_tests.json` цієї вправи, якщо він існує (приклад дивіться у `exercises/word-count/.meta/additional_tests.json`)

Крім того, для зручності додано такі фільтри шаблонів:
- `to_snake`: перетворює рядок тексту (англ. string) на snake_case (напр.: `{{ "CamelCaseString" | to_snake }}` -> `camel_case_string`)
- `camel_case`: перетворює рядок тексту на CamelCase (напр.: `{{ "snake_case_string" | camel_case }}` -> `SnakeCaseString` )
- `error_case`: перевіряє, чи передбачає тестовий випадок викидання помилки (напр.: `{% for case in cases%}{% if case is error_case}`)
- `regex_replace`: заміна в рядку тексту за регулярним виразом (напр.: `{{ "abc123" | regex_replace("\\d", "D") }}` -> `abcDDD`)


### Домовленості

- Загальні макроси для структур шаблонів, які часто повторюються, визначено у `config/generator_macros.j2`.
  - Їх можна імпортувати так:
  `{%- import "generator_macros.j2" as macros with context -%}`
- Усі шаблони тестів мають закінчуватися `{{ macros.footer() }}`.
- Усі назви класів Python мають бути в CamelCase (напр.: `TwoFer`).
  - Перетворити за допомогою `{{ "two-fer" | camel_case }}`
- Усі назви модулів і функцій Python мають бути в snake_case (напр.: `high_scores`, `personal_best`).
  - Перетворити за допомогою `{{ "personalBest" | to_snake }}`
- Тести, специфічні для треку, визначено у файлі опцій `.meta/additional_tests.json`. Обʼєкт JSON, визначений у цьому файлі, має мати один ключ, `cases`, з тією самою структурою, що й `cases` у `canonical-data.json`.
- Тести, специфічні для треку, слід розміщувати після канонічних тестів у файлах тестів.
- Тести, специфічні для треку, слід позначати у файлі тестів таким коментарем:
```
# Additional tests for this track
```


### Структура

Більшість шаблонів матиме приблизно такий вигляд:

```Jinja2
{%- import "generator_macros.j2" as macros with context -%}
{{ macros.header() }}

class {{ exercise | camel_case }}Test(unittest.TestCase):
    {% for case in cases -%}
    def test_{{ case["description"] | to_snake }}(self):
        value = {{ case["input"]["value"] }}
        expected = {{ case["expected"] }}
        self.assertEqual({{ case["property"] }}(value), expected)

    {% endfor %}

{{ macros.footer() }}
```


### Перевизначення імпортів

Назви, які імпортує `macros.header()`, можна перевизначити, додавши список альтернативних назв для імпорту (напр.: `clock`):

```Jinja2
{{ macros.header(["Clock"])}}
```


### Ігнорування властивостей

Іноді може виникнути потреба відфільтрувати властивості, які не тестуються в цьому треку. Макрос `header` також приймає аргумент `ignore` (напр.: `high-scores`):

```Jinja2
{{ macros.header(ignore=["scores"]) }}
```

## Створення шаблону

1. Створіть `.meta/template.j2` для вправи, яку ми реалізуємо, і відкрийте його у своєму редакторі.
2. Скопіюйте і вставте [приклад структури](#Layout) у файл шаблону та збережіть його.
3. Вносьте потрібні зміни у файл шаблону, доки він не даватиме коректний код тестів, звіряючись із `canonical-data.json` цієї вправи щодо назв вхідних даних і структури випадків.
    - Використайте [доступні макроси](../config/generator_macros.j2), щоб не переписувати стандартні розділи.
    - Якщо ми реалізуємо шаблон для наявної вправи, точно повторювати структуру наявного файлу тестів не обовʼязково, але чим менше розбіжностей, тим простіше всім буде перевіряти PR.

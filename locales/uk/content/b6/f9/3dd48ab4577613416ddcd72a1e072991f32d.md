# Докладніше

На цьому етапі силабусу ми вже не раз бачили, як R використовують як імперативну мову, і дедалі частіше як функціональну (особливо з бібліотеками [`purrr`][ref-purrr] та [`dplyr`][ref-dplyr]).

Якщо тепер сказати, що R насамперед обʼєктно-орієнтована мова, це може викликати скепсис!

Як не дивно, але це правда.
Усередині R реалізовано з використанням класів, успадкування, поліморфізму та звичок, типових для програмістів, які працюють з ООП.

Однак той, хто знайомий з Java чи Ruby (з явним ООП) або навіть із Python (який подекуди напівприховано обʼєктно-орієнтований), вважатиме підхід R ... _незвичним_.

Для початку, існує кілька способів побудови класів: мабуть, три, що широко використовуються (S3, S4, R6), а також різні інші, переважно теоретичного інтересу.

Докладний розгляд можна знайти в [Advanced R, 2e][book-advanced-r], розділи 12-16.
Ця книжка 2019 року здебільшого призначена для тих, хто хоче розуміти внутрішню будову R і підтримувати її, тож без ООП не обійтися.

Підручники, більше орієнтовані на кінцевих користувачів, поводяться по-різному.

- «The Art of R Programming» (2011, лише в друкованому вигляді) має розділ про ООП, який охоплює S3 і (стисліше) S4, що були важливі на той час.
  Зауваження, що _«класи S3 мають доволі нашвидкуруч складену структуру»_, і досі напрочуд влучне.
- «R in Action» (3-є видання, 2022) відводить ООП лише 3 сторінки в розділі про просунуте програмування ближче до кінця.
- [R for Data Science, 2e][book-r-data-sci] (2023, 548 сторінок у друкованому виданні) зовсім не згадує про ООП.

У цій концепції ми зосередимося на класах S3, які є найпростішими, найпоширенішими й найдоречнішими для задач типу Exercism.
Деякі практичні вправи на треку R вимагають створити клас S3, в інших це необовʼязково, але щиро заохочується.

## Класи S3

Вони старі: назва S3 означає лише те, що їх запровадили у версії 3 мови S (комерційного попередника R).

Клас S3 до того ж дуже простий: зазвичай це [масив][concept-lists] з принаймні одним додатковим атрибутом.

Цитата з [Advanced R][book-s3]: _«S3 неформальний і створений під конкретну потребу, але в його мінімалізмі є певна елегантність: не можна прибрати жодну його частину й отримати при цьому робочу обʼєктно-орієнтовану систему»._

```R
# create a list
pt2d <- list(x = 2.5, y = 4.2)
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
class(pt2d)
#> [1] "list"
attributes(pt2d)
#> $names
#> [1] "x" "y"

# convert the list to an S3 class
class(pt2d) <- "point2d"
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
#>  - attr(*, "class")= chr "point2d"
class(pt2d)
#> [1] "point2d"
attributes(pt2d)
#> $names
#> [1] "x" "y"

#> $class
#> [1] "point2d"
```

Отже, присвоєння [`class(obj)`][ref-class] просто додає до `obj` один атрибут, у цьому випадку позначаючи pt2d як екземпляр класу point2d.

Кроки створення можна обʼєднати за допомогою [`structure()`][ref-structure]:

```R
pt2d_2 <- structure(list(x = 2.5, y = 4.2), class = "point2d")
pt2d_2 == pt2d
#> Error in pt2d_2 == pt2d : comparison of these types is not implemented
```

Хоча отримані екземпляри за задумом ідентичні, ми ще не реалізували спосіб, яким R міг би це підтвердити.

### Узагальнені методи

Той, хто знайомий з ООП в інших мовах, може замислитися: _«а хіба класи не повинні вміти щось РОБИТИ?»_

Ми можемо переглянути методи, доступні для екземплярів `point2d`, і виявити, що (на відміну від базового `list`) їх поки що немає.

```R
methods(class = "point2d")
#> no methods found
methods(class = "list")
#>  [1] %within%      all.equal     as.col_spec   as.data.frame as_mapper     as_tibble     coerce        common_by    
#>  [9] Ops           pattern_alpha relist        scale_type    select        type.convert  within       
#> see '?methods' for accessing help and source code
```

У більшості мов з ООП методи визначають усередині визначення класу.
Кілька мов (зокрема Ruby) дозволяють додавати й змінювати методи класу пізніше.

Класи S3 влаштовані зовсім інакше.
Замість додавати методи до класу, ми додаємо клас до узагальненого методу.

Будь-хто, працюючи в інтерактивній консолі R, постійно користується узагальненими методами, зазвичай не замислюючись, як їх реалізовано.

Дуже поширений приклад - `print()`, хоча назву цієї функції ми набираємо рідко.
Якщо ввести значення `x` саме по собі в запрошенні консолі, це лише синтаксичний цукор для `print(x)`.

```R
1:4
#> [1] 1 2 3 4
print(1:4)
#> [1] 1 2 3 4
```

Ми вже можемо надрукувати `pt2d`.
Хоча `print()` нічого не знає про клас `point2d`, у нього є розумні типові значення, які дають раду найрізноманітнішим обʼєктам.

```R
pt2d
#> $x
#> [1] 2.5

#> $y
#> [1] 4.2

attr(,"class")
#> [1] "point2d"
```

Це досить громіздко, і нам, можливо, хочеться виводити точку гарно й стисло.

Легко: просто додаймо функцію з назвою `print.point2d()`.
Назва має бути у формі `methodname.classname`, щоб диспетчер знав, що шукати.

```R
print.point2d <- function(pt) {
  cat("Cartesian coords (", pt$x, ", ", pt$y, ")\n", sep="")
}

pt2d
#> Cartesian coords (2.5, 4.2)
```

Тепер припустімо, що ми хочемо створити новий узагальнений метод, наприклад `flipvert()`, щоб змінити знак координати `y`.

Знову ж таки, легко:

```R
flipvert <- function(x, ...) UseMethod("flipvert")
```

Це створює диспетчер, де `x` - наш обʼєкт із класом S3, а `...` опрацьовує будь-які додаткові аргументи, потрібні визначенням методів («крапкові аргументи», як описано в [концепції функцій][concept-functions]).

Далі ми можемо визначити метод для `point2d` і скористатися ним.

```R
flipvert.point2d <- function(pt) {
  pt$y <- -pt$y
  pt
}

flipvert(pt2d)
#> Cartesian coords (2.5, -4.2)

methods("flipvert")
#> [1] flipvert.point2d
```

Тепер R знає, як перевернути нашу точку і як показати результат.

Ми могли б розширити це, створивши класи для 3D, для полярних координат тощо, а потім визначити методи для кожного.

З погляду кінцевого користувача існує лише `flipvert(x, ...)`, і ми можемо покластися на R: він визначить клас вхідних даних і застосує відповідну реалізацію під капотом.

~~~~exercism/caution
Назви функцій у форматі `verb.class` мають вигляд методів S3 і для користувачів, і для парсера R.
Уникаймо подібних назв в інших контекстах.

Щоправда, базовий R іноді порушує це правило.
Слід вважати це прикрою історичною випадковістю (для функцій навіть старших за S3), яку доводиться зберігати заради зворотної сумісності.
~~~~

### Успадкування

Ентузіасти ООП можуть написати кілька довгих підручникових розділів про успадкування, підкласи, міксини й усе решта.

R просто дозволяє передати атрибуту `class` кілька назв: довший вектор рядків тексту (англ. string) замість одного рядка тексту.

Ризикуючи розтягнути приклад до межі, уявімо, що ми створили узагальнений клас `point` і хочемо успадкувати від нього `point2d`, `point3d` тощо.

Тоді визначення `point2d` просто використовує `class = c("point2d", "point")`: конкретний клас і батьківський клас (або класи).

Узагальнені методи, як-от `print()`, тоді послідовно шукатимуть `print.point2d()`, `print.point()` і (ймовірно) `print.default()`, використовуючи першу реалізацію, яку знайде диспетчер.

### Безпека

Багато мов з ООП (Java, C# тощо) використовують інкапсуляцію даних у класах, щоб ретельно перевіряти код під час компіляції та забезпечувати типобезпеку.

Варто памʼятати, що S3 дозволяє робити майже все, що завгодно, навіть якщо це не має жодного сенсу (повідомлення про помилку, якщо взагалі зʼявиться, прийде пізніше).

Цитата з [«Advanced R»][book-s3] (2-е видання, розділ 13.3):

> _Якщо ми мали справу з іншими обʼєктно-орієнтованими мовами, це може викликати неприємне відчуття, але на практиці ця гнучкість рідко створює проблеми. R не заважає нам стріляти собі в ногу, але доки ми не наводимо дуло на власні пальці й не натискаємо гачок, проблем не буде._

Ну, _гаразд?_
R чудово підходить для дослідницького аналізу даних і статистики, часто під час інтерактивної роботи.
Ніхто ж не пропонує використовувати його для написання надзахищених корпоративних фінансових систем!

# Вступ

На цьому етапі силабусу ми вже бачили, як R часто використовують як імперативну мову, і дедалі частіше як функціональну (особливо з бібліотеками [`purrr`][ref-purrr] та [`dplyr`][ref-dplyr]).

А тепер припущення, що R передусім обʼєктно-орієнтована, може викликати певний скепсис!

Як не дивно, але це правда.
Усередині R реалізовано за допомогою класів, успадкування, поліморфізму та поглядів, типових для програмістів ООП.

Однак кожен, хто знайомий із Java чи Ruby (явно ООП) або навіть із Python (напівприховано ООП у деяких аспектах), вважатиме підхід R ... _незвичним_.

Для початку, існує кілька підходів до класів: мабуть, три в поширеному вжитку (S3, S4, R6), а також різні інші, переважно теоретичного інтересу.

Ґрунтовний розгляд можна знайти в [Advanced R, 2e][book-advanced-r], розділи 12-16.
Ця книжка 2019 року орієнтована переважно на тих, хто хоче зрозуміти й підтримувати внутрішню будову R, тож ООП тут конче потрібне.

Підручники, більше орієнтовані на кінцевих користувачів, різняться.

- The Art of R Programming (2011, лише друковане видання) має розділ про ООП, що охоплює S3 і (коротше) S4, які тоді були важливі.
  Зауваження, що _«класи S3 мають доволі нашвидкоруч зібрану структуру»_, досі разюче влучне.
- R in Action (3-є видання, 2022) відводить ООП лише 3 сторінки в розділі про просунуте програмування ближче до кінця.
- [R for Data Science, 2e][book-r-data-sci] (2023, 548 сторінок у друкованому виданні) взагалі не згадує ООП.

Цей концепт зосередиться на класах S3, які найпростіші, найпоширеніші й найдоречніші для задач типу Exercism.
Деякі з практичних вправ на треку R вимагають створити клас S3, в інших це необовʼязково, але мʼяко заохочується.

## Класи S3

Вони старі: назва S3 просто означає, що їх запровадили у версії 3 мови S (комерційного попередника R).

Клас S3 також дуже простий: зазвичай це [масив][concept-lists] з принаймні одним додатковим атрибутом.

Цитуючи [Advanced R][book-s3]: _«S3 неформальний і створений ad hoc, але в його мінімалізмі є певна елегантність: не можна прибрати жодну його частину й далі мати корисну обʼєктно-орієнтовану систему»._

```R
# create a list
pt2d <- list(x = 2.5, y = 4.2)
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
class(pt2d)
#> [1] "list"
attributes(pt2d)
#> $names
#> [1] "x" "y"

# convert the list to an S3 class
class(pt2d) <- "point2d"
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
#>  - attr(*, "class")= chr "point2d"
class(pt2d)
#> [1] "point2d"
attributes(pt2d)
#> $names
#> [1] "x" "y"

#> $class
#> [1] "point2d"
```

Тож присвоєння [`class(obj)`][ref-class] просто додає до `obj` один атрибут, у цьому разі позначаючи pt2d як екземпляр класу point2d.

Кроки створення можна поєднати з [`structure()`][ref-structure]:

```R
pt2d_2 <- structure(list(x = 2.5, y = 4.2), class = "point2d")
pt2d_2 == pt2d
#> Error in pt2d_2 == pt2d : comparison of these types is not implemented
```

Хоча отримані екземпляри умовно ідентичні, ми ще не реалізували спосіб, щоб R це підтвердив.

### Узагальнені методи

Хто знайомий з ООП в інших мовах, може замислитися: _«хіба класи не повинні вміти щось РОБИТИ?»_

Ми можемо перевірити методи, доступні для екземплярів `point2d`, і виявити, що (на відміну від базового `list`) їх наразі немає.

```R
methods(class = "point2d")
#> no methods found
methods(class = "list")
#>  [1] %within%      all.equal     as.col_spec   as.data.frame as_mapper     as_tibble     coerce        common_by    
#>  [9] Ops           pattern_alpha relist        scale_type    select        type.convert  within       
#> see '?methods' for accessing help and source code
```

У більшості мов ООП методи визначено всередині визначення класу.
Кілька мов (зокрема Ruby) дозволяють додавати й змінювати методи класу пізніше.

Класи S3 дуже відрізняються.
Замість додавання методів до класу ми додаємо клас до узагальненого методу.

Кожен, хто працює інтерактивно в консолі R, постійно користується узагальненими методами, зазвичай не замислюючись про те, як їх реалізовано.

Дуже поширений приклад - `print()`, хоча ми рідко набираємо назву цієї функції.
Якщо ввести значення `x` саме по собі в запрошенні консолі, це лише синтаксичний цукор для `print(x)`.

```R
1:4
#> [1] 1 2 3 4
print(1:4)
#> [1] 1 2 3 4
```

Ми вже можемо вивести `pt2d`.
Хоча `print()` нічого не знає про клас `point2d`, у неї є розумні типові значення, щоб обробити найрізноманітніші обʼєкти.

```R
pt2d
#> $x
#> [1] 2.5

#> $y
#> [1] 4.2

attr(,"class")
#> [1] "point2d"
```

Це досить громіздко, тож, можливо, нам потрібен спосіб виводити точку гарно й стисло.

Легко: достатньо додати функцію з назвою `print.point2d()`.
Назва має бути у формі `methodname.classname`, щоб диспетчер знав, що шукати.

```R
print.point2d <- function(pt) {
  cat("Cartesian coords (", pt$x, ", ", pt$y, ")\n", sep="")
}

pt2d
#> Cartesian coords (2.5, 4.2)
```

Тепер припустімо, що ми хочемо створити новий узагальнений метод, наприклад `flipvert()`, щоб змінити знак координати `y`.

І знову легко:

```R
flipvert <- function(x, ...) UseMethod("flipvert")
```

Це створює диспетчер, де `x` - наш обʼєкт із класом S3, а `...` обробляє будь-які додаткові аргументи, які можуть знадобитися визначенням методів («точкові аргументи», як описано в [концепті функцій][concept-functions]).

Потім ми можемо визначити метод для `point2d` і скористатися ним.

```R
flipvert.point2d <- function(pt) {
  pt$y <- -pt$y
  pt
}

flipvert(pt2d)
#> Cartesian coords (2.5, -4.2)

methods("flipvert")
#> [1] flipvert.point2d
```

Тепер R знає, як перевернути нашу точку й показати результат.

Ми могли б розширити це, створивши класи для 3D, для полярних координат тощо, а потім визначити методи для кожного.

З погляду кінцевого користувача існує лише `flipvert(x, ...)`, і ми можемо покластися на R, щоб визначити клас вхідних даних і використати відповідну базову реалізацію.

~~~~exercism/caution
Назви функцій у форматі `verb.class` мають вигляд методів S3, як для користувачів, так і для парсера R.
Уникаймо подібних назв в інших контекстах.

Щоправда, базовий R іноді порушує це правило.
Слід розглядати це як прикру історичну випадковість (для функцій навіть старших за S3), яку треба зберегти заради зворотної сумісності.
~~~~

### Успадкування

Прихильники ООП можуть написати кілька довгих підручникових розділів про успадкування, підкласи, міксини та все інше.

R просто дозволяє передати кілька назв атрибуту `class`: довший вектор рядків тексту (англ. string), а не один рядок тексту.

Ризикуючи розтягнути приклад до межі, припустімо, що ми створили узагальнений клас `point` і хотіли зробити його підкласами `point2d`, `point3d` тощо.

Тоді визначення `point2d` просто використовує `class = c("point2d", "point")`: конкретний клас і батьківський клас (або класи).

Узагальнені методи, як-от `print()`, тоді послідовно шукатимуть `print.point2d()`, `print.point()` і (ймовірно) `print.default()`, використовуючи першу реалізацію, яку знайде диспетчер.

### Безпека

Багато мов ООП (Java, C# тощо) використовують інкапсуляцію даних у класах, щоб виконувати ретельні перевірки під час компіляції та забезпечувати типобезпеку.

Варто памʼятати, що S3 дозволяє робити майже все, що завгодно, навіть якщо це не має сенсу (повідомлення про помилку зʼявиться пізніше, якщо взагалі зʼявиться).

Цитуючи [«Advanced R»][book-s3] (2-е видання, розділ 13.3):

> _Якщо ми користувалися іншими обʼєктно-орієнтованими мовами, це може змусити нас почуватися незатишно, але на практиці ця гнучкість створює мало проблем. R не заважає нам стріляти собі в ногу, але поки ми не націлимо рушницю на власні пальці й не натиснемо на гачок, проблем не буде._

Що ж, _гаразд?_
R чудово підходить для дослідницького аналізу даних і статистики, часто під час інтерактивної роботи.
Ніхто не радить використовувати його для написання високозахищених корпоративних фінансових систем!

# Про

У багатьох обʼєктно-орієнтованих мовах заведено розширювати поведінку через [створення підкласів][wiki-subclass] від батьківського класу: ми успадковуємо методи батька й додаємо власні нові.
Так ми отримуємо ієрархію обʼєктів.

У Julia _немає класів_, тож, відповідно, _немає й підкласів_.
То як же нам успадковувати й розширювати наявну поведінку?

У попередніх концепціях ми бачили, як створити ієрархію типів, а також дізналися, як Julia за допомогою [множинної диспетчеризації][concept-multiple-dispatch] обирає методи за типами аргументів.

Крім того, у Julia є кілька неформальних [інтерфейсів][ref-interfaces], які дають змогу нашим власним типам долучатися до поведінки, уже визначеної для стандартних типів.

Найпростіше це продемонструвати на інтерфейсі ітераторів.

## [Ітератори][ref-iterators]

Раніше в силабусі ми бачили кілька способів, якими Julia може працювати з кожним елементом колекції.

- [Цикли][concept-loops], як-от `for item in items...`
- [Трансляція][concept-vector-operations]: `[1, 2, 3] .- 0.5`
- [Функції вищого порядку][concept-hof]: `map(√, [1, 4, 9])`
- [Включення][concept-comprehensions]: `[x * y for x in 1:3 for y in 4:6 if isodd(x * y)]`
- [Генератори][concept-comprehensions]: `(x^2 for x in 1:1e6)`, які обчислюються ліниво.

Очевидно, що Julia вміє перебирати стандартні колекції елемент за елементом: вектори й діапазони в наведених вище прикладах, а також Set, Dict тощо.

Як нам надати цю можливість власним колекціям, особливо якщо їх можна перебирати ліниво, як генератор?

### Мінімальні вимоги

Щоб створити послідовність для ітерації, нам потрібні (принаймні) дві речі:

1. Спосіб отримати _перший_ елемент.
2. Спосіб отримати _наступний_ елемент із поточного стану.

Julia виконує ці завдання за допомогою методів функції `Base.iterate()` у такі кроки:

1. Спершу автоматично викликається `Base.iterate(iter)`.
    - Якщо перебирати нічого, повертається `nothing`.
    - Інакше повертається `Tuple` з першим поверненим елементом і першим станом: `(firstitem, firststate)`.
2. Якщо на попередній ітерації було повернено елемент, автоматично викликається `Base.iterate(iter, state)`, де `firststate` передається як аргумент `state`.
    - Якщо ітерація завершується, повертається `nothing`.
    - Інакше повертається `Tuple` з наступним елементом і наступним станом: `(nextitem, nextstate)`.
3. Крок 2 повторюється до завершення.

Усі ці кроки відбуваються «під капотом»: виклики методів і стан керуються всередині самим протоколом ітерації (стан залишається непрозорим), а назовні виставляється лише елемент, до якого доходять високорівневі конструкції, як-от цикли.
Інакше кажучи, ми бачимо тільки `item`, а все решта залишається чорною скринькою.

[Множинна диспетчеризація][concept-multiple-dispatch] тут відіграє центральну роль.
Тип `iter` визначає, які методи викликаються, а кількість аргументів визначає, повертається перший чи наступний елемент.

Методи для стандартних типів уже визначено: `Vector`, `Range`, `Set` тощо ([наразі][ref-iterations-collections] загалом 14 типів).

Щоб наш власний тип `MyType` мав ту саму поведінку, спершу потрібно визначити:
- `Base.iterate(iter::MyType)`
- `Base.iterate(iter::MyType, state)`

Усе це, ймовірно, звучить заплутано в абстракції, але насправді може бути досить просто.
Для прикладу уявімо, що нам потрібен тип, який дає степені заданого цілого числа `n` до певної максимальної кількості.

Спершу визначмо власний тип:

```julia
struct Powers
    n::Int      # base number to raise to a power
    count::Int  # maximum length of the sequence
end
```

Тепер ми можемо визначити методи `iterate` для цього типу, але що таке перший елемент і перший стан?

Щоб отримати перший елемент, деяким ітераторам потрібне складне налаштування, але в цьому іграшковому випадку ми бачимо, що перший повернений елемент - це просто базове число, тож достатньо перевірити, чи значення `count` більше або дорівнює одиниці.

Тепер розгляньмо перший стан, який несе інформацію, потрібну для наступної ітерації.
Це вже на наш розсуд, яку інформацію потрібно відслідковувати для цього, і це може бути будь-який тип.

У цьому випадку ми могли б просто відслідковувати «індекс», до якого підносити `n`, або ж знайти продуктивніший варіант: узяти найсвіжіший степінь `n` (тобто повернений елемент) і наступний «індекс» у послідовності.
Ці два числа можна загорнути в `Tuple` і повернути як `state`.

```julia
function Base.iterate(p::Powers)
    # if iteration should continue
    if 1 ≤ p.count
        # return (firstitem, firststate)
        return (p.n, (p.n, 2)) 
    end
    # else terminate iteration
    return nothing
end
```

У цьому прикладі перший елемент (`p.n`) повертається в цикл, а перший стан `(p.n, 2)` передається методу `iterate(P::Powers, state)`.
Там ми можемо обробити стан, щоб отримати наступний елемент, помноживши поточний елемент на базове число й тим самим збільшивши його степінь на `1`.

```julia
function Base.iterate(p::Powers, state)
    # unpack the state
    curr, index = state

    # create next item                 
    next = curr * p.n

    # if iteration should continue
    if index ≤ p.count
        # return (nextitem, nextstate)
        return (next, (next, index + 1))
    end
    # else terminate iteration
    return nothing
end
```

Якщо значення індексу все ще в межах `count`, повертається `Tuple` з елементом `next` і збільшеним станом `(next, index + 1)`.
Коли значення `index` перевищує `count`, натомість повертається `nothing`, що означає завершення ітерації.

Можливо, ми помітили, що методи `iterate(p::Powers)` і `iterate(p::Powers, state)` мають досить схожі тіла функцій.
Насправді, якщо ми кмітливі, ця схожість дає змогу зробити реалізацію компактнішою, використавши лише версію з двома аргументами та типовим значенням для стану: `Base.iterate(p::Powers, state=(1, 1))`
Тоді нам не потрібен був би окремий метод `iterate(p::Powers)` з одним аргументом.
Так часто роблять на практиці, коли це можливо.

~~~~exercism/advanced
Коли ми знайомилися з необовʼязковими аргументами в концепції [Функції][concept-functions], про реалізацію не йшлося.

Відтоді ми дізналися про множинну диспетчеризацію, тож тепер стає зрозуміліше, що Julia автоматично перетворює функцію _з_ необовʼязковими аргументами на кілька методів _без_ необовʼязкових аргументів.

Визначити `Base.iterate(P::Powers, state=(1, 1))` - це рівноцінно тому, щоб окремо визначити і `Base.iterate(P::Powers, state)`, і `Base.iterate(P::Powers)`.

[concept-functions]: https://exercism.org/tracks/julia/concepts/functions
~~~~

Поки що ми вже маємо трохи корисної функціональності: для перших 4 степенів числа 3 ми можемо пройтися циклом по результатах, перевірити, чи задане число є серед результатів, і застосувати агрегатні функції, як-от `sum()`.

```julia-repl
julia> for p in Powers(3, 4)
            println(p)
       end
3
9
27
81

julia> 9 ∈ Powers(3, 4) # ∈ is a synonym for in
true

julia> sum(Powers(3, 4))
120
```

### Додаткові методи

Попри цей добрий початок, працює ще не все.

```julia-repl
julia> [p for p in Powers(3, 4)]
ERROR: MethodError: no method matching length(::Powers)
The function `length` exists, but no method is defined for this combination of argument types.
You may need to implement the `length` method or define `IteratorSize` for this type to be `SizeUnknown`.
```

І справді, `length(Powers(3, 4))` видає точно таке саме повідомлення про помилку.

Це легко виправити, адже довжина є частиною конструктора типу: у цьому випадку 4.
Достатньо визначити `Base.length()` для цього типу, і тоді ми зможемо використовувати включення та `collect()` для цієї послідовності.

```julia-repl
julia> Base.length(P::Powers) = P.count

julia> length(Powers(3, 4))
4

julia> [p for p in Powers(3, 4)]
4-element Vector{Int64}:
  3
  9
 27
 81

julia> collect(Powers(3, 4))
4-element Vector{Any}:
  3
  9
 27
 81

julia> Set(Powers(3, 4))
Set{Int64} with 4 elements:
  81
  27
  9
  3
```

Задля ефективності краще також визначити `Base.eltype()`: тип елементів результату.
Це дає змогу таким функціям, як `collect()`, заздалегідь виділити місце під вихідний `Vector{Int}`, а не раз за разом робити `push!()` у `Vector{Any}`.

Звернімо увагу на синтаксис, якого ми, можливо, ще не бачили: цей метод визначено для _типу_, а не для _примірника_ типу.

```julia-repl
julia> Base.eltype(::Type{Powers}) = Int
```

Ітератори не _зобовʼязані_ мати скінченну довжину.
Використання «нескінченних» послідовностей обмеженіше, але цикл по них може бути корисним, якщо є спосіб `break` вийти з циклу.
Наприклад, ми могли б визначити варіант `Powers`, який генерує значення, менші за певну межу (можливо, `typemax(Int)`, щоб уникнути переповнення цілих чисел).

## Інші інтерфейси

### [Індексація][ref-indexing]

Інтерфейс ітераторів дає змогу взяти довільний власний тип і змусити його поводитися як послідовність, визначивши лише кілька простих методів.

Припустімо, ми також хочемо мати змогу індексувати послідовність:

```julia-repl
julia> P = Powers(3, 4)
Powers(3, 4)

julia> P[2]
ERROR: MethodError: no method matching getindex(::Powers, ::Int64)
The function `getindex` exists, but no method is defined for this combination of argument types.
```

Ми можемо додати цю поведінку, і [посібник][ref-indexing] пояснює, як це зробити.

Щонайменше нам потрібно визначити `getindex()`.

```julia-repl
julia> function Base.getindex(P::Powers, i::Int)
          1 ≤ i ≤ P.count || throw(BoundsError(P, i))
          return p.n ^ i
       end

julia> p = Powers(3, 4)
Powers(3, 4)

julia> p[3]
27
```

Нам також потрібно визначити:

- `firstindex()` і `lastindex()` для підтримки `P[begin]` та `P[end]`.
- Варіанти `getindex()` для підтримки індексації векторами й діапазонами.
- У теорії `setindex!()`, хоча важко уявити, що це взагалі означало б у цьому прикладі.

Однак на цьому етапі ми виконуємо багато роботи лише для того, щоб зробити наш ітератор більш схожим на вектор.

### [AbstractArray][ref-abstractarray]

Можливо, варто подумати про альтернативні інтерфейси, які дають кращу відправну точку.

У цьому випадку можна зробити `Powers` підтипом [`AbstractArray`][ref-abstractarray], що безкоштовно дає нам багато поведінки, властивої масивам.

Для послідовності `Powers` відповідний масив складається з цілих чисел і має один вимір.
Іноді це записують як `AbstractArray{Int, 1}`, але в новішому коді Julia частіше трапляються псевдоніми `AbstractVector{Int}` для одновимірних і `AbstractMatrix{Int}` для двовимірних масивів.

```julia-repl
julia> struct PowersArray <: AbstractVector{Int}
           n::Int
           count::Int
       end
```

Замість `length()` тепер потрібно визначити `size()` з кортежем довжин уздовж кожного виміру: у цьому випадку вимір лише один.

```julia-repl
julia> Base.size(PA::PowersArray) = (PA.count,)
```

Як ми хочемо індексувати записи?
У [концепції багатовимірних масивів][concept-multi-dimensional-arrays] ми запровадили два основні підходи:

- Один індекс на вимір, тобто `M[row, col]` для матриці `M`.
- Єдиний індекс, що відповідає розташуванню записів у памʼяті

Їх називають відповідно `Cartesian` і `Linear`.

У прикладі в нас лише один вимір, тож лінійна індексація тут доречна.

```julia-repl
julia> Base.IndexStyle(::Type{PowersArray}) = IndexLinear()

julia> Base.getindex(PA::PowersArray, i::Int) = PA.n ^ i

julia> p = PowersArray(3, 4)
4-element PowersArray:
  3
  9
 27
 81

julia> p[3]
27
```

Зауважмо, що в цьому випадку ми не визначали `iterate()`.
Julia автоматично надає типову реалізацію на основі нашого визначення `getindex()`.

Визначити власну версію `iterate()` усе ще можливо, і в деяких випадках вона може бути ефективнішою.

Використання інтерфейсу `AbstractArray` особливо цінне, якщо ми хочемо ітерацію вищої розмірності.
Ризикуючи розтягнути іграшковий приклад до межі, це могло б означати перші `m` степенів чисел у `1:n`, що ітеративно визначить масив розміру `(m, n)`.

```julia-repl
struct PowersMatrix{Int} <: AbstractMatrix{Int}
    ns::AbstractVector{Int}
    count::Int
end

Base.size(PM::PowersMatrix) = (PM.count, length(PM.ns))
Base.IndexStyle(::Type{PowersMatrix}) = IndexCartesian()
Base.getindex(PM::PowersMatrix, i::Int, j::Int) = PM.ns[j] ^ i

julia> PM = PowersMatrix(2:6, 4)
4×5 PowersMatrix{Int64}:
  2   3    4    5     6
  4   9   16   25    36
  8  27   64  125   216
 16  81  256  625  1296

julia> PM[3, 2]
27

julia> PM[7] # column major linear indexing
27

julia> PM[21]
BoundsError: attempt to access 4×5 PowersMatrix{Int64} at index [21]
[...]
```

### [Округлення][ref-rounding]

У попередніх концепціях згадувалися різні види округлення для числових типів.

```julia-repl
julia> round(1.7)
2.0

julia> floor(1.7)
1.0

julia> ceil(1.7)
2.0

# specify output type
julia> round(Int, 1.7)
2

julia> round(2.4 + 7.3im)
2.0 + 7.0im
```

Функція [`round()`][ref-round] гнучкіша за це: вона дає змогу вказати [`RoundingMode`][ref-roundingmode] (з 7 наразі підтримуваних), кількість десяткових знаків у результаті та основу системи числення.

Можливо, ми захочемо, щоб ті самі функції працювали з нашими власними типами.
Зазвичай ідеться про складені типи, як-от координати.

```julia-repl
julia> struct Point3D
           x::Float64
           y::Float64
           z::Float64
       end

julia> p = Point3D(7.63, 9.24, 4.50)
Point3D(7.63, 9.24, 4.5)

julia> round(p)
ERROR: MethodError: no method matching round(::Point3D, ::RoundingMode{:Nearest})
The function `round` exists, but no method is defined for this combination of argument types.
```

Не дивно, що існує інтерфейс `Rounding`, який щонайменше вимагає визначити `round()` для нашого типу.

```julia-repl
julia> Base.round(P3D::Point3D, r::RoundingMode) = Point3D(round(P3D.x, r), round(P3D.y, r),round(P3D.z, r))

julia> round(p)
Point3D(8.0, 9.0, 4.0)

julia> ceil(p)
Point3D(8.0, 10.0, 5.0)
```

Оскільки ми включаємо `RoundingMode` у визначення, `floor()` і `ceil()` працюють автоматично.

Звісно, ми вільні визначати складніші форми округлення.

- Можливо, ми захочемо округлити `Point3D` до цілої відстані від початку координат у тому самому напрямку.
- Для кутів ми могли б округлювати до 16 напрямків, якими користуються синоптики (_«вітер ПдПдЗ, 15 вузлів»_), тобто кратних π/8 радіана.
- Можливо, ми захочемо додати можливість указувати `digits`, `sigdigits` або `base`.
- Для проміжків часу є [особливі варіанти][ref-round-periods]

## Підсумок

Інтерфейси досить заплутано пояснювати, бо підхід Julia так відрізняється від більшості інших мов.
Зокрема, назва інтерфейсу може взагалі не згадуватися в реалізації: зовсім не так, як зі [створенням підкласів][wiki-subclass] чи [міксинами][wiki-mixins].

Однак на практиці вони напрочуд прості:

1. Визначмо відповідний тип, вирішивши, чи буде корисним підтипування.
2. Зʼясуймо, які методи потрібні (з [документації][ref-interfaces]).
3. Реалізуймо ці методи для нашого власного типу; зазвичай це лише кілька методів, досить коротких і простих.
4. А про решту автоматично подбає [множинна диспетчеризація][concept-multiple-dispatch].

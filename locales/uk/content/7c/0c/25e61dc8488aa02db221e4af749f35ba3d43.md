# Вступ

## Додавання контексту до помилок

Ми розглянули базову обробку помилок у Go в [концепції помилок][concept-errors].
Як ми там дізналися, типово помилки не несуть із собою трасування стеку.
Тому критично важливо, щоб сама помилка містила достатньо інформації, аби визначити проблему.

Якби ми хотіли додати інформацію до наявної помилки за допомогою вже відомих нам інструментів, ми могли б написати щось таке, щоб створити нову помилку з обʼєднаним текстом початкової помилки та додаткової інформації:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

На щастя, пакет `fmt` зі стандартної бібліотеки містить скорочений варіант для цього у вигляді функції `Errorf`.
Це дозволяє, наприклад, легко додати інформацію про контекст, у якому сталася помилка.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Часто такого способу додавання інформації до помилки цілком достатньо, але бувають випадки, коли ми хочемо дозволити споживачеві нашої помилки перевірити або отримати початкову помилку, яка лежить в основі.
Додавання контексту в такий спосіб називається «обгортанням помилки» в Go.

## Обгортання помилок і перевірка сторожових помилок

Обгортання помилок можна досягти дуже незначною зміною коду, який ми бачили вище.
Щоб обгорнути помилку, потрібно використати команду форматування `%w` замість `%v`.
Під капотом це гарантує, що отримана помилка реалізує метод `Unwrap`, який повертає початкову помилку.
Завдяки цьому `errors.Is` можна використовувати, щоб перевірити, чи певна сторожова помилка трапляється десь у «ланцюжку помилок».
Він робить це, потайки викликаючи `Unwrap` знову і знову, доки відповідну помилку не буде знайдено або ланцюжок не закінчиться.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Хорошою практикою є типово використовувати `%v` і застосовувати `%w` лише тоді, коли ми явно хочемо дозволити споживачеві отримати доступ до помилки, яка лежить в основі ([Google Go Styleguide][google-go-styleguide]).

Якщо ми опинимося в ситуації, коли хочемо перевірити сторожову помилку, але явно не хочемо розгортати, можна використати `==` замість `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Цілком нормально типово працювати з `errors.Is`, але слід завжди памʼятати, що це означає, що буде перевірено весь ланцюжок помилок.

## Перевірка (власних) типів помилок

Існує еквівалент до `errors.Is`, який дозволяє перевіряти та отримувати помилку певного типу з ланцюжка помилок.
Функція для цього - `errors.As`, і так само, як `errors.Is`, вона шукатиме заданий тип помилки по всьому ланцюжку.
`errors.As` лише тоді витягує знайдену помилку, що відповідає типу, щоб з нею можна було працювати далі, наприклад, отримати конкретні поля.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Будьмо обережні з синтаксисом щодо вказівників вище.
Код буде працювати й компілюватися правильно, лише якщо `customError` має точний тип, який реалізує інтерфейс помилки.
У нашому випадку це `*MyCustomError` ([вказівник][concept-pointers] на `MyCustomError`), а не сам `MyCustomError`.

Крім того, другий аргумент має бути вказівником на змінну помилки.
Оскільки наша помилка вже є вказівником, те, що ми передаємо в `errors.As`, є вказівником на вказівник (на MyCustomError).
Лише коли все налаштовано правильно, Go зможе заповнити змінну знайденою помилкою.
~~~~

Як і раніше, `errors.As` не знайшла б тип помилки, якби під час виклику `Errorf` використовувався `%v`.

Якщо ми з якоїсь причини не хочемо розгортати, натомість можна використати твердження типу (еквівалент `==` вище).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

Твердження типу не зможе визначити тип помилки, якщо помилку було обгорнуто.

## Дозволити розгортання помилок власних типів

Іноді самого лише обгортання помилки з деяким додатковим текстом недостатньо.
Замість цього можна створити власний тип помилки, який містить початкову помилку та додаткові структуровані дані, які ми хочемо додати.
Якщо ми хочемо дозволити розгортання для свого типу помилки, єдине, що потрібно зробити, - це вручну додати метод `Unwrap() error`, щоб задовольнити інтерфейс `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

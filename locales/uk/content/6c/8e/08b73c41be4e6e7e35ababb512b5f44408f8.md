# Докладніше

Функцію називають [рекурсивною][recursion], якщо вона викликає саму себе.

Одна ключова відмінність між викликом функції та циклом полягає в тому, що виклик функції кладе адресу повернення в стек.
Це означає, що рекурсивна функція зазвичай вимагає більше місця в стеку, ніж еквівалентний цикл.

Як наслідок, функція, яка продовжує викликати саму себе, може зрештою вичерпати весь стек.
Це називається [переповненням стека][stack-overflow].

Саме тому кожна рекурсивна функція повинна мати принаймні один базовий випадок, тобто ситуацію, коли функція повертає керування, не викликаючи саму себе.
Будь-який рекурсивний виклик зрештою має досягти базового випадку.

Наприклад, функцію факторіала `n! = n * (n - 1) * ... * 1` можна визначити рекурсивно, узявши `1` за базовий випадок:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Зауважимо, що `factorial` має виконати `push rdi` перед рекурсією та `pop rdi` після неї.
Це тому, що після повернення з рекурсивного виклику їй усе ще потрібне `n`, щоб обчислити `n * (n-1)!`.

Зауважимо також, що використання регістра, який зберігає викликана функція, не розвʼязало б цієї проблеми.

Хоча рекурсивна функція потенційно може викликати саму себе, вона сама є викликаною для якоїсь іншої функції.
Це означає, що функція також має зберігати регістри, які зберігає викликана функція, перед їх використанням і відновлювати їхнє значення після використання.
Зазвичай це роблять за допомогою послідовності `push`/`pop`, як ми бачили в попередній концепції.

Оскільки кожен кадр рекурсивної функції, за винятком базового випадку, також викликає іншу функцію й має зберегти власні локальні змінні, цю послідовність `push`/`pop` доводиться повторювати для кожного кадру.
Навіть збереження змінної безпосередньо в стеку, без використання регістрів, усе одно коштуватиме ті самі `8` байтів на кадр.

Це означає, що кожен рекурсивний виклик додає `8` байтів до стека для адреси повернення, яку кладе `call`, плюс `8` байтів для кожної локальної змінної, яку потрібно зберегти.
Функція додаватиме ці байти до стека в кожному кадрі, доки не досягне свого базового випадку.
Лише тоді вона починає розгортатися у зворотному порядку: кожен рекурсивний виклик використовує стільки `pop`, скільки потрібно, а потім виконує `ret`.

Наприклад, якби `factorial` викликали з аргументом `10`, вона викликала б саму себе девʼять разів, перш ніж досягти базового випадку `1`.
На той момент було б використано `144` байти для збереження `n` (`8` байтів) та адреси повернення (`8` байтів) для кожного попереднього кадру.

## Хвостовий виклик

У деяких ситуаціях функція не виконує більше жодної роботи після виклику іншої функції та перед поверненням.

Розглянемо, наприклад:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

Функція `triple_of_square`:

- множить переданий аргумент (у `rdi`) сам на себе, отримуючи його квадрат;
- потім викликає `times_three`, яка повертає потроєний переданий аргумент.

У результаті `triple_of_square` повертає `3*x²`, де `x` - це її аргумент, переданий у `rdi`.

Зауважимо, що після виклику `times_three` у `triple_of_square` більше нічого не робиться, функція просто повертає керування.
У такій ситуації замість `call` функція може використати `jmp` і передати керування викликаній функції:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

Це називається [хвостовим викликом][tail].

Головна перевага хвостового виклику полягає в уникненні додаткових витрат на `call`.
`call` кладе адресу повернення в стек, і щоб керування повернулося до цієї точки, має бути відповідний `ret`.

Хвостовий виклик пропускає обидва: немає адреси повернення, яку треба класти в стек, і немає зайвого `ret`, з яким його парувати, лише власний `ret` викликаної функції.

## Хвостова рекурсія

Хвостовий виклик особливо корисний для рекурсивних функцій, які можуть викликати самі себе багато разів перед поверненням.

Однак не кожен рекурсивний виклик можна безпосередньо перетворити на хвостовий виклик.
Оскільки `jmp` передає керування викликаній функції, після хвостового виклику той, хто викликає, уже не може виконати жодної роботи.

Наприклад, попередня функція `factorial` **не** є хвостовою рекурсією.
Після рекурсивного виклику їй усе ще потрібно помножити результат на поточне `n` за допомогою `imul rax, rdi`.

У таких ситуаціях іноді можна використати акумулятор, який збиратиме проміжні результати й буде повернений наприкінці.
Наприклад, ми можемо визначити `factorial_helper`, яка виконує більшу частину роботи, а потім `factorial` налаштовує акумулятор і передає керування `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Оскільки після рекурсивного виклику більше нічого не робиться, нам також більше не потрібно зберігати `rdi`.
Немає `call` або `push rdi`, тому кожна рекурсивна ітерація додає `0` байтів до стека: додаткове місце в стеку не використовується.
Ця версія може обробляти як завгодно великі `n`, не переповнюючи стек.
Вона і ефективніша, і безпечніша.

У деяких випадках, змінивши порядок функцій, можна навіть уникнути `jmp` до допоміжної функції.
Наприклад, `factorial` і `triple_of_square` можна переписати так:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

У наведеному фрагменті виконання `factorial` переходить до `factorial_helper`.
Те саме відбувається з `triple_of_square` і `times_three`.
В обох випадках виконання продовжується послідовно, і здається, що хвостова функція - це просто локальна мітка всередині «головної» функції.

Насправді немає жодної принципової різниці між будь-якою локальною міткою та функцією.
Асемблер x86-64 не надає жодній з них особливого статусу, це просто адреси в секції з виконуваним кодом, як-от `section .text`.

Таким чином, функцію з хвостовою рекурсією можна вважати по суті тим самим, що й цикл, де рекурсивний виклик повертається на початок, а базовий випадок - це умова, яка завершує цикл.

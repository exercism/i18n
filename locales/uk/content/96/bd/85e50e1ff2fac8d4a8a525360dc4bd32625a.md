# Вступ

В ідеальному світі ми могли б покладатися на те, що все гарно визначено, має конкретні значення і жодних прогалин.

Це суперечить нашому повсякденному досвіду, тому багато мов програмування мають спосіб позначити відсутність значення: null або NULL, nil, None, nothing...

Це було легко запровадити (ще 1965 року), але невдовзі це призвело до жалю.
Згодом винахідник назвав це своєю «помилкою на мільярд доларів».

Останніми десятиліттями творці мов досліджували багато способів зробити null доступним, але (переважно) безпечним.

Kotlin має кілька [загальних принципів][ref-null-safety], які суттєво відрізняються від Java.


- Kotlin має спеціальне значення `null`.
- Усі типи _типово_ не допускають `null`.
- Більшість типів можна _зробити_ такими, що допускають `null`, але програміст має вказати це явно.
- Функції, які можуть завершитися помилкою у вигляді винятку, зазвичай мають варіант із поверненим значенням, що допускає `null`.
- Спеціальний, дуже стислий синтаксис покликаний зробити перевірку null і реагування на нього якомога простішими.

## Створення змінних, що допускають null

Стандартні типи зазвичай мають відповідник, що допускає `null`, із суфіксом `?`: наприклад, `String?` замість `String`.

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Корисні оператори та функції

### Оператор безпечного виклику `?.`

Для `String`, що не допускає `null`, ми можемо отримати властивість `.length`.

Для `String?`, що допускає `null`, той самий синтаксис спричинить помилку, але застосування `?.length` враховує можливість `null`.
Тип поверненого значення - `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Як ми бачили в останньому рядку вище, `?.` також працює з типами, що не допускають `null`.

### Оператор Елвіса `?:`

Розвиваючи ідею оператора безпечного виклику, [оператор Елвіса][wiki-elvis] дає змогу підставити типове значення замість `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### Оператор ствердження «не null» `!!`

Цей оператор змушує трактувати тип, що допускає `null`, як такий, що не допускає `null`, коли програміст у цьому впевнений.
Можливо, часом ми розуміємо логіку програми краще за надмірно обережний компілятор?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Тепер відповідальність на нас: якщо `b` усе ще `null`, ми отримаємо `NullPointerException`.

### Функція `let` (`?.let`)

Передаючи елемент, що допускає `null`, у блок коду, ми могли б зробити окремі перевірки на `null`: `if (item != null) { do something }`.

Простіше й ідіоматичніше використати `item?.let { do something }`.
`do something` виконається лише тоді, коли `item` не `null`.

### Функції типу `somethingOrNone()`

Деякі функції можуть зазнати невдачі, наприклад, коли ми звертаємося за недійсним індексом у рядку тексту (англ. string) чи масиві.

Замість того щоб кидати виняток, ми могли б скористатися варіантом функції `...OrNull`, щоб отримати (у цьому випадку) повернене значення типу `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

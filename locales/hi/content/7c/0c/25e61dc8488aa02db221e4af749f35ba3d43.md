# परिचय

## एरर में संदर्भ जोड़ना

हमने Go में बुनियादी एरर हैंडलिंग [एरर कॉन्सेप्ट][concept-errors] में देखी थी। जैसा कि आपने वहाँ सीखा, डिफ़ॉल्ट रूप से एरर अपने साथ स्टैक ट्रेस नहीं रखती। इसलिए यह ज़रूरी हो जाता है कि एरर में ही इतनी जानकारी हो कि समस्या की पहचान हो सके।

अगर हम अपने मौजूदा ज्ञान से किसी मौजूदा एरर में जानकारी जोड़ना चाहें, तो हम मूल एरर के टेक्स्ट और अतिरिक्त जानकारी को मिलाकर एक नई एरर बनाने के लिए कुछ ऐसा लिख सकते हैं:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

अच्छी बात है कि मानक लाइब्रेरी के `fmt` पैकेज में इसका एक छोटा रूप `Errorf` फंक्शन के रूप में मौजूद है। इससे आप आसानी से यह जानकारी जोड़ सकते हैं कि एरर किस संदर्भ में हुई थी।

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

अक्सर एरर में जानकारी जोड़ने का यह तरीका काफी होता है, लेकिन कुछ मामलों में आप चाहते हैं कि आपकी एरर का उपयोग करने वाला कोड मूल एरर को जाँच सके या निकाल सके। इस तरह संदर्भ जोड़ने को Go में "एरर रैप करना" कहा जाता है।

## एरर रैप करना और सेंटिनल एरर जाँचना

एरर रैपिंग के लिए ऊपर देखे गए कोड में बहुत छोटा-सा बदलाव काफी है। किसी एरर को रैप करने के लिए, आपको `%v` की जगह `%w` फॉर्मेटिंग वर्ब इस्तेमाल करना होगा। पर्दे के पीछे यह सुनिश्चित करता है कि बनने वाली एरर एक `Unwrap` मेथड लागू करती है, जो मूल एरर लौटाती है। इसी वजह से `errors.Is` से यह जाँचा जा सकता है कि कोई खास सेंटिनल एरर "एरर चेन" में कहीं मौजूद है या नहीं। यह ऐसा चुपचाप `Unwrap` को बार-बार कॉल करके करता है, जब तक कि वह एरर मिल न जाए या चेन खत्म न हो जाए।

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

अच्छा अभ्यास यह है कि डिफ़ॉल्ट रूप से `%v` इस्तेमाल करें और `%w` सिर्फ तभी इस्तेमाल करें जब आप साफ़ तौर पर चाहते हों कि आपकी एरर का उपयोग करने वाला कोड अंतर्निहित एरर तक पहुँच सके ([Google Go Styleguide][google-go-styleguide])।

अगर आप ऐसी स्थिति में हों जहाँ आप किसी सेंटिनल एरर को जाँचना चाहते हैं, पर साफ़ तौर पर उसे अनरैप नहीं करना चाहते, तो `errors.Is` की जगह `==` इस्तेमाल कर सकते हैं।

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

डिफ़ॉल्ट रूप से `errors.Is` के साथ काम करना ठीक है, पर आपको हमेशा ध्यान रखना चाहिए कि इसका मतलब है पूरी एरर चेन खोजी जाएगी।

## (कस्टम) एरर टाइप की जाँच

`errors.Is` जैसा ही एक और फंक्शन है, जिससे एरर चेन में से किसी खास टाइप की एरर जाँची और निकाली जा सकती है। इसके लिए फंक्शन है `errors.As`, और `errors.Is` की तरह यह भी पूरी चेन में दिए गए एरर टाइप को खोजता है। `errors.As` तभी उस एरर को निकालता है जो टाइप से मेल खाती है, ताकि आप उसके साथ आगे काम कर सकें, जैसे कोई खास फील्ड निकालना।

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
ऊपर पॉइंटर से जुड़े सिंटैक्स में सावधान रहें। कोड तभी सही ढंग से काम करेगा और कंपाइल होगा जब `customError` का टाइप ठीक वही हो जो एरर इंटरफेस लागू करता है। हमारे मामले में वह `*MyCustomError` है (`MyCustomError` को [पॉइंटर][concept-pointers]), न कि खुद `MyCustomError`।

इसके अलावा, दूसरा आर्गुमेंट एरर वेरिएबल का पॉइंटर होना चाहिए। चूँकि हमारी एरर पहले से ही एक पॉइंटर है, तो `errors.As` को हम जो दे रहे हैं वह एक पॉइंटर का पॉइंटर है (MyCustomError का)। सिर्फ ऐसा सही ढंग से सेट होने पर ही Go उस वेरिएबल में मिली हुई एरर भर सकता है।
~~~~

पहले की तरह, अगर `Errorf` कॉल करते समय `%v` इस्तेमाल किया गया होता, तो `errors.As` एरर टाइप नहीं ढूँढ पाता।

अगर आप किसी वजह से अनरैप नहीं करना चाहते, तो इसकी जगह टाइप असर्शन इस्तेमाल किया जा सकता है (ऊपर के `==` के बराबर)।

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

अगर एरर रैप की गई होती, तो टाइप असर्शन एरर टाइप नहीं पहचान पाता।

## कस्टम टाइप की एरर को अनरैप करने देना

कभी-कभी किसी एरर को थोड़े अतिरिक्त टेक्स्ट के साथ सिर्फ रैप करना काफी नहीं होता। इसके बजाय आप एक कस्टम एरर टाइप बना सकते हैं, जिसमें मूल एरर और वह अतिरिक्त स्ट्रक्चर्ड डेटा रहता है जो आप जोड़ना चाहते हैं। अगर आप अपने एरर टाइप के लिए अनरैपिंग देना चाहते हैं, तो आपको बस एक `Unwrap() error` मेथड खुद जोड़ना होता है, जिससे `Unwrap` इंटरफेस पूरा हो जाए।

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

# परिचय

आम तौर पर ऑपरेटिंग सिस्टम (OS) किसी प्रोग्राम के लिए मेमोरी को एक सामान्य लेआउट में मैप करता है:

| पता  | मेमोरी क्षेत्र            |
| :-----: | :--------------------- |
|  उच्च   | स्टैक                  |
|         | ...                    |
|         | हीप                    |
|         | पढ़ने-लिखने वाला सेगमेंट |
|         | कोड/केवल पढ़ने योग्य सेगमेंट |
|   निम्न   | आरक्षित                |

सेगमेंट में बँटी मेमोरी सेक्शन में व्यवस्थित होती है, और हर सेक्शन की अनुमतियाँ अलग-अलग होती हैं।

अब तक हमने जो फंक्शन बनाए हैं, वे सब **section .text** में थे।
इस सेक्शन में केवल पढ़ने योग्य, एक्ज़ीक्यूटेबल डेटा रहता है।
दूसरे सेक्शन डेटा वेरिएबल घोषित करने के लिए इस्तेमाल होते हैं। ये वेरिएबल केवल पढ़ने योग्य या पढ़ने-लिखने वाले हो सकते हैं, लेकिन एक्ज़ीक्यूटेबल नहीं होते।

## सेक्शन .data

इनिशियलाइज़ किया गया डेटा **section .data** में घोषित किया जाता है।

NASM (The Netwide Assembler, यानी इस ट्रैक में इस्तेमाल होने वाला असेंबलर) में एक इनिशियलाइज़ किए गए वेरिएबल का एक नाम होता है, एक डायरेक्टिव होता है जो डेटा का साइज़ बताता है, और कॉमा से अलग की गई वैल्यू की एक सूची होती है।
इनमें से हर चीज़ को एक स्पेस से अलग किया जाता है, और लेबल के बाद चाहें तो `:` भी लगाया जा सकता है।

मुख्य डायरेक्टिव और उनसे जुड़े डेटा साइज़ ये हैं:

| डायरेक्टिव | साइज़    |
| :-------: | :------ |
|    db     | 1 बाइट  |
|    dw     | 2 बाइट |
|    dd     | 4 बाइट |
|    dq     | 8 बाइट |

उदाहरण के लिए, यह `space` नाम का एक बाइट वेरिएबल `10` वैल्यू के साथ घोषित करता है:

```x86asm
section .data
    space db 10
```

`section .data` में घोषित वेरिएबल बदले जा सकते हैं, यानी वे पढ़ने-लिखने वाले होते हैं।
इनकी स्टोरेज अवधि भी _स्थिर_ होती है, यानी ये पूरे प्रोग्राम के चलने के दौरान मौजूद रहते हैं।

## सेक्शन .rodata

**section .rodata** `section .data` जैसा ही है।
दोनों सेक्शन में इनिशियलाइज़ किया गया डेटा रहता है, जो एक ही तरीके से घोषित किया जाता है और जिसकी स्टोरेज अवधि भी एक जैसी होती है।

इनमें मुख्य अंतर यह है कि `section .rodata` का डेटा बदला नहीं जा सकता, यानी वह केवल पढ़ने योग्य होता है।

~~~~exercism/note
`equ` से बनाए गए स्थिरांक `section .rodata` में बनाए गए स्थिरांकों से अलग होते हैं।

`equ` से बनाया गया स्थिरांक मेमोरी में जगह नहीं घेरता और असेंबलर उसकी जगह सीधे उसकी वैल्यू रख देता है।
वह वास्तव में उस वैल्यू के लिए एक प्लेसहोल्डर होता है।

दूसरी ओर, `section .rodata` में बनाए गए स्थिरांक वास्तव में मेमोरी में संग्रहीत होते हैं और उनका एक पता होता है।
~~~~

## डेटा तक पहुँचना

### लेबल और इनडायरेक्शन

घोषित डेटा के साथ एक नाम जुड़ा होना चाहिए।
इस नाम को **लेबल** कहते हैं।

लेबल एक सिंबल होता है जो मेमोरी में डेटा के उस खास पते को दर्शाता है।
**x86-64 में पते 64-बिट वैल्यू होते हैं**।

NASM में किसी डेटा तक उसके लेबल से सीधे पहुँचने की कोशिश करने पर आवंटित मेमोरी नहीं मिलती, बल्कि उसका पता मिलता है:

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

किसी मेमोरी पते की सामग्री तक पहुँचने के लिए उसे _डीरेफरेंस_ करना पड़ता है।
इसे **इनडायरेक्शन** कहते हैं।

NASM में यह `[]` से किया जाता है:

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

लेकिन कुछ स्थितियों में यह साफ नहीं होता कि डीरेफरेंस की गई मेमोरी का साइज़ क्या है।
ऐसी स्थितियों में साइज़ बताने वाला एक प्रीफिक्स लगाना ज़रूरी होता है।

एक आम x86-64 प्रोग्राम में सबसे ज़रूरी प्रीफिक्स और उनके साइज़ ये हैं:

| प्रीफिक्स | साइज़    |
| :----- | :------ |
| byte   | 1 बाइट  |
| word   | 2 बाइट |
| dword  | 4 बाइट |
| qword  | 8 बाइट |

वही लोड साइज़ साफ-साफ लिखकर भी किया जा सकता है:

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

मेमोरी डीरेफरेंस करते समय हमेशा प्रीफिक्स लगाना अच्छा तरीका है।

### मेमोरी में लिखना

मेमोरी में लिखना भी उसी तरह होता है, पते को डीरेफरेंस करके:

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

ध्यान दीजिए कि ज़्यादातर निर्देशों में आप मेमोरी ऑपरेंड सीधे इस्तेमाल कर सकते हैं, पहले उनकी सामग्री किसी रजिस्टर में लोड करने की ज़रूरत नहीं होती।
लेकिन आम तौर पर इन्हें सोर्स और डेस्टिनेशन, दोनों ऑपरेंड में इस्तेमाल नहीं किया जा सकता; दोनों में से किसी एक में ही किया जा सकता है:

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### LEA निर्देश

किसी वेरिएबल का पता रजिस्टर में रखने के लिए `mov` का इस्तेमाल किया जा सकता है, लेकिन इसी खास काम के लिए एक निर्देश भी है: **lea**।

यह निर्देश मेमोरी-फॉर्म वाला ऑपरेंड लेता है, लेकिन मेमोरी को पढ़ता _नहीं_ है।
इसके बजाय यह प्रभावी पता वाले एक्सप्रेशन की गणना करता है और नतीजा डेस्टिनेशन ऑपरेंड में लिख देता है:

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

मेमोरी के पते निकालकर रजिस्टर में रखने के लिए `lea` का इस्तेमाल करना ज़्यादा सही तरीका माना जाता है।

### सापेक्ष एड्रेसिंग

मेमोरी लोकेशन तक पहुँचते समय NASM का डिफॉल्ट व्यवहार **निरपेक्ष पते**, यानी स्थिर मेमोरी पते बनाना है।

सुरक्षा कारणों से एक्ज़ीक्यूटेबल अक्सर **PIE (Position Independent Executable)** के रूप में बनाए जाते हैं, जिसमें मेमोरी क्षेत्र बेतरतीब जगहों पर रखे जाते हैं।
`PIE` में किसी वेरिएबल का अंतिम पता लिंक के समय पता नहीं होता।
इसलिए कोड पतों की गणना `rip` नाम के एक खास रजिस्टर की वैल्यू से ऑफसेट के रूप में करता है। यह रजिस्टर उस अगले निर्देश की ओर इशारा करता है जो चलाया जाना है।

इसे आम तौर पर **RIP-सापेक्ष एड्रेसिंग** कहते हैं।

NASM में आप `rel` ऑपरेटर से RIP-सापेक्ष एक्सेस माँग सकते हैं:

```x86asm
mov rax, qword [rel variable]
```

किसी सोर्स फाइल में ऊपर `default rel` लिखकर सापेक्ष एड्रेसिंग को डिफॉल्ट भी बनाया जा सकता है।

इस ट्रैक के सारे अभ्यास `PIE` के रूप में कंपाइल और लिंक किए जाते हैं, इसलिए सापेक्ष पते बनाने के लिए `rel` का इस्तेमाल करना चाहिए।

### दृश्यता

किसी भी सेक्शन (जैसे `.text`, `.data`, `.rodata`) में बनाए गए लेबल (फंक्शन और डेटा) उसी सोर्स फाइल के अंदर दिखाई देते हैं।
अगर उन्हें `global` घोषित किया जाए, तो वे दूसरी सोर्स फाइलों को भी दिखाई देते हैं।

इसके उलट, दूसरी सोर्स फाइलों में बनाए गए लेबल मौजूदा सोर्स फाइल को तभी दिखाई देते हैं जब उन्हें `extern` घोषित किया गया हो।
ऐसी स्थिति में असेंबली में डेटा का साइज़ नहीं बताया जाता, यह पहले से पता होना चाहिए।

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

# शेल की बुनियादी बातों का परिचय

## शेल

एक _शेल_ एक प्रोग्राम है जिसकी मदद से आप ऑपरेटिंग सिस्टम से बातचीत करने के लिए कमांड लिख सकते हैं।
शेल ग्राफिकल भी हो सकते हैं; आप जो डेस्कटॉप वातावरण माउस या ट्रैकपैड से चलाते हैं, वह भी एक शेल ही है।
हम कमांड-लाइन इंटरफेस पर ध्यान देंगे, जहाँ आप कमांड लिखते हैं और उनके नतीजे (आमतौर पर) आपके टर्मिनल में छपते हैं।

कमांड-लाइन शेल कई तरह के होते हैं।
Windows में **cmd** और **powershell** उपलब्ध हैं।
Mac और Linux में "यूनिक्स शेल" मिलते हैं, जो कई तरह के हैं।
Mac का डिफॉल्ट शेल **zsh** है।
**csh** एक पुराना शेल है जिसका सिंटैक्स C जैसा है।
**bash** सबसे लोकप्रिय शेल में से एक है, खासकर Linux पर।

सबसे शुरुआती शेल में से एक था Bourne शेल, यानी **sh**।
समय के साथ यह शेल [मानकीकृत][posix] हो गया, ताकि हर यूनिक्स जैसे सिस्टम पर यह उपलब्ध हो।
कई शेल Bourne शेल पर आधारित हैं, और अक्सर इंटरैक्टिव या प्रोग्रामिंग की अतिरिक्त सुविधाएँ देते हैं।

**Bash** भी Bourne शेल पर आधारित है।
इसीलिए इसे "**B**ourne-**a**gain **sh**ell" कहा जाता है।
यह कई Linux सिस्टमों का डिफॉल्ट शेल है।
Bash में कई सुविधाएँ हैं जो इसे एक मज़ेदार इंटरैक्टिव शेल बनाती हैं, जैसे:

* पूरी तरह से अनुकूलन योग्य प्रॉम्प्ट,
* हिस्ट्री से कमांड वापस लाकर उन्हें बदलने की सुविधा,
* चल रहे प्रोसेस को संभालने की सुविधा,
* एलियस, जिनसे टाइपिंग कम हो जाती है,
* और भी बहुत कुछ।

इस ट्रैक का उद्देश्य यह सिखाना नहीं है कि bash को एक इंटरैक्टिव शेल की तरह कैसे इस्तेमाल किया जाए।
इसका उद्देश्य bash से प्रोग्राम लिखना सीखना है।
जोर इस बात पर रहेगा कि समस्याएँ सुलझाने के लिए _सिर्फ_ bash इस्तेमाल कीजिए, हालाँकि बाहरी टूल को कॉल करने पर कोई रोक नहीं है।

## Bash की बुनियादी बातें: कमांड और आर्गुमेंट

Bash अपने इनपुट से कमांड पढ़ता है (जो आमतौर पर या तो टर्मिनल होता है या कोई फाइल)।
इनपुट की जो भी लाइन वह पढ़ता है, उसे एक _कमांड_ माना जाता है, यानी पूरा करने का एक निर्देश।
(कुछ एडवांस्ड मामले भी हैं, जैसे कई लाइनों में फैली कमांड, जिन पर आगे चर्चा करेंगे।)

Bash हर लाइन को **शब्दों** में बाँटता है, जिनके बीच व्हाइटस्पेस अक्षर (स्पेस और टैब) होते हैं।
लाइन का पहला शब्द उस _कमांड_ का नाम होता है जिसे चलाना है।
बाकी सारे शब्द उस कमांड के _आर्गुमेंट_ बन जाते हैं (ऑप्शन, फाइलनाम आदि)।

~~~~exercism/note
नीचे दिए उदाहरणों में हम आपको कुछ इंटरैक्टिव कमांड दिखाएँगे जिन्हें आप चला सकते हैं।

* `#` अक्षर एक _कमेंट_ शुरू करता है।
  कमेंट के बाद लिखे सारे शब्द शेल अनदेखा कर देता है; कमेंट सिर्फ पढ़ने के लिए होता है।
* `$` अक्षर शेल प्रॉम्प्ट दर्शाता है।
  अगर आप कमांड कॉपी कर रहे हैं, तो प्रॉम्प्ट शामिल न करें।
~~~~

```bash
# Note: It is always a good idea to run `ls` before `rm`
# to make sure you know what you are deleting.

$ rm *            # Remove all files in the current directory.
                  # Make sure you run this in a temp directory or you can lose files!
$ ls              # List files in the current directory (no output, no files).
$ touch a   b c   # Create files 'a', 'b' and 'c'.
$ ls              # List files again; this time the outputs: 'a', 'b' and 'c'.
a  b  c
```

`rm` एक ऐप्लिकेशन है जो उसे दी गई फाइलों को हटा देता है।
`*` एक [ग्लोब][glob] अक्षर है, एक "वाइल्डकार्ड" पैटर्न जो मौजूदा डायरेक्टरी की सारी फाइलों से मेल खाता है।
ग्लोब के बारे में हम आगे और बात करेंगे।

क्या आपने ध्यान दिया कि `a` और `b` के बीच कई स्पेस हैं, जबकि `b` और `c` के बीच सिर्फ एक?
आर्गुमेंट के बीच कितना व्हाइटस्पेस है, इससे कोई फर्क नहीं पड़ता!
उदाहरण के लिए:

```bash
$ echo This is a test.
This is a test.
$ echo This    is    a    test.
This is a test.
```

`echo` एक कमांड है जो अपने आर्गुमेंट स्टैंडर्ड आउटपुट पर छापता है (हमारे मामले में यह टर्मिनल है)।
Bash कमांड को पाँच शब्दों में बाँटता है और `echo` कमांड को चार आर्गुमेंट के साथ कॉल करता है।
दूसरे उदाहरण में अतिरिक्त स्पेस से कोई फर्क नहीं पड़ता।
`echo` को पता नहीं होता कि शब्दों के बीच पहले कैसे स्पेस थे।

अगर हम अतिरिक्त व्हाइटस्पेस बनाए रखना चाहते हैं, तो पूरे वाक्य को एक ही आर्गुमेंट की तरह भेजना होगा।
हम यह [कोट][Quotes] लगाकर कर सकते हैं:

```bash
$ echo "This    is    a    test."
This    is    a    test.
```

कोट अपने अंदर की हर चीज़ को एक _ही आर्गुमेंट_ में बदल देते हैं।
आर्गुमेंट `This    is    a    test.` है, जिसमें वे खास स्पेस अक्षर भी शामिल हैं।
ध्यान दीजिए कि कोट आर्गुमेंट का हिस्सा नहीं होते। bash उस एक आर्गुमेंट को `echo` तक पहुँचाने से पहले कोट हटा देता है।

आर्गुमेंट को कमांड के नाम से और एक-दूसरे से व्हाइटस्पेस अलग करता है।
यह याद रखना ज़रूरी है।
उदाहरण के लिए, नीचे दिया गया गलत है:

```bash
$ [-f file]
bash: [-f: command not found
```

इसका उद्देश्य यह जाँचना है कि `file` नाम की कोई फाइल मौजूद है या नहीं।
यह मानना वाजिब लगता है कि `[` और `]` के आसपास का व्हाइटस्पेस मायने नहीं रखता, लेकिन असल में `[` एक कमांड है और उसका अंतिम आर्गुमेंट `]` होना चाहिए।
(हम `[` कमांड पर आगे और विस्तार से बात करेंगे।)
इसलिए हमें `[` को `-f` से और `]` को `file` से अलग रखना होगा।
वरना bash समझेगा कि हम `[-f` नाम की कोई कमांड चलाने की कोशिश कर रहे हैं जिसका एक ही आर्गुमेंट `file]` है।
सही कमांड सारे आर्गुमेंट को व्हाइटस्पेस से अलग करती है:

```bash
$ [ -f file ]
```

(हमने बहुत से लोगों को इस व्यवहार से उलझते देखा है; उन्हें लगता है कि `[...]` "सिर्फ सिंटैक्स" है और वे स्पेस छोड़ सकते हैं; जबकि `[` एक कमांड है और व्हाइटस्पेस ज़रूरी है।)

अगर किसी फाइलनाम में व्हाइटस्पेस या कोई और विशेष अक्षर हो, तो उसे भी कोट में रखना चाहिए:

```bash
$ [ -f "my file" ]
```

## कमांड के प्रकार

Bash कई तरह की कमांड समझता है: एलियस, फंक्शन, बिल्टइन, कीवर्ड और एक्ज़ीक्यूटेबल।
ये सब _कमांड_ हैं और सब लगभग एक जैसे ही काम करते हैं।

डिफॉल्ट रूप से एलियस सिर्फ इंटरैक्टिव शेल में चालू रहते हैं, शेल स्क्रिप्ट में नहीं।
हम यहाँ इन पर बात नहीं करेंगे।

### फंक्शन

एक फंक्शन में शेल कमांड होती हैं और यह किसी छोटी स्क्रिप्ट की तरह काम करता है; यह आर्गुमेंट तक ले सकता है और लोकल वेरिएबल बना सकता है।
जब किसी फंक्शन को कॉल किया जाता है, तो उसके अंदर की कमांड चलती हैं।
फंक्शन पर हम आगे विस्तार से बात करेंगे।

### बिल्टइन

Bash में कुछ बुनियादी कमांड पहले से बने होते हैं, जैसे `cd` (डायरेक्टरी बदलना), `echo` (आउटपुट लिखना) वगैरह।
इन्हें ऐसे फंक्शन मान सकते हैं जो पहले से दिए गए हैं।

### कीवर्ड

कीवर्ड बिल्टइन जैसे ही होते हैं, बस फर्क यह है कि कीवर्ड असल में bash का सिंटैक्स हैं और इन्हें खास नियमों से पढ़ा जा सकता है।
उदाहरण के लिए, `[` एक bash बिल्टइन है, जबकि `[[` एक bash कीवर्ड है; दोनों का इस्तेमाल कई तरह की शर्तें जाँचने के लिए होता है।
लेकिन `[[` कीवर्ड में कुछ अतिरिक्त सुविधाएँ हैं।
उदाहरण के लिए, यह `=~` ऑपरेटर देता है, जो रेगुलर एक्सप्रेशन जाँचता है।

```bash
$ [[ "hello world" =~ e.*o ]]   # returns a "success" status
$ [ "hello world" =~ e.*o ]
bash: [: =~: binary operator expected
```

स्ट्रिंग तुलना के ऑपरेटर `<` और `>` इस बात का दूसरा उदाहरण हैं कि कीवर्ड कोड को कैसे अलग तरीके से पढ़ते हैं।
`[[...]]` के अंदर इन ऑपरेटरों में किसी खास सावधानी की ज़रूरत नहीं होती।

```bash
$ if [[ "$USER" < "n" ]]; then
    echo "$USER is in the first half of the alphabet"
fi
# => glennj is in the first half of the alphabet
```

लेकिन `[...]` के अंदर आपको इन्हें कोट या एस्केप करना होगा, ताकि शेल इन्हें रीडायरेक्शन ऑपरेटर की तरह न पढ़े।

```bash
$ if [ "$USER" < "n" ]; then
    echo "$USER is in the first half of the alphabet"
fi
# => bash: n: No such file or directory

$ if [ "$USER" \< "n" ]; then
    echo "$USER is in the first half of the alphabet"
fi
# => glennj is in the first half of the alphabet
```


### एक्ज़ीक्यूटेबल

bash जिस अंतिम तरह की कमांड चला सकता है, वह _एक्ज़ीक्यूटेबल_ है।
ये आपके कंप्यूटर के फाइलसिस्टम पर मौजूद एक्ज़ीक्यूटेबल फाइलें (प्रोग्राम) हैं जिन्हें आप चला सकते हैं।
(एक्ज़ीक्यूटेबल को _बाहरी कमांड_ या _ऐप्लिकेशन_ भी कहा जाता है।)
एक्ज़ीक्यूटेबल को आमतौर पर सिर्फ उसका नाम टाइप करके चलाया जाता है; फाइल का पूरा पाथ आमतौर पर ज़रूरी नहीं होता।
ऐसा इसलिए हो पाता है क्योंकि bash एक पहले से तय वेरिएबल का इस्तेमाल करता है, जो उसे आम एक्ज़ीक्यूटेबल फाइलों की जगह ढूँढने में मदद करता है।
इस वेरिएबल का नाम `PATH` है।
यह डायरेक्टरी नामों का एक समूह है जिन्हें कोलन अलग करते हैं (जैसे `/usr/bin:/bin`)।
जब कोई कमांड किसी फाइल पाथ के बिना दी जाती है (जैसे `myprogram` या `ls`), और वह एलियस, फंक्शन, बिल्टइन या कीवर्ड नहीं है, तो bash `PATH` की सारी डायरेक्टरियों में ढूँढता है।
डायरेक्टरियों को बाएँ से दाएँ क्रम में देखा जाता है, ताकि पता चले कि किसी में दिए गए नाम का एक्ज़ीक्यूटेबल है या नहीं।

अगर एक्ज़ीक्यूटेबल किसी जाने-पहचाने पाथ के बाहर है, तो उसका फाइल पाथ बताना पड़ेगा।
मौजूदा डायरेक्टरी में मौजूद `myprogram` एक्ज़ीक्यूटेबल के लिए `./myprogram` लिखें; अगर यह `/opt/somedirectory` डायरेक्टरी में है, तो `/opt/somedirectory/myprogram` लिखें।

सुझाव: किसी कमांड के बारे में जानकारी पाने के लिए `type` कमांड इस्तेमाल की जा सकती है:

```bash
$ type rm
rm is hashed (/bin/rm)
# or it might return: `rm is /bin/rm`

$ type cd
cd is a shell builtin
```

## स्क्रिप्ट

एक _स्क्रिप्ट_ किसी फाइल में संग्रहीत कमांड का एक क्रम है।
Bash उस फाइल को पढ़ता है और कमांड को क्रम से चलाता है।
वह अगली कमांड पर तभी बढ़ता है जब मौजूदा कमांड पूरी हो चुकी हो।
अपवाद यह है कि अगर कोई कमांड असिंक्रोनस रूप से (बैकग्राउंड में) चलाने के लिए कही गई हो।
इस मामले की अभी ज़्यादा चिंता न करें; यह कैसे काम करता है, यह हम आगे सीखेंगे।

इस गाइड में दिया कोई भी कमांड लाइन उदाहरण स्क्रिप्ट में भी इस्तेमाल किया जा सकता है।

स्क्रिप्ट बनाना आसान है।
एक नई फाइल बनाकर शुरू कीजिए और उसकी पहली लाइन में यह लिखिए:

```bash
#!/bin/bash
```

इस लाइन को _इंटरप्रेटर डायरेक्टिव_ कहा जाता है (इसे _हैशबैंग_ या **_शीबैंग_** भी कहते हैं)।
यह बताती है कि जब इस फाइल को किसी कमांड में एक्ज़ीक्यूटेबल की तरह इस्तेमाल किया जाए, तो इंटरप्रेटर के रूप में `/bin/bash` इस्तेमाल हो।
जब OS का कर्नेल किसी _नॉन-बाइनरी फाइल_ को चलाता है, तो वह फाइल की पहली लाइन पढ़ता है।
अगर लाइन `#!` से शुरू होती है, तो कर्नेल उस लाइन से तय करता है कि फाइल किस इंटरप्रेटर को सौंपी जाए।
(ऐसा करने के और भी वैध तरीके हैं, नीचे देखिए।)
`#!` फाइल की बिल्कुल शुरुआत में होना चाहिए, उससे पहले कोई स्पेस या खाली लाइन नहीं।
हमारी स्क्रिप्ट की कमांड इसके नीचे अलग-अलग लाइनों में आएँगी।

सुझाव: `#!/bin/bash` की जगह आप यह इस्तेमाल कर सकते हैं

```bash
#!/usr/bin/env bash
```

`env` अपने पहले आर्गुमेंट में दिए नाम के एक्ज़ीक्यूटेबल को `$PATH` में ढूँढता है (यहाँ "bash")।
इस तकनीक की और यह सादे `#!/bin/bash` से कैसे अलग है, इसकी विस्तृत जानकारी के लिए [StackOverflow पर यह सवाल][env bash] देखिए।

इंटरनेट पर मौजूद उन स्क्रिप्ट या उदाहरणों से धोखा न खाइए जो इंटरप्रेटर के रूप में `/bin/sh` इस्तेमाल करते हैं।
**`sh` और `bash` एक नहीं हैं!**
Bash खुद एक "sh-संगत" शेल है, यानी यह ज़्यादातर `sh` स्क्रिप्ट चला सकता है और इसका बहुत सारा सिंटैक्स एक जैसा है।
लेकिन इसका उल्टा सच नहीं है; bash की कुछ सुविधाएँ `sh` में टूट जाएँगी या अप्रत्याशित व्यवहार करेंगी।
वास्तव में, कोई एक `sh` शेल नहीं होता।
ऐसे कई शेल हैं जो POSIX-sh सिंटैक्स का समर्थन करते हैं।
आपके OS के हिसाब से, जब आप `sh` चलाते हैं, तो असल में bash, ash, dash या कोई और शेल चल रहा हो सकता है।

स्क्रिप्ट फाइल बनने के बाद उसे इस तरह चलाया जा सकता है:

```bash
$ bash myscript
```

इस उदाहरण में हम _कमांड_ `bash` चलाते हैं और उसे कहते हैं कि हमारे _आर्गुमेंट_ के रूप में दी गई स्क्रिप्ट पढ़े।
जब हम ऐसा करते हैं, तो `#!` लाइन सिर्फ एक _कमेंट_ रह जाती है।

इसके अलावा, हम अपनी स्क्रिप्ट को चलाने की अनुमति दे सकते हैं।
इस तरीके से हम स्क्रिप्ट को bash को अलग से कॉल किए बिना किसी और एक्ज़ीक्यूटेबल की तरह चला सकते हैं:

```bash
$ chmod +x myscript  # Mark the file as executable.
$ ./myscript         # Now, myscript can be executed directly
                     # instead of having to specify bash.
```

जब हम कमांड को इस तरह चलाते हैं, तो ऑपरेटिंग सिस्टम (OS) `#!` लाइन से तय करता है कि आपकी स्क्रिप्ट चलाने के लिए कौन-सा इंटरप्रेटर इस्तेमाल हो।

# रीडायरेक्शन का परिचय

कमांड लाइन इंटरफेस की दुनिया में प्रोग्राम अक्सर तीन मानक डेटा स्ट्रीम के साथ काम करते हैं:

1. **मानक इनपुट** (`stdin`): जहाँ से प्रोग्राम अपना इनपुट लेता है (आम तौर पर कीबोर्ड से)।
1. **मानक आउटपुट** (`stdout`): जहाँ प्रोग्राम अपना सामान्य आउटपुट भेजता है (आम तौर पर टर्मिनल स्क्रीन पर)।
1. **मानक एरर** (`stderr`): जहाँ प्रोग्राम एरर संदेश भेजता है (आम तौर पर टर्मिनल स्क्रीन पर)।

याद कीजिए, हमने इनका परिचय [पाइपलाइन और कमांड सूचियाँ][pipelines] अध्याय में दिया था।

~~~~exercism/note
पाइपलाइन को रीडायरेक्शन का ही एक रूप माना जा सकता है: एक प्रोग्राम का मानक आउटपुट सीधे दूसरे प्रोग्राम के मानक इनपुट को भेजा जाता है।
पाइपलाइन पर हम पहले ही चर्चा कर चुके हैं।
इस कॉन्सेप्ट में हम देखेंगे कि फाइलों से और फाइलों में रीडायरेक्शन कैसे किया जाता है।
~~~~

शेल रीडायरेक्शन एक शक्तिशाली तरीका है, जिसकी मदद से आप इन स्ट्रीम का गंतव्य बदल सकते हैं।
प्रोग्राम कीबोर्ड से पढ़े या स्क्रीन पर लिखे, इसके बजाय आप फाइल से इनपुट ले सकते हैं या आउटपुट किसी फाइल में भेज सकते हैं।
इससे काफी लचीलापन मिलता है और यह भी तय किया जा सकता है कि प्रोग्राम डेटा के साथ कैसे काम करेंगे।

## मुख्य रीडायरेक्शन ऑपरेटर

यहाँ सबसे आम रीडायरेक्शन ऑपरेटर दिए गए हैं और ये क्या करते हैं:

### `>` (आउटपुट रीडायरेक्शन)

* उद्देश्य: किसी कमांड के मानक आउटपुट (`stdout`) को किसी फाइल में भेजना।
* व्यवहार:
  * अगर फाइल मौजूद नहीं है, तो वह बन जाती है।
  * अगर फाइल मौजूद है, तो उसकी सारी सामग्री मिटाकर उस पर नया लिख दिया जाता है।
* उदाहरण:

  ```bash
  # Sends the output of 'ls -l' to 'file_listing.txt'
  ls -l > file_listing.txt
  ```

~~~~exercism/caution
रीडायरेक्शन कमांड के चलने से **पहले** होता है।
इसका मतलब है कि जिस फाइल से आपको पढ़ना है, उसी फाइल में आप रीडायरेक्ट नहीं कर सकते।

```bash
date > date.txt         # populate the file with the current date
cat date.txt > date.txt # 'date.txt' is now empty!
```

ऊपर के उदाहरण की दूसरी कमांड में,

1. पहले Bash रीडायरेक्शन में लिखी फाइल को छोटा करके खाली कर देता है।
   इससे पहले की सारी सामग्री मिट जाती है और एक खाली फाइल बच जाती है।
2. फिर bash उस अभी खाली हुई फाइल को पढ़ता है।
3. फिर bash उसकी सामग्री (यानी कुछ भी नहीं) वापस उसी फाइल में लिख देता है।
~~~~

### `>>` (आउटपुट जोड़ने वाला रीडायरेक्शन)

* उद्देश्य: किसी कमांड के मानक आउटपुट (`stdout`) को किसी फाइल के अंत में जोड़ना।
* व्यवहार:
  * अगर फाइल मौजूद नहीं है, तो वह बन जाती है।
  * अगर फाइल मौजूद है, तो आउटपुट फाइल के अंत में जुड़ जाता है।
* उदाहरण:

  ```bash
  # Adds "Another line" to the end of the file
  echo "Another line" >> file_listing.txt
  ```

### `<` (इनपुट रीडायरेक्शन)

* उद्देश्य: किसी कमांड का मानक इनपुट (`stdin`) किसी फाइल से लेना।
* व्यवहार: कमांड अपना इनपुट कीबोर्ड के बजाय बताई गई फाइल से पढ़ती है।
* उदाहरण:

  ```bash
  # 'tr' reads from 'lowercase.txt' and
  # output is redirected to 'uppercase.txt'
  tr 'a-z' 'A-Z' < lowercase.txt > uppercase.txt
  ```

### `2>` (एरर रीडायरेक्शन):

* उद्देश्य: किसी कमांड की मानक एरर (`stderr`) को किसी फाइल में भेजना।
* व्यवहार: एरर संदेश टर्मिनल के बजाय बताई गई फाइल में भेजे जाते हैं।
* उदाहरण:
  ```bash
  # Error message from 'rm' is sent to 'error_log.txt'
  rm non_existent_file 2> error_log.txt
  ```

`2>>` की मदद से आप मानक एरर को किसी फाइल के अंत में _जोड़_ सकते हैं।

### कुछ और रीडायरेक्शन

कुछ रीडायरेक्शन ऐसे भी हैं जो `stdin` और `stderr` दोनों को एक साथ मिला देते हैं।
जानकारी के लिए [मैनुअल][manual] देखिए।

## `/dev/null`

`/dev/null` एक खास फाइल है जो

* जब आप इसे पढ़ते हैं, तो एक खाली फाइल होती है, और
* इसमें लिखा गया सारा डेटा फेंक देती है।

इसे कभी-कभी "बिटबकट" भी कहा जाता है।
आउटपुट या एरर छिपाने में यह काम आती है।

```bash
some_command > /dev/null  # Discards stdout
some_command 2> /dev/null # Discards stderr

# Using /dev/null as input will prevent the command
# from reading data from the keyboard
some_command < /dev/null
```

## रीडायरेक्शन को आपस में जोड़ना

एक साथ कई रीडायरेक्शन दिए जा सकते हैं।

```bash
some_command < input.txt > output.txt 2> error.txt
```

एक रीडायरेक्शन की नकल की जा सकती है।

```bash
# send stderr to the same destination as stdout
some_command > output.txt 2>&1
```

जब आप `2>&1` देखें, तो उसे ऐसे पढ़िए: "stderr को वहीं भेजिए जहाँ stdout **इस वक्त** भेज रहा है"।
Bash रीडायरेक्शन के निर्देशों को बाएँ से दाएँ के क्रम में ही चलाता है, यानी आप यह कर सकते हैं:

```bash
# redirect stdout to 'output1.txt'
# redirect stderr to the same place
# then change stdout to 'output2.txt'
some_command > output1.txt 2>&1 > output2.txt
```

## फाइल डिस्क्रिप्टर

शेल प्रोग्रामिंग और Linux/Unix जैसे ऑपरेटिंग सिस्टम में फाइल डिस्क्रिप्टर (FD) एक ऐसा पूर्णांक होता है जो शून्य या उससे बड़ा होता है और किसी खुली फाइल या I/O (इनपुट/आउटपुट) संसाधन की पहचान या हैंडल का काम करता है।
इसे किसी लेबल या संदर्भ संख्या की तरह समझिए, जिसे ऑपरेटिंग सिस्टम खुली फाइलों और डेटा स्ट्रीम का हिसाब रखने के लिए इस्तेमाल करता है।

रीडायरेक्शन में जो संख्याएँ बाईं ओर दिखती हैं, वे फाइल डिस्क्रिप्टर होती हैं।

मानक I/O स्ट्रीम को पहले 3 फाइल डिस्क्रिप्टर दिए जाते हैं:

* मानक इनपुट FD 0 है
* मानक आउटपुट FD 1 है
* मानक एरर FD 2 है

`exec` कमांड और रीडायरेक्शन ऑपरेटरों की मदद से नए फाइल डिस्क्रिप्टर बनाए या सेट किए जा सकते हैं।

```bash
# create FD 3 as a copy of stdout
exec 3>&1
# send stdout to a log file
exec > log.txt

# then redirect both stdout and file descriptor 3
echo "some debug message" >&3  # displayed in the terminal
some_command  2>&1 # stdout and stderr send to 'log.txt'
```

यह तरीका काफी उलझा हुआ लगता है, लेकिन यह उन स्थितियों में बहुत काम आता है जहाँ आपकी स्क्रिप्ट कोई दूसरा सॉफ्टवेयर पैकेज चला रहा हो और वह सॉफ्टवेयर मानक आउटपुट अपने आप पकड़ लेता हो।
इस ट्रैक के यूनिट टेस्ट चलाने के लिए इस्तेमाल होने वाली `bats` कमांड इसी तरह काम करती है: `bats` किसी टेस्ट का stdout और stderr पकड़ लेती है, लेकिन FD 3 पर भेजे गए डीबग संदेश टर्मिनल पर दिखाई देते हैं।
~~~~

## सारांश

रीडायरेक्शन क्यों काम आता है?

* आउटपुट सहेजना: किसी कमांड के परिणाम बाद में देखने या उन पर आगे काम करने के लिए सहेजकर रखना।
* लॉग रखना: डीबगिंग के लिए एरर संदेशों को पकड़कर रखना।
* ऑटोमेशन: कमांडों को एक-दूसरे से जोड़ना, जहाँ एक का आउटपुट दूसरे का इनपुट बन जाता है।
* फिल्टर करना: अनचाहे आउटपुट को हटा देना।
* बैच प्रोसेसिंग: डेटा को हाथ से टाइप करने के बजाय फाइलों से पढ़कर काम करना।
* स्क्रिप्ट लिखना: मज़बूत शेल स्क्रिप्ट लिखने के लिए रीडायरेक्शन ज़रूरी हैं।

शेल रीडायरेक्शन से आप बारीकी से तय कर सकते हैं कि प्रोग्राम डेटा के साथ कैसे काम करें। इससे आप जटिल वर्कफ्लो बना सकते हैं और जानकारी को बेहतर ढंग से संभाल सकते हैं।

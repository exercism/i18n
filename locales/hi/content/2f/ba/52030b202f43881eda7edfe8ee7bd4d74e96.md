# परिचय

## स्ट्रिंग

### अक्षर

**अक्षर एन्कोडिंग** एक ऐसा खास तरीका है जिससे किसी प्राकृतिक भाषा में पाठ के हिस्सों को बाइटों के अनुक्रम के रूप में दर्शाया जाता है।
यहाँ पाठ का "हिस्सा" कोई भी ऐसी इकाई हो सकती है जिसका किसी प्राकृतिक भाषा में महत्व हो, जैसे अक्षर, स्पेस, विराम चिह्न, इमोजी, आइडियोग्राम इत्यादि।

NASM (The Netwide Assembler, यानी इस ट्रैक में इस्तेमाल होने वाला असेंबलर) में **ASCII** का उपयोग करके डेटा परिभाषित करने की सुविधा है।

NASM में अक्षर कॉन्स्टेंट की लंबाई 8 बाइट तक हो सकती है और इन्हें सिंगल कोट (`'`), डबल कोट (`"`) या बैकटिक (`` ` ``) का उपयोग करके घोषित किया जा सकता है:

```x86asm
mov rax, '0' ; this copies the ASCII character '0' (decimal value 48)
mov rcx, "z" ; this copies the ASCII character 'z' (decimal value 122)
mov rdx, ` ` ; this copies the ASCII character ' ' (decimal value 32)
```

खास अक्षरों को बैकटिक में लिखना होता है और `\` से एस्केप करना होता है:

```x86asm
mov rax, `\n` ; this copies the ASCII character newline (decimal value 10)
mov rcx, `\t` ; this copies the ASCII character tab (decimal value 9)
```

ध्यान रखिए कि x86-64 में अलग डेटा टाइप के रूप में किसी भी अक्षर एन्कोडिंग के लिए पहले से कोई सुविधा नहीं है।
असेंबली में डेटा बाइटों का एक अनुक्रम होता है, और उन बाइटों को अक्षर, संख्या या किसी और चीज़ के रूप में समझने का काम प्रोग्रामर पर छोड़ दिया जाता है।

जैसे, ASCII अक्षर '0' एक ही बाइट है जिसकी वैल्यू 48 है।
तो, किसी बाइट में 48 रखना बिल्कुल वैसा ही है जैसे ASCII अक्षर '0' रखना:

```x86asm
mov al, '0' ; al has the value 48
mov cl, 48  ; cl has the value '0'
; al and cl now have the same value
```

इसी वजह से अक्षरों पर काम करने के लिए उन बाइटों की वैल्यू सीधे बदली जाती हैं:

```x86asm
mov al, 'A' ; al now has the value 'A', which is 65 in ASCII
add al, 32 ; al now has the value 97, which is 'a' in ASCII
; so, summing 32 to an uppercase ASCII letter makes it lowercase

mov al, 5 ; al now has the value 5
add al, 48 ; al now has the value 53, which is '5' in ASCII
; so, summing 48 (equivalently, '0') transforms a number between 0 and 9 into an ASCII digit
```

### स्ट्रिंग

**स्ट्रिंग** अक्षरों का एक अनुक्रम होती है।
असेंबली में इसे आम तौर पर एक ऐरे के रूप में बनाया जाता है।

NASM में स्ट्रिंग को उसी तरह घोषित किया जा सकता है जैसे कोई भी ऐरे घोषित किया जाता है:

```x86asm
section .data
    string1 db "h", "e", "l", "l", "o"
```

स्ट्रिंग और दूसरे ऐरे में एक फर्क यह है कि NASM में स्ट्रिंग को वैल्यू अलग करने वाले कॉमा (`,`) के बिना भी घोषित किया जा सकता है।
वैल्यू के बीच कॉमा लगाकर भी लिखा जा सकता है:

```x86asm
section .data
    string2 db "hello"
    string3 db "h", "ello"
```

ध्यान रखिए कि जैसा ऊपर बताया गया, अक्षर सिर्फ बाइट होते हैं (या Unicode एन्कोडिंग में बाइटों का एक अनुक्रम):

```x86asm
section .data
    string1 db "hi"
    string2 db "h", "i"
    string3 db 104, 105
; string1, string2 and string3 are all equivalent
```

चूँकि हर ASCII अक्षर एक बाइट लेता है, इसलिए किसी बड़े साइज़ में उसके बाद की हर बाइट `0` होती है।
जैसे, `'a'` को qword (8 बाइट) के रूप में घोषित करने का मतलब है कि पहली बाइट `'a'` (`97`) है और बाकी सातों बाइट `0` हैं।

इसी वजह से, ये सब बराबर हैं:

```x86asm
section .data
    ; in all of the following, "hello" takes 5 bytes
    string1 dw 'hello'         ; 3 words (2-byte) - 5 bytes for "hello" + 0
    string2 dw 'he', "ll", `o` ; 3 words (2-byte) - 5 bytes for "hello" + 0
    string3 db `hello`, 0      ; 6 bytes - 5 bytes for "hello" + 0
```

~~~~exercism/caution
असेंबली में स्ट्रिंग अपने आप ASCII NUL अक्षर (वैल्यू `0`) से खत्म नहीं होती।

C जैसी उच्च-स्तरीय भाषाओं के साथ काम करते समय यह प्रोग्रामर की जिम्मेदारी है कि वह स्ट्रिंग के अंत में सही टर्मिनेटर लगाए, अगर कोई टर्मिनेटर लगाना ज़रूरी हो।
~~~~

### स्ट्रिंग निर्देश

चूँकि स्ट्रिंग ऐरे होती हैं, आप उनके साथ किसी भी ऐरे की तरह काम कर सकते हैं, यानी मेमोरी को साफ़ तौर पर डीरेफरेंस करके:

```x86asm
section .data
    hello_msg db "hello", 0

section .text
fn:
    lea rdi, [rel hello_msg]
    mov al, byte [rdi]       ; al == 'h'
    mov cl, byte [rdi + 4]   ; cl == 'o'
    ret
```

इसके अलावा, मेमोरी में बाइटों के अनुक्रम में वैल्यू लोड करने, खिसकाने और रखने के लिए कुछ निर्देश होते हैं।
इन्हें _स्ट्रिंग निर्देश_ कहा जाता है, लेकिन इनका उपयोग मेमोरी में बाइटों के किसी भी अनुक्रम के साथ, यानी किसी भी ऐरे के साथ किया जा सकता है।

तीन सबसे ज़रूरी स्ट्रिंग निर्देश हैं `lods`, `stos` और `movs`:

| निर्देश | यह क्या करता है |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| `lods`      | `rsi` से बताए गए मेमोरी लोकेशन से एक वैल्यू `rax` में लोड करता है                                                |
| `stos`      | `rax` से एक वैल्यू को `rdi` से बताए गए मेमोरी लोकेशन में रखता है                                               |
| `movs`      | `rsi` से बताए गए मेमोरी लोकेशन से एक वैल्यू कॉपी करता है और उसे `rdi` से बताए गए मेमोरी लोकेशन में रखता है    |

ध्यान दीजिए कि ये निर्देश कोई स्पष्ट ऑपरेंड _नहीं_ लेते।
इनके ऑपरेंड अंतर्निहित होते हैं।

मोटे तौर पर यह नियम याद रखिए:

1. जब इनका सोर्स ऑपरेंड कोई मेमोरी लोकेशन हो, तो उसका एड्रेस `rsi` में रखा जाना चाहिए (`s` का मतलब source)।
2. जब इनका डेस्टिनेशन ऑपरेंड कोई मेमोरी लोकेशन हो, तो उसका एड्रेस `rdi` में रखा जाना चाहिए (`d` का मतलब destination)।
3. अगर इनमें से कोई एक ऑपरेंड मेमोरी लोकेशन न हो, तो वह `rax` रजिस्टर होता है।

ध्यान दीजिए कि ये निर्देश जो काम करते हैं उसी के हिसाब से मेमोरी एड्रेस को अपने आप डीरेफरेंस कर लेते हैं।

ये सभी अलग-अलग साइज़ में काम कर सकते हैं।
साइज़ बताने के लिए इनके अंत में एक प्रत्यय लगाया जाता है:

| प्रत्यय | मतलब | साइज़    |
| :----: | ------- | :------ |
|  `b`   | बाइट    | 1 बाइट  |
|  `w`   | वर्ड    | 2 बाइट |
|  `d`   | dword   | 4 बाइट |
|  `q`   | qword   | 8 बाइट |

जैसे:

```x86asm
movsb ; copies one byte from the memory location whose address is in `rsi` and stores it into the memory location whose address is in `rdi`
lodsq ; copies one qword (8 bytes) from the memory location whose address is in `rsi` and stores it in `rax`
stosw ; stores one word (2 bytes) from `ax` into the memory location whose address is in `rdi`
```

ये जिन एड्रेसों का उपयोग करते हैं, उन्हें भी ऑपरेशन के साइज़ के हिसाब से अपडेट कर देते हैं।
यह अपडेट **डायरेक्शन फ्लैग (DF)** की वैल्यू के अनुसार होता है:

- अगर `DF` क्लियर है, तो एड्रेस ऑपरेशन के साइज़ के हिसाब से _बढ़_ जाते हैं।
- अगर `DF` सेट है, तो एड्रेस उतने ही के हिसाब से _घट_ जाते हैं।

System V ABI कहता है कि फंक्शन में प्रवेश करते समय डायरेक्शन फ्लैग क्लियर होना चाहिए।
इसलिए, _डिफ़ॉल्ट व्यवहार यह है कि मेमोरी एड्रेसों के बढ़ते क्रम में पढ़ी/लिखी जाती है_।

`cld` निर्देश का उपयोग डायरेक्शन फ्लैग क्लियर करने के लिए किया जा सकता है, जबकि `std` निर्देश का उपयोग उसे सेट करने के लिए किया जाता है:

```x86asm
lea r8, [rdi]
lea r9, [rsi]

movsq ; both rdi and rsi increase (because `DF` is cleared by default) by 8 (`q` for qword)
; so now:
; rdi == r8 + 8
; rsi == r9 + 8

std ; sets `DF`
lodsw ; rsi decreases (because `DF` is set) by 2 (`w` for word)
; so now:
; rdi == r8 + 8
; rsi == r9 + 8 - 2 == r9 + 6

cld ; clears `DF`
stosd ; rdi increases (because `DF` is cleared) by 4 (`d` for dword)
; so now:
; rdi == r8 + 8 + 4 == r8 + 12
; rsi == r9 + 6
```

~~~~exercism/caution
System V ABI के अनुसार, कॉलर को उम्मीद होती है कि जिस फंक्शन को कॉल किया गया था वह लौटने के बाद `DF` को क्लियर कर देगा।
अगर आप कभी `DF` सेट करते हैं, तो `ret` से पहले उसे क्लियर करना न भूलें।
~~~~

#### Rep

इनके अलावा, **rep** निर्देश सीधे मेमोरी के साथ काम नहीं करता।
इसके बजाय, इसे ऊपर बताए गए दूसरे निर्देशों के आगे प्रीफिक्स की तरह लगाया जा सकता है, जिससे वे निर्देश _बार-बार चलते_ हैं।

जब इनके आगे `rep` लगाया जाता है, तो स्ट्रिंग निर्देश `rcx` में मौजूद वैल्यू के बराबर बार दोहराए जाते हैं।
हर बार `rcx` की वैल्यू `1` घटा दी जाती है।
ध्यान रखिए कि निर्देश का उपयोग करने से पहले `rcx` की वैल्यू सेट करनी ज़रूरी है:

```x86asm
mov rcx, 4
rep movsq ; this repeats `movsq` 4 times
          ; it copies 4 * 8 == 32 bytes from a memory location indicated by `rsi` to a memory location indicated by `rdi`
```

~~~~exercism/advanced
आधुनिक CPU पर, बड़े ब्लॉकों में डेटा खिसकाते समय `rep movs` और `rep stos` आम तौर पर तेज़ विकल्प होते हैं।
लेकिन दूसरे स्ट्रिंग निर्देश, और यहाँ तक कि `rep` के बिना काम करने वाले `movs` और `stos` भी, आम तौर पर एक साधारण लूप से धीमे होते हैं।

इस विषय पर और गहराई से जानकारी [इस संदर्भ पुस्तक के अध्याय 16.9, "String instructions"][agner-optimization-guide] में मिल सकती है।

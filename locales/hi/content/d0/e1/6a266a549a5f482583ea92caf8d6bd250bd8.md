# परिचय

**लूप** निर्देशों का एक ऐसा क्रम है जिसे संभवतः एक से अधिक बार चलाया जाता है, जब तक कि कोई अंत की शर्त पूरी न हो जाए।

x86-64 में लूप आमतौर पर पिछले लेबल पर जंप करके बनाया जाता है:

```x86asm
example_loop:
    ...
    jmp example_loop
```

ध्यान दीजिए कि पिछले लेबल पर बिना शर्त जंप हमेशा निष्पादन को उस लेबल पर भेज देगा।
इसका मतलब है कि लूप हमेशा दोहराता रहेगा, जब तक कि दोहराए जा रहे क्रम के बाहर कोई दूसरा जंप न हो।

उदाहरण के लिए, यह लूप समाप्त नहीं होता:

```x86asm
infinite_loop:
    inc rax
    jmp infinite_loop ; always jumps to 'infinite_loop', repeating 'inc rax' forever
```

और यह लूप समाप्त भी हो सकता है, यह शर्त पूरी होने पर निर्भर करता है:

```x86asm
maybe_finite_loop:
    cmp rax, 1
    je out_of_loop ; jumps to 'out_of_loop' if rax == 1, breaking the loop

    inc rax
    jmp maybe_finite_loop ; always jumps to 'maybe_finite_loop'
out_of_loop:
    ...
```

## गिनती के लूप

गिनती करने वाला लूप लगभग हमेशा एक ही तरह से समाप्त होता है: कोई निर्देश जो काउंटर को अपडेट करता है या दो वैल्यू की तुलना करता है, और ठीक उसके बाद एक कंडीशनल जंप आता है जो तय करता है कि दोबारा चक्कर लगाना है या नहीं।

```x86asm
sum_array:
    ; rdi is the memory address of an array
    ; rsi is the number of elements in the array

    mov eax, 0           ; running total
.loop:
    add rax, qword [rdi] ; add the current element
    add rdi, 8           ; advance to the next element
    sub rsi, 1           ; one fewer element to process, setting ZF at zero
    jnz .loop            ; repeat while the counter is not yet zero
    ret
```

~~~~exercism/note
ऊपर दिए गए कोड में `cmp rsi, 0` की ज़रूरत नहीं है, क्योंकि `sub rsi, 1` परिणाम `0` होने पर पहले ही `zero flag (ZF)` सेट कर देता है।

हालाँकि असेंबली में शर्तों की जाँच का मुख्य तरीका `cmp` ही है, कई निर्देश फ्लैग को अपडेट करते हैं।
उदाहरण के लिए, कई पूर्णांक अंकगणित या बिटवाइज़ निर्देश परिणाम `0` होने पर `ZF` अपडेट करते हैं, और परिणाम ऋणात्मक होने पर (यानी, सबसे ऊपर का बिट सेट हो) `SF` अपडेट करते हैं।

आप किसी [संदर्भ][reference] को देखकर पता कर सकते हैं कि कौन-से फ्लैग किस निर्देश से प्रभावित होते हैं।

[reference]: https://www.felixcloutier.com/x86/
~~~~

ध्यान दीजिए कि ऊपर के उदाहरण में `rsi` को `0` से बड़ा माना गया है।
अगर यह `0` होता, तो `sub rsi, 1` `rsi` को `-1` तक कम कर देता, जो एक बहुत बड़ी अनसाइन्ड संख्या है।
लूप के समाप्त होने से पहले इसमें `18,446,744,073,709,551,615` और इटरेशन लगते।
साथ ही, चूँकि ऐरे की लंबाई `0` है, कोई भी मेमोरी एक्सेस सीमा के बाहर होगा।

अगर ऐरे की लंबाई के बारे में कोई गारंटी नहीं है, तो दो आम तरीके हैं।

पहला तरीका है अंत की शर्त को लूप की शुरुआत में ले जाना, और फिर अंत में बिना शर्त जंप रखना:

```x86asm
sum_array:
    mov eax, 0
.loop:
    cmp rsi, 0
    je .done
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jmp .loop
.done:
    ret
```

दूसरा तरीका है लूप शुरू होने से पहले शून्य लंबाई वाले ऐरे के लिए एक बार जाँच कर लेना:

```x86asm
sum_array:
    mov eax, 0

    cmp rsi, 0
    je .done
.loop:
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jnz .loop
.done:
    ret
```

यह दूसरा तरीका आमतौर पर पहले से ज़्यादा कुशल होता है, क्योंकि लूप के अंदर के कोड में ब्रांच की संख्या कम होती है।
इसके बारे में आप आगे किसी कॉन्सेप्ट में और सीखेंगे।

~~~~exercism/advanced
कुछ स्थितियों में, आधुनिक CPU दो अलग-अलग निर्देशों को एक ही ऑपरेशन में मिला सकते हैं।
इस ऑप्टिमाइज़ेशन को **मैक्रोफ्यूज़न** कहा जाता है।

`sub` और `add` जैसे कई अंकगणित निर्देश, तथा `cmp` और `test`, आमतौर पर उसके ठीक बाद आने वाले कंडीशनल जंप के साथ फ्यूज़ हो जाते हैं।
इसका मतलब है कि `cmp rax, rdx` जैसे निर्देश को, जिसके तुरंत बाद कंडीशनल जंप आता है, CPU आमतौर पर एक ही ऑपरेशन मान सकता है।

मैक्रोफ्यूज़न CPU पर निर्भर करता है, और इसमें थोड़ा अंतर होता है कि कौन-से निर्देश किस कंडीशनल जंप के साथ फ्यूज़ होते हैं।

एक उपयोगी संदर्भ है [The microarchitecture of Intel, AMD, and VIA CPUs, by Agner Fog][agner-uarch]।
[Intel optimization reference manual][intel-opt] का भाग 3.4.2.2 (Optimizing for Macrofusion) भी Intel CPU के लिए फ्यूज़ होने वाले जोड़ों की सूची देता है।

[agner-uarch]: https://www.agner.org/optimize/microarchitecture.pdf
[intel-opt]: https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf
~~~~

# परिचय

अब तक सिलेबस में टाइप के बारे में ज़्यादा कुछ नहीं कहा गया, लेकिन Julia में ये साफ़ मौजूद हैं:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

हमने टाइप कभी बताए ही नहीं, फिर भी Julia ने उन्हें असाइन कर दिया।

1. Julia में `types` होते हैं, जो इसके डिज़ाइन के केंद्र में हैं।
2. Julia आम तौर पर `Type Inference` की मदद से टाइप का "अनुमान" लगा सकता है।

JIT कंपाइलर कोड को (पूरा) देखता है, यह देखता है कि किसी वेरिएबल का उपयोग कैसे होता है, और उस उपयोग से मेल खाता कोई उपयुक्त डिफ़ॉल्ट टाइप _अनुमान_ लगा लेता है।

## टाइप प्रोमोशन

पिछले कॉन्सेप्ट में कई ऐसे उदाहरण रहे हैं जहाँ संख्यात्मक टाइप को एक ही रूप में ढाला गया, और शुरुआत सबसे सरल अंकगणित से हुई।

```julia-repl
julia> 2 + 1.3
3.3
```

हमने एक पूर्णांक (Int64) और एक दशमलव संख्या (Float64) जोड़ी, और परिणाम Float64 आया।
इसी तरह:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

ऊपर के उदाहरण में ट्यूपल ने हर एलिमेंट का टाइप बनाए रखा, लेकिन वेक्टर में बदलने पर वे सब एक समान Float64 हो गए।

Julia का कंपाइलर समझता है कि कौन-से टाइप रूपांतरण संभव हैं: पूर्णांक से दशमलव संख्या में जाना कोई समस्या नहीं है, लेकिन दशमलव संख्या से पूर्णांक में जाने पर सटीकता खो जाती है, इसलिए एक `InexactError` मिलती है।
टाइप प्रोमोशन एक्सप्रेशन की सभी वैल्यू को एक साझा टाइप में बदल देता है, जो इतना लचीला होता है कि सभी इनपुट के साथ मेल खा सके।

## टाइप असाइनमेंट

आसान ट्यूटोरियल अभ्यास हल करने के लिए टाइप इन्फ़रेंस पर भरोसा करना ठीक है, लेकिन बड़े प्रोग्राम के लिए आपको शायद ज़्यादा सटीक नियंत्रण की ज़रूरत पड़े।

ज़्यादातर आधुनिक प्रोसेसर पर एक पूर्णांक का डिफ़ॉल्ट `Int64` होता है।
हमने [`Numbers`][numbers] कॉन्सेप्ट में देखा था कि किसी वैल्यू को किसी खास गैर-डिफ़ॉल्ट टाइप में बदला जा सकता है।

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

लेकिन वेरिएबल `x` को फिर भी किसी दूसरे टाइप पर दोबारा असाइन किया जा सकता है:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

यह `type instability` है, जिसका मतलब:

- छोटी स्क्रिप्ट में बहुत सुविधाजनक।
- बड़े प्रोग्राम में प्रदर्शन और विश्वसनीयता के लिए हानिकारक।

इसके बजाय, हम `::` ऑपरेटर का उपयोग करके `x` का टाइप तय कर सकते हैं:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

अब `y` का टाइप `Int16` है, और हमेशा `Int16` ही रहेगा।
इस तरह कंपाइलर जानता है कि इसके लिए कितने बाइट आरक्षित करने हैं, और बाकी कोड को इस भरोसे पर ऑप्टिमाइज़ कर सकता है कि टाइप स्थिर रहेगा।
इस मामले में यह वेरिएबल C जैसी स्टैटिकली टाइप्ड भाषा के वेरिएबल के लगभग समान है।

## टाइप असर्शन

ऊपर बताया गया टाइप असाइनमेंट किसी वेरिएबल असाइनमेंट के बाईं तरफ इस्तेमाल होता है, ताकि उस वेरिएबल का टाइप सीमित किया जा सके।

किसी वैल्यू के साथ, या ऐसी चीज़ के साथ जो मूल्यांकन पर कोई वैल्यू देती है, `::` ऑपरेटर का उपयोग आम तौर पर यह _असर्शन_ होता है कि वैल्यू इसी टाइप की होनी चाहिए, वरना एक एरर फेंकी जानी चाहिए।

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

आम तौर पर इसका उपयोग किसी फंक्शन की रिटर्न वैल्यू के साथ एक आसान अंतिम जाँच के तौर पर किया जाता है, कि फंक्शन ने वैसा ही काम किया जैसा अपेक्षित था।

## टाइप पदानुक्रम

`Int64`, `Int16`, `String`, `Char`: ये टाइप _"कहाँ से आते हैं"_?

बहुत-सी ऑब्जेक्ट-ओरिएंटेड (OO) भाषाओं में हर टाइप एक क्लास होता है, सबक्लासिंग उन्हें एक क्लास पदानुक्रम में सजाती है, और क्लास मेथड उनका व्यवहार तय करते हैं।

Java और Ruby इस पैटर्न के साफ़ उदाहरण हैं, लेकिन Python भी अंदर से इसी तरह काम करता है।

***Julia में कोई क्लास नहीं होती।***

दस्तावेज़ों में बताया गया कारण यह है कि OO फीचर JIT कंपाइलर में बाधा डालते हैं और रनटाइम प्रदर्शन को खराब करते हैं।

फिर भी, इस कोड को देखिए:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

कुछ बातें साफ़ कर लेते हैं:

- `Int16` एक टाइप है, और हम इस टाइप के वेरिएबल बना सकते हैं।
- `Int16`, `Signed` का सबटाइप है, और `supertype()` फंक्शन हमें यह दिखाता है।
- टाइप का एक पदानुक्रम है, जो `Integer`, `Real` और `Number` से होकर ऊपर की ओर `Any` तक जाता है, और `subtypes()` हमें पदानुक्रम की इस शाखा की सूची दिखा देगा।

सभी शाखाएँ `Any` पर आकर खत्म होती हैं, जो इस मायने में अनोखा है कि वह खुद अपना सुपरटाइप है।

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

तो, Julia में `class` का पदानुक्रम नहीं है, लेकिन `type` का पदानुक्रम ज़रूर है।

आगे चलकर हम यह समझने की कोशिश करेंगे कि यह कैसे काम करता है, लेकिन पहले अभी बहुत कुछ खोजना बाकी है।

## टाइप की जाँच करना

हम सामान्य तरीके से समानता की जाँच के लिए `typeof()` का उपयोग कर सकते हैं।

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

टाइप की समानता बिल्कुल सटीक होनी चाहिए, क्योंकि तुलना का यह तरीका टाइप पदानुक्रम को नहीं समझता।

ज़्यादा लचीले ढंग से, `isa` हमें बताएगा कि किसी वैल्यू का टाइप उस टाइप जैसा ही है जिससे हम तुलना कर रहे हैं, या उसका सबटाइप है।
इसका उपयोग फंक्शन रूप में या इन्फ़िक्स रूप में, दोनों तरह से किया जा सकता है।

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

ध्यान दीजिए कि `isa` बाईं ओर एक `value` चाहता है, `type` नहीं।

दो _टाइप_ की इस तरह तुलना करने पर अनपेक्षित परिणाम मिलेंगे।
सही ऑपरेटर `<:` है, जिसे हम आगे के कॉन्सेप्ट में बहुत और देखेंगे।

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## अमूर्त बनाम ठोस टाइप

हमने देखा कि टाइप पदानुक्रम एक पेड़ जैसी संरचना बनाता है (कंप्यूटर विज्ञान के अर्थ में, जिसकी जड़ सबसे ऊपर होती है)।

पेड़ की हर चीज़ एक `node` होती है, और इन्हें श्रेणियों में बाँटा जा सकता है:

1. जिन नोड के सबटाइप होते हैं, उन्हें `abstract` कहा जाता है।
2. जिन नोड के आगे कोई सबटाइप नहीं होता, यानी जो पत्ती नोड होते हैं, उन्हें `concrete` कहा जाता है।

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

यह एक ज़रूरी अंतर है, क्योंकि सिर्फ ठोस टाइप को ही वेरिएबल के रूप में `instantiated` किया जा सकता है।


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

ध्यान दीजिए कि अमूर्त टाइप इस्तेमाल करने पर (इस मामले में) कोई एरर संदेश नहीं आता, बल्कि कंपाइलर एक उपयुक्त ठोस टाइप बना देता है: `Integer` की जगह `Int64`।
कम से कम यह वेरिएबल में किसी गैर-पूर्णांक वैल्यू के असाइन होने को रोक तो देता है:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

इस तरह अमूर्त टाइप के साथ टाइप असाइनमेंट वेरिएबल के टाइप पर एक _बंधन_ लगाता है, कि वह (ऊपर के मामले में) `Integer` के किसी भी सबटाइप का ही हो सकता है।
प्रोग्रामिंग भाषाओं की दुनिया में यह कुछ अनोखा है: यह C के टाइप असाइनमेंट से कमज़ोर है, और Python के हाल के संस्करणों में मिलने वाले टाइप हिंट से ज़्यादा मज़बूत।

`isabstracttype()` और `isconcretetype()` फंक्शन जाँच करने देते हैं।
ध्यान दीजिए कि ये सिर्फ एक-दूसरे के उलट नहीं हैं: किसी आगे के कॉन्सेप्ट में हम देखेंगे कि कुछ टाइप न अमूर्त होते हैं और न ठोस।


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

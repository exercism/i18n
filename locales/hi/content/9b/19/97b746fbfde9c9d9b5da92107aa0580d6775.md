# परिचय

मेमोरी के सेगमेंट होते हैं, और हर सेगमेंट कई सेक्शन में व्यवस्थित होता है, जिनकी अनुमतियाँ अलग-अलग होती हैं। आम तौर पर किसी प्रोग्राम के लिए मेमोरी का नक्शा ऑपरेटिंग सिस्टम (OS) एक सामान्य लेआउट में बनाता है:

| एड्रेस | मेमोरी क्षेत्र |
| :-----: | :--------------------- |
|  उच्च   | स्टैक                  |
|         | ...                    |
|         | हीप                    |
|         | पढ़ने-लिखने योग्य सेगमेंट |
|         | कोड/केवल पढ़ने योग्य सेगमेंट |
|   निम्न   | आरक्षित               |

अब तक हमने जो भी फंक्शन बनाए हैं, वे सब **सेक्शन .text** में थे। इस सेक्शन में ऐसा डेटा रहता है जिसे केवल पढ़ा जा सकता है और चलाया भी जा सकता है। दूसरे सेक्शन डेटा वेरिएबलो को घोषित करने के काम आते हैं। ये वेरिएबल केवल पढ़ने योग्य या पढ़ने-लिखने योग्य हो सकते हैं, लेकिन इन्हें चलाया नहीं जा सकता।

## सेक्शन .data

इनिशियलाइज़ किया गया डेटा **[सेक्शन .data][data]** में घोषित किया जाता है।

NASM (Netwide Assembler, यानी इस ट्रैक में इस्तेमाल होने वाला असेंबलर) में एक इनिशियलाइज़ किए गए वेरिएबल का एक नाम होता है, एक डायरेक्टिव होता है जो डेटा का आकार बताता है, और कॉमा से अलग की गई वैल्यू की एक सूची होती है। इनमें से हर एक को एक स्पेस से दूसरे से अलग किया जाता है, और लेबल के बाद वैकल्पिक रूप से `:` भी आ सकता है।

मुख्य डायरेक्टिव और उनसे जुड़े डेटा आकार ये हैं:

| डायरेक्टिव | आकार    |
| :-------: | :------ |
|    db     | 1 बाइट  |
|    dw     | 2 बाइट |
|    dd     | 4 बाइट |
|    dq     | 8 बाइट |

उदाहरण के लिए, यह `space` नाम का एक बाइट वेरिएबल घोषित करता है जिसकी वैल्यू `10` है:

```x86asm
section .data
    space db 10
```

`section .data` में घोषित वेरिएबलो को बदला जा सकता है, यानी उन्हें पढ़ा और लिखा दोनों जा सकता है। इनकी स्टोरेज अवधि भी _स्टैटिक_ होती है, यानी ये पूरे प्रोग्राम के चलने के दौरान मौजूद रहते हैं।

## सेक्शन .rodata

**सेक्शन .rodata** भी `section .data` जैसा ही होता है। दोनों सेक्शन में इनिशियलाइज़ किया गया डेटा रहता है, जिसे एक ही तरह से घोषित किया जाता है और जिसकी स्टोरेज अवधि भी एक जैसी होती है।

इनमें मुख्य अंतर यह है कि `section .rodata` का डेटा इम्यूटेबल होता है, यानी केवल पढ़ने योग्य।

~~~~exercism/note
`equ` से बनाए गए कॉन्स्टेंट `section .rodata` में बनाए गए कॉन्स्टेंट से अलग होते हैं।

`equ` से बनाया गया कॉन्स्टेंट मेमोरी में जगह नहीं लेता और असेंबलर उसकी वैल्यू को सीधे उसकी जगह रख देता है। असल में यह उस वैल्यू के लिए एक प्लेसहोल्डर होता है।

दूसरी ओर, `section .rodata` में बनाए गए कॉन्स्टेंट वाकई मेमोरी में संग्रहीत होते हैं और उनका एक एड्रेस होता है।
~~~~

## डेटा तक पहुँचना

### लेबल और इनडायरेक्शन

घोषित डेटा के साथ एक नाम जुड़ा होना चाहिए। इस नाम को **लेबल** कहते हैं।

लेबल एक ऐसा सिंबल होता है जो मेमोरी में डेटा के किसी खास एड्रेस को दर्शाता है। **x86-64 में एड्रेस 64-बिट वैल्यू होते हैं**। ऐसा एड्रेस रखने वाली वैल्यू, चाहे वह किसी रजिस्टर में रखी हो या मेमोरी में संग्रहीत हो, वही है जिसे उच्च-स्तरीय भाषाएँ **[पॉइंटर][pointer]** कहती हैं।

NASM में किसी डेटा तक सीधे उसके लेबल से पहुँचने की कोशिश करने पर आवंटित मेमोरी नहीं मिलती, बल्कि उसका एड्रेस मिलता है:

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

किसी मेमोरी एड्रेस की सामग्री तक पहुँचने के लिए उसे _डीरेफरेंस_ करना पड़ता है। इसे **इनडायरेक्शन** कहते हैं।

NASM में यह `[]` से किया जाता है:

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

लेकिन कुछ ऐसी स्थितियाँ होती हैं जब यह साफ नहीं होता कि जिस मेमोरी को डीरेफरेंस किया जा रहा है उसका आकार क्या है। ऐसी स्थितियों में उस आकार को बताने वाला एक प्रीफिक्स इस्तेमाल करना ज़रूरी होता है।

एक सामान्य x86-64 प्रोग्राम में सबसे ज़रूरी प्रीफिक्स और उनके आकार ये हैं:

| प्रीफिक्स | आकार    |
| :----- | :------ |
| byte   | 1 बाइट  |
| word   | 2 बाइट |
| dword  | 4 बाइट |
| qword  | 8 बाइट |

यही लोड आकार को साफ-साफ लिखकर भी किया जा सकता है:

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

मेमोरी डीरेफरेंस करते समय हमेशा प्रीफिक्स इस्तेमाल करना अच्छी आदत है।

### मेमोरी में लिखना

मेमोरी में लिखना भी उसी तरह, एड्रेस को डीरेफरेंस करके किया जाता है:

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

ध्यान दीजिए कि ज़्यादातर निर्देशों में आप मेमोरी ऑपरेंड सीधे इस्तेमाल कर सकते हैं, उनकी सामग्री पहले किसी रजिस्टर में लोड करने की ज़रूरत नहीं होती। लेकिन आम तौर पर इन्हें सोर्स और डेस्टिनेशन, दोनों ऑपरेंड में इस्तेमाल नहीं किया जा सकता; दोनों में से किसी एक में ही किया जा सकता है:

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### LEA निर्देश

हालाँकि किसी वेरिएबल का एड्रेस रजिस्टर में रखने के लिए `mov` का इस्तेमाल किया जा सकता है, लेकिन इसी खास काम के लिए एक निर्देश भी है: **[lea][lea]**।

यह निर्देश मेमोरी-फॉर्म ऑपरेंड लेता है, लेकिन मेमोरी को पढ़ता _नहीं_ है। इसके बजाय यह इफेक्टिव एड्रेस एक्सप्रेशन की गणना करता है और नतीजा डेस्टिनेशन ऑपरेंड में लिख देता है:

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

रजिस्टर में मेमोरी के एड्रेस निकालकर रखने के लिए `lea` का इस्तेमाल करना ज़्यादा स्वाभाविक तरीका है।

### रिलेटिव एड्रेसिंग

मेमोरी लोकेशन तक पहुँचते समय NASM का डिफॉल्ट व्यवहार **एब्सोल्यूट एड्रेस**, यानी तय मेमोरी एड्रेस, बनाना होता है।

सुरक्षा कारणों से एक्ज़ीक्यूटेबल को अक्सर **PIE (Position Independent Executable)** के रूप में बनाया जाता है, जिसमें मेमोरी के क्षेत्र यादृच्छिक जगहों पर रखे जाते हैं। `PIE` में लिंक के समय वेरिएबल का अंतिम एड्रेस ज्ञात नहीं होता। इसलिए कोड एड्रेस की गणना `rip` नाम के एक खास रजिस्टर की वैल्यू से ऑफसेट के रूप में करता है, जो चलाए जाने वाले अगले निर्देश की ओर इशारा करता है।

इसे आम तौर पर **RIP-रिलेटिव एड्रेसिंग** कहा जाता है।

NASM में आप **[rel ऑपरेटर][rel]** से RIP-रिलेटिव एक्सेस माँग सकते हैं:

```x86asm
mov rax, qword [rel variable]
```

किसी सोर्स फाइल के लिए सबसे ऊपर `default rel` लिखकर रिलेटिव एड्रेसिंग को डिफॉल्ट भी बनाया जा सकता है।

इस ट्रैक के सारे अभ्यास `PIE` के रूप में कंपाइल और लिंक किए जाते हैं, इसलिए रिलेटिव एड्रेस बनाने के लिए `rel` का इस्तेमाल करना चाहिए।

ऊपर बताया गया यादृच्छिक लेआउट एक सुरक्षा उपाय है, जिसे एड्रेस स्पेस लेआउट रैंडमाइज़ेशन कहते हैं। हर मेमोरी क्षेत्र के आधार को अप्रत्याशित बनाकर यह हमलावर को वे तय एड्रेस नहीं देता जिन पर हमले की कई तकनीकें निर्भर करती हैं, और `PIE` ही लोडर को इन क्षेत्रों को कहीं भी रखने देता है।

इस वजह से इस ट्रैक में एब्सोल्यूट एड्रेसिंग को सिर्फ हतोत्साहित नहीं किया जाता, वह इस्तेमाल ही नहीं की जा सकती। `[abs variable]` जैसा एब्सोल्यूट रेफरेंस असेंबलर से कहता है कि वह निर्देश के अंदर एक तय 32-बिट एड्रेस डाल दे। Linux पर `PIE` लिंकर इससे बनने वाली रीलोकेशन को अस्वीकार कर देता है, और macOS पर `macho64` फॉर्मेट 32-बिट एब्सोल्यूट एड्रेस को समर्थन ही नहीं देता, इसलिए फाइल असेंबल नहीं हो पाती।

RIP-रिलेटिव एड्रेसिंग दोनों समस्याओं से बच जाती है, क्योंकि निर्देश में सिर्फ `rip` से एक ऑफसेट दर्ज होता है, कोई तय एड्रेस कभी नहीं। इसलिए `PIE` के तहत किसी एड्रेस को रजिस्टर में रखने का स्वाभाविक तरीका `rel` ऑपरेंड के साथ `lea` है:

```x86asm
default rel

section .data
    variable dq 7

section .text
fn:
    lea rax, [rel variable]       ; materialize the address (PIE-safe)
    mov rcx, qword [rel variable] ; load the value through a RIP-relative access
    ...
```

### विज़िबिलिटी

किसी भी सेक्शन (जैसे `.text`, `.data`, `.rodata`) में बनाए गए लेबल (फंक्शन और डेटा) उसी सोर्स फाइल के अंदर दिखाई देते हैं। अगर उन्हें `global` घोषित किया जाए, तो वे दूसरी सोर्स फाइलों को भी दिखाई देते हैं।

इसके उलट, दूसरी सोर्स फाइलों में बनाए गए लेबल मौजूदा सोर्स फाइल को तब दिखाई देते हैं जब उन्हें `extern` घोषित किया गया हो। ऐसे में असेंबली में डेटा के आकार का कोई संकेत नहीं मिलता, यह पहले से ज्ञात होना चाहिए।

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

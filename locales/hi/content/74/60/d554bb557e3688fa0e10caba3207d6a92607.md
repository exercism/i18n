# परिचय

## C भाषा के साथ इंटरफेसिंग: स्ट्रक्चर

C भाषा में, **स्ट्रक्चर** एक समग्र टाइप है, जो अलग-अलग फील्ड से बना होता है।
हर फील्ड का अपना टाइप और आकार होता है।

उदाहरण के लिए, यह तीन पूर्णांकों से बना एक टाइप परिभाषित करता है, जिनमें दो 4 बाइट के और एक 8 बाइट का है:

```c
struct example {
    int32_t first_four_byte_integer;
    uint32_t second_four_byte_integer;
    uint64_t eight_byte_integer;
};
```

एक स्ट्रक्चर में दूसरे स्ट्रक्चर भी हो सकते हैं:

```c
struct example_2 {
    struct example first;
    struct example second;
};
```

अगर स्ट्रक्चर का कोई फील्ड ऐरे है, तो ऐरे के लिए आवंटित सारे बाइट स्ट्रक्चर का हिस्सा होते हैं।
लेकिन अगर फील्ड सिर्फ ऐरे की ओर एक पॉइंटर है, तो ऐरे को कहीं और संग्रहीत करना होगा:

```c
struct with_array {
    char string[20];
};
// all 20 bytes of string are inside struct with_array

struct with_pointer {
    const char *string;
};
// only the 8-byte pointer to the string is inside struct with_pointer
```

### एलाइनमेंट

किसी टाइप का **एलाइनमेंट** दो की एक गैर-ऋणात्मक घात (1, 2, 4, 8, ...) होता है, जो उसके एड्रेस पर एक शर्त लगाता है।
उस टाइप का हर ऑब्जेक्ट ऐसे एड्रेस पर होना चाहिए जो उसके एलाइनमेंट का गुणज हो।

किसी प्रिमिटिव टाइप के लिए, एलाइनमेंट आमतौर पर उसके आकार के बराबर होता है, इसलिए उदाहरण के लिए, एक `int32_t` का एलाइनमेंट आमतौर पर 4 बाइट का होता है।
इसका मतलब है कि `int32_t` को 4-बाइट सीमाओं पर आवंटित करना होगा।

हालाँकि, किसी स्ट्रक्चर का एलाइनमेंट उसके किसी भी फील्ड के एलाइनमेंट में सबसे बड़ा होता है।
इसलिए, उदाहरण के लिए, ऊपर परिभाषित `struct example` का एलाइनमेंट 8 बाइट होगा, क्योंकि यह `uint64_t` का एलाइनमेंट है।

अगर किसी स्ट्रक्चर फील्ड का एलाइनमेंट स्ट्रक्चर के एलाइनमेंट से छोटा है, तो उस फील्ड के बाद पैडिंग बाइट डाले जा सकते हैं।
यह सुनिश्चित करता है कि आगे के फील्ड और पूरा स्ट्रक्चर एलाइनमेंट की शर्तें पूरी करें।
व्यवहार में, इसका मतलब है कि हालाँकि वे पैडिंग बाइट स्ट्रक्चर के आकार में जुड़ते हैं, वे स्ट्रक्चर की वैल्यू में इस्तेमाल नहीं होते:

```c
struct example_3 {
    char one_byte; // alignment of 1
    int four_byte; // alignment of 4
};
// example_3 has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one_byte'
// 3 padding bytes (with undefined value)
// 4 bytes for field 'four_byte'
```

ध्यान दीजिए कि ऊपर परिभाषित स्ट्रक्चर में, फील्ड 'one_byte' का एलाइनमेंट 1 है और इसे किसी भी एड्रेस पर रखा जा सकता है।
चूँकि फील्ड 'four_byte' का एलाइनमेंट 4 है, स्ट्रक्चर के फील्ड को भी 4-बाइट सीमाओं का पालन करना होगा।
इसका मतलब है कि स्ट्रक्चर के किन्हीं भी दो फील्ड के बीच बाइट की संख्या 4 का गुणज होनी चाहिए।
चूँकि 'one_byte' सिर्फ 1 बाइट घेरता है, इसलिए इस सीमा का पालन करने के लिए उसके बाद 3 पैडिंग बाइट डाले जाते हैं।

जब भी संभव हो, आस-पास के फील्ड को समूहित किया जाता है ताकि ज़रूरी पैडिंग बाइट की संख्या कम से कम हो:

```c
struct two_padding {
    char one; // alignment of 1
    char two; // alignment of 1
    int three; // alignment of 4
};
// struct two_padding has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one'
// 1 byte for field 'two'
// 2 padding bytes
// 4 bytes for field 'three'
```

यह समूहन हर फील्ड के एलाइनमेंट का भी पालन करना चाहिए:

```c
struct one_padding {
    char one; // alignment of 1
    int16_t two; // alignment of 2
    int three; // alignment of 4
};
// struct one_padding has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one'
// 1 padding byte
// 2 bytes for field 'two'
// 4 bytes for field 'three'
// Since 'two' has alignment of 2, it must be placed in a 2-byte boundary
// So, there must be 1 padding byte between 'one' and 'two'
```

इसका मतलब है कि स्ट्रक्चर में फील्ड का क्रम बदलने से कभी-कभी उसके आकार में अंतर आ सकता है:

```c
struct example_4 {
    int64_t one;
    short two;
    int32_t three;
};
// example_4 has alignment of 8 (the same as int64_t)
// it occupies 16 bytes in space:
// 8 bytes for field 'one'
// 2 bytes for field 'two'
// 2 padding bytes
// 4 bytes for field 'three'
// two' and 'three' are adjacent and can be grouped to sum up 8 bytes with only 2 bytes of padding

struct example_5 {
    int16_t one;
    int64_t two;
    unsigned int three;
};
// example_5 also has alignment of 8 (the same as int64_t)
// however, it occupies 24 bytes in space:
// 2 bytes for field 'one'
// 6 bytes for padding
// 8 bytes for field 'two'
// 4 bytes for field 'three'
// 4 padding bytes
// 'one' can't be grouped with 'two' because their sum would be higher than the struct's alignment
// 'two' and 'three' also can't be grouped, for the same reason
// so padding bytes must be inserted in full after each field with less than 8 bytes in alignment
```

ध्यान दीजिए कि ऐरे का एलाइनमेंट उसके अंदरूनी टाइप के एलाइनमेंट के समान होता है:

```c
struct array_example {
    char string[10]; // alignment of 1
};
// array_example has alignment of 1 (it can be placed at any address)
// it occupies 10 bytes in space, one for each char in 'string'
```

ऐरे के एलिमेंट को उसी तरह समूहित किया जा सकता है जैसे वे ऐरे का हिस्सा न हों:

```c
struct group_array {
    int16_t arr[3];
    int8_t one_byte;
    int32_t four_byte;
};
// group_array has alignment of 4 because this is the alignment of 'four_byte'
// it occupies 12 bytes in space:
// 4 bytes for arr[0] and arr[1]
// 2 bytes for arr[2]
// 1 byte for 'one_byte'
// 1 padding byte (arr[2] is grouped with 'one_byte')
// 4 bytes for 'four_byte'
```

असेंबली में स्ट्रक्चर को एक्सेस करते समय किसी भी संभव पैडिंग बाइट का ध्यान रखना ज़रूरी है।

### कॉलिंग कन्वेंशन

सामान्य तौर पर, वैल्यू फंक्शन को उसी तरह पास की जाती हैं और फंक्शन से उसी तरह लौटाई जाती हैं जैसा आप अपेक्षा करेंगे:

- पूर्णांक वैल्यू, जिनमें मेमोरी एड्रेस और enum शामिल हैं, जनरल-पर्पस रजिस्टर (GPR) में पास की जाती हैं।
- फ्लोटिंग-पॉइंट वैल्यू `xmm` रजिस्टर में पास की जाती हैं।

स्ट्रक्चर, हालाँकि, एक खास मामला हैं।
सामान्य नियम के तौर पर, स्ट्रक्चर के सारे फील्ड मेमोरी में पास-पास जगह घेरते हैं और जब भी संभव हो एक ही रजिस्टर में रखे जाने चाहिए:

```c
struct single_type {
    int16_t first;
    int16_t second;
    int16_t third;
    int16_t fourth;
};
// this struct occupies 8 bytes
// it is entirely passed in the same GPR register:
// the field 'first' is passed on the lowest 2 bytes
// each subsequent field is passed in the following 2 bytes
```

अगर किसी स्ट्रक्चर में पूर्णांक वैल्यू वाले फील्ड हैं और फ्लोटिंग-पॉइंट वैल्यू वाले फील्ड भी, तो स्ट्रक्चर के हर लगातार 8-बाइट को अलग-अलग वर्गीकृत किया जाना चाहिए:

```c
struct mixed_types {
    double first;
    int second;
    int third;
};
// this struct occupies 16 bytes
// the field 'first' is passed in the first 8 bytes of a xmm register
// the fields 'second' and 'third' are passed in the same GPR register:
// the field 'second' is passed on the lowest 4 bytes
// the field 'third' is passed in the next 4 bytes
```

अगर पूर्णांक और फ्लोटिंग-पॉइंट वैल्यू एक ही 8-बाइट में हों, तो टाइप पूर्णांक होता है और पूरा 8-बाइट (फ्लोटिंग-पॉइंट वैल्यू सहित) GPR में रखा जाता है:

```c
struct mixed_types {
    int32_t integer;
    float floating_point;
};
// this struct occupies 8 bytes
// it is entirely passed in the same GPR register:
// the field 'integer' is passed on the lowest 4 bytes
// the field 'floating_point' is passed on the next 4 bytes
```

~~~~exercism/caution
जब `cvtsi2ss` या `cvtsi2sd` का उपयोग करके फ्लोटिंग-पॉइंट से पूर्णांक में रूपांतरण किया जाता है, तो इससे अंदरूनी बाइट का संगठन बदल जाता है।

आप `movd` (32-बिट वैल्यू के लिए) और `movq` (64-बिट वैल्यू के लिए) का उपयोग करके बिना बिट प्रतिनिधित्व बदले एक `xmm` रजिस्टर से GPR में रॉ बाइट ले जा सकते हैं।
~~~~

हालाँकि, 16 बाइट से बड़े आकार वाले स्ट्रक्चर आमतौर पर मेमोरी में रखे जाते हैं, चाहे हर 8-बाइट का टाइप कुछ भी हो:

```c
struct big_struct {
    uint8_t first;
    double second;
    int64_t third;
};
// this struct occupies 24 bytes, including 7 padding bytes between 'first' and 'second'
// it is entirely passed in memory
```

जब किसी स्ट्रक्चर को फंक्शन को आर्गुमेंट के रूप में पास किया जाता है, तो वह जितने रजिस्टर ज़रूरी हों उतने इस्तेमाल करता है।
अगर उसे मेमोरी में रखा जाता है, तो इसके बजाय स्टैक का उपयोग किया जाता है।

फंक्शन से लौटाए गए स्ट्रक्चर पर भी इसी तरह के नियम लागू होते हैं।
वे आमतौर पर पहले `rax` और `rdx` में लौटाए जाते हैं (अगर पूर्णांक वैल्यू के हों) या `xmm0` और `xmm1` में (अगर फ्लोटिंग-पॉइंट वैल्यू के हों)।
हालाँकि, अगर उन्हें मेमोरी में रखा जाता है, तो कॉलर को उसके लिए जगह आरक्षित करनी होती है और इस मेमोरी लोकेशन का एड्रेस फंक्शन को पहले आर्गुमेंट के रूप में अंतर्निहित रूप से पास करना होता है (`rdi` में)।
फिर फंक्शन स्ट्रक्चर को इस जगह में संग्रहीत करता है और उसका एड्रेस `rax` में लौटाता है।

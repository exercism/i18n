# परिचय

## `jq` में एरर

`jq` दो बड़ी श्रेणियों के एरर बताता है:

1. **कंपाइल-टाइम एरर**: प्रोग्राम खुद ही अमान्य होता है, जैसे सिंटैक्स एरर, ऐसे फंक्शन या वेरिएबल के नाम जो परिभाषित नहीं हैं, इत्यादि।
   ऐसे में `jq` प्रोग्राम चलाने से इनकार कर देता है।

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **रनटाइम एरर**: प्रोग्राम मान्य होता है, लेकिन कोई वैल्यू संसाधित करते समय कुछ गड़बड़ हो जाती है, जैसे किसी संख्या को स्ट्रिंग से इंडेक्स करना, `fromjson` से अमान्य JSON टेक्स्ट पार्स करना, या किसी फंक्शन को गलत टाइप के आर्गुमेंट के साथ कॉल करना।

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

यह कॉन्सेप्ट **रनटाइम एरर** के बारे में है: इन्हें कैसे उठाना है, कैसे पकड़ना है और कैसे रोकना है।

जो रनटाइम एरर पकड़ा न जाए, उस पर `jq` _स्टैंडर्ड एरर_ पर एक संदेश छापता है और स्टेटस `5` के साथ बाहर निकल जाता है।

## एरर उठाना: `error` और `error(message)`

[`error`][man-error] फिल्टर एक एरर उठाता है।

- `error` एक ऐसा एरर उठाता है जिसकी वैल्यू **इनपुट** वैल्यू होती है।
- `error(message)` एक ऐसा एरर उठाता है जिसकी वैल्यू `message` का परिणाम होती है।

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
एरर की वैल्यू _कोई भी_ JSON वैल्यू हो सकती है, सिर्फ स्ट्रिंग नहीं।
संरचित एरर उठाने से `catch` हैंडलर एरर की सामग्री के आधार पर फैसले ले सकता है।

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

अगर स्ट्रिंग के अलावा कोई और एरर वैल्यू पकड़ी न जाए, तो `jq` उसे JSON के रूप में छापता है और साथ में `(not a string)` लिखता है।

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## एरर पकड़ना: `try` और `catch`

एरर को [`try EXP catch HANDLER`][man-try-catch] से पकड़ा जा सकता है।
पहला एक्सप्रेशन चलाया जाता है। अगर वह एरर उठाता है, तो `HANDLER` एक्सप्रेशन **एरर वैल्यू को अपने इनपुट के रूप में** लेकर चलाया जाता है।
हैंडलर जो आउटपुट देता है, वह ऐसे दिया जाता है जैसे वह उस एक्सप्रेशन का आउटपुट हो जिसे `try` किया गया था।

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

छोटा रूप `try EXP`, `try EXP catch empty` के बराबर है: एरर छोड़ दी जाती है और कोई आउटपुट नहीं आता।

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
`try` के अंदर एरर **स्ट्रीम का बाकी हिस्सा रोक देती है**।
जो वैल्यू पहले ही निकल चुकी हैं वे बनी रहती हैं, लेकिन एरर के बाद कुछ भी नहीं चलाया जाता।

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

हैंडलर नया एरर उठा सकता है, या सादे `error` से मूल एरर फिर से उठा सकता है। चूँकि एरर वैल्यू हैंडलर का इनपुट होती है, इससे वह बिना बदले आगे चली जाती है।

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## एरर दबाना: `?` ऑपरेटर

[`?` ऑपरेटर][man-question-mark] जब `EXP?` की तरह लिखा जाता है, तो वह `try EXP` का छोटा रूप है।
यह फेल होने वाले एक्सप्रेशन को ऐसे एक्सप्रेशन में बदल देता है जो बस कोई आउटपुट नहीं देता।

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

यह अक्सर इंडेक्सिंग ऑपरेटर के साथ जुड़ा दिखता है:

- `.foo?` का मतलब `.["foo"]?` है
- `.[]?` तभी हर एलिमेंट पर जाता है जब इनपुट ऐरे या ऑब्जेक्ट हो, वरना खाली रहता है

~~~~exercism/caution
`?` **हर** एरर दबा देता है, उन्हें भी जिनकी आपको उम्मीद नहीं थी।
जब `user` ऑब्जेक्ट नहीं होता, तो `user.name?` चुपचाप कुछ भी नहीं देता, और इससे आपके प्रोग्राम में डेटा की समस्याएँ या टाइपो छिप सकते हैं।
जब आपको यह जानना हो कि कुछ फेल _हुआ_ है, या इनपुट को स्पष्ट रूप से जाँचना हो, तो `try ... catch` का इस्तेमाल कीजिए।
~~~~

## अल्टरनेटिव ऑपरेटर `//`

प्रोग्रामर कभी-कभी सोचते हैं कि जब `a` फेल होता है तो `a // b` `b` देगा।
`jq` के पुराने वर्ज़न में यह सच था, लेकिन `jq` 1.6 के बाद से नहीं।
`//` ऑपरेटर एरर नहीं दबाता।
वह `b` तभी लाता है जब `a` कोई वैल्यू न दे, `false` दे या `null` दे; `a` में आए एरर तब भी आगे चले जाते हैं।

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

अगर आपको एरर के लिए फॉलबैक चाहिए, तो `try a catch b` का इस्तेमाल कीजिए।

## डिस्ट्रक्चरिंग अल्टरनेटिव ऑपरेटर `?//`

[`?//` ऑपरेटर][man-question-mark-slash-slash] डिस्ट्रक्चरिंग और एरर हैंडलिंग को साथ जोड़ता है।
यह बारी-बारी से हर बाइंडिंग पैटर्न आज़माता है, जब तक कोई एक सफल न हो जाए। जो वेरिएबल फेल हुए अल्टरनेटिव में बँधे थे, वे `null` पर सेट हो जाते हैं।

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

यहाँ पहला पैटर्न चाहता है कि `c` एक _ऑब्जेक्ट_ हो जिसमें `d` और `e` की हों, जबकि दूसरा चाहता है कि `c` एक _ऐरे_ हो जिसमें ऐसा ही कोई ऑब्जेक्ट हो।
पहला इनपुट एलिमेंट पहले पैटर्न से बँध जाता है। दूसरा एलिमेंट उस पैटर्न से मेल नहीं खाता, इसलिए उसके लिए दूसरा पैटर्न आज़माया जाता है।

इससे एक ही प्रोग्राम ऐसे इनपुट को डिस्ट्रक्चर कर सकता है जिनका रूप कई में से कोई एक हो सकता है, और इसके लिए `if type == ...` की लंबी चेन लिखने की ज़रूरत नहीं पड़ती।

## प्रोग्राम रोकना: `halt` और `halt_error`

कभी-कभी एरर पर सही कदम यही होता है कि प्रोसेसिंग पूरी तरह रोक दी जाए।

- [`halt`][man-halt] `jq` प्रोग्राम को तुरंत रोक देता है और उसके बाद कोई आउटपुट नहीं आता; एग्ज़िट स्टेटस `0` होता है।
- [`halt_error`][man-halt-error] प्रोग्राम रोक देता है, अपना **इनपुट** _स्टैंडर्ड एरर_ पर कच्चे टेक्स्ट के रूप में छापता है (कोई सजावट नहीं, नई लाइन भी नहीं), और दिए गए स्टेटस के साथ बाहर निकलता है। अगर स्टेटस न दिया जाए तो वह `5` होता है।

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

ध्यान दीजिए कि ये फिल्टर प्रोग्राम को तुरंत रोक देते हैं, भले ही पढ़ने के लिए और इनपुट बचे हों।

### एग्ज़िट स्टेटस

संदर्भ के लिए, `jq` ये एग्ज़िट स्टेटस इस्तेमाल करता है:

| स्टेटस | अर्थ                                             |
| :----: | ------------------------------------------------ |
| `0`    | सफलता                                            |
| `2`    | यूज़ेज एरर (कमांड लाइन के गलत ऑप्शन)              |
| `3`    | कंपाइल एरर                                       |
| `5`    | रनटाइम एरर (या बिना आर्गुमेंट वाला `halt_error`)  |

`--exit-status` / `-e` ऑप्शन के साथ स्टेटस अंतिम आउटपुट वैल्यू दर्शाता है: `true` या संख्याओं के लिए `0`, `false` या `null` के लिए `1`, और आउटपुट न होने पर `4`।

## डीबगिंग में मदद करने वाले फिल्टर

जब आप पता लगा रहे हों कि एरर कहाँ से आ रही है, तो ये फिल्टर मदद करते हैं:

- [`debug`][man-debug] अपने इनपुट को बिना बदले आगे भेज देता है, लेकिन स्टैंडर्ड एरर पर `["DEBUG:", <input>]` छापता है।
  `debug(msgs)` भी `msgs` को डीबग संदेशों के रूप में छापता है।
- [`stderr`][man-stderr] अपना इनपुट कच्चे और सघन रूप में स्टैंडर्ड एरर पर छापता है।
- [`input_line_number`][man-input-line-number] उस इनपुट की लाइन संख्या देता है जो इस समय फिल्टर हो रहा है। यह तब बहुत काम आता है जब किसी फाइल में कई JSON टेक्स्ट हों और उनमें से एक खराब हो।
- [`$__loc__`][man-loc] एक ऑब्जेक्ट देता है जिसमें `file` और `line` की होती हैं और जो बताता है कि यह प्रोग्राम में कहाँ आया है। इसे एरर संदेशों में शामिल किया जा सकता है।

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

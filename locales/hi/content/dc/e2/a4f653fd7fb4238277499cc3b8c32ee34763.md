# निर्देश परिशिष्ट

## काम

दो प्रोसीजर लागू कीजिए।

- `custom_error_message message` एक एरर उत्पन्न करता है, और `message` ही एरर संदेश है।
- `handle_error script` दी गई स्क्रिप्ट चलाता है और एक स्ट्रिंग लौटाता है जो बताती है कि क्या हुआ:

  | जब स्क्रिप्ट…                  | रिटर्न               |
  | --------------------------------- | -------------------- |
  | शून्य से भाग देती है                   | `"division by zero"`    |
  | ऐसी फाइल खोलती है जो मौजूद नहीं है  | `"file does not exist"` |
  | ऐसा प्रोसीजर कॉल करती है जो मौजूद नहीं है  | `"proc does not exist"` |
  | कोई और एरर उत्पन्न करती है            | `"unknown error"`       |
  | सफल होती है                          | `"success"`             |

## एरर उत्पन्न करना

Tcl में एरर उत्पन्न करने के दो कमांड हैं।

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` को पहले आर्गुमेंट के रूप में एक _एरर कोड_ चाहिए।
एरर कोड एक लिस्ट है जो हैंडलर को बताती है कि किस तरह की एरर हुई, ताकि हैंडलर संदेश का टेक्स्ट पढ़े बिना उत्तर दे सके।
इसकी सामग्री आप पर है: `{MYAPP BADTHING}` बस एक उदाहरण है, और कोई भी खाली न होने वाली लिस्ट चलेगी।
परंपरा से, यह सामान्य से विशिष्ट की ओर जाता है।
हैंडलर इसे मिलते-जुलते `try ... trap` पैटर्न से पकड़ता है (नीचे बताया गया है), जैसे `trap {MYAPP BADTHING}`, या हर `MYAPP` एरर को पकड़ने के लिए `trap {MYAPP}`।
`error` तीसरे आर्गुमेंट के रूप में वैकल्पिक एरर कोड लेता है: `error message ?info? ?code?`।

## `catch` से एरर संभालना

[`catch`][catch] एक स्क्रिप्ट चलाता है और एरर उत्पन्न करने के बजाय एक पूर्णांक _कम्प्लीशन कोड_ लौटाता है:

| कोड | अर्थ    |
| ---- | ---------- |
| 0    | `ok`       |
| 1    | `error`    |
| 2    | `return`   |
| 3    | `break`    |
| 4    | `continue` |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

वैकल्पिक दूसरा आर्गुमेंट परिणाम (या एरर संदेश) प्राप्त करता है।
वैकल्पिक तीसरा आर्गुमेंट एक _ऑप्शंस डिक्शनरी_ प्राप्त करता है, जिसमें `-errorcode` और `-errorinfo` (स्टैक ट्रेस) होते हैं।

फायदे:

- यह छोटा और लचीला है।
- सरल मामलों में यह छोटा है, जैसे `if {[catch {open $f} fh]} {...}`।

नुकसान:

- आपको कम्प्लीशन कोड खुद जाँचना होता है।
  एक लापरवाह `if {[catch ...] != 0} { handle error }` `return`, `break` और `continue` को भी एरर मान लेता है।
- जिन एरर को आप नहीं संभालते, वे निगल लिए जाते हैं, जब तक आप उन्हें खुद दोबारा उत्पन्न न करें।
- स्क्रिप्ट असफल हो या न हो, सफाई का कोड चलाने का कोई अंतर्निहित तरीका नहीं है।

## `try` से एरर संभालना

[`try`][try] एक स्क्रिप्ट चलाता है और परिणाम पहले मिलते-जुलते हैंडलर को भेजता है।
एक वैकल्पिक `finally` क्लॉज हमेशा चलता है, जिससे यह फाइल चैनल जैसे संसाधन छोड़ने की अच्छी जगह बन जाता है।

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

फायदे:

- ढाँचा साफ है: हर तरह के परिणाम के लिए एक हैंडलर।
- `finally` हमेशा चलता है।
- जिन परिणामों से कोई हैंडलर नहीं मिलता, वे बिना बदले कॉलर तक पहुँचा दिए जाते हैं।

नुकसान:

- सरल मामलों में यह `catch` से थोड़ा ज़्यादा लंबा है।

### `try ... on` बनाम `try ... trap`

दो तरह के हैंडलर होते हैं।

`on code {msgVar optionsVar}` _कम्प्लीशन कोड_ से मेल खाता है: `ok`, `error`, `return`, `break` या `continue`।
हर एरर का कम्प्लीशन कोड `error` होता है, इसलिए `on error` शून्य से भाग देने और फाइल न मिलने में फर्क नहीं कर सकता।
आपको संदेश का टेक्स्ट देखना पड़ेगा, जो नाज़ुक है: संदेश इंसानों के लिए होते हैं और Tcl के संस्करणों के बीच बदल सकते हैं।

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` _एरर कोड_ से मेल खाता है।
हैंडलर तब मेल खाता है जब पैटर्न `-errorcode` लिस्ट का प्रीफिक्स हो।
यह भरोसे के साथ एरर का प्रकार पहचान लेता है।

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

एक खाली पैटर्न, `trap {}`, किसी भी एरर से मेल खाता है।
हैंडलर क्रम से जाँचे जाते हैं, इसलिए सब कुछ पकड़ने वाले को सबसे अंत में रखिए।

## एरर कोड ढूँढना

`ARITH DIVZERO` के बारे में कहाँ लिखा है?
ज़्यादातर सिर्फ सोर्स कोड में, लेकिन Tcl आपको दिखा देगा।
एरर के बाद, ग्लोबल वेरिएबल `errorCode` में सबसे हाल की एरर का एरर कोड रहता है:

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

किसी प्रोग्राम के अंदर, इसे ऑप्शंस डिक्शनरी से निकालिए:

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

एरर कोड का अंतिम एलिमेंट अक्सर इंसान के पढ़ने योग्य संदेश होता है, या उस चीज़ का नाम जिसने एरर पैदा की।
इसे अपने `trap` पैटर्न से बाहर रखिए: `{ARITH DIVZERO}` पकड़िए, `{ARITH DIVZERO {divide by zero}}` नहीं।

### कुछ आम एरर कोड

यह तालिका पूरी नहीं है।
किसी भी दूसरी एरर का कोड ढूँढने के लिए ऊपर का तरीका इस्तेमाल कीजिए।

| स्थिति             | उदाहरण                  | एरर कोड                    |
| --------------------- | ------------------------ | ----------------------------- |
| शून्य से भाग      | `expr {1 / 0}`           | `ARITH DIVZERO ...`           |
| गणित डोमेन एरर     | `expr {sqrt(-1)}`        | `ARITH DOMAIN ...`            |
| फाइल नहीं मिली        | `open nosuchfile r`      | `POSIX ENOENT ...`            |
| अनुमति नहीं     | `open /root/x w`         | `POSIX EACCES ...`            |
| अज्ञात कमांड       | `no::such::proc`         | `TCL LOOKUP COMMAND name`     |
| अज्ञात वेरिएबल      | `set nosuchvar`          | `TCL LOOKUP VARNAME name`     |
| आर्गुमेंट की गलत संख्या  | `string length a b`      | `TCL WRONGARGS`               |
| अमान्य डिक्शनरी    | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`        |
| अमान्य लिस्ट          | `llength "a \{b"`        | `TCL VALUE LIST ...`          |

`POSIX` एरर कोड ऑपरेटिंग सिस्टम के `errno` नाम इस्तेमाल करते हैं, जैसे `ENOENT`, `EACCES` और `EEXIST`।

## संकेत: स्क्रिप्ट कहाँ चलती है

`handle_error` को उसके कॉलर से एक स्क्रिप्ट मिलती है।
अगर आप इसे `try $script` से चलाते हैं, तो यह `handle_error` के स्कोप में निष्पादित होती है, कॉलर के स्कोप में नहीं।
इसे वहीं निष्पादित करने के लिए जहाँ यह लिखी गई थी, [`uplevel`][uplevel] इस्तेमाल कीजिए: `try {uplevel 1 $script} ...`।

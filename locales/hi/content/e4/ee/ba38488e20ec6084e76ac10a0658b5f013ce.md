# परिचय

## अक्षर

**अक्षर एन्कोडिंग** एक खास तरीका है, जिससे किसी प्राकृतिक भाषा के पाठ के एलिमेंट को बाइट्स के क्रम के रूप में दर्शाया जाता है।
यहाँ "पाठ का एलिमेंट" किसी भी ऐसी इकाई को कह सकते हैं जिसका प्राकृतिक भाषा में कोई अर्थ हो, जैसे अक्षर, स्पेस, विराम चिह्न, इमोजी, आइडियोग्राम, इत्यादि।

NASM (द नेटवाइड असेंबलर, यानी वह असेंबलर जो इस ट्रैक में इस्तेमाल होता है) में **ASCII** का उपयोग करके डेटा परिभाषित करने की सुविधा है।

NASM में अक्षर कॉन्स्टेंट अधिकतम 8 बाइट तक लंबे हो सकते हैं और इन्हें सिंगल कोट (`'`), डबल कोट (`"`) या बैकटिक (`` ` ``) से परिभाषित किया जा सकता है:

```x86asm
mov rax, '0' ; this copies the ASCII character '0' (decimal value 48)
mov rcx, "z" ; this copies the ASCII character 'z' (decimal value 122)
mov rdx, ` ` ; this copies the ASCII character ' ' (decimal value 32)
```

खास अक्षरों को बैकटिक में ही परिभाषित करना होता है और उन्हें `\` से एस्केप करना होता है:

```x86asm
mov rax, `\n` ; this copies the ASCII character newline (decimal value 10)
mov rcx, `\t` ; this copies the ASCII character tab (decimal value 9)
```

ध्यान दीजिए कि x86-64 में किसी भी अक्षर एन्कोडिंग के लिए अलग डेटा टाइप के रूप में कोई बिल्ट-इन सुविधा नहीं है।
असेंबली में डेटा बाइट्स का क्रम होता है, और उन बाइट्स को अक्षर, संख्या या कुछ और समझना प्रोग्रामर पर छोड़ दिया जाता है।

उदाहरण के लिए, ASCII अक्षर '0' एक ही बाइट है जिसकी वैल्यू 48 है।
इसलिए किसी बाइट में 48 रखना ठीक वैसा ही है जैसे उसमें ASCII अक्षर '0' रखना:

```x86asm
mov al, '0' ; al has the value 48
mov cl, 48  ; cl has the value '0'
; al and cl now have the same value
```

इसी वजह से अक्षरों पर काम करने के लिए उन बाइट्स की वैल्यू को सीधे बदला जाता है:

```x86asm
mov al, 'A' ; al now has the value 'A', which is 65 in ASCII
add al, 32 ; al now has the value 97, which is 'a' in ASCII
; so, summing 32 to an uppercase ASCII letter makes it lowercase

mov al, 5 ; al now has the value 5
add al, 48 ; al now has the value 53, which is '5' in ASCII
; so, summing 48 (equivalently, '0') transforms a number between 0 and 9 into an ASCII digit
```

## स्ट्रिंग

**स्ट्रिंग** अक्षरों का एक क्रम है।
असेंबली में इसे आम तौर पर ऐरे के रूप में लागू किया जाता है।

NASM में स्ट्रिंग को उसी तरह घोषित किया जा सकता है जैसे कोई भी ऐरे घोषित किया जाता है:

```x86asm
section .data
    string1 db "h", "e", "l", "l", "o"
```

स्ट्रिंग और दूसरे ऐरे में एक फर्क यह है कि NASM में वैल्यू को कॉमा (`,`) से अलग किए बिना भी स्ट्रिंग घोषित करने की सुविधा है।
वैल्यू के बीच कॉमा लगाकर भी लिखा जा सकता है:

```x86asm
section .data
    string2 db "hello"
    string3 db "h", "ello"
```

ध्यान दीजिए कि जैसा ऊपर बताया गया, अक्षर केवल बाइट होते हैं (या Unicode एन्कोडिंग में बाइट्स का क्रम):

```x86asm
section .data
    string1 db "hi"
    string2 db "h", "i"
    string3 db 104, 105
; string1, string2 and string3 are all equivalent
```

चूँकि हर ASCII अक्षर एक ही बाइट लेता है, इसलिए बड़े साइज़ में उसके बाद आने वाली हर बाइट `0` होती है।
उदाहरण के लिए, `'a'` को क्वर्ड (8 बाइट) के रूप में घोषित करने का मतलब है कि पहली बाइट `'a'` (`97`) है और बाकी सात बाइट सब `0` हैं।

इस कारण ये सब एक जैसे हैं:

```x86asm
section .data
    ; in all of the following, "hello" takes 5 bytes
    string1 dw 'hello'         ; 3 words (2-byte) - 5 bytes for "hello" + 0
    string2 dw 'he', "ll", `o` ; 3 words (2-byte) - 5 bytes for "hello" + 0
    string3 db `hello`, 0      ; 6 bytes - 5 bytes for "hello" + 0
```

~~~~exercism/caution
असेंबली में स्ट्रिंग अपने आप किसी ASCII NUL अक्षर (वैल्यू `0`) पर खत्म नहीं होती।

C जैसी उच्च-स्तरीय भाषाओं के साथ इंटरफ़ेस बनाते समय यह प्रोग्रामर की जिम्मेदारी है कि वह स्ट्रिंग के अंत में सही टर्मिनेटर लगाए, अगर कोई टर्मिनेटर चाहिए तो।
~~~~

## स्ट्रिंग निर्देश

चूँकि स्ट्रिंग ऐरे होती हैं, आप उन पर किसी भी ऐरे की तरह काम कर सकते हैं, यानी मेमोरी को सीधे डीरेफ़रेंस करके:

```x86asm
section .data
    hello_msg db "hello", 0

section .text
fn:
    lea rdi, [rel hello_msg]
    mov al, byte [rdi]       ; al == 'h'
    mov cl, byte [rdi + 4]   ; cl == 'o'
    ret
```

इसके अलावा, मेमोरी में बाइट्स के क्रम में वैल्यू लोड करने, एक जगह से दूसरी जगह ले जाने और संग्रहीत करने के लिए कुछ निर्देश हैं।
हालाँकि इन्हें _स्ट्रिंग निर्देश_ कहा जाता है, इनका उपयोग मेमोरी में बाइट्स के किसी भी क्रम के साथ, यानी किसी भी ऐरे के साथ किया जा सकता है।

तीन सबसे ज़रूरी स्ट्रिंग निर्देश हैं `lods`, `stos` और `movs`:

| निर्देश | यह क्या करता है                                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| `lods`      | `rsi` से बताई गई मेमोरी लोकेशन से एक वैल्यू `rax` में लोड करता है                                                  |
| `stos`      | `rax` से एक वैल्यू को `rdi` से बताई गई मेमोरी लोकेशन में संग्रहीत करता है                                           |
| `movs`      | `rsi` से बताई गई मेमोरी लोकेशन से एक वैल्यू कॉपी करता है और उसे `rdi` से बताई गई मेमोरी लोकेशन में संग्रहीत करता है  |

ध्यान दीजिए कि ये निर्देश कोई स्पष्ट ऑपरेंड नहीं लेते।
इनके ऑपरेंड अपने आप तय माने जाते हैं।

मोटे तौर पर एक नियम यह है:

1. जब इनका सोर्स ऑपरेंड कोई मेमोरी लोकेशन हो, तो उसका एड्रेस `rsi` में रखा जाना चाहिए (`s` यानी source)।
2. जब इनका डेस्टिनेशन ऑपरेंड कोई मेमोरी लोकेशन हो, तो उसका एड्रेस `rdi` में रखा जाना चाहिए (`d` यानी destination)।
3. अगर कोई एक ऑपरेंड मेमोरी लोकेशन न हो, तो वह `rax` रजिस्टर होता है।

ध्यान दीजिए कि ये निर्देश जो काम करते हैं, उसी के हिसाब से मेमोरी एड्रेस को अपने आप डीरेफ़रेंस कर लेते हैं।

ये सभी अलग-अलग साइज़ में काम कर सकते हैं।
साइज़ बताने के लिए निर्देश के नाम के अंत में एक सफिक्स लगाया जाता है:

| सफिक्स | मतलब | साइज़    |
| :----: | ------- | :------ |
|  `b`   | बाइट    | 1 बाइट  |
|  `w`   | वर्ड    | 2 बाइट  |
|  `d`   | ड्वर्ड   | 4 बाइट  |
|  `q`   | क्वर्ड   | 8 बाइट  |

उदाहरण के लिए:

```x86asm
movsb ; copies one byte from the memory location whose address is in `rsi` and stores it into the memory location whose address is in `rdi`
lodsq ; copies one qword (8 bytes) from the memory location whose address is in `rsi` and stores it in `rax`
stosw ; stores one word (2 bytes) from `ax` into the memory location whose address is in `rdi`
```

ये जिन-जिन एड्रेस का उपयोग करते हैं, उन्हें भी ऑपरेशन के साइज़ के हिसाब से अपडेट कर देते हैं।
यह अपडेट **डायरेक्शन फ्लैग (DF)** की वैल्यू के अनुसार होता है:

- अगर `DF` क्लियर है, तो एड्रेस ऑपरेशन के साइज़ के बराबर _बढ़ जाते हैं_।
- अगर `DF` सेट है, तो एड्रेस उतने ही _घट जाते हैं_।

System V ABI कहता है कि फंक्शन में प्रवेश करते समय डायरेक्शन फ्लैग क्लियर होना चाहिए।
इसलिए _डिफ़ॉल्ट व्यवहार यह है कि मेमोरी को एड्रेस के बढ़ते क्रम में पढ़ा और लिखा जाता है_।

डायरेक्शन फ्लैग क्लियर करने के लिए `cld` निर्देश का उपयोग किया जा सकता है, और उसे सेट करने के लिए `std` निर्देश का:

```x86asm
lea r8, [rdi]
lea r9, [rsi]

movsq ; both rdi and rsi increase (because `DF` is cleared by default) by 8 (`q` for qword)
; so now:
; rdi == r8 + 8
; rsi == r9 + 8

std ; sets `DF`
lodsw ; rsi decreases (because `DF` is set) by 2 (`w` for word)
; so now:
; rdi == r8 + 8
; rsi == r9 + 8 - 2 == r9 + 6

cld ; clears `DF`
stosd ; rdi increases (because `DF` is cleared) by 4 (`d` for dword)
; so now:
; rdi == r8 + 8 + 4 == r8 + 12
; rsi == r9 + 6
```

~~~~exercism/caution
System V ABI के अनुसार, कॉलर की अपेक्षा होती है कि कोई भी कॉल किया गया फंक्शन लौटने के बाद `DF` क्लियर हो।

अगर आप कभी `DF` सेट करें, तो `ret` से पहले उसे क्लियर करना न भूलें।
~~~~

### Rep

इनके अलावा, **rep** निर्देश सीधे मेमोरी से कोई लेना-देना नहीं रखता।
इसके बजाय इसे ऊपर बताए गए दूसरे निर्देशों के आगे प्रीफिक्स की तरह लगाया जा सकता है, जिससे वे निर्देश _बार-बार दोहराए जाते हैं_।

जब इनके आगे `rep` लगाया जाता है, तो स्ट्रिंग निर्देश उतनी बार दोहराए जाते हैं जितनी `rcx` में वैल्यू होती है।
हर बार `rcx` की वैल्यू `1` कम हो जाती है।
ध्यान दीजिए कि निर्देश का उपयोग करने से पहले `rcx` की वैल्यू सेट करना ज़रूरी है:

```x86asm
mov rcx, 4
rep movsq ; this repeats `movsq` 4 times
          ; it copies 4 * 8 == 32 bytes from a memory location indicated by `rsi` to a memory location indicated by `rdi`
```

~~~~exercism/advanced
आधुनिक CPU पर, बड़े ब्लॉक में डेटा ले जाते समय `rep movs` और `rep stos` आम तौर पर तेज़ विकल्प होते हैं।
लेकिन बाकी स्ट्रिंग निर्देश, और `rep` के बिना चलने वाले `movs` और `stos` भी, आम तौर पर एक साधारण लूप से धीमे होते हैं।

इस विषय पर और गहराई से जानकारी [इस संदर्भ पुस्तक के अध्याय 16.9, "String instructions"][agner-optimization-guide] में मिल सकती है।

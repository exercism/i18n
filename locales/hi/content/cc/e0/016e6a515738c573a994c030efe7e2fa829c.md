# इसके बारे में

C# के `struct` का `class` से गहरा संबंध है।
इनमें स्थिति और व्यवहार दोनों होते हैं।
इनमें वही तरह के मेंबर हो सकते हैं: कंस्ट्रक्टर, मेथड, फील्ड, प्रॉपर्टी, इत्यादि।

फील्ड और प्रॉपर्टी साधारण टाइप, `struct` या रेफरेंस टाइप हो सकते हैं।
जहाँ तक स्कोप, पढ़ने-लिखने के नियमों और एक्सेस लेवल की बात है, `struct` वही नियमों का पालन करते हैं जो `class` करती हैं।

```csharp
enum Unit
{
    Kg,
    Lb
}

struct Weight
{
    private double count;
    private Unit unit;

    public Weight(double count, Unit unit)
    {
        this.count = count;
        this.unit = unit;
    }

    public override string ToString()
    {
        return count.ToString() + unit.ToString();
    }
}

new Weight(77.5, Unit.Kg).ToString();
// => "77.6Kg"
```

याद रखने वाली मुख्य बातों में से एक यह है कि जब किसी struct को किसी वेरिएबल को असाइन किया जाता है या पैरामीटर के रूप में भेजा जाता है, तो वैल्यू की प्रतिलिपि बन जाती है। इसलिए मूल वेरिएबल में किया गया बदलाव कॉपी किए गए वेरिएबल पर असर नहीं डालेगा, और इसका उल्टा भी सच है।
संक्षेप में, `struct` **वैल्यू टाइप** होते हैं।

यह [लेख][class-or-struct] `struct` और `class` के बीच के अंतरों पर चर्चा करता है।
इस लेख से आप देखेंगे कि `struct` आम तौर पर हल्के और [अपरिवर्तनीय][structs-immutable] होते हैं, हालाँकि कंपाइलर या रनटाइम इस निर्देश को (डिफ़ॉल्ट रूप से) लागू नहीं करते।

कुछ बातें हैं जिनसे आपका सामना होगा (और जिनकी याद कंपाइलर आपको दिलाएगा):

1. `struct` के मेंबर को इनलाइन इनिशियलाइज़ नहीं किया जा सकता।
2. `struct` को इनहेरिट नहीं किया जा सकता।
3. `struct` में हमेशा एक डिफ़ॉल्ट कंस्ट्रक्टर होता है, भले ही कोई गैर-डिफ़ॉल्ट कंस्ट्रक्टर दिया गया हो, और आप स्पष्ट रूप से बिना पैरामीटर वाला कंस्ट्रक्टर नहीं दे सकते।

ऊपर के बिंदु 1 और 3 के परिणामस्वरूप, `struct` बनाने वाले डेवलपर के पास कोई तरीका नहीं है जिससे वह अमान्य इंस्टेंस को अस्तित्व में आने से रोक सके।

## आम `struct`

डॉक्यूमेंटेशन से आप देखेंगे कि प्रिमिटिव और `struct` में गहरा संबंध है।
उदाहरण के लिए [`Int32/int`][int32] देखिए।
`struct` का एक अधिक पारंपरिक उदाहरण [`TimeSpan`][time-span] टाइप है।

`TimeSpan` के इंस्टेंस संख्याओं की तरह व्यवहार करते हैं, जिनमें `>` और `<` जैसे तुलना ऑपरेटर और अंकगणितीय ऑपरेटर होते हैं।
ज़रूरत पड़ने पर आप अपने `struct` के लिए ये ऑपरेटर भी लागू कर सकते हैं।

`TimeSpan` के बारे में एक बात ध्यान देने योग्य है: यह कई इंटरफेस लागू करता है, जैसे `IComparable<TimeSpan>`।
हालाँकि `struct` को दूसरे `struct` से व्युत्पन्न नहीं किया जा सकता, फिर भी ये इंटरफेस लागू कर सकते हैं।

## समानता

`struct` के लिए समानता की जाँच अक्सर `class` की तुलना में बहुत आसान हो सकती है, क्योंकि डिफ़ॉल्ट रूप से यह सीधे फील्ड की समानता की तुलना करती है।
`object.Equals()` (या `GetHashCode()`) को ओवरराइड करने की ज़रूरत नहीं है।
याद रखिए कि अगर आप `Object.GetHashCode()` पर निर्भर हैं, तो आपको यह भी सुनिश्चित करना होगा कि हैश कोड बनाने में शामिल फील्ड (यानी सभी फील्ड) तब न बदलें जब कोई हैश किया गया कलेक्शन इस्तेमाल में हो।
व्यावहारिक रूप से, इसका मतलब है कि इस तरह इस्तेमाल किए जाने वाले `struct` अपरिवर्तनीय होने चाहिए।

मेथड `Equals()` के विपरीत, समानता ऑपरेटर `==` और `!=` का कोई डिफ़ॉल्ट कार्यान्वयन नहीं होता।
अगर आपके `struct` को इनकी ज़रूरत है, तो आपको इन्हें खुद लागू करना होगा।

दूसरी ओर, यह [लेख][equality] बताता है कि अपने खुद के कस्टम `Equals()` और `GetHashCode()` मेथड बनाकर परफॉर्मेंस को कैसे बेहतर बनाया जा सकता है, जैसा अक्सर `class` के साथ किया जाता है।
इस अभ्यास में अंतर लगभग 20% था, हालाँकि वह तुलना बहुत कठोर नहीं थी। यह आँकड़ा कम पड़ सकता है, क्योंकि सभी फील्ड एक ही टाइप के हैं। नीचे देखिए।

[वेब][equality-performance] पर गति सुधारों पर चर्चाएँ हैं: अगर सभी फील्ड एक ही टाइप के हों, तो `Equals()` मेथड को ओवरराइड नहीं किया जाता।
इस अभ्यास में अलग-अलग टाइप के फील्ड शामिल करने पर अंतर लगभग 60% था।
यह Microsoft के डॉक्यूमेंटेशन में नहीं लिखा है, इसलिए यह एक अनडॉक्यूमेंटेड कार्यान्वयन विवरण है, और इसका इस्तेमाल सोच-समझकर ही करना चाहिए।

```csharp
public bool Equals(Weight other)
{
    return count.Equals(other.count) && unit.Equals(other.unit);
}

public override bool Equals(object obj)
{
    return obj is Weight other && Equals(other);
}

public override int GetHashCode()
{
    return HashCode.Combine(count, unit);
}
```

# परिचय

पिछले कॉन्सेप्ट में बताया गया था कि लोकल लेबल और फंक्शन, दोनों ही निष्पादन योग्य कोड वाले किसी सेक्शन, जैसे `section .text`, में सिर्फ एड्रेस होते हैं।

वास्तव में, फंक्शन के साथ भी किसी भी मेमोरी एड्रेस की तरह ही काम किया जा सकता है, यानी उन्हें रजिस्टर में लोड किया जा सकता है, इधर-उधर भेजा जा सकता है, और मेमोरी में संग्रहीत किया जा सकता है।
`call` या `jmp` की मदद से कोड का निष्पादन किसी रजिस्टर या मेमोरी में रखे फंक्शन पर भी भेजा जा सकता है:

```x86asm
section .text
sum_op:
    lea rax, [rdi + rsi] ; loads the sum rdi + rsi into rax
    ret

apply_sum:
    lea rax, [rel sum_op]
    jmp rax              ; tail call
```

जिस फंक्शन एड्रेस को किसी वैल्यू की तरह इधर-उधर भेजा जाता है, उसे [थंक][thunk] कहते हैं।
थंक असेंबली में [हायर-ऑर्डर प्रोग्रामिंग][higher-order] की बुनियाद हैं: ऐसा कोड जो दूसरे कोड पर काम करता है।

## डेटा के रूप में कोड

फंक्शन एड्रेस को मेमोरी में संग्रहीत करके बाद में फिर से निकाला भी जा सकता है:

```x86asm
section .bss
    cached_fn resq 1

section .text
save_op:
    mov qword [rel cached_fn], rdi
    ret

apply_op:
    ; arguments are already set up according to the ABI
    jmp qword [rel cached_fn] ; tail call
```

`save_op` जो फंक्शन एड्रेस मिलता है, उसे `cached_fn` में लिख देता है।
`save_op` के लौटने के बाद भी यह वैल्यू बनी रहती है, इसलिए `apply_op` को बाद में कभी भी कॉल करने पर वह अंतिम बार संग्रहीत एड्रेस पर टेल कॉल करता है।
इससे यह संभव हो जाता है कि रनटाइम पर `apply_op` किस फंक्शन को कॉल करता है, यह बदला जा सके।

## डिस्पैच टेबल

फंक्शन एड्रेस को ऐरे में संग्रहीत करने से किसी इंडेक्स के आधार पर अलग-अलग फंक्शन चुने जा सकते हैं, और यह इंडेक्स किसी रनटाइम शर्त पर भी निर्भर हो सकता है।
इसे [डिस्पैच टेबल][dispatch-table] कहते हैं:

```x86asm
section .data
    dispatch_table dq add_op, sub_op, mul_op

section .text
dispatch:
    ; this function takes two arguments in rdi and rsi, and an index in rdx
    ; it then applies the function corresponding to the index in rdx to the arguments
    lea rax, [rel dispatch_table]
    jmp qword [rax + 8*rdx]  ; tail-call the function address for the index
```

## स्टेटफुल थंक

ऐसा थंक जो कॉल के बीच किसी स्थायी मेमोरी को पढ़ता या बदलता है, वह इस बात पर निर्भर करके अलग तरह से व्यवहार कर सकता है कि उससे पहले क्या हुआ था।
ऐसे थंक का परिणाम केवल अपने आर्गुमेंट पर ही निर्भर नहीं होता, बल्कि और चीज़ों पर भी निर्भर हो सकता है।

उदाहरण के लिए, एक _काउंटर_ जो एक फंक्शन लेता है और उसे मौजूदा काउंट के साथ कॉल करता है, और हर बार काउंट आगे बढ़ाता है:

```x86asm
section .data
    count dq 0

section .text
tick:
    mov rax, rdi               ; saves the function address
    mov rdi, [rel count]       ; loads the current count as the function's argument
    inc qword [rel count]      ; advances the count
    jmp rax                    ; tail-calls the function
```

`tick` दिए गए फंक्शन को मौजूदा काउंट के साथ आर्गुमेंट की तरह कॉल करता है, और फिर काउंट को आगे बढ़ा देता है।
तो पहली बार `tick(square)` कॉल करने पर `square(0)` कॉल होता है, अगली बार `tick(square)` से `square(1)`, उसके बाद `square(2)`, और इसी तरह।

एक और उदाहरण _विलंबित गणना_ हो सकता है:

```x86asm
section .bss
    captured_fn resq 1
    argument resq 1

section .text
delay:
    mov qword [rel captured_fn], rdi ; saves the function
    mov qword [rel argument], rsi    ; saves the argument
    lea rax, [rel invoke]            ; returns the `invoke` function
    ret

invoke:
    mov rdi, qword [rel argument]    ; loads the saved argument into `rdi`
    jmp qword [rel captured_fn]      ; tail-calls the saved function
```

`delay` एक फंक्शन और एक वैल्यू लेता है, उन्हें संग्रहीत करता है, और `invoke` लौटाता है।
`invoke` को कॉल करने पर वह कैप्चर किए गए फंक्शन को सहेजे गए आर्गुमेंट के साथ चलाता है।

हायर-लेवल भाषाओं में आम तौर पर मिलने वाले बहुत से पैटर्न, जैसे कॉलबैक, वर्चुअल मेथड, जनरेटर, करीइंग, फंक्शन कंपोज़िशन और ऐसे ही कई और, स्थायी स्थिति के साथ जोड़े गए थंक पर ही टिके होते हैं।

## स्क्रिप्ट का उपयोग

टेस्ट जनरेट करने के लिए [problem-specifications][problem-specifications] रिपॉज़िटरी की एक लोकल कॉपी ज़रूरी है। अभ्यासों तक सही तरीके से पहुँचने के लिए यह स्क्रिप्ट रूट `python` डायरेक्टरी से चलाई जानी चाहिए।

उपयोग की जानकारी के लिए `bin/generate_tests.py --help` चलाइए।


## टेस्ट टेम्पलेट

[Jinja2] सिंटैक्स वाले टेस्ट टेम्पलेट में कैनोनिकल डेटा से ये कॉन्टेक्स्ट वेरिएबल उपलब्ध रहते हैं:
- `exercise`: अभ्यास का हाइफन लगा नाम (जैसे: `two-fer`)
- `version`: कैनोनिकल डेटा का वर्ज़न (जैसे `1.2.0`)
- `cases`: केस ऑब्जेक्ट का ऐरे, या `cases` ऐरे का ऐरे। जिस अभ्यास पर आप काम कर रहे हैं उसकी सटीक संरचना के लिए `canonical-data.json` देखिए।
- `has_error_case`: बताता है कि किसी टेस्ट केस में कोई एरर आने की अपेक्षा है या नहीं (जैसे: `False`)
- `additional_cases`: संरचना `cases` जैसी ही है, लेकिन यह अभ्यास की `.meta/additional_tests.json` फाइल से भरा जाता है, अगर वह फाइल मौजूद हो (उदाहरण के लिए `exercises/word-count/.meta/additional_tests.json` देखिए)

इसके अलावा, सुविधा के लिए ये टेम्पलेट फिल्टर भी जोड़े गए हैं:
- `to_snake`: स्ट्रिंग को snake_case में बदलता है (जैसे: `{{ "CamelCaseString" | to_snake }}` -> `camel_case_string`)
- `camel_case`: स्ट्रिंग को CamelCase में बदलता है (जैसे: `{{ "snake_case_string" | camel_case }}` -> `SnakeCaseString` )
- `error_case`: जाँचता है कि किसी टेस्ट केस में एरर आने की अपेक्षा है या नहीं (जैसे: `{% for case in cases%}{% if case is error_case}`)
- `regex_replace`: रेजेक्स से स्ट्रिंग बदलना (जैसे: `{{ "abc123" | regex_replace("\\d", "D") }}` -> `abcDDD`)


### कन्वेंशन

- बहुत बार दोहराई जाने वाली टेम्पलेट संरचनाओं के लिए सामान्य उपयोग के मैक्रो `config/generator_macros.j2` में परिभाषित हैं।
  - इन्हें इस तरह इम्पोर्ट किया जा सकता है:
  `{%- import "generator_macros.j2" as macros with context -%}`
- सभी टेस्ट टेम्पलेट का अंत `{{ macros.footer() }}` से होना चाहिए।
- Python में सभी क्लास के नाम CamelCase में होने चाहिए (जैसे: `TwoFer`)।
  - बदलाव के लिए `{{ "two-fer" | camel_case }}` इस्तेमाल कीजिए।
- Python में सभी मॉड्यूल और फंक्शन के नाम snake_case में होने चाहिए (जैसे: `high_scores`, `personal_best`)।
  - बदलाव के लिए `{{ "personalBest" | to_snake }}` इस्तेमाल कीजिए।
- ट्रैक-विशिष्ट टेस्ट ऑप्शन फाइल `.meta/additional_tests.json` में परिभाषित किए जाते हैं। इस फाइल में परिभाषित JSON ऑब्जेक्ट में एक ही की, `cases`, होनी चाहिए, जिसकी संरचना `canonical-data.json` के `cases` जैसी ही हो।
- टेस्ट फाइलों में ट्रैक-विशिष्ट टेस्ट कैनोनिकल टेस्ट के बाद रखे जाने चाहिए।
- टेस्ट फाइल में ट्रैक-विशिष्ट टेस्ट को इस कमेंट से चिह्नित किया जाना चाहिए:
```
# Additional tests for this track
```


### लेआउट

अधिकतर टेम्पलेट कुछ इस तरह दिखते हैं:

```Jinja2
{%- import "generator_macros.j2" as macros with context -%}
{{ macros.header() }}

class {{ exercise | camel_case }}Test(unittest.TestCase):
    {% for case in cases -%}
    def test_{{ case["description"] | to_snake }}(self):
        value = {{ case["input"]["value"] }}
        expected = {{ case["expected"] }}
        self.assertEqual({{ case["property"] }}(value), expected)

    {% endfor %}

{{ macros.footer() }}
```


### इम्पोर्ट को बदलना

`macros.header()` में इम्पोर्ट किए गए नामों को बदला जा सकता है। इसके लिए इम्पोर्ट होने वाले वैकल्पिक नामों का एक ऐरे जोड़ दीजिए (जैसे: `clock`):

```Jinja2
{{ macros.header(["Clock"])}}
```


### प्रॉपर्टी को छोड़ना

कभी-कभार ऐसा हो सकता है कि इस ट्रैक में जिन प्रॉपर्टी की जाँच नहीं होती, उन्हें छानकर हटाना ज़रूरी हो जाए। `header` मैक्रो एक `ignore` आर्गुमेंट भी लेता है (जैसे: `high-scores`):

```Jinja2
{{ macros.header(ignore=["scores"]) }}
```

## टेम्पलेट बनाना

1. जिस अभ्यास को आप लागू कर रहे हैं उसके लिए `.meta/template.j2` बनाइए,
  और उसे अपने एडिटर में खोलिए।
2. टेम्पलेट फाइल में [उदाहरण लेआउट](#Layout) कॉपी-पेस्ट कीजिए
  और सेव कीजिए।
3. टेम्पलेट फाइल में उचित बदलाव तब तक कीजिए जब तक वह
  सही टेस्ट कोड न बनाने लगे। इनपुट के नाम और केस की संरचना के लिए
  अभ्यास की `canonical-data.json` देखिए।
    - दोहराए जाने वाले हिस्सों को फिर से लिखने से बचने के लिए [मौजूद मैक्रो](../config/generator_macros.j2) इस्तेमाल कीजिए।
    - अगर आप किसी मौजूदा अभ्यास के लिए टेम्पलेट बना रहे हैं,
    तो मौजूदा टेस्ट फाइल की संरचना से बिल्कुल मेल खाना ज़रूरी
    नहीं है, लेकिन अंतर कम रखने से इसमें शामिल सभी लोगों के लिए
    PR रिव्यू कहीं ज़्यादा आसान हो जाता है।

# परिचय

## एरर में संदर्भ जोड़ना

Go में बुनियादी एरर हैंडलिंग हमने [एरर कॉन्सेप्ट][concept-errors] में देखी थी।
जैसा कि आपने वहाँ सीखा, डिफ़ॉल्ट रूप से एरर अपने साथ स्टैक ट्रेस नहीं रखती।
इसलिए यह ज़रूरी हो जाता है कि एरर में ही समस्या पहचानने लायक पर्याप्त जानकारी हो।

अगर हम किसी मौजूदा एरर में जानकारी जोड़ना चाहें और उसके लिए वही तरीके इस्तेमाल करें जो हमें पहले से आते हैं, तो हम कुछ इस तरह लिख सकते हैं। इससे मूल एरर के टेक्स्ट और अतिरिक्त जानकारी को मिलाकर एक नया एरर बनेगा:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

अच्छी बात है कि स्टैंडर्ड लाइब्रेरी के `fmt` पैकेज में इसका एक छोटा रूप `Errorf` फंक्शन के रूप में मौजूद है।
इससे आप, उदाहरण के लिए, उस संदर्भ की जानकारी आसानी से जोड़ सकते हैं जिसमें एरर हुई थी।

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

जब तक आपको पक्का न हो कि एरर में पहले से पर्याप्त जानकारी मौजूद है, आपको आदत बना लेनी चाहिए कि किसी फंक्शन से एरर लौटाने से पहले उसमें संदर्भ ज़रूर जोड़ें।
यानी आपका आम एरर हैंडलिंग पैटर्न कुछ इस तरह दिखना चाहिए:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

जैसा कि उदाहरणों में दिख रहा है, यहाँ तय तरीका यह है कि जोड़े गए संदेश को एरर से कोलन (:) से अलग किया जाए।
मूल एरर के संदेश की तरह संदर्भ वाले संदेश की भी शुरुआत बड़े अक्षर से नहीं होनी चाहिए और उसके अंत में पूर्ण विराम नहीं लगाना चाहिए।

~~~~exercism/note
किसी एरर में संदर्भ जोड़ते समय मन करता है कि संदेश "failed to ..." जैसा कुछ लिखकर शुरू किया जाए।
लेकिन जैसे-जैसे एरर फंक्शन की श्रृंखला में ऊपर जाती है, उसमें बहुत सारा अतिरिक्त संदर्भ जुड़ता चला जाता है। इससे अंतिम संदेश, जो लॉग में जाएगा या उपयोगकर्ता को दिखेगा, पढ़ने में कठिन या दोहराव से भरा हो सकता है।

इसे समझाने का एक उदाहरण यहाँ है:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

इसलिए संदर्भ वाले संदेश लिखते समय इस अंतिम परिणाम को ध्यान में रखिए और यह बताने वाला टेक्स्ट जोड़ने से बचिए कि कुछ अपेक्षा के मुताबिक नहीं हुआ।
यह आम तौर पर संदर्भ (जैसे लॉग लेवल "ERROR") और मूल एरर संदेश से ही साफ़ हो जाता है।
~~~~

अक्सर एरर में जानकारी जोड़ने का यह तरीका काफी अच्छा होता है, लेकिन कुछ मामलों में आप चाहते हैं कि आपकी एरर इस्तेमाल करने वाला कोड मूल एरर की जाँच कर सके या उसे वापस पा सके।
इस तरह संदर्भ जोड़ने, जिससे यह मुमकिन हो जाए, को Go में "एरर रैपिंग" कहा जाता है।

## एरर रैप करना और सेंटिनल एरर की जाँच करना

ऊपर देखे गए कोड में बहुत छोटा-सा बदलाव करके ही एरर रैपिंग की जा सकती है।
किसी एरर को रैप करने के लिए `%v` की जगह फॉर्मेटिंग वर्ब `%w` इस्तेमाल करना होता है।
अंदर ही अंदर यह सुनिश्चित करता है कि बनने वाली एरर में एक `Unwrap` मेथड हो, जो मूल एरर लौटाता है।
इसी वजह से `errors.Is` की मदद से यह जाँचा जा सकता है कि कोई खास सेंटिनल एरर "एरर चेन" में कहीं मौजूद है या नहीं।
यह काम वह चुपचाप `Unwrap` को बार-बार कॉल करके करता है, जब तक कि वह एरर मिल न जाए या चेन खत्म न हो जाए।

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

आम `%v` फॉर्मेटिंग वर्ब के साथ `errors.Is` से मूल एरर की जाँच काम नहीं करेगी।

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

इसलिए यह अच्छा तरीका है कि डिफ़ॉल्ट रूप से `%v` इस्तेमाल करें और `%w` सिर्फ तब इस्तेमाल करें जब आप साफ़ तौर पर चाहते हों कि आपकी एरर इस्तेमाल करने वाला कोड मूल एरर तक पहुँच सके ([Google Go Styleguide][google-go-styleguide])।

अगर आप ऐसी स्थिति में हों जहाँ सेंटिनल एरर की जाँच करनी है लेकिन साफ़ तौर पर अनरैप नहीं करना है, तो `errors.Is` की जगह `==` इस्तेमाल कर सकते हैं।

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

इसके उलट, अगर एरर रैप की गई हो तो `==` उसे पहचान नहीं पाएगा।

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

डिफ़ॉल्ट रूप से `errors.Is` के साथ काम करना ठीक है, लेकिन आपको हमेशा यह ध्यान रखना चाहिए कि इससे पूरी एरर चेन खोजी जाती है।

## (कस्टम) एरर टाइप की जाँच करना

`errors.Is` जैसा ही एक और फंक्शन है, जो एरर चेन में से किसी खास टाइप की एरर की जाँच करने और उसे निकालने की सुविधा देता है।
इसके लिए फंक्शन है `errors.As`, और `errors.Is` की तरह यह भी दिए गए एरर टाइप को पूरी चेन में खोजता है।
`errors.As` तभी उस एरर को निकालता है जो टाइप से मेल खाती है, ताकि आप उस पर आगे काम कर सकें, जैसे उसके कुछ खास फील्ड निकाल सकें।

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
ऊपर दिए गए पॉइंटर से जुड़े सिंटैक्स को लेकर सावधान रहिए।
कोड तभी ठीक से काम करेगा और कंपाइल होगा जब `customError` का टाइप ठीक वही हो जो एरर इंटरफ़ेस लागू करता है।
हमारे मामले में वह `*MyCustomError` है (`MyCustomError` का एक [पॉइंटर][concept-pointers]), न कि खुद `MyCustomError`।

इसके अलावा, दूसरा आर्गुमेंट एरर वेरिएबल का पॉइंटर होना चाहिए।
चूँकि हमारी एरर पहले से ही एक पॉइंटर है, तो `errors.As` को जो हम दे रहे हैं वह एक पॉइंटर का पॉइंटर है (MyCustomError का)।
सिर्फ इस तरह ठीक से सेट होने पर ही Go उस वेरिएबल में मिली हुई एरर भर पाता है।
~~~~

पहले की तरह, अगर `Errorf` कॉल करते समय `%v` इस्तेमाल किया गया होता, तो `errors.As` वह एरर टाइप नहीं ढूँढ पाता।

अगर किसी वजह से आप अनरैप नहीं करना चाहते, तो इसकी जगह टाइप असर्शन इस्तेमाल किया जा सकता है (ऊपर के `==` के बराबर)।

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

अगर एरर रैप की गई होती, तो टाइप असर्शन उसका टाइप पहचान नहीं पाता।

## कस्टम टाइप की एरर को अनरैप करने देना

कभी-कभी किसी एरर को सिर्फ कुछ अतिरिक्त टेक्स्ट के साथ रैप करना काफी नहीं होता।
इसके बजाय आप एक कस्टम एरर टाइप बना सकते हैं, जिसमें मूल एरर और जो अतिरिक्त स्ट्रक्चर्ड डेटा आप जोड़ना चाहते हैं, दोनों रहें।
अगर आप अपने एरर टाइप के लिए अनरैपिंग की सुविधा देना चाहते हैं, तो बस एक काम करना है: खुद से एक `Unwrap() error` मेथड जोड़ दीजिए, जिससे `Unwrap` इंटरफ़ेस पूरा हो जाए।

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## कई एरर को मिलाना

Go 1.20 में बिल्ट-इन `errors` पैकेज में एक नया `Join` फंक्शन जोड़ा गया।
`Join` कई एरर को इस तरह जोड़ता है कि अनरैपिंग अब भी मुमकिन रहती है, यानी चेन में किसी खास एरर या एरर टाइप की जाँच की जा सकती है।
इसके साथ, एरर चेन असल में एक एरर ट्री भी हो सकती है।
अधिक जानकारी [रिलीज़ नोट्स][release-notes] और [डॉक्युमेंटेशन][doc-join] में मिल सकती है।

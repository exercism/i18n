# परिचय

C भाषा में **struct** एक संयुक्त टाइप होता है, जो अलग-अलग फील्ड से बनता है।
हर फील्ड का अपना टाइप और अपना आकार होता है।

उदाहरण के लिए, यह एक ऐसा टाइप परिभाषित करता है जो तीन पूर्णांकों से बना है: दो 4 बाइट के और एक 8 बाइट का:

```c
struct example {
    int32_t first_four_byte_integer;
    uint32_t second_four_byte_integer;
    uint64_t eight_byte_integer;
};
```

एक struct में दूसरे struct भी हो सकते हैं:

```c
struct example_2 {
    struct example first;
    struct example second;
};
```

अगर struct का कोई फील्ड ऐरे है, तो ऐरे के लिए आवंटित सारे बाइट उस struct का ही हिस्सा होते हैं।
लेकिन अगर फील्ड सिर्फ ऐरे का पॉइंटर है, तो ऐरे को कहीं और संग्रहीत करना पड़ता है:

```c
struct with_array {
    char string[20];
};
// all 20 bytes of string are inside struct with_array

struct with_pointer {
    const char *string;
};
// only the 8-byte pointer to the string is inside struct with_pointer
```

## अलाइनमेंट

किसी टाइप की **अलाइनमेंट** दो की एक गैर-ऋणात्मक घात (1, 2, 4, 8, ...) होता है, जो उसके एड्रेस पर लगने वाली एक शर्त बताता है।
उस टाइप के हर ऑब्जेक्ट को ऐसे एड्रेस पर होना चाहिए जो उसकी अलाइनमेंट का गुणज हो।

किसी प्रिमिटिव टाइप की अलाइनमेंट आम तौर पर उसके आकार के बराबर होता है। इसलिए, उदाहरण के लिए, एक `int32_t` की अलाइनमेंट आम तौर पर 4 बाइट का होता है।
इसका मतलब है कि `int32_t` को 4 बाइट की सीमाओं पर ही आवंटित किया जाना चाहिए।

लेकिन किसी struct की अलाइनमेंट उसके सारे फील्ड की अलाइनमेंट में सबसे बड़ा होता है।
तो, उदाहरण के लिए, ऊपर परिभाषित `struct example` की अलाइनमेंट 8 बाइट का होगा, क्योंकि `uint64_t` की अलाइनमेंट इतना ही है।

अगर किसी struct के फील्ड की अलाइनमेंट struct की अलाइनमेंट से छोटा है, तो उस फील्ड के बाद पैडिंग बाइट डाले जा सकते हैं।
इससे यह पक्का होता है कि आगे वाले फील्ड और पूरा struct अलाइनमेंट की आवश्यकताएँ पूरी करें।
व्यवहार में इसका मतलब है कि ये पैडिंग बाइट struct के आकार में जुड़ते तो हैं, लेकिन struct की वैल्यू में इस्तेमाल नहीं होते:

```c
struct example_3 {
    char one_byte; // alignment of 1
    int four_byte; // alignment of 4
};
// example_3 has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one_byte'
// 3 padding bytes (with undefined value)
// 4 bytes for field 'four_byte'
```

ध्यान दीजिए कि ऊपर परिभाषित struct में फील्ड 'one_byte' की अलाइनमेंट 1 है और इसे किसी भी एड्रेस पर रखा जा सकता है।
चूँकि फील्ड 'four_byte' की अलाइनमेंट 4 है, struct के फील्ड को भी 4 बाइट की सीमाओं का पालन करना होता है।
इसका मतलब है कि struct के किन्हीं दो फील्ड के बीच बाइट की संख्या 4 का गुणज होनी चाहिए।
चूँकि 'one_byte' सिर्फ 1 बाइट घेरता है, इसलिए इस सीमा का पालन करने के लिए इसके बाद 3 पैडिंग बाइट डाले जाते हैं।

पैडिंग बाइट की संख्या कम से कम करने के लिए आसन्न फील्ड को जहाँ तक संभव हो एक साथ समूहित किया जाता है:

```c
struct two_padding {
    char one; // alignment of 1
    char two; // alignment of 1
    int three; // alignment of 4
};
// struct two_padding has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one'
// 1 byte for field 'two'
// 2 padding bytes
// 4 bytes for field 'three'
```

इस समूहन को हर फील्ड की अलाइनमेंट का भी पालन करना होता है:

```c
struct one_padding {
    char one; // alignment of 1
    int16_t two; // alignment of 2
    int three; // alignment of 4
};
// struct one_padding has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one'
// 1 padding byte
// 2 bytes for field 'two'
// 4 bytes for field 'three'
// Since 'two' has alignment of 2, it must be placed in a 2-byte boundary
// So, there must be 1 padding byte between 'one' and 'two'
```

इसका मतलब है कि struct में फील्ड का क्रम बदल देने से कभी-कभी उसके आकार में फर्क पड़ सकता है:

```c
struct example_4 {
    int64_t one;
    short two;
    int32_t three;
};
// example_4 has one 8-byte field, one 4-byte field and one 2-byte field
// it has an alignment of 8 and occupies 16 bytes in space:
// 8 bytes for field 'one'
// 2 bytes for field 'two'
// 2 padding bytes
// 4 bytes for field 'three'
// two' and 'three' are adjacent and can be grouped to sum up 8 bytes with only 2 bytes of padding

struct example_5 {
    short one;
    int64_t two;
    int32_t three;
};
// example_5 also has one 8-byte field, one 4-byte field and one 2-byte field, in different positions
// it also has an alignment of 8, however, it occupies 24 bytes in space:
// 2 bytes for field 'one'
// 6 bytes for padding
// 8 bytes for field 'two'
// 4 bytes for field 'three'
// 4 bytes for padding
// 'one' can't be grouped with 'two' because their sum would be higher than the struct's alignment
// 'two' and 'three' also can't be grouped, for the same reason
// so padding bytes must be inserted in full after each field with less than 8 bytes in alignment
```

ध्यान दीजिए कि किसी ऐरे का अलाइनमेंट उसके अंतर्निहित टाइप के अलाइनमेंट के बराबर होता है:

```c
struct array_example {
    char string[10]; // alignment of 1
};
// array_example has alignment of 1 (it can be placed at any address)
// it occupies 10 bytes in space, one for each char in 'string'
```

किसी ऐरे के एलिमेंट को उसी तरह समूहित किया जा सकता है जैसे वे ऐरे का हिस्सा न हों:

```c
struct group_array {
    int16_t arr[3];
    int8_t one_byte;
    int32_t four_byte;
};
// group_array has alignment of 4 because this is the alignment of 'four_byte'
// it occupies 12 bytes in space:
// 4 bytes for arr[0] and arr[1]
// 2 bytes for arr[2]
// 1 byte for 'one_byte'
// 1 padding byte (arr[2] is grouped with 'one_byte')
// 4 bytes for 'four_byte'
```

असेंबली में struct को एक्सेस करते समय हर संभव पैडिंग बाइट का हिसाब रखना ज़रूरी है।

## कॉलिंग कन्वेंशन

आम तौर पर, वैल्यू फंक्शन को भेजी जाती हैं और उनसे लौटाई जाती हैं, ठीक वैसे ही जैसी उम्मीद की जाती है:

- पूर्णांक वैल्यू, जिनमें मेमोरी एड्रेस और एनम भी शामिल हैं, सामान्य-उद्देश्य रजिस्टर (GPR) में भेजी जाती हैं।
- फ्लोटिंग-पॉइंट वैल्यू `xmm` रजिस्टर में भेजी जाती हैं।

लेकिन struct एक खास मामला है।
मोटे तौर पर, struct के सारे फील्ड मेमोरी में आसन्न जगह घेरते हैं और जहाँ तक संभव हो उन्हें एक ही रजिस्टर में रखा जाना चाहिए:

```c
struct single_type {
    int16_t first;
    int16_t second;
    int16_t third;
    int16_t fourth;
};
// this struct occupies 8 bytes
// it is entirely passed in the same GPR register:
// the field 'first' is passed on the lowest 2 bytes
// each subsequent field is passed in the following 2 bytes
```

अगर किसी struct में पूर्णांक वैल्यू वाले फील्ड भी हैं और फ्लोटिंग-पॉइंट वैल्यू वाले फील्ड भी, तो struct के हर लगातार 8 बाइट को अलग-अलग वर्गीकृत किया जाना चाहिए:

```c
struct mixed_types {
    double first;
    int second;
    int third;
};
// this struct occupies 16 bytes
// the field 'first' is passed in the first 8 bytes of a xmm register
// the fields 'second' and 'third' are passed in the same GPR register:
// the field 'second' is passed on the lowest 4 bytes
// the field 'third' is passed in the next 4 bytes
```

अगर पूर्णांक और फ्लोटिंग-पॉइंट वैल्यू एक ही 8 बाइट में हों, तो टाइप पूर्णांक माना जाता है और पूरा 8 बाइट (फ्लोटिंग-पॉइंट वैल्यू समेत) GPR में रखा जाता है:

```c
struct mixed_types {
    int32_t integer;
    float floating_point;
};
// this struct occupies 8 bytes
// it is entirely passed in the same GPR register:
// the field 'integer' is passed on the lowest 4 bytes
// the field 'floating_point' is passed on the next 4 bytes
```

~~~~exercism/caution
जब `cvtss2si` या `cvtsd2si` की मदद से फ्लोटिंग-पॉइंट से पूर्णांक में रूपांतरण किया जाता है, तो इससे अंतर्निहित बाइट की व्यवस्था बदल जाती है।

आप `movd` (32-बिट वैल्यू के लिए) और `movq` (64-बिट वैल्यू के लिए) का इस्तेमाल करके `xmm` रजिस्टर से GPR में कच्चे बाइट बिना बिट प्रतिनिधित्व बदले ले जा सकते हैं।
~~~~

लेकिन जिन struct का आकार 16 बाइट से ज़्यादा होता है, वे आम तौर पर मेमोरी में ही रखे जाते हैं, चाहे हर 8 बाइट का टाइप कुछ भी हो:

```c
struct big_struct {
    uint8_t first;
    double second;
    int64_t third;
};
// this struct occupies 24 bytes, including 7 padding bytes between 'first' and 'second'
// it is entirely passed in memory
```

जब किसी struct को फंक्शन के आर्गुमेंट के तौर पर भेजा जाता है, तो वह जितने रजिस्टर चाहिए उतने इस्तेमाल करता है।
अगर उसे मेमोरी में रखा जाता है, तो इसके बजाय स्टैक इस्तेमाल होता है।

इसी तरह के नियम फंक्शन से लौटाए गए struct पर भी लागू होते हैं।
ऐसे struct आम तौर पर पहले `rax` और `rdx` में लौटाए जाते हैं (अगर पूर्णांक वैल्यू का हो) या `xmm0` और `xmm1` में (अगर फ्लोटिंग-पॉइंट वैल्यू का हो)।
लेकिन अगर उसे मेमोरी में रखा जाता है, तो कॉलर को उसके लिए जगह आरक्षित करनी होती है और उस मेमोरी लोकेशन का एड्रेस फंक्शन के अंतर्निहित पहले आर्गुमेंट के तौर पर भेजना होता है (`rdi` में)।
फिर फंक्शन struct को इसी जगह संग्रहीत करता है और उसका एड्रेस `rax` में लौटाता है।

# नलैबिलिटी के बारे में

आदर्श दुनिया में हम यह भरोसा कर सकते थे कि हर चीज़ अच्छी तरह परिभाषित है, हर जगह ठोस वैल्यू हैं और कहीं कोई कमी नहीं है।

यह हमारे रोज़मर्रा के अनुभव से मेल नहीं खाता, इसलिए कई प्रोग्रामिंग भाषाओं में वैल्यू न होने को दिखाने का एक तरीका होता है: null या NULL, nil, None, nothing...

इसे शुरू करना आसान था (1965 में), पर जल्द ही इस पर पछतावा होने लगा। इसके आविष्कारक ने बाद में इसे अपनी ["बिलियन डॉलर मिस्टेक"][web-mistake] कहा।

हाल के दशकों में भाषा के डिज़ाइनरों ने कई ऐसे तरीके खोजे हैं जिनसे नल उपलब्ध भी रहें और (ज़्यादातर) सुरक्षित भी।

Kotlin में कुछ [सामान्य सिद्धांत][ref-null-safety] हैं, जो [Java से काफी अलग हैं][ref-java2kotlin]।
_इन अंतरों का मतलब है कि Kotlin में Java के साथ इंटरऑप के लिए खास सुविधाएँ हैं, हालाँकि उनका ब्यौरा इस कॉन्सेप्ट के दायरे से बाहर है।_

- Kotlin में एक खास `null` वैल्यू होती है।
- सभी टाइप _डिफ़ॉल्ट रूप से_ नॉन-नलैबल होते हैं (यानी वे `null` नहीं हो सकते)।
- सभी टाइप _नलैबल_ बनाए जा सकते हैं, पर यह स्पष्ट रूप से करना पड़ता है।
- जो फंक्शन एक्सेप्शन के साथ फेल हो सकते हैं, उनमें अक्सर नलैबल रिटर्न वैल्यू वाला एक और रूप भी होता है।
- खास और बहुत ही संक्षिप्त सिंटैक्स नल की जाँच करने और उससे निपटने को जितना आसान हो सके, उतना आसान बनाने की कोशिश करता है।

## नलैबल वेरिएबल बनाना

किसी टाइप को उसके बाद `?` लगाकर [नलैबल][ref-nullable-type] बनाया जा सकता है (जैसे `String` की जगह `String?`)।

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## काम के ऑपरेटर और फंक्शन

### [सेफ कॉल ऑपरेटर][ref-safe-call] `?.`

नॉन-नलैबल `String` पर हम `.length` प्रॉपर्टी पा सकते हैं।

नलैबल `String?` पर यही सिंटैक्स फेल हो जाता है, पर `?.length` इस्तेमाल करने से `null` होने की गुंजाइश बनी रहती है। इसका रिटर्न टाइप `Int?` होता है।

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

जैसा कि ऊपर की अंतिम लाइन में दिखा, `?.` नॉन-नलैबल टाइप के साथ भी काम करता है।

### [एल्विस ऑपरेटर][ref-elvis] `?:`

सेफ-कॉल ऑपरेटर के इसी विचार को आगे बढ़ाते हुए, [एल्विस ऑपरेटर][wiki-elvis] हमें `null` की जगह एक डिफ़ॉल्ट वैल्यू देने की सुविधा देता है।

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### [नॉट-नल असर्शन ऑपरेटर][ref-not-null] `!!`

इस ऑपरेटर से किसी नलैबल टाइप को नॉन-नल मानने के लिए बाध्य किया जाता है, तब जब प्रोग्रामर को इसका पूरा भरोसा हो। हो सकता है कि कभी-कभी हम प्रोग्राम का तर्क किसी ज़रूरत से ज़्यादा सतर्क कंपाइलर से बेहतर समझते हों?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

अब ज़िम्मेदारी हमारी है: अगर `b` अभी भी `null` है तो हमें `NullPointerException` मिलता है।

### [let फंक्शन][ref-let] `?.let`

अगर किसी कोड ब्लॉक को कोई नलैबल चीज़ देनी है, तो हम `if (item != null) { do something }` जैसी अलग-अलग नल जाँचें कर सकते हैं।

इसके बजाय `item?.let { do something }` इस्तेमाल करना ज़्यादा आसान और ज़्यादा स्वाभाविक है। `do something` सिर्फ़ तभी चलेगा जब `item` नल न हो।

### `somethingOrNone()` टाइप के फंक्शन

कुछ फंक्शन फेल भी हो सकते हैं, जैसे किसी स्ट्रिंग या ऐरे में गलत इंडेक्स माँगने पर।

एक्सेप्शन फेंकने के बजाय हम फंक्शन का [`...OrNull` वेरिएंट][ref-elem-at-or-null] इस्तेमाल कर सकते हैं, जिससे (इस मामले में) `Int?` रिटर्न वैल्यू मिलती है।

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

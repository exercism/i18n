# সম্পর্কে

## এররে প্রসঙ্গ যোগ করা

আমরা Go-তে [এরর কনসেপ্ট][concept-errors]-এ মৌলিক এরর হ্যান্ডলিং দেখেছি।
সেখানে আপনি শিখেছেন, ডিফল্টভাবে এররগুলো স্ট্যাক ট্রেস বহন করে না।
তাই সমস্যাটি চিহ্নিত করার জন্য এররটিতে যথেষ্ট তথ্য আছে কিনা তা নিশ্চিত করা অত্যন্ত জরুরি।

আমরা যদি ইতিমধ্যে জানা টুল দিয়ে একটি বিদ্যমান এররে তথ্য যোগ করতে চাই, তাহলে মূল এররের টেক্সট ও অতিরিক্ত তথ্য একসাথে নিয়ে একটি নতুন এরর তৈরি করতে এইরকম কিছু লিখতে পারি:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

ভাগ্যবশত, স্ট্যান্ডার্ড লাইব্রেরির `fmt` প্যাকেজে এর একটি সংক্ষিপ্ত রূপ আছে, যেটি হলো `Errorf` ফাংশন।
এটি আপনাকে, উদাহরণস্বরূপ, যে প্রসঙ্গে এররটি ঘটেছে সে সম্পর্কে তথ্য সহজেই যোগ করার সুযোগ দেয়।

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

আপনি যদি নিশ্চিত না হন যে এররটিতে ইতিমধ্যে যথেষ্ট তথ্য রয়েছে, তাহলে একটি ফাংশন থেকে রিটার্ন করার আগে সবসময় এররে প্রসঙ্গ যোগ করার অভ্যাস গড়ে তোলার চেষ্টা করা উচিত।
এর মানে হলো আপনার স্ট্যান্ডার্ড এরর হ্যান্ডলিং প্যাটার্নটি এরকম হওয়া উচিত:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

উদাহরণগুলিতে দেখানো হয়েছে, প্রথা হলো এরর থেকে যোগ করা বার্তাটিকে কোলন দিয়ে আলাদা করা।
মূল এররের বার্তার মতোই, প্রসঙ্গ বার্তাটিও বড় হাতের অক্ষরে শুরু করা উচিত নয় এবং শেষে কোনো দাঁড়ি বা পূর্ণচ্ছেদ যোগ করা উচিত নয়।

~~~~exercism/note
একটি এররে প্রসঙ্গ যোগ করার সময়, বার্তাটি "failed to ..." বা অনুরূপ কিছু দিয়ে শুরু করা লোভনীয়।
তবে, যেহেতু একটি এরর ফাংশন চেইনের উপরে উঠতে উঠতে অনেক অতিরিক্ত প্রসঙ্গ সঞ্চয় করতে পারে, এটি চূড়ান্ত বার্তাটি যা লগ করা হবে বা ব্যবহারকারী দেখবে তা পড়া কঠিন করে তুলতে পারে বা নকলপূর্ণ করে তুলতে পারে।

এটি বোঝানোর জন্য এখানে একটি উদাহরণ:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

তাই প্রসঙ্গ বার্তাগুলি লেখার সময় এই চূড়ান্ত ফলাফলটি মাথায় রাখুন এবং কোনো কিছু প্রত্যাশিতভাবে হয়নি এই বিষয়ে লেখা যোগ করা থেকে বিরত থাকুন।
এটি সাধারণত প্রসঙ্গ (যেমন লগ লেভেল "ERROR") এবং মূল এরর বার্তা থেকেই স্পষ্ট হয়।
~~~~

প্রায়শই একটি এররের জন্য তথ্য যোগ করার এই উপায়টি যথেষ্ট ভালো, তবে এমন কিছু ক্ষেত্রে আছে যেখানে আপনি চান আপনার এররের ব্যবহারকারী মূল অন্তর্নিহিত এররটি পরীক্ষা করতে বা পুনরুদ্ধার করতে পারবে।
এই ধরনের সুবিধা দেয় এমনভাবে প্রসঙ্গ যোগ করাকে Go-তে "এরর র‍্যাপিং" বলা হয়।

## এরর র‍্যাপিং এবং সেন্টিনেল এরর পরীক্ষা করা

আমরা উপরে যে কোডটি দেখেছি, তাতে খুব ছোট একটি পরিবর্তন করে এরর র‍্যাপিং করা যায়।
একটি এরর র‍্যাপ করতে, আপনাকে `%v`-এর পরিবর্তে ফরম্যাটিং ভার্ব `%w` ব্যবহার করতে হবে।
পর্দার আড়ালে, এটি নিশ্চিত করবে যে ফলস্বরূপ এররটি একটি `Unwrap` মেথড ইমপ্লিমেন্ট করে যা মূল এররটি রিটার্ন করে।
সেজন্য, `errors.Is` ব্যবহার করে পরীক্ষা করা যায় যে একটি নির্দিষ্ট সেন্টিনেল এরর "এরর চেইন"-এর কোথাও আছে কিনা।
এটি গোপনে বারবার `Unwrap` কল করে যতক্ষণ না প্রশ্নবিদ্ধ এররটি পাওয়া যায় বা চেইনটি শেষ হয়।

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

নিয়মিত `%v` ফরম্যাটিং ভার্ব ব্যবহার করলে `errors.Is` দিয়ে মূল এরর পরীক্ষা করা কাজ করবে না।

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

ফলস্বরূপ, ডিফল্টভাবে `%v` ব্যবহার করা এবং শুধুমাত্র তখনই `%w` ব্যবহার করা ভালো অভ্যাস যদি আপনি স্পষ্টভাবে আপনার ব্যবহারকারীকে একটি অন্তর্নিহিত এরর অ্যাক্সেস করতে দিতে চান ([Google Go Styleguide][google-go-styleguide])।

আপনি যদি এমন পরিস্থিতিতে পড়েন যেখানে আপনি একটি সেন্টিনেল এরর পরীক্ষা করতে চান কিন্তু স্পষ্টভাবে আনর‍্যাপ করতে চান না, তাহলে `errors.Is`-এর পরিবর্তে `==` ব্যবহার করতে পারেন।

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

বিপরীতে, যদি এররটি র‍্যাপ করা থাকত, তাহলে `==` এটি শনাক্ত করতে পারত না।

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

ডিফল্টভাবে `errors.Is` নিয়ে কাজ করা ঠিক আছে, তবে আপনার সর্বদা সচেতন থাকা উচিত যে এর মানে পুরো এরর চেইনটি অনুসন্ধান করা হবে।

## (কাস্টম) এরর টাইপ পরীক্ষা করা

`errors.Is`-এর একটি সমতুল্য রয়েছে যা এরর চেইন থেকে একটি নির্দিষ্ট টাইপের এরর পরীক্ষা করতে এবং পুনরুদ্ধার করতে দেয়।
এর জন্য ফাংশনটি হলো `errors.As`, এবং `errors.Is`-এর মতোই এটি পুরো চেইন জুড়ে প্রদত্ত এরর টাইপটি খুঁজবে।
`errors.As` শুধুমাত্র তখনই পাওয়া এররটি এক্সট্র্যাক্ট করে যা টাইপের সাথে মেলে যাতে আপনি আরও কাজ করতে পারেন, যেমন নির্দিষ্ট ফিল্ড পুনরুদ্ধার করা।

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
উপরের পয়েন্টারগুলির সিনট্যাক্স সম্পর্কে সাবধান থাকুন।
কোডটি শুধুমাত্র তখনই সঠিকভাবে কাজ করবে এবং কম্পাইল হবে যদি `customError`-এর টাইপটি ঠিক সেই টাইপ হয় যা এরর ইন্টারফেস ইমপ্লিমেন্ট করে।
আমাদের ক্ষেত্রে, সেটি হলো `*MyCustomError` (`MyCustomError`-এর একটি [পয়েন্টার][concept-pointers]), `MyCustomError` নিজে নয়।

এর উপরন্তু, দ্বিতীয় আর্গুমেন্টটি এরর ভ্যারিয়েবলের একটি পয়েন্টার হওয়া দরকার।
যেহেতু আমাদের এররটি ইতিমধ্যে একটি পয়েন্টার, `errors.As`-এ আমরা যা পাস করছি তা হলো একটি পয়েন্টারের পয়েন্টার (MyCustomError-এর প্রতি)।
শুধুমাত্র এটি সঠিকভাবে সেট আপ করলে, Go তারপর পাওয়া এররটি দিয়ে ভ্যারিয়েবলটি পূরণ করতে পারে।
~~~~

আগের মতোই, `Errorf` কল করার সময় `%v` ব্যবহার করা হলে `errors.As` এরর টাইপটি খুঁজে পেত না।

কোনো কারণে আপনি যদি আনর‍্যাপ করতে না চান, তাহলে পরিবর্তে টাইপ অ্যাসারশন ব্যবহার করা যায় (উপরের `==`-এর সমতুল্য)।

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

এররটি র‍্যাপ করা থাকলে টাইপ অ্যাসারশন এরর টাইপটি শনাক্ত করতে পারবে না।

## কাস্টম টাইপের এরর আনর‍্যাপ করার অনুমতি দেওয়া

কখনও কখনও শুধু কিছু অতিরিক্ত টেক্সট দিয়ে একটি এরর র‍্যাপ করা যথেষ্ট নয়।
পরিবর্তে আপনি একটি কাস্টম এরর টাইপ তৈরি করতে পারেন যা মূল এররটি এবং আপনি যে অতিরিক্ত স্ট্রাকচার্ড ডেটা যোগ করতে চান তা ধারণ করে।
আপনি যদি আপনার এরর টাইপের জন্য আনর‍্যাপিং অনুমতি দিতে চান, তাহলে আপনাকে শুধু ম্যানুয়ালি একটি `Unwrap() error` মেথড যোগ করতে হবে যাতে `Unwrap` ইন্টারফেসটি সন্তুষ্ট হয়।

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## একাধিক এরর একত্রিত করা

Go 1.20-এ, বিল্ট-ইন `errors` প্যাকেজে একটি নতুন `Join` ফাংশন যোগ করা হয়েছিল।
`Join` একাধিক এররকে এমনভাবে একত্রিত করতে দেয় যা এখনও আনর‍্যাপিংয়ের অনুমতি দেয়, অর্থাৎ চেইন বরাবর একটি নির্দিষ্ট এরর বা এরর টাইপ পরীক্ষা করা।
এর ফলে, এরর চেইনটি বাস্তবে একটি এরর ট্রি হতে পারে।
আরও তথ্য [রিলিজ নোট][release-notes] এবং [ডকুমেন্টেশন][doc-join]-এ পাওয়া যাবে।

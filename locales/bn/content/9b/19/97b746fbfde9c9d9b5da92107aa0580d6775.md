# সম্পর্কে

মেমরি সাধারণত একটি প্রোগ্রামের জন্য অপারেটিং সিস্টেম (OS) দ্বারা একটি সাধারণ বিন্যাসে ম্যাপ করা হয়:

| অ্যাড্রেস | মেমরি রিজিয়ন         |
| :-----: | :--------------------- |
|  উচ্চ   | স্ট্যাক                  |
|         | ...                    |
|         | হিপ                   |
|         | রিড-অ্যান্ড-রাইট সেগমেন্ট |
|         | কোড/রিড-অনলি সেগমেন্ট |
|   নিম্ন   | রিজার্ভড               |

সেগমেন্টে থাকা মেমরি বিভিন্ন পারমিশন-সহ সেকশনে সাজানো থাকে।

আমরা এখন পর্যন্ত যে ফাংশনগুলো ডিফাইন করেছি, সেগুলো সবই **section .text**-এ ছিল।
এই সেকশনে রিড-অনলি এক্সিকিউটেবল ডেটা থাকে।
অন্য সেকশনগুলো ডেটা ভ্যারিয়েবল ডিক্লেয়ার করতে ব্যবহৃত হয়, যেগুলো রিড-অনলি বা রিড-অ্যান্ড-রাইট হতে পারে, কিন্তু এক্সিকিউটেবল নয়।

## Section .data

ইনিশিয়ালাইজড ডেটা **[section .data][data]**-এ ডিক্লেয়ার করা হয়।

NASM-এ (The Netwide Assembler, এই ট্র্যাক যে অ্যাসেম্বলার ব্যবহার করে), একটি ইনিশিয়ালাইজড ভ্যারিয়েবলের একটি নাম থাকে, একটি ডিরেক্টিভ থাকে যা ডেটার সাইজ নির্দেশ করে, এবং কমা দিয়ে আলাদা করা মানের একটি তালিকা থাকে।
এগুলোর প্রতিটি অন্যটি থেকে একটি স্পেস দিয়ে আলাদা করা থাকে এবং লেবেলের পরে ঐচ্ছিকভাবে একটি `:` থাকতে পারে।

প্রধান ডিরেক্টিভগুলো এবং তাদের সংশ্লিষ্ট ডেটা সাইজ হলো:

| ডিরেক্টিভ | সাইজ    |
| :-------: | :------ |
|    db     | ১ বাইট  |
|    dw     | ২ বাইট |
|    dd     | ৪ বাইট |
|    dq     | ৮ বাইট |

উদাহরণস্বরূপ, এটি `space` নামের একটি বাইট ভ্যারিয়েবল ডিক্লেয়ার করে যার মান `10`:

```x86asm
section .data
    space db 10
```

`section .data`-এ ডিক্লেয়ার করা ভ্যারিয়েবলগুলো মিউটেবল, অর্থাৎ এগুলো রিড-অ্যান্ড-রাইট।
এগুলোর স্টোরেজ ডিউরেশনও _স্ট্যাটিক_, অর্থাৎ প্রোগ্রাম চলার পুরো সময় জুড়ে এগুলো থাকে।

## Section .rodata

**section .rodata** হলো `section .data`-এর মতোই।
দুটি সেকশনেই ইনিশিয়ালাইজড ডেটা থাকে, যা একইভাবে ডিক্লেয়ার করা হয় এবং একই স্টোরেজ ডিউরেশন থাকে।

তাদের মধ্যে প্রধান পার্থক্য হলো `section .rodata`-এর ডেটা ইমিউটেবল, অর্থাৎ রিড-অনলি।

~~~~exercism/note
`equ` দিয়ে ডিফাইন করা কনস্ট্যান্ট `section .rodata`-এ ডিফাইন করা কনস্ট্যান্ট থেকে আলাদা।

`equ` দিয়ে ডিফাইন করা একটি কনস্ট্যান্ট মেমরিতে জায়গা নেয় না এবং অ্যাসেম্বলার সরাসরি এটির মান দিয়ে এটি প্রতিস্থাপন করে।
এটি আসলে সেই মানের জন্য একটি প্লেসহোল্ডার।

অন্যদিকে, `section .rodata`-এ ডিফাইন করা কনস্ট্যান্ট আসলে মেমরিতে সংরক্ষিত থাকে এবং এর একটি অ্যাড্রেস থাকে।
~~~~

## ডেটা অ্যাক্সেস করা

### লেবেল এবং ইন্ডিরেকশন

ডিক্লেয়ার করা ডেটার সাথে একটি নাম যুক্ত থাকতে হয়।
এই নামটিকে **লেবেল** বলা হয়।

একটি লেবেল হলো একটি সিম্বল, যা মেমরিতে ডেটার নির্দিষ্ট অ্যাড্রেস এনকোড করে।
**x86-64-এ অ্যাড্রেসগুলো ৬৪-বিট মান**।
এমন একটি অ্যাড্রেস ধারণ করা একটি মান, যা রেজিস্টারে রাখা হোক বা মেমরিতে সংরক্ষিত হোক, উচ্চস্তরের ভাষাগুলোতে সেটিকেই **[পয়েন্টার][pointer]** বলা হয়।

NASM-এ, লেবেল দিয়ে সরাসরি ডেটা অ্যাক্সেস করার চেষ্টা করলে বরাদ্দ করা মেমরি পাওয়া যায় না, বরং তার অ্যাড্রেস পাওয়া যায়:

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

একটি মেমরি অ্যাড্রেসের বিষয়বস্তু অ্যাক্সেস করার জন্য এটিকে _ডিরেফারেন্স_ করা প্রয়োজন।
একে **ইন্ডিরেকশন** বলা হয়।

NASM-এ এটি `[]` দিয়ে করা হয়:

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

তবে, এমন কিছু পরিস্থিতি আছে যখন ডিরেফারেন্স করা মেমরির সাইজ নিয়ে অস্পষ্টতা থাকতে পারে।
সেসব ক্ষেত্রে, এই সাইজ নির্দেশ করে এমন একটি প্রিফিক্স ব্যবহার করতে হয়।

একটি সাধারণ x86-64 প্রোগ্রামে সবচেয়ে গুরুত্বপূর্ণ প্রিফিক্সগুলো এবং তাদের সাইজ হলো:

| প্রিফিক্স | সাইজ    |
| :----- | :------ |
| byte   | ১ বাইট  |
| word   | ২ বাইট |
| dword  | ৪ বাইট |
| qword  | ৮ বাইট |

একই লোড সাইজ স্পষ্টভাবে উল্লেখ করে লেখা যেতে পারে:

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

মেমরি ডিরেফারেন্স করার সময় সবসময় একটি প্রিফিক্স ব্যবহার করা ভালো অভ্যাস।

### মেমরিতে লেখা

মেমরিতে লেখাও একইভাবে করা হয়, একটি অ্যাড্রেস ডিরেফারেন্স করে:

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

লক্ষ্য করুন, বেশিরভাগ ইন্সট্রাকশনে প্রথমে রেজিস্টারে বিষয়বস্তু লোড না করেই আপনি মেমরি অপারেন্ড ব্যবহার করতে পারেন।
তবে, সাধারণত সোর্স ও ডেস্টিনেশন অপারেন্ড দুটোতেই সেগুলো ব্যবহার করা সম্ভব নয়, দুটোর মধ্যে কেবল একটি ব্যবহার করা যায়:

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### LEA ইন্সট্রাকশন

যদিও একটি `mov` দিয়ে একটি ভ্যারিয়েবলের অ্যাড্রেস রেজিস্টারে সংরক্ষণ করা যায়, এই নির্দিষ্ট উদ্দেশ্যের জন্য একটি ইন্সট্রাকশন আছে: **[lea][lea]**।

এই ইন্সট্রাকশন একটি মেমরি-ফর্ম অপারেন্ড ব্যবহার করে, কিন্তু এটি মেমরি পড়ে _না_।
বরং, এটি এফেক্টিভ অ্যাড্রেস এক্সপ্রেশনটি গণনা করে এবং ফলাফলটি ডেস্টিনেশন অপারেন্ডে লেখে:

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

রেজিস্টারে মেমরি অ্যাড্রেস গণনা ও সংরক্ষণ করতে `lea` ব্যবহার করা বেশি স্বাভাবিক।

### রিলেটিভ অ্যাড্রেসিং

মেমরি লোকেশন অ্যাক্সেস করার সময় NASM-এর ডিফল্ট আচরণ হলো **অ্যাবসোলিউট অ্যাড্রেস** তৈরি করা, অর্থাৎ নির্দিষ্ট মেমরি অ্যাড্রেস।

নিরাপত্তার কারণে, এক্সিকিউটেবলগুলো প্রায়ই **PIE (Position Independent Executable)** হিসেবে বিল্ড করা হয়, যেখানে মেমরি রিজিয়নগুলো র‍্যান্ডমাইজড লোকেশনে রাখা হয়।
একটি `PIE`-তে, লিংক টাইমে একটি ভ্যারিয়েবলের চূড়ান্ত অ্যাড্রেস জানা থাকে না।
তাই কোড বরং `rip` নামের একটি বিশেষ রেজিস্টারের মান থেকে অফসেট হিসেবে অ্যাড্রেস গণনা করে, যা পরবর্তী যে ইন্সট্রাকশনটি এক্সিকিউট হবে সেটির দিকে নির্দেশ করে।

একেই সাধারণত **RIP-রিলেটিভ অ্যাড্রেসিং** বলা হয়।

NASM-এ আপনি **[rel অপারেটর][rel]** দিয়ে RIP-রিলেটিভ অ্যাক্সেস চাইতে পারেন:

```x86asm
mov rax, qword [rel variable]
```

সোর্স ফাইলের শুরুতে `default rel` দিয়ে রিলেটিভ অ্যাড্রেসিংকে ডিফল্টও বানানো যায়।

এই ট্র্যাকের সব অনুশীলনী `PIE` হিসেবে কম্পাইল ও লিংক করা হয়, তাই রিলেটিভ অ্যাড্রেস তৈরি করতে `rel` ব্যবহার করা উচিত।

উপরে উল্লিখিত র‍্যান্ডমাইজড লেআউট হলো একটি প্রশমন ব্যবস্থা, যা address space layout randomization নামে পরিচিত।
প্রতিটি মেমরি রিজিয়নের বেসকে অনুমান করা অসম্ভব করে তোলে, এটি আক্রমণকারীকে সেই নির্দিষ্ট অ্যাড্রেসগুলো থেকে বঞ্চিত করে যেগুলোর ওপর অনেক এক্সপ্লয়টেশন টেকনিক নির্ভর করে, এবং `PIE`-ই লোডারকে সেই রিজিয়নগুলো যেকোনো জায়গায় বসানোর সুযোগ দেয়।

এই কারণে, এই ট্র্যাকে অ্যাবসোলিউট অ্যাড্রেসিং কেবল নিরুৎসাহিতই নয়, এটি ব্যবহারের অযোগ্য।
`[abs variable]`-এর মতো একটি অ্যাবসোলিউট রেফারেন্স অ্যাসেম্বলারকে ইন্সট্রাকশনের ভেতরে একটি নির্দিষ্ট ৩২-বিট অ্যাড্রেস ঢোকাতে বলে।
Linux-এ `PIE` লিংকার এই তৈরি হওয়া রিলোকেশন প্রত্যাখ্যান করে, এবং macOS-এ `macho64` ফরম্যাট ৩২-বিট অ্যাবসোলিউট অ্যাড্রেস একেবারেই সমর্থন করে না, ফলে ফাইলটি অ্যাসেম্বল হতে ব্যর্থ হয়।

RIP-রিলেটিভ অ্যাড্রেসিং দুই সমস্যাই এড়িয়ে যায়, কারণ ইন্সট্রাকশনটি কেবল `rip` থেকে একটি অফসেট এনকোড করে, কখনোই কোনো নির্দিষ্ট অ্যাড্রেস নয়।
তাই `PIE`-এর অধীনে একটি অ্যাড্রেস রেজিস্টারে বসানোর স্বাভাবিক উপায় হলো একটি `rel` অপারেন্ড-সহ `lea`:

```x86asm
default rel

section .data
    variable dq 7

section .text
fn:
    lea rax, [rel variable]       ; materialize the address (PIE-safe)
    mov rcx, qword [rel variable] ; load the value through a RIP-relative access
    ...
```

### ভিজিবিলিটি

যেকোনো সেকশনে (যেমন `.text`, `.data`, `.rodata`) ডিফাইন করা লেবেল (ফাংশন ও ডেটা) একই সোর্স ফাইলের ভেতরে দৃশ্যমান থাকে।
যদি `global` হিসেবে ডিক্লেয়ার করা হয়, তবে সেগুলো অন্য সোর্স ফাইলেও দৃশ্যমান থাকে।

বিপরীতভাবে, অন্য সোর্স ফাইলে ডিফাইন করা লেবেল বর্তমান সোর্স ফাইলে দৃশ্যমান থাকে যদি সেগুলো `extern` হিসেবে ডিক্লেয়ার করা হয়।
এই ক্ষেত্রে, অ্যাসেম্বলিতে ডেটার সাইজের কোনো ইঙ্গিত থাকে না, এটি আগে থেকেই জানা থাকতে হয়।

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

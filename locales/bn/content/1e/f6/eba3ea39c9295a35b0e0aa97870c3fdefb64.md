# পরিচিতি

এখন পর্যন্ত পাঠ্যক্রমে টাইপ নিয়ে বেশি কিছু বলা হয়নি, তবে Julia-তে যে এগুলো আছে, তা স্পষ্ট:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

আমরা কখনো টাইপ নির্দিষ্ট করিনি, তবুও Julia সেগুলো নিজে থেকেই বসিয়ে দিয়েছে।

1. Julia-তে `types` আছে, যেগুলো এর ডিজাইনের কেন্দ্রে রয়েছে।
2. Julia সাধারণত `Type Inference` ব্যবহার করে টাইপটি "অনুমান" করতে পারে।

JIT কম্পাইলার পুরো (সব) কোড দেখে নেবে, একটি ভ্যারিয়েবল কীভাবে ব্যবহৃত হচ্ছে তা দেখবে, এবং সেই ব্যবহারের সাথে মানানসই একটি উপযুক্ত ডিফল্ট টাইপ _অনুমান_ করবে।

## টাইপ প্রমোশন

আগের ধারণাগুলোতে এর অনেক উদাহরণ ছিল, যেখানে সংখ্যাগত টাইপগুলোকে একই রূপে আনা হয়েছে, শুরু হয়েছিল একেবারে সহজ পাটিগণিত থেকেই।

```julia-repl
julia> 2 + 1.3
3.3
```

আমরা একটি ইন্টিজার (Int64) আর একটি ফ্লোটিং-পয়েন্ট (Float64) সংখ্যা যোগ করে পেয়েছি একটি Float64 ফলাফল।
একইভাবে:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

উপরের উদাহরণে একটি টিউপল প্রতিটি এলিমেন্টের টাইপ অক্ষুণ্ণ রেখেছে, কিন্তু ভেক্টরে রূপান্তর করলে সেগুলো সবই একরকম Float64-এ পরিণত হয়েছে।

Julia কম্পাইলার বোঝে কোন টাইপ রূপান্তরগুলো সম্ভব: ইন্টিজার থেকে ফ্লোটে যাওয়ায় কোনো সমস্যা নেই, ফ্লোট থেকে ইন্টিজারে গেলে নির্ভুলতা নষ্ট হয়, তাই একটি `InexactError` উত্থাপিত হয়।
টাইপ প্রমোশন এক্সপ্রেশনের সব মানকে একটি কমন টাইপে রূপান্তর করে, যা সব ইনপুটের সাথে মানানসই হওয়ার মতো যথেষ্ট নমনীয়।

## টাইপ অ্যাসাইনমেন্ট

সহজ টিউটোরিয়াল অনুশীলনী সমাধানের জন্য টাইপ ইনফারেন্সের উপর ভরসা করা ঠিকই আছে, কিন্তু বড় প্রোগ্রামের ক্ষেত্রে আপনার আরও নিখুঁত নিয়ন্ত্রণ দরকার হতে পারে।

বেশিরভাগ আধুনিক প্রসেসরে একটি ইন্টিজারের ডিফল্ট হয় `Int64`।
আমরা [`Numbers`][numbers] ধারণায় দেখেছি যে একটি মানকে ডিফল্ট নয় এমন কোনো নির্দিষ্ট টাইপে রূপান্তর করা যায়।

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

তবে, `x` ভ্যারিয়েবলটিকে এখনও ভিন্ন একটি টাইপে পুনরায় অ্যাসাইন করা যায়:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

একে `type instability` বলা হয়, যা:

- ছোট স্ক্রিপ্টে খুবই সুবিধাজনক।
- বড় প্রোগ্রামে পারফরম্যান্স আর নির্ভরযোগ্যতার জন্য খারাপ।

এর বদলে, `::` অপারেটর ব্যবহার করে আমরা `x`-এর টাইপ নির্দিষ্ট করতে পারি:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

এখন `y`-এর টাইপ `Int16`, এবং সবসময় তাই থাকবে।
তাই কম্পাইলার জানে এর জন্য কত বাইট সংরক্ষণ করতে হবে, এবং বাকি কোডটি একটি স্থির টাইপের উপর নির্ভর করে অপ্টিমাইজ করতে পারে।
এই দিক থেকে ভ্যারিয়েবলটি C-র মতো স্ট্যাটিকালি টাইপড ভাষার ভ্যারিয়েবলের সাথে কমবেশি একই রকম।

## টাইপ অ্যাসারশন

উপরে বর্ণিত টাইপ অ্যাসাইনমেন্ট ভ্যারিয়েবল অ্যাসাইনমেন্টের বাম দিকে ব্যবহার করা হয়, যাতে ওই ভ্যারিয়েবলের টাইপ সীমাবদ্ধ করা যায়।

কোনো মানের সাথে, বা এমন কিছুর সাথে যা মূল্যায়িত হয়ে একটি মান দেয়, `::` অপারেটর ব্যবহার করলে সাধারণত এটি একটি _অ্যাসারশন_, অর্থাৎ মানটি অবশ্যই এই টাইপের হতে হবে, নইলে একটি এরর উত্থাপিত হওয়া উচিত।

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

সাধারণত এটি একটি ফাংশনের রিটার্ন ভ্যালুর সাথে ব্যবহার করা হতে পারে, ফাংশনটি প্রত্যাশামতো কাজ করেছে কি না তার একটি সহজ শেষ পরীক্ষা হিসেবে।

## টাইপ হায়ারার্কি

`Int64`, `Int16`, `String`, `Char`: এই টাইপগুলো আসলে _"কোথা থেকে আসে"_?

অনেক অবজেক্ট-ওরিয়েন্টেড (OO) ভাষায় প্রতিটি টাইপ একটি ক্লাস, সাবক্লাসিং সেগুলোকে একটি ক্লাস হায়ারার্কিতে সাজায়, আর ক্লাস মেথডগুলো আচরণ নির্ধারণ করে।

Java আর Ruby এই ধরনের স্পষ্ট উদাহরণ, কিন্তু Python-ও ভেতরে ভেতরে অনেকটা একই রকম।

***Julia-তে ক্লাস নেই।***

ডকুমেন্টে বলা কারণ হলো, OO-র বৈশিষ্ট্যগুলো JIT কম্পাইলারের সাথে বাধা তৈরি করে আর রানটাইম পারফরম্যান্স নষ্ট করে।

তবুও, এই কোডটি দেখুন:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

কিছু বিস্তারিত যোগ করলে:

- `Int16` একটি টাইপ, এবং আমরা এই টাইপের ভ্যারিয়েবল বানাতে পারি।
- `Int16` হলো `Signed`-এর একটি সাবটাইপ, আর `supertype()` ফাংশনটি তা আমাদের দেখিয়ে দেয়।
- টাইপের একটি হায়ারার্কি আছে, যা `Integer`, `Real` আর `Number` হয়ে উপরে `Any` পর্যন্ত যায়, আর `subtypes()` আমাদের জন্য হায়ারার্কির এই শাখাটি তালিকাভুক্ত করে দেবে।

সব শাখাই শেষ হয় `Any`-তে, যা নিজেই নিজের সুপারটাইপ হওয়ায় অনন্য।

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

তাহলে, Julia-তে `class` হায়ারার্কি নেই, কিন্তু `type` হায়ারার্কি _আছে_।

একসময় আমরা এটা কীভাবে কাজ করে তা খুঁটিয়ে দেখার চেষ্টা করব, তবে আগে আরও অনেক কিছু ঘুরে দেখার আছে।

## টাইপ পরীক্ষা করা

সাধারণ উপায়ে সমতা পরীক্ষা করতে আমরা `typeof()` ব্যবহার করতে পারি।

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

টাইপের সমতা অবশ্যই হুবহু হতে হবে, কারণ এই ধরনের তুলনার টাইপ হায়ারার্কি সম্পর্কে কোনো ধারণা নেই।

আরও নমনীয়ভাবে, `isa` আমাদের বলে দেবে একটি মানের টাইপ তুলনার জন্য দেওয়া টাইপটির সমান কি না, অথবা তার একটি সাবটাইপ কি না।
এটি ফাংশন আকারে বা ইনফিক্স আকারে, দুইভাবেই ব্যবহার করা যায়।

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

মনে রাখবেন, `isa` বাম দিকে একটি `value` আশা করে, `type` নয়।

এইভাবে দুটি _টাইপ_ তুলনা করতে গেলে অপ্রত্যাশিত ফলাফল আসবে।
সঠিক অপারেটর হলো `<:`, যা আমরা ভবিষ্যতের ধারণাগুলোতে আরও অনেকবার দেখব।

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## অ্যাবস্ট্রাক্ট বনাম কংক্রিট টাইপ

আমরা দেখেছি টাইপ হায়ারার্কি একটি ট্রি স্ট্রাকচার তৈরি করে (CS-এর অর্থে, যার মূল থাকে উপরে)।

ট্রির প্রতিটি আইটেম একটি `node`, আর এগুলোকে কয়েকটি শ্রেণিতে ভাগ করা যায়:

1. যে নোডগুলোর সাবটাইপ আছে তাদের `abstract` বলা হয়।
2. লিফ নোডগুলো, যাদের কোনো সাবটাইপ নেই, তাদের `concrete` বলা হয়।

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

এটি একটি গুরুত্বপূর্ণ পার্থক্য, কারণ কেবল কংক্রিট টাইপগুলোই ভ্যারিয়েবল হিসেবে `instantiated` হতে পারে।


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

মনে রাখবেন, একটি অ্যাবস্ট্রাক্ট টাইপ ব্যবহার করতে গেলে (এই ক্ষেত্রে) কোনো এরর বার্তা আসে না, বরং কম্পাইলার উপযুক্ত একটি কংক্রিট টাইপ তৈরি করে: `Integer`-এর বদলে `Int64`।
অন্তত এটি ভ্যারিয়েবলটিকে ইন্টিজার ছাড়া অন্য কিছু অ্যাসাইন করা থেকে আটকায়:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

তাই অ্যাবস্ট্রাক্ট টাইপ দিয়ে টাইপ অ্যাসাইনমেন্ট হলো ভ্যারিয়েবলের টাইপের উপর একটি _সীমাবদ্ধতা_, যা (উপরের ক্ষেত্রে) `Integer`-এর যেকোনো সাবটাইপ পর্যন্ত হতে পারে।
প্রোগ্রামিং ভাষার জগতে এটি একটি অস্বাভাবিক ব্যাপার: C-তে টাইপ অ্যাসাইনমেন্টের চেয়ে দুর্বল, Python-এর সাম্প্রতিক সংস্করণের টাইপ হিন্টের চেয়ে সবল।

`isabstracttype()` আর `isconcretetype()` ফাংশন দুটি পরীক্ষা করার সুযোগ দেয়।
মনে রাখবেন, এরা কেবল একে অন্যের সরল বিপরীত নয়: পরের একটি ধারণায় আমরা দেখব, কিছু টাইপ অ্যাবস্ট্রাক্টও নয় আবার কংক্রিটও নয়।


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

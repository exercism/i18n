# সম্পর্কে

C#-এর `struct` আর `class` ঘনিষ্ঠভাবে সম্পর্কিত। এদের স্টেট ও বিহেভিয়ার থাকে। এরা একই ধরনের মেম্বার রাখতে পারে: কনস্ট্রাক্টর, মেথড, ফিল্ড, প্রপার্টি ইত্যাদি।

ফিল্ড আর প্রপার্টি সাধারণ টাইপ, `struct` বা রেফারেন্স টাইপ হতে পারে। স্কোপ, রিড/রাইট নিয়ম আর অ্যাক্সেস লেভেলের ক্ষেত্রে `struct` ঠিক `class`-এর মতোই একই নিয়ম মেনে চলে।

```csharp
enum Unit
{
    Kg,
    Lb
}

struct Weight
{
    private double count;
    private Unit unit;

    public Weight(double count, Unit unit)
    {
        this.count = count;
        this.unit = unit;
    }

    public override string ToString()
    {
        return count.ToString() + unit.ToString();
    }
}

new Weight(77.5, Unit.Kg).ToString();
// => "77.6Kg"
```

মনে রাখার মতো প্রধান একটি বিষয় হলো, যখন একটি স্ট্রাক্ট কোনো ভ্যারিয়েবলে অ্যাসাইন করা হয় বা প্যারামিটার হিসেবে পাস করা হয়, তখন মানগুলো কপি হয়ে যায়। ফলে মূল ভ্যারিয়েবলে করা পরিবর্তন কপি করা ভ্যারিয়েবলকে প্রভাবিত করে না, আর উল্টোটাও নয়। সংক্ষেপে, `struct` হলো **ভ্যালু টাইপ**।

এই [নিবন্ধে][class-or-struct] `struct` আর `class`-এর মধ্যে পার্থক্য নিয়ে আলোচনা করা হয়েছে। নিবন্ধটি থেকে দেখতে পাবেন, `struct` সাধারণত হালকা ও [ইমিউটেবল][structs-immutable] হয়ে থাকে, যদিও কম্পাইলার বা রানটাইম (ডিফল্টভাবে) এই নির্দেশনা বাধ্যতামূলক করে না।

এমন কয়েকটি বিষয় আছে যেগুলোর মুখোমুখি আপনাকে হতে হবে (আর সেগুলো নিয়েই কম্পাইলার আপনাকে মনে করিয়ে দেবে):

1. `struct`-এর মেম্বার ইনলাইনে ইনিশিয়ালাইজ করা যায় না।
2. `struct` ইনহেরিট করা যায় না
3. নন-ডিফল্ট কনস্ট্রাক্টর দেওয়া থাকলেও `struct`-এর সবসময় একটি ডিফল্ট কনস্ট্রাক্টর থাকে, আর আপনি স্পষ্টভাবে প্যারামিটারবিহীন কনস্ট্রাক্টর দিতে পারবেন না।

উপরের ১ ও ৩ নম্বর পয়েন্টের কারণে, `struct`-এর ডেভেলপারের পক্ষে অবৈধ ইনস্ট্যান্স তৈরি হওয়া ঠেকানোর কোনো উপায় নেই।

## কমন স্ট্রাক্ট

ডকুমেন্টেশন দেখলে বুঝবেন, প্রিমিটিভ আর স্ট্রাক্টের মধ্যে ঘনিষ্ঠ সম্পর্ক আছে। উদাহরণের জন্য [`Int32/int`][int32] দেখুন। আরও প্রচলিত একটি উদাহরণ হলো [`TimeSpan`][time-span] টাইপটি।

`TimeSpan`-এর ইনস্ট্যান্সগুলো অনেকটা সংখ্যার মতো আচরণ করে, যার মধ্যে `>` আর `<`-এর মতো তুলনা অপারেটর এবং গাণিতিক অপারেটর থাকে। প্রয়োজন হলে নিজের `struct`-এর জন্যও আপনি এই অপারেটরগুলো ইমপ্লিমেন্ট করতে পারেন।

`TimeSpan` নিয়ে খেয়াল করার মতো একটি বিষয় হলো, এটি বেশ কিছু ইন্টারফেস ইমপ্লিমেন্ট করে, যেমন `IComparable<TimeSpan>`। `struct` অন্য `struct` থেকে ডিরাইভ করা না গেলেও ইন্টারফেস ইমপ্লিমেন্ট করতে পারে।

## সমতা

`struct`-এর জন্য সমতা পরীক্ষা করা প্রায়ই `class`-এর তুলনায় অনেক সহজ, কারণ এটি ডিফল্টভাবে কেবল ফিল্ডগুলোর সমতা তুলনা করে। `object.Equals()` (বা `GetHashCode()`) ওভাররাইড করার দরকার নেই। মনে রাখবেন, আপনি যদি `Object.GetHashCode()`-এর উপর নির্ভর করেন, তাহলে হ্যাশ কোড তৈরিতে জড়িত ফিল্ডগুলো (অর্থাৎ সব ফিল্ড) হ্যাশড কালেকশন ব্যবহারের সময় যেন পরিবর্তিত না হয়, সেটি আপনাকে নিশ্চিত করতেই হবে। ব্যবহারিকভাবে এর মানে হলো, এভাবে ব্যবহৃত স্ট্রাক্ট ইমিউটেবল হওয়া উচিত।

`Equals()` মেথডের বিপরীতে, সমতা অপারেটর `==` আর `!=`-এর কোনো ডিফল্ট ইমপ্লিমেন্টেশন নেই। আপনার `struct`-এর এগুলো প্রয়োজন হলে আপনাকে সেগুলো নিজেই ইমপ্লিমেন্ট করতে হবে।

অন্যদিকে, এই [নিবন্ধে][equality] বলা হয়েছে কীভাবে নিজের কাস্টম `Equals()` আর `GetHashCode()` মেথড তৈরি করে পারফরম্যান্স উন্নত করা যায়, যা `class`-এর ক্ষেত্রে প্রায়ই করা হয়। এই অনুশীলনীর ক্ষেত্রে খুব একটা কঠোর তুলনায় পার্থক্যটা ছিল প্রায় ২০%, তবে সব ফিল্ড একই টাইপের হওয়ায় সেটি কম হতে পারে, নিচে দেখুন।

[ওয়েবে][equality-performance] গতির উন্নতি নিয়ে আলোচনা আছে, যেখানে সব ফিল্ড একই টাইপের হলে `Equals()` মেথড ওভাররাইড করা হয় না। ভিন্ন ধরনের ফিল্ড যোগ করে এই অনুশীলনীতে পার্থক্যটা ছিল প্রায় ৬০%। মাইক্রোসফটের ডকুমেন্টেশনে এটি উল্লেখ করা নেই, তাই এটি একটি আন-ডকুমেন্টেড ইমপ্লিমেন্টেশন ডিটেইল, আর এর সুবিধা বিচক্ষণতার সাথে নেওয়া উচিত।

```csharp
public bool Equals(Weight other)
{
    return count.Equals(other.count) && unit.Equals(other.unit);
}

public override bool Equals(object obj)
{
    return obj is Weight other && Equals(other);
}

public override int GetHashCode()
{
    return HashCode.Combine(count, unit);
}
```

# Markdown স্পেসিফিকেশন

Exercism-এর ভেতরের সব Markdown ফাইল যেভাবে সাজানো থাকা উচিত, তা নিচে দেওয়া হলো।

এই ডকুমেন্টের কিছু নিয়ম এখনো পুরো Exercism জুড়ে প্রয়োগ করা হয়নি।
এগুলো ঠিক করার জন্য আমরা PR স্বাগত জানাই।
সব নিয়মই আমাদের CI ও লিন্টিং টুলে যোগ করা হচ্ছে, আর নতুন পরিবর্তনের ক্ষেত্রে এগুলো মেনে চলা উচিত।

## হেডিং

- সব ফাইল শুরু হতে হবে একটি লেভেল-১ হেডিং দিয়ে (`# Some heading text`)।
- লেভেল-১ হেডিং থাকে কেবল GitHub বা তার সমতুল্য জায়গায় ব্যবহারের জন্যই।
- ফাইলটি যদি Exercism রেন্ডার করে (যেমন ওয়েবসাইটে দেখানো হয়, CLI দিয়ে রেন্ডার করা হয়), তাহলে এই হেডিংটি সরিয়ে ফেলা হবে এবং প্রসঙ্গ অনুযায়ী একটি হেডিং বসানো হবে।
- কোনো হেডিং আগেরটির চেয়ে এক লেভেলের বেশি নিচে নামতে পারবে না (যেমন `##`-এর পরে কেবল `###` আসতে পারে, `####` নয়)।
- একটি মাত্র লেভেল-১ (`#`) হেডিং ছাড়া কেবল লেভেল-২ (`##`), লেভেল-৩ (`###`) ও লেভেল-৪ (`####`) হেডিং ব্যবহার করা যাবে।

## লিংক

অনুগ্রহ করে [reference links][reference-links] ব্যবহার করুন, যেগুলো Markdown ফাইলের নিচে ডিফাইন করা থাকে, একটি রেফারেন্স স্লাগের সাথে ম্যাপ করা থাকে এবং টেক্সটে ওই স্লাগ দিয়েই রেফার করা হয়।

এই পদ্ধতিতে রক্ষণাবেক্ষণ সহজ হয়, কারণ লিংক কেবল একটিমাত্র জায়গায় আপডেট করতে হয়।

উদাহরণ:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

লিংকে সবসময় অ্যাঙ্কর টেক্সট থাকা উচিত, টেক্সটে URL নিজে বসানো উচিত নয়। যেমন, নিচেরটিতে অ্যাঙ্কর টেক্সট ব্যবহার করা হয়নি, আর এটি পড়তে বেশি কঠিন।

```
If you want some more information, please visit https://google.com.
```

অ্যাঙ্কর টেক্সট ব্যবহার করে সেটিতে লিংক করলে বোঝা ও প্রসঙ্গে বসানো সহজ হয়।

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

যা রেন্ডার হয় এভাবে, "আপনি যদি আরও কিছু তথ্য চান, [Google][google-link] একটি কাজের রিসোর্স।"

## কোড

কোড এলিমেন্ট (যেমন ফাংশন বা কিওয়ার্ড) উল্লেখ করলে কোডটি ব্যাকটিকের মধ্যে রাখতে হবে:

```
- The `printf()` function writes to the console.
```

যা রেন্ডার হয় এভাবে:

- `printf()` ফাংশনটি কনসোলে লেখে।

আরও জটিল কোড (যেমন বহুলাইনের কোড) তিনটি ব্যাকটিকের মধ্যে রাখতে হবে। সিনট্যাক্স হাইলাইটিং চালু করতে খোলা তিনটি ব্যাকটিকের পরে একটি [language identifier][language-identifier] উল্লেখ করতে হবে:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

সম্ভব হলে কোড এমনভাবে ফরম্যাট করুন যেন তা যে পরিবেশে দেখানো হচ্ছে তার সাথে সবচেয়ে প্রাসঙ্গিক হয়। সুযোগ থাকলে আপনার ভাষার ডকুমেন্টেশন দেখুন।

যেমন, Python-এ REPL (read-eval-print loop, অর্থাৎ পড়া, হিসাব করা আর লেখার লুপ) আছে, যা একজন প্রোগ্রামারকে সরাসরি টার্মিনালে কোড টাইপ করার সুযোগ দেয়। কোনো ব্যবহারকারী যদি কোড ডিবাগ করেন, বা কোনো ফাংশন কেমন কাজ করে তা পরীক্ষা করে দেখতে/লক্ষ্য করতে সেটি লোকালি রান করেন, তাহলে তিনি সম্ভবত এ কাজে REPL-ই ব্যবহার করবেন, কারণ ওখানে সরাসরি ইন্টার্যাক্টিভভাবে টাইপ করা বেশি সুবিধাজনক। এ অবস্থায় আমরা উদাহরণের কোডটি এমনভাবে ফরম্যাট করতে পছন্দ করি যেন তা REPL-এ টাইপ করা হচ্ছে, শুরুর দিকে `>>>` দিয়ে:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

অন্য ক্ষেত্রে কোডটি এমনভাবে রাখাই বেশি যুক্তিসঙ্গত যেন তা একটি `.py` ফাইলে আছে। এখানে শিক্ষার্থীর সুবিধা হয়, কারণ তার সামনে এমন কিছু তুলে ধরা হয় যা সে নিজে কোড লিখলে যেমন হতো তার অনুরূপ।

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

দুটি ক্ষেত্রের পার্থক্য বোঝার একটি দ্রুত উপায়, যখন বিষয়টা স্পষ্ট না হয়: কোডটি যদি এমন হয় যা শিক্ষার্থী টার্মিনালে রান করতে পারে, তাহলে সেভাবেই ফরম্যাট করুন। আর এটি যদি এমন কোড হয় যা Exercism রান করতে পারে (টেস্টে, শিক্ষার্থীর লেখা লাইব্রেরি কোডে ইত্যাদি), তাহলে এটিকে রানযোগ্য কোড হিসেবেই ফরম্যাট করাই ডিফল্ট ধরুন।

আমরা তিন ধরনের ব্লক সাপোর্ট করি:

- **exercism/note:** যে ব্লকগুলো কিছু বাড়তি বিশেষ তথ্য আলাদা করে তুলে ধরে
- **exercism/caution:** যেসব বিষয় সম্পর্কে মানুষের জানা উচিত বা যেগুলো নিয়ে সাবধানে চলা উচিত
- **exercism/advanced:** এমন তথ্য যা কেবল তাদের জন্যই প্রাসঙ্গিক যারা কোনো বিষয়ে আরও গভীরে যেতে চান বা যাদের আরও অ্যাডভান্সড জ্ঞান থাকা প্রত্যাশিত।

সব ব্লকই ৪টি টিল্ড দিয়ে লেখা হয়, এই রকমভাবে:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

## মন্তব্য

- HTML মন্তব্যের বদলে Markdown মন্তব্য ব্যবহার করা ভালো (যেমন `<!-- Actual comment -->`-এর বদলে `[comment]: # (Actual comment...)` ব্যবহার করুন

আপনার markdown মন্তব্য সত্যিই সরিয়ে ফেলা হয় কি না, তা পরীক্ষা করতে পারেন: commonmark দিয়ে রেন্ডার করলে [babelmark3]-এ আপনার মন্তব্যটি কেমন দেখায়, তা দেখে নিন।

## ইনলাইন HTML

- ইনলাইন HTML অনুমোদিত, তবে অল্প পরিমাণে ব্যবহার করা উচিত
- সুযোগ থাকলে সবসময় markdown-এর নিজস্ব বিকল্প ব্যবহার করুন (যেমন `<h1>...</h1>`-এর বদলে `# ...` ব্যবহার করুন)

## ছবি

যেহেতু ওয়েবসাইট লাইট ও ডার্ক থিম সাপোর্ট করে, তাই কমিউনিটি থেকে জমা দেওয়া ছবিগুলোকে দুই থিমেই ভালোভাবে রেন্ডার হতে হবে।
এর সমাধান হলো আপনার ছবির নামের শেষে (ফাইল এক্সটেনশনের আগে) একটি সাফিক্স যোগ করা:

1. ছবির নাম `-invertible` দিয়ে শেষ করুন (যেমন `graph-invertible.svg`)। ডার্ক থিমে দেখানোর সময় ছবিটি স্বয়ংক্রিয়ভাবে ইনভার্ট হয়ে যাবে (`filter: invert(100%)`-এর মাধ্যমে)।
1. ছবির নাম `-light` দিয়ে শেষ করুন (যেমন `graph-light.png`) এবং ডার্ক থিমের সাথে খাপ খায় এমন একটি সংস্করণও তৈরি করুন, যার শেষে থাকবে `-dark` (সেটি হবে `graph-dark.png`)। ব্যবহারকারীর থিম অনুযায়ী আমরা স্বয়ংক্রিয়ভাবে সঠিক ছবিটি রেন্ডার করব।

কোনো সাফিক্স ছাড়া ছবিগুলো দুই থিমেই কোনো পরিবর্তন ছাড়াই ব্যবহৃত হবে।
এর মানে হলো, আপনি যদি গ্রেস্কেল ছবি তৈরি করতে চান, তাহলে সাধারণত সেগুলো লাইট থিমে ভালো দেখানোর মতো বানিয়ে নিয়ে সেগুলোকে ইনভার্টিবল করে দিতে পারেন।
কিন্তু আপনি যদি অনেক রঙযুক্ত ছবি ব্যবহার করেন, তাহলে দুটি ভ্যারিয়েন্ট বানানো ভালো।

ছবিটি যেখানে রেন্ডার করা হবে, সেই markdown-এ ছবির পুরো নাম (`-invertible` সহ) যোগ করতে হবে।
লাইট/ডার্ক ছবির ক্ষেত্রে **কেবল** `-light` ভ্যারিয়েন্টটিই যোগ করুন।
এই নিয়ম সব markdown ডকুমেন্টেই মেনে চলা হয়।

কিছু রিপোজিটরি [prettier][prettier] ব্যবহার করে সব Markdown যেন একই রকমভাবে ফরম্যাট হয় তা নিশ্চিত করতে। এতে নিচের সুবিধাগুলো পাওয়া যেতে পারে:

- ফরম্যাটিং নিয়ে কোনো আলোচনা নেই।
- দুর্দান্ত এডিটর/IDE ইন্টিগ্রেশন, ফলে সেভ করার সময়ই ফাইল ফরম্যাট হয়ে যায়।
- ফরম্যাটিংয়ের জন্য CI চেক যোগ করা সহজ।
- একটি স্ক্রিপ্ট দিয়ে সহজেই ফাইল স্বয়ংক্রিয়ভাবে ফরম্যাট করা যায়।

উপরের সবকিছু রিভিউতে অপ্রয়োজনীয় পরিবর্তনের পরিমাণ অনেক কমাতে সাহায্য করতে পারে, যা রিভিউয়ার ও রিভিউ হওয়া ব্যক্তি দুজনের জন্যই বিরক্তিকর।

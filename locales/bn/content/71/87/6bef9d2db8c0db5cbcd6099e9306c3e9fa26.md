# সম্পর্কে

## কম্পোজিট টাইপ

আমাদের প্রোগ্রামে কাস্টম টাইপ ডিফাইন করা প্রায়শই কাজে লাগে।

নতুন প্রিমিটিভ টাইপ তৈরি করা সম্ভব, তবে তা খুব কমই করা হয়।
বিল্ট-ইন [প্রিমিটিভ টাইপ][primitive] কোনো ইচ্ছেমতো নেওয়া সিদ্ধান্ত নয়: JIT কম্পাইলেশনের জন্য Julia যে LLVM কম্পাইলার ব্যবহার করে, তার স্ট্যান্ডার্ড টাইপগুলোর সঙ্গে এগুলো খুব কাছাকাছি মেলে।

আরও অনেক বেশি কাজে লাগে নামযুক্ত ফিল্ডসহ [কম্পোজিট টাইপ][composite-types] ডিফাইন করার সুবিধা।

অন্য ভাষাতেও এরকম কিছু আছে, সেখানে এগুলোকে `structs` বা `records` বলা হয়।
Julia-র ডকুমেন্টেশনে এগুলোকে `composite types` বলা হয়, যদিও (একটু অমিল থাকলেও) ভাষার সিনট্যাক্সে এগুলো `struct` কিওয়ার্ড দিয়ে ডিফাইন করা হয়।

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

উপরের উদাহরণে কয়েকটি বিষয় লক্ষ্য করার মতো:

- `id`-এর জন্য কোনো টাইপ উল্লেখ করা হয়নি, তাই কম্পাইলার এটিকে `id::Any` হিসেবে ব্যাখ্যা করে।
  - **দ্রষ্টব্য:** বাস্তবে কম্পাইলারকে সাহায্য করা ভালো, অর্থাৎ কোনো ফিল্ডের টাইপ একটি কনক্রিট টাইপ দিয়ে উল্লেখ করা।
  - প্যারামিটার ব্যবহার করাও আরেকটি উপায়, তা আমরা [পরবর্তী একটি ধারণায়][parametric] দেখব।
- `Person(id, name, age)`-এর মতো টাইপের নামটিই কনস্ট্রাকটর হিসেবে ব্যবহৃত হয়, যাতে `Person` টাইপের একটি ইনস্ট্যান্স পাওয়া যায়।
- আলাদা আলাদা ফিল্ড ডট নোটেশন দিয়ে অ্যাক্সেস করা যায়, [নেইমড টিউপলের][named-tuple] মতোই।

`Person` টাইপের আইটেমগুলো ইমিউটেবল, তাই সেগুলো আপডেট করা যায় না।

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

মিউটেবিলিটি প্রয়োজন হলে ডিফিনিশনে `mutable` যোগ করুন।

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

ডিফল্টভাবে কনস্ট্রাকটর চায় ফিল্ডগুলো ডিফিনিশনের মতো একই ক্রমে থাকুক, যা আরও জটিল টাইপের ক্ষেত্রে অসুবিধাজনক হয়ে দাঁড়ায়।

`@kwdef` ম্যাক্রো ব্যবহার করলে দুটি নতুন সুবিধা পাওয়া যায়:

- কনস্ট্রাকটর অবস্থান নয়, কিওয়ার্ড ব্যবহার করে।
- ফিল্ডে ডিফল্ট মান থাকতে পারে, এবং চাইলে কনস্ট্রাকটর থেকে বাদও দেওয়া যায়।

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## কম্পোজিট টাইপ হায়ারার্কি

এখন পর্যন্ত আমরা শুধু কনক্রিট কম্পোজিট টাইপ তৈরি করেছি।
খেয়াল করলে দেখবেন, সবগুলোই `Any`-এর সাবটাইপ।

সম্পর্কিত একাধিক টাইপ তৈরি করার সময় সেগুলোর জন্য একটি হায়ারার্কি ডিফাইন করাই সম্ভবত বেশি যুক্তিযুক্ত।
এটা করা খুবই সহজ।

প্রথমে একটি অ্যাবস্ট্রাক্ট টাইপ তৈরি করুন:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

এরপর সম্পর্কটি বোঝাতে টাইপ ডিফিনিশনে একটি `<:` অপারেটর যোগ করুন।

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

প্রয়োজন অনুযায়ী এটি পুনরাবৃত্তি করুন, তবে মনে রাখবেন কনক্রিট টাইপের সাবটাইপিং অনুমোদিত নয়।

আরও জটিল হায়ারার্কির জন্য প্রয়োজন অনুযায়ী অ্যাবস্ট্রাক্ট সাবটাইপ তৈরি করুন।

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

এরকম হায়ারার্কির গুরুত্ব আরও পরিষ্কার হবে যখন আমরা `Multiple Dispatch` ধারণায় পৌঁছাব এবং দেখব কীভাবে ফাংশন আর্গুমেন্ট টাইপ সামলায়।


## ইনার কনস্ট্রাকটর

এই ধারণার শুরুতে দেখেছি, টাইপের নামটিই কনস্ট্রাকটর হিসেবে ব্যবহৃত হয়, সেই টাইপের আইটেম তৈরি করতে:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

এখানে `Person()`-কে `outer constructor` বলা হয়।
ফিল্ডের টাইপগুলো টাইপ ডিফিনিশনের সঙ্গে সঙ্গতিপূর্ণ কি না তা যাচাই করা হয়, এবং দরকার হলে একটি এরর দেখানো হয়।

ধরুন আমরা শুধু _টাইপ_ নয়, ভেতরে পাঠানো _মানগুলোর_ উপরও সীমাবদ্ধতা চাই?

তাহলে আমরা টাইপ ডিফিনিশনের ভেতরে একটি `inner constructor` যোগ করতে পারি, যেটি যথাযথ যাচাই করবে।

উদাহরণস্বরূপ, আমাদের একটি অ্যাবস্ট্রাক্ট টাইপ `AbstractPoint` আছে, যা `(x, y)` কোঅর্ডিনেট নেবে, কিন্তু আমরা চাই এমন একটি সাবটাইপ যেখানে `y > x` সীমাবদ্ধতা থাকবে।

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

`new()` ফাংশন _শুধুমাত্র_ ইনার কনস্ট্রাকটরে ব্যবহার করা যায়, এবং ইনপুটগুলো বৈধ হলে কাঙ্ক্ষিত আইটেমটি রিটার্ন করে।

অবৈধ ইনপুটের জন্য উদাহরণের মতো একটি এরর মেসেজ দিয়ে থেমে যেতে পারি।
অথবা আপনি হয়তো `nothing` বা `missing`-এর মতো একটি প্লেসহোল্ডার ব্যবহার করতে পছন্দ করবেন।
এগুলো সম্পর্কে আরও জানতে [`Nothingness`][nothingness] ধারণাটি দেখুন।

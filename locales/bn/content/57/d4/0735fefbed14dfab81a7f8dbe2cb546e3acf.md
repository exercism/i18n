# Rexx স্টাইল গাইড

এই গাইডে Rexx ট্র্যাকের অনুশীলনীর test ও উদাহরণ ফাইলে ব্যবহারের জন্য নির্ধারিত স্টাইলের বর্ণনা দেওয়া হয়েছে।

## Rexx স্ট্যান্ডার্ড

Code অবশ্যই Rexx Language level 5.0-এর সাথে সঙ্গতিপূর্ণ হওয়া উচিত।

বাহ্যিক লাইব্রেরি ব্যবহারের জন্য Regina Rexx এক্সটেনশন এবং SAA স্ট্যান্ডার্ড ফাংশন ব্যবহার করা যেতে পারে।

AREXX এক্সটেনশন এবং CMS বাফার ম্যানিপুলেশন রুটিন ব্যবহার করা উচিত নয়।

## প্ল্যাটফর্ম

রানটাইম test পরিবেশ Linux-ভিত্তিক, তাই ওই পরিবেশে যে কমান্ডগুলো পাওয়া যায় কেবল সেগুলোই ADDRESS ইনস্ট্রাকশনের ইনভোকেশনে ব্যবহার করা যাবে। এগুলো code-এর কমেন্টে স্পষ্টভাবে উল্লেখ করা উচিত।

## নাম

### ইনস্ট্রাকশন

ইনস্ট্রাকশন (রিজার্ভড ওয়ার্ড) **_ছোট হাতের অক্ষরে_** লেখা উচিত। তাই নিচেরটি স্টাইল গাইডের সুপারিশ মেনে চলে:

```rexx
do while input \= ''
  parse var input char +1 input
  say char
end
```

অথচ নিচের কোনোটিই তা মেনে চলে না, তাই সুপারিশ করা হয় না:

```rexx
/* *** Not recommended *** */
Do While input \= ''
  Parse Var input char +1 input
  Say char
End
```

এবং:

```rexx
/* *** Not recommended *** */
DO WHILE input \= ''
  PARSE VAR input char +1 input
  SAY char
END
```

### বিল্ট-ইন ফাংশন (BIFs)

BIFs **_বড় হাতের অক্ষরে_** লেখা উচিত, যেমনটি এখানে দেখানো হয়েছে:

```rexx
input = 'ABCDE'
say 'Length of input is' LENGTH(input)
say 'First letter of input is' SUBSTR(input, 1, 1)
```

### লেবেল (ইউজার-ডিফাইনড ফাংশন)

লেবেলের নাম **_প্যাসকেল কেসে_** হওয়া উচিত, যেমনটি এখানে দেখানো হয়েছে:

```rexx
greeting = MyFuncSayHello()
say greeting

exit 0

MyFuncSayHello : procedure
  hello = 'Hello there!'
return hello
```

### ভ্যারিয়েবল

ভ্যারিয়েবলের নাম **_ছোট হাতের_** অক্ষর দিয়ে শুরু হওয়া উচিত, তাই এক-শব্দের ভ্যারিয়েবলও ছোট হাতের অক্ষরে হবে।

বহু-শব্দের ভ্যারিয়েবল **_ক্যামেল কেসে_** বা **_স্নেক কেসে_** লেখা যেতে পারে।

এই ট্র্যাকের জন্য গৃহীত রীতি হলো _বেশিরভাগ ভ্যারিয়েবলের জন্য ক্যামেল কেস_ ব্যবহার করা এবং test ভ্যারিয়েবলের জন্য স্নেক কেস রাখা। কনস্ট্যান্ট হিসেবে ব্যবহৃত ভ্যারিয়েবলগুলো ঐচ্ছিকভাবে বড় হাতের অক্ষরেও থাকতে পারে।

```rexx
input = 'ABCDE'
i = 0

personName = 'Alice'
test_person_description = 'Brown hair, blue eyes'

TRUE = 1
PI_CONSTANT = 3.14159
```

## লিটারেল

স্ট্রিং বোঝাতে যথাক্রমে একক কোটেশন **`'`** বা দ্বৈত কোটেশন **`"`** ব্যবহার করা যেতে পারে। নিচের দুটি সমতুল্য:

```rexx
say "Hello, world!"

say 'Hello, world!'
```

প্রত্যেকটি অন্যর ভেতরে কোনো এস্কেপ ক্যারেক্টার ছাড়াই বসানো যায়:

```rexx
say "Please don't do that as it's wrong."

say 'He said, "Please sir, may I have more?".'
```

স্ট্রিংয়ের ভেতরে কোটেশন না থাকলে, অর্থাৎ কোটেশন মেশানোর দরকার না পড়লে, স্ট্রিং বোঝাতে **_একক কোটেশন_** ব্যবহার করা বেশি পছন্দনীয়।

### হেক্সাডেসিমাল ও বাইনারি স্ট্রিং

স্ট্রিংয়ের শেষে যথাক্রমে একটি **`B`** বা একটি **`X`** যোগ করে বাইনারি ও হেক্সাডেসিমাল মান প্রকাশ করা যায়। উদাহরণ:

```rexx
hexvalue = "0A"X

binvalue = "00001010"B
```

এমন মান **_দ্বৈত কোটেশন_** দিয়ে ঘেরা সুপারিশযোগ্য।

সাধারণ স্ট্রিং বোঝাতে একক কোটেশন ব্যবহারের আগের সুপারিশের সাথে মিলিয়ে, এই রীতিটি একটি code base-এ বাইনারি ও হেক্সাডেসিমাল স্ট্রিং চিহ্নিত করা সহজ করবে।

### নিউলাইন টার্মিনেটর

UNIX বা C দ্বারা প্রভাবিত অনেক ভাষায় **_`\n`_** লিটারেলটি **_নিউলাইন_** টার্মিনেটর হিসেবে ব্যবহৃত হয়। এমন ব্যবহার ব্যাপক, এবং এই ট্র্যাকে বেশ কিছু অনুশীলনীতে এই টার্মিনেটরযুক্ত স্ট্রিং ব্যবহার ও নাড়াচাড়া করা জড়িত।

Rexx এই টার্মিনেটর সমর্থন করে না, এবং এস্কেপ ক্যারেক্টার হিসেবে **_`\`_** (বা অন্য কোনো ক্যারেক্টার) সমর্থন করে না।

নিউলাইন ক্যারেক্টারের Rexx সমতুল্য হলো একটি (প্ল্যাটফর্ম-নির্ভর) হেক্সাডেসিমাল মান; UNIX-ভিত্তিক প্ল্যাটফর্মে তা হলো:

**_`"0A"X`_**

(bash shell ব্যবহার করে) নিচের নিউলাইন-সংবলিত স্ট্রিংয়ের Rexx সমতুল্য হলো:

```bash
printf "I have\nthree embedded\nnewlines.\n"
```

হলো:

```rexx
say 'I have' || "0A"X || 'three embedded' || "0A"X || 'newlines.' || "0A"X
```

এই ট্র্যাকের অনুশীলনীগুলো টার্মিনালে দেখানোর জন্য নির্ধারিত স্ট্রিংয়ে প্রয়োজনে কেবল **_`\n`_**-কে **_`"0A"X`_**-এ রূপান্তর করবে। অন্যথায়, **_`\n`_** স্ট্রিংটি কেবল একটি লজিক্যাল নিউলাইন হিসেবে ব্যাখ্যা করা হবে।

## অন্যান্য স্টাইল সংক্রান্ত সুপারিশ

ইনডেন্টেশন দুই, তিন বা চারটি SPACE ক্যারেক্টারের হতে পারে, তবে _দুই ক্যারেক্টারের_ ইনডেন্টেশন এবং ইনডেন্টেশনে ধারাবাহিকতা বেশি পছন্দনীয়।

একটি ফাংশনের শেষ **_return_** ইনস্ট্রাকশনটি লেবেলের নামের সাথে সারিবদ্ধ হওয়া উচিত, যাতে ওই ফাংশনের শেষ স্পষ্টভাবে চিহ্নিত হয়, এবং এটি _সবসময়_ একটি মান রিটার্ন করা উচিত।

বুলিয়ান NOT অপারেটর কয়েকটি ভিন্ন চিহ্ন দিয়ে প্রকাশ করা যায়। এই ট্র্যাকে পছন্দনীয় চিহ্ন **`\`**, এবং এই ব্যবহারের সাথে ধারাবাহিকতা রাখতে সম্পর্কমূলক 'not equals' অপারেটরটি **`\=`** হওয়া উচিত।

বুলিয়ান মান **`false`** ও **`true`** যথাক্রমে **`0`** ও **`1`** দিয়ে প্রকাশ করা হয়। এই মানগুলোর জন্য কোনো পূর্বনির্ধারিত লিটারেল নেই।

এরর অবস্থা রিটার্ন ভ্যালু দিয়ে বোঝানো হয়, যেখানে খালি স্ট্রিং **`''`** বা **`-1`** প্রসঙ্গ অনুযায়ী এরর অবস্থা নির্দেশ করে।

## Test ফাইল লেআউট

একটি অনুশীলনীতে একটি মাত্র test ফাইল থাকবে, যা অনুশীলনীর শীর্ষ-স্তরের ডিরেক্টরিতে থাকবে এবং এর নাম হবে: `<exercise>-check.rexx`

এই রীতি অনুসরণ করলে `acronym` অনুশীলনীর test ফাইলের নাম হবে: `acronym-check.rexx`

প্রতিটি অনুশীলনীর test ফাইল একটি শিথিল কিন্তু নির্দিষ্ট ধরনে সাজানো থাকে, যাতে শিক্ষার্থীরা অনুশীলনীর প্রয়োজনীয়তা বুঝতে পারে এবং অবদানকারীর কাজ, অর্থাৎ test তৈরি করা বা বাড়ানো সহজ হয়।

নিচেরটি `acronym` অনুশীলনীর test ফাইলের একটি অংশ:

```rexx
/* Unit Test Runner: t-rexx */
function = 'Abbreviate'
context('Checking the' function 'function')

/* Unit tests */
check('basic' function||'("Portable Network Graphics")',,
      function||'("Portable Network Graphics")',, 'to be', 'PNG')

check('lowercase words' function||'("Ruby on Rails")',,
      function||'("Ruby on Rails")',, 'to be', 'ROR')
```

ফাইলটি দুটি যৌক্তিক অংশে বিভক্ত, প্রতিটি একটি কমেন্ট লাইন দিয়ে চিহ্নিত।

প্রথম অংশটি **_পরীক্ষাধীন ফাংশন_**-এর নাম (এখানে `Abbreviate` ফাংশন) `function` ভ্যারিয়েবলে অ্যাসাইন করে। এই ভ্যারিয়েবলের নামটি বর্ণনামূলক কিন্তু স্বেচ্ছাকৃত, এবং যেখানেই পরীক্ষাধীন ফাংশনের নাম দরকার সেখানেই বাকি ফাইলে এটির উল্লেখ করা হয়।

এই অংশেই `context` ফাংশনের একটি কল আছে, যার উদ্দেশ্য নিজেই স্পষ্ট।

পরের অংশে unit test-গুলো আছে। `check` ফাংশনের প্রতিটি ইনভোকেশন একটি একক unit test। প্রত্যাশিত প্যারামিটার:

```rexx
check(<test description>,
      <function invocation>,
      [<actual result variable>],
      <test comparator>,
      <expected result>)
```

**\<test description>** হলো test চালানোর সময় যে স্ট্রিংটি দেখানো হয়। এটিকে যতটা সম্ভব বর্ণনামূলক করতে, পরীক্ষাধীন ফাংশনের নাম এবং তার কাছে পাঠানো আর্গুমেন্ট নিয়ে গঠিত একটি স্ট্রিং ব্যবহারের সুপারিশ করা হয়, যেমনটি উদাহরণে দেখানো হয়েছে।

**\<function invocation>** হলো প্রকৃত ফাংশন ইনভোকেশন বা কল, যা তার রিটার্ন ভ্যালু test তুলনার জন্য `check`-এ পাঠায়।

**\<actual result variable>** একটি ঐচ্ছিক প্যারামিটার, এবং ব্যবহার করা হলে এটি এমন একটি ভ্যারিয়েবলের নাম যা test তুলনার জন্য ব্যবহৃত মান ধারণ করে।

এটি ব্যবহারের কারণ হলো পরীক্ষাধীন ফাংশনের রিটার্ন ভ্যালু নয়, বরং রিটার্ন ভ্যালু থেকে _উদ্ভূত_ ফলাফল যাচাই করা সম্ভব করা। একটি স্পষ্ট উদাহরণ হলো যখন রিটার্ন ভ্যালুটি কয়েক কিলোবাইটের একটি স্ট্রিং, যেমনটি দেখানো হয়েছে:

```rexx
expected_length = LENGTH(FUT(...))

check('...', FUT(...), expected_length, 'to be', 50)
```

মনে রাখবেন, \<function invocation> আর্গুমেন্টটি তবুও পাঠাতে হবে।

**\<test comparator>** হলো কোন ধরনের তুলনা করতে হবে তা বর্ণনা করা একটি স্ট্রিং। বেশিরভাগ ক্ষেত্রেই এটি 'to be' স্ট্রিংটি হবে, যা সমতার জন্য তুলনার অনুরোধ করে। অন্য তুলনার বিকল্পের জন্য unit test ফ্রেমওয়ার্কের ডকুমেন্টেশন দেখুন।

**\<expected result>** হলো, স্বতঃস্পষ্টভাবেই, যে মানের সাথে প্রকৃত ফলাফল তুলনা করা হয়।

test ফাইলের মধ্যে ভ্যারিয়েবল অবাধে ডিক্লেয়ার করা যায় (অবশ্যই ব্যবহারের আগে), এবং লিটারেলের জায়গায় `check`-এর আর্গুমেন্ট হিসেবে ব্যবহার করা যায়।

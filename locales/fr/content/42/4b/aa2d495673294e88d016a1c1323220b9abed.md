# À propos

Dans les concepts précédents, on a vu que la directive `global` rend une fonction ou une variable définie dans un fichier source visible depuis les autres fichiers.
De même, la directive `extern` indique à l'assembleur qu'une fonction ou une variable utilisée dans le fichier source courant est définie dans un autre.

Ces deux directives sont le principal moyen pour le code assembleur d'interagir avec d'autres fichiers sources afin d'obtenir de la modularisation.

Pour ce qui est de ces directives, peu importe que le code externe soit défini ou utilisé en assembleur ou dans un langage de haut niveau.
Ainsi, par exemple, même une fonction définie dans un langage de haut niveau peut être utilisée dans du code x86-64 si elle est déclarée `extern`.

De la même manière, la convention d'appel est partagée par toutes ces fonctions, qu'elles soient définies en assembleur ou dans un langage de haut niveau, et même avec le système d'exploitation (OS).

Cependant, comme en assembleur les données ne sont qu'une suite d'octets, il est important de comprendre comment le langage de haut niveau avec lequel on interagit gère la mémoire.

## Les types en C

Le langage C est un choix courant de langage de haut niveau pour interagir avec du code assembleur.
Il facilite l'interaction avec le système d'exploitation, en offrant des surcouches de haut niveau pour de nombreuses tâches importantes, comme afficher à l'écran, lire depuis un clavier ou allouer de la mémoire dynamique.

Dans ce parcours, les tests sont écrits en C, il est donc important de donner un aperçu général du langage.

### Les types primitifs

Le C possède de nombreux types primitifs, et leur taille, en octets, peut varier.
Certains d'entre eux sont résumés dans le tableau suivant, avec leur taille typique sur un système x86-64 :

| type      | nombre d'octets | entier / à virgule flottante |
|-----------|-----------------|------------------------------|
| _Bool     | 1               | entier                       |
| char      | 1               | entier                       |
| short     | 2               | entier                       |
| int       | 4               | entier                       |
| long      | 4 ou 8          | entier                       |
| long long | 8               | entier                       |
| float     | 4               | à virgule flottante          |
| double    | 8               | à virgule flottante          |

Chacun de ces types entiers peut être signé (par défaut) ou non signé.
S'ils sont non signés, il faut le préciser, par exemple : `unsigned int`.

Il existe des alias pour les types entiers, définis pour permettre un contrôle précis de leur taille :

| alias   | nombre d'octets |
|---------|-----------------|
| int8_t  | 1               |
| int16_t | 2               |
| int32_t | 4               |
| int64_t | 8               |

Ces alias peuvent être préfixés par `u` pour indiquer un type non signé, par exemple : `uint64_t`.

D'autres alias notables sont :

| alias  | type                                          |
|--------|-----------------------------------------------|
| bool   | _Bool                                         |
| size_t | généralement un entier non signé de 8 octets  |

Un `_Bool`, ou son alias `bool`, a la particularité d'occuper un octet entier tout en ne pouvant prendre que deux valeurs : `true` (`1`) et `false` (`0`).

Les valeurs de ces types primitifs sont passées aux fonctions et renvoyées par elles selon les règles habituelles pour les entiers et les valeurs à virgule flottante.

### Les énumérations

Une [énumération][enum] est un type qui peut prendre l'un d'une série d'éléments indiqués explicitement :

```c
enum example {
    example_1,
    example_2,
    example_3,
    example_4
};
```

En C, les énumérations sont implicitement converties en un type entier, généralement un `int`, c'est-à-dire un entier de 4 octets.

Par défaut, le premier élément possible d'une énumération est converti en `0` et chaque élément suivant est converti en l'entier suivant.
Ainsi, dans l'`enum example` défini ci-dessus, `example_1` aurait la valeur `0`, `example_2` la valeur `1`, et ainsi de suite.

Il est possible d'indiquer la valeur de n'importe quel élément d'une énumération, et par défaut l'élément suivant prendra l'entier suivant comme valeur :

```c
enum example_2 {
    example_1 = 4,
    example_2 = 8,
    example_3
}; // example_3 is equal to 9
```

### Les adresses mémoire

En C, une adresse mémoire est désignée par un [pointeur][pointer] vers un type et se note avec l'opérateur `*`.
Ainsi, par exemple, `int64_t *` désigne un emplacement mémoire pour un ou plusieurs `int64_t`.

Les adresses sont traitées comme des entiers de 8 octets, comme d'habitude.

### Les tableaux

Les tableaux sont passés aux fonctions et renvoyés par elles sous forme de pointeurs vers leur premier élément.

```c
int64_t example_arr[] = {1, 2, 3}; // this is an array of 3 signed 8-byte integers
fn(example_arr); // this is a function that passes a pointer (int64_t *) to the beginning of the array as argument
```

Chaque élément d'un tableau a la taille du type d'élément du tableau.
Le `example_arr` défini ci-dessus, par exemple, a 3 éléments de 8 octets chacun, soit 24 octets au total.

Comme les tableaux ne stockent pas leur longueur, une valeur séparée est généralement nécessaire pour indiquer le nombre d'éléments, à moins qu'une valeur sentinelle ne marque la fin.

### Les _strings_

Les _strings_ en C sont un tableau de `char`, un type d'un octet.
La plupart des _strings_ sont composés de caractères ASCII et terminés par un NUL, ce qui signifie qu'ils prennent fin lorsqu'on rencontre un octet de valeur `0`.
Ainsi, la longueur d'un _string_ n'a généralement pas besoin d'être passée comme argument séparé.

## Appeler des fonctions de la bibliothèque C

La directive `extern` déclare seulement qu'un symbole est défini dans un autre fichier.
La façon dont un appel à ce symbole est réellement effectué dépend de la manière dont ce code externe est lié.

Pour les fonctions ordinaires liées avec le code, l'éditeur de liens trouve directement la fonction externe, et un simple `call` suffit donc.

Cependant, les fonctions de la bibliothèque standard du C telles que `malloc`, `free` et `printf` sont généralement résolues à l'exécution depuis une bibliothèque partagée, dont l'adresse n'est pas connue au moment où le code est assemblé.
L'appel passe donc par un _stub_ situé à un décalage connu dans une [table de liaison des procédures (PLT)][plt].
Chaque fois qu'on appelle une fonction externe de bibliothèque depuis l'assembleur, NASM exige une indication précisant que cet appel doit être résolu via la PLT.

En `elf64` (format de sortie utilisé par les programmes Linux), cette indication s'ajoute en plaçant `wrt ..plt` (« avec référence à plt ») après l'appel.
Par exemple, `call printf wrt ..plt`.

Dans les programmes `macho64` (format de sortie utilisé par les programmes macOS), en revanche, un tiret bas devant le nom de la fonction suffit.
Par exemple, `extern _printf`, puis `call _printf`.
Cependant, comme ce parcours assemble le code `macho64` avec l'option `--prefix _`, ce tiret bas est ajouté automatiquement par l'assembleur dans les deux situations : par exemple, `extern printf`, puis `call printf`.

À noter que l'exécuteur de tests d'Exercism s'exécute dans une image Linux, donc toute solution soumise qui appelle des fonctions de la bibliothèque C doit utiliser `wrt ..plt`.
On peut utiliser une garde au moment de l'assemblage pour choisir correctement entre les formats de sortie :

```x86asm
extern malloc

%ifidn __OUTPUT_FORMAT__,elf64
    call malloc wrt ..plt       ; elf64: reach the function through the PLT
%else
    call malloc                 ; macho64: the linker generates the call stub
                                ; the underscore is added automatically by an assembler flag
%endif
```

## Les appels système

De nombreuses opérations ne peuvent pas être effectuées directement par les programmes au niveau utilisateur, comme ceux exécutés dans ce parcours.
Lire depuis `stdin`, écrire sur `stdout`, demander de la mémoire dynamique, interagir avec des périphériques, etc., tout cela est pris en charge par le système d'exploitation (OS).

Un programme au niveau utilisateur doit demander explicitement au système d'exploitation d'effectuer ces opérations, quand c'est nécessaire.
Cela se fait avec l'instruction [`syscall`][syscall].
Conceptuellement, on peut voir cette instruction comme un appel à une procédure prédéfinie du système d'exploitation (un appel « système »).

Les arguments d'un appel système doivent être passés au système d'exploitation dans les registres généraux (GPR) : `rdi`, `rsi`, `rdx`, `r10`, `r8` et `r9`.

À noter que l'ordre est presque le même que celui utilisé lors d'un appel de fonction, mais `rcx` est remplacé par `r10`.
C'est parce que `syscall` utilise `rcx` et `r11` pour sauvegarder l'adresse de retour et les drapeaux (qui sont restaurés avant de rendre le contrôle à la fonction appelante).
Ces deux registres doivent être considérés comme écrasés à chaque `syscall`.

Contrairement à `call`, il n'y a pas d'étiquettes pour désigner les « fonctions » du système.
À la place, on y accède par des numéros spécifiques placés dans `rax` avant l'appel.
Toute valeur renvoyée, s'il y en a une, est également placée dans `rax`.

Les conventions ci-dessus sont décrites [dans une annexe de l'ABI System V][linux-convention] qui traite spécifiquement de Linux, et qui est marquée comme purement informative.
En pratique, les appels système disponibles, leur numéro et la manière dont les erreurs sont signalées sont des détails propres au système d'exploitation qui varient beaucoup d'un système à l'autre, et même entre différentes versions d'un même système.

De nombreuses fonctions de la bibliothèque C, et d'autres fonctions proprement définies par le système d'exploitation, sont des surcouches de plus haut niveau au-dessus d'un appel système.
L'ABI recommande de préférer ces surcouches à un simple `syscall`, et Apple [ne garantit pas la compatibilité][mac-qa1118] au niveau de l'interface d'appel système du noyau.

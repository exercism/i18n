# Contribuer au parcours Rust d'Exercism

Les _issues_ et les _pull requests_ sont actuellement fermées automatiquement.
Merci de publier un message sur [le forum d'Exercism] pour proposer des modifications.
Les contributions sont les bienvenues si elles sont coordonnées sur le forum.

[le forum d'Exercism]: https://forum.exercism.org/

## Règles générales

- [Code de conduite](https://exercism.org/code-of-conduct)
- [Les consignes d'Exercism sur les _pull requests_](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## Outillage

Une partie de l'outillage se présente sous forme de scripts bash dans `bin/`.
Il y en a beaucoup plus dans `rust-tooling/`,
qu'il vaut mieux privilégier pour tout ce qui n'est pas trivial.

Il y a aussi une configuration [`mise`](https://mise.jdx.dev/)
avec quelques commandes utiles pour interagir avec le dépôt.
N'hésite pas à la compléter.

Si tu veux exécuter les tests de CI en local, `mise run test` t'emmènera déjà assez loin.

## Exclure des tests et en ajouter des personnalisés

Lorsque tu crées ou mets à jour un exercice, tu peux décider d'exclure certains tests de la génération.
Pour cela, mets `include = false` dans `.meta/tests.toml`.
Pense à ajouter un commentaire expliquant la raison de cette exclusion.

Si tu veux ajouter des tests supplémentaires propres au parcours, tu peux le faire dans un fichier `.meta/additional-tests.json`.
Ne le fais que si tu as une bonne raison de ne pas intégrer ces tests en amont.
Un commentaire dans le test supplémentaire devrait répondre à ces questions :
- Pourquoi ce test n'est-il pas intégré en amont dans `problem-specifications`, c'est-à-dire pourquoi n'a-t-il pas de valeur générale pour les autres langages ?
- Pourquoi ce test est-il tout de même utile pour le parcours Rust ?

## Créer un nouvel exercice

Commence par te familiariser avec la [documentation d'Exercism sur les exercices d'entraînement].

[documentation d'Exercism sur les exercices d'entraînement]: https://exercism.org/docs/building/tracks/practice-exercises

Lance `mise run add-exercise` et tu seras invité à saisir les informations
minimales nécessaires pour générer le _stub_ de l'exercice.
Ensuite, ouvre l'exercice généré et remplis tous les espaces réservés que tu trouves.
Cela comprend notamment :

- écrire le _stub_ de l'exercice dans `src/lib.rs`
- ajouter une solution d'exemple dans `.meta/example.rs`
- ajuster `.meta/test_template.tera`

Les tests sont générés à l'aide du moteur de gabarits [Tera].
L'entrée du gabarit, ce sont les données canoniques de [`problem-specifications`].

Tu trouveras quelques conseils sur l'écriture de gabarits Tera [ici](#tera-templates).

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

De nombreux aspects d'un exercice correctement implémenté sont vérifiés en CI.
Je te recommande de _te lancer, tout simplement_, plutôt que de passer des heures
à étudier et à écrire de la documentation sur le processus.
Si quelque chose casse, corrige-le et ajoute un test ou une automatisation
pour que cela ne se reproduise plus.

Si tu crées un exercice d'entraînement de zéro,
qui n'existe pas dans `problem-specifications`,
tu dois écrire tes tests à la main.
Les tests doivent être triés par complexité croissante,
afin que les apprenants puissent les réactiver un par un et résoudre l'exercice en TDD.
Consulte [la documentation d'Exercism](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)
pour en savoir plus sur l'écriture de bons tests.

Sauf circonstances extraordinaires,
le fichier _stub_ doit compiler avec `cargo test --no-run`.
Cela nous permet de vérifier que les signatures du fichier _stub_
correspondent aux signatures attendues par les tests.
Pour cela, utilise `todo!()` comme corps de chaque fonction.
S'il existe une raison justifiée pour que ce ne soit pas possible,
ajoute une clé `.custom."allowed-to-not-compile"`
dans le `.meta/config.json` de l'exercice, en indiquant la raison.

## Mettre à jour un exercice

De nombreux exercices sont dérivés de [`problem-specifications`].
Cela inclut leur suite de tests et leur documentation destinée aux utilisateurs.
Avant de proposer des modifications ici,
vérifie si elles ne devraient pas plutôt être faites dans `problem-specifications`.

Lance `mise run update-exercise` pour mettre à jour un exercice.
Cela délègue la majeure partie du travail à `configlet sync --update`
et relance le générateur de tests.

Lorsque tu mets à jour un exercice qui n'a pas encore de gabarit Tera,
un nouveau sera généré pour toi.
Tu devras probablement l'ajuster quelque peu.

Tu trouveras des conseils sur l'écriture de gabarits Tera [dans la section suivante](#tera-templates).

## Gabarits Tera

La documentation complète des gabarits Tera se trouve [ici][tera-docs].
Voici quelques approches qui ont fonctionné pour nos besoins spécifiques.

Tu voudras probablement jeter un œil au `canonical-data.json` de l'exercice pour voir à quoi ressemblent tes données d'entrée.
Tu peux utiliser `bin/symlink_problem_specifications.sh` pour créer un lien symbolique vers ces données
dans le répertoire de l'exercice lui-même. Pratique !

Le nom de la propriété d'entrée diffère d'un exercice à l'autre.
Le gabarit par défaut ressemblera à ceci :

```txt
let input = {{ test.input | json_encode() }};
```

Tu devras ajouter le champ d'entrée propre à cet exercice, par exemple

```txt
let input = {{ test.input.integers | json_encode() }};
```

Certains exercices peuvent avoir des valeurs de retour d'erreur.
Tu peux utiliser une structure _if-else_ pour générer quelque chose de différent,
selon la structure des données :

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

Certains exercices comportent plusieurs fonctions que l'apprenant
doit implémenter et qui sont donc testées.
Dans ce cas, les données canoniques contiennent un champ `property`.
Tu peux construire des chaînes de _if-else_ basées sur `test.property` et générer une fonction différente en fonction de cela.

Certains exercices ont leurs cas de test organisés en _groupes de tests_.
Ton gabarit devra en tenir compte.
Dans de nombreux cas, tu peux simplement aplatir la structure. (exemple : [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
Cependant, il arrive que des tests aient la même description dans des groupes différents, ce qui crée des conflits de nommage si la structure est aplatie.
Dans ce cas, tu peux utiliser la description du groupe pour organiser les tests en modules. (exemple : [`forth`](/exercises/practice/forth/.meta/test_template.tera))

Il existe quelques filtres Tera personnalisés dans [`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs).
Voici la liste, que l'on espère à jour :
- `to_hex` formate les entiers en hexadécimal
- `make_ident` transforme une _string_ arbitraire en un identifiant Rust correct.
   Très utile pour générer des noms de fonctions à partir des descriptions de tests.
- `fmt_num` formate les littéraux numériques (insère un `_` tous les trois chiffres)

N'hésite pas à ajouter les tiens dans le _crate_ `rust-tooling`.
En espérant que tu penseras aussi à mettre à jour la liste ici. 🙂

Pour un exemple assez compliqué, jette un œil au gabarit de test de `triangle`.
Il organise les cas de test en modules et détecte dynamiquement quels tests placer derrière des _feature gates_.
Cet exercice réimplémente aussi certains cas de test venus d'amont dans `additional-tests.json`, afin d'y ajouter les informations supplémentaires nécessaires pour générer de bons tests.

[tera-docs]: https://keats.github.io/tera/docs/#templates

## Programme

Le programme est actuellement désactivé en raison de sa faible qualité.
Consulte [ce message du forum](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)
pour un peu de contexte sur cette décision.

Créer un meilleur programme serait très bénéfique,
mais c'est beaucoup de travail et cela demande une bonne communication et une bonne coordination.
Pense à discuter de tes projets sur le forum
avec des personnes qui ont de l'expérience dans la construction de programmes.

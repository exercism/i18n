# Tri

```sather
   numbers.sort;                                  -- the natural order
   words.insertion_sort_by(bind(before(_, _)));   -- an order you supply
```

## Ce dont sort a besoin

`sort` exige que le type des éléments dispose d'`is_lt`. `INT`, `STR`, `CHAR`, `FLTD` et `INTI` en disposent tous. Une classe qui t'est propre n'en dispose pas tant que tu n'en écris pas une.

`insertion_sort_by` n'exige rien du type des éléments : tout ce qu'il a besoin de savoir se trouve dans la routine que tu lui passes.

## Ce que doit être une comparaison

La routine doit définir un ordre cohérent, sinon le résultat n'est pas défini :

- si `before(a, b)` est vrai, alors `before(b, a)` doit être faux ;
- si `a` vient avant `b` et `b` avant `c`, alors `a` vient avant `c` ;
- `before(a, a)` doit être faux.

C'est sur ce dernier point que les gens trébuchent. Écrire `<=` au lieu de `<` revient à dire qu'une chose vient avant elle-même, et un tri auquel on donne une telle comparaison peut produire n'importe quoi.

## Les ex æquo

Ni `sort` ni `insertion_sort_by` ne sont **stables** : les éléments que la comparaison déclare égaux peuvent ressortir dans un ordre ou dans l'autre, et dans cette bibliothèque ils ressortent généralement inversés.

Ainsi, l'astuce qui consiste à trier deux fois (d'abord par nom, puis par points, en espérant que les équipes à égalité de points restent dans l'ordre alphabétique) ne fonctionne pas ici. Et on ne peut pas davantage compter sur l'ordre d'entrée, pour quoi que ce soit.

Si les ex æquo comptent, règle-les **dans la comparaison**. Fais-en un ordre total, pour que deux éléments différents ne soient jamais déclarés égaux :

```sather
   shorter(a, b : STR) : BOOL is
      if a.size /= b.size then return a.size < b.size; end;
      return a < b;                  -- same length: alphabetical
   end;
```

Ça vaut la peine de le faire même quand tu penses que les ex æquo sont impossibles. Une comparaison qui répond faux dans les deux sens laisse le résultat non spécifié, et le bug se manifeste par un ordre qui change sans raison visible.

## Les autres

| Appel | Effet |
| --- | --- |
| `a.sort` | sur place, ordre naturel, non stable |
| `a.insertion_sort_by(lt)` | sur place, ton ordre, stable |
| `a.is_sorted` | vérifie |
| `a.is_sorted_by(lt)` | vérifie selon ton ordre |
| `a.binary_search(e)` | recherche, dans un tableau trié |
| `a.binary_search_by(e, lt)` | recherche, selon ton ordre |

`binary_search` sur un tableau non trié n'échoue pas : il répond n'importe quoi. Sa précondition le dit bien, et les préconditions ne sont pas vérifiées, sauf si l'on donne `-chk` au compilateur.

## Le coût

Le tri par insertion effectue un travail proportionnel au carré de la longueur : parfait pour un classement d'une douzaine d'équipes, mais un mauvais choix pour dix mille enregistrements. `ARR_SORT_ALG::sort_by` est la version en tri rapide de la même idée, à utiliser quand le tableau est grand et que la stabilité n'a pas d'importance.

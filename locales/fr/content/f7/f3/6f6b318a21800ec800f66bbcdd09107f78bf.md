# À propos

Une fonction est [récursive terminale][recursion-tc] si la _dernière_ chose exécutée par la fonction est un appel à elle-même.

Chaque fois qu'une fonction est appelée, un _cadre de pile_ contenant ses variables locales et ses arguments est empilé au sommet de [la pile d'appels][call-stack].
Quand une fonction renvoie, le cadre de pile est retiré de la pile.

Les fonctions récursives terminales permettent [l'optimisation des appels terminaux][tail-call-optimization] (ou l'élimination des appels terminaux).
C'est une optimisation qui permet de réutiliser le dernier cadre de pile pour l'appel de fonction suivant, quand on sait que la fonction précédente n'en a plus besoin.
Cela permet d'éviter le débordement de la pile d'appels, une situation où il y a tellement de cadres sur la pile d'appels qu'il ne reste plus assez de mémoire pour en créer un nouveau.

## L'optimisation des appels terminaux en Elm

Sous certaines conditions, le compilateur Elm est capable d'effectuer automatiquement une optimisation des appels terminaux lors de la compilation vers JavaScript.

L'optimisation peut avoir lieu pour une fonction récursive quand la _dernière_ opération d'une branche consiste à appeler la fonction elle-même dans une simple application de fonction.
Regardons quelques exemples :

```elm
factorial : Int -> Int
factorial n =
  if n <= 1 then
    n
  else
    n * factorial (n-1)
```

L'implémentation ci-dessus n'est pas récursive terminale, car la dernière opération de la branche `else` est une multiplication `n *`.

```elm
factorial : Int -> Int
factorial n =
  factorialHelper n n

factorialHelper : Int -> Int -> Int
factorialHelper n resultSoFar =
  if n <= 1 then
    resultSoFar
  else
    factorialHelper (n-1) (n * resultSoFar)
```

L'implémentation ci-dessus est récursive terminale et sera optimisée, car la dernière opération de la branche `else` est `factorialHelper` qui s'appelle elle-même.
Cela ne serait pas possible pour une fonction dont la signature de type est `Int -> Int`, et en pratique, on obtient souvent l'optimisation des appels terminaux en définissant des fonctions auxiliaires.

## Cas limites

Dans certains cas, le compilateur n'est pas capable d'optimiser les fonctions récursives. Regardons quelques exemples.

Si `f x = f (x - 1)` est récursive terminale, `f x = (x - 1) |> f` ne l'est pas, car l'application de fonction `|>` est la dernière opération et est considérée comme distincte de `f`.
De même, les fonctions qui se terminent par une condition booléenne `f x = x > 0 || f (x - 1)` ne sont pas récursives terminales.

La fonction `f x = if f (x - 1) then 1 else 0` n'est pas récursive terminale, car l'expression dans le `if` n'est pas considérée comme une branche.
De même, un appel récursif dans une instruction `case` ne serait pas optimisé non plus.

La fonction `f x = let y = f (x - 1) in y` n'est pas récursive terminale, car elle s'appelle elle-même dans une instruction `let`, qui n'est pas considérée comme une branche.
En revanche, dans `f x = let g x = g (x - 1) in g x`, la fonction `g` est récursive terminale et sera optimisée, même si elle est définie dans une instruction `let`.

La fonction `f x = if x > 0 then f (x + 1) else 1 + f x` sera optimisée _partiellement_ : la branche `then` peut être optimisée, mais la branche `else` ne le peut pas.
L'optimisation partielle est le mieux que l'on puisse obtenir dans certaines situations, comme le parcours de structures arborescentes ou la définition de fonctions co-récursives.

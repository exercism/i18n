# À propos

Dans les applications C#, le caractère aléatoire est généralement obtenu à l'aide de la classe `System.Random`.

Cet [article][system-random] est une excellente introduction au sujet.

Quand on se familiarise avec une classe d'une bibliothèque, il vaut toujours la peine d'étudier la [documentation][system-random] pour connaître les propriétés, les méthodes et leurs surcharges.

L'exercice de code a mis en évidence un certain nombre de points :

- Le générateur de nombres aléatoires n'a pas besoin de [graine][random-seedless].
- `Random.Next()` peut générer une plage d'entiers
- `Random.Double()` peut générer un nombre décimal entre 0 et 1
- Les bornes supérieures de `Next...()`, `Double()` et `Sample()` sont **exclues**, de sorte que `Random.Next(1,19)` produira des valeurs de 1 à 18, mais pas 19.
- Une fois que tu as ton nombre aléatoire, tu peux en faire ce que tu veux

Il existe 3 façons de mettre en œuvre ce dernier point :

- Tu peux obtenir le nombre aléatoire et le manipuler. Dans le cas de l'exercice de code, cela consisterait à appeler `Random.NextDouble()` et à le multiplier par 100. Ce [passage][random-use-case-array] traite de la sélection aléatoire d'éléments dans un tableau.
- Tu peux hériter de `System.Random` et redéfinir la méthode `Sample()`.
- Tu peux encapsuler une instance de `System.Random` comme membre d'une classe qui t'est propre, par exemple [pour générer des booléens][random-use-cases].

Les nombres générés par `Random` ne sont pas garantis uniques.

Il est [recommandé][random-thread-safety] d'instancier `System.Random` comme membre statique. Mais note qu'il n'est pas _thread-safe_.

Tu peux voir de la documentation qui déconseille l'utilisation de constructeurs sans graine. Cela s'applique surtout à .NET Framework plutôt qu'à .NET Core (que _Exercism_ utilise). Pour tous les détails, lis [ceci][random-multiple-instantiations].

Il est déconseillé d'utiliser `System.Random` pour la cryptographie ou la sécurité. Voir ce [fournisseur][crypto-provider] et ce [générateur de nombres][crypto-rng].

## Sûreté des threads

Dans le contexte des API de bibliothèques, « not thread safe » est simplement une façon de dire que, si tu es susceptible d'accéder aux instances de la classe depuis plusieurs [threads][threading] concurrents, tu dois fournir tes propres mécanismes de synchronisation entre threads ou, dans le cas de collections, envisager d'utiliser une version concurrente de la classe. Sans ces précautions, des [conditions de concurrence][so-race-conditions] risquent de se produire. Si ta base de code n'utilise pas plusieurs threads, et ne risque pas de le faire, alors cet avertissement a peu d'importance.

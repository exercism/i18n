# Introduction

Tu as déjà *utilisé* des flux dans `channel-chatter` et tu les as libérés dans `boatswains-bilge`. Cet exercice est ton premier flux personnalisé : une classe qui implémente le [protocole][stream-protocol], si bien que le même code `with-input-stream` / `read1` / `stream-read1` qui fonctionnait sur un `<string-reader>` fonctionne sur le tien.

## Les _mixins_ : l'autre moitié de la hiérarchie de classes

Tu connais déjà `TUPLE: child < parent …` depuis `dragons-descendants` : une hiérarchie à parent unique où les _slots_ descendent. Factor dispose d'une *seconde* façon d'étendre le graphe de classes : les **_mixins_ ouverts**. Un `MIXIN: m` déclare une classe sans _slots_ que d'autres classes peuvent rejoindre après coup avec `INSTANCE: c m`. L'appartenance est plusieurs à plusieurs : une classe peut être instance d'autant de _mixins_ qu'elle le souhaite.

Le protocole des flux utilise deux _mixins_ pour marquer quelle moitié de l'interface une classe implémente :

```factor
INSTANCE: my-stream input-stream    ! readable
INSTANCE: my-stream output-stream   ! writable
```

Un flux peut être l'un, l'autre, ou les deux. Les méthodes génériques de `input-stream` (ou `output-stream`) s'adressent alors à toute classe ayant rejoint le _mixin_ : c'est ainsi que les `read1`, `stream-contents`, `with-input-stream` et autres génériques ambiants trouvent le chemin jusqu'à ta classe.

Les _mixins_ sont *ouverts* : tu peux ajouter un nouveau membre après la déclaration du _mixin_, même dans un autre vocabulaire. C'est là toute la différence avec `TUPLE: < parent`, où la relation est figée au moment de la déclaration de la classe enfant.

## Les génériques du protocole

Les génériques du protocole vivent dans `io` :

```
stream-read1         ( stream -- elt/f )
stream-read          ( n stream -- seq/f )
stream-read-unsafe   ( n buf stream -- count )
stream-write1        ( elt stream -- )
stream-write         ( seq stream -- )
stream-flush         ( stream -- )
stream-element-type  ( stream -- type )
```

`stream-read1` renvoie l'octet suivant (ou `f` à la fin du flux) ; `stream-write1` en écrit un. `stream-read-unsafe` est la lecture par lots de plus bas niveau que fournissent la plupart des flux d'entrée ; `stream-read` s'appuie dessus et gère l'allocation. `stream-element-type` indique si le flux travaille en octets (`+byte+`) ou en caractères (`+character+`) ; quand tu enveloppes un autre flux, l'implémentation la plus simple délègue simplement au flux sous-jacent.

## Le nettoyage vient de `destructors`

Les flux sont des ressources à libérer : un flux personnalisé étend `disposable` et implémente `dispose*`. C'est le framework de `boatswains-bilge`, appliqué à une classe de flux :

```factor
TUPLE: my-stream < disposable underlying ;

: <my-stream> ( underlying -- s )
    my-stream new-disposable swap >>underlying ;

M: my-stream dispose* underlying>> dispose ;
```

Une fois cela en place, tous les combinateurs `with-…` de `channel-chatter` fonctionnent automatiquement sur ton flux.

# À propos

Dans de nombreux langages orientés objet, il est courant d'étendre les comportements en [créant une sous-classe][wiki-subclass] d'une classe parente, ce qui permet d'hériter des méthodes du parent tout en en ajoutant de nouvelles.
On obtient ainsi une hiérarchie d'objets.

Julia _n'a pas de classes_, et donc, par extension, _n'a pas de sous-classes_.
Comment hériter et étendre des comportements existants ?

On a vu dans les concepts précédents comment créer une hiérarchie de types, ainsi que la manière dont Julia utilise le [dispatch multiple][concept-multiple-dispatch] pour choisir les méthodes en fonction des types d'arguments.

Julia possède aussi plusieurs [interfaces][ref-interfaces] informelles, qui permettent à tes types personnalisés de se brancher sur des comportements déjà définis pour les types standards.

Le plus simple pour l'illustrer est l'interface Iterator.

## [Itérateurs][ref-iterators]

Plus tôt dans le programme, on a vu plusieurs façons dont Julia peut opérer sur chaque élément d'une collection.

- Les [boucles][concept-loops], comme `for item in items...`
- Le [broadcasting][concept-vector-operations] : `[1, 2, 3] .- 0.5`
- Les [fonctions d'ordre supérieur][concept-hof] : `map(√, [1, 4, 9])`
- Les [compréhensions][concept-comprehensions] : `[x * y for x in 1:3 for y in 4:6 if isodd(x * y)]`
- Les [générateurs][concept-comprehensions] : `(x^2 for x in 1:1e6)`, qui sont évalués de façon paresseuse.

De toute évidence, Julia sait parcourir les collections standards élément par élément : les vecteurs et les intervalles dans les exemples ci-dessus, mais aussi les Sets, les Dicts, etc.

Comment ajouter cette capacité à nos propres collections personnalisées, surtout si elles peuvent être parcourues de façon paresseuse comme un générateur ?

### Exigences minimales

Pour créer une séquence que l'on peut parcourir, il faut (au moins) deux choses :

1. Un moyen d'obtenir le _premier_ élément.
2. Un moyen d'obtenir l'élément _suivant_ à partir de l'état courant.

Julia accomplit ces tâches avec des méthodes de la fonction `Base.iterate()`, selon les étapes suivantes :

1. `Base.iterate(iter)` est appelée automatiquement en premier.
    - S'il n'y a rien à parcourir, elle renvoie `nothing`.
    - Sinon, elle renvoie le `Tuple` du premier élément renvoyé et du premier état : `(firstitem, firststate)`.
2. `Base.iterate(iter, state)` est appelée automatiquement si un élément a été renvoyé à l'itération précédente, en prenant `firststate` comme argument `state`.
    - Si l'itération se termine, elle renvoie `nothing`.
    - Sinon, elle renvoie le `Tuple` de l'élément suivant et de l'état suivant : `(nextitem, nextstate)`.
3. Répète l'étape 2 jusqu'à la fin de l'itération.

Toutes ces étapes se déroulent « sous le capot », ce qui signifie que les appels de méthode et l'état sont gérés en interne par le protocole d'itération (l'état restant opaque), et que seul l'élément est exposé aux constructions de haut niveau, comme les boucles.
Autrement dit, on ne voit jamais que l'`item`, tandis que tout le reste demeure dans une boîte noire.

Le [dispatch multiple][concept-multiple-dispatch] est au cœur de tout cela.
Le type d'`iter` détermine quelles méthodes sont appelées, et le nombre d'arguments détermine si c'est le premier élément ou l'élément suivant qui est renvoyé.

Les méthodes pour les types standards sont déjà définies : `Vector`, `Range`, `Set`, etc. ([actuellement][ref-iterations-collections] 14 types au total).

Pour qu'un type personnalisé `MyType` partage les mêmes comportements, il faut d'abord définir :
- `Base.iterate(iter::MyType)`
- `Base.iterate(iter::MyType, state)`

Tout cela peut sembler confus dans l'abstrait, mais ça peut être très simple.
Pour illustrer, imaginons que l'on veuille un type qui donne les puissances d'un entier `n` donné, jusqu'à un nombre maximal.

D'abord, définissons un type personnalisé :

```julia
struct Powers
    n::Int      # base number to raise to a power
    count::Int  # maximum length of the sequence
end
```

On peut maintenant définir les méthodes `iterate` pour ce type, mais quels sont le premier élément et le premier état ?

Pour obtenir le premier élément, certains itérateurs ont besoin d'une mise en place compliquée, mais dans ce cas simpliste, on peut remarquer que le premier élément renvoyé n'est autre que le nombre de base, il suffit donc de vérifier que la valeur de `count` est supérieure ou égale à un.

Intéressons-nous maintenant au premier état, qui transporte l'information utilisée pour l'itération suivante.
C'est à toi de décider quelles informations tu dois garder pour y parvenir, et ce peut être n'importe quel type.

Dans ce cas, on pourrait simplement garder l'« indice » auquel élever `n`, ou bien trouver une option plus performante en utilisant la puissance la plus récente de `n` (c'est-à-dire l'élément renvoyé) et l'« indice » suivant dans la séquence.
On peut regrouper ces deux nombres dans un `Tuple` et le renvoyer comme `state`.

```julia
function Base.iterate(p::Powers)
    # if iteration should continue
    if 1 ≤ p.count
        # return (firstitem, firststate)
        return (p.n, (p.n, 2)) 
    end
    # else terminate iteration
    return nothing
end
```

Dans cet exemple, le premier élément (`p.n`) est renvoyé à la boucle et le premier état `(p.n, 2)` est transmis à la méthode `iterate(P::Powers, state)`.
Là, on peut traiter l'état pour produire l'élément suivant en multipliant l'élément courant par le nombre de base, ce qui augmente sa puissance de `1`.

```julia
function Base.iterate(p::Powers, state)
    # unpack the state
    curr, index = state

    # create next item                 
    next = curr * p.n

    # if iteration should continue
    if index ≤ p.count
        # return (nextitem, nextstate)
        return (next, (next, index + 1))
    end
    # else terminate iteration
    return nothing
end
```

Si la valeur de l'indice reste dans les limites de `count`, le `Tuple` est renvoyé avec l'élément `next` et l'état incrémenté `(next, index + 1)`.
Lorsque la valeur d'`index` dépasse `count`, c'est `nothing` qui est renvoyé à la place, pour indiquer que l'itération est terminée.

Tu as peut-être remarqué que les méthodes `iterate(p::Powers)` et `iterate(p::Powers, state)` ont des corps de fonction assez similaires.
En fait, avec un peu d'astuce, cette similitude permet une implémentation allégée en n'utilisant que la version à deux arguments avec un argument par défaut pour l'état : `Base.iterate(p::Powers, state=(1, 1))`
Avec cela, nous n'aurions pas besoin de la version séparée à un seul argument `iterate(p::Powers)`.
C'est ce que l'on fait couramment en pratique lorsque c'est possible.

~~~~exercism/advanced
Lorsque nous avons introduit les arguments optionnels dans le concept [Fonctions][concept-functions], rien n'a été dit sur l'implémentation.

Depuis, nous avons découvert le dispatch multiple, il est donc plus logique de savoir que Julia convertit automatiquement une fonction _avec_ arguments optionnels en plusieurs méthodes _sans_ arguments optionnels.

Définir `Base.iterate(P::Powers, state=(1, 1))` est exactement équivalent à définir séparément `Base.iterate(P::Powers, state)` et `Base.iterate(P::Powers)`.

[concept-functions]: https://exercism.org/tracks/julia/concepts/functions
~~~~

Pour l'instant, nous avons déjà quelques fonctionnalités utiles : pour les 4 premières puissances de 3, on peut parcourir les résultats avec une boucle, vérifier si un nombre donné figure parmi les résultats, et appliquer des fonctions d'agrégation comme `sum()`.

```julia-repl
julia> for p in Powers(3, 4)
            println(p)
       end
3
9
27
81

julia> 9 ∈ Powers(3, 4) # ∈ is a synonym for in
true

julia> sum(Powers(3, 4))
120
```

### Méthodes supplémentaires

Malgré ce bon début, tout ne fonctionne pas encore.

```julia-repl
julia> [p for p in Powers(3, 4)]
ERROR: MethodError: no method matching length(::Powers)
The function `length` exists, but no method is defined for this combination of argument types.
You may need to implement the `length` method or define `IteratorSize` for this type to be `SizeUnknown`.
```

Comme on pouvait s'y attendre, `length(Powers(3, 4))` donne exactement le même message d'erreur.

C'est facile à corriger, car la longueur fait partie du constructeur du type : 4 dans ce cas.
Il suffit de définir `Base.length()` pour ce type, et on peut alors utiliser les compréhensions et `collect()` sur la séquence.

```julia-repl
julia> Base.length(P::Powers) = P.count

julia> length(Powers(3, 4))
4

julia> [p for p in Powers(3, 4)]
4-element Vector{Int64}:
  3
  9
 27
 81

julia> collect(Powers(3, 4))
4-element Vector{Any}:
  3
  9
 27
 81

julia> Set(Powers(3, 4))
Set{Int64} with 4 elements:
  81
  27
  9
  3
```

Pour des raisons d'efficacité, il vaut mieux définir aussi `Base.eltype()` : le type des éléments du résultat.
Cela permet à des fonctions comme `collect()` de préallouer l'espace du `Vector{Int}` de sortie, plutôt que d'appeler `push!()` de façon répétée sur un `Vector{Any}`.

Remarque la syntaxe, que tu n'as peut-être jamais vue : cette méthode est définie sur le _type_, et non sur une _instance_ du type.

```julia-repl
julia> Base.eltype(::Type{Powers}) = Int
```

Les itérateurs ne sont pas _tenus_ d'avoir une longueur finie.
L'utilisation de séquences « infinies » est plus limitée, mais les parcourir avec une boucle peut être utile tant qu'il existe un moyen de sortir de la boucle avec `break`.
Par exemple, on pourrait définir une variante de `Powers` qui génère des valeurs inférieures à une certaine limite (peut-être `typemax(Int)`, pour éviter le dépassement d'entier).

## Autres interfaces

### [Indexation][ref-indexing]

L'interface des itérateurs nous permet de prendre un type personnalisé quelconque et de le faire se comporter comme une séquence, simplement en définissant quelques méthodes simples.

Supposons que l'on veuille aussi pouvoir indexer la séquence :

```julia-repl
julia> P = Powers(3, 4)
Powers(3, 4)

julia> P[2]
ERROR: MethodError: no method matching getindex(::Powers, ::Int64)
The function `getindex` exists, but no method is defined for this combination of argument types.
```

On peut ajouter ce comportement, et le [manuel][ref-indexing] explique comment.

Au minimum, il faut définir `getindex()`.

```julia-repl
julia> function Base.getindex(P::Powers, i::Int)
          1 ≤ i ≤ P.count || throw(BoundsError(P, i))
          return p.n ^ i
       end

julia> p = Powers(3, 4)
Powers(3, 4)

julia> p[3]
27
```

Il faut aussi définir :

- `firstindex()` et `lastindex()` pour prendre en charge `P[begin]` et `P[end]`.
- Des variantes de `getindex()` pour prendre en charge l'indexation avec des vecteurs et des intervalles.
- En théorie, `setindex!()`, même s'il est difficile de voir ce que cela pourrait bien vouloir dire dans cet exemple.

Cependant, à ce stade, on fournit beaucoup d'efforts juste pour que notre itérateur ressemble davantage à un Vector.

### [AbstractArray][ref-abstractarray]

Cela vaut peut-être la peine de réfléchir à d'autres interfaces qui offrent un meilleur point de départ.

Dans ce cas, on pourrait envisager de faire de `Powers` un sous-type d'[`AbstractArray`][ref-abstractarray], ce qui nous offre gratuitement de nombreux comportements propres aux tableaux.

Pour la séquence `Powers`, le tableau correspondant est un tableau d'entiers, à 1 dimension.
Tu verras parfois cela écrit `AbstractArray{Int, 1}`, mais les alias `AbstractVector{Int}` pour 1D et `AbstractMatrix{Int}` pour 2D sont plus courants dans le code Julia récent.

```julia-repl
julia> struct PowersArray <: AbstractVector{Int}
           n::Int
           count::Int
       end
```

Au lieu de `length()`, il faut maintenant définir `size()` avec un tuple de longueurs le long de chaque dimension : une seule dimension dans ce cas.

```julia-repl
julia> Base.size(PA::PowersArray) = (PA.count,)
```

Comment voulons-nous indexer les entrées ?
Dans le [concept sur les tableaux multidimensionnels][concept-multi-dimensional-arrays], nous avons présenté les deux approches principales :

- Un indice par dimension, donc `M[row, col]` pour une matrice `M`.
- Un indice unique, correspondant à la disposition des entrées en mémoire

On les appelle respectivement `Cartesian` et `Linear`.

Dans cet exemple, nous n'avons qu'une seule dimension, l'indexation linéaire est donc appropriée.

```julia-repl
julia> Base.IndexStyle(::Type{PowersArray}) = IndexLinear()

julia> Base.getindex(PA::PowersArray, i::Int) = PA.n ^ i

julia> p = PowersArray(3, 4)
4-element PowersArray:
  3
  9
 27
 81

julia> p[3]
27
```

Remarque que nous n'avons pas défini `iterate()` dans ce cas.
Julia fournit automatiquement une implémentation par défaut, basée sur notre définition de `getindex()`.

Définir notre propre version d'`iterate()` reste possible, et peut s'avérer plus efficace dans certains cas.

Utiliser l'interface `AbstractArray` est particulièrement utile si l'on veut une itération de dimension supérieure.
Au risque de pousser cet exemple simpliste à bout, cela pourrait signifier les `m` premières puissances des nombres de `1:n`, ce qui définira de façon itérative un tableau de taille `(m, n)`.

```julia-repl
struct PowersMatrix{Int} <: AbstractMatrix{Int}
    ns::AbstractVector{Int}
    count::Int
end

Base.size(PM::PowersMatrix) = (PM.count, length(PM.ns))
Base.IndexStyle(::Type{PowersMatrix}) = IndexCartesian()
Base.getindex(PM::PowersMatrix, i::Int, j::Int) = PM.ns[j] ^ i

julia> PM = PowersMatrix(2:6, 4)
4×5 PowersMatrix{Int64}:
  2   3    4    5     6
  4   9   16   25    36
  8  27   64  125   216
 16  81  256  625  1296

julia> PM[3, 2]
27

julia> PM[7] # column major linear indexing
27

julia> PM[21]
BoundsError: attempt to access 4×5 PowersMatrix{Int64} at index [21]
[...]
```

### [Arrondi][ref-rounding]

Les concepts précédents ont mentionné différentes sortes d'arrondis pour les types numériques.

```julia-repl
julia> round(1.7)
2.0

julia> floor(1.7)
1.0

julia> ceil(1.7)
2.0

# specify output type
julia> round(Int, 1.7)
2

julia> round(2.4 + 7.3im)
2.0 + 7.0im
```

La fonction [`round()`][ref-round] est plus souple que cela : elle permet de préciser le [`RoundingMode`][ref-roundingmode] (parmi les 7 actuellement pris en charge), le nombre de décimales du résultat et la base de numération.

On peut vouloir que les mêmes fonctions prennent en charge nos types personnalisés.
Cela concerne souvent des types composites comme les coordonnées.

```julia-repl
julia> struct Point3D
           x::Float64
           y::Float64
           z::Float64
       end

julia> p = Point3D(7.63, 9.24, 4.50)
Point3D(7.63, 9.24, 4.5)

julia> round(p)
ERROR: MethodError: no method matching round(::Point3D, ::RoundingMode{:Nearest})
The function `round` exists, but no method is defined for this combination of argument types.
```

Sans surprise, il existe une interface `Rounding`, qui exige au minimum que l'on définisse `round()` pour notre type.

```julia-repl
julia> Base.round(P3D::Point3D, r::RoundingMode) = Point3D(round(P3D.x, r), round(P3D.y, r),round(P3D.z, r))

julia> round(p)
Point3D(8.0, 9.0, 4.0)

julia> ceil(p)
Point3D(8.0, 10.0, 5.0)
```

Comme nous incluons `RoundingMode` dans la définition, `floor()` et `ceil()` fonctionnent automatiquement.

Bien sûr, nous sommes libres de définir des formes d'arrondi plus compliquées.

- On pourrait vouloir arrondir `Point3D` à une distance entière de l'origine, dans la même direction.
- Pour les angles, on pourrait vouloir arrondir selon les 16 directions utilisées par les météorologues (_« vent SSO à 15 nœuds »_), c'est-à-dire des multiples de π/8 radians.
- On pourrait vouloir ajouter la possibilité de préciser `digits`, `sigdigits` ou `base`.
- Il existe des [options spéciales][ref-round-periods] pour les périodes de temps

## Résumé

Les interfaces sont assez déroutantes à expliquer, car l'approche de Julia est très différente de celle de la plupart des autres langages.
En particulier, le nom de l'interface peut n'être jamais mentionné dans l'implémentation : contrairement à la [création de sous-classes][wiki-subclass] ou aux [mixins][wiki-mixins].

Pourtant, elles sont étonnamment simples en pratique :

1. Définir un type approprié, en décidant si le sous-typage est utile ou non.
2. Déterminer quelles méthodes sont requises (d'après la [documentation][ref-interfaces]).
3. Implémenter ces méthodes pour ton type personnalisé ; en général quelques méthodes seulement, assez courtes et simples.
4. Laisser le [dispatch multiple][concept-multiple-dispatch] s'occuper du reste, automatiquement.

# Guide de style C

Ce guide décrit le style prévu pour les fichiers d'exemple et de test des exercices du parcours C.

Les règles de ce guide s'ajoutent à celles définies par le fichier [.clang-format][], ou les mettent en évidence.

## Norme C

Le code doit être conforme à la norme C99, plus formellement appelée ISO/IEC 9899:1999.
Les fonctions, types ou autres références de bibliothèque POSIX ou non standard, externes à l'implémentation, ne doivent pas être utilisés.

## Noms

En général, les noms de types, de variables, de structures et de fichiers utilisent la casse `snake_case`, avec toutes les lettres en minuscules et des underscores `_` pour séparer les composants du nom.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Énumérations

Les noms d'énumération sont généralement au singulier plutôt qu'au pluriel.

Les étiquettes d'énumération utilisent la casse `snake_case` avec toutes les lettres en majuscules.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Macros

Les macros qui définissent des constantes se nomment en casse `snake_case` avec toutes les lettres en majuscules.

```c
#define CONSTANT 0x4000
```

La casse `snake_case` en majuscules est appréciée pour les noms de macros, mais les macros qui ressemblent à des fonctions peuvent être nommées en `snake_case` minuscules.

### Types

Les types standard à largeur fixe (dans `stdint.h`) sont préférés aux types entiers de base.

Le type `bool` (de `stdbool.h`) est préféré à `_Bool`.

De même, `size_t` et `ptrdiff_t` (de `stddef.h`) sont préférés pour représenter les quantités liées à la mémoire.

Les types définis par un programme au moyen de `typedef` doivent être nommés avec un suffixe `_t`.
Bien que nous sachions que POSIX réserve le suffixe `_t`, le parcours n'utilise pas POSIX pour le moment.

## Gardes d'inclusion

Des gardes d'inclusion doivent être utilisées dans tous les fichiers d'en-tête.

En général, un jeu de gardes d'inclusion englobe tout le contenu de l'en-tête.

Les gardes de l'implémentation d'exemple (`.meta/example.h`) et du squelette d'exercice (`exercise_name.h`) doivent utiliser des noms de macros qui reprennent le nom de l'exercice.
Les noms de macros de garde doivent suivre la règle ci-dessus concernant la casse des macros.

Par exemple, pour l'exercice `hello-world`, utilise :

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Paramètres

Les paramètres de fonction doivent être nommés à la fois dans la déclaration et dans la définition de toutes les fonctions.
Cela vaut aussi bien pour les fichiers `.c` que `.h`.
Les noms utilisés doivent être identiques dans tous les cas.
Autrement dit, bien que le prototype de fonction suivant soit du C valide, le style est incorrect car le paramètre n'est pas nommé : `void foo(int);`.
Le prototype correct, à condition que toutes les autres déclarations et la définition utilisent elles aussi le nom de paramètre `bar`, serait `void foo(int bar);`.

Lorsque c'est plus simple ou plus approprié, on préfère les paramètres qui exigent de passer les arguments par valeur plutôt que par pointeur.
Note en particulier que cela inclut les paramètres de type `struct`.

Si l'on ne s'attend pas à ce qu'un apprenant modifie les valeurs d'un paramètre de type pointeur dans son implémentation, ce paramètre doit être qualifié `const`.

## Organisation du fichier de test

Le fichier de test de chaque exercice suit une organisation particulière.
Cette organisation vise à la fois à aider les contributeurs à identifier les différentes parties du fichier et à aider les apprenants à comprendre comment fonctionnent les tests.

Comme la plupart des fichiers source C, un fichier de test commence par les directives `#include`.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

Les directives `#include` sont ensuite suivies des fonctions `setUp()` et `tearDown()`.
Jusqu'à présent, aucun exercice ne les utilise (les corps de fonction sont vides), mais elles doivent rester en place pour que les fichiers de test se compilent correctement sur toutes les plateformes.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

Viennent ensuite les éventuelles fonctions auxiliaires utilisées par les fonctions de test.
Les noms de ces fonctions auxiliaires ne doivent pas utiliser le préfixe `test_`.

Viennent ensuite les fonctions de test elles-mêmes.
Leurs noms utilisent le préfixe `test_`.
À l'exception de la première, chaque fonction de test doit avoir `TEST_IGNORE();` comme première instruction.
La première occurrence de cette instruction doit être suivie du commentaire de ligne `// delete this line to run test`.

Par exemple :

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Enfin, le fichier se termine par la fonction `main()`.
Le corps de la fonction `main` suit lui aussi une organisation particulière.
D'abord un appel à `UNITY_BEGIN()` suivi d'une ligne vide, puis les tests.
Le dernier test est suivi d'une autre ligne vide avant de renvoyer le résultat de `UNITY_END()`.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

# À propos

Le type `Result` permet à une fonction de renvoyer une seule valeur qui indique toutes les choses suivantes :
- si l'opération a réussi ou échoué ;
- en cas de succès, la valeur résultante de l'opération ;
- en cas d'échec, la raison de l'échec.

Dans les autres langages de programmation qui ne prennent pas en charge un type comme `Result`, on rencontre souvent les approches suivantes pour atteindre les objectifs mentionnés plus haut :
- une fonction qui renvoie un code numérique indiquant un succès ou la raison de l'échec, et qui exige un paramètre de sortie pour recevoir la valeur en cas de succès ;
- une fonction qui renvoie la valeur en cas de succès ou NULL en cas d'erreur, puis une autre fonction pour obtenir le code d'erreur indiquant la raison de l'échec.

Un autre mécanisme courant de gestion des erreurs est l'exception, qui interrompt brusquement la fonction en cours et
transfère le contrôle au premier gestionnaire de la pile d'appels lorsqu'un échec se produit.  
Si aucun gestionnaire ne « attrape » l'exception, le programme s'interrompt.

## Avantages de l'utilisation du type `Result`

* __Sécurité à la compilation__ : en rendant explicite dans le système de types le succès ou l'échec d'un appel de fonction, le compilateur peut garantir que le code appelant traite tous les cas d'échec, ce qui évite toute une catégorie de bogues qui pourraient survenir avec des valeurs nulles.

* __Sécurité à l'exécution__ : au lieu d'utiliser `null`, le type `Result` utilise `Error` pour représenter un échec, ce qui rend impossible la survenue d'une `NullReferenceException`.

* __Gestion explicite des erreurs__ : le code qui appelle une fonction renvoyant un `Result` doit reconnaître que
l'appel peut échouer ; le code appelant doit traiter ces échecs intentionnellement.  Il n'y a pas d'échecs silencieux ni d'exceptions surprises.

* __Flux de contrôle prévisible__ : un `Result` se renvoie comme n'importe quelle autre valeur ; il ne s'échappe pas de la pile d'appels comme le ferait une exception.  On sait toujours d'où viennent les erreurs et comment elles se propagent.

* __Lisibilité et maintenabilité améliorées__ : en renvoyant un `Result`, la signature d'une fonction indique clairement le comportement attendu en cas de succès comme en cas d'échec.

## Utilisation

Le type `Result` est un type générique contenant deux types sous-jacents :
- le type de la valeur résultante en cas d'opération réussie ;
- le type représentant la raison de l'échec en cas d'échec.

Le type `Result` est aussi une [union discriminée][discriminated-union] avec les cas possibles suivants :
* `Ok <value>` représentant un résultat réussi ;
* `Error <reason>` représentant un échec.

La fonction suivante montre comment créer une valeur `Result` :

```fsharp
let validateName (name: string) : Result<string, string> = 
    match name with
    | null -> Error "Name not found."
    | "" -> Error "Name is empty."
    | _ -> Ok name
```

Dans cet exemple, la valeur `Ok` est une _string_ (le nom donné), et la valeur `Error` est aussi une _string_ (la cause de l'erreur, sous une forme lisible par un humain).

## Lire le contenu d'une valeur `Result`

Prenons la définition de type et la signature de fonction suivantes :

```
type FileOpenError = 
| NotFound
| AccessDenied
| FileLocked

let openFile (filename: string) : Result<int, FileOpenError> =
```

Le code qui appelle la fonction `openFile` peut utiliser le _pattern matching_ pour traiter les cas de succès et d'échec, comme dans l'exemple suivant :

```fsharp
match openFile(filename) with
| Ok handle -> doSomethingWithFile(handle)
| Error NotFound -> printfn $"Error: file {filename} was not found."
| Error AccessDenied -> printfn $"Error: you do not have permission to open the file {filename}."
| Error FileLocked -> printfn $"Error: file {filename} is already in use."
```

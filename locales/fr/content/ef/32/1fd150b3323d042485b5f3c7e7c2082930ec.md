# Introduction

Les _threads_ de Factor sont des *coroutines coopératives* : ils partagent un seul _thread_ du système d'exploitation, se passent la main aux entrées-sorties et aux points où ils cèdent explicitement le contrôle, et ne s'exécutent jamais vraiment simultanément. Ce que tu fais *entre* deux cessions de contrôle se déroule en une seule étape ininterrompue. Mais si une opération composée (lecture-modification-écriture) cède la main en cours de route, un autre _thread_ peut s'interposer et modifier les choses avant que tu aies terminé, et c'est ce qu'on appelle une condition de course.

Cet exercice aborde quatre primitives qui reviennent sans cesse :

## `parallel-map` : _fork/join_ sur une séquence

```
parallel-map ( seq quot: ( elt -- newelt ) -- newseq )
```

Dans [`concurrency.combinators`][combinators]. Crée un _thread_ par élément, exécute la _quotation_, et rassemble les résultats dans une nouvelle séquence, dans le même ordre :

```factor
USING: concurrency.combinators sequences ;

{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }
```

## `spawn` : démarrer un _thread_

```
spawn ( quot name -- thread )
```

Dans [`threads`][threads]. La _quotation_ s'exécute de façon concurrente ; `name` est une étiquette pour le débogage. Le _handle_ de _thread_ renvoyé n'a guère d'intérêt à ce niveau : passe-le à `drop`.

## Les _promises_ : transmission de valeur à usage unique

```
<promise>           ( -- promise )
fulfill             ( value promise -- )
?promise            ( promise -- value )
```

Dans [`concurrency.promises`][promises]. Une _promise_ est une boîte aux lettres à usage unique : un _thread_ la remplit, les autres la lisent. `?promise` bloque jusqu'à ce que la _promise_ ait été remplie, puis renvoie la valeur.

```factor
USING: concurrency.promises kernel threads ;

<promise> [
    [ 42 swap fulfill ] curry "answer" spawn drop
] keep ?promise .
! => 42
```

C'est de `spawn` et de `<promise>` que `parallel-map` est construit ; les écrire à la main est utile quand chaque tâche fait autre chose que « calculer un élément ».

La forme typique d'éclatement puis de regroupement sur une séquence est la suivante : pour chaque entrée, créer une nouvelle _promise_, lancer un _thread_ qui fait le travail et exécute `fulfill` sur cette _promise_, rassembler toutes les _promises_ dans une séquence, puis appeler `?promise` sur chacune pour attendre qu'elle soit terminée. Les variables locales rendent tout cela lisible : lie la _promise_ à un nom avec `:>` à l'intérieur d'une lambda `[| | ]`, pour que la _quotation_ lancée puisse la capturer :

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
inputs [| x |
    <promise> :> p
    [ x do-work t p fulfill ] "worker" spawn drop
    p
] map [ ?promise drop ] each
```

## Les _locks_ : exclusion mutuelle

```
<lock>     ( -- lock )
with-lock  ( lock quot -- )
```

Dans [`concurrency.locks`][locks]. Un seul _thread_ peut détenir un _lock_ donné à la fois. `with-lock` acquiert le _lock_, exécute la _quotation_, puis le libère, même si la _quotation_ lève une exception.

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
USING: concurrency.locks kernel locals ;

[let <lock> :> guard
    guard [ ! exclusive section ! ] with-lock
]
```

Utilise un _lock_ dès qu'une valeur est *lue ou écrite par plus d'un _thread_* et que les opérations qui s'y appliquent ne sont pas naturellement atomiques. Les lectures comme les écritures ont besoin du _lock_ : une lecture qui cède la main en cours de route peut observer un état incohérent.

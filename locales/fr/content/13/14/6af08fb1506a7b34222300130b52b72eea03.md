# Instructions

Plus tu apprends la programmation, plus tu commences à te dire que ce n'est peut-être pas qu'un simple engouement passager. Il y a même peut-être là des opportunités commerciales : des gens écrivent du code, ils veulent le sauvegarder, le partager, collaborer, et même recevoir quelques retours.

Allez, on se lance, construisons un service pour encourager les gens à coder : hup, hup, tout le monde, commencez à utiliser git ! Et appelons-le... GitHup.

Tu te lances dans la construction d'une API REST JSON : des utilisateurs, des pull requests, des commentaires, et le backend est vite terminé.
Voici un exemple de la charge utile renvoyée quand tu demandes au serveur la liste des commentaires d'une pull request :

Bien sûr, le frontend sera fait en Elm, mais il faut d'abord que tu comprennes ce que sont ces fameux décodeurs et encodeurs.

```exercism/note
L'histoire humoristique mise à part, les exigences de cet exercice sont tirées directement des points de terminaison de l'API REST de GitHub pour les commentaires de revue de pull request.
Certains champs ont été retirés des schémas JSON par souci de simplicité, mais on est ici au plus près d'une application du monde réel.
```

## 1. Un ID, s'il te plaît !

Ton œil de lynx a remarqué que les commentaires comme les utilisateurs ont un champ `id`, un endroit parfait pour commencer.

Définis `decodeId` pour qu'il puisse décoder un objet JSON, avec un `id` entier.

```elm
Decode.decodeString decodeId """{id: 10}"""
    --> Ok 10
```

## 2. C'est quoi mon nom, déjà ?

Tu remarques dans l'exemple ci-dessus que tous les utilisateurs n'ont pas de nom.

Définis `decodeName` pour qu'il puisse décoder une _string_ dans le champ `name` s'il y en a une.
Pas de nom ? Pas de problème, renvoie simplement `Nothing`.
Ce décodeur ne doit jamais échouer.

```elm
Decode.decodeString decodeName """{"id": 10, "name": "Otto"}"""
    --> Ok (Just Otto)

Decode.decodeString decodeName """null"""
    --> Ok Nothing
```

## 3. Un utilisateur ? Je le connais à peine !

On est à peu près à mi-chemin pour décoder les utilisateurs, finissons le travail.

Définis `decodeUser` pour qu'il puisse décoder un objet JSON représentant un utilisateur.
Assure-toi d'utiliser `decodeId` et `decodeName` dans `decodeUser`.

```elm
Decode.decodeString decodeUser
    """
    {
      "id": 101,
      "login": "octodog",
      "avatar_url": "https://githup.com/images/error/octodog_happy.gif",
      "site_admin": false
    }
    """
    --> Ok
    -->   { id = 101
    -->   , name = Nothing
    -->   , login = "octodog"
    -->   , avatarUrl = "https://githup.com/images/error/octodog_happy.gif
    -->   , siteAdmin = False
    -->   }
```

## 4. Je suis un commentaire fort et indépendant

Certains commentaires d'une revue de pull request sont autonomes, et n'ont donc pas de `pull_request_review_id`.
Cependant, la spécification indique que dans un tel cas, il doit quand même y avoir un champ `pull_request_review_id`, mais que sa valeur doit être `null`, le `Nothing` du pauvre.

Définis `decodePullRequestReviewId` pour qu'il puisse décoder un entier dans le champ `pull_request_review_id` s'il y en a un.
S'il n'y a pas d'entier, il doit y avoir un `null`, et s'il n'y a pas de `null`, le décodeur doit échouer.

```elm
Decode.decodeString decodePullRequestReviewId """{"pull_request_review_id": 3}"""
    --> Ok (Just 3)

Decode.decodeString decodePullRequestReviewId """{"pull_request_review_id": null}"""
    --> Ok Nothing

Decode.decodeString decodePullRequestReviewId """{"id": 3}"""
    --> Err ...
```

## 5. Activité annexe

Passons à ce champ `side` à l'allure intéressante.
Dans une revue de pull request, tu peux commenter du code qui a été supprimé (du côté `Left` de l'écran) ou du code qui a été ajouté (du côté `Right` de l'écran).

Définis `decodeSide` pour qu'il puisse décoder soit `"LEFT"` soit `"RIGHT"` dans le champ `side` et les associer à la variante de type correspondante.

```elm
Decode.decodeString decodeSide """{"side": "LEFT"}"""
    --> Ok Left

Decode.decodeString decodeSide """{"side": "middle?"}"""
    --> Err ...
```

## 6. Links awakening

Chaque commentaire a un ensemble de liens, qui ne semble pas cohérent d'un commentaire à l'autre.

Définis `decodeLinks` pour qu'il puisse décoder une collection d'URL dans le champ `_links`.
Les noms et le nombre de liens peuvent varier, assure-toi d'en tenir compte.
Les liens eux-mêmes sont des objets JSON qui doivent toujours avoir un champ `href`.

```elm
Decode.decodeString decodeLinks """
    {
      "_links": {
        "self": { "href": "https://api.githup.com/repos/octodog/Hello-World/pulls/comments/1" },
        "html": { "href": "https://githup.com/octodog/Hello-World/pull/1#discussion-diff-1" },
        "pull_request": { "href": "https://api.githup.com/repos/octodog/Hello-World/pulls/1" }
      }
    }
    """
    --> Ok
    -->   (Dict.fromList
    -->       [ ( "self", "https://api.githup.com/repos/octodog/Hello-World/pulls/comments/1" )
    -->       , ( "html", "https://githup.com/octodog/Hello-World/pull/1#discussion-diff-1" )
    -->       , ( "pull_request", "https://api.githup.com/repos/octodog/Hello-World/pulls/1" )
    -->       ]
    -->   )
```

## 7. Oui, des commentaires

On y est presque, finissons le travail.

Définis `decodeComment` et `decodeComments` pour qu'ils puissent décoder respectivement un objet JSON représentant un seul commentaire ou un tableau de commentaires.
Assure-toi d'utiliser toutes les fonctions définies jusqu'ici dans `decodeComment`, à l'exception de `decodeName`.
Bien sûr, `decodeComments` doit aussi utiliser `decodeComment`.

## 8. Tout se tient

Il manque encore une fonctionnalité à tout cela : pouvoir envoyer un nouveau commentaire au serveur.
Pour cela, il te faut réaliser l'inverse d'un décodeur, tu dois pouvoir transformer un `Comment` Elm en une `Value` JSON.

Définis `encodeComment` pour qu'il puisse encoder n'importe quel `Comment` valide.
L'ordre des champs n'a pas d'importance, tant que l'encodeur peut produire une valeur que `decodeComment` peut décoder.

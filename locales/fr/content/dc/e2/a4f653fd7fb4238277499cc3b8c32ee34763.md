# Instructions supplémentaires

## La tâche

Implémente deux procédures.

- `custom_error_message message` lève une erreur, et `message` est le message d'erreur.
- `handle_error script` exécute le script donné et renvoie une _string_ qui décrit ce qui s'est passé :

  | Quand le script…                   | renvoie                 |
  | ---------------------------------- | ----------------------- |
  | divise par zéro                    | `"division by zero"`    |
  | ouvre un fichier qui n'existe pas  | `"file does not exist"` |
  | appelle une proc qui n'existe pas  | `"proc does not exist"` |
  | lève n'importe quelle autre erreur | `"unknown error"`       |
  | réussit                            | `"success"`             |

## Lever des erreurs

Tcl a deux commandes pour lever une erreur.

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` exige un _code d'erreur_ comme premier argument.
Le code d'erreur est une liste qui indique au gestionnaire quel type d'erreur s'est produit, afin qu'il puisse réagir sans analyser le texte du message.
Son contenu est libre : `{MYAPP BADTHING}` n'est qu'un exemple, et n'importe quelle liste non vide fera l'affaire.
Par convention, il va du général au particulier.
Un gestionnaire l'intercepte avec un motif `try ... trap` correspondant (décrit plus bas), comme `trap {MYAPP BADTHING}`, ou `trap {MYAPP}` pour intercepter toutes les erreurs `MYAPP`.
`error` prend un code d'erreur facultatif comme troisième argument : `error message ?info? ?code?`.

## Gérer les erreurs avec `catch`

[`catch`][catch] exécute un script et renvoie un _code d'achèvement_ entier au lieu de lever l'erreur :

| code | signification |
| ---- | ------------- |
| 0    | `ok`          |
| 1    | `error`       |
| 2    | `return`      |
| 3    | `break`       |
| 4    | `continue`    |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

Le deuxième argument facultatif reçoit le résultat (ou le message d'erreur).
Le troisième argument facultatif reçoit un _dictionnaire d'options_, qui contient `-errorcode` et `-errorinfo` (la trace de la pile).

Avantages :

- C'est compact et souple.
- C'est court pour les cas simples, comme `if {[catch {open $f} fh]} {...}`.

Inconvénients :

- Il faut vérifier soi-même le code d'achèvement.
  Un `if {[catch ...] != 0} { handle error }` écrit sans attention traite aussi `return`, `break` et `continue` comme des erreurs.
- Les erreurs que tu ne gères pas sont avalées, sauf si tu les relèves toi-même.
- Il n'y a pas de moyen intégré d'exécuter du code de nettoyage, que le script ait échoué ou non.

## Gérer les erreurs avec `try`

[`try`][try] exécute un script et envoie l'issue au premier gestionnaire qui correspond.
Une clause `finally` facultative s'exécute toujours, ce qui en fait un bon endroit pour libérer des ressources comme les canaux de fichiers.

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

Avantages :

- La structure est claire : un gestionnaire pour chaque type d'issue.
- `finally` s'exécute toujours.
- Les issues qu'aucun gestionnaire ne traite sont transmises à l'appelant sans modification.

Inconvénients :

- C'est un peu plus verbeux que `catch` pour les cas simples.

### `try ... on` face à `try ... trap`

Il existe deux types de gestionnaires.

`on code {msgVar optionsVar}` correspond au _code d'achèvement_ : `ok`, `error`, `return`, `break` ou `continue`.
Toute erreur a le code d'achèvement `error`, donc `on error` ne permet pas de distinguer une division par zéro d'un fichier manquant.
Il faudrait pour cela examiner le texte du message, ce qui est fragile : les messages sont destinés aux humains et peuvent changer d'une version de Tcl à l'autre.

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` correspond au _code d'erreur_.
Le gestionnaire correspond quand le motif est un préfixe de la liste `-errorcode`.
Cela identifie le type d'erreur de façon fiable.

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

Un motif vide, `trap {}`, correspond à n'importe quelle erreur.
Les gestionnaires sont testés dans l'ordre, donc place le gestionnaire fourre-tout en dernier.

## Trouver le code d'erreur

Où `ARITH DIVZERO` est-il documenté ?
Surtout uniquement dans le code source, mais Tcl te le montrera.
Après une erreur, la variable globale `errorCode` contient le code d'erreur de l'erreur la plus récente :

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

Dans un programme, récupère-le depuis le dictionnaire d'options :

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

Le dernier élément d'un code d'erreur est souvent un message lisible par un humain, ou le nom de la chose qui a provoqué l'erreur.
Laisse-le en dehors de ton motif `trap` : utilise `{ARITH DIVZERO}`, pas `{ARITH DIVZERO {divide by zero}}`.

### Quelques codes d'erreur courants

Ce tableau n'est pas complet.
Utilise la technique ci-dessus pour trouver le code de n'importe quelle autre erreur.

| Situation                          | Exemple             | Code d'erreur             |
| ---------------------------------- | ------------------- | ------------------------- |
| Division par zéro                  | `expr {1 / 0}`      | `ARITH DIVZERO ...`       |
| Erreur de domaine mathématique     | `expr {sqrt(-1)}`   | `ARITH DOMAIN ...`        |
| Fichier introuvable                | `open nosuchfile r` | `POSIX ENOENT ...`        |
| Permission refusée                 | `open /root/x w`    | `POSIX EACCES ...`        |
| Commande inconnue                  | `no::such::proc`    | `TCL LOOKUP COMMAND name` |
| Variable inconnue                  | `set nosuchvar`     | `TCL LOOKUP VARNAME name` |
| Nombre d'arguments incorrect       | `string length a b` | `TCL WRONGARGS`           |
| Dictionnaire invalide              | `dict size {1 2 3}` | `TCL VALUE DICTIONARY`    |
| Liste invalide                     | `llength "a \{b"`  | `TCL VALUE LIST ...`      |

Les codes d'erreur `POSIX` utilisent les noms `errno` du système d'exploitation, comme `ENOENT`, `EACCES` et `EEXIST`.

## Indice : où s'exécute le script

`handle_error` reçoit un script de la part de son appelant.
Si tu l'exécutes avec `try $script`, il est évalué dans la portée de `handle_error`, et non dans celle de l'appelant.
Pour l'évaluer là où il a été écrit, utilise [`uplevel`][uplevel] : `try {uplevel 1 $script} ...`.

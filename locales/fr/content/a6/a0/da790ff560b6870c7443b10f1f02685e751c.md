# Stratégie de fusion

Les mainteneurs du parcours Rust [ont décidé](https://github.com/exercism/v3/discussions/1725#discussion-7438) de coucher par écrit notre stratégie de fusion afin de communiquer nos attentes et d'encourager des contributions de qualité.

## Principes généraux

- nous nous efforçons d'accepter _toutes_ les contributions
  - Nous amenons les contributions à un haut niveau de qualité grâce à une revue collaborative et itérative.
  - Nous adoptons une approche de fusion pessimiste. Vois les revues des mainteneurs comme les retours du compilateur Rust. Le volume de retours peut sembler écrasant et frustrant. Mais nous travaillerons avec toi pour aller jusqu'au bout ! Alors, continue comme ça.
- Chaque pull request doit recevoir au moins un « Approval », et aucun « Request Changes », de la part d'un mainteneur du parcours avant de pouvoir être fusionnée.
- Aucun mainteneur ne peut approuver sa propre pull request.

## Le workflow des pull requests

### Définitions

| Terme                 |                                                                                                   Signification |
| --------------------- | --------------------------------------------------------------------------------------------------------------: |
| Contributeur          |                                                                          Toute personne qui soumet une pull request. |
| Mainteneur            |                     Toute personne qui fait partie de l'[équipe @exercism/rust](https://github.com/orgs/exercism/teams/rust). |
| branche de développement | La branche de développement par défaut du dépôt [v3](https://github.com/exercism/v3). Actuellement `master`. |

### Le workflow

1. Les contributeurs commencent par ouvrir une pull request [en brouillon](https://github.blog/2019-02-14-introducing-draft-pull-requests/) ou une pull request complète avec leurs modifications
   1. Utiliser la fonctionnalité de brouillon signale que le travail est prêt pour une revue de haut niveau, mais que certains détails peuvent encore être non implémentés, incomplets ou erronés.
   1. Après un nombre indéterminé d'itérations des étapes 2 et 3, le contributeur marque la pull request comme prête à être relue.
1. Un autre mainteneur doit relire la contribution et fournir des retours.
1. Le contributeur doit traiter _tous_ les retours des mainteneurs dans le cadre de la pull request.
   1. Les mainteneurs doivent envisager d'utiliser la fonctionnalité de suggestion de GitHub pour les changements mineurs ou évidents.
   1. Contester est encouragé lorsqu'un contributeur estime avoir raison et qu'un mainteneur a tort sur un point de retour. « Traiter » un retour n'est pas synonyme de l'implémenter servilement.
1. Le mainteneur doit examiner les retours et, au choix :
   1. approuver
   1. demander des changements supplémentaires. À ce stade, le processus revient à l'étape 3.
1. Une fois la pull request approuvée, un mainteneur la fusionne.
   1. Les mainteneurs fusionnent leurs propres pull requests. Comme les contributeurs ne sont pas nécessairement mainteneurs, c'est un mainteneur qui doit effectuer cette étape.

## Fusion optimiste

Les mainteneurs du parcours Rust ont décidé d'adopter temporairement la fusion optimiste pour accélérer le développement du parcours v3.

- Cela ne s'applique qu'au dépôt v3
- Nous reviendrons à une stratégie de fusion pessimiste dès la mise en production de la v3.
- Nous approuvons et fusionnons du travail incomplet
  - Si ça compile, on le garde.
  - Privilégier la vitesse d'itération aux finesses d'une conception logicielle correcte.
- Chaque pull request doit recevoir au moins un « Approval » de la part d'un mainteneur du parcours avant de pouvoir être fusionnée.

# À propos

À ce stade du programme, tu as déjà vu un grand nombre de définitions de fonctions.
D'habitude, elles étaient présentées sans trop de commentaires sur le résultat affiché dans le REPL :

```julia-repl
julia> f(x) = x^2
f (generic function with 1 method)
```

Pourquoi _« generic function with 1 method »_ ?

Supposons que l'on veuille être plus précis sur les types des arguments.

```julia-repl
julia> f(x::Integer) = x^2
f (generic function with 2 methods)

julia> f(x::Real) = x^2
f (generic function with 3 methods)
```

Ou bien on pourrait changer le nombre d'arguments :

```julia-repl
julia> f(x, y) = x * y
f (generic function with 4 methods)
```

Il semble que les nouvelles définitions d'une même fonction s'appellent des « méthodes ».
Les méthodes sont ajoutées à une liste, au lieu d'écraser l'ancienne définition.

On peut facilement lister les méthodes :

```julia-repl
julia> methods(f)  # output edited for brevity
# 4 methods for generic function "f" from Main:
 [1] f(x, y)
 [2] f(x::Integer)
 [3] f(x::Real)
 [4] f(x)
 ```

Si on appelle la fonction `f`, Julia sait d'une manière ou d'une autre quelle méthode utiliser :

```julia-repl
julia> f(2.5)  # Float64
6.25

julia> f(2)  # Int64
4

julia> f(2, 3)  # Int64, Int64
6
```

## Qu'est-ce qu'une fonction ?

D'après le [manuel][function], une fonction est un objet qui associe un tuple d'arguments à une valeur de retour.
Cela ressemble beaucoup à la définition qu'en donnent les mathématiciens.

On considère généralement les arguments de la fonction dans `f(2, 3)` comme deux éléments distincts, mais le compilateur les voit comme un seul [tuple][tuple].
C'est vrai même pour un seul argument (il faut toutefois ajouter une virgule pour que ce soit plus clair) :

```julia-repl
julia> typeof( (2, 3) )
Tuple{Int64, Int64}

julia> typeof( (2,) )
Tuple{Int64}
```

Si on voit la fonction comme une boîte noire, on peut dire qu'un tuple entre et qu'une valeur de retour sort.
Plus formellement, le tuple est _associé_ à une valeur de retour.

## Comment les fonctions gèrent-elles des nombres et des types d'arguments différents ?

On appelle généralement cela le [polymorphisme][polymorphism].

C'est un sujet majeur de l'informatique depuis plusieurs décennies, et différentes approches ont été adoptées.

L'approche de Julia est inhabituelle, sans être unique pour autant.

- Les fonctions sont [« génériques »][generic], ce qui signifie qu'on peut leur attacher plusieurs méthodes.
- Les fonctions ne sont que des noms, tant qu'aucune méthode ne leur est attachée.
- On peut ajouter des méthodes au besoin, éventuellement en grand nombre (l'opérateur `+` est une fonction qui compte actuellement 161 méthodes).
- Quand on appelle une fonction, Julia examine la signature de l'appel : le nombre d'arguments et le type actuel de chacun.
- La méthode qui correspond le mieux à la signature de l'appel est sélectionnée.
  - En général, le nombre d'arguments doit correspondre exactement (même si l'opérateur [splat/slurp][splat] `...` permet de contourner partiellement cette règle).
  - Les méthodes dont les types correspondent exactement à la signature de l'appel sont privilégiées.
  - Si nécessaire, Julia examine les supertypes de chaque argument de la signature de l'appel pour trouver la méthode qui correspond le mieux, la plus spécifique.
- La méthode choisie est [`dispatched`][dispatch] avec les arguments donnés, et elle renvoie un résultat.
- Si aucune méthode appropriée n'est trouvée, une [`MethodError`][methoderror] est levée.

À noter que Julia est typé dynamiquement, donc le dispatch des méthodes se fait à l'_exécution_.

## Le dispatch multiple : un exemple

La section précédente contenait beaucoup de mots, alors traduisons ces idées en code.
Pour simplifier, les fonctions ci-dessous ne prennent qu'un seul argument, mais il n'est pas rare de trouver des fonctions avec des dizaines d'arguments (par exemple dans les bibliothèques de tracé graphique ou d'apprentissage automatique).

Commençons par définir quelques types personnalisés, pour représenter des formes géométriques.

```julia-repl
julia> abstract type Shape end

julia> struct Circle <: Shape
           radius::Float64
       end

julia> struct Square <: Shape
           side::Float64
       end

julia> struct Rectangle <: Shape
           length::Float64
           width::Float64
       end
```

Ensuite, on peut définir des méthodes pour calculer l'aire de chaque forme.
Chacune prend un argument, d'un type concret défini par l'utilisateur différent dans chaque cas.

```julia-repl
julia> area(c::Circle) = π * c.radius^2
area (generic function with 1 method)

julia> area(s::Square) = s.side^2
area (generic function with 2 methods)

julia> area(r::Rectangle) = r.length * r.width
area (generic function with 3 methods)
```

Maintenant, on peut créer quelques formes et calculer les aires, en s'appuyant sur le mécanisme de dispatch de Julia pour appliquer la bonne formule à chacune.

```julia-repl
julia> circle = Circle(2.3)
Circle(2.3)

julia> area(circle)  # call signature Tuple{Circle}
16.619025137490002

julia> square = Square(1.6)
Square(1.6)

julia> area(square)  # call signature Tuple{Square}
2.5600000000000005

julia> rectangle = Rectangle(1.4, 2.1)
Rectangle(1.4, 2.1)

julia> area(rectangle)  # call signature Tuple{Rectangle}
2.94
```

## [Méthodes paramétriques][parametric]

Les signatures de méthode peuvent prendre des valeurs de type fictives, à peu près de la même façon que les types paramétriques.

La syntaxe est particulière, puisqu'elle exige une clause `where` :

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T} = true
same_type (generic function with 1 method)

julia> same_type([1, 2], 3)
true

julia> same_type([1, 2], "three")
ERROR: MethodError: no method matching same_type(::Vector{Int64}, ::String)
```

L'exemple ci-dessus exige que les deux arguments utilisent le même type `T`, quel qu'il soit.

On peut être plus précis en imposant une contrainte sur `T` :

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T<:Number} = true
same_type (generic function with 2 methods)
```

Avec cette méthode, seuls des types numériques identiques renvoient `true`.

Plusieurs variables fictives sont possibles, séparées par des virgules dans la clause `where`.
Les deux méthodes suivantes se ressemblent :

```julia-repl
julia> func(v::Vector{Number}, x::Number) = true
func (generic function with 1 method)

julia> func(v::Vector{S}, x::T) where {S<:Number, T<:Number} = true
func (generic function with 2 methods)
```

Une différence est que les valeurs de type `S` et `T` sont disponibles dans le corps de la seconde méthode.
C'est le genre d'astuce qu'on n'utilise pas souvent, mais qui peut épargner bien des ennuis dans certaines situations.

Par exemple, dans la définition de type paramétrique suivante, les champs doivent être du même type `T`, contraint à être un sous-type de `Real` :
```julia
struct Point{T<:Real}
    x::T
    y::T
end
```
Cette définition de `Point` accepte un `x` et un `y` du même type, ou bien un `x` et un `y` de types différents, mais il faut alors fournir explicitement un type de conversion.
```julia-repl
julia> Point(4, 5)
 Point{Int64}(4, 5)

julia> Point(3.5, 2)
 MethodError: no method matching Point(::Float64, ::Int64)    # Output truncated for brevity

julia> Point{Float32}(3.5, 2)
 Point{Float32}(3.5f0, 2.0f0)

julia> Point{Int64}(3.5, 2) 
 InexactError: Int64(3.5)      # Output truncated for brevity
```
Si ce niveau de contrôle sur les types peut être souhaitable, un peu d'abstraction peut aussi être utile.
```julia
Point(x::T, y::S) where {T<:Real, S<:Real} = Point{promote_type(T,  S)}(x, y)
```
Ce constructeur externe le permet en autorisant un `Point` à accepter des types hétérogènes pour `x` et `y` sans préciser explicitement le type de conversion.
Les valeurs de type `T` et `S` sont utilisées dans le corps de la fonction, dans `promote_type(T, S)`, pour fournir le type de conversion explicite à la définition d'origine.
```julia-repl
julia> Point(3.5, 2)
 Point{Float64}(3.5, 2.0)
```

## Comparaison avec d'autres langages

Comme Julia examine tous les arguments au moment de choisir une méthode, on appelle cela le [`multiple dispatch`][multiple-dispatch].

Quelques autres langages autorisent le dispatch multiple, comme Common Lisp, même s'il est rarement aussi central dans la conception du langage que chez Julia.

En revanche, dans un langage orienté objet (POO) (par exemple Ruby), les méthodes sont généralement appelées sur une [instance][instance].
La définition privilégie alors le premier argument (nommé `self` ou `this` dans la définition), et pour l'appeler, on rattache le nom de la méthode à l'instance avec un point :

```ruby
irb(main):004:0> "abc".sub("b", "*")
=> "a*c"
```

On parle de [`single dispatch`][single-dispatch], car seule la classe de l'instance (celle de la _string_ « abc » dans l'exemple ci-dessus) sert à choisir une méthode.

Certains langages orientés objet à typage statique prennent en charge le polymorphisme des méthodes, qui ressemble un peu au dispatch multiple.
La grande différence est que la sélection de la méthode se fait uniquement à la _compilation_.

Les langages fonctionnels n'ont généralement qu'une seule définition de fonction, avec une sorte d'expression Select/Case/Match pour gérer les différentes possibilités.
On écrit sa propre logique, généralement aidé par une syntaxe concise de filtrage par motif, absente de Julia.
Bien sûr, Julia fait aussi une forme de filtrage par motif, mais au moment du dispatch plutôt qu'à l'intérieur du corps de la fonction.

## Conclusion

Le dispatch multiple est très flexible et très performant en Julia, il est donc utilisé partout.

Comme le suggère l'exemple des 161 méthodes de `+`, les développeurs Julia cherchent à définir des méthodes aux types précis.
Additionner deux entiers est très différent d'additionner deux nombres décimaux au niveau du bytecode, et additionner un entier à un nombre décimal ajoute une complication supplémentaire : la promotion de type.

Plus le type est spécifique, plus le compilateur peut optimiser : d'une importance marginale dans un petit exercice sur Exercism, mais vital pour les performances des grandes simulations numériques pour lesquelles Julia est conçu.

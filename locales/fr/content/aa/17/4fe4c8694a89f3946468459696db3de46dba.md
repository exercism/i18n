# À propos

## Ajoute du contexte aux erreurs

On a découvert les bases de la gestion des erreurs en Go dans le [concept des erreurs][concept-errors].
Comme tu l'as appris là-bas, par défaut, les erreurs ne transportent pas de traces de pile.
Il est donc essentiel de s'assurer que l'erreur elle-même contient assez d'informations pour identifier le problème.

Si on voulait ajouter des informations à une erreur existante avec les outils que l'on connaît déjà, on pourrait écrire quelque chose comme ceci pour créer une nouvelle erreur à partir du texte combiné de l'erreur d'origine et des informations supplémentaires :

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Heureusement, le paquet `fmt` de la bibliothèque standard contient une version raccourcie de tout ça sous la forme de la fonction `Errorf`.
Elle te permet par exemple d'ajouter facilement des informations sur le contexte dans lequel l'erreur s'est produite.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

À moins d'être sûr que l'erreur contient déjà assez d'informations, essaie de prendre l'habitude d'ajouter systématiquement du contexte à une erreur avant de la renvoyer depuis une fonction.
Autrement dit, ton schéma habituel de gestion des erreurs devrait ressembler à ceci :

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Comme le montrent les exemples, la convention est de séparer l'erreur du message ajouté par deux-points.
Tout comme le message de l'erreur d'origine, le message de contexte ne doit pas commencer par une majuscule et ne doit pas se terminer par un point.

~~~~exercism/note
Quand on ajoute du contexte à une erreur, il est tentant de commencer le message par « failed to … » ou quelque chose du genre.
Cependant, comme une erreur peut accumuler beaucoup de contexte supplémentaire en remontant la chaîne des fonctions, le message final, celui qui sera journalisé ou que verra l'utilisateur, peut devenir plus difficile à lire, voire plein de répétitions.

Voici un exemple pour illustrer :

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Garde donc ce résultat final en tête quand tu écris les messages de contexte, et abstiens-toi d'ajouter du texte sur le fait que quelque chose ne s'est pas passé comme prévu.
C'est généralement évident d'après le contexte (par exemple le niveau de journalisation « ERROR ») et le message d'erreur d'origine.
~~~~

Souvent, cette façon d'ajouter des informations à une erreur suffit, mais il arrive que tu veuilles permettre au code qui consomme ton erreur de vérifier la présence de l'erreur d'origine sous-jacente, ou de la récupérer.
Ajouter du contexte d'une manière qui le permet s'appelle « envelopper une erreur » en Go.

## Enveloppe les erreurs et vérifie les erreurs sentinelles

L'enveloppement d'une erreur s'obtient avec une modification minime du code vu plus haut.
Pour envelopper une erreur, il faut utiliser le verbe de formatage `%w` au lieu de `%v`.
En coulisses, cela garantit que l'erreur obtenue implémente une méthode `Unwrap` qui renvoie l'erreur d'origine.
Grâce à cela, on peut ensuite utiliser `errors.Is` pour vérifier si une erreur sentinelle donnée apparaît quelque part le long de la « chaîne d'erreurs ».
Pour ce faire, la fonction appelle discrètement `Unwrap` à répétition jusqu'à ce que l'erreur en question soit trouvée ou que la chaîne se termine.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Vérifier l'erreur d'origine avec `errors.Is` ne fonctionnerait pas avec le verbe de formatage `%v` habituel.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Par conséquent, il est de bonnes pratiques d'utiliser `%v` par défaut et de n'employer `%w` que si tu veux explicitement permettre au code qui consomme ton erreur d'accéder à une erreur sous-jacente ([Google Go Styleguide][google-go-styleguide]).

Si tu te retrouves dans une situation où tu veux vérifier la présence d'une erreur sentinelle sans vouloir la déballer, tu peux utiliser `==` au lieu de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

À l'inverse, `==` ne reconnaîtrait pas l'erreur si elle avait été enveloppée.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Tu peux tout à fait utiliser `errors.Is` par défaut, mais garde toujours à l'esprit que cela signifie que toute la chaîne d'erreurs sera parcourue.

## Vérifie les types d'erreurs (personnalisés)

Il existe un équivalent de `errors.Is` qui permet de vérifier la présence, dans la chaîne d'erreurs, d'une erreur d'un type donné et de la récupérer.
La fonction en question est `errors.As` et, tout comme `errors.Is`, elle parcourt toute la chaîne à la recherche du type d'erreur donné.
`errors.As` extrait alors seulement l'erreur trouvée qui correspond au type, ce qui te permet de continuer à travailler avec elle, par exemple pour récupérer des champs précis.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Fais attention à la syntaxe concernant les pointeurs ci-dessus.
Le code ne fonctionnera et ne compilera correctement que si `customError` a exactement le type qui implémente l'interface d'erreur.
Dans notre cas, il s'agit de `*MyCustomError` (un [pointeur][concept-pointers] vers `MyCustomError`), et non de `MyCustomError` lui-même.

En plus de cela, le deuxième argument doit être un pointeur vers la variable d'erreur.
Comme notre erreur est déjà un pointeur, ce que l'on passe à `errors.As` est un pointeur vers un pointeur (vers MyCustomError).
C'est seulement avec cette configuration correcte que Go peut ensuite remplir la variable avec l'erreur trouvée.
~~~~

Comme précédemment, `errors.As` n'aurait pas trouvé le type d'erreur si on avait utilisé `%v` lors de l'appel à `Errorf`.

Si, pour une raison ou une autre, tu ne veux pas déballer l'erreur, tu peux plutôt utiliser une assertion de type (l'équivalent du `==` ci-dessus).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

Une assertion de type ne pourra pas identifier le type d'erreur si l'erreur avait été enveloppée.

## Permets de déballer les erreurs de types personnalisés

Parfois, envelopper une erreur avec un simple texte supplémentaire ne suffit pas.
Tu peux alors créer un type d'erreur personnalisé qui contient l'erreur d'origine et les données structurées supplémentaires que tu veux y ajouter.
Si tu veux permettre le déballage de ton type d'erreur, la seule chose à faire est d'ajouter manuellement une méthode `Unwrap() error` pour satisfaire l'interface `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Combine plusieurs erreurs

Dans Go 1.20, une nouvelle fonction `Join` a été ajoutée au paquet `errors` intégré.
`Join` permet de combiner plusieurs erreurs entre elles d'une manière qui autorise toujours le déballage, c'est-à-dire la vérification d'une erreur ou d'un type d'erreur précis le long de la chaîne.
Avec ça, la chaîne d'erreurs peut en réalité être un arbre d'erreurs.
Tu trouveras plus d'informations dans les [notes de version][release-notes] et la [documentation][doc-join].

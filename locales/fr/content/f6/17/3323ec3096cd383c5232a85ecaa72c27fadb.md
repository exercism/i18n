# À propos

En C, une [structure][struct] est un type composite, composé de différents champs.
Chaque champ possède son propre type et sa propre taille.

Par exemple, ceci définit un type composé de trois entiers, deux de 4 octets et un de 8 octets :

```c
struct example {
    int32_t first_four_byte_integer;
    uint32_t second_four_byte_integer;
    uint64_t eight_byte_integer;
};
```

Une structure peut aussi contenir d'autres structures :

```c
struct example_2 {
    struct example first;
    struct example second;
};
```

Si l'un des champs de la structure est un tableau, tous les octets alloués pour le tableau font partie de la structure.
En revanche, si le champ n'est qu'un pointeur vers le tableau, alors le tableau doit être stocké ailleurs :

```c
struct with_array {
    char string[20];
};
// all 20 bytes of string are inside struct with_array

struct with_pointer {
    const char *string;
};
// only the 8-byte pointer to the string is inside struct with_pointer
```

## Alignement

L'[alignement][alignment] d'un type est une puissance de deux positive ou nulle (1, 2, 4, 8, ...) qui représente une contrainte sur son adresse.
Tout objet de ce type doit se trouver à une adresse qui est un multiple de son alignement.

Pour un type primitif, l'alignement est généralement égal à sa taille, ainsi, par exemple, un `int32_t` possède généralement un alignement de 4 octets.
Cela signifie que `int32_t` doit être alloué à des frontières de 4 octets.

L'alignement d'une structure, cependant, est l'alignement maximal parmi ses champs.
Ainsi, par exemple, le type `struct example` défini ci-dessus aurait un alignement de 8 octets, puisque c'est l'alignement de `uint64_t`.

Si l'alignement d'un champ de la structure est inférieur à celui de la structure, des octets de remplissage peuvent être insérés après ce champ.
Cela garantit que les champs suivants et la structure dans son ensemble respectent les contraintes d'alignement.
En pratique, cela signifie que bien que ces octets de remplissage contribuent à la taille de la structure, ils ne sont pas utilisés dans la valeur de la structure :

```c
struct example_3 {
    char one_byte; // alignment of 1
    int four_byte; // alignment of 4
};
// example_3 has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one_byte'
// 3 padding bytes (with undefined value)
// 4 bytes for field 'four_byte'
```

Note que dans la structure définie ci-dessus, le champ 'one_byte' possède un alignement de 1 et peut être placé à n'importe quelle adresse.
Comme le champ 'four_byte' possède un alignement de 4, les champs de la structure doivent aussi respecter des frontières de 4 octets.
Cela signifie qu'il doit y avoir un nombre d'octets multiple de 4 entre deux champs quelconques de la structure.
Comme 'one_byte' n'occupe qu'un seul octet, 3 octets de remplissage sont insérés après lui pour respecter cette frontière.

Les champs adjacents sont regroupés chaque fois que possible afin de minimiser le nombre d'octets de remplissage nécessaires :

```c
struct two_padding {
    char one; // alignment of 1
    char two; // alignment of 1
    int three; // alignment of 4
};
// struct two_padding has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one'
// 1 byte for field 'two'
// 2 padding bytes
// 4 bytes for field 'three'
```

Ce regroupement doit aussi respecter l'alignement de chaque champ :

```c
struct one_padding {
    char one; // alignment of 1
    int16_t two; // alignment of 2
    int three; // alignment of 4
};
// struct one_padding has alignment of 4 (the same as int)
// it occupies 8 bytes in space:
// 1 byte for field 'one'
// 1 padding byte
// 2 bytes for field 'two'
// 4 bytes for field 'three'
// Since 'two' has alignment of 2, it must be placed in a 2-byte boundary
// So, there must be 1 padding byte between 'one' and 'two'
```

Cela signifie que changer l'ordre des champs dans une structure peut parfois entraîner une différence de taille :

```c
struct example_4 {
    int64_t one;
    short two;
    int32_t three;
};
// example_4 has one 8-byte field, one 4-byte field and one 2-byte field
// it has an alignment of 8 and occupies 16 bytes in space:
// 8 bytes for field 'one'
// 2 bytes for field 'two'
// 2 padding bytes
// 4 bytes for field 'three'
// two' and 'three' are adjacent and can be grouped to sum up 8 bytes with only 2 bytes of padding

struct example_5 {
    short one;
    int64_t two;
    int32_t three;
};
// example_5 also has one 8-byte field, one 4-byte field and one 2-byte field, in different positions
// it also has an alignment of 8, however, it occupies 24 bytes in space:
// 2 bytes for field 'one'
// 6 bytes for padding
// 8 bytes for field 'two'
// 4 bytes for field 'three'
// 4 bytes for padding
// 'one' can't be grouped with 'two' because their sum would be higher than the struct's alignment
// 'two' and 'three' also can't be grouped, for the same reason
// so padding bytes must be inserted in full after each field with less than 8 bytes in alignment
```

Note que l'alignement d'un tableau est le même que l'alignement de son type sous-jacent :

```c
struct array_example {
    char string[10]; // alignment of 1
};
// array_example has alignment of 1 (it can be placed at any address)
// it occupies 10 bytes in space, one for each char in 'string'
```

Les éléments d'un tableau peuvent être regroupés de la même manière que s'ils ne faisaient pas partie d'un tableau :

```c
struct group_array {
    int16_t arr[3];
    int8_t one_byte;
    int32_t four_byte;
};
// group_array has alignment of 4 because this is the alignment of 'four_byte'
// it occupies 12 bytes in space:
// 4 bytes for arr[0] and arr[1]
// 2 bytes for arr[2]
// 1 byte for 'one_byte'
// 1 padding byte (arr[2] is grouped with 'one_byte')
// 4 bytes for 'four_byte'
```

Il est important de tenir compte des éventuels octets de remplissage lorsqu'on accède à une structure en assembleur.

## Convention d'appel

En général, les valeurs sont passées aux fonctions et renvoyées par celles-ci comme on peut s'y attendre :

- Les valeurs entières, y compris les adresses mémoire et les énumérations, sont passées dans des registres à usage général (GPR).
- Les valeurs à virgule flottante sont passées dans des registres `xmm`.

Les structures, cependant, sont un cas particulier.
En règle générale, tous les champs d'une structure occupent un espace adjacent en mémoire et doivent être placés dans un seul registre chaque fois que possible :

```c
struct single_type {
    int16_t first;
    int16_t second;
    int16_t third;
    int16_t fourth;
};
// this struct occupies 8 bytes
// it is entirely passed in the same GPR register:
// the field 'first' is passed on the lowest 2 bytes
// each subsequent field is passed in the following 2 bytes
```

Si une structure a des champs avec des valeurs entières et aussi des champs avec des valeurs à virgule flottante, chaque bloc de 8 octets consécutif dans la structure doit être classé séparément :

```c
struct mixed_types {
    double first;
    int second;
    int third;
};
// this struct occupies 16 bytes
// the field 'first' is passed in the first 8 bytes of a xmm register
// the fields 'second' and 'third' are passed in the same GPR register:
// the field 'second' is passed on the lowest 4 bytes
// the field 'third' is passed in the next 4 bytes
```

Si des entiers et des valeurs à virgule flottante se trouvent dans les mêmes 8 octets, le type est entier et l'ensemble des 8 octets (y compris la valeur à virgule flottante) est placé dans un GPR :

```c
struct mixed_types {
    int32_t integer;
    float floating_point;
};
// this struct occupies 8 bytes
// it is entirely passed in the same GPR register:
// the field 'integer' is passed on the lowest 4 bytes
// the field 'floating_point' is passed on the next 4 bytes
```

~~~~exercism/caution
Lorsqu'une conversion est effectuée d'une valeur à virgule flottante vers un entier à l'aide de `cvtss2si` ou `cvtsd2si`, cela modifie l'organisation des octets sous-jacents.

Tu peux utiliser [movd][mov] (pour les valeurs 32 bits) ou [movq][mov] (pour les valeurs 64 bits) pour déplacer des octets bruts d'un registre `xmm` vers un GPR, sans changer la représentation binaire.

[mov]: https://www.felixcloutier.com/x86/movd:movq
~~~~

Cependant, les structures de plus de 16 octets sont généralement placées en mémoire, quel que soit le type de chaque bloc de 8 octets :

```c
struct big_struct {
    uint8_t first;
    double second;
    int64_t third;
};
// this struct occupies 24 bytes, including 7 padding bytes between 'first' and 'second'
// it is entirely passed in memory
```

Lorsqu'une structure est passée comme argument à une fonction, elle utilise autant de registres que nécessaire.
Si elle est placée en mémoire, la pile est utilisée à la place.

Des règles similaires s'appliquent aux structures renvoyées par une fonction.
Elles sont généralement renvoyées d'abord dans `rax` et `rdx` (si leur valeur est entière) ou `xmm0` et `xmm1` (si leur valeur est à virgule flottante).
Si elle est placée en mémoire, cependant, l'appelant doit réserver de l'espace pour elle et passer l'adresse de cet emplacement mémoire comme premier argument implicite à la fonction (dans `rdi`).
La fonction stocke alors la structure dans cet espace et renvoie son adresse dans `rax`.

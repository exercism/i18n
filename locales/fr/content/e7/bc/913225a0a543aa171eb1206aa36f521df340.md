# Générateurs de tests

Les générateurs de tests permettent aux parcours de générer des tests automatiquement, sans avoir à les écrire nous-mêmes. Chaque générateur de tests lit les `canonical data` de l'exercice, qui définissent le nom du test, ses entrées et ses sorties. Tu peux en apprendre plus sur l'approche d'Exercism en matière de suites de tests [ici](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Générer les tests automatiquement élimine toute erreur humaine au moment de les créer. On veut que les tests soient fidèles aux données canoniques. La génération de tests facilite aussi beaucoup le maintien des tests à jour. Quand les données canoniques changent, les tests sont mis à jour automatiquement dès que le générateur correspondant est exécuté.

Un exemple de fichier de données canoniques est disponible [ici](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json).

## Termes courants

Quand on parcourt les données canoniques et le code des générateurs, on rencontre beaucoup de termes courants. Cette liste clarifie ce qu'ils représentent.

* Données canoniques : représente l'ensemble de la suite de tests.
* Cas de données canoniques : la représentation d'un seul cas de test.
* Description : le nom du test.
* Propriété : la méthode à appeler lors de l'exécution du test.
* Entrée : l'entrée du cas de test.
* Valeur attendue : la valeur attendue lors de l'exécution du cas de test.

## Ajouter un générateur simple

Ajouter un générateur de tests est simple. Il suffit d'ajouter une classe au fichier `Generators.fs` du dossier `generators`, en lui donnant le nom de l'exercice (en PascalCase), et d'étendre la classe abstraite `GeneratorExercise`.

Un exemple de générateur simple est l'exercice Bob. Le code source se trouve ci-dessous, mais tu peux aussi le consulter dans le dépôt [ici](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174).

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

C'est un générateur pleinement fonctionnel, aucun autre code n'est à écrire. Sa simplicité vient toutefois du fait que la suite de tests et le programme lui-même sont relativement triviaux.

## Ajouter un générateur complexe

Pour beaucoup de générateurs, le comportement par défaut de la classe `GeneratorExercise` suffit. Cependant, pour les générateurs plus _complexes_, on peut redéfinir une ou plusieurs de ses méthodes virtuelles :

### Méthode : RenderInput

Génère l'entrée d'une méthode de test.

#### Exemple

Le générateur `Gigasecond` génère la valeur d'entrée sous forme de valeur `DateTime` entre parenthèses :

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

À noter que tu peux utiliser le champ `key` pour ne personnaliser la sortie que pour certains champs d'entrée. Le générateur `Yacht` fait exactement cela :

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Méthode : RenderExpected

Génère la valeur attendue d'une méthode de test.

#### Exemple

Le générateur `Connect` génère la valeur attendue sous forme de valeur `Option<T>` :

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Méthode : RenderSut

Génère le système sous test (SUT). C'est la valeur réelle qui est vérifiée par rapport à la valeur attendue.

#### Exemple

Le générateur `RunLengthEncoding` contient un cas de test où il vérifie que l'encodage puis le décodage de l'entrée donnent la même valeur. La méthode `RenderSut` est redéfinie pour transformer ce qui serait un simple appel à une fonction `consistency` inexistante en une chaîne d'appels `encode |> decode` :

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Méthode : RenderArrange

Génère la partie _arrange_ de la méthode de test. C'est dans cette partie que le SUT est créé.

Le comportement par défaut est généralement celui que tu veux. Tu ne voudras le modifier que dans des circonstances très particulières.

Remarque : cette méthode renvoie une `string list`, où chaque `string` correspond à une seule ligne générée dans le fichier de test.

### Méthode : RenderAssert

Génère la partie _assert_ de la méthode de test. C'est dans cette partie que l'assertion est faite pour vérifier le SUT par rapport à la valeur attendue.

Le comportement par défaut est généralement celui que tu veux. Tu ne voudras le modifier que dans des circonstances très particulières.

Remarque : cette méthode renvoie une `string list`, où chaque `string` correspond à une seule ligne générée dans le fichier de test.

### Méthode : RenderSetup

Génère les éventuelles méthodes utilitaires ou de _setup_ supplémentaires. Cela permet de définir des méthodes auxiliaires utilisables dans les méthodes de test.

Le code de _setup_ est ajouté _avant_ les méthodes de test, afin que les méthodes de _setup_ puissent être utilisées dans les méthodes de test.

Remarque : cette méthode renvoie une `string list`, où chaque `string` correspond à une seule ligne générée dans le fichier de test.

#### Exemple

Le générateur `Zipper` ajoute deux méthodes auxiliaires utilisées dans les méthodes de test pour éliminer du code répétitif et fastidieux :

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Méthode : RenderValue

Génère une valeur unique (utilisée pour générer les paramètres d'entrée, la valeur attendue et le SUT).

### Exemple

Le générateur `ComplexNumbers` génère des valeurs différentes selon le type de la valeur :

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Méthode : MapCanonicalDataCase

Transforme le cas de données canoniques. Cela peut être utile si tu veux ajouter ou supprimer des propriétés.

Le comportement par défaut est généralement celui que tu veux. Tu ne voudras le modifier que dans des circonstances très particulières.

#### Exemple

Le générateur `ScaleGenerator` utilise la transformation du cas de données canoniques pour ajouter une propriété manquante avec la valeur `null` (ce qui facilite le traitement par la suite) :

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Méthode : PropertiesUsedAsSutParameter

Indique quelles propriétés doivent être utilisées comme paramètres du SUT.

Le comportement par défaut est généralement celui que tu veux. Tu ne voudras le modifier que dans des circonstances très particulières.

#### Exemple

Le générateur `RailFenceCipher` définit explicitement les propriétés utilisées comme paramètres du SUT afin de changer l'ordre dans lequel elles sont passées :

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Méthode : PropertiesWithIdentifier

Indique quelles propriétés doivent se voir attribuer un identifiant. Si une propriété figure dans cette liste, sa valeur lui est affectée sur une ligne distincte, dans son propre identifiant.

#### Exemple

Le générateur `Transpose` a choisi d'utiliser des identifiants pour toutes les propriétés :

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Méthode : IdentifierTypeAnnotation

Dans certains cas, tu veux qu'un identifiant ait un type explicite. Un cas d'usage courant est celui d'une valeur qui est un tableau vide. Dans ce cas, FsUnit a besoin d'une annotation de type pour exécuter l'assertion avec succès.

#### Exemple

Le générateur `Minesweeper` ajoute une annotation de type `string list` pour les valeurs vides :

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Méthode : AdditionalNamespaces

Renvoie un tableau des espaces de noms supplémentaires à ouvrir dans le fichier de test.

#### Exemple

Le générateur `Gigasecond` travaille avec des instances de `DateTime` et ajoute donc son espace de noms aux espaces de noms supplémentaires :

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Méthode : AssertTemplate

Le modèle d'assertion à utiliser. Tu trouveras tous les modèles d'assertion dans `generators/Templates/_Assert*.liquid`

#### Exemple

Le générateur `RationalNumbers` utilise le modèle `"AssertEqualWithin"` pour permettre de comparer des nombres à virgule flottante avec une tolérance donnée :

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Méthode : TestFileFormat

Le format du fichier de test : un module ou une classe.

Le comportement par défaut est quasiment toujours celui que tu veux. Tu ne voudras le modifier que dans des cas extrêmement rares.

#### Exemple

Le générateur `Grep` se définit comme une classe de test pour pouvoir utiliser des méthodes de _setup_ et de _teardown_ :

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Méthode : TestMethodName

Indique le nom de la méthode de test.

Le comportement par défaut est généralement celui que tu veux. Tu ne voudras le modifier que dans des circonstances très particulières.

#### Exemple

Le générateur `Zipper` nettoie un peu le nom des méthodes de test :

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Méthode : UseFullMethodName

Indique si le nom de méthode de test utilisé doit employer le chemin complet, ce qui signifie que, pour les cas de test imbriqués, le nom de la méthode de test est préfixé par la ou les descriptions parentes.

Le comportement par défaut est généralement celui que tu veux. Tu ne voudras le modifier que dans les cas où plusieurs méthodes de test porteraient sinon le même nom.

#### Méthode : Signature

Le générateur `KindergartenGarden` utilise des noms de méthode complets pour éviter les collisions de noms entre méthodes de test :

```fsharp
override __.UseFullMethodName _ = true
```

### Méthode : SkipTestMethod

Indique si la méthode de test doit être marquée avec la propriété `Skip = true`.

Le comportement par défaut est quasiment toujours celui que tu veux. Tu ne voudras le modifier que dans des cas extrêmement rares.

#### Méthode : Signature

L'exercice `Markdown` est un exercice de réécriture et, à ce titre, tous ses tests devraient déjà être dans un état valide. Par conséquent, il n'ajoute la propriété `Skip` à aucune de ses méthodes de test :

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Mettre à jour des fichiers existants

Il est possible qu'un exercice existant ne corresponde pas aux données canoniques. Tu peux tout à fait mettre à jour le squelette de l'exercice et/ou l'exemple de l'exercice pour qu'ils suivent les données canoniques !

De même, si tu trouves un problème dans l'un des générateurs ou des suites de tests existants, ouvre simplement le générateur que tu veux mettre à jour, apporte tes modifications, puis exécute les générateurs.

## Exécuter les générateurs

Ce dépôt est écrit pour [.NET Core 2.x](https://www.microsoft.com/net/core). Pour exécuter les générateurs, il te suffit de lancer la commande suivante dans le dossier generators :

`dotnet run`

Cette commande prend tous les générateurs d'exercices définis et génère tous les cas de test de chaque exercice. On utilise la réflexion pour récupérer tous les exercices, donc si tu ajoutes un nouveau test, celui-ci sera automatiquement pris en compte lors de l'exécution du générateur.

Si tu n'as besoin d'exécuter qu'un seul générateur, tu peux le faire avec la commande suivante :

`dotnet run -e <exercise>`

Une fois le générateur exécuté, tu peux consulter le résultat de ta génération en te rendant dans le fichier de test de cet exercice. Par exemple, la suite de tests de l'exercice Bob se trouve ici :

`exercises/bob/BobTests.fs`

## Soumettre un générateur

Si le résultat de ton générateur te satisfait, nous serions ravis que tu soumettes une _pull request_ ! Merci d'inclure ton générateur, la suite de tests mise à jour et tout autre fichier correspondant que tu aurais modifié.

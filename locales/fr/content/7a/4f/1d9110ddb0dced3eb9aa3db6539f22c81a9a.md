# Contribue au parcours C

Merci de l'intérêt que tu portes au parcours C d'Exercism !
Toutes les contributions sont les bienvenues, qu'il s'agisse d'un nouvel exercice, d'une modification de l'outillage ou de la documentation, d'une _issue_ ouverte, ou même simplement d'un commentaire sur une _issue_ ou une PR existante.
Ce fichier rassemble les informations dont tu as besoin pour démarrer.

Commence par lire la [documentation d'Exercism][Exercism docs], en particulier la page consacrée à la [contribution à un parcours][contributing to a language track], car ces documents couvrent une bonne partie des informations de base.

Ensuite, sache que quelques points propres à ce dépôt sont expliqués ci-dessous.

Les contributions qui corrigent ou améliorent des exercices existants sont les bienvenues.
Note que les exercices de ce parcours doivent respecter les normes définies dans le dépôt [problem-specifications][].
Les modifications des tests ou de la documentation d'un exercice commun demandent souvent une _pull request_ dans ce dépôt avant de pouvoir être intégrées aux exercices de ce parcours.
En cas de doute, ouvre une [_issue_][issue] sur GitHub et on en discutera.

## Code de conduite

Aide-nous à garder Exercism accueillant.
Merci de lire et de respecter le [Code de conduite][Code of Conduct].

## _Workflow_ Git

1. Fais un _fork_ du dépôt, puis clone-le.
2. Ajoute ce dépôt comme nouveau dépôt distant à ton clone : `git remote add upstream https://github.com/exercism/c.git`
3. Crée une nouvelle branche : `git checkout -b name-of-branch`
4. Commite et pousse comme d'habitude sur ta nouvelle branche
5. Quand tu es prêt à soumettre une _pull request_, fais un _rebase_ de ta branche sur la branche main du dépôt distant afin de pouvoir résoudre les éventuels conflits : `git fetch upstream && git rebase upstream/main` Tu devras peut-être pousser vers ta branche avec `--force` après avoir résolu les conflits.
6. Quand tout est prêt, pousse vers ta branche et crée la _pull request_ comme expliqué ci-dessous.

## _Issues_

On garde la trace des bugs, des améliorations et des demandes d'assistance du dépôt à l'aide des [_issues_][issues] GitHub.

Pour les discussions de plus haut niveau sur l'ensemble du projet, jette un œil aux _issues_ du dépôt [discussions][].

### Bon premier _patch_

On essaie d'étiqueter les _issues_ avec « good first patch » quand on estime qu'elles peuvent être résolues sans trop de contexte sur le code ou le fonctionnement d'Exercism. Pour les trouver, tu peux faire une recherche sur [good-first-patch][].

## _Pull requests_

Ce serait génial que tu suives ces quelques [consignes pour les _pull requests_][pull request guidelines] au moment de créer ta PR, mais ce n'est pas obligatoire.

Les _pull requests_ doivent porter sur une seule _issue_ ou un seul changement.
Les changements de style de code et de formulation sont les bienvenus, mais merci d'ouvrir si possible une PR séparée pour ce genre de modifications.
Merci d'ouvrir une _issue_ avant de créer une PR qui apporte des changements importants (et non rétrocompatibles) à un exercice existant, ou qui touche à de nombreux exercices. Mieux vaut discuter de ces changements avant de se lancer.

Si ta modification concerne un exercice, tu peux lancer les scripts d'intégration continue avant de soumettre la _pull request_ ; sinon, ils seront lancés automatiquement par la suite, comme décrit dans la section [Intégration continue][Continuous Integration].

Quand tu soumets une _pull request_, il nous arrive de te demander des modifications avant d'accepter le _patch_.

Merci de ne pas fermer la première _pull request_ pour en ouvrir une seconde avec ces changements.
Si tu pousses d'autres _commits_ vers une branche pour laquelle tu as ouvert une _pull request_, celle-ci se met à jour automatiquement.

Si tu veux créer une PR avec des changements qui ne sont pas encore tout à fait prêts à être fusionnés dans main (parce que tu aimerais par exemple discuter d'un point particulier), crée la PR normalement, mais utilise l'interface web de GitHub pour [la convertir en brouillon][convert the PR to a draft], afin que les mainteneurs sachent qu'elle n'est pas encore tout à fait prête à être fusionnée.

Comme pour l'ajout de nouveaux _commits_, tu n'as pas besoin de fermer ta _pull request_ pour en ouvrir une nouvelle si tu modifies l'historique (_rebase_, _squash_, _amend_) et que tu utilises git push --force pour mettre à jour la branche de ton _fork_.
La _pull request_ pointe vers cette branche, et non vers des _commits_ précis.

## Style de code

Le style de code attendu pour les contributions qui modifient du code est expliqué dans le [guide de style][style guide].

Le code des exercices est vérifié lors de l'[intégration continue][Continuous Integration] pour s'assurer qu'il respecte les règles d'espacement et d'indentation.
Cette vérification utilise la CLI [`clang-format`][clang-format].
Quand tu ajoutes un exercice ou que tu en modifies un, tu peux vérifier que ta modification respecte ces règles en exécutant l'outil en local avant de commiter.

Sous Linux, `clang-format` devrait être installable via le gestionnaire de paquets de ta distribution.
Sur Mac, tu peux installer le paquet `clang-format` avec [Homebrew][].

Tu peux lancer clang-format sur tous les fichiers en exécutant `format.sh`.
Pour le lancer manuellement sur un seul fichier, tu peux exécuter ce qui suit :

```bash
clang-format -i $(file)
```

## Anatomie d'un exercice

Chaque exercice doit se trouver dans un répertoire `c/exercises/practice/{exercise-name}`.
Voir [implement-an-exercise-from-specification][] pour tous les détails sur la mise en œuvre d'un exercice conforme à la spécification.

La structure d'un répertoire d'exercice est la suivante (note l'usage différent du tiret et du tiret bas pour les noms de répertoires et les noms de fichiers, respectivement) :

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - Ce fichier contient tous les tests de l'exercice.  
`test-framework` - répertoire contenant le harnais de test [Unity][] de [ThrowTheSwitch][].  
  ThrowTheSwitch propose un guide correct sur [les premiers pas avec Unity][getting started with unity] si tu veux un tutoriel.  
  La version d'Unity utilisée est indiquée dans [versions][]. La disposition du fichier de test est décrite dans le [guide de style][test-file-layout].  
  Les tests doivent être écrits de manière à satisfaire le fichier `canonical-data.json` de l'exercice dans le dépôt [problem-specifications][]  
`{exercise-name}.c` / `{exercise-name}.h` - Les fichiers source de l'exercice.  
  Merci d'utiliser des [gardes d'inclusion][include guards] dans tes fichiers d'en-tête.
  Les tests de l'exercice peuvent être lancés avec `make test` depuis la racine du dépôt.
* `makefile` - est le makefile de l'exercice tel qu'il se compilerait.  
Deux règles sont nécessaires,  
test: compiler test_{exercise-name}.c et l'exécuter.
memcheck: compiler test_{exercise-name} avec les options -fsanitize=address, -fno-common, -fno-omit-frame-pointer et l'exécuter
On attend des makefiles qu'ils changent très peu d'un exercice à l'autre, il devrait donc être facile d'en copier un depuis un autre exercice.

**N'oublie pas** d'ajouter l'exercice au fichier `config.json` du parcours. Pour cela, tu devras déterminer la meilleure place de cet exercice dans l'ordre de tous les autres exercices du parcours. Tu devras aussi générer un UUID à ajouter ici. Pour ces deux tâches, tu peux utiliser l'outil [configlet][] ; l'outil vérifiera même le style et formatera le `config.json` pour toi une fois ces modifications faites !

Pour information, pour récupérer l'artefact d'installation de l'outil configlet, va voir la [page des versions de configlet][configlet releases page].

## Intégration continue

Ce dépôt utilise des _workflows_ GitHub pour lancer certains outils à chaque _commit_ poussé sur une _pull request_.
La façon la plus simple de lancer ces _workflows_ sur ta propre contribution est d'ouvrir une PR sur ce dépôt avec tes modifications, de la marquer comme brouillon, puis de laisser la configuration d'intégration continue de ce dépôt tout gérer automatiquement pour toi.

### L'environnement d'intégration continue

GitHub exécute l'intégration continue sur des machines virtuelles qu'il appelle des [_runners_ hébergés][hosted runners].
Les _workflows_ peuvent configurer certains aspects des _runners_ sur lesquels ils souhaitent être exécutés.

Les _workflows_ de ce dépôt précisent seulement qu'ils doivent chacun être exécutés sur Ubuntu 24.04. Les _workflows_ sont épinglés à des versions précises plutôt que de se référer à `latest`, car certains des outils utilisés peuvent se comporter différemment selon la version.

### Lancer l'intégration continue sur ton propre _fork_

Si tu le souhaites, il est aussi possible de lancer l'intégration continue sur ton propre _fork_ : il suffit de cloner ce dépôt normalement sur GitHub.
Les fichiers YAML situés dans [`./.github/workflows/`][workflows] devraient fonctionner exactement de la même manière.
Si tu veux que l'action automatisée [`/format`][format-workflow] fonctionne correctement, tu devras ajouter une clé de déploiement à ton dépôt cloné.

### Les _workflows_

* `checks.yml` lance `shellcheck` sur les scripts des outils, puis exécute les outils suivants :
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * l'action [vérificateur de liens Lychee][lychee]
* `configlet.yml` récupère la dernière version de configlet, puis lance la commande `lint` sur le parcours
* `format-code.yml` cherche la _string_ `/format` dans les commentaires d'une PR ; s'il la trouve, `format.sh` est exécuté sur les exercices et les éventuelles modifications font l'objet d'un _commit_. Une clé de déploiement est nécessaire pour que ce _commit_ puisse relancer l'intégration continue. Cette clé de déploiement est gérée directement par Exercism.
* `test.yml` lance `make` à la racine du dépôt pour tester tous les exercices

### Les outils

Tu peux voir dans les [_workflows_][workflows] que GitHub est configuré pour lancer des outils depuis le répertoire [`./bin`][bin].
Le travail effectué par les outils de ce répertoire est décrit ci-dessous :

* `check-unitybegin` s'assure que chaque fichier de test ajoute correctement la ligne `UNITY_BEGIN()` au début de sa fonction `main()`.
* `fetch-configlet` récupère l'outil `configlet` depuis son [dépôt][configlet].
* `verify-unity-version` vérifie la version du framework de test Unity utilisée par chaque exercice. La version à vérifier est indiquée dans [`./docs/VERSIONS.md`][versions]
* `check-include-guards` vérifie que les gardes d'inclusion utilisées dans le squelette et l'en-tête d'exemple de chaque exercice respectent le bon format, à savoir :

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` récupère l'outil `configlet` depuis son [dépôt][configlet].

### Lancer les outils en local

Tu peux aussi lancer les outils individuellement sur ta propre machine avant de commiter.
Commence par t'assurer que les applications nécessaires sont installées (comme `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] et un compilateur C), puis lance l'outil voulu depuis la racine du dépôt. Par exemple :

```bash
~/git/c$ make
```

Si tu veux lancer seulement quelques tests pour vérifier ton travail, tu peux les indiquer comme cibles de make.

```bash
~/git/c$ make acronym all-your-base allergies
```

## Exécuteur de tests

Ce parcours dispose d'un exécuteur de tests pour Exercism v3 !
Tu peux le découvrir [ici][c-test-runner].

Les exécuteurs de tests offrent une méthode dockerisée pour lancer les tests d'un exercice sur le code d'un apprenant dans Exercism v3.
Cette approche Docker permet notamment aux apprenants de coder directement dans leur navigateur.
Pour en savoir plus, lis la page sur les [exécuteurs de tests][test runners].

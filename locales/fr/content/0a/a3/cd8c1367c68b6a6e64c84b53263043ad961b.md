# À propos

## Les erreurs en `jq`

`jq` signale deux grandes catégories d'erreurs :

1. **Les erreurs de compilation** : le programme lui-même est invalide, qu'il s'agisse d'erreurs de syntaxe, de références à des fonctions ou à des variables non définies, etc. `jq` refuse alors purement et simplement d'exécuter le programme.

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **Les erreurs d'exécution** : le programme est valide, mais quelque chose se passe mal pendant le traitement d'une valeur. Par exemple, on indexe un nombre avec une _string_, on analyse un texte JSON invalide avec `fromjson`, ou on appelle une fonction avec des arguments du mauvais type.

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

Ce concept porte sur les **erreurs d'exécution** : comment les lever, comment les intercepter et comment les arrêter.

Une erreur d'exécution non interceptée amène `jq` à afficher un message sur la sortie d'erreur standard et à quitter avec le statut `5`.

## Lever des erreurs : `error` et `error(message)`

Le filtre [`error`][man-error] lève une erreur.

- `error` lève une erreur dont la valeur est la valeur d'**entrée**.
- `error(message)` lève une erreur dont la valeur est le résultat de `message`.

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
La valeur de l'erreur peut être **n'importe quelle** valeur JSON, pas seulement une _string_.
Lever des erreurs structurées permet à un gestionnaire `catch` de prendre des décisions en fonction du contenu de l'erreur.

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

Si une valeur d'erreur qui n'est pas une _string_ n'est pas interceptée, `jq` l'affiche au format JSON, avec la mention `(not a string)`.

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## Intercepter les erreurs : `try` et `catch`

On peut intercepter les erreurs avec [`try EXP catch HANDLER`][man-try-catch].
La première expression est exécutée ; si elle lève une erreur, l'expression `HANDLER` est exécutée **avec la valeur de l'erreur comme entrée**.
La sortie du gestionnaire est émise comme si c'était celle de l'expression passée à `try`.

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

La forme courte `try EXP` équivaut à `try EXP catch empty` : l'erreur est ignorée et aucune sortie n'est produite.

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
Une erreur **interrompt le reste du flux** à l'intérieur du `try`.
Les valeurs déjà produites sont conservées, mais rien de ce qui suit l'erreur n'est évalué.

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

Un gestionnaire peut lever une nouvelle erreur, ou relancer l'originale avec un simple `error` : comme la valeur de l'erreur est l'entrée du gestionnaire, elle est ainsi propagée telle quelle.

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## Masquer les erreurs : l'opérateur `?`

L'[opérateur `?`][man-question-mark], utilisé sous la forme `EXP?`, est un raccourci pour `try EXP`.
Il transforme une expression qui échoue en une expression qui ne produit tout simplement aucune sortie.

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

On le voit souvent accolé aux opérateurs d'indexation :

- `.foo?` équivaut à `.["foo"]?`
- `.[]?` n'itère que si l'entrée est un tableau ou un objet, et ne produit rien sinon

~~~~exercism/caution
`?` masque **toutes** les erreurs, y compris celles que tu n'avais pas anticipées.
`user.name?` ne produit silencieusement rien quand `user` n'est pas un objet, ce qui peut camoufler des problèmes de données ou des fautes de frappe dans ton programme.
Préfère `try ... catch` quand tu as besoin de savoir **que** quelque chose a échoué, ou valide l'entrée explicitement.
~~~~

## L'opérateur alternatif `//`

Les programmeurs s'attendent parfois à ce que `a // b` produise `b` quand `a` échoue.
C'était vrai dans les anciennes versions de `jq`, mais plus depuis `jq` 1.6.
L'opérateur `//` ne masque pas les erreurs.
Il ne remplace par `b` que lorsque `a` ne produit aucune valeur, ou produit `false` ou `null` ; les erreurs de `a` sont quand même propagées.

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

Utilise `try a catch b` si tu veux une solution de repli en cas d'erreur.

## L'opérateur alternatif de déstructuration `?//`

L'[opérateur `?//`][man-question-mark-slash-slash] combine la déstructuration et la gestion des erreurs.
Il essaie chaque motif de liaison à tour de rôle jusqu'à ce que l'un d'eux réussisse, et les variables liées par les alternatives qui échouent sont mises à `null`.

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

Ici, le premier motif attend que `c` soit un _objet_ avec les clés `d` et `e`, tandis que le second attend que `c` soit un _tableau_ contenant un tel objet.
Le premier élément d'entrée se lie au premier motif ; le second élément échoue sur ce motif, c'est donc le second qui est essayé à la place.

Cela permet à un même programme de déstructurer des entrées qui peuvent prendre plusieurs formes, sans écrire de chaînes explicites de `if type == ...`.

## Arrêter le programme : `halt` et `halt_error`

Parfois, la bonne réaction face à une erreur est de tout arrêter.

- [`halt`][man-halt] arrête immédiatement le programme `jq` sans autre sortie ; le statut de sortie est `0`.
- [`halt_error`][man-halt-error] arrête le programme, affiche son **entrée** sur la sortie d'erreur standard en texte brut (sans aucune décoration, pas même un saut de ligne) et quitte avec le statut donné, `5` par défaut.

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

À noter que ces filtres arrêtent le programme immédiatement, même s'il reste des entrées à lire.

### Les statuts de sortie

Pour référence, `jq` utilise les statuts de sortie suivants :

| Statut | Signification                                    |
| :----: | ------------------------------------------------ |
| `0`    | succès                                           |
| `2`    | erreur d'utilisation (options de ligne de commande incorrectes) |
| `3`    | erreur de compilation                            |
| `5`    | erreur d'exécution (ou `halt_error` sans argument) |

Avec l'option `--exit-status` / `-e`, le statut reflète plutôt la dernière valeur émise : `0` pour `true` ou pour un nombre, `1` pour `false` ou `null`, `4` quand il n'y a aucune sortie.

## Aides au débogage

Pour retrouver l'origine d'une erreur, ces filtres sont utiles :

- [`debug`][man-debug] laisse passer son entrée sans la modifier, mais affiche `["DEBUG:", <input>]` sur la sortie d'erreur standard.
  `debug(msgs)` affiche aussi `msgs` sous forme de messages de débogage.
- [`stderr`][man-stderr] affiche son entrée, brute et compacte, sur la sortie d'erreur standard.
- [`input_line_number`][man-input-line-number] renvoie le numéro de ligne de l'entrée en cours de filtrage, ce qui est précieux quand un fichier contient beaucoup de textes JSON et que l'un d'eux est invalide.
- [`$__loc__`][man-loc] renvoie un objet avec les clés `file` et `line` qui décrit où il se trouve dans le programme, ce que l'on peut intégrer aux messages d'erreur.

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

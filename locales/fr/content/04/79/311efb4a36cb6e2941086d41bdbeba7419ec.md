# Introduction

## L'interface `error`

En Go, la gestion des erreurs ne se fait **pas** au moyen d'exceptions.
À la place, les erreurs sont des _valeurs_ ordinaires de types qui implémentent l'interface `error` intégrée.
L'interface `error` est très minimale.
Elle ne contient qu'une seule méthode `Error()` qui renvoie le message d'erreur sous forme de _string_.

```go
type error interface {
  Error() string
}
```

Chaque fois que tu définis une fonction dans laquelle une erreur peut survenir pendant l'exécution et doit remonter jusqu'à l'appelant, tu dois inclure `error` parmi les types de retour.
Si la fonction prend plusieurs valeurs de retour, par convention `error` est toujours la dernière.

```go
func DoSomething() (int, error) {
  // ...
}
```

## Crée et renvoie une erreur simple

Tu n'as pas toujours besoin d'implémenter toi-même l'interface error.
Pour créer une erreur simple, tu peux utiliser la fonction `errors.New()` qui fait partie du paquet `errors` de la bibliothèque standard.
La seule chose à passer est le message d'erreur sous forme de _string_, et `errors.New()` se charge de créer une valeur qui contient ton message et qui implémente l'interface `error`.

Si la fonction renvoie une erreur, la bonne pratique est de renvoyer la valeur zéro pour tous les autres paramètres de retour :

```go
func DoSomething() (SomeStruct, int, error) {
  // ...
  return SomeStruct{}, 0, errors.New("failed to calculate result")
}
```

~~~~exercism/caution
Tu ne dois pas supposer que toutes les fonctions renvoient des valeurs zéro pour les autres valeurs de retour lorsqu'une erreur est présente.
La meilleure pratique consiste à considérer qu'il n'est pas sûr d'utiliser les autres valeurs de retour si une erreur s'est produite.
Les seules exceptions sont les cas où la documentation indique clairement que les autres valeurs de retour sont significatives en cas d'erreur.
~~~~

Si tu veux utiliser une telle erreur simple à plusieurs endroits, il vaut mieux déclarer une variable pour l'erreur plutôt que d'utiliser `errors.New` en ligne.
Par convention, le nom de cette variable doit commencer par `Err` ou `err` (selon qu'elle est exportée ou non).
Ces variables d'erreur sont souvent appelées erreurs sentinelles.

```go
import "errors"

var ErrNotFound = errors.New("resource was not found")

func DoSomething() error {
  // ...
  return ErrNotFound
}
```

Renvoie `nil` pour l'erreur afin de signaler qu'il n'y a pas eu d'erreur pendant l'exécution de la fonction :

```go
func Foo() (int, error) {
  return 10, nil
}
```

## Vérification des erreurs

Si tu appelles une fonction qui renvoie une erreur, il est courant de stocker la valeur de l'erreur dans une variable appelée `err`.
Avant d'utiliser le résultat réel de la fonction, tu dois vérifier qu'il n'y a pas eu d'erreur.

Pour éviter d'imbriquer le « happy path » de ton code, il faut traiter les cas d'erreur en premier.
On peut utiliser `==` et `!=` pour comparer l'erreur à `nil`, et on sait qu'il y a eu une erreur quand `err` n'est pas `nil`.

```go
func processUserFile() error {
	file, err := os.Open("./users.csv")
	if err != nil {
		return err
	}

	// do something with file
}
```

La plupart du temps, l'erreur remonte la pile d'appels, comme le montre l'exemple ci-dessus.
Une autre façon de traiter l'erreur consiste à la journaliser et à poursuivre avec une autre opération.
La bonne pratique est de renvoyer ou de journaliser l'erreur, jamais les deux.

Comme la plupart des fonctions en Go incluent une erreur parmi les valeurs de retour, tu verras et utiliseras le motif `if err != nil` un peu partout dans le code Go.

## Types d'erreur personnalisés

Si tu veux que ton erreur contienne plus d'informations que le simple message d'erreur, tu peux créer un type d'erreur personnalisé.
Comme mentionné plus haut, tout ce qui implémente l'interface `error` (c'est-à-dire qui possède une méthode `Error() string`) peut servir d'erreur en Go.

En général, on utilise une structure pour créer un type d'erreur personnalisé.
Par convention, les noms des types d'erreur personnalisés doivent se terminer par `Error`.
Il est aussi préférable de définir la méthode `Error() string` avec un récepteur pointeur ; consulte ce [commentaire Stack Overflow][stackoverflow-errors] pour comprendre le raisonnement.
Note que cela signifie que tu dois renvoyer un pointeur vers ton erreur personnalisée, sinon elle ne sera pas considérée comme une `error`, car la valeur non-pointeur ne fournit pas la méthode `Error() string`.

```go
type MyCustomError struct {
  message string
  details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.message, e.details)
}

func someFunction() error {
  // ...
  return &MyCustomError{
    message: "...",
    details: "...",
  }
}
```

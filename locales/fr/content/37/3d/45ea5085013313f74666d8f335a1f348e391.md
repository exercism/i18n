# Introduction

Il est souvent utile de définir des types personnalisés dans nos programmes.

Il est possible de créer de nouveaux types primitifs, mais c'est rarement fait.
Les types primitifs intégrés ne relèvent pas d'un choix arbitraire : ils correspondent étroitement aux types standard du compilateur LLVM utilisé par Julia pour la compilation JIT.

Bien plus utile : la possibilité de définir des types composites, dotés de champs nommés.

D'autres langages ont quelque chose de similaire, qu'ils appellent `structs` ou `records`.
La documentation de Julia les appelle `composite types`, même si (léger décalage) la syntaxe du langage les définit avec le mot-clé `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Quelques points méritent d'être relevés dans l'exemple ci-dessus :

- Aucun type n'est spécifié pour `id`, donc le compilateur l'interprète comme `id::Any`.
- Le nom du type est utilisé comme constructeur, comme dans `Person(id, name, age)`, pour donner une instance de type `Person`.
- On peut accéder aux champs individuellement avec la notation point, comme pour les tuples nommés.

Les objets de type `Person` sont immuables, les modifications ne sont donc pas autorisées.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Si la mutabilité est nécessaire, ajoute `mutable` à la définition.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Par défaut, le constructeur exige que les champs apparaissent dans le même ordre que dans la définition, ce qui devient peu pratique pour des types plus compliqués.

Utiliser la macro `@kwdef` permet deux nouvelles possibilités :

- Le constructeur utilise des mots-clés, et non la position.
- Les champs peuvent avoir des valeurs par défaut et, éventuellement, être omis du constructeur.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hiérarchies de types composites

Jusqu'ici, on n'a créé que des types composites concrets.
Si on vérifie, ils sont tous des sous-types de `Any`.

Quand on crée plusieurs types liés, il est probablement plus judicieux de définir une hiérarchie entre eux.
C'est très facile à faire.

D'abord, crée un type abstrait :

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Ensuite, ajoute un opérateur `<:` dans une définition de type, pour montrer la relation.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Répète autant que nécessaire, en gardant à l'esprit que le sous-typage de types concrets n'est pas autorisé.

Pour une hiérarchie plus complexe, crée des sous-types abstraits selon les besoins.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

L'intérêt d'une telle hiérarchie apparaîtra plus clairement quand on arrivera au concept `Multiple Dispatch`, et qu'on verra comment les fonctions traitent les types de leurs arguments.

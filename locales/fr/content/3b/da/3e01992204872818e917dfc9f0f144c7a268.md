# Inclusion de code

```sather
   include WARM_UP;
   include WARM_UP count -> warm_up_count;
   include WARM_UP describe -> ;
   include WARM_UP count -> beats, describe -> ;
```

Un `include` copie le code d'une autre classe dans celle-ci. C'est une opération à la compilation, sans coût ni relation à l'exécution : les deux classes ne sont pas reliées par la suite.

## La clause

```
   include CLASS  old_name -> new_name , old_name -> ;
```

Chaque entrée renomme un élément. `-> ;` sans nouveau nom l'omet. Tout ce qui n'est pas mentionné est repris tel quel.

Le renommage s'applique à ce que voit l'*extérieur*. Les appels entre les routines incluses continuent de fonctionner : si `describe` appelle `count` et que `count` est renommé en `beats`, `describe` appelle `beats`.

## En inclure plusieurs

```sather
   include WARM_UP;
   include COOL_DOWN;
```

est autorisé, et c'est ainsi que Sather obtient ce que d'autres langages appellent l'héritage multiple, sans les ennuis habituels, car un conflit est une erreur de compilation et il suffit de renommer l'un des deux ou de l'omettre. Rien n'est résolu par un ordre de priorité qu'il faudrait mémoriser.

## private include

```sather
   private include WARM_UP;
```

fait entrer le code pour l'usage propre de cette classe sans l'exposer. Utile quand on veut l'implémentation et non l'interface.

## Les deux ensemble

La forme habituelle pour une famille de classes :

```sather
abstract class $ACT is
   name : STR;
   minutes : INT;
end;

class ACT_BASICS is
   minutes : INT is return 5; end;
end;

class JUGGLING < $ACT is
   include ACT_BASICS;
   name : STR is return "Juggling"; end;
end;
```

`< $ACT` dit ce que la classe sait faire ; `include ACT_BASICS` fournit une partie de la manière de le faire. Si tu changes d'avis sur la manière de faire, le `<` ne bouge pas.

## Pourquoi c'est fait ainsi

Une classe abstraite n'a pas de code, on ne peut donc pas en hériter par accident, et il n'existe pas de superclasse dont le comportement change à ton insu. La réutilisation est une copie prise à la compilation, depuis une classe que tu as nommée, avec chaque renommage écrit noir sur blanc.

Le prix à payer, c'est que la réutilisation doit être demandée explicitement dans chaque classe. C'est le compromis : plus à taper, rien d'implicite.

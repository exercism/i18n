# Instructions

Ce problème s'inspire de l'ordonnancement statique non préemptif des systèmes d'exploitation temps réel, mais il ressemble aussi au Job-Shop Scheduling Problem (JSP) avec une seule ressource. On suppose ici que toutes les tâches sont connues de manière statique. Autrement dit, les temps de libération de toutes les tâches de ce problème sont connus au début du programme. En pratique, le temps de libération des tâches n'est pas connu au démarrage d'un programme et peut être généré à tout moment par des E/S, des interruptions, etc.

Étant donné un tableau de tâches avec leurs paramètres, détermine un ordonnancement dans lequel les tâches peuvent s'exécuter séquentiellement sans se chevaucher. Comme le problème est inspiré de l'ordonnancement des processus d'un RTOS, on suppose qu'un temps non nul est nécessaire entre les tâches, ce qu'on appelle aussi le coût de commutation de contexte. Il existe deux types de tâches différents : les tâches périodiques et les tâches dynamiques. Les deux types possèdent un paramètre d'ID de tâche, qui est une _string_ servant à distinguer les différentes tâches du tableau.

Une **tâche périodique** est une tâche qui s'exécute périodiquement. Autrement dit, la tâche s'exécute une fois toutes les T secondes, où T désigne la période.
Une tâche périodique est définie par les paramètres suivants :
* Temps de début : moment où la première répétition, ou instance, de la tâche commence
* Période : temps entre le début des répétitions de la tâche
* Temps d'exécution : durée de chaque répétition
* Temps de fin : moment où la tâche cesse complètement d'être ordonnancée

Une **tâche dynamique** est une tâche qui ne s'exécute qu'une seule fois.
Une tâche dynamique est définie par les paramètres suivants :
* Temps de libération : premier moment où la tâche PEUT être ordonnancée (ce n'est PAS la même chose que le temps de début)
* Temps d'exécution : durée d'exécution de la tâche
* Échéance : moment auquel la tâche doit avoir terminé son exécution

La fonction à implémenter prend deux entrées. La première entrée est un tableau d'instances de `RealTimeTask`. Les instances de `RealTimeTask` sont fournies soit comme instance de `PeriodicRealTimeTask`, soit comme instance de `DynamicRealTimeTask`, tous les paramètres de tâche étant des entiers. La fonction native `isinstance()` de Python permet de distinguer les deux types de tâches dans le tableau. L'ordre du tableau n'a pas d'importance : il suffit de regarder les paramètres des tâches. La seconde entrée est un entier qui précise le coût de commutation de contexte. Ce coût de commutation de contexte est toujours un entier non négatif.

La sortie doit être un dictionnaire dont les clés sont l'ID de tâche des instances de `RealTimeTask`, et dont les valeurs sont un tableau de tuples de deux éléments. Le format de ces tuples est (temps de début, temps de fin). Les tâches dynamiques ne doivent contenir qu'un seul tuple dans le tableau, tandis que les tâches périodiques peuvent en contenir plusieurs. L'ordre des tuples dans le tableau n'a pas d'importance. Si aucun ordonnancement valide ne peut être créé à partir du tableau de tâches avec le coût de commutation de contexte donné, lève une exception `NoRtosStaticScheduleProducible`. Note que les résultats du modèle Z3 pour les variables devront être convertis en entiers avant d'être renvoyés. Si le résultat du modèle Z3 est de type `IntNumRef`, la méthode de classe `as_long()` peut être utilisée pour le convertir en entier.

Une fonction supplémentaire est fournie pour permettre à l'utilisateur de visualiser l'ordre séquentiel des tâches. Elle peut aussi être activée pour chaque cas de test en passant l'argument nommé `plot` à `True` dans la fonction `check()`. Un diagramme à barres horizontales brisées est utilisé pour représenter et étiqueter chaque tâche. Pour utiliser cette fonction, la bibliothèque Python *matplotlib* doit être installée. Les détails d'installation de *matplotlib* sont disponibles [ici](https://matplotlib.org/stable/users/installing.html).

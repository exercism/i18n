# Générateur de tests du parcours Python d'Exercism

Le parcours Python utilise un script générateur et des modèles [Jinja2][Jinja2] pour créer les fichiers de tests à partir des [données canoniques][canonical data] d'Exercism.

## Utilisation du script

La génération des tests nécessite une copie locale du dépôt [problem-specifications][problem-specifications]. Le script doit être lancé depuis le répertoire `python` racine, afin d'accéder correctement aux exercices.

Lance `bin/generate_tests.py --help` pour obtenir les informations d'utilisation.


## Modèles de tests

Les modèles de tests prennent en charge la syntaxe [Jinja2], et disposent des variables de contexte suivantes, fournies par les données canoniques :
- `exercise` : le nom de l'exercice avec des tirets (ex. : `two-fer`)
- `version` : la version des données canoniques (ex. : `1.2.0`)
- `cases` : une liste d'objets de cas, ou une liste de listes `cases`. Pour connaître la structure exacte de l'exercice sur lequel tu travailles, consulte `canonical-data.json`
- `has_error_case` : indique si un cas de test attend qu'une erreur soit levée (ex. : `False`)
- `additional_cases` : une structure similaire à `cases`, mais remplie à partir du fichier `.meta/additional_tests.json` de l'exercice, s'il existe (pour un exemple, voir `exercises/word-count/.meta/additional_tests.json`)

De plus, les filtres de modèle suivants sont ajoutés pour plus de commodité :
- `to_snake` : convertit une _string_ en snake_case (ex. : `{{ "CamelCaseString" | to_snake }}` -> `camel_case_string`)
- `camel_case` : convertit une _string_ en CamelCase (ex. : `{{ "snake_case_string" | camel_case }}` -> `SnakeCaseString` )
- `error_case` : vérifie si un cas de test attend qu'une erreur soit levée (ex. : `{% for case in cases%}{% if case is error_case}`)
- `regex_replace` : remplacement par expression régulière (ex. : `{{ "abc123" | regex_replace("\\d", "D") }}` -> `abcDDD`)


### Conventions

- Les macros à usage général pour les structures de modèle très répétées sont définies dans `config/generator_macros.j2`.
  - Elles peuvent être importées comme suit :
  `{%- import "generator_macros.j2" as macros with context -%}`
- Tous les modèles de tests doivent se terminer par `{{ macros.footer() }}`.
- Tous les noms de classes Python doivent être en CamelCase (ex. : `TwoFer`).
  - Pour les convertir, utilise `{{ "two-fer" | camel_case }}`
- Tous les noms de modules et de fonctions Python doivent être en snake_case (ex. : `high_scores`, `personal_best`).
  - Pour les convertir, utilise `{{ "personalBest" | to_snake }}`
- Les tests propres au parcours sont définis dans le fichier d'options `.meta/additional_tests.json`. L'objet JSON défini dans ce fichier doit avoir une seule clé, `cases`, dont la structure est identique à celle de `cases` dans `canonical-data.json`.
- Les tests propres au parcours doivent être placés après les tests canoniques dans les fichiers de tests.
- Les tests propres au parcours doivent être signalés dans le fichier de tests par le commentaire suivant :
```
# Additional tests for this track
```


### Structure

La plupart des modèles ressembleront à quelque chose comme ceci :

```Jinja2
{%- import "generator_macros.j2" as macros with context -%}
{{ macros.header() }}

class {{ exercise | camel_case }}Test(unittest.TestCase):
    {% for case in cases -%}
    def test_{{ case["description"] | to_snake }}(self):
        value = {{ case["input"]["value"] }}
        expected = {{ case["expected"] }}
        self.assertEqual({{ case["property"] }}(value), expected)

    {% endfor %}

{{ macros.footer() }}
```


### Redéfinir les imports

Les noms importés dans `macros.header()` peuvent être redéfinis en ajoutant une liste de noms alternatifs à importer (ex. : `clock`) :

```Jinja2
{{ macros.header(["Clock"])}}
```


### Ignorer des propriétés

Il peut arriver, rarement, qu'il soit nécessaire de filtrer des propriétés qui ne sont pas testées dans ce parcours. La macro `header` accepte aussi un argument `ignore` (ex. : `high-scores`) :

```Jinja2
{{ macros.header(ignore=["scores"]) }}
```

## Créer un modèle

1. Crée le fichier `.meta/template.j2` pour l'exercice que tu es en train d'implémenter, et ouvre-le dans ton éditeur.
2. Copie-colle l'[exemple de structure](#Layout) dans le fichier de modèle et enregistre-le.
3. Apporte les modifications nécessaires au fichier de modèle jusqu'à ce qu'il produise du code de test valide, en te référant au fichier `canonical-data.json` de l'exercice pour les noms d'entrées et la structure des cas.
    - Utilise les [macros disponibles](../config/generator_macros.j2) pour éviter de réécrire les sections standardisées.
    - Si tu implémentes un modèle pour un exercice existant, il n'est pas obligatoire de reproduire exactement la structure du fichier de tests existant, mais réduire les différences facilitera grandement la revue de la PR pour toutes les personnes impliquées.

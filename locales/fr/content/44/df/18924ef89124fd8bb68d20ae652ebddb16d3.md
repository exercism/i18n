# Routines liées

```sather
   part : ROUT{STR}:STR := bind(shout(_));
   part.call("who's there");
```

## bind

`bind` prend un appel dans lequel n'importe quelle partie peut être remplacée par `_`. Tout ce qui n'est pas un `_` est évalué **maintenant** et conservé ; chaque `_` devient un argument de la routine liée, dans l'ordre où il est écrit.

```sather
   bind(repeat(2, _))         -- ROUT{STR}:STR
   bind(repeat(_, "Ha"))      -- ROUT{INT}:STR
   bind(repeat(_, _))         -- ROUT{INT,STR}:STR
```

## Les types

| Type | Prend | Renvoie |
| --- | --- | --- |
| `ROUT:INT` | rien | `INT` |
| `ROUT{STR}` | un `STR` | rien |
| `ROUT{STR}:STR` | un `STR` | un `STR` |
| `ROUT{INT,INT}:BOOL` | deux `INT` | `BOOL` |

`ITER{...}` est la même idée pour un itérateur.

## call

`call` fournit les arguments restants. Une routine liée qui ne renvoie rien s'appelle de la même façon, en tant qu'instruction.

## bind se place à droite d'une affectation

On peut déclarer un `bind` dans une variable, ou le passer en argument :

```sather
   part ::= bind(shout(_));                -- yes
   part : ROUT{STR}:STR := bind(shout(_)); -- yes
   rehearse("line", bind(shout(_)));       -- yes
```

mais il ne peut pas aller directement dans un `return` :

```sather
   return bind(shout(_));                  -- does not parse
```

Mets-le dans une variable et renvoie celle-ci. Le message d'erreur pointe vers le `bind` et mentionne des tirets bas, ce qui n'est pas évident à la lecture de la ligne elle-même.

## Où on les utilise

La bibliothèque les prend partout où un comportement doit être fourni :

```sather
   names.sort_by(bind(shorter(_, _)));
   scores.count_if(bind(over(10, _)));
   scores.find_if(bind(is_even(_)));
```

Le tri est le cas le plus clair : `sort_by` sait comment trier et ne sait rien de l'idée que tu te fais de l'ordre, et c'est la routine liée qui fait se rencontrer les deux.

## Une limitation de ce compilateur

Sather 1.2 n'implémente pas les routines liées **dispatched**, c'est-à-dire le fait de lier une routine sur une variable de type abstrait. Le compilateur le dit sans détour :

```
Dispatched bound routines are not implemented yet
```

Fais un `bind` sur un type concret, ou sur une classe, et tout va bien. C'est pourquoi le propre harnais de tests du parcours écrit ses vérifications d'exceptions à la main plutôt que de recourir à une routine liée.

## Routines liées ou classes abstraites ?

Les deux permettent à un appelant de fournir un comportement.

Une routine liée, c'est une seule routine : elle n'a pas besoin de classe et s'écrit là où on l'utilise. Une classe abstraite porte plusieurs routines et un peu d'état, et vaut bien le cérémonial quand la chose fournie comporte plus d'une partie.

Une seule routine à confier : fais un `bind`. Un collaborateur qui en compte plusieurs : écris une classe.

# À propos

Les threads de Factor sont des *coroutines coopératives* sur un seul thread du système d'exploitation. Un thread s'exécute jusqu'à ce qu'il rende explicitement la main ou effectue des entrées-sorties bloquantes, moment auquel l'ordonnanceur choisit un autre thread prêt à s'exécuter. Deux conséquences :

- Tout ce qui s'exécute entre deux cessions de la main est de fait atomique.
- Un véritable parallélisme multi-cœur suppose de sortir du vocabulaire standard `threads` (par exemple `concurrency.distributed` pour des architectures multi-processus).

Les primitives de concurrence standard sont organisées en couches :

| Vocabulaire                 | Fournit                                |
|-----------------------------|----------------------------------------|
| [`threads`][threads]                   | `spawn`, `yield`, identité des threads |
| [`concurrency.promises`][concurrency.promises]      | `<promise>`, `fulfill`, `?promise`     |
| [`concurrency.locks`][concurrency.locks]         | `<lock>`, `with-lock`                  |
| [`concurrency.combinators`][concurrency.combinators]   | `parallel-map`, `parallel-each`        |
| [`concurrency.semaphores`][concurrency.semaphores]    | `<semaphore>`, `acquire`, `release`    |
| [`concurrency.mailboxes`][concurrency.mailboxes]     | boîtes aux lettres par thread, `send`, `receive` |
| [`concurrency.channels`][concurrency.channels]      | canaux de rendez-vous, `to`, `from`    |

```factor
USING: concurrency.combinators concurrency.locks
concurrency.promises kernel sequences threads ;

! parallel-map: fork-join, in order
{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }

! spawn + promise: hand-rolled fork-join
<promise> [
    [ "hello, world" swap fulfill ] curry "greeter" spawn drop
] keep ?promise .   ! => "hello, world"

! <lock> + with-lock: protect a shared mutable slot
<lock> :> guard
guard [ "do thing under lock" drop ] with-lock
```

`parallel-map` est l'API de haut niveau, celle que le Factor idiomatique utilise en premier. Le trio `spawn` / `<promise>` / `?promise` est ce sur quoi `parallel-map` est bâti, ce qui est bien pratique quand la forme de l'itération ne convient pas à un map (par exemple lancer des tâches qui répondent via d'autres canaux).

Les verrous protègent l'*état mutable partagé*, le plus souvent un emplacement de tuple ou une table de hachage que plusieurs threads lisent ou écrivent. Traite les lectures comme les écritures : les deux doivent prendre le verrou dès qu'une mise à jour composite n'est pas atomique ; oublier le verrou d'un côté comme de l'autre est la recette classique de la lecture déchirée.

# À propos

Comme nous l'avons vu dans le concept [`Nothingness`][concept-nothingness], R propose plusieurs façons de représenter des données absentes ([`NULL`][ref-null]), inconnues ([`NA`][ref-na]) ou mathématiquement invalides ([`NaN`][ref-finite], [`Inf`][ref-finite]).
En général, R essaie d'utiliser ces valeurs pour signaler les problèmes là où ils surviennent, puis poursuit son exécution sans lever d'exception.

## `stop()`

Certains problèmes sont trop fondamentaux pour laisser le programme continuer.
Dans ce cas, utilise [`stop(msg)`][ref-stop] pour interrompre immédiatement le programme en levant une `Error` et afficher `msg`.

```R
f <- function() {
    stop("I have a problem")
}
f()
#> Error in f() : I have a problem
```

## `stopifnot()`

Comme l'[`assert`][wiki-assert] d'autres langages, [`stopifnot()`][ref-stopifnot] est un raccourci pratique pour `stop()`.
Les arguments sont un nombre quelconque de conditions booléennes, séparées par des virgules, et le programme ne poursuit son exécution que si elles valent toutes `TRUE`.

```R
stopifnot(1 < 2) # continues OK
stopifnot(1 < 2, 1 == 2)
#> Error: 1 == 2 is not TRUE
```

## `try()`

R dispose de plusieurs façons de gérer les erreurs.
Celles-ci s'inspirent de Common Lisp et diffèrent sensiblement de celles de nombreux langages populaires.

La plus simple consiste à placer le code potentiellement problématique dans un [`try()`][ref-try].

```R
g <- function(val) {
  log10(val)
}

g(3)
#> [1] 0.4771213

g("3")
#> Error in log10(val) : non-numeric argument to mathematical function

# with try() and a default value
h <- function(val) {
  result <- NA
  try(result <- log10(val))
  result
}

h(3) # works as before
#> [1] 0.4771213

h("3") # returns a default value plus the error message
Error in log10(val) : non-numeric argument to mathematical function
#> [1] NA
```

## [`warning()`][ref-warning] et [`message()`][ref-message]

Ce sont des réponses à des conditions non fatales, par exemple :

- Pour avertir d'un problème dont le programme peut au moins partiellement se remettre.
- Pour informer l'utilisateur de la progression d'un programme de longue durée.

Une différence entre les deux est que les avertissements sont mis en cache et (par défaut) affichés au retour de la fonction, alors que les messages sont affichés immédiatement.
Il existe de nombreuses façons de modifier ce comportement par défaut, qui dépassent le cadre de cette page.

```R
w <- function() {
  warning("something strange happened")
  -1
}

w()
#> [1] -1
#> Warning message:
#> In w() : something strange happened

# if warnings are not wanted
suppressWarnings(w())
#> [1] -1
```

La fonction [`suppressWarnings()`][ref-warning] peut parfois être utile dans Exercism, pour éviter de perturber l'exécuteur de tests avec des sorties indésirables.

## Gestionnaires de conditions

R propose une autre façon de gérer les états d'erreur, plus proche dans l'esprit de l'approche de Java et des langages apparentés.

Les détails dépassent le cadre de ce concept, mais les personnes intéressées pourront se tourner vers [`tryCatch`][ref-conditions] et [`withCallingHandlers`][ref-conditions].

On trouvera une bonne discussion dans la [section 8.4][book-handling] d'Advanced R.

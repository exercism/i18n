# À propos

La mémoire d'un programme est généralement organisée par le système d'exploitation (OS) selon une disposition d'ensemble :

| adresse | région mémoire          |
| :-----: | :--------------------- |
|  haute  | pile                   |
|         | ...                    |
|         | tas                    |
|         | segment lecture-écriture |
|         | segment code/lecture seule |
|  basse  | réservée               |

La mémoire, découpée en segments, s'organise en sections dotées de permissions différentes.

Les fonctions que nous avons définies jusqu'ici se trouvaient toutes dans la **section .text**.
Cette section contient des données exécutables en lecture seule.
D'autres sections servent à déclarer des variables, qui peuvent être en lecture seule ou en lecture-écriture, mais qui ne sont pas exécutables.

## La section .data

Les données initialisées se déclarent dans la **[section .data][data]**.

Dans NASM (The Netwide Assembler, l'assembleur utilisé dans ce parcours), une variable initialisée possède un nom, une directive qui indique la taille des données, et une liste de valeurs séparées par des virgules.
Chacun de ces éléments est séparé du suivant par un espace, et l'étiquette peut éventuellement être suivie d'un `:`.

Les principales directives et les tailles de données associées sont :

| directive | taille  |
| :-------: | :------ |
|    db     | 1 octet  |
|    dw     | 2 octets |
|    dd     | 4 octets |
|    dq     | 8 octets |

Par exemple, ceci déclare une variable d'un octet nommée `space` avec la valeur `10` :

```x86asm
section .data
    space db 10
```

Les variables déclarées dans `section .data` sont mutables, c'est-à-dire qu'elles sont en lecture-écriture.
Elles ont aussi une durée de stockage _statique_, ce qui signifie qu'elles existent pendant toute la durée d'exécution du programme.

## La section .rodata

La **section .rodata** est semblable à `section .data`.
Les deux sections contiennent des données initialisées, déclarées de la même manière et ayant la même durée de stockage.

Leur principale différence est que les données de `section .rodata` sont immuables, c'est-à-dire en lecture seule.

~~~~exercism/note
Les constantes définies avec `equ` sont différentes de celles définies dans `section .rodata`.

Une constante définie avec `equ` n'occupe pas d'espace en mémoire et est directement remplacée par sa valeur par l'assembleur.
C'est en fait un simple espace réservé pour cette valeur.

En revanche, les constantes définies dans `section .rodata` sont réellement stockées en mémoire et possèdent une adresse.
~~~~

## Accéder aux données

### Étiquettes et indirection

Les données déclarées doivent avoir un nom qui leur est associé.
Ce nom s'appelle une **étiquette**.

Une étiquette est un symbole qui encode l'adresse précise d'une donnée en mémoire.
**Les adresses en x86-64 sont des valeurs de 64 bits**.
Une valeur qui contient une telle adresse, qu'elle soit conservée dans un registre ou stockée en mémoire, est ce que les langages de haut niveau appellent un **[pointeur][pointer]**.

Dans NASM, essayer d'accéder directement à une donnée par son étiquette ne renvoie pas la mémoire allouée, mais son adresse :

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

Pour accéder au contenu d'une adresse mémoire, il faut la _déréférencer_.
C'est ce qu'on appelle l'**indirection**.

Dans NASM, on utilise pour cela `[]` :

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

Cependant, dans certaines situations, la taille de la mémoire déréférencée peut prêter à ambiguïté.
Dans ces cas-là, il faut utiliser un préfixe qui précise cette taille.

Voici les préfixes les plus importants et leur taille dans un programme x86-64 classique :

| préfixe | taille  |
| :----- | :------ |
| byte   | 1 octet  |
| word   | 2 octets |
| dword  | 4 octets |
| qword  | 8 octets |

Le même chargement peut s'écrire avec la taille indiquée explicitement :

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

C'est une bonne pratique d'utiliser toujours un préfixe lorsqu'on déréférence de la mémoire.

### Écrire en mémoire

L'écriture en mémoire se fait de la même manière, en déréférençant une adresse :

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

À noter que tu peux utiliser des opérandes mémoire dans la plupart des instructions sans d'abord charger leur contenu dans un registre.
Cependant, il n'est généralement pas possible de les utiliser à la fois comme opérande source et comme opérande destination, mais seulement comme l'un des deux :

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### L'instruction LEA

Bien qu'une instruction `mov` puisse servir à stocker l'adresse d'une variable dans un registre, il existe une instruction dédiée à cet usage : **[lea][lea]**.

Cette instruction utilise un opérande de forme mémoire, mais elle ne lit _pas_ la mémoire.
À la place, elle calcule l'expression d'adresse effective et écrit le résultat dans l'opérande destination :

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

Il est plus idiomatique d'utiliser `lea` pour calculer et stocker des adresses mémoire dans des registres.

### Adressage relatif

Lorsqu'on accède à des emplacements mémoire, le comportement par défaut de NASM est de générer des **adresses absolues**, c'est-à-dire des adresses mémoire fixes.

Pour des raisons de sécurité, les exécutables sont souvent construits en **PIE (Position Independent Executable)**, où les régions mémoire sont placées à des emplacements aléatoires.
Dans un `PIE`, l'adresse finale d'une variable n'est pas connue au moment de l'édition des liens.
Le code calcule donc plutôt les adresses comme un décalage par rapport à la valeur d'un registre spécial appelé `rip`, qui pointe vers la prochaine instruction à exécuter.

C'est ce qu'on appelle généralement l'**adressage relatif à RIP**.

Dans NASM, tu peux demander un accès relatif à RIP avec l'**[opérateur rel][rel]** :

```x86asm
mov rax, qword [rel variable]
```

On peut aussi faire de l'adressage relatif la valeur par défaut d'un fichier source, en plaçant `default rel` en haut.

Tous les exercices de ce parcours sont compilés et liés en `PIE`, donc `rel` doit être utilisé pour générer des adresses relatives.

La disposition aléatoire mentionnée ci-dessus est une contre-mesure connue sous le nom de randomisation de l'espace d'adressage.
En rendant imprévisible la base de chaque région mémoire, elle prive un attaquant des adresses fixes sur lesquelles reposent de nombreuses techniques d'exploitation, et c'est `PIE` qui permet au chargeur de placer ces régions n'importe où.

Pour cette raison, l'adressage absolu n'est pas simplement déconseillé dans ce parcours : il est inutilisable.
Une référence absolue comme `[abs variable]` demande à l'assembleur d'intégrer une adresse fixe de 32 bits dans l'instruction.
Sur Linux, l'éditeur de liens `PIE` rejette la relocalisation que cela produit, et sur macOS, le format `macho64` ne prend pas du tout en charge les adresses absolues de 32 bits, si bien que le fichier ne s'assemble pas.

L'adressage relatif à RIP évite ces deux problèmes, puisque l'instruction n'encode qu'un décalage par rapport à `rip` et jamais une adresse fixe.
La façon idiomatique de placer une adresse dans un registre avec `PIE` est donc `lea` avec un opérande `rel` :

```x86asm
default rel

section .data
    variable dq 7

section .text
fn:
    lea rax, [rel variable]       ; materialize the address (PIE-safe)
    mov rcx, qword [rel variable] ; load the value through a RIP-relative access
    ...
```

### Visibilité

Les étiquettes (fonctions et données) définies dans une section quelconque (par exemple `.text`, `.data`, `.rodata`) sont visibles au sein du même fichier source.
Si elles sont déclarées `global`, elles sont aussi visibles depuis d'autres fichiers source.

À l'inverse, les étiquettes définies dans d'autres fichiers source sont visibles depuis le fichier source courant si elles sont déclarées `extern`.
Dans ce cas, aucune indication de taille n'existe en assembleur, il faut donc la connaître à l'avance.

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

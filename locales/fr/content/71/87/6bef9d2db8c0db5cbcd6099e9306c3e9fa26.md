# À propos

## Types composites

Il est souvent utile de définir ses propres types dans nos programmes.

Il est possible de créer de nouveaux types primitifs, mais on le fait rarement.
Les [types primitifs][primitive] intégrés ne relèvent pas d'un choix arbitraire : ils correspondent de près aux types standard du compilateur LLVM que Julia utilise pour la compilation à la volée (JIT).

Bien plus utile, la possibilité de définir des [types composites][composite-types], dotés de champs nommés.

D'autres langages ont quelque chose de semblable, qu'ils appellent `structs` ou `records`.
La documentation de Julia les nomme des `composite types`, bien que (léger décalage) la syntaxe du langage les définisse avec le mot-clé `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Quelques points méritent d'être relevés dans l'exemple ci-dessus :

- Aucun type n'est spécifié pour `id`, le compilateur l'interprète donc comme `id::Any`.
  - **Note :** en pratique, il vaut mieux aider le compilateur en précisant le type d'un champ par un type concret.
  - On verra dans un [futur concept][parametric] que l'utilisation de paramètres est une autre option.
- Le nom du type sert de constructeur, comme dans `Person(id, name, age)`, pour donner une instance de type `Person`.
- On peut accéder aux champs individuellement avec la notation pointée, comme pour les [tuples nommés][named-tuple].

Les éléments de type `Person` sont immuables, les mises à jour ne sont donc pas autorisées.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Si la mutabilité est nécessaire, ajoute `mutable` à la définition.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Par défaut, le constructeur exige que les champs apparaissent dans le même ordre que la définition, ce qui devient peu pratique pour des types plus compliqués.

L'utilisation de la macro `@kwdef` apporte deux nouvelles possibilités :

- Le constructeur utilise des mots-clés, pas la position.
- Les champs peuvent avoir des valeurs par défaut et, éventuellement, être omis du constructeur.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hiérarchies de types composites

Jusqu'ici, on n'a créé que des types composites concrets.
Si tu vérifies, tous sont des sous-types de `Any`.

Quand on crée plusieurs types apparentés, il est probablement plus judicieux de définir une hiérarchie pour eux.
C'est très simple à faire.

D'abord, crée un type abstrait :

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Ensuite, inclus un opérateur `<:` dans une définition de type, pour montrer la relation.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Répète autant que nécessaire, en te rappelant que le sous-typage de types concrets n'est pas autorisé.

Pour une hiérarchie plus complexe, crée des sous-types abstraits selon les besoins.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

L'intérêt d'une telle hiérarchie apparaîtra plus clairement quand on arrivera au concept `Multiple Dispatch`, et qu'on verra comment les fonctions traitent le type de leurs arguments.


## Constructeurs internes

On a vu au début de ce concept que le nom du type sert de constructeur, pour créer des éléments de ce type :

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

Ici, `Person()` est appelé un `outer constructor`.
Les types des champs sont vérifiés pour leur compatibilité avec la définition du type, et une erreur est levée si nécessaire.

Supposons que l'on veuille des contraintes sur les _valeurs_ transmises, et pas seulement sur les _types_ ?

On peut alors inclure un `inner constructor` dans la définition du type, pour effectuer les vérifications appropriées.

Par exemple, on a un type abstrait `AbstractPoint`, destiné à prendre des coordonnées `(x, y)`, mais on veut un sous-type avec la contrainte `y > x`.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

La fonction `new()` ne peut être utilisée _que_ dans les constructeurs internes, et renvoie l'élément souhaité si les entrées s'avèrent valides.

Pour une entrée invalide, on peut s'arrêter avec un message d'erreur, comme dans l'exemple.
Sinon, tu préféreras peut-être utiliser une valeur fictive comme `nothing` ou `missing`.
Consulte le concept [`Nothingness`][nothingness] pour en savoir plus.

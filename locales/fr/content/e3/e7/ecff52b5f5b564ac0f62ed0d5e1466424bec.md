# Introduction

Il est souvent utile de définir des types personnalisés dans nos programmes.

Créer de nouveaux types primitifs est possible, mais rarement fait.
Les types primitifs intégrés ne relèvent pas d'un choix arbitraire : ils correspondent de près aux types standard du compilateur LLVM qu'utilise Julia pour la compilation JIT.

Bien plus utile est la possibilité de définir des types composites, avec des champs nommés.

D'autres langages ont quelque chose de similaire, qu'ils appellent `structs` ou `records`.
La documentation de Julia les appelle `composite types`, même si (avec un léger décalage) la syntaxe du langage les définit avec le mot-clé `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Quelques points méritent d'être notés dans l'exemple ci-dessus :

- Aucun type n'est spécifié pour `id`, le compilateur l'interprète donc comme `id::Any`.
  - En pratique, il vaut mieux aider le compilateur en spécifiant le type d'un champ avec un type concret
- Le nom du type sert de constructeur, comme dans `Person(id, name, age)`, pour donner une instance de type `Person`.
- On peut accéder à chaque champ avec la notation pointée, comme pour les tuples nommés.

Les objets de type `Person` sont immuables, les mises à jour ne sont donc pas autorisées.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Si la mutabilité est nécessaire, ajoute `mutable` à la définition.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Par défaut, le constructeur exige que les champs apparaissent dans le même ordre que la définition, ce qui devient peu pratique pour des types plus compliqués.

Utiliser la macro `@kwdef` apporte deux nouvelles possibilités :

- Le constructeur utilise des mots-clés, et non la position.
- Les champs peuvent avoir des valeurs par défaut et, éventuellement, être omis du constructeur.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hiérarchies de types composites

Jusqu'ici, on n'a créé que des types composites concrets.
Si tu vérifies, tous sont des sous-types de `Any`.

Quand on crée plusieurs types liés, il est probablement plus judicieux de leur définir une hiérarchie.
C'est très facile à faire.

D'abord, on crée un type abstrait :

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Ensuite, on inclut un opérateur `<:` dans une définition de type, pour montrer la relation.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Répète autant que nécessaire, en gardant à l'esprit que le sous-typage de types concrets n'est pas autorisé.

Pour une hiérarchie plus complexe, crée des sous-types abstraits selon les besoins.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

L'intérêt d'une telle hiérarchie deviendra plus clair quand on abordera le concept `Multiple Dispatch` et qu'on verra comment les fonctions gèrent les types d'arguments.

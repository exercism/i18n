# Implémente l'outillage

Après avoir lancé le parcours avec les 20 premiers exercices ou plus et un exécuteur de tests, l'attention doit se porter sur la mise en place de [l'outillage de parcours supplémentaire](/docs/building/tooling).

Il existe deux types d'outillage de parcours :

- Production : apporter un élément essentiel à l'expérience d'apprentissage de ce langage
- Maintenance : faciliter la maintenance du parcours

## Outillage de production

Il existe (pour l'instant) trois outils de production :

- **[Exécuteurs de tests](/docs/building/tooling/test-runners)** : exécutent les tests d'un exercice sur le code d'un apprenant. (obligatoire)
- **[Representers](/docs/building/tooling/representers)** : créent une représentation normalisée d'une solution. (facultatif)
- **[Analyseurs](/docs/building/tooling/analyzers)** : évaluent automatiquement les soumissions des apprenants et fournissent des commentaires dans le style d'un mentor. (facultatif)

## Outillage de maintenance

Pour faciliter la maintenance du parcours, on peut également construire :

- **[Générateurs de tests](/docs/building/tooling/test-generators)** : génèrent ou mettent à jour automatiquement les tests d'un exercice et l'interface de code de l'apprenant. (facultatif)

## Quel outil implémenter ?

Les outils de production sont plus importants que les outils de maintenance.
À ce stade, tu devrais avoir mis en place un exécuteur de tests (sinon, consulte la documentation [Construis un exécuteur de tests](/docs/building/tracks/new/build-test-runner)).

Maintenant que l'exécuteur de tests est en place, le prochain outil sur lequel travailler est le Representer.
Les objectifs du Representer et de l'analyseur se recoupent en partie, mais on te recommande de commencer par le Representer, pour les raisons suivantes :

- les Representers sont généralement (bien) plus faciles à implémenter
- les Representers peuvent avoir un impact bien plus important que les analyseurs sur la charge de mentorat, en donnant davantage de moyens aux mentors
- les Representers s'appliquent à tous les exercices, alors que les analyseurs ne ciblent généralement que certains exercices ou un sous-ensemble

Pour te lancer dans la création d'un Representer, consulte le document [Crée un Representer à partir de zéro](/docs/building/tooling/representers/creating-from-scratch).

Enfin, une fois le Representer en place, le dernier outil à construire est l'analyseur.
Pour te lancer dans la création d'un analyseur, consulte le document [Crée un analyseur à partir de zéro](/docs/building/tooling/analyzers/creating-from-scratch).

À ce stade, il est probablement temps de se recentrer sur l'ajout de nouveaux exercices.
Pour ajouter des exercices plus rapidement, envisage de construire un [générateur de tests](/docs/building/tooling/test-generators).

## Implémentation

L'outillage d'un parcours est généralement (en grande partie) écrit dans le langage du parcours.

```exercism/caution
Bien que tu sois libre d'utiliser d'autres langages, chaque langage supplémentaire rendra la maintenance du parcours plus difficile, tout comme la contribution à celui-ci.
C'est pourquoi on te recommande d'utiliser le langage du parcours quand c'est possible, car cela facilite la maintenance et la contribution.
```

## Déploiement

Les outils de production sont empaquetés et exécutés dans un [conteneur Docker](/docs/building/tooling/docker).
Les images Docker de l'outillage sont déployées automatiquement à l'aide d'un [workflow GitHub Actions](https://github.com/exercism/generic-test-runner/blob/main/.github/workflows/docker.yml).

Les outils de maintenance ne sont _pas_ déployés.

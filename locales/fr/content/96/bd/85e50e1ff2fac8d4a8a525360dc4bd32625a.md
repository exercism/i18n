# Introduction

Dans un monde idéal, on pourrait compter sur le fait que tout soit bien défini, avec des valeurs concrètes et sans lacunes.

Cela contredit notre expérience quotidienne, et c'est pourquoi beaucoup de langages de programmation ont un moyen de représenter l'absence de valeur : null ou NULL, nil, None, nothing...

C'était facile à introduire (en 1965), mais cela n'a pas tardé à susciter des regrets.
Son inventeur l'a par la suite qualifié de « Billion Dollar Mistake ».

Au cours des dernières décennies, les concepteurs de langages ont exploré de nombreuses façons de rendre les valeurs nulles disponibles mais (le plus souvent) sûres.

Kotlin repose sur quelques [principes généraux][ref-null-safety], qui diffèrent nettement de ceux de Java.


- Kotlin possède une valeur `null` spéciale.
- Tous les types sont _par défaut_ non nullables.
- La plupart des types peuvent être _rendus_ nullables, mais le programmeur doit le demander explicitement.
- Les fonctions susceptibles d'échouer avec une exception ont souvent une variante dont la valeur de retour est nullable.
- Une syntaxe spéciale et très concise cherche à rendre aussi simple que possible le test et la gestion des valeurs nulles.

## Crée des variables nullables

Les types standard ont généralement un équivalent nullable, avec un suffixe `?` : par exemple `String?` au lieu de `String`.

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Opérateurs et fonctions utiles

### L'opérateur d'appel sécurisé `?.`

Pour une `String` non nullable, on peut obtenir la propriété `.length`.

Une `String?` nullable échoue avec la même syntaxe, mais utiliser `?.length` permet d'envisager la possibilité d'un `null`.
Le type de retour est `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Comme on l'a vu à la dernière ligne ci-dessus, `?.` fonctionne aussi avec les types non nullables.

### L'opérateur Elvis `?:`

Prolongeant l'idée de l'opérateur d'appel sécurisé, l'[opérateur Elvis][wiki-elvis] permet de fournir une valeur par défaut pour remplacer `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### L'opérateur d'assertion non null `!!`

Avec cet opérateur, un type nullable est forcé d'être traité comme non null, quand le programmeur en est convaincu.
Peut-être comprenons-nous parfois mieux la logique du programme qu'un compilateur trop prudent ?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

La responsabilité nous incombe désormais : si `b` est encore `null`, on obtient une `NullPointerException`.

### La fonction let `?.let`

Si l'on passe un élément nullable à un bloc de code, on pourrait faire des vérifications de null explicites : `if (item != null) { do something }`.

Il est plus simple et plus idiomatique d'utiliser `item?.let { do something }`, le `do something` ne s'exécutant que lorsque `item` n'est pas null.

### Les fonctions du type `somethingOrNone()`

Certaines fonctions peuvent échouer, par exemple lorsqu'on demande un indice invalide dans une _string_ ou dans un tableau.

Plutôt que de lever une exception, on peut utiliser la variante `...OrNull` de la fonction, pour obtenir (dans ce cas) une valeur de retour `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

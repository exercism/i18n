# À propos

Les programmeurs essaient généralement d'écrire un logiciel parfait, et généralement ils échouent.

Les choses tournent mal, de façon inattendue, et il faut pouvoir y faire face.

Certains concepteurs de langages estiment que la priorité est de détecter une erreur le plus rapidement possible, puis de terminer l'exécution avec un message informatif pour faciliter le débogage.

Les langages de science des données ont tendance à adopter une approche plus nuancée.
Certaines erreurs sont si graves qu'un arrêt immédiat est nécessaire, mais il est souvent préférable de signaler un problème comme quelque chose à traiter plus tard, puis de poursuivre l'exécution.

On a vu dans le concept [Néant][nothingness] que Julia fournit divers espaces réservés pour les valeurs problématiques : [`missing`][nothing], [`NaN`][NaN] et `Inf`.
Savoir si ces solutions sont préférables à l'arrêt du programme dans une situation donnée relève du jugement du programmeur.

_Un point de nomenclature_ avant d'entrer dans les détails : la documentation de Julia traite les mots « _error_ » et « _exception_ » comme largement interchangeables.
Le contenu ci-dessous n'est peut-être pas plus cohérent.

## Les types d'erreur standards

À ce stade du programme, tu as forcément vu de nombreux messages d'erreur de Julia.
Par exemple :

```julia-repl
julia> Int(3.14)
ERROR: InexactError: Int64(3.14)
```

Essayer de convertir un nombre décimal en entier entraîne une perte de précision, ce qui produit une `InexactError`.

`InexactError` est un type, l'un des nombreux ([actuellement 25][errors]) intégrés en standard dans Julia.
Tous sont des sous-types de `Exception` :

```julia-repl
julia> supertype(InexactError)
Exception
```

## `throw()`

Certains des types d'erreur standards peuvent être utiles à générer dans ton propre code.

Comme tous les types concrets, les erreurs ont des constructeurs.
Ils prennent des arguments variés, alors consulte la [documentation][errors] pour celui que tu veux utiliser.

```julia-repl
julia> DomainError(42, "out of range")
DomainError(42, "out of range")
```

Pour utiliser l'erreur, il faut envelopper le constructeur dans une fonction [`throw()`][throw] :

```julia-repl
julia> throw(DomainError(42, "out of range"))
ERROR: DomainError with 42:
out of range
```

## `error()`

Pour une solution rapide et sommaire, la fonction [`error()`][error] peut être pratique.
Elle prend une _string_ (ou les composants d'une _string_) comme argument :

```julia-repl
julia> happy = false;
julia> happy || error("😞 something went wrong")
ERROR: 😞 something went wrong
```

## Les erreurs personnalisées

Créer de nouveaux types d'erreur est en principe très facile.
Il suffit d'ajouter un autre sous-type de `Exception` :

```julia-repl
julia> struct MyError <: Exception end

julia> throw(MyError)
ERROR: MyError
```

Cependant, l'exemple ci-dessus n'a pas de champs et le constructeur ne prend aucun argument, donc on n'a aucun contrôle sur le message d'erreur.
On peut ajouter un champ pour le message :

```julia-repl
julia> struct AnotherError <: Exception
           msg::String
       end

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError("Wrong!")
```

Afficher simplement le constructeur ne suffit pas tout à fait.
Compare avec l'exemple précédent où on lançait une `DomainError`.

Pour qu'une erreur personnalisée soit gérée de la même manière que les erreurs intégrées, il faut ajouter une méthode [`showerror()`][showerror] :

```julia-repl
julia> Base.showerror(io::IO, e::AnotherError) =
           print(io, "AnotherError: ", e.msg)

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError: Wrong!
```

Cette fonctionnalité assez mal documentée raccorde en substance notre type d'erreur personnalisé au système de gestion des erreurs standard de Julia.

## Les assertions

L'idée de base d'une assertion, c'est « cette assertion devrait être vraie, alors signale-le bruyamment si elle est fausse ».
L'intérêt est principalement lors du débogage, car du code de production ne devrait jamais échouer à une assertion.

On a vu dans le concept [Types][types] qu'on peut ajouter des assertions de type, par exemple pour vérifier le type de retour d'une fonction.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Plus généralement, la macro [`@assert`][assert] permet de tester toute expression qui s'évalue à un booléen :

```julia-repl
julia> n = 22;
julia> @assert isodd(n) "n must be odd"
ERROR: AssertionError: n must be odd
```

## `try`...`catch`

Certaines erreurs sont nécessairement fatales, mais on attend souvent du programme qu'il s'en remette élégamment.

Par défaut, une erreur termine immédiatement la fonction en cours, et l'erreur (avec son éventuel message informatif) est transmise à la fonction appelante.

Cela remonte toute la pile d'appels, jusqu'à ce que le code de plus haut niveau se termine avec un message d'erreur.

À n'importe quelle étape, l'erreur peut être interceptée par un bloc [`try...catch`][try-catch] qui tente de la gérer.

```julia-repl
julia> n = -1;
julia> try
           log_n = log(n)
       catch problem
           if problem isa DomainError # number out of range
               # See next section for more on @warn and @info
               @warn "you may have supplied a negative real number: $n"
               @info "trying with complex argument"
               log_n = log(Complex(n))  # fallback calculation

           elseif problem isa MethodError # no idea what n is
               @error "please supply a valid argument"
 
           else
              rethrow() # the error could be anything else
           end
      end
┌ Warning: you may have supplied a negative real number: -1
└ @ Main REPL[3]:5
[ Info: trying with complex argument
0.0 + 3.141592653589793im  # success
```

Dans l'exemple ci-dessus, `log(n)` a besoin que `n` soit une valeur réelle positive, ou une valeur complexe quelconque.
Le `try ... catch` intercepte les problèmes liés aux valeurs réelles négatives, et renvoie la bonne réponse complexe `iπ` en notation mathématique.

Si tu fournis, par exemple, un argument de type _string_, il n'y a pas de recours possible à part demander à l'utilisateur de le corriger.

Comme dernier recours général, on a ajouté [`rethrow()`][rethrow] pour tout ce qui n'est ni une `DomainError` ni une `MethodError`.

Il existe aussi d'autres clauses optionnelles :

- [`else`][else], qui est exécutée si la clause `try` réussit ;
- [`finally`][finally], qui peut servir à nettoyer des ressources externes, que le `try` réussisse ou échoue : fermer des fichiers, libérer des connexions à une base de données...

***Remarque :*** Parfois, un `try...catch` est ce qu'il te faut, mais évite de trop l'utiliser.
Si un bloc `if...else` peut le remplacer, il sera bien plus performant que d'intercepter des exceptions.

## La journalisation

Remarque : la fonction `error()`, dont on a parlé plus haut, ne doit pas être confondue avec la macro [`@error`][error_macro].

La fonction génère une exception, qui remontera la pile d'appels à moins d'être interceptée.

La macro `@error`, tout comme ses homologues [`@debug`][debug_macro], [`@info`][info_macro] et [`@warn`][warn_macro], fait partie du module [`Logging`][logging], et vise à générer des messages informatifs sans altérer le déroulement du programme.

La sortie va vers le terminal par défaut (avec un code couleur selon la gravité), même si dans une vraie application il existe bien d'autres possibilités.

```julia-repl
julia> @warn "Something looks not quite right"
┌ Warning: Something looks not quite right
└ @ Main REPL[55]:1

julia> @error "Panic!"
┌ Error: Panic!
└ @ Main REPL[56]:1
```

Voir aussi l'exemple précédent, dans la section `try...catch`.

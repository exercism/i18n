# Spécification Markdown

Voici comment tous les fichiers Markdown d'Exercism doivent être structurés.

Certaines règles de ce document ne sont pas encore appliquées partout sur Exercism.
Les PR pour les corriger sont les bienvenues.
Toutes les règles sont ajoutées à nos outils d'intégration continue et de _linting_, et doivent être respectées pour les nouvelles modifications.

## Titres

- Tous les fichiers doivent commencer par un titre de niveau 1 (`# Some heading text`).
- Les titres de niveau 1 servent uniquement à l'affichage sur GitHub ou équivalent.
- Si le fichier est rendu par Exercism (par exemple affiché sur le site, rendu via la CLI), ce titre est supprimé et un titre contextuel est inséré.
- Aucun titre ne peut descendre de plus d'un niveau sous le précédent (par exemple `##` ne peut être suivi que de `###`, pas de `####`).
- Au-delà du seul titre de niveau 1 (`#`), seuls les titres de niveau 2 (`##`), de niveau 3 (`###`) et de niveau 4 (`####`) peuvent être utilisés.

## Liens

Utilise les [liens de référence][reference-links], qui sont définis en bas du fichier Markdown, associés à un identifiant de référence, puis référencés par cet identifiant dans le texte.

Cette méthode facilite la maintenance, car le ou les liens ne doivent être mis à jour qu'à un seul endroit.

Exemple :

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

Les liens doivent toujours avoir un texte d'ancrage, plutôt que d'insérer l'URL elle-même dans le texte. Par exemple, ce qui suit n'utilise pas de texte d'ancrage et est plus difficile à lire.

```
If you want some more information, please visit https://google.com.
```

Utiliser un texte d'ancrage et le lier est plus facile à comprendre et à replacer dans son contexte.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

Ce qui s'affiche comme « Si tu veux plus d'informations, [Google][google-link] est une ressource utile. »

## Code

Chaque fois que l'on fait référence à des éléments de code (par exemple des fonctions ou des mots-clés), le code doit être entouré de _backticks_ :

```
- The `printf()` function writes to the console.
```

Ce qui s'affiche comme :

- La fonction `printf()` écrit dans la console.

Le code plus complexe (par exemple du code sur plusieurs lignes) doit être entouré de triples _backticks_. Un [identifiant de langage][language-identifier] doit être spécifié après les triples _backticks_ d'ouverture pour activer la coloration syntaxique :

````python
```python
# Define a variable
album = "Abbey Road"
```
````

Dans la mesure du possible, formate le code d'une manière qui corresponde le mieux à l'environnement dans lequel il est présenté. Si elles sont disponibles, consulte la documentation de ton langage.

Par exemple, Python dispose du REPL (_read-eval-print loop_, la boucle lecture-évaluation-affichage), qui permet à un programmeur de saisir du code directement dans un terminal. Si une personne débogue du code, ou exécute une fonction localement pour tester ou observer son fonctionnement, elle aura plus tendance à passer par le REPL, car il est plus pratique d'y saisir du code de façon interactive. Dans cette situation, nous préférons formater le code d'exemple comme s'il était saisi dans le REPL, avec un `>>>` au début :

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

Dans d'autres cas, il est plus judicieux de laisser le code formaté comme s'il se trouvait dans un fichier `.py`. Ici, l'apprenant profite d'un rendu qui imite la façon dont il écrirait lui-même le code.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

Un moyen rapide de distinguer les deux cas quand on hésite : si c'est du code que l'apprenant peut exécuter dans un terminal, formate-le ainsi. Si c'est du code qu'Exercism pourrait exécuter (dans les tests, le code de bibliothèque que l'apprenant écrira, etc.), privilégie un formatage de code exécutable.

## Blocs spéciaux (parfois appelés _admonitions_)

Nous prenons en charge des types de blocs spéciaux que l'on peut ajouter aux documents pour mettre en avant un commentaire qui ne s'intègre pas au corps du texte.

<img width="500" alt="Bloc de note Markdown" src="https://user-images.githubusercontent.com/20866761/139531109-0c0f3ea5-b589-44ff-93ab-d901a45edc56.png">

<img width="500" alt="Bloc d'avertissement Markdown" src="https://user-images.githubusercontent.com/20866761/139531234-9b58b9ab-524b-44fd-bbcb-4e10f2927d27.png">

<img width="500" alt="Bloc avancé Markdown" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

Nous prenons en charge trois types de blocs :

- **exercism/note :** des blocs qui mettent en avant une information supplémentaire particulière
- **exercism/caution :** des éléments que les gens doivent connaître ou aborder avec prudence
- **exercism/advanced :** des informations qui ne concernent que les personnes qui veulent approfondir un sujet ou dont on attend des connaissances plus avancées.

Tous les blocs s'écrivent avec 4 tildes, sous la forme :

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(Remarque : tu peux aussi utiliser des _backticks_ ou d'autres niveaux de tildes dans des circonstances exceptionnelles)

## Disposition

### Une phrase par ligne

Les paragraphes doivent être disposés avec une phrase par ligne. La [documentation d'AsciiDoctor][asciidoctor] explique clairement la logique de cette approche.

Par exemple, un paragraphe unique doit être disposé comme suit :

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## Listes

Utilise le tiret (`-`) comme marqueur de liste à puces pour les listes non ordonnées.

## Commentaires

- Préfère les commentaires Markdown aux commentaires HTML (par exemple utilise `[comment]: # (Actual comment...)` plutôt que `<!-- Actual comment -->`

Tu peux vérifier que ton commentaire Markdown est bien supprimé en regardant à quoi il ressemble une fois rendu via commonmark sur [babelmark3].

## HTML en ligne

- Le HTML en ligne est autorisé, mais doit être utilisé avec parcimonie
- Utilise toujours les alternatives Markdown natives lorsqu'elles existent (par exemple utilise `# ...` plutôt que `<h1>...</h1>`)

## Images

Comme le site prend en charge les thèmes clair et sombre, les images soumises par la communauté doivent s'afficher correctement dans les deux thèmes.
La solution consiste à ajouter un suffixe au nom de ton image (avant l'extension du fichier) :

1. Fais en sorte que le nom de l'image se termine par `-invertible` (par exemple `graph-invertible.svg`). L'image sera automatiquement inversée lorsqu'elle est affichée dans le thème sombre (via `filter: invert(100%)`).
1. Fais en sorte que le nom de l'image se termine par `-light` (par exemple `graph-light.png`) et crée aussi une version compatible avec le thème sombre qui se termine par `-dark` (soit `graph-dark.png`). Nous afficherons automatiquement la bonne image selon le thème de la personne.

Les images sans aucun de ces suffixes seront utilisées sans modification dans les deux thèmes.
Cela signifie que si tu veux créer des images en niveaux de gris, tu peux généralement les rendre belles sur le thème clair, puis les définir comme inversibles.
Mais si tu utilises une image avec beaucoup de couleurs, tu préféreras peut-être en faire deux variantes.

Le nom complet de l'image (y compris `-invertible`) doit être indiqué dans le Markdown à l'endroit où l'image est affichée.
Pour les versions clair/sombre, n'inclus **UNIQUEMENT** la variante `-light`.
Cette logique est respectée dans tous les documents Markdown.

## Formatage automatique

Certains dépôts utilisent [prettier][prettier] pour garantir que tout le Markdown est formaté de manière cohérente. Cela peut apporter les avantages suivants :

- Pas de discussions sur le formatage.
- Une excellente intégration aux éditeurs et IDE, pour que les fichiers soient formatés à l'enregistrement.
- Des vérifications de formatage faciles à ajouter à l'intégration continue.
- Un formatage automatique des fichiers facile à mettre en place avec un script.

Tout ce qui précède aide grandement à réduire le bruit dans les revues, ce qui est frustrant aussi bien pour la personne qui relit que pour celle qui est relue.

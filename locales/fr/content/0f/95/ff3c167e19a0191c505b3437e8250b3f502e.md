# À propos

Les exceptions sont une forme de gestion des erreurs.
On les appelle exceptions parce qu'elles apparaissent généralement lorsqu'on est confronté à un événement inattendu.

À n'importe quel endroit de notre code, on peut « lever » une exception.
On utilise pour cela la méthode `raise`, en lui passant un objet, normalement un objet Exception, mais on peut aussi utiliser de simples _strings_.
Par exemple, tu verras dans les squelettes d'exercice qu'on utilise le `RuntimeError` intégré pour indiquer à Ruby qu'une méthode n'a pas été implémentée.
Tu peux aussi utiliser la syntaxe abrégée `raise(ExceptionObject, params)`.
Si la classe d'exception est omise, `RuntimeError` est utilisée par défaut.

Par exemple :

```ruby
# These are equivalent
raise RuntimeError.new("Please implement this method")
raise RuntimeError, "Please implement this method"
raise "Please implement this method"
```

Quand Ruby voit cela, il fait remonter l'erreur jusqu'au sommet du programme, puis s'arrête.

Par exemple, si tu essaies de diviser quelque chose par zéro, tu verras quelque chose comme ceci :

```ruby
5/0

#=> Traceback (most recent call last):
#=> ...
#=> ZeroDivisionError (divided by 0)
```

Il est important de noter qu'on doit réserver les exceptions aux cas où quelque chose d'exceptionnel se produit, une erreur qui demande un traitement particulier.
On ne doit pas utiliser les exceptions pour le flux de contrôle d'un programme, car c'est considéré comme une mauvaise conception, qui mène souvent à de mauvaises performances et à une mauvaise maintenabilité.

## Hiérarchie des classes

En Ruby, les exceptions suivent une hiérarchie de classes dont `Exception` est la classe de base.
Voici les exceptions intégrées de Ruby les plus courantes :

```
Exception
  NoMemoryError
  ScriptError
    LoadError
    NotImplementedError
    SyntaxError
  SignalException
    Interrupt
  StandardError
    ArgumentError
    IOError
    EOFError
    IndexError
    LocalJumpError
    NameError
      NoMethodError
    RangeError
      FloatDomainError
    RegexpError
    RuntimeError
    SecurityError
    SystemCallError
    SystemStackError
    ThreadError
    TypeError
    ZeroDivisionError
  SystemExit
```

Intercepter les erreurs d'une classe donnée intercepte aussi les erreurs de ses classes filles.
C'est pourquoi intercepter `Exception` peut être dangereux.
Ruby utilise aussi les exceptions pour gérer les « signaux » du système d'exploitation, par exemple `ctrl-c`.
Cela signifie qu'intercepter `Exception` capturera aussi ces « signaux » système.
Donc, pour éviter des comportements inattendus, la pratique courante pour intercepter « toutes les erreurs » consiste à intercepter `StandardError`.

## Syntaxe de rescue
Ruby propose aussi des clauses rescue étendues pour les situations qui demandent un traitement particulier :

```ruby
begin
  # ...
rescue CustomError => error
  # This block is run if a CustomError occurs
rescue AnotherCustomError => error
  # This block is run if a AnotherCustomError occurs
else
  # This block is run if no exception occurred at all
ensure
  # This block always run, regardless of whether an exception occurred
end
```

Cela peut être utile, par exemple, lorsqu'on travaille avec des entrées-sorties réseau où il faut toujours penser à fermer une connexion.

Les blocs rescue de Ruby peuvent aussi utiliser le mot-clé `retry`, qui réexécute tout ce qui se trouve entre begin et rescue :

```ruby
counter = 0
begin
  counter += 1
  api_request
rescue
  retry if counter <= 3
end
```

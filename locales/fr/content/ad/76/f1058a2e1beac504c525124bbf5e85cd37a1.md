# Introduction

En assembleur, toute donnée est une séquence d'octets.
Cela signifie que n'importe quelle donnée peut être vue comme un **tableau** de ces octets sous-jacents.

## Accéder aux éléments d'un tableau

Pour accéder à une valeur quelconque en mémoire, il faut calculer son **adresse effective**.
Une adresse effective est une expression qui peut être composée des éléments suivants :

- une _adresse de base_, par exemple celle indiquée par l'étiquette d'une variable.
- un _registre d'indice_, éventuellement mis à l'échelle par `1`, `2`, `4` ou `8`.
- un _déplacement_ signé sur 32 bits, c'est-à-dire un nombre à ajouter à l'adresse de base (ou à en soustraire).

Note que cet adressage est _indexé à partir de zéro_, de sorte qu'une adresse de base, sans aucun décalage, pointe vers le premier octet d'une variable.
C'est pourquoi déréférencer la mémoire en utilisant simplement une étiquette, sans aucun décalage, comme nous l'avons fait dans les concepts précédents, donne une valeur qui commence à son premier octet :

```x86asm
section .data
    example dq 10 ; example is a 8-byte variable
                  ; so it can be viewed as an array of those 8 bytes
                  ; which can be accessed from index 0 to index 7

section .text
fn:
    mov al, byte [example] ; this accesses the first byte
    mov r8b, byte [example + 2] ; this accesses the third byte
    mov edx, dword [example + 1] ; this accesses 4 bytes starting at the second
```

~~~~exercism/note
x86-64 est [_little endian_][endianness].
Cela signifie que l'octet de poids faible d'une valeur multi-octets est stocké à la plus petite adresse mémoire.

Par conséquent, pour accéder aux octets individuels d'une valeur multi-octets, il faut ajouter un décalage positif à l'adresse de base afin d'atteindre les octets de poids plus fort.

[endianness]: https://en.wikipedia.org/wiki/Endianness
~~~~

Une variable initialisée déclarée avec une liste de valeurs est un tableau de ces valeurs, chaque élément ayant la taille indiquée.
Cependant, les décalages sont toujours exprimés en **_octets_**, même lorsque chaque élément du tableau a une taille supérieure :

```x86asm
section .data
    arr dq 4, 8, 15, 23, 42 ; this defines an array of 5 qwords (8-byte elements)
                            ; the first qword has value 4 and can be accessed at [arr] (offset 0)
                            ; any subsequent qword can be accessed at offsets increasing by the size in bytes of each element (8)

section .text
fn:
    mov rdx, 2
    lea rcx, [rel arr]
    mov rax, qword [rcx + 8*rdx + 8]  ; rdx is an index register scaled by 8
                                      ; 8 is a signed 32-bit displacement
                                      ; rax now holds 8-bytes stored in 'arr' starting at offset:
                                      ; 8*rdx(2) + 8 = 16 + 8 = 24
                                      ; this is the fourth element of the array, i.e., the element 23
```

Note que, comme les adresses sont exprimées en octets, il est possible d'accéder directement à un octet individuel de n'importe quel élément d'un tableau :

```x86asm
section .data
    arr dq 4, 8, 15, 16   ; this defines an array of 4 qwords (8-byte elements)

section .text
fn:
    mov r8, 3
    lea r9, [rel arr]
    mov r10b, byte [r9 + 2*r8 + 1] ; this accesses the byte in 'arr' at offset: 2*r8(3) + 1 = 7
                                   ; this byte is part of the first qword and has value 0 (the fist byte is the least significant one)
```

Pour la même raison, il est possible d'accéder, en une seule instruction, à plus d'octets que la taille d'un élément :

```x86asm
section .data
    arr db 1, 2, 3, 4 ; this defines an array of 4 bytes

section .text
fn:
    mov r11d, dword [rel arr] ; this accesses all bytes in arr as a 32-bit value with bytes
                              ; the least significant byte is 1, the next is 2 and so on
                              ; the resulting number is 0x04030201 or 67305985 in decimal
```

~~~~exercism/caution
L'assembleur n'effectue aucun contrôle des limites sur les accès aux tableaux.
Un indice qui dépasse la fin d'un tableau lit ou écrit de la mémoire en dehors de celui-ci.
Cela peut conduire à des résultats erronés sans aucun avertissement, à la corruption d'autres données et, si la mémoire accédée n'est pas mappée, à une erreur à l'exécution.
C'est au programmeur de veiller à ce que chaque adresse effective reste à l'intérieur du tableau.
~~~~

## Calculer la taille d'un tableau initialisé

NASM (The Netwide Assembler, l'assembleur utilisé par ce parcours) possède un symbole spécial (`$`) qui indique l'emplacement courant en mémoire.
Ce symbole offre un moyen pratique de calculer la taille totale en mémoire occupée par un tableau :

```x86asm
section .data
    example dd 4, 5, 6
    example_length dq $ - example  ; this is a qword variable with the size of the array, in bytes
```

Utilisé juste après `example`, `$` vaut l'adresse en mémoire de la fin du tableau.
Cela signifie que `$ - example` est la différence entre cette adresse et celle pointée par l'étiquette `example`.
C'est exactement la taille totale, en octets, occupée par le tableau pointé par `example`.

Ainsi, en définissant `example_length` avec cette valeur, on a créé une variable de 8 octets qui stocke la taille, ou la longueur, du tableau, en octets.

## La section .bss

Les données non initialisées sont déclarées dans la **section .bss**.
Sur la plupart des plateformes, ces données sont remplies de zéros par le système d'exploitation au lancement du programme.

En NASM, une variable non initialisée possède un nom, une directive qui indique la taille des données et le nombre d'éléments à réserver.
Chacun de ces éléments est séparé des autres par un espace.

Les principales directives et les tailles de données associées sont les suivantes :

| directive | taille  |
| :-------: | :------ |
|   resb    | 1 octet |
|   resw    | 2 octets|
|   resd    | 4 octets|
|   resq    | 8 octets|

Par exemple, ceci réserve un espace non initialisé de `3` octets dans une variable nommée `example` :

```x86asm
section .bss
    example resb 3
```

Et ceci réserve un espace non initialisé de `10` fois `8` octets (soit `80` octets) dans une variable nommée `arr` :

```x86asm
section .bss
    arr resq 10
```

Les variables de `section .bss` sont mutables, c'est-à-dire qu'elles sont accessibles en lecture et en écriture.

Les données non initialisées sont accessibles de la même manière que les données initialisées, en utilisant leur adresse effective.
De même, elles ont une durée de stockage statique et sont accessibles depuis n'importe quelle fonction du même fichier source (et, si elles sont déclarées `global`, depuis d'autres fichiers source également).

## Accéder aux adresses d'un tableau avec l'instruction lea

Comme nous l'avons vu dans un concept précédent, l'instruction `lea` calcule une adresse mémoire effective.
Elle peut servir à calculer l'adresse de n'importe quel élément d'un tableau, selon la même sémantique.

Note qu'en adressage relatif, il est souvent nécessaire de charger l'adresse de la variable dans un registre avant de former une adresse plus complexe :

```x86asm
lea rax, [rel arr]
lea rdx, [rax + 8*r10 - 20] ; accessing 'arr' directly instead of loading it into rax first may yield an error
```

~~~~exercism/note
L'un des avantages de `lea` est qu'elle utilise l'arithmétique de calcul d'adresses pour calculer une valeur sans réellement accéder à la mémoire située à cette adresse.
Cela la rend utile pour effectuer des calculs arithmétiques même lorsqu'aucun des registres ne contient d'adresse mémoire :

```x86asm
mov rcx, 3
mov rdx, 5
lea rax, [rcx + 8*rdx + 10] ; rax = rcx(3) + 8*rdx(5) + 10 = 3 + 40 + 10 = 53
```

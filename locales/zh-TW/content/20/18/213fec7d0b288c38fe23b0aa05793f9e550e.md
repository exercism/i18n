# 簡介

`GenServer`（通用伺服器）是一個[行為][concept-behaviours]，用來抽象化 Elixir 行程之間常見的客戶端與伺服器互動。

還記得我們在學[行程][concept-processes]時提過的接收迴圈嗎？`GenServer`行為提供了抽象機制，用來實作這類迴圈，以及與執行這種迴圈的行程交換訊息。它讓保存狀態與執行非同步程式碼變得更容易。

~~~~exercism/note
請注意，`GenServer`這個名稱的含義很廣。它也用來描述一個_使用_`GenServer`行為的_模組_，以及一個從_使用_`GenServer`行為的模組啟動的_行程_。
~~~~

`GenServer`行為定義了一個必要的回呼 `init/1`，以及幾個值得注意的選用回呼：`handle_call/3`、`handle_cast/2` 和 `handle_info/3`。使用`GenServer`的_客戶端_不應該直接呼叫這些回呼。相對地，`GenServer`模組提供了函式，讓客戶端可以用來與`GenServer`行程溝通。

通常，單一模組會同時定義_客戶端 API_（一組函式，你的 Elixir 應用程式其他部分可以呼叫它們來與這個`GenServer`行程溝通）以及_伺服器回呼實作_（其中包含這個`GenServer`的邏輯）。

我們先看一個簡單的`GenServer`範例，然後再來了解每個回呼的意義。

## 範例

這個範例伺服器可以在長途公路旅行中，回應煩人乘客不斷重複的追問，更精確地說，是這個問題：「我們到了嗎？」。它會記錄這個問題被問了幾次，並回以越來越不耐煩的答覆。

```elixir
defmodule AnnoyingPassengerAutoresponder do
  use GenServer
  # Client API

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg)
  end

  def are_we_there_yet?(pid) do
    GenServer.call(pid, :are_we_there_yet?)
  end

  # Server callbacks

  @impl GenServer
  def init(_init_arg) do
    # the initial count of questions asked is always 0
    state = 0
    {:ok, state}
  end

  @impl GenServer
  def handle_call(:are_we_there_yet?, _from, state) do
    reply =
      cond do
        state <= 3 -> "No."
        state <= 10 -> "I told you #{state} times already. No."
        true -> "..."
      end

    # increase the count of questions asked
    new_state = state + 1
    # reply to the caller
    {:reply, reply, new_state}
  end
end
```

## 回呼

### `init/1`

伺服器可以透過呼叫 `GenServer.start/3` 或 `GenServer.start_link/3` 來啟動。我們在[連結概念][concept-links]中學過這兩個函式的差別。

這兩個函式會：

- 接受一個實作`GenServer`行為的模組作為第一個引數。
- 接受任意值作為第二個引數，稱為 `init_arg`。顧名思義，這個引數會被傳給 `init/1` 回呼。
- 接受一個選用的第三引數，包含執行行程的進階選項，我們現在不談這些。

透過呼叫 `GenServer.start/3` 或 `GenServer.start_link/3` 來啟動伺服器時，會以阻塞的方式呼叫 `init/1` 回呼。`init/1` 的回傳值決定了伺服器能否成功啟動。

`init/1` 回呼通常會回傳下列其中一種值：

- `{:ok, state}`。伺服器會以 `state` 作為初始狀態來啟動它的接收迴圈。`state` 可以是任何型別。
- `{:stop, reason}`。`reason` 可以是任何型別。伺服器不會啟動接收迴圈。行程會以給定的原因結束。

還有更多進階的可能性，我們現在不談。

如果伺服器的接收迴圈啟動了，`GenServer.start/3` 和 `GenServer.start_link/3` 會回傳 `{:ok, pid}` 元組。否則它們會回傳 `{:error, reason}`。

### `handle_call/3`

需要回覆的訊息可以透過 `GenServer.call/2` 傳送給伺服器行程。這個函式預期第一個引數是執行中伺服器行程的 `pid`，第二個引數是訊息。訊息可以是任何型別。

`handle_call/3` 回呼負責處理並回應同步訊息。它會收到三個引數：

1. `message`：傳給 `GenServer.call/2` 作為第二個引數的值。
2. `from`：呼叫 `GenServer.call/2` 的行程 `pid`。這個引數通常可以忽略。
3. `state`：伺服器的目前狀態。請記得它的初始值是在 `init/1` 回呼中設定的。

`handle_call/3` 回呼通常會回傳 `{:reply, reply, state}` 這個三元組。這表示元組中的第二個元素 `reply`（可以是任何型別）會被傳回給呼叫者。元組中的第三個元素 `state`，是伺服器處理完這則訊息後的新狀態。

還有更多進階的可能性，我們現在不談。

~~~~exercism/note
想要從名稱記住這個回呼在做什麼，就想像你打電話「呼叫」某人。

如果對方有空，你會立刻收到回覆（同步地）。
~~~~

### `handle_cast/2`

不需要回覆的訊息可以透過 `GenServer.cast/2` 傳送給伺服器行程。它的引數和 `GenServer.call/2` 的引數完全相同。

`handle_cast/2` 回呼負責處理這些訊息。它會收到兩個引數 `message` 和 `state`，和 `handle_call/3` 回呼的引數相同（除了 `from` 之外）。

`handle_cast/2` 回呼通常會回傳 `{:noreply, state}` 這個二元組。

還有更多進階的可能性，我們現在不談。

~~~~exercism/note
想要從名稱記住這個回呼在做什麼，記得 cast 這個字也有「丟」的意思。

如果你把裝著訊息的瓶子丟進海裡，你不會期待立刻收到回覆，甚至可能永遠不會收到。
~~~~

### 我該用 `call` 還是 `cast`？

即使你的客戶端程式碼不需要伺服器的回覆，也幾乎總是該用 `call`。

使用 `call` 會等待回覆，這可作為一種背壓機制（避免客戶端一次傳送太多訊息）。收到伺服器的回覆，也是唯一能確定伺服器已收到並處理客戶端訊息的方法。

### `handle_info/2`

訊息也可能透過呼叫 `GenServer.call/2` 或 `GenServer.cast/2` 以外的方式進到伺服器的收件匣，例如呼叫一般的 `send/2` 函式。

要處理這類訊息，請使用 `handle_info/2` 回呼。這個回呼的運作方式和 `handle_cast/2` 完全相同。

`GenServer`行為提供了 `handle_info/2` 的全捕捉實作，會記錄非預期訊息的錯誤。如果你覆寫了那個預設實作，請務必總是加入你自己的全捕捉實作。如果你忘了，伺服器在收到非預期訊息時就會崩潰。

## 逾時

上面描述的四個回呼，其回傳值都可以再加上一個元組元素：逾時。例如，`init/1` 不要回傳 `{:ok, state}`，而是回傳 `{:ok, state, timeout}`。

逾時可以用來偵測信箱在特定時間內都沒有訊息。如果伺服器從某個回呼回傳逾時，而且經過指定的毫秒數都沒有訊息送達，就會以 `:timeout` 作為第一個引數來呼叫 `handle_info/2`。

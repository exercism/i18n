# 指令補充

## 任務

實作兩個程序。

- `custom_error_message message`會引發錯誤，`message`就是錯誤訊息。
- `handle_error script`會執行給定的腳本，並回傳一個描述發生什麼事的字串：

  | 當腳本…                          | 回傳                    |
  | -------------------------------- | ----------------------- |
  | 除以零                           | `"division by zero"`    |
  | 開啟不存在的檔案                 | `"file does not exist"` |
  | 呼叫不存在的 proc                | `"proc does not exist"` |
  | 引發其他任何錯誤                 | `"unknown error"`       |
  | 成功                             | `"success"`             |

## 引發錯誤

Tcl 有兩個指令可以用來引發錯誤。

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw`需要一個錯誤碼作為第一個引數。
錯誤碼是一個列表，用來告訴處理器發生了哪一種錯誤，讓它不必解析訊息文字就能做出反應。
錯誤碼的內容由你決定：`{MYAPP BADTHING}`只是個例子，任何非空的列表都可以。
依照慣例，它會從一般排到具體。
處理器會用相符的`try ... trap`模式（下面會說明）來捕捉它，例如`trap {MYAPP BADTHING}`，或用`trap {MYAPP}`捕捉所有`MYAPP`錯誤。
`error`會把選用的錯誤碼當作第三個引數：`error message ?info? ?code?`。

## 用`catch`處理錯誤

[`catch`][catch]會執行腳本，並回傳一個整數的完成碼，而不是引發錯誤：

| 代碼 | 意義       |
| ---- | ---------- |
| 0    | `ok`       |
| 1    | `error`    |
| 2    | `return`   |
| 3    | `break`    |
| 4    | `continue` |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

選用的第二個引數會接收結果（或錯誤訊息）。
選用的第三個引數會接收一個選項字典，裡面有`-errorcode`和`-errorinfo`（堆疊追蹤）。

優點：

- 它很小巧又有彈性。
- 簡單的情況寫起來很短，例如`if {[catch {open $f} fh]} {...}`。

缺點：

- 你必須自己檢查完成碼。
  一個粗心的`if {[catch ...] != 0} { handle error }`會把`return`、`break`和`continue`也當成錯誤。
- 你沒有處理的錯誤會被吞掉，除非你自己重新引發它們。
- 沒有內建的方法可以在腳本失敗與否時都執行清理用的程式碼。

## 用`try`處理錯誤

[`try`][try]會執行腳本，並把結果送給第一個相符的處理器。
選用的`finally`子句一定會執行，所以很適合用來釋放檔案通道之類的資源。

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

優點：

- 結構清楚：每一種結果都有對應的處理器。
- `finally`一定會執行。
- 沒有處理器相符的結果會原封不動地往上傳給呼叫者。

缺點：

- 簡單的情況下比`catch`稍微囉唆一點。

### `try ... on`與`try ... trap`的差別

處理器有兩種。

`on code {msgVar optionsVar}`比對的是完成碼：`ok`、`error`、`return`、`break`或`continue`。
每個錯誤的完成碼都是`error`，所以`on error`分不出是除以零還是檔案不存在。
你只能去看訊息文字，而這很不可靠：訊息是給人看的，而且可能隨 Tcl 版本改變。

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}`比對的是錯誤碼。
當模式是`-errorcode`列表的前綴時，處理器就會相符。
這樣就能可靠地挑出錯誤的種類。

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

空模式`trap {}`會符合任何錯誤。
處理器是依序檢查的，所以把能捕捉全部錯誤的處理器放在最後。

## 找出錯誤碼

`ARITH DIVZERO`的文件在哪裡？
大多只在原始碼裡，不過 Tcl 會把它顯示給你看。
發生錯誤之後，全域變數`errorCode`會保存最近一次錯誤的錯誤碼：

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

在程式裡，可以從選項字典取得：

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

錯誤碼的最後一個元素通常是給人看的訊息，或是造成錯誤的東西的名稱。
在`trap`模式裡省略它：用`{ARITH DIVZERO}`，而不是`{ARITH DIVZERO {divide by zero}}`。

### 一些常見的錯誤碼

這張表並不完整。
用上面的技巧就能找出其他任何錯誤的錯誤碼。

| 情況           | 範例                     | 錯誤碼                    |
| -------------- | ------------------------ | ------------------------- |
| 除以零         | `expr {1 / 0}`           | `ARITH DIVZERO ...`       |
| 數學定義域錯誤 | `expr {sqrt(-1)}`        | `ARITH DOMAIN ...`        |
| 找不到檔案     | `open nosuchfile r`      | `POSIX ENOENT ...`        |
| 權限不足       | `open /root/x w`         | `POSIX EACCES ...`        |
| 未知的指令     | `no::such::proc`         | `TCL LOOKUP COMMAND name` |
| 未知的變數     | `set nosuchvar`          | `TCL LOOKUP VARNAME name` |
| 引數數量錯誤   | `string length a b`      | `TCL WRONGARGS`           |
| 無效的字典     | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`    |
| 無效的列表     | `llength "a \{b"`      | `TCL VALUE LIST ...`      |

`POSIX`錯誤碼使用的是作業系統的`errno`名稱，例如`ENOENT`、`EACCES`和`EEXIST`。

## 提示：腳本在哪裡執行

`handle_error`會從呼叫者那裡收到一個腳本。
如果你用`try $script`執行它，它會在`handle_error`的作用域裡求值，而不是在呼叫者的作用域裡。
若要在它原本寫下的地方求值，請用[`uplevel`][uplevel]：`try {uplevel 1 $script} ...`。

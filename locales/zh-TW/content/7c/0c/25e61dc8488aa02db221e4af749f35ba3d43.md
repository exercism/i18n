# 簡介

## 為錯誤加上脈絡

我們在[錯誤概念][concept-errors]中探討了 Go 的基本錯誤處理。如同你在那裡學到的，錯誤預設不會帶著堆疊追蹤。因此，確保錯誤本身含有足夠的資訊來辨識問題，就變得至關重要。

如果我們想用已知的工具為既有的錯誤加入資訊，可以寫出像這樣的程式碼，建立一個結合原始錯誤文字與額外資訊的新錯誤：

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

幸運的是，標準函式庫中的`fmt`套件以`Errorf`函式的形式，提供了這件事的簡寫版本。這讓你例如可以輕鬆地為錯誤發生的脈絡加入資訊。

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

用這種方式為錯誤加入資訊通常已經足夠，但在某些情況下，你會想讓錯誤的使用方能夠檢查或取出原始的底層錯誤。在 Go 中，以允許這麼做的方式加入脈絡，稱為「包裝錯誤」。

## 包裝錯誤與檢查哨兵錯誤

只要對上面看過的程式碼做非常小的修改，就能達成錯誤包裝。要包裝錯誤，你需要使用格式化動詞`%w`，而不是`%v`。在背後，這會確保產生的錯誤實作了一個`Unwrap`方法，該方法會回傳原始錯誤。因此，就能用`errors.Is`來檢查某個特定的哨兵錯誤是否出現在「錯誤鏈」的某處。它的做法是偷偷地反覆呼叫`Unwrap`，直到找到該錯誤，或鏈結束為止。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

預設使用`%v`，只有在明確想讓使用方存取底層錯誤時才使用`%w`，這是良好的做法（[Google Go Styleguide][google-go-styleguide]）。

如果你發現自己處在想檢查哨兵錯誤、卻明確不想解開的情況，可以改用`==`，而不是`errors.Is`。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

預設使用`errors.Is`沒問題，但你應該隨時意識到，這意味著整條錯誤鏈都會被搜尋。

## 檢查（自訂）錯誤型別

有一個等同於`errors.Is`的東西，可以讓你從錯誤鏈中檢查並取出特定型別的錯誤。負責這件事的函式是`errors.As`，就像`errors.Is`一樣，它會沿著整條鏈搜尋給定的錯誤型別。`errors.As`會在找到符合型別的錯誤時才取出它，讓你能進一步處理，例如取得特定的欄位。

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
上面的指標相關語法要小心。只有當`customError`的型別正好是實作 error 介面的型別時，程式碼才會正確運作並編譯。在我們的情況中，那是`*MyCustomError`（一個指向`MyCustomError`的[指標][concept-pointers]），而不是`MyCustomError`本身。

除此之外，第二個引數必須是指向錯誤變數的指標。由於我們的錯誤已經是個指標，我們傳給`errors.As`的其實是一個指向指標的指標（指向 MyCustomError）。只有正確設定成這樣，Go 才能把找到的錯誤填入該變數。
~~~~

如同先前，如果呼叫`Errorf`時使用的是`%v`，`errors.As`就不會找到該錯誤型別。

如果你因為某些原因不想解開，可以改用型別斷言（等同於上面的`==`）。

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

如果錯誤被包裝過，型別斷言就無法辨識出錯誤型別。

## 讓自訂型別的錯誤可以被解開

有時只用一些額外文字包裝錯誤並不足夠。你可以改為建立一個自訂錯誤型別，用來容納原始錯誤，以及你想加入的額外結構化資料。如果你想讓你的錯誤型別允許解開，唯一要做的就是手動加入一個`Unwrap() error`方法，以滿足`Unwrap`介面。

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

# 簡介

## 錯誤

錯誤難免會發生。在 Elixir 裡，雖然大家常說「讓它崩潰就好」，但有時候我們仍需要把函式呼叫救回已知的良好狀態，以滿足軟體合約。在某些語言裡，錯誤被當成控制流程的一種手段，但在 Elixir 裡並不鼓勵這種模式。我們通常光看名稱就能認出哪些函式可能會拋出錯誤：會拋出錯誤的函式，名稱結尾帶有`!`。這是相對於會回傳`{:ok, value}`或`:error`的函式。看看這些函式庫範例：

```elixir
Map.fetch(%{a: 1}, :b)
# => :error
Map.fetch!(%{a: 1}, :b)
# => raises KeyError
```

## Try/Rescue

Elixir 提供了一種用`try .. rescue`從錯誤中救回的建構。

```elixir
try do
  raise RuntimeError, "error"
rescue
  e in RuntimeError -> :error
end
```

我們來看看這個建構：

- **第 1 行**，用`try`宣告這個程式區塊。
- **第 2 行**，這裡放的是可能出錯的函式呼叫，在這個例子中我們呼叫的是`raise/2`。
- **第 4 行**，在`rescue`區段裡，我們對所拋出錯誤的_模組_名稱做模式配對
  - 在`->`的左側：
    - `e` 會配對到錯誤結構。
    - `in` 是關鍵字。
    - `RuntimeError` 是我們想救回的錯誤。
      - 如果我們想從所有錯誤中救回，可以用`_`代替模組名稱，或完全省略`in`這個關鍵字。
  - 在右側：
    - 當錯誤相符時要執行的指令。

### 錯誤結構

用這種方式救回的錯誤（有時也稱為「例外」）是結構。
在 Elixir 裡，救回錯誤的情況非常少見。
通常救回的錯誤會被記錄下來，或送到外部的監控服務，然後再重新拋出。
這表示我們通常不太在意特定錯誤結構的內部結構。

在[例外概念][exercism-exceptions]中，你會學到更多關於錯誤結構的內容，包括如何定義自己的自訂錯誤。

[exercism-exceptions]: https://exercism.org/tracks/elixir/concepts/exceptions

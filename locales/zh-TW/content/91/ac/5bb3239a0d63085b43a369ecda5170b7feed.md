# 排序

```sather
   numbers.sort;                                  -- the natural order
   words.insertion_sort_by(bind(before(_, _)));   -- an order you supply
```

## `sort` 需要什麼

`sort` 要求元素的型別具有 `is_lt`。`INT`、`STR`、`CHAR`、`FLTD`和`INTI` 都有。自己定義的類別則沒有，除非你自己寫一個。

`insertion_sort_by` 對元素的型別沒有任何要求：它需要知道的一切，都在你交給它的常式裡。

## 比較必須符合什麼條件

這個常式必須定義出一致的順序，否則結果就未定義：

- 如果 `before(a, b)` 為真，那麼 `before(b, a)` 必須為假；
- 如果 `a` 排在 `b` 前面、`b` 排在 `c` 前面，那麼 `a` 也排在 `c` 前面；
- `before(a, a)` 必須為假。

最後一點是大家最常出錯的地方。把 `<` 寫成 `<=`，等於說某個東西排在它自己前面，而拿這種比較去排序，結果什麼都有可能。

## 平手

`sort` 和 `insertion_sort_by` 都**不穩定**：被比較判定為相等的東西，可能以任意順序出現，而在這個程式庫裡，它們通常會反過來。

所以「排兩次」這種技巧，先按名字排、再按分數排，期望同分的隊伍仍保持字母順序，在這裡行不通。想依賴輸入的順序，也一樣不行。

如果平手有差別，就在**比較**裡決定。讓它成為全序，這樣就永遠不會有兩個不同的東西被判定為相等：

```sather
   shorter(a, b : STR) : BOOL is
      if a.size /= b.size then return a.size < b.size; end;
      return a < b;                  -- same length: alphabetical
   end;
```

就算你認為不可能平手，也值得這麼做。一個比較若正著問、反著問都回傳 false，結果就沒有定義，而這個 bug 會以「順序莫名其妙就變了」的形式出現。

## 其他方法

| 呼叫 | 作用 |
| --- | --- |
| `a.sort` | 就地排序，自然順序，不穩定 |
| `a.insertion_sort_by(lt)` | 就地排序，你指定的順序，穩定 |
| `a.is_sorted` | 檢查 |
| `a.is_sorted_by(lt)` | 依你的順序檢查 |
| `a.binary_search(e)` | 在已排序的陣列中尋找 |
| `a.binary_search_by(e, lt)` | 依你的順序尋找 |

在未排序的陣列上呼叫 `binary_search` 不會失敗，只會回傳毫無意義的結果。它的前置條件本身就說明了這一點，而除非編譯器加上`-chk`，否則前置條件不會被檢查。

## 成本

插入排序的工作量大約與長度的平方成正比，用來排十幾支隊伍的排名表很剛好，用在成千上萬筆資料上就不對了。`ARR_SORT_ALG::sort_by` 是同樣概念下的快速排序版本，適合陣列很大、而且不需要穩定性的時候。

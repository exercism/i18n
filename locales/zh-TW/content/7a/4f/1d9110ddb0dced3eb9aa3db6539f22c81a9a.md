# 為 C 語言軌道貢獻

感謝你有興趣為 Exercism 的 C 語言軌道貢獻！
無論是新增練習、修改工具或文件、提出問題，甚至只是在既有的問題或 PR 底下留言，任何貢獻都歡迎。
這份文件提供了一些資訊，幫助你踏出第一步。

首先，請先讀一讀 [Exercism 文件][Exercism docs]，特別是[為語言軌道貢獻][contributing to a language track]的部分，因為這些文件涵蓋了許多基本資訊。

接下來請注意，這個儲存庫有一些特別之處，說明如下。

我們歡迎針對現有練習提出修正與改進的貢獻。
請注意，本軌道的練習必須符合 [problem-specifications][] 儲存庫所訂定的標準。
修改共用練習的測試或文件時，通常得先在該儲存庫提出 PR，之後才能納入本軌道的練習。
如果你不確定，就直接在 GitHub 開一個[問題][issue]，我們再一起討論怎麼改。

## 行為準則

一起讓 Exercism 保持友善歡迎的氛圍。
請閱讀並遵守[行為準則][Code of Conduct]。

## Git 工作流程

1. 先 Fork 再 clone。
2. 在你的 clone 中，把這個儲存庫加為新的 remote：`git remote add upstream https://github.com/exercism/c.git`
3. 建立新的分支：`git checkout -b name-of-branch`
4. 在新分支上照平常的方式 commit 並 push
5. 準備好要送出 PR 時，先把你的分支 rebase 到 upstream 的 main，這樣才能解決衝突：`git fetch upstream && git rebase upstream/main`。解決衝突後，你可能需要用 `--force` 把結果 push 到你的分支。
6. 一切就緒後，把變更 push 到你的分支，並依照下面的說明建立 PR。

## 問題

我們用 GitHub 的[問題][issues]來追蹤這個儲存庫的 bug、功能改進與支援請求。

如果想討論整個專案層級的事，可以到 [discussions][] 儲存庫看看那裡的問題。

### Good First Patch

如果我們認為某個問題不需要太多 Exercism 程式庫或功能的背景知識就能解決，就會為它加上「good first patch」標籤。想找這類問題，可以搜尋 [good-first-patch][]。

## PR

建立 PR 時如果能遵循這份簡單的 [PR 指南][pull request guidelines]，那就太棒了，不過這並非必要。

每個 PR 最好只專注在單一問題或單一變更。
我們歡迎調整程式碼風格與用字，但情況允許的話，請為這類變更另開一個 PR。
如果你的 PR 會對現有練習做出重大（破壞性）變更，或會一次改動許多練習，請先開一個問題再建立 PR。最好先討論過這些變更，再開始動手。

如果你的變更涉及練習，可以在送出 PR 前先執行 CI 腳本，或者讓它們在送出後自動執行，詳情請見[持續整合][Continuous Integration]。

送出 PR 後，我們有時會請你先做一些修改，才會接受這個 PR。

請不要關掉原本的 PR，再另外開一個新的 PR 來放這些修改。
只要你在已開 PR 的分支上再 push commit，PR 就會自動更新。

如果你想建立 PR，但這些變更還沒準備好合併到 main（例如你想先討論某個項目），照平常的方式建立 PR，然後用 GitHub 網站介面[把 PR 轉為草稿][convert the PR to a draft]，讓維護者知道你還沒準備好合併。

就像追加 commit 一樣，如果你改了歷史紀錄（rebase、squash、amend），並用 git push --force 更新你 fork 上的分支，你不需要關掉 PR 再開一個新的。
PR 指向的是那個分支，而不是特定的 commit。

## 程式碼風格

程式碼變更類貢獻所應遵循的程式碼風格，說明在[風格指南][style guide]中。

練習的程式碼會在 [CI][Continuous Integration] 期間被檢查是否符合空白與縮排的風格規則。
這項檢查使用 [`clang-format`][clang-format] 這個 CLI 工具。
新增或修改練習時，你可以在 commit 之前先在本機執行這個工具，確認變更符合這些規則。

在 Linux 上，通常可以透過你的發行版的套件管理器安裝`clang-format`。
在 Mac 上，你可以用 [Homebrew][] 安裝`clang-format`套件。

執行`format.sh`即可對所有檔案執行 clang-format。
若想手動對單一檔案執行，可以執行以下指令：

```bash
clang-format -i $(file)
```

## 練習的結構

每個練習都應該放在`c/exercises/practice/{exercise-name}`目錄中。
想深入了解如何實作符合規格的練習，請參考 [implement-an-exercise-from-specification][]

練習目錄的結構如下（請注意目錄名稱使用連字號，檔案名稱則使用底線）：

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c`：這個檔案包含該練習的所有測試。  
`test-framework`：包含來自 [ThrowTheSwitch][] 的測試框架 [Unity][] 的目錄。  
  如果你想找教學，ThrowTheSwitch 有一份不錯的 [Unity 入門指南][getting started with unity]。  
  所使用的 Unity 版本記錄在[版本][versions]中。測試檔案的結構說明在[風格指南][test-file-layout]中。  
  測試應該寫成符合 [problem-specifications][] 儲存庫中該練習的`canonical-data.json`檔案。  
`{exercise-name}.c` / `{exercise-name}.h`：練習的原始碼檔案。  
  請在標頭檔中使用 [include guard][include guards]。
  在儲存庫根目錄執行`make test`即可執行練習的測試。
* `makefile`：練習用來建置的 makefile。  
其中必須包含兩個規則：
test：編譯 test_{exercise-name}.c 並執行它。
memcheck：加上 -fsanitize=address、-fno-common、-fno-omit-frame-pointer 旗標編譯 test_{exercise-name} 並執行它
Makefile 在各個練習之間通常不太會變動，所以要從其他練習複製一份並不難。

**別忘了**把練習加進本軌道的`config.json`。為此，你需要決定這個練習在所有軌道練習的順序中最適合放在哪裡，還需要產生一個 UUID 加進去。這兩件事都可以用 [configlet][] 工具完成；在你做完這些變更後，這個工具甚至會幫你 lint 並格式化`config.json`！

補充一下：想取得 configlet 工具的安裝檔，請看 [configlet 發佈頁面][configlet releases page]。

## 持續整合

這個儲存庫使用 GitHub 工作流程，在每次 PR 有新 commit 時執行一些工具。
想在自己的貢獻上執行這些工作流程，最簡單的方式是在這個儲存庫上開一個包含你變更的 PR，把 PR 設為草稿，然後讓這個儲存庫的 CI 設定自動幫你處理。

### CI 環境

GitHub 會在稱為[代管執行器][hosted runners]的虛擬機器上執行 CI。
工作流程可以設定一些它們希望在哪種執行器上執行的細節。

這個儲存庫中的工作流程只指定了它們都要在 Ubuntu 24.04 上執行。這些工作流程都固定在特定版本，而不使用`latest`，因為有些使用的工具在不同版本上的行為可能不同。

### 在自己的 fork 上執行 CI

如果你想要，也可以在自己的 fork 上執行 CI，只要在 GitHub 上照平常的方式 clone 這個儲存庫即可。
位於 [`./.github/workflows/`][workflows] 的 YAML 檔案應該也能照常運作。
如果你希望 [`/format`][format-workflow] 這個自動化動作能正常運作，就需要在你的複製出來的儲存庫中加入一組部署金鑰。

### 工作流程

* `checks.yml` 會對工具腳本執行`shellcheck`，接著執行下列工具：
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * [Lychee 連結檢查器][lychee]動作
* `configlet.yml` 會取得最新版的 configlet，然後用它在軌道上執行`lint`指令
* `format-code.yml` 會檢查 PR 上的任何留言是否含有字串`/format`，如果找到，就會對練習執行`format.sh`，並把產生的變更 commit 進去。這個 commit 需要部署金鑰才能重新觸發 CI。部署金鑰由 Exercism 直接管理。
* `test.yml` 會在儲存庫根目錄執行`make`，測試所有練習

### 工具

從[工作流程][workflows]中可以看出，GitHub 被指示從 [`./bin`][bin] 目錄執行工具。
這個目錄中的工具所做的工作如下：

* `check-unitybegin`確保每個測試檔都正確地在`main()`函式開頭加上`UNITY_BEGIN()`這一行。
* `fetch-configlet`會從 configlet 的[儲存庫][configlet]取得`configlet`工具。
* `verify-unity-version`會檢查每個練習所使用的 Unity 測試框架版本。這個檔案應該檢查的版本記錄在 [`./docs/VERSIONS.md`][versions]
* `check-include-guards`會檢查每個練習的 stub 與範例標頭檔所使用的 include guard 格式是否正確，如下：

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet`會從 configlet 的[儲存庫][configlet]取得`configlet`工具。

### 在本機執行工具

你也可以在 commit 之前，在自己的電腦上單獨執行這些工具。
首先請確認已安裝必要的應用程式（例如`clang-format`、[`git`][git]、[`sed`][sed]、[`make`][make]以及 C 編譯器），然後在儲存庫根目錄執行所需的工具。例如：

```bash
~/git/c$ make
```

如果你只想執行部分測試來檢查你的成果，可以把它們指定為 make 的目標。

```bash
~/git/c$ make acronym all-your-base allergies
```

## 測試執行器

這個軌道有 Exercism v3 的測試執行器！
你可以[在這裡][c-test-runner]看看。

測試執行器提供了一種 Docker 化的方式，在 Exercism v3 中針對學生的程式碼執行練習的測試。
這種 Docker 做法讓學生可以在瀏覽器裡寫程式。
想了解更多，請參閱[測試執行器][test runners]。

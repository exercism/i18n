# 關於

## 為錯誤加上背景資訊

我們在[錯誤概念][concept-errors]中介紹了 Go 的基本錯誤處理。正如你在那裡學到的，錯誤預設不會攜帶堆疊追蹤。這使得確保錯誤本身含有足夠的資訊來找出問題，變得至關重要。

如果我們想用已知的工具為現有的錯誤加上資訊，可以寫出像下面這樣的程式碼，建立一個結合原始錯誤文字與額外資訊的新錯誤：

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

幸運的是，標準函式庫的`fmt`套件以`Errorf`函式的形式，提供了這個做法的簡便版本。舉例來說，這讓你能輕鬆加上錯誤發生當下的背景資訊。

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

除非你確定錯誤本身已經含有足夠的資訊，否則應該養成習慣：在從函式回傳錯誤之前，先為它加上背景資訊。也就是說，你標準的錯誤處理模式應該長這樣：

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

如範例所示，慣例是用冒號把錯誤和加上去的訊息隔開。就像原始錯誤的訊息一樣，背景訊息也不應該以大寫開頭，結尾也不要加上句號。

~~~~exercism/note
為錯誤加上背景資訊時，很容易會想用「failed to ...」或類似的字眼開頭。然而，錯誤在沿著函式鏈往上傳遞的過程中會累積大量額外的背景資訊，這會讓最後被記錄下來、或使用者看到的訊息更難閱讀，甚至充滿重複。

底下用一個例子說明：

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

所以撰寫背景訊息時，請把最後的結果放在心上，不要加上描述某件事沒有如預期進行的文字。這一點通常從背景資訊（例如日誌等級為「ERROR」）和原始錯誤訊息就能看出來。
~~~~

這種為錯誤加上資訊的做法通常已經足夠，但有些情況下，你會希望讓錯誤的取用方能夠檢查或取出原始的根本錯誤。在 Go 裡，用允許這種做法的方式加上背景資訊，稱為「包裝錯誤」。

## 包裝錯誤與檢查哨兵錯誤

只要對上面看過的程式碼做一點微小的修改，就能達成錯誤包裝。要包裝一個錯誤，你需要使用格式化動詞`%w`而不是`%v`。在背後，這會確保產生的錯誤實作了一個會回傳原始錯誤的`Unwrap`方法。因此，就可以用`errors.Is`來檢查某個特定的哨兵錯誤是否出現在「錯誤鏈」的某處。它的做法是暗中反覆呼叫`Unwrap`，直到找到該錯誤或鏈結結束為止。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

如果用一般的`%v`格式化動詞，就無法用`errors.Is`檢查原始錯誤。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

因此，預設使用`%v`，只有在明確希望讓取用方存取根本錯誤時才使用`%w`，是良好的做法（[Google Go 風格指南][google-go-styleguide]）。

如果你遇到的狀況是想檢查某個哨兵錯誤，但明確不想解開它，可以用`==`取代`errors.Is`。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

相反地，如果錯誤被包裝過，`==`就無法辨識出它。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

預設使用`errors.Is`沒問題，但你應該隨時意識到，這代表整條錯誤鏈都會被搜尋過。

## 檢查（自訂）錯誤型別

有一個等同於`errors.Is`的方法，可以從錯誤鏈中檢查並取出特定型別的錯誤。對應的函式是`errors.As`，就和`errors.Is`一樣，它會沿著整條鏈搜尋指定的錯誤型別。`errors.As`只有在找到符合型別的錯誤時，才會把它取出來，讓你能進一步處理，例如取出特定的欄位。

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
請留意上面與指標相關的語法。只有在`customError`的型別正好是實作 error 介面的那個型別時，程式碼才能正確運作並編譯。在我們的情況中，那個型別是`*MyCustomError`（指向`MyCustomError`的[指標][concept-pointers]），而不是`MyCustomError`本身。

除此之外，第二個引數必須是錯誤變數的指標。由於我們的錯誤已經是指標，傳給`errors.As`的其實是指標的指標（指向 MyCustomError）。唯有這樣正確設定，Go 才能把找到的錯誤填入該變數。
~~~~

和之前一樣，如果呼叫`Errorf`時用的是`%v`，`errors.As`就找不到該錯誤型別。

如果基於某些原因你不想解開，可以改用型別斷言（等同於上面的`==`）。

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

如果錯誤被包裝過，型別斷言就無法辨識出該錯誤型別。

## 讓自訂型別的錯誤可以被解開

有時候，只用一些額外的文字包裝錯誤並不足夠。你可以改為建立一個自訂錯誤型別，用來保存原始錯誤以及你想加入的額外結構化資料。如果你想讓自己的錯誤型別可以被解開，唯一要做的事，就是手動加上一個`Unwrap() error`方法，以滿足`Unwrap`介面。

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## 合併多個錯誤

在 Go 1.20 中，內建的`errors`套件新增了一個`Join`函式。`Join`讓你以仍然可以解開的方式合併多個錯誤，也就是能沿著鏈檢查特定的錯誤或錯誤型別。如此一來，錯誤鏈實際上可能是一棵錯誤樹。更多資訊可以在[發行說明][release-notes]和[文件][doc-join]中找到。

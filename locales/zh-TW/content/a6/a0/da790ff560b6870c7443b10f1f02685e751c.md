# 合併策略

Rust 賽道的維護者[決定](https://github.com/exercism/v3/discussions/1725#discussion-7438)把我們的合併策略寫下來，以說明我們的期望，並鼓勵大家做出高品質的貢獻。

## 基本原則

- 我們盡可能接受_所有_貢獻
  - 我們會透過協作、疊代式的審查，讓貢獻達到高品質的標準。
  - 我們採用悲觀式合併的做法。把維護者的審查看成 Rust 編譯器給的意見就知道了：意見的量可能會讓人吃不消，甚至感到挫折。但我們會陪你一起把它送到終點線！所以繼續加油喔。
- 每一份 pull request 在合併之前，都必須至少有一位賽道維護者的「Approval」，而且不能有「Request Changes」。
- 維護者不得核准自己的 pull request。

## pull request 工作流程

### 定義

| 詞彙 | 含義 |
| ------------------ | ----------------------------------------------------------------------------------------------------: |
| 貢獻者 | 任何提交 pull request 的人。 |
| 維護者 | 任何屬於 [@exercism/rust 團隊](https://github.com/orgs/exercism/teams/rust)的人。 |
| 開發分支 | [v3](https://github.com/exercism/v3) 儲存庫的預設開發分支。目前是 `master`。 |

### 工作流程

1. 貢獻者先開啟一份 [draft](https://github.blog/2019-02-14-introducing-draft-pull-requests/) 或完整的 pull request，附上自己的變更
   1. 使用 draft 功能代表這份工作已經可以接受高階審查，但細節目前可能還沒實作、還沒完成或有誤。
   1. 在經過不確定次數的步驟 2 到 3 疊代之後，貢獻者把 pull request 標記為可審查。
1. 另一位維護者應審查這份貢獻並提供回饋。
1. 貢獻者應在 pull request 中處理_所有_維護者的回饋。
   1. 對於吹毛求疵或簡單明確的變更，維護者應考慮使用 GitHub 的建議功能。
   1. 當貢獻者認為自己對某項回饋是對的、維護者才是錯的時，鼓勵提出反駁。「處理」一項回饋並不代表要照單全收。
1. 維護者應審查這些回饋，並擇一：
   1. 核准
   1. 要求進一步變更。此時流程回到步驟 3。
1. 核准之後，維護者應合併該 pull request。
   1. 維護者應合併自己的 pull request。由於貢獻者不一定是維護者，因此這一步必須由維護者執行。

## 樂觀式合併

Rust 賽道維護者決定暫時採用樂觀式合併，以加速 v3 賽道的開發。

- 這只適用於 v3 儲存庫
- 等到 v3 正式上線後，我們會回到悲觀式合併策略。
- 我們會核准並合併尚未完成的工作
  - 只要能編譯，我們就留著。
  - 相較於軟體設計的正確細節，更重視疊代速度。
- 每一份 pull request 在合併之前，都必須至少有一位賽道維護者的「Approval」。

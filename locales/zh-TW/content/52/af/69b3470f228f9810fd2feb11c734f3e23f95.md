## 工具

有一些工具是以 bash 腳本的形式放在`bin/`裡。
更多工具放在`rust-tooling/`裡，處理任何非簡單的事情時，都應該優先使用它。

另外還有一份 [`mise`](https://mise.jdx.dev/) 設定，
裡面有幾個和這個 repo 互動的實用指令。
歡迎自行擴充。

如果你想在本機執行 CI 測試，`mise run test` 就能幫你完成大部分的事。

## 排除測試與新增自訂測試

在建立或更新練習時，你可能會決定排除某些測試，不讓它們被產生。
做法是在`.meta/tests.toml`裡設定`include = false`。
請附上註解，說明排除它的原因。

如果你想加入額外、專屬於這個軌道的測試，可以寫在`.meta/additional-tests.json`這個檔案裡。
只有在有充分理由不把這些測試上游時，才這麼做。
在額外測試裡加一段註解，回答下列問題：
- 為什麼這個測試沒有被上游到`problem-specifications`，也就是說，為什麼它對其他語言沒有普遍的價值？
- 那為什麼這個測試對 Rust 軌道仍然有價值？

## 建立新的練習

請先熟悉 [Exercism 關於練習題的文件]。

[Exercism 關於練習題的文件]: https://exercism.org/docs/building/tracks/practice-exercises

執行 `mise run add-exercise`，系統會詢問你產生練習骨架所需的最少資訊。
之後進入產生的練習，把你找到的預留位置都填上。
其中最主要的包括：

- 在`src/lib.rs`裡撰寫練習骨架
- 在`.meta/example.rs`裡加入範例解答
- 調整`.meta/test_template.tera`

測試是用範本引擎 [Tera] 產生的。
範本的輸入是來自 [`problem-specifications`] 的標準資料。

關於撰寫 tera 範本的祕訣，請看[這裡](#tera-templates)。

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

一個正確完成的練習，有許多面向都會在 CI 中檢查。
我建議不要花大把時間研究、撰寫關於流程的文件，_直接動手做_就好。
如果哪裡壞了，修好它，再加上測試或自動化，讓它不會再發生。

如果你是從零開始建立一個練習題，而且它不在`problem-specifications`裡，
那你就得自己手動撰寫測試。
測試應該依複雜度遞增排序，
讓學生可以一個一個取消忽略，用 TDD 解出這個練習。
關於撰寫好測試的更多想法，請看 [Exercism 的文件](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)。

除非有特殊情況，否則骨架檔案應該要能在`cargo test --no-run`下編譯。
這樣我們就能檢查骨架檔案裡的簽名，
是否和測試預期的簽名一致。
為了達到這個目的，把每個函式的主體寫成`todo!()`。
如果有正當理由而做不到，
就在練習的`.meta/config.json`裡加入一個`.custom."allowed-to-not-compile"`鍵，
並在其中寫明原因。

## 更新練習

許多練習都衍生自 [`problem-specifications`]。
包括它們的測試套件和給使用者看的文件。
在這裡提出修改之前，
先確認這些修改是不是應該在`problem-specifications`裡做。

執行 `mise run update-exercise` 來更新練習。
它會把大部分工作交給 `configlet sync --update`，
並重新執行測試產生器。

更新一個還沒有 tera 範本的練習時，
系統會為你產生一個新範本。
你大概得稍微調整一下。

關於撰寫 tera 範本的祕訣，請看[下一節](#tera-templates)。

## Tera 範本

tera 範本的完整文件在[這裡][tera-docs]。
以下是一些符合我們特定需求、確實可行的做法。

你大概會想看一下練習的`canonical-data.json`，了解你的輸入資料長什麼樣子。
你可以用`bin/symlink_problem_specifications.sh`，把這份資料
以符號連結的方式放進實際的練習目錄。很實用！

每個練習的輸入屬性名稱都不一樣。
預設範本大概會長這樣：

```txt
let input = {{ test.input | json_encode() }};
```

你得補上這個練習專屬的輸入欄位，例如：

```txt
let input = {{ test.input.integers | json_encode() }};
```

有些練習可能會有錯誤回傳值。
你可以依資料的結構，用 if-else 產生不同的內容：

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

有些練習有好幾個函式需要學生實作，因此也必須測試。
這種情況下，標準資料裡會有個`property`欄位。
你可以根據`test.property`建立 if-else 鏈，據此產生不同的函式。

有些練習會把測試案例組織成_測試群組_。
你的範本必須處理這種情況。
很多時候，你可以直接把結構攤平。（範例：[`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera)）
不過，不同群組裡的測試有時會有相同的描述，結構一攤平就會造成命名衝突。
這種情況下，你可以用群組描述把測試組織進各個模組。（範例：[`forth`](/exercises/practice/forth/.meta/test_template.tera)）

[`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs) 裡有一些自訂的 tera 篩選器。
以下是這份清單，希望它還跟得上最新狀況：
- `to_hex` 以十六進位格式化整數
- `make_ident` 把任意字串轉成堪用的 Rust 識別字。
   最適合用來從測試描述產生函式名稱。
- `fmt_num` 格式化數字字面值（每三位數插入一個`_`）

歡迎在`rust-tooling`這個 crate 裡加入你自己的篩選器。
希望你會記得順便更新這裡的清單。🙂

想看一個相當複雜的範例，可以參考`triangle`的測試範本。
它把測試案例組織成模組，並動態判斷哪些測試要放到 feature gate 後面。
那個練習也在`additional-tests.json`裡重新實作了幾個來自上游的測試案例，為的是補上產生好測試所需的額外資訊。

[tera-docs]: https://keats.github.io/tera/docs/#templates

## 課程大綱

課程大綱目前因為品質不佳而停用。
關於這個決定的來龍去脈，請看[這篇論壇文章](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)。

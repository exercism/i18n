# 簡介

在理想的世界裡，我們可以仰賴一切都有完善的定義，有具體的值，沒有任何缺口。

然而，這與我們的日常經驗相衝突，因此許多程式語言都有表示「沒有值」的方式：null 或 NULL、nil、None、nothing……

這在（1965 年）當年很容易引入，卻很快就帶來了悔恨。
發明者後來稱它是自己的「十億美元錯誤」。

近幾十年來，語言設計者探索了許多做法，讓 null 既能使用，（大致上）又安全。

Kotlin 有幾項[基本原則][ref-null-safety]，與 Java 有顯著差異。


- Kotlin 有一個特殊的`null`值。
- 所有型別_預設_都不可為 null。
- 大多數型別可以_被指定_為可為 null，但程式設計師必須明確地這麼做。
- 可能因例外而失敗的函式，通常會有回傳值可為 null 的版本。
- 特殊而極為精簡的語法，則盡可能讓 null 的檢查與應對變得容易。

## 建立可為 null 的變數

標準型別通常都有對應的可為 null 版本，在名稱後面加上`?`：例如用`String?`取代`String`。

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## 實用的運算子與函式

### 安全呼叫運算子`?.`

對於不可為 null 的`String`，我們可以取得`.length`屬性。

可為 null 的`String?`用同樣的語法會失敗，但改用`?.length`就能允許`null`的可能。
回傳型別是`Int?`。

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

從上面最後一行可以看到，`?.`也能用在不可為 null 的型別上。

### Elvis 運算子`?:`

延伸安全呼叫運算子的概念，[Elvis 運算子][wiki-elvis]讓我們能提供預設值來取代`null`。

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### 非 null 斷言運算子`!!`

有了這個運算子，當程式設計師有把握時，就能強制把可為 null 的型別當成不可為 null 來處理。
也許有時候，我們對程式邏輯的理解比過度謹慎的編譯器還要好吧？

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

這下責任就落到我們身上了：如果`b`仍然是`null`，就會得到`NullPointerException`。

### let 函式`?.let`

如果要把可為 null 的項目傳進一段程式碼區塊，我們可以逐一做 null 檢查：`if (item != null) { do something }`。

更簡單也更道地的做法是使用`item?.let { do something }`。
只有當`item`不是 null 時，`do something`才會執行。

### `somethingOrNone()`這類函式

有些函式可能會失敗，例如在字串或陣列中要求一個無效的索引時。

比起拋出例外，我們可以使用函式的`...OrNull`版本，藉此取得（在這裡是）`Int?`的回傳值。

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

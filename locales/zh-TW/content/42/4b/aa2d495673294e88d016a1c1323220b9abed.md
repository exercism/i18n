# 關於

在先前的概念中曾提到，`global`指示詞會讓定義在某個原始檔中的函式或變數能被其他檔案看見。同樣地，`extern`指示詞會告知組譯器，目前原始檔所使用的函式或變數是定義在另一個檔案中。

這兩個指示詞是組合語言程式碼與其他原始檔互動以達成模組化的主要方式。

就這些指示詞而言，外部程式碼是以組合語言或高階語言定義或使用，並沒有差別。因此舉例來說，即使某個函式是以高階語言定義，只要宣告為`extern`，就能在 x86-64 程式碼中使用。

同樣地，呼叫慣例在這些函式之間是共通的，不論它們是以組合語言或高階語言定義，甚至與作業系統（OS）之間也是如此。

不過，由於在組合語言中資料只是一串位元組，因此重要的是要了解與之介接的高階語言如何管理記憶體。

## C 型別

C 語言是與組合語言程式碼介接時常用的高階語言。它讓與作業系統互動的工作變得更容易，為許多重要工作提供高階的包裝，例如輸出到螢幕、從鍵盤讀取，或配置動態記憶體。

在這個學習路徑中，測試是以 C 撰寫，因此提供該語言的整體概觀很重要。

~~~~exercism/note
下列任何型別都可以用`const`修飾，這會讓它們變成唯讀。
~~~~

### 基本型別

C 有許多基本型別，它們的位元組大小可能不同。下表整理了其中一些，以及它們在 x86-64 系統上的典型大小：

| 型別      | 位元組數        | 整數／浮點數           |
|-----------|-----------------|------------------------|
| _Bool     | 1               | 整數                   |
| char      | 1               | 整數                   |
| short     | 2               | 整數                   |
| int       | 4               | 整數                   |
| long      | 4 或 8          | 整數                   |
| long long | 8               | 整數                   |
| float     | 4               | 浮點數                 |
| double    | 8               | 浮點數                 |

這些整數型別每一個都可以是有號（預設）或無號。若是無號，就必須明確指定，例如：`unsigned int`。

有些整數型別的別名被定義出來，以便精確控制它們的大小：

| 別名    | 位元組數        |
|---------|-----------------|
| int8_t  | 1               |
| int16_t | 2               |
| int32_t | 4               |
| int64_t | 8               |

這些別名可以加上`u`前置字元來表示無號型別，例如：`uint64_t`。

其他值得注意的別名有：

| 別名   | 型別                                          |
|--------|-----------------------------------------------|
| bool   | _Bool                                         |
| size_t | 通常是無號的 8 位元組整數                     |

`_Bool`，或其別名`bool`，特別之處在於：雖然它佔用整整 1 個位元組，卻只能取兩個值的其中一個：`true`（`1`）和`false`（`0`）。

這些基本型別的值會依照整數與浮點數的一般規則傳入函式並從函式回傳。

### 列舉

[enum][enum] 是一種型別，可以取若干明確指出元素中的其中一個：

```c
enum example {
    example_1,
    example_2,
    example_3,
    example_4
};
```

在 C 中，列舉會隱式轉換成整數型別，通常是`int`，也就是 4 位元組的整數。

預設情況下，列舉中第一個可能的元素會轉換成`0`，之後每個元素則轉換成下一個整數。因此，在上面定義的`enum example`中，`example_1`的值會是`0`，`example_2`的值會是`1`，依此類推。

可以為列舉中任何元素指定值，之後預設下一個元素的值就是下一個整數：

```c
enum example_2 {
    example_1 = 4,
    example_2 = 8,
    example_3
}; // example_3 is equal to 9
```

### 記憶體位址

在 C 中，記憶體位址是以指向某個型別的 [指標][pointer] 來表示，並以`*`運算子標示。因此舉例來說，`int64_t *`指的是一個存放一個或多個`int64_t`的記憶體位置。

位址一如往常會被視為 8 位元組的整數。

### 陣列

陣列會以指向第一個元素的指標形式傳入函式並從函式回傳。

```c
int64_t example_arr[] = {1, 2, 3}; // this is an array of 3 signed 8-byte integers
fn(example_arr); // this is a function that passes a pointer (int64_t *) to the beginning of the array as argument
```

陣列中每個元素的大小等於該陣列元素型別的大小。舉例來說，上面定義的`example_arr`有 3 個元素，每個 8 位元組，總共 24 位元組。

由於陣列不會儲存自己的長度，通常需要另一個值來表示元素數量，除非有哨兵值標示結尾。

### 字串

C 的字串是`char`的陣列，而`char`是 1 位元組的型別。大多數字串由 ASCII 字元組成並以 NUL 結尾，因此當遇到值為`0`的位元組時就結束。這表示字串的長度通常不需要另外當作引數傳入。

## 呼叫 C 函式庫函式

`extern`指示詞只是宣告某個符號定義在另一個檔案中。實際如何呼叫它，取決於那段外部程式碼如何被連結。

對於與你的程式碼連結在一起的普通函式，連結器可以直接找到外部函式，因此單純的`call`就夠了。

不過，標準 C 函式庫函式，例如`malloc`、`free`和`printf`，通常是在執行時從共享函式庫解析，其位址在你的程式碼被組譯時並不知道。因此這個呼叫會經過 [程序連結表（PLT）][plt] 中的一個 stub，它位於已知的位移。從組合語言呼叫外部函式庫函式時，NASM 會要求指出這個呼叫應該由 PLT 解析。

在`elf64`（Linux 程式使用的輸出格式）中，這個指示是在呼叫後面加上`wrt ..plt`（意指 with reference to plt）來完成。例如`call printf wrt ..plt`。

在`macho64`程式（macOS 程式使用的輸出格式）中則相反，在函式名稱前面加一個底線就夠了。例如`extern _printf`，然後`call _printf`。不過，由於這個學習路徑使用`--prefix _`旗標來組譯`macho64`程式碼，組譯器在兩種情況下都會自動加上這個底線，例如`extern printf`，然後`call printf`。

請注意，Exercism 的測試執行器是在 Linux 映像檔中執行，因此任何會呼叫 C 函式庫函式的提交解答都必須使用`wrt ..plt`。可以使用組譯期間的防護來正確地在各種輸出格式之間分派：

```x86asm
extern malloc

%ifidn __OUTPUT_FORMAT__,elf64
    call malloc wrt ..plt       ; elf64: reach the function through the PLT
%else
    call malloc                 ; macho64: the linker generates the call stub
                                ; the underscore is added automatically by an assembler flag
%endif
```

## 系統呼叫

有許多操作是使用者層級程式（例如在這個學習路徑中執行的程式）無法直接完成的。從`stdin`讀取、寫入`stdout`、要求動態記憶體、與周邊裝置互動等，全都由作業系統（OS）處理。

使用者層級程式在需要時必須明確要求作業系統執行這些操作。這是透過[`syscall`][syscall]指令完成的。概念上，這個指令可以想成是對某個預先定義的作業系統程序（也就是「系統」呼叫）的呼叫。

系統呼叫的任何引數都應該透過一般用途暫存器（GPR）傳給作業系統：`rdi`、`rsi`、`rdx`、`r10`、`r8`和`r9`。

請注意，這個順序與函式呼叫所用的幾乎相同，只是`rcx`被換成了`r10`。這是因為`syscall`會用`rcx`和`r11`來保存回傳位址和旗標（在將控制權交還給呼叫端函式之前會還原它們）。這兩個暫存器在每次`syscall`時都必須視為已遭覆寫。

和`call`不同的是，這裡沒有標籤可以指出系統「函式」。取而代之的是，透過呼叫前放入`rax`的特定編號來觸達它們。任何回傳值（如果有的話）也會放在`rax`中。

上述慣例在 [System V ABI 的附錄][linux-convention]中有說明，該附錄專門涵蓋 Linux，且標示為僅供參考。實際上，可用的系統呼叫、它們的編號，以及錯誤的回報方式，都是作業系統層級的細節，在各作業系統之間差異很大，甚至同一個作業系統的不同版本之間也不同。

許多 C 函式庫函式，以及作業系統定義的其他實際函式，都是系統呼叫之上更高階的包裝。ABI 建議應優先使用這些包裝，而非直接使用單純的`syscall`，而且 Apple [不保證核心系統呼叫介面的相容性][mac-qa1118]。

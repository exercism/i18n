# 테스트 생성기

테스트 생성기를 사용하면 트랙에서 테스트를 직접 작성하지 않고도 자동으로 생성할 수 있어요. 각 테스트 생성기는 연습 문제의 `canonical data`에서 읽어오는데, 여기에는 테스트의 이름, 입력, 출력이 정의되어 있어요. Exercism이 테스트 스위트를 다루는 방식에 대해서는 [여기](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md)에서 더 읽어볼 수 있어요.

테스트를 자동으로 생성하면 테스트를 만들 때 생길 수 있는 사람의 실수를 없앨 수 있어요. 테스트가 canonical data와 정확히 일치하기를 바라기 때문이에요. 테스트 생성은 테스트를 최신 상태로 유지하는 것도 훨씬 쉽게 해줘요. canonical data가 바뀌면, 해당 테스트의 생성기를 실행할 때 테스트가 자동으로 갱신돼요.

canonical data 파일의 예는 [여기](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)에서 볼 수 있어요.

## 자주 쓰이는 용어

canonical data와 생성기 코드베이스를 살펴보면 공통적으로 쓰이는 용어가 많아요. 이 목록이 각 용어가 무엇을 나타내는지 이해하는 데 도움이 되면 좋겠어요.

* Canonical Data - 전체 테스트 스위트를 나타내요.
* Canonical Data Case - 하나의 테스트 케이스를 나타낸 것이에요.
* Description - 테스트의 이름이에요.
* Property - 테스트를 실행할 때 호출되는 메서드예요.
* Input - 테스트 케이스의 입력이에요.
* Expected - 테스트 케이스를 실행했을 때의 기댓값이에요.

## 간단한 생성기 추가하기

테스트 생성기를 추가하는 건 간단해요. `generators` 폴더의 `Generators.fs` 파일에 연습 문제 이름(PascalCase)으로 클래스를 추가하고, `GeneratorExercise` 추상 클래스를 상속받으면 돼요.

간단한 생성기의 예로는 Bob 연습 문제가 있어요. 소스 코드는 아래에 있지만, 저장소의 [여기](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174)에서도 볼 수 있어요.

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

이것만으로 완전히 동작하는 생성기이고, 다른 코드는 작성할 필요가 없어요. 다만 이 생성기가 이렇게 단순한 것은 테스트 스위트와 프로그램 자체가 비교적 간단하기 때문이에요.

## 복잡한 생성기 추가하기

대부분의 생성기에서는 `GeneratorExercise` 클래스의 기본 동작으로 충분해요. 하지만 더 _복잡한_ 생성기라면 가상 메서드를 하나 이상 재정의할 수 있어요:

### 메서드: RenderInput

테스트 메서드의 입력을 렌더링해요.

#### 예시

`Gigasecond` 생성기는 입력값을 (괄호로 감싼) `DateTime` 값으로 렌더링해요:

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

참고로, `key` 필드를 사용하면 특정 입력 필드에 대해서만 출력을 다르게 지정할 수 있어요. `Yacht` 생성기가 그렇게 해요:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### 메서드: RenderExpected

테스트 메서드의 기댓값을 렌더링해요.

#### 예시

`Connect` 생성기는 기댓값을 `Option<T>` 값으로 렌더링해요:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### 메서드: RenderSut

테스트 대상 시스템(SUT)을 렌더링해요. SUT는 기댓값과 비교해 검증하는 실제 값이에요.

#### 예시

`RunLengthEncoding` 생성기에는 입력을 인코딩한 다음 디코딩하면 같은 값이 나오는지 검증하는 테스트 케이스가 있어요. `RenderSut` 메서드는 존재하지 않는 `consistency` 함수를 한 번 호출하는 대신 `encode |> decode` 호출을 이어 붙이도록 재정의되어 있어요:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### 메서드: RenderArrange

테스트 메서드의 준비 부분을 렌더링해요. 이 부분에서 SUT가 만들어져요.

대부분의 경우 기본 동작이면 충분해요. 아주 특별한 경우에만 이 동작을 바꿀 필요가 있어요.

참고: 이 메서드는 `string list`를 반환하는데, 각 `string`은 테스트 파일에서 렌더링된 한 줄에 해당해요.

### 메서드: RenderAssert

테스트 메서드의 검증 부분을 렌더링해요. 이 부분에서는 SUT를 기댓값과 비교해 검증해요.

대부분의 경우 기본 동작이면 충분해요. 아주 특별한 경우에만 이 동작을 바꿀 필요가 있어요.

참고: 이 메서드는 `string list`를 반환하는데, 각 `string`은 테스트 파일에서 렌더링된 한 줄에 해당해요.

### 메서드: RenderSetup

추가적인 유틸리티/설정 메서드를 렌더링해요. 테스트 메서드에서 사용할 헬퍼 메서드를 정의할 때 쓸 수 있어요.

설정 코드는 테스트 메서드보다 _먼저_ 추가되어, 설정 메서드를 테스트 메서드에서 사용할 수 있게 해줘요.

참고: 이 메서드는 `string list`를 반환하는데, 각 `string`은 테스트 파일에서 렌더링된 한 줄에 해당해요.

#### 예시

`Zipper` 생성기는 테스트 메서드에서 반복되는 지루한 보일러플레이트 코드를 없애기 위해 사용하는 헬퍼 메서드 두 개를 추가해요:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### 메서드: RenderValue

단일 값을 렌더링해요(입력 매개변수, 기댓값, SUT를 렌더링할 때 사용돼요).

### 예시

`ComplexNumbers` 생성기는 값의 타입에 따라 다른 값으로 렌더링해요:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### 메서드: MapCanonicalDataCase

canonical data 케이스를 매핑해요. 프로퍼티를 추가하거나 제거하고 싶을 때 유용해요.

대부분의 경우 기본 동작이면 충분해요. 아주 특별한 경우에만 이 동작을 바꿀 필요가 있어요.

#### 예시

`ScaleGenerator` 생성기는 canonical data 케이스 매핑을 사용해 빠진 프로퍼티를 `null` 값으로 추가해요(이렇게 하면 나중에 처리하기가 더 쉬워져요):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### 메서드: PropertiesUsedAsSutParameter

SUT의 매개변수로 사용할 프로퍼티를 지정해요.

대부분의 경우 기본 동작이면 충분해요. 아주 특별한 경우에만 이 동작을 바꿀 필요가 있어요.

#### 예시

`RailFenceCipher`는 SUT 매개변수로 사용되는 프로퍼티를 명시적으로 정의해, 전달되는 순서를 바꿔요:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### 메서드: PropertiesWithIdentifier

식별자를 할당할 프로퍼티를 지정해요. 어떤 프로퍼티가 이 목록에 있으면, 그 값은 별도의 줄에서 그 프로퍼티만의 식별자에 할당돼요.

#### 예시

`Transpose` 생성기는 모든 프로퍼티에 식별자를 사용하기로 했어요:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### 메서드: IdentifierTypeAnnotation

어떤 경우에는 식별자에 명시적인 타입을 지정하고 싶을 때가 있어요. 흔한 예로 값이 빈 배열일 때가 그래요. 이런 경우 FsUnit이 검증을 성공적으로 실행하려면 타입 어노테이션이 필요해요.

#### 예시

`Minesweeper` 생성기는 빈 값에 `string list` 타입 어노테이션을 추가해요:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### 메서드: AdditionalNamespaces

테스트 파일에서 열어야 할 추가 네임스페이스 목록을 반환해요.

#### 예시

`Gigasecond` 생성기는 `DateTime` 인스턴스를 다루기 때문에, 추가 네임스페이스 목록에 그 네임스페이스를 추가해요:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### 메서드: AssertTemplate

사용할 검증 템플릿이에요. 전체 검증 템플릿 목록은 `generators/Templates/_Assert*.liquid`에서 볼 수 있어요.

#### 예시

`RationalNumbers` 생성기는 `"AssertEqualWithin"` 템플릿을 사용해, 실수를 특정 허용 오차로 같은지 확인할 수 있게 해줘요:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### 메서드: TestFileFormat

테스트 파일의 형식이에요. 모듈 또는 클래스 중 하나예요.

거의 모든 경우에 기본 동작이면 충분해요. 아주 드문 경우에만 이 동작을 바꿀 필요가 있어요.

#### 예시

`Grep` 생성기는 설정과 정리 메서드를 사용할 수 있도록 스스로를 테스트 클래스로 정의해요:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### 메서드: TestMethodName

테스트 메서드의 이름을 지정해요.

대부분의 경우 기본 동작이면 충분해요. 아주 특별한 경우에만 이 동작을 바꿀 필요가 있어요.

#### 예시

`Zipper` 생성기는 테스트 메서드 이름을 약간 정리해요:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### 메서드: UseFullMethodName

사용할 테스트 메서드 이름이 전체 경로를 사용할지 여부를 나타내요. 즉, 중첩된 테스트 케이스의 경우 테스트 메서드 이름 앞에 상위 설명을 붙여요.

대부분의 경우 기본 동작이면 충분해요. 그렇지 않으면 이름이 같은 테스트 메서드가 여러 개 생기는 경우에만 이 동작을 바꿀 필요가 있어요.

#### 메서드: Signature

`KindergartenGarden` 생성기는 테스트 메서드 이름이 충돌하지 않도록 전체 메서드 이름을 사용해요:

```fsharp
override __.UseFullMethodName _ = true
```

### 메서드: SkipTestMethod

테스트 메서드에 `Skip = true` 프로퍼티를 표시할지 여부를 나타내요.

거의 모든 경우에 기본 동작이면 충분해요. 아주 드문 경우에만 이 동작을 바꿀 필요가 있어요.

#### 메서드: Signature

`Markdown` 연습 문제는 리팩터링 문제라서, 모든 테스트가 이미 올바른 상태여야 해요. 그래서 어떤 테스트 메서드에도 `Skip` 프로퍼티를 추가하지 않아요:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## 기존 파일 업데이트하기

기존 연습 문제가 canonical data와 맞지 않을 수도 있어요. canonical data에 맞게 연습 문제의 스텁이나 예제를 업데이트해도 괜찮아요!

또한 기존 생성기나 테스트 스위트에서 문제를 발견하면, 업데이트하고 싶은 생성기를 열어서 변경한 다음 생성기를 실행하면 돼요.

## 생성기 실행하기

이 저장소는 [.NET Core 2.x](https://www.microsoft.com/net/core)를 기준으로 작성되어 있어요. 생성기를 실행하려면 generators 디렉터리에서 다음 명령을 실행하기만 하면 돼요:

`dotnet run`

이 명령은 정의된 모든 연습 문제 생성기를 가져와, 각 연습 문제의 모든 테스트 케이스를 생성해요. 리플렉션을 사용해 모든 연습 문제를 가져오기 때문에, 새 테스트를 추가하면 생성기를 실행할 때 그 테스트도 자동으로 포함돼요.

생성기 하나만 실행하고 싶다면, 다음 명령을 실행하면 돼요:

`dotnet run -e <exercise>`

생성기를 실행하고 나면, 해당 연습 문제의 테스트 파일로 이동해 생성 결과를 확인할 수 있어요. 예를 들어 Bob 연습 문제의 테스트 스위트는 다음 위치에 있어요:

`exercises/bob/BobTests.fs`

## 생성기 제출하기

생성기의 출력이 마음에 들면, 풀 리퀘스트를 보내주세요! 생성기와 업데이트한 테스트 스위트, 그리고 변경한 관련 파일이 있으면 함께 포함해 주세요.

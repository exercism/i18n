# 개요

`String` 안의 개별 문자는 배열에서 사용하는 것과 같은 서브스크립트 방식으로 접근할 수 있어요.
하지만 문자열에 사용하는 [인덱스][string-indices]는 정수가 _아니어서_ 직접 다룰 수 없어요.
대신 `startIndex`처럼 이미 알고 있는 다른 인덱스를 기준으로 계산해야 해요. `startIndex`는 비어 있지 않은 문자열에서 첫 번째 문자의 위치를 가리켜요. 이 계산에는 [`String`][string-docs]과 [`NSString`][nsstring-docs] 라이브러리에서 제공하는 메서드를 사용해요(`Foundation` 모듈을 가져오면 Swift의 문자열은 모든 NSString 속성과 메서드를 사용할 수 있어요).

예를 들어 다음 문자열이 있다고 해봐요.

```swift
let csv = "apple,pear,peach,orange,cherry,lime,goosberry"
```

"orange"의 "g"를 얻으려고 `csv[21]`처럼 쓸 수는 없어요. 대신 `String.Index` 타입의 값을 계산해서 그 인덱스를 넘겨야 해요.
이 인덱스들은 그 자체로 사람이 읽고 쓰라고 만든 값이 아니에요.
이런 인덱스를 _불투명 인덱스_라고 하는데, 내부에 무엇이 들어 있는지 사람이 알 필요가 없기 때문이에요.

```swift
let index = csv.index(csv.startIndex, offsetBy: 21)
csv[index]
// "g"
print(index)
// prints Index(_rawBits: 1376513)
```

다만 오프셋이 유효한 인덱스가 아니면, 즉 `startIndex`보다 앞이나 `endIndex`보다 뒤의 인덱스를 반환하게 되면 연산에서 오류가 발생해 프로그램이 중단돼요.
이 문제를 막으려면 제한 인덱스를 지정할 수 있어요.
이렇게 하면 옵셔널 인덱스가 반환되는데, 유효하지 않은 인덱스일 때는 nil을 반환해요.

```swift
let tooFar = csv.index(csv.startIndex, offsetBy: 200)
// error: Execution was interrupted, reason: EXC_BAD_INSTRUCTION (code=EXC_I386_INVOP, subcode=0x0).
let tooFarButSafe = csv.index(csv.startIndex, offsetBy: 200, limitedBy: csv.endIndex)
// nil
```

게다가 인덱스는 문자열끼리 공유할 수 없어요.
예를 들어 위에서 계산한 "orange"의 "g"에 대한 `index`를 사용해 `fam = "This is my family: 👨‍👩‍👦‍👦, this is our dog: 🐶, this is our cat: 🐱!"` 문자열을 인덱싱하면, 즉 `fam[index]`는 프로그램을 중단시켜요.

여기에는 여러 이유가 있지만, 결국은 "유니코드는 까다롭다"로 정리돼요.

일반적으로 개별 문자에 임의 접근이 필요하다면 `Array<Character>` 같은 다른 자료 구조를 쓰는 게 좋아요.

## 유용한 메서드

Swift에는 문자열의 첫 번째와 마지막 문자를 가져오는 `first`와 `last` 메서드가 있어요.
이 메서드들은 옵셔널 문자를 반환하므로, 문자열이 비어 있으면 nil을 반환해요.

```swift
let str = "Hello, world!"
print(str.first) // Prints Optional("H")
print(str.last)  // Prints Optional("!")
```

`prefix`와 `suffix` 메서드로 문자열의 일부를 가져올 수도 있어요.
이 메서드들은 정수를 인자로 받아 문자열의 처음 또는 마지막 n개 문자를 담은 부분 문자열을 반환해요.

```swift
let str = "Hello, world!"
print(str.prefix(5)) // Prints "Hello"
print(str.suffix(6)) // Prints "world!"
```

## 더 깊이 알아보기: 유니코드 인덱싱

~~~~exercism/advanced

[유니코드][unicode]는 텍스트를 인코딩하는 표준으로, 다양한 언어와 문자 체계의 수많은 문자를 담고 있어요.
유니코드는 ASCII의 상위 집합이라, 모든 ASCII 문자는 유니코드 문자이기도 해요.
유니코드는 가변 길이 인코딩이라, 어떤 문자는 다른 문자보다 더 많은 바이트를 차지해요.
그게 왜 중요한지는 다음 절에서 설명할게요.

그래서 이 문제를 실제로 보려면 (영어가 아닌) 다른 언어를 살펴봐야 해요. 독일어의 "ü" 문자를 예로 들어볼까요? (여기서는 2바이트 형태를 쓰고 있는데, 1바이트 형태도 있어요.)
언뜻 보면 한 문자 같지만 실제로는 "u"와 "¨" 두 문자예요. 그래서 "ü" 문자열의 길이를 출력하면 Python 같은 언어에서는 2가 나와요.
하지만 사용자나 프로그래머 입장에서는 한 문자라고 말할 거고, Swift도 우리와 같은 생각이에요.
그런데 왜 Swift는 그렇게 하고 Python은 그렇지 않을까요?
답은 Swift가 Python과 다른 문자열 표현 방식을 쓴다는 데 있어요.
Python에서는 문자열이 바이트의 나열로 표현돼서, 문자열의 길이는 메모리에서 차지하는 바이트 수예요.
Swift에서는 문자열이 문자의 나열로 표현돼서, 문자열의 길이는 문자열이 담고 있는 문자의 수예요.
이 차이는 아주 중요한데, Swift에서는 문자열의 길이가 메모리에서 차지하는 바이트 수와 반드시 같지는 않다는 뜻이기 때문이에요.
바로 이 점 때문에 정수로 문자열을 인덱싱할 수 없는 거예요.

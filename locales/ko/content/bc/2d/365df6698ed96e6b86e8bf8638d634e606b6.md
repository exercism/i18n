# 개요

`MACRO:` 선언은 *본문*이 컴파일 타임에 실행되는 워드예요. 본문은 컴파일 타임 스택에서 리터럴 인자를 가져다 쓰고, 그 위에 쿼테이션 하나를 남겨 둬야 해요. 그러면 컴파일러가 매크로 호출 자리에 그 쿼테이션을 대신 넣어 주기 때문에, 런타임 프로그램은 매크로를 보지 못해요. 매크로가 만들어 낸 코드만 보죠.

```factor
USING: kernel macros sequences ;

MACRO: twice ( quot -- compound )
    dup append ;
```

호출하는 쪽에서 `[ 1 + ] twice`라고 쓰면, 컴파일러는 스택에 `[ 1 + ]`를 올린 채로 본문을 실행하고, `[ 1 + 1 + ]`를 돌려받아 그 자리에 끼워 넣어요. 런타임 부담은 없어요. 매크로가 대신한 루프나 컴비네이터는 사라졌으니까요.

## 입력은 리터럴이어야 해요

본문이 컴파일 타임에 실행되기 때문에, 입력은 호출하는 자리에서 모두 *리터럴*이어야 해요. `[ … ]` 쿼테이션, 숫자, 배열, 문자열처럼요. 리터럴이 아닌 값(런타임에야 알 수 있는 값)을 넘기면 컴파일 타임 오류예요.

```factor
! works: [ 1 + ] is a literal quotation
: inc-twice ( x -- y ) [ 1 + ] twice ;

! refused: f is a literal, but the macro can't run with a non-quotation
! input where the body expects to call `append` on it
```

## 구조가 있는 입력은 구조가 있는 출력을 만들어요

흥미로운 매크로들은 *구조*(배열, 리터럴 쌍의 나열)를 받아서, 그 구조에 따라 모양이 달라지는 코드를 만들어 내요. 이 연습 문제의 `each-literal`은 리터럴 나열과 쿼테이션을 받아서, 원소마다 커링되어 인라인된 쿼테이션 사본을 하나씩 만들어 내요. 런타임 프로그램은 분기 없는 코드예요. `each`도 없고, 원소별 디스패치도 없어요. 나열을 순회하는 일은 전부 컴파일 타임에 끝난 거예요.

## 위생 문제가 없는 이유

Lisp 매크로는 *위생* 문제와 씨름해요. 지역 이름을 도입하는 매크로는 호출하는 자리의 이름과 충돌할 수 있어서, `gensym`이나 위생 시스템이 필요하죠. Factor에는 이 문제가 없어요. 쿼테이션은 *해석된 워드 참조*의 나열이거든요. 각 워드는 확장 시점에 기호적으로 조회되는 게 아니라, 파싱 타임에 조회돼요. 매크로가 만든 쿼테이션 안의 `dup`은 호출하는 자리에 어떤 이름이 있든 항상 `kernel:dup`이에요.

그 대가는 있어요. Factor 매크로는 `defmacro`처럼 새로운 바인딩을 도입할 수 없어요. 이미 파서가 본 워드들로 코드를 조립할 뿐이죠. 대부분의 메타프로그래밍에는 이걸로 충분해요.

## 인접한 형식들 (여기서 연습하지 않아요)

- `MACRO::`: `MACRO:`의 로컬 형식 변형이에요. `::`가 `:`의 로컬 형식인 것과 같아요. 본문이 입력을 한 번 넘게 참조할 때 유용해요.
- `<< … >>`: 파싱 타임 평가 블록이에요. 쿼테이션 반환 규약 없이 컴파일 타임에 평범한 Factor 코드를 실행해요. 파싱 타임에 존재해야 하는 값을 계산할 때 유용해요(예: 환경 조회로 만들어 낸 `CONSTANT:`).
- `SYNTAX:`: *파싱 워드*예요. 이것들은 좀 다른 부류예요. 값이 아니라 파서의 토큰 스트림을 다루고, 훨씬 이른 단계에서 실행돼요. 새로운 리터럴 문법(`T{ }`, `H{ }`)을 정의할 때 써요. 이 개념의 범위를 벗어나요.
- `functor:`: 하나의 명세에서 서로 관련된 워드 집합을 생성하는 선언적 템플릿이에요. 매크로 구조 위에 세워졌고, 라이브러리 작성자 영역이에요.

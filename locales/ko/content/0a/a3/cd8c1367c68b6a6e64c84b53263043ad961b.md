# 자세히 알아보기

## `jq`의 오류

`jq`의 오류는 크게 두 가지로 나뉘어요.

1. **컴파일 타임 오류**: 프로그램 자체가 잘못된 경우예요. 문법 오류, 정의되지 않은 함수나 변수 참조 등이 여기에 해당해요.
   이런 경우 `jq`는 프로그램을 아예 실행하지 않아요.

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **런타임 오류**: 프로그램은 유효하지만, 값을 처리하는 도중에 문제가 생기는 경우예요. 숫자에 문자열로 인덱싱한다거나, 잘못된 JSON 텍스트를 `fromjson`으로 파싱한다거나, 타입이 맞지 않는 인자를 함수에 넘기는 경우 등이 있어요.

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

이번 개념에서는 **런타임 오류**를 다뤄요. 오류를 어떻게 발생시키고, 어떻게 잡고, 어떻게 멈추는지 알아봐요.

잡히지 않은 런타임 오류가 발생하면 `jq`는 _표준 오류_에 메시지를 출력하고 상태 코드 `5`로 종료해요.

## 오류 발생시키기: `error`와 `error(message)`

[`error`][man-error] 필터는 오류를 발생시켜요.

- `error`는 **입력** 값을 오류 값으로 하는 오류를 발생시켜요.
- `error(message)`는 `message`의 결과를 오류 값으로 하는 오류를 발생시켜요.

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
오류 값은 문자열만이 아니라 _어떤_ JSON 값이든 될 수 있어요.
구조화된 오류를 발생시키면 `catch` 핸들러가 오류의 내용을 보고 판단을 내릴 수 있어요.

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

문자열이 아닌 오류 값이 잡히지 않으면, `jq`는 그 값을 JSON으로 출력하면서 `(not a string)` 표시를 붙여요.

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## 오류 잡기: `try`와 `catch`

[`try EXP catch HANDLER`][man-try-catch]로 오류를 잡을 수 있어요.
먼저 첫 번째 표현식이 실행되고, 여기서 오류가 발생하면 `HANDLER` 표현식이 **오류 값을 입력으로 받아** 실행돼요.
핸들러의 출력은 마치 시도한 표현식의 출력이었던 것처럼 그대로 출력돼요.

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

더 짧은 형태인 `try EXP`는 `try EXP catch empty`와 같아요. 오류는 버려지고 아무 출력도 나오지 않아요.

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
`try` 안에서 오류가 나면 **스트림의 나머지 부분이 중단돼요**.
이미 만들어진 값은 유지되지만, 오류 이후의 것은 아무것도 평가되지 않아요.

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

핸들러는 새로운 오류를 발생시킬 수도 있고, 그냥 `error`를 써서 원래 오류를 다시 발생시킬 수도 있어요.
오류 값이 핸들러의 입력이므로, 이렇게 하면 오류가 그대로 전달돼요.

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## 오류 억제하기: `?` 연산자

[`?` 연산자][man-question-mark]는 `EXP?`처럼 쓰며 `try EXP`의 줄임 형태예요.
실패하는 표현식을 아무 출력도 내지 않는 표현식으로 바꿔 줘요.

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

인덱싱 연산자에 붙어 있는 모습을 자주 볼 수 있어요.

- `.foo?`는 `.["foo"]?`예요.
- `.[]?`는 입력이 배열이나 객체일 때만 반복하고, 그 외에는 아무것도 내지 않아요.

~~~~exercism/caution
`?`는 예상하지 못한 오류까지 **모든** 오류를 억제해요.
`user`가 객체가 아닐 때 `user.name?`은 조용히 아무것도 내지 않는데, 이렇게 되면 프로그램의 데이터 문제나 오타가 숨겨질 수 있어요.
무언가가 실패했다는 사실을 알아야 한다면 `try ... catch`를 쓰거나 입력을 직접 검증해요.
~~~~

## 대체 연산자 `//`

`a // b`가 `a`가 실패할 때 `b`를 낼 것이라고 기대하는 경우가 있어요.
예전 `jq` 버전에서는 그랬지만, `jq` 1.6 이후로는 아니에요.
`//` 연산자는 오류를 억제하지 않아요.
`a`가 아무 값도 내지 않거나 `false`, `null`을 낼 때만 `b`로 대체하고, `a`에서 난 오류는 그대로 전달돼요.

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

오류에 대한 대비책이 필요하다면 `try a catch b`를 써요.

## 구조 분해 대체 연산자 `?//`

[`?//` 연산자][man-question-mark-slash-slash]는 구조 분해와 오류 처리를 결합해요.
각 바인딩 패턴을 차례로 시도해서 하나가 성공할 때까지 진행하고, 실패한 대안에서 바인딩된 변수는 `null`이 돼요.

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

여기서 첫 번째 패턴은 `c`가 `d`와 `e` 키를 가진 _객체_일 것을 기대하고, 두 번째 패턴은 `c`가 그런 객체를 담은 _배열_일 것을 기대해요.
첫 번째 입력 원소는 첫 번째 패턴에 맞고, 두 번째 원소는 그 패턴에 맞지 않아서 대신 두 번째 패턴을 시도해요.

덕분에 여러 형태 중 하나일 수 있는 입력을, `if type == ...` 같은 조건문을 길게 늘어놓지 않고도 하나의 프로그램에서 구조 분해할 수 있어요.

## 프로그램 중단하기: `halt`와 `halt_error`

때로는 오류에 대한 올바른 대응이 처리를 아예 멈추는 것일 때도 있어요.

- [`halt`][man-halt]는 더 이상의 출력 없이 `jq` 프로그램을 즉시 멈춰요. 종료 상태는 `0`이에요.
- [`halt_error`][man-halt-error]는 프로그램을 멈추고, **입력**을 꾸밈 없이, 줄바꿈도 없이 그대로 _표준 오류_에 출력한 뒤 주어진 상태 코드로 종료해요. 상태 코드를 주지 않으면 `5`예요.

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

이 필터들은 읽어야 할 입력이 더 남아 있어도 프로그램을 즉시 멈춘다는 점에 유의해요.

### 종료 상태

참고로 `jq`는 다음 종료 상태를 사용해요.

| 상태 | 의미                                          |
| :----: | ------------------------------------------------ |
| `0`    | 성공                                          |
| `2`    | 사용법 오류 (잘못된 명령줄 옵션)           |
| `3`    | 컴파일 오류                                    |
| `5`    | 런타임 오류 (`halt_error`에 인자를 주지 않은 경우 포함) |

`--exit-status` / `-e` 옵션을 쓰면 상태 코드가 마지막 출력 값을 반영해요. `true`나 숫자면 `0`, `false`나 `null`이면 `1`, 출력이 없으면 `4`예요.

## 디버깅 도우미

오류가 어디서 비롯됐는지 추적할 때는 다음 필터가 도움이 돼요.

- [`debug`][man-debug]는 입력을 그대로 통과시키면서 `["DEBUG:", <input>]`를 표준 오류에 출력해요.
  `debug(msgs)`는 `msgs`도 디버그 메시지로 출력해요.
- [`stderr`][man-stderr]는 입력을 압축된 원본 형태로 표준 오류에 출력해요.
- [`input_line_number`][man-input-line-number]는 현재 필터링 중인 입력의 줄 번호를 출력해요. 파일에 여러 JSON 텍스트가 들어 있는데 그중 하나가 잘못된 경우 특히 유용해요.
- [`$__loc__`][man-loc]는 프로그램에서 자신이 위치한 곳을 설명하는 `file`과 `line` 키를 가진 객체를 출력해요. 이 객체는 오류 메시지에 넣을 수 있어요.

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

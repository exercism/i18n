# 소개

## 오류에 맥락 더하기

Go의 기본 오류 처리는 [오류 개념][concept-errors]에서 살펴봤어요.
거기서 배웠듯이, 오류는 기본적으로 스택 트레이스를 함께 들고 다니지 않아요.
그래서 오류 자체에 문제를 파악할 만큼 충분한 정보가 담겨 있는지 확인하는 게 아주 중요해요.

지금까지 알고 있는 도구로 기존 오류에 정보를 더하려면, 원래 오류의 텍스트와 추가 정보를 합친 새 오류를 이렇게 만들 수 있어요:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

다행히도 표준 라이브러리의 `fmt` 패키지에는 이를 위한 간편한 방법이 `Errorf` 함수로 들어 있어요.
이를 이용하면 예를 들어 오류가 발생한 맥락에 대한 정보를 손쉽게 덧붙일 수 있어요.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

이렇게 오류에 정보를 더하는 방법으로 충분할 때가 많지만, 오류를 사용하는 쪽에서 바탕이 된 원래 오류를 확인하거나 가져올 수 있게 해 주고 싶은 경우도 있어요.
이렇게 맥락을 더해서 그게 가능하도록 만드는 것을 Go에서는 "오류 래핑"이라고 해요.

## 오류 래핑과 센티넬 오류 확인하기

오류 래핑은 위에서 본 코드를 아주 조금만 바꾸면 할 수 있어요.
오류를 래핑하려면 `%v` 대신 포맷 동사 `%w`를 사용해야 해요.
내부적으로 이렇게 하면, 만들어진 오류가 원래 오류를 반환하는 `Unwrap` 메서드를 구현하게 돼요.
덕분에 `errors.Is`로 특정 센티넬 오류가 "오류 체인" 어딘가에 있는지 확인할 수 있어요.
`errors.Is`는 해당 오류를 찾거나 체인이 끝날 때까지 `Unwrap`을 반복해서 호출하는 방식으로 이걸 해요.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

기본적으로는 `%v`를 쓰고, 오류를 사용하는 쪽에서 기저 오류에 접근할 수 있게 하고 싶을 때만 `%w`를 쓰는 게 좋은 관행이에요 ([Google Go Styleguide][google-go-styleguide]).

센티넬 오류인지 확인하고 싶지만 명시적으로 언래핑은 하고 싶지 않은 상황이라면, `errors.Is` 대신 `==`를 사용할 수 있어요.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

기본적으로 `errors.Is`를 사용해도 괜찮지만, 그렇게 하면 오류 체인 전체를 검색한다는 점을 항상 기억해야 해요.

## (커스텀) 오류 타입 확인하기

`errors.Is`에 대응하는 함수로, 오류 체인에서 특정 타입의 오류를 확인하고 가져올 수 있게 해 주는 게 있어요.
그 함수가 바로 `errors.As`이고, `errors.Is`와 마찬가지로 주어진 오류 타입을 체인 전체에서 찾아요.
`errors.As`는 타입에 맞는 오류를 찾으면 그때 꺼내 주기 때문에, 그 오류로 더 작업할 수 있어요. 예를 들어 특정 필드를 가져올 수 있죠.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
위 코드에서 포인터와 관련된 문법에 주의해야 해요.
코드가 제대로 동작하고 컴파일되려면 `customError`가 오류 인터페이스를 구현하는 정확한 타입이어야 해요.
여기서는 `MyCustomError` 자체가 아니라 `*MyCustomError`(`MyCustomError`에 대한 [포인터][concept-pointers])예요.

게다가 두 번째 인자는 오류 변수에 대한 포인터여야 해요.
우리 오류는 이미 포인터이기 때문에, `errors.As`에 넘기는 것은 포인터에 대한 포인터(MyCustomError에 대한)예요.
이렇게 제대로 준비되어야만 Go가 찾은 오류를 그 변수에 채워 넣을 수 있어요.
~~~~

앞에서와 마찬가지로, `Errorf`를 호출할 때 `%v`를 사용했다면 `errors.As`는 그 오류 타입을 찾지 못했을 거예요.

어떤 이유로든 언래핑하고 싶지 않다면, 대신 타입 단언을 사용할 수 있어요 (위의 `==`와 같아요).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

오류가 래핑되어 있었다면 타입 단언으로는 오류 타입을 알아낼 수 없어요.

## 커스텀 타입 오류를 언래핑할 수 있게 하기

때로는 오류에 텍스트만 덧붙여 래핑하는 것으로는 충분하지 않아요.
그럴 때는 원래 오류와 추가하고 싶은 구조화된 데이터를 함께 담는 커스텀 오류 타입을 만들 수 있어요.
오류 타입에 언래핑을 허용하고 싶다면, `Unwrap` 인터페이스를 만족하도록 `Unwrap() error` 메서드를 직접 추가하기만 하면 돼요.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

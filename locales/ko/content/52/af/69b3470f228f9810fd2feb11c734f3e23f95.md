# Rust Exercism 트랙에 기여하기

이슈와 풀 리퀘스트는 현재 자동으로 닫히고 있어요.
변경 사항을 제안하려면 [Exercism 포럼][the Exercism forum]에 글을 남겨 주세요.
포럼에서 조율된 기여라면 언제든 환영해요.

[the Exercism forum]: https://forum.exercism.org/

## 일반 정책

- [행동 강령](https://exercism.org/code-of-conduct)
- [Exercism의 PR 지침](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## 도구

`bin/`에는 bash 스크립트 형태의 도구가 일부 있어요.
훨씬 더 많은 도구가 `rust-tooling/`에 있고,
사소하지 않은 작업에는 이쪽을 우선하는 게 좋아요.

저장소를 다루는 데 유용한 명령 몇 가지가 담긴 [`mise`](https://mise.jdx.dev/) 설정도 있어요.
자유롭게 확장해도 좋아요.

CI 테스트를 로컬에서 실행하고 싶다면, `mise run test`만으로도 꽤 많은 걸 해결할 수 있어요.

## 테스트 제외와 사용자 정의 테스트 추가

연습 문제를 만들거나 업데이트하다 보면 특정 테스트를 생성하지 않기로 결정할 수 있어요.
그럴 때는 `.meta/tests.toml`에서 `include = false`로 설정하면 돼요.
제외하는 이유를 설명하는 주석을 꼭 남겨 주세요.

트랙 전용 테스트를 추가로 넣고 싶다면 `.meta/additional-tests.json` 파일에 추가할 수 있어요.
이 테스트들을 업스트림하지 않을 만한 확실한 이유가 있을 때만 이렇게 하세요.
추가 테스트에 남긴 주석은 다음 질문에 답해야 해요:
- 왜 이 테스트를 `problem-specifications`에 업스트림하지 않나요? 즉, 왜 다른 언어들에도 일반적으로 유용하지 않나요?
- 그런데 이 테스트는 왜 Rust 트랙에 유용한가요?

## 새 연습 문제 만들기

연습 문제에 관한 [Exercism 문서][Exercism documentation about practice exercises]를 먼저 읽어 보세요.

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

`mise run add-exercise`를 실행하면 연습 문제 스텁을 생성하는 데 필요한 최소한의
정보를 물어봐요.
그다음 생성된 연습 문제로 들어가서 발견한 자리 표시자를 모두 채워 넣으면 돼요.
특히 다음 작업이 포함돼요:

- `src/lib.rs`에 연습 문제 스텁 작성하기
- `.meta/example.rs`에 예제 풀이 추가하기
- `.meta/test_template.tera` 조정하기

테스트는 템플릿 엔진 [Tera]로 생성해요.
템플릿의 입력은 [`problem-specifications`]의 표준 데이터예요.

Tera 템플릿 작성에 관한 팁은 [여기](#tera-templates)에서 확인할 수 있어요.

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

제대로 구현된 연습 문제의 여러 측면은 CI에서 검사해요.
저는 이 과정을 공부하고 문서를 쓰는 데 많은 시간을 쏟기보다는, _그냥 해보는 것_ 을 추천해요.
뭔가 깨지면 고치고, 다시는 같은 일이 생기지 않도록 테스트나 자동화를 추가하세요.

`problem-specifications`에 없는 연습 문제를 처음부터 직접 만든다면,
테스트를 직접 작성해야 해요.
테스트는 복잡도가 커지는 순서로 정렬해야 해요. 그래야 학생이 하나씩 무시 설정을 풀어 가며 TDD로 연습 문제를 풀 수 있어요.
좋은 테스트 작성에 대한 더 많은 생각은 [Exercism 문서](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)를 참고하세요.

특별한 상황이 아니라면,
스텁 파일은 `cargo test --no-run`으로 컴파일되어야 해요.
그래야 스텁 파일의 시그니처가 테스트가 기대하는 시그니처와
일치하는지 확인할 수 있어요.
이를 위해 각 함수의 본문으로 `todo!()`를 사용하세요.
이것이 불가능한 정당한 이유가 있다면,
연습 문제의 `.meta/config.json`에 그 이유를 담은 `.custom."allowed-to-not-compile"` 키를
넣으세요.

## 연습 문제 업데이트하기

많은 연습 문제는 [`problem-specifications`]에서 파생돼요.
테스트 스위트와 사용자 대상 문서도 여기서 나와요.
여기서 변경을 제안하기 전에,
`problem-specifications`에서 해야 할 변경은 아닌지 먼저 확인하세요.

연습 문제를 업데이트하려면 `mise run update-exercise`를 실행하세요.
이 명령은 대부분의 작업을 `configlet sync --update`에 맡기고 테스트 생성기를 다시 실행해요.

아직 Tera 템플릿이 없는 연습 문제를 업데이트하면,
새 템플릿이 자동으로 생성돼요.
아마 어느 정도는 조정해야 할 거예요.

Tera 템플릿 작성에 관한 팁은 [다음 섹션](#tera-templates)에서 확인할 수 있어요.

## Tera 템플릿

Tera 템플릿의 전체 문서는 [여기][tera-docs]에 있어요.
다음은 우리의 특수한 요구에 잘 맞았던 몇 가지 접근법이에요.

연습 문제의 `canonical-data.json`을 보면 입력 데이터가 어떤 형태인지 알 수 있어요.
`bin/symlink_problem_specifications.sh`를 사용하면 이 데이터를
실제 연습 문제 디렉터리에 심볼릭 링크로 걸어 둘 수 있어요. 편리하죠!

입력 프로퍼티의 이름은 연습 문제마다 달라요.
기본 템플릿은 대략 이렇게 생겼어요:

```txt
let input = {{ test.input | json_encode() }};
```

이 연습 문제에 맞는 입력 필드를 추가해야 해요. 예를 들면 다음과 같아요.

```txt
let input = {{ test.input.integers | json_encode() }};
```

일부 연습 문제는 오류 반환 값을 가질 수 있어요.
데이터 구조에 따라 다르게 렌더링하려면 if-else를 사용할 수 있어요:

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

일부 연습 문제에는 학생이 구현해야 하고 따라서 테스트해야 하는 함수가 여러 개 있어요.
이런 경우 표준 데이터에 `property` 필드가 들어 있어요.
`test.property`를 기준으로 if-else 체인을 만들어, 그에 따라 다른 함수를 렌더링할 수 있어요.

일부 연습 문제는 테스트 케이스가 _테스트 그룹_ 으로 묶여 있어요.
템플릿에서 이 점을 고려해야 해요.
대부분의 경우에는 구조를 그냥 평탄화하면 돼요. (예: [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
하지만 서로 다른 그룹에 설명이 같은 테스트가 있으면, 구조를 평탄화했을 때 이름 충돌이 생겨요.
그럴 때는 그룹 설명을 사용해 테스트를 모듈로 구성할 수 있어요. (예: [`forth`](/exercises/practice/forth/.meta/test_template.tera))

[`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs)에는 몇 가지 사용자 정의 Tera 필터가 있어요.
아마도 최신일 목록은 다음과 같아요:
- `to_hex`는 정수를 16진수로 형식화해요
- `make_ident`는 임의의 문자열을 쓸 만한 Rust 식별자로 바꿔 줘요.
   테스트 설명에서 함수 이름을 만들 때 가장 유용해요.
- `fmt_num`은 숫자 리터럴을 형식화해요 (세 자리마다 `_`를 넣어요)

`rust-tooling` 크레이트에 직접 필터를 추가해도 좋아요.
여기 목록도 잊지 않고 업데이트해 주시면 좋겠어요. 🙂

꽤 복잡한 예시로는 `triangle`의 테스트 템플릿을 확인해 보세요.
테스트 케이스를 모듈로 정리하고, 어떤 테스트를 피처 게이트 뒤에 둘지 동적으로 판별해요.
이 연습 문제는 또한 좋은 테스트를 생성하는 데 필요한 정보를 더 담기 위해
`additional-tests.json`에서 업스트림의 일부 테스트 케이스를 다시 구현해요.

[tera-docs]: https://keats.github.io/tera/docs/#templates

## 학습 계획

학습 계획은 현재 품질이 낮아 비활성화되어 있어요.
결정의 배경은 [이 포럼 글](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)을 참고하세요.

더 나은 학습 계획을 만드는 일은 매우 유익하겠지만,
작업량이 많고 좋은 소통과 조율이 필요해요.
학습 계획을 만들어 본 경험이 있는 사람들과 포럼에서
계획을 꼭 논의하세요.

# 정렬

```sather
   numbers.sort;                                  -- the natural order
   words.insertion_sort_by(bind(before(_, _)));   -- an order you supply
```

## `sort`에 필요한 것

`sort`를 쓰려면 원소 타입에 `is_lt`가 있어야 해요. `INT`, `STR`, `CHAR`,
`FLTD`, `INTI`에는 모두 있어요. 직접 만든 클래스에는 직접 작성하기
전까지 없어요.

`insertion_sort_by`는 원소 타입에 아무것도 요구하지 않아요. 알아야 할
모든 것이 넘겨주는 루틴 안에 들어 있어요.

## 비교가 갖춰야 할 것

루틴은 일관된 순서를 정의해야 해요. 그렇지 않으면 결과가 정의되지 않아요.

- `before(a, b)`가 참이면 `before(b, a)`는 거짓이어야 해요.
- `a`가 `b`보다 앞서고 `b`가 `c`보다 앞서면, `a`는 `c`보다 앞서야
  해요.
- `before(a, a)`는 거짓이어야 해요.

마지막 항목에서 사람들이 자주 걸려요. `<` 대신 `<=`를 쓰면 어떤 것이
자기 자신보다 앞선다고 말하는 셈이고, 그런 비교를 받은 정렬은 어떤
결과든 내놓을 수 있어요.

## 동점

`sort`와 `insertion_sort_by`는 둘 다 **안정적**이지 않아요. 비교가
같다고 판단한 항목들은 어느 순서로 나와도 상관없고, 이 라이브러리에서는
대체로 순서가 뒤집혀 나와요.

그래서 이름으로 한 번, 승점으로 다시 한 번 정렬해서 승점이 같은 팀은
이름순으로 남기를 기대하는 요령은 여기서는 통하지 않아요. 입력 순서에
무언가를 기대는 것도 마찬가지예요.

동점이 중요하다면, **비교 안에서** 정리해요. 서로 다른 두 항목이 같은
것으로 판단되는 일이 없도록 전순서로 만들어요.

```sather
   shorter(a, b : STR) : BOOL is
      if a.size /= b.size then return a.size < b.size; end;
      return a < b;                  -- same length: alphabetical
   end;
```

동점이 생길 리 없다고 생각될 때도 이렇게 해 둘 가치가 있어요. 양방향
모두 거짓을 돌려주는 비교는 결과를 정하지 못한 채로 남기고, 그 버그는
뚜렷한 이유 없이 바뀌는 순서로 나타나요.

## 그 밖의 메서드

| 호출 | 하는 일 |
| --- | --- |
| `a.sort` | 제자리에서, 자연스러운 순서로, 안정적이지 않음 |
| `a.insertion_sort_by(lt)` | 제자리에서, 지정한 순서로, 안정적임 |
| `a.is_sorted` | 확인 |
| `a.is_sorted_by(lt)` | 지정한 순서에 맞는지 확인 |
| `a.binary_search(e)` | 정렬된 배열에서 찾기 |
| `a.binary_search_by(e, lt)` | 지정한 순서로 찾기 |

정렬되지 않은 배열에 `binary_search`를 쓰면 실패하지는 않아요. 엉뚱한
답을 내놓을 뿐이에요. 사전 조건이 바로 그렇게 말하고 있고, 컴파일러에
`-chk`를 주지 않는 한 사전 조건은 검사되지 않아요.

## 비용

삽입 정렬은 길이의 제곱에 비례하는 작업을 해요. 열두 팀짜리 순위표에는
괜찮지만 만 개의 레코드에는 맞지 않아요. `ARR_SORT_ALG::sort_by`는 같은
아이디어를 퀵 정렬로 구현한 것으로, 배열이 크고 안정성이 중요하지 않을
때 써요.

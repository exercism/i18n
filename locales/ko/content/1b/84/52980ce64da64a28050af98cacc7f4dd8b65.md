# 개요

[호출 스택][stack], 간단히 **스택**은 메모리의 가장 높은 지점에서 시작해 아래쪽으로 자라는 특별한 자료 구조예요.

## push와 pop

스택은 최소한 두 가지 연산을 지원하고, 그 연산과 이름이 같은 명령어가 있어요:

| 명령어 | 수행하는 연산                                       |
| ------ | --------------------------------------------------- |
| `push` | 스택에 원소를 추가해요                              |
| `pop`  | 가장 최근에 추가된 원소를 제거하고 반환해요         |

즉, 스택은 **후입선출(LIFO)** 자료 구조예요.

가장 최근에 추가된 원소가 있는, 스택의 현재 위치를 추적하기 위해 `rsp` 레지스터를 사용해요.

그래서 [push][push] 명령어는 피연산자 하나를 받아서, 그 피연산자의 내용을 스택에 저장해요.
스택은 아래쪽으로 자라기 때문에, `rsp`의 값은 저장한 값의 크기만큼 줄어들어요.

마찬가지로 [pop][pop] 명령어는 피연산자 하나를 받아서, 스택에서 가장 최근 값(`rsp`가 가리키는 값)을 그 피연산자에 저장해요.
그다음 `rsp`의 값은 가져온 값의 크기만큼 늘어나요.

## 지역 변수

`rsp`의 값을 직접 조작할 수도 있어요.
이 방법은 함수의 지역 변수를 만들 때 자주 쓰여요.

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

스택에 공간을 확보하는 순간, 그 공간에 저장된 값은 _정의되지 않은_ 값이라는 점에 주의해요.

~~~~exercism/note
`pop`도, `rsp`를 직접 조작하는 것도 메모리에 저장된 내용을 실제로 제거하지는 않아요.
스택에서의 "제거"는 `rsp`의 새 주소를 기준으로 한 추상적인 개념일 뿐이에요.

어떤 상황에서는 내부 값을 외부에 노출시켜 보안 문제를 일으킬 수 있어요.
이를 해결하는 한 가지 방법은 함수가 사용한 스택 공간의 내용을 0으로 지우는 거예요.
~~~~

## call과 ret

스택의 주된 목적은 호출된 함수의 반환 주소를 추적하는 거예요.

이전 개념에서 언급했듯이, 실행할 다음 명령어를 가리키는 `rip`라는 특별한 레지스터가 있어요.
이 레지스터는 프로그램의 흐름을 제어하는 데 사용되고, `jmp`나 `call` 같은 명령어에 의해 값이 바뀌어요.

`call` 명령어를 사용할 때마다 `rip`의 현재 값이 암묵적으로 스택에 푸시돼요.
그다음 명령어의 피연산자가 `rip`으로 옮겨져서, 실행이 호출된 함수에서 계속돼요.

`ret` 명령어는 반대 연산을 해요.
스택에서 값을 팝해서 `rip`에 넣고, 그래서 실행이 호출한 함수로 돌아가요.

함수에 진입한 시점에 `rsp`는 반환할 주소를 가리켜요.
이 주소가 바로 `ret`이 스택에서 팝해야 하는 주소예요.

따라서 함수 안에서 `rsp`의 값이 직접이든 `push`로든 바뀌었다면, 함수가 반환하기 전에 반드시 원래대로 되돌려야 해요.

## 피호출자 보존 레지스터와 호출자 보존 레지스터

`rsp` 외에도 함수 호출을 거쳐서 보존해야 하는 레지스터가 있어요: `rbp`, `rbx`, `r12`, `r13`, `r14`, `r15`예요.
일반적으로 호출하는 함수는, 호출된 함수가 이 레지스터들을 바꾸지 않은 상태로 그대로 쓸 수 있기를 기대해요.

즉, _호출된_ 함수는 이 레지스터들을 사용하기 전에 값을 저장하고, 반환하기 전에 원래 값으로 복원해야 해요.
그래서 이 레지스터들을 **피호출자 보존 레지스터**라고 불러요.

다른 범용 레지스터들은 호출된 함수가 바로 사용할 수 있어요.

즉, _호출하는_ 함수는 호출된 함수가 이 레지스터들을 바꿀 수도 있으니, 어떤 함수를 호출하기 전에 값을 저장해 두어야 해요.
그래서 이 레지스터들을 **호출자 보존 레지스터**라고 불러요.

_레지스터의 내용을 저장하는 가장 흔한 방법은 스택에 넣는 거예요._

## 프롤로그와 에필로그

어떤 경우에는 함수가 반환되기 전까지 스택이 많이 사용되어 여러 번 바뀔 수 있어요.
그러면 그 모든 변경 사항을 추적해서 되돌리는 게 복잡해질 수 있어요.

이럴 때 흔히 쓰는 전략은, 함수 안에서 다른 용도로는 바뀌지 않는 레지스터에 `rsp`의 주소를 저장하는 거예요.
그리고 함수가 반환하기 전, 마지막에 간단한 `mov` 명령어로 `rsp`의 값을 복원할 수 있어요.

이 목적으로 아무 레지스터나 써도 되지만, 관례적으로 `rbp`를 베이스 포인터로 사용해요.
`rbp` 자체가 피호출자 보존 레지스터라서, 보통 `push rbp`가 먼저 와요.
이 순서를 보통 **프롤로그**라고 불러요.

마지막에는 `mov rsp, rbp`로 `rsp`를 복원하고, 그다음 스택에서 팝해서 `rbp`도 복원해요.
이 순서를 보통 **에필로그**라고 불러요.

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

~~~~exercism/note
프롤로그/에필로그 순서의 주된 목적은 프로그래머가 `rsp`의 변경 사항을 추적하기 쉽게 돕는 거예요.
물론 컴파일러에게는 이게 훨씬 쉬워요.

그래서 많은 컴파일러는 가능할 때마다 프레임 포인터를 생략하고 프롤로그/에필로그를 제거하는 최적화를 수행해요.
~~~~

## 스택으로 인자 전달하기

[System V ABI][SystemV] 호출 규약에서는 보통 인자를 레지스터로 함수에 전달해요.
하지만 인자가 너무 많거나 레지스터 하나의 크기로는 부족할 때는 스택을 사용할 수 있어요.

이때는 첫 번째 인자가 `rsp`에 더 가깝도록, 값을 역순으로 스택에 추가해요.
함수 진입 시점에 `rsp`는 반환 주소를 가리키는데, x86-64에서 이 값은 8바이트예요.
그래서 스택에 있는 첫 번째 인자가 있다면 `rsp + 8`로 접근할 수 있어요:

```x86asm
mov rdi, 4   ; first argument
mov rsi, 8   ; second argument
mov rdx, 15  ; third argument
mov rcx, 16  ; fourth argument
mov r8, 23   ; fifth argument
mov r9, 42   ; sixth argument

; any remaining integer argument goes on the stack in reversed order
sub rsp, 16
mov qword [rsp], 100      ; seventh argument
mov qword [rsp + 8], 300  ; eighth argument

call many_arguments_fn ; call implicitly pushes `rip` to the stack
; so, at point of entry, 'many_arguments_fn' finds the first six integer arguments in the usual registers
; the seventh argument is found in rsp + 8
; and the eighth argument is found in rsp + 16
```

## 스택 정렬

System V ABI는 call 명령어가 실행되기 _직전_에 스택이 16바이트로 정렬되어 있어야 한다고 규정해요.
`call`은 `rip`를 스택에 푸시하기 때문에, 호출된 함수의 진입 시점에는 스택이 16바이트로 정렬되어 있지 **않아요**.

즉, 다른 함수(특히 외부 함수)를 호출하는 함수는 `call`을 사용하기 전에 스택을 정렬해야 해요.

이것은 `rsp`에서 적절한 값을 빼는 것으로 할 수 있어요.
진입 시점에서 이 값은 16의 배수보다 8만큼 커야 해요: 8, 24, 40 등이에요.
`push` 명령어는 `rsp`에서 값을 빼기 때문에, 홀수 번의 `push`로도 같은 효과를 낼 수 있어요:

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

## 레드 존

System V ABI는 `rsp` 바로 아래에 128바이트 공간을 예약해 두는데, 이 공간은 `rsp`를 조정하지 않고 사용할 수 있어요.
이 공간을 [레드 존][red-zone]이라고 불러요:

```x86asm
fn:
    mov [rsp - 8], rax ; this is safe to use because it is in the red zone
    ret                ; no need to restore rsp
```

레드 존은 리프 함수, 즉 다른 함수를 호출하지 않는 함수에서만 안전하게 사용할 수 있어요.

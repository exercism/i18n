# 자세히 알아보기

## 오류에 맥락 추가하기

Go에서 기본적인 오류 처리는 [errors 개념][concept-errors]에서 살펴봤어요.
거기서 배웠듯이, 기본적으로 오류는 스택 트레이스를 함께 들고 다니지 않아요.
그래서 오류 자체에 문제를 파악하기에 충분한 정보가 담겨 있는지 확인하는 게 아주 중요해요.

이미 알고 있는 도구로 기존 오류에 정보를 추가하고 싶다면, 원래 오류의 텍스트와 추가 정보를 합친 새로운 오류를 만들기 위해 이렇게 작성할 수 있어요:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

다행히도 표준 라이브러리의 `fmt` 패키지에는 이를 위한 간단한 방법이 `Errorf` 함수 형태로 들어 있어요.
덕분에 예를 들어 오류가 발생한 맥락에 대한 정보를 손쉽게 추가할 수 있어요.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

오류에 이미 충분한 정보가 들어 있다고 확신하지 않는 한, 함수에서 오류를 반환하기 전에 항상 맥락을 추가하는 습관을 들이는 게 좋아요.
그러면 표준 오류 처리 패턴은 이렇게 생겼어요:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

예제에서 보듯이, 오류와 추가한 메시지는 콜론으로 구분하는 것이 관례예요.
원래 오류의 메시지와 마찬가지로 맥락 메시지도 대문자로 시작하지 않고 끝에 마침표를 붙이지 않아요.

~~~~exercism/note
오류에 맥락을 추가할 때는 메시지를 "failed to ..." 같은 표현으로 시작하고 싶어지기 쉬워요.
하지만 오류가 함수 체인을 타고 올라가면서 맥락이 잔뜩 쌓일 수 있어서, 최종적으로 로그에 남거나 사용자에게 보이는 메시지가 읽기 어려워지거나 중복으로 가득 찰 수 있어요.

이해를 돕기 위한 예시를 하나 볼까요:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

그러니 맥락 메시지를 작성할 때는 이 최종 결과를 염두에 두고, 무언가가 예상대로 되지 않았다는 사실을 덧붙이지 않도록 해요.
보통은 맥락(예: 로그 레벨 "ERROR")과 원래 오류 메시지에서 충분히 드러나니까요.
~~~~

오류에 정보를 추가하는 이 방식만으로도 충분할 때가 많지만, 오류를 사용하는 쪽에서 원래의 근본 오류를 확인하거나 꺼내 쓸 수 있게 하고 싶은 경우도 있어요.
이를 가능하게 하는 방식으로 맥락을 추가하는 것을 Go에서는 "오류 래핑"이라고 해요.

## 오류 래핑과 센티널 오류 확인하기

오류 래핑은 위에서 본 코드를 아주 조금만 바꾸면 할 수 있어요.
오류를 래핑하려면 `%v` 대신 서식 동사 `%w`를 사용해야 해요.
내부적으로 이렇게 하면 결과로 만들어진 오류가 원래 오류를 반환하는 `Unwrap` 메서드를 구현하게 돼요.
덕분에 `errors.Is`로 특정 센티널 오류가 "오류 체인" 어딘가에 있는지 확인할 수 있어요.
`errors.Is`는 문제의 오류를 찾거나 체인이 끝날 때까지 `Unwrap`을 몰래 반복해서 호출하면서 그 일을 해요.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

일반적인 `%v` 서식 동사로는 `errors.Is`를 사용해 원래 오류를 확인하는 게 동작하지 않아요.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

따라서 기본적으로는 `%v`를 사용하고, 오류를 사용하는 쪽에서 근본 오류에 접근할 수 있게 하고 싶을 때만 `%w`를 사용하는 게 좋은 관행이에요 ([Google Go 스타일 가이드][google-go-styleguide]).

센티널 오류를 확인하고 싶지만 명시적으로 언랩하고 싶지 않은 상황이라면, `errors.Is` 대신 `==`를 사용할 수 있어요.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

반대로, 오류가 래핑되어 있으면 `==`는 그 오류를 알아보지 못해요.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

기본적으로 `errors.Is`를 사용하는 건 괜찮지만, 그러면 오류 체인 전체를 검색한다는 점은 항상 기억하고 있어야 해요.

## (사용자 정의) 오류 타입 확인하기

`errors.Is`에 대응하면서, 오류 체인에서 특정 타입의 오류를 확인하고 꺼내올 수 있게 해주는 함수가 있어요.
그 함수는 `errors.As`이고, `errors.Is`와 마찬가지로 주어진 오류 타입을 체인 전체에서 찾아요.
`errors.As`는 타입이 일치하는 오류를 찾았을 때만 그 오류를 추출해서, 이를테면 특정 필드를 꺼내는 등 추가 작업을 할 수 있게 해줘요.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
위 포인터와 관련된 문법에 주의해야 해요.
이 코드는 `customError`가 error 인터페이스를 구현하는 정확한 타입일 때만 제대로 동작하고 컴파일돼요.
여기서는 `MyCustomError` 자체가 아니라 `*MyCustomError`(`MyCustomError`에 대한 [포인터][concept-pointers])예요.

게다가 두 번째 인자는 오류 변수에 대한 포인터여야 해요.
오류가 이미 포인터이기 때문에, `errors.As`에 넘기는 것은 (MyCustomError에 대한) 포인터의 포인터예요.
이렇게 제대로 설정해야만 Go가 찾은 오류로 그 변수를 채울 수 있어요.
~~~~

앞에서와 마찬가지로, `Errorf`를 호출할 때 `%v`를 사용했다면 `errors.As`는 그 오류 타입을 찾지 못했을 거예요.

어떤 이유로든 언랩하고 싶지 않다면, 대신 타입 단언을 사용할 수 있어요 (위의 `==`와 같아요).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

오류가 래핑되어 있다면 타입 단언으로는 그 오류 타입을 알아낼 수 없어요.

## 사용자 정의 타입의 오류를 언랩할 수 있게 하기

때로는 오류에 텍스트를 덧붙여 래핑하는 것만으로는 충분하지 않아요.
대신 원래 오류와 추가하고 싶은 구조화된 데이터를 담는 사용자 정의 오류 타입을 만들 수 있어요.
오류 타입에서 언랩을 허용하고 싶다면, `Unwrap` 인터페이스를 만족하도록 `Unwrap() error` 메서드를 직접 추가하기만 하면 돼요.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## 여러 오류 합치기

Go 1.20에서는 내장 `errors` 패키지에 새로운 `Join` 함수가 추가됐어요.
`Join`을 사용하면 언랩, 즉 체인을 따라 특정 오류나 오류 타입을 확인하는 것이 여전히 가능한 방식으로 여러 오류를 하나로 합칠 수 있어요.
그 덕분에 오류 체인은 실제로는 오류 트리가 될 수도 있어요.
더 자세한 내용은 [릴리스 노트][release-notes]와 [문서][doc-join]에서 볼 수 있어요.

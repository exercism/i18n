# C 트랙에 기여하기

Exercism C 언어 트랙에 기여하는 데 관심을 가져 주셔서 감사해요!
새로운 연습 문제든, 툴링이나 문서의 변경이든, 이슈 제기든, 심지어 기존 이슈나 PR에 남긴 댓글 하나든 모든 기여를 환영해요.
이 파일에는 시작하는 데 도움이 될 정보가 담겨 있어요.

먼저 [Exercism 문서][Exercism docs]를 읽어 봐요. 특히 [언어 트랙에 기여하기][contributing to a language track]에 관한 정보를 챙겨 봐요. 이 문서들에 기본적인 내용이 많이 담겨 있거든요.

그다음으로, 이 저장소에 특유한 몇 가지 사항이 아래에 설명되어 있으니 참고해요.

기존 연습 문제를 고치고 개선하는 기여를 장려해요.
이 트랙의 연습 문제는 [problem-specifications][] 저장소에서 정한 표준을 따라야 해요.
공통 연습 문제의 테스트나 문서를 바꾸려면, 이 트랙의 연습 문제에 반영하기 전에 해당 저장소에 먼저 풀 리퀘스트를 올려야 하는 경우가 많아요.
확실하지 않다면, 주저하지 말고 GitHub [이슈][issue]를 열어 봐요. 그러면 변경 사항에 대해 함께 이야기해 봐요.

## 행동 강령

Exercism이 계속 환영받는 곳이 될 수 있도록 도와주세요.
[행동 강령][Code of Conduct]을 읽고 따라 주세요.

## Git 워크플로

1. 저장소를 포크하고 클론해요.
2. 클론한 저장소에 이 저장소를 새로운 원격으로 추가해요: `git remote add upstream https://github.com/exercism/c.git`
3. 새 브랜치를 만들어요: `git checkout -b name-of-branch`
4. 새 브랜치에서 평소처럼 커밋하고 푸시해요
5. 풀 리퀘스트를 올릴 준비가 되면, 충돌을 해결할 수 있도록 브랜치를 업스트림 main 위로 리베이스해요: `git fetch upstream && git rebase upstream/main` 충돌을 해결한 뒤에는 `--force`를 사용해 브랜치로 푸시해야 할 수도 있어요.
6. 모든 준비가 끝나면 브랜치로 푸시하고, 아래에 설명된 대로 풀 리퀘스트를 만들어요.

## 이슈

이 저장소에서는 GitHub [이슈][issues]로 버그, 개선 사항, 지원 요청을 관리해요.

프로젝트 전반에 관한 더 큰 논의는 [discussions][] 저장소의 이슈를 확인해 봐요.

### 좋은 첫 패치

Exercism의 코드베이스나 기능에 대한 배경 지식 없이도 해결할 수 있다고 판단되는 이슈에는 "good first patch" 라벨을 붙이려고 해요. 이런 이슈를 찾으려면 [good-first-patch][]를 검색해 봐요.

## 풀 리퀘스트

PR을 만들 때 이 간단한 [풀 리퀘스트 지침][pull request guidelines]을 따르면 좋겠지만, 꼭 필요한 건 아니에요.

풀 리퀘스트는 하나의 이슈나 변경에 집중하는 게 좋아요.
코드 스타일과 문구 변경도 환영하지만, 가능하면 이런 변경은 별도의 PR로 열어 주세요.
기존 연습 문제에 중대한 (호환성을 깨는) 변경을 가하거나 여러 연습 문제에 걸쳐 변경을 가하는 PR을 만들기 전에는 먼저 이슈를 열어 주세요. 이런 변경은 작업을 시작하기 전에 논의하는 게 가장 좋아요.

변경 사항이 연습 문제에 관한 것이라면, 풀 리퀘스트를 올리기 전에 CI 스크립트를 실행할 수 있어요. 그러지 않아도 [지속적 통합][Continuous Integration]에 설명된 대로 나중에 자동으로 실행돼요.

풀 리퀘스트를 올리면, 패치를 받아들이기 전에 변경을 요청할 때가 있어요.

첫 번째 풀 리퀘스트를 닫고 이 변경 사항을 담은 두 번째 풀 리퀘스트를 열지 말아 주세요.
풀 리퀘스트를 연 브랜치에 커밋을 더 푸시하면, 풀 리퀘스트가 자동으로 갱신돼요.

아직 main에 병합할 준비가 되지 않은 변경으로 PR을 만들고 싶다면 (예를 들어 특정 항목에 대해 논의하고 싶을 때), 평소처럼 PR을 만들되 GitHub 웹사이트 인터페이스에서 [PR을 초안으로 전환하기][convert the PR to a draft]를 사용해요. 그러면 메인테이너가 아직 병합할 준비가 되지 않았다는 걸 알 수 있어요.

커밋을 더 추가할 때와 마찬가지로, 히스토리를 변경(리베이스, 스쿼시, 수정)하고 git push --force로 포크의 브랜치를 갱신하더라도 풀 리퀘스트를 닫고 새로 열 필요는 없어요.
풀 리퀘스트는 특정 커밋이 아니라 그 브랜치를 가리켜요.

## 코딩 스타일

코드 변경 기여에 기대되는 코드 스타일은 [스타일 가이드][style guide]에 설명되어 있어요.

연습 문제 코드는 [CI][Continuous Integration] 중에 간격과 들여쓰기 스타일 규칙을 준수하는지 검사해요.
이 검사는 [`clang-format`][clang-format] CLI 도구를 사용해요.
연습 문제를 추가하거나 변경할 때는, 커밋하기 전에 로컬에서 이 도구를 실행해 변경 사항이 이 규칙을 따르는지 확인할 수 있어요.

Linux에서는 배포판의 패키지 관리자를 통해 `clang-format`을 설치할 수 있어요.
Mac에서는 [Homebrew][]로 `clang-format` 패키지를 설치할 수 있어요.

`format.sh`를 실행하면 모든 파일에 clang-format을 실행할 수 있어요.
단일 파일에 수동으로 실행하려면 다음을 실행해요:

```bash
clang-format -i $(file)
```

## 연습 문제의 구성

각 연습 문제는 `c/exercises/practice/{exercise-name}` 디렉터리에 있어야 해요.
명세에 맞는 연습 문제를 구현하는 자세한 방법은 [명세로 연습 문제 구현하기][implement-an-exercise-from-specification]를 참고해요.

연습 문제 디렉터리의 구조는 다음과 같아요 (디렉터리 이름에는 하이픈을, 파일 이름에는 밑줄을 각각 사용한다는 차이에 주의해요):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - 이 파일에는 연습 문제의 모든 테스트가 들어 있어요.  
`test-framework` - [ThrowTheSwitch][]의 테스트 하네스 [Unity][]가 들어 있는 디렉터리예요.  
  튜토리얼이 필요하다면 ThrowTheSwitch에 [Unity 시작하기][getting started with Unity]에 관한 괜찮은 가이드가 있어요.  
  사용하는 Unity 버전은 [버전][versions]에 나와 있어요. 테스트 파일의 배치는 [스타일 가이드][test-file-layout]에 설명되어 있어요.  
  테스트는 [problem-specifications][] 저장소에 있는 연습 문제의 `canonical-data.json` 파일을 만족하도록 작성해야 해요  
`{exercise-name}.c` / `{exercise-name}.h` - 연습 문제의 소스 파일이에요.  
  헤더 파일에는 [인클루드 가드][include guards]를 사용해 주세요.
  연습 문제 테스트는 저장소 루트에서 `make test`로 실행할 수 있어요.
* `makefile` - 연습 문제가 빌드될 때 사용하는 makefile이에요.  
두 가지 규칙이 필요해요,  
test: test_{exercise-name}.c를 컴파일하고 실행해요.
memcheck: test_{exercise-name}을 -fsanitize=address, -fno-common, -fno-omit-frame-pointer 플래그로 컴파일하고 실행해요
Makefile은 연습 문제 간에 거의 바뀌지 않으므로, 다른 연습 문제에서 복사하기 쉬워요.

**잊지 마세요**: 연습 문제를 트랙의 `config.json`에 추가해야 해요. 그러려면 다른 모든 트랙 연습 문제의 순서 안에서 이 연습 문제를 어디에 넣을지 가장 좋은 위치를 정해야 해요. 여기에 추가할 UUID도 생성해야 하고요. 이 두 작업 모두 [configlet][] 도구로 할 수 있어요. 이 도구는 변경을 마친 뒤 `config.json`을 검사하고 포맷해 주기까지 해요!

참고로, configlet 도구의 설치 파일을 받으려면 [configlet 릴리스 페이지][configlet releases page]를 확인해요.

## 지속적 통합

이 저장소는 GitHub 워크플로를 사용해 풀 리퀘스트에 커밋이 생길 때마다 몇 가지 도구를 실행해요.
본인의 기여에 이 워크플로를 실행하는 가장 간단한 방법은, 변경 사항을 담아 이 저장소에 PR을 열고, 그 PR을 초안으로 설정한 다음, 이 저장소의 CI 설정이 자동으로 처리하도록 맡기는 거예요.

### CI 환경

GitHub은 [호스팅된 러너][hosted runners]라고 부르는 가상 머신에서 CI를 실행해요.
워크플로는 실행되기를 원하는 러너의 일부 측면을 설정할 수 있어요.

이 저장소의 워크플로는 각각 Ubuntu 24.04에서 실행되어야 한다는 점만 지정해요. 사용하는 일부 도구가 버전에 따라 다르게 동작할 수 있어서, 워크플로는 `latest`를 참조하는 대신 특정 버전에 고정되어 있어요.

### 본인의 포크에서 CI 실행하기

원한다면 본인의 포크에서도 CI를 실행할 수 있어요. GitHub에서 이 저장소를 평소처럼 클론하면 돼요.
[`./.github/workflows/`][workflows]에 있는 YAML 파일도 똑같이 작동해요.
[`/format`][format-workflow] 자동화 액션이 제대로 작동하게 하려면, 클론한 저장소에 배포 키를 추가해야 해요.

### 워크플로

* `checks.yml`은 도구 스크립트에 `shellcheck`를 실행하고, 이어서 그 도구들 중 다음을 실행해요:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * [Lychee 링크 검사기][lychee] 액션
* `configlet.yml`은 configlet의 최신 버전을 받아온 뒤, 그것으로 트랙에 `lint` 명령을 실행해요
* `format-code.yml`은 PR의 모든 댓글에서 `/format` 문자열을 찾고, 찾으면 연습 문제에 `format.sh`를 실행한 뒤 생긴 변경 사항을 커밋해요. 커밋이 CI를 다시 트리거할 수 있으려면 배포 키가 필요해요. 배포 키는 Exercism이 직접 관리해요.
* `test.yml`은 저장소 루트에서 `make`를 실행해 모든 연습 문제를 테스트해요

### 도구

[워크플로][workflows]를 보면 GitHub이 [`./bin`][bin] 디렉터리의 도구를 실행하도록 지시받는다는 걸 알 수 있어요.
이 디렉터리의 도구들이 하는 일은 다음과 같아요:

* `check-unitybegin`은 모든 테스트 파일이 `main()` 함수 시작 부분에 `UNITY_BEGIN()` 줄을 올바르게 추가하는지 확인해요.
* `fetch-configlet`은 [저장소][configlet]에서 `configlet` 도구를 받아와요.
* `verify-unity-version`은 모든 연습 문제가 사용하는 Unity 테스트 프레임워크의 버전을 확인해요. 이 파일이 확인해야 하는 버전은 [`./docs/VERSIONS.md`][versions]에 지정되어 있어요
* `check-include-guards`는 각 연습 문제의 스텁과 예제 헤더에 사용된 인클루드 가드가 다음과 같은 올바른 형식을 쓰는지 확인해요:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet`은 [저장소][configlet]에서 `configlet` 도구를 받아와요.

### 로컬에서 도구 실행하기

커밋하기 전에 본인 컴퓨터에서 개별 도구를 실행할 수도 있어요.
먼저 필요한 프로그램(`clang-format`, [`git`][git], [`sed`][sed], [`make`][make], C 컴파일러 등)이 설치되어 있는지 확인하고, 저장소 루트에서 필요한 도구를 실행해요. 예를 들면 다음과 같아요:

```bash
~/git/c$ make
```

작업을 확인하기 위해 일부 테스트만 실행하고 싶다면, make의 타깃으로 지정할 수 있어요.

```bash
~/git/c$ make acronym all-your-base allergies
```

# はじめに

_「日付と時刻は、小さな子どもにも教えるようなものです。それがそんなに難しいものでしょうか？」_

多くのプログラマーがその過ちを犯してきました。そして、その後に訪れる経験は、健康や幸福に悪い影響を及ぼしがちです。

日付と時刻を扱う、ちょっとした規模のプログラミングをする人なら誰でも、少なくとも起こりうる問題を理解し、和らげる心づもりを持っておくべきです。

このドキュメントでは、Rが日付と時刻をどのように扱うかの概要を紹介します。ただし、詳しい内容については公式ドキュメントを参照する必要があります。

データサイエンスのための言語であるRでは、日付と時刻は特に重要です。データの多くは時系列の形で届きます。感染症の流行時の日ごとの患者数、政府が報告する月ごとの雇用統計、営巣地の鳥の個体数、主要経済圏の年間GDPなど、例を挙げればきりがありません。

_では、Rは日付と時刻の扱いを簡単にしてくれるのでしょうか？_

_残念ながら、そうではありません！_

Base Rの日付と時刻の機能は評判が良くなく、そのほとんどは今ではあまり使われていません。

[`lubridate`][web-lubridate]パッケージは大きな改善ですが、広く複雑な問題を扱うために設計された、大きく複雑なライブラリであることを覚悟してください。

もともとは独立したパッケージでしたが、`lubridate`は現在、`tidyverse`コレクションに同梱されています。読み込むには`library(lubridate)`か`library(tidyverse)`のどちらかを使います。

`lubridate`を使った作業に役立つリソースには、次のものがあります。

- [リファレンスページ][ref-lubridate]
- PDF形式の[チートシート][cheat-lubridate]
- R for Data Scienceの[章][book-dates-times]

## 日付と日時

`date`は、時刻情報を持たない、ただの1日です。

内部的には、日付は`1970-01-01`からの（符号付きの）日数として保存されます。

```R
today()
#> [1] "2026-04-22"
```

`datetime`は、日付・時刻・タイムゾーンの情報を組み合わせたものです。

内部的には、1970年の初めからのUTCタイムゾーンにおける秒数として保存されます。

```R
now()
#> [1] "2026-04-22 15:37:11 MST"  # mid-afternoon in Arizona
```

意外かもしれませんが、Rには時刻だけの値を表す内部表現がありません。

## `date`と`datetime`の値を扱う

日付や時刻でよくあるニーズは、おそらく次のようなものです。

- 適切な入力形式を解析して、日付や日時を組み立てる。
- 日付や日時から、必要な数値や文字列の形式を取り出す。
- 日付や日時の値にオフセットを適用する。
- 2つの値の間の期間を計算する。
- 現在の日付（`today()`）や日時（`now()`）を取得する。

### 文字列からの解析

日付や時刻の書き方には多くの流儀があり、それぞれの文化に特有の傾向があります。「7/6/23」のような数字だけの日付は曖昧で紛らわしく、多国籍企業で多くの高くつく失敗を引き起こしてきました（_著者は苦い実体験からこう言っています_）。

国際規格（年-月-日）は[`ISO 8601`][wiki-ISO8601]で定義されており、主に2つの利点があります。

- 解析が速く、曖昧さがない。
- 日時を通常のテキストとして扱い、アルファベット順に並べ替えられるため、並べ替えが簡単。

しかし、データサイエンスとは、手に入るデータをそのまま扱うことです。他人がどう整形するかを嘆いても、たいていは無駄です。

Base Rには、書式文字列を受け取る変換関数があります（既定はISO 8601です）。

```R
as.Date("2026-04-22")
#> [1] "2026-04-22"
as.Date("4/22/26", format = "%m/%d/%y")
#> [1] "2026-04-22"
as.POSIXct("2026-04-22 15:30:09 MST")
#> [1] "2026-04-22 15:30:09 MST"
```

書式文字列は、何十年も前から_多くの_言語に含まれている`strptime()`関数に似ています。この構文に馴染みのあるプログラマーは、lubridateの[`fast_strptime()`][ref-parse_dt]関数を任意で使うこともできます。

さらに便利なことに、`lubridate`は、フィールドの順序を名前で表す[ヘルパー関数][ref-parsing]を幅広く提供しています。どの値をどの順序で探すかが関数にわかれば、解析は目を見張るほど柔軟です。

```R
mdy("4/22/26")
#> [1] "2026-04-22"
mdy("April 22nd 26")
#> [1] "2026-04-22"
mdy("Wednesday, April 22nd 2026")
#> [1] "2026-04-22"
mdy_hm("Wednesday, April 22nd 2026, 4:14 pm")
#> [1] "2026-04-22 16:14:00 UTC"  # defaults to your OS timezone
```

### 数値からの組み立て

プログラムが日付や日時の構成要素を別々の数値として持っている場合は、[`make_date()`や`make_datetime()`][ref-make_datetime]で組み立てることができます。

指定できる構成要素は次のとおりで、順序と既定値を示しています。

```R
make_datetime(
  year = 1970L,
  month = 1L,
  day = 1L,
  hour = 0L,
  min = 0L,
  sec = 0,
  tz = "UTC"
)
#> [1] "1970-01-01 UTC"


make_datetime(2026, 4, 22, 17)
#> [1] "2026-04-22 17:00:00 UTC"
```

当然ながら、`make_date()`は年・月・日の引数だけを取ります。

### 人間が読める形式での出力

Rのコンソールは、日付や日時を自動的に文字列表現で表示します。これはたいてい便利ですが、ときに誤解を招きます。

内部的には、日付や日時は文字列ではなく数値です（加えて少数の属性があります）。文字列が期待される場面で日付（日時）を返すと問題が起きるので、変換の方法を知っておく必要があります。

簡単な方法は、Base Rの[`as.character()`][ref-ascharacter]を使うことです。これはISO 8601形式の文字列を出力します。

日時には[`format_ISO8601()`][ref-iso8601]関数もあり、希望する精度に丸めるオプションがあります。

```R
today() |> as.character()  # a date
#> [1] "2026-04-23"
now() |> as.character()  # a datetime
#> [1] "2026-04-23 09:07:09.779319"
now() |> format_ISO8601() # defaults to nearest second
#> [1] "2026-04-23T09:07:38"
```

ISO 8601の出力を見たい非プログラマーはほとんどいないので、文化に特有の日付や時刻の形式を扱えることが欠かせません。

Base Rには[`format()`][ref-format]関数があり、他の多くの言語に含まれる由緒ある`strftime()`関数に似た書式文字列を使います。

```R
format(today(), "%A, %d %B %Y")
#> [1] "Thursday, 23 April 2026"
```

このBase Rのやり方は見た目は悪いものの、信頼できます。よく使われるコードには次のものがあります。

コード | 結果
-- | --
%d | 月の日（5、17、28など）
%a | 曜日の略称（Mon、Tue、Wedなど）
%A | 曜日の完全名（Monday、Tuesdayなど）
%w | 曜日番号（0〜6、日曜が0）
%u | 曜日番号（1〜7、月曜が1）
%b | 月の略称（Jan、Febなど）
%B | 月の完全名（January、Februaryなど）
%y | 2桁の年（例：89）
%Y | 4桁の年（例：1989）
%h | 時（24時間制）
%m | 分
%s | 秒
%z | UTCからのオフセット
%Z | タイムゾーン（文字）

Lubridateは、[`stamp()`][ref-stamp]関数と、より限定された`stamp_date()`や`stamp_time()`で、より人間に優しい代替手段を提供しようとしています。

これらは、望む出力の例となるテンプレート文字列を受け取り、その形式を生成するカスタム関数を作ります。

Lubridateは形式を推測しようとしますが、しばしば曖昧さにぶつかり、誤った結果を出します。曖昧さを解消するために書式文字列（`"dmy"`など）を指定できるようにしておきましょう。

Exercismでは、`locale = "C"`を指定してシステムのロケールを迂回し、英語で処理する（テストが期待するとおりに）のも役立ちます。_ロケールは複雑です！_

```R
sf <- stamp("Saturday, June 27, 2026 at 14:45", locale = "C")
#> Multiple formats matched: "%A, %B %d, %Y at %H:%M"(1), "Saturday, %Om %d, %Y at %H:%M"(1), "Saturday, %B %d, %Y at %H:%M"(1), "%A, %Om %d, %Y at %H:%M"(0)
#> Using: "%A, %B %d, %Y at %H:%M"

sf(make_datetime(2023, 3, 29, 15, 0, 0))
#> [1] "Wednesday, March 29, 2023 at 15:00"
```

### 構成要素の設定と取り出し

Lubridateは、日付や日時の要素を取得・設定するための[多くの関数][ref-set-get]を提供しています。`year()`や`second()`のような明らかなものから、`quarter()`や`epiweek()`のようなより専門的なものまであります。

こうした関数はすべて値を取得するのに使え、そのほとんどは値の設定にも使えます。

```R
dt <- now()
dt
#> [1] "2026-04-23 15:47:11 MST"

# get
month(dt)
#> [1] 4

# set
month(dt) <- 11
dt
#> [1] "2026-11-23 15:47:11 MST"
```

`wday()`（曜日）と`month()`では、既定では整数が出力されますが、次のこともできます。

- `labels = TRUE`を設定すると、現在のロケールに対応する略称の文字列が返ります。
- さらに`abbr = FALSE`を設定すると、完全名が返ります。

```R
d <- today()
d
#> [1] "2026-04-23"
wday(d)
#> [1] 5
wday(d, label = TRUE)
#> [1] Thu
#> Levels: Sun < Mon < Tue < Wed < Thu < Fri < Sat
wday(d, label = TRUE, abbr = FALSE)
#> [1] Thursday
#> Levels: Sunday < Monday < Tuesday < Wednesday < Thursday < Friday < Saturday
```

ラベルは`categorical variables`（カテゴリ変数）で、これは別のコンセプトで扱います。値は一覧に示された`Levels`に制限され、これが並べ替えの順序も示します。

週は既定では日曜から始まりますが、`week_start`引数で変更できます（月曜にするには`1`を使います）。

```R
dt <- make_datetime(2026, 4, 23)

# default behavior
wday(dt)
#> [1] 5
wday(dt, label = T)
#> [1] Thu

# set week_start to Monday
wday(dt, week_start = 1)
#> [1] 4
```

`leap_year()`や`dst()`（夏時間が有効かどうか）など、いくつかのユーティリティ関数は`TRUE`/`FALSE`の値を返します。

月によって長さが異なるため、`days_in_month()`が整数値を返します。

## 期間

`date`と`datetime`の値はどちらも、時間軸上の一瞬を表します。

「昨日のこの時刻」や「今から1週間後」といった概念は、どう扱えばよいのでしょうか？

他の科学向け言語に馴染みのある学習者は、Pythonの`datetime.timedelta`やJuliaの`Period`型をご存じかもしれません。

対照的に、Rには期間を表す方法が3つもあり、それぞれに長所と限界があります。いつもどおり、自分の状況に最も合うものを選びましょう。

さまざまな期間は、`as.period()`、`as_duration()`、`as.interval()`で簡単に相互変換できます。

期間の種類は`is.period()`などで調べられます。

### ピリオド

`period`は、たとえば`hours(3)`のように、時計の時刻を3時間進めるのに使えます。

夏時間（DST）のような不規則さは、ほとんど無視されます。

ピリオドはすべて、単位の複数形の名前です。`years`、`weeks`などです。

```R
d <- today()
d
#> [1] "2026-04-25"

d + weeks(2)
#> [1] "2026-05-09"

# dates are coerced to datetimes at midnight if necessary
d - hours(20)
#> [1] "2026-04-24 04:00:00 UTC"

hours(3)
#> [1] "3H 0M 0S"
```

### デュレーション

`duration`は、たとえば`dhours(3)`のように、物理的な時間を3時間進めます。時計の時刻を物理的な時間からずらす、DSTのような不規則さを考慮します。

デュレーションはすべて、対応するピリオドに`d`の接頭辞を付けます。`dyears`、`dweeks`などです。

```R
dhours(3)
#> [1] "10800s (~3 hours)"
```

### インターバル

`interval`は開始時刻と終了時刻を組み合わせたもので、[`interval()`][ref-interval]関数か`%--%`中置演算子で作成します。

```R
# the next 2 lines were run about 33s apart, so now() is different
dt1 <- now()
dt2 <- now() + hours(1)

# interval(0 function)
ivl <- interval(dt1, dt2)
ivl
#> [1] 2026-04-24 16:24:54 MST--2026-04-24 17:25:27 MST

# infix operator
iv2 <- dt1 %--% dt2
iv2 == iv1
#> [1] TRUE
```

## タイムゾーン

タイムゾーンの扱いは難しいことがあります。以下の引用はPythonのドキュメントによるものですが、Rにも同じように当てはまります。

> 「世界中の時刻調整のルールは、理性的というよりも政治的で、頻繁に変わり、UTC以外にすべてのアプリケーションに適した標準は存在しません。」

タイムゾーンについての一般的なポイントをいくつか挙げます。

- `datetime`は常にタイムゾーン（`tz`）を含みます。`date`はタイムゾーンを意識しません。
- 日時のコンストラクターは、一般に[UTC][wiki-UTC]を既定とします。
- [`now()`][ref-now]関数は例外で、`tz`を含めたローカル時刻をシステムクロックから取得します。既定ではローカルの`tz`が使われますが、`now("UTC")`のように別のものを指定することもできます。

```R
# timezone defaults to UTC
local <- ymd_hm("2026-04-25 10:32")
local
#> [1] "2026-04-25 10:32:00 UTC"

# timezone can be specified
AZ <- ymd_hm("2026-04-25 10:32", tz = "America/Phoenix")
AZ
#> [1] "2026-04-25 10:32:00 MST"

# same clocktime, different tz
local - AZ
#> Time difference of -7 hours
```

タイムゾーンに関わる計算は、ピリオドよりもデュレーションを使うほうが信頼できます。

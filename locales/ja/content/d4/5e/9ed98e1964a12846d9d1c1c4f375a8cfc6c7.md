# はじめに

これまで、シラバスは型についてあまり触れていませんでしたが、Juliaに型が存在することは明らかです：

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

型を指定したことはありませんが、Juliaはそれでも型を割り当てました。

1. Juliaには`types`があり、これは設計の中心です。
2. Juliaは通常、`Type Inference`を使って型を「推測」できます。

JITコンパイラは（すべての）コードを調べ、変数がどのように使われているかを見て、その使われ方と互換性のある適切なデフォルト型を_推論_します。

## 型の昇格

これまでのコンセプトにも、最も単純な算術をはじめ、数値型を同じ型に揃える例がたくさんありました。

```julia-repl
julia> 2 + 1.3
3.3
```

整数（Int64）と浮動小数点数（Float64）を足すと、Float64の結果が得られました。
同様に：

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

上の例では、タプルは各要素の型を保持しましたが、ベクトルに変換すると、すべてが揃ってFloat64になりました。

Juliaのコンパイラは、どの型変換が可能かを理解しています。整数から浮動小数点数への変換は問題ありませんが、浮動小数点数から整数への変換は精度が失われるため、`InexactError`が発生します。
型の昇格は、式の中のすべての値を共通の型に変換します。その型は、すべての入力と互換性を持てるだけの柔軟性を備えています。

## 型の代入

簡単なチュートリアルの演習を解くだけなら型推論に頼っても問題ありませんが、大きなプログラムでは、より正確な制御が必要になることが多いです。

ほとんどの現代のプロセッサでは、整数はデフォルトで`Int64`になります。
[`Numbers`][numbers]のコンセプトで、値をデフォルト以外の特定の型に変換できることを見ました。

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

ただし、変数`x`には別の型の値を再代入できます：

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

これは`type instability`で、次のような性質があります：

- 小規模なスクリプトではとても便利です。
- 大きなプログラムではパフォーマンスと信頼性の面で良くありません。

代わりに、`::`演算子を使って`x`の型を設定できます：

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

これで`y`は`Int16`型になり、今後もずっと`Int16`型です。
そのため、コンパイラは`y`に何バイト確保すればよいかを把握でき、安定した型に依存するように残りのコードを最適化できます。
この点で、この変数はCのような静的型付け言語の変数とほぼ同じです。

## 型アサーション

上で説明した型の代入は、変数への代入の左辺で使われ、その変数の型を制約します。

`::`演算子を値、または値に評価されるものに対して使うのは、一般に、その値がこの型でなければならず、そうでなければエラーを投げるべきだという_アサーション_です。

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

よくあるのは、関数の戻り値に対してこれを使い、関数が期待どおりに動作したかを最後に簡単に確認する方法です。

## 型の階層

`Int64`、`Int16`、`String`、`Char`。これらの型はどこから_来る_のでしょうか。

多くのオブジェクト指向（OO）言語では、各型はクラスであり、サブクラス化によってクラス階層に整理され、クラスメソッドが振る舞いを定義します。

JavaとRubyはこのパターンの明らかな例ですが、Pythonも内部的には似ています。

***Juliaにはクラスがありません。***

記録されている理由は、オブジェクト指向の機能がJITコンパイラの妨げになり、実行時のパフォーマンスを損なうからです。

それでも、このコードを見てください：

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

いくつか詳細を補足します：

- `Int16`は型であり、この型の変数を作成できます。
- `Int16`は`Signed`のサブタイプであり、`supertype()`関数がそれを示してくれます。
- 型の階層があり、`Integer`、`Real`、`Number`を経て頂点の`Any`まで続いています。`subtypes()`はこの階層の枝を一覧表示してくれます。

すべての枝は`Any`で終わります。`Any`は自分自身のスーパータイプでもあるという点で唯一です。

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

つまり、Juliaには`class`の階層はありませんが、`type`の階層は_確かに_あります。

いずれ、これがどのように機能するのかを解き明かしていきますが、その前に探求すべきことはまだたくさんあります。

## 型を調べる

`typeof()`を使えば、いつもの方法で等しいかどうかを調べられます。

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

型の等価性は厳密でなければなりません。この比較方法では型の階層を考慮しないためです。

より柔軟に、`isa`は値が比較対象と同じ型か、そのサブタイプかを教えてくれます。
関数形式でも中置形式でも使えます。

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

`isa`は左側に`value`を期待し、`type`ではないことに注意してください。

この方法で2つの_型_を比較しようとすると、予期しない結果になります。
正しい演算子は`<:`です。これは今後のコンセプトで何度も登場します。

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## 抽象型と具象型

型の階層が木構造をなすことは見ました（計算機科学の意味で、根が上にあります）。

木の中の各項目は`node`で、次のカテゴリに分けられます：

1. サブタイプを持つノードは`abstract`と呼ばれます。
2. サブタイプを持たない葉ノードは`concrete`と呼ばれます。

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

これは重要な区別です。変数として`instantiated`できるのは具象型だけだからです。


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

抽象型を使おうとしても（この場合は）エラーメッセージは出ませんが、コンパイラは適切な具象型を作成します。`Integer`ではなく`Int64`です。
少なくとも、変数に整数以外を代入することは防げます：

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

したがって、抽象型を使った型の代入は、変数の型に対する_制約_であり、（上の例では）`Integer`の任意のサブタイプを許します。
これはプログラミング言語の世界では珍しいものです。Cの型の代入より弱く、最近のバージョンのPythonの型ヒントより強いのです。

`isabstracttype()`と`isconcretetype()`という関数で判定できます。
これらは単にお互いの否定ではないことに注意してください。後のコンセプトで、抽象型でも具象型でもない型があることを見ていきます。


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

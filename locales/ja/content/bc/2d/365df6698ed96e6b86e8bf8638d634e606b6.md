# 概要

`MACRO:`宣言は、*本体*がコンパイル時に実行されるワードです。本体は、コンパイル時のスタックからリテラルの引数を受け取り、スタックに1つのクオテーションを残さなければなりません。コンパイラーはそのクオテーションをマクロ呼び出しと置き換えるので、実行時のプログラムがマクロを目にすることはありません。見えるのは、マクロが生成したコードだけです。

```factor
USING: kernel macros sequences ;

MACRO: twice ( quot -- compound )
    dup append ;
```

呼び出し側が`[ 1 + ] twice`と書くと、コンパイラーは`[ 1 + ]`をスタックに置いて本体を実行し、`[ 1 + 1 + ]`を結果として受け取り、それをそのまま差し込みます。実行時のオーバーヘッドはありません。マクロが置き換えたループやコンビネーターは、跡形もなく消えているからです。

## 入力はリテラルでなければなりません

本体はコンパイル時に実行されるため、呼び出し側の入力はすべて*リテラル*でなければなりません。`[ … ]`のクオテーション、数値、配列、文字列などです。リテラルでない値（実行時にしかわからない値）を渡すと、コンパイル時エラーになります。

```factor
! works: [ 1 + ] is a literal quotation
: inc-twice ( x -- y ) [ 1 + ] twice ;

! refused: f is a literal, but the macro can't run with a non-quotation
! input where the body expects to call `append` on it
```

## 構造の入力が構造の出力を決める

面白いマクロは、*構造*（配列や、ペアのリテラルな並び）を受け取り、その構造に応じた形のコードを生成します。この演習の`each-literal`は、リテラルの並びとクオテーションを受け取り、要素ごとに、クオテーションをカリー化してインライン展開したものを1つずつ出力します。実行時のプログラムは直線的なコードです。`each`も、要素ごとのディスパッチもありません。並びの繰り返しは、すべてコンパイル時に行われました。

## なぜ衛生性の問題が起きないのか

Lispのマクロは*衛生性*と格闘します。ローカル名を導入するマクロは、呼び出し側の名前と衝突することがあり、`gensym`や衛生の仕組みが必要になります。Factorにこの問題はありません。クオテーションは*解決済みのワード参照*の並びだからです。各ワードは、展開時にシンボルとして解決されるのではなく、解析時に解決されます。マクロが組み立てたクオテーションの中の`dup`は、呼び出し側にどんな名前があっても、常に`kernel:dup`です。

その代償として、Factorのマクロは`defmacro`のように新しい束縛を導入することはできません。マクロは、パーサーがすでに見たワードからコードを組み立てます。ほとんどのメタプログラミングには、これで十分です。

## 近い形式（この演習では扱いません）

- `MACRO::`は、`MACRO:`のローカル版です。`::`が`:`のローカル版であるのと同じ関係です。本体が入力を複数回参照するときに便利です。
- `<< … >>`は、解析時評価ブロックです。クオテーションを返すという約束なしに、コンパイル時に通常のFactorコードを実行します。解析時に存在している必要がある値（たとえば、環境の参照から得られる`CONSTANT:`）を計算するのに便利です。
- `SYNTAX:`は*解析ワード*です。これはまた別種のもので、値ではなくパーサーのトークン列を操作し、さらに早い段階で実行されます。新しいリテラル構文（`T{ }`、`H{ }`）を定義するのに使います。この概念の範囲外です。
- `functor:`は、1つの仕様から関連するワードの集合を生成する宣言的なテンプレートです。マクロの仕組みの上に作られており、ライブラリ作者の領域です。

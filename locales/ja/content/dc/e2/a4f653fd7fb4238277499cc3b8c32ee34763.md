# 説明の補足

## 課題

2つのプロシージャを実装します。

- `custom_error_message message`はエラーを発生させ、`message`がそのエラーメッセージになります。
- `handle_error script`は与えられたスクリプトを実行し、何が起きたかを説明する文字列を返します：

  | スクリプトが…したとき                  | 戻り値               |
  | --------------------------------- | -------------------- |
  | 0で除算した                   | `"division by zero"`    |
  | 存在しないファイルを開いた  | `"file does not exist"` |
  | 存在しないプロシージャを呼び出した  | `"proc does not exist"` |
  | その他のエラーを発生させた            | `"unknown error"`       |
  | 成功した                          | `"success"`             |

## エラーを発生させる

Tclにはエラーを発生させるコマンドが2つあります。

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw`は第1引数に_エラーコード_を必要とします。
エラーコードは、どんな種類のエラーが起きたかをハンドラーに伝えるリストで、メッセージのテキストを解析しなくても対応できるようにします。
中身は自由です。`{MYAPP BADTHING}`はあくまで一例で、空でないリストなら何でも構いません。
慣習として、一般的なものから具体的なものへと並べます。
ハンドラーは、一致する`try ... trap`のパターン（後述）でこれを受け取ります。たとえば`trap {MYAPP BADTHING}`、すべての`MYAPP`エラーを受け取るなら`trap {MYAPP}`です。
`error`は、3番目の引数としてエラーコードを省略可能で受け取ります：`error message ?info? ?code?`。

## `catch`でエラーを処理する

[`catch`][catch]はスクリプトを実行し、エラーを発生させる代わりに整数の_完了コード_を返します：

| コード | 意味    |
| ---- | ---------- |
| 0    | `ok`       |
| 1    | `error`    |
| 2    | `return`   |
| 3    | `break`    |
| 4    | `continue` |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

省略可能な第2引数は、結果（またはエラーメッセージ）を受け取ります。
省略可能な第3引数は_オプション辞書_を受け取り、これには`-errorcode`と`-errorinfo`（スタックトレース）が入っています。

メリット：

- 小さくて柔軟です。
- `if {[catch {open $f} fh]} {...}`のような単純なケースでは短く書けます。

デメリット：

- 完了コードは自分で確認する必要があります。
  不注意に`if {[catch ...] != 0} { handle error }`と書くと、`return`、`break`、`continue`もエラーとして扱ってしまいます。
- 処理しなかったエラーは、自分で再度発生させない限り握りつぶされます。
- スクリプトが失敗したかどうかに関わらず後片付けのコードを実行する、組み込みの方法はありません。

## `try`でエラーを処理する

[`try`][try]はスクリプトを実行し、結果を最初に一致したハンドラーに渡します。
省略可能な`finally`節は必ず実行されるので、ファイルチャネルなどのリソースを解放するのに適した場所です。

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

メリット：

- 構造が明確です。結果の種類ごとに1つのハンドラーがあります。
- `finally`は必ず実行されます。
- どのハンドラーにも一致しなかった結果は、そのまま呼び出し元へ渡されます。

デメリット：

- 単純なケースでは`catch`より少し冗長です。

### `try ... on`と`try ... trap`の違い

ハンドラーには2種類あります。

`on code {msgVar optionsVar}`は_完了コード_に一致します：`ok`、`error`、`return`、`break`、`continue`です。
どのエラーも完了コードは`error`なので、`on error`では0除算とファイルが見つからないことを区別できません。
メッセージのテキストを見るしかありませんが、これはもろい方法です。メッセージは人間向けのもので、Tclのバージョンによって変わる可能性があります。

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}`は_エラーコード_に一致します。
パターンが`-errorcode`リストの前方一致であるときに、ハンドラーが一致します。
これならエラーの種類を確実に特定できます。

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

空のパターン`trap {}`は、どのエラーにも一致します。
ハンドラーは順番に確認されるので、すべてを受け取るものは最後に置きます。

## エラーコードの調べ方

`ARITH DIVZERO`はどこに書かれているのでしょうか？
ほとんどはソースコードの中だけですが、Tclが教えてくれます。
エラーが起きたあと、グローバル変数`errorCode`に直近のエラーのエラーコードが入っています：

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

プログラムの中では、オプション辞書から取得します：

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

エラーコードの最後の要素は、人間が読めるメッセージか、エラーを引き起こしたものの名前であることがよくあります。
それは`trap`のパターンには含めません。`{ARITH DIVZERO {divide by zero}}`ではなく`{ARITH DIVZERO}`をtrapします。

### よくあるエラーコード

この表は完全ではありません。
他のエラーのコードを調べるには、上で紹介した方法を使ってください。

| 状況             | 例                  | エラーコード                    |
| --------------------- | ------------------------ | ----------------------------- |
| 0による除算      | `expr {1 / 0}`           | `ARITH DIVZERO ...`           |
| 数学の定義域エラー     | `expr {sqrt(-1)}`        | `ARITH DOMAIN ...`            |
| ファイルが見つからない        | `open nosuchfile r`      | `POSIX ENOENT ...`            |
| アクセスが拒否された     | `open /root/x w`         | `POSIX EACCES ...`            |
| 不明なコマンド       | `no::such::proc`         | `TCL LOOKUP COMMAND name`     |
| 不明な変数      | `set nosuchvar`          | `TCL LOOKUP VARNAME name`     |
| 引数の数が違う  | `string length a b`      | `TCL WRONGARGS`               |
| 無効な辞書    | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`        |
| 無効なリスト          | `llength "a \{b"`        | `TCL VALUE LIST ...`          |

`POSIX`のエラーコードは、`ENOENT`、`EACCES`、`EEXIST`のような、オペレーティングシステムの`errno`名を使います。

## ヒント：スクリプトが実行される場所

`handle_error`は呼び出し元からスクリプトを受け取ります。
`try $script`で実行すると、そのスクリプトは呼び出し元ではなく`handle_error`のスコープで評価されます。
書かれた場所で評価するには、[`uplevel`][uplevel]を使います：`try {uplevel 1 $script} ...`。

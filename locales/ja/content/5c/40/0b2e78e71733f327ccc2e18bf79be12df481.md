# はじめに

## エラー

エラーは起こるものです。Elixirでは、よく「クラッシュさせておけ」と言われますが、ソフトウェアの契約を果たすために、関数呼び出しを既知の正常な状態にまで捕捉しなければならないこともあります。言語によっては、エラーを制御フローの手段として使いますが、Elixirではこのパターンは推奨されません。エラーを発生させる可能性のある関数は、名前を見ればたいてい見分けられます。エラーを発生させる関数は、名前に`!`が付いています。これは、`{:ok, value}`や`:error`を返す関数と対比できます。ライブラリの例を見てみましょう。

```elixir
Map.fetch(%{a: 1}, :b)
# => :error
Map.fetch!(%{a: 1}, :b)
# => raises KeyError
```

## try/rescue

Elixirには、`try .. rescue`を使ってエラーから捕捉するための構文があります。

```elixir
try do
  raise RuntimeError, "error"
rescue
  e in RuntimeError -> :error
end
```

この構文を見てみましょう。

- **1行目**では、`try`でブロックを宣言します。
- **2行目**には、エラーになる可能性のある関数呼び出しを書きます。ここでは`raise/2`を呼び出しています。
- **4行目**の`rescue`セクションでは、発生したエラーの_モジュール_名に対してパターンマッチを行います。
  - `->`の左側では、
    - `e`がエラー構造体にマッチします。
    - `in`はキーワードです。
    - `RuntimeError`は、捕捉したいエラーです。
      - すべてのエラーを捕捉したい場合は、モジュール名の代わりに`_`を使うか、`in`キーワードを完全に省略できます。
  - 右側では、
    - エラーがマッチしたときに実行される処理です。

### エラー構造体

このようにして捕捉するエラー（「例外」と呼ばれることもあります）は、構造体です。
Elixirでエラーを捕捉することは、めったにありません。
通常は、捕捉したエラーをログに記録したり、外部の監視サービスに送信したりしたあと、もう一度発生させます。
つまり、特定のエラー構造体の内部構造を気にする必要は、通常ありません。

[例外のコンセプト][exercism-exceptions]では、エラー構造体についてさらに詳しく学べます。独自のカスタムエラーを定義する方法も含まれます。

[exercism-exceptions]: https://exercism.org/tracks/elixir/concepts/exceptions

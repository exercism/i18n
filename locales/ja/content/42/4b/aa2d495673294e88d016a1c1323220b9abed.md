# 概要

これまでの概念では、`global`ディレクティブを使うと、あるソースファイルで定義した関数や変数を他のファイルから参照できるようになると説明しました。同じように、`extern`ディレクティブは、現在のソースファイルで使う関数や変数が別のファイルで定義されていることをアセンブラーに伝えます。

この2つのディレクティブは、モジュール化のためにアセンブリコードが他のソースファイルとやり取りする主な方法です。

これらのディレクティブから見ると、外部のコードがアセンブリで定義・使用されていても、高水準言語で定義・使用されていても、違いはありません。たとえば、高水準言語で定義された関数でも、`extern`で宣言すればx86-64のコードから使えます。

同じように、呼び出し規約は、アセンブリで定義された関数でも高水準言語で定義された関数でも共通です。さらに、オペレーティングシステム（OS）との間でも共通です。

ただし、アセンブリではデータは単なるバイト列です。そのため、連携する高水準言語がメモリをどのように管理しているかを知っておくことが大切です。

## Cの型

C言語は、アセンブリコードと連携する高水準言語としてよく選ばれます。C言語はOSとのやり取りを簡単にしてくれます。画面への出力、キーボードからの読み取り、動的メモリの確保など、多くの重要な処理に対して高水準のラッパーを提供しているからです。

このトラックではテストがCで書かれているので、ここで言語の概要をひととおり見ておきましょう。

~~~~

### 基本型

Cにはたくさんの基本型があり、そのサイズ（バイト数）は異なることがあります。その一部を、x86-64システムでの一般的なサイズとともに次の表にまとめます：

| 型        | バイト数        | 整数/浮動小数点    |
|-----------|-----------------|------------------------|
| _Bool     | 1               | 整数                   |
| char      | 1               | 整数                   |
| short     | 2               | 整数                   |
| int       | 4               | 整数                   |
| long      | 4または8        | 整数                   |
| long long | 8               | 整数                   |
| float     | 4               | 浮動小数点             |
| double    | 8               | 浮動小数点             |

これらの整数型はそれぞれ、符号付き（これが既定）または符号なしにできます。符号なしにする場合は、たとえば`unsigned int`のように明示する必要があります。

整数型には、サイズを正確に制御するために定義された別名があります：

| 別名    | バイト数        |
|---------|-----------------|
| int8_t  | 1               |
| int16_t | 2               |
| int32_t | 4               |
| int64_t | 8               |

これらの別名の先頭に`u`を付けると、符号なしの型であることを示せます。たとえば`uint64_t`です。

他に注目すべき別名には次のものがあります：

| 別名   | 型                                            |
|--------|-----------------------------------------------|
| bool   | _Bool                                         |
| size_t | 通常は符号なしの8バイト整数                   |

`_Bool`、またはその別名である`bool`は少し特別で、丸々1バイトを占めますが、`true`（`1`）と`false`（`0`）の2つの値のどちらかしかとれません。

これらの基本型の値は、整数と浮動小数点値に関する通常のルールにしたがって、関数に渡されたり、関数から返されたりします。

### 列挙型

[列挙型][enum]は、明示的に指定した複数の要素のうちの1つをとれる型です：

```c
enum example {
    example_1,
    example_2,
    example_3,
    example_4
};
```

Cでは、列挙型は暗黙的に整数型に変換されます。通常は`int`、つまり4バイトの整数です。

既定では、列挙型の最初の要素は`0`に変換され、それ以降の要素は順に次の整数に変換されます。つまり、上で定義した`enum example`では、`example_1`の値は`0`、`example_2`の値は`1`、というようになります。

列挙型の任意の要素に値を指定することもできます。その場合、次の要素の値は既定でその次の整数になります：

```c
enum example_2 {
    example_1 = 4,
    example_2 = 8,
    example_3
}; // example_3 is equal to 9
```

### メモリアドレス

Cでは、メモリアドレスは型への[ポインター][pointer]で参照し、`*`演算子で表します。たとえば、`int64_t *`は1つ以上の`int64_t`のためのメモリ位置を指します。

アドレスは通常どおり、8バイトの整数として扱われます。

### 配列

配列は、先頭要素へのポインターとして関数に渡され、関数から返されます。

```c
int64_t example_arr[] = {1, 2, 3}; // this is an array of 3 signed 8-byte integers
fn(example_arr); // this is a function that passes a pointer (int64_t *) to the beginning of the array as argument
```

配列の各要素は、配列の要素型のサイズを持ちます。たとえば上で定義した`example_arr`は、それぞれ8バイトの要素を3つ持ち、合計で24バイトになります。

配列は長さを保持しないので、終端を示す番兵の値がない限り、通常は要素数を示す別の値が必要です。

### 文字列

Cの文字列は`char`の配列で、`char`は1バイトの型です。ほとんどの文字列はASCII文字からなり、NULで終端されます。つまり、値が`0`のバイトが見つかったところで終わりです。そのため、文字列の長さを別の引数として渡す必要は通常ありません。

## Cライブラリの関数を呼び出す

`extern`ディレクティブは、あるシンボルが別のファイルで定義されていることを宣言するだけです。実際にどのように呼び出されるかは、その外部コードがどのようにリンクされるかによって変わります。

コードと一緒にリンクされる通常の関数なら、リンカーが外部関数を直接見つけられるので、普通の`call`で十分です。

ただし、`malloc`、`free`、`printf`のような標準Cライブラリの関数は通常、実行時に共有ライブラリから解決されます。そのアドレスはコードをアセンブルする時点ではわかりません。そのため、呼び出しは、既知のオフセットに置かれた[手続きリンケージテーブル（PLT）][plt]内のスタブを経由します。アセンブリから外部ライブラリの関数を呼び出すときは常に、その呼び出しをPLTから解決することを示す必要がNASMにはあります。

`elf64`（Linuxプログラムで使われる出力形式）では、呼び出しのあとに`wrt ..plt`（「pltを参照する」という意味）を付けて示します。たとえば`call printf wrt ..plt`です。

一方、`macho64`プログラム（macOSプログラムで使われる出力形式）では、関数名の前にアンダースコアを付けるだけで十分です。たとえば`extern _printf`、次に`call _printf`です。ただし、このトラックでは`macho64`のコードを`--prefix _`フラグを付けてアセンブルするので、どちらの場合でもこのアンダースコアはアセンブラーによって自動的に追加されます。たとえば`extern printf`、次に`call printf`です。

ExercismのテストランナーはLinuxイメージで動作するので、Cライブラリの関数を呼び出す解答は`wrt ..plt`を使う必要があることに注意してください。出力形式を正しく切り替えるには、アセンブル時のガードを使えます：

```x86asm
extern malloc

%ifidn __OUTPUT_FORMAT__,elf64
    call malloc wrt ..plt       ; elf64: reach the function through the PLT
%else
    call malloc                 ; macho64: the linker generates the call stub
                                ; the underscore is added automatically by an assembler flag
%endif
```

## システムコール

このトラックで動くようなユーザーレベルのプログラムが直接実行できない操作はたくさんあります。`stdin`からの読み取り、`stdout`への書き込み、動的メモリの要求、周辺機器とのやり取りなどは、すべてオペレーティングシステム（OS）が処理します。

ユーザーレベルのプログラムは、必要になったときに、それらの操作を実行するようOSに明示的に要求しなければなりません。これは[`syscall`][syscall]命令で行います。概念的には、この命令は、あらかじめ用意されたOSの手続き（「システム」コール）への呼び出しと考えることができます。

システムコールの引数は、GPRでOSに渡します：`rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`。

この順序は関数呼び出しで使われるものとほぼ同じですが、`rcx`が`r10`に置き換わっていることに注意してください。これは、`syscall`が戻りアドレスとフラグを保存するために`rcx`と`r11`を使うからです（これらは呼び出し元の関数に制御を戻す前に復元されます）。どちらのレジスタも、`syscall`のたびに破壊されるものとして扱う必要があります。

`call`とは異なり、システム「関数」を示すラベルはありません。代わりに、呼び出しの前に`rax`に入れた特定の番号で呼び出します。戻り値がある場合は、それも`rax`に入ります。

上記の規約は、Linuxに特化した[System V ABIの付録][linux-convention]で説明されており、あくまで参考情報と位置づけられています。実際には、利用できるシステムコール、その番号、エラーの報告方法はOSレベルの詳細であり、OSによって、さらには同じOSのバージョンによっても大きく異なります。

多くのCライブラリ関数や、OSが定義するその他の実際の関数は、システムコールを包む高水準のラッパーです。ABIは、素の`syscall`よりもこれらのラッパーを使うことを勧めています。またAppleは、カーネルのシステムコールインターフェースでの互換性を[保証していません][mac-qa1118]。

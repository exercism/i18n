# はじめに

## GenServer

`GenServer`（汎用サーバー）は、Elixirのプロセス間でよくあるクライアントとサーバーのやり取りを抽象化する[ビヘイビア][concept-behaviours]です。

[プロセス][concept-processes]について学んだときの、メッセージを受け取るループを覚えていますか？　`GenServer`ビヘイビアは、そうしたループを実装したり、そのようなループを実行しているプロセスとメッセージをやり取りしたりするための抽象化を提供します。これにより、状態を保ったり、非同期のコードを実行したりするのが簡単になります。

~~~~exercism/note
`GenServer`という名前は、複数の意味を背負っているので注意してください。この名前は、`GenServer`ビヘイビアを_使用_する_モジュール_を指すのにも、`GenServer`ビヘイビアを_使用_するモジュールから起動された_プロセス_を指すのにも使われます。
~~~~

`GenServer`ビヘイビアは、必須のコールバックを1つ、`init/1`を定義します。また、いくつか興味深い任意のコールバック、`handle_call/3`、`handle_cast/2`、`handle_info/3`も定義します。`GenServer`を利用する_クライアント_は、これらのコールバックを直接呼び出すことは想定されていません。代わりに、`GenServer`モジュールが、クライアントが`GenServer`プロセスとやり取りするために使える関数を提供します。

多くの場合、1つのモジュールが、_クライアントAPI_（Elixirアプリの他の部分がこの`GenServer`プロセスとやり取りするために呼び出せる関数の集まり）と、この`GenServer`のロジックを含む_サーバーコールバックの実装_の両方を定義します。

まずは`GenServer`の簡単な例を見てみましょう。そのあとで、それぞれのコールバックが何を意味するのかを学びます。

### 例

これは、長いドライブの途中でうるさい同乗者から繰り返し浴びせられる質問、つまり「まだ着かないの？」という問いに応答できるサーバーの例です。このサーバーは、その質問が何回されたかを数えていて、回数が増えるにつれてどんどんイライラした返事を返します。

```elixir
defmodule AnnoyingPassengerAutoresponder do
  use GenServer
  # Client API

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg)
  end

  def are_we_there_yet?(pid) do
    GenServer.call(pid, :are_we_there_yet?)
  end

  # Server callbacks

  @impl GenServer
  def init(_init_arg) do
    # the initial count of questions asked is always 0
    state = 0
    {:ok, state}
  end

  @impl GenServer
  def handle_call(:are_we_there_yet?, _from, state) do
    reply =
      cond do
        state <= 3 -> "No."
        state <= 10 -> "I told you #{state} times already. No."
        true -> "..."
      end

    # increase the count of questions asked
    new_state = state + 1
    # reply to the caller
    {:reply, reply, new_state}
  end
end
```

### コールバック

#### `init/1`

サーバーは、`GenServer.start/3`または`GenServer.start_link/3`を呼び出すことで起動できます。これらの関数の違いについては、[リンクの概念][concept-links]で学びました。

この2つの関数は、次のようになっています。

- 第一引数に、`GenServer`ビヘイビアを実装したモジュールを受け取ります。
- 第二引数に、`init_arg`と呼ばれる任意の値を受け取ります。名前が示すとおり、この引数は`init/1`コールバックに渡されます。
- 省略可能な第三引数に、プロセスを実行するための高度なオプションを受け取ります。これについては今は扱いません。

`GenServer.start/3`または`GenServer.start_link/3`を呼び出してサーバーを起動すると、`init/1`コールバックがブロッキングな方法で呼び出されます。`init/1`の戻り値が、サーバーを正常に起動できるかどうかを決めます。

`init/1`コールバックは、通常、次のいずれかの値を返します。

- `{:ok, state}`。サーバーは`state`を初期状態として、メッセージを受け取るループを開始します。`state`は任意の型でかまいません。
- `{:stop, reason}`。`reason`は任意の型でかまいません。サーバーはメッセージを受け取るループを開始しません。プロセスは与えられた`reason`で終了します。

他にももっと高度な可能性がありますが、今は扱いません。

サーバーのメッセージ受信ループが開始されると、`GenServer.start/3`と`GenServer.start_link/3`は`{:ok, pid}`というタプルを返します。そうでなければ、`{:error, reason}`を返します。

#### `handle_call/3`

返信を必要とするメッセージは、`GenServer.call/2`でサーバープロセスに送ることができます。この関数は、第一引数に実行中のサーバープロセスの`pid`を、第二引数にメッセージを取ります。メッセージは任意の型でかまいません。

`handle_call/3`コールバックは、同期メッセージを処理して応答する役割を担います。3つの引数を受け取ります。

1. `message` - `GenServer.call/2`の第二引数として渡された値。
2. `from` - `GenServer.call/2`を呼び出しているプロセスの`pid`。ほとんどの場合、この引数は無視できます。
3. `state` - サーバーの現在の状態。初期値が`init/1`コールバックで設定されたことを思い出してください。

`handle_call/3`コールバックは、通常、`{:reply, reply, state}`という3要素のタプルを返します。これは、タプルの2番目の要素である任意の型の`reply`が、呼び出し元に返されることを意味します。タプルの3番目の要素`state`は、このメッセージを処理した後のサーバーの新しい状態です。

他にももっと高度な可能性がありますが、今は扱いません。

~~~~exercism/note
このコールバックの役割を名前から覚えるには、
誰かに電話を「かける（call）」ことを思い浮かべてください。

相手が電話に出られる状態なら、すぐに（同期的に）返事が返ってきます。
~~~~

#### `handle_cast/2`

返信を必要としないメッセージは、`GenServer.cast/2`でサーバープロセスに送ることができます。その引数は`GenServer.call/2`と同じです。

`handle_cast/2`コールバックは、そうしたメッセージを処理する役割を担います。`message`と`state`という2つの引数を受け取ります。これらは（`from`を除いて）`handle_call/3`コールバックと同じ引数です。

`handle_cast/2`コールバックは、通常、`{:noreply, state}`という2要素のタプルを返します。

他にももっと高度な可能性がありますが、今は扱いません。

~~~~exercism/note
このコールバックの役割を名前から覚えるには、
「cast」には「投げる（throw）」という意味もあることを思い出してください。

ボトルに入れたメッセージを海に投げ込んだら、
すぐに返事が返ってくることは期待できません。
おそらく永遠に返ってこないかもしれません。
~~~~

#### `call`と`cast`のどちらを使うべきですか？

クライアントのコードがサーバーからの返信を必要としない場合でも、ほとんどの場合`call`を使います。

`call`を使うと返信を待つことになり、これがバックプレッシャーの仕組みとして働きます（クライアントが一度に大量のメッセージを送るのを防ぎます）。また、サーバーがクライアントのメッセージを受け取って処理したことを確実に知る唯一の方法は、サーバーから返信を受け取ることです。

#### `handle_info/2`

メッセージは、`GenServer.call/2`や`GenServer.cast/2`を呼ぶ以外の方法でもサーバーの受信トレイに届くことがあります。たとえば、素の`send/2`関数を呼び出す場合です。

そうしたメッセージを処理するには、`handle_info/2`コールバックを使います。このコールバックは、`handle_cast/2`とまったく同じように動作します。

`GenServer`ビヘイビアは、予期しないメッセージに関するエラーをログに記録する、`handle_info/2`のすべてを受け止める実装を提供します。このデフォルトの実装を上書きする場合は、必ず自分自身の、すべてを受け止める実装を入れるようにしてください。忘れると、予期しないメッセージを受け取ったときにサーバーがクラッシュします。

### タイムアウト

上で説明した4つのコールバックはそれぞれ、タプルの要素をもう1つ、タイムアウトを加えて戻り値を拡張できます。たとえば、`init/1`から`{:ok, state}`を返す代わりに、`{:ok, state, timeout}`を返します。

タイムアウトは、特定の期間メールボックスにメッセージが届かないことを検出するために使えます。サーバーがコールバックのいずれかからタイムアウトを返し、指定されたミリ秒数が経過してもメッセージが届かない場合、`handle_info/2`が第一引数に`:timeout`を渡して呼び出されます。

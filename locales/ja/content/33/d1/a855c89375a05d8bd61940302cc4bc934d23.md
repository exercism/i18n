# 説明の補足

## 実装上の注意

テストは3つのステップに分かれています。

すべてのテストを実行するには`go test`を使います。特定のテストだけを実行したい場合は、`-tags`オプションを使います。

例：

```bash
go test                      # run all tests
go test -tags step1          # run just step 1 tests.
go test -tags 'step1 step2'  # run step1 and step2 tests
```

テストプログラムが必要とするさまざまなものを定義したソースファイル`defs.go`が与えられます。このファイルは、ステップごとに3つのセクションに分かれています。

## ステップ1

ステップ1を完了するには、`Right`、`Left`、`Advance`、`N`、`S`、`E`、`W`、`Dir`を定義します。ステップ2に進む前に、ステップ1を完了してください。

## ステップ2

ステップ1ではロボットの動きを実装しましたが、まだシミュレーションとは言えません。たとえば、ソースコードのどこが「ロボット」なのでしょうか？　「グリッド」はどこにあるのでしょうか？　ロボットの行動をグリッド上の位置に変換する計算は、ロボットの中にあるのでしょうか、それともグリッドの中にあるのでしょうか？　現実の世界は、これとは違います。

ステップ2では、「部屋」を導入します。小さな追加のように思えますが、「部屋」「ロボット」「テストプログラム」それぞれの役割をはっきりさせ、シミュレーションの物理を明らかにし始めるために、大きな変更を加えます。

`Room`と`Robot`は関数として定義します。テストプログラムはこれらをゴルーチンとして起動することで「実体化」させます。情報は、Goのチャネルを通じて、テストプログラム、ロボット、部屋の間を行き来します。

`Room`は「物理エンジン」だと考えてください。壁とロボットがある物理的な部屋をモデル化し、シミュレーションするものです。部屋の座標空間、ロボットと壁の位置を何らかの形でモデル化し、たとえばロボットが壁を通り抜けないようにする必要があります。`Robot`は行動を実行するエージェントであってほしいのですが、`Room`には整合性の取れた真実を保ってほしいのです。

テストプログラムがチャネルを作成し、`Room`と`Robot`の両方を起動します。次に、テストプログラムが`Robot`にコマンドを送ります。コマンドを送り終えると、コマンドチャネルを閉じます。`Robot`はコマンドを受け取り、実行しようとしている行動を`Room`に伝えなければなりません。コマンドチャネルが閉じたことを検知すると、自分自身を終了しなければなりません。部屋は、ロボットの行動が物理的にどんな結果をもたらすかを解釈しなければなりません。ロボットが終了したことを検知すると、ロボットの最終的な位置と向きを伝える最終レポートをテストプログラムに送り返します。

## ステップ3

ステップ3には3つの大きな変更があります。

- ロボットは、個々のコマンドに応答するのではなく、スクリプトを実行します。
- ログチャネルを使うと、ロボットと部屋がメッセージを記録できます。
- 部屋は、複数のロボットが同時に存在して動作することを可能にします。

`Room3`から送られる最終的な位置レポートでは、ロボットチャネルから受け取ったのと同じスライスを、位置と向きを更新したうえでそのまま返してかまいません。次の場合には、ログチャネルにメッセージを送る必要があります。

- 名前のないロボット
- ロボットの名前の重複
- 同じ場所に配置されたロボット
- 部屋の外に配置されたロボット
- スクリプト内の未定義のコマンド
- 未知のロボットからの行動
- 壁に進もうとするロボット
- 別のロボットに進もうとするロボット

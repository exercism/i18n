# Markdown仕様

以下は、Exercism内のすべてのMarkdownファイルがとるべき構成です。

このドキュメントにあるルールの一部は、まだExercism全体には実装されていません。
修正のためのPRを歓迎します。
すべてのルールはCI（継続的インテグレーション）とリントツールに追加されつつあり、新しい変更ではこれらに従うようにしてください。

## 見出し

- すべてのファイルは、レベル1の見出し（`# Some heading text`）で始まる必要があります。
- レベル1の見出しは、GitHubなどで表示するためだけに存在します。
- ファイルがExercismによってレンダリングされる場合（たとえばウェブサイトに表示される、CLIでレンダリングされるなど）、この見出しは削除され、文脈に合った見出しが挿入されます。
- 見出しは、前の見出しから1レベルより深く下げることはできません（たとえば`##`の次に置けるのは`###`までで、`####`は置けません）。
- レベル1（`#`）の見出し1つ以外では、レベル2（`##`）、レベル3（`###`）、レベル4（`####`）の見出しだけを使えます。

## リンク

[参照リンク][reference-links]を使うようにしてください。参照リンクはMarkdownファイルの末尾で定義し、参照スラッグに割り当てて、本文中ではそのスラッグで参照します。

この方法なら、リンクを更新する場所が1か所で済むため、メンテナンスが楽になります。

例：

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

リンクには、URLそのものを本文に書くのではなく、必ずアンカーテキストを付けてください。たとえば、次の例はアンカーテキストを使っていないため、読みにくくなっています。

```
If you want some more information, please visit https://google.com.
```

アンカーテキストにリンクを張るほうが、理解しやすく、文脈もつかみやすくなります。

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

これは次のように表示されます。「もっと情報が欲しい場合は、[Google][google-link]が役に立つリソースです。」

## コード

コードの要素（関数やキーワードなど）に言及するときは、そのコードをバッククォートで囲みます：

```
- The `printf()` function writes to the console.
```

これは次のように表示されます：

- `printf()`関数はコンソールに出力します。

より複雑なコード（複数行のコードなど）は、3つのバッククォートで囲みます。シンタックスハイライトを有効にするには、開始の3つのバッククォートの後に[言語識別子][language-identifier]を指定します：

````python
```python
# Define a variable
album = "Abbey Road"
```
````

可能であれば、そのコードが提示される環境に最も合った形で整形してください。使用している言語のドキュメントがあれば、参照してください。

たとえば、PythonにはREPL（read-eval-print loop：コードを読み込み、評価して結果を出力する対話型の環境）があり、プログラマーはターミナルに直接コードを入力できます。コードをデバッグしているときや、関数をローカルで実行して動作を確かめたいときは、その場で対話的に入力できたほうが便利なので、REPLを使うことが多いでしょう。こうした場合は、REPLに入力するときのように、先頭に`>>>`を付けた形でサンプルコードを整形するのが好ましいです。

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

それ以外の場合は、`.py`ファイルにあるときと同じようにコードを整形したほうが自然なことがあります。こうすると学習者は、自分でコードを書くときの形に近いものを見ながら学べます。

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

どちらにすべきか迷ったときの簡単な見分け方は、学習者がターミナルで実行できるコードなら、その形で整形するというものです。Exercismが実行する可能性のあるコード（テストや、学習者が書くライブラリのコードなど）であれば、実行できるコードとして整形するのが基本です。

## 特別なブロック（admonitionと呼ばれることもあります）

本文にはなじまない補足を抜き出して文書に追加できる、特別な種類のブロックをサポートしています。

<img width="500" alt="Markdownのnoteブロック" src="https://user-images.githubusercontent.com/20866761/139531109-0c0f3ea5-b589-44ff-93ab-d901a45edc56.png">

<img width="500" alt="Markdownのcautionブロック" src="https://user-images.githubusercontent.com/20866761/139531234-9b58b9ab-524b-44fd-bbcb-4e10f2927d27.png">

<img width="500" alt="Markdownのadvancedブロック" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

3種類のブロックをサポートしています：

- **exercism/note:** 特別な補足情報を抜き出すブロック
- **exercism/caution:** 知っておくべきこと、または注意して扱うべきこと
- **exercism/advanced:** もっと深く掘り下げたい人、またはより高度な知識があることが前提の人だけに関係する情報

すべてのブロックは4つのチルダを使って、次の形で書きます：

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

（注：例外的な状況では、バッククォートや別の数のチルダを使ってもかまいません）

## レイアウト

### 1行につき1文

段落は、1行につき1文で書きます。この考え方の理由は[Ascii Doctorのドキュメント][asciidoctor]でわかりやすく説明されています。

たとえば、1つの段落は次のように書きます：

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## リスト

順序なしリストの箇条書きマーカーには、ハイフン（`-`）を使います。

## コメント

- HTMLコメントよりもMarkdownコメントを優先してください（たとえば`<!-- Actual comment -->`ではなく`[comment]: # (Actual comment...)`を使います）

Markdownコメントが削除されるかどうかは、commonmarkを通してレンダリングしたときにコメントがどう見えるかを[babelmark3]で確認すればテストできます。

## インラインHTML

- インラインHTMLは使えますが、控えめにしてください
- 使える場合は、必ずMarkdownネイティブの代替手段を使ってください（たとえば`<h1>...</h1>`ではなく`# ...`を使います）

## 画像

ウェブサイトはライトテーマとダークテーマに対応しているため、コミュニティから投稿された画像はどちらのテーマでもきれいに表示される必要があります。
これを解決するには、画像名の後ろ（拡張子の前）に次の接尾辞を付けます：

1. 画像名を`-invertible`で終わらせます（例：`graph-invertible.svg`）。ダークテーマで表示されるとき、画像は自動的に反転されます（`filter: invert(100%)`による）。
1. 画像名を`-light`で終わらせ（例：`graph-light.png`）、さらにダークテーマ対応版として`-dark`で終わるもの（この場合は`graph-dark.png`）も作成します。ユーザーのテーマに応じて、正しい画像が自動的に表示されます。

どちらの接尾辞も付いていない画像は、両方のテーマでそのまま使われます。
つまり、グレースケールの画像を作りたい場合は、まずライトテーマで見栄えがするように作り、それを反転可能に設定するのが一般的です。
一方、色をたくさん使った画像の場合は、2つのバリエーションを作るといいでしょう。

画像を表示するMarkdownには、完全な画像名（`-invertible`を含む）を書いてください。
ライト用/ダーク用のものは、`-light`のほう**だけ**を含めます。
この仕組みは、すべてのMarkdownドキュメントで守られます。

## 自動フォーマット

一部のリポジトリでは、すべてのMarkdownが一貫した形式でフォーマットされるように[prettier][prettier]を使っています。これには次のような利点があります：

- フォーマットについての議論が不要になります。
- エディターやIDEとの連携が優れており、保存時にファイルをフォーマットできます。
- フォーマットのCIチェックを簡単に追加できます。
- スクリプトを使ってファイルを簡単に自動フォーマットできます。

こうしたことはすべて、レビューでのやり取りを大幅に減らすのに役立ちます。やり取りが増えると、レビューする側もされる側も苛立ってしまいます。

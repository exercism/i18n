# はじめに

`GenServer`（汎用サーバー）は、Elixirのプロセス間でよくあるクライアントとサーバーのやり取りを抽象化する[ビヘイビア][concept-behaviours]です。

[プロセス][concept-processes]について学んだときの、receiveのループを覚えていますか？　`GenServer`ビヘイビアは、そのようなループを実装するための抽象化と、そのループを実行するプロセスとメッセージをやり取りするための抽象化を提供します。状態を保ちながら、非同期のコードを実行しやすくなります。

~~~~exercism/note
`GenServer`という名前は、いくつもの意味を持つので注意してください。これは、`GenServer`ビヘイビアを_使う_モジュールを指すこともあれば、`GenServer`ビヘイビアを_使う_モジュールから起動された_プロセス_を指すこともあります。
~~~~

`GenServer`ビヘイビアは、必須のコールバックである`init/1`と、いくつかの興味深い任意のコールバック、`handle_call/3`、`handle_cast/2`、`handle_info/3`を定義します。`GenServer`を使う_クライアント_は、これらのコールバックを直接呼び出すことは想定されていません。代わりに、`GenServer`モジュールが、クライアントが`GenServer`プロセスとやり取りするために使える関数を提供します。

多くの場合、1つのモジュールが_クライアントAPI_と_サーバーコールバックの実装_の両方を定義します。クライアントAPIとは、Elixirアプリの他の部分がこの`GenServer`プロセスとやり取りするために呼び出せる関数の集まりです。サーバーコールバックの実装には、この`GenServer`のロジックが入っています。

まずは`GenServer`の簡単な例を見てみましょう。その後で、それぞれのコールバックが何を意味するのかを学びます。

## 例

これは、長いドライブ中にうるさい同乗者が何度も繰り返す質問、すなわち「もう着いた？」に応答できるサーバーの例です。このサーバーは、この質問が何回されたかを数えていて、回数が増えるほど、いら立った返事を返します。

```elixir
defmodule AnnoyingPassengerAutoresponder do
  use GenServer
  # Client API

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg)
  end

  def are_we_there_yet?(pid) do
    GenServer.call(pid, :are_we_there_yet?)
  end

  # Server callbacks

  @impl GenServer
  def init(_init_arg) do
    # the initial count of questions asked is always 0
    state = 0
    {:ok, state}
  end

  @impl GenServer
  def handle_call(:are_we_there_yet?, _from, state) do
    reply =
      cond do
        state <= 3 -> "No."
        state <= 10 -> "I told you #{state} times already. No."
        true -> "..."
      end

    # increase the count of questions asked
    new_state = state + 1
    # reply to the caller
    {:reply, reply, new_state}
  end
end
```

## コールバック

### `init/1`

サーバーは、`GenServer.start/3`または`GenServer.start_link/3`を呼び出すことで起動できます。これらの関数の違いについては、[リンクの概念][concept-links]で学びました。

これらの2つの関数には、次の特徴があります。

- 1つ目の引数として、`GenServer`ビヘイビアを実装したモジュールを受け取ります。
- 2つ目の引数として、`init_arg`と呼ばれる任意の値を受け取ります。名前のとおり、この引数は`init/1`コールバックに渡されます。
- 3つ目の引数として、省略可能な、プロセスの実行に関する高度なオプションを受け取ります。これについては今回は扱いません。

`GenServer.start/3`または`GenServer.start_link/3`を呼び出してサーバーを起動すると、`init/1`コールバックがブロッキングで呼び出されます。サーバーを正常に起動できるかどうかは、`init/1`の戻り値で決まります。

`init/1`コールバックは、通常、次のいずれかの値を返します。

- `{:ok, state}`。サーバーは、`state`を初期状態としてreceiveのループを開始します。`state`は任意の型でかまいません。
- `{:stop, reason}`。`reason`は任意の型でかまいません。サーバーはreceiveのループを開始しません。プロセスは与えられたreasonで終了します。

このほかにも、今回は扱わない高度な使い方があります。

サーバーのreceiveのループが開始されると、`GenServer.start/3`と`GenServer.start_link/3`は`{:ok, pid}`というタプルを返します。そうでない場合は`{:error, reason}`を返します。

### `handle_call/3`

返事が必要なメッセージは、`GenServer.call/2`でサーバープロセスに送ることができます。この関数は、1つ目の引数として実行中のサーバープロセスの`pid`を、2つ目の引数としてメッセージを取ります。メッセージは任意の型でかまいません。

`handle_call/3`コールバックは、同期メッセージの処理と応答を担当します。これは3つの引数を受け取ります。

1. `message`は、`GenServer.call/2`の2つ目の引数として渡された値です。
2. `from`は、`GenServer.call/2`を呼び出したプロセスの`pid`です。ほとんどの場合、この引数は無視できます。
3. `state`は、サーバーの現在の状態です。初期値は`init/1`コールバックで設定されたことを覚えておきましょう。

`handle_call/3`コールバックは、通常、`{:reply, reply, state}`という3要素のタプルを返します。これは、タプルの2番目の要素である`reply`（任意の型でかまいません）が呼び出し元に返されることを意味します。タプルの3番目の要素である`state`は、このメッセージを処理したあとのサーバーの新しい状態です。

このほかにも、今回は扱わない高度な使い方があります。

~~~~exercism/note
このコールバックの役割を名前で覚えるには、誰かに電話を「かける」ことを思い浮かべてください。

相手が電話に出られれば、すぐに（同期的に）返事が返ってきます。
~~~~

### `handle_cast/2`

返事が不要なメッセージは、`GenServer.cast/2`でサーバープロセスに送ることができます。引数は`GenServer.call/2`と同じです。

`handle_cast/2`コールバックは、そのようなメッセージの処理を担当します。`message`と`state`の2つの引数を受け取ります。これらは`handle_call/3`コールバックと同じ引数です（`from`を除く）。

`handle_cast/2`コールバックは、通常、`{:noreply, state}`という2要素のタプルを返します。

このほかにも、今回は扱わない高度な使い方があります。

~~~~exercism/note
このコールバックの役割を名前で覚えるには、"cast"には「投げる」という意味もあることを思い出してください。

ボトルメッセージを海に投げ込んでも、すぐに返事が返ってくることは期待できません。ひょっとすると、永遠に返ってこないかもしれません。
~~~~

### `call`と`cast`、どちらを使うべきか

クライアントのコードがサーバーからの返事を必要としない場合でも、ほとんどの場合は`call`を使いましょう。

`call`を使うと返事を待つので、これがバックプレッシャーの仕組みとして働きます（クライアントが一度に多くのメッセージを送りすぎるのを防ぎます）。また、サーバーがクライアントのメッセージを受け取って処理したことを確かめる唯一の方法は、サーバーからの返事を受け取ることです。

### `handle_info/2`

メッセージは、`GenServer.call/2`や`GenServer.cast/2`を呼び出す以外の方法でもサーバーの受信トレイに届くことがあります。たとえば、素の`send/2`関数を呼び出す場合です。

そのようなメッセージを処理するには、`handle_info/2`コールバックを使います。このコールバックは、`handle_cast/2`とまったく同じように動作します。

`GenServer`ビヘイビアは、予期しないメッセージについてのエラーをログに記録する、`handle_info/2`のすべてのメッセージを受け取る実装を提供しています。このデフォルトの実装を上書きする場合は、必ず自分自身でもすべてのメッセージを受け取る実装を入れてください。忘れると、予期しないメッセージを受け取ったときにサーバーがクラッシュします。

## タイムアウト

上で説明した4つのコールバックは、戻り値にタプルの要素をもう1つ、タイムアウトを追加できます。たとえば、`init/1`から`{:ok, state}`を返す代わりに、`{:ok, state, timeout}`を返します。

タイムアウトは、一定のあいだメールボックスにメッセージが届かないことを検知するために使えます。サーバーがコールバックのいずれかでタイムアウトを返したあと、指定したミリ秒数が経過してもメッセージが届かなければ、`handle_info/2`が1つ目の引数に`:timeout`を渡して呼び出されます。

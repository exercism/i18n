# リダイレクト入門

コマンドラインインターフェースの世界では、プログラムはよく3つの標準データストリームを扱います。

1. **標準入力**（`stdin`）：プログラムが入力を受け取る場所です（通常はキーボードから）。
1. **標準出力**（`stdout`）：プログラムが通常の出力を送る場所です（通常は端末の画面へ）。
1. **標準エラー出力**（`stderr`）：プログラムがエラーメッセージを送る場所です（通常は端末の画面へ）。

これらは、[パイプラインとコマンドリスト][pipelines]の章ですでに紹介しましたね。

~~~~exercism/note
パイプラインは、リダイレクトの一種と考えることができます。あるプログラムの標準出力が、別のプログラムの標準入力へ直接送られるからです。
パイプラインについてはすでに扱いました。
この概念では、ファイルへのリダイレクトと、ファイルからのリダイレクトを扱います。
~~~~

シェルのリダイレクトは、これらのストリームの送り先を変えられる強力な仕組みです。
プログラムがキーボードから読み取ったり画面に書き出したりする代わりに、入力をファイルから読み込ませたり、出力をファイルへ送ったりできます。
この仕組みによって、プログラムがデータをどう扱うかを、柔軟に、細かく制御できます。

## 主なリダイレクト演算子

よく使うリダイレクト演算子と、それぞれの働きを紹介します。

### `>`（出力のリダイレクト）

* 目的：コマンドの標準出力（`stdout`）をファイルへリダイレクトします。
* 動作：
  * ファイルが存在しなければ、新しく作成されます。
  * ファイルが存在すれば、中身は上書きされます。
* 例：

  ```bash
  # Sends the output of 'ls -l' to 'file_listing.txt'
  ls -l > file_listing.txt
  ```

~~~~exercism/caution
リダイレクトは、コマンドが実行される**前に**行われます。
つまり、読み取りたいファイルと同じファイルへリダイレクトすることはできません。

```bash
date > date.txt         # populate the file with the current date
cat date.txt > date.txt # 'date.txt' is now empty!
```

上の例の2つ目のコマンドでは、

1. まずBashが、リダイレクトで指定されたファイルを切り詰めます。
   これによって以前の中身が失われ、空のファイルになります。
2. 次にbashが、空になったばかりのファイルを読み取ります。
3. そしてbashが、その中身（つまり何もない状態）をファイルへ書き戻します。
~~~~

### `>>`（出力の追記リダイレクト）

* 目的：コマンドの標準出力（`stdout`）をファイルへ追記します。
* 動作：
  * ファイルが存在しなければ、新しく作成されます。
  * ファイルが存在すれば、出力はファイルの末尾に追加されます。
* 例：

  ```bash
  # Adds "Another line" to the end of the file
  echo "Another line" >> file_listing.txt
  ```

### `<`（入力のリダイレクト）

* 目的：コマンドの標準入力（`stdin`）をファイルからリダイレクトします。
* 動作：コマンドは、キーボードではなく指定したファイルから入力を受け取ります。
* 例：

  ```bash
  # 'tr' reads from 'lowercase.txt' and
  # output is redirected to 'uppercase.txt'
  tr 'a-z' 'A-Z' < lowercase.txt > uppercase.txt
  ```

### `2>`（エラー出力のリダイレクト）：

* 目的：コマンドの標準エラー出力（`stderr`）をファイルへリダイレクトします。
* 動作：エラーメッセージは、端末ではなく指定したファイルへ送られます。
* 例：
  ```bash
  # Error message from 'rm' is sent to 'error_log.txt'
  rm non_existent_file 2> error_log.txt
  ```

標準エラー出力は、`2>>`を使えばファイルへ_追記_できます。

### そのほかのリダイレクト

`stdin`と`stderr`の両方をまとめるリダイレクトもあります。
詳しくは[マニュアル][manual]を参照してください。

## `/dev/null`

`/dev/null`は特別なファイルです。

* 読み取るときは、空のファイルとして扱われます。
* 書き込まれたデータは、すべて捨てられます。

「ビットバケツ」と呼ばれることもあります。
出力やエラーを抑えるのに便利です。

```bash
some_command > /dev/null  # Discards stdout
some_command 2> /dev/null # Discards stderr

# Using /dev/null as input will prevent the command
# from reading data from the keyboard
some_command < /dev/null
```

## リダイレクトの組み合わせ

複数のリダイレクトを同時に指定できます。

```bash
some_command < input.txt > output.txt 2> error.txt
```

リダイレクトはコピーできます。

```bash
# send stderr to the same destination as stdout
some_command > output.txt 2>&1
```

`2>&1`を見かけたら、「stderrを、_stdoutが**現在**指している場所_へリダイレクトする」と読んでください。
Bashはリダイレクトの指示を厳密に左から右へ処理します。つまり、次のようなことができます。

```bash
# redirect stdout to 'output1.txt'
# redirect stderr to the same place
# then change stdout to 'output2.txt'
some_command > output1.txt 2>&1 > output2.txt
```

## ファイルディスクリプタ

シェルプログラミングや、Linux/Unixのようなオペレーティングシステムの文脈では、ファイルディスクリプタ（FD）とは、開いているファイルやI/O（入出力）リソースを識別するための、負でない整数です。
オペレーティングシステムが、開いているファイルやデータストリームを管理するために使うラベルや参照番号だと思うとよいでしょう。

リダイレクトの左側に書かれている数字が、ファイルディスクリプタです。

標準入出力のストリームには、最初の3つのファイルディスクリプタが割り当てられます。

* 標準入力はFD0です
* 標準出力はFD1です
* 標準エラー出力はFD2です

新しいファイルディスクリプタは、`exec`コマンドとリダイレクト演算子で設定したり作成したりできます。

```bash
# create FD 3 as a copy of stdout
exec 3>&1
# send stdout to a log file
exec > log.txt

# then redirect both stdout and file descriptor 3
echo "some debug message" >&3  # displayed in the terminal
some_command  2>&1 # stdout and stderr send to 'log.txt'
```

このテクニックはかなり入り組んで見えますが、スクリプトがほかのソフトウェアパッケージから実行され、標準出力がそのソフトウェアに自動的に取り込まれるような状況では、とても役立ちます。
このトラックの単体テストを実行するために使われる`bats`コマンドは、この仕組みで動いています。`bats`はテストの標準出力と標準エラー出力を取り込みますが、FD3へ送られたデバッグメッセージは端末に表示されます。
~~~~

## まとめ

リダイレクトは何の役に立つのでしょうか？

* 出力の保存：コマンドの結果を保存して、後から確認したり処理したりできます。
* ログの記録：デバッグのためにエラーメッセージを記録します。
* 自動化：あるコマンドの出力を別のコマンドの入力として使い、コマンドをつなげます。
* フィルタリング：不要な出力を捨てます。
* バッチ処理：手で入力する代わりに、ファイルからデータを処理します。
* スクリプト：堅牢なシェルスクリプトを書くには、リダイレクトが欠かせません。

シェルのリダイレクトを使えば、プログラムとデータのやり取りをきめ細かく制御でき、複雑なワークフローを組み立てたり、情報を効率よく管理したりできます。

# Cトラックへのコントリビュート

ExercismのC言語トラックへのコントリビュートに関心を寄せてくださり、ありがとうございます！
新しい演習でも、ツールやドキュメントの変更でも、イシューの起票でも、既存のイシューやPRへのコメントでも、どんな形のコントリビュートも歓迎します。
このファイルでは、はじめの一歩を踏み出すための情報をまとめています。

まずは[Exercism docs][]、とくに[言語トラックへのコントリビュート][]の情報に目を通してください。これらのドキュメントには、基本的な情報が数多くまとめられています。

続いて、このリポジトリに固有のいくつかの点について、以下で説明していることに留意してください。

既存の演習に対する修正や改善のコントリビュートを歓迎します。
このトラックの演習は、[problem-specifications][]リポジトリで定められた標準に準拠している必要があります。
共通の演習のテストやドキュメントへの変更は、このトラックの演習に取り込む前に、多くの場合そのリポジトリへのpull requestが必要になります。
判断に迷ったら、遠慮なくGitHubの[イシュー][issue]を起票してください。変更について一緒に話し合いましょう。

## 行動規範

Exercismが誰にとっても居心地のよい場であり続けるために、ご協力をお願いします。
[行動規範][Code of Conduct]を読んで、守ってください。

## Gitのワークフロー

1. フォークしてクローンします。
2. クローンに、このリポジトリを新しいリモートとして追加します：`git remote add upstream https://github.com/exercism/c.git`
3. 新しいブランチを作成します：`git checkout -b name-of-branch`
4. 新しいブランチで、いつもどおりコミットしてプッシュします
5. プルリクエストを送る準備ができたら、コンフリクトを解消できるように、ブランチをupstreamのmainにリベースします：`git fetch upstream && git rebase upstream/main` コンフリクトを解消したあとは、`--force`を使ってブランチにプッシュする必要があるかもしれません。
6. すべて準備ができたら、ブランチにプッシュし、以下で説明するようにプルリクエストを作成します。

## イシュー

このリポジトリでは、バグ、改善提案、サポートの依頼をGitHubの[イシュー][issues]で管理しています。

プロジェクト全体に関するより高レベルな議論については、[discussions][]リポジトリのイシューをのぞいてみてください。

Exercismのコードベースや機能についてあまり多くの前提知識がなくても解決できそうなイシューには、"good first patch"というラベルを付けようとしています。見つけるには、[good-first-patch][]で検索してみてください。

## プルリクエスト

PRを作成するときは、このシンプルな[プルリクエストのガイドライン][pull request guidelines]に従っていただけると嬉しいですが、必須ではありません。

プルリクエストは、ひとつのイシューまたは変更に焦点を絞ってください。
コードスタイルや文言の変更も歓迎しますが、可能であれば、そうした変更には別のPRを立ててください。
既存の演習に大きな（破壊的な）変更を加えたり、多くの演習にまたがる変更を行ったりするPRを作成する前に、まずイシューを立ててください。こうした変更は、作業を始める前に話し合っておくのがいちばんです。

変更が演習に対するものであれば、プルリクエストを送る前にCIスクリプトを実行できます。あるいは、[継続的インテグレーション][Continuous Integration]で説明されているように、送ったあとに自動で実行されます。

プルリクエストを送っていただくと、パッチを受け入れる前に変更をお願いすることがあります。

最初のプルリクエストを閉じて、変更を加えた2つ目のプルリクエストを開かないでください。
プルリクエストを開いたブランチにさらにコミットをプッシュすると、そのプルリクエストは自動的に更新されます。

まだmainにマージする準備が整っていない変更を含むPRを作りたい場合（たとえば、特定の項目について話し合いたいときなど）は、通常どおりPRを作成し、GitHubのウェブサイトのインターフェースから[PRをドラフトに変換][]して、メンテナーにまだマージの準備ができていないことがわかるようにします。

コミットを追加するときと同じように、履歴を変更した場合（rebase、squash、amend）も、プルリクエストを閉じて新しいものを開く必要はありません。`git push --force`を使って、フォーク上のブランチを更新してください。
プルリクエストは特定のコミットではなく、そのブランチを指しています。

## コーディングスタイル

コード変更のコントリビュートで求められるコードスタイルは、[スタイルガイド][style guide]で説明しています。

演習のコードは、[CI][Continuous Integration]の際に、スペースとインデントのスタイルルールに準拠しているかどうかチェックされます。
このチェックには、[`clang-format`][clang-format]というCLIツールを使います。
演習を追加したり変更したりするときは、コミットする前にツールをローカルで実行して、変更がこれらのルールに準拠しているか確認できます。

Linuxでは、`clang-format`はディストリビューションのパッケージマネージャーからインストールできるはずです。
Macでは、[Homebrew][]を使って`clang-format`パッケージをインストールできます。

clang-formatは、`format.sh`を実行するとすべてのファイルに対して実行できます。
単一のファイルに対して手動で実行するには、次のようにします：

```bash
clang-format -i $(file)
```

## 演習の構成

各演習は、`c/exercises/practice/{exercise-name}`というディレクトリに配置します。
仕様に沿った演習の実装について詳しくは、[implement-an-exercise-from-specification][]を参照してください。

演習ディレクトリの構造は次のとおりです（ディレクトリ名にはハイフン、ファイル名にはアンダースコアを使うという違いに注意してください）：

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - このファイルには、演習のすべてのテストが含まれています。  
`test-framework` - [ThrowTheSwitch][]のテストハーネス[Unity][]が入っているディレクトリです。  
  チュートリアルが必要なら、ThrowTheSwitchが[getting started with Unity][]という手頃なガイドを用意しています。  
  使用しているUnityのバージョンは、[versions][]に記載されています。テストファイルのレイアウトは、[スタイルガイド][test-file-layout]で説明しています。  
  テストは、[problem-specifications][]リポジトリにある演習の`canonical-data.json`ファイルを満たすように書く必要があります  
`{exercise-name}.c` / `{exercise-name}.h` - 演習のソースファイルです。  
  ヘッダーファイルには[include guards][]を使ってください。
  演習のテストは、リポジトリのルートから`make test`を実行して走らせることができます。
* `makefile` - 演習をビルドするためのmakefileです。  
次の2つのルールが必要です。  
test: test_{exercise-name}.cをコンパイルして実行します。
memcheck: -fsanitize=address、-fno-common、-fno-omit-frame-pointerフラグを付けてtest_{exercise-name}をコンパイルして実行します
makefileは演習間であまり変わらないはずなので、別の演習からコピーするのは簡単です。

演習をトラックの`config.json`に追加するのを**忘れないでください**。そのためには、トラックの他のすべての演習の順序の中で、その演習をどこに追加するのが最適か決める必要があります。ここに追加するUUIDも生成する必要があります。この2つの作業には、[configlet][]ツールが使えます。このツールは、変更を加えたあとに`config.json`のlintとフォーマットまでしてくれます！

参考までに、configletツールのインストール用の成果物を入手するには、[configlet releases page][]をチェックしてください。

## 継続的インテグレーション

このリポジトリでは、GitHubのワークフローを使って、プルリクエストへのコミットごとにいくつかのツールを実行しています。
自分のコントリビュートでこれらのワークフローを実行するもっとも簡単な方法は、変更を加えたPRをこのリポジトリで開き、そのPRをドラフトに設定して、あとはこのリポジトリのCI設定に自動で処理を任せることです。

### CI環境

GitHubは、[hosted runners][]と呼んでいる仮想マシン上でCIを実行します。
ワークフローでは、実行したいランナーについていくつかの設定を行えます。

このリポジトリのワークフローは、それぞれUbuntu 24.04で実行するということだけを指定しています。使用するツールの中にはバージョンによって動作が異なるものがあるため、ワークフローは`latest`を参照するのではなく、特定のバージョンに固定されています。

### 自分のフォークでCIを実行する

必要であれば、自分のフォークでもCIを実行できます。GitHubでこのリポジトリを通常どおりクローンするだけです。
[`./.github/workflows/`][workflows]にあるYAMLファイルも、まったく同じように動作するはずです。
[`/format`][format-workflow]の自動アクションを正しく動作させたい場合は、クローンしたリポジトリにデプロイキーを追加する必要があります。

### ワークフロー

* `checks.yml`は、ツールスクリプトに対して`shellcheck`を実行し、その後、それらのツールのうち次のものを実行します：
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * [Lycheeリンクチェッカー][lychee]アクション
* `configlet.yml`は最新バージョンのconfigletを取得し、それを使ってトラックに対して`lint`コマンドを実行します
* `format-code.yml`は、PRのコメント内に`/format`という文字列があるかどうかをチェックし、見つかった場合は演習に対して`format.sh`を実行し、その結果生じた変更をコミットします。コミットがCIを再トリガーできるようにするには、デプロイキーが必要です。デプロイキーはExercismが直接管理しています。
* `test.yml`は、すべての演習をテストするために、リポジトリのルートで`make`を実行します

### ツール

[workflows][]からわかるように、GitHubは[`./bin`][bin]ディレクトリのツールを実行するよう指示されています。
このディレクトリのツールが行う処理は、次のとおりです：

* `check-unitybegin`は、すべてのテストファイルが`main()`関数の先頭に`UNITY_BEGIN()`の行を正しく追加していることを確認します。
* `fetch-configlet`は、[repository][configlet]から`configlet`ツールを取得します。
* `verify-unity-version`は、すべての演習で使われているUnityテストフレームワークのバージョンをチェックします。このファイルがチェックすべきバージョンは、[`./docs/VERSIONS.md`][versions]で指定されています
* `check-include-guards`は、各演習のスタブとサンプルのヘッダーで使われているinclude guardsが、次のような正しい形式になっていることを確認します：

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet`は、[repository][configlet]から`configlet`ツールを取得します。

### ツールをローカルで実行する

コミットする前に、自分のマシンで個々のツールを実行することもできます。
まず、必要なアプリケーション（`clang-format`、[`git`][git]、[`sed`][sed]、[`make`][make]、Cコンパイラーなど）がインストールされていることを確認し、リポジトリのルートから必要なツールを実行します。たとえば、次のとおりです：

```bash
~/git/c$ make
```

作業を確認するために一部のテストだけを実行したい場合は、それらをmakeのターゲットとして指定できます。

```bash
~/git/c$ make acronym all-your-base allergies
```

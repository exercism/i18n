# はじめに

## エラーにコンテキストを追加する

Goの基本的なエラー処理については、[エラーの概念][concept-errors]で見てきました。そこで学んだとおり、エラーはデフォルトではスタックトレースを持ちません。そのため、エラー自体に、問題を特定するのに十分な情報が含まれていることがとても重要になります。

すでに知っている道具だけを使って既存のエラーに情報を追加したいなら、元のエラーと追加情報のテキストを組み合わせた新しいエラーを、次のようにして作れます。

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

ありがたいことに、標準ライブラリの`fmt`パッケージには、このための省略形として`Errorf`関数が用意されています。これを使えば、たとえば、エラーが発生したコンテキストの情報を簡単に追加できます。

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

エラーに情報を追加するこの方法で十分なことも多いですが、エラーを受け取る側が、元のエラーを確認したり取り出したりできるようにしたい場合もあります。このように、後から元のエラーを取り出せる形でコンテキストを追加することを、Goでは「エラーをラップする」と呼びます。

## エラーのラップとセンチネルエラーの確認

エラーのラップは、上で見たコードにほんの少し手を加えるだけで実現できます。エラーをラップするには、`%v`の代わりにフォーマット動詞`%w`を使います。内部的には、これによって、生成されるエラーが、元のエラーを返す`Unwrap`メソッドを実装するようになります。そのおかげで、`errors.Is`を使って、特定のセンチネルエラーが「エラーチェーン」のどこかに現れるかどうかを確認できます。これは、目的のエラーが見つかるか、チェーンが終わるまで、裏で`Unwrap`を繰り返し呼び出すことで行います。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

デフォルトでは`%v`を使い、受け取る側に元のエラーへアクセスさせたいときだけ`%w`を使うのがよい習慣です（[Google Go Styleguide][google-go-styleguide]）。

センチネルエラーを確認したいけれど、アンラップはしたくないという状況なら、`errors.Is`の代わりに`==`を使えます。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

基本的には`errors.Is`を使うで問題ありませんが、これはエラーチェーン全体をたどるということを、いつも意識しておきましょう。

## （カスタム）エラー型の確認

`errors.Is`と同様に、エラーチェーンから特定の型のエラーを確認して取り出すための関数があります。それが`errors.As`で、`errors.Is`と同じように、指定したエラー型をチェーン全体にわたって探します。`errors.As`は、型に一致するエラーが見つかったときにだけ、それを取り出して、たとえば特定のフィールドを取り出すなど、さらに扱えるようにします。

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
上のポインターに関する構文には注意してください。`customError`が、`error`インターフェースを実装する正確な型である場合にだけ、このコードは正しく動作し、コンパイルされます。今回の場合、それは`*MyCustomError`（`MyCustomError`への[ポインター][concept-pointers]）であり、`MyCustomError`そのものではありません。

さらに、2番目の引数は、エラー変数へのポインターである必要があります。今回のエラーはすでにポインターなので、`errors.As`に渡しているのは、（MyCustomErrorへの）ポインターへのポインターになります。これを正しく設定してはじめて、Goは、見つけたエラーをその変数に入れることができます。
~~~~

先ほどと同じく、`Errorf`を呼ぶときに`%v`を使っていたら、`errors.As`はそのエラー型を見つけられなかったでしょう。

何らかの理由でアンラップしたくない場合は、代わりに型アサーションを使えます（上記の`==`に相当します）。

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

エラーがラップされていた場合、型アサーションではそのエラー型を特定できません。

## カスタム型のエラーをアンラップできるようにする

エラーを追加のテキストでラップするだけでは足りないこともあります。その場合は、元のエラーと、追加したい構造化データを保持するカスタムエラー型を作れます。自分のエラー型をアンラップできるようにしたいなら、`Unwrap`インターフェースを満たすように、`Unwrap() error`メソッドを手動で追加するだけです。

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

# はじめに

**コールスタック**、あるいは単に**スタック**は、メモリの最も高い位置から下に向かって伸びていく、特別なデータ構造です。

## `push`と`pop`

スタックは少なくとも2つの操作に対応していて、それぞれ同じ名前の命令があります。

| 命令   | 行う操作                                    |
| ------ | ------------------------------------------- |
| `push` | スタックに要素を追加します                  |
| `pop`  | 最後に追加された要素を取り出して返します    |

つまり、スタックは**後入れ先出し（LIFO）**のデータ構造です。

スタックの現在位置、つまり最も新しい要素がどこにあるかを把握するために、レジスタ`rsp`が使われます。

`push`命令は1つのオペランドを取り、そのオペランドの内容をスタックに格納します。スタックは下に向かって伸びるので、`rsp`の値は格納した値のサイズだけ減ります。

同じように、`pop`命令は1つのオペランドを取り、スタックにある最も新しい値（`rsp`が指している値）をそこに格納します。その後、`rsp`の値は取り出した値のサイズだけ増えます。

## ローカル変数

`rsp`の値を直接操作することもできます。これは、関数のローカル変数を作るときによく使われます。

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

スタックに領域を確保した時点で、その領域に格納されている値は_未定義_であることに注意してください。

~~~~exercism/note
`pop`も`rsp`の直接操作も、メモリに格納された内容を実際に消すわけではありません。スタックからの「削除」は、`rsp`の新しいアドレスによって抽象化されています。

状況によっては、内部の値が外部にさらされることでセキュリティ上の問題につながることもあります。その対策の1つは、関数が使ったスタック領域の内容をゼロで埋めてしまうことです。
~~~~

## `call`と`ret`

スタックの主な目的は、呼び出された関数の戻りアドレスを把握しておくことです。

以前の概念で触れたように、次に実行される命令を指す`rip`という特別なレジスタがあります。このレジスタはプログラムの流れを制御するために使われ、`jmp`や`call`といった命令によって書き換えられます。

`call`命令を使うと、その時点の`rip`の値が暗黙的にスタックにプッシュされます。続いて、その命令のオペランドが`rip`に移動し、呼び出された関数で実行が続きます。

`ret`命令は逆の操作を行います。スタックから`rip`にポップして、実行が呼び出し元の関数に戻ります。

関数に入った時点では、`rsp`は戻り先のアドレスを指しています。これが、`ret`がスタックからポップすべきアドレスです。

そのため、関数の中で`rsp`の値を変えた場合は、直接であれ`push`であれ、関数から戻る前に必ず元に戻す必要があります。

## 呼び出し先保存レジスタと呼び出し元保存レジスタ

`rsp`のほかにも、関数呼び出しをまたいで保存しなければならないレジスタがあります。`rbp`、`rbx`、`r12`、`r13`、`r14`、`r15`です。一般に、呼び出し元の関数は、呼び出した関数によってこれらのレジスタが書き換えられないまま使えることを前提としています。

つまり、_呼び出された_関数は、これらのレジスタを使う前に値を保存し、戻る前に元の値に戻さなければなりません。これが**呼び出し先保存レジスタ**と呼ばれる理由です。

その他の汎用レジスタは、呼び出された関数がそのまま使えます。

つまり、_呼び出し元_の関数は、どの関数を呼び出す前にもこれらのレジスタの値を保存しておく必要があります。呼び出された関数によって書き換えられる可能性があるからです。これが**呼び出し元保存レジスタ**と呼ばれる理由です。

_レジスタの内容を保存する最も一般的な方法は、それをスタックに格納することです。_

## プロローグとエピローグ

場合によっては、スタックが頻繁に使われ、関数から戻るまでに多くの変更が加えられることがあります。すると、それらすべての変更を把握して元に戻すのは複雑になるかもしれません。

そういうときは、関数の中でそれ以外は変わらない別のレジスタに`rsp`のアドレスを保存しておくのが一般的な戦略です。そして最後、関数から戻る前に、単純な`mov`命令で`rsp`の値を復元します。

この目的にはどのレジスタでも使えますが、ベースポインタとして`rbp`を使うのが慣例です。`rbp`自体が呼び出し先保存レジスタなので、その前によく`push rbp`が行われます。この一連の流れは普通**プロローグ**と呼ばれます。

最後に、`mov rsp, rbp`で`rsp`を復元し、続けてスタックからの`pop`で`rbp`も復元します。この一連の流れは普通**エピローグ**と呼ばれます。

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

## スタックで引数を渡す

System V ABIの呼び出し規約では、引数は普通レジスタで関数に渡されます。ただし、引数が多すぎたり、レジスタのサイズに収まらなかったりするときは、スタックが使われることがあります。

その場合、値は逆の順序でスタックに追加され、最初の引数ほど`rsp`に近くなります。関数に入った時点で`rsp`は戻りアドレス（x86-64では8バイトの値）を指しているので、スタック上の最初の引数があれば、`rsp + 8`でアクセスできます。

## スタックの整列

System V ABIは、`call`命令が実行される_直前_に、スタックが16バイトに整列されている必要があると定めています。`call`は`rip`をスタックにプッシュするので、関数に入った時点で、呼び出された関数のスタックは16バイトに整列されて**いません**。

つまり、別の関数（特に外部の関数）を呼び出す関数は、`call`を使う前にスタックを整列させる必要があります。

これは、`rsp`から適切な値を引くことで行えます。関数に入った時点で、この値は16の倍数より8多い値、つまり8、24、40などでなければなりません。`push`命令は`rsp`から値を引くので、同じ効果を得るために奇数個の`push`を使うこともできます。

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

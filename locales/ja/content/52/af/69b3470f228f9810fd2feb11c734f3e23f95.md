現在、Issueとプルリクエストは自動的にクローズされます。
変更を提案する場合は、[the Exercism forum]に投稿してください。
フォーラムで調整していただければ、コントリビュートは大歓迎です。

[the Exercism forum]: https://forum.exercism.org/

- [行動規範](https://exercism.org/code-of-conduct)

## ツール

一部のツールは、`bin/`にあるbashスクリプトとして提供されています。
さらに多くのツールが`rust-tooling/`にあり、少しでも込み入った作業にはこちらを使うのがおすすめです。

リポジトリを操作するための便利なコマンドをいくつか備えた[`mise`](https://mise.jdx.dev/)の設定もあります。
自由に拡張してください。

CIテストをローカルで実行したいときは、`mise run test`である程度まで進められます。

## テストの除外とカスタムテストの追加

演習を作成または更新する際に、特定のテストを生成対象から除外することがあります。
その場合は、`.meta/tests.toml`で`include = false`を設定します。
除外する理由をコメントで書いておいてください。

トラック固有のテストを追加したい場合は、`.meta/additional-tests.json`に書くことができます。
ただし、これらのテストをアップストリームに取り込まない明確な理由があるときに限ります。
追加するテストのコメントには、次の問いに答えるようにしてください。
- なぜそのテストを`problem-specifications`にアップストリームに取り込まないのか、つまり、なぜ他の言語にとって一般的に価値がないのか？
- それでもなぜそのテストがRustトラックにとって価値があるのか？

## 新しい演習の作成

まずは[プラクティス演習に関するExercismのドキュメント]に目を通してください。

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

`mise run add-exercise`を実行すると、演習のスタブを生成するために必要な最小限の情報を尋ねられます。
その後は生成された演習に飛び込んで、見つけたプレースホルダーをすべて埋めてください。
主な作業は次のとおりです。

- `src/lib.rs`に演習のスタブを書く
- `.meta/example.rs`に解答例を追加する
- `.meta/test_template.tera`を調整する

テストはテンプレートエンジン[Tera]を使って生成されます。
テンプレートの入力は、[`problem-specifications`]のカノニカルデータです。

teraテンプレートの書き方のヒントは[こちら](#tera-templates)にあります。

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

正しく実装された演習の多くの側面は、CIでチェックされます。
このプロセスについて長い時間をかけて調べたり、ドキュメントを書いたりするよりも、_とにかくやってみる_ことをおすすめします。
何かが壊れたら、それを直し、同じことが二度と起きないようにテストや自動化を追加してください。

`problem-specifications`に存在しないプラクティス演習をゼロから作る場合は、テストを自分で書く必要があります。
テストは複雑さが増していく順に並べてください。
そうすれば、学習者は`ignore`を1つずつ外して、TDDで演習を解き進められます。
よいテストの書き方についての詳しい考え方は、[Exercismのドキュメント](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)を参照してください。

特別な事情がない限り、スタブファイルは`cargo test --no-run`でコンパイルできるようにしてください。
そうすることで、スタブファイルのシグネチャがテストの期待するシグネチャと一致しているかを確認できます。
そのためには、各関数の本体を`todo!()`にします。
これがどうしてもできない正当な理由がある場合は、演習の`.meta/config.json`に`.custom."allowed-to-not-compile"`キーを含め、そこに理由を書いてください。

## 演習の更新

多くの演習は[`problem-specifications`]から派生しています。
テストスイートやユーザー向けドキュメントも同様です。
ここで変更を提案する前に、その変更を`problem-specifications`側で行うべきかどうかを確認してください。

演習を更新するには、`mise run update-exercise`を実行します。
ほとんどの作業は`configlet sync --update`に任され、テストジェネレーターが再び実行されます。

まだteraテンプレートがない演習を更新すると、新しいテンプレートが自動生成されます。
多少は手を入れる必要があるでしょう。

teraテンプレートの書き方のヒントは[次のセクション](#tera-templates)にあります。

## Teraテンプレート

teraテンプレートの完全なドキュメントは[こちら][tera-docs]にあります。
以下は、このトラック特有のニーズでうまくいったいくつかの方法です。

入力データがどんな形になるかは、演習の`canonical-data.json`を見るのがよいでしょう。
`bin/symlink_problem_specifications.sh`を使うと、このデータを実際の演習ディレクトリにシンボリックリンクできます。便利です！

入力プロパティの名前は演習ごとに異なります。
デフォルトのテンプレートは次のようになります。

```txt
let input = {{ test.input | json_encode() }};
```

その演習に固有の入力フィールドを追加する必要があります。たとえば次のようになります。

```txt
let input = {{ test.input.integers | json_encode() }};
```

演習によっては、エラーの戻り値があることもあります。
データの構造に応じて違う内容を出力するには、`if`と`else`を使えます。

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

演習によっては、学習者が実装し、それによってテストされる複数の関数があることもあります。
その場合、カノニカルデータには`property`フィールドがあります。
`test.property`に基づいて`if`と`else`の連鎖を組み立て、それに応じて違う関数を出力できます。

演習によっては、テストケースが_テストグループ_に分かれています。
テンプレートはそれに対応する必要があります。
多くの場合は、構造をそのまま平坦化できます。（例：[`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera)）
ただし、異なるグループでテストの説明が同じになることがあり、構造を平坦化すると名前が衝突します。
その場合は、グループの説明を使ってテストをモジュールに整理できます。（例：[`forth`](/exercises/practice/forth/.meta/test_template.tera)）

[`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs)には、いくつかのカスタムteraフィルターがあります。
できるだけ最新のはずのリストがこちらです。
- `to_hex`は整数を16進数でフォーマットします
- `make_ident`は任意の文字列をまともなRustの識別子に変換します。
   テストの説明から関数名を生成するときにもっとも役立ちます。
- `fmt_num`は数値リテラルをフォーマットします（3桁ごとに`_`を挿入）

`rust-tooling`クレートに独自のフィルターを自由に追加してください。
ついでにここのリストも更新するのを忘れないでくださいね。🙂

かなり複雑な例としては、`triangle`のテストテンプレートを見てみましょう。
テストケースをモジュールに整理し、どのテストをフィーチャーゲートの背後に置くかを動的に判定します。
この演習では、よいテストを生成するために必要な情報を追加する目的で、上流のテストケースの一部を`additional-tests.json`で再実装もしています。

[tera-docs]: https://keats.github.io/tera/docs/#templates

## シラバス

シラバスは現在、品質が低いため無効化されています。
この決定の背景については、[こちらのフォーラム投稿](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)を参照してください。

よりよいシラバスを作ることはとても有益ですが、多大な労力がかかり、円滑なコミュニケーションと調整が必要です。
シラバスを作った経験のある人たちと、フォーラムで計画を必ず話し合ってください。

# 概要

_「日付と時刻なんて、小さな子どもにだって教えられるものです。そんなに難しいはずがありません」_

多くのプログラマーがこの誤ちを犯してきました。そして、その後に訪れる経験は、健康と幸福に悪い影響を及ぼしがちです。

日付と時刻を扱う、それほど単純ではないプログラミングに取り組むなら、少なくとも潜在的な問題を理解し、軽減する備えをしておくべきです。

このページでは、Rが日付と時刻をどのように扱うかの概要を説明します。ただし、さらに詳しい情報が必要なときは、公式ドキュメントを参照してください。

データサイエンスのための言語であるRでは、日付と時刻は特に重要です。
データの多くは時系列の形で届きます。感染症の流行中の日ごとの患者数、政府が発表する月次の雇用統計、営巣地の鳥の個体数、主要経済国の年間GDPなど、例を挙げればきりがありません。

_では、Rを使えば日付と時刻の扱いは簡単になるのでしょうか？_

残念ながら、そうではありません。

Base Rの日付と時刻の機能は評判が悪く、そのほとんどは今ではあまり使われていません。

[`lubridate`][web-lubridate]パッケージは大きな改善ですが、大きく複雑な問題の幅を扱うために設計された、大きく複雑なライブラリであることを覚悟してください。

もともとは独立したパッケージでしたが、`lubridate`は現在`tidyverse`コレクションに同梱されています。
`library(lubridate)`または`library(tidyverse)`で読み込みます。

`lubridate`を使うのに役立つ資料には、次のようなものがあります。

- [リファレンスページ][ref-lubridate]。
- PDF形式の[チートシート][cheat-lubridate]。
- R for Data Scienceの[章][book-dates-times]。

## 日付と日時

`date`は単なる1日であり、時刻の情報を持ちません。

内部的には、日付は`1970-01-01`からの（符号付きの）日数として保存されます。

```R
today()
#> [1] "2026-04-22"
typeof(today())  # just a number
#> [1] "double"
class(today())  # the class understands how to interpret the raw number
#> [1] "Date"
```

`datetime`は日付・時刻・タイムゾーンの情報を組み合わせたものです。

内部的には、UTCタイムゾーンでの1970年の初めからの秒数として保存されます。

```R
now()
#> [1] "2026-04-22 15:37:11 MST"  # mid-afternoon in Arizona
typeof(now())
#> [1] "double"  # again, just a number
# POSIX datetimes are built into most operating systems as standard
class(now())
#> [1] "POSIXct" "POSIXt"
```

意外に思われるかもしれませんが、Rには時刻だけの値を表す内部表現がありません。この機能が必要な場合（Exercism以外では）、[`hms`][ref-hms]パッケージをインストールできます。

## `date`と`datetime`の値を扱う

おそらく最もよくある日付・時刻のニーズは、次のとおりです。

- 適切な入力形式を解析して、日付や日時を構築する。
- 日付や日時から、必要な数値または文字列の形式を取り出す。
- 日付や日時にオフセットを適用する。
- 2つの値の間の時間の長さを計算する。
- 現在の日付（`today()`）や日時（`now()`）を取得する。

### 文字列からの解析

日付や時刻の書き方には多くの種類があり、文化によって異なる傾向があります。「7/6/23」のようなすべて数字の日付は曖昧で紛らわしく、多国籍企業で多くの高くつく間違いを引き起こしてきました（_著者はこれを苦い経験から述べています_）。

国際標準（y-m-d）は[`ISO 8601`][wiki-ISO8601]で定義されており、主に2つの利点があります。

- 解析が速く、曖昧さがない。
- 日時を通常のテキストとして扱い、アルファベット順に並べ替えられるので、並べ替えが簡単。

しかし、データサイエンスとは、手に入るデータをそのまま扱うことです。他の人がどう整形しているかを嘆いても、意味がないことがほとんどです。

Base Rには、フォーマット文字列を受け取る変換関数があります（デフォルトはISO 8601です）。

```R
as.Date("2026-04-22")
#> [1] "2026-04-22"
as.Date("4/22/26", format = "%m/%d/%y")
#> [1] "2026-04-22"
as.POSIXct("2026-04-22 15:30:09 MST")
#> [1] "2026-04-22 15:30:09 MST"
```

フォーマット文字列は、何十年も前からある`strptime()`関数に似ており、_多くの_言語に含まれています。この構文に慣れている人は、lubridateの[`fast_strptime()`][ref-parse_dt]関数を使うこともできます。

さらに便利なことに、`lubridate`はフィールドの順序を表す名前を持つ[ヘルパー関数][ref-parsing]を幅広く提供しています。どの値がどの順序で現れるかさえ分かれば、解析は驚くほど柔軟です。

```R
mdy("4/22/26")
#> [1] "2026-04-22"
mdy("April 22nd 26")
#> [1] "2026-04-22"
mdy("Wednesday, April 22nd 2026")
#> [1] "2026-04-22"
mdy_hm("Wednesday, April 22nd 2026, 4:14 pm")
#> [1] "2026-04-22 16:14:00 UTC"  # defaults to your OS timezone
```

これらのヘルパー関数は、[`parse_date_time()`][ref-parse_dt]関数の特別な場合です。この関数は`"mdy_hm"`のようなフォーマット文字列を2番目の引数に取ります。

### 数値からの構築

日付や日時の構成要素を別々の数値として持っている場合は、[`make_date()`や`make_datetime()`][ref-make_datetime]で組み立てられます。

指定できる構成要素は次のとおりで、順序とデフォルト値を示しています。

```R
make_datetime(
  year = 1970L,
  month = 1L,
  day = 1L,
  hour = 0L,
  min = 0L,
  sec = 0,
  tz = "UTC"
)
#> [1] "1970-01-01 UTC"

make_datetime(2026, 4, 22, 17)
#> [1] "2026-04-22 17:00:00 UTC"
```

もちろん、`make_date()`は年・月・日の引数だけを取ります。

### 人間が読める形式での出力

Rコンソールは、日付や日時を文字列表現として自動的に表示します。これは通常は便利ですが、ときに誤解を招きます。

内部的には、日付と日時は文字列ではなく数値（といくつかの属性）です。文字列が期待される場所で日付（時刻）を返すと問題が起きるので、変換のしかたを知っておく必要があります。

簡単な方法は、Base Rの[`as.character()`][ref-ascharacter]を使うことです。これはISO 8601形式の文字列を出力します。

日時用の[`format_ISO8601()`][ref-iso8601]関数もあり、希望する精度に丸めるオプションがあります。

```R
today() |> as.character()  # a date
#> [1] "2026-04-23"
now() |> as.character()  # a datetime
#> [1] "2026-04-23 09:07:09.779319"
now() |> format_ISO8601() # defaults to nearest second
#> [1] "2026-04-23T09:07:38"
```

ISO 8601の出力を見たい非プログラマーはほとんどいないので、文化に固有の日付・時刻形式を扱うことは欠かせません。

Base Rには[`format()`][ref-format]関数があり、他の多くの言語に含まれる古くからの`strftime()`関数に似たフォーマット文字列を使います。

```R
format(today(), "%A, %d %B %Y")
#> [1] "Thursday, 23 April 2026"
```

このBase Rの方法は見た目はよくありませんが、信頼できます。よく使うコードの一部を挙げます。

コード | 結果
-- | --
%d | 月内の日（5、17、28など）
%a | 曜日の略称（Mon、Tue、Wedなど）
%A | 曜日の完全名（Monday、Tuesdayなど）
%w | 曜日の番号（0-6、日曜が0）
%u | 曜日の番号（1-7、月曜が1）
%b | 月の略称（Jan、Febなど）
%B | 月の完全名（January、Februaryなど）
%y | 2桁の年（例：89）
%Y | 4桁の年（例：1989）
%h | 時（24時間制）
%m | 分
%s | 秒
%z | UTCからのオフセット
%Z | タイムゾーン（文字列）

Lubridateは、より人間に優しい代替手段として[`stamp()`][ref-stamp]関数を提供することを目指しています。より限定された`stamp_date()`と`stamp_time()`もあります。

これらは、望む出力の例であるテンプレート文字列を受け取り、その形式を生成するカスタム関数を作ります。

Lubridateは形式を推測しようとしますが、しばしば曖昧さに遭遇して間違った結果を出力します。曖昧さを解消するために、`"dmy"`のようなフォーマット文字列を用意できるようにしておきましょう。

Exercismでは、`locale = "C"`を指定してシステムのロケールを回避し、英語で処理する（テストが期待するように）と役立つこともあります。ロケールは複雑です！

```R
sf <- stamp("Saturday, June 27, 2026 at 14:45", locale = "C")
#> Multiple formats matched: "%A, %B %d, %Y at %H:%M"(1), "Saturday, %Om %d, %Y at %H:%M"(1), "Saturday, %B %d, %Y at %H:%M"(1), "%A, %Om %d, %Y at %H:%M"(0)
#> Using: "%A, %B %d, %Y at %H:%M"

sf(make_datetime(2023, 3, 29, 15, 0, 0))
#> [1] "Wednesday, March 29, 2023 at 15:00"
```

### 構成要素の設定と取得

Lubridateには、日付や日時の要素を取得・設定する[多くの関数][ref-set-get]があります。`year()`や`second()`のような分かりやすいものから、`quarter()`や`epiweek()`のようなより専門的なものまであります。

こうした関数はすべて値の取得に使え、そのほとんどは値の設定にも使えます。

```R
dt <- now()
dt
#> [1] "2026-04-23 15:47:11 MST"

# get
month(dt)
#> [1] 4

# set
month(dt) <- 11
dt
#> [1] "2026-11-23 15:47:11 MST"
```

`wday()`（曜日）と`month()`では、デフォルトは整数の出力ですが、次のようになります。

- `labels = TRUE`を設定すると、現在のロケールに対応する省略された文字列を返します。
- さらに`abbr = FALSE`を設定すると、完全名を返します。

```R
d <- today()
d
#> [1] "2026-04-23"
wday(d)
#> [1] 5
wday(d, label = TRUE)
#> [1] Thu
#> Levels: Sun < Mon < Tue < Wed < Thu < Fri < Sat
wday(d, label = TRUE, abbr = FALSE)
#> [1] Thursday
#> Levels: Sunday < Monday < Tuesday < Wednesday < Thursday < Friday < Saturday
```

ラベルは`categorical variables`であり、これは別のコンセプトで扱います。値は列挙された`Levels`に制限され、そこには並べ替えの順序も示されます。

週はデフォルトで日曜から始まりますが、`week_start`引数で変更できます（月曜にするには`1`を使います）。

```R
dt <- make_datetime(2026, 4, 23)

# default behavior
wday(dt)
#> [1] 5
wday(dt, label = T)
#> [1] Thu

# set week_start to Monday
wday(dt, week_start = 1)
#> [1] 4
```

いくつかのユーティリティ関数は`TRUE`/`FALSE`値を返します。たとえば`leap_year()`や`dst()`（夏時間が有効か？）です。

月の長さはそれぞれ異なるので、`days_in_month()`は整数値を返します。

### 丸め

数値は`round()`、`floor()`、`ceiling()`などの[関数][ref-round]で丸められます。

同様に、日付と日時には[関数][ref-round_date]`round_date()`、`floor_date()`、`ceiling_date()`があります。

デフォルトでは秒単位に丸められますが、`unit`引数でさらに多くのオプションが使えます。詳細と豊富な例は[ドキュメント][ref-round_date]を参照してください。

## 時間の長さ

`date`と`datetime`の値はどちらも、時間軸上の1つの時点を表します。

「昨日のこの時間」や「今から1週間後」といった概念は、どう扱えばよいのでしょうか？

他の科学向け言語に慣れた学習者は、Pythonの`datetime.timedelta`やJuliaの`Period`型を知っているかもしれません。

対照的に、Rには時間の長さを表す方法が3つもあり、それぞれに長所と限界があります。いつもどおり、状況に最も合ったものを選びましょう。

さまざまな時間の長さは、`as.period()`、`as_duration()`、`as.interval()`で簡単に相互変換できます。

時間の長さの型は`is.period()`などで調べられます。

### 期間

`period`は、たとえば`hours(3)`のように、時計の時刻を3時間進めるのに使えます。

夏時間（DST）のような不規則さはほぼ無視されます。

期間はすべて、単位名を複数形にしたものです。`years`、`weeks`などです。

```R
d <- today()
d
#> [1] "2026-04-25"

d + weeks(2)
#> [1] "2026-05-09"

# dates are coerced to datetimes at midnight if necessary
d - hours(20)
#> [1] "2026-04-24 04:00:00 UTC"

hours(3)
#> [1] "3H 0M 0S"
```

### デュレーション

`duration`は、たとえば`dhours(3)`のように、物理的な時間を3時間進めます。これは、時計の時刻を物理的な時間からずれさせるDSTなどの不規則さを考慮に入れています。

デュレーションはすべて、対応する期間に`d`の接頭辞を付けます。`dyears`、`dweeks`などです。

```R
dhours(3)
#> [1] "10800s (~3 hours)"
```

### インターバル

`interval`は開始時刻と終了時刻を組み合わせたもので、[`interval()`][ref-interval]関数か`%--%`中置演算子で作ります。

```R
# the next 2 lines were run about 33s apart, so now() is different
dt1 <- now()
dt2 <- now() + hours(1)

# interval(0 function)
ivl <- interval(dt1, dt2)
ivl
#> [1] 2026-04-24 16:24:54 MST--2026-04-24 17:25:27 MST
class(ivl)
#> [1] "Interval"
attr(,"package")
#> [1] "lubridate"

# infix operator
iv2 <- dt1 %--% dt2
iv2 == iv1
#> [1] TRUE

# conversions
as.period(ivl)
#> [1] "1H 0M 32.738214969635S"
as.duration(ivl)
#> [1] "3632.73821496964s (~1.01 hours)"

# components
int_start(ivl)
#> [1] "2026-04-24 16:24:54 MST"

# is datetime within the interval?
(now() - minutes(20)) %within% ivl
#> [1] TRUE
```

## タイムゾーン

タイムゾーンの扱いは難しいことがあります。以下の引用はPythonのドキュメントからのものですが、Rにも同じように当てはまります。

> 「世界中の時間調整のルールは、合理的というより政治的なもので、頻繁に変わり、UTC以外にすべてのアプリケーションに適した標準はありません。」

タイムゾーンについて、一般的なポイントをいくつか挙げます。

- `datetime`は常にタイムゾーン（`tz`）を含みますが、`date`はタイムゾーンを考慮しません。
- 日時のコンストラクターは、一般にデフォルトで[UTC][wiki-UTC]を使います。
- [`now()`][ref-now]関数は例外で、システムクロックから`tz`を含むローカル時刻を取得します。
  デフォルトではローカルの`tz`が使われますが、`now("UTC")`のように別のものを指定できます。

```R
# timezone defaults to UTC
local <- ymd_hm("2026-04-25 10:32")
local
#> [1] "2026-04-25 10:32:00 UTC"

# timezone can be specified
AZ <- ymd_hm("2026-04-25 10:32", tz = "America/Phoenix")
AZ
#> [1] "2026-04-25 10:32:00 MST"

# same clocktime, different tz
local - AZ
#> Time difference of -7 hours
```

タイムゾーンに関連する計算は、期間よりもデュレーションを使うほうが信頼できます。

```R
dt <- make_datetime(2020, 10, 31, 12, tz = "Europe/Helsinki")

# EET is 2h ahead of UTC
dt
#> [1] "2020-10-31 12:00:00 EET"

# A week earler, EEST (summer time) is 3h ahead of UTC

# a 7-day period => midday
dt - days(7)
#> [1] "2020-10-24 12:00:00 EEST"

# a 7-day duration => 1 pm
dt - ddays(7)
#> [1] "2020-10-24 13:00:00 EEST"
```

期間の計算とデュレーションの計算のどちらでも、lubridateは東ヨーロッパ時間から東ヨーロッパ夏時間への切り替えを認識しますが、1時間の時刻変更を調整するのはデュレーションだけです。

# はじめに

## スタック

**コールスタック**、または単に**スタック**は、メモリの最も高い位置から始まって下に向かって伸びる、特別なデータ構造です。

### `push`と`pop`

スタックは少なくとも2つの操作をサポートしており、それぞれに同じ名前の命令があります。

| 命令 | 行われる操作                                 |
| ----------- | --------------------------------------------------- |
| `push`      | スタックに要素を追加します                        |
| `pop`       | 最後に追加された要素を取り除き、それを返します |

つまり、スタックは**後入れ先出し（LIFO）**のデータ構造です。

スタックの現在の位置、つまり最も新しい要素がどこにあるかを把握するために、`rsp`というレジスタが使われます。

`push`命令は1つのオペランドを取り、そのオペランドの内容をスタックに格納します。スタックは下に向かって伸びるので、`rsp`の値は格納した値のサイズだけ減ります。

同様に、`pop`命令は1つのオペランドを取り、スタック内の最も新しい値（`rsp`が指している値）をそこに格納します。その後、`rsp`の値は取り出した値のサイズだけ増えます。

### ローカル変数

`rsp`の値を直接操作することもできます。これは、関数のローカル変数を作るためによく使われます。

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

スタックに領域が確保された時点では、その領域に格納されている値は_未定義_であることに注意してください。

~~~~exercism/note
`pop`も`rsp`の直接操作も、メモリに格納された内容を実際に取り除くわけではありません。スタックからの「取り除き」は、`rsp`の新しいアドレスによって抽象化されています。

状況によっては、これが内部の値を外部にさらすことになり、セキュリティ上の懸念を引き起こすことがあります。これに対処する1つの方法は、関数が使うスタック領域の内容をすべてゼロで埋めることです。
~~~~

### `call`と`ret`

スタックの主な目的は、呼び出された関数の戻りアドレスを把握しておくことです。

以前のコンセプトでも触れましたが、次に実行される命令を指す`rip`という特別なレジスタがあります。このレジスタはプログラムの流れを制御するために使われ、`jmp`や`call`などの命令によって書き換えられます。

`call`命令を使うと、`rip`の現在の値が暗黙的にスタックにプッシュされます。続いて、その命令のオペランドが`rip`に移動し、呼び出された関数で実行が続きます。

`ret`命令は逆の操作を行います。スタックから`rip`へポップし、実行が呼び出し元の関数に戻ります。

関数に入った時点で、`rsp`は戻るべきアドレスを指しています。これが、`ret`がスタックからポップすべきアドレスです。

したがって、関数内で`rsp`の値に加えた変更は、直接であれ`push`によるものであれ、関数が戻る前に元に戻さなければなりません。

### 呼び出し先保存レジスタと呼び出し元保存レジスタ

`rsp`以外にも、関数呼び出しをまたいで保存しなければならないレジスタがあります。`rbp`、`rbx`、`r12`、`r13`、`r14`、`r15`です。一般に、呼び出し元の関数は、呼び出された関数によって変更されずにこれらのレジスタを使えることを期待します。

つまり、_呼び出された_関数は、これらのレジスタを使う前にその値を保存し、戻る前に元の値に復元しなければなりません。これが、これらが**呼び出し先保存レジスタ**と呼ばれる理由です。

その他の汎用レジスタは、呼び出された関数がそのまま使えます。

つまり、_呼び出し元_の関数は、呼び出した関数によって変更される可能性に備えて、関数を呼び出す前にこれらのレジスタの値を保存しなければなりません。これが、これらが**呼び出し元保存レジスタ**と呼ばれる理由です。

_レジスタの内容を保存する最も一般的な方法は、それをスタックに格納することです。_

### プロローグとエピローグ

場合によっては、スタックが頻繁に使われ、関数が戻るまでに多くの変更が加えられることがあります。そのようなときは、すべての変更を把握して元に戻すのは複雑になるかもしれません。

そういう場合は、関数内でそれ以外は変更されない別のレジスタに`rsp`のアドレスを保存するのが一般的な戦略です。そして最後に、関数が戻る前に、単純な`mov`命令で`rsp`の値を復元できます。

この目的にはどのレジスタでも使えますが、`rbp`をベースポインタとして使うのが慣例です。`rbp`自体が呼び出し先保存レジスタなので、その前によく`push rbp`が行われます。この一連の流れは通常**プロローグ**と呼ばれます。

最後に、`mov rsp, rbp`で`rsp`を復元し、続いて`pop`でスタックから`rbp`も復元します。この一連の流れは通常**エピローグ**と呼ばれます。

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

### スタックで引数を渡す

System V ABIの呼び出し規約では、引数は通常レジスタで関数に渡されます。しかし、引数が多すぎる場合や、1つのレジスタのサイズに収まらない場合は、スタックが使われることがあります。

そのような場合は、値が逆順でスタックに追加されるので、最初の引数が`rsp`に近くなります。関数に入った時点で`rsp`は戻りアドレスを指しており、x86-64ではこれが8バイトの値なので、スタック上の（もしあれば）最初の引数は`rsp + 8`でアクセスできます。

### スタックのアラインメント

System V ABIでは、`call`命令が実行される_直前_の時点で、スタックが16バイトに整列されている必要があると定められています。`call`は`rip`をスタックにプッシュするので、関数に入った時点で、呼び出された関数のスタックは16バイトに整列されて**いません**。

つまり、別の関数（特に外部の関数）を呼び出す関数は、`call`を使う前にスタックを整列させる必要があります。

これは、`rsp`から適切な値を引くことで行えます。関数に入った時点で、この値は16の倍数より8大きい値、つまり8、24、40などでなければなりません。`push`命令は`rsp`から値を引くので、同じ効果を得るために奇数個の`push`を使うこともできます。

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

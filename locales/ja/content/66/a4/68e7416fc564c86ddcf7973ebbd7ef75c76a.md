# 概要

## はじめに

Opaque Typeは、Elmにおけるカプセル化の手法です。
情報隠蔽や、実装の詳細を隠すこととも呼ばれます。
また、[Parse, dont validate][parse-dont-validate]パターンを使って検証を強制するのにもよく使われます。
たとえば、有効なメールアドレスしか格納できない`EmailAddress`というOpaque Typeを作れます（何でも格納できる`String`とは対照的です）。

## Opaque Typeを作る

[カスタム型][custom-types]には1つ以上の*バリアント*があり、コンパイラーはそれぞれの*バリアント*を作る関数を、その*バリアント*の名前を使って自動的に生成します。
カスタム型を作れるのは、この方法だけです。
コンパイラーは、これらのバリアントの分解も許します。

```elm
type Maybe a
    = Nothing --> Variant implies a 'Nothing' function, with type 'Maybe a', and destructuring of 'Nothing'
    | Just a  --> Variant implies a 'Just' function, with type 'a -> Maybe a', and destructuring of 'Just _'
```

デフォルトでは、これらはすべてファイル／モジュールの内部にあり、何をエクスポートするかを選ぶのに`exposing`キーワードを使います。
Opaque Typeを作るには、*バリアント*をエクスポートしないようにするだけです。

そうすると、ほとんどの場合、*バリアント*を作ったり取得したりする別の方法を、独自の関数を公開して用意する必要があります。
これらの独自の関数を使えば、*バリアント*を作る／取得するときに何らかのロジックを適用できます。
これによりモジュール内部の実装の詳細が隠れ、公開している関数が同じままであれば、実装の詳細をいくらでも変更できるようになります。

## Parse, don't validate

Opaque Typeの最も一般的な使い道は、[Parse, dont validate][parse-dont-validate]パターンを使って検証を強制することでしょう。
このパターンでは、`String`のように、望むよりも構造や型の安全性が低い入力を受け取り、それを`EmailAddress`のようなより構造化された型にパースする関数を公開します。
その結果として、その型を返すか、エラー（通常は`Maybe`や`Result`）を返します。

たとえば、以下のコードでは、外部のモジュールが`EmailAddress`型を作れるのは`parseEmailAddress`関数を使う場合だけなので、`EmailAddress`型を扱っているときには、それが有効であることが確実です。

```elm
module EmailAddress exposing ( EmailAddress, parseEmailAddress, getEmailAddress )

-- The `EmailAddress` custom type has one variant, also called `EmailAddress`
-- When a custom type has one variant, it is idiomatic to use the same name for both.
type EmailAddress = 
  EmailAddress String

-- create an EmailAddress variant
parseEmailAddress: String -> Maybe EmailAddress
parseEmailAddress candidateEmailAddress =   
  if isValidEmailAddress candidateEmailAddress then
    Just (EmailAddress candidateEmailAddress)
  else
    Nothing

-- get an EmailAddress variant
getEmailAddress: EmailAddress -> String
getEmailAddress ( EmailAddress  emailAdress ) =
  emailAdress

isValidEmailAddress: String -> bool
-- ... 
```

# 概要

1つの命令は、一見すると不可分な1つの動作に見えますが、実際にはそうではありません。
メモリ上の値に5を足す場合を考えてみましょう。

```x86asm
add qword [rel counter], 5
```

内部では、プロセッサにはメモリに直接足し算をする方法がありません。
プロセッサはこの1つの命令を、**マイクロオペレーション**と呼ばれる3つの小さなステップに分解します。

1. メモリから現在の値を**読み出します**。
2. レジスタ上でこの値に5を足して**変更します**。
3. 結果を**書き戻します**。

```x86asm
mov rax, qword [rel counter] ; 1. load the current value
add rax, 5                   ; 2. add five
mov qword [rel counter], rax ; 3. store the result back
```

これは**読み出し・変更・書き戻し（RMW）**と呼ばれる一般的なパターンです。

読み出し（ロード）と書き込み（ストア）は別々の出来事なので、その間には時間の隙間があります。
通常はこれに気づきません。シングルコアでは、各命令が次の命令の前にその効果を完全に及ぼすことが保証されているからです。
そのためこの隙間は見えず、`add`は1つのまとまりとして振る舞います。

しかし、現代のCPUがシングルコアであることはまれで、アプリケーションはしばしば複数のコア上で、互いの順序付けもなく同時に動作します。
複数のコアがまったく同じ瞬間に動作していると、別のコアがこのコアのロードとストアの間の隙間で`counter`を読み書きできます。
2つのスレッドがそれぞれ同じ古い値をロードし、それぞれ5を足し、それぞれの結果をストアします。
2回の加算が起きたのに、値は5しか増えていません。
一方の更新は黙って失われました。

これが**データ競合**で、マルチスレッドコードでよくある問題です。

すべての値がこのように晒されるわけではありません。
各スレッドは自分のレジスタと自分のスタックを持っているので、レジスタに保持された値やスレッドのスタック上のローカル変数はそのスレッド専用で、競合しません。
上の`counter`のように、スレッドが共有するメモリだけが保護を必要とします。

~~~~exercism/note
スタックのプライバシーは保護ではなく慣習です。スレッドのスタックは同じ共有メモリ上にあり、自分のローカルの1つのアドレスを渡したスレッドは、別のスレッドにそこへ到達させてしまいます。
一方、レジスタはハードウェア的に排他的です。各コアが自分のセットを持っており、オペレーティングシステムはスレッドの切り替えのたびにそれらを保存して復元します。
~~~~

x86-64はこの問題を解決するために、命令を不可分にする命令群を提供しています。
それは、それを処理するコアにとってだけでなく、ほかのすべてのコアにとっても1つのまとまりとして振る舞います。
ばらけず、ほかのどのコアにも分割できない操作は、**アトミック**と呼ばれます。

~~~~exercism/note
多くのコアで動くアプリケーションをマルチスレッドと呼ぶのはよくあることです。
しかし、**スレッド**はコアとは同じではありません。
2つのスレッドは同じコア上で交互に並行して動くことも、異なるコア上で同時に並列に動くこともあります。

交互に動くスレッドでも、読み出し・変更・書き戻しが複数の命令に分かれていれば、すでに競合が起き得ます。OSは任意の2つの命令の間でスレッドを切り替えられるからです。
しかし、_1つ_の命令の内部の隙間は、真に並列なコードだけによって露呈します。
OSは命令の間でしかスレッドを切り替えず、1つの命令の途中では切り替えないので、シングルコアでは1つの命令は本質的に安全です。

_複数の_コアにまたがる真のアトミック性を提供するのが、以下の命令です。
~~~~

## アトミックな交換

`xchg`命令は2つのオペランドを交換します。
宛先オペランドはソースオペランドの以前の値と等しくなり、ソースオペランドは宛先オペランドの以前の値と等しくなります。
概念的には、2つの`mov`命令が同時に起きていると考えることができます。

いつもどおり、2つのレジスタオペランドと一緒にも、1つのメモリオペランドと1つのレジスタオペランドと一緒にも使えます。

```x86asm
mov  eax, 1
xchg dword [rdi], eax ; [rdi] = 1, eax = the old value of [rdi]
mov ecx, 2
mov edx, 3
xchg edx, ecx         ; edx = 2, ecx = 3
```

メモリオペランドと一緒に使う場合、`xchg`は_常に_アトミックです。
プロセッサはその間、その場所にロックをかけます。これは次に説明する、`lock`プレフィックスがほかの命令に使うのと同じ仕組みです。

~~~~exercism/caution
オペランドの1つがメモリ位置である場合、`xchg`は自動的にアトミックになります。
これは、その状況ではこの操作がずっと遅くなることも意味します。

アトミック性が必要ないなら、代わりに空いているレジスタを介して素の`mov`命令で交換してください。
~~~~

## `lock`プレフィックス

x86-64で命令をアトミックにする最も一般的な方法は、`lock`プレフィックスを付けることです。
これにより、読み出しと変更と書き戻しが1つの不可分なステップに融合されます。
つまり、コアはその処理全体を通じてメモリを排他的に保持するので、ほかのどのコアもその途中でその場所を読み書きできません。

```x86asm
lock add qword [rel counter], 5 ; the read, the modify, and the write are one step
```

`lock`は宛先がメモリである場合にだけ、そしてそのメモリを読み出し・変更・書き戻しする命令にだけ機能します。

1. `add`、`sub`、`inc`、`dec`、`neg`のような算術演算
2. `and`、`or`、`xor`、`not`のようなビット演算
3. `bts`、`btr`、`btc`といったビット操作
4. 以下で説明する`xadd`や`cmpxchg`のような、その他の専用命令

素の`mov`のようなその他の命令では、このプレフィックスは無効で、プロセッサは無効オペコード例外を発生させます。
単独のロードや単独のストアにはプレフィックスは不要です。自然にアラインされたアクセスはそれ自体ですでにアトミックだからです。

~~~~exercism/caution
ある場所を排他的に保持し、ほかのすべてのコアを締め出すのは、タダではありません。
`lock`プレフィックス付きの操作は、素の形より明らかに遅く、複数のコアが同じ場所を奪い合うとさらに遅くなります。

このプレフィックスは、複数のスレッドによって変更されることが想定されるメモリのために取っておくべきです。
メモリが共有されていない場合や、読み取りしかされない場合は使わないようにしましょう。
~~~~

~~~~exercism/note
共有するアトミックな値は自然にアラインして、1つのキャッシュラインに収まるようにしましょう。
2つのキャッシュラインにまたがるロックされたアクセスは**スプリットロック**と呼ばれ、合法ですが劇的に遅くなります。プロセッサが複数のラインをロックしなければならず、最近のシステムの中にはこれを一律でトラップするものもあるからです。
~~~~

## アトミックなビット操作

ロックできる命令の中でも、ビットテストはこの文書の最後で扱うスピンロックと自然に組み合わせられます。
`bts`、`btr`、`btc`はそれぞれ、選んだ1つのビットをキャリーフラグにコピーしてから、そのビットをセット、クリア、または反転します。
`lock`プレフィックスを付けると、これは1ビットの読み出し・変更・書き戻しになります。ビットはアトミックに変更され、`CF`は変更前の値を報告します。

```x86asm
    lock bts qword [rdi], 0 ; set bit 0; CF = the bit's previous value
    setc al                 ; al = 1 when the bit was already set
```

セットしようとしてそのビットがすでにセットされている場合、別のスレッドが先にそれを確保したということです。
これは、`xchg`がワード全体に対して行うフラグの確保を、1ビットで行う版です。

## 交換と加算

素の`lock add`はメモリを更新しますが、古い値は捨ててしまいます。
古い値こそがまさに欲しいものであることもよくあります。たとえば、各スレッドに別々のチケット番号を渡す場合です。

`xadd`命令（`x`はexchangeの意味）は、加算しつつ以前の値を返します。
合計を宛先に書き込み、元の宛先の値をソースレジスタに残します。

```x86asm
mov  rax, 1
lock xadd qword [rdi], rax ; [rdi] = [rdi] + rax = [rdi] + 1
                           ; rax = the old value of [rdi]
```

`lock`プレフィックスを付けると、これはアトミックな**fetch-and-add**になります。
同じカウンターに対して多数のスレッドから実行すると、呼び出しごとに異なる古い値が返ります。

`lock add`と同様、カウンターは呼び出し回数ちょうどの値になります。
しかし、`lock add`と違い、途中の値もすべて、呼び出し元ごとに1つずつ返されます。

ソースは任意の汎用レジスタでよく、オペランド幅はバイトからクアッドワードまでです。
負の値を足せば、同じ命令がfetch-and-subtractになります。

## 比較と交換

`xadd`は加算し、`xchg`は上書きしますが、どちらも新しい値を現在の値に依存させ、その下で何も変わっていない場合にだけ適用する、ということはできません。
その条件付きの更新を提供するのが`cmpxchg`（compare-and-exchange）であり、これらのプリミティブの中で最も汎用的です。

`cmpxchg dest, src`は`rax`を暗黙のアキュムレータとして使い、それを`dest`と比較します。

- `dest == rax`なら、`dest = src`となり、`ZF = 1`です。
- `dest != rax`なら、`rax = dest`となり、`ZF = 0`です。

アキュムレータはオペランドサイズに従います。バイトなら`al`、より広い形なら`ax`、`eax`、`rax`です。

`dest`は、以前に`rax`にロードされた期待値と等しいときにだけ更新されることに注意しましょう。
この等しさによって、`dest`が新しい値の計算元となった値をまだ保持していることが保証されるので、古い読み出しに基づく更新が適用されることはありません。
これにより、`cmpxchg`はアトミックな更新の構成要素となります。これは[**compare-and-swap（CAS）**][cas]としても知られています。

```x86asm
    mov rax, qword [rdi]          ; rax = the value we expect to find
.retry:
    lea rcx, [rax + 10]           ; rcx = the new value we want to install
    lock cmpxchg qword [rdi], rcx ; if [rdi] still equals rax, store rcx and set ZF
                                  ; otherwise reload rax with the current value, clear ZF
    jnz  .retry                   ; ZF is cleared, so another thread won the race. Recompute and retry
```

この**リトライループ**はロックフリー更新の核心です。
読み出しとcompare-and-exchangeの間の隙間こそ、別のスレッドが割り込む可能性のある瞬間であり、`cmpxchg`は古い読み出しから計算された値のストアを拒否することでそれを捉えます。

知っておく価値のある微妙な点が1つあります。
`cmpxchg`が確認するのは、値が読み出したものと等しいかどうかであり、その場所に一度も触れられなかったかどうかではありません。
もし別のスレッドが隙間の中で値を`A`から`B`へ、そして`A`へと戻したなら、その下で世界が変わったにもかかわらず、交換は_それでも成功します_。

素のカウンターではこれは無害です。等しいカウントは同じように良いカウントだからです。
ロックフリーリストの先頭にあるメモリアドレスではそうはいきません。同じアドレスが今では別の場所を指しているかもしれないからです。
これが[ABA問題][aba]です。

この問題に対する通常の解決策は、値に何らかの「スタンプ」を組み合わせることです。たとえば、増える一方のカウンターです。
スタンプは進む一方なので、一致するスタンプは、その場所が見た目に変わっていないというだけでなく、途中で触れられなかったことを証明します。

しかし、これがマルチスレッド環境で機能するには、メモリアドレスとそのスタンプの両方を一緒に更新しなければなりません。
x86-64ではメモリアドレスは完全なクアッドワードなので、`cmpxchg`だけではそれと同時に別の値も更新するには足りません。

[cmpxchg16b][cmpxchg16b]という倍幅の命令があり、意味的には`cmpxchg`と同じですが、一度に16バイトを扱い、そういう状況で使えます。
ソースオペランドを持たず、代わりに`rcx:rbx`を置き換え値として使います。
唯一のオペランドは16バイトにアラインされたメモリ位置です。
この命令はまた、`rax`だけでなく`rdx:rax`をアキュムレータとして使います。

## メモリの順序付け

ここまでの操作はすべて、1つの場所だけに触れてきました。
スレッドが複数の場所を通じて協調するとき、新しい疑問が現れます。あるスレッドの書き込みは、別のスレッドにどのような順序で見えるようになるのか、という疑問です。
この疑問に答える規則が、プロセッサの**メモリ順序付け**です。

[branchless-code][branchless-code]のコンセプトでは、現代のコアが命令を1つずつ黙々とこなすわけではないという考えを紹介しました。
コアは多くの命令を同時に飛ばしておき、進めるところでは先へ進みます。
つまり、ある書き込みが、プログラムの示すより遅くほかのコアに見えるようになる一方で、そのあとの命令はすでに先へ進んでいることがあります。

x86-64は通常のロードとストアの間で**強いメモリ順序付け**を保つので、各コアでは次のようになります。

1. ロードが、あとのロードの後ろに並べ替えられることはありません。
2. ストアが、あとのストアの後ろに並べ替えられることはありません。
3. ロードが、あとのストアの後ろに並べ替えられることはありません。

唯一あり得る並べ替えは、_異なる_アドレスのあとのロードのあとに、ストアが完了したように見える場合です。

`lock`プレフィックス付きの命令、またはメモリオペランドを持つ`xchg`は、完全なバリアです。どちらの向きにも、何かがそのバリアを越えて移動したようには見えません。
これが、ほとんどの状況で完全な順序付けを保証するのにそれらで十分な理由です。

唯一生き残る並べ替えの背後にある仕組みは、**ストアバッファ**です。
先へ進み続けるために、コアは各ストアをそのバッファに置き、ストアがほかのコアに見えるメモリに届く前に、あとの命令を進めます。
したがって、書き込みのあとに異なる場所の読み出しが続くと、順序が入れ替わって見えることがあります。あとの読み出しが先へ進む間、書き込みはまだバッファに残っているかもしれません。
このモデル、つまり書き込みのあとの読み出しの隙間以外はすべて順序付けられるモデルは、**total store order**と呼ばれます。

そのたった1つの隙間が、ストアしてから確認するハンドシェイクを壊すのに十分です。
2つのスレッドがそれぞれ自分のフラグを書き込んでから相手のフラグを読むと、どちらのストアもまだストアバッファを出ていないため、どちらの読み出しも未設定のまま返ってくることがあります。
`mfence`命令はストアバッファを空にすることでこの隙間を埋めます。それより前のすべての書き込みは、それよりあとのどの読み出しよりも先に見えるようになります。

```x86asm
    mov dword [rdi], 1    ; publish: this thread is ready
    mfence                ; the store above must land before the load below
    mov eax, dword [rsi]  ; observe whether the other thread is ready
```

より範囲の狭いバリアも2つあります。
- `sfence`は書き込み同士の順序を定め、主にストリーミングのノンタイムポーラルストアで重要です。
- `lfence`は読み出しの順序を定めます。

上の通常のアトミックなパターンでは、`lock`プレフィックス付きの命令がすでに完全な順序付けを備えているので、明示的なバリアが必要なのは、上のような素のストアとロードで組み立てたハンドシェイクだけです。

これらの保証には、x86を超えて通用する名前があります。
ある操作が**acquire**順序付けを持つとは、あとのアクセスがその前に移動したように見えない場合です。**release**順序付けを持つとは、前のアクセスがそのあとに移動したように見えない場合です。
x86では、すべてのロードがacquireであり、すべてのストアがreleaseであり、`lock`プレフィックス付きの命令、またはメモリを伴う`xchg`は、両方を同時に備えています。

## スピンと`pause`

フラグをセットしつつ、その以前の状態も返す命令は、[**test-and-set**][test-and-set]として知られています。
これらは[**スピンロック**][spinlock]の基礎として使え、あるコアがコードの一部を排他的にアクセスできるようにします。

2値のフラグとともに`xchg`命令を使う、全体のアルゴリズムは次のとおりです。

1. フラグは`0`から始まります。
2. ロックを獲得するために、コアはフラグの値を`1`と交換します。
3. 返された値が`1`なら、そのロックは別のコアに_保持されている_ということです。現在のコアは待ってから、もう一度ロックの獲得を試みます。
4. 返された値が`0`なら、そのロックは空いていたということです。`xchg`はそれを`1`にセットしたので、ほかのコアはこのコアが解放するまで待ちます。
5. 現在のコアが作業を終えたら、フラグを`0`に更新することでロックを解放します。

```x86asm
acquire:
    mov  eax, 1
    xchg dword [rdi], eax ; try to take the lock; eax = its old value
    test eax, eax
    jnz  .held            ; old value was 1: someone else holds it
    ret                   ; old value was 0: the lock is ours
.held:
    pause                 ; wait before trying again
    jmp  acquire
```

待機ループの中の`pause`命令は、コードの計算内容を変えません。
これはプロセッサに、これがスピンウェイトであることを伝えるヒントです。
CPUはそうすることで、待機中のスレッドの消費電力を減らし、同じコアを共有する兄弟スレッドに譲ることができます。
`pause`のないスピンループも依然として正しく、ただ無駄が多いだけです。

test-and-setでは、`xchg`のような命令は、フラグがすでにセットされていても常にそれをセットすることに注意しましょう。
つまり、ロックがまだ保持されている可能性が高いときでも、スピンするたびにメモリへの排他的アクセスを得てしまいます。

このアルゴリズムには[**test-and-test-and-set**][test-and-test-and-set]として知られる変種があり、まずフラグをテスト（読み出し）して、すでにセットされているか確認します。
そして、ロックが空いているように見えたときにだけ、test-and-set（この場合は`xchg`）を試みます。

```x86asm
acquire:
    mov  eax, 1
    xchg dword [rdi], eax ; try to take the lock
    test eax, eax
    jz   .taken           ; got it
.held:
    pause                 ; wait before trying again
    cmp  dword [rdi], 0   ; watch the lock without writing to it
    jne  .held            ; still held
    jmp  acquire          ; looks free: retry
.taken:
    ret
```

スレッドが作業を終えたら、`mov`を使って`0`を素のストアで書き込むことでロックを解放できます。
`mov`以上のものは必要ありません。x86-64ではロードとストアが、あとのストアの後ろに並べ替えられることはないからです。
前にあるアクセスを追い越さないストアは、**release順序付け**を持つと言われ、x86ではすべての素のストアがそれを持っています。

~~~~exercism/note
メモリ位置をアトミックにテストしてセットする命令なら、スピンロックに使えます。
たとえば、特定のビットをセットしつつ、すでにセットされていたか確認するために、`xchg`の代わりに`lock bts`を使えます。

`bts`が変更する`CF`のようなフラグは、レジスタである`rflags`の一部であることに注意しましょう。
つまり、フラグは各スレッドに固有です。
~~~~

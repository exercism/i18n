# はじめに

1つの命令は、一見するとこれ以上分割できない1つの動作に見えますが、実際にはそうではありません。メモリ上の値に5を足す処理を考えてみましょう。

```x86asm
add qword [rel counter], 5
```

内部では、プロセッサーはメモリに直接足し算をする手段を持っていません。この1つの命令を、**マイクロオペレーション**と呼ばれる3つの小さなステップに分解します。

1. メモリから現在の値を**読み出し**ます。
2. レジスタ上でこの値に5を足して**変更**します。
3. 結果を**書き戻し**ます。

```x86asm
mov rax, qword [rel counter] ; 1. load the current value
add rax, 5                   ; 2. add five
mov qword [rel counter], rax ; 3. store the result back
```

これは**read-modify-write（RMW）**と呼ばれるよくあるパターンです。

読み出し（ロード）と書き込み（ストア）は別々の出来事なので、その間には時間的な隙間があります。通常はこれに気づきません。シングルコアでは、各命令がその効果を完全に及ぼしてから次の命令が実行されることが保証されているからです。そのため、この隙間は目に見えず、`add`は1つのまとまりとして振る舞います。

しかし、現代のCPUがシングルコアであることはまれで、アプリケーションは複数のコアで同時に動くことがよくあります。コア同士の間には順序付けがありません。複数のコアがまったく同じ瞬間に動いていると、このコアのロードのあと、ストアの前に、別のコアがその隙間で`counter`を読み書きできてしまいます。2つのスレッドがそれぞれ同じ古い値をロードし、それぞれ5を足し、それぞれ結果をストアします。足し算は2回行われましたが、値は5しか増えていません。片方の更新が黙って失われたのです。

これが**データ競合**で、マルチスレッドのコードではよくある問題です。

すべての値がこのように危険にさらされるわけではありません。各スレッドは独自のレジスタと独自のスタックを持っているので、レジスタに保持された値や、スレッドのスタック上のローカル変数はそのスレッドだけのものであり、競合することはありません。保護が必要なのは、上の`counter`のように、スレッド間で共有しているメモリだけです。

x86-64には、命令を分割不可能にすることでこの問題を解決する命令群があります。その命令は、それを処理するコアだけでなく、他のすべてのコアにとっても1つのまとまりとして振る舞います。このようにばらばらにならず、他のどのコアにも分割できない操作を**アトミック**と呼びます。

~~~~exercism/note
多くのコアで動くアプリケーションをマルチスレッドと呼ぶことはよくあります。しかし、**スレッド**とコアは同じものではありません。2つのスレッドが同じコア上で同時に動き、互いに交互に実行されることもありますし、別々のコア上で並行して動くこともあります。

交互に実行されるスレッドどうしでも、read-modify-writeが複数の命令に分かれていれば、すでに競合を起こすことがあります。OSは任意の2つの命令の間でスレッドを切り替えられるからです。一方、_単一の_命令の内部にある隙間が露出するのは、真に並行なコードだけです。OSがスレッドを切り替えるのは命令と命令の間だけで、命令の内部で切り替えることは決してないため、単一の命令はシングルコアでは本質的に安全です。

_複数の_コアにまたがる真のアトミック性を提供するのが、以下の命令です。
~~~~

## アトミック交換

`xchg`命令は2つのオペランドを交換します。デスティネーションオペランドはソースオペランドに入っていた以前の値と等しくなり、ソースオペランドはデスティネーションオペランドに入っていた以前の値と等しくなります。概念的には、2つの`mov`命令が同時に起こるようなものだと考えられます。

通常どおり、2つのレジスタオペランドと組み合わせても、1つのメモリオペランドと1つのレジスタオペランドと組み合わせても使えます。

```x86asm
mov  eax, 1
xchg dword [rdi], eax ; [rdi] = 1, eax = the old value of [rdi]
mov ecx, 2
mov edx, 3
xchg edx, ecx         ; edx = 2, ecx = 3
```

メモリオペランドと組み合わせて使う場合、`xchg`は_常に_アトミックです。

~~~~exercism/caution
オペランドの一方がメモリ上の場所である場合、`xchg`は自動的にアトミックになります。これは、その状況ではこの操作がずっと遅くなることも意味します。

アトミック性が必要ないなら、代わりに空いているレジスタを経由して、通常の`mov`命令で交換してください。
~~~~

## `lock`プレフィックス

x86-64で命令をアトミックにする最も一般的な方法は、`lock`プレフィックスを付けることです。これは読み出し、変更、書き込みを1つの分割不可能なステップに融合します。つまり、その処理の間ずっとコアがそのメモリを占有するため、他のコアが途中でその場所を読み書きすることはできません。

```x86asm
lock add qword [rel counter], 5 ; the read, the modify, and the write are one step
```

`lock`が機能するのは、デスティネーションがメモリである場合だけで、しかもそのメモリを読み出し・変更・書き込みする命令に限られます。

1. `add`、`sub`、`inc`、`dec`、`neg`のような算術演算。
2. `and`、`or`、`xor`、`not`のようなビット単位の演算。
3. `bts`、`btr`、`btc`というビット操作。
4. 後述する`xadd`や`cmpxchg`など、そのための専用命令。

~~~~exercism/caution
1つの場所を占有し、他のすべてのコアを締め出すには、それ相応のコストがかかります。`lock`を付けた操作は、付けない場合より明らかに遅く、複数のコアが同じ場所を奪い合うときはさらに遅くなります。

このプレフィックスは、複数のスレッドから変更されることが想定されるメモリに限って使ってください。メモリが共有されていない場合や、読み出されるだけの場合は使わないようにしましょう。
~~~~

## 交換と加算

通常の`lock add`はメモリを更新しますが、古い値は捨ててしまいます。古い値こそが欲しいものであることもよくあります。たとえば、各スレッドに重複しないチケット番号を配るときです。

`xadd`命令（`x`はexchangeの意味）は、加算しながら以前の値を返します。合計をデスティネーションに書き込み、元のデスティネーションの値はソースレジスタに残します。

```x86asm
mov  rax, 1
lock xadd qword [rdi], rax ; [rdi] = [rdi] + rax = [rdi] + 1
                           ; rax = the old value of [rdi]
```

`lock`プレフィックスを付ければ、これはアトミックな**fetch-and-add**になります。同じカウンターに対して多くのスレッドから実行すると、各呼び出しはそれぞれ異なる古い値を返します。

`lock add`と同様、カウンターは最終的に呼び出し回数と正確に一致します。ただし、`lock add`と違って、途中の各値も返され、呼び出し元それぞれが1つずつ受け取ります。

## 比較と交換

`xadd`は加算し、`xchg`は上書きしますが、どちらも、新しい値を現在の値に依存させ、その間に何も変わっていない場合にだけ適用する、ということはできません。この条件付きの更新を提供するのが、比較と交換を行う`cmpxchg`です。これはこれらのプリミティブの中で最も汎用的なものです。

`cmpxchg dest, src`は`rax`を暗黙のアキュムレーターとして使い、それを`dest`と比較します。

- `dest == rax`なら、`dest = src`となり、`ZF = 1`になります。
- `dest != rax`なら、`rax = dest`となり、`ZF = 0`になります。

`dest`が更新されるのは、あらかじめ`rax`にロードしておいた期待値と等しい場合だけである点に注意してください。この等しさによって、`dest`が、新しい値の計算もとになった値のままであることが保証されるため、古くなった読み出しに基づく更新が適用されることはありません。こうして`cmpxchg`は、**compare-and-swap（CAS）**とも呼ばれるアトミックな更新の構成要素になります。

```x86asm
    mov rax, qword [rdi]          ; rax = the value we expect to find
.retry:
    lea rcx, [rax + 10]           ; rcx = the new value we want to install
    lock cmpxchg qword [rdi], rcx ; if [rdi] still equals rax, store rcx and set ZF
                                  ; otherwise reload rax with the current value, clear ZF
    jnz  .retry                   ; ZF is cleared, so another thread won the race. Recompute and retry
```

この**リトライループ**が、ロックフリーな更新の心臓部です。読み出しと比較交換の間の隙間こそ、別のスレッドが割り込むかもしれない瞬間であり、`cmpxchg`は、古い読み出しから計算した値をストアすることを拒むことで、それを受け止めます。

## メモリオーダリング

ここまでの操作はどれも、1つの場所だけに触れてきました。スレッドが複数の場所を通じて協調するようになると、新しい疑問が生まれます。あるスレッドの書き込みは、どのような順序で別のスレッドから見えるようになるのでしょうか。この疑問に答えるのが、プロセッサーの**メモリオーダリング**という規則です。

ブランチレスコードの概念では、現代のコアが命令を1つずつ順番にこなしていくわけではない、という考え方を紹介しました。コアは多数の命令を同時に実行中に保ち、可能なところでは先へと進みます。そのため、書き込みがプログラムの想定より遅れて他のコアから見えるようになる一方で、そのあとの命令はすでに先へ進んでいる、ということが起こります。

x86-64では、通常のロードとストアの間に**強いメモリオーダリング**が保たれています。その結果、各コアでは次のようになります。

1. ロードが、あとのロードの後ろに並べ替えられることはありません。
2. ストアが、あとのストアの後ろに並べ替えられることはありません。
3. ロードが、あとのストアの後ろに並べ替えられることはありません。

並べ替えが起こりうるのは、_異なる_アドレスに対するあとのロードのあとに、ストアが完了したように見える場合だけです。

`lock`を付けた命令、またはメモリオペランドを使う`xchg`は完全なバリアです。どちらの向きにも、それをまたいで移動するものは何もないように見えます。そのため、ほとんどの状況で完全な順序付けを保証するのにこれらで十分なのです。

## スピンと`pause`

フラグを立てると同時に、その以前の状態も返す命令は、**test-and-set**として知られています。これらは**スピンロック**の土台として使うことができ、あるコアがコードのある部分を独占的に使えるようにします。

`xchg`命令を2値のフラグと組み合わせて使う、全体のアルゴリズムは次のとおりです。

1. フラグは`0`から始まります。
2. ロックを取得するには、コアがフラグの値と`1`を交換します。
3. 返された値が`1`なら、ロックは別のコアに_保持されている_ということです。現在のコアは待機してから、もう一度ロックの取得を試みます。
4. 返された値が`0`なら、ロックは空いていたということです。`xchg`によってフラグは`1`に設定されたので、他のコアはこのコアがロックを解放するまで待ちます。
5. 現在のコアが作業を終えたら、フラグに`0`を書くことでロックを解放します。

```x86asm
acquire:
    mov  eax, 1
    xchg dword [rdi], eax ; try to take the lock; eax = its old value
    test eax, eax
    jnz  .held            ; old value was 1: someone else holds it
    ret                   ; old value was 0: the lock is ours
.held:
    pause                 ; wait before trying again
    jmp  acquire
```

待機ループ内の`pause`命令は、コードの計算結果を変えるものではありません。これはスピン待機であることをプロセッサーに伝えるヒントです。するとCPUは、待機中のスレッドの消費電力を抑え、同じコアを共有する兄弟スレッドに実行を譲ることができます。`pause`のないスピンループでも正しく動作しますが、無駄が多いだけです。

スレッドは作業を終えたら、`mov`で`0`をそのままストアしてロックを解放できます。`mov`以外の何も必要ありません。x86-64では、ロードもストアも、あとのストアの後ろに並べ替えられることがないからです。その前にあるアクセスを追い越すことのないストアは、**release ordering**を持つと言われます。x86では、通常のストアがすべてこれを持っています。

~~~~exercism/note
メモリ上の場所をアトミックにテストして設定する命令なら、どれでもスピンロックに使えます。たとえば、`xchg`の代わりに`lock bts`を使って、特定のビットがすでに立っているかを確認しながらそのビットを立てることができます。

`bts`が変更する`CF`のようなフラグは、レジスタである`rflags`の一部である点に注意してください。つまり、フラグは各スレッドに固有のものです。
~~~~

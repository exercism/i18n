# はじめに

スマートポインターは、自動的なメモリ管理を実現するために設計されたC++のモダンな機能で、生のポインターにありがちなメモリリークやダングリングポインターの防止に役立ちます。
生のポインターを包み込むラッパーとして機能し、ポインターが不要になったときの自動的なメモリ解放といった機能を追加します。

## 基本的な構文

スマートポインターは通常、C++標準ライブラリでクラステンプレートとして実装されています。
最もよく使われるスマートポインターは、`std::unique_ptr`と`std::shared_ptr`の2つです。

## ユニークポインター

`std::unique_ptr`は、オブジェクトを独占的に所有するスマートポインターです。
常にただ1つの`std::unique_ptr`だけがそのリソースを所有することを保証します。
所有している`std::unique_ptr`が破棄またはリセットされると、オブジェクトを自動的に破棄し、メモリを解放します。

```cpp
#include <memory>
// Declaring and defining a unique pointer
auto rightful_king_of_england = std::make_unique<std::string>("Excalibur");

// Unique pointers cannot be copied or assigned
auto mordred = rightful_king_of_england; // Error: Cannot copy a unique_ptr
```

## `std::make_unique()`の利点

`std::unique_ptr`を作成するときは、`new`を直接使ってメモリを確保するよりも、`std::make_unique()`を使うのが好ましいです。
`std::make_unique()`には、次のようないくつかの利点があります。
1. **例外安全性**: `std::make_unique()`は例外安全性を保証します。
  オブジェクトの構築中に例外が投げられても、メモリは自動的に解放され、メモリリークを防ぎます。
2. **明確さ**: `std::make_unique()`を使うと、コードがより明確で簡潔になります。
  テンプレート引数が自動的に推論されるため、確保する型を明示的に指定する必要がありません。
3. **最適化の機会**: コンパイラーは、`new`で手動でメモリを確保するよりも`std::make_unique()`を効果的に最適化できる可能性があり、パフォーマンスの向上につながることがあります。
4. **誤用の防止**: `std::unique_ptr`を手動で構築した場合、その基になるリソースを削除できてしまいます。
  そうすると、`std::unique_ptr`がスコープの終わりにそのリソースを削除しようとしたときに、未定義動作を引き起こします。

## 共有ポインター

`std::shared_ptr`は、複数の`std::shared_ptr`で同じリソースの所有権を共有できるスマートポインターです。
そのリソースを参照している共有ポインターの数を追跡し、リソースを所有する最後の共有ポインターがスコープを外れるかリセットされたときにだけメモリを解放します。

```cpp
// Declaring and defining a shared pointer to a dynamically allocated string
auto martian_congressional_republic = std::make_shared<std::string>("protomolecule");

// Creating more shared pointer that shares ownership
auto outer_planets_alliance = martian_congressional_republic;
auto united_nations = martian_congressional_republic;
```

~~~~exercism/caution
C++17以前では、`std::make_shared<T[]>`を使って配列を`std::shared_ptr`で扱うことは直接サポートされていません。
`std::make_shared<T[]>`で配列を確保することは可能ですが、そこから直接共有ポインターを作成すると、単一のオブジェクトと配列のメモリ管理の違いにより、未定義動作を引き起こす可能性があります。
代わりに、`std::vector`やカスタム削除関数を使って、共有ポインターで配列を効果的に管理することを検討してください。
C++17で配列の確保と共有ポインターを扱うときは、常に使用するコンパイラーと標準ライブラリの実装との互換性を確認してください。
~~~~

## `std::make_shared()`の利点

`std::make_unique()`と同様に、`std::make_shared()`にも、メモリ効率の向上、例外安全性、可読性といった利点があります。
制御ブロックと管理対象オブジェクトのメモリ確保を1つの操作にまとめることで、効率を高め、メモリリークのリスクを減らします。
さらに、テンプレート引数が自動的に推論されるため、コードが簡潔になり、可読性が向上します。
C++で`std::shared_ptr`を扱うときは、`std::make_shared()`を使うことで、よりクリーンで安全、かつ効率的なコードになります。

## ウィークポインター

`std::weak_ptr`は、`std::shared_ptr`と対になるクラスで、共有ポインターが管理するオブジェクトへの、所有権を持たない「弱い」参照を提供します。

```cpp
// Creating a shared pointer
auto your_account = std::make_shared<std::string>("secret_subscription_password");
// Creating a shared pointer that shares ownership
auto your_flatmates_account = your_account;

// Creating a weak pointer from the shared pointer
auto your_flatmates_boyfriends_account = your_flatmates_account;
// if your_account and your_flatmates_account are deleted, there is no more reference to the shared pointer.
// your_flatmates_boyfriends_account will be a null pointer and cannot use the associated object any longer.
```

ウィークポインターは、メモリリークを防ぐために循環参照を断ち切る必要がある場面で役立ちます。
`std::weak_ptr`は、`std::shared_ptr`を使うときに起こりうる、循環所有（循環参照とも呼ばれます）の問題に対処するために設計されました。
循環所有の状況では、2つ以上の`std::shared_ptr`が互いを参照し合い、強い参照を持っているためにどのオブジェクトも削除できなくなる循環が生まれ、メモリリークにつながります。
`std::weak_ptr`は、参照カウントに影響を与えずに共有オブジェクトへの弱い参照を持てるようにすることで、この問題の解決策を提供します。
つまり、共有オブジェクトを監視してアクセスできますが、そのオブジェクトの削除を妨げることはありません。
~~~~

## 使い分けの指針

基本的にはスマートポインターを使いましょう。独占的な所有には`std::unique_ptr`、共有の所有には`std::shared_ptr`を使います。
生のポインターは、所有権を持たない参照や、レガシーコードとやり取りする場合にとっておきましょう。
ほとんどの場合、独占的な所有には`std::unique_ptr`で十分です。参照カウントのオーバーヘッドなしに、軽量なメモリ管理を提供してくれます。
`std::shared_ptr`は、本当に所有権を共有する必要がある場合を除いて、オーバーヘッドと複雑さを持ち込むため、使うのは控えめにしましょう。
`std::weak_ptr`は、循環依存を断ち切ったり、共有オブジェクトを監視したりするために特化したもので、一般的に使われるものではありません。

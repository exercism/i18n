# 概要

[条件分岐][conditionals-concept]の概念では、条件に基づいて分岐する命令ファミリーである`jcc`を紹介します。
`jcc`は、条件が満たされたときだけ、プログラムの別の地点に実行を移します。

しかし、現代のCPUは高速で、多くの命令を並列に実行できます。
条件を実行時にチェックしている間、すべての処理を止めて待つのは、コストがかかりすぎます。

そのため、CPUは内部的には待ちません。
[分岐予測器][branch-predictor]を使って条件の結果を推測し、予測した経路を_投機的に_実行し始めます。

予測が当たれば、分岐がなかったかのように実行が進みます。
しかし、予測が外れると、CPUは予測した経路で_行った処理を破棄_して、正しい経路でやり直さなければなりません。

これは**分岐予測ミス**と呼ばれ、遅延を伴うためコストが高くつきます。

分岐の予測が難しいと、こうした予測ミスが積み重なります。
そういう場合は、分岐を完全になくして、条件に関係なく同じ命令が実行されるようにするほうがよいことがあります。
`jcc`を使わずに値の選択を行うコードは、**ブランチレス**と呼ばれます。

コードの分岐を減らしたり、ある分岐の予測をしやすくしたりする書き方には、いくつかの方法があります。
とくにx86-64には、ブランチレスコードを書くためによく使われる2つの命令ファミリーがあります。

## 条件付き移動

[cmovcc][cmov]の命令ファミリーは、特定の条件が満たされたときだけ、転送元オペランドを転送先にコピーします。
それ以外の場合、転送先は変わりません。

`cc`というサフィックスは、`jcc`と同じ命名規則に従い、意味も同じです。

| 命令 | 移動する条件 |
|-------------|--------------------------------------|
| `cmove`     | `cmp A, B`の後で A == B              |
| `cmovne`    | `cmp A, B`の後で A != B              |
| `cmovl`     | `cmp A, B`の後で A < B（符号あり）   |
| `cmovb`     | `cmp A, B`の後で A < B（符号なし）   |
| `cmovg`     | `cmp A, B`の後で A > B（符号あり）   |
| `cmova`     | `cmp A, B`の後で A > B（符号なし）   |

規則は`jcc`と似ています。

1. `l`と`g`は符号ありの比較に使います。`b`と`a`は符号なしに使います。
2. サフィックスに`e`を付けると、等しい場合も含まれます。
3. `n`を付けると、条件が否定されます。
4. フラグがセットされていることを参照する変種もあります。
   たとえば`cmovz`や`cmovc`です。

`rdi`にある符号あり整数の絶対値を求めて`rax`に返すことを考えてみましょう。
`jcc`で書くと、この関数は2つの経路のどちらかを選びます。

```x86asm
abs_branch:
    mov rax, rdi
    cmp rax, 0
    jge .done
    neg rax
.done:
    ret
```

`cmovcc`で書くと、2つの候補値がどちらも無条件に計算され、条件付き移動がそのうちの一方を選びます。

```x86asm
abs_branchless:
    mov rax, rdi
    neg rax            ; rax = -rdi
    cmp rdi, 0
    cmovge rax, rdi    ; if rdi >= 0, rax = rdi
                       ; otherwise rax stays = -rdi
    ; now rax = abs(rdi)
    ret
```

ブランチレスの版は、いつも同じ命令を実行します。
予測器が推測する`jcc`はありません。

`cmovcc`の転送先はレジスタでなければなりません。
転送元にはレジスタかメモリの場所を指定できますが、即値は指定できません。

~~~~exercism/note
上のコードでは、`neg`命令が結果に応じていくつかのフラグを設定します。その中には符号フラグ（SF）も含まれます。
つまり、`cmp rdi, 0`は完全に省けます。

```x86asm
abs_branchless:
    mov rax, rdi
    neg rax            ; rax = -rdi. `neg` sets SF = 1 if the result is negative
    cmovs rax, rdi     ; if SF = 1 (i.e., rax < 0), replace rax with rdi
                       ; otherwise rax stays = -rdi, which is non-negative
    ; now rax = abs(rdi)
    ret
```

`rdi`が正のとき、`neg`は負の結果を生み、SF = 1になるので、`cmovs`が`rdi`を復元します。
`rdi`が0か負のとき、`neg`は非負の結果を生み、SF = 0になるので、`rax`は否定した値（これが正しい絶対値です）を保ちます。

アセンブリコードで値を比較する主な方法は`cmp`ですが、多くの命令も自分の結果に応じてフラグを設定します。
ある命令が影響を与えるフラグの完全な一覧は、たいていその[リファレンス][reference]に載っています。
`neg`の場合は、SF、ZF、CF、OF、PFです。

[reference]: https://www.felixcloutier.com/x86/
~~~~

## 条件付きセット

[setcc][set]の命令ファミリーは、特定の条件が満たされたときは転送先オペランドを`1`に、それ以外のときは`0`に設定します。
転送先は常に_8ビットのオペランド_です。

`cc`サフィックスは、`jcc`や`cmovcc`と同じ命名規則に従います。
たとえば`setz`は、`ZF == 1`なら転送先を`1`に、それ以外なら`0`に設定します。

転送先が8ビットなので、より幅の広い値が必要なときは、`setcc`の後に`movzx`を続けるのが一般的です。

```x86asm
cmp rdi, rsi
setg al             ; al = 1 if rdi > rsi (signed), 0 otherwise
movzx eax, al       ; eax (and rax) = 1 or 0, with the upper bits cleared
```

これは、比較の結果を整数の`0`か`1`に変える際によく使われるイディオムです。

## ブランチレスコードを使うべきとき

ブランチレスコードが、分岐のあるコードよりいつも速いわけではありません。
分岐の予測が非常にしやすいときは、予測器がほぼ毎回当てるので、`jcc`のコストは実質ゼロです。
そうした分岐を置き換えるブランチレスコードは、候補の計算をいつも両方実行するため、かえって遅くなります。

ループカウンターはその典型例です。
`rdi`から始まる`rsi`個の64ビット整数を合計する関数を考えてみましょう。

```x86asm
sum_array:
    xor rax, rax
.loop:
    add rax, [rdi]
    add rdi, 8
    dec rsi
    jnz .loop          ; taken on every iteration except the last
    ret
```

これはまさに分岐予測器が得意とするパターンなので、`sum_array`がいくつの要素を処理しても、この分岐には実質的にコストがかかりません。

ブランチレスコードが効果を発揮するのは、分岐の予測が難しいときや、入力に関係なく一定のタイミングが求められるときです。

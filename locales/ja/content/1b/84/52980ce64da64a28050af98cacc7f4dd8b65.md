# 概要

[コールスタック][stack]、あるいは単に**スタック**は、メモリの最も高い位置から始まり、下に向かって伸びていく特殊なデータ構造です。

## プッシュとポップ

スタックは少なくとも2つの操作をサポートしていて、それぞれ同じ名前の命令があります。

| 命令   | 実行される操作                                     |
| ------ | -------------------------------------------------- |
| `push` | スタックに要素を追加します                         |
| `pop`  | 直前に追加された要素を取り出して返します           |

つまり、スタックは**後入れ先出し（LIFO）**のデータ構造です。

スタックの現在の位置、つまり直前に追加された要素がある場所を把握するために、`rsp`というレジスタを使います。

そこで、[push][push]命令は1つのオペランドを取り、そのオペランドの内容をスタックに格納します。
スタックは下に向かって伸びるので、`rsp`の値は格納した値のサイズだけ減ります。

同様に、[pop][pop]命令は1つのオペランドを取り、スタックの中で最も新しい値（`rsp`が指している値）をそのオペランドに格納します。
その後、`rsp`の値は取り出した値のサイズだけ増えます。

## ローカル変数

`rsp`の値を直接操作することもできます。
これは、関数のローカル変数を作るためによく使われます。

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

スタックに領域を確保した時点では、その領域に格納されている値は_未定義_であることに注意してください。

~~~~exercism/note
`pop`も`rsp`の直接操作も、実際にはメモリに格納された内容を削除しません。スタックからの「削除」は、`rsp`の新しいアドレスによって抽象化されているだけです。

状況によっては、内部の値が外部に漏れることでセキュリティ上の懸念が生じることがあります。これに対処する方法の1つは、関数が使ったスタック領域の内容をゼロで埋めることです。
~~~~

## callとret

スタックの主な目的は、呼び出された関数の戻りアドレスを把握しておくことです。

以前のコンセプトで触れたように、次に実行される命令を指す`rip`という特別なレジスタがあります。
このレジスタはプログラムの流れを制御するために使われ、`jmp`や`call`といった命令によって書き換えられます。

`call`命令を使うと、そのときの`rip`の値が暗黙的にスタックにプッシュされます。
続いて、命令のオペランドが`rip`に移動し、呼び出された関数で実行が続きます。

`ret`命令は逆の操作を行います。
スタックから`rip`にポップして、呼び出し元の関数に実行が戻ります。

関数に入った時点では、`rsp`は戻る先のアドレスを指しています。
これが、`ret`がスタックからポップすべきアドレスです。

したがって、関数の中で直接であれ`push`であれ`rsp`の値を変えたら、関数から戻る前に元に戻さなければなりません。

## 呼び出し先保存レジスタと呼び出し元保存レジスタ

`rsp`のほかにも、関数呼び出しをまたいで保存しなければならないレジスタがあります。`rbp`、`rbx`、`r12`、`r13`、`r14`、`r15`です。
一般に、呼び出し元の関数は、呼び出された関数によってそれらのレジスタが書き換えられないまま使えることを期待しています。

つまり、_呼び出された_関数は、それらのレジスタを使う前に値を保存し、戻る前に元の値に復元しなければなりません。
これが、これらのレジスタが**呼び出し先保存レジスタ**と呼ばれる理由です。

その他の汎用レジスタは、呼び出された関数がそのまま使えます。

つまり、_呼び出し元_の関数は、呼び出された関数によって書き換えられる場合に備えて、関数を呼び出す前にそれらのレジスタの値を保存しなければなりません。
これが、これらのレジスタが**呼び出し元保存レジスタ**と呼ばれる理由です。

_レジスタの内容を保存する最も一般的な方法は、それをスタックに格納することです。_

## プロローグとエピローグ

場合によっては、関数から戻るまでにスタックが頻繁に使われ、多くの変更が加えられることがあります。
そのため、それらすべての変更を把握して元に戻すのは複雑になることがあります。

そのような場合によく使われる戦略は、関数内でそれ以外は変更されない別のレジスタに`rsp`のアドレスを保存しておくことです。
そして、関数から戻る前に、最後に簡単な`mov`命令で`rsp`の値を復元できます。

どのレジスタでもこの目的に使えますが、慣習的に`rbp`をベースポインタとして使います。
`rbp`自体が呼び出し先保存レジスタなので、その前に`push rbp`を置くことがよくあります。
この一連の命令は通常**プロローグ**と呼ばれます。

最後に、`mov rsp, rbp`で`rsp`を復元し、続いてスタックからの`pop`で`rbp`も復元します。
この一連の命令は通常**エピローグ**と呼ばれます。

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

~~~~exercism/note
プロローグとエピローグの主な目的は、`rsp`への変更を把握しやすくするためにプログラマーを助けることです。もちろん、コンパイラーにとってはこれのほうがずっと簡単です。

そのため、多くのコンパイラーは、フレームポインタを省略し、可能なときはプロローグとエピローグを取り除く最適化を行います。
~~~~

## スタックで引数を渡す

[System V ABI][SystemV]の呼び出し規約では、引数は通常レジスタで関数に渡されます。
しかし、引数が多すぎる場合や、1つのレジスタのサイズに収まらない場合は、スタックが使われることがあります。

そのような場合、値は逆の順序でスタックに追加され、最初の引数が`rsp`に近くなります。
関数に入った時点で`rsp`は戻りアドレスを指しており、x86-64ではこれが8バイトの値なので、スタック上の最初の引数があれば`rsp + 8`でアクセスできます。

```x86asm
mov rdi, 4   ; first argument
mov rsi, 8   ; second argument
mov rdx, 15  ; third argument
mov rcx, 16  ; fourth argument
mov r8, 23   ; fifth argument
mov r9, 42   ; sixth argument

; any remaining integer argument goes on the stack in reversed order
sub rsp, 16
mov qword [rsp], 100      ; seventh argument
mov qword [rsp + 8], 300  ; eighth argument

call many_arguments_fn ; call implicitly pushes `rip` to the stack
; so, at point of entry, 'many_arguments_fn' finds the first six integer arguments in the usual registers
; the seventh argument is found in rsp + 8
; and the eighth argument is found in rsp + 16
```

## スタックのアラインメント

System V ABIでは、`call`命令が実行される直前の時点で、スタックが16バイトにアラインされている必要があると定められています。
`call`は`rip`をスタックにプッシュするので、関数に入った時点での呼び出された関数のスタックは16バイトにアラインされて**いません**。

つまり、別の関数（特に外部の関数）を呼び出す関数は、`call`を使う前にスタックをアラインする必要があります。

これは、`rsp`から適切な値を引くことで行えます。
関数に入った時点で、この値は16の倍数より8大きい値、つまり8、24、40などでなければなりません。
`push`命令は`rsp`から引くので、奇数回の`push`でも同じ効果が得られます。

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

## レッドゾーン

System V ABIでは、`rsp`のすぐ下に128バイトの領域が予約されており、`rsp`を一切調整せずに使うことができます。
この領域は[レッドゾーン][red-zone]と呼ばれます。

```x86asm
fn:
    mov [rsp - 8], rax ; this is safe to use because it is in the red zone
    ret                ; no need to restore rsp
```

レッドゾーンを安全に使えるのは、リーフ関数、つまり他の関数を呼び出さない関数だけです。

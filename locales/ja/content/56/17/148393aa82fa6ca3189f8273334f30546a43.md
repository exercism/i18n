# はじめに

## 不透明型

### はじめに

不透明型は、Elmにおけるカプセル化の手法です。情報隠蔽、あるいは実装の詳細の隠蔽と呼ぶ人もいます。また、[Parse, dont validate][parse-dont-validate]パターンを使って検証を強制するのにもよく使われます。たとえば、有効なメールアドレスしか含むことのできない`EmailAddress`という不透明型を作ることができます（何でも含むことのできる`String`とは対照的です）。

### 不透明型を作る

[カスタム型][custom-types]には1つ以上の*バリアント*があり、コンパイラーは*バリアント*名を使って、各*バリアント*を作成する関数を自動的に生成します。カスタム型を作成できるのは、これが唯一の方法です。コンパイラーは、これらのバリアントに対する分解も可能にします。

```elm
type Maybe a
    = Nothing --> Variant implies a 'Nothing' function, with type 'Maybe a', and destructuring of 'Nothing'
    | Just a  --> Variant implies a 'Just' function, with type 'a -> Maybe a', and destructuring of 'Just _'
```

デフォルトでは、これらはすべてファイル／モジュール内部に閉じています。何をエクスポートするかは、`exposing`キーワードで選びます。不透明型を作るには、*バリアント*をエクスポートしないように選ぶだけです。

そうすると、ほとんどの場合、カスタム関数を公開することで、*バリアント*を作成したり取得したりする別の手段を用意する必要があります。これらのカスタム関数を使えば、*バリアント*を作成・取得するときに何らかのロジックを適用できます。これによりモジュールの内部実装の詳細が隠され、公開している関数が同じままであれば、実装の詳細をいくらでも変更できるようになります。

### Parse, don't validate

おそらく不透明型の最も一般的な用途は、[Parse, dont validate][parse-dont-validate]パターンを使った検証の強制です。このパターンでは、`String`のように、望むよりも構造や型安全性の低い入力を受け取る関数を公開し、それを`EmailAddress`のようなより構造化された型へと解析します。戻り値は、その型か、エラー（通常は`Maybe`や`Result`）です。

たとえば、以下のコードでは、外部のモジュールが`EmailAddress`型を作成できるのは`parseEmailAddress`関数を使う場合だけなので、`EmailAddress`型を扱うときには、それが有効であると確信できます。

```elm
module EmailAddress exposing ( EmailAddress, parseEmailAddress, getEmailAddress )

-- The `EmailAddress` custom type has one variant, also called `EmailAddress`
-- When a custom type has one variant, it is idiomatic to use the same name for both.
type EmailAddress = 
  EmailAddress String

-- create an EmailAddress variant
parseEmailAddress: String -> Maybe EmailAddress
parseEmailAddress candidateEmailAddress =   
  if isValidEmailAddress candidateEmailAddress then
    Just (EmailAddress candidateEmailAddress)
  else
    Nothing

-- get an EmailAddress variant
getEmailAddress: EmailAddress -> String
getEmailAddress ( EmailAddress  emailAdress ) =
  emailAdress

isValidEmailAddress: String -> bool
-- ... 
```

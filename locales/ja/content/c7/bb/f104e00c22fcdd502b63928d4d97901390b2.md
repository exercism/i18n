# はじめに

Juliaは、ほとんどのプログラミング言語と同じように、さまざまなコレクション型を提供しています。

もともと順序を持つものもあり（`Vectors`や多次元の`Arrays`など）、その場合は位置によって要素にアクセスできます。
順序を持たないコレクション（`Sets`、`Dicts`）では、キーや値を使って要素にアクセスしなければなりません。

最も単純な例として、`Ints`の`Vector`があり、それを昇順に並べ替えたいとしましょう。

```julia-repl
julia> v = [3, 2, 4, 1]
4-element Vector{Int64}:
 3
 2
 4
 1

julia> sort(v)
4-element Vector{Int64}:
 1
 2
 3
 4

# sort descending
julia> sort(v, rev=true)
4-element Vector{Int64}:
 4
 3
 2
 1
```

簡単です！
`sort()`関数は名前からも明らかなように、並べ替えられた`Vector`を返してくれるように見えます。

_冗談です！_
シラバスのこの段階まで来たなら、話し合うべき細かなニュアンスがあることに、（正しく）気づいているかもしれません。

## 破壊的な関数と非破壊的な関数

`sort(v)`を実行したあと、`v`はどうなっているでしょうか？

```julia-repl
julia> v
4-element Vector{Int64}:
 3
 2
 4
 1

julia> issorted(v)
false
```

元のベクターは変更されていません。
`sort()`は***非破壊的***な関数で、入力の_コピー_を返します。

多くの場面でこれはよい設計です。純粋な関数であり、並列・分散コードであっても動作を推論しやすいからです。

一方で、10億個の文字列からなる配列を並べ替えたいとします。

並べ替えにはおそらく時間がかかります。
さらに、すべてをコピーする必要があり（_遅い！_）、そのコピーを保存するために十分なメモリ（_数ギガバイト！_）を確保しなければなりません。

よく似た次のコードと比べてみましょう。

```julia-repl
# v is as previously

julia> issorted(v)
false

julia> sort!(v)
4-element Vector{Int64}:
 1
 2
 3
 4

julia> v
4-element Vector{Int64}:
 1
 2
 3
 4

julia> issorted(v)
true
```

今度は入力の`Vector`がコピーなしでその場で並べ替えられ、元の順序は永久に失われます。

これは効率的なこともありますが、バグを生んで予期しない副作用を引き起こすこともあり、コードを使うほかの人を混乱させることもあります。
_慎重に選びましょう！_

`sort!()`は「破壊的な関数」で、（_非常に強い_）慣習により、入力を変更する関数は名前の末尾に`!`を付けて、プログラマーへの警告とします。

## ソートインデックスの配列

並べ替える要素が大きなオブジェクトの場合、位置のインデックスを扱うほうが簡単なことがあります。

```julia-repl
julia> langs = ["Julia", "C++", "Python", "Elixir"]
4-element Vector{String}:
 "Julia"
 "C++"
 "Python"
 "Elixir"

julia> inxs = sortperm(langs)  # => Integers
4-element Vector{Int64}:
 2
 4
 1
 3

julia> langs[inxs]  # sort the entire vector
4-element Vector{String}:
 "C++"
 "Elixir"
 "Julia"
 "Python"

julia> langs[inxs[1:2]]  # slice the indices
2-element Vector{String}:
 "C++"
 "Elixir"
```

`langs`はVectorなので、各インデックスは`1:length(langs)`の範囲の整数です。
`sortperm()`の出力は、入力ベクターを並べ替えた結果に対応する、これらの整数の順列です。

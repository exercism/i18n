# ソート

```sather
   numbers.sort;                                  -- the natural order
   words.insertion_sort_by(bind(before(_, _)));   -- an order you supply
```

## `sort`に必要なもの

`sort`を使うには、要素の型に`is_lt`が備わっている必要があります。`INT`、`STR`、`CHAR`、`FLTD`、`INTI`にはどれも備わっています。自分で定義したクラスには、自分で`is_lt`を書くまでは備わりません。

`insertion_sort_by`は、要素の型に何も要求しません。必要な情報はすべて、渡すルーチンの中にあります。

## 比較に求められること

ルーチンは一貫した順序を定義していなければなりません。そうでないと、結果は不定になります。

- `before(a, b)`が`true`なら、`before(b, a)`は`false`でなければなりません。
- `a`が`b`より前で、`b`が`c`より前なら、`a`は`c`より前です。
- `before(a, a)`は`false`でなければなりません。

最後の項目こそ、多くの人がつまずくところです。`<`の代わりに`<=`と書くと、あるものが自分自身より前に来ることになってしまい、そんな比較を渡されたソートは、どんな結果を生むかわかりません。

## 同順位

`sort`も`insertion_sort_by`も**安定**ではありません。比較が等しいとみなしたものがどちらの順序で出てくるかは決まっておらず、このライブラリではたいてい逆順になります。

ですから、2回ソートするという定番のやり方、つまり、まず名前でソートし、次に得点でソートして、得点が同じチームは名前順のまま残ると期待する方法は、ここでは通用しません。入力の順序をあてにすることもできません。

同順位が問題になるなら、**比較の中**で解決しましょう。2つの異なる要素が決して等しいとみなされないよう、全順序にします。

```sather
   shorter(a, b : STR) : BOOL is
      if a.size /= b.size then return a.size < b.size; end;
      return a < b;                  -- same length: alphabetical
   end;
```

同順位など起きないと思っているときでも、こうする価値があります。どちら向きに呼んでもfalseを返す比較では、結果は不定のままになり、そのバグは、見た目には理由のない並び順の変化として現れます。

## そのほかのメソッド

| 呼び出し | 動作 |
| --- | --- |
| `a.sort` | その場で、自然な順序、安定ではない |
| `a.insertion_sort_by(lt)` | その場で、指定した順序、安定 |
| `a.is_sorted` | 確認 |
| `a.is_sorted_by(lt)` | 指定した順序で確認 |
| `a.binary_search(e)` | ソート済みの配列から探す |
| `a.binary_search_by(e, lt)` | 指定した順序で探す |

ソートされていない配列に対して`binary_search`を呼んでも、失敗はしません。返ってくるのは意味のない答えです。そのことは事前条件にも書かれていますが、コンパイラーに`-chk`を渡さない限り、事前条件はチェックされません。

## コスト

挿入ソートは、長さの2乗に比例する手間がかかります。十数チームの順位表ならそれで十分ですが、1万件のレコードには向きません。`ARR_SORT_ALG::sort_by`は、同じ考え方をクイックソートで実装したもので、配列が大きく、安定性が問題にならないときに使います。

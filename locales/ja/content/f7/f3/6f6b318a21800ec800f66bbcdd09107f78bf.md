# 概要

関数が[末尾再帰][recursion-tc]であるとは、その関数が_最後_に実行するのが自分自身への呼び出しである場合をいいます。

関数が呼び出されるたびに、ローカル変数と引数を持つ_スタックフレーム_が[コールスタック][call-stack]の一番上に積まれます。関数が戻ると、そのスタックフレームはスタックから取り除かれます。

末尾再帰の関数は、[末尾呼び出し最適化][tail-call-optimization]（末尾呼び出し除去ともいいます）を可能にします。これは、前の関数がもうそのスタックフレームを必要としないことが保証されているときに、次の関数呼び出しで最後のスタックフレームを再利用できるようにする最適化です。これにより、コールスタックのオーバーフローを心配する必要がやわらぎます。オーバーフローとは、コールスタック上のフレームが多すぎて、新しいフレームを作るためのメモリが残っていない状態のことです。

## Elmにおける末尾呼び出し最適化

ある条件のもとでは、Elmコンパイラーは、JavaScriptへコンパイルするときに末尾呼び出し最適化を自動的に行うことができます。

この最適化は、ある分岐での_最後_の操作が、単純な関数適用としてその関数自身を呼び出すことである場合に、再帰関数に対して行われます。いくつか例を見てみましょう。

```elm
factorial : Int -> Int
factorial n =
  if n <= 1 then
    n
  else
    n * factorial (n-1)
```

上の実装は末尾再帰ではありません。`else`の分岐での最後の操作が`n *`というかけ算だからです。

```elm
factorial : Int -> Int
factorial n =
  factorialHelper n n

factorialHelper : Int -> Int -> Int
factorialHelper n resultSoFar =
  if n <= 1 then
    resultSoFar
  else
    factorialHelper (n-1) (n * resultSoFar)
```

上の実装は末尾再帰であり、最適化されます。`else`の分岐での最後の操作が`factorialHelper`自身の呼び出しだからです。これは型シグネチャーが`Int -> Int`である関数では不可能であり、実際には、末尾呼び出し最適化はヘルパー関数を定義することでしばしば実現されます。

## エッジケース

場合によっては、コンパイラーは再帰関数を最適化できません。いくつか例を見てみましょう。

`f x = f (x - 1)`は末尾再帰ですが、`f x = (x - 1) |> f`はそうではありません。関数適用`|>`が最後の操作であり、`f`とは別のものと見なされるからです。同様に、真偽値の条件で終わる関数`f x = x > 0 || f (x - 1)`も末尾再帰ではありません。

関数`f x = if f (x - 1) then 1 else 0`は末尾再帰ではありません。`if`の中の式は分岐とは見なされないからです。同じように、`case`式の中の再帰呼び出しも最適化されません。

関数`f x = let y = f (x - 1) in y`は末尾再帰ではありません。`let`式の中で自分自身を呼び出しており、それは分岐とは見なされないからです。しかし、`f x = let g x = g (x - 1) in g x`では、関数`g`は末尾再帰であり、`let`式の中で定義されているにもかかわらず最適化されます。

関数`f x = if x > 0 then f (x + 1) else 1 + f x`は_部分的に_最適化されます。`then`の分岐は最適化できますが、`else`の分岐はできません。部分的に最適化するのが、木のような構造をたどる場合や、相互再帰関数を定義する場合など、状況によっては実現できる最善の方法です。

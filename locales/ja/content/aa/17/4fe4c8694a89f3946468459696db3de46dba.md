# 概要

## エラーにコンテキストを追加する

Goでの基本的なエラー処理については、[エラーのコンセプト][concept-errors]で扱いました。そこで学んだとおり、デフォルトではエラーはスタックトレースを保持しません。そのため、エラー自体に問題を特定するのに十分な情報が含まれていることが重要になります。

すでに知っている道具を使って既存のエラーに情報を追加したい場合、元のエラーと追加情報を組み合わせたテキストで新しいエラーを作るには、次のように書くことができます。

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

幸いなことに、標準ライブラリの`fmt`パッケージには、このための省略記法として`Errorf`関数が用意されています。これを使えば、たとえばエラーが発生したコンテキストの情報を簡単に追加できます。

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

エラーにすでに十分な情報が含まれていると確信できる場合を除き、関数からエラーを返す前に、必ずコンテキストを追加する習慣を身につけましょう。つまり、標準的なエラー処理のパターンは次のようになります。

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

例で示したとおり、エラーと追加したメッセージはコロンで区切るのが慣例です。元のエラーのメッセージと同じく、コンテキストのメッセージも先頭を大文字にせず、末尾にピリオドを付けません。

~~~~exercism/note
エラーにコンテキストを追加するとき、メッセージを「failed to ...」のような文言で始めたくなります。しかし、エラーは関数の呼び出し階層をさかのぼるにつれて多くの追加コンテキストを蓄積していくため、最終的にログに出力されたりユーザーが目にしたりするメッセージが読みにくく、重複だらけになってしまうことがあります。

わかりやすい例を挙げます。

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

ですから、コンテキストのメッセージを書くときはこの最終的な結果を思い描き、何かが期待どおりに進まなかったという事実についての文言を加えるのは控えましょう。それはたいてい、コンテキスト（たとえばログレベルの「ERROR」）と元のエラーメッセージから明らかです。
~~~~

このようにエラーに情報を追加する方法で十分なこともよくありますが、エラーの呼び出し元が元のエラーを確認したり取り出したりできるようにしたい場合もあります。これを可能にする形でコンテキストを追加することを、Goでは「エラーのラップ」と呼びます。

## エラーのラップとセンチネルエラーの確認

エラーのラップは、上で見たコードにごく小さな変更を加えるだけで実現できます。エラーをラップするには、フォーマット動詞として`%v`ではなく`%w`を使う必要があります。内部的には、これにより生成されるエラーが、元のエラーを返す`Unwrap`メソッドを実装するようになります。そのため、`errors.Is`を使って、特定のセンチネルエラーが「エラーチェーン」のどこかに現れるかどうかを確認できます。これは、問題のエラーが見つかるかチェーンが終わるまで、裏で`Unwrap`を繰り返し呼び出すことで行われます。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

`errors.Is`で元のエラーを確認する方法は、通常の`%v`フォーマット動詞では機能しません。

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

そのため、デフォルトでは`%v`を使い、呼び出し元に元のエラーへアクセスさせたい場合にだけ`%w`を使うのが良い習慣です（[Google Go Styleguide][google-go-styleguide]）。

センチネルエラーを確認したいけれど、明示的にアンラップしたくないという状況では、`errors.Is`の代わりに`==`を使えます。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

反対に、エラーがラップされていると`==`ではそのエラーを特定できません。

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

デフォルトでは`errors.Is`を使うので問題ありませんが、これはエラーチェーン全体が検索されるということを常に意識しておきましょう。

## （カスタム）エラーの型を確認する

`errors.Is`に相当するもので、エラーチェーンから特定の型のエラーを確認して取り出すことができる関数があります。それが`errors.As`という関数で、`errors.Is`と同じく、指定されたエラーの型をチェーン全体にわたって探します。`errors.As`は、型に一致するエラーが見つかったときにだけそれを取り出すので、そのあとさらに扱うことができます。たとえば特定のフィールドを取り出したりできます。

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
上のポインタに関する構文には注意してください。`customError`が、エラーインターフェースを実装する正確な型である場合にのみ、コードは正しく動作しコンパイルされます。今回の場合、それは`*MyCustomError`（`MyCustomError`への[ポインタ][concept-pointers]）であり、`MyCustomError`そのものではありません。

さらに、2番目の引数はエラー変数へのポインタである必要があります。今回のエラーはすでにポインタなので、`errors.As`に渡しているのはポインタへのポインタ（MyCustomErrorへの）です。これを正しく設定して初めて、Goは見つけたエラーで変数を埋めることができます。
~~~~

前述のとおり、`Errorf`を呼ぶときに`%v`を使っていたら、`errors.As`はそのエラーの型を見つけられません。

何らかの理由でアンラップしたくない場合は、代わりに型アサーションを使えます（上の`==`に相当します）。

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

エラーがラップされていた場合、型アサーションではそのエラーの型を特定できません。

## カスタム型のエラーをアンラップできるようにする

エラーを追加のテキストでラップするだけでは不十分なこともあります。その場合は代わりに、元のエラーと、追加したい構造化データを保持するカスタムのエラー型を作ることができます。自分のエラー型でアンラップを可能にしたい場合は、`Unwrap`インターフェースを満たすように`Unwrap() error`メソッドを手動で追加するだけです。

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## 複数のエラーを組み合わせる

Go 1.20では、組み込みの`errors`パッケージに新しい`Join`関数が追加されました。`Join`を使うと、複数のエラーを、アンラップが可能なまま、つまりチェーンに沿って特定のエラーやエラーの型を確認できる形で組み合わせられます。これにより、エラーチェーンは実際にはエラーツリーになり得ます。詳しくは[リリースノート][release-notes]と[ドキュメント][doc-join]で確認できます。

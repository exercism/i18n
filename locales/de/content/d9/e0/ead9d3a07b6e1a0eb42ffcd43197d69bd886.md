# Über

Es ist unwahrscheinlich, dass du viel Produktionscode findest, der keine Namespaces verwendet.

Ein Beispiel für die Syntax ist:

```csharp
namespace MyNameSpace
{
    public class MyClass {}

    public class OtherClass {}
}
```

Namespaces sind eine Möglichkeit, zusammengehörigen Code zu gruppieren und Namenskonflikte zu vermeiden.

Laut der [offiziellen Dokumentation][namespaces] haben Namespaces zwei Hauptaufgaben:

- Zum einen verwendet .NET Namespaces, um seine vielen Klassen zu organisieren
- Zum anderen kann das Deklarieren eigener Namespaces dir helfen, den Gültigkeitsbereich von Klassen- und Methodennamen in größeren Programmierprojekten zu kontrollieren.

Die Basisklassenbibliothek (BCL) verwendet Namespaces in großem Umfang, um ihre Funktionalität zu organisieren.

## Verweise auf Typen in Namespaces

Auf Typen, die sich in einem Namespace befinden, wird von außerhalb des Namespace verwiesen, indem man dem Typnamen die Punktnotation voranstellt. Alternativ, und meistens üblicher, kannst du eine `using`-Direktive an den Anfang der Datei (oder innerhalb eines Namespace) setzen, und alle Typen im importierten Namespace können ohne Präfix verwendet werden. Innerhalb desselben Namespace musst du Typnamen nicht qualifizieren.

```csharp
namespace MySpace
{
    public class MyClass {}

    public class Foo
    {
        public void Bar()
        {
            var baz = new MyClass();
        }
    }
}

public class Qux
{
    public void Box()
    {
        var nux = new MySpace.MyClass();
    }
}

namespace OtherSpace
{
    using MySpace;

    public class Tix
    {
        public void Jeg()
        {
            var lor = new MyClass();
        }
    }
}
```

Dieser [Artikel][using] erklärt anschaulich, wie die `using`-Direktive verwendet werden kann:

- `using`: du musst Typen nicht mit dem Namespace qualifizieren
- `using static`: du musst Member nicht mit dem Typ qualifizieren (ein gutes Beispiel ist `Math.Max()`).
- `using MyAlias = YourNamespace;`: ersetzt den Namespace-Namen durch einen lesbareren Namen.

## Konflikte zwischen Namespaces

.NET behandelt das Problem zweier Namespaces mit demselben Namen in verschiedenen Assemblys, bei dem es zu einem Konflikt vollqualifizierter Bezeichnernamen käme (etwa wenn mehrere Versionen einer Assembly geladen werden). Dieses Problem wird mit dem [Namespace-Alias-Qualifizierer][namespace-alias-qualifier] und dem [extern-Alias][extern-alias] gelöst.

Ein Grund, dieses recht spezielle Thema anzusprechen, ist die Verwendung des [`::`-Operators][dot-dot-operator]. Du wirst oft sehen, dass der Qualifizierer `global::` Namespaces vorangestellt wird, besonders in generiertem Code. Die Absicht dahinter ist, einen möglichen Konflikt mit einem verschachtelten Namespace oder Klassennamen zu vermeiden. Indem du einem Namespace `global::` voranstellst, stellst du sicher, dass ein Namespace auf oberster Ebene ausgewählt wird.

## Hinweis für Java-Entwickler

Beim Vergleich mit dem `import` von Java-`packages` sollten einige Unterschiede und Gemeinsamkeiten beachtet werden:

- In C# gibt es keine Entsprechung zum Importieren bestimmter Typen.
- `using static` und `import static` sind äquivalent.
- In Java wirken sich Paketnamen auf die Zugänglichkeit zwischen JARs aus. In C# sind Assemblys maßgeblich, und die Zugehörigkeit zum selben Namespace hat keinen Einfluss auf die Zugriffsebene.
- Die Beziehung zwischen Dateisystempfaden und vollqualifizierten Klassennamen in Java spiegelt sich in den Namespaces von C# nicht wider, auch wenn es gute Praxis ist, einer Datei nach Möglichkeit denselben Namen wie die Hauptklasse zu geben, die sie enthält.

# Über

[8th](https://8th-dev.com) ist eine stark typisierte, von FORTH abgeleitete, stapelbasierte Sprache mit RPN-Syntax.

8th unterstützt die Plattformen android, ios32, lin64, mac64, rpi32 und win64. Mit 8th kannst du auf deiner bevorzugten Plattform deinen Code schreiben und testen. Mit einem Klick erzeugst du die ausführbaren Dateien *für* jede Plattform, die 8th unterstützt, *von* jeder Plattform aus, die es unterstützt!

8th enthält alles, was du brauchst: plattformübergreifende GUI-Unterstützung, starke Verschlüsselung, SQLite-Datenbankunterstützung, FFI, REST-Zugriff, einfache Lokalisierung, Hardwarezugriff, JSON-Unterstützung, eine REPL und vieles mehr!

Sicherheit ist bei 8th kein nachträglicher Gedanke. Es wurde von Anfang an so entworfen, dass die häufigsten Sicherheitsprobleme in Software vermieden werden. Wir arbeiten ständig daran, es noch sicherer zu machen.

8th hat ein [Forum](https://8th-dev.com/forum/) sowie eine ausführliche Dokumentation mit einem [Handbuch](https://8th-dev.com/manual.html) und einem verlinkten Wörterbuch der eingebauten und der Bibliotheks-[Wörter](https://8th-dev.com/words.html). [Vergleiche](https://8th-dev.com/compare.html) 8th mit anderen Sprachen!


## Kurze Einführung für Nutzer von „Mainstream“-Sprachen

Wenn du aus C oder Java oder den meisten anderen gängigen Sprachen kommst, mag dir 8th etwas rätselhaft vorkommen. Damit du den richtigen Weg findest, findest du hier einige der wichtigsten Unterschiede zwischen 8th und dem „Mainstream“ sowie ein paar hilfreiche Hinweise:

* Aufgrund der Art und Weise, wie der Interpreter Elemente nachschlägt, musst du eine Var oder ein Wort vor der ersten Verwendung deklarieren. Andernfalls wird die Ausnahme can’t find ... ausgelöst.
    
* Eine Var ist ein benannter Container für andere Elemente. Sie ist nicht der Name des Elements, auf das sie verweist! So kann var x ein Array enthalten, aber es ist falsch, auf x zuzugreifen, als wäre es selbst ein Array, und das löst eine Ausnahme aus.
    
* Du kannst keine Var innerhalb (also lokal in) einem Wort deklarieren, versuch es gar nicht erst! Du kannst jedoch w:@ und w:! verwenden, um auf wortlokale Variablen zuzugreifen.
    
* Versuche, deine eigenen Wörter so zu schreiben, dass sie mit anderen Wörtern zusammengekettet werden können. Zum Beispiel: Die „Datei-Wörter“ führen eine Operation an einer Datei aus und lassen das Datei-Element (und vielleicht weitere Informationen) auf dem Stapel, damit das nächste Wort damit arbeiten kann.

* Halte deine Wörter kurz. Kommentiere sie. Achte besonders darauf, den Stack-Effekt zu kommentieren, und…

* … teste jedes Wort, das du schreibst (am besten, während du es schreibst oder kurz danach), und stelle sicher, dass es dem dokumentierten SED (Stack-Effect Diagram) entspricht. So schreibst du fehlerfreien Code. Teste erneut, wenn du das SED oder den Code änderst.

* Sieh in den Wörtern help und apropos nach, wenn du Details zur Wirkungsweise des SED und zu den Seiteneffekten eines Worts wissen willst, bei dem du dir nicht sicher bist.
    
* In 8th ist eine Ausnahme ein fataler Fehler und führt dazu, dass die Anwendung beendet wird (das ist das Standardverhalten). Erwarte nicht, dass du eine „fängst“ und effektiv behandelst.
    
* Es gibt keinen Compile-/Link-Zyklus. Stattdessen ist 8th eine Engine, die deinen Code zuerst interpretiert und ihn bei Bedarf zur Laufzeit kompiliert. Auf einem Gerät läuft dein Code als nativer Code für die Plattform, nicht als Bytecode in einer VM.

# Einführung

Bisher hat der Lehrplan nicht viel über Typen gesagt, aber offensichtlich gibt es sie in Julia:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

Wir haben die Typen nie angegeben, aber Julia hat sie trotzdem zugewiesen.

1. Julia hat `types`, die zentral für sein Design sind.
2. Julia kann den Typ normalerweise „erraten“, indem es `Type Inference` verwendet.

Der JIT-Compiler durchsucht (den gesamten) Code, sieht, wie eine Variable verwendet wird, und _leitet_ einen geeigneten Standardtyp ab, der mit dieser Verwendung kompatibel ist.

## Typ-Promotion

In früheren Konzepten gab es viele Beispiele, die numerische Typen vereinheitlichen, angefangen bei der einfachsten Arithmetik.

```julia-repl
julia> 2 + 1.3
3.3
```

Wir haben eine Ganzzahl (Int64) und eine Gleitkommazahl (Float64) addiert und ein Float64-Ergebnis erhalten.
Ähnlich:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

Im obigen Fall hat ein Tupel den Typ jedes Elements beibehalten, aber die Umwandlung in einen Vektor hat alle in einen einheitlichen Float64 geändert.

Der Julia-Compiler versteht, welche Typumwandlungen möglich sind: Ganzzahl zu Gleitkommazahl ist kein Problem, Gleitkommazahl zu Ganzzahl verliert Präzision, daher wird ein `InexactError` ausgelöst.
Die Typ-Promotion wandelt alle Werte im Ausdruck in einen gemeinsamen Typ um, der vielseitig genug ist, mit allen Eingaben kompatibel zu sein.

## Typzuweisung

Sich auf Typinferenz zu verlassen, ist für einfache Tutorial-Übungen in Ordnung, aber bei größeren Programmen brauchst du wahrscheinlich eine präzisere Kontrolle.

Auf den meisten modernen Prozessoren hat eine Ganzzahl standardmäßig den Typ `Int64`.
Im [`Numbers`][numbers]-Konzept haben wir gesehen, dass ein Wert in einen bestimmten Nicht-Standardtyp umgewandelt werden kann.

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

Die Variable `x` kann jedoch weiterhin einem anderen Typ zugewiesen werden:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

Das ist `type instability`, was:

- In kleinen Skripten sehr praktisch ist.
- In größeren Programmen schlecht für Leistung und Zuverlässigkeit ist.

Stattdessen können wir den Typ von `x` mit dem Operator `::` festlegen:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

Jetzt ist `y` vom Typ `Int16` und wird es immer bleiben.
Dadurch weiß der Compiler, wie viele Bytes er dafür reservieren muss, und kann den restlichen Code darauf optimieren, sich auf einen stabilen Typ zu verlassen.
Darin ähnelt die Variable mehr oder weniger denen in einer statisch typisierten Sprache wie C.

## Typzusicherung

Die oben beschriebene Typzuweisung wird auf der linken Seite einer Variablenzuweisung verwendet, um den Typ dieser Variable einzuschränken.

Die Verwendung des Operators `::` mit einem Wert oder mit etwas, das zu einem Wert ausgewertet wird, ist im Allgemeinen eine _Zusicherung_, dass der Wert diesen Typ haben muss, andernfalls sollte ein Fehler ausgelöst werden.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Häufig kann dies mit dem Rückgabewert einer Funktion verwendet werden, als einfache letzte Prüfung, dass die Funktion sich wie erwartet verhalten hat.

## Die Typhierarchie

`Int64`, `Int16`, `String`, `Char`: Woher _„kommen“_ diese Typen?

In vielen objektorientierten (OO-)Sprachen ist jeder Typ eine Klasse, die Unterklassenbildung ordnet sie in einer Klassenhierarchie an, und Klassenmethoden definieren die Verhaltensweisen.

Java und Ruby sind offensichtliche Beispiele für dieses Muster, aber selbst Python ist intern ähnlich.

***Julia hat keine Klassen.***

Der dokumentierte Grund ist, dass OO-Features den JIT-Compiler stören und die Laufzeitleistung beeinträchtigen.

Und doch, schau dir diesen Code an:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

Ein paar Details dazu:

- `Int16` ist ein Typ, und wir können Variablen dieses Typs erstellen.
- `Int16` ist ein Untertyp von `Signed`, und die Funktion `supertype()` zeigt uns das.
- Es gibt eine Hierarchie von Typen, die über `Integer`, `Real` und `Number` bis hinauf zu `Any` an der Spitze führt, und `subtypes()` listet diesen Zweig der Hierarchie für uns auf.

Alle Zweige enden in `Any`, das einzigartig darin ist, sein eigener Obertyp zu sein.

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

Julia hat also keine `class`-Hierarchie, aber es _hat_ sehr wohl eine `type`-Hierarchie.

Irgendwann werden wir versuchen zu ergründen, wie das funktioniert, aber zuerst gibt es noch viel mehr zu entdecken.

## Typen testen

Wir können `typeof()` verwenden, um auf Gleichheit zu testen, und zwar auf die übliche Weise.

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

Die Typgleichheit muss exakt sein, denn diese Art des Vergleichs versteht nichts von der Typhierarchie.

Flexibler zeigt uns `isa`, ob ein Wert entweder denselben Typ wie ein Vergleichswert hat oder einen Untertyp davon.
Es kann entweder in Funktions- oder in Infixform verwendet werden.

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

Beachte, dass `isa` links einen `value` erwartet, keinen `type`.

Der Versuch, zwei _Typen_ auf diese Weise zu vergleichen, liefert unerwartete Ergebnisse.
Der richtige Operator ist `<:`, den wir in zukünftigen Konzepten noch viel häufiger sehen werden.

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## Abstrakte und konkrete Typen

Wir haben gesehen, dass die Typhierarchie eine Baumstruktur bildet (im Sinne der Informatik, mit der Wurzel oben).

Jeder Eintrag im Baum ist ein `node`, und diese lassen sich in Kategorien einteilen:

1. Knoten mit Untertypen heißen `abstract`.
2. Blattknoten ohne Untertypen heißen `concrete`.

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

Das ist ein wichtiger Unterschied, denn nur konkrete Typen können als Variablen `instantiated` werden.


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

Beachte, dass der Versuch, einen abstrakten Typ zu verwenden, (in diesem Fall) keine Fehlermeldung erzeugt, aber der Compiler erstellt einen passenden konkreten Typ: `Int64` statt `Integer`.
Zumindest verhindert es, dass der Variablen ein Nicht-Ganzzahl-Wert zugewiesen wird:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

Die Typzuweisung mit einem abstrakten Typ ist also eine _Einschränkung_ des Variablentyps auf einen beliebigen Untertyp von (im obigen Fall) `Integer`.
Das ist in der Welt der Programmiersprachen etwas Ungewöhnliches: schwächer als eine Typzuweisung in C, stärker als ein Typ-Hinweis in neueren Python-Versionen.

Die Funktionen `isabstracttype()` und `isconcretetype()` ermöglichen das Testen.
Beachte, dass sie nicht einfach Negationen voneinander sind: In einem späteren Konzept werden wir sehen, dass einige Typen weder abstrakt noch konkret sein können.


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

# Linting

Der Hauptzweck von [configlet](/docs/building/configlet) ist das Linting: Es wird geprüft, ob die Konfigurationsdateien eines Tracks korrekt aufgebaut sind, und zwar sowohl syntaktisch als auch semantisch. Falsch konfigurierte Tracks werden unter Umständen nicht korrekt synchronisiert, sehen auf der Website falsch aus oder bieten eine suboptimale Nutzererfahrung. Deshalb spielen die Prüfungen von configlet eine wichtige Rolle dabei, die Integrität von Exercism zu wahren.

## Verwendung

Mit dem Befehl `lint` kannst du einen Track linten.

```
configlet [global-options] lint [command-options]

Global options:
  -h, --help                   Show this help message and exit
      --version                Show this tool's version information and exit
  -t, --track-dir <dir>        Specify a track directory to use instead of the current directory
  -v, --verbosity <verbosity>  The verbosity of output. Allowed values: q[uiet], n[ormal], d[etailed]
```

## Regeln

Das sind die Linting-Regeln, die geprüft werden.

### Regel: erforderliche Dateien sind vorhanden

Der Linter sollte prüfen, ob alle erforderlichen Dateien vorhanden sind. Die übungsunabhängigen Dateien, die vorhanden sein müssen, sind:

- `config.json`
- `docs/ABOUT.md`
- `docs/INSTALLATION.md`
- `docs/LEARNING.md`
- `docs/RESOURCES.md`
- `docs/SNIPPET.txt`
- `docs/TESTS.md`
- `exercises/shared/.docs/help.md`
- `exercises/shared/.docs/tests.md`

Die Dateien, die spezifisch für Konzeptübungen sind und vorhanden sein müssen, sind:

- `exercises/concept/<slug>/.docs/hints.md`
- `exercises/concept/<slug>/.docs/instructions.md`
- `exercises/concept/<slug>/.docs/introduction.md`
- `exercises/concept/<slug>/.meta/config.json`

Eine ähnliche Liste wird es für Praxisübungen geben, aber die Spezifikation dafür haben wir noch nicht festgelegt.

Jedes in der `config.json` aufgeführte Konzept sollte die folgenden Dateien haben:

- `concepts/<slug>/about.md`
- `concepts/<slug>/introduction.md`
- `concepts/<slug>/links.json`

## Glossar

1. **Nicht-leerer String**: ein String, der mindestens ein Zeichen enthält, das kein Leerzeichen ist.
2. **kebab-case-String**: ein String, der nur Zeichen aus dem Bereich `[a-z0-9]` enthält, die optional durch Bindestriche getrennt sind (z. B. „two-fer“). Er muss dem regulären Ausdruck entsprechen: `^[a-z0-9]+(-[a-z0-9]+)*$`
3. **Title-Case-String**: ein nicht-leerer String, der den folgenden [Richtlinien des Chicago Manual of Style](https://en.wikipedia.org/wiki/Title_case#Chicago_Manual_of_Style) folgt:
   - Schreibe das erste und das letzte Wort von Titeln und Untertiteln groß.
   - Schreibe „wichtige“ Wörter groß (Substantive, Pronomen, Verben, Adjektive, Adverbien und einige Konjunktionen).
   - Schreibe die Konjunktionen _and_, _but_, _for_, _or_ und _nor_ klein.
   - Schreibe die Artikel _the_, _a_ und _an_ klein.
   - Schreibe Präpositionen klein, unabhängig von ihrer Länge, außer wenn sie betont werden, adverbial oder adjektivisch gebraucht werden oder als Konjunktion dienen.
   - Schreibe die Wörter _to_ und _as_ klein.
   - Schreibe den zweiten Teil lateinischer Artnamen klein.
4. **Sentence-Case-String**: ein nicht-leerer String, der den folgenden [Richtlinien](https://en.wikipedia.org/wiki/Letter_case#Sentence_case) folgt:
   - Schreibe das erste Wort des Satzes groß, ebenso Eigennamen und andere Wörter, die eine spezifischere Regel großschreiben verlangt.
5. **Gültiges `files`-Muster**: Ein nicht-leerer String¹, der den Ort einer in einer Übung verwendeten Datei relativ zum Verzeichnis der Übung angibt. Ein Muster kann einen der folgenden Platzhalter verwenden:

   - `%{kebab_slug}`: der Übungs-Slug im `kebab-case`-Format (z. B. `bit-manipulation`)
   - `%{snake_slug}`: der Übungs-Slug im `snake_case`-Format (z. B. `bit_manipulation`)
   - `%{camel_slug}`: der Übungs-Slug im `camelCase`-Format (z. B. `bitManipulation`)
   - `%{pascal_slug}`: der Übungs-Slug im `PascalCase`-Format (z. B. `BitManipulation`)

6. **Eindeutiger UUID-String der Version 4**: Ein String, der alle folgenden Bedingungen erfüllt:

   - Er existiert nur einmal in der `config.json` auf Track-Ebene eines bestimmten Exercism-Tracks
   - Er existiert nicht in der `config.json` auf Track-Ebene eines anderen Exercism-Tracks
   - Er existiert in keiner `canonical-data.json`-Datei unter https://github.com/exercism/problem-specifications
   - Er existiert nirgendwo sonst auf Exercism
   - Er entspricht dem regulären Ausdruck:

   ```
   ^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
   ```

   Zum Beispiel hat die folgende UUID die korrekte Form:

   ```
   d334ffe3-657e-4725-a950-290b284b6d9f
   ```

   Mit `configlet uuid` kannst du eine passende UUID generieren.

7. **Gültiger Analyzer-`tag`**: Ein nicht-leerer String¹ im Format `<category>:<thing>`.
   Der Wert von `<category>` muss einer der folgenden sein:

- `paradigm` (z. B. `paradigm:functional`)
- `technique` (z. B. `technique:recursion`)
- `construct` (z. B. `construct:bitwise-and`)
- `uses` (z. B. `uses:DateTime.add_seconds`)

Der Wert von `<thing>` muss ein nicht-leerer String¹ sein.

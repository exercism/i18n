# Einführung

## SIMD: Bitweise Operationen

Für die meisten skalaren bitweisen Operationen gibt es gepackte Varianten.
Sie folgen derselben allgemeinen Syntax wie SIMD-Ganzzahloperationen, haben aber kein Größen-Suffix:

| Instruktion | Beschreibung                       |
|-------------|-----------------------------------|
| `pand`      | bitweises AND zweier 128-Bit-Werte |
| `por`       | bitweises OR zweier 128-Bit-Werte  |
| `pxor`      | bitweises XOR zweier 128-Bit-Werte |

Beachte, dass es kein gepacktes `NOT` gibt.
Es gibt jedoch eine ANDN-Operation, die den **Zieloperanden** komplementiert (alle Bits darin umkehrt) und dann das AND zwischen beiden Operanden berechnet.
Sie lässt sich als Kombination aus NOT und AND vorstellen:

| Instruktion | Beschreibung                                                     |
|-------------|-----------------------------------------------------------------|
| `pandn`     | bitweises AND des **komplementierten** Zieloperanden mit dem Quelloperanden |

Beachte, dass eine bitweise Operation Bits an derselben Position in zwei verschiedenen Operanden kombiniert, daher können Lane-Grenzen das Ergebnis nicht verändern.
Dies ist der Grund, warum diese Instruktionen kein Größen-Suffix haben; das Register verhält sich wie eine einzelne 128-Bit-Lane:

```x86asm
pand xmm0, xmm1   ; xmm0 = xmm0 AND xmm1
por  xmm2, xmm3   ; xmm2 = xmm2 OR xmm3
pxor xmm4, xmm5   ; xmm4 = xmm4 XOR xmm5
pandn xmm6, xmm7  ; xmm6 = (NOT xmm6) AND xmm7
```

~~~~exercism/note
Alle Instruktionen in diesem Konzept berechnen Bits, setzen aber keine Flags.
Ein späteres Konzept behandelt bedingte Anweisungen mit gepackten Werten.
~~~~

### Laneweise Verschiebungen

Verschiebungen bewegen im Gegensatz zu den reinen bitweisen Operationen Bits über Positionen hinweg und benötigen daher eine Lane-Größe, um eine Grenze festzulegen.
Innerhalb jeder Lane verhalten sie sich wie ihre skalaren Gegenstücke, und Bits wechseln nie von einer Lane in eine benachbarte:

| Instruktion               | Beschreibung                         |
|---------------------------|-------------------------------------|
| `psllw`, `pslld`, `psllq` | logische Linksverschiebung, pro Lane |
| `psrlw`, `psrld`, `psrlq` | logische Rechtsverschiebung, pro Lane |
| `psraw`, `psrad`          | arithmetische Rechtsverschiebung, pro Lane |

Beachte, dass diese Instruktionen der Syntax für gepackte Ganzzahloperationen folgen, einschließlich eines Größen-Suffix.
Es gibt keine Byte-Lane-Verschiebung, nur Word-, Dword- und, mit Ausnahme der arithmetischen Rechtsverschiebung, Qword-Verschiebungen.

Ein Unterschied zwischen gepackten Verschiebungen und ihren skalaren Gegenstücken liegt im Operationsnamen:

- Statt `shl` und `shr` haben wir `sll` und `srl`, für **s**hift **l**eft (**r**ight) **l**ogical.
- Statt `sar` haben wir `sra`, für **s**hift **r**ight **a**rithmetic.

Obwohl der Name anders ist, ist die Operation dieselbe:

- Eine logische Rechtsverschiebung füllt die obersten Bits mit null.
  Sie entspricht einer vorzeichenlosen Division durch eine Zweierpotenz.
- Eine arithmetische Rechtsverschiebung füllt die obersten Bits mit dem Wert des Vorzeichenbits.
  Sie entspricht einer vorzeichenbehafteten Division durch eine Zweierpotenz, gerundet in Richtung negative Unendlichkeit.
- Eine Verschiebung nach links füllt immer mit null (deshalb gibt es keine arithmetische Linksverschiebung).

Der Verschiebungszähler ist für jede Lane gleich.
Er kann ein Immediate sein oder die unteren 64 Bits eines `xmm`-Registers:

```x86asm
pslld xmm0, 4      ; each 32-bit lane shifted left by 4
psrlw xmm1, 1      ; each 16-bit lane shifted right by 1, zero-filled
psrad xmm2, xmm3   ; each 32-bit lane shifted right by the count in xmm3, sign-filled
```

~~~~exercism/note
Ein Verschiebungszähler, der größer als die Lane-Breite ist, läuft nicht wie bei der skalaren `shl`/`shr`-Familie um.
Er erzeugt einfach null (oder alle Vorzeichenbits bei arithmetischer Rechtsverschiebung).
~~~~

### Bitweise Gleitkommaoperationen

Jede bitweise Instruktion hat auch Gegenstücke mit Gleitkommanamen, die derselben Syntax folgen, die wir bei gepackten Gleitkommaoperationen gesehen haben:

| Ganzzahlname | Gleitkommanamen      |
|--------------|----------------------|
| `pand`       | `andps`, `andpd`     |
| `pandn`      | `andnps`, `andnpd`   |
| `por`        | `orps`, `orpd`       |
| `pxor`       | `xorps`, `xorpd`     |

Da bitweise Operationen auf Bits wirken, berechnen Ganzzahl- und Gleitkommaoperationen in der Praxis dasselbe Ergebnis.
Die unterschiedlichen Namen gibt es aus zwei Gründen:

1. Dokumentation der Absicht, so wie wir je nach Natur der kopierten Bytes `movdqa`, `movaps` oder `movapd` bevorzugen würden.
2. Ganzzahl- und Gleitkommaoperationen haben oft unterschiedliche Ausführungsdomänen.
   Operationen innerhalb derselben Ausführungsdomäne können in der Regel schneller sequenziert werden.

Für Gleitkommawerte gibt es keine Verschiebungsoperation.

### Bitdarstellung von Gleitkommazahlen

Eine IEEE-Gleitkommazahl hat eine ganz andere Bitdarstellung als eine Ganzzahl.

Bei einer vorzeichenlosen Ganzzahl hat jedes Bit eine einheitliche Bedeutung: Es repräsentiert eine Zweierpotenz, die dem Bitindex entspricht.
Die Ganzzahl ist die Summe der Zweierpotenzen, die den gesetzten Bits entsprechen.
Deshalb kann das Verschieben der Bits die Zahl mit einer Zweierpotenz multiplizieren oder dividieren: Wir ändern lediglich den Index jedes gesetzten Bits.

Bei einer vorzeichenbehafteten Ganzzahl werden die meisten Bits genauso interpretiert wie bei einer vorzeichenlosen Ganzzahl.
Das oberste Bit ist jedoch speziell.
Wenn es gesetzt ist, müssen wir die entsprechende Zweierpotenz subtrahieren, anstatt sie zu den anderen zu addieren, was zu einer negativen Zahl führt.
Um das Vorzeichen einer Zahl zu ändern, bräuchten wir konzeptionell zwei Schritte: Alle Bits umkehren (ein `not`) und dann 1 zum Ergebnis addieren (ein `inc`).

Bits in Gleitkommazahlen haben keine einheitliche Bedeutung und müssen je nach Position auf sehr unterschiedliche Weise interpretiert werden:

| Feld     | Indizes (32-Bit) | Indizes (64-Bit) |
|----------|------------------|------------------|
| Vorzeichen | 31               | 63               |
| Exponent | 30-23            | 62-52            |
| Fraktion | 22-0             | 51-0             |

Die resultierende Zahl wird durch `(-1)^sign * 1.fraction * 2^(exponent - bias)` berechnet.
Der Bias hängt von der Genauigkeit ab:

| Größe  | Bias |
|--------|------|
| 32-Bit | 127  |
| 64-Bit | 1023 |

In beiden Formaten wird das Vorzeichen der Zahl ausschließlich durch das Vorzeichenbit bestimmt.
Das Vorzeichen einer Gleitkommazahl ändert man, indem man einfach dieses Bit umkehrt (eine XOR-Operation).
Den Absolutwert erhält man, indem man es einfach löscht (ein AND, bei dem das Bit gelöscht wird):

```x86asm
section .rodata
align 16
abs_mask:  dd 0b0_11111111_11111111111111111111111, 0x7FFFFFFF, 0x7FFFFFFF, 0x7FFFFFFF ; same number in binary and hexadecimal
sign_mask: dd 0b1_00000000_00000000000000000000000, 0x80000000, 0x80000000, 0x80000000 ; same number in binary and hexadecimal

section .text
fn:
  andps xmm0, [rel abs_mask]  ; absolute value: clear the sign bit of all 4 floats
  xorps xmm1, [rel sign_mask] ; negation: flip the sign bit of all 4 floats
  ...
```

Beachte, dass das Verschieben von Bits in dieser Bitdarstellung kein vorhersagbares und einheitliches Ergebnis hat.
Die Fraktion kann in den Exponenten „überlaufen“ und der Exponent in das Vorzeichen.

Manchmal ist es jedoch praktisch, die verschiedenen Teile der Darstellung zu isolieren, um mit ihnen zu arbeiten.

Zum Beispiel sollten die Bits im Exponenten zuerst als vorzeichenlose Zahl interpretiert werden, bevor der Bias davon subtrahiert wird.
Das bedeutet, wir können eine 32-Bit- oder 64-Bit-Ganzzahl erzeugen, deren zugrunde liegende Bitdarstellung einer Zweierpotenz im entsprechenden Gleitkommaformat entspricht.
Dann kann diese rohe Bitdarstellung verwendet werden, um eine andere Gleitkommazahl zu multiplizieren oder zu dividieren.

Zum Beispiel:

```x86asm
mov eax, 210             ; in the exponent position, this would be 2^(210 - 127) = 2^83 in a 32-bit floating-point number
shl eax, 23              ; the bits are now in the correct position for the exponent of a 32-bit floating-point number
movd xmm0, eax           ; we move the raw bits to xmm0
mulss xmm1, xmm0         ; we are multiplying a 32-bit floating-point number in xmm1 by 2^83
```

Umgekehrt könnten wir die Exponenten gepackter Gleitkommazahlen extrahieren, indem wir ein AND mit einer Maske durchführen, bei der die Exponentenbits gesetzt und alle anderen gelöscht sind.
Kombiniert mit einer Verschiebung und einer Subtraktion ergibt dies den Exponenten ohne Bias für jede Lane als vorzeichenbehaftete Ganzzahl:

```x86asm
section .rodata
align 16
exp_mask: dd 0b0_11111111_00000000000000000000000, 0x7F800000, 0x7F800000, 0x7F800000 ; same number in binary and hexadecimal
bias: dd 127, 127, 127, 127

section .text
fn:
  movdqa xmm0, [rel values]   ; 4 packed 32-bit floating-point numbers
  pand   xmm0, [rel exp_mask] ; keep bits 30-23
  psrld  xmm0, 23             ; slide the exponent field to the bottom of each lane
  psubd  xmm0, [rel bias]     ; remove the bias
  ...
```

~~~~exercism/caution
Das Arbeiten mit den rohen Bits von Gleitkommazahlen ist in manchen Situationen nützlich, sollte aber mit Vorsicht erfolgen.
Das Addieren zum oder Subtrahieren vom Exponentenfeld ist nur sicher, wenn kein Über- oder Unterlauf auftritt und die Eingabezahl normal ist.
Außerdem ergibt das Addieren eines gültigen `x` zum Exponentenfeld von `0.0` `2^(x - bias)`, nicht `0.0 * 2^x`.
~~~~

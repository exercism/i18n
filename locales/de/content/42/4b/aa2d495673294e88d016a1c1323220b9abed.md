# Über

In früheren Konzepten wurde erwähnt, dass die `global`-Direktive eine Funktion oder Variable, die in einer Quelldatei definiert ist, für andere Dateien sichtbar macht.
Ähnlich teilt die `extern`-Direktive dem Assembler mit, dass eine Funktion oder Variable, die in der aktuellen Quelldatei verwendet wird, in einer anderen definiert ist.

Diese beiden Direktiven sind der wichtigste Weg, wie Assembly-Code mit anderen Quelldateien interagiert, um Modularisierung zu erreichen.

Für die Zwecke dieser Direktiven ist es unerheblich, ob der externe Code in Assembly oder in einer Hochsprache definiert oder verwendet wird.
So kann zum Beispiel sogar eine in einer Hochsprache definierte Funktion in x86-64-Code verwendet werden, wenn sie als `extern` deklariert ist.

Ebenso gilt die Aufrufkonvention für alle diese Funktionen, egal ob sie in Assembly oder in Hochsprachen definiert sind, und sogar für das Betriebssystem (OS).

Da Daten in Assembly jedoch nur eine Folge von Bytes sind, ist es wichtig zu wissen, wie die angebundene Hochsprache den Speicher verwaltet.

## C-Typen

Die Sprache C ist eine häufige Wahl für eine Hochsprache, die mit Assembly-Code zusammenspielt.
Sie erleichtert die Interaktion mit dem Betriebssystem und bietet High-Level-Wrapper für viele wichtige Aufgaben, etwa das Ausgeben auf dem Bildschirm, das Lesen von einer Tastatur oder das Reservieren von dynamischem Speicher.

In diesem Track sind die Tests in C geschrieben, deshalb ist ein allgemeiner Überblick über die Sprache wichtig.

### Primitive Typen

In C gibt es viele primitive Typen, und ihre Größe in Bytes kann variieren.
Einige davon sind in der folgenden Tabelle mit ihrer typischen Größe auf einem x86-64-System zusammengefasst:

| Typ       | Anzahl Bytes    | Ganzzahl/Gleitkommazahl |
|-----------|-----------------|------------------------|
| _Bool     | 1               | Ganzzahl               |
| char      | 1               | Ganzzahl               |
| short     | 2               | Ganzzahl               |
| int       | 4               | Ganzzahl               |
| long      | 4 oder 8        | Ganzzahl               |
| long long | 8               | Ganzzahl               |
| float     | 4               | Gleitkommazahl         |
| double    | 8               | Gleitkommazahl         |

Jeder dieser Ganzzahltypen kann vorzeichenbehaftet (die Voreinstellung) oder vorzeichenlos sein.
Ist er vorzeichenlos, muss das angegeben werden, zum Beispiel: `unsigned int`.

Für die Ganzzahltypen gibt es Aliase, mit denen sich ihre Größe genau steuern lässt:

| Alias   | Anzahl Bytes    |
|---------|-----------------|
| int8_t  | 1               |
| int16_t | 2               |
| int32_t | 4               |
| int64_t | 8               |

Diesen Aliasen kann ein `u` vorangestellt werden, um einen vorzeichenlosen Typ anzugeben, zum Beispiel: `uint64_t`.

Weitere erwähnenswerte Aliase sind:

| Alias  | Typ                                           |
|--------|-----------------------------------------------|
| bool   | _Bool                                         |
| size_t | meist eine vorzeichenlose 8-Byte-Ganzzahl     |

Ein `_Bool` oder sein Alias `bool` ist insofern besonders, als er zwar ein ganzes Byte belegt, aber nur einen von zwei Werten annehmen kann: `true` (`1`) und `false` (`0`).

Werte dieser primitiven Typen werden nach den üblichen Regeln für Ganzzahlen und Gleitkommawerte an Funktionen übergeben und von ihnen zurückgegeben.

### Enums

Ein [Enum][enum] ist ein Typ, der einen von mehreren ausdrücklich angegebenen Elementen annehmen kann:

```c
enum example {
    example_1,
    example_2,
    example_3,
    example_4
};
```

In C werden Enums implizit in einen Ganzzahltyp umgewandelt, typischerweise `int`, also eine 4-Byte-Ganzzahl.

Standardmäßig wird das erste mögliche Element eines Enums in `0` umgewandelt und alle folgenden Elemente in die jeweils nächste Ganzzahl.
Im oben definierten `enum example` hätte `example_1` also den Wert `0`, `example_2` den Wert `1` und so weiter.

Für jedes Element eines Enums kann der Wert angegeben werden; standardmäßig hat das nächste Element dann die nächste Ganzzahl als Wert:

```c
enum example_2 {
    example_1 = 4,
    example_2 = 8,
    example_3
}; // example_3 is equal to 9
```

### Speicheradressen

In C wird eine Speicheradresse durch einen [Zeiger][pointer] auf einen Typ referenziert und mit dem Operator `*` angegeben.
So verweist zum Beispiel `int64_t *` auf eine Speicherstelle für einen oder mehrere `int64_t`.

Adressen werden wie üblich als 8-Byte-Ganzzahlen behandelt.

### Arrays

Arrays werden als Zeiger auf ihr erstes Element an Funktionen übergeben und von ihnen zurückgegeben.

```c
int64_t example_arr[] = {1, 2, 3}; // this is an array of 3 signed 8-byte integers
fn(example_arr); // this is a function that passes a pointer (int64_t *) to the beginning of the array as argument
```

Jedes Element eines Arrays hat die Größe des Elementtyps des Arrays.
Das oben definierte `example_arr` hat zum Beispiel 3 Elemente zu je 8 Bytes, insgesamt also 24 Bytes.

Da Arrays ihre Länge nicht speichern, braucht man in der Regel einen separaten Wert für die Anzahl der Elemente, es sei denn, ein Sentinel-Wert markiert das Ende.

### Strings

Strings sind in C ein Array aus `char`, einem 1-Byte-Typ.
Die meisten Strings bestehen aus ASCII-Zeichen und sind NUL-terminiert, enden also, sobald ein Byte mit dem Wert `0` auftritt.
Das bedeutet, dass die Länge eines Strings normalerweise nicht als separates Argument übergeben werden muss.

## C-Bibliotheksfunktionen aufrufen

Die `extern`-Direktive deklariert nur, dass ein Symbol in einer anderen Datei definiert ist.
Wie ein Aufruf tatsächlich erfolgt, hängt davon ab, wie dieser externe Code gelinkt wird.

Bei gewöhnlichen Funktionen, die zusammen mit deinem Code gelinkt werden, kann der Linker eine externe Funktion direkt finden, ein einfaches `call` genügt also.

Standardfunktionen der C-Bibliothek wie `malloc`, `free` und `printf` werden jedoch meist zur Laufzeit aus einer Shared Library aufgelöst, deren Adresse beim Assemblieren deines Codes nicht bekannt ist.
Der Aufruf läuft deshalb über einen Stub in einer [Procedure Linkage Table (PLT)][plt], der an einem bekannten Offset liegt.
Beim Aufruf einer externen Bibliotheksfunktion aus Assembly verlangt NASM einen Hinweis darauf, dass dieser Aufruf über die PLT aufgelöst werden soll.

In `elf64` (Ausgabeformat von Linux-Programmen) geschieht das durch Anhängen von `wrt ..plt` („with reference to plt“) an den Aufruf.
Zum Beispiel: `call printf wrt ..plt`.

In `macho64`-Programmen (Ausgabeformat von macOS-Programmen) genügt dagegen ein Unterstrich vor dem Funktionsnamen.
Zum Beispiel `extern _printf`, dann `call _printf`.
Da dieser Track `macho64`-Code jedoch mit dem Flag `--prefix _` assembliert, fügt der Assembler den Unterstrich in beiden Fällen automatisch hinzu, zum Beispiel `extern printf`, dann `call printf`.

Beachte, dass der Test-Runner von Exercism in einem Linux-Image läuft. Jede eingereichte Lösung, die C-Bibliotheksfunktionen aufruft, muss daher `wrt ..plt` verwenden.
Mit einer Bedingung, die der Assembler zur Assemblierungszeit auswertet, lässt sich korrekt zwischen den Ausgabeformaten unterscheiden:

```x86asm
extern malloc

%ifidn __OUTPUT_FORMAT__,elf64
    call malloc wrt ..plt       ; elf64: reach the function through the PLT
%else
    call malloc                 ; macho64: the linker generates the call stub
                                ; the underscore is added automatically by an assembler flag
%endif
```

## Systemaufrufe

Viele Operationen können Programme auf Benutzerebene, wie sie auch in diesem Track laufen, nicht direkt ausführen.
Das Lesen von `stdin`, das Schreiben nach `stdout`, das Anfordern von dynamischem Speicher, die Interaktion mit Peripheriegeräten und so weiter erledigt alles das Betriebssystem (OS).

Ein Programm auf Benutzerebene muss das Betriebssystem ausdrücklich bitten, diese Operationen auszuführen, wenn sie nötig sind.
Das geschieht mit der Instruktion [`syscall`][syscall].
Vom Konzept her kann man diese Instruktion als Aufruf einer vordefinierten Betriebssystemprozedur betrachten (ein „System“-Aufruf).

Alle Argumente für den Systemaufruf werden dem Betriebssystem in Allzweckregistern (GPRs) übergeben: `rdi`, `rsi`, `rdx`, `r10`, `r8` und `r9`.

Beachte, dass die Reihenfolge fast dieselbe ist wie bei einem Funktionsaufruf, nur dass `rcx` durch `r10` ersetzt wird.
Das liegt daran, dass `syscall` `rcx` und `r11` nutzt, um die Rücksprungadresse und die Flags zu sichern (die wiederhergestellt werden, bevor die Kontrolle an die aufrufende Funktion zurückgeht).
Beide Register gelten nach jedem `syscall` als überschrieben.

Anders als bei `call` gibt es keine Labels, die die System-„Funktionen“ bezeichnen.
Stattdessen werden sie über bestimmte Nummern erreicht, die vor dem Aufruf in `rax` abgelegt werden.
Ein etwaiger Rückgabewert wird ebenfalls in `rax` abgelegt.

Die obigen Konventionen sind [in einem Anhang der System V ABI][linux-convention] beschrieben, der speziell Linux behandelt und nur als informativ gekennzeichnet ist.
In der Praxis sind die verfügbaren Systemaufrufe, ihre Nummern und die Art der Fehlermeldung Details auf Betriebssystemebene, die sich zwischen verschiedenen Betriebssystemen und sogar zwischen Versionen desselben Betriebssystems stark unterscheiden.

Viele C-Bibliotheksfunktionen und andere tatsächliche Funktionen des Betriebssystems sind übergeordnete Wrapper um einen Systemaufruf.
Die ABI empfiehlt, diesen Wrappern den Vorzug vor einem einfachen `syscall` zu geben, und Apple [garantiert keine Kompatibilität][mac-qa1118] an der Systemaufrufschnittstelle des Kerns.

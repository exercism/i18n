# Über

Eine [Schleife][control] ist eine Folge von Befehlen, die potenziell mehr als einmal ausgeführt wird, bis eine Abbruchbedingung erfüllt ist.

In x86-64 wird eine Schleife normalerweise mit einem Sprung zu einem vorherigen Label erzeugt:

```x86asm
example_loop:
    ...
    jmp example_loop
```

Beachte, dass ein unbedingter Sprung zu einem vorherigen Label die Ausführung immer zu diesem Label überträgt.
Das bedeutet, dass die Schleife sich für immer wiederholt, es sei denn, es gibt einen weiteren Sprung aus der wiederholten Sequenz heraus.

Zum Beispiel endet diese Schleife nicht:

```x86asm
infinite_loop:
    inc rax
    jmp infinite_loop ; always jumps to 'infinite_loop', repeating 'inc rax' forever
```

Und diese Schleife kann enden, je nachdem, ob die Bedingung erfüllt ist:

```x86asm
maybe_finite_loop:
    cmp rax, 1
    je out_of_loop ; jumps to 'out_of_loop' if rax == 1, breaking the loop

    inc rax
    jmp maybe_finite_loop ; always jumps to 'maybe_finite_loop'
out_of_loop:
    ...
```

## Zählschleifen

Eine Zählschleife endet fast immer auf die gleiche Weise: ein Befehl, der einen Zähler aktualisiert oder zwei Werte vergleicht, unmittelbar gefolgt von einem bedingten Sprung, der entscheidet, ob erneut die Schleife durchlaufen wird.

```x86asm
sum_array:
    ; rdi is the memory address of an array
    ; rsi is the number of elements in the array

    mov eax, 0           ; running total
.loop:
    add rax, qword [rdi] ; add the current element
    add rdi, 8           ; advance to the next element
    sub rsi, 1           ; one fewer element to process, setting ZF at zero
    jnz .loop            ; repeat while the counter is not yet zero
    ret
```

~~~~exercism/note
`cmp rsi, 0` ist im obigen Code nicht notwendig, weil `sub rsi, 1` bereits das `zero flag (ZF)` setzt, wenn das Ergebnis `0` ist.

Obwohl `cmp` die Hauptmethode ist, um Bedingungen in Assembly zu testen, aktualisieren viele Befehle die Flags.
Zum Beispiel aktualisieren viele Befehle für ganzzahlige Arithmetik oder Bitoperationen `ZF`, wenn das Ergebnis `0` ist, und `SF`, wenn das Ergebnis negativ ist (d. h. das höchste Bit ist gesetzt).

Du kannst eine [Referenz][reference] prüfen, um zu sehen, welche Flags von jedem Befehl beeinflusst werden.

[reference]: https://www.felixcloutier.com/x86/
~~~~

Beachte, dass im obigen Beispiel angenommen wird, dass `rsi` größer als `0` ist.
Wenn es `0` wäre, dann würde `sub rsi, 1` `rsi` auf `-1` reduzieren, was eine sehr große vorzeichenlose Zahl ist.
Es würden `18,446,744,073,709,551,615` weitere Iterationen dauern, bevor die Schleife schließlich endet.
Da die Länge des Arrays außerdem `0` ist, wäre jeder Speicherzugriff außerhalb der Grenzen.

Wenn es keine Garantien für die Länge eines Arrays gibt, gibt es zwei übliche Ansätze.

Der erste besteht darin, die Abbruchbedingung an den Anfang der Schleife zu verschieben und dann einen unbedingten Sprung am Ende zu haben:

```x86asm
sum_array:
    mov eax, 0
.loop:
    cmp rsi, 0
    je .done
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jmp .loop
.done:
    ret
```

Der zweite besteht darin, einmal auf ein Array der Länge null zu testen, bevor die Schleife beginnt:

```x86asm
sum_array:
    mov eax, 0

    cmp rsi, 0
    je .done
.loop:
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jnz .loop
.done:
    ret
```

Dieser zweite Ansatz ist normalerweise effizienter als der erste, weil es weniger Verzweigungen im Schleifenblock gibt.
Du wirst mehr darüber in einem zukünftigen Konzept lernen.

## Mikro-Ops

Ein Prozessor führt einen Befehl wie `add` oder `jnz` nicht direkt aus.
Die Frontend-Einheit der CPU _decodiert_ jeden Befehl zuerst in einen oder mehrere kleinere interne Schritte, genannt **Mikrooperationen** (oder **Mikro-Ops**).
Der Prozessor plant und führt dann diese Mikro-Ops aus, häufig mehrere pro Zyklus und außerhalb ihrer ursprünglichen Reihenfolge.

Die meisten einfachen Befehle decodieren zu einer einzigen Mikro-Op, während ein komplexerer Befehl zu mehreren decodieren kann.
Da die tatsächliche Arbeitslast des Prozessors der Strom der Mikro-Ops ist, ist das Produzieren von weniger davon für dieselbe Aufgabe eine Möglichkeit, wie Code schneller wird.

## Macrofusion

Wie bereits erwähnt, endet eine Schleife normalerweise mit irgendeiner Art von bedingtem Sprung.
Das ist so verbreitet, dass moderne Prozessoren für dieses Muster während der Decodierung optimiert sind.

Ein Flag-setzender Befehl, unmittelbar gefolgt von einem bedingten Sprung, der diese Flags liest, kann zusammen zu einer **einzigen** Mikro-Op decodiert werden, anstatt zu je einer.
Dies wird **Macrofusion** genannt.

Das fusionierte Paar verhält sich wie eine Operation: Der Zähler wird aktualisiert und die Verzweigungsentscheidung wird zusammen in einer einzigen Mikro-Op getroffen.
Der Kontrollfluss der Schleife kostet dann fast nichts zusätzlich zu der Arbeit, die die Schleife tatsächlich leistet.

Als Faustregel gilt, dass zwei Arten von Paaren normalerweise auf diese Weise fusionieren:

- Arithmetische Befehle wie `add` oder `sub`, unmittelbar gefolgt von einem bedingten Sprung.
- Ein `cmp`, `test` oder `and`, unmittelbar gefolgt von einem bedingten Sprung.

```x86asm
    ...
    add rdi, 8       ; advance a pointer
    cmp rdi, rsi     ; compare it against the end address
    jb .loop         ; repeat while still below the end
```

Fusion tritt nur auf, wenn der bedingte Sprung **unmittelbar** nach dem Flag-setzenden Befehl kommt, ohne dass etwas dazwischen liegt.

~~~~exercism/note
Macrofusion hängt von der CPU ab und es gibt einige Variationen, welche Befehle mit welchem bedingten Sprung fusionieren.

Eine nützliche Referenz ist [The microarchitecture of Intel, AMD, and VIA CPUs, by Agner Fog][agner-uarch].
Abschnitt 3.4.2.2 (Optimizing for Macrofusion) des [Intel optimization reference manual][intel-opt] listet ebenfalls fusionierbare Paare für Intel-CPUs auf.

[intel-opt]: https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf
[agner-uarch]: https://www.agner.org/optimize/microarchitecture.pdf
~~~~

## Der `loop`-Befehl

Es gibt einige Befehle, die verwendet werden können, um schleifenähnliches Verhalten zu erzeugen.
Einer davon ist [loop][loop].

Sein einziger Operand ist ein Label, das die Adresse zum Anfang der Schleife enthält.

Der `loop`-Befehl verwendet den Wert in `rcx` als Zähler und dekrementiert ihn jedes Mal um 1.
Sobald der Wert in `rcx` null erreicht, endet die Schleife und die Ausführung wird sequenziell fortgesetzt:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    loop .example ; this repeats the sequence starting in .example 10 times (the value in rcx)
                  ; at each time, rcx is decremented by 1
```

Es gibt zwei Varianten des `loop`-Befehls, die bei jeder Iteration das Zero Flag (`ZF`) prüfen.
Abgesehen davon, dass sie die Schleife stoppen, sobald `rcx` null erreicht, stoppen sie auch, wenn die Bedingung _nicht_ erfüllt ist.

| Befehl            | Bedingung |
| ----------------- | --------- |
| `loope`/`loopz`   | `ZF` == 1 |
| `loopne`/`loopnz` | `ZF` == 0 |

Das `ZF` wird von diesen Befehlen **nicht gesetzt**.
Es muss ein `cmp`, `test` oder ein anderer Befehl, der `ZF` ändert, davor stehen:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    cmp rax, 3
    loopne .example ; this repeats the sequence starting in .example while rcx > 0 and rax != 3
```

~~~~exercism/caution
Trotz ihrer Bequemlichkeit sind `loop`, `loope` und `loopne` auf modernen Prozessoren normalerweise viel langsamer als die entsprechende `sub`/`jnz`- oder `cmp`/`jnz`-Sequenz.

Eine gute Referenz zur Leistung von Befehlen auf vielen verschiedenen CPUs sind die [Agner's tables][agner-tables].

[agner-tables]: https://www.agner.org/optimize/instruction_tables.pdf
~~~~

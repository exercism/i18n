# Über

Factors Threads sind *kooperative Coroutinen* auf einem einzigen Betriebssystem-Thread.
Ein Thread läuft so lange, bis er explizit yield aufruft oder blockierende E/A ausführt;
an diesem Punkt wählt der Scheduler einen anderen lauffähigen Thread aus. Daraus folgen
zwei Dinge:

- Alles zwischen zwei yield-Aufrufen ist effektiv atomar.
- Echte Mehrkern-Parallelität erfordert, über das Standard-Vocab `threads` hinauszugehen
  (z. B. `concurrency.distributed` für Multi-Prozess-Designs).

Die Standard-Primitive für Nebenläufigkeit sind in Schichten angeordnet:

| Vocab                       | Bietet                                 |
|-----------------------------|----------------------------------------|
| [`threads`][threads]                   | `spawn`, `yield`, Thread-Identität     |
| [`concurrency.promises`][concurrency.promises]      | `<promise>`, `fulfill`, `?promise`     |
| [`concurrency.locks`][concurrency.locks]         | `<lock>`, `with-lock`                  |
| [`concurrency.combinators`][concurrency.combinators]   | `parallel-map`, `parallel-each`        |
| [`concurrency.semaphores`][concurrency.semaphores]    | `<semaphore>`, `acquire`, `release`    |
| [`concurrency.mailboxes`][concurrency.mailboxes]     | Posteingänge pro Thread, `send`, `receive` |
| [`concurrency.channels`][concurrency.channels]      | Rendezvous-Handles, `to`, `from`       |

```factor
USING: concurrency.combinators concurrency.locks
concurrency.promises kernel sequences threads ;

! parallel-map: fork-join, in order
{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }

! spawn + promise: hand-rolled fork-join
<promise> [
    [ "hello, world" swap fulfill ] curry "greeter" spawn drop
] keep ?promise .   ! => "hello, world"

! <lock> + with-lock: protect a shared mutable slot
<lock> :> guard
guard [ "do thing under lock" drop ] with-lock
```

`parallel-map` ist die High-Level-API und das, wozu idiomatisches Factor zuerst greift.
Das Trio `spawn` / `<promise>` / `?promise` ist das, worauf `parallel-map` aufbaut. Das
ist praktisch, wenn die Form der Iteration nicht zu map passt (z. B. wenn du Worker
startest, die über andere Kanäle zurückkommunizieren).

Locks schützen *gemeinsam genutzten veränderlichen Zustand*, typischerweise einen
Tuple-Slot oder eine Hashtable, die mehr als ein Thread liest oder schreibt. Geh sowohl
bei Lesezugriffen als auch bei Schreibzugriffen davon aus, dass sie das Lock brauchen,
wenn es irgendeine nicht-atomare zusammengesetzte Aktualisierung gibt; ein fehlendes Lock
auf einer der beiden Seiten ist das klassische Rezept für einen zerrissenen Lesevorgang.

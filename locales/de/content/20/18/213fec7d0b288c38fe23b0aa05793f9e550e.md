# Einführung

`GenServer` (generischer Server) ist ein [Behaviour][concept-behaviours], das die üblichen Client-Server-Interaktionen zwischen Elixir-Prozessen abstrahiert.

Erinnerst du dich noch an die receive-Schleife, die wir beim Thema [Prozesse][concept-processes] kennengelernt haben? Das `GenServer`-Behaviour bietet Abstraktionen, um solche Schleifen zu implementieren und um Nachrichten mit einem Prozess auszutauschen, der eine solche Schleife ausführt. Es macht es einfacher, Zustand zu verwalten und asynchronen Code auszuführen.

~~~~exercism/note
Sei gewarnt: Der Name `GenServer` ist mehrdeutig. Er bezeichnet auch ein _Modul_, das das `GenServer`-Behaviour _verwendet_, sowie einen _Prozess_, der von einem Modul gestartet wurde, das das `GenServer`-Behaviour _verwendet_.
~~~~

Das `GenServer`-Behaviour definiert einen erforderlichen Callback, `init/1`, und ein paar interessante optionale Callbacks: `handle_call/3`, `handle_cast/2` und `handle_info/3`. Die _Clients_, die einen `GenServer` verwenden, sollen diese Callbacks nicht direkt aufrufen. Stattdessen stellt das `GenServer`-Modul Funktionen bereit, mit denen Clients mit einem `GenServer`-Prozess kommunizieren können.

Häufig definiert ein einzelnes Modul sowohl eine _Client-API_, also eine Reihe von Funktionen, die andere Teile deiner Elixir-App aufrufen können, um mit diesem `GenServer`-Prozess zu kommunizieren, als auch _Implementierungen der Server-Callbacks_, die die Logik dieses `GenServer` enthalten.

Schauen wir uns zuerst ein einfaches Beispiel für einen `GenServer` an und lernen dann, was die einzelnen Callbacks bedeuten.

## Beispiel

Das ist ein Beispielserver, der auf die wiederholten Fragen nerviger Mitfahrer auf einem langen Roadtrip antworten kann, genauer gesagt auf die Frage: „Sind wir schon da?". Er zählt mit, wie oft diese Frage gestellt wurde, und gibt zunehmend genervtere Antworten zurück.

```elixir
defmodule AnnoyingPassengerAutoresponder do
  use GenServer
  # Client API

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg)
  end

  def are_we_there_yet?(pid) do
    GenServer.call(pid, :are_we_there_yet?)
  end

  # Server callbacks

  @impl GenServer
  def init(_init_arg) do
    # the initial count of questions asked is always 0
    state = 0
    {:ok, state}
  end

  @impl GenServer
  def handle_call(:are_we_there_yet?, _from, state) do
    reply =
      cond do
        state <= 3 -> "No."
        state <= 10 -> "I told you #{state} times already. No."
        true -> "..."
      end

    # increase the count of questions asked
    new_state = state + 1
    # reply to the caller
    {:reply, reply, new_state}
  end
end
```

## Callbacks

### `init/1`

Ein Server kann gestartet werden, indem du `GenServer.start/3` oder `GenServer.start_link/3` aufrufst. Den Unterschied zwischen diesen beiden Funktionen haben wir im [Links-Konzept][concept-links] kennengelernt.

Diese beiden Funktionen:

- Akzeptieren ein Modul, das das `GenServer`-Behaviour implementiert, als erstes Argument.
- Akzeptieren irgendetwas als zweites Argument namens `init_arg`. Wie der Name vermuten lässt, wird dieses Argument an den `init/1`-Callback übergeben.
- Akzeptieren ein optionales drittes Argument mit fortgeschrittenen Optionen für das Ausführen des Prozesses, die wir jetzt nicht behandeln.

Wenn du einen Server mit `GenServer.start/3` oder `GenServer.start_link/3` startest, wird der `init/1`-Callback blockierend aufgerufen. Der Rückgabewert von `init/1` entscheidet, ob der Server erfolgreich gestartet werden kann.

Der `init/1`-Callback gibt üblicherweise einen dieser Werte zurück:

- `{:ok, state}`. Der Server startet seine receive-Schleife und verwendet `state` als seinen Anfangszustand. `state` kann einen beliebigen Typ haben.
- `{:stop, reason}`. `reason` kann einen beliebigen Typ haben. Der Server startet seine receive-Schleife nicht. Der Prozess wird mit dem angegebenen Grund beendet.

Es gibt noch weitere, fortgeschrittenere Möglichkeiten, die wir jetzt nicht behandeln.

Wenn die receive-Schleife des Servers startet, geben die Funktionen `GenServer.start/3` und `GenServer.start_link/3` ein `{:ok, pid}`-Tupel zurück. Andernfalls geben sie `{:error, reason}` zurück.

### `handle_call/3`

Eine Nachricht, die eine Antwort erfordert, kann mit `GenServer.call/2` an einen Serverprozess gesendet werden. Diese Funktion erwartet die `pid` eines laufenden Serverprozesses als erstes Argument und die Nachricht als zweites Argument. Die Nachricht kann einen beliebigen Typ haben.

Der `handle_call/3`-Callback ist für das Behandeln und Beantworten synchroner Nachrichten zuständig. Er erhält drei Argumente:

1. `message` – der Wert, der als zweites Argument an `GenServer.call/2` übergeben wurde.
2. `from` – die `pid` des Prozesses, der `GenServer.call/2` aufruft. Dieses Argument kannst du meistens ignorieren.
3. `state` – der aktuelle Zustand des Servers. Denk daran, dass sein Anfangswert im `init/1`-Callback gesetzt wurde.

Der `handle_call/3`-Callback gibt üblicherweise ein 3-Tupel `{:reply, reply, state}` zurück. Das bedeutet, dass das zweite Element des Tupels, ein `reply`, das einen beliebigen Typ haben kann, an den Aufrufer zurückgeschickt wird. Das dritte Element des Tupels, `state`, ist der neue Zustand des Servers nach dem Behandeln dieser Nachricht.

Es gibt noch weitere, fortgeschrittenere Möglichkeiten, die wir jetzt nicht behandeln.

~~~~exercism/note
Um dir anhand des Namens zu merken, was dieser Callback tut,
stell dir vor, du „rufst“ jemanden am Telefon an.

Wenn diese Person verfügbar ist, bekommst du sofort eine Antwort (synchron).
~~~~

### `handle_cast/2`

Eine Nachricht, die keine Antwort erfordert, kann mit `GenServer.cast/2` an einen Serverprozess gesendet werden. Ihre Argumente sind mit denen von `GenServer.call/2` identisch.

Der `handle_cast/2`-Callback ist für das Behandeln dieser Nachrichten zuständig. Er erhält zwei Argumente, `message` und `state`, also dieselben Argumente wie beim `handle_call/3`-Callback (mit Ausnahme von `from`).

Der `handle_cast/2`-Callback gibt üblicherweise ein 2-Tupel `{:noreply, state}` zurück.

Es gibt noch weitere, fortgeschrittenere Möglichkeiten, die wir jetzt nicht behandeln.

~~~~exercism/note
Um dir anhand des Namens zu merken, was dieser Callback tut,
denk daran, dass „to cast“ auch „werfen“ bedeutet.

Wenn du eine Flaschenpost ins Meer wirfst,
erwartest du nicht, sofort eine Antwort zu bekommen,
vielleicht nie.
~~~~

### Soll ich `call` oder `cast` verwenden?

Verwende fast immer `call`, auch wenn dein Client-Code die Antwort des Servers nicht braucht.

Die Verwendung von `call` wartet auf die Antwort, was als Backpressure-Mechanismus dient (um zu verhindern, dass Clients zu viele Nachrichten auf einmal senden). Eine Antwort vom Server zu erhalten ist außerdem die einzige Möglichkeit, sicher zu sein, dass der Server die Nachricht des Clients empfangen und verarbeitet hat.

### `handle_info/2`

Nachrichten können auch auf anderem Weg als durch den Aufruf von `GenServer.call/2` oder `GenServer.cast/2` im Postfach des Servers landen, zum Beispiel durch den Aufruf der einfachen Funktion `send/2`.

Um solche Nachrichten zu behandeln, verwende den `handle_info/2`-Callback. Dieser Callback funktioniert genau wie `handle_cast/2`.

Das `GenServer`-Behaviour bietet eine Catch-all-Implementierung von `handle_info/2`, die Fehler über unerwartete Nachrichten protokolliert. Wenn du diese Standardimplementierung überschreibst, stelle sicher, dass du immer deine eigene Catch-all-Implementierung einbaust. Wenn du das vergisst, stürzt der Server ab, sobald er eine unerwartete Nachricht erhält.

## Timeouts

Der Rückgabewert jedes der vier oben beschriebenen Callbacks kann um ein weiteres Tupel-Element erweitert werden, einen Timeout. Statt zum Beispiel `{:ok, state}` aus `init/1` zurückzugeben, gibst du `{:ok, state, timeout}` zurück.

Der Timeout kann verwendet werden, um festzustellen, dass über einen bestimmten Zeitraum keine Nachrichten im Postfach eingegangen sind. Wenn der Server aus einem seiner Callbacks einen Timeout zurückgibt und die angegebene Anzahl an Millisekunden vergangen ist, ohne dass eine Nachricht eintrifft, wird `handle_info/2` mit `:timeout` als erstem Argument aufgerufen.

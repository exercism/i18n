# Über

Eine Funktion ist [rekursiv][recursion], wenn sie sich selbst aufruft.

Ein wesentlicher Unterschied zwischen einem Funktionsaufruf und einer Schleife besteht darin, dass ein Funktionsaufruf die Rücksprungadresse auf den Stack legt. Deshalb braucht eine rekursive Funktion meist mehr Stack-Speicher als eine äquivalente Schleife.

Die Folge ist, dass eine Funktion, die sich immer wieder selbst aufruft, irgendwann den gesamten Stack-Speicher aufbrauchen kann. Das nennt man einen [Stack-Überlauf][stack-overflow].

Deshalb braucht jede rekursive Funktion mindestens einen Basisfall: eine Situation, in der die Funktion zurückkehrt, ohne sich selbst aufzurufen. Jeder rekursive Aufruf muss irgendwann einen Basisfall erreichen.

Zum Beispiel lässt sich die Fakultätsfunktion `n! = n * (n - 1) * ... * 1` rekursiv definieren, mit `1` als Basisfall:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Beachte, dass `factorial` vor der Rekursion `push rdi` ausführen und danach `pop rdi` ausführen muss. Der Grund ist, dass es `n` noch braucht, nachdem der rekursive Aufruf zurückgekehrt ist, um `n * (n-1)!` zu berechnen.

Beachte außerdem, dass ein callee-saved-Register dieses Problem nicht lösen würde.

Obwohl eine rekursive Funktion ein potenzieller Aufrufer ihrer selbst ist, wird sie selbst von einer anderen Funktion aufgerufen. Das heißt, die Funktion muss auch callee-saved-Register sichern, bevor sie sie benutzt, und ihren Wert wiederherstellen, nachdem sie sie benutzt hat. Das geschieht üblicherweise mit einer `push`/`pop`-Folge, wie wir sie in einem früheren Konzept gesehen haben.

Da jeder Frame einer rekursiven Funktion, mit Ausnahme des Basisfalls, ebenfalls ein Aufrufer ist, der seine eigenen lokalen Variablen sichern muss, muss diese `push`/`pop`-Folge für jeden Frame wiederholt werden. Selbst wenn man die Variable direkt auf dem Stack ablegt, ohne Register zu benutzen, würde das pro Frame dieselben `8` Bytes kosten.

Das bedeutet, dass jeder rekursive Aufruf `8` Bytes für die von `call` auf den Stack gelegte Rücksprungadresse hinzufügt, plus `8` Bytes für jede lokale Variable, die gesichert werden muss. Die Funktion fügt diese Bytes mit jedem Frame weiter zum Stack hinzu, bis sie ihren Basisfall erreicht. Erst dann beginnt sie, sich in umgekehrter Reihenfolge abzubauen, wobei jeder rekursive Aufruf so viele `pop` benutzt wie nötig und danach ein `ret` ausführt.

Wenn `factorial` zum Beispiel mit dem Argument `10` aufgerufen würde, würde es sich neunmal selbst aufrufen, bevor es den Basisfall `1` erreicht. Zu diesem Zeitpunkt wären `144` Bytes belegt, um für jeden vorherigen Frame das `n` (`8` Bytes) und die Rücksprungadresse (`8` Bytes) zu speichern.

## Endaufruf

In manchen Situationen erledigt eine Funktion nach dem Aufruf einer anderen und vor der Rückkehr keine Arbeit mehr.

Betrachte zum Beispiel:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

Die Funktion `triple_of_square`:

- multipliziert das übergebene Argument (in `rdi`) mit sich selbst und erhält so sein Quadrat;
- dann ruft sie `times_three` auf, was das Dreifache des übergebenen Arguments zurückgibt.

Damit gibt `triple_of_square` `3*x²` zurück, wobei `x` das Argument ist, das in `rdi` übergeben wird.

Beachte, dass in `triple_of_square` nach dem Aufruf von `times_three` keine Arbeit mehr anfällt, die Funktion kehrt einfach zurück. In einer solchen Situation kann eine Funktion statt `call` ein `jmp` verwenden und die Ausführung an die aufgerufene Funktion übergeben:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

Das nennt man einen [Endaufruf][tail].

Der größte Vorteil eines Endaufrufs ist, dass die zusätzlichen Kosten von `call` entfallen. Ein `call` legt eine Rücksprungadresse auf den Stack, und damit die Ausführung dorthin zurückkehrt, muss es ein passendes `ret` geben.

Ein Endaufruf lässt beides weg: Es gibt keine Rücksprungadresse, die auf den Stack gelegt werden müsste, und kein zusätzliches `ret` als Gegenstück, nur das eigene `ret` der aufgerufenen Funktion.

## Endrekursion

Ein Endaufruf ist besonders nützlich für rekursive Funktionen, die sich vor der Rückkehr viele Male selbst aufrufen können.

Allerdings lässt sich nicht jeder rekursive Aufruf direkt in einen Endaufruf umwandeln. Da ein `jmp` die Kontrolle an die aufgerufene Funktion übergibt, kann der Aufrufer nach dem Endaufruf keine Arbeit mehr erledigen.

Die frühere Funktion `factorial` ist zum Beispiel **nicht** endrekursiv. Nach dem rekursiven Aufruf muss sie das Ergebnis noch mit dem aktuellen `n` multiplizieren, mit `imul rax, rdi`.

In solchen Situationen ist es manchmal möglich, einen Akkumulator zu verwenden, der Teilergebnisse sammelt und am Ende zurückgegeben wird. Zum Beispiel können wir einen `factorial_helper` definieren, der den Großteil der Arbeit erledigt, und `factorial` richtet dann einen Akkumulator ein und übergibt die Kontrolle an `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Da nach dem rekursiven Aufruf keine Arbeit mehr anfällt, müssen wir `rdi` auch nicht mehr sichern. Es gibt kein `call` und kein `push rdi`, also fügt jede rekursive Iteration `0` Bytes zum Stack hinzu: Es wird kein zusätzlicher Stack-Speicher belegt. Diese Version kann beliebig große `n` verarbeiten, ohne den Stack zum Überlaufen zu bringen. Sie ist sowohl effizienter als auch sicherer.

In manchen Fällen lässt sich sogar das `jmp` zum Helfer vermeiden, indem man die Reihenfolge der Funktionen geschickt wählt. Zum Beispiel lassen sich `factorial` und `triple_of_square` so umschreiben:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

Im obigen Ausschnitt läuft die Ausführung von `factorial` direkt weiter in `factorial_helper`. Dasselbe passiert mit `triple_of_square` und `times_three`. In beiden Fällen läuft die Ausführung einfach der Reihe nach weiter, und es scheint, als wäre die Endfunktion nur ein lokales Label innerhalb der „Hauptfunktion“.

In Wirklichkeit gibt es keinen wesentlichen Unterschied zwischen einem lokalen Label und einer Funktion. x86-64-Assembly behandelt keinen von ihnen besonders; sie sind einfach Adressen in einem Abschnitt mit ausführbarem Code wie `section .text`.

So kann man sich eine endrekursive Funktion im Wesentlichen genauso vorstellen wie eine Schleife, in der der rekursive Aufruf zum Anfang zurückspringt und der Basisfall die Bedingung ist, die die Schleife beendet.

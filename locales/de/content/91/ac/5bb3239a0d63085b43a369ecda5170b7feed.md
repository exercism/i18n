# Sortieren

```sather
   numbers.sort;                                  -- the natural order
   words.insertion_sort_by(bind(before(_, _)));   -- an order you supply
```

## Was sort braucht

`sort` setzt voraus, dass der Elementtyp `is_lt` hat. Bei `INT`, `STR`, `CHAR`,
`FLTD` und `INTI` ist das der Fall. Bei einer eigenen Klasse nicht, bis du
eine schreibst.

`insertion_sort_by` verlangt nichts vom Elementtyp: Alles, was es wissen
muss, steckt in der Routine, die du ihm übergibst.

## Wie ein Vergleich sein muss

Die Routine muss eine widerspruchsfreie Ordnung definieren, sonst ist das
Ergebnis nicht definiert:

- wenn `before(a, b)` wahr ist, muss `before(b, a)` falsch sein;
- wenn `a` vor `b` kommt und `b` vor `c`, dann kommt `a` vor `c`;
- `before(a, a)` muss falsch sein.

Über den letzten Punkt stolpern die Leute. Wenn du `<=` statt `<` schreibst,
sagst du, dass ein Ding vor sich selbst kommt, und eine Sortierung, die das
bekommt, kann alles Mögliche produzieren.

## Gleichstände

Weder `sort` noch `insertion_sort_by` ist **stabil**: Dinge, die der Vergleich
als gleich ansieht, können in beliebiger Reihenfolge herauskommen, und in
dieser Bibliothek kommen sie im Allgemeinen umgekehrt heraus.

Der Trick, zweimal zu sortieren, erst nach Namen, dann nach Punkten, in der
Erwartung, dass punktgleiche Teams alphabetisch bleiben, funktioniert hier
also nicht. Und darauf, dass die Eingabereihenfolge irgendetwas garantiert,
kannst du dich ebenfalls nicht verlassen.

Wenn Gleichstände eine Rolle spielen, entscheide sie **im Vergleich**. Mach
daraus eine totale Ordnung, sodass niemals zwei verschiedene Dinge als gleich
gelten:

```sather
   shorter(a, b : STR) : BOOL is
      if a.size /= b.size then return a.size < b.size; end;
      return a < b;                  -- same length: alphabetical
   end;
```

Das lohnt sich auch dann, wenn du glaubst, dass Gleichstände nicht vorkommen
können. Ein Vergleich, der in beide Richtungen falsch antwortet, lässt das
Ergebnis unbestimmt, und der Bug zeigt sich als eine Reihenfolge, die sich
ohne sichtbaren Grund ändert.

## Die anderen

| Aufruf | Bewirkt |
| --- | --- |
| `a.sort` | an Ort und Stelle, natürliche Ordnung, nicht stabil |
| `a.insertion_sort_by(lt)` | an Ort und Stelle, deine Ordnung, stabil |
| `a.is_sorted` | prüfen |
| `a.is_sorted_by(lt)` | gegen deine Ordnung prüfen |
| `a.binary_search(e)` | finden, auf einem sortierten Array |
| `a.binary_search_by(e, lt)` | finden, gegen deine Ordnung |

`binary_search` auf einem unsortierten Array schlägt nicht fehl, es antwortet
Unsinn. Seine Vorbedingung sagt genau das, und Vorbedingungen werden nicht
geprüft, solange dem Compiler nicht `-chk` mitgegeben wird.

## Kosten

Insertionsort leistet Arbeit proportional zum Quadrat der Länge, was für eine
Rangliste mit einem Dutzend Teams in Ordnung ist und für zehntausend
Datensätze falsch. `ARR_SORT_ALG::sort_by` ist die Quicksort-Version derselben
Idee, für den Fall, dass das Array groß ist und Stabilität keine Rolle spielt.

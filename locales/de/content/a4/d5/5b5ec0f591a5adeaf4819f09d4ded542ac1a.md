# Anleitung

Dieses Problem ist dem nicht-präemptiven statischen Scheduling von Echtzeitbetriebssystemen nachempfunden, ähnelt aber auch dem Job-Shop-Problem (JSP) mit nur einer Ressource. Es wird davon ausgegangen, dass alle Tasks statisch bekannt sind. Mit anderen Worten: Die Release-Zeiten aller Tasks sind zu Beginn des Programms bekannt. In der Praxis sind die Release-Zeiten von Tasks zu Programmbeginn nicht bekannt; sie können jederzeit durch I/O, Interrupts usw. erzeugt werden.

Gegeben ist eine Liste von Tasks mit Parametern. Bestimme einen Zeitplan, in dem die Tasks sequenziell und ohne Überschneidung ausgeführt werden können. Da das Problem dem Prozess-Scheduling von RTOS nachempfunden ist, nehmen wir an, dass zwischen zwei Tasks eine von null verschiedene Zeit benötigt wird, der sogenannte Context-Switching-Overhead. Es gibt zwei verschiedene Arten von Tasks: periodische und dynamische. Beide Arten haben einen Task-ID-Parameter, einen String, mit dem sich die einzelnen Tasks in der Task-Liste unterscheiden lassen.

Ein **periodischer Task** ist ein Task, der periodisch ausgeführt wird. Mit anderen Worten: Der Task wird alle T Sekunden einmal ausgeführt, wobei T die Periode ist.
Ein periodischer Task wird durch die folgenden Parameter definiert:
* Startzeit: Zeitpunkt, zu dem die erste Wiederholung, also die erste Instanz, des Tasks beginnt
* Periode: Zeit zwischen dem Start der einzelnen Wiederholungen des Tasks
* Ausführungszeit: Zeit, die jede Wiederholung läuft
* Endzeit: Zeitpunkt, ab dem der gesamte Task nicht mehr eingeplant wird

Ein **dynamischer Task** ist ein Task, der nur ein einziges Mal ausgeführt wird.
Ein dynamischer Task wird durch die folgenden Parameter definiert:
* Release-Zeit: frühester Zeitpunkt, zu dem der Task eingeplant werden KANN (NICHT dasselbe wie die Startzeit)
* Ausführungszeit: Zeit, die der Task läuft
* Deadline: Zeitpunkt, bis zu dem der Task die Ausführung beendet haben muss

Die zu implementierende Funktion nimmt zwei Eingabewerte entgegen. Der erste Eingabewert ist eine Liste von Instanzen von `RealTimeTask`. Instanzen von `RealTimeTask` werden entweder als Instanz von `PeriodicRealTimeTask` oder von `DynamicRealTimeTask` übergeben, wobei alle Task-Parameter Ganzzahlen sind.
Die in Python eingebaute Funktion `isinstance()` kann verwendet werden, um zwischen den beiden Tasks in der Liste zu unterscheiden. Die Reihenfolge der Liste ist unerheblich; schau nur auf die Parameter der Tasks.
Der zweite Eingabewert ist eine einzelne Ganzzahl, die den Context-Switching-Overhead angibt. Der Context-Switching-Overhead ist immer eine nichtnegative Ganzzahl.

Der Rückgabewert sollte ein Dictionary sein, dessen Schlüssel die Task-ID aus den `RealTimeTask`-Instanzen sind und dessen Wert eine Liste von Zweiertupeln ist. Die Zweiertupel haben das Format (Startzeit, Endzeit). Dynamische Tasks sollten nur ein Zweiertupel in der Liste enthalten, periodische Tasks dagegen möglicherweise mehr als eines. Die Reihenfolge der Zweiertupel in der Liste spielt keine Rolle. Wenn sich aus der Liste der Tasks mit dem gegebenen Context-Switching-Overhead kein gültiger Zeitplan erstellen lässt, löse eine `NoRtosStaticScheduleProducible`-Ausnahme aus. Beachte, dass die Z3-Modellergebnisse für Variablen vor der Ausgabe in `int` umgewandelt werden müssen. Wenn das Z3-Modellergebnis vom Typ `IntNumRef` ist, kann die Klassenmethode `as_long()` zur Umwandlung in eine Ganzzahl verwendet werden.

Zusätzlich wird eine Funktion bereitgestellt, mit der du dir die sequenzielle Reihenfolge der Tasks veranschaulichen kannst. Diese Funktion lässt sich auch für einzelne Testfälle aktivieren, indem du das Schlüsselwortargument `plot` in der Funktion `check()` auf `True` setzt. Zur Darstellung und Beschriftung jedes Tasks wird ein gebrochenes horizontales Balkendiagramm verwendet. Um diese Funktion nutzen zu können, muss die Python-Bibliothek *matplotlib* installiert sein. Details zur Installation von *matplotlib* findest du [hier](https://matplotlib.org/stable/users/installing.html).

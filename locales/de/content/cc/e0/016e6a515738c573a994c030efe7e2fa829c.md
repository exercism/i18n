# Über

C#-`struct`s sind eng mit `class`es verwandt.
Sie haben Zustand und Verhalten.
Sie können dieselben Arten von Membern haben: Konstruktoren, Methoden, Felder, Eigenschaften usw.

Felder und Eigenschaften können einfache Typen, `struct`s oder Referenztypen sein.
`struct`s befolgen dieselben Regeln für Gültigkeitsbereich, Lese-/Schreibregeln und Zugriffsebenen wie `class`es.

```csharp
enum Unit
{
    Kg,
    Lb
}

struct Weight
{
    private double count;
    private Unit unit;

    public Weight(double count, Unit unit)
    {
        this.count = count;
        this.unit = unit;
    }

    public override string ToString()
    {
        return count.ToString() + unit.ToString();
    }
}

new Weight(77.5, Unit.Kg).ToString();
// => "77.6Kg"
```

Eines der wichtigsten Dinge, die du dir merken solltest, ist, dass beim Zuweisen eines Structs an eine Variable oder beim Übergeben als Parameter die Werte kopiert werden. Änderungen an der ursprünglichen Variable wirken sich also nicht auf die kopierte aus und umgekehrt.
Zusammengefasst sind `struct`s **Werttypen**.

Dieser [Artikel][class-or-struct] behandelt die Unterschiede zwischen `struct`s und `class`es.
Du wirst in dem Artikel sehen, dass `struct`s tendenziell leichtgewichtig und [unveränderlich][structs-immutable] sind, obwohl diese Empfehlung (standardmäßig) nicht vom Compiler oder der Laufzeitumgebung erzwungen wird.

Es gibt ein paar Dinge, auf die du stoßen wirst (und an die dich der Compiler erinnern wird):

1. Member eines `struct`s können nicht inline initialisiert werden.
2. Ein `struct` kann nicht vererbt werden.
3. Ein `struct` hat immer einen Standardkonstruktor, selbst wenn ein nicht standardmäßiger Konstruktor bereitgestellt wird, und du kannst keinen expliziten parameterlosen Konstruktor bereitstellen.

Aufgrund der Punkte 1 und 3 oben kann der Entwickler eines `struct`s nicht verhindern, dass ungültige Instanzen entstehen.

## Häufige Structs

Du wirst in der Dokumentation sehen, dass es eine enge Beziehung zwischen primitiven Typen und Structs gibt.
Siehe [`Int32/int`][int32] für ein Beispiel.
Ein konventionelleres Beispiel für ein `struct` ist der Typ [`TimeSpan`][time-span].

Instanzen von `TimeSpan` verhalten sich ähnlich wie Zahlen, mit Vergleichsoperatoren wie `>` und `<` und arithmetischen Operatoren.
Du kannst diese Operatoren für deine eigenen `struct`s implementieren, wenn du sie brauchst.

Eine Sache, die du über `TimeSpan` wissen solltest, ist, dass es eine Reihe von Schnittstellen implementiert, z. B. `IComparable<TimeSpan>`.
Obwohl `struct`s nicht von anderen `struct`s abgeleitet werden können, können sie Schnittstellen implementieren.

## Gleichheit

Das Testen auf Gleichheit ist bei `struct`s oft viel einfacher als bei `class`es, da standardmäßig einfach die Felder auf Gleichheit verglichen werden.
Es ist nicht nötig, `object.Equals()` (oder `GetHashCode()`) zu überschreiben.
Denk daran: Wenn du dich auf `Object.GetHashCode()` verlässt, musst du trotzdem sicherstellen, dass sich die an der Erzeugung des Hashcodes beteiligten Felder (also alle Felder) nicht ändern, während eine gehashte Sammlung verwendet wird.
Effektiv bedeutet das, dass Structs, die auf diese Weise verwendet werden, unveränderlich sein sollten.

Im Gegensatz zur Methode `Equals()` gibt es keine Standardimplementierung der Gleichheitsoperatoren `==` und `!=`.
Wenn dein `struct` sie braucht, musst du sie implementieren.

Andererseits beschreibt dieser [Artikel][equality], wie die Performance optimiert werden kann, indem du deine eigenen benutzerdefinierten `Equals()`- und `GetHashCode()`-Methoden erstellst, wie es bei `class`es oft gemacht wird.
Der Unterschied war bei dieser Übung in einem nicht sehr strengen Vergleich etwa 20 %, aber das könnte niedrig angesetzt sein, weil alle Felder denselben Typ haben. Siehe unten.

Im [Web][equality-performance] gibt es Diskussionen über Geschwindigkeitsverbesserungen, wenn die `Equals()`-Methode nicht überschrieben wird und alle Felder denselben Typ haben.
Der Unterschied bei dieser Übung durch die Aufnahme unterschiedlicher Felder betrug etwa 60 %.
Das wird in der Microsoft-Dokumentation nicht erwähnt, was es zu einem nicht dokumentierten Implementierungsdetail macht, und es sollte mit Bedacht genutzt werden.

```csharp
public bool Equals(Weight other)
{
    return count.Equals(other.count) && unit.Equals(other.unit);
}

public override bool Equals(object obj)
{
    return obj is Weight other && Equals(other);
}

public override int GetHashCode()
{
    return HashCode.Combine(count, unit);
}
```

# Markdown-Spezifikation

So sollten alle Markdown-Dateien innerhalb von Exercism strukturiert sein.

Einige der Regeln in diesem Dokument sind noch nicht in ganz Exercism umgesetzt.
Wir freuen uns über PRs, die das beheben.
Alle Regeln werden nach und nach in unsere CI und unsere Linting-Tools aufgenommen und sollten bei neuen Änderungen eingehalten werden.

## Überschriften

- Alle Dateien müssen mit einer Überschrift der Ebene 1 beginnen (`# Some heading text`).
- Überschriften der Ebene 1 gibt es nur für die Darstellung auf GitHub oder einer vergleichbaren Plattform.
- Wenn die Datei von Exercism gerendert wird (z. B. auf der Website angezeigt oder über die Kommandozeile gerendert), wird diese Überschrift entfernt und eine kontextbezogene Überschrift eingefügt.
- Keine Überschrift darf mehr als eine Ebene unter der vorherigen liegen (z. B. darf auf `##` nur `###` folgen, nicht `####`).
- Abgesehen von der einen Überschrift der Ebene 1 (`#`) dürfen nur Überschriften der Ebene 2 (`##`), Ebene 3 (`###`) und Ebene 4 (`####`) verwendet werden.

## Links

Bitte verwende [Referenzlinks][reference-links], die am Ende der Markdown-Datei definiert, einem Referenz-Slug zugeordnet und im Text über diesen Slug referenziert werden.

Diese Methode erleichtert die Pflege, da Links nur an einer einzigen Stelle aktualisiert werden müssen.

Beispiel:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

Links sollten immer Ankertext haben, statt die URL selbst in den Text zu schreiben. Das folgende Beispiel verwendet keinen Ankertext und ist schwerer zu lesen.

```
If you want some more information, please visit https://google.com.
```

Ankertext zu verwenden und ihn zu verlinken, ist leichter zu verstehen und einzuordnen.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

Das wird gerendert als: „Wenn du mehr Informationen möchtest, ist [Google][google-link] eine nützliche Anlaufstelle.“

## Code

Wenn du dich auf Codeelemente beziehst (z. B. Funktionen oder Schlüsselwörter), sollte der Code in Backticks gesetzt werden:

```
- The `printf()` function writes to the console.
```

Das wird gerendert als:

- Die Funktion `printf()` schreibt in die Konsole.

Komplexerer Code (z. B. mehrzeiliger Code) sollte in dreifache Backticks gesetzt werden. Nach den öffnenden dreifachen Backticks sollte ein [Sprachbezeichner][language-identifier] angegeben werden, um die Syntaxhervorhebung zu aktivieren:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

Formatiere den Code nach Möglichkeit so, wie es für die Umgebung, in der er präsentiert wird, am sinnvollsten ist. Wenn verfügbar, zieh bitte die Dokumentation für deine Sprache heran.

Python hat zum Beispiel die REPL (read-eval-print loop), in der du Code direkt in ein Terminal tippen kannst. Wenn du gerade Code debuggst oder eine Funktion lokal ausführst, um zu testen oder zu beobachten, wie sie funktioniert, nutzt du dafür eher eine REPL, weil es dort bequemer ist, interaktiv zu tippen. In dieser Situation formatieren wir Beispielcode lieber so, als würde er in die REPL getippt, mit einem führenden `>>>`:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

In anderen Fällen ist es sinnvoller, den Code so zu belassen, als stünde er in einer `.py`-Datei. Hier profitiert der Lernende davon, etwas zu sehen, das nachahmt, wie er den Code selbst schreiben würde.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

Ein schneller Weg, die beiden Fälle zu unterscheiden, wenn es unklar ist: Wenn es Code ist, den der Lernende in einem Terminal ausführen kann, formatiere ihn so. Wenn es Code ist, den Exercism ausführen könnte (in Tests, Bibliothekscode, den der Lernende schreibt, usw.), formatiere ihn standardmäßig als ausführbaren Code.

## Spezielle Blöcke (manchmal Admonitions genannt)

Wir unterstützen spezielle Blocktypen, die du zu Dokumenten hinzufügen kannst, um Kommentare hervorzuheben, die nicht in den Haupttext passen.

<img width="500" alt="Markdown-Notizblock" src="https://user-images.githubusercontent.com/20866761/139531109-0c0f3ea5-b589-44ff-93ab-d901a45edc56.png">

<img width="500" alt="Markdown-Warnblock" src="https://user-images.githubusercontent.com/20866761/139531234-9b58b9ab-524b-44fd-bbcb-4e10f2927d27.png">

<img width="500" alt="Markdown-Block für Fortgeschrittene" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

Wir unterstützen drei Arten von Blöcken:

- **exercism/note:** Blöcke, die besonders wichtige Zusatzinformationen hervorheben
- **exercism/caution:** Dinge, die man wissen sollte oder mit denen man vorsichtig umgehen sollte
- **exercism/advanced:** Informationen, die nur für Menschen relevant sind, die tiefer in etwas eintauchen möchten oder von denen erweitertes Wissen erwartet wird

Alle Blöcke werden mit 4 Tilden geschrieben, in dieser Form:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(Hinweis: In Ausnahmefällen kannst du auch Backticks oder andere Anzahlen von Tilden verwenden)

## Layout

### Ein Satz pro Zeile

Absätze sollten mit einem Satz pro Zeile formatiert werden. Die [Ascii-Doctor-Dokumentation][asciidoctor] erklärt die Logik dahinter anschaulich.

Ein einzelner Absatz sollte zum Beispiel so formatiert werden:

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## Listen

Verwende das Bindestrichzeichen (`-`) als Aufzählungszeichen für unsortierte Listen.

## Kommentare

- Bevorzuge Markdown-Kommentare statt HTML-Kommentare (verwende z. B. `[comment]: # (Actual comment...)` statt `<!-- Actual comment -->`)

Du kannst testen, ob dein Markdown-Kommentar entfernt wird, indem du nachschaust, wie dein Kommentar aussieht, wenn er über CommonMark gerendert wird, und zwar bei [babelmark3].

## Inline-HTML

- Inline-HTML ist erlaubt, sollte aber sparsam eingesetzt werden
- Verwende immer native Markdown-Alternativen, wenn es sie gibt (verwende z. B. `# ...` statt `<h1>...</h1>`)

## Bilder

Da die Website helle und dunkle Designs unterstützt, müssen von der Community eingereichte Bilder in beiden Designs gut aussehen.
Die Lösung dafür ist, den Bildnamen (vor der Dateiendung) mit einem Suffix zu versehen:

1. Lass den Bildnamen auf `-invertible` enden (z. B. `graph-invertible.svg`). Das Bild wird automatisch invertiert, wenn es im dunklen Design angezeigt wird (über `filter: invert(100%)`).
1. Lass den Bildnamen auf `-light` enden (z. B. `graph-light.png`) und erstelle zusätzlich eine mit dem dunklen Design kompatible Version, die auf `-dark` endet (also `graph-dark.png`). Wir rendern dann automatisch das richtige Bild, je nach Design des Nutzers.

Bilder ohne eines der beiden Suffixe werden in beiden Designs unverändert verwendet.
Das heißt: Wenn du Graustufenbilder erstellen möchtest, kannst du sie in der Regel für das helle Design gut aussehen lassen und sie dann als invertierbar festlegen.
Wenn du aber ein Bild mit vielen Farben verwendest, möchtest du vielleicht zwei Varianten erstellen.

Der vollständige Bildname (einschließlich `-invertible`) sollte im Markdown dort angegeben werden, wo das Bild gerendert wird.
Bei Light-/Dark-Bildern gib **NUR** die `-light`-Variante an.
Diese Logik gilt in allen Markdown-Dokumenten.

## Automatische Formatierung

Einige Repositories verwenden [prettier][prettier], um sicherzustellen, dass alles Markdown einheitlich formatiert ist. Das kann folgende Vorteile bringen:

- Keine Diskussionen über Formatierung.
- Tolle Editor-/IDE-Integration, sodass Dateien beim Speichern formatiert werden können.
- Einfache CI-Prüfungen für die Formatierung lassen sich hinzufügen.
- Dateien lassen sich einfach per Skript automatisch formatieren.

All das kann den Änderungsaufwand bei Reviews deutlich verringern, der sowohl für den Reviewer als auch für die reviewte Person frustrierend ist.

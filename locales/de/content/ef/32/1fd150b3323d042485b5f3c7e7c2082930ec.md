# Einführung

Die Threads von Factor sind *kooperative Coroutinen*: Sie teilen sich einen einzigen Betriebssystem-Thread, übergeben sich die Kontrolle bei I/O und an expliziten Yield-Punkten und laufen nie wirklich gleichzeitig. Alles, was du *zwischen* zwei Yield-Punkten tust, geschieht in einem einzigen, ununterbrochenen Schritt. Wenn aber eine zusammengesetzte Operation (Lesen-Ändern-Schreiben) mittendrin einen Yield macht, kann sich ein anderer Thread dazwischenschieben und die Welt verändern, bevor du fertig bist. Und genau das ist eine Race Condition.

Diese Übung behandelt vier Grundbausteine, die dir immer wieder begegnen:

## `parallel-map`: Fork/Join über eine Sequenz

```
parallel-map ( seq quot: ( elt -- newelt ) -- newseq )
```

Zu finden in [`concurrency.combinators`][combinators]. Erzeugt für jedes Element einen Thread, führt die Quotation aus und sammelt die Ergebnisse in derselben Reihenfolge wieder in einer neuen Sequenz ein:

```factor
USING: concurrency.combinators sequences ;

{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }
```

## `spawn`: Einen Thread starten

```
spawn ( quot name -- thread )
```

Zu finden in [`threads`][threads]. Die Quotation läuft nebenläufig; `name` ist eine Bezeichnung zum Debuggen. Der zurückgegebene Thread-Handle ist auf dieser Ebene meist uninteressant; `drop` ihn einfach.

## Promises: einmalige Wertübergabe

```
<promise>           ( -- promise )
fulfill             ( value promise -- )
?promise            ( promise -- value )
```

Zu finden in [`concurrency.promises`][promises]. Ein Promise ist ein Briefkasten für einen einzigen Wert: Ein Thread erfüllt es, andere lesen daraus. `?promise` blockiert, bis das Promise erfüllt wurde, und gibt dann den Wert zurück.

```factor
USING: concurrency.promises kernel threads ;

<promise> [
    [ 42 swap fulfill ] curry "answer" spawn drop
] keep ?promise .
! => 42
```

`spawn` + `<promise>` ist das, woraus `parallel-map` gebaut ist; sie selbst von Hand zu verdrahten ist nützlich, wenn jede Aufgabe etwas anderes tut als „ein Element zu berechnen“.

Das typische Fan-out/Join-Muster über eine Sequenz sieht so aus: Für jede Eingabe erzeugst du ein frisches Promise, startest einen Thread, der die Arbeit erledigt und das Promise mit `fulfill` erfüllt, sammelst alle Promises in einer Sequenz und rufst dann für jedes einzelne `?promise` auf, um auf seine Fertigstellung zu warten. Locals machen das lesbar: Binde das Promise mit `:>` innerhalb eines `[| | ]`-Lambdas an einen Namen, damit die gestartete Quotation es einschließen kann:

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
inputs [| x |
    <promise> :> p
    [ x do-work t p fulfill ] "worker" spawn drop
    p
] map [ ?promise drop ] each
```

## Locks: gegenseitiger Ausschluss

```
<lock>     ( -- lock )
with-lock  ( lock quot -- )
```

Zu finden in [`concurrency.locks`][locks]. Ein bestimmtes Lock kann immer nur ein Thread halten. `with-lock` erwirbt es, führt die Quotation aus und gibt es wieder frei, auch wenn die Quotation eine Ausnahme auslöst.

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
USING: concurrency.locks kernel locals ;

[let <lock> :> guard
    guard [ ! exclusive section ! ] with-lock
]
```

Verwende ein Lock immer dann, wenn ein Wert *von mehr als einem Thread gelesen oder geschrieben wird* und die Operationen darauf nicht von Natur aus atomar sind. Sowohl Lese- als auch Schreibzugriffe brauchen das Lock: Ein Lesevorgang, der mittendrin einen Yield macht, kann einen zerrissenen Zustand sehen.

# Über

Der [Call-Stack][stack], oder einfach **Stack**, ist eine spezielle Datenstruktur, die am oberen Ende des Speichers beginnt und nach unten wächst.

## Push und Pop

Der Stack unterstützt mindestens zwei Operationen, mit Befehlen desselben Namens:

| Befehl | Ausgeführte Operation                              |
| ----------- | --------------------------------------------------- |
| `push`      | fügt ein Element zum Stack hinzu                    |
| `pop`       | entfernt das zuletzt hinzugefügte Element und gibt es zurück |

Das bedeutet, dass der Stack eine **Last-in-first-out**-Datenstruktur (LIFO) ist.

Um den aktuellen Punkt des Stacks im Blick zu behalten, an dem sich das zuletzt hinzugefügte Element befindet, wird das Register `rsp` verwendet.

Ein [push][push]-Befehl nimmt also einen Operanden und legt dessen Inhalt auf dem Stack ab.
Da der Stack nach unten wächst, wird der Wert in `rsp` um die Größe des abgelegten Werts verringert.

Ebenso nimmt ein [pop][pop]-Befehl einen Operanden und schreibt den zuletzt abgelegten Wert des Stacks (den, auf den `rsp` zeigt) hinein.
Anschließend wird der Wert in `rsp` um die Größe des entnommenen Werts erhöht.

## Lokale Variablen

Du kannst den Wert von `rsp` auch direkt verändern.
Das wird oft genutzt, um lokale Variablen für eine Funktion anzulegen.

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

Beachte: In dem Moment, in dem Speicherplatz auf dem Stack reserviert wird, ist der dort gespeicherte Wert _undefiniert_.

~~~~exercism/note
Weder `pop` noch das direkte Verändern von `rsp` entfernt tatsächlich die im Speicher abgelegten Inhalte.
Das „Entfernen“ vom Stack wird über die neue Adresse in `rsp` abstrahiert.

In manchen Kontexten kann das Sicherheitsbedenken hervorrufen, weil interne Werte nach außen sichtbar werden.
Eine Möglichkeit, damit umzugehen, ist, den Inhalt jedes von der Funktion genutzten Stack-Bereichs auf null zu setzen.
~~~~

## Call und Ret

Der Hauptzweck des Stacks ist es, die Rücksprungadresse aufgerufener Funktionen zu verwalten.

Wie in einem früheren Konzept erwähnt, gibt es ein spezielles Register namens `rip`, das auf den nächsten auszuführenden Befehl zeigt.
Dieses Register steuert den Ablauf eines Programms und wird von Befehlen wie `jmp` und `call` verändert.

Immer wenn ein `call`-Befehl ausgeführt wird, wird der aktuelle Wert in `rip` implizit auf den Stack gelegt.
Anschließend wird der Operand des Befehls nach `rip` verschoben, sodass die Ausführung in der aufgerufenen Funktion fortgesetzt wird.

Ein `ret`-Befehl macht das Gegenteil.
Er holt einen Wert vom Stack nach `rip`, sodass die Ausführung zur aufrufenden Funktion zurückkehrt.

Beim Eintritt in die Funktion zeigt `rsp` auf die Adresse, zu der zurückgesprungen werden soll.
Das ist die Adresse, die `ret` vom Stack holen muss.

Jede Änderung des Werts von `rsp` innerhalb einer Funktion, ob direkt oder durch `push`, muss also vor der Rückkehr der Funktion rückgängig gemacht werden.

## Callee-saved- und Caller-saved-Register

Neben `rsp` gibt es weitere Register, die über Funktionsaufrufe hinweg erhalten bleiben müssen: `rbp`, `rbx`, `r12`, `r13`, `r14` und `r15`.
Im Allgemeinen erwartet die aufrufende Funktion, diese Register verwenden zu können, ohne dass eine aufgerufene Funktion sie verändert.

Das bedeutet, dass die _aufgerufene_ Funktion die Werte in diesen Registern sichern muss, bevor sie sie verwendet, und sie vor der Rückkehr auf ihre ursprünglichen Werte zurücksetzen muss.
Deshalb heißen sie **Callee-saved-Register**.

Andere Allzweckregister stehen der aufgerufenen Funktion direkt zur Verfügung.

Das bedeutet, dass die _aufrufende_ Funktion die Werte in diesen Registern sichern muss, bevor sie eine Funktion aufruft, falls die aufgerufene Funktion sie verändert.
Deshalb heißen sie **Caller-saved-Register**.

_Der gebräuchlichste Weg, den Inhalt eines Registers zu sichern, ist, ihn auf dem Stack abzulegen._

## Prolog und Epilog

In manchen Fällen wird der Stack stark beansprucht, mit vielen Änderungen, bevor die Funktion zurückkehrt.
Dann kann es aufwendig sein, all diese Änderungen zu verfolgen, um sie rückgängig zu machen.

In solchen Fällen ist eine übliche Strategie, die Adresse von `rsp` in einem anderen Register zu sichern, das innerhalb der Funktion ansonsten unverändert bleibt.
Am Ende, vor der Rückkehr der Funktion, kann der Wert von `rsp` dann mit einem einfachen `mov`-Befehl wiederhergestellt werden.

Obwohl jedes Register dafür verwendet werden kann, ist es üblich, `rbp` als Basiszeiger zu nutzen.
Da `rbp` selbst ein Callee-saved-Register ist, geht dem oft ein `push rbp` voraus.
Diese Sequenz nennt man üblicherweise **Prolog**.

Am Ende wird `rsp` mit `mov rsp, rbp` wiederhergestellt, und danach wird auch `rbp` mit einem `pop` vom Stack wiederhergestellt.
Diese Sequenz nennt man üblicherweise **Epilog**.

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

~~~~exercism/note
Der Hauptzweck der Prolog-/Epilog-Sequenzen ist es, dem Programmierer zu helfen, die Änderungen an `rsp` im Blick zu behalten.
Für einen Compiler ist das natürlich viel einfacher.

Deshalb aktivieren viele Compiler eine Optimierung, die den Frame-Pointer weglässt und Prologe/Epiloge entfernt, wann immer möglich.
~~~~

## Argumente über den Stack übergeben

In der Aufrufkonvention der [System V ABI][SystemV] werden Argumente üblicherweise in Registern an Funktionen übergeben.
Wenn es jedoch zu viele Argumente gibt oder sie mehr als die Größe eines Registers benötigen, kann der Stack verwendet werden.

In diesen Fällen werden Werte in umgekehrter Reihenfolge auf den Stack gelegt, sodass das erste Argument näher an `rsp` liegt.
Da `rsp` beim Eintritt auf die Rücksprungadresse zeigt, die in x86-64 einen 8-Byte-Wert belegt, ist das erste Argument auf dem Stack, falls vorhanden, unter `rsp + 8` erreichbar:

```x86asm
mov rdi, 4   ; first argument
mov rsi, 8   ; second argument
mov rdx, 15  ; third argument
mov rcx, 16  ; fourth argument
mov r8, 23   ; fifth argument
mov r9, 42   ; sixth argument

; any remaining integer argument goes on the stack in reversed order
sub rsp, 16
mov qword [rsp], 100      ; seventh argument
mov qword [rsp + 8], 300  ; eighth argument

call many_arguments_fn ; call implicitly pushes `rip` to the stack
; so, at point of entry, 'many_arguments_fn' finds the first six integer arguments in the usual registers
; the seventh argument is found in rsp + 8
; and the eighth argument is found in rsp + 16
```

## Stack-Ausrichtung

Die System V ABI schreibt vor, dass der Stack unmittelbar _bevor_ der `call`-Befehl ausgeführt wird, auf 16 Byte ausgerichtet sein muss.
Da `call` `rip` auf den Stack legt, ist der Stack beim Eintritt in die aufgerufene Funktion **nicht** auf 16 Byte ausgerichtet.

Das bedeutet, dass eine Funktion, die eine andere aufruft (und insbesondere externe Funktionen), den Stack vor der Verwendung von `call` ausrichten muss.

Das gelingt, indem du einen passenden Wert von `rsp` abziehst.
Beim Eintritt muss dieser Wert 8 mehr als ein Vielfaches von 16 sein: 8, 24, 40 usw.
Da ein `push`-Befehl von `rsp` abzieht, kannst du für denselben Effekt eine ungerade Anzahl von `push` verwenden:

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

## Red Zone

Die System V ABI reserviert einen 128-Byte-Bereich direkt unterhalb von `rsp`, der ohne jede Anpassung von `rsp` genutzt werden kann.
Dieser Bereich ist als [Red Zone][red-zone] bekannt:

```x86asm
fn:
    mov [rsp - 8], rax ; this is safe to use because it is in the red zone
    ret                ; no need to restore rsp
```

Die Red Zone kann nur von einer Blattfunktion sicher genutzt werden, also von einer Funktion, die keine andere aufruft.

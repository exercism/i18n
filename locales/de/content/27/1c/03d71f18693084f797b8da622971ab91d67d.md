# Test-Generator für den Exercism-Python-Track

Der Python-Track verwendet ein Generator-Skript und [Jinja2][Jinja2]-Templates, um
Testdateien aus Exercisms [kanonischen Daten][canonical data] zu erstellen.

## Verwendung des Skripts

Um Tests zu generieren, brauchst du eine lokale Kopie des Repositories
[problem-specifications][problem-specifications]. Du solltest das Skript aus dem
`python`-Wurzelverzeichnis heraus ausführen, damit es korrekt auf die Übungen
zugreifen kann.

Führe `bin/generate_tests.py --help` aus, um Hinweise zur Verwendung zu bekommen.


## Test-Templates

Test-Templates unterstützen die [Jinja2]-Syntax und haben die folgenden
Kontextvariablen aus den kanonischen Daten zur Verfügung:
- `exercise`: Der Name der Übung mit Bindestrichen (z. B. `two-fer`)
- `version`: Die Version der kanonischen Daten (z. B. `1.2.0`)
- `cases`: Eine Liste von Fall-Objekten oder eine Liste von `cases`-Listen. Für die genaue
Struktur der Übung, an der du arbeitest, schau bitte in
`canonical-data.json` nach
- `has_error_case`: Gibt an, ob ein Testfall erwartet, dass ein
Fehler ausgelöst wird (z. B. `False`)
- `additional_cases`: ähnliche Struktur wie `cases`, wird aber aus der Datei `.meta/additional_tests.json` der Übung gefüllt, falls eine existiert (ein Beispiel findest du in `exercises/word-count/.meta/additional_tests.json`)

Zusätzlich gibt es die folgenden Template-Filter, die dir die Arbeit erleichtern:
- `to_snake`: Wandelt einen String in snake_case um (z. B. `{{ "CamelCaseString" | to_snake }}` -> `camel_case_string`)
- `camel_case`: Wandelt einen String in CamelCase um (z. B. `{{ "snake_case_string" | camel_case }}` -> `SnakeCaseString` )
- `error_case`: Prüft, ob ein Testfall erwartet, dass ein Fehler ausgelöst wird (z. B. `{% for case in cases%}{% if case is error_case}`)
- `regex_replace`: Ersetzt Strings per Regex (z. B. `{{ "abc123" | regex_replace("\\d", "D") }}` -> `abcDDD`)


### Konventionen

- Makros für den allgemeinen Gebrauch bei stark wiederholten Template-Strukturen sind in `config/generator_macros.j2` definiert.
  - Du kannst sie so importieren:
  `{%- import "generator_macros.j2" as macros with context -%}`
- Alle Test-Templates sollten mit `{{ macros.footer() }}` enden.
- Alle Python-Klassennamen sollten in CamelCase geschrieben sein (z. B. `TwoFer`).
  - Umwandeln mit `{{ "two-fer" | camel_case }}`
- Alle Python-Modul- und Funktionsnamen sollten in snake_case geschrieben sein
(z. B. `high_scores`, `personal_best`).
  - Umwandeln mit `{{ "personalBest" | to_snake }}`
- Track-spezifische Tests werden in der optionalen Datei `.meta/additional_tests.json` definiert. Das in dieser Datei definierte JSON-Objekt soll
einen einzigen Schlüssel haben, `cases`, der dieselbe Struktur hat wie `cases` in
`canonical-data.json`.
- Track-spezifische Tests sollten in den Testdateien nach den kanonischen Tests
stehen.
- Track-spezifische Tests sollten in der Testdatei mit folgendem Kommentar
markiert werden:
```
# Additional tests for this track
```


### Layout

Die meisten Templates sehen ungefähr so aus:

```Jinja2
{%- import "generator_macros.j2" as macros with context -%}
{{ macros.header() }}

class {{ exercise | camel_case }}Test(unittest.TestCase):
    {% for case in cases -%}
    def test_{{ case["description"] | to_snake }}(self):
        value = {{ case["input"]["value"] }}
        expected = {{ case["expected"] }}
        self.assertEqual({{ case["property"] }}(value), expected)

    {% endfor %}

{{ macros.footer() }}
```


### Imports überschreiben

Die in `macros.header()` importierten Namen kannst du überschreiben, indem du
eine Liste alternativer Namen zum Importieren hinzufügst (z. B. `clock`):

```Jinja2
{{ macros.header(["Clock"])}}
```


### Eigenschaften ignorieren

In seltenen Fällen kann es nötig sein, Eigenschaften herauszufiltern, die
in diesem Track nicht getestet werden. Das Makro `header` akzeptiert außerdem
ein `ignore`-Argument (z. B. `high-scores`):

```Jinja2
{{ macros.header(ignore=["scores"]) }}
```

## Ein Template erstellen

1. Erstelle `.meta/template.j2` für die Übung, die du implementierst,
  und öffne sie in deinem Editor.
2. Kopiere das [Beispiel-Layout](#Layout) in die Template-Datei
  und speichere sie.
3. Nimm die passenden Änderungen an der Template-Datei vor, bis sie
  gültigen Testcode erzeugt, und orientiere dich dabei an der `canonical-data.json` der Übung für
  die Namen der Eingaben und die Struktur der Fälle.
    - Nutze die [verfügbaren Makros](../config/generator_macros.j2), um zu vermeiden, standardisierte Abschnitte neu zu schreiben.
    - Wenn du ein Template für eine bestehende Übung implementierst,
    musst du nicht exakt die Struktur der vorhandenen Testdatei
    übernehmen, aber möglichst wenige Unterschiede machen das Review des PRs für alle Beteiligten zu einem deutlich reibungsloseren Prozess.

# Einführung

## Fehlern Kontext hinzufügen

Die grundlegende Fehlerbehandlung in Go haben wir im [Fehler-Konzept][concept-errors] behandelt.
Wie du dort gelernt hast, tragen Fehler standardmäßig keinen Stacktrace mit sich herum.
Deshalb ist es entscheidend, dass der Fehler selbst genug Informationen enthält, um das Problem zu erkennen.

Wenn wir mit den Werkzeugen, die wir bereits kennen, Informationen zu einem vorhandenen Fehler hinzufügen wollten, könnten wir etwa so einen neuen Fehler erzeugen, der den Text des ursprünglichen Fehlers und die zusätzlichen Informationen kombiniert:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Zum Glück enthält das Paket `fmt` aus der Standardbibliothek dafür eine Kurzform: die Funktion `Errorf`.
Damit kannst du zum Beispiel ganz leicht Informationen über den Kontext hinzufügen, in dem der Fehler aufgetreten ist.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Oft ist diese Art, einem Fehler Informationen hinzuzufügen, völlig ausreichend. Es gibt aber Fälle, in denen du dem Nutzer deines Fehlers erlauben willst, den ursprünglichen zugrunde liegenden Fehler zu prüfen oder abzurufen.
Kontext so hinzuzufügen, dass das möglich ist, nennt man in Go „einen Fehler wrappen“.

## Fehler wrappen und auf Sentinel-Fehler prüfen

Fehler-Wrapping erreicht man mit einer sehr kleinen Änderung am Code von oben.
Um einen Fehler zu wrappen, musst du statt `%v` das Formatierungsverb `%w` verwenden.
Im Hintergrund sorgt das dafür, dass der resultierende Fehler eine `Unwrap`-Methode implementiert, die den ursprünglichen Fehler zurückgibt.
Deshalb kann `errors.Is` dann prüfen, ob ein bestimmter Sentinel-Fehler irgendwo in der „Fehlerkette“ auftaucht.
Das macht es, indem es heimlich immer wieder `Unwrap` aufruft, bis der gesuchte Fehler gefunden wurde oder die Kette endet.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Es ist gute Praxis, standardmäßig `%v` zu verwenden und `%w` nur dann, wenn du dem Nutzer ausdrücklich Zugriff auf einen zugrunde liegenden Fehler gewähren willst ([Google Go Styleguide][google-go-styleguide]).

Wenn du einen Sentinel-Fehler prüfen willst, aber ausdrücklich nicht entpacken möchtest, kannst du statt `errors.Is` `==` verwenden.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Es ist in Ordnung, standardmäßig mit `errors.Is` zu arbeiten, aber dir sollte immer bewusst sein, dass dabei die ganze Fehlerkette durchsucht wird.

## Auf (eigene) Fehlertypen prüfen

Es gibt ein Gegenstück zu `errors.Is`, mit dem du einen Fehler eines bestimmten Typs aus der Fehlerkette prüfen und abrufen kannst.
Die Funktion dafür ist `errors.As`, und genau wie `errors.Is` sucht sie den angegebenen Fehlertyp in der ganzen Kette.
`errors.As` extrahiert den gefundenen Fehler, der zum Typ passt, nur dann, damit du weiter damit arbeiten kannst, z. B. bestimmte Felder abrufen.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Sei vorsichtig mit der Syntax für die Zeiger oben.
Der Code funktioniert und kompiliert nur dann korrekt, wenn `customError` genau den Typ hat, der das error-Interface implementiert.
In unserem Fall ist das `*MyCustomError` (ein [Zeiger][concept-pointers] auf `MyCustomError`) und nicht `MyCustomError` selbst.

Außerdem muss das zweite Argument ein Zeiger auf die Fehlervariable sein.
Da unser Fehler schon ein Zeiger ist, übergeben wir an `errors.As` einen Zeiger auf einen Zeiger (auf MyCustomError).
Nur wenn das korrekt eingerichtet ist, kann Go die Variable mit dem gefundenen Fehler füllen.
~~~~

Wie zuvor würde `errors.As` den Fehlertyp nicht finden, wenn beim Aufruf von `Errorf` `%v` verwendet worden wäre.

Wenn du aus irgendeinem Grund nicht entpacken willst, kannst du stattdessen eine Type Assertion verwenden (entspricht dem `==` von oben).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

Eine Type Assertion kann den Fehlertyp nicht identifizieren, wenn der Fehler gewrappt worden wäre.

## Fehler eigener Typen entpacken lassen

Manchmal reicht es nicht, einen Fehler nur mit etwas zusätzlichem Text zu wrappen.
Stattdessen kannst du einen eigenen Fehlertyp erstellen, der den ursprünglichen Fehler und die zusätzlichen strukturierten Daten enthält, die du hinzufügen willst.
Wenn du das Entpacken für deinen Fehlertyp erlauben willst, musst du nur manuell eine `Unwrap() error`-Methode hinzufügen, damit das `Unwrap`-Interface erfüllt ist.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

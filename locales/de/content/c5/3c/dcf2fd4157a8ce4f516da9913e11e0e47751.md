# Über Nullbarkeit

In einer idealen Welt könnten wir darauf vertrauen, dass alles sauber definiert ist, mit konkreten Werten und ohne Lücken.

Das steht im Widerspruch zu unserer alltäglichen Erfahrung, und deshalb haben viele Programmiersprachen eine Möglichkeit, die Abwesenheit eines Werts darzustellen: null oder NULL, nil, None, nothing...

Das war leicht einzuführen (damals im Jahr 1965), doch schon bald bereute man es.
Der Erfinder nannte es später seinen [„Billion Dollar Mistake“][web-mistake].

In den letzten Jahrzehnten haben Sprachdesigner viele Wege erkundet, Nulls verfügbar, aber (meist) sicher zu machen.

Kotlin hat einige [allgemeine Prinzipien][ref-null-safety], die [sich deutlich von Java unterscheiden][ref-java2kotlin].
_Die Unterschiede bedeuten, dass Kotlin spezielle Funktionalität für die Interoperabilität mit Java hat, doch die Details gehen über den Rahmen dieses Konzepts hinaus._

- Kotlin hat einen speziellen `null`-Wert.
- Alle Typen sind _standardmäßig_ nicht nullbar (d. h. sie können nicht `null` sein).
- Alle Typen können _nullbar_ sein, aber das muss ausdrücklich angegeben werden.
- Funktionen, die mit einer Ausnahme fehlschlagen können, haben oft eine Variante mit einem nullbaren Rückgabewert.
- Eine spezielle, sehr knappe Syntax versucht, das Prüfen auf Nullwerte und den Umgang damit so einfach wie möglich zu machen.

## Nullbare Variablen erzeugen

Ein Typ wird [nullbar][ref-nullable-type], indem du das Suffix `?` anhängst (z. B. `String?` statt `String`).

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Nützliche Operatoren und Funktionen

### Der [Safe-Call-Operator][ref-safe-call] `?.`

Bei einem nicht nullbaren `String` können wir die Eigenschaft `.length` abrufen.

Bei einem nullbaren `String?` schlägt dieselbe Syntax fehl, aber mit `?.length` berücksichtigst du die Möglichkeit eines `null`.
Der Rückgabetyp ist `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Wie wir in der letzten Zeile oben gesehen haben, funktioniert `?.` auch mit nicht nullbaren Typen.

### Der [Elvis-Operator][ref-elvis] `?:`

Der [Elvis-Operator][wiki-elvis] erweitert die Idee des Safe-Call-Operators und lässt uns einen Standardwert angeben, der `null` ersetzt.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### [Not-Null-Assertion-Operator][ref-not-null] `!!`

Mit diesem Operator wird ein nullbarer Typ gezwungen, als nicht null behandelt zu werden, wenn man sich dessen sicher ist.
Vielleicht verstehen wir die Programmlogik manchmal besser als ein übervorsichtiger Compiler?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Die Verantwortung liegt jetzt bei uns: Wenn `b` immer noch `null` ist, bekommen wir eine `NullPointerException`.

### Die [Let-Funktion][ref-let] `?.let`

Wenn wir ein nullbares Element an einen Codeblock übergeben, könnten wir gezielte Null-Prüfungen durchführen: `if (item != null) { do something }`.

Einfacher und idiomatischer ist `item?.let { do something }`.
Das `do something` wird nur ausgeführt, wenn `item` nicht null ist.

### Funktionen der Art `somethingOrNone()`

Manche Funktionen können fehlschlagen, zum Beispiel wenn du einen ungültigen Index in einem String oder einer Liste abfragst.

Statt eine Ausnahme auszulösen, können wir die [`...OrNull`-Variante][ref-elem-at-or-null] der Funktion verwenden und bekommen (in diesem Fall) einen Rückgabewert vom Typ `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

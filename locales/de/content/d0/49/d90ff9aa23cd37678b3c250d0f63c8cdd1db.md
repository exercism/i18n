# Über

Programmierer versuchen normalerweise, perfekte Software zu schreiben, und scheitern normalerweise damit.

Dinge gehen schief, unerwartet, und wir müssen damit umgehen können.

Manche Sprachentwickler sind der Meinung, dass es vor allem darauf ankommt, einen Fehler so schnell wie möglich zu erkennen und die Ausführung dann mit einer aussagekräftigen Meldung zu beenden, die beim Debuggen hilft.

Sprachen für Data Science neigen zu einem differenzierteren Ansatz.
Manche Fehler sind so schwerwiegend, dass die Ausführung sofort beendet werden muss, aber oft ist es besser, ein Problem als etwas zu markieren, das später behandelt wird, und die Ausführung fortzusetzen.

Wir haben im Konzept [Nichts][nothingness] gesehen, dass Julia verschiedene Platzhalter für problematische Werte bereitstellt: [`missing`][nothing], [`NaN`][NaN] und `Inf`.
Ob diese in einer konkreten Situation besser geeignet sind als ein Programmabbruch, muss man als Programmierer selbst beurteilen.

_Eine Frage der Nomenklatur_, bevor wir ins Detail gehen: die Julia-Dokumentation behandelt die Wörter „Fehler" und „Ausnahme" als weitgehend austauschbar.
Der folgende Inhalt ist möglicherweise ebenso inkonsistent.

## Standardfehlertypen

Bis zu diesem Punkt im Lehrplan hast du sicher schon viele Fehlermeldungen von Julia gesehen.
Zum Beispiel:

```julia-repl
julia> Int(3.14)
ERROR: InexactError: Int64(3.14)
```

Der Versuch, eine Gleitkommazahl in eine Ganzzahl umzuwandeln, geht mit einem Genauigkeitsverlust einher, deshalb bekommen wir einen `InexactError`.

`InexactError` ist ein Typ, einer von mehreren ([derzeit 25][errors]), die standardmäßig in Julia eingebaut sind.
Alle sind Untertypen von `Exception`:

```julia-repl
julia> supertype(InexactError)
Exception
```

## `throw()`

Einige der Standardfehlertypen könnten auch in deinem eigenen Code nützlich sein.

Wie alle konkreten Typen haben die Fehler Konstruktoren.
Sie nehmen unterschiedliche Argumente entgegen. Schau also in der [Dokumentation][errors] nach dem Fehler, den du verwenden willst.

```julia-repl
julia> DomainError(42, "out of range")
DomainError(42, "out of range")
```

Um den Fehler zu verwenden, verpackst du den Konstruktor in einen Aufruf der Funktion [`throw()`][throw]:

```julia-repl
julia> throw(DomainError(42, "out of range"))
ERROR: DomainError with 42:
out of range
```

## `error()`

Für eine schnelle, unkomplizierte Lösung ist die Funktion [`error()`][error] praktisch.
Sie nimmt einen String (oder die Bestandteile eines Strings) als Argument entgegen:

```julia-repl
julia> happy = false;
julia> happy || error("😞 something went wrong")
ERROR: 😞 something went wrong
```

## Eigene Fehler

Neue Fehlertypen zu erstellen ist im Prinzip ganz einfach.
Du fügst einfach einen weiteren Untertyp von `Exception` hinzu:

```julia-repl
julia> struct MyError <: Exception end

julia> throw(MyError)
ERROR: MyError
```

Das obige Beispiel hat allerdings keine Felder, und der Konstruktor nimmt keine Argumente entgegen. Wir haben also keine Kontrolle über die Fehlermeldung.
Wir können ein Feld für die Meldung hinzufügen:

```julia-repl
julia> struct AnotherError <: Exception
           msg::String
       end

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError("Wrong!")
```

Den Konstruktor einfach auszugeben, ist noch nicht ganz richtig.
Vergleiche das frühere Beispiel, in dem wir einen `DomainError` ausgelöst haben.

Damit ein eigener Fehler genauso behandelt wird wie eingebaute Fehler, müssen wir eine Methode [`showerror()`][showerror] hinzufügen:

```julia-repl
julia> Base.showerror(io::IO, e::AnotherError) =
           print(io, "AnotherError: ", e.msg)

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError: Wrong!
```

Diese recht schlecht dokumentierte Funktion hängt unseren eigenen Fehlertyp im Wesentlichen in Julias Standard-Fehlerbehandlungssystem ein.

## Assertions

Die Grundidee einer Assertion ist: „Diese Aussage sollte wahr sein, also beschwere dich laut, wenn sie falsch ist."
Der Nutzen liegt vor allem beim Debuggen, denn Produktionscode sollte niemals eine Assertion verletzen.

Wir haben im Konzept [Typen][types] gesehen, dass wir Typ-Assertions hinzufügen können, um zum Beispiel den Rückgabetyp einer Funktion zu prüfen.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Allgemeiner gesagt, mit dem Makro [`@assert`][assert] können wir jeden Ausdruck prüfen, der zu einem booleschen Wert ausgewertet wird:

```julia-repl
julia> n = 22;
julia> @assert isodd(n) "n must be odd"
ERROR: AssertionError: n must be odd
```

## `try`...`catch`

Manche Fehler sind zwangsläufig fatal, aber oft erwarten wir, dass sich das Programm elegant erholt.

Standardmäßig beendet ein Fehler sofort die aktuelle Funktion, und der Fehler (mit einer aussagekräftigen Meldung) wird an die aufrufende Funktion weitergegeben.

Das setzt sich den Aufrufstapel hinauf fort, bis der Code auf oberster Ebene mit einer Fehlermeldung abbricht.

Auf jeder Stufe kann der Fehler mit einem [`try...catch`][try-catch]-Block abgefangen werden, der versucht, ihn zu behandeln.

```julia-repl
julia> n = -1;
julia> try
           log_n = log(n)
       catch problem
           if problem isa DomainError # number out of range
               # See next section for more on @warn and @info
               @warn "you may have supplied a negative real number: $n"
               @info "trying with complex argument"
               log_n = log(Complex(n))  # fallback calculation

           elseif problem isa MethodError # no idea what n is
               @error "please supply a valid argument"
 
           else
              rethrow() # the error could be anything else
           end
      end
┌ Warning: you may have supplied a negative real number: -1
└ @ Main REPL[3]:5
[ Info: trying with complex argument
0.0 + 3.141592653589793im  # success
```

Im obigen Beispiel braucht `log(n)` für `n` entweder einen positiven reellen Wert oder einen beliebigen komplexen Wert.
Das `try ... catch` fängt Probleme mit negativen reellen Werten ab und gibt die korrekte komplexe Antwort `iπ` in mathematischer Schreibweise zurück.

Wenn du zum Beispiel ein String-Argument übergibst, gibt es keine Rettung, außer den Benutzer zu bitten, es zu korrigieren.

Als letzten Auffang für alles, was weder `DomainError` noch `MethodError` ist, haben wir [`rethrow()`][rethrow] hinzugefügt.

Es gibt außerdem weitere optionale Klauseln:

- [`else`][else]: wird ausgeführt, wenn die `try`-Klausel erfolgreich ist;
- [`finally`][finally]: kann zum Aufräumen externer Ressourcen verwendet werden, unabhängig davon, ob `try` erfolgreich ist oder fehlschlägt: Dateien schließen, Datenbankverbindungen trennen ...

***Hinweis:*** Manchmal ist ein `try...catch` genau das, was du brauchst, aber bitte überstrapaziere es nicht.
Wenn stattdessen ein `if...else`-Block verwendet werden kann, ist er deutlich performanter als das Abfangen von Ausnahmen.

## Logging

Beachte, dass die oben besprochene Funktion `error()` nicht mit dem Makro [`@error`][error_macro] verwechselt werden darf.

Die Funktion erzeugt eine Ausnahme, die den Aufrufstapel hinaufgereicht wird, wenn sie nicht abgefangen wird.

Das Makro `@error` ist zusammen mit seinen Gegenstücken [`@debug`][debug_macro], [`@info`][info_macro] und [`@warn`][warn_macro] Teil des Moduls [`Logging`][logging] und soll aussagekräftige Meldungen erzeugen, ohne den Programmablauf zu verändern.

Die Ausgabe geht standardmäßig an das Terminal (nach Schweregrad farbcodiert), in einer echten Anwendung gibt es aber viele weitere Möglichkeiten.

```julia-repl
julia> @warn "Something looks not quite right"
┌ Warning: Something looks not quite right
└ @ Main REPL[55]:1

julia> @error "Panic!"
┌ Error: Panic!
└ @ Main REPL[56]:1
```

Siehe auch das vorherige Beispiel unter `try...catch`.

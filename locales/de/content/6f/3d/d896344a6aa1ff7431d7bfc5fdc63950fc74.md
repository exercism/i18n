# Über

Wie im Konzept [`Nothingness`][concept-nothingness] beschrieben, hat R verschiedene Möglichkeiten, Daten darzustellen, die fehlen ([`NULL`][ref-null]), unbekannt ([`NA`][ref-na]) oder mathematisch ungültig ([`NaN`][ref-finite], [`Inf`][ref-finite]) sind.
Im Allgemeinen versucht R, solche Werte zu verwenden, um Probleme direkt an der Stelle zu kennzeichnen, und läuft weiter, ohne eine Exception auszulösen.

## `stop()`

Manche Probleme sind zu grundlegend, um das Programm weiterlaufen zu lassen.
In diesem Fall verwendest du [`stop(msg)`][ref-stop], um das Programm sofort mit einem `Error` zu stoppen und `msg` auszugeben.

```R
f <- function() {
    stop("I have a problem")
}
f()
#> Error in f() : I have a problem
```

## `stopifnot()`

Ähnlich wie ein [`assert`][wiki-assert] in anderen Sprachen ist [`stopifnot()`][ref-stopifnot] ein praktischer Wrapper für `stop()`.
Die Argumente sind eine beliebige Anzahl boolescher Bedingungen, durch Kommas getrennt, und das Programm läuft nur weiter, wenn alle `TRUE` sind.

```R
stopifnot(1 < 2) # continues OK
stopifnot(1 < 2, 1 == 2)
#> Error: 1 == 2 is not TRUE
```

## `try()`

R hat verschiedene Möglichkeiten, mit Fehlern umzugehen.
Sie basieren auf Common Lisp und unterscheiden sich deutlich von vielen populären Sprachen.

Die einfachste ist, potenziell problematischen Code in [`try()`][ref-try] einzupacken.

```R
g <- function(val) {
  log10(val)
}

g(3)
#> [1] 0.4771213

g("3")
#> Error in log10(val) : non-numeric argument to mathematical function

# with try() and a default value
h <- function(val) {
  result <- NA
  try(result <- log10(val))
  result
}

h(3) # works as before
#> [1] 0.4771213

h("3") # returns a default value plus the error message
Error in log10(val) : non-numeric argument to mathematical function
#> [1] NA
```

## [`warning()`][ref-warning] und [`message()`][ref-message]

Das sind Reaktionen auf nicht fatale Bedingungen, zum Beispiel:

- Um vor einem Problem zu warnen, von dem sich das Programm zumindest teilweise erholen könnte.
- Um den Benutzer über den Fortschritt in einem lang laufenden Programm zu informieren.

Ein Unterschied zwischen ihnen ist, dass Warnungen zwischengespeichert und (standardmäßig) ausgegeben werden, wenn die Funktion zurückkehrt, während Meldungen sofort ausgegeben werden.
Es gibt viele Möglichkeiten, das Standardverhalten zu ändern, was hier den Rahmen sprengt.

```R
w <- function() {
  warning("something strange happened")
  -1
}

w()
#> [1] -1
#> Warning message:
#> In w() : something strange happened

# if warnings are not wanted
suppressWarnings(w())
#> [1] -1
```

Die Funktion [`suppressWarnings()`][ref-warning] kann gelegentlich innerhalb von Exercism nützlich sein, um den Test-Runner nicht mit unerwünschter Ausgabe zu verwirren.

## Condition-Handler

R hat eine alternative Möglichkeit, mit Fehlerzuständen umzugehen, die dem Ansatz von Java und verwandten Sprachen näher steht.

Details gehen über den Rahmen dieses Konzepts hinaus, aber wer interessiert ist, sollte sich [`tryCatch`][ref-conditions] und [`withCallingHandlers`][ref-conditions] ansehen.

Eine gute Erläuterung findet sich in [Abschnitt 8.4][book-handling] von Advanced R.

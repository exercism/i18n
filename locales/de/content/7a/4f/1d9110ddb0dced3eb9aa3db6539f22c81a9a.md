# Zum C-Track beitragen

Danke für dein Interesse, zum C-Track von Exercism beizutragen!
Alle Beiträge sind willkommen, sei es eine neue Übung, eine Änderung an den Tools oder der Dokumentation, ein eröffnetes Issue oder auch nur ein Kommentar zu einem bestehenden Issue oder PR.
Diese Datei enthält Informationen, die dir den Einstieg erleichtern.

Lies zuerst die [Exercism-Dokumentation][Exercism docs], insbesondere die Informationen zum [Beitragen zu einem Sprach-Track][contributing to a language track], denn diese Dokumente decken viele Grundlagen ab.

Beachte außerdem, dass es einige Besonderheiten dieses Repositorys gibt, die weiter unten erklärt werden.

Wir freuen uns über Beiträge, die bestehende Übungen korrigieren und verbessern.
Bitte beachte, dass die Übungen dieses Tracks den Standards entsprechen müssen, die im Repository [problem-specifications][] festgelegt sind.
Änderungen an den Tests oder der Dokumentation einer gemeinsamen Übung erfordern oft einen Pull Request in jenem Repository, bevor sie in die Übungen dieses Tracks übernommen werden können.
Wenn du unsicher bist, eröffne einfach ein GitHub-[Issue][issue] und wir besprechen die Änderung.

## Verhaltenskodex

Hilf uns, Exercism einladend zu halten.
Bitte lies den [Verhaltenskodex][Code of Conduct] und halte dich daran.

## Git-Workflow

1. Forke und klone das Repository.
2. Füge dieses Repository als neues Remote zu deinem Klon hinzu: `git remote add upstream https://github.com/exercism/c.git`
3. Erstelle einen neuen Branch: `git checkout -b name-of-branch`
4. Committe und pushe wie gewohnt auf deinem neuen Branch
5. Wenn du bereit bist, einen Pull Request einzureichen, rebase deinen Branch auf den upstream main, damit du eventuelle Konflikte auflösen kannst: `git fetch upstream && git rebase upstream/main` Nach dem Auflösen von Konflikten musst du deinen Branch möglicherweise mit `--force` pushen.
6. Wenn alles bereit ist, pushe auf deinen Branch und erstelle den Pull Request wie unten beschrieben.

## Issues

Wir erfassen Bugs, Verbesserungen und Support-Anfragen im Repository mithilfe von GitHub-[Issues][issues].

Für übergeordnete Diskussionen über das Projekt als Ganzes schau dir die Issues im Repository [discussions][] an.

### Good First Patch

Wir versuchen, Issues mit „good first patch“ zu kennzeichnen, wenn wir denken, dass sie sich ohne viel Kontext über die Codebasis oder die Funktionsweise von Exercism lösen lassen. Um sie zu finden, kannst du nach [good-first-patch][] suchen.

## Pull Requests

Es wäre großartig, wenn du beim Erstellen deines PR diese einfachen [Pull-Request-Richtlinien][pull request guidelines] befolgst, aber es ist nicht Pflicht.

Ein Pull Request sollte sich auf ein einzelnes Issue oder eine einzelne Änderung konzentrieren.
Änderungen am Code-Stil und an Formulierungen sind willkommen, aber bitte eröffne dafür nach Möglichkeit einen separaten PR.
Bitte eröffne ein Issue, bevor du einen PR erstellst, der wesentliche (brechende) Änderungen an einer bestehenden Übung oder Änderungen über viele Übungen hinweg vornimmt. Am besten besprichst du solche Änderungen, bevor du die Arbeit machst.

Wenn sich deine Änderung auf eine Übung bezieht, kannst du die CI-Skripte vor dem Einreichen des Pull Requests ausführen, oder sie werden danach automatisch ausgeführt, wie unter [Kontinuierliche Integration][Continuous Integration] beschrieben.

Wenn du einen Pull Request einreichst, bitten wir dich manchmal um Änderungen, bevor wir den Patch annehmen.

Bitte schließe nicht den ersten Pull Request und eröffne keinen zweiten mit diesen Änderungen.
Wenn du weitere Commits auf einen Branch pushst, für den du einen Pull Request eröffnet hast, wird der Pull Request automatisch aktualisiert.

Wenn du einen PR mit Änderungen erstellen möchtest, die noch nicht ganz bereit zum Mergen in den main sind (vielleicht möchtest du zum Beispiel einen bestimmten Punkt besprechen), erstelle den PR wie gewohnt, aber nutze die Weboberfläche von GitHub, um [den PR in einen Entwurf umzuwandeln][convert the PR to a draft], damit die Maintainer wissen, dass er noch nicht ganz bereit zum Mergen ist.

Wie beim Hinzufügen weiterer Commits musst du deinen Pull Request nicht schließen und einen neuen öffnen, wenn du die Historie änderst (Rebase, Squash, Amend) und `git push --force` verwendest, um den Branch in deinem Fork zu aktualisieren.
Der Pull Request zeigt auf diesen Branch, nicht auf bestimmte Commits.

## Code-Stil

Der erwartete Code-Stil für Beiträge zu Codeänderungen ist im [Styleguide][style guide] erklärt.

Der Übungscode wird während der [CI][Continuous Integration] auf Übereinstimmung mit den Regeln für Abstände und Einrückung geprüft.
Die Prüfung verwendet das Kommandozeilen-Tool [`clang-format`][clang-format].
Wenn du eine Übung hinzufügst oder anpasst, kannst du prüfen, ob deine Änderung diesen Regeln entspricht, indem du das Tool vor dem Committen lokal ausführst.

Unter Linux sollte `clang-format` über den Paketmanager deiner Distribution installierbar sein.
Auf einem Mac kannst du das Paket `clang-format` mit [Homebrew][] installieren.

clang-format kann für alle Dateien ausgeführt werden, indem du `format.sh` ausführst.
Um es manuell für eine einzelne Datei auszuführen, kannst du Folgendes eingeben:

```bash
clang-format -i $(file)
```

## Aufbau einer Übung

Jede Übung sollte in einem Verzeichnis `c/exercises/practice/{exercise-name}` liegen.
Ausführliche Details zur Umsetzung einer Übung, die der Spezifikation entspricht, findest du unter [eine Übung aus einer Spezifikation implementieren][implement-an-exercise-from-specification]

Die Struktur eines Übungsverzeichnisses sieht so aus (beachte die unterschiedliche Verwendung von Bindestrichen und Unterstrichen für Verzeichnis- bzw. Dateinamen):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - Diese Datei enthält alle Tests für die Übung.  
`test-framework` - Verzeichnis mit dem Test-Harness [Unity][] von [ThrowTheSwitch][].  
  ThrowTheSwitch hat eine ordentliche Anleitung zum [Einstieg mit Unity][getting started with unity], falls du ein Tutorial möchtest.  
  Die verwendete Unity-Version steht in [Versionen][versions]. Der Aufbau der Testdatei ist im [Styleguide][test-file-layout] beschrieben.  
  Die Tests sollten so geschrieben sein, dass sie die Datei `canonical-data.json` für die Übung im Repository [problem-specifications][] erfüllen  
`{exercise-name}.c` / `{exercise-name}.h` - Die Quelldateien der Übung.  
  Bitte verwende [Include Guards][include guards] in deinen Header-Dateien.
  Die Übungstests können mit `make test` aus dem Repository-Stammverzeichnis ausgeführt werden.
* `makefile` - ist das Makefile der Übung, so wie sie gebaut würde.  
Zwei Regeln sind erforderlich,  
test: kompiliert test_{exercise-name}.c und führt es aus.
memcheck: kompiliert test_{exercise-name} mit den Flags -fsanitize=address, -fno-common, -fno-omit-frame-pointer und führt es aus
Makefiles ändern sich zwischen den Übungen erfahrungsgemäß nur sehr wenig, daher sollte es einfach sein, eines von einer anderen Übung zu kopieren.

**Vergiss nicht**, die Übung zur `config.json` des Tracks hinzuzufügen. Dafür musst du die beste Stelle finden, an der die Übung in der Reihenfolge aller anderen Track-Übungen stehen soll. Außerdem musst du eine UUID generieren, die du hier hinzufügst. Für beide Aufgaben kannst du das Tool [configlet][] verwenden; das Tool lintet und formatiert die `config.json` sogar für dich, nachdem du diese Änderungen vorgenommen hast!

Übrigens: Um das Installationsartefakt für das configlet-Tool zu bekommen, schau dir die [configlet-Releases-Seite][configlet releases page] an.

## Kontinuierliche Integration

Dieses Repository verwendet GitHub-Workflows, um bei jedem Commit zu einem Pull Request einige Tools auszuführen.
Der einfachste Weg, diese Workflows für deinen eigenen Beitrag auszuführen, ist, einen PR mit deinen Änderungen in diesem Repository zu eröffnen, den PR als Entwurf zu markieren und dann die CI-Einrichtung dieses Repositorys die Dinge automatisch für dich erledigen zu lassen.

### CI-Umgebung

GitHub führt die CI auf virtuellen Maschinen aus, die es als [gehostete Runner][hosted runners] bezeichnet.
Workflows können einige Aspekte der Runner festlegen, auf denen sie laufen sollen.

Die Workflows in diesem Repository legen nur fest, dass sie jeweils auf Ubuntu 24.04 ausgeführt werden sollen. Die Workflows sind auf bestimmte Versionen festgelegt und verweisen nicht auf `latest`, da sich einige verwendete Tools bei unterschiedlichen Versionen anders verhalten können.

### CI im eigenen Fork ausführen

Wenn du möchtest, kannst du die CI auch in deinem eigenen Fork ausführen: Klone dieses Repository einfach wie üblich auf GitHub.
Die YAML-Dateien unter [`./.github/workflows/`][workflows] sollten genauso funktionieren.
Wenn du möchtest, dass die automatisierte Action [`/format`][format-workflow] korrekt funktioniert, musst du deinem geklonten Repository einen Deploy-Key hinzufügen.

### Die Workflows

* `checks.yml` führt `shellcheck` für die Tool-Skripte aus und ruft anschließend die folgenden dieser Tools auf:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * die Action [Lychee Link Checker][lychee]
* `configlet.yml` lädt die neueste Version von configlet herunter und führt damit dann den Befehl `lint` für den Track aus
* `format-code.yml` sucht in jedem Kommentar eines PR nach der Zeichenkette `/format`. Wird sie gefunden, wird `format.sh` für die Übungen ausgeführt und alle daraus entstehenden Änderungen werden committet. Ein Deploy-Key ist erforderlich, damit der Commit die CI erneut auslösen kann. Der Deploy-Key wird direkt von Exercism verwaltet.
* `test.yml` führt `make` im Repository-Stammverzeichnis aus, um alle Übungen zu testen

### Die Tools

Du siehst an den [Workflows][workflows], dass GitHub angewiesen wird, Tools aus dem Verzeichnis [`./bin`][bin] auszuführen.
Die Arbeit, die die Tools in diesem Verzeichnis erledigen, wird wie folgt beschrieben:

* `check-unitybegin` stellt sicher, dass jede Testdatei die Zeile `UNITY_BEGIN()` korrekt am Anfang ihrer Funktion `main()` hinzufügt.
* `fetch-configlet` lädt das Tool `configlet` aus seinem [Repository][configlet] herunter.
* `verify-unity-version` prüft die Version des Unity-Testframeworks, die jede Übung verwendet. Die Version, die diese Datei prüfen soll, ist in [`./docs/VERSIONS.md`][versions] angegeben
* `check-include-guards` prüft, dass die in jedem Übungs-Stub und Beispiel-Header verwendeten Include Guards das korrekte Format verwenden, und zwar wie folgt:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` lädt das Tool `configlet` aus seinem [Repository][configlet] herunter.

### Tools lokal ausführen

Du kannst einzelne Tools auch auf deinem eigenen Rechner ausführen, bevor du committest.
Stelle zuerst sicher, dass die nötigen Anwendungen installiert sind (wie `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] und ein C-Compiler), und führe dann das gewünschte Tool aus dem Repository-Stammverzeichnis aus. Zum Beispiel:

```bash
~/git/c$ make
```

Wenn du nur einige der Tests ausführen möchtest, um deine Arbeit zu prüfen, kannst du sie als Ziele für make angeben.

```bash
~/git/c$ make acronym all-your-base allergies
```

Dieser Track hat einen Test-Runner für Exercism v3!

Dieser Docker-Ansatz ermöglicht Lernenden das Programmieren im Browser.

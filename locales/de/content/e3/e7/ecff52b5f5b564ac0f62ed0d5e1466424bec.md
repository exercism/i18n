# Einführung

Es ist oft nützlich, in unseren Programmen eigene Typen zu definieren.

Es ist möglich, neue primitive Typen zu erstellen, aber das wird selten gemacht.
Die eingebauten primitiven Typen sind keine willkürliche Wahl: Sie entsprechen weitgehend den Standardtypen im LLVM-Compiler, den Julia für die JIT-Kompilierung verwendet.

Deutlich nützlicher ist die Möglichkeit, zusammengesetzte Typen mit benannten Feldern zu definieren.

Andere Sprachen haben etwas Ähnliches und nennen sie `structs` oder `records`.
Die Julia-Dokumentation nennt sie `composite types`, obwohl die Sprachsyntax sie (eine kleine Ungenauigkeit) mit dem Schlüsselwort `struct` definiert.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Ein paar Punkte im obigen Beispiel sind erwähnenswert:

- Für `id` ist kein Typ angegeben, daher interpretiert der Compiler das als `id::Any`.
  - In der Praxis ist es am besten, dem Compiler zu helfen, indem du den Typ eines Felds mit einem konkreten Typ angibst
- Der Typname wird als Konstruktor verwendet, wie in `Person(id, name, age)`, um ein Exemplar vom Typ `Person` zu erzeugen.
- Auf einzelne Felder kannst du mit der Punktnotation zugreifen, genau wie bei benannten Tupeln.

Exemplare vom Typ `Person` sind unveränderlich, Änderungen sind also nicht erlaubt.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Wenn Veränderbarkeit nötig ist, füge `mutable` zur Definition hinzu.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Der Konstruktor verlangt standardmäßig, dass die Felder in derselben Reihenfolge wie in der Definition erscheinen, was bei komplizierteren Typen unpraktisch wird.

Mit dem Makro `@kwdef` kommen zwei neue Möglichkeiten hinzu:

- Der Konstruktor verwendet Schlüsselwörter statt Positionen.
- Felder können Standardwerte haben und im Konstruktor optional weggelassen werden.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarchien zusammengesetzter Typen

Bisher haben wir nur konkrete zusammengesetzte Typen erstellt.
Wenn du nachprüfst, sind alle Untertypen von `Any`.

Wenn du mehrere verwandte Typen erstellst, ist es wahrscheinlich sinnvoller, eine Hierarchie für sie zu definieren.
Das ist ganz einfach.

Erstelle zuerst einen abstrakten Typ:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Füge als Nächstes einen `<:`-Operator in eine Typdefinition ein, um die Beziehung anzuzeigen.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Wiederhole das nach Bedarf, und denke daran, dass die Untertypisierung konkreter Typen nicht erlaubt ist.

Für eine komplexere Hierarchie erstelle bei Bedarf abstrakte Untertypen.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

Der Nutzen einer solchen Hierarchie wird klarer, wenn wir zum Konzept `Multiple Dispatch` gelangen und sehen, wie Funktionen mit Argumenttypen umgehen.

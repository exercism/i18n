# Über

Eine Funktion ist [tail-rekursiv][recursion-tc], wenn das _Letzte_, was die Funktion ausführt, ein Aufruf ihrer selbst ist.

Jedes Mal, wenn eine Funktion aufgerufen wird, wird ein _Stackframe_ mit ihren lokalen Variablen und Argumenten oben auf [den Funktionsaufrufstapel][call-stack] gelegt.
Wenn eine Funktion zurückkehrt, wird der Stackframe wieder vom Stack entfernt.

Tail-rekursive Funktionen ermöglichen die [Tail-Call-Optimierung][tail-call-optimization] (oder Tail-Call-Eliminierung).
Das ist eine Optimierung, bei der der nächste Funktionsaufruf den letzten Stackframe wiederverwenden kann, wenn sicher ist, dass die vorherige Funktion ihn nicht mehr braucht.
Damit musst du dir keine Sorgen mehr machen, dass der Funktionsaufrufstapel überläuft. Das passiert, wenn so viele Frames auf dem Aufrufstapel liegen, dass kein Speicher mehr bleibt, um einen weiteren anzulegen.

## Tail-Call-Optimierung in Elm

Unter bestimmten Bedingungen kann der Elm-Compiler beim Kompilieren nach JavaScript automatisch eine Tail-Call-Optimierung durchführen.

Die Optimierung kann bei einer rekursiven Funktion stattfinden, wenn die _letzte_ Operation in einem Zweig darin besteht, die Funktion selbst in einer einfachen Funktionsanwendung aufzurufen.
Schauen wir uns ein paar Beispiele an:

```elm
factorial : Int -> Int
factorial n =
  if n <= 1 then
    n
  else
    n * factorial (n-1)
```

Die obige Implementierung ist nicht tail-rekursiv, denn die letzte Operation im `else`-Zweig ist eine Multiplikation `n *`.

```elm
factorial : Int -> Int
factorial n =
  factorialHelper n n

factorialHelper : Int -> Int -> Int
factorialHelper n resultSoFar =
  if n <= 1 then
    resultSoFar
  else
    factorialHelper (n-1) (n * resultSoFar)
```

Die obige Implementierung ist tail-rekursiv und wird optimiert, denn die letzte Operation im `else`-Zweig ist, dass `factorialHelper` sich selbst aufruft.
Für eine Funktion mit der Typsignatur `Int -> Int` wäre das nicht möglich, und in der Praxis erreicht man die Tail-Call-Optimierung oft, indem man Hilfsfunktionen definiert.

## Randfälle

In manchen Fällen kann der Compiler rekursive Funktionen nicht optimieren. Schauen wir uns ein paar Beispiele an.

`f x = f (x - 1)` ist zwar tail-rekursiv, `f x = (x - 1) |> f` jedoch nicht, denn die Funktionsanwendung `|>` ist die letzte Operation und gilt als getrennt von `f`.
Ebenso sind Funktionen, die mit einer booleschen Bedingung enden, wie `f x = x > 0 || f (x - 1)`, nicht tail-rekursiv.

Die Funktion `f x = if f (x - 1) then 1 else 0` ist nicht tail-rekursiv, denn der Ausdruck im `if` gilt nicht als Zweig.
Ebenso würde ein rekursiver Aufruf in einer `case`-Anweisung nicht optimiert.

Die Funktion `f x = let y = f (x - 1) in y` ist nicht tail-rekursiv, weil sie sich selbst in einer `let`-Anweisung aufruft, die nicht als Zweig gilt.
In `f x = let g x = g (x - 1) in g x` ist die Funktion `g` dagegen tail-rekursiv und wird optimiert, obwohl sie in einer `let`-Anweisung definiert ist.

Die Funktion `f x = if x > 0 then f (x + 1) else 1 + f x` wird _teilweise_ optimiert: der `then`-Zweig kann optimiert werden, der `else`-Zweig nicht.
Die teilweise Optimierung ist in manchen Situationen das Beste, was möglich ist, etwa beim Durchlaufen baumartiger Strukturen oder beim Definieren ko-rekursiver Funktionen.

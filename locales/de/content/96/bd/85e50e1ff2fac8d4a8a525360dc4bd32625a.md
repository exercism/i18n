# Einführung

In einer idealen Welt könnten wir uns darauf verlassen, dass alles schön definiert ist, mit konkreten Werten und ohne Lücken.

Das widerspricht unserer alltäglichen Erfahrung, und deshalb haben viele Programmiersprachen eine Möglichkeit, die Abwesenheit eines Werts darzustellen: null oder NULL, nil, None, nothing ...

Das war (damals 1965) einfach einzuführen, führte aber schon bald zu Bedauern.
Der Erfinder nannte es später seinen „Milliarden-Dollar-Fehler“.

In den letzten Jahrzehnten haben Sprachdesigner viele Wege erkundet, Nullwerte verfügbar, aber (meist) sicher zu machen.

Kotlin hat einige [allgemeine Prinzipien][ref-null-safety], die sich deutlich von Java unterscheiden.


- Kotlin hat einen besonderen Wert `null`.
- Alle Typen sind _standardmäßig_ nicht-nullable.
- Die meisten Typen können nullable _gemacht_ werden, aber der Programmierer muss das ausdrücklich veranlassen.
- Funktionen, die mit einer Exception fehlschlagen können, haben oft eine Variante mit einem nullable Rückgabewert.
- Eine besondere, sehr knappe Syntax versucht, das Prüfen auf Nullwerte und das Reagieren darauf so einfach wie möglich zu machen.

## Nullable Variablen erstellen

Standardtypen haben in der Regel ein nullable Gegenstück mit dem Suffix `?`: zum Beispiel `String?` statt `String`.

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Nützliche Operatoren und Funktionen

### Der Safe-Call-Operator `?.`

Für einen nicht-nullable `String` können wir die Eigenschaft `.length` abrufen.

Ein nullable `String?` schlägt mit derselben Syntax fehl, aber mit `?.length` berücksichtigen wir die Möglichkeit eines `null`.
Der Rückgabetyp ist `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Wie wir in der letzten Zeile oben gesehen haben, funktioniert `?.` auch mit nicht-nullable Typen.

### Der Elvis-Operator `?:`

Der [Elvis-Operator][wiki-elvis] erweitert die Idee des Safe-Call-Operators und lässt uns einen Standardwert angeben, der `null` ersetzt.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### Der Not-Null-Assertion-Operator `!!`

Mit diesem Operator wird ein nullbarer Typ gezwungen, als nicht-null behandelt zu werden, wenn der Programmierer sich dessen sicher ist.
Vielleicht verstehen wir die Programmlogik manchmal besser als ein übervorsichtiger Compiler?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Die Verantwortung liegt jetzt bei uns: Wenn `b` immer noch `null` ist, bekommen wir eine `NullPointerException`.

### Die Let-Funktion `?.let`

Wenn wir ein nullbares Element an einen Block übergeben, könnten wir gezielte Null-Prüfungen durchführen: `if (item != null) { do something }`.

Einfacher und idiomatischer ist `item?.let { do something }`.
Das `do something` wird nur ausgeführt, wenn `item` nicht null ist.

### Funktionen vom Typ `somethingOrNone()`

Manche Funktionen können fehlschlagen, zum Beispiel wenn man einen ungültigen Index in einem String oder einer Liste abfragt.

Statt eine Exception zu werfen, könnten wir die `...OrNull`-Variante der Funktion verwenden, um (in diesem Fall) einen Rückgabewert vom Typ `Int?` zu bekommen.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

# Von Travis migrieren

Hier ist ein Beispiel für eine `.travis.yml` (aus dem `elm`-Track):

```yml
sudo: false
language: node_js
node_js:
  - lts/*
script:
  - bin/fetch-configlet
  - bin/configlet lint
  - bin/build.sh
```

Um das schnell in GitHub Actions umzuwandeln, gehst du so vor:

## Die Vorlagenvariablen ermitteln

| Variable                    | Wert                                 |
| --------------------------- | ------------------------------------ |
| `<track>`                   | `elm`                                |
| `<image-name>`              | `ubuntu-latest`                      |
| `<action to setup tooling>` | `actions/setup-node@v1`              |
| `<install dependencies>`    | `npm ci` (geschieht in `build.sh`)   |
| `<code-extensions>`         | `.elm`                               |

> Die Setup-Action habe ich über [diese Suche](https://github.com/actions/?q=setup+node&type=&language=) gefunden.
> Den Namen des Images habe ich [der Standard-Distribution für Travis](https://blog.travis-ci.com/2019-04-15-xenial-default-build-environment) entnommen.

## Die Schritte ermitteln

- `bin/fetch-configlet`: brauchst du nicht mehr, wenn du den [`configlet.yml`][workflow-template-configlet-yml]-Workflow verwendest
- `bin/configlet lint`: brauchst du nicht mehr, wenn du den [`configlet.yml`][workflow-template-configlet-yml]-Workflow verwendest
- `bin/build.sh`: ein einzelnes Skript, das alles erledigt

## Die „scripts“ vorbereiten

Dieser Track verwendet den `bin`-Ordner. Erstelle also im `bin`-Ordner die folgenden Dateien:

```bash
# bin/pr
bin/build.sh
```

```bash
# bin/pr-check
echo "No checks yet"
```

```bash
# bin/ci
bin/build.sh
```

```bash
# bin/ci-check
echo "No checks yet"
```

Wenn du diese als _getrennte_ Binärdateien anlegst, kannst du später optimieren. Im Moment musst du noch nichts inline einbauen.

## Jetzt sollte es funktionieren

Das reicht aus, um auf GitHub Actions umzusteigen, und du kannst deine Skripte später optimieren.

1. Entferne aus `build.sh` die Schritte, die nur einmal laufen sollten, und verschiebe sie in die Dateien `ci-check.sh` und `pre-check.sh` (Tipp: Du kannst `lint.sh` anlegen und aus beiden „Scripts“ aufrufen).
2. Füge in `pr.sh` und `pr-check.sh` Optimierungen hinzu, die anhand der Eingabeargumente bestimmen, welche Dateien oder Übungen geprüft werden.
3. Füge zusätzliche Prüfungen hinzu.
4. Dokumentiere, wie du die Prüfungen lokal ausführst und was jede einzelne erreichen soll.

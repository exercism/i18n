# Überblick

## Fehler in `jq`

`jq` unterscheidet zwei grobe Fehlerkategorien:

1. **Kompilierfehler**: Das Programm selbst ist ungültig: Syntaxfehler, Verweise auf nicht definierte Funktionen oder Variablen und so weiter.
   `jq` weigert sich, das Programm überhaupt auszuführen.

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **Laufzeitfehler**: Das Programm ist gültig, aber bei der Verarbeitung eines Werts geht etwas schief: eine Zahl mit einem String indizieren, ungültigen JSON-Text mit `fromjson` parsen, eine Funktion mit Argumenten des falschen Typs aufrufen und so weiter.

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

In diesem Konzept geht es um **Laufzeitfehler**: wie du sie auslöst, wie du sie abfängst und wie du das Programm anhältst.

Ein nicht abgefangener Laufzeitfehler führt dazu, dass `jq` eine Meldung auf der _Standardfehlerausgabe_ ausgibt und mit Status `5` beendet wird.

## Fehler auslösen: `error` und `error(message)`

Der Filter [`error`][man-error] löst einen Fehler aus.

- `error` löst einen Fehler aus, dessen Wert der **Eingabewert** ist.
- `error(message)` löst einen Fehler aus, dessen Wert das Ergebnis von `message` ist.

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
Der Fehlerwert kann _jeder_ JSON-Wert sein, nicht nur ein String.
Strukturierte Fehler zu erzeugen ermöglicht es einem `catch`-Handler, Entscheidungen anhand des Inhalts des Fehlers zu treffen.

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

Wenn ein Fehlerwert, der kein String ist, nicht abgefangen wird, gibt `jq` ihn als JSON aus und versieht ihn mit dem Hinweis `(not a string)`.

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## Fehler abfangen: `try` und `catch`

Fehler lassen sich mit [`try EXP catch HANDLER`][man-try-catch] abfangen.
Der erste Ausdruck wird ausgeführt; löst er einen Fehler aus, wird der Ausdruck `HANDLER` **mit dem Fehlerwert als Eingabewert** ausgeführt.
Die Ausgabe des Handlers wird so ausgegeben, als wäre sie die Ausgabe des Ausdrucks gewesen, der in `try` ausgeführt wurde.

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

Die kürzere Form `try EXP` entspricht `try EXP catch empty`: Der Fehler wird verworfen und es wird keine Ausgabe erzeugt.

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
Ein Fehler **bricht den Rest des Streams** innerhalb von `try` ab.
Bereits erzeugte Werte bleiben erhalten, aber nichts nach dem Fehler wird ausgewertet.

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

Ein Handler kann einen neuen Fehler auslösen oder den ursprünglichen mit einem einfachen `error` erneut auslösen. Da der Fehlerwert die Eingabe des Handlers ist, wird er dabei unverändert weitergegeben.

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## Fehler unterdrücken: der `?`-Operator

Der [`?`-Operator][man-question-mark], in der Form `EXP?` verwendet, ist eine Kurzform für `try EXP`.
Er verwandelt einen fehlschlagenden Ausdruck in einen, der einfach keine Ausgabe erzeugt.

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

Man sieht ihn oft an den Indexoperatoren:

- `.foo?` ist `.["foo"]?`
- `.[]?` iteriert nur, wenn die Eingabe ein Array oder Objekt ist, und ist ansonsten leer

~~~~exercism/caution
`?` unterdrückt **jeden** Fehler, auch solche, die du nicht erwartet hast.
`user.name?` erzeugt stillschweigend nichts, wenn `user` kein Objekt ist. Dadurch können Datenprobleme oder Tippfehler in deinem Programm verborgen bleiben.
Bevorzuge `try ... catch`, wenn du wissen musst, _dass_ etwas fehlgeschlagen ist, oder validiere die Eingabe ausdrücklich.
~~~~

## Der Alternativoperator `//`

Programmierer erwarten manchmal, dass `a // b` `b` liefert, wenn `a` fehlschlägt.
In alten Versionen von `jq` war das so, seit `jq` 1.6 aber nicht mehr.
Der Operator `//` unterdrückt keine Fehler.
Er setzt `b` nur dann ein, wenn `a` keinen Wert, `false` oder `null` erzeugt; Fehler in `a` werden weiterhin weitergereicht.

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

Verwende `try a catch b`, wenn du einen Fallback für Fehler möchtest.

## Der Alternativoperator `?//` zum Destrukturieren

Der [`?//`-Operator][man-question-mark-slash-slash] kombiniert Destrukturierung mit Fehlerbehandlung.
Er probiert nacheinander jedes Bindungsmuster aus, bis eines erfolgreich ist; Variablen, die von den fehlschlagenden Alternativen gebunden wurden, werden auf `null` gesetzt.

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

Hier erwartet das erste Muster, dass `c` ein _Objekt_ mit den Schlüsseln `d` und `e` ist, während das zweite erwartet, dass `c` ein _Array_ ist, das ein solches Objekt enthält.
Das erste Eingabeelement wird mit dem ersten Muster gebunden; das zweite Element erfüllt dieses Muster nicht, also wird stattdessen das zweite Muster ausprobiert.

Dadurch kann ein einzelnes Programm Eingaben destrukturieren, die eine von mehreren Formen annehmen können, ohne explizite `if type == ...`-Ketten zu schreiben.

## Das Programm anhalten: `halt` und `halt_error`

Manchmal ist die richtige Reaktion auf einen Fehler, die Verarbeitung ganz zu stoppen.

- [`halt`][man-halt] beendet das `jq`-Programm sofort ohne weitere Ausgabe; der Exit-Status ist `0`.
- [`halt_error`][man-halt-error] beendet das Programm, gibt seine **Eingabe** als Rohtext auf der _Standardfehlerausgabe_ aus (ohne Ausschmückung, nicht einmal mit einem abschließenden Zeilenumbruch) und beendet das Programm mit dem angegebenen Status, standardmäßig `5`.

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

Beachte, dass diese Filter das Programm sofort anhalten, selbst wenn noch weitere Eingaben gelesen werden müssen.

### Exit-Status

Zur Orientierung verwendet `jq` diese Exit-Status:

| Status | Bedeutung                                        |
| :----: | ------------------------------------------------ |
| `0`    | Erfolg                                           |
| `2`    | Nutzungsfehler (ungültige Kommandozeilenoptionen) |
| `3`    | Kompilierfehler                                  |
| `5`    | Laufzeitfehler (oder `halt_error` ohne Argument) |

Mit der Option `--exit-status` / `-e` spiegelt der Status stattdessen den letzten Ausgabewert wider: `0` für `true` oder Zahlen, `1` für `false` oder `null`, `4` für keine Ausgabe.

## Debugging-Hilfsmittel

Wenn du herausfinden willst, woher ein Fehler kommt, helfen dir diese Filter:

- [`debug`][man-debug] reicht seine Eingabe unverändert weiter, gibt aber `["DEBUG:", <input>]` auf der Standardfehlerausgabe aus.
  `debug(msgs)` gibt außerdem `msgs` als Debug-Meldungen aus.
- [`stderr`][man-stderr] gibt seine Eingabe roh und kompakt auf der Standardfehlerausgabe aus.
- [`input_line_number`][man-input-line-number] gibt die Zeilennummer der Eingabe aus, die gerade gefiltert wird. Das ist von unschätzbarem Wert, wenn eine Datei viele JSON-Texte enthält und einer davon fehlerhaft ist.
- [`$__loc__`][man-loc] gibt ein Objekt mit den Schlüsseln `file` und `line` aus, das beschreibt, wo im Programm es vorkommt; dieses Objekt kann in Fehlermeldungen eingebettet werden.

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

# Test-Generatoren

Mit Test-Generatoren können Tracks Tests automatisch generieren, ohne dass wir sie selbst schreiben müssen. Jeder Test-Generator liest die `canonical data` der Übung ein, die den Namen des Tests, seine Eingaben und Ausgaben definiert. Mehr über den Ansatz von Exercism bei Testsuiten findest du [hier](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Wenn du Tests automatisch generierst, schließt das jegliche Anwenderfehler beim Erstellen von Tests aus. Die Tests sollen in Bezug auf die kanonischen Daten korrekt sein. Die Testgenerierung macht es außerdem viel einfacher, die Tests aktuell zu halten. Wenn sich die kanonischen Daten ändern, werden die Tests automatisch aktualisiert, sobald der Generator für diesen Test ausgeführt wird.

Ein Beispiel für eine Datei mit kanonischen Daten findest du [hier](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)

## Häufige Begriffe

Wenn du die kanonischen Daten und den Generator-Code durchgehst, stößt du auf viele wiederkehrende Begriffe. Diese Liste soll klären, wofür sie stehen.

* Kanonische Daten - Stehen für die gesamte Testsuite.
* Fall der kanonischen Daten - Die Darstellung eines einzelnen Testfalls.
* Beschreibung - Der Name des Tests.
* Eigenschaft - Die Methode, die beim Ausführen des Tests aufgerufen wird.
* Eingabewert - Die Eingabe für den Testfall.
* Erwarteter Wert - Der erwartete Wert beim Ausführen des Testfalls.

## Einen einfachen Generator hinzufügen

Einen Test-Generator hinzuzufügen ist unkompliziert. Füge einfach in der Datei `Generators.fs` im Ordner `generators` eine Klasse mit dem Namen der Übung (in PascalCase) hinzu und erweitere die abstrakte Klasse `GeneratorExercise`.

Ein Beispiel für einen einfachen Generator ist die Übung Bob. Den Quellcode findest du unten, du kannst ihn dir aber auch im Repository [hier](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174) ansehen.

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

Das ist ein voll funktionsfähiger Generator, es muss kein weiterer Code geschrieben werden. Seine Einfachheit kommt jedoch daher, dass die Testsuite und das Programm selbst relativ trivial sind.

## Einen komplexen Generator hinzufügen

Bei vielen Generatoren reicht das Standardverhalten der Klasse `GeneratorExercise` aus. Bei _komplexeren_ Generatoren kannst du jedoch eine oder mehrere ihrer virtuellen Methoden überschreiben:

### Methode: RenderInput

Rendert die Eingabe einer Testmethode.

#### Beispiel

Der Generator `Gigasecond` rendert den Eingabewert als (eingeklammerten) `DateTime`-Wert:

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

Beachte, dass du das Feld `key` verwenden kannst, um die Ausgabe nur für bestimmte Eingabefelder anzupassen. Der Generator `Yacht` macht das:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Methode: RenderExpected

Rendert den erwarteten Wert einer Testmethode.

#### Beispiel

Der Generator `Connect` rendert den erwarteten Wert als `Option<T>`-Wert:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Methode: RenderSut

Rendert das System Under Test (SUT). Das ist der tatsächliche Wert, der gegen den erwarteten Wert geprüft wird.

#### Beispiel

Der Generator `RunLengthEncoding` hat einen Testfall, in dem geprüft wird, dass das Kodieren und anschließende Dekodieren der Eingabe denselben Wert ergibt. Die Methode `RenderSut` wird überschrieben, um das, was ein einzelner Aufruf einer nicht existierenden Funktion `consistency` wäre, in eine Kette von `encode |> decode`-Aufrufen umzuwandeln:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Methode: RenderArrange

Rendert den Arrange-Teil der Testmethode. In diesem Teil wird das SUT erzeugt.

Das Standardverhalten ist meistens genau das, was du willst. Nur in ganz besonderen Fällen solltest du es ändern.

Hinweis: Diese Methode gibt eine `string list` zurück, wobei jedes `string` einer einzelnen gerenderten Zeile in der Testdatei entspricht.

### Methode: RenderAssert

Rendert den Assert-Teil der Testmethode. In diesem Teil wird die Assertion ausgeführt, um das SUT gegen den erwarteten Wert zu prüfen.

Das Standardverhalten ist meistens genau das, was du willst. Nur in ganz besonderen Fällen solltest du es ändern.

Hinweis: Diese Methode gibt eine `string list` zurück, wobei jedes `string` einer einzelnen gerenderten Zeile in der Testdatei entspricht.

### Methode: RenderSetup

Rendert alle zusätzlichen Hilfs- oder Setup-Methoden. Damit kannst du Hilfsmethoden definieren, die in den Testmethoden verwendet werden können.

Der Setup-Code wird _vor_ den Testmethoden eingefügt, damit die Setup-Methoden in den Testmethoden verwendet werden können.

Hinweis: Diese Methode gibt eine `string list` zurück, wobei jedes `string` einer einzelnen gerenderten Zeile in der Testdatei entspricht.

#### Beispiel

Der Generator `Zipper` fügt zwei Hilfsmethoden hinzu, die in den Testmethoden verwendet werden, um etwas lästigen Boilerplate-Code loszuwerden:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Methode: RenderValue

Rendert einen einzelnen Wert (der verwendet wird, um Eingabeparameter, den erwarteten Wert und das SUT zu rendern).

### Beispiel

Der Generator `ComplexNumbers` rendert verschiedene Werte, je nach Typ des Werts:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Methode: MapCanonicalDataCase

Ordnet den Fall der kanonischen Daten zu. Das kann nützlich sein, wenn du Eigenschaften hinzufügen oder entfernen möchtest.

Das Standardverhalten ist meistens genau das, was du willst. Nur in ganz besonderen Fällen solltest du es ändern.

#### Beispiel

Der Generator `ScaleGenerator` nutzt die Zuordnung des Falls der kanonischen Daten, um eine fehlende Eigenschaft als `null`-Wert hinzuzufügen (was die spätere Verarbeitung erleichtert):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Methode: PropertiesUsedAsSutParameter

Legt fest, welche Eigenschaften als Parameter für das SUT verwendet werden sollen.

Das Standardverhalten ist meistens genau das, was du willst. Nur in ganz besonderen Fällen solltest du es ändern.

#### Beispiel

`RailFenceCipher` definiert die als SUT-Parameter verwendeten Eigenschaften explizit, um die Reihenfolge zu ändern, in der sie übergeben werden:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Methode: PropertiesWithIdentifier

Legt fest, welchen Eigenschaften ein Bezeichner zugewiesen werden soll. Steht eine Eigenschaft in dieser Liste, wird ihr Wert in einer separaten Zeile ihrem eigenen Bezeichner zugewiesen.

#### Beispiel

Der Generator `Transpose` hat sich dafür entschieden, für alle Eigenschaften Bezeichner zu verwenden:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Methode: IdentifierTypeAnnotation

Manchmal möchtest du, dass ein Bezeichner einen expliziten Typ hat. Ein häufiger Anwendungsfall ist ein Wert, der eine leere Liste ist. In dem Fall braucht FsUnit eine Typannotation, damit es die Assertion erfolgreich ausführen kann.

#### Beispiel

Der Generator `Minesweeper` fügt für leere Werte eine Typannotation `string list` hinzu:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Methode: AdditionalNamespaces

Gibt eine Liste zusätzlicher Namespaces zurück, die in der Testdatei geöffnet werden sollen.

#### Beispiel

Der Generator `Gigasecond` arbeitet mit `DateTime`-Instanzen und fügt deshalb seinen Namespace zur Liste der zusätzlichen Namespaces hinzu:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Methode: AssertTemplate

Die zu verwendende Assert-Vorlage. Die vollständige Liste der Assert-Vorlagen findest du in `generators/Templates/_Assert*.liquid`

#### Beispiel

Der Generator `RationalNumbers` verwendet die Vorlage `"AssertEqualWithin"`, um Gleitkommazahlen mit einer bestimmten Toleranz auf Gleichheit zu prüfen:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Methode: TestFileFormat

Das Format der Testdatei: entweder ein Modul oder eine Klasse.

Das Standardverhalten ist praktisch immer genau das, was du willst. Nur in extrem seltenen Fällen solltest du es ändern.

#### Beispiel

Der Generator `Grep` definiert sich selbst als Testklasse, um Setup- und Teardown-Methoden verwenden zu können:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Methode: TestMethodName

Legt den Namen der Testmethode fest.

Das Standardverhalten ist meistens genau das, was du willst. Nur in ganz besonderen Fällen solltest du es ändern.

#### Beispiel

Der Generator `Zipper` bereinigt den Namen der Testmethode ein wenig:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Methode: UseFullMethodName

Gibt an, ob der verwendete Name der Testmethode den vollständigen Pfad verwenden soll. Bei verschachtelten Testfällen wird dem Namen der Testmethode dann die Beschreibung der übergeordneten Fälle vorangestellt.

Das Standardverhalten ist meistens genau das, was du willst. Nur wenn es sonst mehrere Testmethoden mit demselben Namen gäbe, solltest du es ändern.

#### Methode: Signature

Der Generator `KindergartenGarden` verwendet vollständige Methodennamen, um Namenskonflikte zwischen Testmethoden zu vermeiden:

```fsharp
override __.UseFullMethodName _ = true
```

### Methode: SkipTestMethod

Gibt an, ob die Testmethode mit der Eigenschaft `Skip = true` markiert werden soll.

Das Standardverhalten ist praktisch immer genau das, was du willst. Nur in extrem seltenen Fällen solltest du es ändern.

#### Methode: Signature

Die Übung `Markdown` ist eine Refactoring-Übung, und daher sollten sich alle ihre Tests bereits in einem gültigen Zustand befinden. Deshalb fügt sie für keine ihrer Testmethoden die Eigenschaft `Skip` hinzu:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Bestehende Dateien aktualisieren

Es kann vorkommen, dass eine bestehende Übung nicht zu den kanonischen Daten passt. Du darfst die Stub-Datei der Übung und/oder das Übungsbeispiel gerne an die kanonischen Daten anpassen!

Wenn du außerdem ein Problem mit einem der bestehenden Generatoren oder Testsuiten findest, öffne einfach den Generator, den du aktualisieren möchtest, nimm deine Änderungen vor und führe dann die Generatoren aus.

## Die Generatoren ausführen

Dieses Repository ist auf [.NET Core 2.x](https://www.microsoft.com/net/core) ausgelegt. Um die Generatoren auszuführen, musst du nur den folgenden Befehl im Verzeichnis generators ausführen:

`dotnet run`

Dieser Befehl nimmt alle definierten Übungsgeneratoren und generiert für jede Übung alle Testfälle. Wir verwenden Reflektion, um alle Übungen zu ermitteln. Wenn du also einen neuen Test hinzufügst, wird er beim Ausführen des Generators automatisch berücksichtigt.

Wenn du nur einen einzelnen Generator ausführen möchtest, geht das mit dem folgenden Befehl:

`dotnet run -e <exercise>`

Sobald der Generator ausgeführt wurde, kannst du die Ausgabe deiner Generierung ansehen, indem du zur Testdatei für diese Übung navigierst. Die Testsuite für die Übung Bob findest du zum Beispiel hier:

`exercises/bob/BobTests.fs`

## Einen Generator einreichen

Wenn du mit der Ausgabe deines Generators zufrieden bist, würden wir uns freuen, wenn du einen Pull Request einreichst! Bitte füge deinen Generator, die aktualisierte Testsuite und alle anderen zugehörigen Dateien, die du geändert hast, hinzu.

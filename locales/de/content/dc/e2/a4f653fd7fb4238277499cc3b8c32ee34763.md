# Ergänzung zu den Anweisungen

## Die Aufgabe

Implementiere zwei Prozeduren.

- `custom_error_message message` löst einen Fehler aus, und `message` ist die Fehlermeldung.
- `handle_error script` führt das übergebene Skript aus und gibt einen String zurück, der beschreibt, was passiert ist:

  | Wenn das Skript…                  | Rückgabe             |
  | --------------------------------- | -------------------- |
  | durch null teilt                  | `"division by zero"`    |
  | eine Datei öffnet, die es nicht gibt | `"file does not exist"` |
  | eine Prozedur aufruft, die es nicht gibt | `"proc does not exist"` |
  | einen beliebigen anderen Fehler auslöst | `"unknown error"`       |
  | erfolgreich ist                   | `"success"`             |

## Fehler auslösen

Tcl hat zwei Befehle, um einen Fehler auszulösen.

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` erwartet einen _Fehlercode_ als erstes Argument.
Der Fehlercode ist eine Liste, die einem Handler sagt, welche Art von Fehler aufgetreten ist, damit er reagieren kann, ohne den Nachrichtentext zu parsen.
Sein Inhalt ist dir überlassen: `{MYAPP BADTHING}` ist nur ein Beispiel, und jede nicht leere Liste funktioniert.
Üblicherweise geht er vom Allgemeinen zum Spezifischen.
Ein Handler fängt ihn mit einem passenden `try ... trap`-Muster ab (weiter unten beschrieben), etwa `trap {MYAPP BADTHING}` oder `trap {MYAPP}`, um jeden `MYAPP`-Fehler abzufangen.
`error` nimmt einen optionalen Fehlercode als drittes Argument: `error message ?info? ?code?`.

## Fehler mit `catch` behandeln

[`catch`][catch] führt ein Skript aus und gibt eine Ganzzahl als _Abschlusscode_ zurück, statt den Fehler auszulösen:

| Code | Bedeutung    |
| ---- | ------------ |
| 0    | `ok`         |
| 1    | `error`      |
| 2    | `return`     |
| 3    | `break`      |
| 4    | `continue`   |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

Das optionale zweite Argument erhält das Ergebnis (oder die Fehlermeldung).
Das optionale dritte Argument erhält ein _Optionswörterbuch_ mit `-errorcode` und `-errorinfo` (dem Stacktrace).

Vorteile:

- Er ist klein und flexibel.
- Für einfache Fälle ist er kurz, etwa `if {[catch {open $f} fh]} {...}`.

Nachteile:

- Du musst den Abschlusscode selbst prüfen.
  Ein unbedachtes `if {[catch ...] != 0} { handle error }` behandelt auch `return`, `break` und `continue` als Fehler.
- Fehler, die du nicht behandelst, werden verschluckt, es sei denn, du löst sie selbst erneut aus.
- Es gibt keine eingebaute Möglichkeit, Aufräumcode auszuführen, egal ob das Skript fehlgeschlagen ist oder nicht.

## Fehler mit `try` behandeln

[`try`][try] führt ein Skript aus und schickt das Ergebnis an den ersten passenden Handler.
Ein optionaler `finally`-Block wird immer ausgeführt, was ihn zu einem guten Ort macht, um Ressourcen wie Dateikanäle freizugeben.

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

Vorteile:

- Die Struktur ist klar: ein Handler für jede Art von Ergebnis.
- `finally` wird immer ausgeführt.
- Ergebnisse, zu denen kein Handler passt, werden unverändert an den Aufrufer weitergegeben.

Nachteile:

- Für einfache Fälle ist es etwas ausführlicher als `catch`.

### `try ... on` im Vergleich zu `try ... trap`

Es gibt zwei Arten von Handlern.

`on code {msgVar optionsVar}` passt auf den _Abschlusscode_: `ok`, `error`, `return`, `break` oder `continue`.
Jeder Fehler hat den Abschlusscode `error`, daher kann `on error` eine Division durch null nicht von einer fehlenden Datei unterscheiden.
Du müsstest dir den Nachrichtentext ansehen, was fragil ist: Meldungen sind für Menschen gedacht und können sich zwischen Tcl-Versionen ändern.

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` passt auf den _Fehlercode_.
Der Handler passt, wenn das Muster ein Präfix der `-errorcode`-Liste ist.
So lässt sich die Art des Fehlers zuverlässig erkennen.

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

Ein leeres Muster, `trap {}`, passt auf jeden Fehler.
Handler werden der Reihe nach geprüft, setze den Sammel-Handler also ans Ende.

## Den Fehlercode finden

Wo ist `ARITH DIVZERO` dokumentiert?
Meist nur im Quellcode, aber Tcl zeigt ihn dir.
Nach einem Fehler enthält die globale Variable `errorCode` den Fehlercode des letzten Fehlers:

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

In einem Programm bekommst du ihn aus dem Optionswörterbuch:

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

Das letzte Element eines Fehlercodes ist oft eine für Menschen lesbare Meldung oder der Name dessen, was den Fehler ausgelöst hat.
Lass es aus deinem `trap`-Muster weg: Nutze `{ARITH DIVZERO}`, nicht `{ARITH DIVZERO {divide by zero}}`.

### Einige häufige Fehlercodes

Diese Tabelle ist nicht vollständig.
Nutze die obige Technik, um den Code für andere Fehler zu finden.

| Situation                 | Beispiel                 | Fehlercode                    |
| ------------------------- | ------------------------ | ----------------------------- |
| Division durch null      | `expr {1 / 0}`           | `ARITH DIVZERO ...`           |
| Mathematischer Domänenfehler | `expr {sqrt(-1)}`     | `ARITH DOMAIN ...`            |
| Datei nicht gefunden     | `open nosuchfile r`      | `POSIX ENOENT ...`            |
| Zugriff verweigert       | `open /root/x w`         | `POSIX EACCES ...`            |
| Unbekannter Befehl       | `no::such::proc`         | `TCL LOOKUP COMMAND name`     |
| Unbekannte Variable      | `set nosuchvar`          | `TCL LOOKUP VARNAME name`     |
| Falsche Anzahl an Argumenten | `string length a b`  | `TCL WRONGARGS`               |
| Ungültiges Wörterbuch    | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`        |
| Ungültige Liste          | `llength "a \{b"`        | `TCL VALUE LIST ...`          |

`POSIX`-Fehlercodes verwenden die `errno`-Namen des Betriebssystems, etwa `ENOENT`, `EACCES` und `EEXIST`.

## Hinweis: Wo das Skript läuft

`handle_error` erhält ein Skript von seinem Aufrufer.
Wenn du es mit `try $script` ausführst, wird es im Gültigkeitsbereich von `handle_error` ausgewertet, nicht im Gültigkeitsbereich des Aufrufers.
Um es dort auszuwerten, wo es geschrieben wurde, nutze [`uplevel`][uplevel]: `try {uplevel 1 $script} ...`.

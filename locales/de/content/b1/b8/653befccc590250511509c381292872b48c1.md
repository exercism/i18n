# Einführung

Eine Funktion ist **rekursiv**, wenn sie sich selbst aufruft.

Ein wesentlicher Unterschied zwischen einem Funktionsaufruf und einer Schleife ist, dass beim Aufruf einer Funktion die Rücksprungadresse auf den Stack gelegt wird.
Deshalb braucht eine rekursive Funktion meist mehr Stack-Speicher als eine entsprechende Schleife.

Die Folge: Eine Funktion, die sich immer weiter selbst aufruft, kann irgendwann den gesamten Stack-Speicher aufbrauchen.
Das nennt man einen **Stack Overflow**.

Deshalb braucht jede rekursive Funktion mindestens einen Basisfall: eine Situation, in der die Funktion zurückkehrt, ohne sich selbst aufzurufen.
Jeder rekursive Aufruf muss irgendwann einen Basisfall erreichen.

Zum Beispiel lässt sich die Fakultätsfunktion `n! = n * (n - 1) * ... * 1` rekursiv definieren, mit `1` als Basisfall:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Beachte, dass `factorial` vor dem rekursiven Aufruf `push rdi` ausführen muss und danach `pop rdi`.
Das liegt daran, dass es `n` noch braucht, wenn der rekursive Aufruf zurückkehrt, um `n * (n-1)!` zu berechnen.

Beachte außerdem, dass ein callee-saved-Register dieses Problem nicht lösen würde.

Auch wenn eine rekursive Funktion sich selbst aufrufen kann, wird sie selbst von einer anderen Funktion aufgerufen.
Das bedeutet, dass die Funktion auch callee-saved-Register sichern muss, bevor sie sie benutzt, und ihren Wert danach wiederherstellen muss.
Das geschieht meist mit einer `push`/`pop`-Sequenz, wie wir sie in einem früheren Konzept gesehen haben.

Da jeder Frame einer rekursiven Funktion, mit Ausnahme des Basisfalls, auch ein Aufrufer ist, der seine eigenen lokalen Variablen sichern muss, muss diese `push`/`pop`-Sequenz für jeden Frame wiederholt werden.
Selbst wenn man die Variable direkt im Stack ablegt, ohne Register zu benutzen, kostet das weiterhin dieselben `8` Bytes pro Frame.

Das bedeutet, dass jeder rekursive Aufruf `8` Bytes für die von `call` auf den Stack gelegte Rücksprungadresse hinzufügt, plus `8` Bytes für jede lokale Variable, die gesichert werden muss.
Die Funktion fügt diese Bytes mit jedem Frame weiter zum Stack hinzu, bis sie ihren Basisfall erreicht.
Erst dann beginnt sie, sich in umgekehrter Reihenfolge abzubauen: Jeder rekursive Aufruf führt so viele `pop` aus wie nötig und danach ein `ret`.

Wenn `factorial` zum Beispiel mit dem Argument `10` aufgerufen würde, würde es sich neunmal selbst aufrufen, bevor es den Basisfall `1` erreicht.
Zu diesem Zeitpunkt wären `144` Bytes belegt, um `n` (`8` Bytes) und die Rücksprungadresse (`8` Bytes) für jeden vorherigen Frame zu speichern.

## Tail Call

In manchen Situationen erledigt eine Funktion nach dem Aufruf einer anderen Funktion und vor der Rückkehr keine weitere Arbeit.

Betrachte zum Beispiel:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

Die Funktion `triple_of_square`:

- multipliziert das übergebene Argument (in `rdi`) mit sich selbst und erhält so sein Quadrat;
- dann ruft sie `times_three` auf, was das Dreifache des übergebenen Arguments zurückgibt.

Als Ergebnis gibt `triple_of_square` `3*x²` zurück, wobei `x` das in `rdi` übergebene Argument ist.

Beachte, dass in `triple_of_square` nach dem Aufruf von `times_three` keine Arbeit mehr anfällt: Die Funktion kehrt einfach zurück.
In einer solchen Situation kann eine Funktion statt `call` auch `jmp` verwenden und die Ausführung an die aufgerufene Funktion übergeben:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

Das nennt man einen **Tail Call**.

Der Hauptvorteil eines Tail Calls ist, dass die zusätzlichen Kosten von `call` entfallen.
Ein `call` legt eine Rücksprungadresse auf den Stack, und damit die Kontrolle dorthin zurückkehrt, muss es ein passendes `ret` geben.

Ein Tail Call überspringt beides: Es gibt keine Rücksprungadresse, die gelegt werden müsste, und kein zusätzliches `ret`, mit dem sie sich paaren müsste, nur das eigene `ret` der aufgerufenen Funktion.

## Tail-Rekursion

Ein Tail Call ist besonders nützlich für rekursive Funktionen, die sich vor der Rückkehr viele Male selbst aufrufen können.

Allerdings lässt sich nicht jeder rekursive Aufruf direkt in einen Tail Call umwandeln.
Da ein `jmp` die Kontrolle an die aufgerufene Funktion übergibt, kann der Aufrufer nach dem Tail Call keine Arbeit mehr erledigen.

Die frühere Funktion `factorial` ist zum Beispiel **nicht** Tail-rekursiv.
Nach dem rekursiven Aufruf muss sie das Ergebnis noch mit dem aktuellen `n` multiplizieren, und zwar mit `imul rax, rdi`.

In solchen Situationen ist es manchmal möglich, einen Akkumulator zu verwenden, der Teilergebnisse sammelt und am Ende zurückgegeben wird.
Zum Beispiel können wir einen `factorial_helper` definieren, der den größten Teil der Arbeit erledigt; `factorial` richtet dann einen Akkumulator ein und übergibt die Kontrolle an `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Da nach dem rekursiven Aufruf keine Arbeit mehr anfällt, müssen wir `rdi` auch nicht mehr sichern.
Es gibt kein `call` und kein `push rdi`, und daher fügt jede rekursive Iteration `0` Bytes zum Stack hinzu: Es wird kein zusätzlicher Stack-Speicher belegt.
Diese Version kommt mit beliebig großem `n` zurecht, ohne den Stack zum Überlaufen zu bringen.
Sie ist sowohl effizienter als auch sicherer.

In manchen Fällen lässt sich durch Umsortieren der Funktionen sogar das `jmp` zum Helfer vermeiden.
Zum Beispiel lassen sich `factorial` und `triple_of_square` so umschreiben:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

Im obigen Ausschnitt geht die Ausführung von `factorial` direkt in `factorial_helper` über.
Dasselbe passiert bei `triple_of_square` und `times_three`.
In beiden Fällen läuft die Ausführung der Reihe nach weiter, und es sieht so aus, als wäre die Tail-Funktion nur ein lokales Label innerhalb der „Hauptfunktion“.

In Wirklichkeit gibt es keinen wesentlichen Unterschied zwischen einem lokalen Label und einer Funktion.
x86-64-Assembly behandelt beide nicht unterschiedlich: Sie sind einfach Adressen in einem Abschnitt mit ausführbarem Code, wie `section .text`.

So kann man sich eine Tail-rekursive Funktion im Wesentlichen genauso vorstellen wie eine Schleife, in der der rekursive Aufruf zurück an den Anfang springt und der Basisfall die Bedingung ist, die die Schleife beendet.

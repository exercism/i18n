# Über

An diesem Punkt im Lehrplan hast du schon viele Funktionsdefinitionen gesehen. Normalerweise wurden sie ohne viele Worte zur Ausgabe in der REPL gezeigt:

```julia-repl
julia> f(x) = x^2
f (generic function with 1 method)
```

Warum steht dort _„generic function with 1 method"_?

Angenommen, wir wollen die Argumenttypen genauer festlegen.

```julia-repl
julia> f(x::Integer) = x^2
f (generic function with 2 methods)

julia> f(x::Real) = x^2
f (generic function with 3 methods)
```

Oder wir ändern die Anzahl der Argumente:

```julia-repl
julia> f(x, y) = x * y
f (generic function with 4 methods)
```

Offenbar heißen neue Definitionen derselben Funktion „Methoden". Methoden werden an eine Liste angehängt, statt die alte Definition zu überschreiben.

Wir können die Methoden leicht auflisten:

```julia-repl
julia> methods(f)  # output edited for brevity
# 4 methods for generic function "f" from Main:
 [1] f(x, y)
 [2] f(x::Integer)
 [3] f(x::Real)
 [4] f(x)
 ```

Wenn wir die Funktion `f` aufrufen, weiß Julia irgendwie, welche Methode sie verwenden soll:

```julia-repl
julia> f(2.5)  # Float64
6.25

julia> f(2)  # Int64
4

julia> f(2, 3)  # Int64, Int64
6
```

## Was ist eine Funktion?

Laut [Handbuch][function] ist eine Funktion ein Objekt, das ein Tupel von Argumenten auf einen Rückgabewert abbildet. Das kommt der Definition nahe, die Mathematiker verwenden.

Normalerweise denken wir bei den Argumenten in `f(2, 3)` an zwei getrennte Dinge, aber der Compiler sieht sie als ein einziges [Tupel][tuple]. Das gilt sogar für ein einzelnes Argument (wir müssen dann allerdings ein Komma ergänzen, damit das deutlicher wird):

```julia-repl
julia> typeof( (2, 3) )
Tuple{Int64, Int64}

julia> typeof( (2,) )
Tuple{Int64}
```

Betrachten wir die Funktion als Blackbox, können wir sagen: Ein Tupel geht hinein, ein Rückgabewert kommt heraus. Formaler ausgedrückt wird das Tupel auf einen Rückgabewert _abgebildet_.

## Wie gehen Funktionen mit unterschiedlich vielen Argumenten und unterschiedlichen Argumenttypen um?

Das nennt man gewöhnlich [„Polymorphie"][polymorphism].

Das ist seit mehreren Jahrzehnten ein großes Thema in der Informatik, und es wurden verschiedene Ansätze gewählt.

Julias Ansatz ist ungewöhnlich, aber nicht einzigartig.

- Funktionen sind [„generisch"][generic], das heißt, an sie können mehrere Methoden angehängt sein.
- Funktionen sind nur Namen, solange keine Methoden daran hängen.
- Methoden lassen sich nach Bedarf hinzufügen, möglicherweise in großer Zahl (der Operator `+` ist derzeit eine Funktion mit 161 Methoden).
- Wenn eine Funktion aufgerufen wird, untersucht Julia die Aufrufsignatur: die Anzahl der Argumente und den aktuellen Typ jedes einzelnen.
- Ausgewählt wird die Methode, die am besten zur Aufrufsignatur passt.
  - Im Allgemeinen muss die Anzahl der Argumente genau übereinstimmen (der [Splat/Slurp][splat]-Operator `...` kann das allerdings teilweise umgehen).
  - Methoden, deren Typen genau zur Aufrufsignatur passen, werden bevorzugt.
  - Falls nötig, schaut Julia sich die Obertypen jedes Arguments in der Aufrufsignatur an, um die am besten passende, spezifischste Methode zu finden.
- Die gewählte Methode wird mit den gegebenen Argumenten [`dispatched`][dispatch] und gibt ein Ergebnis zurück.
- Wird keine passende Methode gefunden, wird ein [`MethodError`][methoderror] ausgelöst.

Beachte, dass Julia dynamisch typisiert ist, der Methoden-Dispatch also zur _Laufzeit_ stattfindet.

## Multiple Dispatch: ein Beispiel

Der vorherige Abschnitt war sehr wortreich, also übersetzen wir diese Ideen in Code. Der Einfachheit halber haben die folgenden Funktionen nur ein Argument, aber Funktionen mit Dutzenden von Argumenten sind keine Seltenheit (etwa in Plot-Paketen oder beim maschinellen Lernen).

Definiere zunächst einige eigene Typen, um geometrische Formen darzustellen.

```julia-repl
julia> abstract type Shape end

julia> struct Circle <: Shape
           radius::Float64
       end

julia> struct Square <: Shape
           side::Float64
       end

julia> struct Rectangle <: Shape
           length::Float64
           width::Float64
       end
```

Als Nächstes können wir Methoden definieren, die den Flächeninhalt jeder Form berechnen. Jede nimmt ein Argument, jeweils von einem anderen konkreten, selbst definierten Typ.

```julia-repl
julia> area(c::Circle) = π * c.radius^2
area (generic function with 1 method)

julia> area(s::Square) = s.side^2
area (generic function with 2 methods)

julia> area(r::Rectangle) = r.length * r.width
area (generic function with 3 methods)
```

Jetzt können wir einige Formen erzeugen und ihre Flächen berechnen, wobei wir uns auf Julias Dispatch-Mechanismus verlassen, der für jede die richtige Formel verwendet.

```julia-repl
julia> circle = Circle(2.3)
Circle(2.3)

julia> area(circle)  # call signature Tuple{Circle}
16.619025137490002

julia> square = Square(1.6)
Square(1.6)

julia> area(square)  # call signature Tuple{Square}
2.5600000000000005

julia> rectangle = Rectangle(1.4, 2.1)
Rectangle(1.4, 2.1)

julia> area(rectangle)  # call signature Tuple{Rectangle}
2.94
```

## [Parametrische Methoden][parametric]

Methodensignaturen können Platzhalter-Typwerte annehmen, ungefähr so wie parametrische Typen.

Die Syntax ist eigenwillig und erfordert eine `where`-Klausel:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T} = true
same_type (generic function with 1 method)

julia> same_type([1, 2], 3)
true

julia> same_type([1, 2], "three")
ERROR: MethodError: no method matching same_type(::Vector{Int64}, ::String)
```

Das obige Beispiel verlangt, dass beide Argumente denselben Typ `T` verwenden, egal welcher das ist.

Wir können genauer sein, indem wir eine Einschränkung für `T` angeben:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T<:Number} = true
same_type (generic function with 2 methods)
```

Bei dieser Methode geben nur identische numerische Typen `true` zurück.

Mehrere Platzhaltervariablen sind möglich, durch Kommas getrennt in der `where`-Klausel. Die folgenden zwei Methoden sehen ähnlich aus:

```julia-repl
julia> func(v::Vector{Number}, x::Number) = true
func (generic function with 1 method)

julia> func(v::Vector{S}, x::T) where {S<:Number, T<:Number} = true
func (generic function with 2 methods)
```

Ein Unterschied ist, dass die Typwerte `S` und `T` im Funktionskörper der zweiten Methode verwendet werden können. Das ist eine Art Trick, den du vielleicht nicht oft einsetzt, der dir aber in manchen Situationen viel Ärger ersparen kann.

Zum Beispiel müssen in der folgenden parametrischen Typdefinition die Felder denselben Typ `T` haben, der als Subtyp von `Real` eingeschränkt ist:
```julia
struct Point{T<:Real}
    x::T
    y::T
end
```
Diese `Point`-Definition akzeptiert ein `x` und ein `y` desselben Typs, oder sie akzeptiert ein `x` und ein `y` unterschiedlicher Typen, dann muss aber ein expliziter Konvertierungstyp angegeben werden.
```julia-repl
julia> Point(4, 5)
 Point{Int64}(4, 5)

julia> Point(3.5, 2)
 MethodError: no method matching Point(::Float64, ::Int64)    # Output truncated for brevity

julia> Point{Float32}(3.5, 2)
 Point{Float32}(3.5f0, 2.0f0)

julia> Point{Int64}(3.5, 2) 
 InexactError: Int64(3.5)      # Output truncated for brevity
```
So viel Kontrolle über die Typen mag wünschenswert sein, doch ein wenig Abstraktion kann ebenfalls nützlich sein.
```julia
Point(x::T, y::S) where {T<:Real, S<:Real} = Point{promote_type(T,  S)}(x, y)
```
Dieser äußere Konstruktor liefert das, indem ein `Point` für `x` und `y` inhomogene Typen akzeptieren kann, ohne den Konvertierungstyp explizit anzugeben. Die Typwerte `T` und `S` werden im Funktionskörper in `promote_type(T, S)` verwendet, um den expliziten Konvertierungstyp für die ursprüngliche Definition zu liefern.
```julia-repl
julia> Point(3.5, 2)
 Point{Float64}(3.5, 2.0)
```

## Vergleich mit anderen Sprachen

Da Julia bei der Auswahl einer Methode alle Argumente untersucht, nennt man das [`multiple dispatch`][multiple-dispatch].

Einige andere Sprachen erlauben Multiple Dispatch, etwa Common Lisp, doch selten ist es so zentral für das Sprachdesign wie in Julia.

Im Gegensatz dazu werden in einer objektorientierten Sprache (OO) (z. B. Ruby) Methoden üblicherweise auf einer [Instanz][instance] aufgerufen. Die Definition bevorzugt nun das erste Argument (mit einem Namen wie `self` oder `this` in der Definition), und der Methodenname wird zum Aufruf mit einem Punkt an die Instanz gehängt:

```ruby
irb(main):004:0> "abc".sub("b", "*")
=> "a*c"
```

Das nennt man [`single dispatch`][single-dispatch], denn nur die Klasse der Instanz (des Strings „abc" im obigen Beispiel) wird verwendet, um eine Methode auszuwählen.

Einige statisch typisierte OO-Sprachen unterstützen Methodenpolymorphie, die dem Multiple Dispatch einigermaßen ähnlich sieht. Der große Unterschied ist, dass die Methodenauswahl nur zur _Kompilierzeit_ stattfindet.

Funktionale Sprachen haben meist nur eine einzige Funktionsdefinition, mit irgendeiner Art von Select/Case/Match-Ausdruck, um die verschiedenen Möglichkeiten zu behandeln. Du schreibst deine eigene Logik, meist unterstützt durch eine knappe Pattern-Matching-Syntax, die Julia nicht hat. Natürlich betreibt auch Julia eine Form von Pattern-Matching, aber beim Dispatch statt innerhalb des Funktionskörpers.

## Fazit

Multiple Dispatch ist in Julia sehr flexibel und leistungsstark und wird deshalb sehr häufig eingesetzt.

Wie das Beispiel der 161 Methoden für `+` zeigt, versuchen Julia-Programmierer, Methoden mit eng gefassten Typen zu definieren. Zwei Ganzzahlen zu addieren ist auf Bytecode-Ebene etwas ganz anderes, als zwei Gleitkommazahlen zu addieren, und eine Ganzzahl zu einer Gleitkommazahl zu addieren, bringt zusätzlich die Komplikation der Typ-Promotion mit sich.

Je spezifischer der Typ, desto mehr Optimierungen kann der Compiler vornehmen: Bei einer Spielzeugübung auf Exercism ist das von untergeordneter Bedeutung, aber für die Leistung in den großen numerischen Simulationen, für die Julia gemacht ist, entscheidend.

_Wenn du weißt, welche Eingaben eine Methode bekommt, dann sag es dem Compiler!_

# Merge-Strategie

Die Maintainer des Rust-Tracks [haben entschieden](https://github.com/exercism/v3/discussions/1725#discussion-7438), unsere Merge-Strategie schriftlich festzuhalten, um Erwartungen zu kommunizieren und qualitativ hochwertige Beiträge zu fördern.

## Allgemeine Grundsätze

- wir sind bestrebt, _alle_ Beiträge anzunehmen
  - Durch gemeinsame, iterative Reviews bringen wir Beiträge auf ein hohes Qualitätsniveau.
  - Wir verfolgen einen pessimistischen Merge-Ansatz. Stell dir die Reviews der Maintainer wie das Feedback des Rust-Compilers vor. Die Menge an Feedback kann überwältigend und frustrierend wirken. Aber wir arbeiten mit dir zusammen, damit es ins Ziel kommt! Also mach weiter so.
- Jeder Pull Request muss mindestens eine Genehmigung („Approval") und keine Änderungsanfrage („Request Changes") von einem Maintainer des Tracks haben, bevor er gemergt werden kann.
- Kein Maintainer kann seinen eigenen Pull Request genehmigen.

## Pull-Request-Workflow

### Definitionen

| Begriff            |                                                                                               Bedeutung |
| ------------------ | ----------------------------------------------------------------------------------------------------: |
| Beitragende        |                                               Jede Person, die einen Pull Request einreicht. |
| Maintainer         |                    Jede Person, die zum [@exercism/rust Team](https://github.com/orgs/exercism/teams/rust) gehört. |
| Entwicklungsbranch | Der Standard-Entwicklungsbranch des [v3](https://github.com/exercism/v3)-Repositorys. Derzeit `master`. |

### Der Workflow

1. Beitragende beginnen damit, einen Pull Request als [Entwurf](https://github.blog/2019-02-14-introducing-draft-pull-requests/) oder einen vollständigen Pull Request mit ihren Änderungen zu eröffnen
   1. Wenn du die Entwurfsfunktion verwendest, signalisierst du, dass die Arbeit für ein Review auf hoher Ebene bereit ist, dass Details aber möglicherweise noch nicht umgesetzt, unvollständig oder falsch sind.
   1. Nach einer nicht näher festgelegten Anzahl von Durchläufen der Schritte 2 bis 3 markieren die Beitragenden den Pull Request als bereit für das Review.
1. Ein weiterer Maintainer sieht sich den Beitrag an und gibt Feedback.
1. Die beitragende Person arbeitet _das gesamte_ Feedback der Maintainer im Rahmen dieses Pull Requests ab.
   1. Für Kleinigkeiten oder eindeutige Änderungen können Maintainer die Vorschlagsfunktion von GitHub nutzen.
   1. Widerspruch ist erwünscht, wenn eine beitragende Person der Meinung ist, dass sie recht hat und ein Maintainer bei einem Feedback-Punkt falsch liegt. Einen Feedback-Punkt zu „abarbeiten" ist nicht dasselbe, wie ihn sklavisch umzusetzen.
1. Der Maintainer sieht sich das Feedback an und
   1. genehmigt es
   1. bittet um weitere Änderungen. An diesem Punkt kehrt der Prozess zu Schritt 3 zurück.
1. Nach der Genehmigung merged ein Maintainer seinen Pull Request.
   1. Maintainer mergen ihre eigenen Pull Requests. Da Beitragende nicht zwangsläufig Maintainer sind, muss ein Maintainer diesen Schritt ausführen.

## Optimistisches Merging

Die Maintainer des Rust-Tracks haben entschieden, vorübergehend Optimistic Merging einzuführen, um die Entwicklung des v3-Tracks zu beschleunigen.

- Das gilt nur für das v3-Repository.
- Sobald v3 in Produktion geht, kehren wir zu einer pessimistischen Merge-Strategie zurück.
- Wir genehmigen und mergen unvollständige Arbeit.
  - Wenn es kompiliert, behalten wir es.
  - Geschwindigkeit bei der Iteration ist uns wichtiger als die Feinheiten eines korrekten Software-Designs.
- Jeder Pull Request muss mindestens eine „Genehmigung" von einem Maintainer des Tracks haben, bevor er gemergt werden kann.

# Überblick

## Zusammengesetzte Typen

Es ist oft nützlich, in unseren Programmen eigene Typen zu definieren.

Neue primitive Typen lassen sich zwar erstellen, das wird aber selten gemacht.
Die eingebauten [primitiven Typen][primitive] sind keine willkürliche Wahl: Sie entsprechen weitgehend den Standardtypen im LLVM-Compiler, den Julia für die JIT-Kompilierung verwendet.

Deutlich nützlicher ist die Möglichkeit, [zusammengesetzte Typen][composite-types] mit benannten Feldern zu definieren.

Andere Sprachen haben etwas Ähnliches und nennen sie `structs` oder `records`.
Die Julia-Dokumentation bezeichnet sie als `composite types`, obwohl die Syntax der Sprache sie (eine kleine Diskrepanz) mit dem Schlüsselwort `struct` definiert.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Am obigen Beispiel sind ein paar Punkte erwähnenswert:

- Für `id` ist kein Typ angegeben, daher interpretiert der Compiler das als `id::Any`.
  - **Hinweis:** In der Praxis ist es am besten, dem Compiler zu helfen, indem du den Typ eines Feldes mit einem konkreten Typ angibst.
  - Wir werden in einem [zukünftigen Konzept][parametric] sehen, dass die Verwendung von Parametern eine weitere Möglichkeit ist.
- Der Typname wird als Konstruktor verwendet, wie in `Person(id, name, age)`, um eine Instanz des Typs `Person` zu erhalten.
- Auf einzelne Felder kann mit Punktnotation zugegriffen werden, genau wie bei [benannten Tupeln][named-tuple].

Elemente des Typs `Person` sind unveränderlich, daher sind Änderungen nicht erlaubt.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Wenn Veränderbarkeit erforderlich ist, füge `mutable` zur Definition hinzu.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Der Konstruktor verlangt standardmäßig, dass die Felder in derselben Reihenfolge wie in der Definition erscheinen, was bei komplizierteren Typen unpraktisch wird.

Die Verwendung des Makros `@kwdef` ermöglicht zwei neue Fähigkeiten:

- Der Konstruktor verwendet Schlüsselwortargumente statt Positionen.
- Felder können Standardwerte haben und optional aus dem Konstruktor weggelassen werden.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarchien zusammengesetzter Typen

Bisher haben wir nur konkrete zusammengesetzte Typen erstellt.
Wenn du nachprüfst, sind alle Untertypen von `Any`.

Wenn du mehrere verwandte Typen erstellst, ist es wahrscheinlich sinnvoller, eine Hierarchie für sie zu definieren.
Das ist ganz einfach.

Erstelle zuerst einen abstrakten Typ:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Füge als Nächstes einen `<:`-Operator in eine Typdefinition ein, um die Beziehung anzuzeigen.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Wiederhole das nach Bedarf, und denke daran, dass Untertypisierung konkreter Typen nicht erlaubt ist.

Für eine komplexere Hierarchie erstelle nach Bedarf abstrakte Untertypen.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

Der Nutzen einer solchen Hierarchie wird klarer, wenn wir das Konzept `Multiple Dispatch` erreichen und sehen, wie Funktionen mit Argumenttypen umgehen.


## Innere Konstruktoren

Wir haben am Anfang dieses Konzepts gesehen, dass der Name des Typs als Konstruktor verwendet wird, um Elemente dieses Typs zu erstellen:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

Hier wird `Person()` als `outer constructor` bezeichnet.
Die Feldtypen werden auf Kompatibilität mit der Typdefinition geprüft, und bei Bedarf wird ein Fehler ausgelöst.

Angenommen, wir wollen Beschränkungen für die _Werte_, die übergeben werden, nicht nur für die _Typen_?

Dann können wir einen `inner constructor` innerhalb der Typdefinition angeben, um geeignete Prüfungen durchzuführen.

Zum Beispiel haben wir einen abstrakten Typ `AbstractPoint`, der `(x, y)`-Koordinaten aufnehmen soll, aber wir wollen einen Untertyp mit der Einschränkung `y > x`.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

Die Funktion `new()` kann _nur_ in inneren Konstruktoren verwendet werden und gibt das gewünschte Element zurück, wenn die Eingabewerte als gültig erkannt werden.

Bei ungültiger Eingabe könnten wir mit einer Fehlermeldung abbrechen, wie im Beispiel.
Alternativ kannst du einen Platzhalter wie `nothing` oder `missing` verwenden.
Weitere Informationen dazu findest du im [`Nothingness`][nothingness]-Konzept.

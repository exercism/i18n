# Einführung

Ein vorheriges Konzept hat gepackte Gleitkommawerte vorgestellt: mehrere Zahlen in einem einzigen `xmm`-Register, die Lane-weise und parallel bearbeitet werden.
Dieselben `xmm`-Register können auch gepackte _Ganzzahlen_ enthalten.

## Syntax

Das meiste vom SIMD-Gleitkommamodell lässt sich unverändert auf gepackte Ganzzahlen übertragen:

- Ein 128-Bit-Register wird in Lanes unterteilt
- Instruktionen wirken parallel auf Lanes an derselben Position
- Speicheroperanden folgen denselben 16-Byte-Ausrichtungsregeln

Die Syntax ist jedoch etwas anders:

1. Ein _Präfix_ `p`, das angibt, dass die Instruktion auf _gepackten_ Daten arbeitet.
2. Die ausgeführte Operation, mit demselben Namen wie ihr Nicht-SIMD-Gegenstück (auch _skalar_ genannt) (z. B. `add`, `mul` usw.).
3. Ein Suffix, das die Größe jeder Lane angibt.

Gepackte Ganzzahlen haben vier Lane-Größen, und jede hat ihr eigenes Suffix:

| Lane-Breite | Bytes | Lanes in 128 Bit | Suffix |
|------------|-------|-------------------|--------|
| Byte       | 1     | 16                | b      |
| Wort       | 2     | 8                 | w      |
| Dword      | 4     | 4                 | d      |
| Qword      | 8     | 2                 | q      |

Zum Beispiel:

| Instruktion | Bedeutung                              |
|-------------|--------------------------------------|
| `paddb`     | gepacktes `add`, 8-Bit-Lanes (16 Lanes) |
| `paddw`     | gepacktes `add`, 16-Bit-Lanes (8 Lanes) |
| `paddd`     | gepacktes `add`, 32-Bit-Lanes (4 Lanes) |
| `paddq`     | gepacktes `add`, 64-Bit-Lanes (2 Lanes) |

Einige Instruktionen nehmen Lanes mit einer Größe als Eingabe, liefern aber eine andere Größe als Ausgabe.
Sie folgen derselben allgemeinen Konvention, aber mit _zwei_ Größen-Suffixen.
Das erste gibt die Größe der Eingabe-Lane an, das zweite die Größe der Ausgabe-Lane:

| Instruktion  | Bedeutung                                           |
|--------------|---------------------------------------------------|
| `pmovsxwd`   | gepacktes `movsx`, von 16-Bit-Lanes zu 32-Bit-Lanes |
| `pmuldq`     | gepacktes `mul`, von 32-Bit-Lanes zu 64-Bit-Lanes   |

## Speichertransfers

Zwei Instruktionen mit Ganzzahl-Namen kopieren 128 Bit zwischen einem `xmm`-Register und dem Speicher:

| Instruktion | Beschreibung                                             |
|-------------|---------------------------------------------------------|
| `movdqa`    | gepackte Ganzzahlen von oder nach einer _ausgerichteten_ Speicherstelle kopieren   |
| `movdqu`    | gepackte Ganzzahlen von oder nach einer _nicht ausgerichteten_ Speicherstelle kopieren |

Sie verhalten sich wie `movaps` und `movups`: `movdqa` löst bei einer falsch ausgerichteten Adresse einen Fehler aus, während `movdqu` jede akzeptiert.
Alle vier kopieren 128 Bit, ohne sie zu interpretieren.
Das Paar mit Ganzzahl-Namen wird konventionell für Ganzzahldaten verwendet, nicht weil es vorgeschrieben wäre.

~~~~exercism/note
`dq` steht hier für `double-qword`, also 128 Bit (16 Byte).
~~~~

## Addition/Subtraktion

Addition und Subtraktion folgen der Namensregel:

```x86asm
paddb xmm0, xmm1 ; 16 lanes: each  8-bit, xmm0 += xmm1
paddw xmm2, xmm3 ;  8 lanes: each 16-bit, xmm2 += xmm3

psubd xmm4, xmm5 ;  4 lanes: each 32-bit, xmm4 -= xmm5
psubq xmm6, xmm7 ;  2 lanes: each 64-bit, xmm6 -= xmm7
```

Es gibt keine getrennte vorzeichenbehaftete und vorzeichenlose Form.
Im Zweierkomplement erzeugen Addition und Subtraktion dieselben Bits, egal ob die Lanes als vorzeichenbehaftet oder vorzeichenlos gelesen werden. Deshalb genügt eine Instruktion für beide.
Die Interpretation liegt bei dir, genau wie bei skalarem `add` und `sub`.

Diese Instruktionen **schlagen bei Überlauf um**, genau wie ihre skalaren Gegenstücke.
Eine 8-Bit-Lane hält Werte modulo 256. Ein `paddb` von `200 + 100` ergibt also `300 - 256 = 44` und verwirft die Bits, die nicht hineinpassen.

Beachte, dass diese zusätzlichen Bits nicht auf die nächste Lane übertragen werden.
Jede Lane wird getrennt von den anderen bearbeitet, obwohl sie sich dasselbe Register teilen.

## Sättigende Addition/Subtraktion

Ganzzahl-SIMD fügt eine Operation hinzu, die Gleitkomma-SIMD nicht hat: **sättigende** Addition und Subtraktion, die _begrenzen_ statt umzuschlagen.
Ein Ergebnis über dem Bereich der Lane wird zum größten Wert, den die Lane halten kann; ein Ergebnis unterhalb des Bereichs wird zum kleinsten.

Die sättigenden Formen fügen `s` (vorzeichenbehaftet) oder `us` (vorzeichenlos) vor dem Größen-Suffix ein:

| Instruktion | Bedeutung                                    |
|-------------|--------------------------------------------|
| `paddsb`    | `add`, sättigend, vorzeichenbehaftete 8-Bit-Lanes |
| `paddusb`   | `add`, sättigend, vorzeichenlose 8-Bit-Lanes |
| `psubsw`    | `sub`, sättigend, vorzeichenbehaftete 16-Bit-Lanes |
| `psubusw`   | `sub`, sättigend, vorzeichenlose 16-Bit-Lanes |

Der Begrenzungsbereich ist der volle darstellbare Bereich für eine Ganzzahl der entsprechenden Größe und Vorzeichenbehaftung.
Für ein Byte:

- Vorzeichenlose Bytes werden auf `[0, 255]` begrenzt: Ein `paddusb` von `200 + 100` ergibt `255`, und ein `psubusb` von `5 - 10` ergibt `0`.
- Vorzeichenbehaftete Bytes werden auf `[-128, 127]` begrenzt: Ein `paddsb` von `100 + 50` ergibt `127`.

Sättigung ist wichtig, wenn eine Lane eine begrenzte Größe enthält, etwa einen Pixelkanal oder ein Audio-Sample.
Ein Umschlagen würde einen zu hellen Pixel dunkel machen, während Begrenzen ihn auf maximaler Helligkeit hält, was das gewünschte Ergebnis ist.

~~~~exercism/note
Sättigende Addition und Subtraktion gibt es nur für Byte- und Wort-Lanes, nicht für Dword- oder Qword-Lanes.
~~~~

## Multiplikation

Die Multiplikation zweier N-Bit-Werte kann ein 2N-Bit-Produkt ergeben, aber die Ziel-Lane ist nur N Bit breit.
SIMD-Operationen lösen das, indem sie angeben, welche Hälfte des Produkts behalten wird: entweder die unteren N Bits oder die oberen N Bits.

Für 16-Bit-Lanes werden drei Instruktionen verwendet:

| Instruktion | Bedeutung                                                       |
|-------------|---------------------------------------------------------------|
| `pmullw`    | `mul`, 16-Bit-Lanes, die unteren 16 Bits jedes Produkts behalten |
| `pmulhw`    | `mul`, 16-Bit-Lanes, die oberen 16 Bits behalten, vorzeichenbehaftete Operanden |
| `pmulhuw`   | `mul`, 16-Bit-Lanes, die oberen 16 Bits behalten, vorzeichenlose Operanden |

Die unteren 16 Bits eines Produkts sind gleich, egal ob die Operanden als vorzeichenbehaftet oder vorzeichenlos gelesen werden. Deshalb gibt es nur ein einziges `pmullw`.

Die oberen 16 Bits hängen jedoch von der Vorzeichenbehaftung des Ergebnisses ab.
Deshalb hat die Multiplikation der oberen Hälfte getrennte Formen für vorzeichenbehaftete und vorzeichenlose Multiplikation:

1. `pmulhw`, für vorzeichenbehaftete Multiplikation.
2. `pmulhuw`, mit einem zusätzlichen `u`, für vorzeichenlose Multiplikation.

Beachte die Syntax:

1. Ein `p`, für gepackte Ganzzahlen.
2. Die ausgeführte Operation, `mul`.
3. Ein `h`, das angibt, dass die oberen („high“) Bits des Ergebnisses ausgewählt werden.
4. Ein optionales `u`, wenn das Ergebnis als vorzeichenlos interpretiert werden soll (d. h., es wird nicht vorzeichenerweitert).
5. Schließlich das Größen-Suffix `w`, das angibt, dass es sich um eine Wort-Operation (16 Bit) handelt.

Die gepackte Multiplikation für Wörter folgt genau der obigen Regel.
Dword-Multiplikation (32 Bit) folgt ebenfalls der Regel, aber es gibt nur die Variante, die die untere Hälfte auswählt: `pmulld`.

Es gibt keine Variante der Dword-Multiplikation, die die oberen Bits auswählt.
Es gibt jedoch Varianten, die die Multiplikation _erweitern_ und das vollständige 64-Bit-Produkt der _geradzahligen_ Lanes (also der Lanes an Position 0 und 2) speichern:

| Instruktion | Bedeutung                                                                          |
|-------------|----------------------------------------------------------------------------------|
| `pmuludq`   | die geradzahligen 32-Bit-Elemente vorzeichenlos multiplizieren, zu 2 vollständigen 64-Bit-Produkten |
| `pmuldq`    | die geradzahligen 32-Bit-Elemente vorzeichenbehaftet multiplizieren, zu 2 vollständigen 64-Bit-Produkten |

Beachte, dass die Syntax `dq` verwendet, möglicherweise mit einem `u` davor für vorzeichenlose Multiplikation.
Das liegt daran, dass die Instruktionen `dword`-Lanes entgegennehmen und `qword`-Lanes ausgeben.

## Division

Es gibt keine gepackte Ganzzahldivision.
Code, der sie braucht, wandelt die Werte in Gleitkommazahlen um, dividiert und wandelt sie zurück.

## Erweiterung von Ganzzahlen

Es gibt gepackte Entsprechungen für `movsx` und `movzx`.
Sie folgen derselben Syntax, die wir für Instruktionen erwähnt haben, deren Eingaben eine andere Lane-Größe haben als ihre Ausgabe:

```x86asm
pmovsxwd xmm0, xmm1   ; 4 words -> 4 dwords, sign-extended
pmovzxbw xmm0, xmm1   ; 8 bytes -> 8 words, zero-extended
```

Beachte, dass die Anzahl der Lanes durch die größere (Ausgabe-)Breite festgelegt wird.
Die Instruktion liest so viele Lanes aus dem unteren Teil der Quelle.
Das ist dieselbe Semantik, die wir bereits für gepackte `cvt`-Instruktionen zwischen Gleitkommazahlen mit einfacher und doppelter Genauigkeit gesehen haben.

## Umwandlung zwischen Ganzzahlen und Gleitkommazahlen

Es gibt Instruktionen, um zwischen vorzeichenbehafteten 32-Bit-Ganzzahlen und Gleitkomma-Lanes umzuwandeln.
Sie folgen der üblichen Syntax für `cvt`- und `cvtt`-Instruktionen, aber statt `si` wird eine gepackte Ganzzahl durch `dq` dargestellt:

```x86asm
cvtdq2ps xmm0, xmm1 ; convert 32-bit signed integers in xmm1 to 32-bit floats in xmm0
cvtdq2pd xmm2, xmm3 ; convert 32-bit signed integers in xmm3 to 64-bit floats in xmm2
cvtps2dq xmm4, xmm5 ; convert 32-bit floats in xmm5 to 32-bit signed integers in xmm4
```

~~~~exercism/caution
Die Instruktionen, die `pi` zur Darstellung gepackter Ganzzahlen verwenden, schreiben in Legacy-`mmx`-Register und sind auf x86-64 praktisch veraltet.
Bevorzuge die `dq`-Formen, die `xmm`-Register verwenden.
~~~~

Dieselben Anmerkungen, die für die skalare Umwandlung zwischen Gleitkommazahlen und Ganzzahlen gemacht wurden, gelten auch hier.
Gleitkommazahlen werden gemäß einem speziellen Register namens MXCSR gerundet, dessen Modus du beim Eintritt in eine Funktion nicht voraussetzen kannst.
Es gibt eine `cvtt`-Variante (mit einem zusätzlichen `t`), die das Ergebnis immer abschneidet.

Es ist auch möglich, `round` zu verwenden, um gepackte Gleitkommawerte vor der Umwandlung in einen bekannten Zustand zu bringen.
Der Rundungssteuerwert ist derselbe wie bei skalarem `round`, und die Syntax ist für gepackte Gleitkommawerte ebenfalls dieselbe:

```x86asm
roundps xmm0, xmm1, 1 ; xmm0 = floor(xmm1), packed 32-bit floats
roundpd xmm2, xmm3, 2 ; xmm2 = ceil(xmm3), packed 64-bit floats
```

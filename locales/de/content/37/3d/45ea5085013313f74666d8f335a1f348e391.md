# Einführung

Oft ist es nützlich, in unseren Programmen eigene Typen zu definieren.

Neue primitive Typen zu erstellen ist möglich, wird aber selten gemacht.
Die eingebauten primitiven Typen sind keine willkürliche Wahl: Sie entsprechen weitgehend den Standardtypen im LLVM-Compiler, den Julia für die JIT-Kompilierung verwendet.

Deutlich nützlicher ist die Möglichkeit, zusammengesetzte Typen mit benannten Feldern zu definieren.

Andere Sprachen haben etwas Ähnliches und nennen sie `structs` oder `records`.
Die Julia-Dokumentation bezeichnet sie als `composite types`, obwohl die Sprachsyntax sie (eine kleine Unstimmigkeit) mit dem Schlüsselwort `struct` definiert.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Ein paar Punkte sind im obigen Beispiel erwähnenswert:

- Für `id` ist kein Typ angegeben, also interpretiert der Compiler das als `id::Any`.
- Der Typname wird als Konstruktor verwendet, wie in `Person(id, name, age)`, um eine Instanz vom Typ `Person` zu erzeugen.
- Auf einzelne Felder kann mit der Punktnotation zugegriffen werden, genau wie bei benannten Tupeln.

Objekte vom Typ `Person` sind unveränderlich, daher sind Aktualisierungen nicht erlaubt.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Wenn Veränderbarkeit nötig ist, füge `mutable` zur Definition hinzu.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Der Konstruktor verlangt standardmäßig, dass die Felder in derselben Reihenfolge wie in der Definition auftreten, was bei komplizierteren Typen unpraktisch wird.

Die Verwendung des Makros `@kwdef` ermöglicht zwei neue Fähigkeiten:

- Der Konstruktor verwendet Schlüsselwörter statt Positionen.
- Felder können Standardwerte haben und optional im Konstruktor weggelassen werden.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarchien zusammengesetzter Typen

Bisher haben wir nur konkrete zusammengesetzte Typen erstellt.
Wenn du nachprüfst, sind alle Subtypen von `Any`.

Wenn du mehrere verwandte Typen erstellst, ist es wahrscheinlich sinnvoller, eine Hierarchie für sie zu definieren.
Das ist ganz einfach.

Erstelle zuerst einen abstrakten Typ:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Füge als Nächstes einen `<:`-Operator in eine Typdefinition ein, um die Beziehung zu zeigen.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Wiederhole das nach Bedarf und denke daran, dass Subtypisierung konkreter Typen nicht erlaubt ist.

Für eine komplexere Hierarchie erstelle nach Bedarf abstrakte Subtypen.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

Der Wert einer solchen Hierarchie wird klarer, wenn wir zum Konzept `Multiple Dispatch` kommen und sehen, wie Funktionen mit Argumenttypen umgehen.

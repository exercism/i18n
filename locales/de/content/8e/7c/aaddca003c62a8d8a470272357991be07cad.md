# C-Styleguide

Dieser Leitfaden beschreibt den Stil, der für die Beispiel- und Testdateien der Übungen im C-Track verwendet werden soll.

Die Regeln in diesem Leitfaden ergänzen die Regeln der [.clang-format][]-Datei oder heben sie hervor.

## C-Standard

Code sollte dem C99-Standard entsprechen, der formell als ISO/IEC 9899:1999 bekannt ist.
POSIX oder anderweitig nicht standardisierte Bibliotheksfunktionen, Typen oder andere Referenzen, die außerhalb der Implementierung liegen, sollten nicht verwendet werden.

## Namen

Im Allgemeinen sollten die Namen von Typen, Variablen, Strukturen und Dateien Snake Case verwenden, wobei alle Buchstaben klein geschrieben werden und Unterstriche `_` die Namensteile trennen.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Enums

Enum-Namen sollten in der Regel im Singular stehen, nicht im Plural.

Enum-Labels sollten Snake Case verwenden, wobei alle Buchstaben groß geschrieben werden.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Makros

Makros, die Konstanten definieren, werden in Snake Case mit allen Buchstaben in Großbuchstaben benannt.

```c
#define CONSTANT 0x4000
```

Snake Case in Großbuchstaben für Makronamen ist erwünscht, aber Makros, die Funktionen ähneln, dürfen in Snake Case mit Kleinbuchstaben benannt werden.

### Typen

Die standardmäßigen Typen mit fester Breite (in `stdint.h`) sind den grundlegenden Ganzzahltypen vorzuziehen.

Der Typ `bool` (aus `stdbool.h`) ist `_Bool` vorzuziehen.

Ebenso sind `size_t` und `ptrdiff_t` (aus `stddef.h`) vorzuziehen, wenn speicherbezogene Größen dargestellt werden.

Typen, die ein Programm mit `typedef` definiert, sollten ein Suffix `_t` tragen.
Auch wenn dem Track bewusst ist, dass POSIX das Suffix `_t` reserviert, nutzt der Track derzeit kein POSIX.

## Include Guards

In allen Header-Dateien sollten Include Guards verwendet werden.

Im Allgemeinen sollte ein Satz Include Guards den gesamten Inhalt der Header-Datei umschließen.

Guards in der Beispielimplementierung (`.meta/example.h`) und im Übungs-Stub (`exercise_name.h`) sollten Makronamen verwenden, die dem Übungsnamen folgen.
Guard-Makronamen sollten hinsichtlich der Groß- und Kleinschreibung der obigen Regel für Makros folgen.

Für die Übung `hello-world` verwendest du zum Beispiel:

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Parameter

Funktionsparameter sollten sowohl in der Deklaration als auch in der Definition aller Funktionen benannt werden.
Das gilt für `.c`- und `.h`-Dateien gleichermaßen.
Die verwendeten Namen sollten in allen Fällen übereinstimmen.
Das heißt, der folgende Funktionsprototyp ist zwar gültiges C, aber der Stil ist falsch, weil der Parameter keinen Namen hat: `void foo(int);`.
Der korrekte Prototyp wäre `void foo(int bar);`, vorausgesetzt, alle anderen Deklarationen und die Definition verwenden ebenfalls den Parameternamen `bar`.

Wo es einfacher oder passender ist, sind Parameter vorzuziehen, bei denen Argumente als Wert statt als Zeiger übergeben werden.
Beachte insbesondere, dass dies auch Parameter vom Typ `struct` einschließt.

Wenn nicht erwartet wird, dass Lernende die Werte eines Zeigerparameters in ihrer Implementierung ändern, sollte dieser Parameter mit `const` qualifiziert werden.

## Aufbau der Testdatei

Die Testdatei jeder Übung folgt einem bestimmten Aufbau.
Der Aufbau soll sowohl Mitwirkenden helfen, die Teile der Datei zu erkennen, als auch Lernenden helfen zu verstehen, wie die Tests funktionieren.

Wie die meisten C-Quelldateien beginnt eine Testdatei mit Includes.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

Auf die Includes folgen dann die Funktionen `setUp()` und `tearDown()`.
Bisher verwendet keine Übung sie (die Funktionskörper sind leer), dennoch müssen sie vorhanden bleiben, damit die Testdateien auf allen Plattformen korrekt kompiliert werden.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

Als Nächstes kommen alle Hilfsfunktionen, die von den Testfunktionen verwendet werden.
Die Namen solcher Hilfsfunktionen sollten nicht das Präfix `test_` verwenden.

Danach kommen die Testfunktionen selbst.
Die Namen dieser Funktionen verwenden das Präfix `test_`.
Mit Ausnahme der ersten sollte jede Testfunktion `TEST_IGNORE();` als erste Anweisung enthalten.
Nach dem ersten Vorkommen sollte der Zeilenkommentar `// delete this line to run test` stehen.

Zum Beispiel:

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Zuletzt steht die Funktion `main()` in der Datei.
Der Funktionskörper von main folgt selbst einem bestimmten Aufbau.
Zuerst ein Aufruf von `UNITY_BEGIN()`, gefolgt von einer leeren Zeile, dann die Tests.
Nach dem letzten Test folgt eine weitere leere Zeile, bevor das Ergebnis von `UNITY_END()` zurückgegeben wird.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

# Überblick

Der Speicher wird für ein Programm üblicherweise vom Betriebssystem (OS) in einem allgemeinen Layout abgebildet:

| Adresse | Speicherbereich          |
| :-----: | :----------------------- |
|  hoch   | Stack                    |
|         | ...                      |
|         | Heap                     |
|         | Lese- und Schreibsegment |
|         | Code-/Nur-Lese-Segment   |
| niedrig | reserviert               |

Der Speicher ist in Segmente gegliedert, die wiederum in Abschnitte mit unterschiedlichen Berechtigungen unterteilt sind.

Die Funktionen, die wir bisher definiert haben, lagen alle in **Abschnitt .text**.
Dieser Abschnitt enthält schreibgeschützte, ausführbare Daten.
Andere Abschnitte werden verwendet, um Datenvariablen zu deklarieren, die schreibgeschützt oder beschreibbar sein können, aber nicht ausführbar sind.

## Abschnitt .data

Die initialisierten Daten werden in **[Abschnitt .data][data]** deklariert.

In NASM (The Netwide Assembler, der Assembler, der in diesem Track verwendet wird) hat eine initialisierte Variable einen Namen, eine Direktive, die die Datengröße angibt, und eine Liste von Werten, die durch Kommas getrennt sind.
Jedes davon wird durch ein Leerzeichen von den anderen getrennt, und auf das Label kann optional ein `:` folgen.

Die wichtigsten Direktiven und ihre zugehörigen Datengrößen sind:

| Direktive | Größe   |
| :-------: | :------ |
|    db     | 1 Byte  |
|    dw     | 2 Bytes |
|    dd     | 4 Bytes |
|    dq     | 8 Bytes |

Zum Beispiel deklariert dies eine Byte-Variable mit dem Namen `space` und dem Wert `10`:

```x86asm
section .data
    space db 10
```

In `section .data` deklarierte Variablen sind veränderbar, das heißt, man kann sie lesen und schreiben.
Sie haben außerdem eine _statische_ Speicherdauer, das heißt, sie existieren während der gesamten Laufzeit des Programms.

## Abschnitt .rodata

**Abschnitt .rodata** ähnelt `section .data`.
Beide Abschnitte enthalten initialisierte Daten, die auf dieselbe Weise deklariert werden und dieselbe Speicherdauer haben.

Der Hauptunterschied zwischen ihnen ist, dass Daten in `section .rodata` unveränderlich sind, das heißt schreibgeschützt.

~~~~exercism/note
Konstanten, die mit `equ` definiert werden, unterscheiden sich von denen, die in `section .rodata` definiert werden.

Eine mit `equ` definierte Konstante belegt keinen Speicherplatz und wird vom Assembler direkt durch ihren Wert ersetzt.
Sie ist tatsächlich ein Platzhalter für diesen Wert.

Konstanten, die dagegen in `section .rodata` definiert werden, sind wirklich im Speicher abgelegt und haben eine Adresse.
~~~~

## Zugriff auf Daten

### Labels und Indirektion

Deklarierte Daten müssen einen Namen haben, der ihnen zugeordnet ist.
Dieser Name heißt **Label**.

Ein Label ist ein Symbol, das die konkrete Adresse der Daten im Speicher kodiert.
**Adressen in x86-64 sind 64-Bit-Werte**.
Ein Wert, der eine solche Adresse enthält, ob er in einem Register gehalten oder im Speicher abgelegt wird, ist das, was höhere Programmiersprachen einen **[Zeiger][pointer]** nennen.

Wenn du in NASM versuchst, mit dem Label direkt auf Daten zuzugreifen, erhältst du nicht den belegten Speicherbereich, sondern dessen Adresse:

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

Um auf den Inhalt einer Speicheradresse zuzugreifen, musst du sie _dereferenzieren_.
Das nennt man **Indirektion**.

In NASM geschieht das mit `[]`:

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

Es gibt jedoch Situationen, in denen unklar sein kann, wie groß der Speicherbereich ist, auf den dereferenziert wird.
In diesen Fällen musst du ein Präfix angeben, das diese Größe festlegt.

Dies sind die wichtigsten Präfixe und ihre Größen in einem typischen x86-64-Programm:

| Präfix | Größe   |
| :----- | :------ |
| byte   | 1 Byte  |
| word   | 2 Bytes |
| dword  | 4 Bytes |
| qword  | 8 Bytes |

Derselbe Ladevorgang kann mit explizit angegebener Größe geschrieben werden:

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

Es ist gute Praxis, beim Dereferenzieren von Speicher immer ein Präfix zu verwenden.

### In den Speicher schreiben

Das Schreiben in den Speicher funktioniert genauso, indem du eine Adresse dereferenzierst:

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

Beachte, dass du in den meisten Befehlen Speicheroperanden verwenden kannst, ohne den Inhalt vorher in ein Register zu laden.
Normalerweise ist es aber nicht möglich, sie sowohl als Quell- als auch als Zieloperand zu verwenden, sondern nur als einen von beiden:

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### Der LEA-Befehl

Obwohl du mit einem `mov` die Adresse einer Variablen in einem Register speichern kannst, gibt es einen Befehl, der genau diesem Zweck dient: **[lea][lea]**.

Dieser Befehl verwendet einen Operanden in Speicherform, liest aber _nicht_ den Speicher.
Stattdessen berechnet er den Ausdruck der effektiven Adresse und schreibt das Ergebnis in den Zieloperanden:

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

Es ist idiomatischer, `lea` zu verwenden, um Speicheradressen zu berechnen und in Registern zu speichern.

### Relative Adressierung

Beim Zugriff auf Speicherstellen erzeugt NASM standardmäßig **absolute Adressen**, das heißt feste Speicheradressen.

Aus Sicherheitsgründen werden ausführbare Dateien oft als **PIE (Position Independent Executable)** gebaut, bei dem die Speicherbereiche an zufälligen Stellen platziert werden.
In einem `PIE` ist die endgültige Adresse einer Variablen zur Linkzeit nicht bekannt.
Statttdessen berechnet der Code Adressen als Offset vom Wert in einem speziellen Register namens `rip`, das auf den nächsten auszuführenden Befehl zeigt.

Das nennt man üblicherweise **RIP-relative Adressierung**.

In NASM kannst du den RIP-relativen Zugriff mit dem **[rel-Operator][rel]** anfordern:

```x86asm
mov rax, qword [rel variable]
```

Die relative Adressierung kann für eine Quelldatei auch zum Standard gemacht werden, indem `default rel` an den Anfang gesetzt wird.

Alle Übungen in diesem Track werden als `PIE` kompiliert und gelinkt, also sollte `rel` verwendet werden, um relative Adressen zu erzeugen.

Das oben erwähnte zufällige Layout ist eine Schutzmaßnahme, die als Address Space Layout Randomization bekannt ist.
Indem sie die Basis jedes Speicherbereichs unvorhersehbar macht, entzieht sie einem Angreifer die festen Adressen, auf die sich viele Exploit-Techniken verlassen, und `PIE` ist es, was den Loader diese Bereiche überhaupt irgendwo platzieren lässt.

Deshalb ist die absolute Adressierung in diesem Track nicht nur unerwünscht, sondern schlicht unbrauchbar.
Eine absolute Referenz wie `[abs variable]` verlangt vom Assembler, eine feste 32-Bit-Adresse in den Befehl einzubetten.
Unter Linux lehnt der `PIE`-Linker die Relokation ab, die dadurch entsteht, und unter macOS unterstützt das Format `macho64` 32-Bit-Absolutadressen überhaupt nicht, sodass die Datei nicht assembliert werden kann.

Die RIP-relative Adressierung vermeidet beide Probleme, denn der Befehl kodiert nur einen Offset relativ zu `rip` und niemals eine feste Adresse.
Die idiomatische Art, unter `PIE` eine Adresse in ein Register zu laden, ist daher `lea` mit einem `rel`-Operanden:

```x86asm
default rel

section .data
    variable dq 7

section .text
fn:
    lea rax, [rel variable]       ; materialize the address (PIE-safe)
    mov rcx, qword [rel variable] ; load the value through a RIP-relative access
    ...
```

### Sichtbarkeit

Labels (Funktionen und Daten), die in einem beliebigen Abschnitt definiert sind (z. B. `.text`, `.data`, `.rodata`), sind innerhalb derselben Quelldatei sichtbar.
Wenn sie als `global` deklariert sind, sind sie auch für andere Quelldateien sichtbar.

Umgekehrt sind Labels, die in anderen Quelldateien definiert sind, für die aktuelle Quelldatei sichtbar, wenn sie als `extern` deklariert sind.
In diesem Fall gibt es im Assemblercode keinen Hinweis auf die Datengröße; diese muss im Voraus bekannt sein.

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

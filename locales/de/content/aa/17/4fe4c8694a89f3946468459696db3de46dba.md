# Über

## Kontext zu Fehlern hinzufügen

Wir haben die grundlegende Fehlerbehandlung in Go im [Fehler-Konzept][concept-errors] behandelt.
Wie du dort gelernt hast, tragen Fehler standardmäßig keinen Stacktrace mit sich.
Deshalb ist es entscheidend, sicherzustellen, dass der Fehler selbst genug Informationen enthält, um das Problem zu identifizieren.

Wenn wir mit den uns bereits bekannten Werkzeugen Informationen zu einem bestehenden Fehler hinzufügen wollten, könnten wir etwa Folgendes schreiben, um einen neuen Fehler mit dem kombinierten Text aus dem ursprünglichen Fehler und den zusätzlichen Informationen zu erstellen:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Zum Glück enthält das Paket `fmt` aus der Standardbibliothek dafür eine Kurzform in Form der Funktion `Errorf`.
Damit kannst du zum Beispiel ganz einfach Informationen über den Kontext hinzufügen, in dem der Fehler aufgetreten ist.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Wenn du nicht sicher bist, dass der Fehler bereits genug Informationen enthält, solltest du dir angewöhnen, einem Fehler immer Kontext hinzuzufügen, bevor du ihn aus einer Funktion zurückgibst.
Das heißt, dein Standardmuster für die Fehlerbehandlung sollte so aussehen:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Wie in den Beispielen gezeigt, trennt man konventionell den Fehler und die hinzugefügte Nachricht durch einen Doppelpunkt.
Genau wie die Nachricht des ursprünglichen Fehlers sollte auch die Kontextnachricht nicht großgeschrieben werden, und am Ende sollte kein Punkt gesetzt werden.

~~~~exercism/note
Wenn du einem Fehler Kontext hinzufügst, ist es verlockend, die Nachricht mit „failed to ..." oder Ähnlichem zu beginnen.
Da ein Fehler jedoch, während er die Funktionskette hinaufwandert, viel zusätzlichen Kontext ansammeln kann, kann dies die endgültige Nachricht, die protokolliert wird oder die der Nutzer sieht, schwerer lesbar machen oder mit Wiederholungen füllen.

Hier ein Beispiel zur Veranschaulichung:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Denk also beim Schreiben der Kontextnachrichten an dieses Endergebnis und verzichte darauf, Text darüber hinzuzufügen, dass etwas nicht wie erwartet verlaufen ist.
Das wird in der Regel aus dem Kontext (z. B. Log-Level „ERROR") und der ursprünglichen Fehlernachricht deutlich.
~~~~

Oft ist diese Art, einem Fehler Informationen hinzuzufügen, gut genug, aber es gibt Fälle, in denen du dem Konsumenten deines Fehlers erlauben möchtest, den ursprünglichen zugrunde liegenden Fehler zu prüfen oder abzurufen.
Kontext so hinzuzufügen, dass dies möglich ist, nennt man in Go „einen Fehler umhüllen".

## Fehler umhüllen und auf Sentinel-Fehler prüfen

Das Umhüllen von Fehlern lässt sich mit einer sehr kleinen Änderung am oben gezeigten Code erreichen.
Um einen Fehler zu umhüllen, musst du das Formatierungsverb `%w` anstelle von `%v` verwenden.
Im Hintergrund sorgt das dafür, dass der resultierende Fehler eine `Unwrap`-Methode implementiert, die den ursprünglichen Fehler zurückgibt.
Dadurch kann dann `errors.Is` verwendet werden, um zu prüfen, ob ein bestimmter Sentinel-Fehler irgendwo entlang der „Fehlerkette" auftaucht.
Das macht es, indem es heimlich wiederholt `Unwrap` aufruft, bis der fragliche Fehler gefunden wurde oder die Kette endet.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Die Prüfung auf den ursprünglichen Fehler mit `errors.Is` würde mit dem regulären Formatierungsverb `%v` nicht funktionieren.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Folglich ist es gute Praxis, standardmäßig `%v` zu verwenden und `%w` nur dann einzusetzen, wenn du deinem Konsumenten ausdrücklich den Zugriff auf einen zugrunde liegenden Fehler ermöglichen möchtest ([Google-Go-Styleguide][google-go-styleguide]).

Wenn du in eine Situation kommst, in der du auf einen Sentinel-Fehler prüfen, aber ausdrücklich nicht entpacken möchtest, kannst du `==` anstelle von `errors.Is` verwenden.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Im Gegensatz dazu würde `==` den Fehler nicht erkennen, wenn er umhüllt wurde.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Es ist in Ordnung, standardmäßig mit `errors.Is` zu arbeiten, aber du solltest dir immer bewusst sein, dass dabei die gesamte Fehlerkette durchsucht wird.

## Auf (benutzerdefinierte) Fehlertypen prüfen

Es gibt ein Gegenstück zu `errors.Is`, mit dem du einen Fehler eines bestimmten Typs aus der Fehlerkette prüfen und abrufen kannst.
Die Funktion dafür ist `errors.As`, und genau wie `errors.Is` sucht sie entlang der gesamten Kette nach dem angegebenen Fehlertyp.
`errors.As` extrahiert den passenden gefundenen Fehler erst dann, sodass du weiter damit arbeiten kannst, z. B. bestimmte Felder auslesen.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Sei vorsichtig mit der Syntax in Bezug auf die obigen Pointer.
Der Code funktioniert und kompiliert nur dann korrekt, wenn `customError` genau den Typ hat, der das Fehler-Interface implementiert.
In unserem Fall ist das `*MyCustomError` (ein [Pointer][concept-pointers] auf `MyCustomError`), nicht `MyCustomError` selbst.

Darüber hinaus muss das zweite Argument ein Pointer auf die Fehlervariable sein.
Da unser Fehler bereits ein Pointer ist, übergeben wir an `errors.As` einen Pointer auf einen Pointer (auf MyCustomError).
Nur wenn das korrekt eingerichtet ist, kann Go die Variable mit dem gefundenen Fehler füllen.
~~~~

Wie zuvor hätte `errors.As` den Fehlertyp nicht gefunden, wenn beim Aufruf von `Errorf` `%v` verwendet worden wäre.

Wenn du aus irgendeinem Grund nicht entpacken möchtest, kannst du stattdessen eine Type Assertion verwenden (entspricht `==` oben).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

Eine Type Assertion kann den Fehlertyp nicht identifizieren, wenn der Fehler umhüllt worden wäre.

## Fehler benutzerdefinierter Typen entpackbar machen

Manchmal reicht es nicht aus, einen Fehler nur mit etwas zusätzlichem Text zu umhüllen.
Stattdessen kannst du einen benutzerdefinierten Fehlertyp erstellen, der den ursprünglichen Fehler und die zusätzlichen strukturierten Daten enthält, die du hinzufügen möchtest.
Wenn du das Entpacken für deinen Fehlertyp ermöglichen möchtest, musst du lediglich manuell eine `Unwrap() error`-Methode hinzufügen, damit das `Unwrap`-Interface erfüllt wird.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Mehrere Fehler kombinieren

In Go 1.20 wurde eine neue Funktion `Join` zum eingebauten Paket `errors` hinzugefügt.
`Join` ermöglicht es, mehrere Fehler so zu kombinieren, dass das Entpacken weiterhin möglich bleibt, d. h., dass du entlang der Kette nach einem bestimmten Fehler oder Fehlertyp suchen kannst.
Damit kann die Fehlerkette in Wirklichkeit tatsächlich ein Fehlerbaum sein.
Weitere Informationen findest du in den [Release Notes][release-notes] und der [Dokumentation][doc-join].

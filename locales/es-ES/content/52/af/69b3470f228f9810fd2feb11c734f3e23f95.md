# Contribuir al track de Rust de Exercism

Actualmente, las issues y los pull requests se cierran automáticamente.
Escribe un mensaje en [el foro de Exercism][the Exercism forum] para proponer cambios.
Las contribuciones son muy bienvenidas si se coordinan en el foro.

[the Exercism forum]: https://forum.exercism.org/

## Políticas generales

- [Código de Conducta](https://exercism.org/code-of-conduct)
- [Directrices de Exercism sobre pull requests](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## Herramientas

Hay algunas herramientas en forma de scripts de bash en `bin/`.
Hay muchas más en `rust-tooling/`, que conviene preferir para cualquier cosa que no sea trivial.

También hay una configuración de [`mise`](https://mise.jdx.dev/)
con un par de comandos útiles para interactuar con el repositorio.
No dudes en ampliarla.

Si quieres ejecutar los tests de CI en local, `mise run test` te llevará bastante lejos.

## Excluir tests y añadir tests personalizados

Al crear o actualizar un ejercicio, puede que decidas excluir ciertos tests para que no se generen.
Puedes hacerlo estableciendo `include = false` en `.meta/tests.toml`.
Incluye un comentario explicando el motivo de la exclusión.

Si quieres añadir tests adicionales específicos del track, puedes hacerlo en un archivo `.meta/additional-tests.json`.
Hazlo solo si tienes una buena razón para no subir estos tests a upstream.
Un comentario en el test adicional debería responder a estas preguntas:
- ¿Por qué no se incluye el test en `problem-specifications`, es decir, por qué no resulta de utilidad general para otros lenguajes?
- ¿Por qué resulta útil el test para el track de Rust de todos modos?

## Crear un ejercicio nuevo

Familiarízate con la [documentación de Exercism sobre ejercicios de práctica][Exercism documentation about practice exercises].

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

Ejecuta `mise run add-exercise` y se te pedirá la información mínima
necesaria para generar el stub del ejercicio.
Después, entra en el ejercicio generado y rellena los marcadores de posición que encuentres.
Esto incluye, sobre todo:

- escribir el stub del ejercicio en `src/lib.rs`
- añadir una solución de ejemplo en `.meta/example.rs`
- ajustar `.meta/test_template.tera`

Los tests se generan con el motor de plantillas [Tera].
La entrada de la plantilla son los datos canónicos de [`problem-specifications`].

Encontrarás algunos consejos sobre cómo escribir plantillas de tera [aquí](#tera-templates).

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

En CI se comprueban muchos aspectos de un ejercicio implementado correctamente.
Te recomiendo que, en lugar de pasar mucho tiempo estudiando y escribiendo
documentación sobre el proceso, _simplemente lo hagas_.
Si algo se rompe, arréglalo y añade un test o una automatización
para que no vuelva a pasar.

Si vas a crear un ejercicio de práctica desde cero,
uno que no esté en `problem-specifications`,
tendrás que escribir los tests manualmente.
Los tests deben ordenarse de menor a mayor complejidad,
para que los estudiantes puedan ir dejándolos de ignorar uno a uno y resolver el ejercicio con TDD.
Consulta [la documentación de Exercism](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)
para ver más ideas sobre cómo escribir buenos tests.

Salvo en circunstancias extraordinarias,
el archivo stub debería compilar con `cargo test --no-run`.
Esto nos permite comprobar que las firmas del archivo stub
coinciden con las firmas que esperan los tests.
Para conseguirlo, usa `todo!()` como cuerpo de cada función.
Si hay una razón justificada por la que esto no es posible,
incluye una clave `.custom."allowed-to-not-compile"`
en el `.meta/config.json` del ejercicio con el motivo.

## Actualizar un ejercicio

Muchos ejercicios derivan de [`problem-specifications`].
Esto incluye sus tests y su documentación para el usuario.
Antes de proponer cambios aquí,
comprueba si deberían hacerse en `problem-specifications`.

Ejecuta `mise run update-exercise` para actualizar un ejercicio.
Esto delega la mayor parte del trabajo en `configlet sync --update`
y vuelve a ejecutar el generador de tests.

Cuando actualices un ejercicio que aún no tenga una plantilla de tera,
se generará una nueva automáticamente.
Es probable que tengas que ajustarla en mayor o menor medida.

Encontrarás algunos consejos sobre cómo escribir plantillas de tera [en la siguiente sección](#tera-templates).

## Plantillas de tera

La documentación completa de las plantillas de tera está [aquí][tera-docs].
A continuación se describen algunos enfoques que nos han funcionado para nuestras necesidades concretas.

Seguramente querrás echar un vistazo al `canonical-data.json` del ejercicio para ver cómo son tus datos de entrada.
Puedes usar `bin/symlink_problem_specifications.sh` para enlazar estos datos simbólicamente en el directorio real del ejercicio. ¡Muy práctico!

El nombre de la propiedad de entrada es distinto en cada ejercicio.
La plantilla predeterminada será algo así:

```txt
let input = {{ test.input | json_encode() }};
```

Tendrás que añadir el campo de entrada concreto de este ejercicio, por ejemplo:

```txt
let input = {{ test.input.integers | json_encode() }};
```

Algunos ejercicios pueden tener valores devueltos de error.
Puedes usar un if-else para generar algo distinto
en función de la estructura de los datos:

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

Algunos ejercicios tienen varias funciones que el estudiante debe implementar
y que, por tanto, también hay que testear.
En ese caso, los datos canónicos contienen un campo `property`.
Puedes construir cadenas de if-else basadas en `test.property` y generar una función distinta en función de eso.

Algunos ejercicios tienen sus casos de test organizados en _grupos de tests_.
Tu plantilla tendrá que tenerlo en cuenta.
En muchos casos, puedes simplemente aplanar la estructura. (ejemplo: [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
Sin embargo, a veces los tests tienen la misma descripción en grupos distintos, lo que provoca conflictos de nombres si se aplana la estructura.
En ese caso, puedes usar la descripción del grupo para organizar los tests en módulos. (ejemplo: [`forth`](/exercises/practice/forth/.meta/test_template.tera))

Hay algunos filtros de tera personalizados en [`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs).
Esta es la lista, con suerte actualizada:
- `to_hex` formatea los enteros en hexadecimal
- `make_ident` convierte un string arbitrario en un identificador de Rust decente.
   Muy útil para generar nombres de funciones a partir de las descripciones de los tests.
- `fmt_num` formatea literales numéricos (inserta `_` cada tres dígitos)

No dudes en añadir los tuyos en el crate `rust-tooling`.
Esperemos que te acuerdes de actualizar también esta lista. 🙂

Para ver un ejemplo bastante complicado, echa un vistazo a la plantilla de tests de `triangle`.
Organiza los casos de test en módulos y detecta dinámicamente qué tests poner detrás de feature gates.
Ese ejercicio también reimplementa algunos casos de test de upstream en `additional-tests.json`, para añadirles la información adicional necesaria para generar buenos tests.

[tera-docs]: https://keats.github.io/tera/docs/#templates

## Temario

El temario está actualmente desactivado debido a su baja calidad.
Consulta [esta publicación del foro](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)
para saber algo más sobre el contexto de la decisión.

Crear un temario mejor sería muy beneficioso,
pero es mucho trabajo y requiere buena comunicación y coordinación.
Asegúrate de comentar en el foro cualquier plan que tengas
con personas que tengan experiencia creando temarios.

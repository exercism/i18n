# Introducción

Los hilos de Factor son *corrutinas cooperativas*: comparten un único hilo del sistema operativo, se ceden el control entre sí en las operaciones de E/S y en los puntos de cesión explícitos, y nunca se ejecutan realmente al mismo tiempo. Todo lo que haces *entre* cesiones ocurre como un paso ininterrumpido. Pero si una operación compuesta (leer, modificar y escribir) cede el control a mitad de camino, otro hilo puede colarse y cambiar el mundo antes de que termines, y eso es una condición de carrera.

Este ejercicio cubre cuatro primitivas que aparecen una y otra vez:

## `parallel-map`: fork/join sobre una secuencia

```
parallel-map ( seq quot: ( elt -- newelt ) -- newseq )
```

En [`concurrency.combinators`][combinators]. Crea un hilo por cada elemento, ejecuta la quotation y recoge los resultados en una nueva secuencia en el mismo orden:

```factor
USING: concurrency.combinators sequences ;

{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }
```

## `spawn`: iniciar un hilo

```
spawn ( quot name -- thread )
```

En [`threads`][threads]. La quotation se ejecuta de forma concurrente; `name` es una etiqueta para depurar. El manejador de hilo que se devuelve no tiene mucho interés a este nivel: usa `drop` para descartarlo.

## Promesas: traspaso de un valor de un solo uso

```
<promise>           ( -- promise )
fulfill             ( value promise -- )
?promise            ( promise -- value )
```

En [`concurrency.promises`][promises]. Una promesa es un buzón de un solo uso: un hilo la cumple, otros la leen. `?promise` se bloquea hasta que la promesa se ha cumplido y luego devuelve el valor.

```factor
USING: concurrency.promises kernel threads ;

<promise> [
    [ 42 swap fulfill ] curry "answer" spawn drop
] keep ?promise .
! => 42
```

`spawn` + `<promise>` es aquello con lo que está construido `parallel-map`; hacerlo a mano es útil cuando cada tarea hace algo distinto de «calcular un elemento».

La típica forma de dispersión y unión sobre una secuencia es: para cada entrada crear una promesa nueva, crear un hilo que haga el trabajo y `fulfill` la promesa, reunir todas las promesas en una secuencia y luego aplicar `?promise` a cada una para esperar a que terminen. Las variables locales hacen que esto sea legible: vincula la promesa a un nombre con `:>` dentro de una lambda `[| | ]` para que la quotation creada pueda capturarla en su cierre:

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
inputs [| x |
    <promise> :> p
    [ x do-work t p fulfill ] "worker" spawn drop
    p
] map [ ?promise drop ] each
```

## Bloqueos: exclusión mutua

```
<lock>     ( -- lock )
with-lock  ( lock quot -- )
```

En [`concurrency.locks`][locks]. Solo un hilo puede mantener un bloqueo concreto a la vez. `with-lock` lo adquiere, ejecuta la quotation y lo libera, incluso si la quotation lanza una excepción.

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
USING: concurrency.locks kernel locals ;

[let <lock> :> guard
    guard [ ! exclusive section ! ] with-lock
]
```

Usa un bloqueo siempre que un valor sea *leído o escrito por más de un hilo* y las operaciones sobre él no sean atómicas de forma natural. Tanto las lecturas como las escrituras necesitan el bloqueo: una lectura que cede el control a mitad de camino puede ver un estado a medias.

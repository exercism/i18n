# Generador de tests del track de Python de Exercism

El track de Python usa un script generador y plantillas de [Jinja2][Jinja2] para
crear los ficheros de test a partir de los [datos canónicos][canonical data] de Exercism.

## Uso del script

La generación de tests requiere una copia local del repositorio
[problem-specifications][problem-specifications]. El script debe ejecutarse desde el
directorio raíz `python`, para poder acceder correctamente a los ejercicios.

Ejecuta `bin/generate_tests.py --help` para consultar la información de uso.


## Plantillas de test

Las plantillas de test admiten la sintaxis de [Jinja2] y tienen disponibles las
siguientes variables de contexto de los datos canónicos:
- `exercise`: el nombre del ejercicio con guiones (p. ej., `two-fer`)
- `version`: la versión de los datos canónicos (p. ej., `1.2.0`)
- `cases`: un array de objetos de caso o un array de arrays `cases`. Para ver la
estructura exacta del ejercicio en el que trabajas, consulta
`canonical-data.json`
- `has_error_case`: indica si algún caso de test espera que se lance un
error (p. ej., `False`)
- `additional_cases`: tiene una estructura similar a `cases`, pero se rellena desde el fichero `.meta/additional_tests.json` del ejercicio, si existe (para ver un ejemplo, consulta `exercises/word-count/.meta/additional_tests.json`)

Además, se añaden los siguientes filtros de plantilla para mayor comodidad:
- `to_snake`: convierte un string a snake_case (p. ej., `{{ "CamelCaseString" | to_snake }}` -> `camel_case_string`)
- `camel_case`: convierte un string a CamelCase (p. ej., `{{ "snake_case_string" | camel_case }}` -> `SnakeCaseString` )
- `error_case`: comprueba si un caso de test espera que se lance un error (p. ej., `{% for case in cases%}{% if case is error_case}`)
- `regex_replace`: reemplazo de strings mediante expresiones regulares (p. ej., `{{ "abc123" | regex_replace("\\d", "D") }}` -> `abcDDD`)


### Convenciones

- Las macros de uso general para estructuras de plantilla muy repetidas se definen en `config/generator_macros.j2`.
  - Se pueden importar así:
  `{%- import "generator_macros.j2" as macros with context -%}`
- Todas las plantillas de test deben terminar con `{{ macros.footer() }}`.
- Todos los nombres de clase de Python deben estar en CamelCase (p. ej., `TwoFer`).
  - Conviértelos con `{{ "two-fer" | camel_case }}`
- Todos los nombres de módulo y de función de Python deben estar en snake_case
(p. ej., `high_scores`, `personal_best`).
  - Conviértelos con `{{ "personalBest" | to_snake }}`
- Los tests específicos del track se definen en el fichero de opciones `.meta/additional_tests.json`. El objeto JSON definido en este fichero debe
tener una única clave, `cases`, con la misma estructura que `cases` en
`canonical-data.json`.
- Los tests específicos del track deben colocarse después de los tests canónicos en los
ficheros de test.
- Los tests específicos del track deben marcarse en el fichero de test con el siguiente comentario:
```
# Additional tests for this track
```


### Estructura

La mayoría de las plantillas tendrán un aspecto similar a este:

```Jinja2
{%- import "generator_macros.j2" as macros with context -%}
{{ macros.header() }}

class {{ exercise | camel_case }}Test(unittest.TestCase):
    {% for case in cases -%}
    def test_{{ case["description"] | to_snake }}(self):
        value = {{ case["input"]["value"] }}
        expected = {{ case["expected"] }}
        self.assertEqual({{ case["property"] }}(value), expected)

    {% endfor %}

{{ macros.footer() }}
```


### Sobrescribir las importaciones

Los nombres importados en `macros.header()` se pueden sobrescribir añadiendo
un array de nombres alternativos que importar (p. ej.: `clock`):

```Jinja2
{{ macros.header(["Clock"])}}
```


### Ignorar propiedades

En raras ocasiones, puede ser necesario filtrar las propiedades que
no se prueban en este track. La macro `header` también acepta un
argumento `ignore` (p. ej., `high-scores`):

```Jinja2
{{ macros.header(ignore=["scores"]) }}
```

## Crear una plantilla

1. Crea el fichero `.meta/template.j2` para el ejercicio que estás implementando
  y ábrelo en tu editor.
2. Copia y pega el [ejemplo de estructura](#estructura) en el fichero de plantilla
  y guárdalo.
3. Haz los cambios necesarios en el fichero de plantilla hasta que produzca
  código de test válido, consultando el `canonical-data.json` del ejercicio para
  los nombres de entrada y la estructura de los casos.
    - Usa las [macros disponibles](../config/generator_macros.j2) para evitar reescribir las secciones estandarizadas.
    - Si estás implementando una plantilla para un ejercicio existente,
    no es obligatorio que coincida exactamente con la estructura del fichero
    de test existente, pero reducir las diferencias hará que la revisión del PR sea mucho más fluida para todos.

# Acerca de

A estas alturas del temario, ya has visto muchas definiciones de funciones.
Normalmente se presentaban sin comentar apenas la salida del REPL:

```julia-repl
julia> f(x) = x^2
f (generic function with 1 method)
```

¿Por qué aparece _«generic function with 1 method»_?

Supongamos que queremos ser más específicos con los tipos de los argumentos.

```julia-repl
julia> f(x::Integer) = x^2
f (generic function with 2 methods)

julia> f(x::Real) = x^2
f (generic function with 3 methods)
```

O podemos cambiar el número de argumentos:

```julia-repl
julia> f(x, y) = x * y
f (generic function with 4 methods)
```

Parece que las nuevas definiciones de una misma función se llaman «métodos».
Los métodos se añaden a una lista, en lugar de sobrescribir la definición anterior.

Podemos listar los métodos fácilmente:

```julia-repl
julia> methods(f)  # output edited for brevity
# 4 methods for generic function "f" from Main:
 [1] f(x, y)
 [2] f(x::Integer)
 [3] f(x::Real)
 [4] f(x)
 ```

Si llamamos a la función `f`, Julia de algún modo sabe qué método usar:

```julia-repl
julia> f(2.5)  # Float64
6.25

julia> f(2)  # Int64
4

julia> f(2, 3)  # Int64, Int64
6
```

## ¿Qué es una función?

Según el [manual][function], una función es un objeto que asigna una tupla de argumentos a un valor devuelto.
Se parece bastante a la definición que usan los matemáticos.

Normalmente pensamos en los argumentos de la función en `f(2, 3)` como dos elementos separados, pero el compilador los ve como una sola [tupla][tuple].
Esto es cierto incluso para un único argumento (aunque hay que añadir una coma para que quede más claro):

```julia-repl
julia> typeof( (2, 3) )
Tuple{Int64, Int64}

julia> typeof( (2,) )
Tuple{Int64}
```

Si vemos la función como una caja negra, podemos decir que entra una tupla y sale un valor devuelto.
Más formalmente, la tupla se _asigna_ a un valor devuelto.

## ¿Cómo manejan las funciones distintos números y tipos de argumentos?

A esto se le suele llamar [«polimorfismo»][polymorphism].

Ha sido un tema central en la informática durante varias décadas, y se han adoptado distintos enfoques.

El enfoque de Julia es poco habitual, aunque no único.

- Las funciones son [«genéricas»][generic], lo que significa que pueden tener varios métodos asociados.
- Las funciones no son más que nombres hasta que se les asocian métodos.
- Se pueden añadir métodos según se necesiten, potencialmente en gran cantidad (el operador `+` es una función con 161 métodos, actualmente).
- Cuando se llama a una función, Julia examina la signatura de la llamada: el número de argumentos y el tipo actual de cada uno.
- Se selecciona el método que mejor coincide con la signatura de la llamada.
  - En general, el número de argumentos debe coincidir exactamente (aunque el operador [splat/slurp][splat] `...` puede saltárselo en parte).
  - Se prefieren los métodos cuyos tipos coinciden exactamente con la signatura de la llamada.
  - Si es necesario, Julia examina los supertipos de cada argumento de la signatura de la llamada para encontrar el método que mejor coincide y es más específico.
- El método elegido se somete a [`dispatched`][dispatch] con los argumentos dados y devuelve un resultado.
- Si no se encuentra ningún método adecuado, se lanza un [`MethodError`][methoderror].

Ten en cuenta que Julia tiene tipado dinámico, así que el despacho de métodos ocurre en _tiempo de ejecución_.

## Despacho múltiple: un ejemplo

La sección anterior tenía muchas palabras, así que traduzcamos esas ideas a código.
Por simplificar, las funciones de abajo tienen un solo argumento, pero no es raro encontrar funciones con docenas de argumentos (como en los paquetes de gráficos o en el aprendizaje automático).

Empecemos definiendo algunos tipos personalizados para representar figuras geométricas.

```julia-repl
julia> abstract type Shape end

julia> struct Circle <: Shape
           radius::Float64
       end

julia> struct Square <: Shape
           side::Float64
       end

julia> struct Rectangle <: Shape
           length::Float64
           width::Float64
       end
```

A continuación podemos definir métodos para calcular el área de cada figura.
Cada uno recibe un argumento, de un tipo concreto distinto, definido por el usuario, en cada caso.

```julia-repl
julia> area(c::Circle) = π * c.radius^2
area (generic function with 1 method)

julia> area(s::Square) = s.side^2
area (generic function with 2 methods)

julia> area(r::Rectangle) = r.length * r.width
area (generic function with 3 methods)
```

Ahora podemos crear algunas figuras y calcular las áreas, confiando en el mecanismo de despacho de Julia para usar la fórmula correcta en cada caso.

```julia-repl
julia> circle = Circle(2.3)
Circle(2.3)

julia> area(circle)  # call signature Tuple{Circle}
16.619025137490002

julia> square = Square(1.6)
Square(1.6)

julia> area(square)  # call signature Tuple{Square}
2.5600000000000005

julia> rectangle = Rectangle(1.4, 2.1)
Rectangle(1.4, 2.1)

julia> area(rectangle)  # call signature Tuple{Rectangle}
2.94
```

## [Métodos paramétricos][parametric]

Las signaturas de los métodos pueden tomar valores de tipo ficticios, más o menos igual que los tipos paramétricos.

La sintaxis es peculiar y requiere una cláusula `where`:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T} = true
same_type (generic function with 1 method)

julia> same_type([1, 2], 3)
true

julia> same_type([1, 2], "three")
ERROR: MethodError: no method matching same_type(::Vector{Int64}, ::String)
```

El ejemplo anterior exige que ambos argumentos usen el mismo tipo `T`, sea cual sea.

Podemos ser más específicos imponiendo una restricción a `T`:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T<:Number} = true
same_type (generic function with 2 methods)
```

Con este método, solo los tipos numéricos idénticos devuelven `true`.

Se pueden usar varias variables ficticias, separadas por comas en la cláusula `where`.
Los dos métodos siguientes se parecen:

```julia-repl
julia> func(v::Vector{Number}, x::Number) = true
func (generic function with 1 method)

julia> func(v::Vector{S}, x::T) where {S<:Number, T<:Number} = true
func (generic function with 2 methods)
```

Una diferencia es que los valores de tipo `S` y `T` están disponibles para usarlos dentro del cuerpo de la función del segundo método.
Es el tipo de truco que quizá no uses a menudo, pero que en algunas circunstancias puede ahorrarte muchos problemas.

Por ejemplo, en la siguiente definición de tipo paramétrico, los campos deben ser del mismo tipo `T`, que está restringido a ser un subtipo de `Real`:
```julia
struct Point{T<:Real}
    x::T
    y::T
end
```
Esta definición de `Point` acepta una `x` y una `y` del mismo tipo, o puede aceptar una `x` y una `y` de tipos distintos, pero en ese caso hay que indicar un tipo de conversión explícito.
```julia-repl
julia> Point(4, 5)
 Point{Int64}(4, 5)

julia> Point(3.5, 2)
 MethodError: no method matching Point(::Float64, ::Int64)    # Output truncated for brevity

julia> Point{Float32}(3.5, 2)
 Point{Float32}(3.5f0, 2.0f0)

julia> Point{Int64}(3.5, 2) 
 InexactError: Int64(3.5)      # Output truncated for brevity
```
Aunque este nivel de control sobre los tipos puede ser deseable, también puede resultar útil tener algo de abstracción.
```julia
Point(x::T, y::S) where {T<:Real, S<:Real} = Point{promote_type(T,  S)}(x, y)
```
Este constructor externo lo consigue permitiendo que un `Point` acepte tipos no homogéneos para `x` y `y` sin especificar explícitamente el tipo de conversión.
Los valores de tipo `T` y `S` se usan en el cuerpo de la función, en `promote_type(T, S)`, para aportar el tipo de conversión explícito a la definición original.
```julia-repl
julia> Point(3.5, 2)
 Point{Float64}(3.5, 2.0)
```

## Comparación con otros lenguajes

Como Julia examina todos los argumentos al seleccionar un método, a esto se le llama [`multiple dispatch`][multiple-dispatch].

Unos pocos lenguajes permiten el despacho múltiple, como Common Lisp, aunque rara vez es tan central en el diseño del lenguaje como en Julia.

En cambio, en un lenguaje orientado a objetos (POO), por ejemplo Ruby, los métodos se suelen llamar sobre una [instancia][instance].
La definición ahora privilegia el primer argumento (con un nombre como `self` o `this` en la definición), y para llamar al método, su nombre se escribe a continuación de la instancia, separado por un punto:

```ruby
irb(main):004:0> "abc".sub("b", "*")
=> "a*c"
```

A esto se le llama [`single dispatch`][single-dispatch], ya que para elegir un método solo se usa la clase de la instancia (la del string «abc» en el ejemplo anterior).

Algunos lenguajes POO con tipado estático admiten el polimorfismo de métodos, que se parece bastante al despacho múltiple.
La gran diferencia es que la selección del método solo ocurre en _tiempo de compilación_.

Los lenguajes funcionales suelen tener una única definición de función, con algún tipo de expresión Select/Case/Match para manejar las distintas posibilidades.
Tú escribes tu propia lógica, normalmente con la ayuda de una sintaxis concisa de coincidencia de patrones de la que Julia carece.
Por supuesto, Julia también hace una forma de coincidencia de patrones, pero en el despacho en lugar de dentro del cuerpo de la función.

## Conclusión

El despacho múltiple es muy flexible y tiene un rendimiento muy alto en Julia, por lo que se usa muchísimo.

Como sugiere el ejemplo de los 161 métodos de `+`, quienes programan en Julia procuran definir métodos con tipos muy específicos.
Sumar dos enteros es muy distinto de sumar dos números de coma flotante a nivel de bytecode, y sumar un entero a un número de coma flotante añade además la complicación de la promoción de tipos.

Cuanto más específico es el tipo, más optimizaciones puede hacer el compilador: algo de importancia marginal en un ejercicio de juguete en Exercism, pero vital para el rendimiento en las grandes simulaciones numéricas para las que Julia fue diseñado.

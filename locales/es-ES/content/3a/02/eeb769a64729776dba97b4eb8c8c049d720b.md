# Acerca de

En las aplicaciones de C#, la aleatoriedad se implementa generalmente mediante la clase `System.Random`.

Este [artículo][system-random] es una excelente introducción al tema.

Cuando te familiarizas con una clase de una biblioteca, siempre merece la pena estudiar la [documentación][system-random] de sus propiedades y métodos y de sus sobrecargas.

El ejercicio de programación puso de manifiesto varias cuestiones:

- El generador de números aleatorios no requiere una [semilla][random-seedless].
- `Random.Next()` puede generar un rango de números enteros
- `Random.Double()` puede generar un número decimal entre 0 y 1
- Los límites superiores de `Next...()`, `Double()` y `Sample()` son **exclusivos**, de modo que `Random.Next(1,19)` producirá valores del 1 al 18, pero no el 19.
- Una vez que tienes tu número aleatorio, puedes hacer con él lo que quieras

Hay 3 patrones para implementar este último punto:

- Puedes obtener el número aleatorio y manipularlo. En el caso del ejercicio de programación, esto consistiría en llamar a `Random.NextDouble()` y multiplicar por 100. Este [artículo][random-use-case-array] trata sobre cómo hacer selecciones aleatorias de un array.
- Puedes heredar de `System.Random` y sobrescribir el método `Sample()`.
- Puedes encapsular una instancia de `System.Random` como miembro de una clase propia, por ejemplo, para generar valores Boolean. Consulta estos [casos de uso][random-use-cases].

No se garantiza que los números generados por `Random` sean únicos.

Se [recomienda][random-thread-safety] que instancies `System.Random` como miembro estático. Pero ten en cuenta que no es seguro para subprocesos.

Puede que veas documentación que desaconseja el uso de constructores sin semilla. Esto se aplica sobre todo a .NET Framework, y no a .NET Core (que es lo que usa _Exercism_). Para conocer toda la historia, lee [esto][random-multiple-instantiations].

Se te recomienda no usar `System.Random` para criptografía ni para seguridad. Consulta este [proveedor][crypto-provider] y este [generador de números][crypto-rng].

## Seguridad para subprocesos

Cuando se aplica en el contexto de las API de bibliotecas, «no es seguro para subprocesos» es simplemente una forma abreviada de decir que, si es probable que accedas a instancias de la clase a través de varios [subprocesos][threading] concurrentes, deberías proporcionar tus propios mecanismos de sincronización de subprocesos o, en el caso de las colecciones, plantearte la posibilidad de usar una versión concurrente de la clase. Si no tomas estas precauciones, es probable que se produzcan [condiciones de carrera][so-race-conditions]. Si tu base de código no usa varios subprocesos, y no es probable que llegue a hacerlo, esta advertencia apenas te preocupará.

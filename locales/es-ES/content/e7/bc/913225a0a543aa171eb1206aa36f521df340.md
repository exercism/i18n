# Generadores de tests

Los generadores de tests permiten que los tracks generen tests automáticamente sin tener que escribirlos nosotros mismos. Cada generador de tests lee los `canonical data` del ejercicio, que definen el nombre del test, sus entradas y sus salidas. Puedes leer más sobre el enfoque de exercism respecto a las suites de tests [aquí](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Generar los tests automáticamente elimina cualquier tipo de error humano al crearlos. Queremos que los tests sean precisos con respecto a sus datos canónicos. La generación de tests también hace mucho más fácil mantenerlos actualizados. A medida que cambian los datos canónicos, los tests se actualizarán automáticamente cuando se ejecute el generador de ese test.

Puedes encontrar un ejemplo de archivo de datos canónicos [aquí](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)

## Términos comunes

Al revisar los datos canónicos y el código base de los generadores, usamos mucha terminología común. Esta lista aclara, con suerte, qué representa cada término.

* Datos canónicos - Representan la suite de tests completa.
* Caso de datos canónicos - La representación de un único caso de test.
* Descripción - El nombre del test.
* Propiedad - El método que se llama al ejecutar el test.
* Entrada - La entrada del caso de test.
* Valor esperado - El valor esperado al ejecutar el caso de test.

## Añadir un generador simple

Añadir un generador de tests es sencillo. Basta con añadir una clase al archivo `Generators.fs` de la carpeta `generators` con el nombre del ejercicio (en PascalCase) y extender la clase abstracta `GeneratorExercise`.

Un ejemplo de generador simple sería el ejercicio Bob. A continuación puedes ver el código fuente, aunque también puedes consultarlo en el repositorio [aquí](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174).

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

Este generador funciona por completo; no hace falta escribir ningún otro código. Sin embargo, su sencillez se debe a que la suite de tests y el propio programa son relativamente triviales.

## Añadir un generador complejo

Para muchos generadores, el comportamiento por defecto de la clase `GeneratorExercise` es suficiente. Sin embargo, para generadores más _complejos_, se puede sobrescribir uno o varios de sus métodos virtuales:

### Método: RenderInput

Renderiza la entrada de un método de test.

#### Ejemplo

El generador `Gigasecond` renderiza el valor de entrada como un valor `DateTime` (entre paréntesis):

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

Ten en cuenta que puedes usar el campo `key` para personalizar la salida solo en campos de entrada concretos. El generador `Yacht` lo hace así:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Método: RenderExpected

Renderiza el valor esperado de un método de test.

#### Ejemplo

El generador `Connect` renderiza el valor esperado como un valor `Option<T>`:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Método: RenderSut

Renderiza el sistema bajo prueba (SUT). Es el valor real que se verifica contra el valor esperado.

#### Ejemplo

El generador `RunLengthEncoding` tiene un caso de test en el que verifica que codificar y luego decodificar la entrada da como resultado el mismo valor. El método `RenderSut` se sobrescribe para convertir lo que sería una única llamada a una función `consistency` inexistente en una cadena de llamadas `encode |> decode`:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Método: RenderArrange

Renderiza la parte arrange del método de test. En esta parte se crea el SUT.

El comportamiento por defecto suele ser el que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

Nota: este método devuelve un `string list`, donde cada `string` corresponde a una única línea renderizada del archivo de test.

### Método: RenderAssert

Renderiza la parte assert del método de test. En esta parte se hace la aserción para verificar el SUT contra el valor esperado.

El comportamiento por defecto suele ser el que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

Nota: este método devuelve un `string list`, donde cada `string` corresponde a una única línea renderizada del archivo de test.

### Método: RenderSetup

Renderiza los métodos adicionales de utilidad o de configuración. Esto se puede usar para definir métodos auxiliares que se puedan usar en los métodos de test.

El código de configuración se añade _antes_ de los métodos de test, para que los métodos de configuración se puedan usar en los métodos de test.

Nota: este método devuelve un `string list`, donde cada `string` corresponde a una única línea renderizada del archivo de test.

#### Ejemplo

El generador `Zipper` añade dos métodos auxiliares que se usan en los métodos de test para eliminar parte del tedioso código repetitivo:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Método: RenderValue

Renderiza un único valor (que se usa para renderizar los parámetros de entrada, el valor esperado y el SUT).

### Ejemplo

El generador `ComplexNumbers` renderiza valores distintos según el tipo del valor:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Método: MapCanonicalDataCase

Mapea el caso de datos canónicos. Puede ser útil si quieres añadir o quitar propiedades.

El comportamiento por defecto suele ser el que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

#### Ejemplo

El generador `ScaleGenerator` usa el mapeo del caso de datos canónicos para añadir una propiedad que falta con el valor `null` (lo que facilita el procesamiento posterior):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Método: PropertiesUsedAsSutParameter

Especifica qué propiedades deben usarse como parámetros del SUT.

El comportamiento por defecto suele ser el que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

#### Ejemplo

El generador `RailFenceCipher` define explícitamente las propiedades usadas como parámetros del SUT para cambiar el orden en que se pasan:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Método: PropertiesWithIdentifier

Especifica qué propiedades deben tener un identificador asignado. Si una propiedad está en esta lista, se le asignará su valor en una línea aparte, a su propio identificador.

#### Ejemplo

El generador `Transpose` ha optado por usar identificadores para todas las propiedades:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Método: IdentifierTypeAnnotation

En algunos casos, quieres que un identificador tenga un tipo explícito. Un caso de uso habitual es cuando un valor es una lista vacía. En esos casos, FsUnit necesita una anotación de tipo para poder ejecutar la aserción correctamente.

#### Ejemplo

El generador `Minesweeper` añade una anotación de tipo `string list` para los valores vacíos:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Método: AdditionalNamespaces

Devuelve una lista de espacios de nombres adicionales que abrir en el archivo de test.

#### Ejemplo

El generador `Gigasecond` trabaja con instancias de `DateTime` y, por tanto, añade su espacio de nombres a la lista de espacios de nombres adicionales:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Método: AssertTemplate

La plantilla de aserción que usar. Puedes encontrar la lista completa de plantillas de aserción en `generators/Templates/_Assert*.liquid`

#### Ejemplo

El generador `RationalNumbers` usa la plantilla `"AssertEqualWithin"` para permitir comprobar la igualdad de los valores double con una tolerancia concreta:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Método: TestFileFormat

El formato del archivo de test: un módulo o una clase.

El comportamiento por defecto es casi siempre el que quieres. Solo en casos extremadamente raros querrás cambiarlo.

#### Ejemplo

El generador `Grep` se define como una clase de test para poder usar métodos de configuración y de limpieza:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Método: TestMethodName

Especifica el nombre del método de test.

El comportamiento por defecto suele ser el que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

#### Ejemplo

El generador `Zipper` hace una pequeña limpieza del nombre del método de test:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Método: UseFullMethodName

Indica si el nombre del método de test que se usa debe usar la ruta completa, lo que significa que, en los casos de test anidados, se antepondrá al nombre del método de test la descripción del caso o casos padres.

El comportamiento por defecto suele ser el que quieres. Solo querrás cambiarlo en los casos en los que, de otro modo, habría varios métodos de test con el mismo nombre.

#### Método: Signature

El generador `KindergartenGarden` usa nombres de método completos para evitar colisiones entre nombres de métodos de test:

```fsharp
override __.UseFullMethodName _ = true
```

### Método: SkipTestMethod

Indica si el método de test debe marcarse con la propiedad `Skip = true`.

El comportamiento por defecto es casi siempre el que quieres. Solo en casos extremadamente raros querrás cambiarlo.

#### Método: Signature

El ejercicio `Markdown` es un ejercicio de refactorización y, como tal, todos sus tests ya deberían estar en un estado válido. Por eso no añade la propiedad `Skip` a ninguno de sus métodos de test:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Actualizar los archivos existentes

Es posible que un ejercicio existente no coincida con los datos canónicos. No pasa nada por actualizar el stub del ejercicio o el ejemplo del ejercicio para que sigan los datos canónicos.

Además, si encuentras algún problema en uno de los generadores o suites de tests existentes, basta con abrir el generador que quieras actualizar, hacer tus cambios y volver a ejecutar los generadores.

## Ejecutar los generadores

Este repositorio está escrito para [.NET Core 2.x](https://www.microsoft.com/net/core). Para ejecutar los generadores, solo tienes que ejecutar el siguiente comando en el directorio de los generadores:

`dotnet run`

Este comando toma todos los generadores de ejercicios definidos y genera todos los casos de test de cada ejercicio. Usamos reflexión para obtener todos los ejercicios, así que, si añades un test nuevo, se incluirá automáticamente al ejecutar el generador.

Si solo necesitas ejecutar un único generador, puedes hacerlo con el siguiente comando:

`dotnet run -e <exercise>`

Una vez ejecutado el generador, puedes ver el resultado de la generación navegando hasta el archivo de test de ese ejercicio. Por ejemplo, la suite de tests del ejercicio Bob se encuentra en:

`exercises/bob/BobTests.fs`

## Enviar un generador

Si estás contento con el resultado de tu generador, ¡nos encantaría que enviaras un pull request! Incluye tu generador, la suite de tests actualizada y cualquier otro archivo correspondiente que hayas cambiado.

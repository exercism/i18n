## Añadir contexto a los errores

Exploramos el manejo básico de errores en Go en el [concepto de errores][concept-errors].
Como aprendiste allí, por defecto los errores no llevan consigo trazas de pila.
Por eso es crucial asegurarse de que el propio error contenga suficiente información para identificar el problema.

Si quisiéramos añadir información a un error existente con las herramientas que ya conocemos, podríamos escribir algo así para crear un nuevo error con el texto combinado del error original y la información adicional:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Por suerte, el paquete `fmt` de la biblioteca estándar contiene una versión abreviada de esto en forma de la función `Errorf`.
Eso te permite, por ejemplo, añadir fácilmente información sobre el contexto en el que ocurrió el error.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

A menos que estés seguro de que el error ya incluye suficiente información, deberías intentar coger el hábito de añadir siempre contexto a un error antes de devolverlo desde una función.
Eso significa que tu patrón estándar de manejo de errores debería tener este aspecto:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Como se muestra en los ejemplos, la convención es separar el error del mensaje añadido con dos puntos.
Al igual que el mensaje del error original, el mensaje de contexto tampoco debe empezar con mayúscula ni llevar punto al final.

~~~~exercism/note
Al añadir contexto a un error, es tentador empezar el mensaje con «failed to ...» o algo similar.
Sin embargo, como un error puede acumular mucho contexto adicional a medida que sube por la cadena de funciones, esto puede hacer que el mensaje final que se registre o que vea el usuario sea más difícil de leer o esté lleno de duplicaciones.

Aquí tienes un ejemplo para ilustrarlo:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Así que ten en cuenta este resultado final cuando escribas los mensajes de contexto y evita añadir texto sobre el hecho de que algo no salió como se esperaba.
Esto suele quedar claro por el contexto (por ejemplo, el nivel de registro «ERROR») y el mensaje del error original.
~~~~

A menudo, esta forma de añadir información a un error es suficientemente buena, pero hay casos en los que quieres permitir que quien consume tu error compruebe u obtenga el error subyacente original.
Añadir contexto de una forma que permita esto se llama «envolver un error» en Go.

## Envolver errores y comprobar errores centinela

Envolver errores se puede conseguir con un cambio muy pequeño en el código que vimos antes.
Para envolver un error, necesitas usar el verbo de formato `%w` en lugar de `%v`.
Internamente, esto se asegurará de que el error resultante implemente un método `Unwrap` que devuelve el error original.
Por eso, se puede usar `errors.Is` para comprobar si un error centinela concreto aparece en algún punto de la «cadena de errores».
Lo hace llamando internamente a `Unwrap` repetidamente hasta que se encuentra el error en cuestión o termina la cadena.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Comprobar el error original con `errors.Is` no funcionaría con el verbo de formato habitual `%v`.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Como resultado, es una buena práctica usar `%v` por defecto y usar `%w` solo si quieres permitir explícitamente que quien consume tu error acceda a un error subyacente ([Google Go Styleguide][google-go-styleguide]).

Si te encuentras en una situación en la que quieres comprobar un error centinela pero explícitamente no quieres desenvolverlo, puedes usar `==` en lugar de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

En cambio, `==` no identificaría el error si estuviera envuelto.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Está bien trabajar con `errors.Is` por defecto, pero siempre debes ser consciente de que esto significa que se buscará en toda la cadena de errores.

## Comprobar tipos de error (personalizados)

Existe un equivalente a `errors.Is` que permite comprobar y obtener un error de un tipo específico de la cadena de errores.
La función para eso es `errors.As` y, al igual que `errors.Is`, buscará el tipo de error dado a lo largo de toda la cadena.
`errors.As` solo extrae entonces el error que encontró y que coincide con el tipo para que puedas seguir trabajando con él, por ejemplo, obtener campos específicos.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Ten cuidado con la sintaxis relativa a los punteros anteriores.
El código solo funcionará y compilará correctamente si `customError` tiene el tipo exacto que implementa la interfaz de error.
En nuestro caso, ese es `*MyCustomError` (un [puntero][concept-pointers] a `MyCustomError`), no `MyCustomError` en sí.

Además, el segundo argumento debe ser un puntero a la variable de error.
Como nuestro error ya es un puntero, lo que pasamos a `errors.As` es un puntero a un puntero (a MyCustomError).
Solo con esto configurado correctamente, Go puede rellenar la variable con el error que encontró.
~~~~

Como antes, `errors.As` no habría encontrado el tipo de error si se hubiera usado `%v` al llamar a `Errorf`.

Si no quieres desenvolver por algún motivo, puedes usar en su lugar una aserción de tipo (equivalente al `==` anterior).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

Una aserción de tipo no podrá identificar el tipo de error si el error estuviera envuelto.

## Permitir desenvolver errores de tipos personalizados

A veces, envolver un error con algo de texto adicional no es suficiente.
En su lugar, puedes crear un tipo de error personalizado que contenga el error original y los datos estructurados adicionales que quieres añadir.
Si quieres permitir desenvolver tu tipo de error, lo único que tienes que hacer es añadir manualmente un método `Unwrap() error` para que se satisfaga la interfaz `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Combinar varios errores

En Go 1.20, se añadió una nueva función `Join` al paquete `errors` integrado.
`Join` permite combinar varios errores juntos de una forma que aún permite desenvolverlos, es decir, comprobar un error o tipo de error concreto a lo largo de la cadena.
Con eso, la cadena de errores puede ser en realidad un árbol de errores.
Puedes encontrar más información en las [notas de la versión][release-notes] y la [documentación][doc-join].

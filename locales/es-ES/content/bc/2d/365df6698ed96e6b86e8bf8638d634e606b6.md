# Acerca de

Una declaración `MACRO:` es una palabra cuyo *cuerpo* se ejecuta en tiempo de compilación. El cuerpo consume argumentos literales de la pila en tiempo de compilación y debe dejar una quotation en ella. El compilador sustituye entonces esa quotation por la llamada a la macro, de modo que el programa en tiempo de ejecución nunca ve la macro: solo el código que esta produjo.

```factor
USING: kernel macros sequences ;

MACRO: twice ( quot -- compound )
    dup append ;
```

Si quien llama escribe `[ 1 + ] twice`, el compilador ejecuta el cuerpo con `[ 1 + ]` en la pila, obtiene `[ 1 + 1 + ]` y lo inserta en su lugar. No hay coste adicional en tiempo de ejecución: el bucle o combinador que la macro sustituyó ha desaparecido.

## Las entradas deben ser literales

Como el cuerpo se ejecuta en tiempo de compilación, cada entrada debe ser un *literal* en el punto de llamada: una quotation `[ … ]`, un número, un array, un string. Pasar un valor no literal (uno que solo se conoce en tiempo de ejecución) es un error de compilación.

```factor
! works: [ 1 + ] is a literal quotation
: inc-twice ( x -- y ) [ 1 + ] twice ;

! refused: f is a literal, but the macro can't run with a non-quotation
! input where the body expects to call `append` on it
```

## Las entradas estructurales producen salidas estructurales

Las macros interesantes toman una *estructura* (un array, una secuencia literal de pares) y producen código cuya forma depende de esa estructura. `each-literal`, de este ejercicio, toma una secuencia literal y una quotation, y emite una copia currificada e insertada en línea de la quotation por cada elemento. El programa en tiempo de ejecución es código lineal (sin `each`, sin despacho por elemento), y la iteración de la secuencia ocurrió por completo en tiempo de compilación.

## Por qué no hay problema de higiene

Las macros de Lisp lidian con la *higiene*: una macro que introduce un nombre local puede chocar con nombres del punto de llamada, lo que exige `gensym` o un sistema de higiene. Factor no tiene este problema, porque las quotations son secuencias de *referencias a palabras ya resueltas*: cada palabra se busca en tiempo de análisis, no simbólicamente en tiempo de expansión. Un `dup` dentro de una quotation construida por una macro será siempre `kernel:dup`, sin importar qué nombres existan en el punto de llamada.

El precio: las macros de Factor no pueden introducir nuevos enlaces como sí puede hacerlo `defmacro`. Construyen código a partir de palabras que el analizador ya ha visto. Para la mayoría de la metaprogramación, esto es suficiente.

## Formas relacionadas (no se practican aquí)

- `MACRO::`: variante con locales de `MACRO:`, del mismo modo que `::` es la forma con locales de `:`. Útil cuando el cuerpo hace referencia a sus entradas más de una vez.
- `<< … >>`: bloque de evaluación en tiempo de análisis. Ejecuta Factor normal en tiempo de compilación sin el contrato de devolver una quotation. Útil para calcular un valor que debe existir en tiempo de análisis (por ejemplo, un `CONSTANT:` derivado de una consulta al entorno).
- `SYNTAX:`: *palabras de análisis*. Son harina de otro costal: operan sobre el flujo de tokens del analizador, no sobre valores, y se ejecutan en una fase aún anterior. Sirven para definir nuevas sintaxis literales (`T{ }`, `H{ }`). Fuera del alcance de este concepto.
- `functor:`: plantillas declarativas que generan conjuntos de palabras relacionadas a partir de una única especificación. Se construyen sobre la maquinaria de las macros; territorio de autores de bibliotecas.

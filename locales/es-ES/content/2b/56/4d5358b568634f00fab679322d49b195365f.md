# Introducción

_«Las fechas y las horas son algo que enseñamos a niños pequeños. ¿Qué puede tener de difícil?»_

Muchos programadores han cometido ese error, y la experiencia posterior suele tener un mal efecto en su salud y su felicidad.

Cualquiera que haga programación no trivial con fechas y horas debería estar preparado al menos para entender y mitigar los posibles problemas.

Este documento intentará dar una visión general de cómo maneja R las fechas y las horas, pero para más detalles será necesario consultar la documentación completa.

Como lenguaje de ciencia de datos, las fechas y las horas tienen una importancia particular en R. Gran parte de los datos llega en forma de series temporales: el número diario de pacientes durante un brote de enfermedad, las cifras mensuales de empleo publicadas por los gobiernos, las poblaciones de aves en una colonia de nidificación, el PIB anual de las principales economías y un sinfín de ejemplos más.

_¿Significa esto que R hace sencillo el manejo de fechas y horas?_

Lamentablemente, ¡no!

La funcionalidad de fechas y horas en el R base tiene mala reputación y hoy en día casi no se usa.

El paquete [`lubridate`][web-lubridate] es una gran mejora, pero prepárate para una biblioteca grande y complicada, diseñada para manejar una gama amplia y complicada de problemas.

Originalmente independiente, `lubridate` ahora se distribuye con la colección `tidyverse`. Cárgalo con `library(lubridate)` o `library(tidyverse)`.

Los recursos que te ayudarán a trabajar con `lubridate` incluyen:

- Una [página de referencia][ref-lubridate].
- Una [chuleta][cheat-lubridate] en formato PDF.
- Un [capítulo][book-dates-times] de R for Data Science.

## Fechas y datetimes

Un `date` es solo un día, sin información de hora.

Internamente, las fechas se almacenan como el número (con signo) de días transcurridos desde `1970-01-01`.

```R
today()
#> [1] "2026-04-22"
```

Un `datetime` combina información de fecha, hora y zona horaria.

Internamente, se almacena como el número de segundos transcurridos desde el comienzo de 1970 en la zona horaria UTC.

```R
now()
#> [1] "2026-04-22 15:37:11 MST"  # mid-afternoon in Arizona
```

Quizá sorprendentemente, R no tiene ninguna representación interna para valores que solo contienen una hora.

## Trabajar con valores `date` y `datetime`

Quizá las necesidades de fecha y hora más frecuentes sean:

- Analizar algún formato de entrada adecuado para construir una fecha o un datetime.
- Obtener el formato numérico o de string requerido a partir de una fecha o un datetime.
- Aplicar un desplazamiento a un valor de fecha o datetime.
- Calcular el lapso de tiempo entre dos de esos valores.
- Obtener la fecha actual (con `today()`) y/o el datetime actual (con `now()`).

### Analizar a partir de strings

Hay muchas maneras de escribir fechas y horas, que tienden a ser específicas de cada cultura. Las fechas compuestas solo por números, como «7/6/23», son ambiguas y confusas, y han provocado muchos errores costosos en organizaciones multinacionales (_el autor lo dice por amarga experiencia personal_).

El estándar internacional (a-m-d) se define en [`ISO 8601`][wiki-ISO8601], y tiene dos ventajas principales:

- El análisis es rápido y no da lugar a ambigüedades.
- Ordenar es fácil, ya que el datetime se puede tratar como texto normal y ordenar alfabéticamente.

Sin embargo, la ciencia de datos consiste en trabajar con los datos que puedas encontrar, y a menudo no tiene sentido quejarse de cómo los formatea otra gente.

El R base tiene funciones de conversión que aceptan un string de formato (por defecto, ISO 8601).

```R
as.Date("2026-04-22")
#> [1] "2026-04-22"
as.Date("4/22/26", format = "%m/%d/%y")
#> [1] "2026-04-22"
as.POSIXct("2026-04-22 15:30:09 MST")
#> [1] "2026-04-22 15:30:09 MST"
```

Los strings de formato se parecen a la función `strptime()`, que existe desde hace décadas y está incluida en _muchos_ lenguajes. Los programadores que estén familiarizados con esta sintaxis pueden usar, si quieren, la función [`fast_strptime()`][ref-parse_dt] de lubridate.

De forma más útil, `lubridate` proporciona una amplia gama de [funciones auxiliares][ref-parsing], con nombres que representan el orden de los campos. Una vez que las funciones saben qué valores buscar y en qué orden, el análisis es sorprendentemente flexible.

```R
mdy("4/22/26")
#> [1] "2026-04-22"
mdy("April 22nd 26")
#> [1] "2026-04-22"
mdy("Wednesday, April 22nd 2026")
#> [1] "2026-04-22"
mdy_hm("Wednesday, April 22nd 2026, 4:14 pm")
#> [1] "2026-04-22 16:14:00 UTC"  # defaults to your OS timezone
```

### Construir a partir de valores numéricos

En situaciones en las que tu programa tiene los componentes de una fecha o un datetime como números separados, se pueden ensamblar con [`make_date()` o `make_datetime()`][ref-make_datetime].

Estos son los componentes que se pueden proporcionar, junto con su orden y sus valores por defecto:

```R
make_datetime(
  year = 1970L,
  month = 1L,
  day = 1L,
  hour = 0L,
  min = 0L,
  sec = 0,
  tz = "UTC"
)
#> [1] "1970-01-01 UTC"


make_datetime(2026, 4, 22, 17)
#> [1] "2026-04-22 17:00:00 UTC"
```

Naturalmente, `make_date()` solo acepta los argumentos year, month y day.

### Mostrar en formato legible para las personas

La consola de R muestra automáticamente las fechas y los datetimes como una representación en forma de string. Normalmente esto resulta cómodo, pero a veces induce a error.

Internamente, las fechas y los datetimes son números (además de unos cuantos atributos), no strings. Devolver una fecha (o un datetime) cuando se espera un string causará problemas, así que necesitamos saber cómo hacer la conversión.

Un enfoque sencillo consiste en usar [`as.character()`][ref-ascharacter] del R base, que devuelve un string en formato ISO 8601.

También existe una función [`format_ISO8601()`][ref-iso8601] para datetimes, que tiene opciones para redondear a la precisión deseada.

```R
today() |> as.character()  # a date
#> [1] "2026-04-23"
now() |> as.character()  # a datetime
#> [1] "2026-04-23 09:07:09.779319"
now() |> format_ISO8601() # defaults to nearest second
#> [1] "2026-04-23T09:07:38"
```

A pocas personas que no programan les apetece ver la salida en ISO 8601, así que saber manejar formatos de fecha y hora específicos de cada cultura es esencial.

El R base proporciona la función [`format()`][ref-format], que usa strings de formato similares a las venerables funciones `strftime()` incluidas en muchos otros lenguajes.

```R
format(today(), "%A, %d %B %Y")
#> [1] "Thursday, 23 April 2026"
```

Ese enfoque del R base es feo pero fiable. Estos son algunos de los códigos más comunes:

Código | Resultado
-- | --
%d | Número del día del mes (5, 17, 28, etc.)
%a | Día de la semana abreviado (Mon, Tue, Wed, etc.)
%A | Día de la semana completo (Monday, Tuesday, etc.)
%w | Número del día de la semana (0-6, el domingo es 0)
%u | Número del día de la semana (1-7, el lunes es 1)
%b | Mes abreviado (Jan, Feb, etc.)
%B | Mes completo (January, February, etc.)
%y | Año con 2 dígitos (p. ej. 89)
%Y | Año con 4 dígitos (p. ej. 1989)
%h | horas (reloj de 24 h)
%m | minutos
%s | segundos
%z | desplazamiento respecto a UTC
%Z | Zona horaria (carácter)

Lubridate pretende ofrecer una alternativa más amigable para las personas con la función [`stamp()`][ref-stamp], y las más específicas `stamp_date()` y `stamp_time()`.

Estas toman un string de plantilla que es un ejemplo de la salida deseada, y crean una función personalizada para generar ese formato.

Lubridate intenta adivinar el formato, pero a menudo se topa con ambigüedades y produce un resultado incorrecto. Prepárate para proporcionar strings de formato (como `"dmy"`) para desambiguar.

Para Exercism, también puede ser útil especificar `locale = "C"`, para saltarte la configuración regional de tu sistema y trabajar en inglés (como esperan los tests).
_¡Las configuraciones regionales son complicadas!_

```R
sf <- stamp("Saturday, June 27, 2026 at 14:45", locale = "C")
#> Multiple formats matched: "%A, %B %d, %Y at %H:%M"(1), "Saturday, %Om %d, %Y at %H:%M"(1), "Saturday, %B %d, %Y at %H:%M"(1), "%A, %Om %d, %Y at %H:%M"(0)
#> Using: "%A, %B %d, %Y at %H:%M"

sf(make_datetime(2023, 3, 29, 15, 0, 0))
#> [1] "Wednesday, March 29, 2023 at 15:00"
```

### Establecer o extraer componentes

Lubridate proporciona [muchas funciones][ref-set-get] para obtener o establecer elementos de una fecha o un datetime: las obvias, como `year()` y `second()`, pero también otras más especializadas, como `quarter()` y `epiweek()`.

Todas estas funciones se pueden usar para obtener un valor, y la mayoría también se puede usar para establecerlo.

```R
dt <- now()
dt
#> [1] "2026-04-23 15:47:11 MST"

# get
month(dt)
#> [1] 4

# set
month(dt) <- 11
dt
#> [1] "2026-11-23 15:47:11 MST"
```

Para `wday()` (día de la semana) y `month()`, la salida predeterminada es un número entero, pero:

- Establecer `labels = TRUE` devuelve un string de caracteres abreviado correspondiente a la configuración regional actual.
- Si además se establece `abbr = FALSE`, devuelve el nombre completo.

```R
d <- today()
d
#> [1] "2026-04-23"
wday(d)
#> [1] 5
wday(d, label = TRUE)
#> [1] Thu
#> Levels: Sun < Mon < Tue < Wed < Thu < Fri < Sat
wday(d, label = TRUE, abbr = FALSE)
#> [1] Thursday
#> Levels: Sunday < Monday < Tuesday < Wednesday < Thursday < Friday < Saturday
```

Las etiquetas son `categorical variables`, que serán el tema de otro concepto. Los valores están restringidos a los `Levels` listados, que también muestran el orden de clasificación.

La semana empieza en domingo de forma predeterminada, pero esto se puede cambiar con el argumento `week_start` (usa `1` para el lunes).

```R
dt <- make_datetime(2026, 4, 23)

# default behavior
wday(dt)
#> [1] 5
wday(dt, label = T)
#> [1] Thu

# set week_start to Monday
wday(dt, week_start = 1)
#> [1] 4
```

Algunas funciones auxiliares devuelven valores `TRUE`/`FALSE`, como `leap_year()` y `dst()` (¿está activo el horario de verano?).

Los meses tienen distinta duración, así que `days_in_month()` da el valor entero.

## Lapsos de tiempo

Tanto los valores `date` como los `datetime` representan un instante a lo largo de la línea temporal.

¿Cómo manejamos conceptos como «ayer a esta hora» o «dentro de una semana»?

Quienes estén familiarizados con otros lenguajes orientados a la ciencia quizá conozcan `datetime.timedelta` en Python o el tipo `Period` en Julia.

En cambio, R tiene nada menos que tres formas de representar lapsos de tiempo, con distintas ventajas y limitaciones. Como siempre, elige la que mejor se adapte a tu contexto.

Los distintos lapsos se pueden convertir fácilmente entre sí con `as.period()`, `as_duration()` y `as.interval()`.

Los tipos de lapso se pueden consultar con `is.period()`, etc.

### Periodos

Un `period`, como `hours(3)`, se puede usar para incrementar una hora de reloj en 3 horas.

Las irregularidades, como el horario de verano (DST), se ignoran en gran medida.

Todos los periodos son el nombre pluralizado de una unidad: `years`, `weeks`, etc.

```R
d <- today()
d
#> [1] "2026-04-25"

d + weeks(2)
#> [1] "2026-05-09"

# dates are coerced to datetimes at midnight if necessary
d - hours(20)
#> [1] "2026-04-24 04:00:00 UTC"

hours(3)
#> [1] "3H 0M 0S"
```

### Duraciones

Una `duration`, como `dhours(3)`, incrementa el tiempo físico en 3 horas, respetando irregularidades como el horario de verano que hacen que la hora de reloj se desvíe de la hora física.

Todas las duraciones añaden un prefijo `d` al periodo correspondiente: `dyears`, `dweeks`, etc.

```R
dhours(3)
#> [1] "10800s (~3 hours)"
```

### Intervalos

Un `interval` es una combinación de una hora de inicio y una de fin, creado con la función [`interval()`][ref-interval] o con el operador infijo `%--%`.

```R
# the next 2 lines were run about 33s apart, so now() is different
dt1 <- now()
dt2 <- now() + hours(1)

# interval(0 function)
ivl <- interval(dt1, dt2)
ivl
#> [1] 2026-04-24 16:24:54 MST--2026-04-24 17:25:27 MST

# infix operator
iv2 <- dt1 %--% dt2
iv2 == iv1
#> [1] TRUE
```

## Zonas horarias

Trabajar con zonas horarias puede resultar complicado. La cita siguiente procede de la documentación de Python, pero es igualmente relevante para R:

> «Las reglas para ajustar la hora en todo el mundo son más políticas que racionales, cambian con frecuencia y no existe ningún estándar adecuado para todas las aplicaciones aparte de UTC.»

Algunos puntos generales sobre las zonas horarias:

- Un `datetime` siempre incluye una zona horaria (`tz`); un `date` no tiene en cuenta la zona horaria.
- Los constructores de datetime suelen usar [UTC][wiki-UTC] de forma predeterminada.
- La función [`now()`][ref-now] es una excepción: obtiene tu hora local del reloj del sistema, incluida la `tz`.
  Por defecto se usa la `tz` local, pero se pueden especificar otras, como en `now("UTC")`.

```R
# timezone defaults to UTC
local <- ymd_hm("2026-04-25 10:32")
local
#> [1] "2026-04-25 10:32:00 UTC"

# timezone can be specified
AZ <- ymd_hm("2026-04-25 10:32", tz = "America/Phoenix")
AZ
#> [1] "2026-04-25 10:32:00 MST"

# same clocktime, different tz
local - AZ
#> Time difference of -7 hours
```

La aritmética relacionada con zonas horarias es más fiable con las duraciones que con los periodos.

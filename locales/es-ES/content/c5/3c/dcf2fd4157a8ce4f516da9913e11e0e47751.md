# Sobre la nulabilidad

En un mundo ideal, podríamos confiar en que todo esté bien definido, con valores concretos y sin huecos.

Esto choca con nuestra experiencia cotidiana y, por eso, muchos lenguajes de programación tienen una forma de representar la ausencia de un valor: null o NULL, nil, None, nothing...

Fue fácil introducirlo (allá por 1965), pero pronto dio lugar a arrepentimientos.
Su inventor lo llamó más tarde su [«error de mil millones de dólares»][web-mistake].

En las últimas décadas, quienes diseñan lenguajes han explorado muchas formas de que los nulos estén disponibles pero sean (en su mayoría) seguros.

Kotlin tiene algunos [principios generales][ref-null-safety], que [difieren notablemente de los de Java][ref-java2kotlin].
_Estas diferencias hacen que Kotlin tenga funcionalidades especiales para tratar con la interoperabilidad con Java, aunque los detalles quedan fuera del alcance de este concepto._

- Kotlin tiene un valor `null` especial.
- Todos los tipos son, _por defecto_, no anulables (es decir, no pueden ser `null`).
- Todos los tipos pueden ser _anulables_, pero hay que indicarlo de forma explícita.
- Es probable que las funciones que pueden fallar con una excepción tengan una variante con un valor devuelto anulable.
- Una sintaxis especial y muy concisa trata de hacer que comprobar los nulos y responder a ellos sea lo más fácil posible.

## Crear variables anulables

Un tipo puede volverse [anulable][ref-nullable-type] si añades el sufijo `?` (por ejemplo, `String?` en lugar de `String`).

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operadores y funciones útiles

### El [operador de llamada segura][ref-safe-call] `?.`

Para un `String` no anulable, podemos obtener la propiedad `.length`.

Un `String?` anulable falla con la misma sintaxis, pero usar `?.length` contempla la posibilidad de un `null`.
El tipo devuelto es `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Como vimos en la última línea de arriba, `?.` también funciona con tipos no anulables.

### El [operador Elvis][ref-elvis] `?:`

Ampliando la idea del operador de llamada segura, el [operador Elvis][wiki-elvis] nos permite proporcionar un valor por defecto que sustituya a `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### El [operador de aserción no nula][ref-not-null] `!!`

Con este operador, un tipo anulable se fuerza a tratarse como no anulable, cuando quien programa está seguro de ello.
¿Y si a veces entendemos la lógica del programa mejor que un compilador demasiado cauteloso?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Ahora la responsabilidad es nuestra: si `b` sigue siendo `null`, obtendremos una `NullPointerException`.

### La [función let][ref-let] `?.let`

Si pasamos un elemento anulable a un bloque de código, podríamos hacer comprobaciones específicas de nulos con `if (item != null) { do something }`.

Es más sencillo y más idiomático usar `item?.let { do something }`.
El `do something` solo se ejecutará cuando `item` no sea null.

### Funciones del tipo `somethingOrNone()`

Algunas funciones pueden fallar, por ejemplo, cuando pides un índice no válido en un string o en un array.

En lugar de lanzar una excepción, podríamos usar la [variante `...OrNull`][ref-elem-at-or-null] de la función para obtener (en este caso) un valor devuelto `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

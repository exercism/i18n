# Introducción

En un mundo ideal, podríamos confiar en que todo esté bien definido, con valores concretos y sin huecos.

Esto choca con nuestra experiencia cotidiana y, por eso, muchos lenguajes de programación tienen una forma de representar la ausencia de un valor: null o NULL, nil, None, nothing...

Fue fácil de introducir (allá por 1965), pero no tardó en dar lugar a arrepentimientos.
Más tarde, su inventor lo llamó su «error de mil millones de dólares».

En las últimas décadas, los diseñadores de lenguajes han explorado muchas formas de que los valores nulos estén disponibles pero sean (en su mayoría) seguros.

Kotlin tiene unos cuantos [principios generales][ref-null-safety], que difieren bastante de los de Java.


- Kotlin tiene un valor especial `null`.
- Todos los tipos son _por defecto_ no nulables.
- La mayoría de los tipos se pueden _hacer_ nulables, pero quien programa debe indicarlo explícitamente.
- Es probable que las funciones que pueden fallar con una excepción tengan una variante con un valor devuelto nulable.
- Una sintaxis especial y muy concisa intenta que comprobar si hay valores nulos y responder a ellos sea lo más fácil posible.

## Crear variables nulables

Los tipos estándar suelen tener un equivalente nulable, con el sufijo `?`: por ejemplo, `String?` en lugar de `String`.

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operadores y funciones útiles

### El operador de llamada segura `?.`

Para un `String` no nulable, podemos obtener la propiedad `.length`.

Un `String?` nulable falla con esa misma sintaxis, pero usar `?.length` tiene en cuenta la posibilidad de un `null`.
El tipo devuelto es `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Como veíamos en la última línea de arriba, `?.` también funciona con tipos no nulables.

### El operador Elvis `?:`

Siguiendo la idea del operador de llamada segura, el [operador Elvis][wiki-elvis] nos permite indicar un valor predeterminado que sustituya a `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### El operador de aserción no nula `!!`

Con este operador, un tipo nulable se fuerza a tratarse como no nulo, cuando quien programa está seguro de ello.
¿Quizá a veces entendemos la lógica del programa mejor que un compilador demasiado cauteloso?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Ahora la responsabilidad es nuestra: si `b` sigue siendo `null`, obtenemos una `NullPointerException`.

### La función let `?.let`

Si pasamos un elemento nulable a un bloque de código, podríamos hacer comprobaciones específicas de nulos `if (item != null) { do something }`.

Es más sencillo e idiomático usar `item?.let { do something }`.
El `do something` solo se ejecutará cuando `item` no sea nulo.

### Funciones del tipo `somethingOrNone()`

Algunas funciones pueden fallar, por ejemplo al pedir un índice no válido en un string o un array.

En lugar de lanzar una excepción, podríamos usar la variante `...OrNull` de la función para obtener (en este caso) un valor devuelto `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

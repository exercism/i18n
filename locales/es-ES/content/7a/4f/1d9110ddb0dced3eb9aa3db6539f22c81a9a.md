# Contribuir al track de C

¡Gracias por tu interés en contribuir al track de C de Exercism!
Todas las contribuciones son bienvenidas: ya sea un nuevo ejercicio, un cambio en las herramientas o la documentación, un issue abierto o incluso un simple comentario en un issue o una PR ya existentes.
Este archivo ofrece información que te ayudará a empezar.

En primer lugar, échale un vistazo a la [documentación de Exercism][Exercism docs], en concreto a la información sobre [cómo contribuir a un track de lenguaje][contributing to a language track], ya que estos documentos cubren buena parte de la información básica.

Después, ten en cuenta que hay algunas cosas específicas de este repositorio que se explican a continuación.

Animamos a hacer contribuciones que aporten correcciones y mejoras a los ejercicios existentes.
Ten en cuenta que los ejercicios de este track deben cumplir los estándares definidos en el repositorio [problem-specifications][problem-specifications].
Los cambios en los tests o en la documentación de un ejercicio común a menudo requerirán una pull request en ese repositorio antes de poder incorporarse a los ejercicios de este track.
Si tienes dudas, abre un [issue][issue] en GitHub y hablamos del cambio.

## Código de Conducta

Ayúdanos a que Exercism siga siendo un espacio acogedor.
Lee y respeta el [Código de Conducta][Code of Conduct].

## Flujo de trabajo con Git

1. Haz un fork y clona el repositorio.
2. Añade este repositorio como un nuevo remoto a tu clon: `git remote add upstream https://github.com/exercism/c.git`
3. Crea una nueva rama: `git checkout -b name-of-branch`
4. Haz commit y push como de costumbre en tu nueva rama
5. Cuando estés listo para enviar una pull request, haz rebase de tu rama sobre la rama main del upstream para poder resolver los conflictos: `git fetch upstream && git rebase upstream/main` Es posible que tengas que hacer push a tu rama con `--force` después de resolver los conflictos.
6. Cuando lo tengas todo listo, haz push a tu rama y crea la pull request como se describe a continuación.

## Issues

Llevamos un registro de los errores, las mejoras y las solicitudes de soporte del repositorio mediante los [issues][issues] de GitHub.

Para debates de más alto nivel sobre el proyecto en su conjunto, consulta los issues del repositorio [discussions][discussions].

### Good first patch

Intentamos etiquetar los issues con «good first patch» si creemos que se pueden resolver sin demasiado contexto sobre el código base o el funcionamiento de Exercism. Para encontrarlos, puedes buscar [good-first-patch][good-first-patch].

## Pull requests

Estaría genial que siguieras estas sencillas [pautas para las pull requests][pull request guidelines] al crear tu PR, pero no es obligatorio.

Las pull requests deben centrarse en un único issue o cambio.
Agradecemos los cambios en el estilo del código y en la redacción, pero si es posible, abre una PR aparte para ellos.
Abre un issue antes de crear una PR que introduzca cambios importantes (rupturistas) en un ejercicio existente o que afecte a muchos ejercicios. Lo mejor es hablar de estos cambios antes de ponerse manos a la obra.

Si tu cambio afecta a un ejercicio, puedes ejecutar los scripts de CI antes de enviar la pull request, o bien se ejecutarán automáticamente después, como se describe en [integración continua][Continuous Integration].

Cuando envíes una pull request, a veces te pediremos que hagas cambios antes de aceptar el parche.

No cierres la primera pull request ni abras una segunda con esos cambios.
Si haces push de más commits a una rama para la que has abierto una pull request, esta se actualizará automáticamente.

Si quieres crear una PR con cambios que aún no están listos para fusionarse con main (quizá quieras comentar algún punto concreto, por ejemplo), créala con normalidad, pero usa la interfaz web de GitHub para [convertir la PR en borrador][convert the PR to a draft] y que los mantenedores sepan que todavía no está lista para fusionarse.

Al igual que cuando añades más commits, no necesitas cerrar tu pull request ni abrir una nueva si cambias el historial (rebase, squash, amend) y usas git push --force para actualizar la rama en tu fork.
La pull request apunta a esa rama, no a commits concretos.

## Estilo de código

El estilo de código que se espera en las contribuciones de cambios de código se explica en la [guía de estilo][style guide].

El código de los ejercicios se comprueba durante la [CI][Continuous Integration] para verificar que cumple las reglas de estilo de espaciado y sangría.
La comprobación utiliza la herramienta de línea de comandos [`clang-format`][clang-format].
Al añadir un ejercicio o modificar uno existente, puedes comprobar que tu cambio cumple estas reglas ejecutando la herramienta en local antes de hacer commit.

En Linux, `clang-format` debería estar disponible para instalarlo desde el gestor de paquetes de tu distribución.
En Mac, puedes instalar el paquete `clang-format` con [Homebrew][Homebrew].

Puedes ejecutar clang-format sobre todos los archivos con `format.sh`.
Para ejecutarlo manualmente sobre un solo archivo, puedes usar lo siguiente:

```bash
clang-format -i $(file)
```

## Anatomía de un ejercicio

Cada ejercicio debe estar contenido en un directorio `c/exercises/practice/{exercise-name}`.
Consulta [implementar un ejercicio a partir de la especificación][implement-an-exercise-from-specification] para obtener más detalles sobre cómo implementar un ejercicio que se ajuste a la especificación

La estructura de un directorio de ejercicio es la siguiente (fíjate en el uso distinto del guion y del guion bajo para los nombres de directorio y de archivo, respectivamente):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c`: este archivo contiene todos los tests del ejercicio.  
`test-framework`: directorio que contiene el arnés de pruebas [Unity][Unity] de [ThrowTheSwitch][ThrowTheSwitch].  
  ThrowTheSwitch tiene una guía bastante buena sobre [primeros pasos con Unity][getting started with Unity] por si quieres un tutorial.  
  La versión de Unity utilizada se indica en [versiones][versions]. La estructura del archivo de test se describe en la [guía de estilo][test-file-layout].  
  Los tests deben escribirse para satisfacer el archivo `canonical-data.json` del ejercicio en el repositorio [problem-specifications][problem-specifications]  
`{exercise-name}.c` / `{exercise-name}.h`: los archivos fuente del ejercicio.  
  Usa [guardas de inclusión][include guards] en tus archivos de cabecera.
  Los tests del ejercicio se pueden ejecutar con `make test` desde la raíz del repositorio.
* `makefile`: es el makefile con el que se compila el ejercicio.  
Se requieren dos reglas:  
test: compila test_{exercise-name}.c y lo ejecuta.
memcheck: compila test_{exercise-name} con los flags -fsanitize=address, -fno-common y -fno-omit-frame-pointer, y lo ejecuta
Se espera que los makefiles cambien muy poco de un ejercicio a otro, así que debería ser fácil copiar el de un ejercicio para otro.

**No olvides** añadir el ejercicio al `config.json` del track. Para ello tendrás que determinar cuál es el mejor lugar para añadir el ejercicio dentro del orden de todos los demás ejercicios del track. También tendrás que generar un UUID para añadirlo ahí. Para ambas tareas puedes usar la herramienta [configlet][configlet]; ¡incluso te pasará el linter y dará formato al `config.json` después de que hayas hecho estos cambios!

Aviso: para conseguir el artefacto de instalación de la herramienta configlet, echa un vistazo a la [página de versiones de configlet][configlet releases page].

## Integración continua

Este repositorio usa flujos de trabajo de GitHub para ejecutar algunas herramientas en cada commit de una pull request.
La forma más sencilla de ejecutar estos flujos de trabajo con tu propia contribución es abrir una PR en este repositorio con tus cambios, marcarla como borrador y dejar que la configuración de CI de este repositorio se encargue de todo automáticamente.

### Entorno de CI

GitHub ejecuta la CI en máquinas virtuales a las que llama [runners alojados][hosted runners].
Los flujos de trabajo pueden configurar algunos aspectos de los runners en los que quieren ejecutarse.

Los flujos de trabajo de este repositorio solo especifican que cada uno debe ejecutarse en Ubuntu 24.04. Están fijados a versiones concretas en lugar de referirse a `latest`, ya que algunas de las herramientas utilizadas pueden comportarse de forma distinta según la versión.

### Ejecutar la CI en tu propio fork

Si quieres, también puedes ejecutar la CI en tu propio fork; simplemente clona este repositorio como de costumbre en GitHub.
Los archivos YAML que están en [`./.github/workflows/`][workflows] deberían funcionar igual.
Si quieres que la acción automatizada [`/format`][format-workflow] funcione correctamente, tendrás que añadir una clave de despliegue a tu repositorio clonado.

### Los flujos de trabajo

* `checks.yml` ejecuta `shellcheck` sobre los scripts de las herramientas y, a continuación, ejecuta las siguientes de esas herramientas:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * [acción del comprobador de enlaces Lychee][lychee]
* `configlet.yml` descarga la última versión de configlet y después ejecuta el comando `lint` sobre el track
* `format-code.yml` busca la cadena `/format` en cualquier comentario de una PR; si la encuentra, se ejecuta `format.sh` sobre los ejercicios y se hace commit de los cambios resultantes. Se necesita una clave de despliegue para que el commit pueda volver a activar la CI. La clave de despliegue la gestiona Exercism directamente.
* `test.yml` ejecuta `make` en la raíz del repositorio para probar todos los ejercicios

### Las herramientas

Como puedes ver en los [flujos de trabajo][workflows], a GitHub se le indica que ejecute herramientas del directorio [`./bin`][bin].
El trabajo que realizan las herramientas de este directorio se describe a continuación:

* `check-unitybegin` se asegura de que cada archivo de test añada correctamente la línea `UNITY_BEGIN()` al principio de su función `main()`.
* `fetch-configlet` descarga la herramienta `configlet` desde su [repositorio][configlet].
* `verify-unity-version` comprueba la versión del framework de tests Unity que usa cada ejercicio. La versión que debe buscar este archivo se especifica en [`./docs/VERSIONS.md`][versions]
* `check-include-guards` comprueba que las guardas de inclusión utilizadas en cada archivo de cabecera de stub y de ejemplo de los ejercicios sigan el formato correcto, que es el siguiente:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` descarga la herramienta `configlet` desde su [repositorio][configlet].

### Ejecutar las herramientas en local

También puedes ejecutar las herramientas por separado en tu propia máquina antes de hacer commit.
Primero asegúrate de tener instaladas las aplicaciones necesarias (como `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] y un compilador de C) y, después, ejecuta la herramienta que necesites desde la raíz del repositorio. Por ejemplo:

```bash
~/git/c$ make
```

Si quieres ejecutar solo algunos de los tests para comprobar tu trabajo, puedes indicarlos como objetivos de make.

```bash
~/git/c$ make acronym all-your-base allergies
```

## Test runner

¡Este track tiene un test runner para Exercism v3!
Puedes verlo [aquí][c-test-runner].

Los test runners ofrecen una forma dockerizada de ejecutar los tests de un ejercicio contra el código de un estudiante en Exercism v3.
Este enfoque con Docker ayuda a que los estudiantes puedan programar directamente en el navegador.

# Guía de estilo de C

Esta guía describe el estilo previsto para los archivos de ejemplo y de test de los ejercicios de la pista de C.

Las reglas de esta guía se suman a las establecidas por el archivo [.clang-format][], o sirven para destacarlas.

## Estándar de C

El código debe ajustarse al estándar C99, conocido formalmente como ISO/IEC 9899:1999.
No se deben usar POSIX ni, en general, funciones de biblioteca, tipos u otras referencias no estándar que sean externas a la implementación.

## Nombres

En general, los nombres de tipos, variables, estructuras y archivos deben usar snake case, con todas las letras en minúscula, y se usan guiones bajos `_` para separar los componentes del nombre.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Enumeraciones

Los nombres de las enumeraciones deben estar, por lo general, en singular en lugar de en plural.

Las etiquetas de las enumeraciones deben usar snake case con todas las letras en mayúscula.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Macros

Las macros que definen constantes se nombran usando snake case con todas las letras en mayúscula.

```c
#define CONSTANT 0x4000
```

Se agradece el uso de snake case con mayúsculas para los nombres de las macros, pero las macros que se parecen a funciones pueden nombrarse en snake case con minúsculas.

### Tipos

Se prefieren los tipos estándar de ancho fijo (de `stdint.h`) a los tipos enteros básicos.

Se prefiere el tipo `bool` (de `stdbool.h`) a `_Bool`.

Del mismo modo, para representar cantidades relacionadas con la memoria se prefieren `size_t` y `ptrdiff_t` (de `stddef.h`).

Los tipos que un programa define con `typedef` deben nombrarse con el sufijo `_t`.
Aunque somos conscientes de que POSIX reserva el sufijo `_t`, la pista no utiliza POSIX actualmente.

## Guardas de inclusión

Se deben usar guardas de inclusión en todos los archivos de cabecera.

Por lo general, un conjunto de guardas de inclusión debe envolver todo el contenido de la cabecera.

Las guardas de la implementación de ejemplo (`.meta/example.h`) y del esqueleto del ejercicio (`exercise_name.h`) deben usar nombres de macro que sigan el nombre del ejercicio.
Los nombres de las macros de guarda deben seguir la regla anterior sobre macros en lo relativo a las mayúsculas y minúsculas.

Por ejemplo, para el ejercicio `hello-world`, usa:

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Parámetros

Los parámetros de las funciones deben nombrarse tanto en la declaración como en la definición de todas las funciones.
Esto se aplica tanto a los archivos `.c` como a los `.h`.
Los nombres usados deben coincidir en todos los casos.
Es decir, aunque el siguiente prototipo de función es C válido, el estilo es incorrecto porque el parámetro no tiene nombre: `void foo(int);`.
El prototipo correcto, siempre que todas las demás declaraciones y la definición usen también el nombre de parámetro `bar`, sería `void foo(int bar);`.

Cuando resulte más sencillo o más apropiado, se prefieren los parámetros que requieren pasar los argumentos por valor en lugar de por puntero.
Fíjate especialmente en que esto incluye los parámetros de tipo `struct`.

En el caso de que no se espere que el estudiante cambie los valores de un parámetro de tipo puntero dentro de su implementación, ese parámetro debe calificarse como `const`.

## Formato

El repositorio usa la herramienta `clang-format`, como se describe en la [guía de contribución][contributing guide].

## Estructura del archivo de test

El archivo de test de cada ejercicio sigue una estructura concreta.
La estructura pretende ayudar tanto a los colaboradores a identificar las partes del archivo como a los estudiantes a entender cómo funcionan los tests.

Como la mayoría de los archivos fuente de C, un archivo de test comienza con los includes.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

A los includes les siguen las funciones `setUp()` y `tearDown()`.
Hasta ahora, ningún ejercicio las usa (los cuerpos de las funciones están vacíos), pero deben permanecer en su sitio para que los archivos de test se compilen correctamente en todas las plataformas.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

A continuación vienen las funciones auxiliares que usan las funciones de test.
Los nombres de esas funciones auxiliares no deben usar el prefijo `test_`.

Después vienen las propias funciones de test.
Los nombres de estas funciones usan el prefijo `test_`.
Salvo la primera, cada función de test debe tener `TEST_IGNORE();` como primera instrucción.
A la primera aparición de esto le debe seguir el comentario de línea `// delete this line to run test`.

Por ejemplo:

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Al final del archivo está la función `main()`.
El cuerpo de la función main sigue a su vez una estructura concreta.
Primero, una llamada a `UNITY_BEGIN()` seguida de una línea vacía; después, los tests.
Al último test le sigue otra línea vacía antes de devolver el resultado de `UNITY_END()`.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

## Tipos compuestos

A menudo resulta útil definir tipos personalizados en nuestros programas.

Crear tipos primitivos nuevos es posible, pero rara vez se hace.
Los [tipos primitivos][primitive] integrados no son una elección arbitraria: se corresponden estrechamente con los tipos estándar del compilador LLVM que Julia usa para la compilación JIT.

Mucho más útil es la posibilidad de definir [tipos compuestos][composite-types] con campos con nombre.

Otros lenguajes tienen algo parecido y los llaman `structs` o `records`.
La documentación de Julia se refiere a ellos como `composite types`, aunque (en un pequeño desajuste) la sintaxis del lenguaje los define con la palabra clave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale la pena señalar algunos puntos en el ejemplo anterior:

- No se especifica ningún tipo para `id`, así que el compilador lo interpreta como `id::Any`.
  - **Nota**: en la práctica, lo mejor es ayudar al compilador especificando el tipo de un campo con un tipo concreto.
  - Veremos en un [futuro concepto][parametric] que usar parámetros es otra opción.
- El nombre del tipo se usa como constructor, como en `Person(id, name, age)`, para obtener una instancia de tipo `Person`.
- Se puede acceder a los campos individuales con la notación de punto, igual que con las [tuplas con nombre][named-tuple].

Los elementos de tipo `Person` son inmutables, así que no se permiten actualizaciones.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Si necesitas mutabilidad, añade `mutable` a la definición.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

El constructor, de forma predeterminada, exige que los campos aparezcan en el mismo orden que en la definición, lo que resulta incómodo para tipos más complicados.

Usar la macro `@kwdef` permite dos capacidades nuevas:

- El constructor usa palabras clave, no posiciones.
- Los campos pueden tener valores por defecto y, opcionalmente, se pueden omitir en el constructor.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Jerarquías de tipos compuestos

Hasta ahora, solo hemos creado tipos compuestos concretos.
Si lo compruebas, todos son subtipos de `Any`.

Cuando creas varios tipos relacionados, probablemente tenga más sentido definir una jerarquía para ellos.
Es muy sencillo de hacer.

Primero, crea un tipo abstracto:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

A continuación, incluye un operador `<:` en la definición de un tipo para mostrar la relación.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Repite según sea necesario, recordando que no se permite crear subtipos de tipos concretos.

Para una jerarquía más compleja, crea subtipos abstractos según los necesites.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

El valor de una jerarquía así quedará más claro cuando lleguemos al concepto `Multiple Dispatch` y veamos cómo las funciones manejan los tipos de los argumentos.


## Constructores internos

Al principio de este concepto vimos que el nombre del tipo se usa como constructor para crear elementos de ese tipo:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

Aquí, `Person()` se conoce como `outer constructor`.
Se comprobará que los tipos de los campos son compatibles con la definición del tipo y, si es necesario, se lanzará un error.

¿Y si queremos restricciones sobre los _valores_ que se pasan, y no solo sobre los _tipos_?

Entonces podemos incluir un `inner constructor` dentro de la definición del tipo para llevar a cabo las comprobaciones oportunas.

Por ejemplo, tenemos un tipo abstracto `AbstractPoint`, pensado para tomar coordenadas `(x, y)`, pero queremos un subtipo con la restricción `y > x`.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

La función `new()` _solo_ se puede usar en constructores internos y devuelve el elemento deseado si las entradas resultan ser válidas.

Si la entrada no es válida, podemos detenernos con un mensaje de error, como en el ejemplo.
Como alternativa, puede que prefieras usar un valor de relleno como `nothing` o `missing`.
Consulta el concepto [`Nothingness`][nothingness] para saber más sobre ellos.

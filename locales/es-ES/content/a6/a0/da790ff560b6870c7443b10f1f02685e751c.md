# Estrategia de fusión

Los maintainers del track de Rust [han decidido](https://github.com/exercism/v3/discussions/1725#discussion-7438) dejar por escrito nuestra estrategia de fusión para comunicar las expectativas y fomentar contribuciones de calidad.

## Principios generales

- nos esforzamos por aceptar _todas_ las contribuciones
  - Llevaremos las contribuciones a un alto nivel de calidad mediante una revisión colaborativa e iterativa.
  - Adoptamos un enfoque de fusión pesimista. Piensa en las revisiones de los maintainers como en los comentarios del compilador de Rust. La cantidad de comentarios puede resultar abrumadora y frustrante. Pero trabajaremos contigo para llevarlo hasta la meta. Así que ¡sigue con el buen trabajo!
- Todo pull request debe tener al menos una «Approval», y ninguna «Request Changes», de un maintainer del track antes de poder fusionarse.
- Ningún maintainer puede aprobar su propio pull request.

## Flujo de trabajo de los pull request

### Definiciones

| Término            |                                                                                                     Significado |
| ------------------ | --------------------------------------------------------------------------------------------------------------: |
| Colaborador        |                                                                       Cualquier persona que envíe un pull request. |
| Maintainer         | Cualquier persona que pertenezca al [equipo @exercism/rust](https://github.com/orgs/exercism/teams/rust). |
| rama de desarrollo | La rama de desarrollo por defecto del repositorio [v3](https://github.com/exercism/v3). Actualmente, `master`. |

### El flujo de trabajo

1. Los colaboradores empiezan abriendo un pull request [en borrador](https://github.blog/2019-02-14-introducing-draft-pull-requests/) o un pull request completo con sus cambios
   1. Usar la función de borrador indica que el trabajo está listo para una revisión general, aunque los detalles pueden estar aún sin implementar, incompletos o ser incorrectos.
   1. Después de un número indeterminado de iteraciones de los pasos 2 y 3, el colaborador marca el pull request como listo para revisar.
1. Otro maintainer revisará la contribución y aportará comentarios.
1. El colaborador debe responder a _todos_ los comentarios del maintainer como parte del pull request.
   1. Los maintainers deben plantearse usar la función de sugerencias de GitHub para cambios menores o triviales.
   1. Se anima a rebatir cuando el colaborador cree que tiene razón y el maintainer se equivoca en un comentario. «Responder» a un comentario no es sinónimo de implementarlo ciegamente.
1. El maintainer revisará los comentarios y, o bien:
   1. aprobar
   1. solicitar más cambios. En este punto, el proceso vuelve al paso 3.
1. Una vez aprobado, un maintainer fusionará su pull request.
   1. Los maintainers fusionarán sus propios pull requests. Como los colaboradores no son necesariamente maintainers, un maintainer debe encargarse de este paso.

## Fusión optimista

Los maintainers del track de Rust han decidido adoptar temporalmente la fusión optimista para agilizar el desarrollo del track v3.

- Esto solo se aplica al repositorio v3
- Volveremos a una estrategia de fusión pesimista cuando publiquemos la v3 en producción.
- Aprobaremos y fusionaremos trabajo incompleto
  - Si compila, nos lo quedamos.
  - Priorizamos la velocidad de iteración frente a los detalles más finos de un diseño de software correcto.
- Todo pull request debe tener al menos una «Approval» de un maintainer del track antes de poder fusionarse.

# Introducción

## La interfaz de error

En Go, la gestión de errores **no** se hace mediante excepciones.
En su lugar, los errores son _valores_ normales de tipos que implementan la interfaz `error` integrada.
La interfaz `error` es muy minimalista.
Solo contiene un método, `Error()`, que devuelve el mensaje de error como un string.

```go
type error interface {
  Error() string
}
```

Siempre que definas una función en la que pueda producirse un error durante la ejecución que deba llegar a quien la llama, tienes que incluir `error` como uno de los tipos devueltos.
Si la función devuelve varios valores, por convención `error` es siempre el último.

```go
func DoSomething() (int, error) {
  // ...
}
```

## Crear y devolver un error simple

No siempre tienes que implementar tú mismo la interfaz de error.
Para crear un error simple, puedes usar la función `errors.New()`, que forma parte del paquete `errors` de la biblioteca estándar.
Lo único que tienes que pasar es el mensaje de error como un string, y `errors.New()` se encargará de crear un valor que contenga tu mensaje e implemente la interfaz `error`.

Si la función devuelve un error, es buena práctica devolver el valor cero para el resto de los valores devueltos:

```go
func DoSomething() (SomeStruct, int, error) {
  // ...
  return SomeStruct{}, 0, errors.New("failed to calculate result")
}
```

~~~~exercism/caution
No des por sentado que todas las funciones devuelven valores cero en el resto de los valores devueltos cuando hay un error.
Lo mejor es dar por sentado que no es seguro usar ninguno de los demás valores devueltos si se ha producido un error.
Las únicas excepciones son los casos en los que la documentación indica claramente que los demás valores devueltos son significativos cuando hay un error.
~~~~

Si quieres usar un error simple como este en varios sitios, deberías declarar una variable para el error en lugar de usar `errors.New` directamente.
Por convención, el nombre de la variable debe empezar por `Err` o `err` (según si es exportada o no).
A estas variables de error se las suele llamar _errores centinela_.

```go
import "errors"

var ErrNotFound = errors.New("resource was not found")

func DoSomething() error {
  // ...
  return ErrNotFound
}
```

Devuelve `nil` como error para indicar que no hubo errores durante la ejecución de la función:

```go
func Foo() (int, error) {
  return 10, nil
}
```

## Comprobación de errores

Si llamas a una función que devuelve un error, lo habitual es guardar el valor del error en una variable llamada `err`.
Antes de usar el resultado real de la función, tienes que comprobar que no hubo ningún error.

Para evitar anidar el «camino feliz» de tu código, conviene gestionar primero los casos de error.
Podemos usar `==` y `!=` para comparar el error con `nil`, y sabemos que hubo un error cuando `err` no es `nil`.

```go
func processUserFile() error {
	file, err := os.Open("./users.csv")
	if err != nil {
		return err
	}

	// do something with file
}
```

La mayoría de las veces, el error se devolverá hacia arriba por la pila de funciones, como se muestra en el ejemplo anterior.
Otra forma de gestionar el error podría ser registrarlo y continuar con alguna otra operación.
Es buena práctica devolver el error o registrarlo, pero nunca las dos cosas.

Como la mayoría de las funciones en Go incluyen un error como uno de los valores devueltos, verás y usarás el patrón `if err != nil` por todas partes en el código de Go.

## Tipos de error personalizados

Si quieres que tu error incluya más información que únicamente el mensaje de error, puedes crear un tipo de error personalizado.
Como se ha mencionado antes, todo lo que implemente la interfaz `error` (es decir, que tenga un método `Error() string`) puede servir como error en Go.

Normalmente, se usa una estructura para crear un tipo de error personalizado.
Por convención, los nombres de los tipos de error personalizados deben terminar en `Error`.
Además, lo mejor es definir el método `Error() string` con un receptor de puntero; consulta este [comentario de Stackoverflow][stackoverflow-errors] para entender el motivo.
Ten en cuenta que esto significa que tienes que devolver un puntero a tu error personalizado, porque de lo contrario no contará como `error`, ya que el valor no puntero no proporciona el método `Error() string`.

```go
type MyCustomError struct {
  message string
  details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.message, e.details)
}

func someFunction() error {
  // ...
  return &MyCustomError{
    message: "...",
    details: "...",
  }
}
```

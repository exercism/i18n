# Acerca de

La memoria de un programa suele estar mapeada por el sistema operativo (SO) según un diseño general:

| dirección | región de memoria           |
| :-----: | :--------------------- |
|  alta   | pila                   |
|         | ...                    |
|         | heap                   |
|         | segmento de lectura y escritura |
|         | segmento de código/solo lectura |
|   baja   | reservada              |

La memoria en segmentos se organiza en secciones, con permisos diferentes.

Las funciones que hemos definido hasta ahora estaban todas en la **sección .text**.
Esta sección contiene datos ejecutables de solo lectura.
Otras secciones se usan para declarar variables de datos, que pueden ser de solo lectura o de lectura y escritura, pero no ejecutables.

## Sección .data

Los datos inicializados se declaran en la **[sección .data][data]**.

En NASM (The Netwide Assembler, el ensamblador que usa este track), una variable inicializada tiene un nombre, una directiva que indica el tamaño de los datos y una lista de valores separados por comas.
Cada uno de estos elementos se separa del siguiente con un espacio y, opcionalmente, la etiqueta puede ir seguida de un `:`.

Las principales directivas y sus tamaños de datos correspondientes son:

| directiva | tamaño    |
| :-------: | :------ |
|    db     | 1 byte  |
|    dw     | 2 bytes |
|    dd     | 4 bytes |
|    dq     | 8 bytes |

Por ejemplo, esto declara una variable de un byte llamada `space` con el valor `10`:

```x86asm
section .data
    space db 10
```

Las variables declaradas en `section .data` son mutables, es decir, son de lectura y escritura.
También tienen una duración de almacenamiento _estática_, lo que significa que existen durante toda la ejecución del programa.

## Sección .rodata

La **sección .rodata** es similar a `section .data`.
Ambas secciones contienen datos inicializados, que se declaran de la misma manera y tienen la misma duración de almacenamiento.

La principal diferencia entre ellas es que los datos de `section .rodata` son inmutables, es decir, de solo lectura.

~~~~exercism/note
Las constantes definidas con `equ` son distintas de las definidas en `section .rodata`.

Una constante definida con `equ` no ocupa espacio en memoria y el ensamblador la sustituye directamente por su valor.
De hecho, es un marcador de posición para ese valor.

Por otro lado, las constantes definidas en `section .rodata` sí se almacenan en memoria y tienen una dirección.
~~~~

## Acceso a los datos

### Etiquetas e indirección

Los datos declarados deben tener un nombre asociado.
Ese nombre se denomina **etiqueta**.

Una etiqueta es un símbolo que codifica la dirección concreta de unos datos en memoria.
**Las direcciones en x86-64 son valores de 64 bits**.
Un valor que contiene una dirección de este tipo, ya se guarde en un registro o se almacene en memoria, es lo que los lenguajes de alto nivel llaman un **[puntero][pointer]**.

En NASM, intentar acceder a los datos directamente con su etiqueta no devuelve la memoria asignada, sino su dirección:

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

Para acceder al contenido de una dirección de memoria, es necesario _desreferenciarla_.
Esto se denomina **indirección**.

En NASM, esto se hace con `[]`:

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

Sin embargo, hay situaciones en las que puede haber ambigüedad respecto al tamaño de la memoria desreferenciada.
En esos casos, debe usarse un prefijo que especifique ese tamaño.

Estos son los prefijos más importantes y sus tamaños en un programa típico de x86-64:

| prefijo | tamaño    |
| :----- | :------ |
| byte   | 1 byte  |
| word   | 2 bytes |
| dword  | 4 bytes |
| qword  | 8 bytes |

La misma carga puede escribirse indicando el tamaño de forma explícita:

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

Es una buena práctica usar siempre un prefijo al desreferenciar memoria.

### Escribir en memoria

Escribir en memoria se hace de la misma manera, desreferenciando una dirección:

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

Ten en cuenta que puedes usar operandos de memoria en la mayoría de las instrucciones sin cargar antes el contenido en un registro.
Sin embargo, normalmente no es posible usarlos a la vez en el operando de origen y en el de destino, solo en uno de los dos:

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### La instrucción LEA

Aunque se puede usar un `mov` para guardar la dirección de una variable en un registro, existe una instrucción con este propósito específico: **[lea][lea]**.

Esta instrucción usa un operando en forma de memoria, pero _no_ lee la memoria.
En su lugar, calcula la expresión de dirección efectiva y escribe el resultado en el operando de destino:

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

Es más idiomático usar `lea` para calcular y guardar direcciones de memoria en registros.

### Direccionamiento relativo

Al acceder a posiciones de memoria, el comportamiento predeterminado de NASM es generar **direcciones absolutas**, es decir, direcciones de memoria fijas.

Por motivos de seguridad, los ejecutables suelen compilarse como **PIE (Position Independent Executable, ejecutable independiente de la posición)**, donde las regiones de memoria se colocan en ubicaciones aleatorias.
En un `PIE`, la dirección final de una variable no se conoce en el momento del enlazado.
Así que el código, en su lugar, calcula las direcciones como un desplazamiento respecto al valor de un registro especial llamado `rip`, que apunta a la siguiente instrucción que se va a ejecutar.

Esto suele denominarse **direccionamiento relativo a RIP**.

En NASM puedes solicitar un acceso relativo a RIP con el **[operador rel][rel]**:

```x86asm
mov rax, qword [rel variable]
```

El direccionamiento relativo también puede establecerse como predeterminado para un fichero de código fuente con `default rel` al principio.

Todos los ejercicios de este track se compilan y enlazan como `PIE`, así que debe usarse `rel` para generar direcciones relativas.

La disposición aleatoria mencionada antes es una mitigación conocida como aleatorización del diseño del espacio de direcciones.
Al hacer impredecible la base de cada región de memoria, le niega al atacante las direcciones fijas en las que se basan muchas técnicas de explotación, y `PIE` es lo que permite al cargador colocar esas regiones en cualquier lugar.

Por este motivo, el direccionamiento absoluto no solo no se recomienda en este track, sino que es inutilizable.
Una referencia absoluta como `[abs variable]` pide al ensamblador que incruste una dirección fija de 32 bits en la instrucción.
En Linux, el enlazador de `PIE` rechaza la reubicación que esto produce, y en macOS el formato `macho64` no admite direcciones absolutas de 32 bits en absoluto, por lo que el fichero no se puede ensamblar.

El direccionamiento relativo a RIP evita ambos problemas, ya que la instrucción solo codifica un desplazamiento respecto a `rip` y nunca una dirección fija.
Por tanto, la forma idiomática de colocar una dirección en un registro con `PIE` es `lea` con un operando `rel`:

```x86asm
default rel

section .data
    variable dq 7

section .text
fn:
    lea rax, [rel variable]       ; materialize the address (PIE-safe)
    mov rcx, qword [rel variable] ; load the value through a RIP-relative access
    ...
```

### Visibilidad

Las etiquetas (funciones y datos) definidas en cualquier sección (por ejemplo, `.text`, `.data`, `.rodata`) son visibles dentro del mismo fichero de código fuente.
Si se declaran `global`, también son visibles para otros ficheros de código fuente.

A la inversa, las etiquetas definidas en otros ficheros de código fuente son visibles para el fichero actual si se declaran `extern`.
En este caso, el ensamblado no indica el tamaño de los datos, que debe conocerse de antemano.

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

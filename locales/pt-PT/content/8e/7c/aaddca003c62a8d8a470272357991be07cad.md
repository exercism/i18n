# Guia de estilo de C

Este guia descreve o estilo a seguir nos ficheiros de exemplo e de teste dos exercícios do percurso de C.

As regras deste guia complementam as definidas pelo ficheiro [.clang-format][], ou chamam a atenção para elas.

## Norma de C

O código deve estar em conformidade com a norma C99, formalmente conhecida como ISO/IEC 9899:1999.
Não devem ser usadas funções de biblioteca POSIX, nem funções, tipos ou outras referências não normalizadas ou externas à implementação.

## Nomes

Em geral, os nomes de tipos, variáveis, estruturas e ficheiros devem usar snake case, com todas as letras em minúsculas, e usa-se o underscore `_` para separar os componentes do nome.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Enumerações

Os nomes das enumerações devem, normalmente, estar no singular e não no plural.

Os rótulos das enumerações devem usar snake case, com todas as letras em maiúsculas.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Macros

As macros que definem constantes são nomeadas em snake case, com todas as letras em maiúsculas.

```c
#define CONSTANT 0x4000
```

Prefere-se o snake case em maiúsculas para os nomes das macros, mas as macros que se assemelham a funções podem ser nomeadas em snake case com minúsculas.

### Tipos

Os tipos de largura fixa normalizados (em `stdint.h`) são preferíveis aos tipos inteiros básicos.

O tipo `bool` (de `stdbool.h`) é preferível a `_Bool`.

Do mesmo modo, `size_t` e `ptrdiff_t` (de `stddef.h`) são preferíveis para representar quantidades relacionadas com a memória.

Os tipos definidos por um programa com `typedef` devem ser nomeados com o sufixo `_t`.
Embora tenhamos consciência de que o POSIX reserva o sufixo `_t`, o percurso não utiliza atualmente o POSIX.

## Guardas de inclusão

Devem usar-se guardas de inclusão em todos os ficheiros de cabeçalho.

Em geral, um conjunto de guardas de inclusão deve envolver todo o conteúdo do cabeçalho.

As guardas da implementação de exemplo (`.meta/example.h`) e do stub do exercício (`exercise_name.h`) devem usar nomes de macro que sigam o nome do exercício.
Os nomes das macros das guardas devem seguir a regra acima relativa à capitalização das macros.

Por exemplo, para o exercício `hello-world`, usa:

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Parâmetros

Os parâmetros das funções devem ser nomeados tanto na declaração como na definição de todas as funções.
Isto aplica-se tanto a ficheiros `.c` como `.h`.
Os nomes usados devem ser iguais em todos os casos.
Ou seja, embora o seguinte protótipo de função seja C válido, o estilo está incorreto porque o parâmetro não tem nome: `void foo(int);`.
O protótipo correto, desde que todas as outras declarações e a definição usem também o nome de parâmetro `bar`, seria `void foo(int bar);`.

Sempre que seja mais simples ou mais adequado, são preferíveis os parâmetros que exigem passar argumentos por valor em vez de por ponteiro.
Repara, em especial, que isto inclui parâmetros do tipo `struct`.

Se não se espera que o aluno altere os valores de um parâmetro do tipo ponteiro na sua implementação, esse parâmetro deve ser qualificado com `const`.

## Formatação

O repositório usa a ferramenta `clang-format`, como se descreve no [guia de contribuição][].

## Estrutura dos ficheiros de teste

O ficheiro de teste de cada exercício segue uma estrutura própria.
A estrutura destina-se a ajudar os contribuidores a identificar partes do ficheiro e a ajudar os alunos a compreender como funcionam os testes.

Como a maioria dos ficheiros de código C, um ficheiro de teste começa com os includes.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

A seguir aos includes vêm as funções `setUp()` e `tearDown()`.
Até agora, nenhum exercício as usa (o corpo das funções está vazio), mas têm de permanecer no lugar para que os ficheiros de teste compilem corretamente em todas as plataformas.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

A seguir vêm as funções auxiliares usadas pelas funções de teste.
Os nomes dessas funções auxiliares não devem usar o prefixo `test_`.

Depois vêm as próprias funções de teste.
Os nomes destas funções usam o prefixo `test_`.
Com exceção da primeira, cada função de teste deve ter `TEST_IGNORE();` como primeira instrução.
A primeira ocorrência disto deve ser seguida do comentário de linha `// delete this line to run test`.

Por exemplo:

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Por último, no ficheiro, está a função `main()`.
O corpo da função main segue, ele próprio, uma estrutura específica.
Primeiro, uma chamada a `UNITY_BEGIN()`, seguida de uma linha vazia; depois, os testes.
Depois do último teste há outra linha vazia, antes de devolver o resultado de `UNITY_END()`.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

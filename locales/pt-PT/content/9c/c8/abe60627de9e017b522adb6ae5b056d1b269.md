# Acerca de

Um [ciclo][control] é uma sequência de instruções que é potencialmente executada mais do que uma vez, até se cumprir uma condição de fim.

Em x86-64, um ciclo é normalmente criado com um salto para uma etiqueta anterior:

```x86asm
example_loop:
    ...
    jmp example_loop
```

Repara que um salto incondicional para uma etiqueta anterior transfere sempre a execução para essa etiqueta.
Isto significa que o ciclo vai repetir-se para sempre, a menos que haja outro salto para fora da sequência repetida.

Por exemplo, este ciclo não termina:

```x86asm
infinite_loop:
    inc rax
    jmp infinite_loop ; always jumps to 'infinite_loop', repeating 'inc rax' forever
```

E este ciclo pode terminar, dependendo de a condição se cumprir:

```x86asm
maybe_finite_loop:
    cmp rax, 1
    je out_of_loop ; jumps to 'out_of_loop' if rax == 1, breaking the loop

    inc rax
    jmp maybe_finite_loop ; always jumps to 'maybe_finite_loop'
out_of_loop:
    ...
```

## Ciclos de contagem

Um ciclo de contagem termina quase sempre da mesma forma: uma instrução que atualiza um contador ou compara dois valores, seguida imediatamente por um salto condicional que decide se deve dar outra volta.

```x86asm
sum_array:
    ; rdi is the memory address of an array
    ; rsi is the number of elements in the array

    mov eax, 0           ; running total
.loop:
    add rax, qword [rdi] ; add the current element
    add rdi, 8           ; advance to the next element
    sub rsi, 1           ; one fewer element to process, setting ZF at zero
    jnz .loop            ; repeat while the counter is not yet zero
    ret
```

~~~~exercism/note
O `cmp rsi, 0` não é necessário no código acima, porque o `sub rsi, 1` já define o `zero flag (ZF)` quando o resultado é `0`.

Embora o `cmp` seja a principal forma de testar condições em assembly, muitas instruções atualizam os flags.
Por exemplo, muitas instruções de aritmética de inteiros ou de operações bit a bit atualizam o `ZF` quando o resultado é `0`, e o `SF` quando o resultado é negativo (ou seja, quando o bit mais significativo está a 1).

Podes consultar uma [referência][reference] para ver que flags são afetados por cada instrução.

[reference]: https://www.felixcloutier.com/x86/
~~~~

Repara que, no exemplo acima, se presume que o `rsi` é maior do que `0`.
Se fosse `0`, o `sub rsi, 1` reduziria o `rsi` a `-1`, que é um número sem sinal muito grande.
Seriam precisas mais `18,446,744,073,709,551,615` iterações até o ciclo terminar finalmente.
Além disso, como o comprimento do array é `0`, qualquer acesso à memória ficaria fora dos limites.

Se não houver garantias quanto ao comprimento de um array, há duas abordagens comuns.

A primeira é passar a condição de fim para o início do ciclo e ter depois um salto incondicional no fim:

```x86asm
sum_array:
    mov eax, 0
.loop:
    cmp rsi, 0
    je .done
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jmp .loop
.done:
    ret
```

A segunda é testar uma vez se o array tem comprimento zero antes do início do ciclo:

```x86asm
sum_array:
    mov eax, 0

    cmp rsi, 0
    je .done
.loop:
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jnz .loop
.done:
    ret
```

Esta segunda abordagem é normalmente mais eficiente do que a primeira, porque há menos ramificações no corpo do ciclo.
Vais aprender mais sobre isto num conceito futuro.

## Micro-operações

Um processador não executa diretamente uma instrução como `add` ou `jnz`.
O front-end da CPU primeiro _descodifica_ cada instrução em um ou mais passos internos mais pequenos, chamados **micro-operações** (ou **micro-ops**).
O processador depois agenda e executa estas micro-ops, frequentemente várias por ciclo e fora da ordem original.

A maioria das instruções simples descodifica-se numa única micro-op, enquanto uma instrução mais complexa pode descodificar-se em várias.
Como a carga de trabalho real do processador é o fluxo de micro-ops, produzir menos micro-ops para a mesma tarefa é uma forma de tornar o código mais rápido.

## Macrofusion

Como já foi referido, um ciclo termina geralmente com algum tipo de salto condicional.
Isto é tão comum que os processadores modernos são otimizados para este padrão durante a descodificação.

Uma instrução que define flags, seguida imediatamente por um salto condicional que lê esses flags, pode ser descodificada em conjunto numa **única** micro-op, em vez de uma para cada.
A isto chama-se **macrofusion**.

O par fundido comporta-se como uma única operação: o contador é atualizado e a decisão de ramificação é tomada em conjunto, numa única micro-op.
O fluxo de controlo do ciclo passa então a custar quase nada além do trabalho que o ciclo realmente faz.

Como regra geral, dois tipos de pares fundem-se normalmente desta forma:

- Instruções aritméticas como `add` ou `sub`, seguidas imediatamente por um salto condicional.
- Um `cmp`, `test` ou `and`, seguido imediatamente por um salto condicional.

```x86asm
    ...
    add rdi, 8       ; advance a pointer
    cmp rdi, rsi     ; compare it against the end address
    jb .loop         ; repeat while still below the end
```

A fusão só acontece quando o salto condicional vem **imediatamente** a seguir à instrução que define os flags, sem nada pelo meio.

~~~~exercism/note
A macrofusion depende da CPU e há alguma variação quanto às instruções que se fundem com cada salto condicional.

Uma referência útil é [The microarchitecture of Intel, AMD, and VIA CPUs, by Agner Fog][agner-uarch].
A secção 3.4.2.2 (Optimizing for Macrofusion) do [Intel optimization reference manual][intel-opt] também lista os pares que se podem fundir nas CPUs Intel.

[intel-opt]: https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf
[agner-uarch]: https://www.agner.org/optimize/microarchitecture.pdf
~~~~

## A instrução `loop`

Há algumas instruções que podem ser usadas para criar um comportamento semelhante a um ciclo.
Uma delas é a [loop][loop].

O seu único operando é uma etiqueta que contém o endereço do início do ciclo.

A instrução `loop` usa o valor em `rcx` como contador, decrementando-o em 1 de cada vez.
Quando o valor em `rcx` chega a zero, o ciclo termina e a execução continua sequencialmente:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    loop .example ; this repeats the sequence starting in .example 10 times (the value in rcx)
                  ; at each time, rcx is decremented by 1
```

Há duas variantes da instrução `loop` que verificam o flag de zero (`ZF`) em cada iteração.
Além de pararem o ciclo quando o `rcx` chega a zero, também param quando a condição _não_ se cumpre.

| instrução         | condição  |
| ----------------- | --------- |
| `loope`/`loopz`   | `ZF` == 1 |
| `loopne`/`loopnz` | `ZF` == 0 |

O `ZF` **não é definido** por essas instruções.
Tem de haver um `cmp`, um `test` ou outra instrução que altere o `ZF` antes delas:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    cmp rax, 3
    loopne .example ; this repeats the sequence starting in .example while rcx > 0 and rax != 3
```

~~~~exercism/caution
Apesar da sua conveniência, `loop`, `loope` e `loopne` são geralmente muito mais lentas nos processadores modernos do que a sequência equivalente `sub`/`jnz` ou `cmp`/`jnz`.

Uma boa referência sobre o desempenho das instruções em muitas CPUs diferentes são as [tabelas do Agner][agner-tables].

[agner-tables]: https://www.agner.org/optimize/instruction_tables.pdf

# Introdução

Num mundo ideal, podíamos contar com tudo bem definido, com valores concretos e sem lacunas.

Isto entra em conflito com a nossa experiência quotidiana e, por isso, muitas linguagens de programação têm uma forma de representar a ausência de um valor: null ou NULL, nil, None, nothing...

Foi fácil de introduzir (lá em 1965), mas depressa deu origem a arrependimentos.
O inventor viria a chamar-lhe o seu "Billion Dollar Mistake".

Nas últimas décadas, os criadores de linguagens exploraram muitas formas de tornar os nulls disponíveis mas (na sua maioria) seguros.

O Kotlin tem alguns [princípios gerais][ref-null-safety], que são bastante diferentes dos do Java.


- O Kotlin tem um valor `null` especial.
- Todos os tipos são, _por predefinição_, não anuláveis.
- A maioria dos tipos pode ser _tornada_ anulável, mas o programador tem de o pedir explicitamente.
- As funções que podem falhar com uma exceção têm geralmente uma variante com um valor devolvido anulável.
- Há uma sintaxe especial e muito concisa que tenta tornar tão fácil quanto possível testar e reagir a nulls.

## Criar variáveis anuláveis

Os tipos padrão têm geralmente um equivalente anulável, com o sufixo `?`: por exemplo, `String?` em vez de `String`.

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operadores e funções úteis

### O operador de chamada segura `?.`

Para uma `String` não anulável, podemos obter a propriedade `.length`.

Uma `String?` anulável falha com a mesma sintaxe, mas usar `?.length` permite a possibilidade de um `null`.
O tipo devolvido é `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Como vimos na última linha acima, o `?.` também funciona com tipos não anuláveis.

### O operador Elvis `?:`

Ampliando a ideia do operador de chamada segura, o [operador Elvis][wiki-elvis] permite-nos fornecer um valor predefinido para substituir o `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### Operador de asserção de não nulo `!!`

Com este operador, um tipo anulável é forçado a ser tratado como não nulo, quando o programador tem a certeza disso.
Talvez nós às vezes compreendamos a lógica do programa melhor do que um compilador demasiado cauteloso?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

A responsabilidade passa agora para nós: se o `b` continuar a ser `null`, recebemos uma `NullPointerException`.

### A função let `?.let`

Ao passar um item anulável a um bloco de código, podíamos fazer verificações específicas de null `if (item != null) { do something }`.

É mais simples e mais idiomático usar `item?.let { do something }`.
O `do something` só é executado quando o `item` não é null.

### Funções do tipo `somethingOrNone()`

Algumas funções podem falhar, por exemplo quando se pede um índice inválido numa string ou numa lista.

Em vez de lançar uma exceção, podemos usar a variante `...OrNull` da função, para obter (neste caso) um valor devolvido `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

# Sobre

A memória é normalmente mapeada para um programa pelo Sistema Operativo (SO) com um esquema geral:

| endereço | região de memória          |
| :-----: | :--------------------- |
|  alto   | pilha                  |
|         | ...                    |
|         | heap                   |
|         | segmento de leitura e escrita |
|         | segmento de código/só de leitura |
|   baixo   | reservada               |

A memória, em segmentos, está organizada em secções, com permissões diferentes.

As funções que definimos até agora estavam todas na **secção .text**.
Esta secção contém dados executáveis só de leitura.
Outras secções são usadas para declarar variáveis de dados, que podem ser só de leitura ou de leitura e escrita, mas não são executáveis.

## Secção .data

Os dados inicializados são declarados na **[secção .data][data]**.

No NASM (The Netwide Assembler, o assembler usado neste percurso), uma variável inicializada tem um nome, uma diretiva que indica o tamanho dos dados e uma lista de valores separados por vírgulas.
Cada um destes elementos está separado do seguinte por um espaço, e o rótulo pode opcionalmente ser seguido de `:`.

As principais diretivas e os respetivos tamanhos de dados são:

| diretiva | tamanho    |
| :-------: | :------ |
|    db     | 1 byte  |
|    dw     | 2 bytes |
|    dd     | 4 bytes |
|    dq     | 8 bytes |

Por exemplo, isto declara uma variável de um byte chamada `space` com o valor `10`:

```x86asm
section .data
    space db 10
```

As variáveis declaradas em `section .data` são mutáveis, ou seja, são de leitura e escrita.
Têm também uma duração de armazenamento _estática_, o que significa que existem durante todo o tempo de execução do programa.

## Secção .rodata

A **secção .rodata** é semelhante a `section .data`.
Ambas as secções contêm dados inicializados, declarados da mesma forma e com a mesma duração de armazenamento.

A principal diferença entre elas é que os dados em `section .rodata` são imutáveis, ou seja, só de leitura.

~~~~exercism/note
As constantes definidas com `equ` são diferentes das definidas em `section .rodata`.

Uma constante definida com `equ` não ocupa espaço em memória e é diretamente substituída pelo seu valor pelo assembler.
É, na verdade, um marcador para esse valor.

Por outro lado, as constantes definidas em `section .rodata` são realmente armazenadas em memória, tendo um endereço.
~~~~

## Aceder aos dados

### Rótulos e indireção

Os dados declarados têm de ter um nome associado.
Este nome chama-se **rótulo**.

Um rótulo é um símbolo que codifica o endereço específico dos dados em memória.
**Os endereços em x86-64 são valores de 64 bits**.
Um valor que contém um endereço deste tipo, quer esteja num registo quer esteja guardado em memória, é aquilo a que as linguagens de alto nível chamam um **[ponteiro][pointer]**.

Em NASM, tentar aceder diretamente aos dados através do seu rótulo não devolve a memória alocada, mas sim o seu endereço:

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

Para aceder ao conteúdo de um endereço de memória, é necessário _desreferenciá-lo_.
A isto chama-se **indireção**.

Em NASM, isto faz-se com `[]`:

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

No entanto, há situações em que pode haver ambiguidade quanto ao tamanho da memória desreferenciada.
Nesses casos, tem de se usar um prefixo que especifique esse tamanho.

Estes são os prefixos mais importantes e os respetivos tamanhos num programa típico de x86-64:

| prefixo | tamanho    |
| :----- | :------ |
| byte   | 1 byte  |
| word   | 2 bytes |
| dword  | 4 bytes |
| qword  | 8 bytes |

O mesmo carregamento pode ser escrito com o tamanho indicado explicitamente:

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

É boa prática usar sempre um prefixo ao desreferenciar memória.

### Escrever na memória

A escrita na memória faz-se da mesma forma, desreferenciando um endereço:

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

Repara que podes usar operandos de memória na maioria das instruções sem primeiro carregar o conteúdo para um registo.
No entanto, normalmente não é possível usá-los simultaneamente no operando de origem e no operando de destino, apenas num dos dois:

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### A instrução LEA

Embora se possa usar um `mov` para guardar o endereço de uma variável num registo, existe uma instrução com esse propósito específico: **[lea][lea]**.

Esta instrução usa um operando em forma de memória, mas _não_ lê a memória.
Em vez disso, calcula a expressão do endereço efetivo e escreve o resultado no operando de destino:

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

É mais idiomático usar `lea` para calcular e guardar endereços de memória em registos.

### Endereçamento relativo

Ao aceder a posições de memória, o comportamento predefinido no NASM é gerar **endereços absolutos**, ou seja, endereços de memória fixos.

Por razões de segurança, os executáveis são frequentemente compilados como **PIE (Position Independent Executable)**, em que as regiões de memória são colocadas em posições aleatorizadas.
Num `PIE`, o endereço final de uma variável não é conhecido no momento da ligação.
Por isso, o código calcula antes os endereços como um desvio em relação ao valor de um registo especial chamado `rip`, que aponta para a próxima instrução a executar.

A isto chama-se normalmente **endereçamento relativo a RIP**.

Em NASM, podes pedir acesso relativo a RIP com o **[operador rel][rel]**:

```x86asm
mov rax, qword [rel variable]
```

O endereçamento relativo também pode ser tornado predefinido para um ficheiro de código-fonte com `default rel` no início.

Todos os exercícios deste percurso são compilados e ligados como `PIE`, por isso deve usar-se `rel` para gerar endereços relativos.

A disposição aleatorizada mencionada acima é uma mitigação conhecida como randomização da disposição do espaço de endereços.
Ao tornar imprevisível a base de cada região de memória, nega a um atacante os endereços fixos nos quais muitas técnicas de exploração se baseiam, e é o `PIE` que permite ao carregador colocar essas regiões em qualquer sítio.

Por isso, o endereçamento absoluto não é apenas desaconselhado neste percurso, é inutilizável.
Uma referência absoluta como `[abs variable]` pede ao assembler que incorpore um endereço fixo de 32 bits na instrução.
No Linux, o linker de `PIE` rejeita a relocalização que isto produz, e no macOS o formato `macho64` não suporta de todo endereços absolutos de 32 bits, por isso o ficheiro não consegue ser montado.

O endereçamento relativo a RIP evita ambos os problemas, uma vez que a instrução codifica apenas um desvio em relação a `rip` e nunca um endereço fixo.
A forma idiomática de colocar um endereço num registo com `PIE` é, por isso, `lea` com um operando `rel`:

```x86asm
default rel

section .data
    variable dq 7

section .text
fn:
    lea rax, [rel variable]       ; materialize the address (PIE-safe)
    mov rcx, qword [rel variable] ; load the value through a RIP-relative access
    ...
```

### Visibilidade

Os rótulos (funções e dados) definidos em qualquer secção (por exemplo, `.text`, `.data`, `.rodata`) são visíveis dentro do mesmo ficheiro de código-fonte.
Se forem declarados `global`, também são visíveis para outros ficheiros de código-fonte.

Por outro lado, os rótulos definidos noutros ficheiros de código-fonte são visíveis para o ficheiro de código-fonte atual se forem declarados `extern`.
Neste caso, não há indicação do tamanho dos dados em assembly, este tem de ser conhecido antecipadamente.

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

# Contribuir para o percurso de C

Obrigado pelo teu interesse em contribuir para o percurso de linguagem C do Exercism!
Todas as contribuições são bem-vindas: um novo exercício, uma alteração às ferramentas ou à documentação, um issue aberto ou até apenas um comentário num issue ou PR existente.
Este ficheiro dá-te informação para te ajudar a começar.

Primeiro, lê a [documentação do Exercism][Exercism docs], em especial a informação sobre [contribuir para um percurso de linguagem][contributing to a language track], porque estes documentos cobrem grande parte da informação básica.

Depois, repara que há algumas coisas específicas deste repositório que são explicadas abaixo.

Encorajamos contribuições que tragam correções e melhorias aos exercícios existentes.
Repara que os exercícios deste percurso têm de cumprir as normas definidas no repositório [problem-specifications][].
As alterações aos testes ou à documentação de um exercício comum exigem muitas vezes um pull request nesse repositório antes de poderem ser incorporadas nos exercícios deste percurso.
Se tiveres dúvidas, abre na mesma um [issue][] no GitHub e discutimos a mudança.

## Código de Conduta

Ajuda-nos a manter o Exercism acolhedor.
Lê e cumpre o [Código de Conduta][Code of Conduct].

## Fluxo de trabalho com Git

1. Faz fork e clona.
2. Adiciona este repositório como um novo remote ao teu clone: `git remote add upstream https://github.com/exercism/c.git`
3. Cria um novo ramo: `git checkout -b name-of-branch`
4. Faz commit e push como habitualmente no teu novo ramo
5. Quando estiveres pronto para submeteres um pull request, faz rebase do teu ramo sobre o main do upstream para poderes resolver quaisquer conflitos: `git fetch upstream && git rebase upstream/main` Podes precisar de fazer push para o teu ramo com `--force` depois de resolveres os conflitos.
6. Quando tiveres tudo pronto, faz push para o teu ramo e cria o pull request como se descreve abaixo.

## Issues

Acompanhamos bugs, melhorias e pedidos de apoio no repositório através dos [issues][] do GitHub.

Para discussões de nível mais elevado sobre o projeto como um todo, consulta os issues no repositório [discussions][].

### Bom primeiro patch

Estamos a tentar rotular os issues com «good first patch» quando achamos que podem ser resolvidos sem demasiado contexto sobre a base de código ou o funcionamento do Exercism. Para os encontrares, podes fazer uma pesquisa por [good-first-patch][].

## Pull requests

Seria ótimo se seguisses estas simples [diretrizes para pull requests][pull request guidelines] ao criares o teu PR, mas não é obrigatório.

Os pull requests devem focar-se num único issue ou alteração.
Agradecemos alterações ao estilo de código e à redação, mas abre um PR separado para essas alterações, se possível.
Abre um issue antes de criares um PR que faça alterações significativas (disruptivas) a um exercício existente ou que mexa em muitos exercícios. O melhor é discutires estas alterações antes de fazeres o trabalho.

Se a tua alteração for num exercício, podes executar os scripts de CI antes de submeteres o pull request, ou então eles serão executados automaticamente depois, como se descreve em [Integração Contínua][Continuous Integration].

Ao submeteres um pull request, por vezes vamos pedir-te que faças alterações antes de aceitarmos o patch.

Não feches o primeiro pull request para abrires um segundo com essas alterações.
Se fizeres push de mais commits para um ramo para o qual já abriste um pull request, este é atualizado automaticamente.

Se quiseres criar um PR com alterações que ainda não estão prontas a serem integradas no main (talvez queiras discutir algum ponto em particular, por exemplo), cria o PR normalmente mas usa a interface do site do GitHub para [converter o PR em rascunho][convert the PR to a draft], para que os responsáveis saibam que ainda não está pronto a ser integrado.

Tal como acontece ao adicionares mais commits, não precisas de fechar o teu pull request e de abrir um novo se alterares o histórico (rebase, squash, amend) e usares git push --force para atualizar o ramo no teu fork.
O pull request aponta para esse ramo, e não para commits específicos.

## Estilo de código

O estilo de código esperado para contribuições que alterem código está explicado no [guia de estilo][style guide].

O código dos exercícios é verificado durante a [CI][Continuous Integration] quanto ao cumprimento das regras de estilo de espaçamento e indentação.
A verificação usa a ferramenta de linha de comandos [`clang-format`][clang-format].
Ao adicionares ou alterares um exercício, podes verificar se a tua alteração cumpre estas regras executando a ferramenta localmente antes de fazeres commit.

No Linux, o `clang-format` deve estar disponível para instalação através do gestor de pacotes da tua distribuição.
No Mac, podes instalar o pacote `clang-format` com o [Homebrew][].

Podes executar o clang-format sobre todos os ficheiros correndo o `format.sh`.
Para o executares manualmente sobre um único ficheiro, podes executar o seguinte:

```bash
clang-format -i $(file)
```

## Anatomia de um exercício

Cada exercício deve estar contido num diretório `c/exercises/practice/{exercise-name}`.
Consulta [implementar um exercício a partir da especificação][implement-an-exercise-from-specification] para detalhes aprofundados sobre como implementar um exercício que corresponda à especificação

A estrutura de um diretório de exercício é a seguinte (repara no uso diferente de hífenes e underscores para nomes de diretórios e de ficheiros, respetivamente):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - Este ficheiro contém todos os testes do exercício.  
`test-framework` - diretório que contém a estrutura de testes [Unity][] do [ThrowTheSwitch][].  
  O ThrowTheSwitch tem um guia decente sobre [primeiros passos com o Unity][getting started with unity], caso queiras um tutorial.  
  A versão do Unity usada está indicada em [versões][versions]. A disposição do ficheiro de testes está descrita no [guia de estilo][test-file-layout].  
  Os testes devem ser escritos de modo a satisfazerem o ficheiro `canonical-data.json` do exercício no repositório [problem-specifications][]  
`{exercise-name}.c` / `{exercise-name}.h` - Os ficheiros de código do exercício.  
  Usa [include guards][] nos teus ficheiros de cabeçalho.
  Os testes do exercício podem ser executados com `make test` a partir da raiz do repositório.
* `makefile` - é o makefile do exercício tal como ele seria construído.  
São necessárias duas regras,  
test: compila test_{exercise-name}.c e executa-o.
memcheck: compila test_{exercise-name} com as flags -fsanitize=address, -fno-common, -fno-omit-frame-pointer e executa-o.
Espera-se que os makefiles mudem muito pouco de exercício para exercício, por isso deve ser fácil copiar um de outro exercício.

**Não te esqueças** de adicionar o exercício ao `config.json` do percurso. Para isso, vais ter de determinar o melhor lugar para adicionar o exercício na ordem de todos os outros exercícios do percurso. Também vais ter de gerar um UUID para adicionar aqui. Para ambas as tarefas podes usar a ferramenta [configlet][]; a ferramenta até faz o lint e formata o `config.json` por ti depois de fazeres estas alterações!

A título informativo: para obteres o artefacto de instalação da ferramenta configlet, consulta a [página de lançamentos do configlet][configlet releases page].

## Integração contínua

Este repositório usa fluxos de trabalho do GitHub para executar algumas ferramentas em cada commit de um pull request.
A forma mais simples de executares estes fluxos de trabalho na tua própria contribuição é abrires um PR neste repositório com as tuas alterações, definires o PR como rascunho e depois deixares a configuração de CI deste repositório tratar das coisas por ti automaticamente.

### Ambiente de CI

O GitHub executa a CI em máquinas virtuais a que chama [hosted runners][].
Os fluxos de trabalho podem configurar alguns aspetos dos runners onde querem ser executados.

Os fluxos de trabalho deste repositório apenas especificam que cada um deve ser executado no Ubuntu 24.04. Os fluxos de trabalho estão fixados em versões específicas em vez de referirem `latest`, porque algumas ferramentas usadas podem comportar-se de forma diferente em versões diferentes.

### Executar a CI no teu próprio fork

Se quiseres, também é possível executar a CI no teu próprio fork; basta clonares este repositório normalmente no GitHub.
Os ficheiros YAML que estão em [`./.github/workflows/`][workflows] devem funcionar da mesma forma.
Se quiseres que a ação automática [`/format`][format-workflow] funcione corretamente, vais ter de adicionar uma chave de implementação ao teu repositório clonado.

### Os fluxos de trabalho

* `checks.yml` executa o `shellcheck` sobre os scripts das ferramentas e, em seguida, executa as seguintes dessas ferramentas:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * ação [verificador de links Lychee][lychee]
* `configlet.yml` obtém a versão mais recente do configlet e a partir daí executa o comando `lint` sobre o percurso
* `format-code.yml` procura a string `/format` em qualquer comentário de um PR; se a encontrar, o `format.sh` é executado sobre os exercícios e quaisquer alterações resultantes são enviadas num commit. É necessária uma chave de implementação para que o commit consiga voltar a acionar a CI. A chave de implementação é administrada diretamente pelo Exercism.
* `test.yml` executa o `make` na raiz do repositório para testar todos os exercícios

### As ferramentas

Podes ver pelos [fluxos de trabalho][workflows] que se instrui o GitHub a executar ferramentas a partir do diretório [`./bin`][bin].
O trabalho que as ferramentas neste diretório desempenham descreve-se a seguir:

* `check-unitybegin` garante que todos os ficheiros de teste adicionam corretamente a linha `UNITY_BEGIN()` no início da sua função `main()`.
* `fetch-configlet` obtém a ferramenta `configlet` a partir do seu [repositório][configlet].
* `verify-unity-version` verifica a versão da estrutura de testes Unity usada por cada exercício. A versão que este ficheiro deve verificar está especificada em [`./docs/VERSIONS.md`][versions]
* `check-include-guards` verifica se os include guards usados no stub e no cabeçalho de exemplo de cada exercício estão no formato correto, que é o seguinte:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` obtém a ferramenta `configlet` a partir do seu [repositório][configlet].

### Executar as ferramentas localmente

Também podes executar ferramentas individuais na tua própria máquina antes de fazeres commit.
Primeiro, certifica-te de que tens instaladas as aplicações necessárias (como `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] e um compilador de C) e depois executa a ferramenta pretendida a partir da raiz do repositório. Por exemplo:

```bash
~/git/c$ make
```

Se quiseres executar apenas alguns dos testes para verificar o teu trabalho, podes especificá-los como alvos do make.

```bash
~/git/c$ make acronym all-your-base allergies
```

Este percurso tem um executor de testes para o Exercism v3!
Podes vê-lo [aqui][c-test-runner].

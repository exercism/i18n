# Introdução

É frequentemente útil definir tipos personalizados nos nossos programas.

Criar novos tipos primitivos é possível, mas raramente se faz.
Os tipos primitivos incorporados não são uma escolha arbitrária: correspondem de perto aos tipos padrão do compilador LLVM que a Julia usa para compilação JIT.

Muito mais útil é a capacidade de definir tipos compostos, com campos com nome.

Outras linguagens têm algo semelhante, chamando-lhes `structs` ou `records`.
A documentação da Julia refere-se a eles como `composite types`, embora (num pequeno desencontro) a sintaxe da linguagem os defina com a palavra-chave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale a pena notar alguns pontos no exemplo acima:

- Não é especificado nenhum tipo para `id`, por isso o compilador interpreta isto como `id::Any`.
  - Na prática, o melhor é ajudar o compilador especificando o tipo de um campo com um tipo concreto
- O nome do tipo é usado como construtor, como em `Person(id, name, age)`, para dar uma instância do tipo `Person`.
- Podes aceder a campos individuais com a notação de ponto, tal como nos tuplos com nome.

Os itens do tipo `Person` são imutáveis, por isso não é possível atualizá-los.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Se for necessária mutabilidade, acrescenta `mutable` à definição.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Por omissão, o construtor exige que os campos apareçam pela mesma ordem da definição, o que se torna inconveniente para tipos mais complicados.

Usar a macro `@kwdef` permite duas novas capacidades:

- O construtor usa palavras-chave, não posições.
- Os campos podem ter valores predefinidos e podem, opcionalmente, ser omitidos do construtor.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarquias de tipos compostos

Até agora, só criámos tipos compostos concretos.
Se verificares, todos são subtipos de `Any`.

Quando crias vários tipos relacionados, provavelmente faz mais sentido definir uma hierarquia para eles.
Isto faz-se com muita facilidade.

Primeiro, cria um tipo abstrato:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

A seguir, inclui um operador `<:` numa definição de tipo, para mostrar a relação.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Repete conforme for necessário, lembrando-te de que não é permitido criar subtipos de tipos concretos.

Para uma hierarquia mais complexa, cria subtipos abstratos conforme necessário.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

O valor de uma hierarquia destas tornar-se-á mais claro quando chegarmos ao conceito `Multiple Dispatch` e virmos como as funções lidam com os tipos dos argumentos.

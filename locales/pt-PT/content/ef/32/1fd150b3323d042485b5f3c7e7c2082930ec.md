# Introdução

As threads do Factor são *corrotinas cooperativas*: partilham uma única thread do sistema operativo, passam o controlo umas às outras em operações de E/S e em pontos de cedência explícitos, e nunca correm verdadeiramente em simultâneo. Tudo o que fazes *entre* cedências acontece como um passo ininterrupto. Mas se uma operação composta (ler-modificar-escrever) ceder a meio, outra thread pode intrometer-se e alterar o mundo antes de terminares. E isso é uma condição de corrida.

Este exercício aborda quatro primitivas que surgem vezes sem conta:

## `parallel-map`: fork/join sobre uma sequência

```
parallel-map ( seq quot: ( elt -- newelt ) -- newseq )
```

Em [`concurrency.combinators`][combinators]. Cria uma thread por elemento, executa a quotation e recolhe os resultados numa nova sequência pela mesma ordem:

```factor
USING: concurrency.combinators sequences ;

{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }
```

## `spawn`: iniciar uma thread

```
spawn ( quot name -- thread )
```

Em [`threads`][threads]. A quotation é executada em simultâneo; `name` é uma etiqueta para depuração. O identificador da thread devolvido é pouco interessante a este nível. Usa `drop` para o descartar.

## Promessas: entrega única de valores

```
<promise>           ( -- promise )
fulfill             ( value promise -- )
?promise            ( promise -- value )
```

Em [`concurrency.promises`][promises]. Uma promessa é uma caixa de correio de uso único: uma thread cumpre-a, as outras leem-na. `?promise` bloqueia até a promessa ser cumprida e depois devolve o valor.

```factor
USING: concurrency.promises kernel threads ;

<promise> [
    [ 42 swap fulfill ] curry "answer" spawn drop
] keep ?promise .
! => 42
```

`spawn` + `<promise>` é aquilo de que `parallel-map` é construído; criá-los manualmente é útil quando cada tarefa faz algo diferente de «calcular um elemento».

A forma típica de fan-out/join sobre uma sequência é: para cada elemento, cria uma promessa nova, cria uma thread que faz o trabalho e faz `fulfill` da promessa, recolhe todas as promessas numa sequência e depois faz `?promise` a cada uma para esperar pela conclusão. As variáveis locais tornam isto legível: liga a promessa a um nome com `:>` dentro de uma lambda `[| | ]` para que a quotation criada a possa capturar:

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
inputs [| x |
    <promise> :> p
    [ x do-work t p fulfill ] "worker" spawn drop
    p
] map [ ?promise drop ] each
```

## Bloqueios: exclusão mútua

```
<lock>     ( -- lock )
with-lock  ( lock quot -- )
```

Em [`concurrency.locks`][locks]. Apenas uma thread pode deter um determinado bloqueio de cada vez. `with-lock` adquire, executa a quotation e liberta, mesmo que a quotation lance uma exceção.

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
USING: concurrency.locks kernel locals ;

[let <lock> :> guard
    guard [ ! exclusive section ! ] with-lock
]
```

Usa um bloqueio sempre que um valor é *lido ou escrito por mais do que uma thread* e as operações sobre ele não são naturalmente atómicas. Tanto as leituras como as escritas precisam do bloqueio: uma leitura que cede a meio pode ver um estado inconsistente.

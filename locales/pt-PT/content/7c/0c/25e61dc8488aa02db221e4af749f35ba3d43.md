# Introdução

## Acrescentar contexto aos erros

Explorámos o tratamento básico de erros em Go no [conceito de erros][concept-errors].
Como aprendeste aí, por omissão os erros não trazem consigo stack traces.
Por isso, é crucial garantir que o próprio erro contém informação suficiente para identificar o problema.

Se quiséssemos acrescentar informação a um erro existente com as ferramentas que já conhecemos, podíamos escrever algo assim para criar um novo erro com o texto combinado do erro original e da informação adicional:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Felizmente, o pacote `fmt` da biblioteca padrão inclui uma versão abreviada disto, na forma da função `Errorf`.
Isso permite-te, por exemplo, acrescentar facilmente informação sobre o contexto em que o erro ocorreu.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Muitas vezes, esta forma de acrescentar informação a um erro é suficiente, mas há casos em que queres permitir que quem consome o teu erro verifique ou recupere o erro original subjacente.
Acrescentar contexto de uma forma que permita isto chama-se «encapsular um erro» em Go.

## Encapsular erros e verificar erros sentinela

O encapsulamento de erros consegue-se com uma alteração muito pequena ao código que vimos acima.
Para encapsular um erro, tens de usar o verbo de formatação `%w` em vez de `%v`.
Nos bastidores, isto garante que o erro resultante implementa um método `Unwrap` que devolve o erro original.
Por causa disso, podes depois usar `errors.Is` para verificar se um determinado erro sentinela aparece em algum ponto da «cadeia de erros».
Faz isso chamando `Unwrap` repetidamente, sem que o vejas, até encontrar o erro em questão ou chegar ao fim da cadeia.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

É boa prática usar `%v` por omissão e só usar `%w` se quiseres explicitamente permitir que quem consome o teu erro aceda a um erro subjacente ([Google Go Styleguide][google-go-styleguide]).

Se te encontrares numa situação em que queres verificar um erro sentinela mas não queres explicitamente desencapsular, podes usar `==` em vez de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Não há problema em trabalhar com `errors.Is` por omissão, mas deves ter sempre em conta que isso significa que toda a cadeia de erros será percorrida.

## Verificar tipos de erro (personalizados)

Existe um equivalente ao `errors.Is` que permite verificar e recuperar um erro de um tipo específico a partir da cadeia de erros.
A função para isso é `errors.As` e, tal como o `errors.Is`, procura o tipo de erro indicado ao longo de toda a cadeia.
O `errors.As` só depois de encontrar extrai o erro que corresponde ao tipo, para que possas continuar a trabalhar com ele, por exemplo, para obter campos específicos.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Tem cuidado com a sintaxe dos ponteiros acima.
O código só funciona e compila corretamente se `customError` tiver exatamente o tipo que implementa a interface de erro.
No nosso caso, esse tipo é `*MyCustomError` (um [ponteiro][concept-pointers] para `MyCustomError`), e não o próprio `MyCustomError`.

Além disso, o segundo argumento tem de ser um ponteiro para a variável do erro.
Como o nosso erro já é um ponteiro, o que passamos ao `errors.As` é um ponteiro para um ponteiro (para MyCustomError).
Só com isto configurado corretamente é que o Go consegue preencher a variável com o erro que encontrou.
~~~~

Tal como antes, o `errors.As` não teria encontrado o tipo de erro se tivesse sido usado `%v` ao chamar `Errorf`.

Se, por alguma razão, não quiseres desencapsular, podes usar antes uma asserção de tipo (equivalente ao `==` acima).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

A asserção de tipo não conseguirá identificar o tipo de erro se o erro tiver sido encapsulado.

## Permitir desencapsular erros de tipos personalizados

Às vezes, encapsular um erro apenas com algum texto adicional não é suficiente.
Em vez disso, podes criar um tipo de erro personalizado que contém o erro original e os dados estruturados adicionais que queres acrescentar.
Se quiseres permitir o desencapsulamento do teu tipo de erro, só tens de acrescentar manualmente um método `Unwrap() error`, para que a interface `Unwrap` fique satisfeita.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

# Sobre

A esta altura do plano de estudos, já viste o R ser usado muitas vezes como linguagem imperativa e, cada vez mais, como linguagem funcional (sobretudo com as bibliotecas [`purrr`][ref-purrr] e [`dplyr`][ref-dplyr]).

Sugerir agora que o R é sobretudo orientado a objetos pode provocar algum ceticismo!

Por estranho que pareça, é uma afirmação verdadeira.
Internamente, o R está implementado com classes, herança, polimorfismo e o tipo de atitudes típicas de quem programa orientado a objetos.

No entanto, quem conhece Java ou Ruby (explicitamente orientadas a objetos) ou até Python (semi-veladamente orientadas a objetos, em alguns aspetos) vai achar a abordagem do R... _pouco familiar_.

Para começar, há vários modelos de classes: talvez três de uso comum (S3, S4, R6), além de vários outros de interesse sobretudo teórico.

Encontras uma discussão aprofundada em [Advanced R, 2e][book-advanced-r], capítulos 12 a 16.
Este livro de 2019 destina-se sobretudo a quem quer compreender e manter o funcionamento interno do R, por isso a orientação a objetos é essencial.

Os manuais mais orientados para o utilizador final variam.

- The Art of R Programming (2011, apenas em papel) tem um capítulo sobre orientação a objetos que aborda S3 e (mais brevemente) S4, que eram importantes na altura.
  O comentário de que _"as classes S3 têm uma estrutura um tanto ou quanto remendada"_ continua espantosamente atual.
- R in Action (3.ª ed., 2022) relega a orientação a objetos para 3 páginas de um capítulo sobre Programação Avançada, já perto do fim.
- [R for Data Science, 2e][book-r-data-sci] (2023, com 548 páginas na edição em papel) não faz qualquer menção à orientação a objetos.

Este conceito vai centrar-se nas classes S3, que são as mais simples, as mais comuns e as mais relevantes para problemas do tipo que encontras no Exercism.
Alguns dos exercícios de prática do percurso de R pedem-te que cries uma classe S3; noutros, isso é opcional, mas é incentivado de forma simpática.

## Classes S3

Estas são antigas: o nome S3 significa apenas que foram introduzidas na versão 3 da linguagem S (um precursor comercial do R).

Uma classe S3 é também muito simples: tipicamente, uma [lista][concept-lists] com pelo menos um atributo extra.

Citando [Advanced R][book-s3]: _"O S3 é informal e ad hoc, mas há uma certa elegância no seu minimalismo: não se lhe pode tirar nenhuma parte e continuar a ter um sistema de orientação a objetos útil."_

```R
# create a list
pt2d <- list(x = 2.5, y = 4.2)
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
class(pt2d)
#> [1] "list"
attributes(pt2d)
#> $names
#> [1] "x" "y"

# convert the list to an S3 class
class(pt2d) <- "point2d"
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
#>  - attr(*, "class")= chr "point2d"
class(pt2d)
#> [1] "point2d"
attributes(pt2d)
#> $names
#> [1] "x" "y"

#> $class
#> [1] "point2d"
```

Por isso, fazer uma atribuição a [`class(obj)`][ref-class] limita-se a acrescentar um atributo a `obj`, neste caso identificando pt2d como uma instância da classe point2d.

Os passos de criação podem ser combinados com [`structure()`][ref-structure]:

```R
pt2d_2 <- structure(list(x = 2.5, y = 4.2), class = "point2d")
pt2d_2 == pt2d
#> Error in pt2d_2 == pt2d : comparison of these types is not implemented
```

Embora as instâncias resultantes sejam nocionalmente idênticas, ainda não implementámos uma forma de o R confirmar isso.

### Métodos genéricos

Quem está habituado à orientação a objetos noutras linguagens pode estar a perguntar-se: _"as classes não deviam ser capazes de FAZER coisas?"_

Podemos verificar os métodos disponíveis para instâncias de `point2d` e descobrir que (ao contrário da `list` subjacente) não existe nenhum de momento.

```R
methods(class = "point2d")
#> no methods found
methods(class = "list")
#>  [1] %within%      all.equal     as.col_spec   as.data.frame as_mapper     as_tibble     coerce        common_by    
#>  [9] Ops           pattern_alpha relist        scale_type    select        type.convert  within       
#> see '?methods' for accessing help and source code
```

Na maioria das linguagens orientadas a objetos, os métodos são definidos dentro da definição da classe.
Algumas linguagens (nomeadamente o Ruby) permitem-te acrescentar e modificar métodos de classe mais tarde.

As classes S3 são muito diferentes.
Em vez de acrescentarmos métodos a uma classe, acrescentamos a classe a um método genérico.

Quem trabalha interativamente na consola do R usa métodos genéricos a toda a hora, normalmente sem pensar em como estão implementados.

Um exemplo muito comum é `print()`, ainda que raramente escrevas o nome da função.
Escrever um valor `x` sozinho na linha de comandos da consola é apenas açúcar sintático para `print(x)`.

```R
1:4
#> [1] 1 2 3 4
print(1:4)
#> [1] 1 2 3 4
```

Já conseguimos imprimir `pt2d`.
Ainda que `print()` não saiba nada sobre a classe `point2d`, tem predefinições sensatas para lidar com uma grande variedade de objetos.

```R
pt2d
#> $x
#> [1] 2.5

#> $y
#> [1] 4.2

attr(,"class")
#> [1] "point2d"
```

Isto é bastante verboso e podemos querer uma forma de imprimir o ponto de maneira concisa e bonita.

É fácil: basta acrescentar uma função chamada `print.point2d()`.
O nome tem de ter a forma `methodname.classname`, para que o mecanismo de despacho saiba o que procurar.

```R
print.point2d <- function(pt) {
  cat("Cartesian coords (", pt$x, ", ", pt$y, ")\n", sep="")
}

pt2d
#> Cartesian coords (2.5, 4.2)
```

Agora suponhamos que queremos criar um novo método genérico, por exemplo `flipvert()` para inverter o sinal da coordenada `y`.

Mais uma vez, é fácil:

```R
flipvert <- function(x, ...) UseMethod("flipvert")
```

Isto cria um mecanismo de despacho, em que `x` é o nosso objeto com uma classe S3 e `...` trata de quaisquer argumentos extra de que as definições de métodos possam precisar ("dot args", como se descreve no [conceito de funções][concept-functions]).

Podemos então definir o método para `point2d` e usá-lo.

```R
flipvert.point2d <- function(pt) {
  pt$y <- -pt$y
  pt
}

flipvert(pt2d)
#> Cartesian coords (2.5, -4.2)

methods("flipvert")
#> [1] flipvert.point2d
```

Agora, o R já sabe como inverter o nosso ponto e como mostrar o resultado.

Poderíamos ampliar isto criando classes para 3D, para coordenadas polares, etc., e depois definir métodos para cada uma.

Do ponto de vista do utilizador final, só existe `flipvert(x, ...)`, e podemos contar com o R para determinar a classe do valor de entrada e usar a implementação subjacente adequada.

~~~~exercism/caution
Nomes de funções no formato `verb.class` parecem métodos S3, tanto para quem as usa como para o analisador sintático do R.
Evita usar nomes semelhantes noutros contextos.

É certo que o R base às vezes infringe esta regra.
Devemos encarar isso como um acidente histórico infeliz (para funções ainda mais antigas do que o S3), que tem de ser preservado por compatibilidade retroativa.
~~~~

### Herança

Os entusiastas da orientação a objetos conseguem escrever vários capítulos inteiros de manuais sobre herança, subclasses, mixins e tudo o resto.

O R limita-se a permitir-te indicar vários nomes no atributo `class`: um vetor de strings mais longo, em vez de uma única string.

Correndo o risco de levar o exemplo ao limite, suponhamos que tínhamos criado uma classe genérica `point` e queríamos derivar dela subclasses como `point2d`, `point3d`, etc.

Nesse caso, a definição de `point2d` usa simplesmente `class = c("point2d", "point")`: a classe específica e a classe (ou classes) mãe.

Métodos genéricos como `print()` vão então procurar, por ordem, `print.point2d()`, `print.point()` e (provavelmente) `print.default()`, usando a primeira implementação que o mecanismo de despacho encontrar.

### Segurança

Muitas linguagens orientadas a objetos (Java, C#, etc.) aproveitam o encapsulamento de dados dentro das classes para fazer verificações criteriosas em tempo de compilação e impor segurança de tipos.

Tem em atenção que o S3 te deixa fazer praticamente o que quiseres, mesmo que não faça sentido (qualquer mensagem de erro aparece mais tarde, se aparecer).

Citando [Advanced R][book-s3] (2.ª ed., secção 13.3):

> _Se já usaste outras linguagens orientadas a objetos, isto pode dar-te um certo enjoo, mas, na prática, esta flexibilidade causa poucos problemas. O R não te impede de dar um tiro no pé, mas desde que não apontes a arma aos dedos do pé e puxes o gatilho, não terás problemas._

Bom... _está bem?_
O R é excelente para ciência de dados exploratória e estatística, muitas vezes quando se trabalha de forma interativa.
Ninguém está a sugerir que o uses para escrever sistemas de finanças empresariais altamente seguros!

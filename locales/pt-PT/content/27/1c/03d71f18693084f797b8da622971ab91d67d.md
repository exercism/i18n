## Utilização do script

A geração de testes exige uma cópia local do repositório [problem-specifications][problem-specifications].
O script deve ser executado a partir do diretório raiz `python`, para aceder corretamente
aos exercícios.

Executa `bin/generate_tests.py --help` para veres informações de utilização.


## Modelos de teste

Os modelos de teste suportam a sintaxe de [Jinja2] e têm as seguintes variáveis de
contexto disponíveis a partir dos dados canónicos:
- `exercise`: o nome do exercício com hífenes (ex.: `two-fer`)
- `version`: a versão dos dados canónicos (ex.: `1.2.0`)
- `cases`: uma lista de objetos de caso ou uma lista de listas `cases`. Para saberes a
estrutura exata do exercício em que estás a trabalhar, consulta o
`canonical-data.json`
- `has_error_case`: indica se algum caso de teste espera que seja lançado um
erro (ex.: `False`)
- `additional_cases`: estrutura semelhante a `cases`, mas é preenchida a partir do ficheiro `.meta/additional_tests.json` do exercício, se existir (para veres um exemplo, consulta `exercises/word-count/.meta/additional_tests.json`)

Além disso, são adicionados os seguintes filtros de modelo por conveniência:
- `to_snake`: converte uma string em snake_case (ex.: `{{ "CamelCaseString" | to_snake }}` -> `camel_case_string`)
- `camel_case`: converte uma string em CamelCase (ex.: `{{ "snake_case_string" | camel_case }}` -> `SnakeCaseString` )
- `error_case`: verifica se um caso de teste espera que seja lançado um erro (ex.: `{% for case in cases%}{% if case is error_case}`)
- `regex_replace`: substituição de texto com regex (ex.: `{{ "abc123" | regex_replace("\\d", "D") }}` -> `abcDDD`)


### Convenções

- As macros de uso geral para estruturas de modelo muito repetidas estão definidas em `config/generator_macros.j2`.
  - Podem ser importadas com o seguinte:
  `{%- import "generator_macros.j2" as macros with context -%}`
- Todos os modelos de teste devem terminar com `{{ macros.footer() }}`.
- Todos os nomes de classes Python devem estar em CamelCase (ex.: `TwoFer`).
  - Converte com `{{ "two-fer" | camel_case }}`
- Todos os nomes de módulos e funções Python devem estar em snake_case
(ex.: `high_scores`, `personal_best`).
  - Converte com `{{ "personalBest" | to_snake }}`
- Os testes específicos da track estão definidos no ficheiro de opções `.meta/additional_tests.json`. O objeto JSON definido nesse ficheiro deve
ter uma única chave, `cases`, com a mesma estrutura que `cases` em
`canonical-data.json`.
- Os testes específicos da track devem ser colocados depois dos testes
canónicos nos ficheiros de teste.
- Os testes específicos da track devem ser assinalados no ficheiro de teste com o seguinte comentário:
```
# Additional tests for this track
```


### Estrutura

A maioria dos modelos terá um aspeto semelhante a este:

```Jinja2
{%- import "generator_macros.j2" as macros with context -%}
{{ macros.header() }}

class {{ exercise | camel_case }}Test(unittest.TestCase):
    {% for case in cases -%}
    def test_{{ case["description"] | to_snake }}(self):
        value = {{ case["input"]["value"] }}
        expected = {{ case["expected"] }}
        self.assertEqual({{ case["property"] }}(value), expected)

    {% endfor %}

{{ macros.footer() }}
```


### Substituir as importações

Os nomes importados em `macros.header()` podem ser substituídos adicionando
uma lista de nomes alternativos a importar (ex.:`clock`):

```Jinja2
{{ macros.header(["Clock"])}}
```


### Ignorar propriedades

Em raras ocasiões, pode ser necessário filtrar propriedades que
não são testadas nesta track. A macro `header` também aceita um
argumento `ignore` (ex.: `high-scores`):

```Jinja2
{{ macros.header(ignore=["scores"]) }}
```

## Criar um modelo

1. Cria o ficheiro `.meta/template.j2` para o exercício que estás a implementar
  e abre-o no teu editor.
2. Copia e cola a [estrutura de exemplo](#Layout) no ficheiro de modelo
  e guarda-o.
3. Faz as alterações necessárias ao ficheiro de modelo até ele produzir
  código de teste válido, consultando o `canonical-data.json` do exercício para
  saberes os nomes dos parâmetros de entrada e a estrutura dos casos.
    - Usa as [macros disponíveis](../config/generator_macros.j2) para evitar reescrever secções normalizadas.
    - Se estás a implementar um modelo para um exercício existente,
    não é obrigatório corresponder exatamente à estrutura do ficheiro de teste
    existente, mas minimizar as diferenças tornará a revisão do PR um processo muito mais simples para todos os envolvidos.

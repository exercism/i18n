# Introdução

Muitas vezes, é útil definir tipos personalizados nos nossos programas.

É possível criar novos tipos primitivos, mas isso raramente acontece.
Os tipos primitivos incorporados não são uma escolha arbitrária: correspondem de perto aos tipos padrão do compilador LLVM usado pelo Julia para a compilação JIT.

Muito mais útil é a capacidade de definir tipos compostos, com campos com nome.

Outras linguagens têm algo semelhante, chamando-lhes `structs` ou `records`.
A documentação do Julia refere-se a eles como `composite types`, embora (numa ligeira discrepância) a sintaxe da linguagem os defina com a palavra-chave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale a pena reparar em alguns pontos no exemplo acima:

- Não é especificado nenhum tipo para `id`, por isso o compilador interpreta-o como `id::Any`.
- O nome do tipo é usado como construtor, como em `Person(id, name, age)`, para dar uma instância do tipo `Person`.
- Pode aceder-se a cada campo individualmente com a notação de ponto, tal como nos tuplos com nome.

Os itens do tipo `Person` são imutáveis, por isso não é permitido atualizá-los.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Se a mutabilidade for necessária, acrescenta `mutable` à definição.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Por predefinição, o construtor exige que os campos apareçam pela mesma ordem da definição, o que se torna pouco prático em tipos mais complicados.

Usar a macro `@kwdef` permite duas novas capacidades:

- O construtor usa palavras-chave, não a posição.
- Os campos podem ter valores predefinidos e, opcionalmente, podem ser omitidos no construtor.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarquias de tipos compostos

Até agora, só criámos tipos compostos concretos.
Se verificares, todos são subtipos de `Any`.

Quando crias vários tipos relacionados, provavelmente faz mais sentido definir uma hierarquia para eles.
Isto é muito fácil de fazer.

Primeiro, cria um tipo abstrato:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

A seguir, inclui o operador `<:` numa definição de tipo, para mostrar a relação.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Repete conforme for necessário, tendo em conta que não é permitido criar subtipos de tipos concretos.

Para uma hierarquia mais complexa, cria subtipos abstratos conforme necessário.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

O valor de uma hierarquia destas tornar-se-á mais claro quando chegarmos ao conceito `Multiple Dispatch` e virmos como as funções lidam com os tipos dos argumentos.

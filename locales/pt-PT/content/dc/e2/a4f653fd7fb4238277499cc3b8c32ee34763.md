# Anexo às instruções

## A tarefa

Implementa dois procedimentos.

- `custom_error_message message` gera um erro, e `message` é a mensagem do erro.
- `handle_error script` executa o script dado e devolve uma string que descreve o que aconteceu:

  | Quando o script…                  | devolve               |
  | --------------------------------- | -------------------- |
  | divide por zero                   | `"division by zero"`    |
  | abre um ficheiro que não existe   | `"file does not exist"` |
  | chama um proc que não existe      | `"proc does not exist"` |
  | gera qualquer outro erro          | `"unknown error"`       |
  | tem sucesso                       | `"success"`             |

## Gerar erros

O Tcl tem dois comandos para gerar um erro.

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` exige um _código de erro_ como primeiro argumento.
O código de erro é uma lista que indica a um manipulador que tipo de erro aconteceu, para que possa responder sem analisar o texto da mensagem.
O conteúdo é contigo: `{MYAPP BADTHING}` é apenas um exemplo, e qualquer lista não vazia serve.
Por convenção, vai do geral para o específico.
Um manipulador captura-o com um padrão `try ... trap` correspondente (descrito abaixo), como `trap {MYAPP BADTHING}`, ou `trap {MYAPP}` para capturar todos os erros `MYAPP`.
`error` aceita um código de erro opcional como terceiro argumento: `error message ?info? ?code?`.

## Tratar erros com `catch`

[`catch`][catch] executa um script e devolve um número inteiro, o _código de conclusão_, em vez de gerar o erro:

| código | significado |
| ---- | ---------- |
| 0    | `ok`       |
| 1    | `error`    |
| 2    | `return`   |
| 3    | `break`    |
| 4    | `continue` |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

O segundo argumento opcional recebe o resultado (ou a mensagem de erro).
O terceiro argumento opcional recebe um _dicionário de opções_, que tem o `-errorcode` e o `-errorinfo` (o stack trace).

Prós:

- É pequeno e flexível.
- É curto para casos simples, como `if {[catch {open $f} fh]} {...}`.

Contras:

- Tens de verificar o código de conclusão tu mesmo.
  Um `if {[catch ...] != 0} { handle error }` descuidado trata `return`, `break` e `continue` como erros também.
- Os erros que não tratas são engolidos, a menos que os voltes a lançar tu mesmo.
- Não há forma incorporada de executar código de limpeza, quer o script tenha falhado quer não.

## Tratar erros com `try`

[`try`][try] executa um script e envia o desfecho ao primeiro manipulador correspondente.
Uma cláusula `finally` opcional é sempre executada, o que a torna um bom lugar para libertar recursos como canais de ficheiros.

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

Prós:

- A estrutura é clara: um manipulador para cada tipo de desfecho.
- O `finally` é sempre executado.
- Os desfechos a que nenhum manipulador corresponde são passados ao chamador sem alterações.

Contras:

- É um pouco mais verboso do que o `catch` para casos simples.

### `try ... on` versus `try ... trap`

Há dois tipos de manipulador.

`on code {msgVar optionsVar}` corresponde ao _código de conclusão_: `ok`, `error`, `return`, `break` ou `continue`.
Todos os erros têm o código de conclusão `error`, por isso `on error` não consegue distinguir uma divisão por zero de um ficheiro em falta.
Terias de olhar para o texto da mensagem, o que é frágil: as mensagens destinam-se a humanos e podem mudar entre versões do Tcl.

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` corresponde ao _código de erro_.
O manipulador corresponde quando o padrão é um prefixo da lista `-errorcode`.
Isto identifica o tipo de erro de forma fiável.

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

Um padrão vazio, `trap {}`, corresponde a qualquer erro.
Os manipuladores são verificados por ordem, por isso coloca o que apanha tudo em último lugar.

## Encontrar o código de erro

Onde está documentado o `ARITH DIVZERO`?
Principalmente apenas no código-fonte, mas o Tcl mostra-to.
Depois de um erro, a variável global `errorCode` contém o código de erro do erro mais recente:

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

Dentro de um programa, obtém-lo a partir do dicionário de opções:

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

O último elemento de um código de erro é muitas vezes uma mensagem legível para humanos, ou o nome da coisa que causou o erro.
Deixa-o de fora do teu padrão `trap`: usa `{ARITH DIVZERO}` no trap, não `{ARITH DIVZERO {divide by zero}}`.

### Alguns códigos de erro comuns

Esta tabela não está completa.
Usa a técnica acima para encontrar o código de qualquer outro erro.

| Situação             | Exemplo                  | Código de erro                |
| --------------------- | ------------------------ | ----------------------------- |
| Divisão por zero      | `expr {1 / 0}`           | `ARITH DIVZERO ...`           |
| Erro de domínio matemático | `expr {sqrt(-1)}`   | `ARITH DOMAIN ...`            |
| Ficheiro não encontrado | `open nosuchfile r`     | `POSIX ENOENT ...`            |
| Permissão negada      | `open /root/x w`         | `POSIX EACCES ...`            |
| Comando desconhecido  | `no::such::proc`         | `TCL LOOKUP COMMAND name`     |
| Variável desconhecida | `set nosuchvar`          | `TCL LOOKUP VARNAME name`     |
| Número errado de argumentos | `string length a b` | `TCL WRONGARGS`              |
| Dicionário inválido   | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`        |
| Lista inválida        | `llength "a \{b"`        | `TCL VALUE LIST ...`          |

Os códigos de erro `POSIX` usam os nomes `errno` do sistema operativo, tais como `ENOENT`, `EACCES` e `EEXIST`.

## Dica: onde o script é executado

`handle_error` recebe um script do seu chamador.
Se o executares com `try $script`, é avaliado no âmbito do `handle_error`, não no do chamador.
Para o avaliar onde foi escrito, usa [`uplevel`][uplevel]: `try {uplevel 1 $script} ...`.

# Acerca

## Erros em `jq`

O `jq` reporta dois grandes tipos de erros:

1. **Erros de compilação**: o próprio programa é inválido, como erros de sintaxe, referências a funções ou variáveis indefinidas, entre outros.
   O `jq` recusa-se a executar o programa.

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **Erros de execução**: o programa é válido, mas algo corre mal durante o processamento de um valor, como indexar um número com uma string, analisar texto JSON inválido com `fromjson`, chamar uma função com argumentos do tipo errado, entre outros.

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

Este conceito aborda os **erros de execução**: como os lançar, como os capturar e como parar o programa.

Um erro de execução não capturado faz com que o `jq` imprima uma mensagem no _erro padrão_ e termine com o código `5`.

## Lançar erros: `error` e `error(message)`

O filtro [`error`][man-error] lança um erro.

- `error` lança um erro cujo valor é o **valor de entrada**.
- `error(message)` lança um erro cujo valor é o resultado de `message`.

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
O valor do erro pode ser _qualquer_ valor JSON, não apenas uma string.
Lançar erros estruturados permite que um handler de `catch` tome decisões com base no conteúdo do erro.

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

Se um valor de erro que não seja uma string não for capturado, o `jq` imprime-o como JSON, assinalado com `(not a string)`.

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## Capturar erros: `try` e `catch`

Os erros podem ser capturados com [`try EXP catch HANDLER`][man-try-catch].
A primeira expressão é executada; se lançar um erro, a expressão `HANDLER` é executada **com o valor do erro como valor de entrada**.
A saída do handler é produzida como se fosse a saída da expressão que está a ser tentada.

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

A forma mais curta `try EXP` é equivalente a `try EXP catch empty`: o erro é descartado e não é produzida qualquer saída.

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
Um erro **interrompe o resto do fluxo** dentro do `try`.
Os valores já produzidos mantêm-se, mas nada depois do erro é avaliado.

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

Um handler pode lançar um novo erro ou voltar a lançar o erro original com um simples `error`. Como o valor do erro é o valor de entrada do handler, isso propaga-o sem alterações.

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## Suprimir erros: o operador `?`

O [operador `?`][man-question-mark], usado como `EXP?`, é uma forma abreviada de `try EXP`.
Transforma uma expressão que falha numa expressão que simplesmente não produz saída.

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

Aparece muitas vezes associado aos operadores de indexação:

- `.foo?` é `.["foo"]?`
- `.[]?` itera apenas se o valor de entrada for um array ou um objeto; caso contrário, é vazio

~~~~exercism/caution
O `?` suprime **todos** os erros, incluindo os que não previste.
`user.name?` não produz nada silenciosamente quando `user` não é um objeto, o que pode esconder problemas nos dados ou erros de escrita no teu programa.
Dá preferência a `try ... catch` quando precisas de saber _que_ algo falhou, ou valida explicitamente o valor de entrada.
~~~~

## O operador alternativo `//`

Os programadores por vezes esperam que `a // b` produza `b` quando `a` falha.
Isso era verdade em versões antigas do `jq`, mas já não acontece desde o `jq` 1.6.
O operador `//` não suprime erros.
Apenas substitui o valor por `b` quando `a` não produz nenhum valor, `false` ou `null`; os erros em `a` continuam a propagar-se.

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

Usa `try a catch b` se quiseres uma alternativa para os erros.

## O operador alternativo de desestruturação `?//`

O [operador `?//`][man-question-mark-slash-slash] combina a desestruturação com o tratamento de erros.
Tenta cada padrão de ligação pela ordem até um deles funcionar, e as variáveis ligadas pelas alternativas que falham ficam com o valor `null`.

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

Aqui, o primeiro padrão espera que `c` seja um _objeto_ com as chaves `d` e `e`, enquanto o segundo espera que `c` seja um _array_ que contém um objeto desse tipo.
O primeiro elemento do valor de entrada liga-se ao primeiro padrão; o segundo elemento falha esse padrão, por isso é tentado o segundo padrão.

Isto permite que um único programa desestruture valores de entrada que podem assumir uma de várias formas, sem escrever cadeias explícitas de `if type == ...`.

## Parar o programa: `halt` e `halt_error`

Por vezes, a resposta certa a um erro é parar o processamento por completo.

- [`halt`][man-halt] para o programa `jq` imediatamente, sem mais nenhuma saída; o código de saída é `0`.
- [`halt_error`][man-halt-error] para o programa, imprime o seu **valor de entrada** no _erro padrão_ como texto simples (sem qualquer decoração, nem sequer uma mudança de linha) e termina com o código indicado, que por omissão é `5`.

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

Repara que estes filtros param o programa imediatamente, mesmo que ainda haja mais valores de entrada por ler.

### Códigos de saída

Para referência, o `jq` usa estes códigos de saída:

| Código | Significado                                      |
| :----: | ------------------------------------------------ |
| `0`    | sucesso                                          |
| `2`    | erro de utilização (opções de linha de comandos inválidas) |
| `3`    | erro de compilação                               |
| `5`    | erro de execução (ou `halt_error` sem argumento) |

Com a opção `--exit-status` / `-e`, o código reflete antes o último valor de saída: `0` para `true` ou números, `1` para `false` ou `null`, `4` quando não há saída.

## Auxiliares de depuração

Para descobrir de onde vem um erro, estes filtros ajudam:

- [`debug`][man-debug] deixa passar o seu valor de entrada inalterado, mas imprime `["DEBUG:", <input>]` no erro padrão.
  `debug(msgs)` também imprime `msgs` como mensagens de depuração.
- [`stderr`][man-stderr] imprime o seu valor de entrada no erro padrão, em bruto e de forma compacta.
- [`input_line_number`][man-input-line-number] produz o número da linha do valor de entrada que está a ser filtrado neste momento. Isto é inestimável quando um ficheiro contém muitos textos JSON e um deles está mal.
- [`$__loc__`][man-loc] produz um objeto com as chaves `file` e `line` que descrevem onde, no programa, ele ocorre; podes incorporar esse objeto em mensagens de erro.

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

# Sobre a Anulabilidade

Num mundo ideal, podíamos contar com tudo bem definido, com valores concretos e sem lacunas.

Isto entra em conflito com a nossa experiência do dia a dia e, por isso, muitas linguagens de programação têm uma forma de representar a ausência de um valor: null ou NULL, nil, None, nothing...

Isto foi fácil de introduzir (lá por 1965), mas depressa deu origem a arrependimentos.
O inventor acabou por lhe chamar o seu [«Billion Dollar Mistake»][web-mistake].

Nas últimas décadas, os criadores de linguagens têm explorado muitas formas de tornar os nulls disponíveis mas (quase sempre) seguros.

Kotlin tem alguns [princípios gerais][ref-null-safety], que [diferem significativamente do Java][ref-java2kotlin].
_As diferenças significam que Kotlin tem funcionalidades especiais para lidar com a interoperabilidade com o Java, embora os detalhes estejam para lá do âmbito deste Conceito._

- Kotlin tem um valor `null` especial.
- Todos os tipos são, _por omissão_, não anuláveis (ou seja, não podem ser `null`).
- Todos os tipos podem ser _anuláveis_, mas isso tem de ser feito explicitamente.
- As funções que podem falhar com uma exceção têm provavelmente uma variante com um valor devolvido anulável.
- Uma sintaxe especial e muito concisa tenta tornar a verificação e a resposta a nulls o mais fácil possível.

## Criar variáveis anuláveis

Um tipo pode ser tornado [anulável][ref-nullable-type] adicionando o sufixo `?` (por exemplo, `String?` em vez de `String`).

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operadores e funções úteis

### O [operador de chamada segura][ref-safe-call] `?.`

Para uma `String` não anulável, podemos obter a propriedade `.length`.

Uma `String?` anulável falha com a mesma sintaxe, mas usar `?.length` permite a possibilidade de um `null`.
O tipo devolvido é `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Como vimos na última linha acima, o `?.` também funciona com tipos não anuláveis.

### O [operador Elvis][ref-elvis] `?:`

Ampliando a ideia do operador de chamada segura, o [operador Elvis][wiki-elvis] permite-nos fornecer um valor por omissão para substituir o `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### [Operador de asserção não nulo][ref-not-null] `!!`

Com este operador, um tipo anulável é forçado a ser tratado como não nulo, quando o programador está confiante nisso.
Talvez às vezes compreendamos a lógica do programa melhor do que um compilador demasiado cauteloso?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

A responsabilidade é agora nossa: se `b` continuar a ser `null`, obtemos uma `NullPointerException`.

### [Função let][ref-let] `?.let`

Se passarmos um item anulável a um bloco de código, podíamos fazer verificações de null específicas com `if (item != null) { do something }`.

É mais simples e mais idiomático usar `item?.let { do something }`.
O `do something` só será executado quando o `item` não for null.

### Funções do tipo `somethingOrNone()`

Algumas funções podem falhar, por exemplo quando pedimos um índice inválido numa string ou numa lista.

Em vez de lançar uma exceção, podemos usar a [variante `...OrNull`][ref-elem-at-or-null] da função, para obter (neste caso) um valor devolvido `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

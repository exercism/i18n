# Prepara-te para receber contribuições de desconhecidos em código aberto

A esta altura, já deves conseguir aceitar contribuições de pessoas desconhecidas.
Escreve alguma [documentação de contribuição](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors) para ajudar desconhecidos a contribuir.

## Issues

Se há exercícios que queres incluir no track, mas que ainda não implementaste, abre issues para cada exercício.
Em geral, recomendamos que abras issues para as tarefas para as quais aceitarias contribuições.

Temos uma secção especial no site que lista _tarefas_, que são issues com uma ou mais etiquetas especiais.
Ter as tuas issues listadas no site é uma ótima forma de conseguir mais contribuições.
Para mais informações sobre como fazer com que as tuas issues apareçam no site, consulta a [documentação de tarefas](/docs/building/product/tasks).

## Outros aspetos a considerar

- Existe um guia de estilo para a tua linguagem de programação?
- Esses estilos são incentivados ou impostos?
- Há convenções que devamos adotar neste track por uma questão de consistência?
- Conseguimos impô-las?
- Existe um linter? Existem muitos? Devemos usar um?
- Existe uma convenção comum para nomes de ficheiros? Se não, qual deveria ser a nossa convenção?

Pode valer a pena abrir issues separadas para as coisas que queres tratar.

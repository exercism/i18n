# Introdução

A esta altura do percurso, já viste o R usado muitas vezes como linguagem imperativa e, cada vez mais, como linguagem funcional (sobretudo com as bibliotecas [`purrr`][ref-purrr] e [`dplyr`][ref-dplyr]).

Sugerir agora que o R é sobretudo orientado a objetos pode provocar algum ceticismo!

Por estranho que pareça, é uma afirmação verdadeira.
Internamente, o R é implementado com classes, herança, polimorfismo e o tipo de atitudes típicas dos programadores de POO.

No entanto, quem está familiarizado com Java ou Ruby (explicitamente POO) ou até com Python (semiocultamente POO, em certos aspetos) vai achar a abordagem do R... _pouco familiar_.

Para começar, existem vários modelos de classes: talvez três de uso comum (S3, S4, R6), além de vários outros de interesse sobretudo teórico.

Encontra-se uma discussão aprofundada no [Advanced R, 2e][book-advanced-r], capítulos 12 a 16.
Este livro de 2019 destina-se sobretudo a quem quer compreender e manter o funcionamento interno do R, pelo que a POO é essencial.

Os manuais mais virados para o utilizador final variam.

- The Art of R Programming (2011, apenas em papel) tem um capítulo sobre POO que aborda S3 e (mais brevemente) S4, que eram importantes na altura.
  O comentário de que _"as classes S3 têm uma estrutura um tanto ou quanto remendada"_ continua a ser surpreendentemente verdadeiro.
- R in Action (3e, 2022) remete a POO para 3 páginas de um capítulo sobre Programação Avançada, perto do fim.
- [R for Data Science, 2e][book-r-data-sci] (2023, com 548 páginas na edição em papel) não faz qualquer menção a POO.

Este Conceito vai concentrar-se nas classes S3, que são as mais simples, as mais comuns e as mais relevantes para problemas do tipo do Exercism.
Alguns dos exercícios de prática do trilho de R pedem que cries uma classe S3; outros tornam isso opcional, mas incentivam-no gentilmente.

## Classes S3

Estas são antigas: o nome S3 significa apenas que foram introduzidas na versão 3 da linguagem S (um precursor comercial do R).

Uma classe S3 é também muito simples: tipicamente, uma [lista][concept-lists] com pelo menos um atributo extra.

A citar o [Advanced R][book-s3]: _"O S3 é informal e ad hoc, mas há uma certa elegância no seu minimalismo: não consegues retirar qualquer parte dele e continuar a ter um sistema de OO útil."_

```R
# create a list
pt2d <- list(x = 2.5, y = 4.2)
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
class(pt2d)
#> [1] "list"
attributes(pt2d)
#> $names
#> [1] "x" "y"

# convert the list to an S3 class
class(pt2d) <- "point2d"
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
#>  - attr(*, "class")= chr "point2d"
class(pt2d)
#> [1] "point2d"
attributes(pt2d)
#> $names
#> [1] "x" "y"

#> $class
#> [1] "point2d"
```

Portanto, fazer uma atribuição a [`class(obj)`][ref-class] acrescenta apenas um atributo a `obj`, neste caso identificando pt2d como instância da classe point2d.

Os passos de criação podem ser combinados com [`structure()`][ref-structure]:

```R
pt2d_2 <- structure(list(x = 2.5, y = 4.2), class = "point2d")
pt2d_2 == pt2d
#> Error in pt2d_2 == pt2d : comparison of these types is not implemented
```

Embora as instâncias resultantes sejam nocionalmente idênticas, ainda não implementámos uma forma de o R o confirmar.

### Métodos genéricos

Quem estiver familiarizado com POO noutras linguagens poderá estar a pensar: _"as classes não deviam conseguir FAZER coisas?"_

Podemos verificar os métodos disponíveis para instâncias de `point2d` e descobrir que (ao contrário da `list` subjacente) atualmente não há nenhum.

```R
methods(class = "point2d")
#> no methods found
methods(class = "list")
#>  [1] %within%      all.equal     as.col_spec   as.data.frame as_mapper     as_tibble     coerce        common_by    
#>  [9] Ops           pattern_alpha relist        scale_type    select        type.convert  within       
#> see '?methods' for accessing help and source code
```

Na maioria das linguagens de POO, os métodos são definidos dentro da definição da classe.
Algumas linguagens (sobretudo o Ruby) permitem-te adicionar e modificar métodos de classe mais tarde.

As classes S3 são muito diferentes.
Em vez de adicionarmos métodos a uma classe, adicionamos a classe a um método genérico.

Quem trabalha interativamente na consola do R usa métodos genéricos a toda a hora, normalmente sem pensar em como estão implementados.

Um exemplo muito comum é `print()`, mesmo que raramente escrevas o nome da função.
Introduzir um valor `x` sozinho no prompt da consola é apenas açúcar sintático para `print(x)`.

```R
1:4
#> [1] 1 2 3 4
print(1:4)
#> [1] 1 2 3 4
```

Já conseguimos imprimir `pt2d`.
Embora `print()` não saiba nada sobre a classe `point2d`, tem predefinições sensatas para lidar com uma grande variedade de objetos.

```R
pt2d
#> $x
#> [1] 2.5

#> $y
#> [1] 4.2

attr(,"class")
#> [1] "point2d"
```

Isto é bastante verboso, e podemos querer uma forma de imprimir o ponto de modo conciso e legível.

Fácil: basta adicionar uma função chamada `print.point2d()`.
O nome tem de ter a forma `methodname.classname`, para que o despachante saiba o que procurar.

```R
print.point2d <- function(pt) {
  cat("Cartesian coords (", pt$x, ", ", pt$y, ")\n", sep="")
}

pt2d
#> Cartesian coords (2.5, 4.2)
```

Agora suponhamos que queremos criar um novo método genérico, por exemplo `flipvert()` para inverter o sinal da coordenada `y`.

Novamente, fácil:

```R
flipvert <- function(x, ...) UseMethod("flipvert")
```

Isto cria um despachante, em que `x` é o nosso objeto com uma classe S3 e `...` trata de quaisquer argumentos extra de que as definições dos métodos possam precisar ("argumentos ponto", como descrito no [conceito de Funções][concept-functions]).

Podemos então definir o método para `point2d` e usá-lo.

```R
flipvert.point2d <- function(pt) {
  pt$y <- -pt$y
  pt
}

flipvert(pt2d)
#> Cartesian coords (2.5, -4.2)

methods("flipvert")
#> [1] flipvert.point2d
```

O R já sabe como inverter o nosso ponto e como mostrar o resultado.

Podíamos expandir isto criando classes para 3D, para coordenadas polares, etc., e depois definir métodos para cada uma.

Do ponto de vista do utilizador final, existe apenas `flipvert(x, ...)`, e podemos confiar no R para determinar a classe da entrada e usar a implementação subjacente adequada.

~~~~exercism/caution
Nomes de funções no formato `verb.class` parecem métodos S3, tanto para os utilizadores como para o analisador sintático do R.
Evita usar nomes semelhantes noutros contextos.

É certo que o R base por vezes viola esta regra.
Devemos encarar isso como um infeliz acidente histórico (para funções ainda mais antigas do que o S3), que tem de ser preservado por compatibilidade com versões anteriores.
~~~~

### Herança

Os entusiastas da POO podem escrever vários capítulos de manual longos sobre herança, subclasses, mixins e tudo o resto.

O R limita-se a permitir-te fornecer vários nomes ao atributo `class`: um vetor de strings mais longo, em vez de uma única string.

Correndo o risco de esticar o exemplo até ao ponto de rutura, suponhamos que tínhamos criado uma classe genérica `point` e que queríamos criar as suas subclasses `point2d`, `point3d`, etc.

Então a definição de `point2d` usa simplesmente `class = c("point2d", "point")`: a classe específica e a classe mãe (ou classes).

Métodos genéricos como `print()` vão depois procurar em sequência por `print.point2d()`, `print.point()` e (provavelmente) `print.default()`, usando a primeira implementação que o despachante encontrar.

### Segurança

Muitas linguagens de POO (Java, C#, etc.) tiram partido do encapsulamento de dados dentro das classes para fazer verificações cuidadas em tempo de compilação e impor a segurança de tipos.

Repara que o S3 te deixa fazer praticamente o que quiseres, mesmo que não faça sentido (qualquer mensagem de erro aparece mais tarde, se chegar a aparecer).

A citar o ["Advanced R"][book-s3] (2e, secção 13.3):

> _Se já usaste outras linguagens de OO, isto pode deixar-te enjoado, mas na prática esta flexibilidade causa poucos problemas. O R não te impede de disparar no próprio pé, mas desde que não apontes a arma aos dedos e puxes o gatilho, não terás problemas._

Bem, _está bem?_
O R é soberbo para ciência de dados exploratória e estatística, muitas vezes em trabalho interativo.
Ninguém está a sugerir que o uses para escrever sistemas empresariais de finanças altamente seguros!

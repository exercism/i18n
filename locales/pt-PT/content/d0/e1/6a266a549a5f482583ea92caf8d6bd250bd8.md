# Introdução

Um **ciclo** é uma sequência de instruções que pode ser executada mais do que uma vez, até se atingir uma condição de fim.

Em x86-64, um ciclo é normalmente criado com um salto para uma etiqueta anterior:

```x86asm
example_loop:
    ...
    jmp example_loop
```

Repara que um salto incondicional para uma etiqueta anterior transfere sempre a execução para essa etiqueta.
Isto significa que o ciclo vai repetir-se indefinidamente, a menos que exista outro salto para fora da sequência repetida.

Por exemplo, este ciclo não termina:

```x86asm
infinite_loop:
    inc rax
    jmp infinite_loop ; always jumps to 'infinite_loop', repeating 'inc rax' forever
```

E este ciclo pode terminar, dependendo de a condição se verificar:

```x86asm
maybe_finite_loop:
    cmp rax, 1
    je out_of_loop ; jumps to 'out_of_loop' if rax == 1, breaking the loop

    inc rax
    jmp maybe_finite_loop ; always jumps to 'maybe_finite_loop'
out_of_loop:
    ...
```

## Ciclos de contagem

Um ciclo de contagem termina quase sempre da mesma forma: uma instrução que atualiza um contador ou compara dois valores, imediatamente seguida de um salto condicional que decide se se dá mais uma volta.

```x86asm
sum_array:
    ; rdi is the memory address of an array
    ; rsi is the number of elements in the array

    mov eax, 0           ; running total
.loop:
    add rax, qword [rdi] ; add the current element
    add rdi, 8           ; advance to the next element
    sub rsi, 1           ; one fewer element to process, setting ZF at zero
    jnz .loop            ; repeat while the counter is not yet zero
    ret
```

~~~~exercism/note
`cmp rsi, 0` não é necessário no código acima porque `sub rsi, 1` já define o `zero flag (ZF)` quando o resultado é `0`.

Embora `cmp` seja a principal forma de testar condições em assembly, muitas instruções atualizam os flags.
Por exemplo, muitas instruções de aritmética inteira ou de operações bit a bit atualizam o `ZF` quando o resultado é `0`, e o `SF` quando o resultado é negativo (ou seja, quando o bit de topo está a 1).

Podes consultar uma [referência][reference] para ver que flags são afetados por cada instrução.

[reference]: https://www.felixcloutier.com/x86/
~~~~

Repara que, no exemplo acima, se presume que `rsi` é maior do que `0`.
Se fosse `0`, então `sub rsi, 1` reduziria `rsi` a `-1`, que é um número sem sinal muito grande.
Seriam precisas mais `18,446,744,073,709,551,615` iterações até o ciclo terminar.
Além disso, como o comprimento do array é `0`, qualquer acesso à memória estaria fora dos limites.

Se não houver garantias quanto ao comprimento de um array, há duas abordagens comuns.

A primeira é mover a condição de fim para o início do ciclo e ter depois um salto incondicional no fim:

```x86asm
sum_array:
    mov eax, 0
.loop:
    cmp rsi, 0
    je .done
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jmp .loop
.done:
    ret
```

A segunda é testar uma vez se o array tem comprimento zero antes do início do ciclo:

```x86asm
sum_array:
    mov eax, 0

    cmp rsi, 0
    je .done
.loop:
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jnz .loop
.done:
    ret
```

Esta segunda abordagem é normalmente mais eficiente do que a primeira, porque há menos ramificações no corpo do ciclo.
Vais aprender mais sobre isto num conceito futuro.

~~~~exercism/advanced
Em algumas situações, as CPUs modernas conseguem fundir duas instruções diferentes numa única operação.
Esta otimização chama-se **macrofusion**.

Muitas instruções aritméticas, como `sub` e `add`, bem como `cmp` e `test`, fundem-se habitualmente com um salto condicional que vem logo a seguir.
Isto significa que uma instrução como `cmp rax, rdx` imediatamente seguida de um salto condicional pode normalmente ser tratada pela CPU como uma única operação.

A Macrofusion depende da CPU e há alguma variação quanto às instruções que se fundem com cada salto condicional.

Uma referência útil é [The microarchitecture of Intel, AMD, and VIA CPUs, by Agner Fog][agner-uarch].
A secção 3.4.2.2 (Optimizing for Macrofusion) do [Intel optimization reference manual][intel-opt] também lista pares que se fundem em CPUs Intel.

[agner-uarch]: https://www.agner.org/optimize/microarchitecture.pdf
[intel-opt]: https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf
~~~~

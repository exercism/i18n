# Sobre

Os programadores tentam normalmente escrever software perfeito e, na maioria das vezes, falham.

As coisas correm mal, de forma inesperada, e precisamos de ser capazes de lidar com isso.

Alguns criadores de linguagens consideram que a prioridade é detetar um erro o mais depressa possível e terminar a execução com uma mensagem informativa que ajude na depuração.

As linguagens de ciência de dados tendem a adotar uma abordagem mais matizada.
Alguns erros são tão graves que é necessária uma terminação imediata, mas muitas vezes é melhor assinalar um problema como algo a tratar mais tarde e continuar a execução.

Vimos no Conceito [Nada][nothingness] que a Julia disponibiliza vários marcadores para valores problemáticos: [`missing`][nothing], [`NaN`][NaN] e `Inf`.
Se estes são uma abordagem melhor do que terminar o programa numa situação específica é uma questão de bom senso do programador.

_Uma nota de nomenclatura_ antes de entrar nos detalhes: a documentação da Julia trata as palavras "erro" e "exceção" como, em grande medida, intercambiáveis.
O conteúdo abaixo pode ser igualmente inconsistente.

## Tipos de erro padrão

A esta altura do programa de estudos, já deves ter visto muitas mensagens de erro da Julia.
Por exemplo:

```julia-repl
julia> Int(3.14)
ERROR: InexactError: Int64(3.14)
```

Tentar converter um número de vírgula flutuante num inteiro implica uma perda de precisão, por isso obtemos um `InexactError`.

`InexactError` é um tipo, um de vários ([atualmente 25][errors]) incorporados na Julia como padrão.
Todos são subtipos de `Exception`:

```julia-repl
julia> supertype(InexactError)
Exception
```

## `throw()`

Alguns dos tipos de erro padrão podem ser úteis para gerar no teu próprio código.

Tal como todos os tipos concretos, os erros têm construtores.
Aceitam uma variedade de argumentos, por isso consulta a [documentação][errors] para o que queres usar.

```julia-repl
julia> DomainError(42, "out of range")
DomainError(42, "out of range")
```

Para usar o erro, envolve o construtor numa função [`throw()`][throw]:

```julia-repl
julia> throw(DomainError(42, "out of range"))
ERROR: DomainError with 42:
out of range
```

## `error()`

Para uma abordagem rápida e improvisada, a função [`error()`][error] pode ser conveniente.
Aceita uma string (ou os componentes de uma string) como argumento:

```julia-repl
julia> happy = false;
julia> happy || error("😞 something went wrong")
ERROR: 😞 something went wrong
```

## Erros personalizados

Criar novos tipos de erro é, em princípio, muito fácil.
Basta adicionar outro subtipo de `Exception`:

```julia-repl
julia> struct MyError <: Exception end

julia> throw(MyError)
ERROR: MyError
```

No entanto, o exemplo acima não tem campos e o construtor não aceita argumentos, por isso não temos controlo sobre a mensagem de erro.
Podemos adicionar um campo de mensagem:

```julia-repl
julia> struct AnotherError <: Exception
           msg::String
       end

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError("Wrong!")
```

Imprimir simplesmente o construtor ainda não é bem o que queremos.
Compara com o exemplo anterior em que lançámos um `DomainError`.

Para que um erro personalizado seja tratado da mesma forma que os erros incorporados, temos de adicionar um método [`showerror()`][showerror]:

```julia-repl
julia> Base.showerror(io::IO, e::AnotherError) =
           print(io, "AnotherError: ", e.msg)

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError: Wrong!
```

Esta funcionalidade, um tanto mal documentada, liga na essência o nosso tipo de erro personalizado ao sistema de tratamento de erros padrão da Julia.

## Asserções

A ideia básica de uma asserção é "esta afirmação deve ser verdadeira, por isso protesta ruidosamente se for falsa".
O valor disto está sobretudo na depuração, pois o código de produção nunca deve falhar uma asserção.

Vimos no Conceito [Tipos][types] que podemos adicionar asserções de tipo, por exemplo para verificar o tipo devolvido por uma função.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

De um modo mais geral, a macro [`@assert`][assert] permite-nos testar qualquer expressão que resulte num valor booleano:

```julia-repl
julia> n = 22;
julia> @assert isodd(n) "n must be odd"
ERROR: AssertionError: n must be odd
```

## `try`...`catch`

Alguns erros são necessariamente fatais, mas muitas vezes esperamos que o programa recupere de forma graciosa.

Por predefinição, um erro termina imediatamente a função atual e o erro (com qualquer mensagem informativa) é passado à função que fez a chamada.

Isto continua pela pilha de chamadas acima, até que o código de nível superior termine com uma mensagem de erro.

Em qualquer fase, o erro pode ser intercetado com um bloco [`try...catch`][try-catch] que tenta tratá-lo.

```julia-repl
julia> n = -1;
julia> try
           log_n = log(n)
       catch problem
           if problem isa DomainError # number out of range
               # See next section for more on @warn and @info
               @warn "you may have supplied a negative real number: $n"
               @info "trying with complex argument"
               log_n = log(Complex(n))  # fallback calculation

           elseif problem isa MethodError # no idea what n is
               @error "please supply a valid argument"
 
           else
              rethrow() # the error could be anything else
           end
      end
┌ Warning: you may have supplied a negative real number: -1
└ @ Main REPL[3]:5
[ Info: trying with complex argument
0.0 + 3.141592653589793im  # success
```

No exemplo acima, `log(n)` precisa que `n` seja um valor real positivo ou qualquer valor complexo.
O `try ... catch` deteta problemas com valores reais negativos e devolve a resposta complexa correta `iπ` em notação matemática.

Se forneceres, por exemplo, um argumento do tipo string, não há recuperação possível a não ser pedir ao utilizador que o corrija.

Como último recurso, adicionámos [`rethrow()`][rethrow] para tudo o que não seja `DomainError` nem `MethodError`.

Há também mais cláusulas opcionais:

- [`else`][else], que é executada se a cláusula `try` tiver êxito;
- [`finally`][finally], que pode ser usada para limpar recursos externos, independentemente de o `try` ter êxito ou falhar: fechar ficheiros, fechar ligações a bases de dados...

***Nota:*** Às vezes um `try...catch` é o que precisas, mas evita usá-lo em excesso.
Se puderes usar um bloco `if...else` em vez disso, será muito mais eficiente do que capturar exceções.

## Registo

Repara que a função `error()`, discutida acima, não deve ser confundida com a macro [`@error`][error_macro].

A função gera uma exceção, que será propagada pela pilha de chamadas a menos que seja capturada.

A macro `@error`, juntamente com as suas congéneres [`@debug`][debug_macro], [`@info`][info_macro] e [`@warn`][warn_macro], faz parte do módulo [`Logging`][logging] e destina-se a gerar mensagens informativas sem alterar o fluxo do programa.

A saída vai para o terminal por predefinição (com cores codificadas por gravidade), embora numa aplicação real haja muitas outras possibilidades.

```julia-repl
julia> @warn "Something looks not quite right"
┌ Warning: Something looks not quite right
└ @ Main REPL[55]:1

julia> @error "Panic!"
┌ Error: Panic!
└ @ Main REPL[56]:1
```

Vê também o exemplo anterior, em `try...catch`.

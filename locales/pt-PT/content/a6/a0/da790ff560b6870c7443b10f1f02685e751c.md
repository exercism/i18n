# estratégia de merge

Os mantenedores do percurso Rust [decidiram](https://github.com/exercism/v3/discussions/1725#discussion-7438) registar por escrito a nossa estratégia de merge, para comunicar as expectativas e incentivar contribuições de qualidade.

## princípios gerais

- esforçamo-nos por aceitar _todas_ as contribuições
  - Vamos elevar as contribuições a um elevado padrão de qualidade através de uma revisão colaborativa e iterativa.
  - Adotamos uma abordagem pessimista ao merge. Pensa nas revisões dos mantenedores como o feedback do compilador de Rust. A quantidade de feedback pode parecer esmagadora e frustrante. Mas vamos trabalhar contigo para levar isto até à meta! Por isso, continua o bom trabalho.
- Cada pull request tem de ter pelo menos uma "Approval" e nenhuma "Request Changes" de um mantenedor do percurso antes de se lhe poder fazer merge.
- Nenhum mantenedor pode aprovar o seu próprio pull request.

## fluxo de trabalho do pull request

### definições

| Termo              |                                                                                               Significado |
| ------------------ | --------------------------------------------------------------------------------------------------------: |
| Contribuidor       |                                                                      Qualquer pessoa que submeta um pull request. |
| Mantenedor         |              Qualquer pessoa que pertença à [equipa @exercism/rust](https://github.com/orgs/exercism/teams/rust). |
| ramo de desenvolvimento | O ramo de desenvolvimento predefinido do repositório [v3](https://github.com/exercism/v3). Atualmente, `master`. |

### o fluxo de trabalho

1. Os contribuidores começam por abrir um pull request em [rascunho](https://github.blog/2019-02-14-introducing-draft-pull-requests/) ou um pull request completo com as suas alterações
   1. Usar a funcionalidade de rascunho sinaliza que o trabalho está pronto para uma revisão de alto nível, mas que os detalhes podem ainda não estar implementados, estar incompletos ou estar errados.
   1. Depois de um número não especificado de iterações dos passos 2 e 3, o contribuidor marca o pull request como pronto para revisão.
1. Um outro mantenedor deve rever a contribuição e dar feedback.
1. O contribuidor deve dar resposta a _todo_ o feedback dos mantenedores como parte do pull request.
   1. Os mantenedores devem ponderar usar a funcionalidade de sugestões do GitHub para alterações de pormenor ou de resolução simples.
   1. Contestar é bem-vindo quando o contribuidor acredita que tem razão e que um mantenedor está errado quanto a um ponto do feedback. "Dar resposta" a um ponto do feedback não é sinónimo de o implementar servilmente.
1. O mantenedor deve analisar o feedback e, ou:
   1. aprovar
   1. pedir alterações adicionais. Neste ponto, o processo volta ao passo 3.
1. Após a aprovação, um mantenedor deve fazer merge do pull request.
   1. Os mantenedores devem fazer merge dos seus próprios pull requests. Como os contribuidores não são necessariamente mantenedores, é um mantenedor que tem de realizar este passo.

## merge otimista

Os mantenedores do percurso Rust decidiram adotar o merge otimista temporariamente, para acelerar o desenvolvimento do percurso v3.

- Isto só se aplica ao repositório v3
- Voltaremos a uma estratégia de merge pessimista quando lançarmos a v3 em produção.
- Vamos aprovar e fazer merge de trabalho incompleto
  - Se compilar, ficamos com ele.
  - Damos prioridade à velocidade de iteração em vez dos pormenores mais finos de um design de software correto.
- Cada pull request tem de ter pelo menos uma "Approval" de um mantenedor do percurso antes de se lhe poder fazer merge.

# Sobre

O código escalar baseia-se em flags definidas por várias instruções para ramificar em resposta a uma determinada condição.
Os valores empacotados, no entanto, representam não um, mas muitos valores em paralelo.
Uma mesma condição pode falhar para um lane e verificar-se para outro.

É por isso que o código SIMD é [sem ramificações][branchless-code] por predefinição.

Em vez de se basear em flags, as comparações empacotadas produzem habitualmente uma **máscara** no operando de destino.
Para cada lane, a comparação preenche todo o lane com uns quando é verdadeira e com zeros quando é falsa.
Lido como um inteiro com sinal, um lane verdadeiro é `-1` e um lane falso é `0`.

Esta máscara pode depois ser combinada com [operações bit a bit][simd-bitwise] para filtrar lanes específicos.

## Comparações empacotadas

Um `cmp` escalar é genérico no sentido em que é usado para definir várias flags ao mesmo tempo.
Outra instrução pode depois consumir essas flags para ramificar ou efetuar cálculos.

No entanto, como uma comparação empacotada verifica uma condição e calcula uma máscara ao mesmo tempo, não é genérica.
É preciso indicar à comparação a condição exata que está a ser testada.

Há duas formas de o fazer:

- As comparações de inteiros recebem a condição como sufixo: `eq` para igualdade e `gt` para maior que.
  As outras variantes constroem-se compondo o resultado de uma destas.
- As comparações de vírgula flutuante recebem a condição codificada num imediato.
  Valores diferentes desse imediato correspondem a condições diferentes que estão a ser testadas.

Para além do uso de um sufixo condicional específico nas comparações de inteiros, a sintaxe segue a mesma estrutura que já vimos:

- Para inteiros, `p` + `cmp` + condição + tamanho (`b`, `w`, `d` ou `q`).
- Para números de vírgula flutuante, `cmp` + `p` + tamanho (`s` ou `d`).
  A condição é passada num imediato como operando extra.

### Comparações de inteiros

Como referido, só existem comparações de inteiros para igualdade e para maior que:

| instrução                                  | descrição                        |
|--------------------------------------------|----------------------------------|
| `pcmpeqb`, `pcmpeqw`, `pcmpeqd`, `pcmpeqq` | igualdade por lane               |
| `pcmpgtb`, `pcmpgtw`, `pcmpgtd`, `pcmpgtq` | maior que **com sinal** por lane |

```x86asm
movdqa  xmm0, [rel scores]
pcmpgtd xmm0, [rel threshold] ; lane i = 0xFFFFFFFF (-1) if scores[i] > threshold[i], else 0
```

Para criar uma comparação de menor que, usa `gt` com os operandos trocados: `a < b` == `b > a`.

Repara que a comparação é **com sinal**.
Para efetuar uma comparação sem sinal, inverte o bit mais significativo de ambos os operandos.
Isto pode ser feito com um XOR com uma máscara em que só o bit mais significativo está definido.

~~~~exercism/note
Dois truques úteis são:

1. Fazer XOR de um registo consigo próprio para produzir tudo a zeros.
2. Comparar um registo consigo próprio para produzir tudo a uns.

Por exemplo:

```x86asm
pxor    xmm4, xmm4 ; xmm4 = all zeros
pcmpeqd xmm7, xmm7 ; xmm7 = all ones
```

Tudo a zeros e tudo a uns são máscaras comuns para codificar "falso em todo o lado" e "verdadeiro em todo o lado", respetivamente.
Também podem ser usadas para representar `0` empacotado ou `-1` empacotado, que são valores sentinela comuns.
Por exemplo, o NUL que marca o fim de uma string é um `0`.
~~~~

### Comparações de vírgula flutuante

Os lanes de vírgula flutuante usam uma forma diferente: uma única instrução, `cmpps` (e `cmppd` para lanes de 64 bits), com a condição como imediato:

```x86asm
movaps xmm0, [rel readings]
cmpps  xmm0, [rel limits], 1 ; condition 1 is "less than": lane i = all ones if readings[i] < limits[i]
```

O NASM também tem pseudo-instruções que correspondem ao imediato correto e são mais fáceis de memorizar.
Em todas as seguintes, o `x` em `px` pode ser `s` (números de vírgula flutuante de 32 bits) ou `d` (números de vírgula flutuante de 64 bits):

| pseudo-instrução | imediato  | comparação             |
|------------------|-----------|------------------------|
| `cmpeqpx`        | 0         | a == b                 |
| `cmpltpx`        | 1         | a <  b                 |
| `cmplepx`        | 2         | a <= b                 |
| `cmpunordpx`     | 3         | a é NaN ou b é NaN     |
| `cmpneqpx`       | 4         | a != b                 |
| `cmpnltpx`       | 5         | a >= b                 |
| `cmpnlepx`       | 6         | a >  b                 |
| `cmpordpx`       | 7         | nem a nem b é NaN      |

~~~~exercism/caution
O NaN compara-se como não ordenado: não é menor que, nem igual a, nem maior que nada, incluindo ele próprio.
Os predicados ordenados, como `cmpltps`, devolvem falso quando um dos operandos é NaN, enquanto os predicados não ordenados devolvem verdadeiro.
É por isso que existem `cmpordps` e `cmpunordps`, para testar explicitamente se há NaN.
~~~~

## Selecionar com uma máscara

Uma máscara codifica o resultado de uma condição.
Pode depois ser usada para escolher, lane a lane, entre dois conjuntos de valores de acordo com essa condição.
Retiramos o lane de um valor onde a máscara é verdadeira e de outro onde é falsa:

```x86asm
; result = (a AND mask) OR (b AND NOT mask)
movdqa xmm2, xmm0  ; xmm0 holds the mask, keep a copy
pand   xmm2, xmm3  ; xmm2 = a AND mask: lanes of a where mask is true
pandn  xmm0, xmm4  ; xmm0 = NOT mask AND b: lanes of b where mask is false
por    xmm2, xmm0  ; combine the two halves
```

Este padrão é a forma empacotada da seleção sem ramificações.
Todos os lanes são calculados, e é só a máscara que decide que valor sobrevive, sem qualquer `jcc`.

## Blends dedicados

Existem instruções que efetuam essa mesma seleção diretamente, lendo um bit por elemento a partir de um registo de máscara.
Chamam-se instruções **blend**:

| instrução   | elemento     | origem da máscara |
|-------------|--------------|-------------------|
| `pblendvb`  | byte         | `xmm0` implícito  |
| `blendvps`  | lane de 32 bits | `xmm0` implícito |
| `blendvpd`  | lane de 64 bits | `xmm0` implícito |

Repara que a primeira instrução segue a sintaxe dos inteiros, enquanto as outras duas seguem a sintaxe dos números de vírgula flutuante.
No entanto, como estas instruções selecionam simplesmente bytes em bruto, qualquer uma delas pode ser usada tanto com inteiros como com números de vírgula flutuante.

Para cada elemento, o blend mantém o destino quando o bit mais significativo do elemento correspondente da máscara está a zero, e toma a fonte quando está a um.
Só esse **bit mais significativo** é consultado, o que uma máscara de comparação satisfaz, já que os seus lanes são todos uns ou todos zeros.
O registo da máscara é sempre `xmm0`, que é implícito:

```x86asm
movaps   xmm0, [rel mask]  ; the selecting mask must be in xmm0
movaps   xmm1, [rel b]     ; destination: kept where the mask bit is clear
blendvps xmm1, [rel a]     ; source: taken where the mask bit is set
```

Também é possível usar `pblendvb` para selecionar lanes de uma máscara de comparação para qualquer outro tamanho.
Como todos os bytes de um lane verdadeiro são uns, `pblendvb` seleciona-os todos.

~~~~exercism/note
Estas instruções acrescentam todas um `v` depois da operação que efetuam (`blend`).
Este `v` significa _variável_, porque a seleção não é estática: depende de um registo.

Existem também variantes sem `v`, que selecionam de acordo com um imediato.
Seguem o mesmo padrão, selecionando um lane `i` se o bit `i` do imediato estiver definido.
~~~~

## De uma máscara de volta ao escalar

Apesar de poderoso, o código SIMD não tem grande parte da flexibilidade do código escalar.
Em muitas situações, é necessário passar de um registo empacotado de volta para o mundo das instruções escalares.

A família de instruções `movmsk` serve de ponte entre os dois mundos.
Estas instruções extraem o **bit mais significativo** de cada lane para um registo de uso geral:

| instrução   | recolhe                       | largura do resultado |
|-------------|-------------------------------|----------------------|
| `pmovmskb`  | o bit mais significativo de cada um dos 16 bytes | 16 bits   |
| `movmskps`  | o bit mais significativo de cada um dos 4 dwords | 4 bits    |
| `movmskpd`  | o bit mais significativo de cada um dos 2 qwords | 2 bits    |

Se for usada depois de uma comparação, cada bit a um representa um lane "verdadeiro" e cada bit a zero, um lane "falso".
Este resultado pode depois ser manipulado como habitualmente com instruções escalares.
Por exemplo, uma `popcnt` conta o número de correspondências e uma `tzcnt` encontra a primeira.

O registo de uso geral pode ter 32 ou 64 bits de largura.

## Testar um vetor inteiro

Existe também uma variante empacotada da instrução escalar `test`: `ptest`.

É semelhante à sua equivalente escalar, na medida em que efetua uma operação AND entre dois operandos, sem os modificar.
Ao contrário de `test`, o `ptest` também efetua uma operação ANDN, negando o primeiro operando.

Assim, o `ptest` pode ser visto como uma versão não destrutiva do `pand` e do `pandn` que define flags de acordo com o resultado.
Tal como estas duas instruções, o `ptest` trata todo o registo SIMD como um único lane e, por isso, não tem prefixo de tamanho.

Se o resultado de uma operação AND for `0`, a `ZF` fica definida, e se a operação ANDN der `0`, é a `CF` que fica definida.
Isto significa que o `ptest` pode ser usado para verificar tanto uma máscara de tudo a uns como uma de tudo a zeros:

1. Usar `ptest` num registo consigo próprio define a `ZF` apenas se o registo for todo zeros.
   Isto imita o truque escalar comum de usar `test` num registo consigo próprio para verificar se é `0`.
2. Usar `ptest` num registo com uma máscara de tudo a uns define a `CF` apenas se o registo for todo uns.
   Além disso, define a `ZF` apenas se o registo for todo zeros, o que permite verificar as duas máscaras ao mesmo tempo.

```x86asm
pxor  xmm0, xmm0   ; xmm0 = all zeros
ptest xmm0, xmm0   ; xmm0 AND xmm0 == 0 => ZF is set
                   ; (NOT xmm0) AND xmm0 == 0 => CF is set

; Using ptest on a register with itself makes ZF set only if the register is all zeros

pcmpeqb xmm1, xmm1 ; xmm1 = all ones
ptest   xmm0, xmm1 ; xmm0 AND xmm1 == 0 => ZF is set
                   ; (NOT xmm0) AND xmm1 != 0 => CF is cleared

pcmpeqb xmm3, xmm3 ; xmm3 = all ones
ptest   xmm3, xmm1 ; xmm3 AND xmm1 != 0 => ZF is cleared
                   ; (NOT xmm3) AND xmm1 == 0 => CF is set

mov eax, -1
movd  xmm2, eax    ; xmm2 = {-1, 0, 0, 0}
ptest xmm2, xmm1   ; xmm2 AND xmm1 != 0 => ZF is cleared
                   ; (NOT xmm2) AND xmm1 != 0 => CF is cleared

; After using ptest on a register with an all-ones mask, ZF is only set if the register is all zeros.
; CF may be:
; 1. cleared, if the register is all zeros or is partially set
; 2. set, if the register is all ones
```

O resultado de um `ptest` pode ser usado para ramificar ou em instruções sem ramificações, como `setcc` ou `cmovcc`, como habitualmente.

## AVX e mais além

O AVX dá às comparações, aos blends e ao `ptest` uma forma com o prefixo `v` em registos mais largos.

O blend variável muda de forma.
A máscara já não é o `xmm0` implícito, mas sim um quarto operando explícito:

```x86asm
vpcmpgtd  ymm0, ymm1, ymm2       ; eight 32-bit lanes compared at once
vblendvps ymm0, ymm1, ymm2, ymm3 ; ymm3 is the mask, named explicitly
vptest    ymm0, ymm0
```

As extensões AVX-512 alteram o modelo mais profundamente.

Em primeiro lugar, acrescentam uma nova classe de registos SIMD de 64 bytes, chamados `zmm`.
Estes expandem os registos `ymm` correspondentes, tal como os registos `ymm` expandem os registos `xmm`.

Em segundo lugar, estas extensões criam também toda uma nova classe de **registos opmask**, de `k0` a `k7`, cujo principal objetivo é servir de máscara para as instruções SIMD.
As comparações já não escrevem em vetores, mas sim num destes novos registos.
Também podem ser usados diretamente em muitas instruções como predicados com uma máscara de escrita `{k}`, selecionando lanes _diretamente_:

```x86asm
vpcmpgtd  k1, zmm0, zmm1         ; k1 gets one bit per lane
vmovdqa32 zmm2{k1}, zmm3         ; copy only the lanes whose bits are set in k1
```

Por fim, existem novas instruções para operar sobre esses novos registos, incluindo copiá-los para registos de uso geral.
Isto torna as instruções `movmsk` desnecessárias, e não há suporte para instruções `movmsk` em registos `zmm`.

Estas extensões são mencionadas por uma questão de completude.
Os exercícios deste track usam as formas SSE.

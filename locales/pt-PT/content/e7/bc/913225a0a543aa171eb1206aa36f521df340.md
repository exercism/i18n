# Geradores de testes

Os geradores de testes permitem que as tracks gerem testes automaticamente, sem que tenhamos de os escrever à mão. Cada gerador de testes lê os `canonical data` do exercício, que definem o nome do teste, as suas entradas e as suas saídas. Podes ler mais sobre a abordagem do Exercism aos conjuntos de testes [aqui](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Gerar testes automaticamente elimina qualquer tipo de erro do utilizador ao criar testes. Queremos que os testes estejam corretos em relação aos seus dados canónicos. A geração de testes também torna muito mais fácil manter os testes atualizados. À medida que os dados canónicos mudam, os testes são atualizados automaticamente quando executas o gerador desse teste.

Encontras um exemplo de um ficheiro de dados canónicos [aqui](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)

## Termos comuns

Quando exploras os dados canónicos e o código dos geradores, deparas-te com muita terminologia comum. Esta lista ajuda a clarificar o que cada termo representa.

* Dados Canónicos - Representam o conjunto de testes completo.
* Caso de Dados Canónicos - A representação de um único caso de teste.
* Descrição - O nome do teste.
* Propriedade - O método a chamar ao executar o teste.
* Entrada - A entrada do caso de teste.
* Esperado - O valor esperado ao executar o caso de teste.

## Adicionar um gerador simples

Adicionar um gerador de testes é simples. Basta acrescentares uma classe ao ficheiro `Generators.fs` na pasta `generators`, com o nome do exercício (em PascalCase), e estenderes a classe abstrata `GeneratorExercise`.

Um exemplo de um gerador simples é o exercício Bob. O código-fonte está abaixo, mas também o podes ver no repositório [aqui](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174).

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

Este é um gerador totalmente funcional, não é preciso escrever mais código. No entanto, a sua simplicidade vem do facto de o conjunto de testes e o próprio programa serem relativamente triviais.

## Adicionar um gerador complexo

Para muitos geradores, o comportamento predefinido da classe `GeneratorExercise` chega. No entanto, para geradores mais _complexos_, podes substituir um ou mais dos seus métodos virtuais:

### Método: RenderInput

Renderiza a entrada de um método de teste.

#### Exemplo

O gerador `Gigasecond` renderiza o valor de entrada como um valor `DateTime` (entre parênteses):

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

Repara que podes usar o campo `key` para personalizar a saída apenas de campos de entrada específicos. O gerador `Yacht` faz isso mesmo:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Método: RenderExpected

Renderiza o valor esperado de um método de teste.

#### Exemplo

O gerador `Connect` renderiza o valor esperado como um valor `Option<T>`:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Método: RenderSut

Renderiza o Sistema em Teste (SUT, do inglês *System Under Test*). É o valor real que é verificado em relação ao valor esperado.

#### Exemplo

O gerador `RunLengthEncoding` tem um caso de teste em que verifica que codificar e depois descodificar a entrada dá o mesmo valor. O método `RenderSut` é substituído para converter o que seria uma única chamada a uma função `consistency` que não existe numa cadeia de chamadas `encode |> decode`:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Método: RenderArrange

Renderiza a parte de preparação do método de teste. É nesta parte que o SUT é criado.

O comportamento predefinido é habitualmente o que queres. Só em circunstâncias muito especiais é que vais querer alterá-lo.

Nota: este método devolve uma `string list`, em que cada `string` corresponde a uma única linha renderizada no ficheiro de teste.

### Método: RenderAssert

Renderiza a parte de verificação do método de teste. É nesta parte que se faz a verificação para confirmar que o SUT corresponde ao valor esperado.

O comportamento predefinido é habitualmente o que queres. Só em circunstâncias muito especiais é que vais querer alterá-lo.

Nota: este método devolve uma `string list`, em que cada `string` corresponde a uma única linha renderizada no ficheiro de teste.

### Método: RenderSetup

Renderiza quaisquer métodos utilitários ou de preparação adicionais. Isto pode ser usado para definir métodos auxiliares que podem ser usados nos métodos de teste.

O código de preparação é adicionado _antes_ dos métodos de teste, para permitir que os métodos de preparação sejam usados nos métodos de teste.

Nota: este método devolve uma `string list`, em que cada `string` corresponde a uma única linha renderizada no ficheiro de teste.

#### Exemplo

O gerador `Zipper` acrescenta dois métodos auxiliares que são usados nos métodos de teste para eliminar algum código repetitivo e aborrecido:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Método: RenderValue

Renderiza um único valor (que é usado para renderizar os parâmetros de entrada, o valor esperado e o SUT).

### Exemplo

O gerador `ComplexNumbers` renderiza valores diferentes consoante o tipo do valor:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Método: MapCanonicalDataCase

Mapeia o caso de dados canónicos. Isto pode ser útil se quiseres acrescentar ou remover propriedades.

O comportamento predefinido é habitualmente o que queres. Só em circunstâncias muito especiais é que vais querer alterá-lo.

#### Exemplo

O gerador `ScaleGenerator` usa o mapeamento do caso de dados canónicos para acrescentar uma propriedade em falta com o valor `null` (o que facilita o processamento posterior):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Método: PropertiesUsedAsSutParameter

Especifica que propriedades devem ser usadas como parâmetros do SUT.

O comportamento predefinido é habitualmente o que queres. Só em circunstâncias muito especiais é que vais querer alterá-lo.

#### Exemplo

O `RailFenceCipher` define explicitamente as propriedades usadas como parâmetros do SUT para alterar a ordem em que são passadas:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Método: PropertiesWithIdentifier

Especifica que propriedades devem ter um identificador atribuído. Se uma propriedade estiver nesta lista, o seu valor é-lhe atribuído numa linha separada, ao seu próprio identificador.

#### Exemplo

O gerador `Transpose` optou por usar identificadores para todas as propriedades:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Método: IdentifierTypeAnnotation

Em alguns casos, queres que um identificador tenha um tipo explícito. Um caso comum é quando um valor é uma lista vazia. Nesses casos, o FsUnit precisa de uma anotação de tipo para conseguir executar a verificação com êxito.

#### Exemplo

O gerador `Minesweeper` acrescenta uma anotação de tipo `string list` para valores vazios:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Método: AdditionalNamespaces

Devolve uma lista de namespaces adicionais a abrir no ficheiro de teste.

#### Exemplo

O gerador `Gigasecond` trabalha com instâncias de `DateTime` e, por isso, acrescenta o seu namespace à lista de namespaces adicionais:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Método: AssertTemplate

O modelo de verificação a usar. Encontras a lista completa de modelos de verificação em `generators/Templates/_Assert*.liquid`

#### Exemplo

O gerador `RationalNumbers` usa o modelo `"AssertEqualWithin"` para permitir comparar doubles por igualdade com uma tolerância específica:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Método: TestFileFormat

O formato do ficheiro de teste: um módulo ou uma classe.

O comportamento predefinido é praticamente sempre o que queres. Só em casos extremamente raros é que vais querer alterá-lo.

#### Exemplo

O gerador `Grep` define-se como uma classe de teste para permitir usar métodos de preparação e de limpeza:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Método: TestMethodName

Especifica o nome do método de teste.

O comportamento predefinido é habitualmente o que queres. Só em circunstâncias muito especiais é que vais querer alterá-lo.

#### Exemplo

O gerador `Zipper` faz alguma limpeza ao nome do método de teste:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Método: UseFullMethodName

Indica se o nome do método de teste usado deve seguir o caminho completo. Para casos de teste aninhados, isso significa que o nome do método de teste será precedido pela descrição do(s) caso(s) pai.

O comportamento predefinido é habitualmente o que queres. Só em casos em que, de outra forma, houvesse vários métodos de teste com o mesmo nome é que vais querer alterá-lo.

#### Método: Signature

O gerador `KindergartenGarden` usa nomes de métodos completos para evitar conflitos entre nomes de métodos de teste:

```fsharp
override __.UseFullMethodName _ = true
```

### Método: SkipTestMethod

Indica se o método de teste deve ser marcado com a propriedade `Skip = true`.

O comportamento predefinido é praticamente sempre o que queres. Só em casos extremamente raros é que vais querer alterá-lo.

#### Método: Signature

O exercício `Markdown` é um exercício de refatoração e, como tal, todos os seus testes já devem estar num estado válido. Por isso, não acrescenta a propriedade `Skip` a nenhum dos seus métodos de teste:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Atualizar ficheiros existentes

É possível que um exercício existente não corresponda aos dados canónicos. Não há problema em atualizar o stub do exercício e/ou o exemplo do exercício para seguir os dados canónicos!

Além disso, se encontrares um problema num dos geradores ou conjuntos de testes existentes, basta abrires o gerador que queres atualizar, fazeres as tuas alterações e executares os geradores.

## Executar os geradores

Este repositório é programado com [.NET Core 2.x](https://www.microsoft.com/net/core). Para executar os geradores, basta executares o seguinte comando no diretório dos geradores:

`dotnet run`

Este comando usa todos os geradores de exercícios que estão definidos e gera todos os casos de teste de cada exercício. Usamos reflexão para obter todos os exercícios, por isso, se estiveres a acrescentar um novo teste, ele é incluído automaticamente quando executas o gerador.

Se só precisares de executar um único gerador, podes fazê-lo com o seguinte comando:

`dotnet run -e <exercise>`

Depois de executares o gerador, podes ver o resultado da geração navegando até ao ficheiro de teste desse exercício. Por exemplo, o conjunto de testes do exercício Bob encontra-se em:

`exercises/bob/BobTests.fs`

## Submeter um gerador

Se estiveres satisfeito com o resultado do teu gerador, gostaríamos muito que submetesses um pull request! Inclui o teu gerador, o conjunto de testes atualizado e quaisquer outros ficheiros correspondentes que possas ter alterado.

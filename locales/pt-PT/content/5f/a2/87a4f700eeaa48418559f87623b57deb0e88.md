# Especificação de Markdown

O seguinte descreve a forma como todos os ficheiros Markdown dentro do Exercism devem ser estruturados.

Algumas das regras deste documento ainda não estão implementadas em todo o Exercism.
Agradecemos PRs que as corrijam.
Todas as regras estão a ser adicionadas às nossas ferramentas de CI e de linting e devem ser respeitadas em alterações novas.

## Títulos

- Todos os ficheiros devem começar com um título de nível 1 (`# Some heading text`).
- Os títulos de nível 1 existem apenas para serem consumidos no GitHub ou equivalente.
- Se o ficheiro for apresentado pelo Exercism (por exemplo, mostrado no site ou renderizado através da CLI), este título é removido e é inserido um título contextual.
- Nenhum título pode descer mais de um nível em relação ao anterior (por exemplo, a `##` só pode seguir-se `###`, e não `####`).
- Para além do único título de nível 1 (`#`), só podem ser usados títulos de nível 2 (`##`), de nível 3 (`###`) e de nível 4 (`####`).

## Ligações

Usa [ligações de referência][reference-links], que são definidas no fundo do ficheiro Markdown, associadas a um identificador de referência e referenciadas por esse identificador no texto.

Este método facilita a manutenção, uma vez que as ligações só têm de ser atualizadas num único local.

Exemplo:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

As ligações devem ter sempre texto âncora, em vez de colocar o próprio URL no texto. Por exemplo, o seguinte não usa texto âncora e é mais difícil de ler.

```
If you want some more information, please visit https://google.com.
```

Usar texto âncora e ligá-lo é mais fácil de compreender e de contextualizar.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

O que é apresentado como «Se quiseres mais informações, o [Google][google-link] é um recurso útil.»

## Código

Sempre que se refere um elemento de código (por exemplo, funções ou palavras-chave), o código deve ser envolvido em acentos graves:

```
- The `printf()` function writes to the console.
```

O que é apresentado como:

- A função `printf()` escreve para a consola.

Código mais complexo (por exemplo, código com várias linhas) deve ser envolvido em três acentos graves. Deve indicar-se um [identificador de linguagem][language-identifier] a seguir aos três acentos graves de abertura, para ativar o realce de sintaxe:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

Quando possível, formata o código da forma mais relevante para o ambiente em que é apresentado. Se estiver disponível, consulta a documentação da tua linguagem.

Por exemplo, o Python tem o REPL (ciclo ler-avaliar-imprimir), que permite a quem programa escrever código diretamente num terminal. Se alguém estiver a depurar código, ou a correr uma função localmente para testar ou observar como funciona, é mais provável que use um REPL para isso, porque é mais conveniente escrever de forma interativa aí. Nesta situação, preferimos formatar o código de exemplo como se estivesse a ser escrito no REPL, com um `>>>` inicial:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

Noutros casos, faz mais sentido deixar o código formatado como se estivesse num ficheiro `.py`. Aqui, o estudante beneficia de ver algo que imita a forma como ele próprio escreveria o código.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

Uma forma rápida de distinguir os dois casos quando não é claro: se for código que o estudante pode correr num terminal, formata-o dessa forma. Se for código que o Exercism pode correr (em testes, código de biblioteca que o estudante vai escrever, etc.), opta por formatá-lo como código executável.

## Blocos especiais (por vezes chamados de admonições)

Suportamos tipos especiais de blocos que podem ser adicionados aos documentos para destacar comentários que não encaixam no corpo principal do texto.

<img width="500" alt="Bloco avançado do Markdown" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

Suportamos três tipos de blocos:

- **exercism/note:** Blocos que destacam informação adicional especialmente relevante
- **exercism/caution:** Coisas que as pessoas devem conhecer ou com que devem ter cuidado
- **exercism/advanced:** Informação que só é relevante para quem quer aprofundar um tema ou de quem se espera um conhecimento mais avançado.

Todos os blocos são escritos com 4 tiles, na forma de:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(Nota: em circunstâncias excecionais, também podes usar acentos graves ou outros níveis de tiles)

## Disposição

### Uma frase por linha

Os parágrafos devem ser dispostos com uma frase por linha. A [documentação do Ascii Doctor][asciidoctor] explica claramente a lógica disto.

Por exemplo, um único parágrafo deve ser disposto da seguinte forma:

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## Listas

Usa o caráter de hífen (`-`) como marcador das listas não ordenadas.

## Comentários

- Dá preferência a comentários Markdown em vez de comentários HTML (por exemplo, usa `[comment]: # (Actual comment...)` em vez de `<!-- Actual comment -->`)

Podes testar se o teu comentário Markdown é removido verificando como fica quando é renderizado com o commonmark no [babelmark3].

## HTML em linha

- O HTML em linha é permitido, mas deve ser usado com moderação
- Usa sempre alternativas nativas de Markdown quando existirem (por exemplo, usa `# ...` em vez de `<h1>...</h1>`)

## Imagens

Como o site suporta temas claro e escuro, as imagens submetidas pela comunidade têm de ser apresentadas corretamente em ambos os temas.
A solução é acrescentar um sufixo ao nome da imagem (antes da extensão do ficheiro):

1. Fazer com que o nome da imagem termine em `-invertible` (por exemplo, `graph-invertible.svg`). A imagem é invertida automaticamente quando é mostrada no tema escuro (através de `filter: invert(100%)`).
1. Fazer com que o nome da imagem termine em `-light` (por exemplo, `graph-light.png`) e criar também uma versão compatível com o tema escuro que termine em `-dark` (que seria `graph-dark.png`). Apresentamos automaticamente a imagem correta em função do tema do utilizador.

As imagens sem nenhum destes sufixos são usadas sem modificações em ambos os temas.
Isto significa que, se quiseres criar imagens em tons de cinzento, normalmente podes fazê-las ficar bem no tema claro e depois marcá-las como invertíveis.
Mas, se estiveres a usar uma imagem com muitas cores, talvez queiras criar duas variantes.

O nome completo da imagem (incluindo `-invertible`) deve ser colocado no Markdown onde a imagem é apresentada.
Para as imagens de tema claro/escuro, inclui **APENAS** a variante `-light`.
Esta lógica é respeitada em todos os documentos Markdown.

## Formatação automática

Alguns repositórios usam o [prettier][prettier] para garantir que todo o Markdown é formatado de forma consistente. Isto pode trazer os seguintes benefícios:

- Não há discussões sobre formatação.
- Excelente integração com editores e IDEs, para que os ficheiros possam ser formatados ao guardar.
- É fácil adicionar verificações de formatação à CI.
- É fácil formatar ficheiros automaticamente com um script.

Tudo o que foi referido acima ajuda bastante a reduzir o ruído nas revisões, o que é frustrante tanto para quem revê como para quem é revisto.

# Sobre

Nos conceitos anteriores, foi mencionado que a diretiva `global` torna uma função ou variável definida num ficheiro fonte visível a outros ficheiros.
Da mesma forma, a diretiva `extern` informa o assembler de que uma função ou variável usada no ficheiro fonte atual está definida noutro.

Estas duas diretivas são a principal forma de o código assembly interagir com outros ficheiros fonte para conseguir modularização.

Para efeitos destas diretivas, é indiferente se o código externo está definido ou é usado em assembly ou numa linguagem de alto nível.
Assim, por exemplo, até uma função definida numa linguagem de alto nível pode ser usada em código x86-64 se for declarada `extern`.

Da mesma forma, a convenção de chamada é partilhada por todas essas funções, definidas em assembly ou em linguagens de alto nível, e até com o Sistema Operativo (SO).

No entanto, como em assembly os dados são apenas uma sequência de bytes, é importante ter em conta como a linguagem de alto nível com que se faz a interface gere a memória.

## Tipos em C

A linguagem C é uma escolha comum como linguagem de alto nível para interagir com código assembly.
Facilita a tarefa de interagir com o SO, oferecendo camadas de abstração de alto nível para muitas tarefas importantes, como imprimir no ecrã, ler do teclado ou alocar memória dinâmica.

Neste track, os testes estão escritos em C, por isso é importante dar uma visão geral da linguagem.

### Tipos primitivos

Existem muitos tipos primitivos em C e o seu tamanho, em bytes, pode variar.
Alguns deles estão resumidos na tabela seguinte, com o seu tamanho típico num sistema x86-64:

| tipo      | número de bytes | inteiro / vírgula flutuante |
|-----------|-----------------|------------------------|
| _Bool     | 1               | inteiro                |
| char      | 1               | inteiro                |
| short     | 2               | inteiro                |
| int       | 4               | inteiro                |
| long      | 4 ou 8          | inteiro                |
| long long | 8               | inteiro                |
| float     | 4               | vírgula flutuante      |
| double    | 8               | vírgula flutuante      |

Cada um desses tipos inteiros pode ter sinal (o comportamento predefinido) ou não ter sinal.
Caso não tenha sinal, isso tem de ser especificado, por exemplo: `unsigned int`.

Existem aliases para os tipos inteiros, definidos para permitir um controlo preciso sobre o seu tamanho:

| alias   | número de bytes |
|---------|-----------------|
| int8_t  | 1               |
| int16_t | 2               |
| int32_t | 4               |
| int64_t | 8               |

Esses aliases podem ter o prefixo `u` para indicar um tipo sem sinal, por exemplo: `uint64_t`.

Outros aliases de interesse são:

| alias  | tipo                                          |
|--------|-----------------------------------------------|
| bool   | _Bool                                         |
| size_t | normalmente um inteiro sem sinal de 8 bytes   |

Um `_Bool`, ou o seu alias `bool`, é especial porque, apesar de ocupar 1 byte inteiro, só pode assumir um de dois valores: `true` (`1`) e `false` (`0`).

Os valores destes tipos primitivos são passados para as funções e devolvidos por elas de acordo com as regras habituais para inteiros e valores de vírgula flutuante.

### Enums

Um [enum][enum] é um tipo que pode assumir um de vários elementos indicados explicitamente:

```c
enum example {
    example_1,
    example_2,
    example_3,
    example_4
};
```

Em C, os enums são convertidos implicitamente num tipo inteiro, que é tipicamente um `int`, ou seja, um inteiro de 4 bytes.

Por predefinição, o primeiro elemento possível de um enum é convertido em `0` e todos os elementos seguintes são convertidos no inteiro seguinte.
Assim, no `enum example` definido acima, `example_1` teria o valor `0`, `example_2` teria o valor `1` e assim por diante.

É possível indicar o valor de qualquer elemento de um enum e, depois, por predefinição, o elemento seguinte teria como valor o inteiro seguinte:

```c
enum example_2 {
    example_1 = 4,
    example_2 = 8,
    example_3
}; // example_3 is equal to 9
```

### Endereços de memória

Em C, um endereço de memória é referenciado por um [ponteiro][pointer] para um tipo e indicado com o operador `*`.
Assim, por exemplo, `int64_t *` refere-se a uma posição de memória para um ou mais `int64_t`.

Os endereços são tratados como inteiros de 8 bytes, como habitualmente.

### Arrays

Os arrays são passados para as funções, e devolvidos por elas, como ponteiros para o seu primeiro elemento.

```c
int64_t example_arr[] = {1, 2, 3}; // this is an array of 3 signed 8-byte integers
fn(example_arr); // this is a function that passes a pointer (int64_t *) to the beginning of the array as argument
```

Cada elemento de um array tem o tamanho do tipo de elemento do array.
O `example_arr` definido acima, por exemplo, tem 3 elementos de 8 bytes cada, o que dá 24 bytes no total.

Como os arrays não guardam o seu comprimento, normalmente é necessário um valor separado para indicar o número de elementos, a menos que um valor sentinela marque o fim.

### Strings

As strings em C são um array de `char`, que é um tipo de 1 byte.
A maioria das strings é de carateres ASCII e termina com NUL, ou seja, termina quando se encontra um byte com o valor `0`.
Isto significa que o comprimento de uma string normalmente não precisa de ser passado como argumento separado.

## Chamar funções da biblioteca C

A diretiva `extern` apenas declara que um símbolo está definido noutro ficheiro.
A forma como uma chamada a esse símbolo é efetivamente feita depende de como esse código externo é ligado.

Para funções comuns ligadas juntamente com o teu código, o ligador consegue encontrar uma função externa diretamente, por isso basta um simples `call`.

No entanto, as funções da biblioteca padrão de C, como `malloc`, `free` e `printf`, são normalmente resolvidas em tempo de execução a partir de uma biblioteca partilhada, cujo endereço não é conhecido quando o teu código é montado.
A chamada passa, por isso, por um stub numa [Procedure Linkage Table (PLT)][plt], colocada num deslocamento conhecido.
Sempre que chamas uma função de biblioteca externa a partir de assembly, o NASM exige uma indicação de que esta chamada deve ser resolvida a partir da PLT.

Em `elf64` (formato de saída usado pelos programas Linux), essa indicação é feita acrescentando `wrt ..plt` (com referência à plt) depois da chamada.
Por exemplo, `call printf wrt ..plt`.

Em programas `macho64` (formato de saída usado pelos programas macOS), por outro lado, basta um sublinhado antes do nome da função.
Por exemplo, `extern _printf` e depois `call _printf`.
No entanto, como neste track o código `macho64` é montado com a flag `--prefix _`, esse sublinhado é acrescentado automaticamente pelo assembler nas duas situações, por exemplo, `extern printf` e depois `call printf`.

Repara que o test-runner do Exercism é executado numa imagem Linux, por isso qualquer solução submetida que chame funções da biblioteca C tem de usar `wrt ..plt`.
É possível usar uma guarda em tempo de montagem para escolher corretamente entre formatos de saída:

```x86asm
extern malloc

%ifidn __OUTPUT_FORMAT__,elf64
    call malloc wrt ..plt       ; elf64: reach the function through the PLT
%else
    call malloc                 ; macho64: the linker generates the call stub
                                ; the underscore is added automatically by an assembler flag
%endif
```

## Chamadas de sistema

Há muitas operações que os programas ao nível do utilizador, como os que são executados neste track, não conseguem realizar diretamente.
Ler de `stdin`, escrever em `stdout`, pedir memória dinâmica, interagir com periféricos, etc., são tudo operações tratadas pelo Sistema Operativo (SO).

Um programa ao nível do utilizador tem de pedir explicitamente ao SO para realizar essas operações, quando necessário.
Isto faz-se com a instrução [`syscall`][syscall].
Concetualmente, esta instrução pode ser vista como uma chamada a um procedimento predefinido do SO (uma chamada de "sistema").

Qualquer argumento da chamada de sistema deve ser passado ao SO em GPRs: `rdi`, `rsi`, `rdx`, `r10`, `r8` e `r9`.

Repara que a sequência é quase igual à usada numa chamada de função, mas `rcx` é substituído por `r10`.
Isto acontece porque `rcx` e `r11` são usados pelo `syscall` para guardar o endereço de retorno e as flags (que são restauradas antes de devolver o controlo à função que fez a chamada).
Ambos os registos têm de ser tratados como alterados em cada `syscall`.

Ao contrário de `call`, não existem etiquetas que indiquem as "funções" do sistema.
Em vez disso, chega-se a elas através de números específicos colocados em `rax` antes da chamada.
Qualquer valor devolvido, se existir, é também colocado em `rax`.

As convenções acima estão descritas [num apêndice da System V ABI][linux-convention] que abrange especificamente o Linux e está marcado como meramente informativo.
Na prática, as chamadas de sistema disponíveis, o seu número e a forma como os erros são comunicados são detalhes ao nível do SO que variam muito entre SOs e até entre versões diferentes do mesmo SO.

Muitas funções da biblioteca C, e outras funções reais definidas pelo SO, são camadas de abstração de nível mais alto sobre uma chamada de sistema.
A ABI recomenda que se prefira estas camadas a um `syscall` simples, e a Apple [não garante compatibilidade][mac-qa1118] na interface de chamadas de sistema do kernel.

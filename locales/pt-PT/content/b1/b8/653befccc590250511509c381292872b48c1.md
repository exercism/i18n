# Introdução

Uma função é **recursiva** quando chama a si própria.

Uma diferença fundamental entre uma chamada de função e um ciclo é que chamar uma função coloca o endereço de retorno na pilha.
Isto significa que uma função recursiva costuma exigir mais espaço de pilha do que um ciclo equivalente.

Por conseguinte, uma função que não pare de se chamar a si própria pode acabar por esgotar todo o espaço de pilha.
É a isto que se chama **stack overflow**.

É por isso que todas as funções recursivas têm de ter pelo menos um caso base, ou seja, uma situação em que a função devolve um valor sem se chamar a si própria.
Qualquer chamada recursiva tem de chegar, mais tarde ou mais cedo, a um caso base.

Por exemplo, a função fatorial `n! = n * (n - 1) * ... * 1` pode ser definida recursivamente com `1` como caso base:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Repara que a `factorial` tem de fazer `push rdi` antes de se chamar recursivamente e `pop rdi` depois.
Isto acontece porque ainda precisa de `n` depois de a chamada recursiva regressar, para calcular `n * (n-1)!`.

Repara também que usar um registo preservado pela função chamada não resolveria este problema.

Apesar de uma função recursiva poder chamar-se a si própria, ela é, ela própria, a função chamada por outra qualquer.
Isso significa que a função também tem de guardar os registos preservados pela função chamada antes de os usar, e repor o seu valor depois de os usar.
Isto costuma fazer-se com uma sequência de `push`/`pop`, como já vimos num conceito anterior.

Como cada frame de uma função recursiva, com exceção do caso base, é também uma função que chama outra e que precisa de preservar as suas próprias variáveis locais, esta sequência de `push`/`pop` tem de se repetir em cada frame.
Mesmo guardar a variável diretamente na pilha, sem usar registos, continuaria a custar os mesmos `8` bytes por frame.

Isto significa que cada chamada recursiva acrescenta `8` bytes à pilha para o endereço de retorno que o `call` coloca lá, mais `8` bytes por cada variável local que precise de guardar.
A função vai continuar a acrescentar esses bytes à pilha em cada frame até chegar ao caso base.
Só nessa altura começa a desenrolar-se em ordem inversa, com cada chamada recursiva a usar tantos `pop` quantos forem necessários e, por fim, um `ret`.

Por exemplo, se a `factorial` fosse chamada com o argumento `10`, chamar-se-ia a si própria nove vezes antes de chegar ao caso base de `1`.
Nessa altura, já teriam sido usados `144` bytes para guardar o `n` (`8` bytes) e o endereço de retorno (`8` bytes) de cada frame anterior.

## Chamada de cauda

Há situações em que uma função não faz mais trabalho nenhum depois de chamar outra e antes de regressar.

Considera, por exemplo:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

A função `triple_of_square`:

- multiplica o argumento recebido (em `rdi`) por si próprio, para obter o seu quadrado;
- depois chama a `times_three`, que devolve três vezes o argumento recebido.

Assim, a `triple_of_square` devolve `3*x²`, em que `x` é o seu argumento, passado em `rdi`.

Repara que a `triple_of_square` não faz trabalho nenhum depois de chamar a `times_three`: a função simplesmente regressa.
Numa situação como esta, em vez de usar `call`, uma função pode usar `jmp` e transferir a execução para a função chamada:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

É a isto que se chama uma **chamada de cauda**.

A principal vantagem de uma chamada de cauda é evitar o custo extra do `call`.
Um `call` coloca um endereço de retorno na pilha e, para que o controlo volte a esse ponto, tem de haver um `ret` correspondente.

Uma chamada de cauda dispensa as duas coisas: não há endereço de retorno para colocar na pilha nem `ret` extra com que fazer par, apenas o `ret` da própria função chamada.

## Recursão de cauda

Uma chamada de cauda é especialmente útil em funções recursivas que podem chamar-se a si próprias muitas vezes antes de regressar.

No entanto, nem todas as chamadas recursivas podem ser convertidas diretamente numa chamada de cauda.
Como o `jmp` transfere o controlo para a função chamada, quem chama não pode fazer mais trabalho nenhum depois da chamada de cauda.

Por exemplo, a função `factorial` que vimos antes **não** usa recursão de cauda.
Depois da chamada recursiva, ainda precisa de multiplicar o resultado pelo `n` atual, com `imul rax, rdi`.

Em situações como esta, às vezes é possível usar um acumulador que recolhe os cálculos parciais e é devolvido no fim.
Por exemplo, podemos definir uma `factorial_helper` que faz a maior parte do trabalho, e depois a `factorial` prepara um acumulador e transfere o controlo para a `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Como não se faz mais trabalho nenhum depois da chamada recursiva, também já não precisamos de guardar o `rdi`.
Não há `call` nem `push rdi`, por isso cada iteração recursiva acrescenta `0` bytes à pilha: não se usa espaço de pilha adicional.
Esta versão consegue lidar com um `n` arbitrariamente grande sem esgotar a pilha.
É ao mesmo tempo mais eficiente e mais segura.

Em alguns casos, com uma alteração da ordem das funções, é possível evitar até o `jmp` para a função auxiliar.
Por exemplo, a `factorial` e a `triple_of_square` podem ser reescritas desta forma:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

No excerto acima, a execução da `factorial` cai diretamente na `factorial_helper`.
O mesmo acontece com a `triple_of_square` e a `times_three`.
Nos dois casos, a execução continua sequencialmente e parece que a função de cauda é apenas uma etiqueta local dentro da função «principal».

Na realidade, não há nenhuma diferença essencial entre uma etiqueta local e uma função.
O assembly x86-64 não dá tratamento especial a nenhuma delas: são apenas endereços numa secção com código executável, como `section .text`.

Assim, uma função recursiva de cauda pode ser vista como essencialmente o mesmo que um ciclo, em que a chamada recursiva salta de volta para o início e o caso base é a condição que termina o ciclo.

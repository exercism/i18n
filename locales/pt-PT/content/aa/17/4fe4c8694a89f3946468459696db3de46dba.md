# Sobre

## Adicionar contexto aos erros

Explorámos o tratamento básico de erros em Go no [conceito de erros][concept-errors].
Como aprendeste aí, por defeito os erros não transportam stack traces.
Por isso, é fundamental garantir que o próprio erro contém informação suficiente para identificar o problema.

Se quiséssemos acrescentar informação a um erro já existente com as ferramentas que já conhecemos, podíamos escrever algo assim para criar um novo erro com o texto combinado do erro original e da informação adicional:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Felizmente, o pacote `fmt` da biblioteca padrão contém uma versão abreviada disto na forma da função `Errorf`.
Isso permite-te, por exemplo, acrescentar facilmente informação sobre o contexto em que o erro ocorreu.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

A menos que tenhas a certeza de que o erro já inclui informação suficiente, deves tentar criar o hábito de acrescentar sempre contexto a um erro antes de o devolveres de uma função.
Isso significa que o teu padrão habitual de tratamento de erros deve ser assim:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Como mostram os exemplos, a convenção é separar o erro da mensagem acrescentada com dois pontos.
Tal como a mensagem do erro original, também a mensagem de contexto não deve começar com maiúscula, nem deve levar um ponto final no fim.

~~~~exercism/note
Quando acrescentas contexto a um erro, é tentador começar a mensagem com "falha ao ..." ou algo semelhante.
No entanto, como um erro pode acumular muito contexto adicional à medida que sobe pela cadeia de funções, isso pode tornar a mensagem final, que será registada ou que o utilizador verá, mais difícil de ler e cheia de repetições.

Eis um exemplo para ilustrar:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Por isso, tem em conta este resultado final ao escreveres as mensagens de contexto e evita acrescentar texto sobre o facto de algo não ter corrido como esperado.
Isto costuma ser claro a partir do contexto (por exemplo, o nível de registo "ERROR") e da mensagem do erro original.
~~~~

Muitas vezes, esta forma de acrescentar informação a um erro é suficientemente boa, mas há casos em que queres permitir que quem consome o teu erro verifique ou obtenha o erro original subjacente.
Acrescentar contexto de forma que isto seja possível chama-se "encapsular um erro" em Go.

## Encapsular erros e verificar erros sentinela

O encapsulamento de erros consegue-se com uma alteração mínima ao código que vimos acima.
Para encapsular um erro, tens de usar o verbo de formatação `%w` em vez de `%v`.
Nos bastidores, isto garante que o erro resultante implementa um método `Unwrap` que devolve o erro original.
Por causa disso, o `errors.Is` pode ser usado para verificar se um determinado erro sentinela aparece em algum ponto da "cadeia de erros".
Fá-lo chamando secretamente `Unwrap` repetidamente até o erro em questão ser encontrado ou a cadeia terminar.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Verificar o erro original com `errors.Is` não funcionaria com o verbo de formatação normal `%v`.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Como resultado, é boa prática usar `%v` por defeito e só usar `%w` se quiseres explicitamente permitir que quem consome o teu erro aceda a um erro subjacente ([Google Go Styleguide][google-go-styleguide]).

Se te encontrares numa situação em que queres verificar um erro sentinela mas explicitamente não queres desencapsular, podes usar `==` em vez de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Em contrapartida, o `==` não identificaria o erro se este estivesse encapsulado.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Não há problema em trabalhar com `errors.Is` por defeito, mas deves ter sempre em conta que isso significa que toda a cadeia de erros será percorrida.

## Verificar tipos de erro (personalizados)

Há um equivalente ao `errors.Is` que permite verificar e obter um erro de um tipo específico a partir da cadeia de erros.
A função para isso é `errors.As` e, tal como `errors.Is`, procura o tipo de erro indicado ao longo de toda a cadeia.
O `errors.As` só extrai o erro que encontrou que corresponde ao tipo, para que possas trabalhar mais com ele, por exemplo, obter campos específicos.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Tem cuidado com a sintaxe relativa aos ponteiros acima.
O código só funcionará e compilará corretamente se o `customError` tiver exatamente o tipo que implementa a interface de erro.
No nosso caso, esse tipo é `*MyCustomError` (um [ponteiro][concept-pointers] para `MyCustomError`), e não o próprio `MyCustomError`.

Além disso, o segundo argumento tem de ser um ponteiro para a variável do erro.
Como o nosso erro já é um ponteiro, o que estamos a passar ao `errors.As` é um ponteiro para um ponteiro (para MyCustomError).
Só com isto configurado corretamente é que o Go consegue preencher a variável com o erro que encontrou.
~~~~

Tal como antes, o `errors.As` não teria encontrado o tipo de erro se se tivesse usado `%v` ao chamar `Errorf`.

Se, por alguma razão, não quiseres desencapsular, podes usar antes uma asserção de tipo (equivalente ao `==` acima).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

A asserção de tipo não conseguirá identificar o tipo de erro se o erro tiver sido encapsulado.

## Permitir que erros de tipos personalizados sejam desencapsulados

Por vezes, encapsular um erro apenas com algum texto adicional não é suficiente.
Podes, em vez disso, criar um tipo de erro personalizado que contém o erro original e os dados estruturados adicionais que queres acrescentar.
Se quiseres permitir o desencapsulamento do teu tipo de erro, a única coisa que tens de fazer é acrescentar manualmente um método `Unwrap() error` para satisfazer a interface `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Combinar vários erros

No Go 1.20, foi acrescentada uma nova função `Join` ao pacote `errors` integrado.
O `Join` permite combinar vários erros de uma forma que continua a permitir o desencapsulamento, ou seja, verificar um erro específico ou um tipo de erro ao longo da cadeia.
Com isto, a cadeia de erros pode, na realidade, ser uma árvore de erros.
Podes encontrar mais informação nas [notas de lançamento][release-notes] e na [documentação][doc-join].

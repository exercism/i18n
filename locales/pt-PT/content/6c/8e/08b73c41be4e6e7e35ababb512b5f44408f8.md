# Sobre

Uma função é [recursiva][recursion] quando se chama a si própria.

Uma diferença fundamental entre uma chamada de função e um ciclo é que chamar uma função empilha na pilha o endereço de retorno. Isto significa que uma função recursiva costuma exigir mais espaço na pilha do que um ciclo equivalente.

Como consequência, uma função que continua a chamar-se a si própria pode acabar por esgotar todo o espaço da pilha. A isto chama-se um [stack overflow][stack-overflow].

É por isso que todas as funções recursivas têm de ter pelo menos um caso base, ou seja, uma situação em que a função devolve sem se chamar a si própria. Qualquer chamada recursiva tem de acabar por chegar a um caso base.

Por exemplo, a função fatorial `n! = n * (n - 1) * ... * 1` pode ser definida de forma recursiva com `1` como caso base:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Repara que `factorial` tem de fazer `push rdi` antes de se chamar recursivamente e `pop rdi` depois. Isto acontece porque ainda precisa de `n` quando a chamada recursiva devolve, para calcular `n * (n-1)!`.

Repara também que usar um registo preservado pela função chamada não resolveria este problema.

Mesmo que uma função recursiva seja um potencial chamador de si própria, é também ela própria a função chamada por outra. Isso significa que a função também tem de guardar os registos preservados pela função chamada antes de os usar, e restaurar o seu valor depois de os usar. Isto costuma ser feito com uma sequência de `push`/`pop`, como vimos num conceito anterior.

Como cada frame de uma função recursiva, à exceção do caso base, é também um chamador que tem de preservar as suas próprias variáveis locais, esta sequência de `push`/`pop` tem de ser repetida em cada frame. Mesmo guardar a variável diretamente na pilha, sem usar registos, continuaria a custar os mesmos `8` bytes por frame.

Isto significa que cada chamada recursiva acrescenta `8` bytes à pilha para o endereço de retorno empilhado pelo `call`, mais `8` bytes por cada variável local que precisa de guardar. A função vai continuar a acrescentar esses bytes à pilha a cada frame até atingir o caso base. Só então começa a desenrolar-se em ordem inversa, com cada chamada recursiva a usar tantos `pop` quantos forem necessários e, por fim, um `ret`.

Por exemplo, se `factorial` fosse chamada com o argumento `10`, chamar-se-ia a si própria nove vezes antes de chegar ao caso base de `1`. Nesse momento, teriam sido usados `144` bytes para guardar o `n` (`8` bytes) e o endereço de retorno (`8` bytes) de cada frame anterior.

## Chamada de cauda

Em algumas situações, uma função não realiza mais nenhum trabalho depois de chamar outra e antes de devolver.

Considera, por exemplo:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

A função `triple_of_square`:

- multiplica o argumento recebido (em `rdi`) por si próprio, obtendo o seu quadrado;
- de seguida chama `times_three`, que devolve o argumento recebido multiplicado por três.

Como resultado, `triple_of_square` devolve `3*x²`, em que `x` é o seu argumento, passado em `rdi`.

Repara que não é feito mais nenhum trabalho em `triple_of_square` depois de chamar `times_three`: a função simplesmente devolve. Numa situação como esta, em vez de usar `call`, uma função pode usar `jmp` e transferir a execução para a função chamada:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

A isto chama-se uma [chamada de cauda][tail].

A principal vantagem de uma chamada de cauda é evitar o custo extra do `call`. Um `call` empilha um endereço de retorno na pilha e, para o controlo voltar a esse ponto, tem de haver um `ret` correspondente.

Uma chamada de cauda evita ambos: não há endereço de retorno para empilhar nem `ret` extra com que fazer par, apenas o `ret` da própria função chamada.

## Recursão de cauda

Uma chamada de cauda é particularmente útil para funções recursivas que podem chamar-se a si próprias muitas vezes antes de devolver.

No entanto, nem todas as chamadas recursivas podem ser convertidas diretamente numa chamada de cauda. Como um `jmp` transfere o controlo para a função chamada, o chamador não pode realizar mais nenhum trabalho depois da chamada de cauda.

Por exemplo, a função `factorial` anterior **não** é recursiva de cauda. Depois da chamada recursiva, ainda precisa de multiplicar o resultado pelo `n` atual, usando `imul rax, rdi`.

Em situações como esta, é por vezes possível usar um acumulador que vai reunindo os cálculos parciais e é devolvido no fim. Por exemplo, podemos definir um `factorial_helper` que faz a maior parte do trabalho e, depois, a `factorial` prepara um acumulador e transfere o controlo para o `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Como não é feito mais nenhum trabalho depois da chamada recursiva, também já não precisamos de guardar o `rdi`. Não há nenhum `call` nem `push rdi`, pelo que cada iteração recursiva acrescenta `0` bytes à pilha: não é usado espaço adicional na pilha. Esta versão consegue lidar com valores de `n` arbitrariamente grandes sem transbordar a pilha. É ao mesmo tempo mais eficiente e mais segura.

Em alguns casos, manipulando a ordem das funções, é possível evitar até o `jmp` para a função auxiliar. Por exemplo, `factorial` e `triple_of_square` podem ser reescritas desta forma:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

No excerto acima, a execução de `factorial` passa diretamente para `factorial_helper`. O mesmo acontece com `triple_of_square` e `times_three`. Em ambos os casos, a execução continua de forma sequencial e parece que a função de cauda é apenas uma etiqueta local dentro da função «principal».

Na realidade, não existe nenhuma diferença essencial entre uma etiqueta local qualquer e uma função. O assembly x86-64 não dá nenhum tratamento especial a nenhuma delas: são apenas endereços numa secção com código executável, como `section .text`.

Desta forma, uma função recursiva de cauda pode ser encarada como essencialmente o mesmo que um ciclo, em que a chamada recursiva salta de volta para o início e o caso base é a condição que termina o ciclo.

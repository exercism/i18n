# Introdução

Até agora, o plano de estudos não disse muito sobre tipos, mas é evidente que eles existem em Julia:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

Nunca especificámos os tipos, mas Julia atribuiu-os na mesma.

1. Julia tem `types`, que são centrais para o seu design.
2. Julia consegue normalmente "adivinhar" o tipo, recorrendo à `Type Inference`.

O compilador JIT percorre (todo) o código, vê como uma variável é usada e _infere_ um tipo predefinido adequado, compatível com essa utilização.

## Promoção de tipos

Tem havido muitos exemplos em conceitos anteriores que forçam os tipos numéricos a uniformizar-se, começando pela aritmética mais simples.

```julia-repl
julia> 2 + 1.3
3.3
```

Somámos um número inteiro (Int64) e um número de vírgula flutuante (Float64) e obtivemos um resultado Float64.
Do mesmo modo:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

No caso acima, um tuplo preservou o tipo de cada elemento, mas a conversão para um vetor alterou-os todos para um Float64 uniforme.

O compilador de Julia sabe que conversões de tipos são possíveis: de inteiro para vírgula flutuante não há problema, de vírgula flutuante para inteiro perde-se precisão, por isso é lançado um `InexactError`.
A promoção de tipos converte todos os valores da expressão num tipo comum, suficientemente versátil para ser compatível com todos os valores de entrada.

## Atribuição de tipo

Confiar na inferência de tipos serve bem para resolver exercícios simples de tutorial, mas em programas maiores é provável que precises de um controlo mais preciso.

Na maioria dos processadores modernos, um inteiro assume por predefinição o tipo `Int64`.
Vimos no Conceito [`Numbers`][numbers] que um valor pode ser convertido num tipo específico diferente do predefinido.

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

No entanto, a variável `x` pode continuar a ser reatribuída a um tipo diferente:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

Isto é `type instability`, que é:

- Muito conveniente em scripts pequenos.
- Má para o desempenho e a fiabilidade em programas maiores.

Em vez disso, podemos definir o tipo de `x` com o operador `::`:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

Agora, `y` é do tipo `Int16` e será sempre.
Assim, o compilador sabe quantos bytes reservar e pode otimizar o resto do código para contar com um tipo estável.
Nisto, a variável é mais ou menos semelhante às de uma linguagem de tipos estáticos como C.

## Asserção de tipo

A atribuição de tipo, descrita acima, usa-se no lado esquerdo de uma atribuição de variável para restringir o tipo dessa variável.

Usar o operador `::` com um valor, ou com algo que é avaliado como um valor, é geralmente uma _asserção_ de que o valor tem de ser desse tipo; caso contrário, deve ser lançado um erro.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Habitualmente, isto pode usar-se com o valor devolvido de uma função, como uma última verificação simples de que a função se comportou como esperado.

## A hierarquia de tipos

`Int64`, `Int16`, `String`, `Char`: de onde _"vêm"_ estes tipos.

Em muitas linguagens orientadas a objetos (OO), cada tipo é uma classe, a criação de subclasses organiza-as numa hierarquia de classes e os métodos de classe definem os comportamentos.

Java e Ruby são exemplos óbvios deste padrão, mas até o Python é semelhante a nível interno.

***Julia não tem classes.***

A razão documentada é que as características de OO interferem com o compilador JIT e prejudicam o desempenho em tempo de execução.

E, no entanto, repara neste código:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

Preenchendo alguns detalhes:

- `Int16` é um tipo, e podemos criar variáveis deste tipo.
- `Int16` é um subtipo de `Signed`, e a função `supertype()` mostra-nos isso.
- Existe uma hierarquia de tipos, que sobe através de `Integer`, `Real` e `Number` até `Any`, no topo, e a função `subtypes()` lista para nós este ramo da hierarquia.

Todos os ramos terminam em `Any`, que é o único que é o seu próprio supertipo.

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

Portanto, Julia não tem uma hierarquia de `class`, mas _tem_ uma hierarquia de `type`.

Mais adiante vamos tentar desvendar como isto funciona, mas há muito mais para explorar primeiro.

## Testar os tipos

Podemos usar `typeof()` para testar a igualdade da forma habitual.

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

A igualdade de tipos tem de ser exata, pois esta forma de comparação não tem em conta a hierarquia de tipos.

De forma mais flexível, `isa` diz-nos se um valor tem o mesmo tipo que um comparador, ou um subtipo desse tipo.
Pode ser usado tanto na forma de função como na forma infixa.

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

Repara que `isa` espera um `value` à esquerda, não um `type`.

Tentar comparar dois _tipos_ desta forma dá resultados inesperados.
O operador correto é `<:`, que veremos muito mais vezes em conceitos futuros.

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## Tipos abstratos versus tipos concretos

Vimos que a hierarquia de tipos forma uma estrutura de árvore (no sentido da informática, com a raiz no topo).

Cada item da árvore é um `node`, e estes podem dividir-se em categorias:

1. Os nós com subtipos chamam-se `abstract`.
2. Os nós folha, sem subtipos, chamam-se `concrete`.

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

Esta distinção é importante, porque só os tipos concretos podem ser `instantiated` como variáveis.


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

Repara que tentar usar um tipo abstrato não dá mensagem de erro (neste caso), mas o compilador cria um tipo concreto adequado: `Int64` em vez de `Integer`.
Pelo menos, impede que a variável receba um valor não inteiro:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

A atribuição de tipo com um tipo abstrato é, assim, uma _restrição_ ao tipo da variável, a qualquer subtipo de (no caso acima) `Integer`.
Isto é algo invulgar no mundo das linguagens de programação: mais fraco do que uma atribuição de tipo em C e mais forte do que uma dica de tipo nas versões recentes do Python.

As funções `isabstracttype()` e `isconcretetype()` permitem fazer testes.
Nota que não são apenas a negação uma da outra: veremos num Conceito mais adiante que alguns tipos não são nem abstratos nem concretos.


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

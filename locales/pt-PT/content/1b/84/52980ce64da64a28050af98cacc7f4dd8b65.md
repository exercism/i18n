# Sobre

A [pilha de chamadas][stack], ou apenas **pilha**, é uma estrutura de dados especial que começa no ponto mais alto da memória e cresce para baixo.

## Empilhar e desempilhar

A pilha suporta pelo menos duas operações, com instruções com o mesmo nome:

| Instrução | Operação realizada                                 |
| ----------- | --------------------------------------------------- |
| `push`      | adiciona um elemento à pilha                        |
| `pop`       | remove e devolve o elemento adicionado mais recentemente |

Isto significa que a pilha é uma estrutura de dados **último a entrar, primeiro a sair (LIFO)**.

Para acompanhar o ponto atual da pilha, onde se encontra o elemento mais recente, usa-se o registo `rsp`.

Assim, uma instrução [push][push] recebe um operando e armazena o conteúdo desse operando na pilha.
À medida que a pilha cresce para baixo, o valor em `rsp` é reduzido pelo tamanho do valor armazenado.

Da mesma forma, uma instrução [pop][pop] recebe um operando e armazena nele o valor mais recente da pilha (aquele para o qual `rsp` aponta).
O valor em `rsp` é então aumentado pelo tamanho do valor obtido.

## Variáveis locais

Também é possível manipular diretamente o valor de `rsp`.
Isto é frequentemente usado para criar variáveis locais para uma função.

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

Repara que, no momento em que o espaço é reservado na pilha, o valor armazenado nesse espaço é _indefinido_.

~~~~exercism/note
Nem `pop` nem a manipulação direta de `rsp` removem realmente o conteúdo armazenado na memória.
A "remoção" da pilha é abstraída a partir do novo endereço em `rsp`.

Em alguns contextos, isto pode causar preocupações de segurança ao expor valores internos a fontes externas.
Uma forma de lidar com isto é anular o conteúdo de qualquer espaço da pilha usado pela função.
~~~~

## Chamada e retorno

O principal objetivo da pilha é acompanhar o endereço de retorno das funções chamadas.

Como foi mencionado num conceito anterior, existe um registo especial chamado `rip` que aponta para a próxima instrução a executar.
Este registo é usado para controlar o fluxo de um programa, sendo modificado por instruções como `jmp` e `call`.

Sempre que uma instrução `call` é usada, o valor atual em `rip` é implicitamente empilhado na pilha.
De seguida, o operando da instrução é movido para `rip`, para que a execução continue na função chamada.

Uma instrução `ret` faz a operação oposta.
Desempilha da pilha para `rip`, para que a execução regresse à função chamadora.

No ponto de entrada, `rsp` aponta para o endereço a devolver.
Este é o endereço que `ret` tem de desempilhar da pilha.

Assim, qualquer alteração ao valor de `rsp` dentro de uma função, quer diretamente quer com `push`, tem de ser revertida antes de a função terminar.

## Registos preservados pela função chamada e pela função chamadora

Além de `rsp`, há outros registos que têm de ser preservados ao longo das chamadas de funções: `rbp`, `rbx`, `r12`, `r13`, `r14` e `r15`.
Em geral, a função chamadora espera poder usar esses registos sem que sejam alterados por uma função chamada.

Isto significa que a função _chamada_ tem de guardar os valores nesses registos antes de os usar e restaurá-los aos valores originais antes de terminar.
É por isso que são chamados **registos preservados pela função chamada**.

Os outros registos de uso geral estão diretamente disponíveis para utilização pela função chamada.

Isto significa que a função _chamadora_ tem de guardar os valores nesses registos antes de chamar qualquer função, caso sejam modificados pela função chamada.
É por isso que são chamados **registos preservados pela função chamadora**.

_A forma mais comum de guardar o conteúdo de um registo é armazená-lo na pilha._

## Prólogo e epílogo

Em alguns casos, a pilha pode ser muito utilizada, com muitas modificações antes de a função terminar.
Assim, acompanhar todas essas alterações para as reverter pode ser complexo.

Nesses casos, uma estratégia comum é guardar o endereço de `rsp` noutro registo que, de resto, permaneça inalterado dentro da função.
E depois, o valor de `rsp` pode ser restaurado com uma simples instrução `mov` no final, antes de a função terminar.

Embora qualquer registo possa ser usado para este efeito, é convencional usar `rbp` como ponteiro de base.
Como `rbp` é ele próprio um registo preservado pela função chamada, isto é frequentemente precedido por um `push rbp`.
Esta sequência é normalmente chamada **prólogo**.

No final, a restauração de `rsp` é feita com um `mov rsp, rbp` e depois `rbp` também é restaurado com um `pop` da pilha.
Esta sequência é normalmente chamada **epílogo**.

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

~~~~exercism/note
O principal objetivo das sequências de prólogo/epílogo é ajudar o programador a acompanhar as alterações a `rsp`.
Isto é, naturalmente, muito mais fácil de fazer para um compilador.

É por isso que muitos compiladores emitem uma otimização para omitir o ponteiro de frame e remover prólogos/epílogos sempre que possível.
~~~~

## Passagem de argumentos com a pilha

Na convenção de chamada [System V ABI][SystemV], os argumentos são normalmente passados às funções em registos.
No entanto, quando há demasiados argumentos, ou quando precisam de mais do que o tamanho de um registo, pode usar-se a pilha.

Nesses casos, os valores são adicionados à pilha por ordem inversa, para que o primeiro argumento fique mais próximo de `rsp`.
Como, no ponto de entrada, `rsp` aponta para o endereço de retorno, que é um valor de 8 bytes em x86-64, o primeiro argumento na pilha, se existir, pode ser acedido em `rsp + 8`:

```x86asm
mov rdi, 4   ; first argument
mov rsi, 8   ; second argument
mov rdx, 15  ; third argument
mov rcx, 16  ; fourth argument
mov r8, 23   ; fifth argument
mov r9, 42   ; sixth argument

; any remaining integer argument goes on the stack in reversed order
sub rsp, 16
mov qword [rsp], 100      ; seventh argument
mov qword [rsp + 8], 300  ; eighth argument

call many_arguments_fn ; call implicitly pushes `rip` to the stack
; so, at point of entry, 'many_arguments_fn' finds the first six integer arguments in the usual registers
; the seventh argument is found in rsp + 8
; and the eighth argument is found in rsp + 16
```

## Alinhamento da pilha

A System V ABI estabelece que a pilha tem de estar alinhada a 16 bytes imediatamente _antes_ de a instrução `call` ser executada.
Como `call` empilha `rip` na pilha, no ponto de entrada a pilha da função chamada **não** está alinhada a 16 bytes.

Isto significa que uma função que chama outra (e, em especial, funções externas) tem de alinhar a pilha antes de usar `call`.

Isto pode ser feito subtraindo um valor adequado a `rsp`.
No ponto de entrada, este valor tem de ser 8 a mais do que um múltiplo de 16: 8, 24, 40, etc.
Como uma instrução `push` subtrai a `rsp`, pode usar-se um número ímpar de `push` para o mesmo efeito:

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

## Zona vermelha

A System V ABI reserva um espaço de 128 bytes imediatamente abaixo de `rsp` que pode ser usado sem qualquer ajuste de `rsp`.
Este espaço é conhecido como [zona vermelha][red-zone]:

```x86asm
fn:
    mov [rsp - 8], rax ; this is safe to use because it is in the red zone
    ret                ; no need to restore rsp
```

A zona vermelha só é segura para utilização por uma função folha, ou seja, uma que não chama outra.

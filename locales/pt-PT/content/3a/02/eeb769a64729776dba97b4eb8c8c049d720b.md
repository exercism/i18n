# Sobre

Nas aplicações em C#, a aleatoriedade é geralmente implementada com a classe `System.Random`.

Este [artigo][system-random] é uma excelente introdução ao tema.

Quando começas a familiarizar-te com uma classe de biblioteca, vale sempre a pena estudar a [documentação][system-random] das propriedades, dos métodos e das respetivas sobrecargas.

O exercício de programação destacou várias questões:

- O gerador de números aleatórios não precisa de uma [semente][random-seedless].
- `Random.Next()` pode gerar um intervalo de números inteiros
- `Random.Double()` pode gerar um número de vírgula flutuante entre 0 e 1
- Os limites superiores em `Next...()`, `Double()` e `Sample()` são **exclusivos**, pelo que `Random.Next(1,19)` devolve valores de 1 a 18, mas não 19.
- Depois de teres o teu número aleatório, podes fazer com ele o que quiseres

Há três padrões para implementar o último ponto:

- Podes obter o número aleatório e manipulá-lo. No caso do exercício de programação, isso consiste em chamar `Random.NextDouble()` e multiplicar por 100. Este [texto][random-use-case-array] explica como fazer seleções aleatórias a partir de um array.
- Podes herdar de `System.Random` e substituir o método `Sample()`.
- Podes encapsular uma instância de `System.Random` como membro de uma classe tua, por exemplo [para gerar Boolean][random-use-cases].

Os números gerados pelo `Random` não são garantidamente únicos.

É [recomendado][random-thread-safety] que instancies `System.Random` como membro estático. Mas repara que não é seguro em termos de threads.

Podes encontrar documentação que desaconselha o uso de construtores sem semente. Isto aplica-se sobretudo ao .NET Framework e não ao .NET Core (que é o que o _Exercism_ usa). Para a história completa, lê [isto][random-multiple-instantiations].

Recomenda-se que não uses `System.Random` para criptografia ou segurança. Vê este [fornecedor][crypto-provider] e este [gerador de números][crypto-rng].

## Segurança de threads

No contexto das APIs de bibliotecas, «não é seguro em termos de threads» é apenas uma forma abreviada de dizer que, se provavelmente vais aceder a instâncias da classe através de várias [threads][threading] em simultâneo, deves criar os teus próprios mecanismos de sincronização de threads ou, no caso das coleções, considerar a possibilidade de usar uma versão concorrente da classe. Sem estas precauções, é provável que ocorram [condições de corrida][so-race-conditions]. Se a tua base de código não usa várias threads, e é pouco provável que venha a usar, este aviso não te deve preocupar.

# Contribuir para o percurso de Rust do Exercism

As issues e os pull requests estão, neste momento, a ser fechados automaticamente.
Faz uma publicação no [fórum do Exercism][the Exercism forum] para propores alterações.
As contribuições são muito bem-vindas, desde que sejam coordenadas no fórum.

[the Exercism forum]: https://forum.exercism.org/

## Políticas gerais

- [Código de Conduta](https://exercism.org/code-of-conduct)
- [Diretrizes de PR do Exercism](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## Ferramentas

Algumas ferramentas estão disponíveis como scripts bash em `bin/`.
Há muito mais em `rust-tooling/`,
que deves preferir para tudo o que não seja trivial.

Existe também uma configuração do [`mise`](https://mise.jdx.dev/)
com alguns comandos úteis para interagir com o repositório.
Podes estendê-la à vontade.

Se quiseres correr testes de CI localmente, `mise run test` leva-te bastante longe.

## Excluir testes e acrescentar testes personalizados

Ao criar ou atualizar um exercício, podes decidir excluir alguns testes da geração.
Podes fazê-lo definindo `include = false` em `.meta/tests.toml`.
Inclui um comentário a explicar a razão dessa exclusão.

Se quiseres acrescentar testes adicionais específicos do percurso, podes fazê-lo num ficheiro `.meta/additional-tests.json`.
Só deves fazer isto se tiveres um bom motivo para não enviar estes testes para o projeto principal.
Um comentário no teste adicional deve responder a estas perguntas:
- Porque é que o teste não é enviado para o `problem-specifications`, ou seja, porque é que não tem valor geral para outras linguagens?
- Porque é que o teste tem valor para o percurso de Rust, mesmo assim?

## Criar um novo exercício

Familiariza-te com a [documentação do Exercism sobre exercícios de prática][Exercism documentation about practice exercises].

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

Corre `mise run add-exercise` e ser-te-á pedida a informação mínima
necessária para gerar o stub do exercício para ti.
Depois disso, entra no exercício gerado e preenche todos os marcadores de posição que encontrares.
Isto inclui, em particular:

- escrever o stub do exercício em `src/lib.rs`
- acrescentar uma solução de exemplo em `.meta/example.rs`
- ajustar o `.meta/test_template.tera`

Os testes são gerados com o motor de templates [Tera].
A entrada do template são os dados canónicos do [`problem-specifications`].

Encontras algumas dicas sobre como escrever templates tera [aqui](#tera-templates).

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

Muitos aspetos de um exercício corretamente implementado são verificados na CI.
Em vez de passares muito tempo a estudar e a escrever
documentação sobre o processo, aconselho-te a _põe mãos à obra_.
Se algo se estragar, corrige-o e acrescenta um teste ou automação
para que não volte a acontecer.

Se estiveres a criar um exercício de prática de raiz,
um que não exista no `problem-specifications`,
tens de escrever os testes manualmente.
Os testes devem estar ordenados por complexidade crescente,
para que os estudantes os possam ativar um a um e resolver o exercício com TDD.
Vê a [documentação do Exercism](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)
para mais ideias sobre como escrever bons testes.

Exceto em circunstâncias extraordinárias,
o ficheiro stub deve compilar com `cargo test --no-run`.
Isto permite-nos verificar que as assinaturas no ficheiro stub
correspondem às assinaturas esperadas pelos testes.
Usa `todo!()` como corpo de cada função para conseguires isto.
Se houver uma razão justificada para que isto não seja possível,
inclui uma chave `.custom."allowed-to-not-compile"`
no `.meta/config.json` do exercício, com a razão.

## Atualizar um exercício

Muitos exercícios são derivados do [`problem-specifications`].
Isto inclui o conjunto de testes e a documentação dirigida aos utilizadores.
Antes de propores alterações aqui,
verifica se não deveriam ser feitas antes no `problem-specifications`.

Corre `mise run update-exercise` para atualizar um exercício.
Isto delega a maior parte do trabalho ao `configlet sync --update`
e volta a correr o gerador de testes.

Quando atualizas um exercício que ainda não tem um template tera,
é gerado um novo para ti.
Muito provavelmente terás de o ajustar um pouco.

Encontras algumas dicas sobre como escrever templates tera [na secção seguinte](#tera-templates).

## Templates Tera

A documentação completa dos templates tera está [aqui][tera-docs].
A seguir estão algumas abordagens que funcionaram para as nossas necessidades específicas.

Provavelmente vais querer ver o `canonical-data.json` do exercício para perceberes como são os teus dados de entrada.
Podes usar `bin/symlink_problem_specifications.sh` para criar uma ligação simbólica destes dados
na pasta do exercício propriamente dita. Muito prático!

O nome da propriedade de entrada é diferente de exercício para exercício.
O template predefinido será algo assim:

```txt
let input = {{ test.input | json_encode() }};
```

Terás de acrescentar o campo de entrada específico deste exercício, por exemplo

```txt
let input = {{ test.input.integers | json_encode() }};
```

Alguns exercícios podem devolver valores de erro.
Podes usar um if-else para gerar algo diferente,
consoante a estrutura dos dados:

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

Alguns exercícios têm várias funções que precisam de ser implementadas
pelo estudante e, por isso, testadas.
Nesse caso, os dados canónicos contêm um campo `property`.
Podes construir cadeias de if-else com base em `test.property` e gerar uma função diferente com base nisso.

Alguns exercícios têm os seus casos de teste organizados em _grupos de teste_.
O teu template terá de ter isso em conta.
Em muitos casos, podes simplesmente aplanar a estrutura. (exemplo: [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
No entanto, às vezes os testes têm a mesma descrição em grupos diferentes, o que dá origem a conflitos de nomes se a estrutura for aplanada.
Nesse caso, podes usar a descrição do grupo para organizar os testes em módulos. (exemplo: [`forth`](/exercises/practice/forth/.meta/test_template.tera))

Há alguns filtros tera personalizados em [`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs).
Aqui está a lista, que se espera estar atualizada:
- `to_hex` formata inteiros em hexadecimal
- `make_ident` transforma uma string arbitrária num identificador Rust decente.
   Muito útil para gerar nomes de funções a partir das descrições dos testes.
- `fmt_num` formata literais numéricos (insere um `_` a cada três algarismos)

Podes acrescentar os teus na crate `rust-tooling`.
Esperemos que te lembres de atualizar também a lista aqui. 🙂

Para um exemplo bastante complicado, vê o template de testes do `triangle`.
Organiza os casos de teste em módulos e deteta dinamicamente que testes devem ficar atrás de feature gates.
Esse exercício também reimplementa alguns casos de teste do projeto principal no `additional-tests.json`, para lhes acrescentar mais informação necessária à geração de bons testes.

[tera-docs]: https://keats.github.io/tera/docs/#templates

## Programa

O programa está atualmente desativado devido à sua baixa qualidade.
Vê [esta publicação no fórum](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)
para perceberes o contexto desta decisão.

Criar um programa melhor seria muito benéfico,
mas dá muito trabalho e exige boa comunicação e coordenação.
Certifica-te de que discutes no fórum quaisquer planos que tenhas
com pessoas que tenham experiência a construir programas.

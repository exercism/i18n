# Sobre

## Tipos compostos

Muitas vezes é útil definir tipos personalizados nos nossos programas.

Criar novos tipos primitivos é possível, mas raramente se faz.
Os [tipos primitivos][primitive] incorporados não são uma escolha arbitrária: correspondem de perto aos tipos padrão do compilador LLVM que a Julia usa para a compilação JIT.

Muito mais útil é a capacidade de definir [tipos compostos][composite-types], com campos com nome.

Outras linguagens têm algo semelhante, chamando-lhes `structs` ou `records`.
A documentação da Julia refere-se a eles como `composite types`, embora (numa ligeira dissonância) a sintaxe da linguagem os defina com a palavra-chave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale a pena notar alguns pontos no exemplo acima:

- Não é especificado nenhum tipo para `id`, por isso o compilador interpreta-o como `id::Any`.
  - **Nota:**: na prática, o melhor é ajudar o compilador especificando o tipo de um campo com um tipo concreto.
  - Veremos num [Conceito futuro][parametric] que usar parâmetros é outra opção.
- O nome do tipo é usado como construtor, como em `Person(id, name, age)`, para criar uma instância do tipo `Person`.
- Podes aceder aos campos individuais com a notação de ponto, tal como nas [tuplas com nome][named-tuple].

Os itens do tipo `Person` são imutáveis, por isso não é possível atualizá-los.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Se for precisa mutabilidade, acrescenta `mutable` à definição.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Por omissão, o construtor exige que os campos apareçam na mesma ordem da definição, o que se torna inconveniente em tipos mais complicados.

Usar a macro `@kwdef` permite duas novas capacidades:

- O construtor usa palavras-chave, não a posição.
- Os campos podem ter valores por omissão e podem, opcionalmente, ser omitidos no construtor.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarquias de tipos compostos

Até agora, só criámos tipos compostos concretos.
Se verificares, todos são subtipos de `Any`.

Quando crias vários tipos relacionados, provavelmente faz mais sentido definir uma hierarquia para eles.
Isso é muito fácil de fazer.

Primeiro, cria um tipo abstrato:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

A seguir, inclui o operador `<:` numa definição de tipo, para mostrar a relação.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Repete conforme for necessário, tendo em conta que não é permitido criar subtipos de tipos concretos.

Para uma hierarquia mais complexa, cria subtipos abstratos conforme for preciso.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

O valor de uma hierarquia destas tornar-se-á mais claro quando chegarmos ao Conceito `Multiple Dispatch` e virmos como as funções lidam com os tipos dos argumentos.


## Construtores internos

Vimos no início deste Conceito que o nome do tipo é usado como construtor, para criar itens desse tipo:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

Aqui, `Person()` é conhecido como um `outer constructor`.
Os tipos dos campos serão verificados quanto à compatibilidade com a definição do tipo, e será lançado um erro se for necessário.

Suponhamos que queremos restrições sobre os _valores_ recebidos, e não apenas sobre os _tipos_.

Nesse caso, podemos incluir um `inner constructor` dentro da definição do tipo, para fazer as verificações adequadas.

Por exemplo, temos um tipo abstrato `AbstractPoint`, pensado para receber coordenadas `(x, y)`, mas queremos um subtipo com a restrição `y > x`.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

A função `new()` só pode ser usada em construtores internos e devolve o item pretendido se os valores de entrada forem considerados válidos.

Se os valores de entrada forem inválidos, podemos parar com uma mensagem de erro, como no exemplo.
Em alternativa, podes preferir usar um valor de preenchimento como `nothing` ou `missing`.
Consulta o Conceito [`Nothingness`][nothingness] para saberes mais sobre isto.

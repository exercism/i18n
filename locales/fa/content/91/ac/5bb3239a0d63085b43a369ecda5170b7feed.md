# مرتب‌سازی

```sather
   numbers.sort;                                  -- the natural order
   words.insertion_sort_by(bind(before(_, _)));   -- an order you supply
```

## مرتب‌سازی به چه چیزی نیاز دارد

`sort` نیاز دارد که نوع عنصر دارای `is_lt` باشد. `INT`، `STR`، `CHAR`، `FLTD` و `INTI` همگی این را دارند. کلاس خودتان اما تا وقتی که خودتان یکی ننویسید، این را ندارد.

`insertion_sort_by` هیچ انتظاری از نوع عنصر ندارد: هر آنچه لازم است بداند، در رویه‌ای است که به آن می‌دهید.

## یک مقایسه باید چگونه باشد

رویه باید یک ترتیب سازگار تعریف کند، وگرنه نتیجه تعریف‌نشده است:

- اگر `before(a, b)` «درست» باشد، آن‌گاه `before(b, a)` باید «غلط» باشد؛
- اگر `a` پیش از `b` بیاید و `b` پیش از `c`، آن‌گاه `a` پیش از `c`؛
- `before(a, a)` باید «غلط» باشد.

مورد آخر همانی است که بیشتر مردم روی آن گیر می‌کنند. نوشتن `<=` به‌جای `<` می‌گوید که یک عنصر پیش از خودش می‌آید و مرتب‌سازی‌ای که چنین مقایسه‌ای دریافت کند، می‌تواند هر نتیجه‌ای تولید کند.

## حالت‌های تساوی

نه `sort` و نه `insertion_sort_by` **پایدار** نیستند: عناصری که مقایسه آن‌ها را برابر می‌داند، ممکن است به هر ترتیبی بیرون بیایند و در این کتابخانه معمولاً برعکس بیرون می‌آیند.

بنابراین ترفند مرتب‌سازی دو بار (یک‌بار بر اساس اسم، سپس بر اساس امتیاز، به این امید که تیم‌های هم‌امتیاز ترتیب الفبایی خود را حفظ کنند) اینجا کار نمی‌کند. همچنین نمی‌توان برای هیچ کاری به ترتیب ورودی تکیه کرد.

اگر تساوی‌ها مهم‌اند، آن‌ها را **در خود مقایسه** تعیین کنید. آن را به یک ترتیب کامل تبدیل کنید تا هرگز دو عنصر متفاوت برابر خوانده نشوند:

```sather
   shorter(a, b : STR) : BOOL is
      if a.size /= b.size then return a.size < b.size; end;
      return a < b;                  -- same length: alphabetical
   end;
```

این کار ارزشش را دارد، حتی وقتی فکر می‌کنید تساوی‌ها ممکن است پیش نیایند. مقایسه‌ای که در هر دو جهت «غلط» پاسخ دهد، نتیجه را نامشخص می‌گذارد و این bug به شکل ترتیبی ظاهر می‌شود که بدون هیچ دلیل قابل‌مشاهده‌ای تغییر می‌کند.

## موارد دیگر

| فراخوانی | کاری که می‌کند |
| --- | --- |
| `a.sort` | درجا، ترتیب طبیعی، پایدار نیست |
| `a.insertion_sort_by(lt)` | درجا، ترتیب شما، پایدار |
| `a.is_sorted` | بررسی می‌کند |
| `a.is_sorted_by(lt)` | بررسی بر اساس ترتیب شما |
| `a.binary_search(e)` | جست‌وجو، روی یک آرایه‌ی مرتب |
| `a.binary_search_by(e, lt)` | جست‌وجو، بر اساس ترتیب شما |

`binary_search` روی یک آرایه‌ی نامرتب شکست نمی‌خورد، بلکه پاسخ بی‌معنی می‌دهد. پیش‌شرط آن هم همین را می‌گوید و پیش‌شرط‌ها بررسی نمی‌شوند، مگر اینکه به کامپایلر `-chk` داده شود.

## هزینه

مرتب‌سازی درجی کاری متناسب با مربع طول انجام می‌دهد که برای یک جدول رده‌بندی ۱۲ تیمی خوب است و برای ۱۰٬۰۰۰ رکورد نامناسب. `ARR_SORT_ALG::sort_by` نسخه‌ی مرتب‌سازی سریع از همین ایده است، برای زمانی که آرایه بزرگ است و پایداری اهمیتی ندارد.

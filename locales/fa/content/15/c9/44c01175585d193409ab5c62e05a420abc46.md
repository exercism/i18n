# مقدمه

## شرط‌ها

### RFLAGs

یک ثبات ویژه به نام `rflags` وجود دارد.
بیت‌های آن مانند «پرچم» برای شرط‌های مختلف عمل می‌کنند.

برخی از آن‌ها در ادامه فهرست شده‌اند:

| اسم      | نماد | بیت |
| :------- | :----: | :-: |
| رقم نقلی |   CF   |  ۰  |
| صفر      |   ZF   |  ۶  |
| علامت    |   SF   |  ۷  |
| سرریز    |   OF   | ۱۱  |

### دستورهای مقایسه

پرچم‌های `rflags` به‌طور مستقیم _تغییر نمی‌کنند_.
در عوض، آن‌ها توسط دستورهای مختلفی تنظیم می‌شوند.

برای نمونه، `ZF` توسط بسیاری از عملیات حسابی یا بیتی، وقتی نتیجه صفر است، تنظیم می‌شود.

یکی از رایج‌ترین دستورهایی که برای بررسی شرط‌ها استفاده می‌شود `cmp` است.
این دستور دو عملوند می‌گیرد و پرچم‌ها را به‌روزرسانی می‌کند، اما **عملوندهایش را تغییر نمی‌دهد**.

#### دستور CMP

دستور `cmp` عملوند دوم را از اولی کم می‌کند و پرچم‌ها را بر اساس نتیجه تنظیم می‌کند.

اگر A عملوند اول و B عملوند دوم باشد:

| پرچم | تنظیم می‌شود وقتی               |
| :--: | :----------------------------- |
|  CF  | A < B (بدون علامت)              |
|  ZF  | A == B                         |
|  SF  | A < B (علامت‌دار، بدون سرریز)   |
|  OF  | سرریز در تفریق علامت‌دار         |

### انشعاب

به‌طور پیش‌فرض، کد در x86-64 به‌صورت ترتیبی از بالا به پایین اجرا می‌شود.

اما موقعیت‌های زیادی وجود دارد که تغییر این رفتار لازم است.
برای نمونه، برای اجرای مجموعه‌ی متفاوتی از دستورها در پاسخ به یک شرط.

در زبان‌های سطح بالاتر، این کار معمولاً با انتزاع‌هایی مانند شرط‌های `if...else` انجام می‌شود.
با این حال، این‌ها در x86-64 وجود ندارند.

در عوض، x86-64 دستورهایی فراهم می‌کند که اجرا را به‌طور مؤثر به محل دیگری از کد منتقل می‌کنند.
به این کار `branching` می‌گویند.

~~~~exercism/note
ما قبلاً دو دستور از این نوع دیده‌ایم: `call` و `ret`.

وقتی یک تابع فراخوانی می‌شود، اجرا از فراخوان به تابع فراخوانی‌شده منتقل می‌شود.
و هنگام بازگشت، اجرا دوباره به فراخوان منتقل می‌شود.

اگر `ret` پیدا نشود، اجرا از یک تابع به تابع بعدی ادامه پیدا می‌کند.
این گاهی می‌تواند برای بهینه‌سازی جریان کد استفاده شود.
~~~~

#### پرش غیرشرطی

دستور **jmp** اجرای برنامه را به‌طور غیرشرطی به نقطه‌ی دیگری از کد منتقل می‌کند.
عملوند تک آن یک برچسب است که آدرس نقطه‌ای را دارد که اجرا از آنجا ادامه می‌یابد.

برای نمونه، تابع زیر را در نظر بگیرید:

```x86asm
fn:
    mov rax, 5
    jmp end

    add rax, 10
end:
    ret
```

وقتی `fn` فراخوانی می‌شود، اجرا از `mov rax, 5` شروع می‌شود.
این کار مقدار `rax` را در آن نقطه ۵ قرار می‌دهد.

دستور بعدی `jmp end` است که اجرا را به برچسب `end` منتقل می‌کند.

بعد از `end`، دستور بعدی `ret` است که اجرا را به تابع فراخوان برمی‌گرداند.

توجه کنید که چون `add rax, 10` بعد از `jmp end` و قبل از `end` قرار دارد، هرگز اجرا نمی‌شود.
مقدار `rax` هنگام بازگشت `fn` برابر ۵ است.

#### پرش شرطی

خانواده‌ی دستورهای **jcc** اجرای برنامه را فقط در صورت برآورده شدن شرطی مشخص، به نقطه‌ی دیگری منتقل می‌کنند.
در غیر این صورت، اجرا به‌طور ترتیبی ادامه می‌یابد.

هر شرط به یک یا چند پرچم در `rflags` نگاشت می‌شود.
برخی از گونه‌های `jcc` بررسی می‌کنند که پرچمی تنظیم شده است و برخی دیگر بررسی می‌کنند که پاک شده است.

`cc` در `jcc` تحت‌اللفظی نیست، بلکه به پسوند مشخص مرتبط با پرچم آزموده‌شده اشاره دارد.

پسوندهای زیادی وجود دارد و بسیاری از آن‌ها همان شرطی را بررسی می‌کنند که پسوند دیگری بررسی می‌کند.
برخی از آن‌ها مستقیماً به یک پرچم اشاره دارند، به‌طوری که دستور اگر آن پرچم مشخص تنظیم شده باشد، به یک برچسب می‌پرد:

| پسوند | می‌پرد اگر |
| :----: | :------: |
|   z    | ZF == ۱  |
|   c    | CF == ۱  |
|   s    | SF == ۱  |
|   o    | OF == ۱  |

بسیاری دیگر طوری انتخاب شده‌اند که به معنایشان در دستور `cmp` اشاره کنند.
برای نمونه:

| دستور    | پسوند | می‌پرد اگر         |
| ----------- | :----: | :--------------- |
| cmp A, B    |   e    | A == B           |
| cmp A, B    |   l    | A < B (علامت‌دار)   |
| cmp A, B    |   b    | A < B (بدون علامت) |
| cmp A, B    |   g    | A > B (علامت‌دار)   |
| cmp A, B    |   a    | A > B (بدون علامت) |

می‌توان `e` را بعد از `l`، `b`، `g` یا `a` اضافه کرد تا برابری را نیز در شرط بگنجاند:

```x86asm
cmp rcx, r8
jge two      ; this jumps to 'two' if rcx is greater than, or equal to, r8 in a signed comparison
jbe two      ; this jumps to 'two' if rcx is lesser than, or equal to, r8 in an unsigned comparison
```

برای همه‌ی پسوندها، گونه‌هایی وجود دارد که رفتار مخالف را بررسی می‌کنند.
نحوه‌ی نگارش آن‌ها یکسان است، اما یک `n` قبل از پسوند دارند.

برای نمونه، `jnz` وقتی می‌پرد که `ZF` تنظیم **نشده** باشد.
به همین ترتیب، `jnae` وقتی می‌پرد که A بزرگتر یا مساوی B **نباشد** (A و B به‌عنوان اعداد صحیح بدون علامت تفسیر می‌شوند).

~~~~exercism/note
برخی پسوندها نام‌های دیگری برای همان شرط‌ها هستند.
برای نمونه، `jz` (پسوند `z`، برای `ZF`) و `je` (پسوند `e`، برای برابری) هر دو وقتی `ZF` تنظیم شده باشد می‌پرند.
این به این دلیل است که با `cmp`، `ZF` وقتی تنظیم می‌شود که تفریق صفر شود، که متناظر با برابر بودن دو عملوند است.

با این حال، پسوندهای دیگر ترکیبی از پرچم‌ها را بررسی می‌کنند و نمی‌توان آن‌ها را مستقیماً با یک پسوند تک‌پرچمی جایگزین کرد.

پسوندی را ترجیح دهید که معناشناسی مقایسه‌تان را بهتر توصیف می‌کند.
~~~~

### برچسب‌های محلی

برچسب‌ها در کل فایل مبدأ قابل مشاهده‌اند و محلیِ یک تابع نیستند.
بنابراین استفاده‌ی دوباره از یک اسم برچسب ممکن نیست.

برای تقلید رفتار یک برچسب محلی، NASM نشانه‌گذاری ویژه‌ای برای برچسبی دارد که با یک نقطه (`.`) قبل از آن اعلان می‌شود.
این نشانه‌گذاری برچسبی را تعریف می‌کند که به‌طور ضمنی شامل اسم برچسب قبلیِ بدون نقطه است:

```x86asm
section .text
fn1:
    ...
.example: ; this is fn1.example
    ...
    ret

fn2:
    ...
.example: ; this is fn2.example
    ...
    ret
```

هنوز می‌توان با استفاده از اسم کامل برچسب، از هر جای کد به این برچسب پرش کرد، برای نمونه `jmp fn1.example`.

با این حال، پرشی که از بخش برچسب شروع‌شده از نقطه استفاده کند، به برچسب _داخل_ تابع بالایی انجام می‌شود.
برای نمونه، `.example` طوری رفتار می‌کند که گویی محلیِ همان تابع است:

```x86asm
section .text
fn1:
    ...
.example:
    ...
    jmp .example ; this jumps to fn1.example

fn2:
    ...
.example:
    ...
    jmp .example ; this jumps to fn2.example
```

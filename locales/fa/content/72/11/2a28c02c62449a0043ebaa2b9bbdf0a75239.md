# مقدمه

## RFLAGs

ثبات ویژه‌ای به اسم `rflags` وجود دارد.
بیت‌های آن مانند پرچم‌هایی برای شرایط گوناگون عمل می‌کنند.

برخی از آن‌ها در ادامه آمده است:

| اسم      | نماد   | بیت |
| :------- | :----: | :-: |
| نقلی     |   CF   |  ۰  |
| صفر      |   ZF   |  ۶  |
| علامت    |   SF   |  ۷  |
| سرریز    |   OF   | ۱۱  |

## دستورهای مقایسه

پرچم‌های `rflags` به‌طور _مستقیم_ تغییر نمی‌کنند.
در عوض، دستورهای مختلف زیادی آن‌ها را تنظیم می‌کنند.

برای نمونه، بسیاری از عملیات‌های حسابی یا بیتی وقتی نتیجه صفر باشد، `ZF` را تنظیم می‌کنند.

یکی از رایج‌ترین دستورهایی که برای آزمودن شرط‌ها به کار می‌رود، `cmp` است.
این دستور دو عملوند می‌گیرد و پرچم‌ها را به‌روزرسانی می‌کند، اما **عملوندهایش را تغییر نمی‌دهد**.

### دستور CMP

دستور `cmp` عملوند دوم را از اولی کم می‌کند و پرچم‌ها را بر اساس نتیجه تنظیم می‌کند.

اگر A عملوند اول و B عملوند دوم باشد:

| پرچم | تنظیم می‌شود وقتی              |
| :--: | :----------------------------- |
|  CF  | A < B (بدون علامت)             |
|  ZF  | A == B                         |
|  SF  | A < B (علامت‌دار، بدون سرریز)  |
|  OF  | سرریز در تفریق علامت‌دار        |

## انشعاب

به‌طور پیش‌فرض، کد در x86-64 به‌صورت ترتیبی از بالا به پایین اجرا می‌شود.

اما موقعیت‌های زیادی وجود دارد که لازم است این رفتار تغییر کند.
برای نمونه، برای اجرای مجموعه‌ای متفاوت از دستورها در پاسخ به یک شرط.

در زبان‌های سطح بالاتر، این کار معمولاً با انتزاع‌هایی مثل شرط‌های `if...else` انجام می‌شود.
اما چنین چیزی در x86-64 وجود ندارد.

در عوض، x86-64 دستورهایی فراهم می‌کند که اجرا را به‌طور مؤثر به نقطه‌ی دیگری از کد منتقل می‌کنند.
به این کار `branching` می‌گویند.

~~~~exercism/note
پیش‌تر دو دستور از این نوع را دیده‌ایم: `call` و `ret`.

وقتی تابعی فراخوانی می‌شود، اجرا از فراخوان به تابع فراخوانی‌شده منتقل می‌شود.
و هنگام بازگشت، اجرا دوباره به فراخوان منتقل می‌شود.

اگر `ret`ی پیدا نشود، اجرا از یک تابع به تابع بعدی ادامه پیدا می‌کند.
این کار گاهی می‌تواند برای بهینه‌سازی جریان کد به کار برود.
~~~~

### پرش غیرشرطی

دستور **jmp** اجرای برنامه را به‌طور غیرشرطی به نقطه‌ی دیگری از کد منتقل می‌کند.
تنها عملوند آن برچسبی است که نشانی نقطه‌ای را در خود دارد که اجرا از آن‌جا ادامه می‌یابد.

برای نمونه، تابع زیر را در نظر بگیرید:

```x86asm
fn:
    mov rax, 5
    jmp end

    add rax, 10
end:
    ret
```

وقتی `fn` فراخوانی می‌شود، اجرا از `mov rax, 5` شروع می‌شود.
این دستور مقدار درون `rax` را در آن نقطه برابر ۵ قرار می‌دهد.

دستور بعدی `jmp end` است که اجرا را به برچسب `end` منتقل می‌کند.

بعد از `end`، دستور بعدی `ret` است که اجرا را دوباره به تابع فراخوان منتقل می‌کند.

توجه کنید که چون `add rax, 10` بعد از `jmp end` و قبل از `end` قرار دارد، هرگز اجرا نمی‌شود.
مقدار `rax` هنگام بازگشت `fn` برابر ۵ است.

### پرش شرطی

خانواده‌ی دستورهای **jcc** فقط در صورتی اجرای برنامه را به نقطه‌ی دیگری منتقل می‌کنند که شرط خاصی برقرار باشد.
در غیر این صورت، اجرا به‌صورت ترتیبی ادامه می‌یابد.

هر شرط به یک یا چند پرچم در `rflags` نگاشت می‌شود.
برخی از گونه‌های `jcc` بررسی می‌کنند که پرچمی تنظیم شده است و برخی دیگر بررسی می‌کنند که پرچمی پاک شده است.

`cc` در `jcc` تحت‌اللفظی نیست، بلکه به پسوند خاصی اشاره دارد که به پرچم آزموده‌شده مربوط است.

پسوندهای زیادی وجود دارد و بسیاری از آن‌ها همان شرطی را می‌آزمایند که پسوند دیگری می‌آزماید.
برخی از آن‌ها مستقیماً به یک پرچم اشاره دارند، طوری که اگر آن پرچم خاص تنظیم شده باشد، دستور به برچسبی می‌پرد:

| پسوند | می‌پرد اگر |
| :----: | :------: |
|   z    | ZF == ۱  |
|   c    | CF == ۱  |
|   s    | SF == ۱  |
|   o    | OF == ۱  |

بسیاری دیگر طوری انتخاب شده‌اند که به معنایشان در دستور `cmp` اشاره کنند.
برای نمونه:

| دستور    | پسوند | می‌پرد اگر       |
| ----------- | :----: | :--------------- |
| cmp A, B    |   e    | A == B           |
| cmp A, B    |   l    | A < B (علامت‌دار) |
| cmp A, B    |   b    | A < B (بدون علامت) |
| cmp A, B    |   g    | A > B (علامت‌دار) |
| cmp A, B    |   a    | A > B (بدون علامت) |

می‌توان بعد از `l`، `b`، `g` یا `a` حرف `e` را اضافه کرد تا برابری هم در شرط گنجانده شود:

```x86asm
cmp rcx, r8
jge two      ; this jumps to 'two' if rcx is greater than, or equal to, r8 in a signed comparison
jbe two      ; this jumps to 'two' if rcx is lesser than, or equal to, r8 in an unsigned comparison
```

برای همه‌ی پسوندها، گونه‌هایی وجود دارد که رفتار مخالف را بررسی می‌کنند.
نحوه‌ی نگارش آن‌ها یکسان است، فقط یک `n` قبل از پسوند اضافه می‌شود.

برای نمونه، `jnz` وقتی می‌پرد که `ZF` **تنظیم نشده** باشد.
به همین ترتیب، `jnae` وقتی می‌پرد که A بزرگ‌تر یا مساوی B **نباشد** (A و B به‌عنوان اعداد صحیح بدون علامت تفسیر می‌شوند).

~~~~exercism/note
برخی از پسوندها نام‌های دیگری برای همان شرط‌ها هستند.
برای نمونه، `jz` (پسوند `z`، برای `ZF`) و `je` (پسوند `e`، برای برابری) هر دو وقتی می‌پرند که `ZF` تنظیم شده باشد.
دلیلش این است که در `cmp`، وقتی تفریق صفر شود `ZF` تنظیم می‌شود و این یعنی دو عملوند برابرند.

اما پسوندهای دیگر ترکیبی از پرچم‌ها را می‌آزمایند و نمی‌توان آن‌ها را مستقیماً با پسوندی که به یک پرچم اشاره دارد جایگزین کرد.

پسوندی را ترجیح دهید که معنای مقایسه‌ی شما را بهتر توصیف می‌کند.
~~~~

## برچسب‌های محلی

برچسب‌ها در کل فایل منبع دیده می‌شوند و به یک تابع خاص محدود نیستند.
پس نمی‌توان اسم یک برچسب را دوباره به کار برد.

برای شبیه‌سازی رفتار یک برچسب محلی، NASM برای برچسبی که با نقطه (`.`) در ابتدایش تعریف می‌شود، یک نشانه‌گذاری خاص دارد.
این نشانه‌گذاری برچسبی تعریف می‌کند که به‌طور ضمنی اسم برچسب بدون‌نقطه‌ی قبلی را در خود دارد:

```x86asm
section .text
fn1:
    ...
.example: ; this is fn1.example
    ...
    ret

fn2:
    ...
.example: ; this is fn2.example
    ...
    ret
```

هنوز می‌توان از هر جای کد با استفاده از اسم کامل برچسب به آن پرش کرد، برای نمونه `jmp fn1.example`.

اما پرشی که از بخش برچسب از نقطه به بعد استفاده کند، به برچسب _درون_ تابع بالایی انجام می‌شود.
برای نمونه، `.example` طوری رفتار می‌کند که گویی محلی همان تابع است:

```x86asm
section .text
fn1:
    ...
.example:
    ...
    jmp .example ; this jumps to fn1.example

fn2:
    ...
.example:
    ...
    jmp .example ; this jumps to fn2.example
```

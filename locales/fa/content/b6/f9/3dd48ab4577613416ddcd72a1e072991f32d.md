# درباره

تا اینجای برنامه‌ی درسی، R را دیده‌اید که اغلب به‌عنوان یک زبان امری به کار می‌رود و کمکم رنگ یک زبان تابعی می‌گیرد (خصوصاً با کتابخانه‌های [`purrr`][ref-purrr] و [`dplyr`][ref-dplyr]).

اینکه حالا بگوییم R در درجه‌ی اول شیءگرا است، ممکن است کمی تردید برانگیزد!

به‌طرز عجیبی، این جمله درست است.
R در درون با کلاس‌ها، وراثت، چندریختی و همان نوع طرز فکری که برنامه‌نویسان شیءگرا معمولاً دارند پیاده‌سازی شده است.

اما هرکس با Java یا Ruby (که صراحتاً شیءگرا هستند) یا حتی Python (که از برخی جهات نیمه‌پنهان شیءگرا است) آشنا باشد، رویکرد R را ... _ناآشنا_ خواهد یافت.

برای شروع، چندین طراحی کلاس وجود دارد: شاید سه مورد که کاربرد رایج دارند (S3، S4، R6) و چند مورد دیگر که بیشتر از نظر نظری جالب‌اند.

بحثی کامل را می‌توانید در [Advanced R, 2e][book-advanced-r]، فصل‌های ۱۲ تا ۱۶ پیدا کنید.
این کتاب ۲۰۱۹ عمدتاً برای کسانی است که می‌خواهند ساختار درونی R را بفهمند و نگهداری کنند، و شیءگرایی برای این کار ضروری است.

کتاب‌های درسی‌ای که بیشتر مخاطب نهایی را در نظر می‌گیرند، متفاوت‌اند.

- کتاب The Art of R Programming (۲۰۱۱، فقط چاپی) فصلی درباره‌ی شیءگرایی دارد که S3 و (به‌طور خلاصه‌تر) S4 را پوشش می‌دهد؛ این‌ها در آن زمان مهم بودند.
  این جمله‌ی نقل‌شده که «کلاس‌های S3 ساختاری نسبتاً سرهم‌بندی دارند» هنوز به‌طرز چشمگیری درست است.
- کتاب R in Action (ویرایش سوم، ۲۰۲۲) شیءگرایی را به ۳ صفحه در فصلی درباره‌ی برنامه‌نویسی پیشرفته نزدیک انتهای کتاب محدود می‌کند.
- کتاب [R for Data Science, 2e][book-r-data-sci] (۲۰۲۳، با ۵۴۸ صفحه در نسخه‌ی چاپی) هیچ اشاره‌ای به شیءگرایی نمی‌کند.

این مفهوم بر کلاس‌های S3 تمرکز می‌کند، که ساده‌ترین، رایج‌ترین و مرتبط‌ترین با مسائل سبک Exercism هستند.
برخی از تمرین‌های عملی در مسیر R از شما می‌خواهند یک کلاس S3 بسازید، و در بقیه این کار اختیاری است اما با ملایمت تشویق می‌شود.

## کلاس‌های S3

این کلاس‌ها قدیمی‌اند: اسم S3 فقط به این معناست که در نسخه‌ی ۳ زبان S معرفی شدند (زبان S پیش‌درآمد تجاری R بود).

یک کلاس S3 هم بسیار ساده است: معمولاً یک [لیست][concept-lists] با دست‌کم یک ویژگی اضافه.

به نقل از [Advanced R][book-s3]: «S3 غیررسمی و موردی است، اما در مینیمال بودنش نوعی ظرافت هست: نمی‌توانید هیچ بخشی از آن را بردارید و هنوز یک سیستم شیءگرای کاربردی داشته باشید.»

```R
# create a list
pt2d <- list(x = 2.5, y = 4.2)
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
class(pt2d)
#> [1] "list"
attributes(pt2d)
#> $names
#> [1] "x" "y"

# convert the list to an S3 class
class(pt2d) <- "point2d"
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
#>  - attr(*, "class")= chr "point2d"
class(pt2d)
#> [1] "point2d"
attributes(pt2d)
#> $names
#> [1] "x" "y"

#> $class
#> [1] "point2d"
```

پس انجام یک انتساب به [`class(obj)`][ref-class] فقط یک ویژگی به `obj` اضافه می‌کند؛ در اینجا pt2d را به‌عنوان نمونه‌ای از کلاس point2d مشخص می‌کند.

می‌توان مراحل ساخت را با [`structure()`][ref-structure] ترکیب کرد:

```R
pt2d_2 <- structure(list(x = 2.5, y = 4.2), class = "point2d")
pt2d_2 == pt2d
#> Error in pt2d_2 == pt2d : comparison of these types is not implemented
```

هرچند نمونه‌های حاصل به‌طور نظری یکسان‌اند، هنوز راهی پیاده‌سازی نکرده‌ایم که R بتواند این را تأیید کند.

### متدهای عمومی

هرکس با شیءگرایی در زبان‌های دیگر آشنا باشد، ممکن است بپرسد: «مگر قرار نبود کلاس‌ها بتوانند کارهایی _انجام دهند_؟»

می‌توانیم متدهای موجود برای نمونه‌های `point2d` را بررسی کنیم و ببینیم که (برخلاف `list` زیرین) در حال حاضر هیچ متدی وجود ندارد.

```R
methods(class = "point2d")
#> no methods found
methods(class = "list")
#>  [1] %within%      all.equal     as.col_spec   as.data.frame as_mapper     as_tibble     coerce        common_by    
#>  [9] Ops           pattern_alpha relist        scale_type    select        type.convert  within       
#> see '?methods' for accessing help and source code
```

در بیشتر زبان‌های شیءگرا، متدها درون تعریف کلاس تعریف می‌شوند.
چند زبان (به‌ویژه Ruby) اجازه می‌دهند بعداً متدهای کلاس را اضافه و تغییر دهید.

کلاس‌های S3 بسیار متفاوت‌اند.
به‌جای اضافه کردن متدها به یک کلاس، کلاس را به یک متد عمومی اضافه می‌کنیم.

هرکس به‌صورت تعاملی در کنسول R کار کند، دائم از متدهای عمومی استفاده می‌کند، معمولاً بدون اینکه به نحوه‌ی پیاده‌سازی‌شان فکر کند.

یک مثال بسیار رایج `print()` است، هرچند به‌ندرت اسم تابع را تایپ می‌کنید.
وارد کردن یک مقدار `x` به‌تنهایی در اعلان کنسول، فقط شکر نحوی برای `print(x)` است.

```R
1:4
#> [1] 1 2 3 4
print(1:4)
#> [1] 1 2 3 4
```

همین حالا هم می‌توانیم `pt2d` را چاپ کنیم.
هرچند `print()` هیچ چیزی درباره‌ی کلاس `point2d` نمی‌داند، پیش‌فرض‌های معقولی برای رسیدگی به انواع گوناگون اشیا دارد.

```R
pt2d
#> $x
#> [1] 2.5

#> $y
#> [1] 4.2

attr(,"class")
#> [1] "point2d"
```

این خیلی پرگو است و شاید بخواهیم راهی داشته باشیم که نقطه را به‌صورت مختصر و زیبا چاپ کنیم.

ساده است: فقط تابعی به اسم `print.point2d()` اضافه کنید.
اسم باید به شکل `methodname.classname` باشد تا توزیع‌کننده بداند دنبال چه چیزی بگردد.

```R
print.point2d <- function(pt) {
  cat("Cartesian coords (", pt$x, ", ", pt$y, ")\n", sep="")
}

pt2d
#> Cartesian coords (2.5, 4.2)
```

حالا فرض کنید می‌خواهیم یک متد عمومی تازه بسازیم، مثلاً `flipvert()` برای معکوس کردن علامت مختص `y`.

باز هم ساده است:

```R
flipvert <- function(x, ...) UseMethod("flipvert")
```

این یک توزیع‌کننده می‌سازد؛ در آن `x` شیء ما با یک کلاس S3 است و `...` هر آرگومان اضافی‌ای را که تعریف‌های متد ممکن است نیاز داشته باشند مدیریت می‌کند («آرگومان‌های نقطه»، همان‌طور که در [مفهوم توابع][concept-functions] توضیح داده شده است).

سپس می‌توانیم متد را برای `point2d` تعریف و از آن استفاده کنیم.

```R
flipvert.point2d <- function(pt) {
  pt$y <- -pt$y
  pt
}

flipvert(pt2d)
#> Cartesian coords (2.5, -4.2)

methods("flipvert")
#> [1] flipvert.point2d
```

اکنون R می‌داند چگونه نقطه‌ی ما را برگرداند و نتیجه را نمایش دهد.

می‌توانیم این را با ساختن کلاس‌هایی برای حالت سه‌بعدی، مختصات قطبی و غیره گسترش دهیم و سپس برای هرکدام متد تعریف کنیم.

از دید کاربر نهایی فقط `flipvert(x, ...)` وجود دارد و می‌توانیم به R تکیه کنیم تا کلاس ورودی را تشخیص دهد و پیاده‌سازی زیرین مناسب را به کار ببرد.

~~~~exercism/caution
اسم‌های توابع در قالب `verb.class` هم برای کاربران و هم برای تجزیه‌گر R شبیه متدهای S3 به نظر می‌رسند.
لطفاً از به کار بردن نام‌گذاری مشابه در زمینه‌های دیگر پرهیز کنید.

البته R پایه گاهی این قاعده را نقض می‌کند.
باید این را یک اتفاق تاریخی ناگوار بدانیم (برای توابعی حتی قدیمی‌تر از S3) که باید برای سازگاری با گذشته حفظ شود.
~~~~

### وراثت

علاقه‌مندان به شیءگرایی می‌توانند چندین فصل طولانی کتاب درباره‌ی وراثت، زیرکلاس‌سازی، میکسین‌ها و باقی ماجرا بنویسند.

R فقط اجازه می‌دهد چندین اسم به ویژگی `class` بدهید: یک بردار رشته‌ی بلندتر، نه یک رشته‌ی تکی.

با این خطر که مثال را تا مرز شکستن بکشیم، فرض کنید یک کلاس عمومی `point` ساخته بودیم و می‌خواستیم از آن زیرکلاس‌های `point2d`، `point3d` و غیره بسازیم.

در این صورت تعریف `point2d` به‌سادگی از `class = c("point2d", "point")` استفاده می‌کند: کلاس خاص و کلاس والد (یا کلاس‌های والد).

متدهای عمومی مانند `print()` سپس به ترتیب دنبال `print.point2d()`، `print.point()` و (احتمالاً) `print.default()` می‌گردند و نخستین پیاده‌سازی‌ای را که توزیع‌کننده پیدا کند به کار می‌برند.

# مولدهای تست

مولدهای تست به ترک‌ها اجازه می‌دهند تست‌ها را به‌طور خودکار تولید کنند، بدون اینکه خودمان آن‌ها را بنویسیم. هر مولد تست از `canonical data` تمرین می‌خواند، که اسم تست، ورودی‌ها و خروجی‌های آن را تعریف می‌کند. می‌توانید درباره‌ی رویکرد Exercism به مجموعه‌های تست [اینجا](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md) بیشتر بخوانید.

تولید خودکار تست‌ها هر نوع خطای کاربر را هنگام ساخت تست‌ها از میان برمی‌دارد. می‌خواهیم تست‌ها نسبت به داده‌های متعارف خود دقیق باشند. تولید تست همچنین به‌روز نگه داشتن تست‌ها را بسیار ساده‌تر می‌کند. با تغییر داده‌های متعارف، به‌محض اجرای مولد آن تست، تست‌ها به‌طور خودکار به‌روزرسانی می‌شوند.

نمونه‌ای از یک فایل داده‌های متعارف را می‌توانید [اینجا](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json) ببینید.

## اصطلاحات رایج

هنگام بررسی داده‌های متعارف و کد مولدها، اصطلاحات رایج زیادی به کار می‌بریم. امیدواریم این فهرست روشن کند که هر یک از آن‌ها به چه چیزی اشاره دارند.

* داده‌های متعارف: کل مجموعه‌ی تست را نشان می‌دهد.
* مورد داده‌های متعارف: نمایش یک مورد تست تکی.
* توضیحات: اسم تست.
* ویژگی: متدی که هنگام اجرای تست فراخوانی می‌شود.
* ورودی: ورودی مورد تست.
* مقدار مورد انتظار: مقداری که هنگام اجرای مورد تست انتظار می‌رود.

## افزودن یک مولد ساده

افزودن یک مولد تست ساده است. کافی است کلاسی با اسم تمرین (به‌صورت PascalCase) به فایل `Generators.fs` در پوشه‌ی `generators` اضافه کنید و کلاس انتزاعی `GeneratorExercise` را گسترش دهید.

تمرین Bob نمونه‌ای از یک مولد ساده است. کد منبع آن در ادامه آمده است، اما می‌توانید آن را در مخزن [اینجا](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174) هم ببینید.

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

این یک مولد کاملاً کارآمد است و نیازی به نوشتن کد دیگری نیست. با این حال، سادگی آن از این روست که مجموعه‌ی تست و خود برنامه نسبتاً پیش‌پاافتاده‌اند.

## افزودن یک مولد پیچیده

برای بسیاری از مولدها، رفتار پیش‌فرض کلاس `GeneratorExercise` کافی است. اما برای مولدهای _پیچیده‌تر_ می‌توانید یک یا چند متد مجازی آن را بازنویسی کنید:

### متد: RenderInput

ورودی یک متد تست را رندر می‌کند.

#### مثال

مولد `Gigasecond` مقدار ورودی را به‌صورت یک مقدار `DateTime` (در پرانتز) رندر می‌کند:

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

توجه کنید که می‌توانید از فیلد `key` استفاده کنید تا خروجی را فقط برای فیلدهای ورودی مشخصی سفارشی کنید. مولد `Yacht` این کار را انجام می‌دهد:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### متد: RenderExpected

مقدار مورد انتظار یک متد تست را رندر می‌کند.

#### مثال

مولد `Connect` مقدار مورد انتظار را به‌صورت یک مقدار `Option<T>` رندر می‌کند:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### متد: RenderSut

سیستم تحت تست (SUT) را رندر می‌کند. این همان مقدار واقعی است که با مقدار مورد انتظار بررسی می‌شود.

#### مثال

مولد `RunLengthEncoding` یک مورد تست دارد که در آن بررسی می‌کند رمزگذاری و سپس رمزگشایی ورودی به همان مقدار می‌انجامد. متد `RenderSut` بازنویسی شده است تا آنچه یک فراخوانی واحد به تابع ناموجود `consistency` می‌شد را به زنجیره‌ای از فراخوانی‌های `encode |> decode` تبدیل کند:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### متد: RenderArrange

بخش آماده‌سازی متد تست را رندر می‌کند. در این بخش، SUT ساخته می‌شود.

رفتار پیش‌فرض معمولاً همان چیزی است که می‌خواهید. فقط در شرایط بسیار خاصی ممکن است بخواهید آن را تغییر دهید.

توجه: این متد یک `string list` برمی‌گرداند که هر `string` آن به یک خط رندر‌شده در فایل تست متناظر است.

### متد: RenderAssert

بخش تأیید متد تست را رندر می‌کند. در این بخش، برای بررسی SUT در برابر مقدار مورد انتظار، تأیید انجام می‌شود.

رفتار پیش‌فرض معمولاً همان چیزی است که می‌خواهید. فقط در شرایط بسیار خاصی ممکن است بخواهید آن را تغییر دهید.

توجه: این متد یک `string list` برمی‌گرداند که هر `string` آن به یک خط رندر‌شده در فایل تست متناظر است.

### متد: RenderSetup

هر متد کمکی/آماده‌سازی اضافی را رندر می‌کند. این کار را می‌توان برای تعریف متدهای کمکی‌ای استفاده کرد که در متدهای تست به کار می‌روند.

کد آماده‌سازی _پیش از_ متدهای تست اضافه می‌شود تا متدهای آماده‌سازی در متدهای تست قابل استفاده باشند.

توجه: این متد یک `string list` برمی‌گرداند که هر `string` آن به یک خط رندر‌شده در فایل تست متناظر است.

#### مثال

مولد `Zipper` دو متد کمکی اضافه می‌کند که در متدهای تست استفاده می‌شوند تا مقداری کد تکراری و خسته‌کننده حذف شود:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### متد: RenderValue

یک مقدار تکی را رندر می‌کند (که برای رندر پارامترهای ورودی، مقدار مورد انتظار و SUT به کار می‌رود).

### مثال

مولد `ComplexNumbers` بسته به نوع مقدار، مقادیر متفاوتی رندر می‌کند:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### متد: MapCanonicalDataCase

مورد داده‌های متعارف را نگاشت می‌کند. اگر بخواهید ویژگی‌ای اضافه یا حذف کنید، این می‌تواند مفید باشد.

رفتار پیش‌فرض معمولاً همان چیزی است که می‌خواهید. فقط در شرایط بسیار خاصی ممکن است بخواهید آن را تغییر دهید.

#### مثال

مولد `ScaleGenerator` از نگاشت مورد داده‌های متعارف استفاده می‌کند تا یک ویژگی جاافتاده را با مقدار `null` اضافه کند (که پردازش بعدی را آسان‌تر می‌کند):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### متد: PropertiesUsedAsSutParameter

مشخص می‌کند کدام ویژگی‌ها باید به‌عنوان پارامترهای SUT استفاده شوند.

رفتار پیش‌فرض معمولاً همان چیزی است که می‌خواهید. فقط در شرایط بسیار خاصی ممکن است بخواهید آن را تغییر دهید.

#### مثال

`RailFenceCipher` ویژگی‌های استفاده‌شده به‌عنوان پارامترهای SUT را به‌صراحت تعریف می‌کند تا ترتیب ارسال آن‌ها را تغییر دهد:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### متد: PropertiesWithIdentifier

مشخص می‌کند به کدام ویژگی‌ها باید شناسه‌ای اختصاص یابد. اگر ویژگی‌ای در این فهرست باشد، مقدارش در خطی جداگانه به شناسه‌ی خودش اختصاص داده می‌شود.

#### مثال

مولد `Transpose` تصمیم گرفته است برای همه‌ی ویژگی‌ها از شناسه استفاده کند:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### متد: IdentifierTypeAnnotation

در برخی موارد می‌خواهید یک شناسه نوع صریحی داشته باشد. یک کاربرد رایج آن زمانی است که مقدار یک فهرست خالی است. در آن موارد، FsUnit برای اجرای موفق تأیید به یک حاشیه‌نویسی نوع نیاز دارد.

#### مثال

مولد `Minesweeper` برای مقادیر خالی یک حاشیه‌نویسی نوع `string list` اضافه می‌کند:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### متد: AdditionalNamespaces

فهرستی از فضای‌نام‌های اضافی را برمی‌گرداند که در فایل تست باز شوند.

#### مثال

مولد `Gigasecond` با نمونه‌های `DateTime` کار می‌کند و بنابراین فضای‌نام آن را به فهرست فضای‌نام‌های اضافی اضافه می‌کند:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### متد: AssertTemplate

قالب تأیید که باید استفاده شود. فهرست کامل قالب‌های تأیید را می‌توانید در `generators/Templates/_Assert*.liquid` پیدا کنید.

#### مثال

مولد `RationalNumbers` از قالب `"AssertEqualWithin"` استفاده می‌کند تا برابری مقادیر double را با یک تلورانس مشخص بررسی کند:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### متد: TestFileFormat

قالب فایل تست: یا یک ماژول یا یک کلاس.

رفتار پیش‌فرض تقریباً همیشه همان چیزی است که می‌خواهید. فقط در موارد بسیار نادری ممکن است بخواهید آن را تغییر دهید.

#### مثال

مولد `Grep` خودش را به‌عنوان یک کلاس تست تعریف می‌کند تا امکان استفاده از متدهای آماده‌سازی و پاک‌سازی فراهم شود:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### متد: TestMethodName

اسم متد تست را مشخص می‌کند.

رفتار پیش‌فرض معمولاً همان چیزی است که می‌خواهید. فقط در شرایط بسیار خاصی ممکن است بخواهید آن را تغییر دهید.

#### مثال

مولد `Zipper` کمی روی اسم متدهای تست پاک‌سازی انجام می‌دهد:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### متد: UseFullMethodName

نشان می‌دهد که آیا اسم متد تستِ استفاده‌شده باید مسیر کامل را به کار ببرد؛ یعنی برای موارد تست تودرتو، توضیحات والد (یا والدها) پیش از اسم متد تست قرار می‌گیرد.

رفتار پیش‌فرض معمولاً همان چیزی است که می‌خواهید. فقط در مواردی که در غیر این صورت چند متد تست با اسم یکسان وجود می‌داشت، ممکن است بخواهید آن را تغییر دهید.

#### متد: Signature

مولد `KindergartenGarden` از اسم‌های کامل متد استفاده می‌کند تا از برخورد اسم متدهای تست جلوگیری کند:

```fsharp
override __.UseFullMethodName _ = true
```

### متد: SkipTestMethod

نشان می‌دهد که آیا متد تست باید با ویژگی `Skip = true` علامت‌گذاری شود.

رفتار پیش‌فرض تقریباً همیشه همان چیزی است که می‌خواهید. فقط در موارد بسیار نادری ممکن است بخواهید آن را تغییر دهید.

#### متد: Signature

تمرین `Markdown` یک تمرین بازآرایی است و بنابراین همه‌ی تست‌هایش از پیش باید در وضعیت معتبری باشند. به همین دلیل، برای هیچ‌یک از متدهای تستش ویژگی `Skip` را اضافه نمی‌کند:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## به‌روزرسانی فایل‌های موجود

ممکن است یک تمرین موجود با داده‌های متعارف هم‌خوان نباشد. اشکالی ندارد که اسکلت تمرین و/یا نمونه‌ی تمرین را برای هماهنگی با داده‌های متعارف به‌روزرسانی کنید!

همچنین اگر در یکی از مولدها یا مجموعه‌های تست موجود مشکلی دیدید، کافی است مولد مورد نظرتان را باز کنید، تغییراتتان را اعمال کنید و سپس مولدها را اجرا کنید.

## اجرای مولدها

این مخزن بر پایه‌ی [.NET Core 2.x](https://www.microsoft.com/net/core) نوشته شده است. برای اجرای مولدها فقط کافی است فرمان زیر را در پوشه‌ی مولدها اجرا کنید:

`dotnet run`

این فرمان همه‌ی مولدهای تمرین تعریف‌شده را برمی‌دارد و همه‌ی موارد تست هر تمرین را تولید می‌کند. ما از reflection برای یافتن همه‌ی تمرین‌ها استفاده می‌کنیم؛ بنابراین اگر تست جدیدی اضافه کنید، هنگام اجرای مولد، آن تست به‌طور خودکار گنجانده می‌شود.

اگر فقط می‌خواهید یک مولد را اجرا کنید، می‌توانید فرمان زیر را اجرا کنید:

`dotnet run -e <exercise>`

پس از اجرای مولد، می‌توانید خروجی تولید را با رفتن به فایل تست آن تمرین ببینید. برای مثال، مجموعه‌ی تست تمرین Bob را می‌توانید در اینجا پیدا کنید:

`exercises/bob/BobTests.fs`

## ارسال یک مولد

اگر از خروجی مولدتان راضی هستید، خوشحال می‌شویم یک pull request ارسال کنید! لطفاً مولدتان، مجموعه‌ی تست به‌روزشده و هر فایل مرتبط دیگری را که تغییر داده‌اید ضمیمه کنید.

# درباره‌ی پوچ‌پذیری

در یک دنیای آرمانی می‌توانستیم به این تکیه کنیم که همه‌چیز به‌خوبی تعریف شده است، با مقدارهای مشخص و بدون هیچ شکافی.

این با تجربه‌ی روزمره‌ی ما در تضاد است و از این رو بسیاری از زبان‌های برنامه‌نویسی راهی برای نمایش نبود یک مقدار دارند: `null` یا `NULL`، `nil`، `None`، هیچ‌چیز...

معرفی آن آسان بود (در سال ۱۹۶۵)، اما خیلی زود به پشیمانی انجامید.

مخترعش بعدها آن را [«اشتباه یک‌میلیارد دلاری»][web-mistake] نامید.

در دهه‌های اخیر، طراحان زبان‌ها راه‌های بسیاری را بررسی کرده‌اند تا مقدارهای `null` در دسترس و در عین حال (بیشتر وقت‌ها) ایمن باشند.

Kotlin چند [اصل کلی][ref-null-safety] دارد که [تفاوت چشمگیری با Java][ref-java2kotlin] دارند. _این تفاوت‌ها یعنی Kotlin قابلیت‌های ویژه‌ای برای تعامل با Java دارد، هرچند جزئیات آن فراتر از حوزه‌ی این مفهوم است._

- Kotlin یک مقدار `null` ویژه دارد.
- همه‌ی نوع‌ها به‌طور _پیش‌فرض_ غیرپوچ‌پذیر هستند (یعنی نمی‌توانند `null` باشند).
- همه‌ی نوع‌ها می‌توانند _«پوچ‌پذیر»_ باشند، اما این کار باید به‌صراحت انجام شود.
- توابعی که ممکن است با یک «استثنا» شکست بخورند، به‌احتمال زیاد نسخه‌ای با مقدار بازگشتی پوچ‌پذیر دارند.
- یک نحوه‌ی نگارش ویژه و بسیار فشرده می‌کوشد بررسی و پاسخ به `null` را تا حد امکان آسان کند.

## ساختن متغیرهای پوچ‌پذیر

می‌توان یک نوع را با افزودن پسوند `?` [پوچ‌پذیر][ref-nullable-type] کرد (مثلاً `String?` به جای `String`).

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## عملگرها و توابع مفید

### [عملگر فراخوانی ایمن][ref-safe-call] `?.`

برای یک `String` غیرپوچ‌پذیر می‌توانیم ویژگی `.length` را به دست آوریم.

یک `String?` پوچ‌پذیر با همین نحوه‌ی نگارش خطا می‌دهد، اما استفاده از `?.length` امکان `null` بودن را در نظر می‌گیرد. نوع بازگشتی `Int?` است.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

همان‌طور که در خط آخر بالا دیدیم، `?.` با نوع‌های غیرپوچ‌پذیر هم کار می‌کند.

### [عملگر الویس][ref-elvis] `?:`

با گسترش ایده‌ی عملگر فراخوانی ایمن، [عملگر الویس][wiki-elvis] به ما اجازه می‌دهد به جای `null` یک مقدار پیش‌فرض بدهیم.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### [عملگر تأیید غیرپوچ بودن][ref-not-null] `!!`

با این عملگر، وقتی برنامه‌نویس مطمئن باشد، نوع پوچ‌پذیر به‌زور به‌عنوان غیرپوچ در نظر گرفته می‌شود. شاید ما گاهی منطق برنامه را بهتر از یک کامپایلر بیش‌ازحد محتاط می‌فهمیم؟

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

حالا مسئولیت بر عهده‌ی خودمان است: اگر `b` هنوز `null` باشد، یک `NullPointerException` می‌گیریم.

### [تابع `let`][ref-let] `?.let`

اگر بخواهیم یک عنصر پوچ‌پذیر را به یک «بلوک کد» بدهیم، می‌توانیم بررسی‌های مشخصی برای `null` انجام دهیم: `if (item != null) { do something }`.

استفاده از `item?.let { do something }` ساده‌تر و مرسوم‌تر است. بخش `do something` تنها زمانی اجرا می‌شود که `item` برابر `null` نباشد.

### توابعی از نوع `somethingOrNone()`

برخی توابع ممکن است شکست بخورند، مثلاً وقتی اندیسی نامعتبر در یک رشته یا فهرست درخواست می‌کنیم.

به جای پرتاب یک استثنا، می‌توانیم از [نسخه‌ی `...OrNull`][ref-elem-at-or-null] تابع استفاده کنیم تا (در این مورد) مقدار بازگشتی `Int?` بگیریم.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

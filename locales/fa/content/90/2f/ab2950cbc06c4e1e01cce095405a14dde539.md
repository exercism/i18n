# قرارداد

```sather
   spare_capacity(load : INT) : INT
      pre load >= 0 and load <= limit
      post result >= 0
   is
      return limit - load;
   end;
```

| بند | چه می‌گوید | اگر نقض شود، تقصیر کیست |
| --- | --- | --- |
| `pre` | آنچه هنگام ورود باید برقرار باشد | تقصیر فراخواننده |
| `post` | آنچه هنگام بازگشت برقرار است | تقصیر روال |

هر دو یک `BOOL` می‌گیرند و هر دو می‌توانند از آرگومان‌های روال و ویژگی‌های شیء استفاده کنند. `post` می‌تواند از `result` هم استفاده کند، همان مقداری که بازگردانده می‌شود.

## assert

در بدنه‌ی یک روال، `assert` چیزی را بیان می‌کند که در آن نقطه باید درست باشد:

```sather
      assert load <= limit;
```

این هم با همان کلیدی بررسی می‌شود که بقیه با آن بررسی می‌شوند.

## نامتغیرهای کلاس

یک کلاس می‌تواند چیزی را بیان کند که بین فراخوانی‌ها برای هر شیء از آن درست باشد:

```sather
   invariant : BOOL is
      return checks >= 0 and limit > 0;
   end;
```

هنگامی که بررسی روشن باشد، هنگام ورود به هر روال عمومی و خروج از آن بررسی می‌شود.

## روشن کردن آن

| کلید | چه چیزی را بررسی می‌کند |
| --- | --- |
| `-chk` | همه چیز: pre، post، assert، invariant، محدوده، حساب |
| `-chk_no` | هیچ چیز |

توجه کنید که `-chk_pre` به‌تنهایی بررسی پیش‌شرط را در این کامپایلر *روشن نمی‌کند*؛ چیزی که کار می‌کند `-chk` است. هر نقض، روال و خط منبع را چاپ می‌کند و برنامه را متوقف می‌کند. این یک استثنا نیست و `protect` آن را نمی‌گیرد.

رویه‌ی معمول این است که با `-chk` توسعه دهید و Test کنید و بدون آن عرضه کنید تا بررسی‌ها در برنامه‌ی عرضه‌شده هزینه‌ای نداشته باشند. اما این کار تنها زمانی به‌صرفه است که Testها واقعاً آن مسیرها را اجرا کنند.

## چه چیزی یک قرارداد خوب می‌سازد

بگویید روال به چه چیزی نیاز دارد، نه اینکه چطور کار می‌کند:

```sather
   pre load >= 0 and load <= limit        -- yes
   pre load /= 47                         -- what?
```

یک `post` که بدنه را دوباره تکرار می‌کند، چیزی به کسی یاد نمی‌دهد:

```sather
   post result = limit - load             -- says the body twice
   post result >= 0                       -- says something worth knowing
```

## وراثت

یک زیرنوع می‌تواند یک `pre` را تضعیف کند و یک `post` را تقویت کند (بیشتر بپذیرد، بیشتر وعده بدهد)، اما هرگز برعکس آن، وگرنه کدی که برای اَبَرنوع نوشته شده از کار می‌افتد. این همان قاعده‌ای است که قراردادها برای قابل‌بررسی کردنش وجود دارند.

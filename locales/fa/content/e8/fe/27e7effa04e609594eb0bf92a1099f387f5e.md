# مقدمه

نوع‌های Elm امکان استفاده از نوع‌های جنریک را فراهم می‌کنند که معمولاً به انعطاف‌پذیری یک رابط می‌افزایند.
برای مثال، نوع `Maybe a` می‌تواند مقداری از هر نوعی را در خود نگه دارد.

```elm
type Maybe a = Nothing | Just a
```

توجه کنید که در مثال بالا، پارامتر نوع `a` در هر دو طرف علامت تساوی `=` استفاده شده است.
می‌گوییم که `a` به داده‌ای درون تعریف نوع مقید شده است.

## تکنیک نوع شبح

اما در بعضی موارد، پارامتر نوع فقط در سمت چپ معادله ظاهر می‌شود.

```elm
type Distance unit = Distance Float
```

در تعریف `Distance` در بالا، `unit` یک پارامتر نوع آزاد است و به هیچ داده‌ای در نوع مقید نشده است.
به این نوع، **نوع شبح** هم می‌توان گفت.

وقتی بخواهیم محدودیت‌هایی را در زمان کامپایل اعمال کنیم، به‌طرز شگفت‌آوری مفید است.
برای مثال، می‌خواهیم مطمئن شویم که فقط فاصله‌هایی با واحد یکسان را با هم جمع می‌کنیم.

```elm
-- Distance is an opaque type, since the module does not expose its variants.
-- This means that users may only use the functions meter, foot and add to manipulate distances.
module Distance exposing (Distance, Meter, Foot, meter, foot, add)

-- The Distance type has a phantom type 'unit'.
type Distance unit = Distance Float

-- We define two types that will be used in place
-- of the phantom type 'unit' in our constructor functions.
type Meter = Meter
type Foot = Foot

-- Constructor for Meter
meter : Distance Meter
meter = Distance 1.0

-- Constructor for Foot
foot : Distance Foot
foot = Distance 0.3048

-- The add function cannot take two parameters of different types.
-- So we cannot add meters and feet by mistake.
add : Distance unit -> Distance unit -> Distance unit
add (Distance d1) (Distance d2) = Distance (d1 + d2)
```

کدی که بیرون از آن ماژول است، نمی‌تواند به داخل نوع `Distance` دسترسی داشته باشد.
کاربران می‌توانند دو `Distance Meter` را جمع کنند، اما نمی‌توانند یک `Distance Meter` را با یک `Distance Foot` جمع کنند.

```elm
import Distance exposing (Distance)

-- Compiles
twoMeters = Distance.add Distance.meter Distance.meter

-- Does not compile
errDist = Distance.add Distance.meter Distance.foot
```

## رکوردهای قابل توسعه به‌عنوان نوع شبح

هیچ محدودیتی در اینکه کدام نوع‌ها می‌توانند شبح باشند وجود ندارد و از نوع‌های رکورد هم می‌توان استفاده کرد.
رکوردها وقتی به‌عنوان نوع شبح به کار می‌روند، می‌توانند محدودیت‌های پیچیده‌ای را بیان کنند که می‌توانند هنگام عبور از توابع تغییر کنند.

بیایید یک واحد فاصله‌ی جدید به اسم `LegoBlock` را درون ماژول `Distance` اضافه کنیم.
بلوک‌های فیزیکی، چون اشیایی استانداردشده هستند، همیشه دو ویژگی دارند: فاصله‌هایشان غیرکسری و غیرمنفی است.

```elm
type LegoBlock = LegoBlock

fourStuds : Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
fourStuds = Distance 4.0
```

`nonFractional` و `nonNegative` فیلدهای رکوردی هستند که بیرون از یک آرگومان نوع وجود ندارد، پس مناسب است که به آن‌ها نوع `()` را بدهیم؛ این نوع، __نوع واحد__ نام دارد و هیچ اطلاعاتی جز این که وجود دارد، در خود نگه نمی‌دارد.

البته به دست آوردن فاصله‌های دلخواه `LegoBlock` ممکن است، مثلاً بعد از محاسبه‌ی تفاضل یا نسبت فاصله‌ها.

```elm
negativeStud : Distance { properties | unit: LegoBlock, nonFractional : () }
negativeStud = Distance -1.0

threeFiddyStud : Distance { properties | unit: LegoBlock, nonNegative : () }
threeFiddyStud = Distance 3.50

crazyStud : Distance { properties | unit: LegoBlock }
crazyStud = Distance -13.37
```

همه‌ی مقادیر بالا معتبرند و کامپایل می‌شوند، اما ما به مقادیری مثل `fourStuds` که هم ویژگی `nonFractional` و هم `nonNegative` را دارند علاقه‌ی ویژه‌ای داریم، چون نماینده‌ی بلوک‌های فیزیکی‌ای هستند که می‌توان آن‌ها را با هم ترکیب کرد.

```elm
combineLegoBlocks
  :  Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
  -> Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
  -> Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
combineLegoBlocks = add
```

بیایید چند تابع اضافه کنیم تا کاربران بتوانند فاصله‌های `LegoBlock` را بسازند و پالایش کنند.

```elm
newLegoBlock : Float -> Distance { properties | unit: LegoBlock }
newLegoBlock dist = Distance dist

floorDistance : Distance properties -> Distance { properties | nonFractional : () }
floorDistance (Distance dist) = Distance (toFloat (floor dist))

ceilingDistance : Distance properties -> Distance { properties | nonFractional : () }
ceilingDistance (Distance dist) = Distance (toFloat (ceiling dist))

absDistance : Distance properties -> Distance { properties | nonNegative : () }
absDistance (Distance dist) = Distance (abs dist)
```

توجه کنید که `floorDistance`، `ceilingDistance` و `absDistance` می‌توانند واحدهایی غیر از `LegoBlock` را هم بپردازند و به طور کلی هیچ فرضی درباره‌ی ویژگی‌های ورودی نمی‌کنند؛ آن‌ها فقط تضمین می‌کنند که خروجی ویژگی مشخصی داشته باشد، یا `nonFractional` یا `nonNegative`.

بیایید به چند نتیجه نگاه کنیم.

```elm
import Distance exposing (Distance)

-- Compiles
distance1 = combineLegoBlocks fourStuds fourStuds

-- Does not compile
distance2 = combineLegoBlocks fourStuds threeFiddyStud

-- Compiles
distance3 = combineLegoBlocks fourStuds (floorDistance threeFiddyStud)

-- Does not compile
distance4 = combineLegoBlocks fourStuds negativeStud

-- Compiles
distance5 = combineLegoBlocks fourStuds (absDistance negativeStud)

-- Does not compile
distance6 = combineLegoBlocks fourStuds crazyStud

-- Compiles
distance7 = combineLegoBlocks fourStuds (floorDistance (absDistance crazyStud))

-- Compiles
distance8 = combineLegoBlocks fourStuds (ceilingDistance (absDistance crazyStud))
```

به طور کلی، `floorDistance` و `ceilingDistance` نتایج متفاوتی می‌دهند، اما تضمین‌های یکسانی ارائه می‌کنند.
این نقطه‌ی قوت تکنیک نوع شبح است: فراهم کردن گزینه‌های انعطاف‌پذیر برای کاربران و در همان حال حفظ تضمین‌های قوی.

# راهنمای سبک Rexx

این راهنما سبکی را توصیف می‌کند که برای استفاده در فایل‌های test و مثال تمرین‌های ترک Rexx در نظر گرفته شده است.

## استاندارد Rexx

code باید با سطح 5.0 زبان Rexx سازگار باشد.

افزونه‌های Regina Rexx و توابع استاندارد SAA برای دسترسی به کتابخانه‌ی خارجی را می‌توان به کار برد.

نباید از افزونه‌های AREXX و روتین‌های دستکاری بافر CMS استفاده کرد.

## پلتفرم

محیط test زمان اجرا مبتنی بر Linux است؛ بنابراین در فراخوانی‌های دستور ADDRESS فقط می‌توان از فرمان‌هایی استفاده کرد که در آن محیط موجودند. این موارد باید در توضیحات code به‌وضوح برجسته شوند.

## اسم‌ها

### دستورها

دستورها (کلمات رزروشده) باید با **_حروف کوچک_** نوشته شوند. بنابراین، نمونه‌ی زیر با توصیه‌های این راهنما سازگار است:

```rexx
do while input \= ''
  parse var input char +1 input
  say char
end
```

در حالی که هیچ‌کدام از دو مورد زیر سازگار نیستند و بنابراین توصیه نمی‌شوند:

```rexx
/* *** Not recommended *** */
Do While input \= ''
  Parse Var input char +1 input
  Say char
End
```

و:

```rexx
/* *** Not recommended *** */
DO WHILE input \= ''
  PARSE VAR input char +1 input
  SAY char
END
```

### توابع درون‌ساخت (BIFs)

BIFها باید با **_حروف بزرگ_** نوشته شوند، همان‌طور که اینجا نشان داده شده:

```rexx
input = 'ABCDE'
say 'Length of input is' LENGTH(input)
say 'First letter of input is' SUBSTR(input, 1, 1)
```

### برچسب‌ها (توابع تعریف‌شده توسط کاربر)

اسم برچسب‌ها باید به صورت **_Pascal case_** باشد، همان‌طور که اینجا نشان داده شده:

```rexx
greeting = MyFuncSayHello()
say greeting

exit 0

MyFuncSayHello : procedure
  hello = 'Hello there!'
return hello
```

### متغیرها

اسم متغیرها باید با حرف **_کوچک_** شروع شود، بنابراین متغیرهای تک‌کلمه‌ای با حروف کوچک خواهند بود.

متغیرهای چندکلمه‌ای را می‌توان با **_camel case_** یا **_snake case_** بیان کرد.

قراردادی که برای این ترک برگزیده شده این است که _camel case برای بیشتر متغیرها_ به کار رود و snake case برای متغیرهای test نگه داشته شود. متغیرهایی که به عنوان ثابت در نظر گرفته می‌شوند می‌توانند به‌صورت اختیاری با حروف بزرگ نوشته شوند.

```rexx
input = 'ABCDE'
i = 0

personName = 'Alice'
test_person_description = 'Brown hair, blue eyes'

TRUE = 1
PI_CONSTANT = 3.14159
```

## لیترال‌ها

رشته‌ها را می‌توان با گیومه‌ی تک یا دوتایی، به‌ترتیب **`'`** و **`"`**، نشان داد. موارد زیر معادل هم هستند:

```rexx
say "Hello, world!"

say 'Hello, world!'
```

هرکدام را می‌توان بدون نیاز به نویسه‌ی گریز داخل دیگری جاسازی کرد:

```rexx
say "Please don't do that as it's wrong."

say 'He said, "Please sir, may I have more?".'
```

مگر اینکه رشته‌ها شامل گیومه‌های جاسازی‌شده باشند و در نتیجه نیاز به ترکیب گیومه‌ها باشد، ترجیح این است که رشته‌ها با **_گیومه‌ی تک_** نشان داده شوند.

### رشته‌های هگزادسیمال و دودویی

مقادیر دودویی و هگزادسیمال را می‌توان به‌ترتیب با افزودن **`B`** یا **`X`** به یک رشته نمایش داد. مثال‌ها:

```rexx
hexvalue = "0A"X

binvalue = "00001010"B
```

توصیه می‌شود چنین مقادیری با **_گیومه‌ی دوتایی_** محدود شوند.

همراه با توصیه‌ی پیشین درباره‌ی استفاده از گیومه‌ی تک برای نمایش رشته‌های ساده، این قرارداد باید شناسایی رشته‌های دودویی و هگزادسیمال را در یک code base آسان‌تر کند.

### پایان‌دهنده‌ی خط جدید
در بسیاری از زبان‌های متأثر از UNIX یا C، از لیترال **_`\n`_** به عنوان پایان‌دهنده‌ی **_خط جدید_** استفاده می‌شود. این کاربرد رواج گسترده‌ای دارد و چندین تمرین در این ترک به استفاده و دستکاری رشته‌هایی با این پایان‌دهنده می‌پردازند.

Rexx از این پایان‌دهنده پشتیبانی نمی‌کند و **_`\`_** (یا هر نویسه‌ی دیگری) را نیز به عنوان نویسه‌ی گریز پشتیبانی نمی‌کند.

معادل Rexx نویسه‌ی خط جدید یک مقدار هگزادسیمال (وابسته به پلتفرم) است؛ در پلتفرم‌های برگرفته از UNIX چنین است:

**_`"0A"X`_**

معادل Rexx رشته‌ی زیر، با خط جدیدهای جاسازی‌شده (با استفاده از bash):

```bash
printf "I have\nthree embedded\nnewlines.\n"
```

چنین است:

```rexx
say 'I have' || "0A"X || 'three embedded' || "0A"X || 'newlines.' || "0A"X
```

تمرین‌های این ترک فقط زمانی **_`\n`_** را به **_`"0A"X`_** تبدیل می‌کنند که در رشته‌ای برای نمایش در ترمینال لازم باشد. در غیر این صورت، رشته‌ی **_`\n`_** صرفاً به عنوان یک خط جدید منطقی تفسیر می‌شود.

## توصیه‌های سبکی دیگر

تورفتگی می‌تواند دو، سه یا چهار نویسه‌ی فاصله باشد، هرچند تورفتگی _دو نویسه‌ای_ و یکدستی در تورفتگی ترجیح داده می‌شود.

آخرین دستور **_return_** در یک تابع باید با اسم برچسب هم‌تراز باشد تا بدین‌سان پایان آن تابع به‌روشنی مشخص شود و باید _همیشه_ مقداری برگرداند.

عملگر NOT «منطقی» را می‌توان با چند نماد مختلف نشان داد. نماد ترجیح‌داده‌شده در این ترک **`\`** است و برای حفظ سازگاری با این کاربرد، عملگر رابطه‌ای «نامساوی» باید **`\=`** باشد.

مقادیر منطقی **`false`** و **`true`** به‌ترتیب با **`0`** و **`1`** نمایش داده می‌شوند. هیچ لیترال از پیش تعریف‌شده‌ای برای این مقادیر وجود ندارد.

وضعیت‌های خطا با مقادیر بازگشتی نشان داده می‌شوند؛ یا رشته‌ی خالی **`''`** یا **`-1`** بسته به بافت، وضعیت خطا را مشخص می‌کند.

## چیدمان فایل test

هر تمرین یک فایل test واحد دارد که در پوشه‌ی سطح بالای تمرین قرار می‌گیرد و چنین نام‌گذاری می‌شود: `<exercise>-check.rexx`

با پیروی از این قرارداد، فایل test تمرین `acronym` چنین نامی می‌گیرد: `acronym-check.rexx`

فایل test هر تمرین به شکلی آزاد ولی مشخص چیده می‌شود تا هم به یادگیرندگان در فهم الزامات تمرین کمک کند و هم کار مشارکت‌کننده را در پیاده‌سازی یا گسترش testها آسان‌تر سازد.

آنچه در ادامه می‌آید زیرمجموعه‌ای از فایل test تمرین `acronym` است:

```rexx
/* Unit Test Runner: t-rexx */
function = 'Abbreviate'
context('Checking the' function 'function')

/* Unit tests */
check('basic' function||'("Portable Network Graphics")',,
      function||'("Portable Network Graphics")',, 'to be', 'PNG')

check('lowercase words' function||'("Ruby on Rails")',,
      function||'("Ruby on Rails")',, 'to be', 'ROR')
```

این فایل به دو بخش منطقی تقسیم می‌شود که هرکدام با یک خط کامنت مشخص می‌شوند.

بخش اول اسم **_تابع تحت test_** (اینجا تابع `Abbreviate`) را به متغیر `function` نسبت می‌دهد. این اسم متغیر توصیفی اما دلبخواه است و در ادامه‌ی فایل هرجا که به اسم تابع تحت test نیاز باشد به آن ارجاع داده می‌شود.

در این بخش نیز فراخوانی تابع `context` هست که هدفش خودش پیداست.

بخش بعدی شامل testهای واحد است. هر فراخوانی تابع `check` یک test واحد است. پارامترهای مورد انتظار:

```rexx
check(<test description>,
      <function invocation>,
      [<actual result variable>],
      <test comparator>,
      <expected result>)
```

**\<test description>** رشته‌ای است که هنگام اجرای test تولید می‌شود. برای اینکه تا حد ممکن توصیفی باشد، توصیه می‌شود رشته‌ای متشکل از اسم تابع تحت test و آرگومان‌های داده‌شده به آن، مطابق مثال، به کار رود.

**\<function invocation>** همان فراخوانی واقعی تابع است، پس مقدار بازگشتی‌اش برای مقایسه‌ی test به `check` داده می‌شود.

**\<actual result variable>** پارامتری اختیاری است و در صورت استفاده، اسم متغیری است که مقدار مورد استفاده برای مقایسه‌ی test را در خود دارد.

دلیل استفاده از آن این است که بررسی نتیجه‌هایی _برگرفته از_ مقدار بازگشتی تابع تحت test را ممکن می‌کند، نه خود مقدار بازگشتی. مثال آشکار آن جایی است که مقدار بازگشتی رشته‌ای چندکیلوبایتی باشد، همان‌طور که نشان داده شده:

```rexx
expected_length = LENGTH(FUT(...))

check('...', FUT(...), expected_length, 'to be', 50)
```

توجه کنید که آرگومان \<function invocation> همچنان باید ارسال شود.

**\<test comparator>** رشته‌ای است که نوع مقایسه‌ی مورد انجام را توصیف می‌کند. در بیشتر موارد این همان رشته‌ی 'to be' است که مقایسه برای برابری را درخواست می‌کند. برای سایر گزینه‌های مقایسه به مستندات چارچوب test واحد مراجعه کنید.

**\<expected result>** به‌وضوح مقداری است که نتیجه‌ی واقعی با آن مقایسه می‌شود.

متغیرها را می‌توان آزادانه در فایل test تعریف کرد (طبعاً پیش از استفاده) و به جای لیترال‌ها، به عنوان آرگومان‌های `check` به کار برد.

# مقدمه

## افزودن زمینه به خطاها

ما در [مفهوم خطا][concept-errors] به بررسی مدیریت پایه‌ی خطا در Go پرداختیم.
همان‌طور که آنجا یاد گرفتید، خطاها به‌طور پیش‌فرض stack trace را با خود حمل نمی‌کنند.
همین موضوع حیاتی می‌کند که مطمئن شوید خود خطا اطلاعات کافی برای شناسایی مشکل را در خود دارد.

اگر می‌خواستیم با ابزارهایی که تا حالا می‌شناسیم اطلاعاتی را به یک خطای موجود اضافه کنیم، می‌توانستیم چیزی شبیه این بنویسیم تا خطای تازه‌ای با متن ترکیب‌شده‌ی خطای اصلی و اطلاعات اضافی بسازیم:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

خوشبختانه، بسته‌ی `fmt` از کتابخانه‌ی استاندارد نسخه‌ی کوتاه‌شده‌ای از این کار را در قالب تابع `Errorf` دارد.
این به شما اجازه می‌دهد، مثلاً، به‌سادگی اطلاعاتی را درباره‌ی زمینه‌ای که خطا در آن رخ داده است اضافه کنید.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

اغلب این شیوه‌ی افزودن اطلاعات به خطا به‌قدر کافی خوب است، اما مواردی هست که می‌خواهید به مصرف‌کننده‌ی خطایتان اجازه دهید خطای اصلی زیرین را بررسی یا بازیابی کند.
افزودن زمینه به شکلی که این امکان را بدهد، در Go «بسته‌بندی خطا» نامیده می‌شود.

## بسته‌بندی خطاها و بررسی خطاهای sentinel

بسته‌بندی خطا با تغییری بسیار کوچک در کدی که بالا دیدیم انجام می‌شود.
برای بسته‌بندی یک خطا، باید فعل قالب‌بندی `%w` را به‌جای `%v` به کار ببرید.
در پشت‌صحنه، این کار مطمئن می‌شود که خطای حاصل متد `Unwrap` را پیاده‌سازی می‌کند که خطای اصلی را برمی‌گرداند.
به همین دلیل، می‌توان از `errors.Is` استفاده کرد تا بررسی شود آیا خطای sentinel خاصی جایی در «زنجیره‌ی خطا» ظاهر می‌شود یا نه.
این کار را با فراخوانی مخفیانه و مکرر `Unwrap` انجام می‌دهد تا وقتی که خطای مورد نظر پیدا شود یا زنجیره به پایان برسد.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

روش خوب این است که به‌طور پیش‌فرض از `%v` استفاده کنید و تنها وقتی از `%w` استفاده کنید که صراحتاً می‌خواهید به مصرف‌کننده‌تان اجازه‌ی دسترسی به یک خطای زیرین را بدهید ([راهنمای سبک Go گوگل][google-go-styleguide]).

اگر در موقعیتی قرار گرفتید که می‌خواهید یک خطای sentinel را بررسی کنید اما صراحتاً نمی‌خواهید آن را باز کنید، می‌توانید به‌جای `errors.Is` از `==` استفاده کنید.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

کار کردن با `errors.Is` به‌طور پیش‌فرض اشکالی ندارد، اما همیشه باید آگاه باشید که این یعنی کل زنجیره‌ی خطا جست‌وجو خواهد شد.

## بررسی انواع خطای (سفارشی)

معادلی برای `errors.Is` وجود دارد که امکان می‌دهد خطایی با نوعی خاص را از زنجیره‌ی خطا بررسی و بازیابی کنید.
تابع این کار `errors.As` است و درست مانند `errors.Is` نوع خطای داده‌شده را در سراسر زنجیره جست‌وجو می‌کند.
`errors.As` تنها زمانی خطای پیدا‌شده‌ی منطبق با آن نوع را استخراج می‌کند تا بتوانید بیشتر با آن کار کنید، مثلاً فیلدهای مشخصی را بازیابی کنید.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
مراقب نحوه‌ی نگارش مربوط به اشاره‌گرهای بالا باشید.
کد تنها زمانی درست کار و کامپایل می‌شود که `customError` دقیقاً همان نوعی را داشته باشد که واسط خطا را پیاده‌سازی می‌کند.
در مورد ما، این `*MyCustomError` است (یک [اشاره‌گر][concept-pointers] به `MyCustomError`)، نه خود `MyCustomError`.

علاوه بر این، آرگومان دوم باید اشاره‌گری به متغیر خطا باشد.
چون خطای ما از قبل یک اشاره‌گر است، آنچه به `errors.As` می‌فرستیم اشاره‌گری به یک اشاره‌گر (به `MyCustomError`) است.
تنها وقتی این چیدمان درست باشد، Go می‌تواند متغیر را با خطای پیدا‌شده پر کند.
~~~~

مثل قبل، اگر هنگام فراخوانی `Errorf` از `%v` استفاده می‌شد، `errors.As` نوع خطا را پیدا نمی‌کرد.

اگر به دلیلی نمی‌خواهید بازگشایی کنید، می‌توان به‌جای آن از تأیید نوع استفاده کرد (معادل `==` بالا).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

اگر خطا بسته‌بندی شده باشد، تأیید نوع نمی‌تواند نوع خطا را شناسایی کند.

## امکان باز کردن خطاهای انواع سفارشی

گاهی فقط بسته‌بندی یک خطا با مقداری متن اضافی کافی نیست.
در عوض می‌توانید یک نوع خطای سفارشی بسازید که خطای اصلی و داده‌ی ساخت‌یافته‌ی اضافی‌ای را که می‌خواهید بیفزایید در خود نگه دارد.
اگر می‌خواهید امکان بازگشایی برای نوع خطای شما فراهم باشد، تنها کاری که باید بکنید این است که به‌صورت دستی یک متد `Unwrap() error` اضافه کنید تا واسط `Unwrap` برآورده شود.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

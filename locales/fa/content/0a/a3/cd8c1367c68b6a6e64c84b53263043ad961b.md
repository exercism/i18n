# درباره

## خطا در `jq`

`jq` دو دسته‌ی کلی خطا گزارش می‌کند:

1. **خطاهای زمان کامپایل**: خود برنامه نامعتبر است: خطا در نحوه‌ی نگارش، ارجاع به توابع یا متغیرهای تعریف‌نشده و از این قبیل.
   `jq` از اجرای برنامه به‌کل خودداری می‌کند.

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **خطاهای زمان اجرا**: برنامه معتبر است، اما هنگام پردازش یک مقدار چیزی اشتباه پیش می‌رود: اندیس‌گذاری روی یک عدد با یک رشته، تجزیه‌ی متن JSON نامعتبر با `fromjson`، فراخوانی یک تابع با آرگومان‌هایی از نوع نادرست و از این قبیل.

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

این مفهوم درباره‌ی **خطاهای زمان اجرا** است: چطور آن‌ها را ایجاد کنیم، چطور بگیریم و چطور متوقفشان کنیم.

خطای زمان اجرای گرفته‌نشده باعث می‌شود `jq` پیامی را در «خطای استاندارد» چاپ کند و با وضعیت `5` خارج شود.

## ایجاد خطا: `error` و `error(message)`

فیلتر [`error`][man-error] یک خطا ایجاد می‌کند.

- `error` خطایی ایجاد می‌کند که مقدارش **مقدار ورودی** است.
- `error(message)` خطایی ایجاد می‌کند که مقدارش نتیجه‌ی `message` است.

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
مقدار خطا می‌تواند _هر_ مقدار JSON باشد، نه فقط یک رشته.
ایجاد خطاهای ساختاریافته به گرداننده‌ی `catch` اجازه می‌دهد بر اساس محتوای خطا تصمیم بگیرد.

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

اگر مقدار خطای غیررشته‌ای گرفته نشود، `jq` آن را به‌صورت JSON چاپ می‌کند و با `(not a string)` مشخص می‌کند.

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## گرفتن خطا: `try` و `catch`

خطاها را می‌توان با [`try EXP catch HANDLER`][man-try-catch] گرفت.
عبارت اول اجرا می‌شود؛ اگر خطایی ایجاد کند، عبارت `HANDLER` **با مقدار خطا به‌عنوان ورودی‌اش** اجرا می‌شود.
خروجی گرداننده همان‌طور چاپ می‌شود که اگر خروجی عبارت امتحان‌شده بود.

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

شکل کوتاه‌تر `try EXP` معادل `try EXP catch empty` است: خطا دور ریخته می‌شود و هیچ خروجی‌ای تولید نمی‌شود.

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
یک خطا **بقیه‌ی جریان** را درون `try` متوقف می‌کند.
مقادیری که تا آن لحظه تولید شده‌اند حفظ می‌شوند، اما هیچ‌چیز بعد از خطا ارزیابی نمی‌شود.

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

گرداننده می‌تواند خطای تازه‌ای ایجاد کند، یا خطای اصلی را با یک `error` ساده دوباره ایجاد کند؛ چون مقدار خطا همان ورودی گرداننده است، این کار آن را بدون تغییر منتشر می‌کند.

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## سرکوب خطا: عملگر `?`

عملگر [`?`][man-question-mark]، وقتی به شکل `EXP?` نوشته شود، کوتاه‌نوشتِ `try EXP` است.
عبارت شکست‌خورده را به عبارتی تبدیل می‌کند که به‌سادگی هیچ خروجی‌ای تولید نمی‌کند.

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

اغلب آن را چسبیده به عملگرهای اندیس‌گذاری می‌بینید:

- `.foo?` معادل `.["foo"]?` است
- `.[]?` فقط وقتی ورودی آرایه یا شیء باشد پیمایش می‌کند و در غیر این صورت خالی است

~~~~exercism/caution
`?` **هر** خطایی را سرکوب می‌کند، از جمله خطاهایی که پیش‌بینی نکرده‌اید.
`user.name?` وقتی `user` یک شیء نباشد، بی‌صدا هیچ تولید نمی‌کند و این می‌تواند مشکلات داده یا غلط‌های تایپی در برنامه‌تان را پنهان کند.
وقتی لازم است بدانید _که_ چیزی شکست خورده است، `try ... catch` را ترجیح دهید یا ورودی را به‌صراحت اعتبارسنجی کنید.
~~~~

## عملگر جایگزین `//`

برنامه‌نویسان گاهی انتظار دارند `a // b` وقتی `a` شکست می‌خورد، `b` را تولید کند.
این در نسخه‌های قدیمی `jq` درست بود، اما از `jq` 1.6 به بعد نه.
عملگر `//` خطاها را سرکوب نمی‌کند.
فقط وقتی `b` را جایگزین می‌کند که `a` هیچ مقداری تولید نکند، یا `false` یا `null` تولید کند؛ خطاهای درون `a` همچنان منتشر می‌شوند.

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

اگر برای خطاها جانشین می‌خواهید، از `try a catch b` استفاده کنید.

## عملگر جایگزین ساختارشکنی `?//`

عملگر [`?//`][man-question-mark-slash-slash] ساختارشکنی را با مدیریت خطا ترکیب می‌کند.
هر الگوی اتصال را به‌ترتیب امتحان می‌کند تا یکی موفق شود، و متغیرهایی که در گزینه‌های ناموفق اتصال یافته‌اند `null` می‌شوند.

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

اینجا الگوی اول انتظار دارد `c` یک _شیء_ با کلیدهای `d` و `e` باشد، در حالی که الگوی دوم انتظار دارد `c` یک _آرایه_ شامل چنین شیئی باشد.
اولین عنصر ورودی با الگوی اول اتصال می‌یابد؛ عنصر دوم در آن الگو شکست می‌خورد، پس الگوی دوم امتحان می‌شود.

این امکان را می‌دهد که یک برنامه، ورودی‌هایی با یکی از چند شکل ممکن را بدون نوشتن زنجیره‌های صریح `if type == ...` ساختارشکنی کند.

## متوقف کردن برنامه: `halt` و `halt_error`

گاهی واکنش درست به یک خطا این است که پردازش را به‌کل متوقف کنیم.

- [`halt`][man-halt] برنامه‌ی `jq` را بی‌درنگ و بدون خروجی بیشتر متوقف می‌کند؛ وضعیت خروج `0` است.
- [`halt_error`][man-halt-error] برنامه را متوقف می‌کند، **ورودی**اش را به‌صورت متن خام در خطای استاندارد چاپ می‌کند (بدون هیچ تزئینی، حتی بدون خط جدید) و با وضعیت داده‌شده خارج می‌شود؛ وضعیت پیش‌فرض `5` است.

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

توجه کنید که این فیلترها برنامه را بی‌درنگ متوقف می‌کنند، حتی اگر ورودی‌های بیشتری برای خواندن باقی مانده باشد.

### وضعیت‌های خروج

برای مرجع، `jq` از این وضعیت‌های خروج استفاده می‌کند:

| وضعیت | معنا                                             |
| :----: | ------------------------------------------------ |
| `0`    | موفقیت                                           |
| `2`    | خطای استفاده (گزینه‌های نادرست خط فرمان)           |
| `3`    | خطای زمان کامپایل                                |
| `5`    | خطای زمان اجرا (یا `halt_error` بدون آرگومان)     |

با گزینه‌ی `--exit-status` / `-e`، وضعیت در عوض بازتاب آخرین مقدار خروجی است: `0` برای `true` یا اعداد، `1` برای `false` یا `null`، `4` برای نبود خروجی.

## کمک‌کننده‌های debug

وقتی می‌خواهید رد یک خطا را پیدا کنید، این فیلترها کمک می‌کنند:

- [`debug`][man-debug] ورودی‌اش را بدون تغییر عبور می‌دهد، اما `["DEBUG:", <input>]` را در خطای استاندارد چاپ می‌کند.
  `debug(msgs)` هم `msgs` را به‌عنوان پیام‌های debug چاپ می‌کند.
- [`stderr`][man-stderr] ورودی‌اش را خام و فشرده در خطای استاندارد چاپ می‌کند.
- [`input_line_number`][man-input-line-number] شماره‌ی خطِ ورودی‌ای را که اکنون فیلتر می‌شود خروجی می‌دهد، که وقتی یک فایل شامل متن‌های JSON زیادی است و یکی از آن‌ها خراب است بسیار ارزشمند است.
- [`$__loc__`][man-loc] شیئی با کلیدهای `file` و `line` خروجی می‌دهد که محل قرارگیری خود در برنامه را توصیف می‌کند و می‌توان آن را در پیام‌های خطا گنجاند.

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

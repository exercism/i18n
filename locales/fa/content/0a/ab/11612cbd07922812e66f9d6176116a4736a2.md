# درباره

نوع‌های Elm امکان نوع‌های جنریک را فراهم می‌کنند که معمولاً انعطاف‌پذیری یک رابط را بیشتر می‌کنند.
برای نمونه، نوع `Maybe a` می‌تواند مقداری از هر نوعی را در خود نگه دارد.

```elm
type Maybe a = Nothing | Just a
```

توجه کنید که در مثال بالا، پارامتر نوع `a` در دو طرف علامت تساوی `=` به کار رفته است.
می‌گوییم که `a` به داده‌ای درون تعریف نوع مقید شده است.

## تکنیک نوع فانتوم

اما در برخی موارد، پارامتر نوع فقط در سمت چپ معادله ظاهر می‌شود.

```elm
type Distance unit = Distance Float
```

در تعریف `Distance` در بالا، `unit` یک پارامتر نوع آزاد است و به هیچ داده‌ای در نوع مقید نیست.
می‌توانیم این نوع را **«نوع فانتوم»** هم بنامیم.

وقتی می‌خواهیم محدودیت‌هایی را در زمان کامپایل اعمال کنیم، به‌طرز غافلگیرکننده‌ای مفید است.
برای نمونه، می‌خواهیم مطمئن شویم که فقط فاصله‌هایی با واحد یکسان را با هم جمع می‌کنیم.

```elm
-- Distance is an opaque type, since the module does not expose its variants.
-- This means that users may only use the functions meter, foot and add to manipulate distances.
module Distance exposing (Distance, Meter, Foot, meter, foot, add)

-- The Distance type has a phantom type 'unit'.
type Distance unit = Distance Float

-- We define two types that will be used in place
-- of the phantom type 'unit' in our constructor functions.
type Meter = Meter
type Foot = Foot

-- Constructor for Meter
meter : Distance Meter
meter = Distance 1.0

-- Constructor for Foot
foot : Distance Foot
foot = Distance 0.3048

-- The add function cannot take two parameters of different types.
-- So we cannot add meters and feet by mistake.
add : Distance unit -> Distance unit -> Distance unit
add (Distance d1) (Distance d2) = Distance (d1 + d2)
```

کدی که بیرون از آن ماژول باشد نمی‌تواند به درون نوع `Distance` دسترسی پیدا کند.
کاربران می‌توانند دو `Distance Meter` را با هم جمع کنند، اما نمی‌توانند یک `Distance Meter` را با یک `Distance Foot` جمع کنند.

```elm
import Distance exposing (Distance)

-- Compiles
twoMeters = Distance.add Distance.meter Distance.meter

-- Does not compile
errDist = Distance.add Distance.meter Distance.foot
```

## رکوردهای قابل توسعه به‌عنوان نوع فانتوم

هیچ محدودیتی وجود ندارد که کدام نوع‌ها می‌توانند فانتوم باشند و نوع‌های رکورد هم می‌توانند به کار روند.
رکوردهای Elm [قابل توسعه][extensible-records] هستند، یعنی می‌توانند فیلدهایی بیشتر از آنچه اعلام می‌کنند داشته باشند.
وقتی به‌عنوان نوع فانتوم به کار می‌روند، رکوردها می‌توانند محدودیت‌های پیچیده‌ای را بیان کنند که در گذر از توابع دگرگون می‌شوند.

بیایید واحد فاصله‌ی جدیدی به اسم `LegoBlock` درون ماژول `Distance` اضافه کنیم.
بلوک‌های فیزیکی، چون اشیایی قانون‌مند هستند، همیشه دو ویژگی دارند: فاصله‌شان کسری ندارد و منفی نیست.

```elm
type LegoBlock = LegoBlock

fourStuds : Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
fourStuds = Distance 4.0
```

`nonFractional` و `nonNegative` فیلدهای رکوردی هستند که بیرون از یک آرگومان نوع وجود ندارد؛ پس مناسب است که به آن‌ها نوع `()` را بدهیم، که __«نوع واحد»__ نام دارد و هیچ اطلاعاتی جز این که وجود دارد در خود نگه نمی‌دارد.

البته که به دست آوردن فاصله‌های دلخواه `LegoBlock` ممکن است، مثلاً بعد از محاسبه‌ی اختلاف یا نسبت فاصله‌ها.

```elm
negativeStud : Distance { properties | unit: LegoBlock, nonFractional : () }
negativeStud = Distance -1.0

threeFiddyStud : Distance { properties | unit: LegoBlock, nonNegative : () }
threeFiddyStud = Distance 3.50

crazyStud : Distance { properties | unit: LegoBlock }
crazyStud = Distance -13.37
```

همه‌ی مقدارهای بالا معتبرند و کامپایل می‌شوند، اما ما به مقدارهایی مانند `fourStuds` که هم ویژگی `nonFractional` و هم ویژگی `nonNegative` را دارند توجه ویژه‌ای داریم، زیرا آن‌ها نماینده‌ی بلوک‌های فیزیکی‌ای هستند که می‌توان آن‌ها را با هم ترکیب کرد

```elm
combineLegoBlocks
  :  Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
  -> Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
  -> Distance { properties | unit: LegoBlock, nonFractional : (), nonNegative: () }
combineLegoBlocks = add
```

بیایید چند تابع اضافه کنیم تا کاربران بتوانند فاصله‌های `LegoBlock` را بسازند و بپالایند.

```elm
newLegoBlock : Float -> Distance { properties | unit: LegoBlock }
newLegoBlock dist = Distance dist

floorDistance : Distance properties -> Distance { properties | nonFractional : () }
floorDistance (Distance dist) = Distance (toFloat (floor dist))

ceilingDistance : Distance properties -> Distance { properties | nonFractional : () }
ceilingDistance (Distance dist) = Distance (toFloat (ceiling dist))

absDistance : Distance properties -> Distance { properties | nonNegative : () }
absDistance (Distance dist) = Distance (abs dist)
```

توجه کنید که `floorDistance`، `ceilingDistance` و `absDistance` می‌توانند واحدهایی جز `LegoBlock` را هم پردازش کنند و به‌طور کلی هیچ فرضی درباره‌ی ویژگی‌های ورودی نمی‌کنند؛ آن‌ها فقط تضمین می‌کنند که خروجی ویژگی مشخصی داشته باشد، یا `nonFractional` یا `nonNegative`.

بیایید چند نمونه از نتیجه‌ها را ببینیم.

```elm
import Distance exposing (Distance)

-- Compiles
distance1 = combineLegoBlocks fourStuds fourStuds

-- Does not compile
distance2 = combineLegoBlocks fourStuds threeFiddyStud

-- Compiles
distance3 = combineLegoBlocks fourStuds (floorDistance threeFiddyStud)

-- Does not compile
distance4 = combineLegoBlocks fourStuds negativeStud

-- Compiles
distance5 = combineLegoBlocks fourStuds (absDistance negativeStud)

-- Does not compile
distance6 = combineLegoBlocks fourStuds crazyStud

-- Compiles
distance7 = combineLegoBlocks fourStuds (floorDistance (absDistance crazyStud))

-- Compiles
distance8 = combineLegoBlocks fourStuds (ceilingDistance (absDistance crazyStud))
```

به‌طور کلی، `floorDistance` و `ceilingDistance` نتیجه‌های متفاوتی می‌دهند، اما تضمین‌های یکسانی دارند.
این نقطه‌قوت تکنیک نوع فانتوم است: فراهم کردن گزینه‌های انعطاف‌پذیر برای کاربران، در حالی که تضمین‌های محکم حفظ می‌شوند.

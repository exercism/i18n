# مقدمه

تا اینجا، سرفصل چیز زیادی درباره‌ی نوع‌ها نگفته است، اما واضح است که در Julia وجود دارند:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

ما هیچ‌وقت نوع‌ها را مشخص نکردیم، اما Julia به‌هرحال آن‌ها را تعیین کرد.

1. Julia دارای `types` است و این‌ها در طراحی آن نقشی محوری دارند.
2. Julia معمولاً می‌تواند نوع را با استفاده از `Type Inference` «حدس» بزند.

کامپایلر JIT تمام کد را بررسی می‌کند، می‌بیند که یک متغیر چگونه استفاده می‌شود، و یک نوع پیش‌فرض مناسب و سازگار با آن کاربرد را _استنتاج_ می‌کند.

## ارتقای نوع

در مفاهیم پیشین مثال‌های زیادی وجود داشته که انواع عددی را به یک شکل واحد تبدیل می‌کنند، و از ساده‌ترین عملیات حسابی آغاز می‌شود.

```julia-repl
julia> 2 + 1.3
3.3
```

ما یک عدد صحیح (Int64) و یک عدد اعشاری (Float64) را جمع کردیم و نتیجه‌ی Float64 گرفتیم. به‌طور مشابه:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

در حالت بالا، یک تاپل نوع هر عنصر را حفظ کرد، اما تبدیل آن به یک بردار همه‌ی آن‌ها را به یک Float64 یکدست تغییر داد.

کامپایلر Julia می‌داند که کدام تبدیل‌های نوع امکان‌پذیرند: تبدیل عدد صحیح به اعشاری مشکلی ندارد، اما تبدیل اعشاری به صحیح دقت را از دست می‌دهد و در نتیجه `InexactError` ایجاد می‌شود.
ارتقای نوع همه‌ی مقادیر موجود در عبارت را به یک نوع مشترک تبدیل می‌کند، نوعی که به‌اندازه‌ی کافی انعطاف‌پذیر باشد تا با همه‌ی ورودی‌ها سازگار باشد.

## تخصیص نوع

تکیه بر استنتاج نوع برای حل تمرین‌های ساده‌ی آموزشی مشکلی ندارد، اما برای برنامه‌های بزرگ‌تر احتمالاً به کنترل دقیق‌تری نیاز خواهید داشت.

در بیشتر پردازنده‌های مدرن، یک عدد صحیح به‌طور پیش‌فرض `Int64` است.
در مفهوم [`Numbers`][numbers] دیدیم که یک مقدار را می‌توان به یک نوع خاص و غیرپیش‌فرض تبدیل کرد.

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

اما متغیر `x` هنوز می‌تواند به یک نوع متفاوت دوباره تخصیص داده شود:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

این همان `type instability` است، که یعنی:

- در اسکریپت‌های کوچک بسیار راحت است.
- در برنامه‌های بزرگ‌تر برای کارایی و پایایی مضر است.

در عوض، می‌توانیم نوع `x` را با استفاده از عملگر `::` تعیین کنیم:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

اکنون `y` از نوع `Int16` است و همیشه خواهد بود.
بنابراین، کامپایلر می‌داند که چند بایت برای آن رزرو کند، و می‌تواند بقیه‌ی کد را طوری بهینه‌سازی کند که بر یک نوع پایدار تکیه داشته باشد.
از این نظر، این متغیر کمابیش شبیه متغیرهای یک زبان با نوع‌دهی ایستا مانند C است.

## تأیید نوع

تخصیص نوع، که در بالا توصیف شد، در سمت چپ یک انتساب متغیر به کار می‌رود تا نوع آن متغیر را محدود کند.

استفاده از عملگر `::` همراه با یک مقدار، یا چیزی که به یک مقدار ارزیابی می‌شود، عموماً یک _ادعا_ است بر اینکه آن مقدار باید از این نوع باشد، وگرنه باید یک خطا پرتاب شود.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

معمولاً ممکن است این کار با مقدار بازگشتی یک تابع به کار رود، به‌عنوان یک بررسی ساده و نهایی بر اینکه تابع همان‌طور که انتظار می‌رفت رفتار کرده است.

## سلسله‌مراتب نوع

`Int64`، `Int16`، `String`، `Char`: این نوع‌ها _«از کجا می‌آیند»_؟

در بسیاری از زبان‌های شیءگرا (OO)، هر نوع یک کلاس است، زیرکلاس‌سازی آن‌ها را در یک سلسله‌مراتب کلاس مرتب می‌کند، و متدهای کلاس رفتارها را تعریف می‌کنند.

Java و Ruby نمونه‌های آشکاری از این الگو هستند، اما حتی Python هم در باطن مشابه است.

***Julia هیچ کلاسی ندارد.***

دلیل مستندشده این است که ویژگی‌های شیءگرا با کامپایلر JIT تداخل می‌کنند و به کارایی زمان اجرا آسیب می‌زنند.

و با این حال، به این کد نگاه کنید:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

با روشن‌کردن چند جزئیات:

- `Int16` یک نوع است، و می‌توانیم متغیرهایی از این نوع بسازیم.
- `Int16` یک زیرنوع از `Signed` است، و تابع `supertype()` این را به ما نشان می‌دهد.
- سلسله‌مراتبی از انواع وجود دارد که از `Integer`، `Real` و `Number` بالا می‌رود تا به `Any` در بالای آن می‌رسد، و `subtypes()` این شاخه از سلسله‌مراتب را برای ما فهرست می‌کند.

همه‌ی شاخه‌ها به `Any` ختم می‌شوند، که در اینکه فوق‌نوع خودش باشد یکتاست.

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

پس Julia سلسله‌مراتب `class` ندارد، اما سلسله‌مراتب `type` را _دارد_.

در نهایت تلاش خواهیم کرد بفهمیم این چطور کار می‌کند، اما پیش از آن چیزهای بسیار بیشتری برای کشف کردن وجود دارد.

## آزمودن نوع‌ها

می‌توانیم از `typeof()` برای آزمودن برابری به روش معمول استفاده کنیم.

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

برابری نوع باید دقیق باشد، چون این شکل از مقایسه هیچ درکی از سلسله‌مراتب نوع ندارد.

به شکلی انعطاف‌پذیرتر، `isa` به ما می‌گوید که آیا یک مقدار همان نوع مقایسه‌کننده را دارد، یا یک زیرنوع از آن را.
می‌توان آن را هم به شکل تابعی و هم به شکل میان‌وندی به کار برد.

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

توجه کنید که `isa` در سمت چپ یک `value` انتظار دارد، نه یک `type`.

تلاش برای مقایسه‌ی دو _نوع_ به این روش نتایج غیرمنتظره‌ای به بار می‌آورد.
عملگر درست `<:` است، که در مفاهیم آینده بسیار بیشتر آن را خواهیم دید.

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## انواع انتزاعی در برابر انواع عینی

دیدیم که سلسله‌مراتب نوع ساختاری درختی می‌سازد (به معنای علوم کامپیوتر، با ریشه در بالا).

هر عنصر در این درخت یک `node` است، و این‌ها را می‌توان به دسته‌هایی تقسیم کرد:

1. گره‌هایی که زیرنوع دارند `abstract` نامیده می‌شوند.
2. گره‌های برگ، که زیرنوع ندارند، `concrete` نامیده می‌شوند.

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

این یک تمایز مهم است، چون فقط انواع عینی را می‌توان به‌عنوان متغیر `instantiated` کرد.


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

توجه کنید که تلاش برای استفاده از یک نوع انتزاعی (در این مورد) هیچ پیام خطایی نمی‌دهد، اما کامپایلر یک نوع عینی مناسب می‌سازد: `Int64` به‌جای `Integer`.
حداقل مانع از آن می‌شود که متغیر به یک غیرعدد صحیح تخصیص یابد:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

بنابراین تخصیص نوع با یک نوع انتزاعی یک _محدودیت_ بر نوع متغیر است، به هر زیرنوعی از `Integer` (در حالت بالا).
این در دنیای زبان‌های برنامه‌نویسی چیز غیرمعمولی است: ضعیف‌تر از یک تخصیص نوع در C، و قوی‌تر از یک راهنمای نوع در نسخه‌های اخیر Python.

توابع `isabstracttype()` و `isconcretetype()` امکان آزمودن را فراهم می‌کنند.
توجه کنید که این‌ها فقط نقیض یکدیگر نیستند: در مفهومی بعدی خواهیم دید که برخی انواع می‌توانند نه انتزاعی باشند و نه عینی.


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

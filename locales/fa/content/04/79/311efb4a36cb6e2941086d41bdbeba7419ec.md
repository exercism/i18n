# مقدمه

## رابط `error`

مدیریت خطا در Go **نه** با استثناها انجام می‌شود.
در عوض، خطاها _مقدارهای_ معمولی از نوع‌هایی هستند که رابط توکار `error` را پیاده‌سازی می‌کنند.
رابط `error` بسیار کمینه است.
فقط یک متد دارد، `Error()`، که پیام خطا را به‌صورت رشته برمی‌گرداند.

```go
type error interface {
  Error() string
}
```

هر بار تابعی تعریف می‌کنید که ممکن است هنگام اجرا خطایی در آن رخ دهد که باید به فراخوانی‌کننده برسد، باید `error` را به‌عنوان یکی از نوع‌های بازگشتی بگنجانید.
اگر تابع چند مقدار بازگشتی داشته باشد، طبق قرارداد `error` همیشه آخرین مورد است.

```go
func DoSomething() (int, error) {
  // ...
}
```

## ساختن و برگرداندن یک خطای ساده

لازم نیست همیشه خودتان رابط `error` را پیاده‌سازی کنید.
برای ساختن یک خطای ساده می‌توانید از تابع `errors.New()` استفاده کنید که بخشی از پکیج کتابخانه‌ی استاندارد `errors` است.
فقط کافی است پیام خطا را به‌صورت رشته بدهید؛ `errors.New()` خودش مقداری را می‌سازد که پیام شما را در خود دارد و رابط `error` را پیاده‌سازی می‌کند.

اگر تابع خطا برمی‌گرداند، بهتر است برای سایر پارامترهای بازگشتی مقدار صفر را برگردانید:

```go
func DoSomething() (SomeStruct, int, error) {
  // ...
  return SomeStruct{}, 0, errors.New("failed to calculate result")
}
```

~~~~exercism/caution
نباید فرض کنید که اگر خطایی وجود دارد، همه‌ی توابع برای سایر مقادیر بازگشتی مقدار صفر برمی‌گردانند.
بهتر است فرض کنید اگر خطایی رخ داده باشد، استفاده از هیچ‌یک از مقادیر بازگشتی دیگر امن نیست.
تنها استثنا مواردی است که مستندات به روشنی بگوید سایر مقادیر بازگشتی در صورت وجود خطا معنا دارند.
~~~~

اگر می‌خواهید چنین خطای ساده‌ای را در چند جا استفاده کنید، به جای اینکه `errors.New` را همان‌جا به کار ببرید، باید یک متغیر برای خطا اعلام کنید.
طبق قرارداد، اسم متغیر باید با `Err` یا `err` شروع شود (بسته به اینکه صادرشده باشد یا نه).
به این متغیرهای خطا اغلب _خطاهای نگهبان_ می‌گویند.

```go
import "errors"

var ErrNotFound = errors.New("resource was not found")

func DoSomething() error {
  // ...
  return ErrNotFound
}
```

برای نشان دادن اینکه هنگام اجرای تابع خطایی رخ نداده است، `nil` را به‌عنوان خطا برگردانید:

```go
func Foo() (int, error) {
  return 10, nil
}
```

## بررسی خطا

اگر تابعی را فراخوانی کنید که خطا برمی‌گرداند، معمولاً مقدار خطا را در متغیری به اسم `err` نگه می‌دارند.
پیش از استفاده از نتیجه‌ی واقعی تابع، باید بررسی کنید که خطایی وجود نداشته باشد.

برای اینکه «مسیر موفق» کدتان تودرتو نشود، بهتر است ابتدا حالت‌های خطا را مدیریت کنید.
می‌توانیم با `==` و `!=` خطا را با `nil` مقایسه کنیم؛ وقتی `err` برابر `nil` نباشد، می‌دانیم خطایی رخ داده است.

```go
func processUserFile() error {
	file, err := os.Open("./users.csv")
	if err != nil {
		return err
	}

	// do something with file
}
```

بیشتر اوقات، خطا همان‌طور که در مثال بالا دیدید در پشته‌ی توابع به بالا برگردانده می‌شود.
راه دیگر مدیریت خطا این است که آن را لاگ کنید و کار دیگری را ادامه دهید.
بهتر است خطا را یا برگردانید یا لاگ کنید، نه هر دو.

چون بیشتر توابع Go خطا را به‌عنوان یکی از مقادیر بازگشتی دارند، الگوی `if err != nil` را همه‌جای کد Go می‌بینید و به کار می‌برید.

## نوع‌های خطای سفارشی

اگر می‌خواهید خطایتان اطلاعات بیشتری از فقط پیام خطا داشته باشد، می‌توانید یک نوع خطای سفارشی بسازید.
همان‌طور که پیش‌تر گفته شد، هر چیزی که رابط `error` را پیاده‌سازی کند (یعنی متد `Error() string` داشته باشد) می‌تواند در Go به‌عنوان خطا به کار برود.

معمولاً برای ساختن نوع خطای سفارشی از یک `struct` استفاده می‌شود.
طبق قرارداد، اسم نوع‌های خطای سفارشی باید با `Error` تمام شود.
همچنین بهتر است متد `Error() string` را با گیرنده‌ی اشاره‌گر تعریف کنید؛ برای آشنایی با دلیل آن، این [نظر Stackoverflow][stackoverflow-errors] را ببینید.
توجه کنید که این یعنی باید اشاره‌گری به خطای سفارشی‌تان برگردانید، وگرنه به‌عنوان `error` به حساب نمی‌آید، چون مقدار غیراشاره‌گر متد `Error() string` را ارائه نمی‌دهد.

```go
type MyCustomError struct {
  message string
  details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.message, e.details)
}

func someFunction() error {
  // ...
  return &MyCustomError{
    message: "...",
    details: "...",
  }
}
```

# درباره

`struct`های C# با `class`ها رابطه‌ی نزدیکی دارند.
آن‌ها حالت و رفتار دارند.
می‌توانند همان انواع اعضا را داشته باشند: سازنده‌ها، متدها، فیلدها، ویژگی‌ها و غیره.

فیلدها و ویژگی‌ها می‌توانند از انواع ساده، `struct` یا انواع ارجاعی باشند.
`struct`ها همان قواعد مربوط به حوزه‌ی دید، قواعد خواندن/نوشتن و سطوح دسترسی را رعایت می‌کنند که `class`ها رعایت می‌کنند.

```csharp
enum Unit
{
    Kg,
    Lb
}

struct Weight
{
    private double count;
    private Unit unit;

    public Weight(double count, Unit unit)
    {
        this.count = count;
        this.unit = unit;
    }

    public override string ToString()
    {
        return count.ToString() + unit.ToString();
    }
}

new Weight(77.5, Unit.Kg).ToString();
// => "77.6Kg"
```

یکی از مهم‌ترین نکاتی که باید به خاطر بسپارید این است که وقتی یک `struct` به متغیری نسبت داده می‌شود یا به عنوان پارامتر پاس داده می‌شود، مقادیر کپی می‌شوند؛ بنابراین تغییر در متغیر اصلی روی نسخه‌ی کپی‌شده اثری نمی‌گذارد و برعکس.
به طور خلاصه، `struct`ها **انواع مقداری** هستند.

این [مقاله][class-or-struct] تفاوت‌های میان `struct`ها و `class`ها را بررسی می‌کند.
از مقاله خواهید دید که `struct`ها معمولاً سبک و [تغییرناپذیر][structs-immutable] هستند، هرچند کامپایلر یا محیط اجرا این توصیه را (به طور پیش‌فرض) الزام نمی‌کند.

چند مورد هست که با آن‌ها روبه‌رو خواهید شد (و کامپایلر هم آن‌ها را به شما یادآوری می‌کند):

1. اعضای یک `struct` را نمی‌توان به صورت درجا مقداردهی اولیه کرد.
2. `struct` قابل ارث‌بری نیست
3. `struct` همیشه یک سازنده‌ی پیش‌فرض دارد، حتی اگر سازنده‌ی غیرپیش‌فرضی ارائه کرده باشید، و نمی‌توانید سازنده‌ی بدون پارامتر صریح تعریف کنید.

در نتیجه‌ی موارد ۱ و ۳ بالا، توسعه‌دهنده‌ی یک `struct` هیچ راهی ندارد که از به وجود آمدن نمونه‌های نامعتبر جلوگیری کند.

## `struct`های رایج

از مستندات خواهید دید که میان انواع اولیه و `struct`ها رابطه‌ی نزدیکی وجود دارد.
برای نمونه، [`Int32/int`][int32] را ببینید.
نمونه‌ی مرسوم‌تر یک `struct`، نوع [`TimeSpan`][time-span] است.

نمونه‌های `TimeSpan` تقریباً مثل عدد رفتار می‌کنند، با عملگرهای مقایسه‌ای مانند `>` و `<` و عملگرهای حسابی.
هر وقت لازم باشد می‌توانید این عملگرها را برای `struct`های خودتان پیاده‌سازی کنید.

نکته‌ای که درباره‌ی `TimeSpan` باید در نظر بگیرید این است که چندین رابط، مانند `IComparable<TimeSpan>`، را پیاده‌سازی می‌کند.
`struct`ها هرچند نمی‌توانند از `struct`های دیگر مشتق شوند، می‌توانند رابط‌ها را پیاده‌سازی کنند.

## برابری

آزمایش برابری برای `struct`ها اغلب می‌تواند بسیار ساده‌تر از `class`ها باشد، چون به طور پیش‌فرض فقط فیلدها را از نظر برابری مقایسه می‌کند.
نیازی به بازنویسی `object.Equals()` (یا `GetHashCode()`) نیست.
به یاد داشته باشید که اگر به `Object.GetHashCode()` تکیه می‌کنید، باز هم باید مطمئن شوید فیلدهای دخیل در تولید کد هش (یعنی همه‌ی فیلدها) تا وقتی یک مجموعه‌ی هش در حال استفاده است تغییر نکنند.
در عمل، این یعنی `struct`هایی که به این شکل استفاده می‌شوند باید تغییرناپذیر باشند.

برخلاف متد `Equals()`، برای عملگرهای برابری، یعنی `==` و `!=`، پیاده‌سازی پیش‌فرضی وجود ندارد.
اگر `struct` شما به آن‌ها نیاز دارد، باید خودتان آن‌ها را پیاده‌سازی کنید.

از طرف دیگر، این [مقاله][equality] توضیح می‌دهد که چگونه می‌توان با ساختن متدهای سفارشی `Equals()` و `GetHashCode()`، همان‌طور که برای `class`ها معمول است، کارایی را بهبود داد.
در مورد این تمرین، این تفاوت در یک مقایسه‌ی نه‌چندان دقیق حدود ۲۰٪ بود، اما ممکن است کمتر از واقعیت باشد، چون همه‌ی فیلدها از یک نوع‌اند (ادامه را ببینید).

در [وب][equality-performance] بحث‌هایی درباره‌ی بهبود سرعت وجود دارد، برای حالتی که متد `Equals()` بازنویسی نشده است و همه‌ی فیلدها از یک نوع‌اند.
در این تمرین، تفاوت در صورت داشتن فیلدهای ناهمگون حدود ۶۰٪ بود.
این مطلب در مستندات مایکروسافت ذکر نشده است، پس یک جزئیات پیاده‌سازی مستندنشده به شمار می‌رود و باید با احتیاط از آن بهره برد.

```csharp
public bool Equals(Weight other)
{
    return count.Equals(other.count) && unit.Equals(other.unit);
}

public override bool Equals(object obj)
{
    return obj is Weight other && Equals(other);
}

public override int GetHashCode()
{
    return HashCode.Combine(count, unit);
}
```

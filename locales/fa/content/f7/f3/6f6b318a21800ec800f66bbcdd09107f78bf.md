# درباره

یک تابع زمانی «بازگشتی دنباله‌دار» است که _آخرین_ کاری که در آن اجرا می‌شود، فراخوانی خودش باشد.

هر بار که تابعی فراخوانی می‌شود، یک «قاب پشته» همراه با متغیرهای محلی و آرگومان‌هایش روی [پشته‌ی فراخوانی تابع][call-stack] قرار می‌گیرد. وقتی تابع برمی‌گردد، آن قاب پشته از روی پشته برداشته می‌شود.

توابع بازگشتی دنباله‌دار امکان «بهینه‌سازی فراخوانی دنباله» (یا حذف فراخوانی دنباله) را فراهم می‌کنند. این بهینه‌سازی اجازه می‌دهد قاب پشته‌ی آخرین، توسط فراخوانی بعدی تابع دوباره استفاده شود، در حالی که تضمین شده تابع قبلی دیگر به آن نیازی ندارد. این کار نگرانی سرریز شدن پشته‌ی فراخوانی تابع را کاهش می‌دهد؛ وضعیتی که در آن آنقدر قاب روی پشته‌ی فراخوانی تابع وجود دارد که حافظه‌ای برای ساختن یکی دیگر باقی نمی‌ماند.

## بهینه‌سازی فراخوانی دنباله در Elm

در برخی شرایط، کامپایلر Elm هنگام کامپایل به JavaScript می‌تواند به‌طور خودکار بهینه‌سازی فراخوانی دنباله را انجام دهد.

این بهینه‌سازی می‌تواند برای یک تابع بازگشتی رخ دهد، وقتی _آخرین_ عملیات در یک شاخه با فراخوانی خود تابع در یک «اعمال تابع» ساده انجام شود. بیایید چند مثال را ببینیم:

```elm
factorial : Int -> Int
factorial n =
  if n <= 1 then
    n
  else
    n * factorial (n-1)
```

پیاده‌سازی بالا بازگشتی دنباله‌دار نیست، چون آخرین عملیات در شاخه‌ی `else` یک ضرب `n *` است.

```elm
factorial : Int -> Int
factorial n =
  factorialHelper n n

factorialHelper : Int -> Int -> Int
factorialHelper n resultSoFar =
  if n <= 1 then
    resultSoFar
  else
    factorialHelper (n-1) (n * resultSoFar)
```

پیاده‌سازی بالا بازگشتی دنباله‌دار است و بهینه می‌شود، چون آخرین عملیات در شاخه‌ی `else` فراخوانی خودش توسط `factorialHelper` است. این کار برای تابعی با امضای نوع `Int -> Int` امکان‌پذیر نیست، و در عمل بهینه‌سازی فراخوانی دنباله اغلب با تعریف توابع کمکی به دست می‌آید.

## حالت‌های مرزی

در برخی موارد، کامپایلر نمی‌تواند توابع بازگشتی را بهینه کند. بیایید چند مثال را ببینیم.

در حالی که `f x = f (x - 1)` بازگشتی دنباله‌دار است، `f x = (x - 1) |> f` این‌طور نیست، چون اعمال تابع `|>` آخرین عملیات است و جدا از `f` در نظر گرفته می‌شود. به همین ترتیب، توابعی که با شرط‌های منطقی `f x = x > 0 || f (x - 1)` پایان می‌یابند بازگشتی دنباله‌دار نیستند.

تابع `f x = if f (x - 1) then 1 else 0` بازگشتی دنباله‌دار نیست، چون عبارتی که در `if` قرار دارد یک شاخه در نظر گرفته نمی‌شود. به همین ترتیب، فراخوانی بازگشتی در یک دستور `case` هم بهینه نمی‌شود.

تابع `f x = let y = f (x - 1) in y` بازگشتی دنباله‌دار نیست، چون خودش را در یک دستور `let` فراخوانی می‌کند که یک شاخه در نظر گرفته نمی‌شود. با این حال، در `f x = let g x = g (x - 1) in g x` تابع `g` بازگشتی دنباله‌دار است و بهینه می‌شود، حتی اگر در یک دستور `let` تعریف شده باشد.

تابع `f x = if x > 0 then f (x + 1) else 1 + f x` _تا حدی_ بهینه می‌شود: شاخه‌ی `then` بهینه می‌شود اما شاخه‌ی `else` نه. بهینه‌سازی جزئی بهترین نتیجه‌ای است که در برخی موقعیت‌ها می‌توان به آن رسید، مانند پیمایش ساختارهای درخت‌مانند یا تعریف توابع هم‌بازگشتی.

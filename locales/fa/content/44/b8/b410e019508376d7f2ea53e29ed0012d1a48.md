# درباره

یک اعلان `GENERIC:` واژه‌ای را معرفی می‌کند که رفتارش به کلاس یکی از آرگومان‌هایش بستگی دارد. رفتار مشخص را *«متدها»* (`M:`) فراهم می‌کنند که کلاس‌های مشخصی را هدف می‌گیرند.

```factor
GENERIC: stringify ( obj -- str )
M: integer stringify number>string ;
M: string  stringify ;
M: f       stringify drop "(none)" ;
```

وقتی `stringify` فراخوانی می‌شود، Factor بالای پشته را بررسی می‌کند، خاص‌ترین متدی را که کلاسش مطابقت دارد جست‌وجو می‌کند و آن را اجرا می‌کند. اگر هیچ متدی مطابقت نداشته باشد، یک خطا پرتاب می‌شود.

## کلاس «دیسپچ»

به‌طور پیش‌فرض، دیسپچ روی بالاترین آرگومان (نخستین ورودی اعلام‌شده در اثر پشته) انجام می‌شود. برای دیسپچ چندآرگومانی، به `HOOK:` و `MATH:` نگاه کنید که به‌ترتیب روی آرگومان دوم یا ارتقای عددی دیسپچ می‌کنند.

## افزودن متد به یک «ژنریک»

می‌توانید هر زمان یک ژنریک را گسترش دهید، حتی از «واژگان» دیگری، تا زمانی که بتوانید هم ژنریک و هم کلاس را `USE:` کنید:

```factor
USING: math ;
M: ratio  area drop 0 ;     ! adds an `area` method for ratios
```

## متدها روی کلاس‌های توکار

ژنریک‌ها روی کلاس‌های توکار (`integer`، `string`، `array`، `f`، `t`) هم به‌خوبی روی «تاپل‌های» تعریف‌شده توسط کاربر کار می‌کنند. متدها روی `f` و `t` به‌ویژه برای «محمول‌هایی» به سبک «is-set?» مفیدند که پیش‌فرض‌های طبیعی دارند.

## چه زمانی ژنریک انتخاب درستی است

در این موارد سراغ `GENERIC:` بروید:

- یک عملیات واحد برای ورودی‌های مختلف پیاده‌سازی‌های *واقعاً متفاوتی* داشته باشد (نه فقط یک `case` روی برچسب‌ها).
- انتظار داشته باشید که بعداً کدهای دیگر نوع‌های تازه‌ای اضافه کنند.
- می‌خواهید سیستم نوع تضمین کند که عملیات برای هر کلاس مرتبط تعریف شده است؛ Factor هم می‌تواند متدهای جاافتاده را برایتان فهرست کند.

اگر تفاوت تنها برشماری کوچک و ثابتی از برچسب‌ها باشد، یک `case` ساده‌تر است.

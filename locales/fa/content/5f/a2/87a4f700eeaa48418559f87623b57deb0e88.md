# مشخصات Markdown

آنچه در ادامه می‌آید، شیوه‌ای است که همه‌ی فایل‌های Markdown در Exercism باید بر اساس آن ساختاردهی شوند.

برخی از قواعد این سند هنوز در سراسر Exercism پیاده‌سازی نشده‌اند.
از PRهایی که آن‌ها را اصلاح کنند استقبال می‌کنیم.
همه‌ی قواعد در حال افزوده‌شدن به CI و ابزارهای لینتر ما هستند و در تغییرات جدید باید رعایت شوند.

## سرتیترها

- همه‌ی فایل‌ها باید با یک سرتیتر سطح ۱ شروع شوند (`# Some heading text`).
- سرتیترهای سطح ۱ صرفاً برای اینکه در GitHub یا محیط‌های مشابه خوانده شوند وجود دارند.
- اگر فایل توسط Exercism رندر شود (مثلاً در وب‌سایت نمایش داده شود یا از طریق CLI رندر شود)، این سرتیتر حذف می‌شود و یک سرتیتر زمینه‌ای درج می‌شود.
- هیچ سرتیتری نمی‌تواند بیش از یک سطح از سرتیتر قبلی پایین‌تر برود (مثلاً پس از `##` فقط `###` می‌تواند بیاید، نه `####`).
- علاوه بر تنها سرتیتر سطح ۱ (`#`)، فقط می‌توان از سرتیترهای سطح ۲ (`##`)، سطح ۳ (`###`) و سطح ۴ (`####`) استفاده کرد.

## پیوندها

لطفاً از [پیوندهای ارجاعی][reference-links] استفاده کنید که در انتهای فایل Markdown تعریف می‌شوند، به یک نامک ارجاعی نگاشت می‌شوند و در متن با همان نامک ارجاع داده می‌شوند.

این روش نگهداری را آسان‌تر می‌کند، چون پیوندها فقط در یک مکان باید به‌روزرسانی شوند.

مثال:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

پیوندها همیشه باید متن لنگر داشته باشند، نه اینکه خود URL در متن آورده شود.
برای مثال، نمونه‌ی زیر متن لنگر ندارد و خواندنش سخت‌تر است.

```
If you want some more information, please visit https://google.com.
```

استفاده از متن لنگر و پیوند دادن آن، درک و بافت‌مند کردن مطلب را آسان‌تر می‌کند.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

که به این صورت رندر می‌شود: «اگر اطلاعات بیشتری می‌خواهید، [Google][google-link] منبعی مفید است.»

## Code

هر زمان که به عناصر code اشاره می‌شود (مثلاً توابع یا کلیدواژه‌ها)، code باید در بکتیک قرار گیرد:

```
- The `printf()` function writes to the console.
```

که به این صورت رندر می‌شود:

- تابع `printf()` در کنسول می‌نویسد.

code پیچیده‌تر (مثلاً code چندخطی) باید در سه بکتیک قرار گیرد.
برای فعال شدن برجسته‌سازی نحوه‌ی نگارش، باید بعد از سه بکتیک باز، یک [شناسه‌ی زبان][language-identifier] مشخص شود:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

تا حد امکان، code را به شکلی قالب‌بندی کنید که با محیطی که در آن ارائه می‌شود بیشترین تناسب را داشته باشد.
اگر در دسترس است، لطفاً به مستندات زبان خود مراجعه کنید.

برای مثال، Python یک REPL دارد (حلقه‌ی خواندن، ارزیابی و چاپ) که به برنامه‌نویس اجازه می‌دهد code را مستقیماً در ترمینال تایپ کند.
اگر کاربری در حال debug کردن code باشد یا تابعی را به‌صورت محلی اجرا کند تا نحوه‌ی کارش را آزمایش یا مشاهده کند، احتمالاً برای این کار از REPL استفاده می‌کند، چون تایپ تعاملی در آن راحت‌تر است.
در این حالت، ترجیح می‌دهیم code نمونه را طوری قالب‌بندی کنیم که گویی در REPL تایپ می‌شود، با یک `>>>` در ابتدا:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

در موارد دیگر، منطقی‌تر است که code را همان‌طور که در یک فایل `.py` نوشته می‌شود رها کنیم.
اینجا دانشجو از اینکه چیزی ببیند که نحوه‌ی نوشتن خودش را تقلید می‌کند، بهره‌مند می‌شود.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

یک راه سریع برای تشخیص این دو حالت وقتی موضوع روشن نیست: اگر این code چیزی است که دانشجو می‌تواند در ترمینال اجرا کند، همان‌طور قالب‌بندی کنید.
اگر code از آن دسته باشد که ممکن است Exercism آن را اجرا کند (در tests، code کتابخانه‌ای که دانشجو می‌نویسد و غیره)، به‌طور پیش‌فرض آن را به‌عنوان code قابل اجرا قالب‌بندی کنید.

## بلوک‌های ویژه (که گاهی admonition نامیده می‌شوند)

ما از انواع خاصی از بلوک‌ها پشتیبانی می‌کنیم که می‌توان آن‌ها را به سند اضافه کرد تا توضیحاتی را که با بدنه‌ی اصلی متن جور در نمی‌آیند، جدا کنند.

<img width="500" alt="بلوک پیشرفته Markdown" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

ما از سه نوع بلوک پشتیبانی می‌کنیم:

- **exercism/note:** بلوک‌هایی که اطلاعات ویژه‌ی اضافی را بیرون می‌کشند
- **exercism/caution:** مواردی که افراد باید از آن‌ها آگاه باشند یا با احتیاط با آن‌ها برخورد کنند
- **exercism/advanced:** اطلاعاتی که فقط برای کسانی مرتبط است که می‌خواهند چیزی را عمیق‌تر بکاوند یا انتظار می‌رود دانش پیشرفته‌تری داشته باشند.

همه‌ی بلوک‌ها با ۴ تیلدا نوشته می‌شوند، به این شکل:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(توجه: در شرایط استثنایی می‌توانید از بکتیک یا سطوح دیگری از تیلدا هم استفاده کنید)

## چیدمان

### یک جمله در هر خط

پاراگراف‌ها باید با یک جمله در هر خط چیده شوند.
[مستندات Ascii Doctor][asciidoctor] منطق این کار را به‌روشنی توضیح می‌دهد.

برای مثال، یک پاراگراف واحد باید به این صورت چیده شود:

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## فهرست‌ها

از نویسه‌ی خط تیره (`-`) به‌عنوان نشانگر فهرست برای فهرست‌های نامرتب استفاده کنید.

## توضیحات

- توضیحات Markdown را به توضیحات HTML ترجیح دهید (مثلاً از `[comment]: # (Actual comment...)` به‌جای `<!-- Actual comment -->` استفاده کنید)

می‌توانید بررسی کنید که توضیح Markdown شما حذف می‌شود؛ کافی است ببینید توضیحتان هنگام رندر با commonmark در [babelmark3] چه شکلی است.

## HTML درون‌خطی

- HTML درون‌خطی مجاز است، اما باید کم استفاده شود
- اگر جایگزین‌های بومی Markdown در دسترس باشند، همیشه از آن‌ها استفاده کنید (مثلاً به‌جای `<h1>...</h1>` از `# ...` استفاده کنید)

## تصاویر

از آنجا که وب‌سایت از پوسته‌های روشن و تیره پشتیبانی می‌کند، تصاویر ارسالی جامعه باید در هر دو پوسته خوب رندر شوند.
راه‌حل این است که به انتهای اسم تصویر (پیش از پسوند فایل) پسوندی اضافه کنید:

1. اسم تصویر به `-invertible` ختم شود (مثلاً `graph-invertible.svg`). تصویر هنگام نمایش در پوسته‌ی تیره به‌طور خودکار معکوس می‌شود (از طریق `filter: invert(100%)`).
1. اسم تصویر به `-light` ختم شود (مثلاً `graph-light.png`) و همچنین نسخه‌ای سازگار با پوسته‌ی تیره بسازید که به `-dark` ختم می‌شود (که همان `graph-dark.png` است). ما بسته به پوسته‌ی کاربر، تصویر درست را به‌طور خودکار رندر می‌کنیم.

تصاویری که هیچ‌یک از این دو پسوند را ندارند، بدون تغییر در هر دو پوسته استفاده می‌شوند.
این یعنی اگر می‌خواهید تصاویر خاکستری بسازید، معمولاً می‌توانید آن‌ها را طوری بسازید که در پوسته‌ی روشن خوب به نظر برسند و سپس آن‌ها را برای معکوس‌شدن تنظیم کنید.
اما اگر از تصویری با رنگ‌های زیاد استفاده می‌کنید، شاید بهتر باشد دو نسخه بسازید.

اسم کامل تصویر (شامل `-invertible`) باید در همان جایی از Markdown که تصویر رندر می‌شود، اضافه شود.
برای تصاویر روشن/تیره، **فقط** نسخه‌ی `-light` را وارد کنید.
این منطق در همه‌ی مستندات Markdown رعایت می‌شود.

## قالب‌بندی خودکار

بعضی مخازن از [prettier][prettier] استفاده می‌کنند تا مطمئن شوند همه‌ی Markdown به‌طور یکدست قالب‌بندی می‌شود.
این کار می‌تواند مزایای زیر را به همراه داشته باشد:

- بدون بحث درباره‌ی قالب‌بندی.
- یکپارچگی عالی با ویرایشگر/IDE، طوری که فایل‌ها هنگام ذخیره قالب‌بندی شوند.
- افزودن بررسی‌های CI برای قالب‌بندی آسان است.
- قالب‌بندی خودکار فایل‌ها با یک اسکریپت آسان است.

همه‌ی موارد بالا می‌توانند به‌شدت به کاهش تغییرات پراکنده در بازبینی‌ها کمک کنند، چیزی که هم برای بازبین و هم برای بازبینی‌شونده آزاردهنده است.

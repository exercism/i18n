# مقدمه

تا اینجای سرفصل، دیده‌اید که R اغلب به‌عنوان یک زبان دستوری به کار می‌رود و به‌تدریج به‌عنوان یک زبان تابعی (به‌ویژه با کتابخانه‌های [`purrr`][ref-purrr] و [`dplyr`][ref-dplyr]).

حالا اگر بگوییم که R اساساً «شیءگرا» است، ممکن است کمی تردید برانگیزد!

به‌طرز عجیبی، این حرف درست است.
در داخل، R با «کلاس‌ها»، «وراثت»، «چندریختی» و همان نوع نگرش‌های معمول برنامه‌نویسان شیءگرا پیاده‌سازی شده است.

با این حال، هر کسی که با Java یا Ruby (که صریحاً شیءگرا هستند) یا حتی Python (که در برخی جنبه‌ها نیمه‌پنهان شیءگراست) آشنا باشد، رویکرد R را ... _ناآشنا_ خواهد یافت.

برای شروع، چندین طراحی کلاس وجود دارد: شاید سه مورد در استفاده‌ی رایج (S3، S4، R6)، به‌علاوه‌ی موارد مختلف دیگر که عمدتاً جنبه‌ی نظری دارند.

بحثی مفصل را می‌توانید در [Advanced R, 2e][book-advanced-r]، فصل‌های ۱۲ تا ۱۶ بیابید.
این کتاب سال ۲۰۱۹ عمدتاً برای کسانی نوشته شده که می‌خواهند درون R را بفهمند و نگهداری کنند، بنابراین شیءگرایی ضروری است.

کتاب‌های درسی که بیشتر به کاربر نهایی توجه دارند، متفاوت‌اند.

- کتاب The Art of R Programming (۲۰۱۱، فقط چاپی) فصلی درباره‌ی شیءگرایی دارد که S3 و (به‌طور مختصرتر) S4 را پوشش می‌دهد، که در آن زمان مهم بودند.
  این نکته که _«کلاس‌های S3 ساختاری نسبتاً سرهم‌بندی‌شده دارند»_ هنوز به‌طرز چشمگیری درست است.
- کتاب R in Action (ویرایش سوم، ۲۰۲۲) شیءگرایی را به ۳ صفحه در فصلی درباره‌ی برنامه‌نویسی پیشرفته نزدیک پایان کتاب تنزل می‌دهد.
- کتاب [R for Data Science, 2e][book-r-data-sci] (۲۰۲۳، با ۵۴۸ صفحه در نسخه‌ی چاپی) هیچ اشاره‌ای به شیءگرایی نمی‌کند.

این مفهوم بر کلاس‌های S3 تمرکز خواهد کرد، که ساده‌ترین، رایج‌ترین و مرتبط‌ترین با مسائل سبک Exercism هستند.
برخی از تمرین‌های عملی در مسیر R از شما می‌خواهند یک کلاس S3 بسازید؛ برخی دیگر این کار را اختیاری اما با تشویق ملایم می‌گذارند.

## کلاس‌های S3

این‌ها قدیمی‌اند: نام S3 فقط یعنی آن‌ها در نسخه‌ی ۳ زبان S معرفی شدند (زبانی تجاری که R از آن پدید آمد).

یک کلاس S3 هم بسیار ساده است: معمولاً یک [لیست][concept-lists] با دست‌کم یک صفت اضافی.

به نقل از [Advanced R][book-s3]: _«S3 غیررسمی و موردی است، اما نوعی ظرافت در مینیمال‌بودنش هست: نمی‌توانید هیچ بخشی از آن را بردارید و هنوز یک سیستم شیءگرای مفید داشته باشید.»_

```R
# create a list
pt2d <- list(x = 2.5, y = 4.2)
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
class(pt2d)
#> [1] "list"
attributes(pt2d)
#> $names
#> [1] "x" "y"

# convert the list to an S3 class
class(pt2d) <- "point2d"
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
#>  - attr(*, "class")= chr "point2d"
class(pt2d)
#> [1] "point2d"
attributes(pt2d)
#> $names
#> [1] "x" "y"

#> $class
#> [1] "point2d"
```

بنابراین انتساب به [`class(obj)`][ref-class] فقط یک صفت به `obj` اضافه می‌کند، و در این حالت pt2d را به‌عنوان نمونه‌ای از کلاس point2d مشخص می‌کند.

مراحل ساخت را می‌توان با [`structure()`][ref-structure] ترکیب کرد:

```R
pt2d_2 <- structure(list(x = 2.5, y = 4.2), class = "point2d")
pt2d_2 == pt2d
#> Error in pt2d_2 == pt2d : comparison of these types is not implemented
```

هرچند نمونه‌های حاصل از نظر مفهومی یکسان‌اند، هنوز راهی پیاده‌سازی نکرده‌ایم که R بتواند این را تأیید کند.

### روش‌های جنریک

هر کسی که با شیءگرایی در زبان‌های دیگر آشنا باشد، ممکن است بپرسد: «مگر قرار نیست کلاس‌ها بتوانند کارهایی انجام دهند؟»

می‌توانیم روش‌های موجود برای نمونه‌های `point2d` را بررسی کنیم و ببینیم که (برخلاف `list` زیرین) در حال حاضر هیچ روشی وجود ندارد.

```R
methods(class = "point2d")
#> no methods found
methods(class = "list")
#>  [1] %within%      all.equal     as.col_spec   as.data.frame as_mapper     as_tibble     coerce        common_by    
#>  [9] Ops           pattern_alpha relist        scale_type    select        type.convert  within       
#> see '?methods' for accessing help and source code
```

در بیشتر زبان‌های شیءگرا، روش‌ها درون تعریف کلاس تعریف می‌شوند.
چند زبان (به‌ویژه Ruby) به شما اجازه می‌دهند بعداً روش‌های کلاس را اضافه و تغییر دهید.

کلاس‌های S3 بسیار متفاوت‌اند.
به‌جای افزودن روش‌ها به یک کلاس، کلاس را به یک «روش جنریک» اضافه می‌کنیم.

هر کسی که به‌صورت تعاملی در کنسول R کار می‌کند، همیشه از روش‌های جنریک استفاده می‌کند، معمولاً بدون اینکه به نحوه‌ی پیاده‌سازی آن‌ها فکر کند.

یک نمونه‌ی بسیار رایج `print()` است، حتی اگر به‌ندرت اسم تابع را تایپ کنید.
وارد کردن یک مقدار `x` به‌تنهایی در اعلان کنسول، فقط شکر نحوی برای `print(x)` است.

```R
1:4
#> [1] 1 2 3 4
print(1:4)
#> [1] 1 2 3 4
```

از قبل می‌توانیم `pt2d` را چاپ کنیم.
هرچند `print()` هیچ چیزی درباره‌ی کلاس `point2d` نمی‌داند، پیش‌فرض‌های معقولی برای رسیدگی به انواع گوناگون اشیاء دارد.

```R
pt2d
#> $x
#> [1] 2.5

#> $y
#> [1] 4.2

attr(,"class")
#> [1] "point2d"
```

این خیلی پرحرف است و ممکن است راهی بخواهیم که نقطه را به‌طور مختصر و زیبا چاپ کند.

ساده است: فقط تابعی به اسم `print.point2d()` اضافه کنید.
اسم باید به شکل `methodname.classname` باشد تا توزیع‌کننده بداند دنبال چه چیزی بگردد.

```R
print.point2d <- function(pt) {
  cat("Cartesian coords (", pt$x, ", ", pt$y, ")\n", sep="")
}

pt2d
#> Cartesian coords (2.5, 4.2)
```

حالا فرض کنید می‌خواهیم یک روش جنریک جدید بسازیم، مثلاً `flipvert()` برای معکوس کردن علامت مختصه‌ی `y`.

باز هم ساده است:

```R
flipvert <- function(x, ...) UseMethod("flipvert")
```

این یک «توزیع‌کننده» می‌سازد، که در آن `x` شیء ما با یک کلاس S3 است و `...` هر آرگومان اضافی را که تعریف‌های روش ممکن است لازم داشته باشند مدیریت می‌کند («آرگومان‌های نقطه»، همان‌طور که در [مفهوم توابع][concept-functions] توضیح داده شده).

سپس می‌توانیم روش را برای `point2d` تعریف کنیم و از آن استفاده کنیم.

```R
flipvert.point2d <- function(pt) {
  pt$y <- -pt$y
  pt
}

flipvert(pt2d)
#> Cartesian coords (2.5, -4.2)

methods("flipvert")
#> [1] flipvert.point2d
```

حالا R می‌داند چطور نقطه‌ی ما را معکوس کند و نتیجه را نمایش دهد.

می‌توانیم این را با ساختن کلاس‌هایی برای 3D، برای مختصات قطبی و غیره گسترش دهیم و سپس برای هر کدام روش تعریف کنیم.

از دید کاربر نهایی، فقط `flipvert(x, ...)` وجود دارد و می‌توانیم به R تکیه کنیم تا کلاس ورودی را تعیین کند و پیاده‌سازی زیرین مناسب را به کار ببرد.

~~~~exercism/caution
اسم‌های توابع به شکل `verb.class` هم برای کاربران و هم برای تجزیه‌گر R شبیه روش‌های S3 به نظر می‌رسند.
لطفاً از به‌کار بردن نام‌گذاری مشابه در زمینه‌های دیگر خودداری کنید.

باید پذیرفت که R پایه گاهی این قاعده را نقض می‌کند.
باید این را یک حادثه‌ی تاریخی ناگوار در نظر بگیریم (برای توابعی حتی قدیمی‌تر از S3)، که باید برای سازگاری با عقب حفظ شود.
~~~~

### وراثت

شیفتگان شیءگرایی می‌توانند فصل‌های طولانی متعددی از کتاب‌های درسی درباره‌ی وراثت، زیرکلاس‌سازی، میکسین‌ها و بقیه‌ی موارد بنویسند.

R فقط به شما اجازه می‌دهد چندین اسم به صفت `class` بدهید: بردار بلندتری از رشته‌ها، نه یک رشته‌ی واحد.

با این خطر که مثال را تا مرز شکستن بکشیم، فرض کنید یک کلاس جنریک `point` ساخته بودیم و می‌خواستیم آن را به `point2d`، `point3d` و غیره زیرکلاس کنیم.

در این صورت تعریف `point2d` به‌سادگی از `class = c("point2d", "point")` استفاده می‌کند: کلاس خاص و کلاس والد (یا کلاس‌ها).

روش‌های جنریک مانند `print()` سپس به ترتیب دنبال `print.point2d()`، `print.point()` و (احتمالاً) `print.default()` می‌گردند و اولین پیاده‌سازی‌ای را که توزیع‌کننده پیدا کند به کار می‌برند.

# ساخت Test Runner

Test Runner یکی از بخش‌های ضروری ابزارهاست که این موارد را ممکن می‌کند:

- اینکه وب‌سایت به‌طور خودکار بررسی کند آیا نسخه‌ای که دانش‌آموز فرستاده همه‌ی تست‌ها را پاس می‌کند یا نه.
- اینکه دانش‌آموزان بتوانند تمرین‌ها را با [ویرایشگر درون‌مرورگر](/docs/using/solving-exercises/using-the-online-editor) حل کنند ([بدون نیاز به CLI](/docs/using/solving-exercises/working-locally)).

برای شروع ساخت یک Test Runner، سند [ساخت Test Runner از صفر](/docs/building/tooling/test-runners/creating-from-scratch) را ببینید.

## پیاده‌سازی

ابزارهای هر track معمولاً (و در بیشتر موارد) با زبان همان track نوشته می‌شوند.

```exercism/caution
استفاده از زبان‌های دیگر آزاد است، اما هر زبان اضافی نگه‌داری و مشارکت در track را سخت‌تر می‌کند.
بنابراین توصیه می‌کنیم تا حد امکان از زبان همان track استفاده کنید، چون نگه‌داری و مشارکت را آسان‌تر می‌کند.
```

## استقرار

Test Runner به‌صورت یک [کانتینر Docker](/docs/building/tooling/docker) بسته‌بندی و اجرا می‌شود.
تصاویر Docker مربوط به Test Runner به‌طور خودکار با یک [گردش‌کار GitHub Actions](https://github.com/exercism/generic-test-runner/blob/main/.github/workflows/docker.yml) مستقر می‌شوند.

## تست کردن

وقتی یک Test Runner ساخته شد، می‌توانید از تصویر Docker آن در راه‌اندازی یکپارچه‌سازی مداوم track خود استفاده کنید تا تمرین‌های track را بررسی کنید.
مزیت اصلی این روش این است که محیط production را بهتر شبیه‌سازی می‌کند؛ به عبارت دیگر، می‌توانید مطمئن‌تر باشید که همه چیز در production هم کار می‌کند.
یک عیب احتمالی این است که ممکن است گردش‌کار یکپارچه‌سازی مداوم را کندتر کند.
این شما هستید که به‌عنوان maintainer تصمیم می‌گیرید کدام روش برای track شما بهتر جواب می‌دهد.

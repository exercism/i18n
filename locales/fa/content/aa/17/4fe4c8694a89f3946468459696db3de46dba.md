# درباره

## افزودن زمینه به خطاها

ما در [مفهوم خطا][concept-errors] به بررسی مدیریت پایه‌ی خطا در Go پرداختیم. همان‌طور که آنجا یاد گرفتید، خطاها به‌طور پیش‌فرض ردیابی پشته را با خود حمل نمی‌کنند. همین باعث می‌شود اطمینان از اینکه خود خطا اطلاعات کافی برای شناسایی مشکل دارد، حیاتی باشد.

اگر می‌خواستیم با ابزارهایی که از قبل می‌شناسیم اطلاعاتی به یک خطای موجود اضافه کنیم، می‌توانستیم چیزی شبیه این بنویسیم تا خطای جدیدی با متن ترکیب‌شده‌ی خطای اصلی و اطلاعات اضافی بسازیم:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

خوشبختانه، بسته‌ی `fmt` از کتابخانه‌ی استاندارد، نسخه‌ی کوتاه‌تری از این کار را در قالب تابع `Errorf` در خود دارد. این به شما اجازه می‌دهد، برای مثال، به‌راحتی اطلاعاتی درباره‌ی زمینه‌ای که خطا در آن رخ داده اضافه کنید.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

مگر اینکه مطمئن باشید خطا از قبل اطلاعات کافی دارد، بهتر است عادت کنید همیشه پیش از بازگرداندن خطا از یک تابع، زمینه را به آن اضافه کنید. یعنی الگوی استاندارد مدیریت خطای شما باید شبیه این باشد:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

همان‌طور که در مثال‌ها نشان داده شد، قرارداد این است که خطا را با دونقطه از پیام اضافه‌شده جدا کنید. درست مانند پیام خطای اصلی، پیام زمینه هم نباید با حرف بزرگ شروع شود و نباید در انتهای آن نقطه‌ای گذاشت.

~~~~exercism/note
وقتی زمینه‌ای به یک خطا اضافه می‌کنید، وسوسه می‌شوید پیام را با «failed to ...» یا مشابه آن شروع کنید. با این حال، چون خطا در حین بالا رفتن از زنجیره‌ی توابع می‌تواند زمینه‌ی اضافی زیادی جمع کند، این کار می‌تواند پیام نهایی را که لاگ می‌شود یا کاربر می‌بیند، سخت‌خوان یا پر از تکرار کند.

این یک مثال برای روشن شدن مطلب است:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

پس هنگام نوشتن پیام‌های زمینه، این نتیجه‌ی نهایی را در ذهن داشته باشید و از اضافه کردن متنی درباره‌ی اینکه چیزی آن‌طور که انتظار می‌رفت پیش نرفت، خودداری کنید. این معمولاً از زمینه (مثلاً سطح لاگ «ERROR») و پیام خطای اصلی روشن است.
~~~~

اغلب این روش افزودن اطلاعات به خطا به‌قدر کافی خوب است، اما مواردی هست که می‌خواهید به مصرف‌کننده‌ی خطای خود اجازه دهید خطای اصلی زیرین را بررسی یا بازیابی کند. افزودن زمینه به گونه‌ای که این امکان را فراهم کند، در Go «بسته‌بندی خطا» نامیده می‌شود.

## بسته‌بندی خطاها و بررسی خطاهای نگهبان

بسته‌بندی خطا با تغییری بسیار کوچک در کدی که بالاتر دیدیم امکان‌پذیر است. برای بسته‌بندی یک خطا، باید به‌جای `%v` از فعل قالب‌بندی `%w` استفاده کنید. در پشت صحنه، این کار تضمین می‌کند که خطای حاصل متدی به اسم `Unwrap` را پیاده‌سازی کند که خطای اصلی را برمی‌گرداند. به همین دلیل، می‌توان از `errors.Is` استفاده کرد تا بررسی شود آیا یک «خطای نگهبان» مشخص جایی در طول «زنجیره‌ی خطا» ظاهر می‌شود یا نه. این کار را با فراخوانی مخفیانه‌ی `Unwrap` به‌صورت مکرر انجام می‌دهد تا خطای مورد نظر پیدا شود یا زنجیره به پایان برسد.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

بررسی خطای اصلی با `errors.Is` با فعل قالب‌بندی معمولی `%v` کار نمی‌کرد.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

در نتیجه، روش خوب این است که به‌صورت پیش‌فرض از `%v` استفاده کنید و تنها اگر صراحتاً می‌خواهید به مصرف‌کننده‌تان اجازه‌ی دسترسی به خطای زیرین را بدهید، از `%w` استفاده کنید ([راهنمای سبک Go گوگل][google-go-styleguide]).

اگر در موقعیتی قرار گرفتید که می‌خواهید یک خطای نگهبان را بررسی کنید اما صراحتاً نمی‌خواهید آن را بازگشایی کنید، می‌توانید به‌جای `errors.Is` از `==` استفاده کنید.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

در مقابل، اگر خطا بسته‌بندی شده باشد، `==` آن را شناسایی نمی‌کند.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

کار کردن با `errors.Is` به‌صورت پیش‌فرض اشکالی ندارد، اما باید همیشه آگاه باشید که این یعنی کل زنجیره‌ی خطا جست‌وجو می‌شود.

## بررسی انواع (سفارشی) خطا

معادلی برای `errors.Is` وجود دارد که امکان بررسی و بازیابی خطایی از یک نوع مشخص را از زنجیره‌ی خطا فراهم می‌کند. تابع این کار `errors.As` است و درست مانند `errors.Is` نوع خطای داده‌شده را در کل زنجیره جست‌وجو می‌کند. `errors.As` تنها زمانی خطای پیدا‌شده‌ای را که با آن نوع مطابقت دارد استخراج می‌کند تا بتوانید بیشتر با آن کار کنید، مثلاً فیلدهای مشخصی را بازیابی کنید.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
مراقب نحوه‌ی نگارش مربوط به اشاره‌گرهای بالا باشید. کد تنها زمانی درست کار و کامپایل می‌شود که `customError` دقیقاً همان نوعی را داشته باشد که رابط خطا را پیاده‌سازی می‌کند. در مورد ما، این نوع `*MyCustomError` است (یک [اشاره‌گر][concept-pointers] به `MyCustomError`)، نه خود `MyCustomError`.

علاوه بر این، آرگومان دوم باید اشاره‌گری به متغیر خطا باشد. چون خطای ما از قبل یک اشاره‌گر است، آنچه به `errors.As` می‌دهیم اشاره‌گری به یک اشاره‌گر (به MyCustomError) است. تنها با درست تنظیم شدن این موارد است که Go می‌تواند متغیر را با خطایی که پیدا کرده پر کند.
~~~~

مثل قبل، اگر هنگام فراخوانی `Errorf` از `%v` استفاده می‌شد، `errors.As` نمی‌توانست آن نوع خطا را پیدا کند.

اگر به دلایلی نمی‌خواهید بازگشایی کنید، می‌توان به‌جای آن از تأیید نوع استفاده کرد (معادل `==` در بالا).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

اگر خطا بسته‌بندی شده باشد، تأیید نوع نمی‌تواند نوع خطا را شناسایی کند.

## امکان بازگشایی برای خطاهای انواع سفارشی

گاهی فقط بسته‌بندی یک خطا همراه با متنی اضافی کافی نیست. می‌توانید به‌جای آن یک نوع خطای سفارشی بسازید که خطای اصلی و داده‌ی ساخت‌یافته‌ی اضافی‌ای را که می‌خواهید اضافه کنید در خود نگه دارد. اگر می‌خواهید برای نوع خطای خود امکان بازگشایی فراهم کنید، تنها کاری که باید بکنید این است که به‌صورت دستی متدی به اسم `Unwrap() error` اضافه کنید تا رابط `Unwrap` برآورده شود.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## ترکیب چند خطا

در Go 1.20، تابع جدیدی به اسم `Join` به بسته‌ی داخلی `errors` اضافه شد. `Join` امکان می‌دهد چند خطا را به گونه‌ای با هم ترکیب کنید که همچنان بازگشایی، یعنی بررسی یک خطا یا نوع خطای مشخص در طول زنجیره، ممکن باشد. با این کار، زنجیره‌ی خطا در واقعیت می‌تواند یک درخت خطا باشد. اطلاعات بیشتر را می‌توانید در [یادداشت‌های انتشار][release-notes] و [مستندات][doc-join] پیدا کنید.

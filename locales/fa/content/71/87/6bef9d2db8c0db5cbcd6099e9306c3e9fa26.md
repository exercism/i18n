# درباره

## نوع ترکیبی

تعریف نوع‌های سفارشی در برنامه‌هایمان اغلب مفید است.

ساختن نوع‌های اولیه‌ی جدید ممکن است، اما به‌ندرت انجام می‌شود.
[نوع‌های اولیه‌ی][primitive] توکار انتخابی دلبخواهی نیستند: آن‌ها کاملاً با نوع‌های استانداردِ کامپایلر LLVM که Julia برای کامپایل JIT از آن استفاده می‌کند، مطابقت دارند.

بسیار مفیدتر، توانایی تعریف «[انواع ترکیبی][composite-types]» با فیلدهای نام‌دار است.

زبان‌های دیگر نیز ساختاری مشابه دارند و آن‌ها را `structs` یا `records` می‌نامند.
مستندات Julia آن‌ها را `composite types` می‌نامد، هرچند (با کمی ناهماهنگی) نحوه‌ی نگارش زبان آن‌ها را با کلیدواژه‌ی `struct` تعریف می‌کند.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

چند نکته در مثال بالا ارزش توجه دارد:

- برای `id` هیچ نوعی مشخص نشده است، بنابراین کامپایلر آن را `id::Any` تفسیر می‌کند.
  - **نکته:**: در عمل، بهترین کار این است که با مشخص کردن نوع یک فیلد به‌صورت یک نوع عینی، به کامپایلر کمک کنید.
  - در یک [مفهوم آینده][parametric] خواهیم دید که استفاده از پارامترها گزینه‌ی دیگری است.
- از اسم نوع به‌عنوان سازنده استفاده می‌شود، مانند `Person(id, name, age)`، تا نمونه‌ای از نوع `Person` ساخته شود.
- به فیلدهای تک‌تک می‌توان با نماد نقطه دسترسی داشت، همان‌طور که در [تاپل‌های نام‌دار][named-tuple].

نمونه‌های نوع `Person` تغییرناپذیرند، بنابراین به‌روزرسانی مجاز نیست.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

اگر تغییرپذیری لازم باشد، `mutable` را به تعریف اضافه کنید.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

سازنده به‌طور پیش‌فرض لازم می‌داند که فیلدها به همان ترتیبی که در تعریف آمده‌اند ظاهر شوند، و این برای نوع‌های پیچیده‌تر ناخوشایند می‌شود.

استفاده از ماکروی `@kwdef` دو قابلیت تازه فراهم می‌کند:

- سازنده از کلیدواژه‌ها استفاده می‌کند، نه از جایگاه.
- فیلدها می‌توانند مقدار پیش‌فرض داشته باشند و به‌صورت اختیاری می‌توان آن‌ها را از سازنده حذف کرد.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## سلسله‌مراتب نوع ترکیبی

تا اینجا فقط نوع‌های ترکیبی عینی ساخته‌ایم.
اگر بررسی کنید، همه زیرنوع‌های `Any` هستند.

وقتی چند نوع مرتبط می‌سازید، احتمالاً منطقی‌تر است که برای آن‌ها سلسله‌مراتبی تعریف کنید.
این کار بسیار ساده است.

ابتدا یک نوع انتزاعی بسازید:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

سپس، عملگر `<:` را در تعریف نوع بگنجانید تا رابطه را نشان دهید.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

در صورت نیاز تکرار کنید و به یاد داشته باشید که زیرنوع‌سازیِ نوع‌های عینی مجاز نیست.

برای سلسله‌مراتب پیچیده‌تر، به‌اندازه‌ی لازم زیرنوع‌های انتزاعی بسازید.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

ارزش چنین سلسله‌مراتبی وقتی روشن‌تر می‌شود که به مفهوم `Multiple Dispatch` برسیم و ببینیم توابع چگونه با انواع آرگومان‌ها برخورد می‌کنند.


## سازنده‌های درونی

در آغاز این مفهوم دیدیم که از اسم نوع به‌عنوان سازنده استفاده می‌شود تا نمونه‌هایی از آن نوع ساخته شود:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

در اینجا، `Person()` با نام `outer constructor` شناخته می‌شود.
انواع فیلدها از نظر سازگاری با تعریف نوع بررسی می‌شوند و در صورت لزوم خطایی صادر می‌شود.

فرض کنید بخواهیم بر _مقدارهای_ ورودی محدودیت بگذاریم، نه فقط بر _نوع‌ها_؟

در این صورت می‌توانیم یک `inner constructor` را درون تعریف نوع بگنجانیم تا بررسی‌های لازم را انجام دهد.

برای مثال، یک نوع انتزاعی `AbstractPoint` داریم که قرار است مختصات `(x, y)` بگیرد، اما زیرنوعی با محدودیت `y > x` می‌خواهیم.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

تابع `new()` را _فقط_ می‌توان در سازنده‌های درونی به کار برد، و اگر ورودی‌ها معتبر باشند نمونه‌ی موردنظر را برمی‌گرداند.

برای ورودی نامعتبر، می‌توانیم مانند مثال با یک پیام خطا متوقف شویم.
در غیر این صورت، ممکن است ترجیح دهید از یک جای‌نگهدار مانند `nothing` یا `missing` استفاده کنید.
برای اطلاعات بیشتر درباره‌ی این‌ها، به مفهوم [`Nothingness`][nothingness] مراجعه کنید.

# پیوست دستورالعمل‌ها

## وظیفه

دو رویه پیاده‌سازی کنید.

- `custom_error_message message` یک خطا ایجاد می‌کند، و `message` پیام خطا است.
- `handle_error script` اسکریپت داده‌شده را اجرا می‌کند و رشته‌ای برمی‌گرداند که توضیح می‌دهد چه اتفاقی افتاده است:

  | وقتی اسکریپت… | مقدار بازگشتی |
  | --- | --- |
  | تقسیم بر صفر | `"division by zero"` |
  | فایلی را باز می‌کند که وجود ندارد | `"file does not exist"` |
  | یک رویه را فراخوانی می‌کند که وجود ندارد | `"proc does not exist"` |
  | هر خطای دیگری ایجاد می‌کند | `"unknown error"` |
  | موفق می‌شود | `"success"` |

## ایجاد خطاها

Tcl دو دستور برای ایجاد خطا دارد.

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` یک _کد خطا_ را به عنوان اولین آرگومانش لازم دارد.
کد خطا فهرستی است که به یک گرداننده می‌گوید چه نوع خطایی رخ داده است، تا بتواند بدون تجزیه‌ی متن پیام پاسخ دهد.
محتوای آن به خودتان بستگی دارد: `{MYAPP BADTHING}` فقط یک مثال است، و هر فهرست غیرخالی کار می‌کند.
طبق قرارداد، از عمومی به خاص می‌رود.
یک گرداننده آن را با یک الگوی `try ... trap` منطبق (که در ادامه توضیح داده می‌شود) می‌گیرد، مانند `trap {MYAPP BADTHING}`، یا `trap {MYAPP}` برای گرفتن هر خطای `MYAPP`.
`error` یک کد خطای اختیاری به عنوان سومین آرگومانش می‌گیرد: `error message ?info? ?code?`.

## مدیریت خطاها با `catch`

[`catch`][catch] یک اسکریپت را اجرا می‌کند و به جای ایجاد خطا، یک _کد تکمیل_ صحیح برمی‌گرداند:

| کد | معنی |
| --- | --- |
| 0 | `ok` |
| 1 | `error` |
| 2 | `return` |
| 3 | `break` |
| 4 | `continue` |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

آرگومان دوم اختیاری، نتیجه (یا پیام خطا) را دریافت می‌کند.
آرگومان سوم اختیاری، یک _دیکشنری گزینه‌ها_ را دریافت می‌کند که شامل `-errorcode` و `-errorinfo` (ردیابی پشته) است.

مزایا:

- کوچک و انعطاف‌پذیر است.
- برای موارد ساده کوتاه است، مانند `if {[catch {open $f} fh]} {...}`.

معایب:

- باید خودتان کد تکمیل را بررسی کنید.
  یک `if {[catch ...] != 0} { handle error }` بی‌دقت، `return`، `break` و `continue` را هم به عنوان خطا در نظر می‌گیرد.
- خطاهایی که مدیریت نمی‌کنید، بلعیده می‌شوند مگر اینکه خودتان دوباره آنها را ایجاد کنید.
- هیچ راه داخلی برای اجرای کد پاک‌سازی، چه اسکریپت شکست بخورد و چه نه، وجود ندارد.

## مدیریت خطاها با `try`

[`try`][try] یک اسکریپت را اجرا می‌کند و نتیجه را به اولین گرداننده‌ی منطبق می‌فرستد.
یک بند `finally` اختیاری همیشه اجرا می‌شود، که آن را به مکان خوبی برای آزادسازی منابعی مانند کانال‌های فایل تبدیل می‌کند.

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

مزایا:

- ساختار واضح است: یک گرداننده برای هر نوع نتیجه.
- `finally` همیشه اجرا می‌شود.
- نتایجی که هیچ گرداننده‌ای با آنها منطبق نمی‌شود، بدون تغییر به فراخواننده منتقل می‌شوند.

معایب:

- برای موارد ساده کمی پرحرف‌تر از `catch` است.

### `try ... on` در برابر `try ... trap`

دو نوع گرداننده وجود دارد.

`on code {msgVar optionsVar}` با _کد تکمیل_ منطبق می‌شود: `ok`، `error`، `return`، `break` یا `continue`.
هر خطا کد تکمیل `error` را دارد، بنابراین `on error` نمی‌تواند تقسیم بر صفر را از یک فایل گم‌شده تشخیص دهد.
باید به متن پیام نگاه کنید، که شکننده است: پیام‌ها برای انسان‌ها هستند و ممکن است بین نسخه‌های Tcl تغییر کنند.

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` با _کد خطا_ منطبق می‌شود.
گرداننده زمانی منطبق می‌شود که الگو پیشوندی از فهرست `-errorcode` باشد.
این نوع خطا را به طور قابل اعتماد مشخص می‌کند.

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

یک الگوی خالی، `trap {}`، با هر خطایی منطبق می‌شود.
گرداننده‌ها به ترتیب بررسی می‌شوند، پس جامع‌ترین را آخر قرار دهید.

## یافتن کد خطا

`ARITH DIVZERO` کجا مستند شده است؟
بیشتر فقط در کد منبع، اما Tcl آن را به شما نشان می‌دهد.
پس از یک خطا، متغیر سراسری `errorCode` کد خطای آخرین خطا را نگه می‌دارد:

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

در داخل یک برنامه، آن را از دیکشنری گزینه‌ها دریافت کنید:

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

آخرین عنصر یک کد خطا اغلب یک پیام قابل خواندن برای انسان است، یا نام آنچه باعث خطا شده است.
آن را از الگوی `trap` خود حذف کنید: `{ARITH DIVZERO}` را trap کنید، نه `{ARITH DIVZERO {divide by zero}}`.

### چند کد خطای رایج

این جدول کامل نیست.
از تکنیک بالا برای یافتن کد هر خطای دیگر استفاده کنید.

| موقعیت | مثال | کد خطا |
| --- | --- | --- |
| تقسیم بر صفر | `expr {1 / 0}` | `ARITH DIVZERO ...` |
| خطای دامنه‌ی ریاضی | `expr {sqrt(-1)}` | `ARITH DOMAIN ...` |
| فایل یافت نشد | `open nosuchfile r` | `POSIX ENOENT ...` |
| دسترسی رد شد | `open /root/x w` | `POSIX EACCES ...` |
| دستور ناشناخته | `no::such::proc` | `TCL LOOKUP COMMAND name` |
| متغیر ناشناخته | `set nosuchvar` | `TCL LOOKUP VARNAME name` |
| تعداد آرگومان‌های نادرست | `string length a b` | `TCL WRONGARGS` |
| دیکشنری نامعتبر | `dict size {1 2 3}` | `TCL VALUE DICTIONARY` |
| فهرست نامعتبر | `llength "a \{b"` | `TCL VALUE LIST ...` |

کدهای خطای `POSIX` از نام‌های `errno` سیستم‌عامل استفاده می‌کنند، مانند `ENOENT`، `EACCES` و `EEXIST`.

## راهنما: اسکریپت کجا اجرا می‌شود

`handle_error` یک اسکریپت از فراخواننده‌اش دریافت می‌کند.
اگر آن را با `try $script` اجرا کنید، در محدوده‌ی `handle_error` ارزیابی می‌شود، نه محدوده‌ی فراخواننده.
برای ارزیابی آن در جایی که نوشته شده است، از [`uplevel`][uplevel] استفاده کنید: `try {uplevel 1 $script} ...`.

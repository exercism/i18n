# مقدمة

## واجهة `error`

لا تتم معالجة الأخطاء في Go عبر الاستثناءات.
بل إن الأخطاء *قيم* عادية من أنواع تُطبّق الواجهة المدمجة `error`.
وواجهة `error` بسيطة للغاية.
فهي تحتوي على طريقة واحدة فقط هي `Error()`، التي تُرجع رسالة الخطأ على هيئة سلسلة نصية.

```go
type error interface {
  Error() string
}
```

كلما عرّفت دالة قد يحدث فيها خطأ أثناء التنفيذ ويحتاج إلى الوصول إلى المستدعي، عليك أن تُضمّن `error` ضمن أنواع الإرجاع.
وإذا كانت للدالة قيم إرجاع متعددة، فمن المتعارف عليه أن يأتي `error` دائمًا في المرتبة الأخيرة.

```go
func DoSomething() (int, error) {
  // ...
}
```

## إنشاء خطأ بسيط وإرجاعه

لا يلزمك دائمًا أن تُطبّق واجهة `error` بنفسك.
لإنشاء خطأ بسيط، يمكنك استخدام الدالة `errors.New()` من حزمة المكتبة القياسية `errors`.
كل ما تحتاج إلى تمريره هو رسالة الخطأ على هيئة سلسلة نصية، وستتولى `errors.New()` إنشاء قيمة تحتوي على رسالتك وتُطبّق واجهة `error`.

وإذا أرجعت الدالة خطأً، فمن الممارسات الجيدة إرجاع القيمة الصفرية لبقية معاملات الإرجاع:

```go
func DoSomething() (SomeStruct, int, error) {
  // ...
  return SomeStruct{}, 0, errors.New("failed to calculate result")
}
```

~~~~exercism/caution
لا ينبغي أن تفترض أن جميع الدوال تُرجع قيمًا صفرية لبقية قيم الإرجاع عند وجود خطأ.
من أفضل الممارسات أن تفترض أنه لا يمكن الاعتماد على أي من قيم الإرجاع الأخرى إذا حدث خطأ.
الاستثناء الوحيد هو الحالات التي يذكر فيها التوثيق بوضوح أن قيم الإرجاع الأخرى ذات معنى عند حدوث خطأ.
~~~~

إذا أردت استخدام خطأ بسيط كهذا في مواضع متعددة، فبدلًا من استخدام `errors.New` في موضعها، عرّف متغيرًا للخطأ.
ومن المتعارف عليه أن يبدأ اسم المتغير بـ `Err` أو `err` (حسب ما إذا كان مُصدَّرًا أم لا).
غالبًا ما تُسمّى متغيرات الأخطاء هذه *الأخطاء الحارسة*.

```go
import "errors"

var ErrNotFound = errors.New("resource was not found")

func DoSomething() error {
  // ...
  return ErrNotFound
}
```

أرجِع `nil` للخطأ لتشير إلى عدم حدوث أي أخطاء أثناء تنفيذ الدالة:

```go
func Foo() (int, error) {
  return 10, nil
}
```

## التحقق من الأخطاء

إذا استدعيت دالة تُرجع خطأً، فمن الشائع تخزين قيمة الخطأ في متغير باسم `err`.
وقبل أن تستخدم النتيجة الفعلية للدالة، عليك أن تتحقق من عدم وجود خطأ.

ولتجنّب تعشيش «المسار السعيد» في كودك، ينبغي التعامل مع حالات الخطأ أولًا.
يمكننا استخدام `==` و`!=` لمقارنة الخطأ بـ `nil`، ونعرف أن هناك خطأ عندما لا يكون `err` مساويًا لـ `nil`.

```go
func processUserFile() error {
	file, err := os.Open("./users.csv")
	if err != nil {
		return err
	}

	// do something with file
}
```

في معظم الحالات، سيُرجع الخطأ إلى أعلى مكدّس الدوال كما في المثال أعلاه.
وثمة أسلوب آخر لمعالجة الخطأ، وهو تسجيله ثم المتابعة بعملية أخرى.
ومن الممارسات الجيدة إما إرجاع الخطأ أو تسجيله، وليس كليهما.

ولأن معظم الدوال في Go تتضمن خطأً ضمن قيم الإرجاع، فسترى نمط `if err != nil` وتستخدمه في كل مكان في كود Go.

## أنواع الأخطاء المخصصة

إذا أردت أن يتضمن خطؤك معلومات أكثر من مجرد سلسلة رسالة الخطأ، يمكنك إنشاء نوع خطأ مخصص.
وكما ذُكر سابقًا، فإن كل ما يُطبّق واجهة `error` (أي يمتلك طريقة `Error() string`) يمكن أن يكون خطأً في Go.

وعادةً ما تُستخدم بنية لإنشاء نوع خطأ مخصص.
ومن المتعارف عليه أن تنتهي أسماء أنواع الأخطاء المخصصة بـ `Error`.
ومن الأفضل أيضًا تعريف طريقة `Error() string` بمستقبِل مؤشّر، انظر [تعليق Stackoverflow][stackoverflow-errors] هذا لتعرف السبب.
لاحظ أن هذا يعني أنك تحتاج إلى إرجاع مؤشر إلى خطئك المخصص، وإلا فلن يُحتسب `error` لأن القيمة غير المؤشّرة لا توفّر طريقة `Error() string`.

```go
type MyCustomError struct {
  message string
  details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.message, e.details)
}

func someFunction() error {
  // ...
  return &MyCustomError{
    message: "...",
    details: "...",
  }
}
```

# مقدمة إلى أساسيات الصدفة

## الصدفات

_الصدفة_ برنامج يتيح لك إدخال أوامر للتفاعل مع نظام التشغيل.
قد تكون الصدفات رسومية؛ فبيئة سطح المكتب التي تستخدمها بالفأرة أو لوحة اللمس هي صدفة.
سنركّز على واجهات سطر الأوامر، حيث تكتب الأوامر وتُطبع النتائج (عادةً) في الطرفية.

هناك العديد من صدفات سطر الأوامر المختلفة.
يوفّر Windows الأمرين **cmd** و**powershell**.
ويوفّر Mac وLinux «صدفات Unix»، وهي كثيرة.
الصدفة الافتراضية على Mac هي **zsh**.
**csh** صدفة قديمة ذات صياغة شبيهة بلغة C.
**bash** من أكثر الصدفات شيوعًا، خاصة على Linux.

من أوائل الصدفات على الإطلاق صدفة Bourne، واسمها **sh**.
ومع الوقت أصبحت هذه الصدفة [موحّدة قياسيًا][posix] بحيث تُوفَّر على كل نظام شبيه بـ Unix.
تعتمد صدفات كثيرة على صدفة Bourne، وغالبًا ما تضيف وظائف تفاعلية أو برمجية إضافية.

**Bash** مبنية على صدفة Bourne.
ولهذا تُسمى «**B**ourne-**a**gain **sh**ell».
وهي الصدفة الافتراضية في كثير من أنظمة Linux.
توفّر Bash إمكانات كثيرة تجعلها صدفة تفاعلية ممتعة، منها:

* مطالبة أوامر قابلة للتخصيص بالكامل،
* القدرة على استدعاء الأوامر من السجل وتعديلها،
* القدرة على التعامل مع العمليات الجارية،
* أسماء مستعارة تقلّل الكتابة،
* وغير ذلك.

لا يتناول هذا المسار كيفية استخدام bash كصدفة تفاعلية.
بل يتناول تعلّم كتابة البرامج باستخدام bash.
سيكون التركيز على استخدام bash _وحده_ لحل المشكلات، مع أنه لا قيود على الاستعانة بأدوات خارجية.

## أساسيات Bash: الأوامر والوسائط

تقرأ Bash الأوامر من مدخلاتها (وهي عادةً إما طرفية وإما ملف).
وكل سطر من المدخلات تقرؤه يُعامل على أنه _أمر_، أي تعليمة يجب تنفيذها.
(هناك حالات متقدمة قليلة، مثل الأوامر الممتدة على عدة أسطر، سنتناولها لاحقًا.)

تقسم Bash كل سطر إلى **كلمات** تفصل بينها محارف المسافات البيضاء (المسافات وحروف الجدولة).
الكلمة الأولى في السطر هي اسم _الأمر_ المطلوب تنفيذه.
وتصبح كل الكلمات المتبقية _وسائط_ لذلك الأمر (خيارات، أسماء ملفات، وما إلى ذلك).

~~~~exercism/note
في الأمثلة أدناه سنعرض لك بعض الأوامر التفاعلية التي يمكنك تشغيلها.

* يبدأ المحرف `#` _تعليقًا_.
  وتتجاهل الصدفة أي كلمات تلي التعليق؛ فالتعليق للقراءة فقط.
* يشير المحرف `$` إلى مطالبة الصدفة. 
  وإذا كنت تنسخ الأمر، فلا تُضمّن المطالبة.
~~~~

```bash
# Note: It is always a good idea to run `ls` before `rm`
# to make sure you know what you are deleting.

$ rm *            # Remove all files in the current directory.
                  # Make sure you run this in a temp directory or you can lose files!
$ ls              # List files in the current directory (no output, no files).
$ touch a   b c   # Create files 'a', 'b' and 'c'.
$ ls              # List files again; this time the outputs: 'a', 'b' and 'c'.
a  b  c
```

`rm` تطبيق يحذف الملفات المُعطاة له.
`*` محرف [glob][glob]، وهو نمط «بدل» يطابق كل الملفات في الدليل الحالي.
سنتحدث أكثر عن أنماط glob لاحقًا.

هل لاحظت وجود عدة مسافات بين `a` و`b`، ومسافة واحدة فقط بين `b` و`c`؟
لا يهم مقدار المسافات البيضاء بين الوسائط!
على سبيل المثال:

```bash
$ echo This is a test.
This is a test.
$ echo This    is    a    test.
This is a test.
```

`echo` أمر يطبع وسائطه إلى الخرج القياسي (وهو في حالتنا الطرفية).
تقسم Bash الأمر إلى خمس كلمات، وتستدعي الأمر `echo` بأربعة وسائط.
لا تُحدث المسافات الزائدة في المثال الثاني أي فرق.
ولا يعرف `echo` كيف كانت المسافات بين الكلمات في الأصل.

إذا أردنا الحفاظ على المسافات الزائدة، فعلينا تمرير الجملة كوسيط واحد.
يمكننا فعل ذلك باستخدام [علامات التنصيص][Quotes]:

```bash
$ echo "This    is    a    test."
This    is    a    test.
```

تجمّع علامات التنصيص كل ما بداخلها في _وسيط واحد_.
الوسيط هو `This    is    a    test.` بما فيه تلك المسافات تحديدًا.
لاحظ أن علامات التنصيص ليست جزءًا من الوسيط؛ إذ تزيلها bash قبل تسليم ذلك الوسيط الواحد إلى `echo`.

تفصل المسافات البيضاء الوسائط عن اسم الأمر وعن بعضها بعضًا.
من المهم تذكّر ذلك.
على سبيل المثال، ما يلي خطأ:

```bash
$ [-f file]
bash: [-f: command not found
```

القصد هنا اختبار وجود ملف اسمه `file`.
من المنطقي أن نفترض أن المسافات حول `[` و`]` لا تهم، لكن `[` في الحقيقة أمر، ويشترط أن يكون وسيطه الأخير `]`.
(سنتناول الأمر `[` بمزيد من التفصيل لاحقًا.) 
لذلك يجب أن نفصل `[` عن `-f` و`]` عن `file`.
وإلا فستظن bash أننا نحاول تنفيذ أمر اسمه `[-f` بوسيط واحد هو `file]`.
الأمر الصحيح يفصل كل الوسائط بمسافات بيضاء:

```bash
$ [ -f file ]
```

(نرى كثيرًا من الناس يحيّرهم هذا السلوك؛ إذ يظنون أن `[...]` مجرد «صياغة» ويمكنهم حذف المسافات؛ لكن `[` أمر، والمسافات مطلوبة.)

إذا كان اسم الملف يحتوي على مسافات أو محارف خاصة أخرى، فيجب تنصيقه أيضًا:

```bash
$ [ -f "my file" ]
```

## أنواع الأوامر

تفهم Bash عدة أنواع مختلفة من الأوامر: الأسماء المستعارة، والدوال، والأوامر المدمجة، والكلمات المفتاحية، والملفات التنفيذية.
وكلها _أوامر_، وتتصرف جميعها بطريقة متشابهة جدًا.

افتراضيًا لا تكون الأسماء المستعارة مفعّلة إلا في الصدفات التفاعلية، لا في نصوص الصدفة البرمجية.
ولن نتناولها هنا.

### الدوال

تحتوي الدالة على أوامر صدفة، وتتصرف كثيرًا مثل نص برمجي صغير؛ بل يمكنها أن تأخذ وسائط وتنشئ متغيرات محلية.
وعند استدعاء دالة، تُنفَّذ الأوامر داخلها.
سنغطي الدوال بتفصيل لاحقًا.

### الأوامر المدمجة

تحتوي Bash على بعض الأوامر الأساسية المدمجة فيها، مثل: `cd` (تغيير الدليل)، و`echo` (كتابة الخرج)، وما إلى ذلك.
ويمكن اعتبارها دوالً جاهزة مقدَّمة مسبقًا.

### الكلمات المفتاحية

الكلمات المفتاحية شبيهة بالأوامر المدمجة، والفرق الرئيسي أنها في الحقيقة من صياغة bash نفسها وقد تُحلَّل وفق قواعد خاصة.
على سبيل المثال، `[` أمر مدمج في bash، بينما `[[` كلمة مفتاحية في bash؛ وكلاهما يُستخدم لاختبار شروط متنوعة.
لكن الكلمة المفتاحية `[[` لها وظائف إضافية.
فهي توفّر مثلًا العامل `=~` الذي يختبر التعبيرات النمطية.

```bash
$ [[ "hello world" =~ e.*o ]]   # returns a "success" status
$ [ "hello world" =~ e.*o ]
bash: [: =~: binary operator expected
```

عوامل المقارنة بين السلاسل النصية `<` و`>` مثال آخر على كيفية تحليل الكلمات المفتاحية للكود بشكل مختلف.
وداخل `[[...]]` لا تحتاج هذه العوامل إلى أي عناية خاصة.

```bash
$ if [[ "$USER" < "n" ]]; then
    echo "$USER is in the first half of the alphabet"
fi
# => glennj is in the first half of the alphabet
```

لكن داخل `[...]` عليك تنصيقها أو تهريبها حتى لا تحللها الصدفة كعوامل إعادة توجيه.

```bash
$ if [ "$USER" < "n" ]; then
    echo "$USER is in the first half of the alphabet"
fi
# => bash: n: No such file or directory

$ if [ "$USER" \< "n" ]; then
    echo "$USER is in the first half of the alphabet"
fi
# => glennj is in the first half of the alphabet
```


### الملفات التنفيذية

النوع الأخير من الأوامر التي تستطيع bash تنفيذها هو _الملف التنفيذي_.
وهي ملفات تنفيذية (برامج) على نظام ملفات حاسوبك يمكنك تشغيلها.
(وقد تُسمى الملفات التنفيذية أيضًا _أوامر خارجية_ أو _تطبيقات_.)
يُستدعى الملف التنفيذي عادةً بكتابة اسمه فقط؛ فالمسار الكامل إلى الملف لا يكون مطلوبًا في الغالب.
ويمكن فعل ذلك لأن bash تستخدم متغيرًا معرَّفًا مسبقًا يساعدها في إيجاد موقع الملفات التنفيذية الشائعة.
هذا المتغير اسمه `PATH`.
وهو مجموعة أسماء أدلة يفصل بينها محرف النقطتين الرأسيتين (مثل `/usr/bin:/bin`). 
وعندما يُحدَّد أمر (مثل `myprogram` أو `ls`) دون مسار ملف (وليس اسمًا مستعارًا أو دالة أو أمرًا مدمجًا أو كلمة مفتاحية)، تبحث bash في الأدلة المذكورة في `PATH`.
وتُبحث الأدلة بالترتيب، من اليسار إلى اليمين، للتحقق مما إذا كانت تحتوي على ملف تنفيذي بالاسم المعطى.

إذا كان الملف التنفيذي خارج مسار معروف، فيجب تحديد مسار الملف التنفيذي.
فبالنسبة للملف التنفيذي `myprogram` في الدليل الحالي، استخدم `./myprogram`؛ وإذا كان في الدليل `/opt/somedirectory` فاستخدم `/opt/somedirectory/myprogram`.

نصيحة: يمكن استخدام الأمر `type` للحصول على تفاصيل عن الأمر:

```bash
$ type rm
rm is hashed (/bin/rm)
# or it might return: `rm is /bin/rm`

$ type cd
cd is a shell builtin
```

## النصوص البرمجية

_النص البرمجي_ تسلسل من الأوامر مخزّن في ملف.
تقرأ bash الملف وتعالج الأوامر بالترتيب.
ولا تنتقل إلى الأمر التالي إلا بعد انتهاء الأمر الحالي.
والاستثناء هو أن يكون أمر ما قد حُدّد ليعمل بشكل غير متزامن (في الخلفية).
لا تقلق كثيرًا بشأن هذه الحالة الآن؛ فسنتعلم كيف يعمل ذلك لاحقًا.

أي مثال على سطر أوامر في هذا الدليل يمكن استخدامه أيضًا في نص برمجي.

إنشاء نص برمجي أمر سهل.
ابدأ بإنشاء ملف جديد، وضع هذا في السطر الأول:

```bash
#!/bin/bash
```

يُسمى هذا السطر _توجيه المفسّر_ (ويُسمى أيضًا _hashbang_ أو **_shebang_**).
وهو يحدد أن `/bin/bash` هو المفسّر الذي يُستخدم عندما يُستعمل الملف كملف تنفيذي في أمر ما.
عندما ينفّذ نواة نظام التشغيل _ملفًا غير ثنائي_، فإنه يقرأ السطر الأول من الملف.
وإذا بدأ السطر بـ`#!`، استخدمت النواة السطر لتحديد المفسّر الذي يُحال إليه الملف.
(وهناك طرق صحيحة أخرى لفعل ذلك أيضًا، انظر أدناه.)
ويجب أن يكون `#!` في بداية الملف تمامًا، دون مسافات أو أسطر فارغة قبله.
ستظهر أوامر نصنا البرمجي في أسطر منفصلة تحت هذا السطر.

نصيحة: بدلًا من `#!/bin/bash`، يمكنك استخدام

```bash
#!/usr/bin/env bash
```

يبحث `env` في `$PATH` عن الملف التنفيذي الذي يسميه وسيطه الأول (في هذه الحالة «bash»).
ولشرح أكثر تفصيلًا لهذه التقنية وكيف تختلف عن `#!/bin/bash` التقليدي، انظر [هذا السؤال في StackOverflow][env bash].

لا تنخدع بنصوص برمجية أو أمثلة على الإنترنت تستخدم `/bin/sh` كمفسّر.
**`sh` ليس `bash`!**
فـbash نفسها صدفة «متوافقة مع sh»، بمعنى أنها تستطيع تشغيل معظم نصوص `sh` البرمجية وتحمل كثيرًا من الصياغة نفسها.
لكن العكس غير صحيح؛ فبعض ميزات bash تتعطل أو تسبب سلوكًا غير متوقع في `sh`.
في الواقع، لا توجد صدفة `sh` واحدة.
فهناك تطبيقات صدفات كثيرة تدعم صياغة POSIX-sh.
وبحسب نظام تشغيلك، قد تكون في الحقيقة تشغّل bash أو ash أو dash أو صدفة أخرى عندما تشغّل `sh`.

بعد إنشاء ملف النص البرمجي، يمكن تنفيذه بهذه الطريقة:

```bash
$ bash myscript
```

في هذا المثال ننفّذ _الأمر_ `bash` ونطلب منه قراءة النص البرمجي الذي أعطيناه له بوصفه _وسيطًا_.
وعندما نفعل ذلك بهذه الطريقة، يكون سطر `#!` مجرد _تعليق_.

بدلًا من ذلك، يمكننا منح نصوصنا البرمجية صلاحيات تنفيذ.
بهذه الطريقة يمكننا تنفيذ النص البرمجي كأي ملف تنفيذي آخر بدلًا من استدعاء bash يدويًا:

```bash
$ chmod +x myscript  # Mark the file as executable.
$ ./myscript         # Now, myscript can be executed directly
                     # instead of having to specify bash.
```

وعندما نشغّل الأمر بهذه الطريقة، يستخدم نظام التشغيل سطر `#!` لتحديد المفسّر الذي سيُستخدم لتشغيل نصك البرمجي.

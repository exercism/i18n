# نبذة

## إضافة السياق إلى الأخطاء

استكشفنا معالجة الأخطاء الأساسية في Go في [مفهوم الأخطاء][concept-errors]. وكما تعلمت هناك، لا تحمل الأخطاء افتراضيًا تتبّعات المكدس معها. وهذا يجعل من الضروري التأكد من أن الخطأ نفسه يحتوي على معلومات كافية لتحديد المشكلة.

إذا أردنا إضافة معلومات إلى خطأ موجود باستخدام الأدوات التي نعرفها بالفعل، يمكننا كتابة شيء كهذا لإنشاء خطأ جديد يجمع نص الخطأ الأصلي والمعلومات الإضافية:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

لحسن الحظ، تحتوي حزمة `fmt` من المكتبة القياسية على صيغة مختصرة لهذا على شكل دالة `Errorf`. وهذا يتيح لك، على سبيل المثال، إضافة معلومات بسهولة عن السياق الذي وقع فيه الخطأ.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

ما لم تكن متأكدًا من أن الخطأ يتضمن بالفعل معلومات كافية، فحاول أن تعتاد على إضافة السياق إلى الخطأ دائمًا قبل إرجاعه من دالة. وهذا يعني أن نمط معالجة الأخطاء المعتاد لديك يجب أن يبدو هكذا:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

كما يظهر في الأمثلة، العُرف هو فصل الخطأ عن الرسالة المضافة بنقطتين. وكما هو الحال مع رسالة الخطأ الأصلية، يجب ألا تبدأ رسالة السياق بحرف كبير وألا تُضاف نقطة في نهايتها.

~~~~exercism/note
عند إضافة السياق إلى خطأ ما، قد يغريك أن تبدأ الرسالة بعبارة "failed to ..." أو ما شابه. لكن بما أن الخطأ قد يراكم الكثير من السياق الإضافي أثناء صعوده في سلسلة الدوال، فقد يجعل هذا الرسالة النهائية التي ستُسجَّل أو التي سيراها المستخدم أصعب في القراءة أو مليئة بالتكرار.

إليك مثالًا للتوضيح:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

لذا أبقِ هذه النتيجة النهائية في ذهنك عند كتابة رسائل السياق، وامتنع عن إضافة نص عن كون شيء ما لم يجرِ كما هو متوقع. فهذا عادةً واضح من السياق (مثل مستوى السجل "ERROR") ورسالة الخطأ الأصلية.
~~~~

غالبًا ما تكون طريقة إضافة المعلومات هذه إلى الخطأ كافية، لكن هناك حالات تريد فيها أن تتيح لمستهلك خطئك التحقق من الخطأ الأصلي الكامن أو استرجاعه. وتسمى إضافة السياق بالطريقة التي تتيح ذلك "تغليف الخطأ" في Go.

## تغليف الأخطاء والتحقق من الأخطاء الحارسة

يمكن تحقيق تغليف الأخطاء بتغيير بسيط جدًا في الكود الذي رأيناه أعلاه. لتغليف خطأ، عليك استخدام فعل التنسيق `%w` بدلًا من `%v`. خلف الكواليس، سيضمن هذا أن الخطأ الناتج يطبّق طريقة `Unwrap` تُرجع الخطأ الأصلي. ولهذا يمكن بعد ذلك استخدام `errors.Is` للتحقق مما إذا كان خطأ حارس معيّن يظهر في مكان ما على "سلسلة الأخطاء". وهي تفعل ذلك عبر استدعاء `Unwrap` سرًا بشكل متكرر حتى يُعثر على الخطأ المعني أو تنتهي السلسلة.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

لن يعمل التحقق من الخطأ الأصلي باستخدام `errors.Is` مع فعل التنسيق العادي `%v`.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

ونتيجةً لذلك، من الممارسات الجيدة استخدام `%v` افتراضيًا، ولا تستخدم `%w` إلا إذا أردت صراحةً أن تتيح لمستهلكك الوصول إلى خطأ كامن ([دليل أسلوب Google Go][google-go-styleguide]).

إذا وجدت نفسك في موقف تريد فيه التحقق من خطأ حارس لكنك لا تريد فكّ التغليف صراحةً، يمكنك استخدام `==` بدلًا من `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

في المقابل، لن يتعرف `==` على الخطأ إذا كان مغلّفًا.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

لا بأس بالعمل مع `errors.Is` افتراضيًا، لكن ينبغي أن تكون مدركًا دائمًا أن هذا يعني البحث في سلسلة الأخطاء بأكملها.

## التحقق من أنواع الأخطاء (المخصصة)

هناك ما يكافئ `errors.Is` ويتيح التحقق من خطأ من نوع معيّن واسترجاعه من سلسلة الأخطاء. والدالة المخصصة لذلك هي `errors.As`، ومثل `errors.Is` تمامًا، ستبحث عن نوع الخطأ المعطى على طول السلسلة بأكملها. لا يستخرج `errors.As` الخطأ الذي وجده والمطابق للنوع إلا بعد ذلك لتتمكن من العمل عليه أكثر، مثل استرجاع حقول معيّنة.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
كن حذرًا مع الصياغة المتعلقة بالمؤشرات أعلاه. لن يعمل الكود ويُصرَّف بشكل صحيح إلا إذا كان `customError` من النوع الدقيق الذي يطبّق واجهة الخطأ. وفي حالتنا، هذا هو `*MyCustomError` (مؤشر إلى `MyCustomError`)، وليس `MyCustomError` نفسه.

وفوق ذلك، يجب أن تكون الوسيطة الثانية مؤشرًا إلى متغير الخطأ. وبما أن خطأنا مؤشر بالفعل، فإن ما نمرره إلى `errors.As` هو مؤشر إلى مؤشر (إلى MyCustomError). وبإعداد هذا بشكل صحيح فقط، يمكن لـ Go عندئذٍ أن يملأ المتغير بالخطأ الذي وجده.
~~~~

وكما في السابق، لم يكن `errors.As` ليعثر على نوع الخطأ لو استُخدم `%v` عند استدعاء `Errorf`.

وإذا كنت لا تريد فكّ التغليف لسبب ما، يمكنك استخدام تأكيد النوع بدلًا من ذلك (مكافئ لـ `==` أعلاه).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

لن يتمكن تأكيد النوع من التعرف على نوع الخطأ لو كان الخطأ مغلّفًا.

## السماح بفكّ تغليف أخطاء من أنواع مخصصة

أحيانًا لا يكفي مجرد تغليف خطأ ببعض النص الإضافي. يمكنك بدلًا من ذلك إنشاء نوع خطأ مخصص يحمل الخطأ الأصلي والبيانات المهيكلة الإضافية التي تريد إضافتها. وإذا أردت السماح بفكّ التغليف لنوع خطئك، فكل ما عليك فعله هو إضافة طريقة `Unwrap() error` يدويًا بحيث تُستوفى واجهة `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## دمج أخطاء متعددة

في Go 1.20، أُضيفت دالة `Join` جديدة إلى حزمة `errors` المدمجة. تتيح `Join` دمج أخطاء متعددة معًا بطريقة لا تزال تسمح بفكّ التغليف، أي التحقق من خطأ معيّن أو نوع خطأ على طول السلسلة. وبهذا، قد تكون سلسلة الأخطاء في الواقع شجرة أخطاء فعلًا. يمكن العثور على مزيد من المعلومات في [ملاحظات الإصدار][release-notes] و[التوثيق][doc-join].

## التغاير المشترك والتغاير المضاد

عند استخدام أنواع الاتحاد، يجب أن تكون على دراية بمفهومَي التغاير المشترك والتغاير المضاد. هذان المفهومان مشروحان في [التوثيق](https://www.php.net/manual/en/language.oop5.variance.php)، لكن هذه الأمثلة قد تساعدك.

لنفترض أن لدينا صنف `Calculator` يستخدم دالة مثل المثال السابق:

```php
class Calculator
{
    public function add(int|float $x, int|float $y): int|float
    {
        return $x + $y;
    }
}
```

إذا ورثت من الصنف، فيُسمح لك بتغيير أنواع المعاملات وأنواع الإرجاع، لكن وفق القواعد التالية فقط.

أولًا، يمكن أن تكون أنواع المعاملات "أوسع"، أي أنها تقبل أنواعًا أكثر من الصنف الأساسي. على سبيل المثال، هذا مسموح:

```php
class StringCalc extends Foo
{
    public function add(float|int|string $x, float|int|string $y): int|float
    {
        if (!is_numeric($x) || !is_numeric($y)) {
            throw new \InvalidArgumentException('$x and $y must be numeric');
        }
        return $x + $y;
    }
}
```

يمكننا استبدال `Calculator` الأصلي بـ `StringCalc` وسيظل كل شيء يعمل. سيظل بإمكان المستدعي تمرير قيم من النوع `float` أو `int` كما كان في الأصل، وسيظل نوع الإرجاع هو `int` أو `float` المتوقع.

وبالمثل، يمكنك تضييق نوع الإرجاع، أي جعله أكثر تحديدًا بإزالة أنواع من نوع الاتحاد. هذا المثال يستفيد من هذه القاعدة:

```php
class IntCalc extends Calculator
{
    public function add(float|int $x, float|int $y) : int
    {
        return (int)($x + $y);
    }
}
```

بما أن `IntCalc` لا يزال يقبل `int` و`float`، فيمكنه أن يحل محل `Calculator` الأصلي بلا مشاكل.

لقراءة المزيد عمّا هو مسموح وما هو غير مسموح، يمكنك الرجوع إلى [مبدأ استبدال ليسكوف (LSP)](https://en.wikipedia.org/wiki/Liskov_substitution_principle).

ولمثال على ما لن يكون مسموحًا، ألقِ نظرة على `InvalidCalc` أدناه:

```php
class InvalidCalc extends Calculator
{
    public function add(int $x, int $y) : int|float|string
    {
        // Declaration must be compatible with Calculator->add(x: float|int, y: float|int)

        // Return type declaration must be compatible with Calculator->add(x: float|int, y: float|int) : float|int
    }
}
```

لن يُصرَّف صنف `InvalidCalc` وسيواجه مشكلتين. فبتقليله لما هو مسموح به كمعامل، لن يستطيع `InvalidCalc` أن يحل محل `Calculator` الأصلي لأنه لم يعد يقبل `float`. إضافة إلى ذلك، يمكنه الآن أن يُرجع `string`، وهو أيضًا ليس ضمن أنواع الإرجاع المسموح بها في الصنف الأصلي.

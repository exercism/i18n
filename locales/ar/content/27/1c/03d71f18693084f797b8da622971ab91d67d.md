## استخدام السكربت

يتطلب توليد الاختبارات نسخة محلية من مستودع [problem-specifications][problem-specifications].
ويُستحسن تشغيل السكربت من المجلد الجذر `python` حتى يصل إلى التمارين
بشكل صحيح.

شغّل `bin/generate_tests.py --help` للاطلاع على معلومات الاستخدام.


## قوالب الاختبار

تدعم قوالب الاختبار صيغة [Jinja2]، وتتيح متغيرات السياق التالية المستمدة
من البيانات القياسية:
- `exercise`: اسم التمرين بصيغة الشرطات الواصلة (مثال: `two-fer`)
- `version`: إصدار البيانات القياسية (مثال: `1.2.0`)
- `cases`: قائمة من كائنات الحالات أو قائمة من قوائم `cases`. للاطلاع على البنية
الدقيقة الخاصة بالتمرين الذي تعمل عليه، راجع
`canonical-data.json`
- `has_error_case`: يبيّن ما إذا كانت أي حالة اختبار تتوقع رفع خطأ
(مثال: `False`)
- `additional_cases`: بنية مشابهة لـ `cases`، لكنها تُملأ من ملف `.meta/additional_tests.json` الخاص بالتمرين إن وُجد (للاطلاع على مثال، انظر `exercises/word-count/.meta/additional_tests.json`)

إضافة إلى ذلك، أُضيفت مرشّحات القوالب التالية للتسهيل:
- `to_snake`: يحوّل سلسلة نصية إلى صيغة snake_case (مثال: `{{ "CamelCaseString" | to_snake }}` -> `camel_case_string`)
- `camel_case`: يحوّل سلسلة نصية إلى صيغة CamelCase (مثال: `{{ "snake_case_string" | camel_case }}` -> `SnakeCaseString` )
- `error_case`: يتحقق مما إذا كانت حالة اختبار تتوقع رفع خطأ (مثال: `{% for case in cases%}{% if case is error_case}`)
- `regex_replace`: استبدال نصي بتعبير نمطي (مثال: `{{ "abc123" | regex_replace("\\d", "D") }}` -> `abcDDD`)


### الاصطلاحات

- تُعرَّف الماكروات ذات الاستخدام العام للبنى المتكررة كثيرًا في القوالب في `config/generator_macros.j2`.
  - يمكن استيرادها كما يلي:
  `{%- import "generator_macros.j2" as macros with context -%}`
- يجب أن تنتهي كل قوالب الاختبار بـ `{{ macros.footer() }}`.
- يجب أن تكون أسماء أصناف Python بصيغة CamelCase (مثال: `TwoFer`).
  - حوّلها باستخدام `{{ "two-fer" | camel_case }}`
- يجب أن تكون أسماء الوحدات والدوال في Python بصيغة snake_case
(مثال: `high_scores`، `personal_best`).
  - حوّلها باستخدام `{{ "personalBest" | to_snake }}`
- تُعرَّف الاختبارات الخاصة بالمسار في ملف الخيارات `.meta/additional_tests.json`. ويجب أن يحتوي
كائن JSON المعرّف في هذا الملف على مفتاح واحد، هو `cases`، وله البنية نفسها التي لـ
`cases` في `canonical-data.json`.
- يجب وضع الاختبارات الخاصة بالمسار بعد الاختبارات القياسية في ملفات
الاختبار.
- يجب تمييز الاختبارات الخاصة بالمسار في ملف الاختبار بالتعليق التالي:
```
# Additional tests for this track
```


### البنية

ستبدو معظم القوالب على هذا النحو:

```Jinja2
{%- import "generator_macros.j2" as macros with context -%}
{{ macros.header() }}

class {{ exercise | camel_case }}Test(unittest.TestCase):
    {% for case in cases -%}
    def test_{{ case["description"] | to_snake }}(self):
        value = {{ case["input"]["value"] }}
        expected = {{ case["expected"] }}
        self.assertEqual({{ case["property"] }}(value), expected)

    {% endfor %}

{{ macros.footer() }}
```


### تجاوز الاستيرادات

يمكن تجاوز الأسماء المستوردة في `macros.header()` بإضافة
قائمة بالأسماء البديلة التي تريد استيرادها (مثال: `clock`):

```Jinja2
{{ macros.header(["Clock"])}}
```


### تجاهل الخصائص

في حالات نادرة، قد تحتاج إلى استبعاد الخصائص التي
لا تُختبر في هذا المسار. ويقبل ماكرو `header` أيضًا
وسيط `ignore` (مثال: `high-scores`):

```Jinja2
{{ macros.header(ignore=["scores"]) }}
```

## إنشاء قالب

1. أنشئ ملف `.meta/template.j2` للتمرين الذي تنفّذه،
  وافتحه في محررك.
2. انسخ [مثال البنية](#Layout) والصقه في ملف القالب
  ثم احفظه.
3. أجرِ التعديلات المناسبة على ملف القالب حتى يُنتج
  كود اختبار صالحًا، بالرجوع إلى `canonical-data.json` الخاص بالتمرين
  لمعرفة أسماء المدخلات وبنية الحالات.
    - استخدم [الماكروات المتاحة](../config/generator_macros.j2) لتجنّب إعادة كتابة الأقسام الموحّدة.
    - إذا كنت تنفّذ قالبًا لتمرين موجود،
    فلست مضطرًا لمطابقة البنية الدقيقة لملف الاختبار الحالي،
    لكن تقليل الفروق سيجعل مراجعة طلبات الدمج عملية أكثر سلاسة للجميع.

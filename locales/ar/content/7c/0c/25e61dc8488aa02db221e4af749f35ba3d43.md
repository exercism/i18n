# مقدمة

## إضافة السياق إلى الأخطاء

استكشفنا معالجة الأخطاء الأساسية في Go في [مفهوم الأخطاء][concept-errors].
وكما تعلّمت هناك، فإن الأخطاء افتراضيًا لا تحمل معها تتبّعات المكدس.
وهذا يجعل من الضروري التأكد من أن الخطأ نفسه يحتوي على معلومات كافية لتحديد المشكلة.

لو أردنا إضافة معلومات إلى خطأ موجود بالأدوات التي نعرفها بالفعل، لأمكننا كتابة شيء كهذا لإنشاء خطأ جديد يجمع نصّ الخطأ الأصلي والمعلومات الإضافية:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

لحسن الحظ، تحتوي حزمة `fmt` من المكتبة القياسية على نسخة مختصرة من ذلك في صورة دالة `Errorf`.
وهذا يتيح لك، على سبيل المثال، إضافة معلومات عن السياق الذي وقع فيه الخطأ بسهولة.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

غالبًا ما تكون هذه الطريقة لإضافة المعلومات إلى خطأ كافية، لكن هناك حالات تريد فيها أن تتيح لمستهلك خطأك التحقق من الخطأ الأصلي الكامن خلفه أو استرجاعه.
وتُسمّى إضافة السياق بالطريقة التي تتيح ذلك «تغليف الخطأ» في Go.

## تغليف الأخطاء والتحقق من الأخطاء المرجعية

يمكن تحقيق تغليف الخطأ بتغيير بسيط جدًا في الكود الذي رأيناه أعلاه.
لتغليف خطأ، عليك استخدام فعل التنسيق `%w` بدلًا من `%v`.
وهذا سيضمن، من خلف الكواليس، أن الخطأ الناتج يطبّق طريقة `Unwrap` تُرجع الخطأ الأصلي.
وبفضل ذلك يمكن استخدام `errors.Is` للتحقق مما إذا كان خطأ مرجعي معيّن يظهر في مكان ما على امتداد «تسلسل الأخطاء».
وهي تفعل ذلك باستدعاء `Unwrap` سرًّا بشكل متكرر حتى يُعثر على الخطأ المعني أو ينتهي التسلسل.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

من الممارسات الجيدة استخدام `%v` افتراضيًا، وعدم استخدام `%w` إلا إذا أردت صراحةً أن تتيح لمستهلك خطأك الوصول إلى خطأ كامن ([Google Go Styleguide][google-go-styleguide]).

إذا وجدت نفسك في موقف تريد فيه التحقق من خطأ مرجعي لكنك لا تريد فك التغليف صراحةً، يمكنك استخدام `==` بدلًا من `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

لا بأس في العمل مع `errors.Is` افتراضيًا، لكن يجب أن تكون على دراية دائمًا بأن هذا يعني البحث في تسلسل الأخطاء بأكمله.

## التحقق من أنواع الأخطاء (المخصصة)

هناك ما يكافئ `errors.Is` ويتيح التحقق من خطأ من نوع معيّن في تسلسل الأخطاء واسترجاعه.
والدالة التي تفعل ذلك هي `errors.As`، وهي تمامًا مثل `errors.Is` تبحث عن نوع الخطأ المعطى على امتداد التسلسل بأكمله.
ولا تستخرج `errors.As` الخطأ الذي وجدته والمطابق للنوع إلا عندئذٍ، لتتمكن من العمل عليه أكثر، مثل استرجاع حقول معيّنة.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
كن حذرًا مع الصياغة المتعلقة بالمؤشرات أعلاه.
لن يعمل الكود ولن يُترجم بشكل صحيح إلا إذا كان `customError` من النوع نفسه بالضبط الذي يطبّق واجهة الخطأ.
في حالتنا، هذا النوع هو `*MyCustomError` ([مؤشر][concept-pointers] إلى `MyCustomError`)، وليس `MyCustomError` نفسه.

وفوق ذلك، يجب أن يكون الوسيط الثاني مؤشرًا إلى متغير الخطأ.
ولأن خطأنا هو بالفعل مؤشر، فإن ما نمرّره إلى `errors.As` هو مؤشر إلى مؤشر (إلى MyCustomError).
وفقط عند إعداد ذلك بشكل صحيح يمكن لـ Go أن يملأ المتغير بالخطأ الذي وجده.
~~~~

وكما سبق، لن تكون `errors.As` قد وجدت نوع الخطأ لو استُخدم `%v` عند استدعاء `Errorf`.

إذا لم ترغب في فك التغليف لسبب ما، يمكنك استخدام تأكيد النوع بدلًا من ذلك (وهو مكافئ لـ `==` أعلاه).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

لن يتمكن تأكيد النوع من تحديد نوع الخطأ إذا كان الخطأ قد غُلّف.

## السماح بفك تغليف الأخطاء ذات الأنواع المخصصة

أحيانًا لا يكفي مجرد تغليف خطأ ببعض النص الإضافي.
يمكنك بدلًا من ذلك إنشاء نوع خطأ مخصص يحمل الخطأ الأصلي والبيانات المهيكلة الإضافية التي تريد إضافتها.
وإذا أردت السماح بفك التغليف لنوع خطأك، فكل ما عليك فعله هو إضافة طريقة `Unwrap() error` يدويًا لتستوفي واجهة `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

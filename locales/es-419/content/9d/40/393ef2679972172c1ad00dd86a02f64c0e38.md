# Análisis estático

El uso principal de [configlet](/docs/building/configlet) es el análisis estático: comprobar que los archivos de configuración de un track estén correctamente estructurados, tanto sintáctica como semánticamente. Los tracks mal configurados pueden no sincronizarse correctamente, verse mal en el sitio web o dar una experiencia de usuario poco óptima, así que las comprobaciones de configlet cumplen un papel importante a la hora de mantener la integridad de Exercism.

## Uso

El comando `lint` se puede usar para analizar un track.

```
configlet [global-options] lint [command-options]

Global options:
  -h, --help                   Show this help message and exit
      --version                Show this tool's version information and exit
  -t, --track-dir <dir>        Specify a track directory to use instead of the current directory
  -v, --verbosity <verbosity>  The verbosity of output. Allowed values: q[uiet], n[ormal], d[etailed]
```

## Reglas

Estas son las reglas de análisis estático que se comprueban.

### Regla: los archivos requeridos están presentes

El linter debería comprobar que estén presentes todos los archivos requeridos. Los archivos que no son específicos de un ejercicio y que deben estar presentes son:

- `config.json`
- `docs/ABOUT.md`
- `docs/INSTALLATION.md`
- `docs/LEARNING.md`
- `docs/RESOURCES.md`
- `docs/SNIPPET.txt`
- `docs/TESTS.md`
- `exercises/shared/.docs/help.md`
- `exercises/shared/.docs/tests.md`

Los archivos específicos de los ejercicios de concepto que deben estar presentes son:

- `exercises/concept/<slug>/.docs/hints.md`
- `exercises/concept/<slug>/.docs/instructions.md`
- `exercises/concept/<slug>/.docs/introduction.md`
- `exercises/concept/<slug>/.meta/config.json`

Habrá una lista similar para los ejercicios de práctica, pero todavía no hemos definido la especificación para eso.

Cada concepto listado en `config.json` debería tener los siguientes archivos:

- `concepts/<slug>/about.md`
- `concepts/<slug>/introduction.md`
- `concepts/<slug>/links.json`

## Glosario

1. **String no vacío**: un string que contiene al menos un carácter que no sea un espacio en blanco.
2. **String en kebab-case**: un string que solo contiene caracteres del rango `[a-z0-9]`, separados opcionalmente por guiones (p. ej., «two-fer»). Debe coincidir con la expresión regular: `^[a-z0-9]+(-[a-z0-9]+)*$`
3. **String en Title Case**: un string no vacío que sigue las siguientes [pautas del Manual de Estilo de Chicago](https://en.wikipedia.org/wiki/Title_case#Chicago_Manual_of_Style):
   - Se escriben en mayúscula la primera y la última palabra de títulos y subtítulos.
   - Se escriben en mayúscula las palabras «importantes» (sustantivos, pronombres, verbos, adjetivos, adverbios y algunas conjunciones).
   - Se escriben en minúscula las conjunciones _and_, _but_, _for_, _or_ y _nor_.
   - Se escriben en minúscula los artículos _the_, _a_ y _an_.
   - Se escriben en minúscula las preposiciones, sin importar su longitud, salvo cuando son tónicas, se usan de forma adverbial o adjetival, o se usan como conjunciones.
   - Se escriben en minúscula las palabras _to_ y _as_.
   - Se escribe en minúscula la segunda parte de los nombres de especies en latín.
4. **String en Sentence Case**: un string no vacío que sigue las siguientes [pautas](https://en.wikipedia.org/wiki/Letter_case#Sentence_case):
   - Se escribe en mayúscula la primera palabra de la oración, así como los nombres propios y otras palabras según lo exija una regla más específica.
5. **Patrón de `files` válido**: un string¹ no vacío que especifica la ubicación de un archivo usado en un ejercicio, relativa al directorio del ejercicio. Un patrón puede usar uno de los siguientes marcadores de posición:

   - `%{kebab_slug}`: el slug del ejercicio en `kebab-case` (p. ej., `bit-manipulation`)
   - `%{snake_slug}`: el slug del ejercicio en `snake_case` (p. ej., `bit_manipulation`)
   - `%{camel_slug}`: el slug del ejercicio en `camelCase` (p. ej., `bitManipulation`)
   - `%{pascal_slug}`: el slug del ejercicio en `PascalCase` (p. ej., `BitManipulation`)

6. **String de UUID versión 4 único**: un string que cumple todas estas condiciones:

   - Solo existe una vez en el archivo `config.json` de nivel de track de un track de Exercism dado
   - No existe en el archivo `config.json` de nivel de track de ningún otro track de Exercism
   - No existe en ningún archivo `canonical-data.json` de https://github.com/exercism/problem-specifications
   - No existe en ningún otro lugar de Exercism
   - Coincide con la expresión regular:

   ```
   ^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
   ```

   Por ejemplo, el siguiente UUID tiene la forma correcta:

   ```
   d334ffe3-657e-4725-a950-290b284b6d9f
   ```

   Puedes ejecutar `configlet uuid` para generar un UUID adecuado.

7. **`tag` de analyzer válido**: un string¹ no vacío con el formato `<category>:<thing>`.
   El valor de `<category>` debe ser uno de los siguientes:

- `paradigm` (p. ej., `paradigm:functional`)
- `technique` (p. ej., `technique:recursion`)
- `construct` (p. ej., `construct:bitwise-and`)
- `uses` (p. ej., `uses:DateTime.add_seconds`)

El valor de `<thing>` debe ser un string¹ no vacío.

# Acerca de

En conceptos anteriores, se mencionó que la directiva `global` hace que una función o una variable definida en un archivo fuente sea visible para otros archivos.
De manera similar, la directiva `extern` le informa al ensamblador que una función o una variable usada en el archivo fuente actual está definida en otro.

Esas dos directivas son la forma principal en que el código ensamblador interactúa con otros archivos fuente para lograr la modularización.

Para los propósitos de estas directivas, es indiferente si el código externo está definido o se usa en ensamblador o en un lenguaje de alto nivel.
Así, por ejemplo, incluso una función definida en un lenguaje de alto nivel puede usarse en código x86-64 si se declara `extern`.

De la misma manera, la convención de llamada se comparte entre todas esas funciones, ya estén definidas en ensamblador o en lenguajes de alto nivel, e incluso con el sistema operativo (SO).

Sin embargo, como en ensamblador los datos son solo una secuencia de bytes, es importante tener en cuenta cómo gestiona la memoria el lenguaje de alto nivel con el que se interactúa.

## Tipos de C

El lenguaje C es una opción común como lenguaje de alto nivel para interactuar con código ensamblador.
Facilita la tarea de interactuar con el SO, ya que ofrece envoltorios de alto nivel para muchas tareas importantes, como imprimir en pantalla, leer desde un teclado o asignar memoria dinámica.

En este track, las pruebas están escritas en C, así que es importante ofrecer una visión general del lenguaje.

Esto los hace de solo lectura.

### Tipos primitivos

En C hay muchos tipos primitivos y su tamaño, en bytes, puede variar.
Algunos de ellos se resumen en la siguiente tabla, con su tamaño típico en un sistema x86-64:

| tipo      | número de bytes | entero/punto flotante |
|-----------|-----------------|-----------------------|
| _Bool     | 1               | entero                |
| char      | 1               | entero                |
| short     | 2               | entero                |
| int       | 4               | entero                |
| long      | 4 u 8           | entero                |
| long long | 8               | entero                |
| float     | 4               | punto flotante        |
| double    | 8               | punto flotante        |

Cada uno de esos tipos enteros puede ser con signo (el valor predeterminado) o sin signo.
Si son sin signo, hay que especificarlo, por ejemplo: `unsigned int`.

Hay alias para los tipos enteros que están definidos para ofrecer un control preciso sobre su tamaño:

| alias   | número de bytes |
|---------|-----------------|
| int8_t  | 1               |
| int16_t | 2               |
| int32_t | 4               |
| int64_t | 8               |

Esos alias pueden llevar el prefijo `u` para indicar un tipo sin signo, por ejemplo: `uint64_t`.

Otros alias que vale la pena mencionar son:

| alias  | tipo                                          |
|--------|-----------------------------------------------|
| bool   | _Bool                                         |
| size_t | normalmente un entero sin signo de 8 bytes    |

Un `_Bool`, o su alias `bool`, tiene la particularidad de que, aunque ocupa 1 byte completo, solo puede asumir uno de dos valores: `true` (`1`) y `false` (`0`).

Los valores de esos tipos primitivos se pasan a las funciones y se devuelven desde ellas de acuerdo con las reglas habituales para enteros y valores de punto flotante.

### Enumeraciones

Una [enumeración][enum] es un tipo que puede asumir uno de una serie de elementos indicados explícitamente:

```c
enum example {
    example_1,
    example_2,
    example_3,
    example_4
};
```

En C, las enumeraciones se convierten implícitamente a un tipo entero, que normalmente es un `int`, es decir, un entero de 4 bytes.

De forma predeterminada, el primer elemento posible de una enumeración se convierte a `0` y todos los elementos siguientes se convierten al siguiente entero.
Así, en el `enum example` definido arriba, `example_1` tendría el valor `0`, `example_2` tendría el valor `1`, y así sucesivamente.

Es posible indicar el valor de cualquier elemento de una enumeración y, entonces, de forma predeterminada, el siguiente elemento tendría como valor el siguiente entero:

```c
enum example_2 {
    example_1 = 4,
    example_2 = 8,
    example_3
}; // example_3 is equal to 9
```

### Direcciones de memoria

En C, se hace referencia a una dirección de memoria mediante un [puntero][pointer] a un tipo, y se denota con el operador `*`.
Así, por ejemplo, `int64_t *` hace referencia a una ubicación de memoria para uno o más `int64_t`.

Las direcciones se tratan como enteros de 8 bytes, como es habitual.

### Arrays

Los arrays se pasan a las funciones y se devuelven desde ellas como punteros a su primer elemento.

```c
int64_t example_arr[] = {1, 2, 3}; // this is an array of 3 signed 8-byte integers
fn(example_arr); // this is a function that passes a pointer (int64_t *) to the beginning of the array as argument
```

Cada elemento de un array tiene el tamaño del tipo de elemento del array.
El `example_arr` definido arriba, por ejemplo, tiene 3 elementos de 8 bytes cada uno, lo que da 24 bytes en total.

Como los arrays no almacenan su longitud, normalmente se necesita un valor aparte para indicar el número de elementos, a menos que un valor centinela marque el final.

### Strings

Los strings en C son un array de `char`, que es un tipo de 1 byte.
La mayoría de los strings son de caracteres ASCII y terminan en NUL, así que acaban cuando se encuentra un byte con el valor `0`.
Esto significa que, por lo general, no es necesario pasar la longitud de un string como un argumento aparte.

## Llamar a funciones de la biblioteca de C

La directiva `extern` solo declara que un símbolo está definido en otro archivo.
Cómo se hace realmente una llamada a él depende de cómo se enlace ese código externo.

Para las funciones ordinarias que se enlazan junto con tu código, el enlazador puede encontrar una función externa directamente, así que basta con un `call` normal.

Sin embargo, las funciones de la biblioteca estándar de C, como `malloc`, `free` y `printf`, normalmente se resuelven en tiempo de ejecución desde una biblioteca compartida, cuya dirección no se conoce cuando se ensambla tu código.
Por eso la llamada pasa por un stub en una [tabla de enlace de procedimientos (PLT)][plt], ubicada en un desplazamiento conocido.
Siempre que se llama a una función de biblioteca externa desde ensamblador, NASM requiere una indicación de que esa llamada debe resolverse desde la PLT.

En `elf64` (el formato de salida que usan los programas de Linux), esta indicación se hace agregando `wrt ..plt` («con referencia a la plt») después de la llamada.
Por ejemplo, `call printf wrt ..plt`.

En los programas `macho64` (el formato de salida que usan los programas de macOS), en cambio, basta con un guion bajo antes del nombre de la función.
Por ejemplo, `extern _printf`, y luego `call _printf`.
Sin embargo, como este track ensambla el código `macho64` con la opción `--prefix _`, el ensamblador agrega ese guion bajo automáticamente en ambas situaciones; por ejemplo, `extern printf`, y luego `call printf`.

Ten en cuenta que el test-runner de Exercism se ejecuta en una imagen de Linux, así que cualquier solución enviada que llame a funciones de la biblioteca de C debe usar `wrt ..plt`.
Se puede usar una guarda en tiempo de ensamblado para despachar correctamente entre formatos de salida:

```x86asm
extern malloc

%ifidn __OUTPUT_FORMAT__,elf64
    call malloc wrt ..plt       ; elf64: reach the function through the PLT
%else
    call malloc                 ; macho64: the linker generates the call stub
                                ; the underscore is added automatically by an assembler flag
%endif
```

## Llamadas al sistema

Hay muchas operaciones que los programas de usuario, como los que se ejecutan en este track, no pueden realizar directamente.
Leer desde `stdin`, escribir en `stdout`, solicitar memoria dinámica, interactuar con periféricos, etc., todo eso lo maneja el sistema operativo (SO).

Cuando lo necesita, un programa de usuario debe solicitarle explícitamente al SO que realice esas operaciones.
Esto se hace con la instrucción [`syscall`][syscall].
Conceptualmente, esta instrucción puede verse como una llamada a algún procedimiento predefinido del SO (una llamada al sistema).

Cualquier argumento de la llamada al sistema debe pasarse al SO en los GPR: `rdi`, `rsi`, `rdx`, `r10`, `r8` y `r9`.

Ten en cuenta que la secuencia es casi la misma que se usa en una llamada a función, pero `rcx` se reemplaza por `r10`.
Esto se debe a que `syscall` usa `rcx` y `r11` para guardar la dirección de retorno y los flags (que se restauran antes de devolver el control a la función que hizo la llamada).
Ambos registros deben tratarse como alterados en cada `syscall`.

A diferencia de `call`, no hay etiquetas que indiquen las «funciones» del sistema.
En su lugar, se accede a ellas mediante números específicos colocados en `rax` antes de la llamada.
Cualquier valor devuelto, si lo hay, también se coloca en `rax`.

Las convenciones anteriores se describen [en un apéndice de la ABI de System V][linux-convention] que cubre Linux específicamente, y está marcado solo como informativo.
En la práctica, las llamadas al sistema disponibles, su número y cómo se reportan los errores son detalles propios de cada SO que varían mucho entre SO, e incluso entre distintas versiones de un mismo SO.

Muchas funciones de la biblioteca de C, y otras funciones reales definidas por el SO, son envoltorios de más alto nivel sobre una llamada al sistema.
La ABI recomienda preferir estos envoltorios antes que un `syscall` simple, y Apple [no garantiza la compatibilidad][mac-qa1118] en la interfaz de llamadas al sistema del kernel.

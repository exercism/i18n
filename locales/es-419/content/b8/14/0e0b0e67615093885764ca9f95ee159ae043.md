# Introducción

A estas alturas del temario, ya has visto R usarse a menudo como lenguaje imperativo y, cada vez más, como lenguaje funcional (sobre todo con las bibliotecas [`purrr`][ref-purrr] y [`dplyr`][ref-dplyr]).

¡Sugerir ahora que R es principalmente orientado a objetos puede provocar cierto escepticismo!

Por extraño que parezca, es una afirmación verdadera.
Internamente, R está implementado con clases, herencia, polimorfismo y ese tipo de actitudes típicas de quienes programan con POO.

Sin embargo, quien conozca Java o Ruby (POO explícita) o incluso Python (POO semiencubierta, en cierto modo) encontrará el enfoque de R ... _poco familiar_.

Para empezar, hay varios diseños de clases: quizá tres de uso común (S3, S4, R6), además de otros varios de interés principalmente teórico.

Puedes encontrar un análisis exhaustivo en [Advanced R, 2e][book-advanced-r], capítulos 12 a 16.
Este libro de 2019 está dirigido en gran medida a quienes quieren entender y mantener el funcionamiento interno de R, así que la POO es esencial.

Los libros de texto más orientados al usuario final varían.

- The Art of R Programming (2011, solo en papel) tiene un capítulo sobre POO que cubre S3 y (más brevemente) S4, que eran importantes en esa época.
  El comentario de que _«las clases S3 tienen una estructura más bien improvisada»_ sigue siendo llamativamente cierto.
- R in Action (3e, 2022) relega la POO a 3 páginas de un capítulo sobre Programación avanzada casi al final.
- [R for Data Science, 2e][book-r-data-sci] (2023, con 548 páginas en la edición impresa) no menciona la POO en absoluto.

Este Concepto se centrará en las clases S3, que son las más simples, las más comunes y las más relevantes para problemas de tipo Exercism.
Algunos de los ejercicios de práctica del track de R te piden crear una clase S3; en otros es opcional, pero se te anima amablemente a hacerlo.

## Clases S3

Son antiguas: el nombre S3 solo significa que se introdujeron en la versión 3 del lenguaje S (un precursor comercial de R).

Una clase S3 también es muy simple: típicamente, una [Lista][concept-lists] con al menos un atributo adicional.

Citando [Advanced R][book-s3]: _«S3 es informal y ad hoc, pero hay cierta elegancia en su minimalismo: no puedes quitarle ninguna parte y seguir teniendo un sistema de POO útil»._

```R
# create a list
pt2d <- list(x = 2.5, y = 4.2)
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
class(pt2d)
#> [1] "list"
attributes(pt2d)
#> $names
#> [1] "x" "y"

# convert the list to an S3 class
class(pt2d) <- "point2d"
str(pt2d)
#> List of 2
#>  $ x: num 2.5
#>  $ y: num 4.2
#>  - attr(*, "class")= chr "point2d"
class(pt2d)
#> [1] "point2d"
attributes(pt2d)
#> $names
#> [1] "x" "y"

#> $class
#> [1] "point2d"
```

Así que asignarle un valor a [`class(obj)`][ref-class] solo agrega un atributo a `obj`, en este caso identificando a pt2d como una instancia de la clase point2d.

Los pasos de creación se pueden combinar con [`structure()`][ref-structure]:

```R
pt2d_2 <- structure(list(x = 2.5, y = 4.2), class = "point2d")
pt2d_2 == pt2d
#> Error in pt2d_2 == pt2d : comparison of these types is not implemented
```

Aunque las instancias resultantes son teóricamente idénticas, todavía no hemos implementado una forma para que R lo confirme.

### Métodos genéricos

Quien conozca la POO en otros lenguajes quizá se pregunte: _«¿acaso las clases no deberían poder HACER cosas?»_

Podemos revisar los métodos disponibles para las instancias de `point2d` y descubrir que (a diferencia de la `list` subyacente) actualmente no hay ninguno.

```R
methods(class = "point2d")
#> no methods found
methods(class = "list")
#>  [1] %within%      all.equal     as.col_spec   as.data.frame as_mapper     as_tibble     coerce        common_by    
#>  [9] Ops           pattern_alpha relist        scale_type    select        type.convert  within       
#> see '?methods' for accessing help and source code
```

En la mayoría de los lenguajes con POO, los métodos se definen dentro de la definición de la clase.
Algunos lenguajes (en particular Ruby) te permiten agregar y modificar métodos de clase más adelante.

Las clases S3 son muy distintas.
En lugar de agregar métodos a una clase, le agregamos la clase a un método genérico.

Cualquiera que trabaje de forma interactiva en la consola de R usa métodos genéricos todo el tiempo, normalmente sin pensar en cómo están implementados.

Un ejemplo muy común es `print()`, aunque rara vez escribas el nombre de la función.
Escribir un valor `x` por sí solo en el símbolo del sistema de la consola es solo azúcar sintáctica para `print(x)`.

```R
1:4
#> [1] 1 2 3 4
print(1:4)
#> [1] 1 2 3 4
```

Ya podemos imprimir `pt2d`.
Aunque `print()` no sabe nada de la clase `point2d`, tiene valores predeterminados razonables para manejar una amplia variedad de objetos.

```R
pt2d
#> $x
#> [1] 2.5

#> $y
#> [1] 4.2

attr(,"class")
#> [1] "point2d"
```

Eso es bastante verboso, y quizá queramos una forma de imprimir el punto de manera más legible y concisa.

Fácil: solo agrega una función llamada `print.point2d()`.
El nombre debe tener la forma `methodname.classname`, para que el despachador sepa qué buscar.

```R
print.point2d <- function(pt) {
  cat("Cartesian coords (", pt$x, ", ", pt$y, ")\n", sep="")
}

pt2d
#> Cartesian coords (2.5, 4.2)
```

Ahora supongamos que queremos crear un nuevo método genérico, por ejemplo `flipvert()` para invertir el signo de la coordenada `y`.

Otra vez, fácil:

```R
flipvert <- function(x, ...) UseMethod("flipvert")
```

Esto crea un despachador, donde `x` es nuestro objeto con una clase S3 y `...` se encarga de cualquier argumento extra que puedan necesitar las definiciones de métodos («dot args», como se describe en el [Concepto de Funciones][concept-functions]).

Luego podemos definir el método para `point2d` y usarlo.

```R
flipvert.point2d <- function(pt) {
  pt$y <- -pt$y
  pt
}

flipvert(pt2d)
#> Cartesian coords (2.5, -4.2)

methods("flipvert")
#> [1] flipvert.point2d
```

Ahora R sabe cómo invertir nuestro punto y cómo mostrar el resultado.

Podríamos ampliar esto creando clases para 3D, para coordenadas polares, etc., y luego definir métodos para cada una.

Desde la perspectiva del usuario final, solo existe `flipvert(x, ...)`, y podemos confiar en que R determine la clase del argumento y use la implementación subyacente adecuada.

~~~~exercism/caution
Los nombres de funciones con el formato `verb.class` parecen métodos S3, tanto para quienes usan R como para el analizador sintáctico de R.
Por favor, evita usar nombres parecidos en otros contextos.

Es cierto que el R base a veces infringe esta regla.
Deberíamos verlo como un desafortunado accidente histórico (para funciones incluso más antiguas que S3) que hay que conservar por compatibilidad con versiones anteriores.
~~~~

### Herencia

Quienes son entusiastas de la POO pueden escribir varios capítulos largos de un libro de texto sobre herencia, subclases, mixins y todo lo demás.

R simplemente te permite dar varios nombres al atributo `class`: un vector de strings más largo en lugar de un solo string.

A riesgo de forzar el ejemplo hasta el límite, supongamos que hubiéramos creado una clase `point` genérica y quisiéramos derivar de ella las subclases `point2d`, `point3d`, etc.

Entonces la definición de `point2d` simplemente usa `class = c("point2d", "point")`: la clase específica y la clase (o clases) padre.

Los métodos genéricos como `print()` buscarán entonces en secuencia `print.point2d()`, `print.point()` y (probablemente) `print.default()`, y usarán la primera implementación que encuentre el despachador.

### Seguridad

Muchos lenguajes con POO (Java, C#, etc.) aprovechan la encapsulación de datos dentro de las clases para hacer comprobaciones cuidadosas en tiempo de compilación y garantizar la seguridad de tipos.

Ten en cuenta que S3 te deja hacer prácticamente lo que quieras, incluso si no tiene ningún sentido (el mensaje de error, si acaso, llega después).

Citando ["Advanced R"][book-s3] (2e, sección 13.3):

> _Si has usado otros lenguajes orientados a objetos, esto puede darte un poco de náusea, pero en la práctica esta flexibilidad causa pocos problemas. R no te impide dispararte en el pie, pero mientras no apuntes el arma a tus dedos y aprietes el gatillo, no tendrás problema._

Bueno, _¿de acuerdo?_
R es excelente para la ciencia de datos exploratoria y la estadística, a menudo cuando se trabaja de forma interactiva.
¡Nadie está sugiriendo que lo uses para escribir sistemas de finanzas corporativas de alta seguridad!

# Acerca de la nulabilidad

En un mundo ideal, podríamos confiar en que todo esté bien definido, con valores concretos y sin vacíos.

Esto choca con nuestra experiencia cotidiana y, por eso, muchos lenguajes de programación tienen una forma de representar la ausencia de un valor: null o NULL, nil, None, nothing...

Fue fácil de introducir (allá por 1965), pero pronto provocó arrepentimiento.
Su inventor después lo llamó su ["Billion Dollar Mistake"][web-mistake].

En las últimas décadas, quienes diseñan lenguajes han explorado muchas formas de que los valores nulos estén disponibles pero sean (en su mayoría) seguros.

Kotlin tiene algunos [principios generales][ref-null-safety], que [difieren bastante de los de Java][ref-java2kotlin].
_Estas diferencias hacen que Kotlin tenga funcionalidad especial para tratar con la interoperabilidad con Java, aunque los detalles quedan fuera del alcance de este concepto._

- Kotlin tiene un valor `null` especial.
- Todos los tipos son _por defecto_ no nulables (es decir, no pueden ser `null`).
- Todos los tipos pueden ser _nulables_, pero eso debe hacerse de forma explícita.
- Es probable que las funciones que puedan fallar con una excepción tengan una variante con un valor de retorno nulable.
- Una sintaxis especial y muy concisa intenta que comprobar valores nulos y responder a ellos sea lo más fácil posible.

## Crear variables nulables

Un tipo puede volverse [nulable][ref-nullable-type] si le agregas el sufijo `?` (por ejemplo, `String?` en lugar de `String`).

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operadores y funciones útiles

### El [operador de llamada segura][ref-safe-call] `?.`

Para un `String` no nulable, podemos obtener la propiedad `.length`.

Un `String?` nulable falla con esa misma sintaxis, pero usar `?.length` contempla la posibilidad de un `null`.
El tipo de retorno es `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Como vimos en la última línea de arriba, `?.` también funciona con tipos no nulables.

### El [operador Elvis][ref-elvis] `?:`

Siguiendo la idea del operador de llamada segura, el [operador Elvis][wiki-elvis] nos permite dar un valor por defecto para reemplazar `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### [Operador de aserción de no nulo][ref-not-null] `!!`

Con este operador, un tipo nulable se fuerza a tratarse como no nulo, cuando quien programa está seguro de ello.
¿Quizás a veces entendemos la lógica del programa mejor que un compilador demasiado cauteloso?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Ahora la responsabilidad es nuestra: si `b` sigue siendo `null`, obtenemos una `NullPointerException`.

### La [función let][ref-let] `?.let`

Si pasamos un elemento nulable a un bloque de código, podríamos hacer comprobaciones específicas de nulos: `if (item != null) { do something }`.

Es más simple y más idiomático usar `item?.let { do something }`,
el `do something` solo se ejecutará cuando `item` no sea nulo.

### Funciones del tipo `somethingOrNone()`

Algunas funciones pueden fallar, por ejemplo cuando pides un índice inválido en un string o un array.

En lugar de lanzar una excepción, podríamos usar la [variante `...OrNull`][ref-elem-at-or-null] de la función para obtener (en este caso) un valor de retorno `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

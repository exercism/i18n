# Guía de estilo de C

Esta guía describe el estilo previsto para los archivos de ejemplo y de prueba de los ejercicios del track de C.

Las reglas de esta guía complementan las que establece el archivo [.clang-format][], o bien sirven para destacarlas.

## Estándar de C

El código debe cumplir con el estándar C99, conocido formalmente como ISO/IEC 9899:1999.
No deben usarse POSIX ni, en general, funciones de biblioteca, tipos u otras referencias no estándar que sean externas a la implementación.

## Nombres

En general, los nombres de tipos, variables, estructuras y archivos deben usar snake case, con todas las letras en minúscula y guiones bajos `_` para separar los componentes del nombre.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Enums

Por lo general, los nombres de los enum van en singular y no en plural.

Las etiquetas de los enum deben usar snake case, con todas las letras en mayúscula.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Macros

Las macros que definen constantes se nombran usando snake case, con todas las letras en mayúscula.

```c
#define CONSTANT 0x4000
```

Se agradece usar snake case en mayúsculas para los nombres de macros, pero las macros que se parecen a funciones pueden nombrarse en snake case con minúsculas.

### Tipos

Se prefieren los tipos estándar de ancho fijo (de `stdint.h`) sobre los tipos enteros básicos.

Se prefiere el tipo `bool` (de `stdbool.h`) sobre `_Bool`.

Del mismo modo, se prefieren `size_t` y `ptrdiff_t` (de `stddef.h`) para representar cantidades relacionadas con la memoria.

Los tipos que un programa define con `typedef` deben nombrarse con el sufijo `_t`.
Aunque sabemos que POSIX reserva el sufijo `_t`, el track no utiliza POSIX actualmente.

## Guardas de inclusión

Se deben usar guardas de inclusión en todos los archivos de encabezado.

Por lo general, un conjunto de guardas de inclusión debe envolver todo el contenido del encabezado.

Las guardas en la implementación de ejemplo (`.meta/example.h`) y en el esqueleto del ejercicio (`exercise_name.h`) deben usar nombres de macro que sigan el nombre del ejercicio.
Los nombres de las macros de guarda deben seguir la regla anterior sobre el uso de mayúsculas y minúsculas en macros.

Por ejemplo, para el ejercicio `hello-world`, usa:

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Parámetros

Los parámetros de función deben nombrarse tanto en la declaración como en la definición de todas las funciones.
Esto se aplica tanto a los archivos `.c` como a los `.h`.
Los nombres usados deben coincidir en todos los casos.
Es decir, aunque el siguiente prototipo de función es C válido, el estilo es incorrecto porque el parámetro no tiene nombre: `void foo(int);`.
El prototipo correcto, siempre que todas las demás declaraciones y la definición también usen el nombre de parámetro `bar`, sería `void foo(int bar);`.

Cuando sea más simple o más apropiado, se prefieren los parámetros que requieren pasar argumentos por valor en lugar de por puntero.
Nota en especial que esto incluye los parámetros de tipo `struct`.

En caso de que no se espere que el estudiante cambie los valores de un parámetro de tipo puntero dentro de su implementación, ese parámetro debe calificarse como `const`.

## Formato

El repositorio usa la herramienta `clang-format`, como se describe en la [guía de contribución][contributing guide].

## Estructura del archivo de prueba

El archivo de prueba de cada ejercicio sigue una estructura particular.
La estructura busca tanto ayudar a quienes contribuyen a identificar las partes del archivo como ayudar a quienes aprenden a entender cómo funcionan las pruebas.

Como la mayoría de los archivos fuente en C, un archivo de prueba comienza con los includes.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

Después de los includes vienen las funciones `setUp()` y `tearDown()`.
Hasta ahora, ningún ejercicio las usa (los cuerpos de las funciones están vacíos), pero deben permanecer en su lugar para que los archivos de prueba se compilen correctamente en todas las plataformas.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

Luego vienen las funciones auxiliares que usan las funciones de prueba.
Los nombres de esas funciones auxiliares no deben usar el prefijo `test_`.

Después vienen las funciones de prueba en sí.
Los nombres de estas funciones usan el prefijo `test_`.
Excepto la primera, cada función de prueba debe tener `TEST_IGNORE();` como su primera sentencia.
La primera aparición de esto debe ir seguida del comentario de línea `// delete this line to run test`.

Por ejemplo:

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Lo último en el archivo es la función `main()`.
El cuerpo de la función main sigue a su vez una estructura particular.
Primero una llamada a `UNITY_BEGIN()` seguida de una línea vacía, luego las pruebas.
Después de la última prueba va otra línea vacía, antes de devolver el resultado de `UNITY_END()`.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

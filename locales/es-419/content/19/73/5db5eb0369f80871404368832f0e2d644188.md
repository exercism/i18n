# Acerca de

A estas alturas del temario, ya has visto muchas definiciones de funciones.
Por lo general, se presentaban sin muchos comentarios sobre la salida en el REPL:

```julia-repl
julia> f(x) = x^2
f (generic function with 1 method)
```

¿Por qué _«generic function with 1 method»_?

Supongamos que queremos ser más específicos con los tipos de los argumentos.

```julia-repl
julia> f(x::Integer) = x^2
f (generic function with 2 methods)

julia> f(x::Real) = x^2
f (generic function with 3 methods)
```

O podríamos cambiar la cantidad de argumentos:

```julia-repl
julia> f(x, y) = x * y
f (generic function with 4 methods)
```

Parece que las nuevas definiciones de la misma función se llaman «métodos».
Los métodos se agregan a una lista, en lugar de sobrescribir la definición anterior.

Podemos listar los métodos fácilmente:

```julia-repl
julia> methods(f)  # output edited for brevity
# 4 methods for generic function "f" from Main:
 [1] f(x, y)
 [2] f(x::Integer)
 [3] f(x::Real)
 [4] f(x)
 ```

Si llamamos a la función `f`, Julia de alguna manera sabe qué método usar:

```julia-repl
julia> f(2.5)  # Float64
6.25

julia> f(2)  # Int64
4

julia> f(2, 3)  # Int64, Int64
6
```

## ¿Qué es una función?

Según el [manual][function], una función es un objeto que asigna una tupla de argumentos a un valor de retorno.
Esto se acerca a la definición que usan los matemáticos.

Normalmente pensamos en los argumentos de la función en `f(2, 3)` como dos elementos separados, pero el compilador los ve como una sola [tupla][tuple].
Esto es cierto incluso para un solo argumento (aunque hay que agregar una coma para que quede más claro):

```julia-repl
julia> typeof( (2, 3) )
Tuple{Int64, Int64}

julia> typeof( (2,) )
Tuple{Int64}
```

Si vemos la función como una caja negra, podemos decir que entra una tupla y sale un valor de retorno.
Más formalmente, a la tupla se le _asigna_ un valor de retorno.

## ¿Cómo manejan las funciones distintas cantidades y tipos de argumentos?

A esto se le suele llamar ["polimorfismo"][polymorphism].

Este ha sido un tema importante en las ciencias de la computación durante varias décadas, y se han adoptado distintos enfoques.

El enfoque de Julia es poco común, aunque no único.

- Las funciones son ["genéricas"][generic], lo que significa que pueden tener varios métodos asociados.
- Las funciones son solo nombres, hasta que se les asocian métodos.
- Los métodos se pueden agregar según sea necesario, potencialmente en grandes cantidades (actualmente, el operador `+` es una función con 161 métodos).
- Cuando se llama a una función, Julia examina la signatura de la llamada: la cantidad de argumentos y el tipo actual de cada uno.
- Se selecciona el método que mejor coincide con la signatura de la llamada.
  - En general, la cantidad de argumentos debe coincidir exactamente (aunque el operador [splat/slurp][splat] `...` puede saltarse esto en parte).
  - Se prefieren los métodos cuyos tipos coinciden exactamente con la signatura de la llamada.
  - Si es necesario, Julia revisará los supertipos de cada argumento de la signatura de la llamada para encontrar el método más específico y que mejor coincida.
- Al método elegido se le aplica [`dispatched`][dispatch] con los argumentos dados, y este devuelve un resultado.
- Si no se encuentra un método adecuado, se lanza un [`MethodError`][methoderror].

Ten en cuenta que Julia tiene tipado dinámico, así que el despacho de métodos ocurre en _tiempo de ejecución_.

## Despacho múltiple: un ejemplo

La sección anterior tenía muchas palabras, así que llevemos esas ideas al código.
Por simplicidad, las funciones de abajo tienen un solo argumento, pero no es raro encontrar funciones con decenas de argumentos (como en los paquetes de gráficos o en el aprendizaje automático).

Empieza por definir algunos tipos personalizados para representar figuras geométricas.

```julia-repl
julia> abstract type Shape end

julia> struct Circle <: Shape
           radius::Float64
       end

julia> struct Square <: Shape
           side::Float64
       end

julia> struct Rectangle <: Shape
           length::Float64
           width::Float64
       end
```

Luego podemos definir métodos para calcular el área de cada figura.
Cada uno recibe un argumento, de un tipo concreto definido por el usuario distinto en cada caso.

```julia-repl
julia> area(c::Circle) = π * c.radius^2
area (generic function with 1 method)

julia> area(s::Square) = s.side^2
area (generic function with 2 methods)

julia> area(r::Rectangle) = r.length * r.width
area (generic function with 3 methods)
```

Ahora podemos crear algunas figuras y calcular sus áreas, confiando en el mecanismo de despacho de Julia para usar la fórmula correcta en cada caso.

```julia-repl
julia> circle = Circle(2.3)
Circle(2.3)

julia> area(circle)  # call signature Tuple{Circle}
16.619025137490002

julia> square = Square(1.6)
Square(1.6)

julia> area(square)  # call signature Tuple{Square}
2.5600000000000005

julia> rectangle = Rectangle(1.4, 2.1)
Rectangle(1.4, 2.1)

julia> area(rectangle)  # call signature Tuple{Rectangle}
2.94
```

## [Métodos paramétricos][parametric]

Las signaturas de los métodos pueden aceptar valores de tipo ficticios, más o menos de la misma manera que los tipos paramétricos.

La sintaxis es particular, pues requiere una cláusula `where`:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T} = true
same_type (generic function with 1 method)

julia> same_type([1, 2], 3)
true

julia> same_type([1, 2], "three")
ERROR: MethodError: no method matching same_type(::Vector{Int64}, ::String)
```

El ejemplo de arriba requiere que ambos argumentos usen el mismo tipo `T`, sea cual sea.

Podemos ser más específicos imponiendo una restricción sobre `T`:

```julia-repl
julia> same_type(v::Vector{T}, x::T) where {T<:Number} = true
same_type (generic function with 2 methods)
```

Con este método, solo los tipos numéricos idénticos devuelven `true`.

Es posible usar varias variables ficticias, separadas por comas en la cláusula `where`.
Los dos métodos siguientes se parecen:

```julia-repl
julia> func(v::Vector{Number}, x::Number) = true
func (generic function with 1 method)

julia> func(v::Vector{S}, x::T) where {S<:Number, T<:Number} = true
func (generic function with 2 methods)
```

Una diferencia es que los valores de tipo `S` y `T` están disponibles para usarlos dentro del cuerpo de la función del segundo método.
Este es el tipo de truco que quizá no uses a menudo, pero que en algunas circunstancias te puede ahorrar muchos problemas.

Por ejemplo, en la siguiente definición de tipo paramétrico, los campos deben ser del mismo tipo `T`, que está restringido a ser un subtipo de `Real`:
```julia
struct Point{T<:Real}
    x::T
    y::T
end
```
Esta definición de `Point` acepta una `x` y una `y` del mismo tipo, o puede aceptar una `x` y una `y` de tipos distintos, pero entonces hay que proporcionar un tipo de conversión explícito.
```julia-repl
julia> Point(4, 5)
 Point{Int64}(4, 5)

julia> Point(3.5, 2)
 MethodError: no method matching Point(::Float64, ::Int64)    # Output truncated for brevity

julia> Point{Float32}(3.5, 2)
 Point{Float32}(3.5f0, 2.0f0)

julia> Point{Int64}(3.5, 2) 
 InexactError: Int64(3.5)      # Output truncated for brevity
```
Aunque este nivel de control sobre los tipos puede ser deseable, también puede ser útil tener un poco de abstracción.
```julia
Point(x::T, y::S) where {T<:Real, S<:Real} = Point{promote_type(T,  S)}(x, y)
```
Este constructor externo lo logra al permitir que un `Point` acepte tipos no homogéneos para `x` y `y` sin especificar explícitamente el tipo de conversión.
Los valores de tipo `T` y `S` se usan en el cuerpo de la función, en `promote_type(T, S)`, para proporcionar el tipo de conversión explícito que necesita la definición original.
```julia-repl
julia> Point(3.5, 2)
 Point{Float64}(3.5, 2.0)
```

## Comparación con otros lenguajes

Como Julia examina todos los argumentos al seleccionar un método, a esto se le llama [`multiple dispatch`][multiple-dispatch].

Algunos otros lenguajes permiten el despacho múltiple, como Common Lisp, aunque rara vez es tan central en el diseño del lenguaje como en Julia.

En cambio, en un lenguaje orientado a objetos (OO), como Ruby, los métodos se suelen llamar sobre una [instancia][instance].
La definición ahora privilegia el primer argumento (con un nombre como `self` o `this` en la definición), y para llamar al método se escribe su nombre precedido de un punto sobre la instancia:

```ruby
irb(main):004:0> "abc".sub("b", "*")
=> "a*c"
```

A esto se le llama [`single dispatch`][single-dispatch], ya que solo la clase de la instancia (la del string «abc» en el ejemplo de arriba) se usa para elegir un método.

Algunos lenguajes orientados a objetos con tipado estático admiten polimorfismo de métodos, que se parece un poco al despacho múltiple.
La gran diferencia es que la selección del método solo ocurre en _tiempo de compilación_.

Los lenguajes funcionales suelen tener una sola definición de función, con algún tipo de expresión Select/Case/Match para manejar las distintas posibilidades.
Tú escribes tu propia lógica, normalmente con la ayuda de una sintaxis concisa de coincidencia de patrones que Julia no tiene.
Por supuesto, Julia también hace una forma de coincidencia de patrones, pero en el despacho, no dentro del cuerpo de la función.

## Conclusión

El despacho múltiple es muy flexible y muy eficiente en Julia, así que se usa muchísimo.

Como sugiere el ejemplo de los 161 métodos de `+`, quienes programan en Julia procuran definir métodos con tipos muy específicos.
Sumar dos enteros es muy distinto de sumar dos números de punto flotante a nivel del bytecode, y sumar un entero a un número de punto flotante agrega la complicación adicional de la promoción de tipos.

Cuanto más específico es el tipo, más optimizaciones puede hacer el compilador: algo de importancia marginal en un ejercicio de juguete en Exercism, pero vital para el rendimiento en las grandes simulaciones numéricas para las que Julia está diseñada.

_Si sabes qué argumentos va a recibir un método, ¡díselo al compilador!_

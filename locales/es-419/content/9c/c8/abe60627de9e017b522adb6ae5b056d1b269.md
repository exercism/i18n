# Acerca de

Un [bucle][control] es una secuencia de instrucciones que se ejecuta potencialmente más de una vez, hasta que se cumple una condición de fin.

En x86-64, un bucle normalmente se crea con un salto a una etiqueta anterior:

```x86asm
example_loop:
    ...
    jmp example_loop
```

Ten en cuenta que un salto incondicional a una etiqueta anterior siempre transferirá la ejecución a esa etiqueta.
Esto significa que el bucle seguirá repitiéndose para siempre, a menos que haya otro salto hacia afuera de la secuencia repetida.

Por ejemplo, este bucle no termina:

```x86asm
infinite_loop:
    inc rax
    jmp infinite_loop ; always jumps to 'infinite_loop', repeating 'inc rax' forever
```

Y este bucle puede terminar, dependiendo de si se cumple la condición:

```x86asm
maybe_finite_loop:
    cmp rax, 1
    je out_of_loop ; jumps to 'out_of_loop' if rax == 1, breaking the loop

    inc rax
    jmp maybe_finite_loop ; always jumps to 'maybe_finite_loop'
out_of_loop:
    ...
```

## Bucles de conteo

Un bucle de conteo casi siempre termina de la misma manera: una instrucción que actualiza un contador o compara dos valores, seguida inmediatamente por un salto condicional que decide si se repite otra vez.

```x86asm
sum_array:
    ; rdi is the memory address of an array
    ; rsi is the number of elements in the array

    mov eax, 0           ; running total
.loop:
    add rax, qword [rdi] ; add the current element
    add rdi, 8           ; advance to the next element
    sub rsi, 1           ; one fewer element to process, setting ZF at zero
    jnz .loop            ; repeat while the counter is not yet zero
    ret
```

~~~~exercism/note
`cmp rsi, 0` no es necesario en el código anterior porque `sub rsi, 1` ya establece la `zero flag (ZF)` cuando el resultado es `0`.

Aunque `cmp` es la forma principal de comprobar condiciones en ensamblador, muchas instrucciones actualizan las banderas.
Por ejemplo, muchas instrucciones aritméticas con enteros o de bits actualizan `ZF` cuando el resultado es `0`, y `SF` cuando el resultado es negativo (es decir, cuando el bit más alto está establecido).

Puedes consultar una [referencia][reference] para ver qué banderas afecta cada instrucción.

[reference]: https://www.felixcloutier.com/x86/
~~~~

Ten en cuenta que en el ejemplo anterior se presume que `rsi` es mayor que `0`.
Si fuera `0`, entonces `sub rsi, 1` reduciría `rsi` a `-1`, que es un número sin signo muy grande.
Harían falta `18,446,744,073,709,551,615` iteraciones más antes de que el bucle finalmente terminara.
Además, como la longitud del array es `0`, cualquier acceso a memoria quedaría fuera de los límites.

Si no hay garantías sobre la longitud de un array, hay dos enfoques comunes.

El primero es mover la condición de fin al comienzo del bucle y luego tener un salto incondicional al final:

```x86asm
sum_array:
    mov eax, 0
.loop:
    cmp rsi, 0
    je .done
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jmp .loop
.done:
    ret
```

El segundo es comprobar una vez si el array tiene longitud cero antes del comienzo del bucle:

```x86asm
sum_array:
    mov eax, 0

    cmp rsi, 0
    je .done
.loop:
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jnz .loop
.done:
    ret
```

Este segundo enfoque suele ser más eficiente que el primero, porque hay menos ramificaciones en el cuerpo del bucle.
Aprenderás más sobre esto en un concepto futuro.

## Microoperaciones

Un procesador no ejecuta una instrucción como `add` o `jnz` directamente.
El front-end de la CPU primero _decodifica_ cada instrucción en uno o más pasos internos más pequeños, llamados **microoperaciones** (o **micro-ops**).
Luego el procesador planifica y ejecuta estas microoperaciones, con frecuencia varias por ciclo y fuera de su orden original.

La mayoría de las instrucciones simples se decodifican en una sola microoperación, mientras que una instrucción más compleja puede decodificarse en varias.
Como la carga de trabajo real del procesador es el flujo de microoperaciones, producir menos de ellas para la misma tarea es una forma de que el código sea más rápido.

## Macrofusión

Como se mencionó antes, un bucle normalmente termina con algún tipo de salto condicional.
Esto es tan común que los procesadores modernos están optimizados para este patrón durante la decodificación.

Una instrucción que establece banderas, seguida inmediatamente por un salto condicional que lee esas banderas, puede decodificarse en conjunto como una **única** microoperación, en lugar de una para cada una.
Esto se llama **macrofusión**.

El par fusionado se comporta como una sola operación: el contador se actualiza y la decisión de ramificación se toma en conjunto, en una sola microoperación.
Así, el flujo de control del bucle casi no cuesta nada por encima del trabajo que el bucle realmente hace.

Como regla general, dos tipos de pares suelen fusionarse así:

- Instrucciones aritméticas como `add` o `sub`, seguidas inmediatamente por un salto condicional.
- Un `cmp`, `test` o `and`, seguido inmediatamente por un salto condicional.

```x86asm
    ...
    add rdi, 8       ; advance a pointer
    cmp rdi, rsi     ; compare it against the end address
    jb .loop         ; repeat while still below the end
```

La fusión solo ocurre cuando el salto condicional viene **inmediatamente** después de la instrucción que establece banderas, sin nada en medio.

~~~~exercism/note
La macrofusión depende de la CPU y hay cierta variación en qué instrucciones se fusionan con qué salto condicional.

Una referencia útil es [The microarchitecture of Intel, AMD, and VIA CPUs, by Agner Fog][agner-uarch].
La sección 3.4.2.2 (Optimizing for Macrofusion) del [Intel optimization reference manual][intel-opt] también enumera pares fusionables para las CPU Intel.

[intel-opt]: https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf
[agner-uarch]: https://www.agner.org/optimize/microarchitecture.pdf
~~~~

## La instrucción `loop`

Hay algunas instrucciones que pueden usarse para crear un comportamiento similar a un bucle.
Una de ellas es [loop][loop].

Su único operando es una etiqueta que contiene la dirección del inicio del bucle.

La instrucción `loop` usa el valor de `rcx` como contador y lo decrementa en 1 cada vez.
Cuando el valor de `rcx` llega a cero, el bucle termina y la ejecución continúa de forma secuencial:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    loop .example ; this repeats the sequence starting in .example 10 times (the value in rcx)
                  ; at each time, rcx is decremented by 1
```

Hay dos variantes de la instrucción `loop` que verifican la bandera de cero (`ZF`) en cada iteración.
Además de detener el bucle cuando `rcx` llega a cero, también se detienen cuando la condición _no_ se cumple.

| instrucción       | condición |
| ----------------- | --------- |
| `loope`/`loopz`   | `ZF` == 1 |
| `loopne`/`loopnz` | `ZF` == 0 |

Esas instrucciones **no establecen** `ZF`.
Debe haber un `cmp`, un `test` u otra instrucción que cambie `ZF` antes de ellas:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    cmp rax, 3
    loopne .example ; this repeats the sequence starting in .example while rcx > 0 and rax != 3
```

~~~~exercism/caution
A pesar de su comodidad, `loop`, `loope` y `loopne` suelen ser mucho más lentas en los procesadores modernos que la secuencia equivalente de `sub`/`jnz` o `cmp`/`jnz`.

Una buena referencia sobre el rendimiento de las instrucciones en muchas CPU diferentes son las [tablas de Agner][agner-tables].

[agner-tables]: https://www.agner.org/optimize/instruction_tables.pdf

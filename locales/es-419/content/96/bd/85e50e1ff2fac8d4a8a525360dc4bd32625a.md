# Introducción

En un mundo ideal, podríamos confiar en que todo esté bien definido, con valores concretos y sin vacíos.

Esto choca con nuestra experiencia cotidiana y, por eso, muchos lenguajes de programación tienen una forma de representar la ausencia de un valor: null o NULL, nil, None, nothing...

Fue fácil de introducir (allá por 1965), pero pronto dio lugar a lamentaciones.
Su inventor lo llamó más tarde su «error de los mil millones de dólares».

En las últimas décadas, quienes diseñan lenguajes han explorado muchas maneras de que los null estén disponibles pero (en su mayoría) sean seguros.

Kotlin tiene algunos [principios generales][ref-null-safety], que difieren bastante de los de Java.


- Kotlin tiene un valor `null` especial.
- Todos los tipos son, _por defecto_, no nulables.
- La mayoría de los tipos se pueden _convertir_ en nulables, pero quien programa debe pedirlo de forma explícita.
- Es probable que las funciones que pueden fallar con una excepción tengan una variante con un valor de retorno nulable.
- Una sintaxis especial y muy concisa intenta que comprobar los null y responder a ellos sea lo más fácil posible.

## Crear variables nulables

Los tipos estándar suelen tener un equivalente nulable, con el sufijo `?`: por ejemplo, `String?` en lugar de `String`.

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operadores y funciones útiles

### El operador de llamada segura `?.`

Para un `String` no nulable, podemos obtener la propiedad `.length`.

Un `String?` nulable falla con esa misma sintaxis, pero usar `?.length` contempla la posibilidad de un `null`.
El tipo de retorno es `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Como vimos en la última línea de arriba, `?.` también funciona con tipos no nulables.

### El operador Elvis `?:`

Siguiendo la idea del operador de llamada segura, el [operador Elvis][wiki-elvis] nos permite dar un valor por defecto que reemplace a `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### El operador de aserción de no nulidad `!!`

Con este operador, un tipo nulable se trata a la fuerza como no nulable, cuando quien programa está seguro de ello.
¿Quizás a veces entendemos la lógica del programa mejor que un compilador demasiado cauteloso?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Ahora la responsabilidad es nuestra: si `b` sigue siendo `null`, obtenemos una `NullPointerException`.

### La función Let `?.let`

Si vamos a pasar un elemento nulable a un bloque de código, podríamos hacer comprobaciones específicas de null con `if (item != null) { do something }`.

Es más simple y más idiomático usar `item?.let { do something }`,
El `do something` solo se ejecuta cuando `item` no es null.

### Funciones del tipo `somethingOrNone()`

Algunas funciones pueden fallar; por ejemplo, al pedir un índice inválido en un string o un array.

En lugar de lanzar una excepción, podríamos usar la variante `...OrNull` de la función para obtener (en este caso) un valor de retorno `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

# Especificación de Markdown

A continuación se describe cómo deben estructurarse todos los archivos Markdown dentro de Exercism.

Algunas de las reglas de este documento todavía no están implementadas en todo Exercism.
Agradecemos los PRs que las corrijan.
Todas las reglas se están agregando a nuestra CI y a nuestras herramientas de linting, y deben respetarse en los cambios nuevos.

## Encabezados

- Todos los archivos deben comenzar con un encabezado de nivel 1 (`# Some heading text`).
- Los encabezados de nivel 1 existen únicamente para consumirse en GitHub o su equivalente.
- Si Exercism renderiza el archivo (por ejemplo, si se muestra en el sitio web o se renderiza a través de la CLI), este encabezado se elimina y se inserta un encabezado contextual.
- Ningún encabezado puede descender más de un nivel por debajo del anterior (por ejemplo, después de `##` solo puede venir `###`, no `####`).
- Además del único encabezado de nivel 1 (`#`), solo pueden usarse encabezados de nivel 2 (`##`), nivel 3 (`###`) y nivel 4 (`####`).

## Enlaces

Usa [enlaces de referencia][reference-links], que se definen al final del archivo Markdown, se asocian a un slug de referencia y se referencian con ese slug en el texto.

Este método facilita el mantenimiento, ya que los enlaces solo deben actualizarse en un único lugar.

Ejemplo:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

Los enlaces siempre deben tener texto de ancla, en lugar de poner la URL directamente en el texto. Por ejemplo, lo siguiente no usa texto de ancla y es más difícil de leer.

```
If you want some more information, please visit https://google.com.
```

Usar texto de ancla y enlazarlo es más fácil de entender y de contextualizar.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

Que se renderiza como: «Si quieres más información, [Google][google-link] es un recurso útil».

## Código

Siempre que se haga referencia a elementos de código (por ejemplo, funciones o palabras clave), el código debe ir entre acentos graves:

```
- The `printf()` function writes to the console.
```

Que se renderiza como:

- La función `printf()` escribe en la consola.

El código más complejo (por ejemplo, código de varias líneas) debe ir entre tres acentos graves. Debe especificarse un [identificador de lenguaje][language-identifier] después de los tres acentos graves de apertura para habilitar el resaltado de sintaxis:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

Cuando sea posible, da formato al código de la manera que sea más relevante para el entorno en el que se presenta. Si están disponibles, consulta la documentación de tu lenguaje.

Por ejemplo, Python tiene el REPL (bucle de lectura, evaluación e impresión), que permite a quien programa escribir código directamente en una terminal. Si alguien estaba depurando código, o ejecutando una función localmente para probar u observar cómo funciona, es más probable que use un REPL para hacerlo, ya que ahí es más cómodo escribir de forma interactiva. En esta situación, preferimos dar formato al código de ejemplo como si se estuviera escribiendo en el REPL, con un `>>>` al inicio:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

En otros casos, tiene más sentido dejar el código con el formato que tendría en un archivo `.py`. Aquí, el estudiante se beneficia de que se le muestre algo que imita cómo escribiría el código por su cuenta.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

Una forma rápida de distinguir entre los dos casos cuando no está claro: si es código que el estudiante puede ejecutar en una terminal, dale ese formato. Si es código que Exercism podría ejecutar (en pruebas, en código de biblioteca que el estudiante escribirá, etc.), por defecto dale formato como código ejecutable.

## Bloques especiales (a veces llamados admoniciones)

Admitimos tipos especiales de bloques que pueden agregarse a los documentos para destacar comentarios que no encajan en el cuerpo principal del texto.

<img width="500" alt="Bloque avanzado de Markdown" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

Admitimos tres tipos de bloques:

- **exercism/note:** Bloques que destacan información adicional especial
- **exercism/caution:** Cosas que la gente debería conocer o con las que debería tener cuidado
- **exercism/advanced:** Información que solo es relevante para quienes quieren profundizar más en algo o se espera que tengan conocimientos más avanzados.

Todos los bloques se escriben usando 4 virgulillas, con la forma:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(Nota: en circunstancias excepcionales también puedes usar acentos graves u otros niveles de virgulillas)

## Disposición

### Una oración por línea

Los párrafos deben escribirse con una oración por línea. La [documentación de Ascii Doctor][asciidoctor] explica claramente la lógica de esto.

Por ejemplo, un solo párrafo debe escribirse así:

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## Listas

Usa el carácter de guion (`-`) como marcador de viñeta para las listas sin orden.

## Comentarios

- Prefiere los comentarios de Markdown en lugar de los comentarios de HTML (por ejemplo, usa `[comment]: # (Actual comment...)` en lugar de `<!-- Actual comment -->`

Puedes comprobar que tu comentario de Markdown se elimina revisando cómo se ve al renderizarse con commonmark en [babelmark3].

## HTML en línea

- El HTML en línea está permitido, pero debe usarse con moderación
- Usa siempre las alternativas nativas de Markdown si están disponibles (por ejemplo, usa `# ...` en lugar de `<h1>...</h1>`)

## Imágenes

Como el sitio web admite temas claros y oscuros, las imágenes enviadas por la comunidad deben verse bien en ambos temas.
La solución es agregar un sufijo al nombre de tu imagen (antes de la extensión del archivo):

1. Haz que el nombre de la imagen termine en `-invertible` (por ejemplo, `graph-invertible.svg`). La imagen se invertirá automáticamente cuando se muestre en el tema oscuro (mediante `filter: invert(100%)`).
1. Haz que el nombre de la imagen termine en `-light` (por ejemplo, `graph-light.png`) y crea también una versión compatible con el tema oscuro que termine en `-dark` (que sería `graph-dark.png`). Renderizaremos automáticamente la imagen correcta según el tema del usuario.

Las imágenes sin ninguno de los dos sufijos se usarán sin modificaciones en ambos temas.
Esto significa que, si quieres crear imágenes en escala de grises, por lo general puedes hacer que se vean bien en el tema claro y luego configurarlas como invertibles.
Pero si usas una imagen con muchos colores, quizás quieras hacer dos variantes.

El nombre completo de la imagen (incluido `-invertible`) debe agregarse al Markdown donde se renderiza la imagen.
Para las de claro/oscuro, **SOLO** incluye la variante `-light`.
Esta lógica se respeta en todos los documentos de Markdown.

## Formato automático

Algunos repositorios usan [prettier][prettier] para asegurarse de que todo el Markdown tenga un formato consistente. Esto puede aportar los siguientes beneficios:

- Sin discusiones sobre el formato.
- Una excelente integración con el editor o IDE, de modo que los archivos se pueden formatear al guardar.
- Es fácil agregar comprobaciones de CI para el formato.
- Es fácil formatear archivos automáticamente con un script.

Todo lo anterior puede ayudar mucho a reducir el ruido en las revisiones, que es frustrante tanto para quien revisa como para quien es revisado.

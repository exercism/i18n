# Migrar desde Travis

Aquí tienes un ejemplo de `.travis.yml` (tomado del track `elm`):

```yml
sudo: false
language: node_js
node_js:
  - lts/*
script:
  - bin/fetch-configlet
  - bin/configlet lint
  - bin/build.sh
```

Para convertir esto rápidamente a GitHub Actions, sigue estos pasos:

## Determina las variables de la plantilla

| variable                    | valor                                |
| --------------------------- | ------------------------------------ |
| `<track>`                   | `elm`                                |
| `<image-name>`              | `ubuntu-latest`                      |
| `<action to setup tooling>` | `actions/setup-node@v1`              |
| `<install dependencies>`    | `npm ci` (sucede dentro de `build.sh`) |
| `<code-extensions>`         | `.elm`                               |

> Encontré la acción de configuración con [esta búsqueda](https://github.com/actions/?q=setup+node&type=&language=).
> Encontré el nombre de la imagen al consultar la [distribución predeterminada de Travis](https://blog.travis-ci.com/2019-04-15-xenial-default-build-environment).

## Determina los pasos

- `bin/fetch-configlet`: ya no lo necesitas cuando usas el flujo de trabajo [`configlet.yml`][workflow-template-configlet-yml]
- `bin/configlet lint`: ya no lo necesitas cuando usas el flujo de trabajo [`configlet.yml`][workflow-template-configlet-yml]
- `bin/build.sh`: un solo script que hace todo

## Prepara los «scripts»

Este track usa la carpeta `bin`, así que dentro de la carpeta `bin`, crea los siguientes archivos:

```bash
# bin/pr
bin/build.sh
```

```bash
# bin/pr-check
echo "No checks yet"
```

```bash
# bin/ci
bin/build.sh
```

```bash
# bin/ci-check
echo "No checks yet"
```

Crearlos como binarios _separados_ permitirá optimizar más adelante. No hace falta integrar nada en línea por ahora.

## Ahora debería funcionar

Esto es suficiente para convertir a GitHub Actions, con la posibilidad de optimizar tus scripts.

1. De `build.sh`, elimina los pasos que deberían ejecutarse solo una vez y extráelos a los archivos `ci-check.sh` y `pre-check.sh` (sugerencia: puedes crear `lint.sh` y llamarlo desde ambos «scripts»).
2. A `pr.sh` y `pr-check.sh`, agrégales optimizaciones que usen los argumentos de entrada para determinar qué archivos o ejercicios comprobar.
3. Agrega comprobaciones adicionales.
4. Agrega documentación sobre cómo ejecutar las comprobaciones localmente y qué intenta lograr cada una.

# Anexo a las instrucciones

## La tarea

Implementa dos procedimientos.

- `custom_error_message message` lanza un error, y `message` es el mensaje de error.
- `handle_error script` ejecuta el script dado y devuelve una cadena que describe lo que pasó:

  | Cuando el script…                  | devuelve                 |
  | ---------------------------------- | ------------------------ |
  | divide entre cero                  | `"division by zero"`    |
  | abre un archivo que no existe      | `"file does not exist"` |
  | llama a un proc que no existe      | `"proc does not exist"` |
  | lanza cualquier otro error         | `"unknown error"`       |
  | tiene éxito                        | `"success"`             |

## Lanzar errores

Tcl tiene dos comandos para lanzar un error.

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` requiere un _código de error_ como primer argumento.
El código de error es una lista que le dice a un manejador qué tipo de error ocurrió, para que pueda responder sin analizar el texto del mensaje.
Su contenido depende de ti: `{MYAPP BADTHING}` es solo un ejemplo, y cualquier lista no vacía sirve.
Por convención, va de lo general a lo específico.
Un manejador lo captura con un patrón `try ... trap` que coincida (descrito abajo), como `trap {MYAPP BADTHING}`, o `trap {MYAPP}` para capturar todos los errores de `MYAPP`.
`error` acepta un código de error opcional como tercer argumento: `error message ?info? ?code?`.

## Manejar errores con `catch`

[`catch`][catch] ejecuta un script y devuelve un _código de finalización_ entero en lugar de lanzar el error:

| código | significado |
| ------ | ----------- |
| 0      | `ok`        |
| 1      | `error`     |
| 2      | `return`    |
| 3      | `break`     |
| 4      | `continue`  |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

El segundo argumento opcional recibe el resultado (o el mensaje de error).
El tercer argumento opcional recibe un _diccionario de opciones_, que tiene `-errorcode` y `-errorinfo` (la traza de la pila).

Ventajas:

- Es pequeño y flexible.
- Es breve para casos simples, como `if {[catch {open $f} fh]} {...}`.

Desventajas:

- Tienes que revisar el código de finalización por tu cuenta.
  Un `if {[catch ...] != 0} { handle error }` descuidado también trata `return`, `break` y `continue` como errores.
- Los errores que no manejas se tragan a menos que los vuelvas a lanzar por tu cuenta.
- No hay una forma integrada de ejecutar código de limpieza, falle o no el script.

## Manejar errores con `try`

[`try`][try] ejecuta un script y envía el resultado al primer manejador que coincida.
Una cláusula `finally` opcional siempre se ejecuta, lo que la convierte en un buen lugar para liberar recursos como los canales de archivo.

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

Ventajas:

- La estructura es clara: un manejador para cada tipo de resultado.
- `finally` siempre se ejecuta.
- Los resultados que ningún manejador captura se pasan al llamador sin cambios.

Desventajas:

- Es un poco más verboso que `catch` para casos simples.

### `try ... on` frente a `try ... trap`

Hay dos tipos de manejador.

`on code {msgVar optionsVar}` hace coincidir el _código de finalización_: `ok`, `error`, `return`, `break` o `continue`.
Todo error tiene el código de finalización `error`, así que `on error` no puede distinguir una división entre cero de un archivo que falta.
Tendrías que mirar el texto del mensaje, lo cual es frágil: los mensajes son para personas y pueden cambiar entre versiones de Tcl.

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` hace coincidir el _código de error_.
El manejador coincide cuando el patrón es un prefijo de la lista `-errorcode`.
Así se identifica el tipo de error de forma confiable.

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

Un patrón vacío, `trap {}`, coincide con cualquier error.
Los manejadores se revisan en orden, así que pon el comodín al final.

## Encontrar el código de error

¿Dónde está documentado `ARITH DIVZERO`?
Casi solo en el código fuente, pero Tcl te lo muestra.
Después de un error, la variable global `errorCode` guarda el código de error del error más reciente:

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

Dentro de un programa, obtenlo del diccionario de opciones:

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

El último elemento de un código de error suele ser un mensaje legible para personas, o el nombre de lo que causó el error.
Déjalo fuera de tu patrón `trap`: usa `{ARITH DIVZERO}`, no `{ARITH DIVZERO {divide by zero}}`.

### Algunos códigos de error comunes

Esta tabla no está completa.
Usa la técnica de arriba para encontrar el código de cualquier otro error.

| Situación             | Ejemplo                  | Código de error               |
| --------------------- | ------------------------ | ----------------------------- |
| División entre cero   | `expr {1 / 0}`           | `ARITH DIVZERO ...`           |
| Error de dominio matemático | `expr {sqrt(-1)}` | `ARITH DOMAIN ...`            |
| Archivo no encontrado | `open nosuchfile r`      | `POSIX ENOENT ...`            |
| Permiso denegado      | `open /root/x w`         | `POSIX EACCES ...`            |
| Comando desconocido   | `no::such::proc`         | `TCL LOOKUP COMMAND name`     |
| Variable desconocida  | `set nosuchvar`          | `TCL LOOKUP VARNAME name`     |
| Número de argumentos incorrecto | `string length a b` | `TCL WRONGARGS`          |
| Diccionario inválido  | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`        |
| Lista inválida        | `llength "a \{b"`       | `TCL VALUE LIST ...`          |

Los códigos de error `POSIX` usan los nombres de `errno` del sistema operativo, como `ENOENT`, `EACCES` y `EEXIST`.

## Pista: dónde se ejecuta el script

`handle_error` recibe un script de quien lo llama.
Si lo ejecutas con `try $script`, se evalúa en el ámbito de `handle_error`, no en el del llamador.
Para evaluarlo donde fue escrito, usa [`uplevel`][uplevel]: `try {uplevel 1 $script} ...`.

# Estrategia de fusión

Los mantenedores del track de Rust [han decidido](https://github.com/exercism/v3/discussions/1725#discussion-7438) documentar nuestra estrategia de fusión para comunicar las expectativas y fomentar contribuciones de calidad.

## Principios generales

- Nos esforzamos por aceptar _todas_ las contribuciones
  - Llevaremos las contribuciones a un alto estándar de calidad mediante una revisión colaborativa e iterativa.
  - Adoptamos un enfoque de fusión pesimista. Piensa en las revisiones de los mantenedores como en los comentarios del compilador de Rust. La cantidad de comentarios puede resultar abrumadora y frustrante. ¡Pero trabajaremos contigo para llevarlo hasta la meta! Así que sigue con el buen trabajo.
- Todo pull request debe tener al menos una «Approval» y ninguna «Request Changes» de un mantenedor del track antes de poder fusionarse.
- Ningún mantenedor puede aprobar su propio pull request.

## Flujo de trabajo de pull request

### Definiciones

| Término            |                                                                                               Significado |
| ------------------ | ----------------------------------------------------------------------------------------------------: |
| Colaborador        |                                                                     Cualquier persona que envíe un pull request. |
| Mantenedor         |         Cualquier persona que pertenezca al [equipo @exercism/rust](https://github.com/orgs/exercism/teams/rust). |
| Rama de desarrollo | La rama de desarrollo predeterminada del repositorio [v3](https://github.com/exercism/v3). Actualmente `master`. |

### El flujo de trabajo

1. Los colaboradores empiezan abriendo un pull request en [borrador](https://github.blog/2019-02-14-introducing-draft-pull-requests/) o un pull request completo con sus cambios
   1. Usar la funcionalidad de borrador indica que el trabajo está listo para una revisión de alto nivel, pero que los detalles pueden estar sin implementar, incompletos o incorrectos.
   1. Después de un número no especificado de iteraciones de los pasos 2 y 3, el colaborador marca el pull request como listo para revisión.
1. Otro mantenedor revisará la contribución y proporcionará comentarios.
1. El colaborador atenderá _todos_ los comentarios del mantenedor como parte del pull request.
   1. Los mantenedores considerarán usar la funcionalidad de sugerencias de GitHub para cambios menores o evidentes.
   1. Se anima a expresar desacuerdo cuando un colaborador cree que tiene razón y un mantenedor se equivoca sobre un punto de los comentarios. «Atender» un comentario no es sinónimo de implementarlo ciegamente.
1. El mantenedor revisará los comentarios y hará una de dos cosas:
   1. aprobar
   1. solicitar cambios adicionales. En este punto, el proceso vuelve al paso 3.
1. Tras la aprobación, un mantenedor fusionará su pull request.
   1. Los mantenedores fusionarán sus propios pull requests. Como los colaboradores no son necesariamente mantenedores, un mantenedor debe realizar este paso.

## Fusión optimista

Los mantenedores del track de Rust han decidido adoptar la fusión optimista de forma temporal para acelerar el desarrollo del track v3.

- Esto solo aplica al repositorio v3
- Volveremos a una estrategia de fusión pesimista cuando lancemos la v3 a producción.
- Aprobaremos y fusionaremos trabajo incompleto
  - Si compila, lo conservamos.
  - Priorizamos la velocidad de iteración sobre los detalles finos de un diseño de software correcto.
- Todo pull request debe tener al menos una «Approval» de un mantenedor del track antes de poder fusionarse.

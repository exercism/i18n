# Acerca de

En las aplicaciones de C#, la aleatoriedad generalmente se implementa con la clase `System.Random`.

Este [artículo][system-random] es una excelente introducción al tema.

Cuando te familiarizas con una clase de una biblioteca, siempre vale la pena estudiar la [documentación][system-random] de sus propiedades y métodos, y de sus sobrecargas.

El ejercicio de programación puso de relieve varios puntos:

- El generador de números aleatorios no requiere una [semilla][random-seedless].
- `Random.Next()` puede generar un rango de números enteros
- `Random.Double()` puede generar un double entre 0 y 1
- Los límites superiores en `Next...()`, `Double()` y `Sample()` son **exclusivos**, así que `Random.Next(1,19)` devolverá valores del 1 al 18, pero no el 19.
- Una vez que tengas tu número aleatorio, puedes hacer con él lo que quieras

Hay 3 patrones para implementar el último punto:

- Puedes obtener el número aleatorio y manipularlo. En el caso del ejercicio de programación, esto consistiría en llamar a `Random.NextDouble()` y multiplicar por 100. Este [artículo][random-use-case-array] explica cómo hacer selecciones aleatorias de un array.
- Puedes heredar de `System.Random` y sobrescribir el método `Sample()`.
- Puedes encapsular una instancia de `System.Random` como miembro de una clase propia, por ejemplo [para generar valores Boolean][random-use-cases].

Los números que genera `Random` no tienen garantía de ser únicos.

Se [recomienda][random-thread-safety] que instancies `System.Random` como miembro estático. Pero ten en cuenta que no es seguro para hilos.

Es posible que veas documentación que desaconseja el uso de constructores sin semilla. Esto se aplica sobre todo a .NET Framework y no tanto a .NET Core (que es lo que usa _Exercism_). Para conocer la historia completa, lee [esto][random-multiple-instantiations].

Se te recomienda no usar `System.Random` para criptografía o seguridad. Consulta este [proveedor][crypto-provider] y este [generador de números][crypto-rng].

## Seguridad de los hilos

Cuando se aplica en el contexto de las API de una biblioteca, «no es seguro para hilos» es simplemente una forma abreviada de decir que, si es probable que accedas a instancias de la clase desde varios [hilos][threading] simultáneos, deberías proporcionar tus propios mecanismos de sincronización de hilos o, en el caso de las colecciones, considerar la posibilidad de usar una versión concurrente de la clase. Si no tomas estas precauciones, es probable que ocurran [condiciones de carrera][so-race-conditions]. Si tu código no usa varios hilos, y es poco probable que lo haga, esta advertencia es de poca importancia.

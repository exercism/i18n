## Agregar contexto a los errores

Exploramos el manejo básico de errores en Go en el [concepto de errores][concept-errors].
Como aprendiste ahí, por defecto los errores no llevan consigo trazas de pila.
Por eso es fundamental asegurarte de que el error mismo contenga suficiente información para identificar el problema.

Si quisiéramos agregar información a un error existente con las herramientas que ya conocemos, podríamos escribir algo así para crear un error nuevo con el texto combinado del error original y la información adicional:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Por suerte, el paquete `fmt` de la biblioteca estándar incluye una versión abreviada de esto en forma de la función `Errorf`.
Eso te permite, por ejemplo, agregar fácilmente información sobre el contexto en el que ocurrió el error.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

A menos que tengas la certeza de que el error ya incluye suficiente información, procura adquirir el hábito de agregar siempre contexto a un error antes de devolverlo desde una función.
Eso significa que tu patrón estándar de manejo de errores debería verse así:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Como se muestra en los ejemplos, la convención es separar el error del mensaje agregado con dos puntos.
Igual que el mensaje del error original, el mensaje de contexto tampoco debe empezar con mayúscula ni llevar punto al final.

~~~~exercism/note
Cuando agregas contexto a un error, es tentador empezar el mensaje con «no se pudo ...» o algo parecido.
Sin embargo, como un error puede acumular mucho contexto adicional a medida que sube por la cadena de funciones, esto puede hacer que el mensaje final que se registrará o que verá el usuario sea más difícil de leer o quede lleno de repeticiones.

Aquí hay un ejemplo para ilustrarlo:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Así que ten en cuenta este resultado final al escribir los mensajes de contexto y evita agregar texto sobre el hecho de que algo no salió como se esperaba.
Esto por lo general ya queda claro por el contexto (por ejemplo, el nivel de registro «ERROR») y por el mensaje del error original.
~~~~

A menudo esta forma de agregar información a un error es suficientemente buena, pero hay casos en los que quieres permitir que quien consume tu error pueda comprobar u obtener el error original subyacente.
Agregar contexto de una manera que permita esto se llama «envolver un error» en Go.

## Envolver errores y comprobar errores centinela

Se puede envolver un error con un cambio muy pequeño en el código que vimos arriba.
Para envolver un error, necesitas usar el verbo de formato `%w` en lugar de `%v`.
Detrás de escena, esto se asegura de que el error resultante implemente un método `Unwrap` que devuelve el error original.
Por eso, después se puede usar `errors.Is` para comprobar si un error centinela específico aparece en algún punto de la «cadena de errores».
Lo hace llamando a `Unwrap` de forma interna, repetidamente, hasta que se encuentre el error en cuestión o hasta que termine la cadena.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Comprobar el error original con `errors.Is` no funcionaría con el verbo de formato `%v` normal.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Por eso, es una buena práctica usar `%v` de forma predeterminada y usar `%w` solo si quieres permitir explícitamente que quien consume tu error acceda a un error subyacente ([Guía de estilo de Go de Google][google-go-styleguide]).

Si te encuentras en una situación en la que quieres comprobar un error centinela pero explícitamente no quieres desenvolverlo, puedes usar `==` en lugar de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

En cambio, `==` no identificaría el error si estuviera envuelto.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Está bien trabajar con `errors.Is` de forma predeterminada, pero ten siempre presente que eso significa que se buscará en toda la cadena de errores.

## Comprobar tipos de error (personalizados)

Existe un equivalente a `errors.Is` que permite comprobar y obtener un error de un tipo específico de la cadena de errores.
La función para eso es `errors.As` y, al igual que `errors.Is`, buscará el tipo de error dado a lo largo de toda la cadena.
Solo cuando lo encuentra, `errors.As` extrae el error que coincide con el tipo para que puedas seguir trabajando con él, por ejemplo, obtener campos específicos.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Ten cuidado con la sintaxis de los punteros de arriba.
El código solo funcionará y compilará correctamente si `customError` tiene exactamente el tipo que implementa la interfaz de error.
En nuestro caso, ese es `*MyCustomError` (un [puntero][concept-pointers] a `MyCustomError`), no `MyCustomError` en sí.

Además, el segundo argumento debe ser un puntero a la variable del error.
Como nuestro error ya es un puntero, lo que le pasamos a `errors.As` es un puntero a un puntero (a MyCustomError).
Solo con esto configurado correctamente, Go puede entonces llenar la variable con el error que encontró.
~~~~

Como antes, `errors.As` no habría encontrado el tipo de error si se hubiera usado `%v` al llamar a `Errorf`.

Si por alguna razón no quieres desenvolver, puedes usar en su lugar una aserción de tipo (equivalente al `==` de arriba).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

Una aserción de tipo no podrá identificar el tipo de error si el error hubiera sido envuelto.

## Permitir desenvolver errores de tipos personalizados

A veces, solo envolver un error con algo de texto adicional no es suficiente.
En su lugar, puedes crear un tipo de error personalizado que contenga el error original y los datos estructurados adicionales que quieras agregar.
Si quieres permitir que tu tipo de error se pueda desenvolver, lo único que tienes que hacer es agregar manualmente un método `Unwrap() error` para cumplir con la interfaz `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Combinar varios errores

En Go 1.20, se agregó una nueva función `Join` al paquete `errors` integrado.
`Join` permite combinar varios errores en uno solo de una manera que aún permite desenvolverlos, es decir, comprobar si hay un error o un tipo de error específico a lo largo de la cadena.
Con eso, la cadena de errores puede en realidad ser un árbol de errores.
Puedes encontrar más información en las [notas de la versión][release-notes] y en la [documentación][doc-join].

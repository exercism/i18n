# Introducción

Los hilos de Factor son *corrutinas cooperativas*: comparten un mismo hilo del sistema operativo, se pasan el control entre sí en las operaciones de E/S y en los puntos de cesión explícitos, y nunca se ejecutan de forma realmente simultánea. Todo lo que haces *entre* cesiones ocurre como un solo paso ininterrumpido. Pero si una operación compuesta (leer, modificar y escribir) cede a mitad de camino, otro hilo puede colarse y cambiar el mundo antes de que termines, y eso es una condición de carrera.

Este ejercicio cubre cuatro primitivas que aparecen una y otra vez:

## `parallel-map`: fork/join sobre una secuencia

```
parallel-map ( seq quot: ( elt -- newelt ) -- newseq )
```

En [`concurrency.combinators`][combinators]. Crea un hilo por elemento, ejecuta la cita y recoge los resultados en una nueva secuencia en el mismo orden:

```factor
USING: concurrency.combinators sequences ;

{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }
```

## `spawn`: iniciar un hilo

```
spawn ( quot name -- thread )
```

En [`threads`][threads]. La cita se ejecuta de forma concurrente; `name` es una etiqueta para depurar. A este nivel, el manejador de hilo que se devuelve no tiene mucho interés: descártalo con `drop`.

## Promesas: transferencia de un valor de un solo uso

```
<promise>           ( -- promise )
fulfill             ( value promise -- )
?promise            ( promise -- value )
```

En [`concurrency.promises`][promises]. Una promesa es un buzón de un solo uso: un hilo la cumple y los demás la leen. `?promise` se bloquea hasta que la promesa se haya cumplido, y luego devuelve el valor.

```factor
USING: concurrency.promises kernel threads ;

<promise> [
    [ 42 swap fulfill ] curry "answer" spawn drop
] keep ?promise .
! => 42
```

`spawn` + `<promise>` es la base con la que se construye `parallel-map`; armarlos a mano es útil cuando cada tarea hace algo distinto de «calcular un elemento».

La típica forma de abanico/unión sobre una secuencia es la siguiente: por cada entrada, crea una promesa nueva, lanza un hilo que haga el trabajo y cumpla la promesa con `fulfill`, recoge todas las promesas en una secuencia y luego haz `?promise` con cada una para esperar a que termine. Las variables locales hacen que esto se lea bien: vincula la promesa a un nombre con `:>` dentro de una lambda `[| | ]` para que la cita lanzada pueda capturarla:

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
inputs [| x |
    <promise> :> p
    [ x do-work t p fulfill ] "worker" spawn drop
    p
] map [ ?promise drop ] each
```

## Bloqueos: exclusión mutua

```
<lock>     ( -- lock )
with-lock  ( lock quot -- )
```

En [`concurrency.locks`][locks]. Solo un hilo puede tener tomado un bloqueo determinado a la vez. `with-lock` lo adquiere, ejecuta la cita y lo libera, incluso si la cita lanza una excepción.

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
USING: concurrency.locks kernel locals ;

[let <lock> :> guard
    guard [ ! exclusive section ! ] with-lock
]
```

Usa un bloqueo siempre que *más de un hilo lea o escriba* un valor y las operaciones sobre ese valor no sean atómicas de forma natural. Tanto las lecturas como las escrituras necesitan el bloqueo, porque una lectura que ceda a mitad de camino puede ver un estado a medio actualizar.

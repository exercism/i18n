# Contribuir al track de C

¡Gracias por tu interés en contribuir al track del lenguaje C de Exercism!
Todas las contribuciones son bienvenidas: ya sea un nuevo ejercicio, un cambio en las herramientas o la documentación, un issue abierto o incluso solo un comentario en un issue o PR existente.
Este archivo ofrece información para ayudarte a empezar.

En primer lugar, lee la [documentación de Exercism][Exercism docs], en particular la información sobre [cómo contribuir a un track de lenguaje][contributing to a language track], ya que estos documentos cubren gran parte de la información básica.

Además, ten en cuenta que hay algunas cosas específicas de este repositorio que se explican a continuación.

Fomentamos las contribuciones que aporten correcciones y mejoras a los ejercicios existentes.
Ten en cuenta que los ejercicios de este track deben cumplir con los estándares definidos en el repositorio [problem-specifications][].
Los cambios en los tests o la documentación de un ejercicio común a menudo requerirán un pull request en ese repositorio antes de poder incorporarse a los ejercicios de este track.
Si no estás seguro, abre un [issue][] en GitHub y hablaremos del cambio.

## Código de Conducta

Ayúdanos a que Exercism siga siendo un espacio acogedor.
Lee y sigue el [Código de Conducta][Code of Conduct].

## Flujo de trabajo con Git

1. Haz un fork y clona.
2. Agrega este repositorio como un nuevo remoto a tu clon: `git remote add upstream https://github.com/exercism/c.git`
3. Crea una nueva rama: `git checkout -b name-of-branch`
4. Haz commit y push como de costumbre en tu nueva rama
5. Cuando estés listo para enviar un pull request, haz rebase de tu rama sobre main de upstream para poder resolver cualquier conflicto: `git fetch upstream && git rebase upstream/main` Es posible que necesites hacer push a tu rama usando `--force` después de resolver los conflictos.
6. Cuando tengas todo listo, haz push a tu rama y crea el pull request como se describe a continuación.

## Issues

Llevamos un registro de bugs, mejoras y solicitudes de soporte en el repositorio usando los [issues][] de GitHub.

Para conversaciones de más alto nivel sobre el proyecto en general, revisa los issues en el repositorio [discussions][].

### Good First Patch

Intentamos etiquetar los issues con «good first patch» si creemos que se pueden resolver sin demasiado contexto sobre el código base o el funcionamiento de Exercism. Para encontrarlos, puedes buscar [good-first-patch][].

## Pull Requests

Sería genial que siguieras estas sencillas [pautas para pull requests][pull request guidelines] al crear tu PR, pero no es obligatorio.

Los pull requests deben centrarse en un solo issue o cambio.
Aceptamos cambios en el estilo del código y en la redacción, pero por favor abre un PR aparte para esos cambios si es posible.
Abre un issue antes de crear un PR que haga cambios importantes (que rompen compatibilidad) en un ejercicio existente o que cambie muchos ejercicios. Lo mejor es hablar de estos cambios antes de hacer el trabajo.

Si tu cambio es en un ejercicio, puedes ejecutar los scripts de CI antes de enviar el pull request, o se ejecutarán automáticamente después, como se describe en [Integración continua][Continuous Integration].

Al enviar un pull request, a veces te pediremos que hagas cambios antes de aceptar el parche.

Por favor, no cierres el primer pull request y abras uno segundo con esos cambios.
Si haces push de más commits a una rama para la que abriste un pull request, este se actualiza automáticamente.

Si quieres crear un PR con cambios que aún no están listos para fusionarse en main (quizá quieras hablar de algún punto en particular, por ejemplo), crea el PR como de costumbre, pero usa la interfaz web de GitHub para [convertir el PR en borrador][convert the PR to a draft] para que los mantenedores sepan que aún no está listo para fusionarse.

Al igual que con agregar más commits, no necesitas cerrar tu pull request y abrir uno nuevo si cambias el historial (rebase, squash, amend) y usas git push --force para actualizar la rama en tu fork.
El pull request apunta a esa rama, no a commits específicos.

## Estilo de código

El estilo de código esperado para las contribuciones de cambios de código se explica en la [guía de estilo][style guide].

El código de los ejercicios se revisa durante la [CI][Continuous Integration] para comprobar que cumpla con las reglas de estilo de espaciado e indentación.
La comprobación usa la herramienta CLI [`clang-format`][clang-format].
Cuando agregues o modifiques un ejercicio, puedes comprobar que tu cambio cumple con estas reglas ejecutando la herramienta localmente antes de hacer commit.

En Linux, `clang-format` debería estar disponible para instalar mediante el gestor de paquetes de tu distribución.
En Mac puedes instalar el paquete `clang-format` usando [Homebrew][].

clang-format se puede ejecutar en todos los archivos ejecutando `format.sh`.
Para ejecutarlo manualmente en un solo archivo, puedes ejecutar lo siguiente:

```bash
clang-format -i $(file)
```

## Anatomía de un ejercicio

Cada ejercicio debe estar contenido en un directorio `c/exercises/practice/{exercise-name}`.
Consulta [implementar un ejercicio a partir de la especificación][implement-an-exercise-from-specification] para obtener detalles exhaustivos sobre cómo implementar un ejercicio que coincida con la especificación

La estructura de un directorio de ejercicio es la siguiente (observa el uso diferente de guiones y guiones bajos para nombres de directorios y nombres de archivos, respectivamente):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - Este archivo contiene todos los tests del ejercicio.  
`test-framework` - directorio que contiene el arnés de pruebas [Unity][] de [ThrowTheSwitch][].  
  ThrowTheSwitch tiene una guía decente sobre [cómo empezar con Unity][getting started with Unity] si quieres un tutorial.  
  La versión de Unity usada se indica en [versiones][versions]. La estructura del archivo de test se describe en la [guía de estilo][test-file-layout].  
  Los tests deben escribirse para satisfacer el archivo `canonical-data.json` del ejercicio en el repositorio [problem-specifications][]  
`{exercise-name}.c` / `{exercise-name}.h` - Los archivos fuente del ejercicio.  
  Por favor, usa [guardas de inclusión][include guards] en tus archivos de encabezado.
  Los tests del ejercicio se pueden ejecutar usando `make test` desde la raíz del repositorio.
* `makefile` - es el makefile del ejercicio tal como se compilaría.  
Se requieren dos reglas,  
test: compila test_{exercise-name}.c y ejecútalo.
memcheck: compila test_{exercise-name} con las flags -fsanitize=address, -fno-common, -fno-omit-frame-pointer y ejecútalo
Se espera que los makefiles cambien muy poco entre ejercicios, así que debería ser fácil copiar uno de otro ejercicio.

**No olvides** agregar el ejercicio al `config.json` del track. Para esto tendrás que determinar el mejor lugar para agregar el ejercicio dentro del orden de todos los demás ejercicios del track. También tendrás que generar un UUID para agregarlo aquí. Para ambas tareas puedes usar la herramienta [configlet][]; ¡la herramienta incluso hará lint y formateará el `config.json` por ti después de que hayas hecho estos cambios!

Para tu información: para obtener el artefacto de instalación de la herramienta configlet, consulta la [página de releases de configlet][configlet releases page].

## Integración continua

Este repositorio usa flujos de trabajo de GitHub para ejecutar algunas herramientas en cada commit de un pull request.
La forma más sencilla de ejecutar estos flujos de trabajo en tu propia contribución es abrir un PR en este repositorio con tus cambios, marcarlo como borrador y luego dejar que la configuración de CI de este repositorio se encargue de todo automáticamente.

### Entorno de CI

GitHub ejecuta la CI en máquinas virtuales a las que llama [ejecutores alojados][hosted runners].
Los flujos de trabajo pueden configurar algunos aspectos de los ejecutores en los que quieren ejecutarse.

Los flujos de trabajo de este repositorio solo especifican que cada uno debe ejecutarse en Ubuntu 24.04. Los flujos de trabajo están fijados a versiones específicas en lugar de referirse a `latest`, ya que algunas herramientas usadas pueden comportarse de forma diferente en distintas versiones.

### Ejecutar la CI en tu propio fork

Si quieres, también es posible ejecutar la CI en tu propio fork; simplemente clona este repositorio como de costumbre en GitHub.
Los archivos YAML ubicados en [`./.github/workflows/`][workflows] deberían funcionar igual.
Si quieres que la acción automatizada [`/format`][format-workflow] funcione correctamente, tendrás que agregar una clave de implementación a tu repositorio clonado.

### Los flujos de trabajo

* `checks.yml` ejecuta `shellcheck` en los scripts de herramientas y luego ejecuta las siguientes de esas herramientas:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * acción del [comprobador de enlaces Lychee][lychee]
* `configlet.yml` obtiene la última versión de configlet y luego ejecuta el comando `lint` en el track
* `format-code.yml` busca la cadena `/format` en cualquier comentario de un PR; si la encuentra, se ejecuta `format.sh` en los ejercicios y se hace commit de los cambios resultantes. Se requiere una clave de implementación para que el commit pueda volver a activar la CI. La clave de implementación la administra Exercism directamente.
* `test.yml` ejecuta `make` en la raíz del repositorio para probar todos los ejercicios

### Las herramientas

Puedes ver en los [flujos de trabajo][workflows] que se le indica a GitHub que ejecute herramientas del directorio [`./bin`][bin].
El trabajo que realizan las herramientas de este directorio se describe a continuación:

* `check-unitybegin` asegura que cada archivo de test agregue correctamente la línea `UNITY_BEGIN()` al inicio de su función `main()`.
* `fetch-configlet` obtiene la herramienta `configlet` de su [repositorio][configlet].
* `verify-unity-version` comprueba la versión del framework de test Unity usado por cada ejercicio. La versión que este archivo debe comprobar se especifica en [`./docs/VERSIONS.md`][versions]
* `check-include-guards` comprueba que las guardas de inclusión usadas en el stub y el encabezado de ejemplo de cada ejercicio usen el formato correcto, como se muestra a continuación:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` obtiene la herramienta `configlet` de su [repositorio][configlet].

### Ejecutar las herramientas localmente

También puedes ejecutar herramientas individuales en tu propia máquina antes de hacer commit.
Primero asegúrate de tener instaladas las aplicaciones necesarias (como `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] y un compilador de C), y luego ejecuta la herramienta requerida desde la raíz del repositorio. Por ejemplo:

```bash
~/git/c$ make
```

Si quieres ejecutar solo algunos de los tests para comprobar tu trabajo, puedes especificarlos como objetivos de make.

```bash
~/git/c$ make acronym all-your-base allergies
```

## Test runner

¡Este track tiene un test runner para Exercism v3!
Puedes verlo [aquí][c-test-runner].

Los test runners proporcionan un método dockerizado para ejecutar los tests de un ejercicio contra el código de un estudiante en Exercism v3.
Este enfoque con Docker ayuda a permitir que los estudiantes programen en el navegador.

# Introducción

Hasta ahora, el temario no ha dicho mucho sobre los tipos, pero está claro que existen en Julia:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

Nunca especificamos los tipos, pero Julia los asignó de todos modos.

1. Julia tiene `types`, que son centrales en su diseño.
2. Julia normalmente puede «adivinar» el tipo, usando `Type Inference`.

El compilador JIT revisará (todo) el código, verá cómo se usa una variable y _inferirá_ un tipo predeterminado adecuado y compatible con ese uso.

## Promoción de tipos

Ha habido muchos ejemplos en conceptos anteriores que fuerzan tipos numéricos a la uniformidad, empezando por la aritmética más simple.

```julia-repl
julia> 2 + 1.3
3.3
```

Sumamos un número entero (Int64) y un número de punto flotante (Float64), y obtuvimos un resultado Float64.
De manera similar:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

En el caso anterior, una tupla conservó el tipo de cada elemento, pero al convertirla en un vector, todos cambiaron a un Float64 uniforme.

El compilador de Julia entiende qué conversiones de tipos son posibles: de entero a punto flotante no hay problema; de punto flotante a entero se pierde precisión, así que se lanza un `InexactError`.
La promoción de tipos convierte todos los valores de la expresión a un tipo común, lo bastante versátil para ser compatible con todos los valores implicados.

## Asignación de tipos

Confiar en la inferencia de tipos está bien para resolver ejercicios sencillos de tutorial, pero para programas más grandes es probable que necesites un control más preciso.

En la mayoría de los procesadores modernos, un entero es `Int64` por defecto.
Vimos en el concepto [`Numbers`][numbers] que un valor se puede convertir a un tipo particular distinto del predeterminado.

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

Sin embargo, a la variable `x` todavía se le puede asignar un tipo diferente:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

Esto es `type instability`, que es:

- Muy conveniente en scripts pequeños.
- Malo para el rendimiento y la fiabilidad en programas más grandes.

En cambio, podemos fijar el tipo de `x` usando el operador `::`:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

Ahora `y` es, y siempre será, de tipo `Int16`.
Así, el compilador sabe cuántos bytes reservarle y puede optimizar el resto del código para apoyarse en un tipo estable.
En esto, la variable se parece más o menos a las de un lenguaje de tipado estático como C.

## Aserción de tipos

La asignación de tipos, descrita antes, se usa en el lado izquierdo de una asignación de variable para restringir el tipo de esa variable.

Usar el operador `::` con un valor, o con algo que se evalúa a un valor, es en general una _aserción_ de que el valor debe ser de este tipo; de lo contrario, debería lanzarse un error.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Es común usarlo con el valor que devuelve una función, como una última comprobación sencilla de que la función se comportó como se esperaba.

## La jerarquía de tipos

`Int64`, `Int16`, `String`, `Char`: ¿de dónde _"vienen"_ estos tipos?

En muchos lenguajes orientados a objetos (OO), cada tipo es una clase, la creación de subclases las organiza en una jerarquía de clases y los métodos de clase definen los comportamientos.

Java y Ruby son ejemplos claros de este patrón, pero incluso Python es similar internamente.

***Julia no tiene clases.***

La razón documentada es que las características de la orientación a objetos interfieren con el compilador JIT y perjudican el rendimiento en tiempo de ejecución.

Y aun así, mira este código:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

Con algunos detalles:

- `Int16` es un tipo, y podemos crear variables de este tipo.
- `Int16` es un subtipo de `Signed`, y la función `supertype()` nos lo muestra.
- Hay una jerarquía de tipos que sube por `Integer`, `Real` y `Number` hasta `Any` en la cima, y `subtypes()` nos listará esta rama de la jerarquía.

Todas las ramas terminan en `Any`, que tiene la particularidad de ser su propio supertipo.

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

Así que Julia no tiene una jerarquía de `class`, pero _sí_ tiene una jerarquía de `type`.

Con el tiempo intentaremos desentrañar cómo funciona esto, pero antes hay mucho más por explorar.

## Comprobar tipos

Podemos usar `typeof()` para comprobar la igualdad de la forma habitual.

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

La igualdad de tipos debe ser exacta, ya que esta forma de comparación no entiende la jerarquía de tipos.

De forma más flexible, `isa` nos dirá si un valor tiene el mismo tipo que el comparador o un subtipo de él.
Se puede usar tanto en forma de función como de infijo.

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

Fíjate que `isa` espera un `value` a la izquierda, no un `type`.

Intentar comparar dos _tipos_ de esta manera dará resultados inesperados.
El operador correcto es `<:`, que veremos mucho más en conceptos futuros.

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## Tipos abstractos y concretos

Vimos que la jerarquía de tipos forma una estructura de árbol (en el sentido de las ciencias de la computación, con la raíz arriba).

Cada elemento del árbol es un `node`, y estos se pueden dividir en categorías:

1. Los nodos con subtipos se llaman `abstract`.
2. Los nodos hoja, sin subtipos, se llaman `concrete`.

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

Esta es una distinción importante, porque solo los tipos concretos se pueden `instantiated` como variables.


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

Fíjate que intentar usar un tipo abstracto no da ningún mensaje de error (en este caso), pero el compilador crea un tipo concreto adecuado: `Int64` en lugar de `Integer`.
Al menos evita que a la variable se le asigne algo que no sea un entero:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

Por lo tanto, la asignación de tipos con un tipo abstracto es una _restricción_ sobre el tipo de la variable, a cualquiera de los subtipos de (en el caso anterior) `Integer`.
Esto es algo poco común en el mundo de los lenguajes de programación: más débil que una asignación de tipo en C, más fuerte que una sugerencia de tipo en versiones recientes de Python.

Las funciones `isabstracttype()` y `isconcretetype()` permiten comprobarlo.
Fíjate que no son simplemente la negación una de la otra: en un concepto posterior veremos que algunos tipos no pueden ser ni abstractos ni concretos.


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

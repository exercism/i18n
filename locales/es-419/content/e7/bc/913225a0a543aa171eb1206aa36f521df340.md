# Generadores de tests

Los generadores de tests permiten que los tracks generen tests automáticamente sin tener que escribirlos nosotros mismos. Cada generador de tests lee el `canonical data` del ejercicio, que define el nombre del test, sus argumentos y sus valores esperados. Puedes leer más sobre el enfoque de exercism para los conjuntos de tests [aquí](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Generar los tests automáticamente elimina cualquier tipo de error humano al crearlos. Queremos que los tests sean precisos con respecto a sus datos canónicos. La generación de tests también hace mucho más fácil mantenerlos actualizados. Cuando los datos canónicos cambian, los tests se actualizan automáticamente al ejecutar el generador de ese test.

Puedes encontrar un ejemplo de archivo de datos canónicos [aquí](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)

## Términos comunes

Cuando revisas los datos canónicos y el código base de los generadores, verás que usamos mucha terminología común. Esperamos que esta lista aclare qué representa cada término.

* Datos canónicos - Representan todo el conjunto de tests.
* Caso de datos canónicos - La representación de un solo caso de test.
* Descripción - El nombre del test.
* Propiedad - El método que se llama al ejecutar el test.
* Argumento - El valor que recibe el caso de test.
* Valor esperado - El valor que se espera al ejecutar el caso de test.

## Cómo agregar un generador simple

Agregar un generador de tests es sencillo. Solo agrega una clase al archivo `Generators.fs` de la carpeta `generators`, con el nombre del ejercicio (en PascalCase), y extiende la clase abstracta `GeneratorExercise`.

Un ejemplo de un generador simple sería el ejercicio Bob. El código fuente aparece abajo, pero también puedes verlo en el repositorio [aquí](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174).

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

Este es un generador que funciona por completo; no hace falta escribir ningún otro código. Sin embargo, su sencillez se debe a que el conjunto de tests y el programa en sí son relativamente triviales.

## Cómo agregar un generador complejo

Para muchos generadores, el comportamiento predeterminado de la clase `GeneratorExercise` es suficiente. Sin embargo, para generadores más _complejos_, puedes sobrescribir uno o más de sus métodos virtuales:

### Método: RenderInput

Renderiza el argumento de un método de test.

#### Ejemplo

El generador `Gigasecond` renderiza el argumento como un valor `DateTime` entre paréntesis:

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

Ten en cuenta que puedes usar el campo `key` para personalizar la salida solo en argumentos específicos. El generador `Yacht` lo hace así:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Método: RenderExpected

Renderiza el valor esperado de un método de test.

#### Ejemplo

El generador `Connect` renderiza el valor esperado como un valor `Option<T>`:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Método: RenderSut

Renderiza el sistema bajo prueba (SUT). Este es el valor real que se verifica contra el valor esperado.

#### Ejemplo

El generador `RunLengthEncoding` tiene un caso de test en el que verifica que codificar y luego decodificar el argumento da como resultado el mismo valor. Se sobrescribe el método `RenderSut` para convertir lo que sería una sola llamada a una función `consistency` inexistente en una cadena de llamadas `encode |> decode`:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Método: RenderArrange

Renderiza la parte de preparación del método de test. En esta parte se crea el SUT.

El comportamiento predeterminado suele ser lo que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

Nota: este método devuelve un `string list`, donde cada `string` corresponde a una sola línea renderizada del archivo de test.

### Método: RenderAssert

Renderiza la parte de aserción del método de test. En esta parte se hace la aserción para verificar el SUT contra el valor esperado.

El comportamiento predeterminado suele ser lo que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

Nota: este método devuelve un `string list`, donde cada `string` corresponde a una sola línea renderizada del archivo de test.

### Método: RenderSetup

Renderiza los métodos adicionales de utilidad o de preparación. Esto se puede usar para definir métodos auxiliares que se pueden usar en los métodos de test.

El código de preparación se agrega _antes_ de los métodos de test, para que los métodos de preparación se puedan usar en los métodos de test.

Nota: este método devuelve un `string list`, donde cada `string` corresponde a una sola línea renderizada del archivo de test.

#### Ejemplo

El generador `Zipper` agrega dos métodos auxiliares que se usan en los métodos de test para eliminar algo de código repetitivo y tedioso:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Método: RenderValue

Renderiza un solo valor (que se usa para renderizar los argumentos, el valor esperado y el SUT).

### Ejemplo

El generador `ComplexNumbers` renderiza valores distintos según el tipo del valor:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Método: MapCanonicalDataCase

Mapea el caso de datos canónicos. Esto puede ser útil si quieres agregar o quitar propiedades.

El comportamiento predeterminado suele ser lo que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

#### Ejemplo

El generador `ScaleGenerator` usa el mapeo del caso de datos canónicos para agregar una propiedad que falta con el valor `null` (lo que hace más fácil el procesamiento posterior):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Método: PropertiesUsedAsSutParameter

Especifica qué propiedades deben usarse como parámetros del SUT.

El comportamiento predeterminado suele ser lo que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

#### Ejemplo

El generador `RailFenceCipher` define de forma explícita las propiedades que se usan como parámetros del SUT para cambiar el orden en que se pasan:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Método: PropertiesWithIdentifier

Especifica qué propiedades deben tener un identificador asignado. Si una propiedad está en esta lista, se le asignará su valor en una línea aparte, a su propio identificador.

#### Ejemplo

El generador `Transpose` eligió usar identificadores para todas las propiedades:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Método: IdentifierTypeAnnotation

En algunos casos, quieres que un identificador tenga un tipo explícito. Un caso de uso común es cuando un valor es una lista vacía. En esos casos, FsUnit necesita una anotación de tipo para poder ejecutar la aserción correctamente.

#### Ejemplo

El generador `Minesweeper` agrega una anotación de tipo `string list` para los valores vacíos:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Método: AdditionalNamespaces

Devuelve una lista de espacios de nombres adicionales que se abren en el archivo de test.

#### Ejemplo

El generador `Gigasecond` trabaja con instancias de `DateTime` y, por eso, agrega su espacio de nombres a la lista de espacios de nombres adicionales:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Método: AssertTemplate

La plantilla de aserción que se debe usar. Puedes encontrar la lista completa de plantillas de aserción en `generators/Templates/_Assert*.liquid`

#### Ejemplo

El generador `RationalNumbers` usa la plantilla `"AssertEqualWithin"` para permitir comprobar la igualdad de valores `double` con una tolerancia específica:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Método: TestFileFormat

El formato del archivo de test: un módulo o una clase.

El comportamiento predeterminado es casi siempre lo que quieres. Solo en casos extremadamente raros querrás cambiarlo.

#### Ejemplo

El generador `Grep` se define como una clase de test para permitir el uso de métodos de preparación y de limpieza:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Método: TestMethodName

Especifica el nombre del método de test.

El comportamiento predeterminado suele ser lo que quieres. Solo en circunstancias muy especiales querrás cambiarlo.

#### Ejemplo

El generador `Zipper` hace una pequeña limpieza del nombre del método de test:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Método: UseFullMethodName

Indica si el nombre del método de test que se usa debe usar la ruta completa, lo que significa que, en los casos de test anidados, antepondrá al nombre del método de test la descripción de los padres.

El comportamiento predeterminado suele ser lo que quieres. Solo querrás cambiarlo cuando, de lo contrario, hubiera varios métodos de test con el mismo nombre.

#### Método: Signature

El generador `KindergartenGarden` usa nombres de método completos para evitar que los nombres de los métodos de test choquen:

```fsharp
override __.UseFullMethodName _ = true
```

### Método: SkipTestMethod

Indica si el método de test debe marcarse con la propiedad `Skip = true`.

El comportamiento predeterminado es casi siempre lo que quieres. Solo en casos extremadamente raros querrás cambiarlo.

#### Método: Signature

El ejercicio `Markdown` es un ejercicio de refactorización y, como tal, todos sus tests ya deberían estar en un estado válido. Por eso no agrega la propiedad `Skip` a ninguno de sus métodos de test:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Actualizar archivos existentes

Es posible que un ejercicio existente no coincida con los datos canónicos. ¡No hay problema en actualizar el stub del ejercicio y/o el ejemplo del ejercicio para que sigan los datos canónicos!

Además, si encuentras un problema en alguno de los generadores o conjuntos de tests existentes, simplemente abre el generador que quieras actualizar, haz tus cambios y luego ejecuta los generadores.

## Ejecutar los generadores

Este repositorio está escrito para [.NET Core 2.x](https://www.microsoft.com/net/core). Para ejecutar los generadores, solo tienes que ejecutar el siguiente comando en el directorio de los generadores:

`dotnet run`

Este comando toma todos los generadores de tests de los ejercicios que están definidos y genera todos los casos de test de cada ejercicio. Usamos reflexión para obtener todos los ejercicios, así que si agregas un test nuevo, este se incluirá automáticamente al ejecutar el generador.

Si solo necesitas ejecutar un generador, puedes hacerlo con el siguiente comando:

`dotnet run -e <exercise>`

Una vez que se haya ejecutado el generador, puedes ver el resultado de tu generación si vas al archivo de test de ese ejercicio. Por ejemplo, el conjunto de tests del ejercicio Bob está en:

`exercises/bob/BobTests.fs`

## Enviar un generador

Si estás conforme con el resultado de tu generador, ¡nos encantaría que enviaras un pull request! Incluye tu generador, el conjunto de tests actualizado y cualquier otro archivo correspondiente que hayas cambiado.

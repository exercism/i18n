# Introducción

## La interfaz de error

En Go, el manejo de errores **no** se hace con excepciones.
En su lugar, los errores son _valores_ normales de tipos que implementan la interfaz `error` incorporada.
La interfaz `error` es muy minimalista.
Contiene un solo método, `Error()`, que devuelve el mensaje de error como string.

```go
type error interface {
  Error() string
}
```

Cada vez que defines una función en la que puede ocurrir un error durante la ejecución que necesita llegar a quien la llama, debes incluir `error` como uno de los tipos de retorno.
Si la función tiene varios valores de retorno, por convención `error` es siempre el último.

```go
func DoSomething() (int, error) {
  // ...
}
```

## Crear y devolver un error simple

No siempre tienes que implementar tú la interfaz de error.
Para crear un error simple, puedes usar la función `errors.New()`, que forma parte del paquete `errors` de la biblioteca estándar.
Lo único que necesitas pasar es el mensaje de error como string, y `errors.New()` se encargará de crear un valor que contiene tu mensaje e implementa la interfaz `error`.

Si la función devuelve un error, es buena práctica devolver el valor cero para todos los demás parámetros de retorno:

```go
func DoSomething() (SomeStruct, int, error) {
  // ...
  return SomeStruct{}, 0, errors.New("failed to calculate result")
}
```

~~~~exercism/caution
No debes asumir que todas las funciones devuelven valores cero para los demás valores de retorno cuando hay un error.
Lo mejor es asumir que no es seguro usar ninguno de los otros valores de retorno si ocurrió un error.
Las únicas excepciones son los casos en los que la documentación indica claramente que los demás valores de retorno son significativos en caso de error.
~~~~

Si quieres usar un error simple como este en varios lugares, debes declarar una variable para el error en lugar de usar `errors.New` en línea.
Por convención, el nombre de la variable debe empezar con `Err` o `err` (según si es exportada o no).
A estas variables de error se las suele llamar _errores centinela_.

```go
import "errors"

var ErrNotFound = errors.New("resource was not found")

func DoSomething() error {
  // ...
  return ErrNotFound
}
```

Devuelve `nil` como error para indicar que no hubo errores durante la ejecución de la función:

```go
func Foo() (int, error) {
  return 10, nil
}
```

## Verificación de errores

Si llamas a una función que devuelve un error, es común guardar el valor del error en una variable llamada `err`.
Antes de usar el resultado real de la función, debes comprobar que no hubo ningún error.

Para evitar anidar el flujo normal de tu código, conviene manejar primero los casos de error.
Podemos usar `==` y `!=` para comparar el error con `nil`, y sabemos que hubo un error cuando `err` no es `nil`.

```go
func processUserFile() error {
	file, err := os.Open("./users.csv")
	if err != nil {
		return err
	}

	// do something with file
}
```

La mayoría de las veces, el error se devolverá hacia arriba en la pila de funciones, como se muestra en el ejemplo anterior.
Otra forma de manejar el error podría ser registrarlo y continuar con alguna otra operación.
Es buena práctica devolver o registrar el error, nunca ambas cosas.

Como la mayoría de las funciones en Go incluyen un error como uno de los valores de retorno, verás y usarás el patrón `if err != nil` por todas partes en el código de Go.

## Tipos de error personalizados

Si quieres que tu error incluya más información que solo el mensaje de error como string, puedes crear un tipo de error personalizado.
Como se mencionó antes, todo lo que implemente la interfaz `error` (es decir, que tenga un método `Error() string`) puede servir como error en Go.

Normalmente, se usa un struct para crear un tipo de error personalizado.
Por convención, los nombres de los tipos de error personalizados deben terminar en `Error`.
Además, lo mejor es definir el método `Error() string` con un receptor puntero; consulta este [comentario de Stack Overflow][stackoverflow-errors] para entender el razonamiento.
Ten en cuenta que esto significa que debes devolver un puntero a tu error personalizado; de lo contrario, no contará como `error`, porque el valor que no es puntero no proporciona el método `Error() string`.

```go
type MyCustomError struct {
  message string
  details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.message, e.details)
}

func someFunction() error {
  // ...
  return &MyCustomError{
    message: "...",
    details: "...",
  }
}
```

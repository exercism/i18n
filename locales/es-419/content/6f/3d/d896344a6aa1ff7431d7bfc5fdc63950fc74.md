# Acerca de

Como vimos en el concepto [`Nothingness`][concept-nothingness], R tiene varias formas de representar datos que están ausentes ([`NULL`][ref-null]), son desconocidos ([`NA`][ref-na]) o son matemáticamente inválidos ([`NaN`][ref-finite], [`Inf`][ref-finite]).
En general, R intentará usar estos valores para señalar problemas sobre la marcha y continuar sin lanzar una excepción.

## `stop()`

Algunos problemas son demasiado fundamentales como para dejar que el programa continúe.
En ese caso, usa [`stop(msg)`][ref-stop] para detener el programa de inmediato con un `Error` e imprimir `msg`.

```R
f <- function() {
    stop("I have a problem")
}
f()
#> Error in f() : I have a problem
```

## `stopifnot()`

Similar a un [`assert`][wiki-assert] en otros lenguajes, [`stopifnot()`][ref-stopifnot] es un envoltorio conveniente para `stop()`.
Los argumentos son un número arbitrario de condiciones booleanas, separadas por comas, y el programa solo continuará si todas son `TRUE`.

```R
stopifnot(1 < 2) # continues OK
stopifnot(1 < 2, 1 == 2)
#> Error: 1 == 2 is not TRUE
```

## `try()`

R tiene varias formas de manejar errores.
Estas se basan en Common Lisp y difieren bastante de las de muchos lenguajes populares.

La más simple es envolver el código potencialmente problemático en [`try()`][ref-try].

```R
g <- function(val) {
  log10(val)
}

g(3)
#> [1] 0.4771213

g("3")
#> Error in log10(val) : non-numeric argument to mathematical function

# with try() and a default value
h <- function(val) {
  result <- NA
  try(result <- log10(val))
  result
}

h(3) # works as before
#> [1] 0.4771213

h("3") # returns a default value plus the error message
Error in log10(val) : non-numeric argument to mathematical function
#> [1] NA
```

## [`warning()`][ref-warning] y [`message()`][ref-message]

Estas son respuestas a condiciones no fatales, por ejemplo:

- Para advertir sobre un problema del que el programa podría recuperarse al menos en parte.
- Para informar al usuario del progreso en un programa de larga duración.

Una diferencia entre ambas es que las advertencias se guardan en caché y (por defecto) se muestran cuando la función termina, mientras que los mensajes se muestran de inmediato.
Hay muchas formas de cambiar el comportamiento por defecto, que van más allá del alcance de este concepto.

```R
w <- function() {
  warning("something strange happened")
  -1
}

w()
#> [1] -1
#> Warning message:
#> In w() : something strange happened

# if warnings are not wanted
suppressWarnings(w())
#> [1] -1
```

La función [`suppressWarnings()`][ref-warning] puede ser útil en ocasiones dentro de Exercism, para evitar confundir al test runner con salidas no deseadas.

## Manejadores de condiciones

R tiene una forma alternativa de tratar los estados de error, más cercana en espíritu al enfoque de Java y lenguajes relacionados.

Los detalles quedan fuera del alcance de este concepto, pero quien esté interesado puede consultar [`tryCatch`][ref-conditions] y [`withCallingHandlers`][ref-conditions].

Hay un buen análisis en la [sección 8.4][book-handling] de Advanced R.

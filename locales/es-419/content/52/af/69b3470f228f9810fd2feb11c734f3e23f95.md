# Cómo contribuir al track de Rust de Exercism

Por ahora, los issues y los pull requests se cierran automáticamente.
Publica un mensaje en [el foro de Exercism][the Exercism forum] para proponer cambios.
Las contribuciones son muy bienvenidas si se coordinan en el foro.

[the Exercism forum]: https://forum.exercism.org/

## Políticas generales

- [Código de conducta](https://exercism.org/code-of-conduct)
- [Guías de PR de Exercism](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## Herramientas

Parte de las herramientas están presentes como scripts de bash en `bin/`.
Hay muchas más en `rust-tooling/`,
y deberías preferir estas para cualquier cosa no trivial.

También hay una configuración de [`mise`](https://mise.jdx.dev/)
con un par de comandos útiles para interactuar con el repositorio.
Siéntete libre de ampliarla.

Si quieres ejecutar las pruebas de CI localmente, `mise run test` te llevará bastante lejos.

## Excluir pruebas y agregar pruebas personalizadas

Mientras creas o actualizas un ejercicio, puedes decidir excluir ciertas pruebas para que no se generen.
Puedes hacerlo estableciendo `include = false` en `.meta/tests.toml`.
Incluye un comentario con la razón para excluirla.

Si quieres agregar pruebas adicionales específicas del track, puedes hacerlo en un archivo `.meta/additional-tests.json`.
Hazlo solo si tienes una buena razón para no subir estas pruebas al upstream.
Un comentario en la prueba adicional debería responder estas preguntas:
- ¿Por qué la prueba no se sube al upstream `problem-specifications`, es decir, por qué no es valiosa en general para otros lenguajes?
- ¿Por qué la prueba sí es valiosa para el track de Rust?

## Crear un ejercicio nuevo

Familiarízate con la [documentación de Exercism sobre los ejercicios de práctica][Exercism documentation about practice exercises].

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

Ejecuta `mise run add-exercise` y se te pedirá la información mínima
necesaria para generarte el esqueleto del ejercicio.
Después de eso, entra al ejercicio generado y completa los marcadores de posición que encuentres.
Esto incluye, sobre todo:

- escribir el esqueleto del ejercicio en `src/lib.rs`
- agregar una solución de ejemplo en `.meta/example.rs`
- ajustar `.meta/test_template.tera`

Las pruebas se generan con el motor de plantillas [Tera].
La entrada de la plantilla son los datos canónicos de [`problem-specifications`].

Encuentra algunos consejos sobre cómo escribir plantillas de tera [aquí](#tera-templates).

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

Muchos aspectos de un ejercicio implementado correctamente se verifican en CI.
Te recomiendo que, en lugar de pasar mucho tiempo estudiando y escribiendo
documentación sobre el proceso, _simplemente lo hagas_.
Si algo se rompe, arréglalo y agrega una prueba o automatización
para que no vuelva a pasar.

Si estás creando un ejercicio de práctica desde cero,
uno que no está en `problem-specifications`,
tienes que escribir las pruebas a mano.
Las pruebas deben estar ordenadas por complejidad creciente,
para que los estudiantes puedan quitarles el ignore una por una y resolver el ejercicio con TDD.
Consulta [la documentación de Exercism](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)
para más ideas sobre cómo escribir buenas pruebas.

Salvo en circunstancias extraordinarias,
el archivo esqueleto debería compilar con `cargo test --no-run`.
Esto nos permite verificar que las firmas del archivo esqueleto
coincidan con las firmas que esperan las pruebas.
Usa `todo!()` como cuerpo de cada función para lograrlo.
Si hay una razón justificada por la que esto no es posible,
incluye una clave `.custom."allowed-to-not-compile"`
en el `.meta/config.json` del ejercicio que contenga la razón.

## Actualizar un ejercicio

Muchos ejercicios se derivan de [`problem-specifications`].
Esto incluye su conjunto de pruebas y la documentación que ven los usuarios.
Antes de proponer cambios aquí,
verifica si deberían hacerse en `problem-specifications`.

Ejecuta `mise run update-exercise` para actualizar un ejercicio.
Esto delega la mayor parte del trabajo a `configlet sync --update`
y vuelve a ejecutar el generador de pruebas.

Cuando actualizas un ejercicio que todavía no tiene una plantilla de tera,
se generará una nueva para ti.
Es probable que tengas que ajustarla en cierta medida.

Encuentra algunos consejos sobre cómo escribir plantillas de tera [en la siguiente sección](#tera-templates).

## Plantillas de tera

La documentación completa de las plantillas de tera está [aquí][tera-docs].
A continuación hay algunos enfoques que han funcionado para nuestras necesidades específicas.

Probablemente quieras mirar el `canonical-data.json` del ejercicio para ver cómo son tus datos de entrada.
Puedes usar `bin/symlink_problem_specifications.sh` para enlazar simbólicamente estos datos
en el directorio real del ejercicio. ¡Muy útil!

El nombre de la propiedad de entrada es distinto en cada ejercicio.
La plantilla predeterminada será algo como esto:

```txt
let input = {{ test.input | json_encode() }};
```

Tendrás que agregar el campo específico de entrada para este ejercicio, por ejemplo:

```txt
let input = {{ test.input.integers | json_encode() }};
```

Algunos ejercicios pueden tener valores de retorno de error.
Puedes usar un if-else para renderizar algo distinto,
según la estructura de los datos:

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

Algunos ejercicios tienen varias funciones que el estudiante debe implementar
y que, por lo tanto, hay que probar.
En ese caso, los datos canónicos contienen un campo `property`.
Puedes construir cadenas de if-else basadas en `test.property` y renderizar una función distinta según eso.

Algunos ejercicios tienen sus casos de prueba organizados en _grupos de pruebas_.
Tu plantilla tendrá que tenerlo en cuenta.
En muchos casos, puedes simplemente aplanar la estructura. (ejemplo: [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
Sin embargo, a veces las pruebas tienen la misma descripción en grupos distintos, lo que genera conflictos de nombres si se aplana la estructura.
En ese caso, puedes usar la descripción del grupo para organizar las pruebas en módulos. (ejemplo: [`forth`](/exercises/practice/forth/.meta/test_template.tera))

Hay algunos filtros de tera personalizados en [`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs).
Esta es la lista, con suerte actualizada:
- `to_hex` formatea los enteros en hexadecimal
- `make_ident` convierte un string arbitrario en un identificador de Rust decente.
   Es lo más útil para generar nombres de funciones a partir de las descripciones de las pruebas.
- `fmt_num` formatea literales numéricos (inserta un `_` cada tres dígitos)

Siéntete libre de agregar los tuyos en el crate `rust-tooling`.
Con suerte, te acordarás de actualizar también esta lista. 🙂

Para un ejemplo bastante complicado, mira la plantilla de pruebas de `triangle`.
Organiza los casos de prueba en módulos y detecta dinámicamente qué pruebas hay que poner detrás de feature gates.
Ese ejercicio también reimplementa algunos casos de prueba del upstream en `additional-tests.json`, para agregarles la información adicional necesaria para generar buenas pruebas.

[tera-docs]: https://keats.github.io/tera/docs/#templates

## Temario

El temario está desactivado por ahora debido a su baja calidad.
Consulta [esta publicación del foro](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)
para conocer algo del contexto de la decisión.

Crear un temario mejor sería muy beneficioso,
pero es mucho trabajo y requiere buena comunicación y coordinación.
Asegúrate de comentar en el foro cualquier plan que tengas
con personas que tengan experiencia creando temarios.

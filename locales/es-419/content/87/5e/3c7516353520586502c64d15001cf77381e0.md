# Prepárate para recibir contribuciones de desconocidos en tu proyecto de código abierto

En este punto ya deberías poder aceptar contribuciones de desconocidos.
Escribe algo de [documentación para contribuir](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors) que ayude a los desconocidos a contribuir.

## Issues

Si hay ejercicios que quieres incluir en el track, pero que aún no has implementado, abre un issue para cada ejercicio.
En general, recomendamos abrir issues para las tareas en las que aceptarías contribuciones.

Tenemos una sección especial en el sitio web que lista _tareas_, que son issues con una o más etiquetas especiales.
Que tus issues aparezcan listados en el sitio web es una gran forma de conseguir más contribuciones.
Para más información sobre cómo hacer que tus issues aparezcan en el sitio web, consulta la [documentación de tareas](/docs/building/product/tasks).

## Otras cosas a tener en cuenta

- ¿Existe una guía de estilo para tu lenguaje de programación?
- ¿Estos estilos se fomentan o se hacen cumplir?
- ¿Hay convenciones que deberíamos adoptar en este track para mantener la consistencia?
- ¿Podemos hacer que se cumplan?
- ¿Existe un linter? ¿Hay muchos? ¿Deberíamos usar alguno?
- ¿Existe una convención común para los nombres de archivo? Si no, ¿cuál debería ser nuestra convención?

Puede valer la pena abrir issues separados para las cosas que quieras abordar.

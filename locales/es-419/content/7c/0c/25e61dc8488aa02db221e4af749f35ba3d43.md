# Introducción

## Agregar contexto a los errores

Exploramos el manejo básico de errores en Go en el [concepto de errores][concept-errors].
Como aprendiste allí, de forma predeterminada los errores no llevan consigo trazas de pila.
Eso hace fundamental asegurarte de que el error en sí contenga suficiente información para identificar el problema.

Si quisiéramos agregar información a un error existente con las herramientas que ya conocemos, podríamos escribir algo como esto para crear un nuevo error con el texto combinado del error original y la información adicional:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Por suerte, el paquete `fmt` de la biblioteca estándar contiene una versión abreviada de esto en forma de la función `Errorf`.
Eso te permite, por ejemplo, agregar fácilmente información sobre el contexto en el que ocurrió el error.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

A menudo esta forma de agregar información a un error es suficiente, pero hay casos en los que quieres permitir que quien consume tu error compruebe o recupere el error original subyacente.
Agregar contexto de una forma que permita esto se llama «envolver un error» en Go.

## Envolver errores y comprobar errores centinela

Envolver un error se puede lograr con un cambio muy pequeño en el código que vimos arriba.
Para envolver un error, necesitas usar el verbo de formato `%w` en lugar de `%v`.
Detrás de escena, esto hará que el error resultante implemente un método `Unwrap` que devuelve el error original.
Gracias a eso, `errors.Is` se puede usar para comprobar si un error centinela específico aparece en algún punto de la «cadena de errores».
Lo hace llamando a `Unwrap` repetidamente de forma encubierta hasta que se encuentra el error en cuestión o termina la cadena.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Es una buena práctica usar `%v` de forma predeterminada y usar `%w` solo si quieres permitir explícitamente que quien consume tu error acceda a un error subyacente ([Guía de estilo de Google para Go][google-go-styleguide]).

Si te encuentras en una situación en la que quieres comprobar un error centinela pero explícitamente no quieres desenvolverlo, puedes usar `==` en lugar de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Está bien trabajar con `errors.Is` de forma predeterminada, pero siempre debes tener en cuenta que esto significa que se buscará en toda la cadena de errores.

## Comprobar tipos de error (personalizados)

Existe un equivalente a `errors.Is` que permite comprobar y recuperar un error de un tipo específico de la cadena de errores.
La función para eso es `errors.As` y, al igual que `errors.Is`, buscará el tipo de error dado a lo largo de toda la cadena.
`errors.As` extrae, solo en ese caso, el error que encontró y que coincide con el tipo, para que puedas seguir trabajando con él, por ejemplo, recuperar campos específicos.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Ten cuidado con la sintaxis de los punteros de arriba.
El código solo funcionará y compilará correctamente si `customError` tiene el tipo exacto que implementa la interfaz de error.
En nuestro caso, ese es `*MyCustomError` (un [puntero][concept-pointers] a `MyCustomError`), no `MyCustomError` en sí.

Además, el segundo argumento debe ser un puntero a la variable de error.
Como nuestro error ya es un puntero, lo que le pasamos a `errors.As` es un puntero a un puntero (a MyCustomError).
Solo con esto configurado correctamente, Go puede llenar la variable con el error que encontró.
~~~~

Como antes, `errors.As` no habría encontrado el tipo de error si se hubiera usado `%v` al llamar a `Errorf`.

Si no quieres desenvolver por algún motivo, puedes usar la aserción de tipo en su lugar (equivalente a `==` arriba).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

La aserción de tipo no podrá identificar el tipo de error si el error se hubiera envuelto.

## Permitir que se desenvuelvan los errores de tipos personalizados

A veces, solo envolver un error con algo de texto adicional no es suficiente.
En su lugar, puedes crear un tipo de error personalizado que contenga el error original y los datos estructurados adicionales que quieres agregar.
Si quieres permitir que se desenvuelva tu tipo de error, lo único que debes hacer es agregar manualmente un método `Unwrap() error` para satisfacer la interfaz `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

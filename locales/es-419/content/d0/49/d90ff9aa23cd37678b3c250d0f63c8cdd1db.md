# Acerca de

Por lo general, quienes programan intentan escribir software perfecto, y por lo general fracasan.

Las cosas salen mal, de forma inesperada, y necesitamos poder lidiar con eso.

Algunos diseñadores de lenguajes creen que la prioridad es detectar un error lo antes posible y luego terminar la ejecución con un mensaje informativo que ayude a depurar.

Los lenguajes de ciencia de datos tienden a adoptar un enfoque más matizado.
Algunos errores son tan graves que es necesario terminar de inmediato, pero a menudo es mejor marcar un problema como algo que se resolverá más tarde y luego continuar la ejecución.

Vimos en el concepto [Nada][nothingness] que Julia ofrece varios marcadores de posición para valores problemáticos: [`missing`][nothing], [`NaN`][NaN] e `Inf`.
Si estos son un mejor enfoque que terminar el programa en una situación concreta es algo que queda a criterio de quien programa.

_Un apunte sobre la nomenclatura_ antes de entrar en los detalles: la documentación de Julia trata las palabras «error» y «excepción» como prácticamente intercambiables.
El contenido que sigue puede ser igual de inconsistente.

## Tipos de error estándar

A esta altura del temario, ya debes haber visto muchos mensajes de error de Julia.
Por ejemplo:

```julia-repl
julia> Int(3.14)
ERROR: InexactError: Int64(3.14)
```

Convertir un número de punto flotante en un entero implica una pérdida de precisión, así que obtenemos un `InexactError`.

`InexactError` es un tipo, uno de varios ([actualmente 25][errors]) que vienen incluidos de forma estándar en Julia.
Todos son subtipos de `Exception`:

```julia-repl
julia> supertype(InexactError)
Exception
```

## `throw()`

Puede que algunos de los tipos de error estándar te resulten útiles para generarlos en tu propio código.

Como todos los tipos concretos, los errores tienen constructores.
Aceptan una variedad de argumentos, así que consulta la [documentación][errors] del que quieras usar.

```julia-repl
julia> DomainError(42, "out of range")
DomainError(42, "out of range")
```

Para usar el error, envuelve el constructor en una función [`throw()`][throw]:

```julia-repl
julia> throw(DomainError(42, "out of range"))
ERROR: DomainError with 42:
out of range
```

## `error()`

Para una solución rápida y sin complicaciones, la función [`error()`][error] puede resultar cómoda.
Recibe un string (o los componentes de un string) como argumento:

```julia-repl
julia> happy = false;
julia> happy || error("😞 something went wrong")
ERROR: 😞 something went wrong
```

## Errores personalizados

Crear nuevos tipos de error es, en principio, muy fácil.
Basta con agregar otro subtipo de `Exception`:

```julia-repl
julia> struct MyError <: Exception end

julia> throw(MyError)
ERROR: MyError
```

Sin embargo, el ejemplo anterior no tiene campos y el constructor no acepta argumentos, así que no tenemos control sobre el mensaje de error.
Podemos agregar un campo para el mensaje:

```julia-repl
julia> struct AnotherError <: Exception
           msg::String
       end

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError("Wrong!")
```

Imprimir el constructor sin más todavía no da el resultado correcto.
Compara con el ejemplo anterior, en el que lanzamos un `DomainError`.

Para que un error personalizado se maneje igual que los errores integrados, necesitamos agregar un método [`showerror()`][showerror]:

```julia-repl
julia> Base.showerror(io::IO, e::AnotherError) =
           print(io, "AnotherError: ", e.msg)

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError: Wrong!
```

Esta funcionalidad, bastante mal documentada, en esencia conecta nuestro tipo de error personalizado con el sistema estándar de manejo de errores de Julia.

## Aserciones

La idea básica de una aserción es «esta afirmación debería ser verdadera, así que protesta con fuerza si es falsa».
Esto sirve sobre todo durante la depuración, ya que el código de producción nunca debería fallar una aserción.

Vimos en el concepto [Tipos][types] que podemos agregar aserciones de tipo, por ejemplo para comprobar el tipo de retorno de una función.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

De forma más general, la macro [`@assert`][assert] nos permite comprobar cualquier expresión que evalúe a un Boolean:

```julia-repl
julia> n = 22;
julia> @assert isodd(n) "n must be odd"
ERROR: AssertionError: n must be odd
```

## `try`...`catch`

Algunos errores son necesariamente fatales, pero a menudo esperamos que el programa se recupere sin mayores problemas.

De forma predeterminada, un error termina de inmediato la función actual, y el error (con cualquier mensaje informativo) se pasa a la función que hizo la llamada.

Esto continúa hacia arriba por la pila de llamadas, hasta que el código de nivel superior termina con un mensaje de error.

En cualquier etapa, el error se puede interceptar con un bloque [`try...catch`][try-catch] que intenta manejarlo.

```julia-repl
julia> n = -1;
julia> try
           log_n = log(n)
       catch problem
           if problem isa DomainError # number out of range
               # See next section for more on @warn and @info
               @warn "you may have supplied a negative real number: $n"
               @info "trying with complex argument"
               log_n = log(Complex(n))  # fallback calculation

           elseif problem isa MethodError # no idea what n is
               @error "please supply a valid argument"
 
           else
              rethrow() # the error could be anything else
           end
      end
┌ Warning: you may have supplied a negative real number: -1
└ @ Main REPL[3]:5
[ Info: trying with complex argument
0.0 + 3.141592653589793im  # success
```

En el ejemplo anterior, `log(n)` necesita que `n` sea un valor real positivo o cualquier valor complejo.
El `try ... catch` atrapa los problemas con valores reales negativos y devuelve la respuesta compleja correcta, `iπ`, en notación matemática.

Si proporcionas, por ejemplo, un argumento de tipo string, no hay forma de recuperarse salvo pedirle al usuario que lo corrija.

Como último recurso para todo lo demás, agregamos [`rethrow()`][rethrow] para cualquier cosa que no sea `DomainError` ni `MethodError`.

También hay más cláusulas opcionales:

- [`else`][else], que se ejecuta si la cláusula `try` tiene éxito;
- [`finally`][finally], que se puede usar para limpiar recursos externos, sin importar si el `try` tiene éxito o falla: cerrar archivos, liberar conexiones a bases de datos...

***Nota:*** A veces un `try...catch` es lo que necesitas, pero evita usarlo en exceso.
Si en su lugar se puede usar un bloque `if...else`, su rendimiento será mucho mejor que el de atrapar excepciones.

## Registro

Ten en cuenta que la función `error()`, que ya comentamos, no debe confundirse con la macro [`@error`][error_macro].

La función genera una excepción, que se pasará hacia arriba por la pila de llamadas a menos que se atrape.

La macro `@error`, junto con sus equivalentes [`@debug`][debug_macro], [`@info`][info_macro] y [`@warn`][warn_macro], forma parte del módulo [`Logging`][logging] y está pensada para generar mensajes informativos sin alterar el flujo del programa.

La salida va a la terminal de forma predeterminada (con colores según la gravedad), aunque en una aplicación real hay muchas otras posibilidades.

```julia-repl
julia> @warn "Something looks not quite right"
┌ Warning: Something looks not quite right
└ @ Main REPL[55]:1

julia> @error "Panic!"
┌ Error: Panic!
└ @ Main REPL[56]:1
```

Consulta también el ejemplo anterior, en la sección de `try...catch`.

# Introducción

A menudo es útil definir tipos personalizados en nuestros programas.

Es posible crear tipos primitivos nuevos, pero rara vez se hace.
Los tipos primitivos incorporados no son una elección arbitraria: coinciden estrechamente con los tipos estándar del compilador LLVM que Julia usa para la compilación JIT.

Mucho más útil es la capacidad de definir tipos compuestos, con campos con nombre.

Otros lenguajes tienen algo similar y los llaman `structs` o `records`.
La documentación de Julia se refiere a ellos como `composite types`, aunque (con una pequeña discordancia) la sintaxis del lenguaje los define con la palabra clave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale la pena notar algunos puntos en el ejemplo anterior:

- No se especifica ningún tipo para `id`, así que el compilador lo interpreta como `id::Any`.
  - En la práctica, lo mejor es ayudar al compilador especificando el tipo de un campo con un tipo concreto
- El nombre del tipo se usa como constructor, como en `Person(id, name, age)`, para obtener una instancia de tipo `Person`.
- Se puede acceder a los campos individuales con la notación de punto, igual que con las tuplas con nombres.

Los elementos de tipo `Person` son inmutables, así que no se permiten actualizaciones.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Si se necesita mutabilidad, agrega `mutable` a la definición.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

El constructor, por defecto, requiere que los campos aparezcan en el mismo orden que en la definición, lo cual se vuelve incómodo para tipos más complicados.

Usar la macro `@kwdef` habilita dos capacidades nuevas:

- El constructor usa palabras clave, no la posición.
- Los campos pueden tener valores por defecto y, opcionalmente, se pueden omitir en el constructor.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Jerarquías de tipos compuestos

Hasta ahora, solo hemos creado tipos compuestos concretos.
Si lo verificas, todos son subtipos de `Any`.

Cuando creas varios tipos relacionados, probablemente tenga más sentido definir una jerarquía para ellos.
Esto es muy fácil de hacer.

Primero, crea un tipo abstracto:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Luego, incluye un operador `<:` en la definición de un tipo, para mostrar la relación.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Repite según sea necesario, recordando que no se permite definir subtipos de tipos concretos.

Para una jerarquía más compleja, crea subtipos abstractos según sea necesario.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

El valor de una jerarquía así se aclarará más cuando lleguemos al concepto `Multiple Dispatch` y veamos cómo las funciones manejan los tipos de los argumentos.

# Introducción

Cualquier dato en el lenguaje ensamblador es una secuencia de bytes.
Esto significa que cualquier dato se puede ver como un **array** de esos bytes subyacentes.

## Acceder a los elementos de un array

Para acceder a cualquier valor en memoria, es necesario calcular su **dirección efectiva**.
Una dirección efectiva es una expresión que puede constar de:

- una _dirección base_, por ejemplo, la que indica la etiqueta de una variable.
- un _registro de índice_, que puede estar escalado por `1`, `2`, `4` u `8`.
- un _desplazamiento_ de 32 bits con signo, que es un número que se suma a la dirección base (o se resta de ella).

Ten en cuenta que esta dirección está _indexada desde cero_, así que una dirección base, sin ningún desplazamiento, apunta al primer byte de una variable.
Por eso, cuando se desreferencia la memoria usando solo una etiqueta sin ningún desplazamiento, como hicimos en conceptos anteriores, se obtiene un valor que empieza en su primer byte:

```x86asm
section .data
    example dq 10 ; example is a 8-byte variable
                  ; so it can be viewed as an array of those 8 bytes
                  ; which can be accessed from index 0 to index 7

section .text
fn:
    mov al, byte [example] ; this accesses the first byte
    mov r8b, byte [example + 2] ; this accesses the third byte
    mov edx, dword [example + 1] ; this accesses 4 bytes starting at the second
```

~~~~exercism/note
x86-64 es [little endian][endianness].
Esto significa que el byte menos significativo de un valor de varios bytes se almacena en la dirección de memoria más baja.

En consecuencia, al acceder a los bytes individuales de un valor de varios bytes, es necesario sumar un desplazamiento positivo a la dirección base para llegar a los bytes más significativos.

[endianness]: https://en.wikipedia.org/wiki/Endianness
~~~~

Una variable inicializada y declarada con una lista de valores es un array de esos valores, y cada elemento tiene el tamaño especificado.
Sin embargo, los desplazamientos siempre son en **_bytes_**, incluso cuando cada elemento del array tiene un tamaño mayor:

```x86asm
section .data
    arr dq 4, 8, 15, 23, 42 ; this defines an array of 5 qwords (8-byte elements)
                            ; the first qword has value 4 and can be accessed at [arr] (offset 0)
                            ; any subsequent qword can be accessed at offsets increasing by the size in bytes of each element (8)

section .text
fn:
    mov rdx, 2
    lea rcx, [rel arr]
    mov rax, qword [rcx + 8*rdx + 8]  ; rdx is an index register scaled by 8
                                      ; 8 is a signed 32-bit displacement
                                      ; rax now holds 8-bytes stored in 'arr' starting at offset:
                                      ; 8*rdx(2) + 8 = 16 + 8 = 24
                                      ; this is the fourth element of the array, i.e., the element 23
```

Fíjate que, como las direcciones son en bytes, es posible acceder directamente a un byte individual de cualquier elemento de un array:

```x86asm
section .data
    arr dq 4, 8, 15, 16   ; this defines an array of 4 qwords (8-byte elements)

section .text
fn:
    mov r8, 3
    lea r9, [rel arr]
    mov r10b, byte [r9 + 2*r8 + 1] ; this accesses the byte in 'arr' at offset: 2*r8(3) + 1 = 7
                                   ; this byte is part of the first qword and has value 0 (the fist byte is the least significant one)
```

Por la misma razón, es posible acceder a más de lo que ocupa un elemento en una sola instrucción:

```x86asm
section .data
    arr db 1, 2, 3, 4 ; this defines an array of 4 bytes

section .text
fn:
    mov r11d, dword [rel arr] ; this accesses all bytes in arr as a 32-bit value with bytes
                              ; the least significant byte is 1, the next is 2 and so on
                              ; the resulting number is 0x04030201 or 67305985 in decimal
```

~~~~exercism/caution
El lenguaje ensamblador no realiza ninguna comprobación de límites en los accesos a arrays.
Un índice que se pasa del final de un array lee o escribe memoria fuera de él.
Esto puede dar lugar a resultados incorrectos sin que te enteres, a la corrupción de otros datos y, si la memoria a la que se accede no está mapeada, a un error en tiempo de ejecución.
Es responsabilidad de quien programa mantener cada dirección efectiva dentro del array.
~~~~

## Calcular el tamaño de un array inicializado

NASM (The Netwide Assembler, el ensamblador que usa este track) tiene un símbolo especial (`$`) que indica la ubicación actual en memoria.
Este símbolo ofrece una forma cómoda de calcular el tamaño total en memoria que ocupa un array:

```x86asm
section .data
    example dd 4, 5, 6
    example_length dq $ - example  ; this is a qword variable with the size of the array, in bytes
```

Cuando se usa justo después de `example`, `$` tiene la dirección en memoria del final del array.
Esto significa que `$ - example` es la diferencia entre esa dirección y la que señala la etiqueta `example`.
Ese es exactamente el tamaño total, en bytes, que ocupa el array al que apunta `example`.

Así que, al definir `example_length` con este valor, hemos creado una variable de 8 bytes que guarda el tamaño, o longitud, del array, en bytes.

## La sección .bss

Los datos sin inicializar se declaran en la **section .bss**.
En la mayoría de las plataformas, el sistema operativo rellena estos datos con ceros al inicio del programa.

En NASM, una variable sin inicializar tiene un nombre, una directiva que indica el tamaño de los datos y el número de elementos que se van a reservar.
Cada uno de estos se separa del otro con un espacio.

Las principales directivas y sus tamaños de datos correspondientes son:

| directiva | tamaño  |
| :-------: | :------ |
|   resb    | 1 byte  |
|   resw    | 2 bytes |
|   resd    | 4 bytes |
|   resq    | 8 bytes |

Por ejemplo, esto reserva espacio sin inicializar para `3` bytes en una variable llamada `example`:

```x86asm
section .bss
    example resb 3
```

Y esto reserva espacio sin inicializar para `10` veces `8` bytes (es decir, `80` bytes) en una variable llamada `arr`:

```x86asm
section .bss
    arr resq 10
```

Las variables en `section .bss` son mutables, es decir, se pueden leer y escribir.

Se puede acceder a los datos sin inicializar de la misma manera que a los datos inicializados, usando su dirección efectiva.
Del mismo modo, también tienen duración de almacenamiento estático y son accesibles desde cualquier función del mismo archivo fuente (y, si se declaran `global`, también desde otros archivos fuente).

## Acceder a las direcciones de un array con la instrucción Lea

Como vimos en un concepto anterior, la instrucción `lea` calcula una dirección de memoria efectiva.
Se puede usar para calcular la dirección de cualquier elemento de un array, siguiendo la misma semántica.

Fíjate que, con el direccionamiento relativo, muchas veces es necesario cargar la dirección de la variable en un registro antes de formar una dirección más compleja:

```x86asm
lea rax, [rel arr]
lea rdx, [rax + 8*r10 - 20] ; accessing 'arr' directly instead of loading it into rax first may yield an error
```

~~~~exercism/note
Una de las ventajas de `lea` es que usa aritmética de cálculo de direcciones para calcular un valor sin acceder realmente a la memoria de esa dirección.
Esto lo hace útil para hacer cálculos aritméticos incluso cuando ninguno de los registros contiene una dirección de memoria:

```x86asm
mov rcx, 3
mov rdx, 5
lea rax, [rcx + 8*rdx + 10] ; rax = rcx(3) + 8*rdx(5) + 10 = 3 + 40 + 10 = 53
```
~~~~

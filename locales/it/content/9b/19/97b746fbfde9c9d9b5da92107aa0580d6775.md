# Informazioni

La memoria di un programma viene solitamente organizzata dal sistema operativo (OS) secondo una struttura generale:

| indirizzo | regione di memoria          |
| :-----: | :--------------------- |
|  alto   | stack                  |
|         | ...                    |
|         | heap                   |
|         | segmento di lettura e scrittura |
|         | segmento di codice/sola lettura |
|   basso   | riservata               |

La memoria a segmenti è organizzata in sezioni, con permessi diversi.

Le funzioni che abbiamo definito finora erano tutte nella **sezione .text**.
Questa sezione contiene dati eseguibili in sola lettura.
Altre sezioni vengono usate per dichiarare variabili di dati, che possono essere di sola lettura o di lettura e scrittura, ma non sono eseguibili.

## La sezione .data

I dati inizializzati si dichiarano nella **[sezione .data][data]**.

In NASM (The Netwide Assembler, l'assembler usato in questo percorso), una variabile inizializzata ha un nome, una direttiva che ne indica la dimensione dei dati e una lista di valori separati da virgole.
Ciascuno di questi elementi è separato dall'altro da uno spazio, e l'etichetta può essere opzionalmente seguita da due punti (`:`).

Le direttive principali e le relative dimensioni dei dati sono:

| direttiva | dimensione    |
| :-------: | :------ |
|    db     | 1 byte  |
|    dw     | 2 byte |
|    dd     | 4 byte |
|    dq     | 8 byte |

Ad esempio, questo dichiara una variabile di tipo byte chiamata `space` con il valore `10`:

```x86asm
section .data
    space db 10
```

Le variabili dichiarate in `section .data` sono mutabili, cioè sono di lettura e scrittura.
Hanno anche una durata di memorizzazione _statica_, il che significa che esistono per tutta la durata di esecuzione del programma.

## La sezione .rodata

La **sezione .rodata** è simile a `section .data`.
Entrambe le sezioni contengono dati inizializzati, che si dichiarano allo stesso modo e hanno la stessa durata di memorizzazione.

La differenza principale tra loro è che i dati in `section .rodata` sono immutabili, cioè di sola lettura.

~~~~exercism/note
Le costanti definite con `equ` sono diverse da quelle definite in `section .rodata`.

Una costante definita con `equ` non occupa spazio in memoria e viene sostituita direttamente con il suo valore dall'assembler.
È in effetti un segnaposto per quel valore.

Al contrario, le costanti definite in `section .rodata` sono davvero memorizzate in memoria e hanno un indirizzo.
~~~~

## Accedere ai dati

### Etichette e indirezione

I dati dichiarati devono avere un nome associato.
Questo nome si chiama **etichetta**.

Un'etichetta è un simbolo che codifica l'indirizzo specifico dei dati in memoria.
**Gli indirizzi in x86-64 sono valori a 64 bit**.
Un valore che contiene un tale indirizzo, che sia tenuto in un registro o memorizzato in memoria, è quello che i linguaggi di livello superiore chiamano **[puntatore][pointer]**.

In NASM, provare ad accedere ai dati direttamente con la loro etichetta non restituisce la memoria allocata, ma il suo indirizzo:

```x86asm
section .data
    example dq 27 ; this declares a 8-byte variable initialized with 27

section .text
fn:
    mov rax, example ; this stores the address of the declared variable in rax, not its contents
    ...
```

Per accedere al contenuto di un indirizzo di memoria, è necessario _dereferenziarlo_.
Questa operazione si chiama **indirezione**.

In NASM, si fa con `[]`:

```x86asm
section .data
    example dq -27 ; this declares a 8-byte variable initialized with -27

section .text
fn:
    mov rax, [example] ; this dereferences example and access the value stored in memory (-27)
    ...
```

Tuttavia, ci sono situazioni in cui può esserci un'ambiguità riguardo alla dimensione della memoria dereferenziata.
In questi casi, bisogna usare un prefisso che specifichi questa dimensione.

Questi sono i prefissi più importanti e le loro dimensioni in un tipico programma x86-64:

| prefisso | dimensione    |
| :----- | :------ |
| byte   | 1 byte  |
| word   | 2 byte |
| dword  | 4 byte |
| qword  | 8 byte |

Lo stesso caricamento si può scrivere indicando la dimensione in modo esplicito:

```x86asm
    mov rax, qword [example] ; same dereference, size stated explicitly
```

È buona norma usare sempre un prefisso quando si dereferenzia la memoria.

### Scrivere in memoria

Anche la scrittura in memoria avviene allo stesso modo, dereferenziando un indirizzo:

```x86asm
section .data
    example1 db 10            ; example1 is a 1-byte memory location initialized with value 10
    example2 dq -456          ; example2 is a 8-byte memory location initialized with value -456
    example3 dd 54            ; example3 is a 4-byte memory location initialized with value 54

section .text
fn:
    mov byte [example1], 20   ; example1 now has value 20
    mov qword [example2], rdx ; example2 now has value equal to the contents in rdx
    mov dword [example3], eax ; example3 now has value equal to the contents in eax
```

Nota che puoi usare operandi in memoria nella maggior parte delle istruzioni senza caricare prima il contenuto in un registro.
Tuttavia, di solito non è possibile usarli sia nell'operando sorgente che in quello di destinazione, ma solo in uno dei due:

```x86asm
section .data
    example4 dw 4
    example5 dq -8
    example6 dd 15

section .text
fn:
    add word [example4], 5     ; example4 is now a 2-byte memory location with the value 4 + 5 = 9
    imul rax, qword [example5] ; rax = rax * (-8)
    ; this is not possible -> sub dword [example6], dword [example6]
```

### L'istruzione LEA

Anche se un `mov` può servire a memorizzare in un registro l'indirizzo di una variabile, esiste un'istruzione con questo scopo specifico: **[lea][lea]**.

Questa istruzione usa un operando in forma di memoria, ma _non_ legge la memoria.
Calcola invece l'espressione dell'indirizzo effettivo e scrive il risultato nell'operando di destinazione:

```x86asm
lea rax, [example] ; this stores the address of 'example' in rax
```

È più idiomatico usare `lea` per calcolare e memorizzare gli indirizzi di memoria nei registri.

### Indirizzamento relativo

Quando si accede a locazioni di memoria, il comportamento predefinito in NASM è generare **indirizzi assoluti**, cioè indirizzi di memoria fissi.

Per motivi di sicurezza, gli eseguibili sono spesso costruiti come **PIE (eseguibile indipendente dalla posizione)**, in cui le regioni di memoria sono collocate in posizioni casuali.
In un `PIE`, l'indirizzo finale di una variabile non è noto al momento del linking.
Quindi il codice calcola invece gli indirizzi come offset dal valore in un registro speciale chiamato `rip`, che punta alla prossima istruzione da eseguire.

Questo si chiama di solito **indirizzamento relativo a RIP**.

In NASM puoi richiedere l'accesso relativo a RIP con l'**[operatore rel][rel]**:

```x86asm
mov rax, qword [rel variable]
```

L'indirizzamento relativo può anche essere reso predefinito per un file sorgente con `default rel` in cima.

Tutti gli esercizi di questo percorso sono compilati e linkati come `PIE`, quindi `rel` dovrebbe essere usato per generare indirizzi relativi.

La disposizione casuale menzionata sopra è una mitigazione nota come address space layout randomization.
Rendendo imprevedibile la base di ogni regione di memoria, nega a un attaccante gli indirizzi fissi su cui si basano molte tecniche di exploit, e `PIE` è ciò che permette al loader di collocare quelle regioni in qualsiasi posizione.

Per questo motivo, in questo percorso l'indirizzamento assoluto non è solo sconsigliato, ma inutilizzabile.
Un riferimento assoluto come `[abs variable]` chiede all'assembler di incorporare un indirizzo fisso a 32 bit nell'istruzione.
Su Linux il linker `PIE` rifiuta la rilocazione che ne deriva, e su macOS il formato `macho64` non supporta affatto gli indirizzi assoluti a 32 bit, quindi il file non riesce a essere assemblato.

L'indirizzamento relativo a RIP evita entrambi i problemi, dato che l'istruzione codifica solo un offset da `rip` e mai un indirizzo fisso.
Il modo idiomatico per inserire un indirizzo in un registro con `PIE` è quindi `lea` con un operando `rel`:

```x86asm
default rel

section .data
    variable dq 7

section .text
fn:
    lea rax, [rel variable]       ; materialize the address (PIE-safe)
    mov rcx, qword [rel variable] ; load the value through a RIP-relative access
    ...
```

### Visibilità

Le etichette (funzioni e dati) definite in una qualsiasi sezione (ad esempio `.text`, `.data`, `.rodata`) sono visibili all'interno dello stesso file sorgente.
Se dichiarate `global`, sono visibili anche agli altri file sorgente.

Viceversa, le etichette definite in altri file sorgente sono visibili al file sorgente corrente se dichiarate `extern`.
In questo caso, nell'assembly non c'è alcuna indicazione della dimensione dei dati: questa va conosciuta in anticipo.

```x86asm
default rel

section .data

global number1 ; 'number1' is a variable visible to other source files
number1 db 200

extern number2 ; 'number2' is a variable visible to the current source file, but defined in another

section .text

extern sum ; sum is a function visible to the current source file, but defined in another

fn:
    mov dil, byte [number1]
    mov sil, byte [number2]
    call sum
    ...
```

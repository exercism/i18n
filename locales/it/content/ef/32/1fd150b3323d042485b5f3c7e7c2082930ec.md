# Introduzione

I thread di Factor sono *coroutine cooperative*: condividono un solo thread del sistema operativo, si passano il controllo a vicenda in corrispondenza dell'I/O e dei punti di yield espliciti, e non vengono mai eseguiti davvero in simultanea. Tutto ciò che fai *tra* uno yield e l'altro avviene come un unico passo ininterrotto. Ma se un'operazione composta (lettura-modifica-scrittura) cede il controllo a metà, un altro thread può inserirsi e cambiare il mondo prima che tu abbia finito: è una race condition.

In questo esercizio tratteremo quattro primitive che ricorrono continuamente:

## `parallel-map`: fork/join su una sequenza

```
parallel-map ( seq quot: ( elt -- newelt ) -- newseq )
```

Si trova in [`concurrency.combinators`][combinators]. Genera un thread per ogni elemento, esegue la quotation e raccoglie i risultati in una nuova sequenza nello stesso ordine:

```factor
USING: concurrency.combinators sequences ;

{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }
```

## `spawn`: avviare un thread

```
spawn ( quot name -- thread )
```

Si trova in [`threads`][threads]. La quotation viene eseguita in modo concorrente; `name` è un'etichetta per il debug. L'handle del thread restituito è per lo più irrilevante a questo livello: fai `drop`.

## Promises: consegna di un valore una sola volta

```
<promise>           ( -- promise )
fulfill             ( value promise -- )
?promise            ( promise -- value )
```

Si trova in [`concurrency.promises`][promises]. Una promise è una casella postale a colpo singolo: un thread la soddisfa, gli altri la leggono. `?promise` si blocca finché la promise non è stata soddisfatta, poi restituisce il valore.

```factor
USING: concurrency.promises kernel threads ;

<promise> [
    [ 42 swap fulfill ] curry "answer" spawn drop
] keep ?promise .
! => 42
```

`spawn` + `<promise>` è ciò su cui è costruito `parallel-map`; realizzarli a mano è utile quando ogni attività fa qualcosa di diverso dal «calcolare un elemento».

La tipica struttura fan-out/join su una sequenza è questa: per ogni input crea una nuova promise, genera un thread che svolge il lavoro e `fulfill`a la promise, raccogli tutte le promise in una sequenza, poi chiama `?promise` su ciascuna per attenderne il completamento. Le locals rendono tutto questo leggibile: lega la promise a un nome con `:>` dentro una lambda `[| | ]`, così la quotation generata può catturarla:

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
inputs [| x |
    <promise> :> p
    [ x do-work t p fulfill ] "worker" spawn drop
    p
] map [ ?promise drop ] each
```

## Locks: mutua esclusione

```
<lock>     ( -- lock )
with-lock  ( lock quot -- )
```

Si trova in [`concurrency.locks`][locks]. Solo un thread alla volta può tenere un dato lock. `with-lock` acquisisce, esegue la quotation e rilascia, anche se la quotation solleva un'eccezione.

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
USING: concurrency.locks kernel locals ;

[let <lock> :> guard
    guard [ ! exclusive section ! ] with-lock
]
```

Usa un lock ogni volta che un valore viene *letto o scritto da più di un thread* e le operazioni su di esso non sono naturalmente atomiche. Sia le letture che le scritture hanno bisogno del lock: una lettura che cede il controllo a metà può vedere uno stato incoerente.

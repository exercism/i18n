# Introduzione

## Aggiungere contesto agli errori

Abbiamo esplorato la gestione di base degli errori in Go nel [concetto degli errori][concept-errors].
Come hai imparato lì, per impostazione predefinita gli errori non portano con sé lo stack trace.
Per questo è fondamentale assicurarsi che l'errore stesso contenga abbastanza informazioni per identificare il problema.

Se volessimo aggiungere informazioni a un errore esistente con gli strumenti che già conosciamo, potremmo scrivere qualcosa del genere per creare un nuovo errore con il testo combinato dell'errore originale e delle informazioni aggiuntive:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Per fortuna, il pacchetto `fmt` della libreria standard contiene una versione abbreviata per farlo, sotto forma della funzione `Errorf`.
Questo ti permette, per esempio, di aggiungere facilmente informazioni sul contesto in cui si è verificato l'errore.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Spesso questo modo di aggiungere informazioni a un errore è sufficiente, ma ci sono casi in cui vuoi permettere al consumatore del tuo errore di verificare o recuperare l'errore originale sottostante.
Aggiungere contesto in un modo che lo permetta si chiama, in Go, «wrapping di un errore».

## Fare wrapping degli errori e verificare gli errori sentinella

Il wrapping degli errori si può ottenere con una piccolissima modifica al codice che abbiamo visto sopra.
Per fare il wrapping di un errore, devi usare il verbo di formattazione `%w` invece di `%v`.
Dietro le quinte, questo farà sì che l'errore risultante implementi un metodo `Unwrap` che restituisce l'errore originale.
Per questo, `errors.Is` può essere usato per verificare se un particolare errore sentinella compare da qualche parte lungo la «catena di errori».
Lo fa chiamando di nascosto `Unwrap` ripetutamente, finché l'errore in questione non viene trovato o la catena non finisce.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

È buona pratica usare `%v` per impostazione predefinita e usare `%w` solo se vuoi permettere esplicitamente al consumatore di accedere a un errore sottostante ([Google Go Styleguide][google-go-styleguide]).

Se ti trovi in una situazione in cui vuoi verificare la presenza di un errore sentinella ma non vuoi esplicitamente fare l'unwrap, puoi usare `==` invece di `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Va bene lavorare con `errors.Is` per impostazione predefinita, ma dovresti sempre essere consapevole che questo significa che verrà cercata l'intera catena di errori.

## Verificare tipi di errore (personalizzati)

Esiste un equivalente di `errors.Is` che permette di verificare e recuperare dalla catena di errori un errore di un tipo specifico.
La funzione che lo fa è `errors.As` e, proprio come `errors.Is`, cercherà il tipo di errore indicato lungo tutta la catena.
Solo a quel punto `errors.As` estrae l'errore trovato che corrisponde al tipo, così puoi lavorarci ulteriormente, ad esempio recuperando campi specifici.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Fai attenzione alla sintassi per quanto riguarda i puntatori qui sopra.
Il codice funzionerà e verrà compilato correttamente solo se `customError` ha esattamente il tipo che implementa l'interfaccia error.
Nel nostro caso, è `*MyCustomError` (un [puntatore][concept-pointers] a `MyCustomError`), non `MyCustomError` stesso.

Inoltre, il secondo argomento deve essere un puntatore alla variabile dell'errore.
Dato che il nostro errore è già un puntatore, quello che passiamo a `errors.As` è un puntatore a un puntatore (a MyCustomError).
Solo con questa configurazione corretta Go può riempire la variabile con l'errore che ha trovato.
~~~~

Come prima, `errors.As` non avrebbe trovato il tipo di errore se fosse stato usato `%v` quando si chiama `Errorf`.

Se per qualche motivo non vuoi fare l'unwrap, puoi usare invece l'asserzione di tipo (equivalente a `==` sopra).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

L'asserzione di tipo non sarà in grado di identificare il tipo di errore se l'errore fosse stato sottoposto a wrapping.

## Permettere l'unwrap di errori di tipi personalizzati

A volte limitarsi a fare il wrapping di un errore con del testo aggiuntivo non è sufficiente.
Puoi invece creare un tipo di errore personalizzato che contiene l'errore originale e i dati strutturati aggiuntivi che vuoi aggiungere.
Se vuoi permettere l'unwrap del tuo tipo di errore, l'unica cosa che devi fare è aggiungere manualmente un metodo `Unwrap() error` in modo che l'interfaccia `Unwrap` sia soddisfatta.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

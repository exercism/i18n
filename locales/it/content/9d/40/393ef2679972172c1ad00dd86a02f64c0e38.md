# Linting

Il principale utilizzo di [configlet](/docs/building/configlet) è il linting: controllare se i file di configurazione di una traccia sono strutturati correttamente, sia sintatticamente che semanticamente. Le tracce configurate male potrebbero non sincronizzarsi correttamente, apparire sbagliate sul sito web o offrire un'esperienza utente non ottimale, quindi i controlli di configlet svolgono un ruolo importante nel preservare l'integrità di Exercism.

## Utilizzo

Il comando `lint` può essere usato per fare il linting di una traccia.

```
configlet [global-options] lint [command-options]

Global options:
  -h, --help                   Show this help message and exit
      --version                Show this tool's version information and exit
  -t, --track-dir <dir>        Specify a track directory to use instead of the current directory
  -v, --verbosity <verbosity>  The verbosity of output. Allowed values: q[uiet], n[ormal], d[etailed]
```

## Regole

Queste sono le regole di linting che vengono controllate.

### Regola: i file obbligatori sono presenti

Il linter dovrebbe controllare se tutti i file obbligatori sono presenti. I file non specifici di un esercizio che devono essere presenti sono:

- `config.json`
- `docs/ABOUT.md`
- `docs/INSTALLATION.md`
- `docs/LEARNING.md`
- `docs/RESOURCES.md`
- `docs/SNIPPET.txt`
- `docs/TESTS.md`
- `exercises/shared/.docs/help.md`
- `exercises/shared/.docs/tests.md`

I file specifici degli esercizi concettuali che devono essere presenti sono:

- `exercises/concept/<slug>/.docs/hints.md`
- `exercises/concept/<slug>/.docs/instructions.md`
- `exercises/concept/<slug>/.docs/introduction.md`
- `exercises/concept/<slug>/.meta/config.json`

Ci sarà un elenco simile per gli esercizi pratici, ma non abbiamo ancora definito la specifica per questo.

Ogni concetto elencato nel `config.json` dovrebbe avere i seguenti file:

- `concepts/<slug>/about.md`
- `concepts/<slug>/introduction.md`
- `concepts/<slug>/links.json`

## Glossario

1. **Stringa non vuota**: una stringa che contiene almeno un carattere diverso da uno spazio bianco.
2. **Stringa in kebab-case**: una stringa che contiene solo caratteri nell'intervallo `[a-z0-9]`, facoltativamente separati da trattini (ad es. «two-fer»). Deve corrispondere all'espressione regolare: `^[a-z0-9]+(-[a-z0-9]+)*$`
3. **Stringa in Title Case**: una stringa non vuota che segue le [linee guida del Chicago Manual of Style](https://en.wikipedia.org/wiki/Title_case#Chicago_Manual_of_Style) riportate di seguito:
   - Metti in maiuscolo la prima e l'ultima parola di titoli e sottotitoli.
   - Metti in maiuscolo le parole «principali» (sostantivi, pronomi, verbi, aggettivi, avverbi e alcune congiunzioni).
   - Scrivi in minuscolo le congiunzioni _and_, _but_, _for_, _or_ e _nor_.
   - Scrivi in minuscolo gli articoli _the_, _a_ e _an_.
   - Scrivi in minuscolo le preposizioni, indipendentemente dalla lunghezza, tranne quando sono accentate, usate in funzione avverbiale o aggettivale, oppure usate come congiunzioni.
   - Scrivi in minuscolo le parole _to_ e _as_.
   - Scrivi in minuscolo la seconda parte dei nomi di specie latini.
4. **Stringa in Sentence Case**: una stringa non vuota che segue le [linee guida](https://en.wikipedia.org/wiki/Letter_case#Sentence_case) riportate di seguito:
   - Metti in maiuscolo la prima parola della frase, così come i nomi propri e le altre parole richieste da una regola più specifica.
5. **Pattern `files` valido**: una stringa non vuota¹ che specifica la posizione di un file usato in un esercizio, relativa alla directory dell'esercizio. Un pattern può usare uno dei seguenti segnaposto:

   - `%{kebab_slug}`: lo slug dell'esercizio in `kebab-case` (ad es. `bit-manipulation`)
   - `%{snake_slug}`: lo slug dell'esercizio in `snake_case` (ad es. `bit_manipulation`)
   - `%{camel_slug}`: lo slug dell'esercizio in `camelCase` (ad es. `bitManipulation`)
   - `%{pascal_slug}`: lo slug dell'esercizio in `PascalCase` (ad es. `BitManipulation`)

6. **Stringa UUID versione 4 univoca**: una stringa che soddisfa tutte queste condizioni:

   - Esiste una sola volta nel file `config.json` a livello di traccia di una data traccia di Exercism
   - Non esiste nel file `config.json` a livello di traccia di nessun'altra traccia di Exercism
   - Non esiste in nessun file `canonical-data.json` in https://github.com/exercism/problem-specifications
   - Non esiste in nessun altro punto di Exercism
   - Corrisponde all'espressione regolare:

   ```
   ^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
   ```

   Ad esempio, l'UUID riportato di seguito ha la forma corretta:

   ```
   d334ffe3-657e-4725-a950-290b284b6d9f
   ```

   Puoi eseguire `configlet uuid` per generare un UUID adatto.

7. **`tag` dell'analyzer valido**: una stringa non vuota¹ formattata come `<category>:<thing>`.
   Il valore di `<category>` deve essere uno dei seguenti:

- `paradigm` (ad es. `paradigm:functional`)
- `technique` (ad es. `technique:recursion`)
- `construct` (ad es. `construct:bitwise-and`)
- `uses` (ad es. `uses:DateTime.add_seconds`)

Il valore di `<thing>` deve essere una stringa non vuota¹.

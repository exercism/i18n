# Introduzione

Spesso è utile definire tipi personalizzati nei nostri programmi.

Creare nuovi tipi primitivi è possibile, ma raramente viene fatto.
I tipi primitivi integrati non sono una scelta arbitraria: corrispondono da vicino ai tipi standard del compilatore LLVM che Julia usa per la compilazione JIT.

Molto più utile è la possibilità di definire tipi compositi, con campi con nome.

Altri linguaggi hanno qualcosa di simile, e li chiamano `structs` o `records`.
La documentazione di Julia li chiama `composite types`, anche se (con una lieve discordanza) la sintassi del linguaggio li definisce con la parola chiave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale la pena notare alcuni punti nell'esempio qui sopra:

- Per `id` non è specificato alcun tipo, quindi il compilatore lo interpreta come `id::Any`.
  - In pratica, è meglio aiutare il compilatore specificando il tipo di un campo con un tipo concreto
- Il nome del tipo viene usato come costruttore, come in `Person(id, name, age)`, per ottenere un'istanza di tipo `Person`.
- Si può accedere ai singoli campi con la notazione con il punto, come per le tuple con nome.

Gli elementi di tipo `Person` sono immutabili, quindi gli aggiornamenti non sono consentiti.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Se la mutabilità è necessaria, aggiungi `mutable` alla definizione.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Il costruttore, per impostazione predefinita, richiede che i campi compaiano nello stesso ordine della definizione, il che diventa scomodo per i tipi più complicati.

L'uso della macro `@kwdef` consente due nuove possibilità:

- Il costruttore usa le parole chiave, non la posizione.
- I campi possono avere valori predefiniti e, facoltativamente, possono essere omessi dal costruttore.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Gerarchie di tipi compositi

Finora abbiamo creato solo tipi compositi concreti.
Se controlli, sono tutti sottotipi di `Any`.

Quando si creano più tipi correlati, probabilmente ha più senso definire una gerarchia per essi.
È molto facile da fare.

Per prima cosa, crea un tipo astratto:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Poi, includi un operatore `<:` in una definizione di tipo, per mostrare la relazione.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Ripeti secondo necessità, ricordando che non è consentito creare sottotipi di tipi concreti.

Per una gerarchia più complessa, crea sottotipi astratti secondo necessità.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

Il valore di una tale gerarchia diventerà più chiaro quando arriveremo al concetto di `Multiple Dispatch` e vedremo come le funzioni gestiscono i tipi degli argomenti.

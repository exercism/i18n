# Informazioni

## Aggiungere contesto agli errori

Abbiamo esplorato la gestione di base degli errori in Go nel [concetto degli errori][concept-errors].
Come hai imparato lì, per impostazione predefinita gli errori non si portano dietro gli stack trace.
Per questo è fondamentale assicurarsi che l'errore stesso contenga abbastanza informazioni per identificare il problema.

Se volessimo aggiungere informazioni a un errore esistente con gli strumenti che già conosciamo, potremmo scrivere qualcosa del genere per creare un nuovo errore con il testo combinato dell'errore originale e delle informazioni aggiuntive:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Per fortuna, il pacchetto `fmt` della libreria standard contiene una versione abbreviata di tutto ciò, sotto forma della funzione `Errorf`.
Questo ti permette, per esempio, di aggiungere facilmente informazioni sul contesto in cui si è verificato l'errore.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

A meno che tu non sia sicuro che l'errore contenga già abbastanza informazioni, dovresti cercare di prendere l'abitudine di aggiungere sempre del contesto a un errore prima di restituirlo da una funzione.
Questo significa che il tuo schema standard di gestione degli errori dovrebbe assomigliare a questo:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Come mostrato negli esempi, la convenzione è separare l'errore dal messaggio aggiunto con i due punti.
Proprio come il messaggio dell'errore originale, anche il messaggio di contesto non dovrebbe iniziare con la maiuscola e non dovrebbe avere un punto alla fine.

~~~~exercism/note
Quando si aggiunge contesto a un errore, è allettante iniziare il messaggio con «failed to ...» o qualcosa di simile.
Tuttavia, poiché un errore può accumulare molto contesto aggiuntivo mentre risale la catena di funzioni, questo può rendere più difficile da leggere il messaggio finale che verrà registrato nei log o che l'utente vedrà, riempiendolo di duplicazioni.

Ecco un esempio per illustrarlo:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Tieni quindi a mente questo risultato finale quando scrivi i messaggi di contesto, ed evita di aggiungere testo sul fatto che qualcosa non è andato come previsto.
Di solito questo è chiaro dal contesto (ad esempio il livello di log "ERROR") e dal messaggio di errore originale.
~~~~

Spesso questo modo di aggiungere informazioni a un errore è sufficiente, ma ci sono casi in cui vuoi permettere a chi consuma il tuo errore di verificare o recuperare l'errore originale sottostante.
Aggiungere contesto in un modo che lo permetta si chiama «wrapping di un errore» in Go.

## Fare il wrapping degli errori e verificare gli errori sentinella

Il wrapping degli errori si può ottenere con una modifica davvero minima al codice che abbiamo visto sopra.
Per fare il wrapping di un errore, devi usare il verbo di formattazione `%w` al posto di `%v`.
Dietro le quinte, questo farà in modo che l'errore risultante implementi un metodo `Unwrap` che restituisce l'errore originale.
Per questo motivo, `errors.Is` può essere usato per verificare se un particolare errore sentinella compare da qualche parte lungo la «catena di errori».
Lo fa chiamando segretamente `Unwrap` ripetutamente finché l'errore in questione non viene trovato o la catena non finisce.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Verificare l'errore originale con `errors.Is` non funzionerebbe con il normale verbo di formattazione `%v`.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Di conseguenza, è buona pratica usare `%v` per impostazione predefinita e ricorrere a `%w` solo se vuoi permettere esplicitamente a chi consuma il tuo errore di accedere a un errore sottostante ([Google Go Styleguide][google-go-styleguide]).

Se ti trovi in una situazione in cui vuoi verificare la presenza di un errore sentinella ma non vuoi esplicitamente fare l'unwrap, puoi usare `==` al posto di `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Al contrario, `==` non identificherebbe l'errore se fosse stato sottoposto a wrapping.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Va bene lavorare con `errors.Is` per impostazione predefinita, ma dovresti sempre essere consapevole che questo significa che verrà cercata l'intera catena di errori.

## Verificare tipi di errore (personalizzati)

Esiste un equivalente di `errors.Is` che permette di verificare e recuperare un errore di un tipo specifico dalla catena di errori.
La funzione per farlo è `errors.As` e, proprio come `errors.Is`, cercherà il tipo di errore indicato lungo tutta la catena.
`errors.As` estrae l'errore che ha trovato e che corrisponde al tipo solo a quel punto, così puoi lavorarci ulteriormente, ad esempio per recuperare campi specifici.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Fai attenzione alla sintassi per quanto riguarda i puntatori qui sopra.
Il codice funzionerà e si compilerà correttamente solo se `customError` ha esattamente il tipo che implementa l'interfaccia error.
Nel nostro caso, è `*MyCustomError` (un [puntatore][concept-pointers] a `MyCustomError`), non `MyCustomError` stesso.

Inoltre, il secondo argomento deve essere un puntatore alla variabile dell'errore.
Dato che il nostro errore è già un puntatore, quello che passiamo a `errors.As` è un puntatore a un puntatore (a MyCustomError).
Solo se questo è impostato correttamente, Go può riempire la variabile con l'errore che ha trovato.
~~~~

Come prima, `errors.As` non avrebbe trovato il tipo di errore se fosse stato usato `%v` quando si chiama `Errorf`.

Se per qualche motivo non vuoi fare l'unwrap, al suo posto puoi usare l'asserzione di tipo (equivalente a `==` sopra).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

L'asserzione di tipo non sarà in grado di identificare il tipo di errore se l'errore fosse stato sottoposto a wrapping.

## Permettere l'unwrap di errori di tipi personalizzati

A volte fare il wrapping di un errore con un po' di testo aggiuntivo non è sufficiente.
Puoi invece creare un tipo di errore personalizzato che contiene l'errore originale e i dati strutturati aggiuntivi che vuoi aggiungere.
Se vuoi permettere l'unwrap del tuo tipo di errore, l'unica cosa che devi fare è aggiungere manualmente un metodo `Unwrap() error`, in modo che l'interfaccia `Unwrap` sia soddisfatta.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Combinare più errori

In Go 1.20, una nuova funzione `Join` è stata aggiunta al pacchetto `errors` integrato.
`Join` permette di combinare più errori insieme in un modo che consente comunque l'unwrap, cioè di verificare la presenza di un errore o di un tipo di errore specifico lungo la catena.
Con questo, la catena di errori può in realtà essere davvero un albero di errori.
Maggiori informazioni si trovano nelle [note di rilascio][release-notes] e nella [documentazione][doc-join].

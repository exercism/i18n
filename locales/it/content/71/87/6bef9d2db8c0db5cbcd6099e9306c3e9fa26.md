# Informazioni

## Tipi compositi

Spesso è utile definire tipi personalizzati nei nostri programmi.

Creare nuovi tipi primitivi è possibile, ma si fa raramente.
I [tipi primitivi][primitive] predefiniti non sono una scelta arbitraria: corrispondono da vicino ai tipi standard del compilatore LLVM che Julia usa per la compilazione JIT.

Molto più utile è la possibilità di definire [tipi compositi][composite-types], con campi con nome.

Altri linguaggi hanno qualcosa di simile, e li chiamano `structs` o `records`.
La documentazione di Julia li chiama `composite types`, anche se (con una piccola incongruenza) la sintassi del linguaggio li definisce con la parola chiave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale la pena notare alcuni punti nell'esempio qui sopra:

- Non è specificato alcun tipo per `id`, quindi il compilatore lo interpreta come `id::Any`.
  - **Nota:** nella pratica, è meglio aiutare il compilatore specificando per un campo un tipo concreto.
  - Vedremo in un [concetto futuro][parametric] che usare i parametri è un'altra opzione.
- Il nome del tipo viene usato come costruttore, come in `Person(id, name, age)`, per ottenere un'istanza di tipo `Person`.
- Si può accedere ai singoli campi con la notazione a punto, come per le [tuple con nome][named-tuple].

Gli elementi di tipo `Person` sono immutabili, quindi non si possono aggiornare.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Se serve la mutabilità, aggiungi `mutable` alla definizione.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Per impostazione predefinita, il costruttore richiede che i campi compaiano nello stesso ordine della definizione, il che diventa scomodo per tipi più complicati.

Usare la macro `@kwdef` permette due nuove possibilità:

- Il costruttore usa le parole chiave, non la posizione.
- I campi possono avere valori predefiniti e, facoltativamente, possono essere omessi dal costruttore.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Gerarchie di tipi compositi

Finora abbiamo creato solo tipi compositi concreti.
Se controlli, sono tutti sottotipi di `Any`.

Quando si creano più tipi correlati, probabilmente ha più senso definire una gerarchia.
È molto semplice da fare.

Per prima cosa, crea un tipo astratto:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Poi, includi un operatore `<:` in una definizione di tipo, per mostrare la relazione.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Ripeti quanto necessario, ricordando che il sottotipaggio dei tipi concreti non è consentito.

Per una gerarchia più complessa, crea i sottotipi astratti che servono.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

Il valore di una gerarchia del genere diventerà più chiaro quando arriveremo al concetto `Multiple Dispatch` e vedremo come le funzioni gestiscono i tipi degli argomenti.


## Costruttori interni

All'inizio di questo concetto abbiamo visto che il nome del tipo viene usato come costruttore, per creare elementi di quel tipo:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

Qui, `Person()` è noto come `outer constructor`.
I tipi dei campi vengono controllati per compatibilità con la definizione del tipo, e viene generato un errore se necessario.

Supponiamo di voler porre vincoli sui _valori_ passati, non solo sui _tipi_?

Allora possiamo includere un `inner constructor` all'interno della definizione del tipo, per eseguire i controlli del caso.

Per esempio, abbiamo un tipo astratto `AbstractPoint`, pensato per ricevere coordinate `(x, y)`, ma vogliamo un sottotipo con il vincolo `y > x`.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

La funzione `new()` può essere usata _solo_ nei costruttori interni e restituisce l'elemento desiderato se gli input risultano validi.

Per un input non valido, potremmo fermarci con un messaggio di errore, come nell'esempio.
In alternativa, potresti preferire usare un segnaposto come `nothing` o `missing`.
Vedi il concetto [`Nothingness`][nothingness] per saperne di più.

# Introduzione

Finora il programma del corso non ha detto molto sui tipi, ma in Julia esistono, eccome:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

Non abbiamo mai specificato i tipi, ma Julia li ha assegnati comunque.

1. Julia ha i `types`, che sono centrali nel suo design.
2. Di solito Julia riesce a «indovinare» il tipo, usando la `Type Inference`.

Il compilatore JIT esamina (tutto) il codice, vede come viene usata una variabile e _inferisce_ un tipo predefinito adatto, compatibile con quell'uso.

## Promozione dei tipi

Nei concetti precedenti ci sono stati molti esempi che forzano i tipi numerici a uniformarsi, a cominciare dalla più semplice aritmetica.

```julia-repl
julia> 2 + 1.3
3.3
```

Abbiamo sommato un intero (Int64) e un numero in virgola mobile (Float64) e abbiamo ottenuto un risultato Float64.
Allo stesso modo:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

Nel caso precedente, una tupla ha conservato il tipo di ogni elemento, ma la conversione in un vettore li ha cambiati tutti in un Float64 uniforme.

Il compilatore Julia sa quali conversioni di tipo sono possibili: da intero a virgola mobile non è un problema, da virgola mobile a intero si perde precisione, quindi viene sollevato un `InexactError`.
La promozione dei tipi converte tutti i valori dell'espressione in un tipo comune, abbastanza versatile da essere compatibile con tutti gli input.

## Assegnazione del tipo

Affidarsi all'inferenza dei tipi va bene per risolvere semplici esercizi dei tutorial, ma per programmi più grandi probabilmente avrai bisogno di un controllo più preciso.

Sulla maggior parte dei processori moderni, un intero ha come tipo predefinito `Int64`.
Nel concetto [`Numbers`][numbers] abbiamo visto che un valore può essere convertito in un tipo particolare diverso da quello predefinito.

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

Tuttavia, alla variabile `x` si può comunque assegnare un tipo diverso:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

Questa è la `type instability`, cioè:

- Molto comoda negli script piccoli.
- Dannosa per le prestazioni e l'affidabilità nei programmi più grandi.

Invece, possiamo fissare il tipo di `x` usando l'operatore `::`:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

Ora `y` è, e resterà sempre, di tipo `Int16`.
Così il compilatore sa quanti byte riservare per essa e può ottimizzare il resto del codice contando su un tipo stabile.
Sotto questo aspetto, la variabile è più o meno simile a quelle di un linguaggio a tipizzazione statica come il C.

## Asserzione di tipo

L'assegnazione del tipo, descritta sopra, si usa a sinistra di un'assegnazione di variabile per vincolare il tipo di quella variabile.

Usare l'operatore `::` con un valore, o con qualcosa che restituisce un valore, è in genere un'_asserzione_ che quel valore deve essere di questo tipo, altrimenti dovrebbe essere generato un errore.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Spesso lo si usa con il valore restituito da una funzione, come semplice controllo finale che la funzione si sia comportata come previsto.

## La gerarchia dei tipi

`Int64`, `Int16`, `String`, `Char`: da dove _«vengono»_ questi tipi.

In molti linguaggi orientati agli oggetti (OO), ogni tipo è una classe, la creazione di sottoclassi le organizza in una gerarchia di classi e i metodi di classe definiscono i comportamenti.

Java e Ruby sono esempi evidenti di questo schema, ma anche Python è simile al suo interno.

***Julia non ha classi.***

Il motivo documentato è che le funzionalità OO interferiscono con il compilatore JIT e danneggiano le prestazioni in fase di esecuzione.

Eppure, guarda questo codice:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

Aggiungiamo qualche dettaglio:

- `Int16` è un tipo e possiamo creare variabili di questo tipo.
- `Int16` è un sottotipo di `Signed` e la funzione `supertype()` ce lo mostra.
- Esiste una gerarchia di tipi che risale attraverso `Integer`, `Real` e `Number` fino ad `Any` in cima, e `subtypes()` ci elencherà questo ramo della gerarchia.

Tutti i rami terminano in `Any`, che ha la particolarità di essere il supertipo di se stesso.

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

Quindi Julia non ha una gerarchia di `class`, ma _ha_ una gerarchia di `type`.

Prima o poi cercheremo di capire come funziona, ma prima c'è molto altro da esplorare.

## Verificare i tipi

Possiamo usare `typeof()` per verificare l'uguaglianza nel modo consueto.

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

L'uguaglianza tra tipi deve essere esatta, perché questa forma di confronto non tiene conto della gerarchia dei tipi.

In modo più flessibile, `isa` ci dice se un valore ha lo stesso tipo di un termine di confronto oppure un suo sottotipo.
Si può usare sia in forma di funzione sia in forma infissa.

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

Nota che `isa` si aspetta un `value` a sinistra, non un `type`.

Provare a confrontare due _tipi_ in questo modo darà risultati inattesi.
L'operatore corretto è `<:`, che rivedremo spesso nei concetti futuri.

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## Tipi astratti e tipi concreti

Abbiamo visto che la gerarchia dei tipi forma una struttura ad albero (in senso informatico, con la radice in alto).

Ogni elemento dell'albero è un `node`, e questi si dividono in categorie:

1. I nodi che hanno sottotipi si chiamano `abstract`.
2. I nodi foglia, senza sottotipi, si chiamano `concrete`.

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

Questa distinzione è importante, perché solo i tipi concreti possono essere `instantiated` come variabili.


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

Nota che provare a usare un tipo astratto non dà alcun messaggio di errore (in questo caso), ma il compilatore crea un tipo concreto appropriato: `Int64` invece di `Integer`.
Almeno impedisce che alla variabile venga assegnato un valore non intero:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

L'assegnazione del tipo con un tipo astratto è quindi un _vincolo_ sul tipo della variabile, a qualsiasi sottotipo di (nel caso precedente) `Integer`.
È qualcosa di insolito nel mondo dei linguaggi di programmazione: più debole di un'assegnazione di tipo in C, più forte di un type hint nelle versioni recenti di Python.

Le funzioni `isabstracttype()` e `isconcretetype()` permettono di verificarlo.
Nota che non sono semplicemente la negazione l'una dell'altra: in un concetto successivo vedremo che alcuni tipi non sono né astratti né concreti.


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

# Informazioni

L'assembly scritto a mano è pieno di ripetizioni.
La stessa breve sequenza di istruzioni compare ancora e ancora, con poche variazioni, e ci sono poche astrazioni per ridurre il codice ripetitivo.
Non solo: programmare in assembly richiede di gestire valori senza una semantica ovvia.
Non ci sono parametri con un nome e la maggior parte dei dettagli della macchina sottostante deve essere gestita manualmente da chi programma.

NASM, l'assembler usato dal track, offre alcuni strumenti che possono aiutare chi programma con entrambi i problemi.
Questi strumenti vengono eseguiti _in fase di assemblaggio_, prima che qualsiasi istruzione raggiunga il processore.
Guidano l'assembler su come riscrivere il testo sorgente prima ancora che venga tradotto in codice macchina.

Gli strumenti più importanti tra questi sono le **macro**, che si possono immaginare come una ricetta per l'assembler.
Vengono espanse nel punto in cui sono usate, come se il codice fosse stato scritto lì a mano.

[Le macro][macro] possono accettare una serie di token letterali come parametri, il che le rende riutilizzabili in contesti diversi.
Tuttavia, non sono funzioni: non c'è nessuna `call`, nessuna `ret`, nessun trasferimento di controllo verso un altro punto del codice.

## Macro su una singola riga

La definizione più semplice dà un nome ad un valore o ad una breve espressione con `%define`:

```x86asm
%define WIDTH 8
%define BUFFER_SIZE (WIDTH * 16)
```

Ogni occorrenza successiva di `WIDTH` viene sostituita con `8` prima dell'assemblaggio.
La sostituzione è testuale, quindi il nome viene sostituito ovunque compaia, sia in un operando sia dentro un'altra definizione.

~~~~exercism/note
Per le _costanti_ numeriche, preferisci `equ` a `%define`.

Una macro su una singola riga dichiarata con `%define` viene espansa solo quando viene usata, e può essere riassegnata o rimossa.
Una costante `equ`, invece, viene valutata nel punto in cui è definita e non viene mai modificata.
~~~~

Un `%define` può anche accettare parametri _con un nome_, comportandosi come una piccola funzione inline:

```x86asm
%define double(x) ((x) + (x))

    mov eax, double(WIDTH)   ; assembled as mov eax, ((8) + (8))
```

~~~~exercism/caution
Racchiudi tra parentesi sia l'intero corpo sia ogni parametro.
Con `%define square(x) x*x`, la chiamata `square(1+1)` si espande in `1+1*1+1`, che vale `3`.
Scritto come `%define square(x) ((x)*(x))`, la stessa chiamata si espande in `((1+1)*(1+1))`, che vale `4`.
~~~~

I nomi definiti con `%define` distinguono tra maiuscole e minuscole.
La variante `%idefine` rende il nome insensibile alle maiuscole e minuscole, se lo si desidera.

Le macro su una singola riga sono utili per dare un significato a varie parti del codice.
Se usate con attenzione, migliorano la leggibilità e riducono la probabilità di errori di battitura.
Per esempio, un registro che ha uno scopo dedicato all'interno di una funzione può essere definito in base al suo scopo:

```x86asm
%define COUNTER rcx
    ...
.loop:
    ...
    dec COUNTER
    jnz .loop
    ...
```

## Macro su più righe

Un'intera sequenza di codice, con un numero qualsiasi di righe, si cattura con `%macro` e si chiude con `%endmacro`.
Un numero dopo il nome indica quanti argomenti accetta la macro, che può anche essere zero.
Quando si passano gli argomenti, questi sono separati da una virgola (`,`):

```x86asm
%macro example_macro 0
...
%endmacro
```

Gli argomenti nelle macro su più righe non hanno un nome.
Si indicano come `%1`, `%2` e così via, nell'ordine in cui vengono passati:

```x86asm
; Multiplies two values, returning the result in the first argument
%macro mult_two 2        ; %1 = accumulator, %2 = value
    imul %1, %2
%endmacro

    mult_two eax, ecx    ; multiplies eax and ecx and returns the result into eax
    mult_two r8, r9      ; multiplies r8 and r9 and returns the result into r8
```

Nota che gli argomenti devono essere sintatticamente validi per le operazioni eseguite nel corpo della macro.
Qui `mult_two eax, ecx` e `mult_two r8, r9` si assemblano entrambi, ma `mult_two eax, cl` no, dato che `imul eax, cl` non è definito.

Le macro possono anche accettare un numero arbitrario di argomenti.
Questo si fa con la notazione `n-*`, dove `n` è il numero minimo di argomenti:

```x86asm
%macro multi_args 4-*
    ; this macro may take 4, 5, 6, ... arguments but not just 1 or 2 or 3
%endmacro
```

In una macro su più righe, `%0` indica il _numero_ di argomenti della macro.
Questo è particolarmente utile nelle macro che possono accettare un numero arbitrario di argomenti.

### Etichette all'interno di una macro

Una macro che definisce un'etichetta ordinaria si rompe nel momento in cui viene usata due volte, perché anche l'etichetta verrebbe definita due volte.
Per usare etichette all'interno di una macro che può essere chiamata più di una volta, è necessario anteporre `%%` a tale etichetta.
Questo indica all'assembler di dare a questa etichetta un nome diverso ed univoco ad ogni espansione:

```x86asm
; clobbers rcx
%macro clear_n 2         ; %1 = base address, %2 = count of dwords to clear
    xor ecx, ecx
%%loop:
    mov dword [%1 + rcx*4], 0
    inc ecx
    cmp ecx, %2          ; %2 is compared with ecx: it is an immediate or a 32-bit operand
    jb %%loop
%endmacro

    clear_n rdi, 4       ; gets its own %%loop
    clear_n rsi, 8       ; a different %%loop, no clash
```

## Ripetere in fase di assemblaggio

È possibile ripetere un blocco di codice su una riga usando [`times`][times].
Questo è particolarmente utile quando si dichiarano valori ripetuti in memoria:

```x86asm
section .data
negative_block: times 16 db -1
; this assembles to 16 db -1 in sequence, i.e., an array of 16 bytes, all equal to -1
```

Per ripetere codice su più righe, possiamo invece usare `%rep`:

```x86asm
%rep 2          ; number of repetitions: 2
    add rcx, 32
    mov dword [rsi + rcx], 0
%endrep
```

Nota che il numero di ripetizioni si specifica subito dopo `%rep` e che c'è un `%endrep` per chiudere il blocco ripetuto.

È comune usare un contatore in fase di assemblaggio dentro un blocco `%rep`, proprio come un ciclo in fase di esecuzione usa un contatore.
Mentre una costante intera in fase di assemblaggio si può dichiarare con `equ`, come abbiamo già visto, per le _variabili_ intere in fase di assemblaggio usiamo invece `%assign`.
A differenza di `%define`, `%assign` viene valutato immediatamente in un numero e può essere riassegnato:

```x86asm
    xor eax, eax
%assign i 0
%rep 4
    add eax, i           ; add 0, then 1, then 2, then 3
%assign i i + 1
%endrep
```

Dopo che il preprocessore è stato eseguito, il ciclo non c'è più e restano quattro istruzioni `add`, con i valori immediati `0`, `1`, `2` e `3` incorporati.
Questo è lo srotolamento del ciclo fatto dall'assembler: nessun registro contatore e nessun salto, solo codice lineare.

Un altro uso comune di `%rep` è gestire gli argomenti in una macro che può accettarne un numero qualsiasi.
In quel caso, `%rep` di solito è abbinato a `%rotate`, che ruota gli argomenti di una macro, così che il secondo argomento diventi il primo.
Applicazioni ripetute di `%rotate` portano il terzo argomento, poi il quarto e così via, al primo posto, assicurando che ogni argomento possa essere gestito a turno:

```x86asm
%macro may_args 1-*
    %rep %0 ; repeats for as many times as the number of arguments
        ... ; do something
    %rotate 1
    %endrep
%endmacro
```

## Assembly condizionale

Ci sono vari condizionali disponibili per il [preprocessore][preprocessor].
Selezionano tra diversi percorsi, espandendo il proprio corpo sul posto, ma solo quando la loro condizione è vera.

`%if` ... `%elif` ... `%else` ... `%endif` selezionano un ramo in base a un test numerico:

```x86asm
%if WIDTH > 4
    mov eax, 2
%elif WIDTH > 2
    mov eax, 1
%else
    mov eax, 0
%endif
```

`%ifdef` e `%ifndef` sono simili, ma verificano se un nome è stato definito.
Per esempio, si possono usare per assicurarsi che il contenuto di un file sia incluso una sola volta, anche quando il file è richiamato da più di un sorgente:

```x86asm
%ifndef MY_FILE
%define MY_FILE
... ; whole file here
%endif
```

Potresti aver notato che alla fine di ogni file `.asm` di questo track c'è questo pezzo di codice:

```x86asm
%ifidn __OUTPUT_FORMAT__,elf64
section .note.GNU-stack noalloc noexec nowrite progbits
%endif
```

`%ifidn` confronta due testi per verificare che corrispondano esattamente.
Il built-in `__OUTPUT_FORMAT__` si espande nel formato di output corrente, quindi quel codice verifica se il formato di output è `elf64`, il formato usato dai sistemi Linux.
Se lo è, viene aggiunta una nota al file oggetto che dichiara i permessi che lo stack dovrebbe avere, una misura di sicurezza comune.
Se non lo è, non cambia nulla.

## Strutture

Raggiungere un campo di un record in memoria significa sommare l'offset in byte del campo ad un indirizzo di base.
Scrivere quegli offset come numeri grezzi è soggetto a errori e ne nasconde il significato.
[`struc`][struc] e `endstruc` danno invece un nome a una disposizione, trasformando ogni campo in un offset simbolico calcolato in fase di assemblaggio.

All'interno del blocco, le direttive di prenotazione `resb`, `resw`, `resd` e `resq` riservano uno o più byte, word, doubleword o quadword.
Dare ad ogni campo un `.` iniziale mantiene il suo nome nello scope della struttura:

```x86asm
struc thread
    .color:   resd 1     ; offset 0
    .tension: resq 1     ; offset 4 : 0 + 4 (the size of a dword)
    .name:    resb 16    ; offset 12: 4 + 8 (the size of a qword)
endstruc
```

Ogni nome di campo ora rappresenta il suo offset, quindi `thread.color` è `0`, `thread.tension` è `4` e `thread.name` è `12`.
NASM definisce anche `<struc>_size` come totale, dove `<struc>` è il nome dello `struc`.
Per esempio, qui `thread_size` sarebbe `4 + 8 + 16 = 28`.

Un campo si raggiunge sommando il suo offset ad un registro di base, e `thread_size` è il passo da un record al successivo:

```x86asm
    mov [rdi + thread.color], eax        ; write the color field
    mov ecx, [rdi + thread.tension]      ; read the tension field
    add rdi, thread_size                 ; advance to the next record
```

Uno `struc` descrive solo una forma, non alloca memoria da solo.
Per creare un'istanza inizializzata, puoi usare `istruc ... iend` dopo un'etichetta.
All'interno di un'istanza, `at` colloca un valore in un campo con un nome:

```x86asm
warp_thread:
istruc thread
    at thread.color,   dd 0x00FF00
    at thread.tension, dq 7
    at thread.name,    db "warp", 0
iend
```

Nota che `thread.name` è inizializzato con `"warp", 0`, che occupa solo 5 byte.
Gli altri 11 byte riservati per esso nello `struc` vengono automaticamente riempiti con zeri da `iend`, che estende l'istanza fino a `thread_size` con `0`.

Uno `struc` è solo zucchero sintattico per memoria che possiamo anche dichiarare manualmente.
Per esempio, il codice qui sopra è equivalente al seguente, dove `times 11 db 0` assicura che vengano allocati 16 byte alla fine:

```x86asm
warp_thread:
    dd 0x00FF00
    dq 7
    db "warp", 0
    times 11 db 0
```

## Suddividere in file

Spesso le macro sono tenute in un file a parte e richiamate in ogni sorgente che ne ha bisogno con `%include`:

```x86asm
%include "patterns.mac"
```

Il file indicato viene inserito testualmente in quel punto, prima dell'assemblaggio, esattamente come se il suo contenuto fosse stato digitato lì.
Questo mantiene le definizioni in un unico posto e permette a più file sorgente di condividerle.

Se il file delle macro può essere assemblato da solo, dovrebbe avere l'estensione `.asm`.
Nota che le macro non hanno linkage.
Anche se il file delle macro viene assemblato, le sue macro sono visibili solo ad un altro file che lo include con `%include`.

Altrimenti, un file destinato solo a essere incluso con `%include` può avere qualsiasi estensione.
L'uso di `.asm` o di `.mac` è una convenzione comune.

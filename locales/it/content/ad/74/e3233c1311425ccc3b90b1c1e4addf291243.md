# Introduzione

## Cicli

Un **ciclo** è una sequenza di istruzioni che può essere eseguita più di una volta, finché non si raggiunge una condizione di fine.

In x86-64, un ciclo si crea di solito con un salto a un'etichetta precedente:

```x86asm
example_loop:
    ...
    jmp example_loop
```

Tieni presente che un salto incondizionato a un'etichetta precedente trasferisce sempre l'esecuzione a quell'etichetta.
Questo significa che il ciclo continuerà a ripetersi all'infinito, a meno che non ci sia un altro salto verso l'esterno della sequenza ripetuta.

Per esempio, questo ciclo non termina:

```x86asm
infinite_loop:
    inc rax
    jmp infinite_loop ; always jumps to 'infinite_loop', repeating 'inc rax' forever
```

E questo ciclo può terminare, a seconda che la condizione sia soddisfatta:

```x86asm
maybe_finite_loop:
    cmp rax, 1
    je out_of_loop ; jumps to 'out_of_loop' if rax == 1, breaking the loop

    inc rax
    jmp maybe_finite_loop ; always jumps to 'maybe_finite_loop'
out_of_loop:
    ...
```

### Cicli contatori

Un ciclo contatore termina quasi sempre allo stesso modo: un'istruzione che aggiorna un contatore o confronta due valori, seguita subito da un salto condizionale che decide se fare un altro giro.

```x86asm
sum_array:
    ; rdi is the memory address of an array
    ; rsi is the number of elements in the array

    mov eax, 0           ; running total
.loop:
    add rax, qword [rdi] ; add the current element
    add rdi, 8           ; advance to the next element
    sub rsi, 1           ; one fewer element to process, setting ZF at zero
    jnz .loop            ; repeat while the counter is not yet zero
    ret
```

~~~~exercism/note
Nel codice sopra, `cmp rsi, 0` non è necessario, perché `sub rsi, 1` imposta già il `zero flag (ZF)` quando il risultato è `0`.

Sebbene `cmp` sia il modo principale per verificare le condizioni in assembly, molte istruzioni aggiornano i flag.
Per esempio, molte istruzioni di aritmetica su interi o di operazioni bit a bit aggiornano `ZF` quando il risultato è `0`, e `SF` quando il risultato è negativo (cioè quando il bit più alto è impostato).

Puoi consultare un [riferimento][reference] per vedere quali flag sono modificati da ciascuna istruzione.

[reference]: https://www.felixcloutier.com/x86/
~~~~

Nota che nell'esempio sopra si presume che `rsi` sia maggiore di `0`.
Se fosse `0`, `sub rsi, 1` ridurrebbe `rsi` a `-1`, che è un numero senza segno molto grande.
Servirebbero altre `18,446,744,073,709,551,615` iterazioni prima che il ciclo terminasse.
Inoltre, dato che la lunghezza dell'array è `0`, qualsiasi accesso alla memoria sarebbe fuori dai limiti.

Se non ci sono garanzie sulla lunghezza di un array, ci sono due approcci comuni.

Il primo consiste nello spostare la condizione di fine all'inizio del ciclo, mettendo poi un salto incondizionato alla fine:

```x86asm
sum_array:
    mov eax, 0
.loop:
    cmp rsi, 0
    je .done
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jmp .loop
.done:
    ret
```

Il secondo consiste nel verificare una volta sola se l'array ha lunghezza zero, prima dell'inizio del ciclo:

```x86asm
sum_array:
    mov eax, 0

    cmp rsi, 0
    je .done
.loop:
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jnz .loop
.done:
    ret
```

Questo secondo approccio di solito è più efficiente del primo, perché ci sono meno diramazioni nel corpo del ciclo.
Ne saprai di più in un concetto futuro.

~~~~exercism/advanced
In alcune situazioni, le CPU moderne riescono a unire due istruzioni diverse in un'unica operazione.
Questa ottimizzazione si chiama **macrofusion**.

Molte istruzioni aritmetiche come `sub` e `add`, così come `cmp` e `test`, si fondono di solito con un salto condizionale che le segue subito dopo.
Questo significa che un'istruzione come `cmp rax, rdx` seguita immediatamente da un salto condizionale può di solito essere trattata dalla CPU come un'unica operazione.

La macrofusion dipende dalla CPU e c'è una certa variabilità su quali istruzioni si fondano con quale salto condizionale.

Un riferimento utile è [The microarchitecture of Intel, AMD, and VIA CPUs, by Agner Fog][agner-uarch].
Anche la sezione 3.4.2.2 (Optimizing for Macrofusion) dell'[Intel optimization reference manual][intel-opt] elenca le coppie che possono fondersi per le CPU Intel.

[agner-uarch]: https://www.agner.org/optimize/microarchitecture.pdf
[intel-opt]: https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf
~~~~

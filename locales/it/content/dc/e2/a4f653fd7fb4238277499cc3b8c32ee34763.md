# Appendice alle istruzioni

## Il compito

Implementa due procedure.

- `custom_error_message message` genera un errore, e `message` è il messaggio di errore.
- `handle_error script` esegue lo script dato e restituisce una stringa che descrive cos'è successo:

  | Quando lo script…                  | restituisce          |
  | --------------------------------- | -------------------- |
  | divide per zero                   | `"division by zero"`    |
  | apre un file che non esiste       | `"file does not exist"` |
  | chiama una proc che non esiste    | `"proc does not exist"` |
  | genera qualsiasi altro errore     | `"unknown error"`       |
  | ha successo                       | `"success"`             |

## Generare errori

Tcl ha due comandi per generare un errore.

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` richiede un _codice di errore_ come primo argomento.
Il codice di errore è una lista che dice a un gestore che tipo di errore è successo, così può rispondere senza analizzare il testo del messaggio.
Il suo contenuto lo decidi tu: `{MYAPP BADTHING}` è solo un esempio, e va bene qualsiasi lista non vuota.
Per convenzione, va dal generale allo specifico.
Un gestore intercetta l'errore con un pattern `try ... trap` corrispondente (descritto più avanti), come `trap {MYAPP BADTHING}`, oppure `trap {MYAPP}` per intercettare ogni errore `MYAPP`.
`error` accetta un codice di errore opzionale come terzo argomento: `error message ?info? ?code?`.

## Gestire gli errori con `catch`

[`catch`][catch] esegue uno script e restituisce un _codice di completamento_ intero invece di generare l'errore:

| codice | significato |
| ---- | ---------- |
| 0    | `ok`       |
| 1    | `error`    |
| 2    | `return`   |
| 3    | `break`    |
| 4    | `continue` |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

Il secondo argomento opzionale riceve il risultato (o il messaggio di errore).
Il terzo argomento opzionale riceve un _dizionario delle opzioni_, che contiene `-errorcode` e `-errorinfo` (la traccia dello stack).

Pro:

- È piccolo e flessibile.
- È breve per i casi semplici, come `if {[catch {open $f} fh]} {...}`.

Contro:

- Devi controllare il codice di completamento da solo.
  Un `if {[catch ...] != 0} { handle error }` scritto senza attenzione tratta anche `return`, `break` e `continue` come errori.
- Gli errori che non gestisci vengono soppressi, a meno che non li rigeneri.
- Non c'è un modo integrato per eseguire codice di pulizia indipendentemente dal fatto che lo script sia fallito o meno.

## Gestire gli errori con `try`

[`try`][try] esegue uno script e invia l'esito al primo gestore corrispondente.
Una clausola `finally` opzionale viene sempre eseguita: è un buon posto per rilasciare risorse come i canali dei file.

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

Pro:

- La struttura è chiara: un gestore per ogni tipo di esito.
- `finally` viene sempre eseguita.
- Gli esiti che nessun gestore intercetta vengono passati al chiamante senza modifiche.

Contro:

- È un po' più verboso di `catch` per i casi semplici.

### `try ... on` rispetto a `try ... trap`

Ci sono due tipi di gestore.

`on code {msgVar optionsVar}` corrisponde al _codice di completamento_: `ok`, `error`, `return`, `break` o `continue`.
Ogni errore ha il codice di completamento `error`, quindi `on error` non può distinguere una divisione per zero da un file mancante.
Dovresti guardare il testo del messaggio, il che è fragile: i messaggi sono pensati per gli esseri umani e possono cambiare tra versioni di Tcl.

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` corrisponde al _codice di errore_.
Il gestore corrisponde quando il pattern è un prefisso della lista `-errorcode`.
In questo modo si individua il tipo di errore in modo affidabile.

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

Un pattern vuoto, `trap {}`, corrisponde a qualsiasi errore.
I gestori vengono controllati in ordine, quindi metti per ultimo quello che intercetta tutto.

## Trovare il codice di errore

Dove è documentato `ARITH DIVZERO`?
Quasi solo nel codice sorgente, ma Tcl te lo mostrerà.
Dopo un errore, la variabile globale `errorCode` contiene il codice di errore dell'errore più recente:

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

Dentro un programma, ottienilo dal dizionario delle opzioni:

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

L'ultimo elemento di un codice di errore è spesso un messaggio leggibile, oppure il nome della cosa che ha causato l'errore.
Lascialo fuori dal pattern `trap`: usa `{ARITH DIVZERO}`, non `{ARITH DIVZERO {divide by zero}}`.

### Alcuni codici di errore comuni

Questa tabella non è completa.
Usa la tecnica qui sopra per trovare il codice di qualsiasi altro errore.

| Situazione            | Esempio                  | Codice di errore              |
| --------------------- | ------------------------ | ----------------------------- |
| Divisione per zero    | `expr {1 / 0}`           | `ARITH DIVZERO ...`           |
| Errore di dominio matematico | `expr {sqrt(-1)}`        | `ARITH DOMAIN ...`            |
| File non trovato      | `open nosuchfile r`      | `POSIX ENOENT ...`            |
| Permesso negato       | `open /root/x w`         | `POSIX EACCES ...`            |
| Comando sconosciuto   | `no::such::proc`         | `TCL LOOKUP COMMAND name`     |
| Variabile sconosciuta | `set nosuchvar`          | `TCL LOOKUP VARNAME name`     |
| Numero di argomenti errato | `string length a b`      | `TCL WRONGARGS`               |
| Dizionario non valido | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`        |
| Lista non valida      | `llength "a \{b"`        | `TCL VALUE LIST ...`          |

I codici di errore `POSIX` usano i nomi `errno` del sistema operativo, come `ENOENT`, `EACCES` e `EEXIST`.

## Suggerimento: dove viene eseguito lo script

`handle_error` riceve uno script dal chiamante.
Se lo esegui con `try $script`, viene valutato nello scope di `handle_error`, non in quello del chiamante.
Per valutarlo dove è stato scritto, usa [`uplevel`][uplevel]: `try {uplevel 1 $script} ...`.

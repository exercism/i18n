# Introduzione

`GenServer` (server generico) è un [behaviour][concept-behaviours] che astrae le comuni interazioni client-server tra processi Elixir.

Ricordi il ciclo di ricezione di quando abbiamo imparato a conoscere i [processi][concept-processes]? Il behaviour `GenServer` fornisce astrazioni per implementare quei cicli e per scambiare messaggi con un processo che esegue un ciclo di questo tipo. Rende più semplice mantenere lo stato ed eseguire codice asincrono.

~~~~exercism/note
Attenzione: il nome `GenServer` ha più di un significato. Viene usato anche per descrivere un _modulo_ che _usa_ il behaviour `GenServer`, oltre che un _processo_ avviato da un modulo che _usa_ il behaviour `GenServer`.
~~~~

Il behaviour `GenServer` definisce un callback obbligatorio, `init/1`, e alcuni callback opzionali interessanti: `handle_call/3`, `handle_cast/2` e `handle_info/3`. I _client_ che usano un `GenServer` non devono chiamare direttamente quei callback. Al loro posto, il modulo `GenServer` fornisce funzioni che i client possono usare per comunicare con un processo `GenServer`.

Spesso un singolo modulo definisce sia una _client API_, cioè un insieme di funzioni che altre parti della tua app Elixir possono chiamare per comunicare con questo processo `GenServer`, sia le _implementazioni dei callback del server_, che contengono la logica di questo `GenServer`.

Vediamo prima un semplice esempio di `GenServer`, poi scopriremo cosa significa ciascun callback.

## Esempio

Questo è un esempio di server in grado di rispondere alle ripetitive insistenze di passeggeri fastidiosi durante un lungo viaggio in auto, più precisamente alla domanda: «siamo arrivati?». Tiene traccia di quante volte è stata posta questa domanda, restituendo risposte sempre più seccate.

```elixir
defmodule AnnoyingPassengerAutoresponder do
  use GenServer
  # Client API

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg)
  end

  def are_we_there_yet?(pid) do
    GenServer.call(pid, :are_we_there_yet?)
  end

  # Server callbacks

  @impl GenServer
  def init(_init_arg) do
    # the initial count of questions asked is always 0
    state = 0
    {:ok, state}
  end

  @impl GenServer
  def handle_call(:are_we_there_yet?, _from, state) do
    reply =
      cond do
        state <= 3 -> "No."
        state <= 10 -> "I told you #{state} times already. No."
        true -> "..."
      end

    # increase the count of questions asked
    new_state = state + 1
    # reply to the caller
    {:reply, reply, new_state}
  end
end
```

## Callback

### `init/1`

Un server può essere avviato chiamando `GenServer.start/3` o `GenServer.start_link/3`. Abbiamo imparato la differenza tra queste due funzioni nel [concetto di link][concept-links].

Queste due funzioni:

- Accettano come primo argomento un modulo che implementa il behaviour `GenServer`.
- Accettano come secondo argomento qualsiasi cosa, chiamata `init_arg`. Come suggerisce il nome, questo argomento viene passato al callback `init/1`.
- Accettano un terzo argomento opzionale con opzioni avanzate per l'esecuzione del processo, che non tratteremo adesso.

Avviare un server chiamando `GenServer.start/3` o `GenServer.start_link/3` chiamerà il callback `init/1` in modo bloccante. Il valore restituito da `init/1` determina se il server può essere avviato con successo.

Il callback `init/1` di solito restituisce uno di questi valori:

- `{:ok, state}`. Il server avvierà il suo ciclo di ricezione usando `state` come stato iniziale. `state` può essere di qualsiasi tipo.
- `{:stop, reason}`. `reason` può essere di qualsiasi tipo. Il server non avvierà il suo ciclo di ricezione. Il processo terminerà con il motivo indicato.

Esistono anche possibilità più avanzate che non tratteremo adesso.

Se il ciclo di ricezione del server parte, le funzioni `GenServer.start/3` e `GenServer.start_link/3` restituiscono una tupla `{:ok, pid}`. Altrimenti restituiscono `{:error, reason}`.

### `handle_call/3`

Un messaggio che richiede una risposta può essere inviato a un processo server con `GenServer.call/2`. Questa funzione si aspetta come primo argomento il `pid` di un processo server in esecuzione, e come secondo argomento il messaggio. Il messaggio può essere di qualsiasi tipo.

Il callback `handle_call/3` è responsabile della gestione e della risposta ai messaggi sincroni. Riceve tre argomenti:

1. `message`: il valore passato come secondo argomento a `GenServer.call/2`.
2. `from`: il `pid` del processo che chiama `GenServer.call/2`. Il più delle volte questo argomento può essere ignorato.
3. `state`: lo stato attuale del server. Ricorda che il suo valore iniziale è stato impostato nel callback `init/1`.

Il callback `handle_call/3` di solito restituisce una tupla di 3 elementi, `{:reply, reply, state}`. Questo significa che il secondo elemento della tupla, una `reply` che può essere di qualsiasi tipo, verrà inviata al chiamante. Il terzo elemento della tupla, `state`, è il nuovo stato del server dopo aver gestito questo messaggio.

Esistono anche possibilità più avanzate che non tratteremo adesso.

~~~~exercism/note
Per memorizzare cosa fa questo callback dal suo nome,
pensa a «chiamare» qualcuno al telefono.

Se quella persona è disponibile, riceverai una risposta immediatamente (in modo sincrono).
~~~~

### `handle_cast/2`

Un messaggio che non richiede una risposta può essere inviato a un processo server con `GenServer.cast/2`. I suoi argomenti sono identici a quelli di `GenServer.call/2`.

Il callback `handle_cast/2` è responsabile della gestione di quei messaggi. Riceve due argomenti, `message` e `state`, che sono gli stessi del callback `handle_call/3` (tranne `from`).

Il callback `handle_cast/2` di solito restituisce una tupla di 2 elementi, `{:noreply, state}`.

Esistono anche possibilità più avanzate che non tratteremo adesso.

~~~~exercism/note
Per memorizzare cosa fa questo callback dal suo nome,
ricorda che «to cast» significa anche «to throw».

Se lanci un messaggio in bottiglia in mare,
non ti aspetti di ricevere una risposta immediata,
o magari mai.
~~~~

### Devo usare `call` o `cast`?

Quasi sempre usa `call`, anche se il codice client non ha bisogno della risposta dal server.

Usare `call` attende la risposta, che funge da meccanismo di contropressione (per impedire ai client di inviare troppi messaggi tutti insieme). Ricevere una risposta dal server è anche l'unico modo per essere sicuri che il server abbia ricevuto e gestito il messaggio del client.

### `handle_info/2`

I messaggi possono anche finire nella casella di posta del server per vie diverse dalla chiamata a `GenServer.call/2` o `GenServer.cast/2`, per esempio chiamando la semplice funzione `send/2`.

Per gestire questi messaggi, usa il callback `handle_info/2`. Questo callback funziona esattamente allo stesso modo di `handle_cast/2`.

Il behaviour `GenServer` fornisce un'implementazione catch-all di `handle_info/2` che registra gli errori relativi ai messaggi inattesi. Se sovrascrivi quell'implementazione predefinita, assicurati di includere sempre un'implementazione catch-all. Se te ne dimentichi, il server andrà in crash se riceve un messaggio inatteso.

## Timeout

Il valore restituito da ciascuno dei quattro callback descritti sopra può essere esteso con un ulteriore elemento della tupla, un timeout. Per esempio, invece di restituire `{:ok, state}` da `init/1`, restituisci `{:ok, state, timeout}`.

Il timeout può essere usato per rilevare l'assenza di messaggi nella casella di posta per un periodo specifico. Se il server restituisce un timeout da uno dei suoi callback, e sono trascorsi il numero di millisecondi specificato senza che arrivi alcun messaggio, viene chiamato `handle_info/2` con `:timeout` come primo argomento.

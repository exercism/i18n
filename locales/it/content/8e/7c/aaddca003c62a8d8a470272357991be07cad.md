# Guida di stile per il C

Questa guida descrive lo stile da usare con i file di esempio e di test degli esercizi del percorso C.

Le regole contenute in questa guida si aggiungono a quelle stabilite dal file [.clang-format][], oppure le richiamano esplicitamente.

## Standard C

Il codice dovrebbe essere conforme allo standard C99, noto più formalmente come ISO/IEC 9899:1999.
Non si dovrebbero usare POSIX né altre funzioni di libreria, tipi o altri riferimenti non standard esterni all'implementazione.

## Nomi

In generale, i nomi di tipi, variabili, strutture e file dovrebbero usare lo snake case, con tutte le lettere minuscole e con l'underscore `_` che separa i componenti del nome.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Enum

Di solito i nomi degli enum dovrebbero essere al singolare anziché al plurale.

Le etichette degli enum dovrebbero usare lo snake case con tutte le lettere maiuscole.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Macro

Le macro che definiscono costanti si nominano usando lo snake case con tutte le lettere maiuscole.

```c
#define CONSTANT 0x4000
```

Lo snake case maiuscolo per i nomi delle macro è apprezzato, ma le macro che assomigliano a funzioni possono essere nominate in snake case minuscolo.

### Tipi

I tipi standard a larghezza fissa (in `stdint.h`) sono preferiti ai tipi interi di base.

Il tipo `bool` (di `stdbool.h`) è preferito a `_Bool`.

Allo stesso modo, `size_t` e `ptrdiff_t` (di `stddef.h`) sono preferiti per rappresentare quantità legate alla memoria.

I tipi definiti da un programma con `typedef` dovrebbero avere il suffisso `_t`.
Pur sapendo che POSIX riserva il suffisso `_t`, al momento il percorso non utilizza POSIX.

## Include guard

Le include guard dovrebbero essere usate in tutti gli header.

In generale, un solo insieme di include guard dovrebbe racchiudere l'intero contenuto dell'header.

Le guardie nell'implementazione di esempio (`.meta/example.h`) e nello stub dell'esercizio (`exercise_name.h`) dovrebbero usare nomi di macro che seguono il nome dell'esercizio.
I nomi delle macro di guardia dovrebbero seguire la regola sulle macro vista sopra per quanto riguarda le maiuscole.

Per esempio, per l'esercizio `hello-world`, usa:

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Parametri

I parametri delle funzioni dovrebbero avere un nome sia nella dichiarazione sia nella definizione di tutte le funzioni.
Questo vale sia per i file `.c` sia per i file `.h`.
I nomi usati dovrebbero coincidere in ogni occorrenza.
Vale a dire che, anche se il seguente prototipo di funzione è C valido, lo stile è scorretto perché il parametro non ha un nome: `void foo(int);`.
Il prototipo corretto, a patto che tutte le altre dichiarazioni e la definizione usino anch'esse il nome di parametro `bar`, sarebbe `void foo(int bar);`.

Dove è più semplice o più appropriato, sono preferiti i parametri che richiedono il passaggio degli argomenti per valore anziché per puntatore.
Nota in particolare che questo vale anche per i parametri di tipo `struct`.

Se non ci si aspetta che lo studente modifichi i valori di un parametro di tipo puntatore all'interno della propria implementazione, quel parametro dovrebbe essere qualificato come `const`.

## Formato

Il repository usa lo strumento `clang-format`, come descritto nella [guida per i contributori][contributing guide].

## Struttura del file di test

Il file di test di ogni esercizio segue una struttura particolare.
La struttura serve sia ad aiutare i contributori a individuare le parti del file, sia ad aiutare gli studenti a capire come funzionano i test.

Come la maggior parte dei file sorgente C, un file di test inizia con le direttive include.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

Dopo le direttive include vengono le funzioni `setUp()` e `tearDown()`.
Finora nessun esercizio le usa (i corpi delle funzioni sono vuoti), ma devono restare al loro posto per permettere ai file di test di compilare correttamente su tutte le piattaforme.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

Subito dopo vengono le eventuali funzioni ausiliarie usate dalle funzioni di test.
I nomi di queste funzioni ausiliarie non dovrebbero usare il prefisso `test_`.

Poi ci sono le funzioni di test vere e proprie.
I nomi di queste funzioni usano il prefisso `test_`.
Tranne la prima, ogni funzione di test dovrebbe avere `TEST_IGNORE();` come prima istruzione.
La prima occorrenza di questa dovrebbe essere seguita dal commento di riga `// delete this line to run test`.

Per esempio:

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Alla fine del file c'è la funzione `main()`.
Anche il corpo della funzione main segue una struttura particolare.
Prima una chiamata a `UNITY_BEGIN()` seguita da una riga vuota, poi i test.
L'ultimo test è seguito da un'altra riga vuota prima di restituire il risultato di `UNITY_END()`.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

# Migrare da Travis

Ecco un esempio di `.travis.yml` (preso dalla track `elm`):

```yml
sudo: false
language: node_js
node_js:
  - lts/*
script:
  - bin/fetch-configlet
  - bin/configlet lint
  - bin/build.sh
```

Per convertirlo rapidamente in GitHub Actions, segui questi passaggi:

## Determinare le variabili del template

| variabile                  | valore                               |
| -------------------------- | ------------------------------------ |
| `<track>`                  | `elm`                                |
| `<image-name>`             | `ubuntu-latest`                      |
| `<action to setup tooling>` | `actions/setup-node@v1`             |
| `<install dependencies>`   | `npm ci` (avviene all'interno di `build.sh`) |
| `<code-extensions>`        | `.elm`                               |

> Ho trovato l'action di setup tramite [questa ricerca](https://github.com/actions/?q=setup+node&type=&language=).
> Ho trovato il nome dell'immagine guardando la [distribuzione predefinita di Travis](https://blog.travis-ci.com/2019-04-15-xenial-default-build-environment).

## Determinare i passaggi

- `bin/fetch-configlet`: non serve più quando si usa il workflow [`configlet.yml`][workflow-template-configlet-yml]
- `bin/configlet lint`: non serve più quando si usa il workflow [`configlet.yml`][workflow-template-configlet-yml]
- `bin/build.sh`: un unico script che fa tutto

## Preparare gli «scripts»

Questa track usa la cartella `bin`, quindi all'interno della cartella `bin`, crea i seguenti file:

```bash
# bin/pr
bin/build.sh
```

```bash
# bin/pr-check
echo "No checks yet"
```

```bash
# bin/ci
bin/build.sh
```

```bash
# bin/ci-check
echo "No checks yet"
```

Crearli come binari _separati_ permetterà di ottimizzare in seguito. Per ora non c'è bisogno di inserire nulla inline.

## Compilare i template

Ecco il diff per [`workflows/ci.yml`][workflow-template-ci-yml].

```diff

  #

- # Replace <install dependencies> with a cli command to install the dependencies
- # Replace <code-extensions> with file extensions that should trigger the workflow
- #
- # Find Github Actions to setup tooling here:
- # - https://github.com/actions/?q=setup&type=&language=
- # - https://github.com/actions/starter-workflows/tree/main/ci
- # - https://github.com/marketplace?type=actions&query=setup
- #
  # Requires scripts:
- # - scripts/ci-check
- # - scripts/ci

+ # - bin/ci

- name: <track> / main
+ name: elm / main

  on:
    push:
      branches: [main]
    workflow_dispatch:

  jobs:
    precheck:
-     runs-on: <image-name>
+     runs-on: ubuntu-latest

      steps:
        - uses: actions/checkout@v2
-       - name: Use <setup tooling>
-         uses: <action to setup tooling>
+       - name: Use Node LTS
+         uses: actions/setup-node@v1

-           # here, use the LTS/stable version of the track's tooling

-     runs-on: <image-name>
+     runs-on: ubuntu-latest

      strategy:
        matrix:
-         # here, add all SUPPORTED versions only
-         # version: [10.x, 12.x, 14.x]
+         version: [10.x, 12.x, 14.x]

      steps:
        - uses: actions/checkout@v2
-       - name: Use <setup tooling> ${{ matrix.version }}
-         uses: <action to setup tooling>
+       - name: Use Node ${{ matrix.version }}

-           # below: see how to inject the version

-         run: <install dependencies>
```

[`workflows/pr.yml`][workflow-template-pr-ci-yml] ha le stesse modifiche, con la notevole eccezione del bash-fu che chiama gli script `pr-check` e `pr` passando come argomento ogni file modificato:

```diff
# # .github/workflows/pr.yml

# # ...

-       - name: Run exercism/<track> ci pre-check (stub files, config integrity) for changed exercises
+       - name: Run exercism/elm ci pre-check (stub files, config integrity) for changed exercises
          run: |
            PULL_REQUEST_URL=$(jq -r ".pull_request.url" "$GITHUB_EVENT_PATH")
            curl --url $"${PULL_REQUEST_URL}/files" --header 'authorization: Bearer ${{ secrets.GITHUB_TOKEN }}' | \
-             jq -c '.[] | select(.status == "added" or .status == "modified") | select(.filename | match("\\.(<code-extensions>|md|json)$")) | .filename' | \
+             jq -c '.[] | select(.status == "added" or .status == "modified") | select(.filename | match("\\.(elm|md|json)$")) | .filename' | \
-             xargs -r scripts/pr-check
+             xargs -r bin/pr-check

  # ...
```

## Ora dovrebbe funzionare

Questo basta per convertire il tutto in GitHub Actions, con la possibilità di ottimizzare gli script.

1. Da `build.sh`, rimuovi i passaggi che dovrebbero essere eseguiti una sola volta ed estraili nei file `ci-check.sh` e `pre-check.sh` (suggerimento: puoi creare `lint.sh` e chiamarlo da entrambi gli «scripts»)
2. A `pr.sh` e `pr-check.sh`, aggiungi ottimizzazioni che usano gli argomenti di input per determinare quali file o esercizi controllare.
3. Aggiungi controlli aggiuntivi
4. Aggiungi documentazione su come eseguire i controlli in locale e su cosa cerca di ottenere ciascuno.

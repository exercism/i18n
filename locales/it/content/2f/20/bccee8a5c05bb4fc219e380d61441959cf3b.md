# Linee guida per i contributi

Se vuoi partecipare allo sviluppo del track Pharo, segui le istruzioni qui sotto: ti aiuteranno ad iniziare.

Ci teniamo a migliorare questo track e a mostrare agli sviluppatori un modo diverso di pensare al codice! :tada:

Leggi come [partecipare ad un track di Exercism](https://github.com/exercism/docs/tree/master/contributing-to-language-tracks) e assicurati di leggere anche il [Codice di condotta di Exercism](https://exercism.io/code-of-conduct).

Accogliamo con piacere pull request di ogni tipo. Nessun contributo è troppo piccolo, soprattutto quelli che correggono e migliorano gli esercizi esistenti. Ricorda che gli esercizi di questo track devono rispettare gli [standard validi per tutto Exercism](https://github.com/exercism/docs/tree/master/language-tracks/exercises), ma se non sei sicuro di come fare una modifica, apri una issue su GitHub e ne parleremo.

>__Nota__: l'organizzazione di Exercism ha deciso di [sospendere i contributi della comunità allargata di Exercism](https://exercism.org/blog/freeing-our-maintainers). Il track Pharo è escluso da questa politica, dato che la nostra comunità è piuttosto piccola (in altre parole: qualsiasi contributore del track Pharo può ancora creare issue e inviare PR).

## Prerequisiti

Ci aspettiamo che tu abbia già [una certa familiarità](./docs/RESOURCES.md) con lo sviluppo in Pharo e con l'uso di [Iceberg Git](https://github.com/pharo-vcs/iceberg).

## Preparazione dell'ambiente di sviluppo

Per iniziare, assicurati di avere un ambiente di sviluppo Exercism completo e di avere installato i seguenti artefatti:

### __Immagine Pharo e IDE__

Per creare gli esempi di codice veri e propri ti serve un ambiente di sviluppo Pharo (un'immagine Pharo in esecuzione, cioè l'IDE).

1. Usa [PharoLauncher](https://pharo.org/download) per creare una nuova immagine di sviluppo stabile dalla categoria `Official distributions` (al 05/24 l'immagine stabile è: Pharo 12.0 - 64bit (stable)) ed avviala (puoi usare anche [zerconf](https://get.pharo.org/) se lo conosci).
2. Avvia l'immagine per verificare che tutto funzioni.

> __Nota__: se hai problemi di TIMEOUT, fai riferimento alle [istruzioni di installazione per l'utente](./docs/INSTALLATION.md).

### __Configurazione dei repository git__

1. Se non l'hai già fatto, fai un fork di `https://exercism/pharo-smalltalk` su GitHub.
2. Per clonare il tuo fork, valuta il comando seguente nel Playground dell'immagine Pharo in esecuzione:
```
Metacello new
 baseline: 'Exercism';
 repository: 'github://exercism/pharo-smalltalk:main/releases/latest';
 load: 'dev'
```
In pratica questo clona il repository git del track Pharo e carica il codice sorgente del track nell'immagine Pharo, cioè la sua baseline di sviluppo. La cartella locale con il repository clonato si troverà in (a seconda delle tue preferenze di Iceberg): `<path-to-Pharo-image>/pharo-local/iceberg/<your-id/pharo-smalltalk`.
> __Nota__: i sorgenti dell'immagine Pharo sono sincronizzati e serializzati in file `*.st` che si trovano nella sottocartella `src` della directory appena citata.

2. Un altro modo per fare la stessa cosa è clonare il tuo fork tramite CLI: `git clone https://github.com/<your id>/pharo-smalltalk` come progetto GitHub e specificare `<your id>` come nome del proprietario e `pharo-smalltalk` come nome del progetto.
Poi installa la baseline `dev` di Metacello (non quella predefinita) in Iceberg usando il menu contestuale di Metacello dell'immagine Pharo in esecuzione (ad esempio, fai clic con il tasto destro sul progetto "pharo-smalltalk" che hai appena clonato, seleziona la seconda opzione del menu di Metacello e digita `dev`).

3. Dopo aver caricato il progetto nell'immagine Pharo, non dimenticare di __salvare l'immagine__ (voce di menu Pharo -> Save).

__Repository opzionali__
1. In alternativa puoi fare `git clone https://github.com/exercism/pharo-smalltalk` come repository di staging in cui generare esercizi e asset da caricare (separatamente dalla scrittura del codice in Pharo). Tieni presente che le modifiche generate dallo strumento Configlet in questo repository dovranno essere copiate nel repository del tuo fork locale. Il suggerimento è usare qualcosa come `~/development/exercism/pharo-staging` per evitare confusione (nota: può trovarsi ovunque). Questo repository non è necessario: puoi comunque generare le modifiche di Configlet direttamente nel repository del tuo fork (che è sincronizzato con la tua immagine Pharo), se sei sicuro di quali modifiche includere nel commit.
2. Puoi anche clonare le [problem specifications](https://github.com/exercism/problem-specifications) di Exercism, nel caso in cui tu voglia lavorare su esercizi di pratica partendo da zero. Mettile anche in una sottocartella del workspace di Exercism configurato più sotto (questo repo serve a generare i file readme.md degli esercizi ed è un riferimento per i test suggeriti).

### __Nota sui branch del repository usati__

Il branch `main` è il branch di sviluppo principale, quello in cui viene unito tutto. Se lavori a qualche modifica al codice, crea un branch di funzionalità che parte da main e fai lì i tuoi commit. Una volta completato, apri una PR su GitHub da unire a `main` del repository di base (Exercism/pharo-smalltalk). Questo branch una volta si chiamava `master`: __ora è deprecato__.

### __Configurazione degli strumenti CLI di Exercism__

Questi strumenti servono per interagire con il progetto Exercism:
1. l'[interfaccia a riga di comando di exercism](https://exercism.io/cli-walkthrough), configurandola sulla directory di sviluppo degli esercizi di Exercism chiamata workspace (ad esempio `exercism configure -w ~/development/exercism`). Può essere il percorso del repository del tuo fork locale oppure, facoltativamente, quello del repository di staging.
2. il [configlet](https://github.com/exercism/configlet#usage) di Exercism, linter e generatore per creare i metadati degli esercizi ed eseguire le validazioni. Per installare Configlet segui le istruzioni del paragrafo [Usalo nel tuo track](https://github.com/exercism/configlet#use-in-your-track) (vedi bin/fetch-configlet).

## Lavorare sugli esercizi di Exercism

L'organizzazione di Exercism distingue tra esercizi concettuali (che spiegano la teoria dei linguaggi di programmazione) ed esercizi di pratica. I paragrafi che seguono si concentrano per ora solo sul contributo agli esercizi di pratica.

### __Panoramica__

Passi per completare un esercizio:
1a. Creare un esercizio di pratica da zero (dalle problem specifications).
1b. Lavorare alla soluzione di un esercizio di pratica esistente.
2a. Generare i file sorgente serializzati della soluzione dell'esercizio in una directory e generare i metadati dell'esercizio.
2b. Adeguare la baseline del progetto per includere il nuovo esercizio completato come parte del progetto.
3. Fare commit delle modifiche nel fork del tuo repository e pubblicare le modifiche aprendo una PR.

#### TLDR: guida rapida per generare ed esportare un esercizio di pratica
In breve: ti basta generare ed esportare l'esercizio da Pharo, eseguendo nel Playground:
```Smalltalk
"Obtain exercise from problem specification"
ExercismExerciseGenerator new generateExerciseFrom: 'path-to-problem-specifications/exercises/slug-name' asFileReference.

"Update exercise version within Pharo image  (with updated test cases) to output exercise directory (once you have solution class defined)"
ExercismGenerator new 
	exercisesDirReference: 'path-to-local-repository/exercises/practice' asFileReference;
	generateForExercise: 'slug-name'.
```
  > __Nota__: trovi maggiori dettagli nei passaggi sotto.

![Flusso di lavoro per completare un esercizio di pratica](/docs/images/overview-exercism-pharo-contribution.svg)

### __1. Creare un nuovo esercizio di pratica__
*TLDR: tutti i dettagli e la descrizione delle API relative alla generazione degli esercizi si trovano nel commento di classe della classe `ExercismExerciseGenerator`.*

__Nuovi esercizi dal repository delle problem specifications__
- Se vuoi iniziare un esercizio di pratica completamente nuovo (passo 1a), puoi usare il repository delle problem specifications e generare la classe di test per l'esercizio in questione eseguendo:
`ExercismExerciseGenerator generateFrom: <path-to-problem-specifications/exercises>`: questo genera le classi di test per tutti gli esercizi del repository delle problem specifications nel pacchetto `ExerciseWIP`.

  > __Nota__: puoi ottenere lo stesso risultato con una voce di menu dell'immagine Pharo (menu World -> Exercism -> Generate test cases).
- Più precisamente, puoi generare la classe di test per un esercizio specifico con: `ExercismExerciseGenerator generateExerciseFrom: '<path-to-problem-specifications/exercises/slug-name>' asFileReference`.

Il risultato dell'istruzione precedente sarà una nuova classe di test `<SlugNameTest>` (una sottoclasse di ExercismTest) con i metodi di test generati nel pacchetto `ExerciseWIP`.

__Rigenerare un esercizio esistente dal repository delle problem specifications__
Se vuoi rigenerare i metodi di test di un esercizio esistente (già definito nel pacchetto della soluzione, ad esempio `Exercise@TwoFer`), puoi usare il codice seguente. Tieni presente che gli altri metodi non verranno toccati (ad esempio uuid, version, ecc.)

 `ExercismExerciseGenerator new regenerateExerciseFrom: 'path-to-problem-specifications/exercises/exercise-slug' asFileReference`

__Da zero__
Se hai un'idea interessante, consulta la documentazione su come aggiungere nuovi esercizi.

Nel progetto c'è un esempio di esercizio definito dall'utente, vedi `DieTest`. Se sovrascrivi il metodo customData, il generatore creerà per te i file necessari.

Tieni presente che:
- Ogni esercizio deve essere autonomo. Non fare riferimento a file esterni alla directory dell'esercizio: non verranno inclusi quando l'utente scarica l'esercizio.
- Gli esercizi devono rispettare gli [standard validi per tutto Exercism](https://exercism.org/docs/building/tracks/practice-exercises).
- Gli esercizi dovrebbero usare solo le librerie principali di Pharo.
- Ogni esercizio dovrebbe:
  - essere archiviato in un progetto di primo livello chiamato `Exercism@<ExerciseName>`
  - avere un TestCase chiamato `<ExerciseName>Test` (in CamelCase) e una soluzione di esempio chiamata `<ExerciseName>`
  - il TestCase dovrebbe avere un commento di classe in formato markdown che descrive l'esercizio. Questo testo viene usato anche per generare un file README.md.
- Non fare commit di file o directory di configurazione all'interno dell'esercizio (potrebbe essere rivisto per esercizi futuri; facci sapere se diventa un problema).
- Assicurati di generare un nuovo UUID per l'esercizio usando `UUIDGenerator next` e inserisci quel valore nel metodo `uuid` del test.

> __Nota__: purtroppo l'attuale generatore di UUID di Pharo non è conforme alla RFC 4122, versione 4. Perciò conviene usare l'UUID generato da configlet, valutando: `/bin/configlet uuid`

### __2. Lavorare su un esercizio esistente__

Ci sono molti modi per dare una mano, ma di gran lunga il contributo più facile e più utile è completare una soluzione per uno degli esercizi attualmente «aperti».

  * Assicurati che la tua immagine sia aggiornata all'ultima versione di main di exercism/pharo-smalltalk (e riporta le eventuali modifiche nel tuo fork)

  * Gli esercizi sono tutti TestCase generati automaticamente dal repository delle problem specifications citato sopra. Li troverai come sottoclassi di ExercismTest nel pacchetto ExercismWIP. Tieni presente che un ExercismTest rigenerato potrebbe essere già nel pacchetto dell'esercizio, se la soluzione era già presente. Il pacchetto ExercismWIP si usa per gli esercizi nuovi o in corso di sviluppo che non sono ancora stati pubblicati insieme alla classe della soluzione.

  * Una volta che hai scelto un esercizio su cui vuoi lavorare, crea una issue su GitHub specificando «Convert Exercise <name>». Così gli altri sapranno che ci stai lavorando e sarà anche la base per la tua pull request successiva.

  * Ogni esercizio WIP ha già la descrizione del problema nel suo commento di classe; esegui i suoi test e sviluppa una soluzione con il TDD (nel debugger, se esegui il primo test da solo).

  * Potrebbe essere necessario __adeguare il test se non è Smalltalk idiomatico__ (il nostro generatore è piuttosto elementare; detto questo, alcune correzioni potrebbero essere opportune come PR verso il testo [problem-specification](https://github.com/exercism/problem-specifications) a monte).

  * Aggiorna i metadati dell'esercizio sul lato classe dell'esercizio sovrascrivendo il metodo #exercise e compilando difficoltà, argomenti, ecc. Dovresti anche inserire del testo di suggerimento nella scheda dei commenti del Test (in basso, sostituendo il testo TBD)

  * Aggiorna il pacchetto dell'esempio scelto in `Exercise@<ExerciseName>` (cioè spostalo fuori dal pacchetto WIP), passo 1b.
  * Crea un nuovo branch in Iceberg con il nome dell'esercizio che hai scelto (puoi usare lo strumento Iceberg e inserire il numero della issue indicato sopra).
  * Prima di inviare la tua pull request, esegui tutti i test degli esercizi Pharo e assicurati che __passino tutti__.


### Test

Al livello più basilare, Exercism ruota tutto intorno ai test e al testing con le [test suite](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Gli esercizi Exercism di Pharo sono organizzati in sottopacchetti, ognuno dei quali contiene un TestCase che deve essere compatibile con [SUunit](https://en.wikipedia.org/wiki/SUnit). È la libreria xUnit originale e non servono framework di terze parti aggiuntivi per gli esercizi.

Per testare un esercizio, eseguilo dal test runner integrato facendo clic sull'orb di test. L'orb diventerà verde se i test hanno successo, oppure arancione o rosso rispettivamente in caso di fallimenti o errori. In alternativa puoi eseguire i test manualmente nel playground, valutando:

```smalltalk
<ExerciseName>Test suite run. "single exercise"

AllExercismTests suite run. "all exercises"
```
> __Nota:__ se vuoi definire un tuo caso di test (non generato), puoi metterlo nel protocollo `extra` della classe di test.
Per coerenza, usiamo l'ordine dei parametri di test: `self assert: actual equals: expected` nel metodo di test.


Per testare in un'immagine non di sviluppo, segui i [passaggi di installazione per l'utente](./docs/INSTALLATION.md). Se usi quell'immagine per testare le successive baseline di sviluppo, potresti dover eliminare le seguenti directory di sviluppo per assicurarti di avere il codice più recente:
`./pharo/pharo-local/iceberg, ./pharo/pharo-local/package-cache`


### __3. Pubblicare un esercizio completato__

Ora che hai finito con la soluzione e hai fatto i commit sul tuo branch di funzionalità locale, dovresti completare questi passaggi:  
#### Generare il codice sorgente dell'esercizio
Questo si riferisce al passo 2a: __generare i file di codice sorgente__ per la soluzione e le classi di test.

__Generare i sorgenti di output per tutti gli esercizi__
- `ExercismGenerator generate` genera tutti i file sorgente di tutti gli esercizi. Esegue il comando `generate` di configlet e rigenera anche `config.json`, che elenca tutti gli esercizi validi. (Oppure nel menu World scegli: "Exercism" -> "Regenerate meta data")

#### Generare i sorgenti di output per un esercizio specifico
- Per usare la directory predefinita (`repository-root/exercises/practice`)
```
ExercismGenerator new generateForExercise: 'slug-name'
```

Quando devi esportare in una directory di esercizio specifica:
```
ExercismGenerator new 
	exercisesDirReference: 'path-to-exercises/practice' asFileReference;
	generateForExercise: 'slug-name'
```

> __Note__: 
  - ExercismGenerator aggiorna automaticamente il config.json principale (lo crea se non è presente).
  - sincronizza tutti i documenti, i metadati e i percorsi dei file per gli esercizi specificati usando il comando di configlet. Vedi i dettagli: [Usare sync quando si aggiunge un nuovo esercizio](https://github.com/exercism/configlet#using-sync-when-adding-a-new-exercise-to-a-track)

####  Aggiornare la baseline del progetto Pharo-smalltalk
Passo 2b: aggiorna la baseline del progetto Pharo-smalltalk aggiungendo il nome dell'esercizio all'elenco del metodo `BaselineOfExercism>>exercisePackageNames`. Così il tuo esercizio verrà caricato quando il progetto viene caricato con il comando di Metacello insieme al nuovo esercizio.
  
#### Inviare una pull request
Passo 3: prima di creare la PR, controlla che gli artefatti di Exercism siano corretti eseguendo il comando CLI:
`bin/configlet lint` (l'automazione CI eseguirà comunque il linting quando la PR viene inviata).  
Se tutto va bene, puoi creare la PR:
- fai il push del tuo branch sul tuo fork e poi crea una pull request su `exercism/pharo-Smalltalk` 

> __Dettagli finali__: 

- È importante [abilitare le modifiche dei maintainer](https://help.github.com/en/articles/allowing-changes-to-a-pull-request-branch-created-from-a-fork), così possiamo collaborare con te nel tuo branch.
-  Le pull request dovrebbero concentrarsi su un singolo esercizio, una singola issue o una modifica concettualmente coerente. Per maggiori dettagli, fai riferimento alle [linee guida per le pull request](https://github.com/exercism/docs/tree/main/building/github#guides) di Exercism.
- Segui la tua PR e rispondi a eventuali domande.
- Infine invia eventuali aggiustamenti e un maintainer unirà la tua pull request perché la soluzione finale appaia sul sito.

## Informazioni aggiuntive per i maintainer

### Stile di codice

Il codice in questo repository dovrebbe seguire, dove possibile, le convenzioni di [Pharo with style](https://github.com/SquareBracketAssociates/Booklet-PharoWithStyle). Puoi fare riferimento anche al più generico [Smalltalk with style](http://sdmeta.gforge.inria.fr/FreeBooks/WithStyle/SmalltalkWithStyle.pdf).

Quando crei esercizi, dovresti usare anche il formattatore di codice integrato (meta-t FO nell'editor), così come le code critique.

### Modifiche incompatibili

Se prevedi di fare modifiche significative o incompatibili, apri una issue così possiamo discuterne prima di unirle. Se la discussione riguarda più del solo track Pharo, apri una issue anche in [exercism/discussions](https://github.com/exercism/discussions/issues).

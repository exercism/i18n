# Contribuire alla traccia Rust di Exercism

Al momento issue e pull request vengono chiuse automaticamente.
Per proporre modifiche, scrivi un post sul [forum di Exercism].
I contributi sono molto graditi, purché vengano coordinati sul forum.

[forum di Exercism]: https://forum.exercism.org/

## Politiche generali

- [Codice di condotta](https://exercism.org/code-of-conduct)
- [Linee guida di Exercism per le pull request](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## Strumenti

Alcuni strumenti sono presenti come script bash in `bin/`.
Molti altri si trovano in `rust-tooling/`, che va preferito per qualsiasi cosa non banale.

C'è anche una configurazione di [`mise`](https://mise.jdx.dev/)
con un paio di comandi utili per interagire con il repo.
Se vuoi, puoi estenderla.

Se vuoi eseguire i test della CI in locale, `mise run test` ti farà arrivare già molto avanti.

## Escludere test e aggiungerne di personalizzati

Mentre crei o aggiorni un esercizio, potresti decidere di escludere alcuni test dalla generazione.
Puoi farlo impostando `include = false` in `.meta/tests.toml`.
Aggiungi un commento che spieghi il motivo dell'esclusione.

Se vuoi aggiungere altri test specifici della traccia, puoi farlo in un file `.meta/additional-tests.json`.
Fallo solo se hai una buona ragione per non portare questi test a monte.
Un commento nel test aggiuntivo dovrebbe rispondere a queste domande:
- Perché il test non viene portato a monte in `problem-specifications`, cioè perché non è generalmente utile agli altri linguaggi?
- Perché il test è comunque utile per la traccia Rust?

## Creare un nuovo esercizio

Fai prima una lettura della [documentazione di Exercism sugli esercizi di pratica].

[documentazione di Exercism sugli esercizi di pratica]: https://exercism.org/docs/building/tracks/practice-exercises

Esegui `mise run add-exercise` e ti verranno chieste le informazioni minime
necessarie a generare lo stub dell'esercizio.
Dopodiché, entra nell'esercizio generato e sostituisci tutti i segnaposto che trovi.
In particolare:

- scrivere lo stub dell'esercizio in `src/lib.rs`
- aggiungere una soluzione di esempio in `.meta/example.rs`
- modificare `.meta/test_template.tera`

I test vengono generati con il motore di template [Tera].
L'input del template sono i dati canonici di [`problem-specifications`].

Trovi alcuni consigli su come scrivere i template tera [qui](#tera-templates).

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

Molti aspetti di un esercizio implementato correttamente vengono controllati nella CI.
Il mio consiglio è di non passare un sacco di tempo a studiare e scrivere
documentazione sul processo: _fallo e basta_.
Se qualcosa si rompe, sistemalo e aggiungi un test o un'automazione,
così non succederà più.

Se stai creando da zero un esercizio di pratica,
uno che non è presente in `problem-specifications`,
devi scrivere i test a mano.
I test dovrebbero essere ordinati per complessità crescente,
così gli studenti possono riattivarli uno alla volta e risolvere l'esercizio con il TDD.
Per altre riflessioni su come scrivere buoni test, dai un'occhiata alla [documentazione di Exercism](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md).

Salvo circostanze straordinarie,
il file stub dovrebbe compilare con `cargo test --no-run`.
Questo ci permette di verificare che le firme nel file stub
corrispondano a quelle attese dai test.
Per ottenere questo, usa `todo!()` come corpo di ogni funzione.
Se c'è una ragione giustificata per cui questo non è possibile,
aggiungi una chiave `.custom."allowed-to-not-compile"`
nel file `.meta/config.json` dell'esercizio, indicando il motivo.

## Aggiornare un esercizio

Molti esercizi derivano da [`problem-specifications`].
Questo vale per la loro suite di test e per la documentazione rivolta agli studenti.
Prima di proporre qui delle modifiche,
verifica se non sia il caso di farle in `problem-specifications`.

Esegui `mise run update-exercise` per aggiornare un esercizio.
Questo delega gran parte del lavoro a `configlet sync --update`
e rilancia il generatore di test.

Quando aggiorni un esercizio che non ha ancora un template tera,
ne verrà generato uno nuovo.
Probabilmente dovrai ritoccarlo un po'.

Trovi alcuni consigli su come scrivere i template tera [nella prossima sezione](#tera-templates).

## I template tera

La documentazione completa dei template tera è [qui][tera-docs].
Qui di seguito trovi alcuni approcci che hanno funzionato per le nostre esigenze specifiche.

Probabilmente vorrai dare un'occhiata al file `canonical-data.json` dell'esercizio per vedere com'è fatto il tuo input.
Puoi usare `bin/symlink_problem_specifications.sh` per creare un link simbolico a questi dati
nella directory effettiva dell'esercizio. Comodo!

Il nome della proprietà di input è diverso per ogni esercizio.
Il template predefinito sarà più o meno così:

```txt
let input = {{ test.input | json_encode() }};
```

Dovrai aggiungere il campo specifico di input per questo esercizio, ad esempio

```txt
let input = {{ test.input.integers | json_encode() }};
```

Alcuni esercizi possono avere valori restituiti che indicano un errore.
Puoi usare un if-else per generare qualcosa di diverso,
a seconda della struttura dei dati:

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

Alcuni esercizi hanno più funzioni che lo studente deve implementare
e che quindi vanno testate.
In quel caso i dati canonici contengono un campo `property`.
Puoi costruire catene di if-else basate su `test.property` e generare una funzione diversa di conseguenza.

Alcuni esercizi hanno i casi di test organizzati in _gruppi di test_.
Il tuo template dovrà tenerne conto.
In molti casi puoi semplicemente appiattire la struttura. (esempio: [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
A volte però i test hanno la stessa descrizione in gruppi diversi, il che porta a conflitti di nomi se la struttura viene appiattita.
In quel caso puoi usare la descrizione del gruppo per organizzare i test in moduli. (esempio: [`forth`](/exercises/practice/forth/.meta/test_template.tera))

In [`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs) ci sono alcuni filtri tera personalizzati.
Ecco la lista, che speriamo sia aggiornata:
- `to_hex` formatta gli interi in esadecimale
- `make_ident` trasforma una stringa qualsiasi in un identificatore Rust decente.
   È molto utile per generare nomi di funzione a partire dalle descrizioni dei test.
- `fmt_num` formatta i letterali numerici (inserisce `_` ogni tre cifre)

Se vuoi, puoi aggiungerne di tuoi nel crate `rust-tooling`.
Speriamo che ti ricordi di aggiornare anche questa lista. 🙂

Per un esempio piuttosto complicato, dai un'occhiata al template di test di `triangle`.
Organizza i casi di test in moduli e rileva dinamicamente quali test mettere dietro i feature gate.
Quell'esercizio reimplementa anche alcuni casi di test provenienti da monte in `additional-tests.json`, per aggiungere loro le informazioni in più necessarie a generare buoni test.

[tera-docs]: https://keats.github.io/tera/docs/#templates

## Programma didattico

Al momento il programma didattico è disattivato perché è di bassa qualità.
Per avere un po' di contesto sulla decisione, vedi [questo post sul forum](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882).

Creare un programma didattico migliore sarebbe molto vantaggioso,
ma è un lavoro enorme e richiede buona comunicazione e coordinamento.
Assicurati di discutere sul forum qualsiasi piano tu abbia
con persone che hanno esperienza nella creazione di programmi didattici.

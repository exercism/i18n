# Informazioni

Una dichiarazione `MACRO:` è una parola il cui *corpo* viene eseguito in fase di compilazione. Il corpo consuma argomenti letterali dallo stack di compilazione e deve lasciarvi una quotation. Il compilatore poi sostituisce quella quotation al posto della chiamata alla macro, così il programma in esecuzione non vede mai la macro, solo il codice che ha prodotto.

```factor
USING: kernel macros sequences ;

MACRO: twice ( quot -- compound )
    dup append ;
```

Se il chiamante scrive `[ 1 + ] twice`, il compilatore esegue il corpo con `[ 1 + ]` sullo stack, ottiene `[ 1 + 1 + ]` e lo inserisce al suo posto. Non c'è alcun costo a runtime: il ciclo o combinator che la macro ha sostituito è sparito.

## Gli input devono essere letterali

Dato che il corpo viene eseguito in fase di compilazione, ogni input deve essere un *letterale* nel punto di chiamata: una quotation `[ … ]`, un numero, un array, una stringa. Passare un valore non letterale (uno che si conosce solo a runtime) è un errore in fase di compilazione.

```factor
! works: [ 1 + ] is a literal quotation
: inc-twice ( x -- y ) [ 1 + ] twice ;

! refused: f is a literal, but the macro can't run with a non-quotation
! input where the body expects to call `append` on it
```

## Gli input strutturali determinano un output strutturale

Le macro interessanti prendono una *struttura* (un array, una sequenza letterale di coppie) e producono codice la cui forma dipende da quella struttura. `each-literal`, in questo esercizio, prende una sequenza letterale e una quotation, ed emette per ogni elemento una copia della quotation con currying e inlining. Il programma in esecuzione è codice lineare (nessun `each`, nessun dispatch per elemento), e l'iterazione della sequenza è avvenuta interamente in fase di compilazione.

## Perché non c'è un problema di igiene

Le macro di Lisp si scontrano con l'*igiene*: una macro che introduce un nome locale può entrare in collisione con i nomi presenti nel punto di chiamata, e servono `gensym` o un sistema di igiene. Factor non ha questo problema, perché le quotation sono sequenze di *riferimenti a parole già risolti*: ogni parola viene cercata in fase di parsing, non simbolicamente in fase di espansione. Un `dup` dentro una quotation costruita da una macro sarà sempre `kernel:dup`, indipendentemente dai nomi che esistono nel punto di chiamata.

Il prezzo da pagare: le macro di Factor non possono introdurre nuovi binding come può fare `defmacro`. Costruiscono codice a partire da parole che il parser ha già visto. Per gran parte della metaprogrammazione, questo basta.

## Forme correlate (non usate in questo esercizio)

- `MACRO::`: variante in forma locals di `MACRO:`, allo stesso modo in cui `::` è la forma locals di `:`. È utile quando il corpo fa riferimento ai suoi input più di una volta.
- `<< … >>`: blocco di valutazione in fase di parsing. Esegue Factor normale in fase di compilazione senza il vincolo di restituire una quotation. È utile per calcolare un valore che deve esistere in fase di parsing (ad esempio una `CONSTANT:` ricavata da una ricerca nell'ambiente).
- `SYNTAX:`: *parsing words*. Una bestia diversa: operano sul flusso di token del parser, non sui valori, e vengono eseguite in una fase ancora precedente. Servono a definire nuove sintassi letterali (`T{ }`, `H{ }`). Fuori dall'ambito di questo concetto.
- `functor:`: template dichiarativi che generano insiemi di parole correlate a partire da un'unica specifica. Costruiti sopra il meccanismo delle macro; roba da autori di librerie.

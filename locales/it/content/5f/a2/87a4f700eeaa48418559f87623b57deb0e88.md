# Specifiche Markdown

Quella che segue è la struttura che tutti i file Markdown all'interno di Exercism dovrebbero avere.

Alcune regole di questo documento non sono ancora state implementate in tutto Exercism.
Accogliamo con piacere le PR per sistemarle.
Tutte le regole vengono aggiunte ai nostri strumenti di CI e di linting, e vanno rispettate per le nuove modifiche.

## Titoli

- Tutti i file devono iniziare con un titolo di livello 1 (`# Some heading text`).
- I titoli di livello 1 servono esclusivamente alla visualizzazione su GitHub o su piattaforme equivalenti.
- Se il file viene renderizzato da Exercism (ad esempio, visualizzato sul sito web, renderizzato tramite la CLI), questo titolo verrà rimosso e ne verrà inserito uno contestuale.
- Nessun titolo può scendere di più di un livello rispetto al precedente (ad esempio, `##` può essere seguito solo da `###`, non da `####`).
- Oltre all'unico titolo di livello 1 (`#`), si possono usare solo titoli di livello 2 (`##`), livello 3 (`###`) e livello 4 (`####`).

## Link

Usa i [link di riferimento][reference-links], che vengono definiti in fondo al file Markdown, associati a uno slug di riferimento e richiamati nel testo tramite quello slug.

Questo metodo semplifica la manutenzione, dato che i link devono essere aggiornati in un solo punto.

Esempio:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

I link dovrebbero sempre avere un testo di ancoraggio, invece di inserire l'URL stesso nel testo. Ad esempio, il seguente non usa un testo di ancoraggio ed è più difficile da leggere.

```
If you want some more information, please visit https://google.com.
```

Usare un testo di ancoraggio e collegarlo è più facile da capire e da contestualizzare.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

Che viene visualizzato come «Se vuoi qualche informazione in più, [Google][google-link] è una risorsa utile».

## Codice

Ogni volta che ci si riferisce a elementi di codice (ad esempio funzioni o parole chiave), il codice va racchiuso tra backtick:

```
- The `printf()` function writes to the console.
```

Che viene visualizzato come:

- The `printf()` function writes to the console.

Il codice più complesso (ad esempio codice su più righe) va racchiuso tra tre backtick. Dopo i tre backtick di apertura va specificato un [identificatore di linguaggio][language-identifier] per abilitare l'evidenziazione della sintassi:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

Quando possibile, formatta il codice nel modo più adatto all'ambiente in cui viene presentato. Se sono disponibili, fai riferimento alla documentazione del tuo linguaggio.

Ad esempio, Python ha il REPL (read-eval-print loop), che permette a chi programma di digitare codice direttamente nel terminale. Se qualcuno sta eseguendo il debug di un codice, o esegue una funzione in locale per provare/osservare come funziona, è più probabile che usi il REPL, perché è più comodo digitare in modo interattivo. In questa situazione, preferiamo formattare il codice di esempio come se fosse digitato nel REPL, con `>>>` all'inizio:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

In altri casi, ha più senso lasciare il codice formattato come se fosse in un file `.py`. Qui lo studente trae vantaggio dal vedere qualcosa che imita il modo in cui scriverebbe il codice da sé.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

Un modo rapido per distinguere i due casi quando non è chiaro: se è codice che lo studente può eseguire in un terminale, formattalo in quel modo. Se è codice che potrebbe essere eseguito da Exercism (nei test, codice di libreria che scriverà lo studente, ecc.), formattalo come codice eseguibile.

## Blocchi speciali (a volte chiamati admonition)

Supportiamo tipi speciali di blocchi che si possono aggiungere ai documenti per mettere in evidenza osservazioni che non si inseriscono bene nel corpo principale del testo.

<img width="500" alt="Blocco note di Markdown" src="https://user-images.githubusercontent.com/20866761/139531109-0c0f3ea5-b589-44ff-93ab-d901a45edc56.png">

<img width="500" alt="Blocco cautela di Markdown" src="https://user-images.githubusercontent.com/20866761/139531234-9b58b9ab-524b-44fd-bbcb-4e10f2927d27.png">

<img width="500" alt="Blocco avanzato di Markdown" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

Supportiamo tre tipi di blocchi:

- **exercism/note:** blocchi che mettono in evidenza informazioni speciali aggiuntive
- **exercism/caution:** cose che le persone dovrebbero sapere o su cui dovrebbero procedere con cautela
- **exercism/advanced:** informazioni rilevanti solo per chi vuole approfondire qualcosa o che si presume abbia conoscenze più avanzate.

Tutti i blocchi si scrivono usando 4 tilde, nella forma:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(Nota: in circostanze eccezionali puoi anche usare i backtick o altri livelli di tilde)

## Impaginazione

### Una frase per riga

I paragrafi dovrebbero essere disposti usando una frase per riga. La [documentazione di Ascii Doctor][asciidoctor] spiega chiaramente la logica di tutto questo.

Ad esempio, un singolo paragrafo dovrebbe essere disposto così:

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## Elenchi

Usa il carattere trattino (`-`) come marcatore dei punti elenco negli elenchi non ordinati.

## Commenti

- Preferisci i commenti Markdown ai commenti HTML (ad esempio, usa `[comment]: # (Actual comment...)` invece di `<!-- Actual comment -->`

Puoi verificare che il tuo commento Markdown venga rimosso controllando come appare quando viene renderizzato con commonmark su [babelmark3].

## HTML inline

- L'HTML inline è consentito, ma va usato con parsimonia
- Usa sempre le alternative native di Markdown quando esistono (ad esempio, usa `# ...` invece di `<h1>...</h1>`)

## Immagini

Poiché il sito supporta temi chiari e scuri, le immagini inviate dalla community devono essere visualizzate bene in entrambi i temi.
La soluzione è aggiungere un suffisso al nome dell'immagine (prima dell'estensione del file):

1. Fai in modo che il nome dell'immagine termini con `-invertible` (ad esempio `graph-invertible.svg`). L'immagine verrà invertita automaticamente quando viene mostrata nel tema scuro (tramite `filter: invert(100%)`).
1. Fai in modo che il nome dell'immagine termini con `-light` (ad esempio `graph-light.png`) e crea anche una versione compatibile con il tema scuro che termini con `-dark` (cioè `graph-dark.png`). Visualizzeremo automaticamente l'immagine corretta a seconda del tema dell'utente.

Le immagini senza nessuno dei due suffissi verranno usate senza modifiche in entrambi i temi.
Questo significa che, se vuoi creare immagini in scala di grigi, in genere puoi renderle gradevoli sul tema chiaro e poi impostarle come invertibili.
Ma se usi un'immagine con molti colori, potresti preferire creare due varianti.

Il nome completo dell'immagine (incluso `-invertible`) va aggiunto al Markdown nel punto in cui l'immagine viene visualizzata.
Per quelle chiaro/scuro, includi **SOLO** la variante `-light`.
Questa logica viene rispettata in tutta la documentazione Markdown.

## Formattazione automatica

Alcuni repository usano [prettier][prettier] per garantire che tutto il Markdown sia formattato in modo coerente. Questo può portare i seguenti vantaggi:

- Nessuna discussione sulla formattazione.
- Ottima integrazione con editor e IDE, così i file possono essere formattati al salvataggio.
- È facile aggiungere controlli di CI per la formattazione.
- È facile formattare automaticamente i file usando uno script.

Tutto quanto sopra può aiutare molto a ridurre il continuo rifacimento nelle revisioni, che è frustrante sia per chi rivede sia per chi viene rivisto.

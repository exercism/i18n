# Informazioni

Un [ciclo][control] è una sequenza di istruzioni che viene potenzialmente eseguita più di una volta, finché non viene soddisfatta una condizione di terminazione.

In x86-64 un ciclo viene di solito creato con un salto a un'etichetta precedente:

```x86asm
example_loop:
    ...
    jmp example_loop
```

Nota che un salto incondizionato a un'etichetta precedente trasferirà sempre l'esecuzione a quell'etichetta.
Questo significa che il ciclo continuerà a ripetersi all'infinito, a meno che non ci sia un altro salto verso l'esterno della sequenza ripetuta.

Per esempio, questo ciclo non termina:

```x86asm
infinite_loop:
    inc rax
    jmp infinite_loop ; always jumps to 'infinite_loop', repeating 'inc rax' forever
```

E questo ciclo può terminare, a seconda che la condizione sia soddisfatta:

```x86asm
maybe_finite_loop:
    cmp rax, 1
    je out_of_loop ; jumps to 'out_of_loop' if rax == 1, breaking the loop

    inc rax
    jmp maybe_finite_loop ; always jumps to 'maybe_finite_loop'
out_of_loop:
    ...
```

## Cicli con contatore

Un ciclo con contatore termina quasi sempre allo stesso modo: un'istruzione che aggiorna un contatore o confronta due valori, seguita immediatamente da un salto condizionale che decide se fare un altro giro.

```x86asm
sum_array:
    ; rdi is the memory address of an array
    ; rsi is the number of elements in the array

    mov eax, 0           ; running total
.loop:
    add rax, qword [rdi] ; add the current element
    add rdi, 8           ; advance to the next element
    sub rsi, 1           ; one fewer element to process, setting ZF at zero
    jnz .loop            ; repeat while the counter is not yet zero
    ret
```

~~~~exercism/note
`cmp rsi, 0` non è necessario nel codice qui sopra perché `sub rsi, 1` imposta già il `zero flag (ZF)` quando il risultato è `0`.

Anche se `cmp` è il modo principale per verificare le condizioni in assembly, molte istruzioni aggiornano i flag.
Per esempio, molte istruzioni aritmetiche su interi o bitwise aggiornano `ZF` quando il risultato è `0`, e `SF` quando il risultato è negativo (cioè quando il bit più alto è impostato).

Puoi controllare un [riferimento][reference] per vedere quali flag sono influenzati da ciascuna istruzione.

[reference]: https://www.felixcloutier.com/x86/
~~~~

Nota che nell'esempio qui sopra, si presume che `rsi` sia maggiore di `0`.
Se fosse `0`, allora `sub rsi, 1` ridurrebbe `rsi` a `-1`, che è un numero senza segno molto grande.
Servirebbero altre `18,446,744,073,709,551,615` iterazioni prima che il ciclo finisse.
Inoltre, dato che la lunghezza dell'array è `0`, qualsiasi accesso alla memoria sarebbe fuori dai limiti.

Se non ci sono garanzie sulla lunghezza di un array, ci sono due approcci comuni.

Il primo consiste nello spostare la condizione di terminazione all'inizio del ciclo, e poi mettere un salto incondizionato alla fine:

```x86asm
sum_array:
    mov eax, 0
.loop:
    cmp rsi, 0
    je .done
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jmp .loop
.done:
    ret
```

Il secondo consiste nel verificare una volta se l'array è di lunghezza zero prima dell'inizio del ciclo:

```x86asm
sum_array:
    mov eax, 0

    cmp rsi, 0
    je .done
.loop:
    add rax, qword [rdi]
    add rdi, 8
    sub rsi, 1
    jnz .loop
.done:
    ret
```

Questo secondo approccio è di solito più efficiente del primo, perché ci sono meno salti condizionali nel corpo del ciclo.
Imparerai di più su questo in un concetto futuro.

## Micro-operazioni

Un processore non esegue direttamente un'istruzione come `add` o `jnz`.
Il front-end della CPU prima _decodifica_ ogni istruzione in uno o più passaggi interni più piccoli, chiamati **micro-operazioni** (o **micro-op**).
Il processore poi pianifica ed esegue queste micro-operazioni, spesso diverse per ciclo e fuori dal loro ordine originale.

La maggior parte delle istruzioni semplici si decodifica in una singola micro-operazione, mentre un'istruzione più complessa può decodificarsi in diverse.
Poiché il carico di lavoro reale del processore è il flusso di micro-operazioni, produrne meno per lo stesso compito è un modo per rendere il codice più veloce.

## Macrofusione

Come accennato in precedenza, un ciclo di solito termina con un qualche tipo di salto condizionale.
Questo è così comune che i processori moderni sono ottimizzati per questo schema durante la decodifica.

Un'istruzione che imposta i flag, seguita immediatamente da un salto condizionale che legge quei flag, può essere decodificata insieme in una **singola** micro-operazione, invece che una per ciascuna.
Questa si chiama **macrofusione**.

La coppia fusa si comporta come un'unica operazione: il contatore viene aggiornato e la decisione di salto viene presa insieme, in una singola micro-operazione.
Il flusso di controllo del ciclo non costa quindi quasi nulla in aggiunta al lavoro che il ciclo svolge davvero.

Come regola generale, due tipi di coppie di solito si fondono in questo modo:

- Istruzioni aritmetiche come `add` o `sub`, seguite immediatamente da un salto condizionale.
- Un `cmp`, `test` o `and`, seguito immediatamente da un salto condizionale.

```x86asm
    ...
    add rdi, 8       ; advance a pointer
    cmp rdi, rsi     ; compare it against the end address
    jb .loop         ; repeat while still below the end
```

La fusione avviene solo quando il salto condizionale viene **immediatamente** dopo l'istruzione che imposta i flag, senza nulla in mezzo.

~~~~exercism/note
La macrofusione dipende dalla CPU e c'è una certa variazione su quali istruzioni si fondano con quale salto condizionale.

Un riferimento utile è [The microarchitecture of Intel, AMD, and VIA CPUs, by Agner Fog][agner-uarch].
La sezione 3.4.2.2 (Optimizing for Macrofusion) del [Intel optimization reference manual][intel-opt] elenca anche le coppie fusibili per le CPU Intel.

[intel-opt]: https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf
[agner-uarch]: https://www.agner.org/optimize/microarchitecture.pdf
~~~~

## L'istruzione `loop`

Ci sono alcune istruzioni che possono essere usate per creare un comportamento simile a un ciclo.
Una di queste è [loop][loop].

Il suo unico operando è un'etichetta che contiene l'indirizzo dell'inizio del ciclo.

L'istruzione `loop` usa il valore in `rcx` come contatore, decrementandolo di 1 ogni volta.
Quando il valore in `rcx` raggiunge zero, il ciclo termina e l'esecuzione continua in sequenza:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    loop .example ; this repeats the sequence starting in .example 10 times (the value in rcx)
                  ; at each time, rcx is decremented by 1
```

Ci sono due varianti dell'istruzione `loop` che controllano il flag di zero (`ZF`) a ogni iterazione.
Oltre a fermare il ciclo quando `rcx` raggiunge zero, si fermano anche quando la condizione _non_ è soddisfatta.

| istruzione       | condizione |
| ----------------- | --------- |
| `loope`/`loopz`   | `ZF` == 1 |
| `loopne`/`loopnz` | `ZF` == 0 |

Il `ZF` **non viene impostato** da queste istruzioni.
Deve esserci un `cmp`, `test` o un'altra istruzione che modifica `ZF` prima di esse:

```x86asm
section .text
fn:
    mov rax, 0
    mov rcx, 10
.example:
    inc rax
    cmp rax, 3
    loopne .example ; this repeats the sequence starting in .example while rcx > 0 and rax != 3
```

~~~~exercism/caution
Nonostante la loro comodità, `loop`, `loope` e `loopne` sono di solito molto più lenti sui processori moderni rispetto alla sequenza equivalente `sub`/`jnz` o `cmp`/`jnz`.

Un buon riferimento sulle prestazioni delle istruzioni in molte CPU diverse sono le [Agner's tables][agner-tables].

[agner-tables]: https://www.agner.org/optimize/instruction_tables.pdf
~~~~

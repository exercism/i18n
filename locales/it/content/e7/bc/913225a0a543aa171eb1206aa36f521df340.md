# Generatori di test

I generatori di test consentono ai track di generare i test automaticamente, senza doverli scrivere a mano. Ogni generatore di test legge il `canonical data` dell'esercizio, che definisce il nome del test, i suoi input e i suoi output. Puoi leggere di più sull'approccio di Exercism alle suite di test [qui](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Generare i test automaticamente elimina qualsiasi tipo di errore umano nella creazione dei test. Vogliamo che i test siano accurati rispetto al loro canonical data. La generazione dei test rende anche molto più facile mantenerli aggiornati. Quando il canonical data cambia, i test vengono aggiornati automaticamente nel momento in cui si esegue il generatore di quel test.

Un esempio di file di canonical data si trova [qui](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)

## Termini comuni

Quando esaminiamo il canonical data e il codice dei generatori, usiamo molti termini ricorrenti. Questo elenco dovrebbe chiarire cosa rappresentano.

* Canonical Data: rappresenta l'intera suite di test.
* Canonical Data Case: una rappresentazione di un singolo caso di test.
* Description: il nome del test.
* Property: il metodo da chiamare quando si esegue il test.
* Input: l'input del caso di test.
* Expected: il valore atteso quando si esegue il caso di test.

## Aggiungere un generatore semplice

Aggiungere un generatore di test è semplice. Basta aggiungere una classe al file `Generators.fs` nella cartella `generators`, con il nome dell'esercizio (in PascalCase), ed estendere la classe astratta `GeneratorExercise`.

Un esempio di generatore semplice è l'esercizio Bob. Il codice sorgente è qui sotto, ma puoi anche vederlo nel repository [qui](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174).

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

Questo è un generatore perfettamente funzionante: non serve scrivere altro codice. Tuttavia, la sua semplicità deriva dal fatto che la suite di test e il programma stesso sono relativamente banali.

## Aggiungere un generatore complesso

Per molti generatori, il comportamento predefinito della classe `GeneratorExercise` è sufficiente. Per i generatori più _complessi_, però, è possibile sovrascrivere uno o più dei suoi metodi virtuali:

### Metodo: RenderInput

Renderizza l'input di un metodo di test.

#### Esempio

Il generatore `Gigasecond` renderizza il valore di input come un valore `DateTime` (tra parentesi):

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

Nota che puoi usare il campo `key` per personalizzare l'output solo per campi di input specifici. Il generatore `Yacht` fa così:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Metodo: RenderExpected

Renderizza il valore atteso di un metodo di test.

#### Esempio

Il generatore `Connect` renderizza il valore atteso come un valore `Option<T>`:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Metodo: RenderSut

Renderizza il System Under Test (SUT). È il valore effettivo che viene verificato rispetto al valore atteso.

#### Esempio

Il generatore `RunLengthEncoding` ha un caso di test in cui verifica che codificare e poi decodificare l'input dia come risultato lo stesso valore. Il metodo `RenderSut` viene sovrascritto per convertire quella che sarebbe una singola chiamata a una funzione `consistency` inesistente in una catena di chiamate `encode |> decode`:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Metodo: RenderArrange

Renderizza la parte di arrange del metodo di test. In questa parte viene creato il SUT.

Nella maggior parte dei casi il comportamento predefinito è quello che vuoi. Solo in circostanze molto particolari ti conviene cambiarlo.

Nota: questo metodo restituisce una `string list`, in cui ogni `string` corrisponde a una singola riga renderizzata nel file di test.

### Metodo: RenderAssert

Renderizza la parte di assert del metodo di test. In questa parte viene fatta l'asserzione per verificare il SUT rispetto al valore atteso.

Nella maggior parte dei casi il comportamento predefinito è quello che vuoi. Solo in circostanze molto particolari ti conviene cambiarlo.

Nota: questo metodo restituisce una `string list`, in cui ogni `string` corrisponde a una singola riga renderizzata nel file di test.

### Metodo: RenderSetup

Renderizza eventuali metodi aggiuntivi di utilità o di setup. Può servire a definire metodi ausiliari da usare nei metodi di test.

Il codice di setup viene aggiunto _prima_ dei metodi di test, così che i metodi di setup possano essere usati nei metodi di test.

Nota: questo metodo restituisce una `string list`, in cui ogni `string` corrisponde a una singola riga renderizzata nel file di test.

#### Esempio

Il generatore `Zipper` aggiunge due metodi ausiliari, usati nei metodi di test per eliminare un po' di codice ripetitivo e noioso:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Metodo: RenderValue

Renderizza un singolo valore (usato per renderizzare i parametri di input, il valore atteso e il SUT).

### Esempio

Il generatore `ComplexNumbers` renderizza valori diversi a seconda del tipo del valore:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Metodo: MapCanonicalDataCase

Mappa il caso di canonical data. Può essere utile se vuoi aggiungere o rimuovere proprietà.

Nella maggior parte dei casi il comportamento predefinito è quello che vuoi. Solo in circostanze molto particolari ti conviene cambiarlo.

#### Esempio

Il generatore `ScaleGenerator` usa la mappatura del caso di canonical data per aggiungere una proprietà mancante con valore `null` (così è più facile elaborarla in seguito):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Metodo: PropertiesUsedAsSutParameter

Specifica quali proprietà devono essere usate come parametri per il SUT.

Nella maggior parte dei casi il comportamento predefinito è quello che vuoi. Solo in circostanze molto particolari ti conviene cambiarlo.

#### Esempio

Il generatore `RailFenceCipher` definisce esplicitamente le proprietà usate come parametri del SUT per cambiare l'ordine in cui vengono passate:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Metodo: PropertiesWithIdentifier

Specifica a quali proprietà deve essere assegnato un identificatore. Se una proprietà è in questo elenco, le verrà assegnato il suo valore su una riga separata, con un identificatore proprio.

#### Esempio

Il generatore `Transpose` ha scelto di usare identificatori per tutte le proprietà:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Metodo: IdentifierTypeAnnotation

In alcuni casi, vuoi che un identificatore abbia un tipo esplicito. Un caso d'uso comune è quando un valore è una lista vuota. In questi casi, FsUnit ha bisogno di un'annotazione di tipo per eseguire correttamente l'asserzione.

#### Esempio

Il generatore `Minesweeper` aggiunge un'annotazione di tipo `string list` per i valori vuoti:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Metodo: AdditionalNamespaces

Restituisce un elenco di namespace aggiuntivi da aprire nel file di test.

#### Esempio

Il generatore `Gigasecond` lavora con istanze di `DateTime`, e quindi aggiunge il suo namespace all'elenco dei namespace aggiuntivi:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Metodo: AssertTemplate

Il template di assert da usare. Trovi l'elenco completo dei template di assert in `generators/Templates/_Assert*.liquid`

#### Esempio

Il generatore `RationalNumbers` usa il template `"AssertEqualWithin"` per poter verificare l'uguaglianza dei numeri in virgola mobile con una tolleranza specifica:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Metodo: TestFileFormat

Il formato del file di test: un modulo o una classe.

Il comportamento predefinito è quasi sempre quello che vuoi. Solo in casi estremamente rari ti conviene cambiarlo.

#### Esempio

Il generatore `Grep` si definisce come classe di test per poter usare metodi di setup e teardown:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Metodo: TestMethodName

Specifica il nome del metodo di test.

Nella maggior parte dei casi il comportamento predefinito è quello che vuoi. Solo in circostanze molto particolari ti conviene cambiarlo.

#### Esempio

Il generatore `Zipper` fa un po' di pulizia nel nome del metodo di test:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Metodo: UseFullMethodName

Indica se il nome del metodo di test usato deve usare il percorso completo. Per i casi di test annidati, questo significa anteporre al nome del metodo di test la descrizione del genitore o dei genitori.

Nella maggior parte dei casi il comportamento predefinito è quello che vuoi. Ti conviene cambiarlo solo nei casi in cui altrimenti ci sarebbero più metodi di test con lo stesso nome.

#### Metodo: Signature

Il generatore `KindergartenGarden` usa i nomi completi dei metodi per evitare conflitti tra i nomi dei metodi di test:

```fsharp
override __.UseFullMethodName _ = true
```

### Metodo: SkipTestMethod

Indica se il metodo di test deve essere contrassegnato con la proprietà `Skip = true`.

Il comportamento predefinito è quasi sempre quello che vuoi. Solo in casi estremamente rari ti conviene cambiarlo.

#### Metodo: Signature

L'esercizio `Markdown` è un esercizio di riorganizzazione e, come tale, tutti i suoi test dovrebbero già essere in uno stato valido. Perciò non aggiunge la proprietà `Skip` a nessuno dei suoi metodi di test:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Aggiornare i file esistenti

Può capitare che un esercizio esistente non corrisponda al canonical data. Va benissimo aggiornare lo stub dell'esercizio e/o l'esempio dell'esercizio per seguire il canonical data!

Inoltre, se trovi un problema in uno dei generatori o delle suite di test esistenti, apri semplicemente il generatore che vuoi aggiornare, fai le tue modifiche e poi esegui i generatori.

## Eseguire i generatori

Questo repository è scritto per [.NET Core 2.x](https://www.microsoft.com/net/core). Per eseguire i generatori ti basta lanciare il comando seguente nella cartella dei generatori:

`dotnet run`

Questo comando prende tutti i generatori di esercizi definiti e genera tutti i casi di test per ogni esercizio. Usiamo la reflection per recuperare tutti gli esercizi, quindi se stai aggiungendo un nuovo test, il test verrà incluso automaticamente quando esegui il generatore.

Se ti serve eseguire un solo generatore, puoi farlo lanciando il comando seguente:

`dotnet run -e <exercise>`

Dopo aver eseguito il generatore, puoi vedere l'output della generazione andando al file di test di quell'esercizio. Ad esempio, la suite di test dell'esercizio Bob si trova in:

`exercises/bob/BobTests.fs`

## Inviare un generatore

Se sei soddisfatto dell'output del tuo generatore, ci piacerebbe molto che inviassi una pull request! Includi il tuo generatore, la suite di test aggiornata e qualsiasi altro file corrispondente che hai modificato.

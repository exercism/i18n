# Contribuire al track C

Grazie per il tuo interesse a contribuire al track C di Exercism!
Tutti i contributi sono benvenuti: un nuovo esercizio, una modifica agli strumenti o alla documentazione, una issue aperta o anche solo un commento su una issue o una PR esistenti.
Questo file fornisce le informazioni necessarie per iniziare.

Per prima cosa, dai un'occhiata alla [documentazione di Exercism][Exercism docs], in particolare alle informazioni su come [contribuire a un track][contributing to a language track]: questi documenti coprono gran parte delle informazioni di base.

Inoltre, tieni presente che ci sono alcune cose specifiche di questo repository, spiegate qui di seguito.

Incoraggiamo i contributi che apportano correzioni e miglioramenti agli esercizi esistenti.
Tieni presente che gli esercizi di questo track devono rispettare gli standard definiti nel repository [problem-specifications][].
Le modifiche ai test o alla documentazione di un esercizio comune spesso richiedono una pull request in quel repository prima di poter essere integrate negli esercizi di questo track.
Se hai dei dubbi, apri pure una [issue][] su GitHub e ne discuteremo insieme.

## Flusso di lavoro con Git

1. Fai un fork e clona.
2. Aggiungi questo repository come nuovo remote al tuo clone: `git remote add upstream https://github.com/exercism/c.git`
3. Crea un nuovo branch: `git checkout -b name-of-branch`
4. Fai commit e push come al solito sul tuo nuovo branch
5. Quando sei pronto a inviare una pull request, fai il rebase del tuo branch su main di upstream in modo da poter risolvere eventuali conflitti: `git fetch upstream && git rebase upstream/main` Dopo aver risolto i conflitti, potresti dover fare push sul tuo branch usando `--force`.
6. Quando è tutto pronto, fai push sul tuo branch e crea la pull request come descritto di seguito.

## Issue

Teniamo traccia di bug, miglioramenti e richieste di supporto nel repository usando le [issue][] di GitHub.

Per discussioni di più alto livello sul progetto nel suo insieme, dai un'occhiata alle issue nel repository [discussions][].

### Good First Patch

Cerchiamo di etichettare le issue con "good first patch" quando pensiamo che possano essere risolte senza troppa conoscenza del codice o delle funzionalità di Exercism. Per trovarle, puoi cercare [good-first-patch][].

## Pull request

Sarebbe fantastico se seguissi queste semplici [linee guida per le pull request][pull request guidelines] mentre crei la tua PR, ma non è obbligatorio.

Le pull request dovrebbero concentrarsi su una singola issue o modifica.
Accogliamo con favore modifiche allo stile del codice e alla formulazione, ma se possibile apri una PR separata per queste modifiche.
Apri una issue prima di creare una PR che apporta modifiche significative (breaking) a un esercizio esistente o che modifica molti esercizi. È meglio discutere queste modifiche prima di fare il lavoro.

Se la tua modifica riguarda un esercizio, puoi eseguire gli script della CI prima di inviare la pull request, oppure verranno eseguiti automaticamente dopo, come descritto nell'[integrazione continua][Continuous Integration].

Quando invii una pull request, a volte ti chiederemo di apportare modifiche prima di accettare la patch.

Non chiudere la prima pull request e aprirne una seconda con queste modifiche.
Se fai push di altri commit su un branch per cui hai aperto una pull request, questa si aggiorna automaticamente.

Se vuoi creare una PR con modifiche che non sono ancora del tutto pronte per essere unite a main (magari perché vorresti discutere di un punto specifico, per esempio), crea la PR normalmente ma usa l'interfaccia web di GitHub per [convertire la PR in bozza][convert the PR to a draft], così i maintainer sapranno che non è ancora pronta per essere unita.

Come quando aggiungi altri commit, non devi chiudere la pull request e aprirne una nuova se modifichi la cronologia (rebase, squash, amend) e usi git push --force per aggiornare il branch sul tuo fork.
La pull request punta a quel branch, non a commit specifici.

## Stile del codice

Lo stile del codice richiesto per i contributi che modificano il codice è spiegato nella [guida di stile][style guide].

Il codice degli esercizi viene controllato durante la [CI][Continuous Integration] per verificarne la conformità alle regole di stile su spaziatura e indentazione.
Il controllo usa lo strumento CLI [`clang-format`][clang-format].
Quando aggiungi un esercizio o lo modifichi, puoi verificare che la tua modifica sia conforme a queste regole eseguendo lo strumento in locale prima di fare il commit.

Su Linux, `clang-format` dovrebbe essere disponibile per l'installazione tramite il gestore di pacchetti della tua distribuzione.
Su Mac, puoi installare il pacchetto `clang-format` usando [Homebrew][].

`clang-format` può essere eseguito su tutti i file lanciando `format.sh`.
Per eseguirlo manualmente su un singolo file, puoi eseguire il comando seguente:

```bash
clang-format -i $(file)
```

## Anatomia di un esercizio

Ogni esercizio dovrebbe trovarsi in una directory `c/exercises/practice/{exercise-name}`.
Vedi [implement-an-exercise-from-specification][] per i dettagli approfonditi su come implementare un esercizio conforme alla specifica

La struttura di una directory di esercizio è la seguente (nota l'uso diverso del trattino e del trattino basso, rispettivamente per i nomi delle directory e dei file):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c`: questo file contiene tutti i test per l'esercizio.  
`test-framework`: directory che contiene il test harness [Unity][] di [ThrowTheSwitch][].  
  ThrowTheSwitch ha una guida niente male su come [iniziare con Unity][getting started with unity], se desideri un tutorial.  
  La versione di Unity utilizzata è indicata in [versions][]. La struttura del file di test è descritta nella [guida di stile][test-file-layout].  
  I test dovrebbero essere scritti in modo da soddisfare il file `canonical-data.json` dell'esercizio nel repository [problem-specifications][]  
`{exercise-name}.c` / `{exercise-name}.h`: i file sorgente dell'esercizio.  
  Usa le [include guard][include guards] nei tuoi file header.
  I test dell'esercizio possono essere eseguiti con `make test` dalla radice del repository.
* `makefile`: è il makefile dell'esercizio così come verrebbe compilato.  
Sono richieste due regole,  
test: compila test_{exercise-name}.c ed eseguilo.
memcheck: compila test_{exercise-name} con i flag -fsanitize=address, -fno-common, -fno-omit-frame-pointer ed eseguilo
I makefile tendono a cambiare molto poco da un esercizio all'altro, quindi dovrebbe essere facile copiarne uno da un altro esercizio.

**Non dimenticare** di aggiungere l'esercizio al `config.json` del track. Per farlo, dovrai determinare il punto migliore in cui inserire l'esercizio nell'ordine di tutti gli altri esercizi del track. Dovrai anche generare un UUID da aggiungere qui. Per entrambe queste attività puoi usare lo strumento [configlet][]: dopo aver apportato le modifiche, lo strumento eseguirà persino il lint e la formattazione del `config.json` per te!

A proposito: per ottenere l'artefatto di installazione dello strumento configlet, dai un'occhiata alla [pagina delle release di configlet][configlet releases page].

## Integrazione continua

Questo repository usa i workflow di GitHub per eseguire alcuni strumenti a ogni commit su una pull request.
Il modo più semplice per eseguire questi workflow sul tuo contributo è aprire una PR su questo repository con le tue modifiche, impostarla come bozza e poi lasciare che la configurazione della CI di questo repository se ne occupi automaticamente.

### Ambiente della CI

GitHub esegue la CI su macchine virtuali che chiama [hosted runners][].
I workflow possono configurare alcuni aspetti dei runner su cui desiderano essere eseguiti.

I workflow di questo repository specificano solo che ciascuno deve essere eseguito su Ubuntu 24.04. I workflow sono bloccati a versioni specifiche invece di riferirsi a `latest`, poiché alcuni strumenti utilizzati possono comportarsi diversamente su versioni diverse.

### Eseguire la CI sul tuo fork

Se vuoi, è anche possibile eseguire la CI sul tuo fork: ti basta clonare questo repository normalmente su GitHub.
I file YAML che si trovano in [`./.github/workflows/`][workflows] dovrebbero funzionare allo stesso modo.
Se vuoi che l'azione automatica [`/format`][format-workflow] funzioni correttamente, dovrai aggiungere una deploy key al repository clonato.

### I workflow

* `checks.yml` esegue `shellcheck` sugli script degli strumenti e poi esegue i seguenti tra quegli strumenti:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * azione di [controllo dei link Lychee][lychee]
* `configlet.yml` scarica l'ultima versione di configlet, con cui esegue poi il comando `lint` sul track
* `format-code.yml` cerca la stringa `/format` in qualsiasi commento di una PR; se la trova, esegue `format.sh` sugli esercizi e viene eseguito il commit di eventuali modifiche risultanti. Perché il commit possa riattivare la CI è necessaria una deploy key. La deploy key è gestita direttamente da Exercism.
* `test.yml` esegue `make` dalla radice del repository per testare tutti gli esercizi

### Gli strumenti

Dai [workflows][] puoi vedere che a GitHub viene chiesto di eseguire gli strumenti dalla directory [`./bin`][bin].
Il lavoro svolto dagli strumenti in questa directory è descritto di seguito:

* `check-unitybegin` verifica che ogni file di test aggiunga correttamente la riga `UNITY_BEGIN()` all'inizio della sua funzione `main()`.
* `fetch-configlet` scarica lo strumento `configlet` dal suo [repository][configlet].
* `verify-unity-version` controlla la versione del framework di test Unity usata da ogni esercizio. La versione che questo file deve controllare è specificata in [`./docs/VERSIONS.md`][versions]
* `check-include-guards` controlla che le include guard usate nell'header stub e nell'header di esempio di ogni esercizio utilizzino il formato corretto, come segue:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` scarica lo strumento `configlet` dal suo [repository][configlet].

### Eseguire gli strumenti in locale

Puoi anche eseguire i singoli strumenti sulla tua macchina prima di fare il commit.
Per prima cosa, assicurati di avere installate le applicazioni necessarie (come `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] e un compilatore C), poi esegui lo strumento richiesto dalla radice del repository. Ad esempio:

```bash
~/git/c$ make
```

Se vuoi eseguire solo alcuni dei test per verificare il tuo lavoro, puoi specificarli come target di make.

```bash
~/git/c$ make acronym all-your-base allergies
```

Questo track ha un test runner per Exercism v3!

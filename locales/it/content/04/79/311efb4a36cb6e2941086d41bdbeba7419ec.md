# Introduzione

## L'interfaccia error

La gestione degli errori **non** avviene tramite eccezioni in Go.
Invece, gli errori sono normali _valori_ di tipi che implementano l'interfaccia `error` predefinita.
L'interfaccia `error` è molto minimale.
Contiene un solo metodo `Error()` che restituisce il messaggio di errore come stringa.

```go
type error interface {
  Error() string
}
```

Ogni volta che definisci una funzione in cui potrebbe verificarsi un errore durante l'esecuzione e che deve raggiungere il chiamante, devi includere `error` tra i tipi restituiti.
Se la funzione ha più valori restituiti, per convenzione `error` è sempre l'ultimo.

```go
func DoSomething() (int, error) {
  // ...
}
```

## Creare e restituire un errore semplice

Non devi sempre implementare tu stesso l'interfaccia error.
Per creare un errore semplice, puoi usare la funzione `errors.New()`, che fa parte del pacchetto `errors` della libreria standard.
L'unica cosa che devi passare è il messaggio di errore come stringa, e `errors.New()` si occuperà di creare un valore che contiene il messaggio e implementa l'interfaccia `error`.

Se la funzione restituisce un errore, è buona pratica restituire il valore zero per tutti gli altri valori restituiti:

```go
func DoSomething() (SomeStruct, int, error) {
  // ...
  return SomeStruct{}, 0, errors.New("failed to calculate result")
}
```

~~~~exercism/caution
Non dovresti dare per scontato che tutte le funzioni restituiscano valori zero per gli altri valori restituiti quando è presente un errore.
È buona pratica presumere che non sia sicuro usare nessuno degli altri valori restituiti se si è verificato un errore.
Le uniche eccezioni sono i casi in cui la documentazione afferma chiaramente che gli altri valori restituiti sono significativi in caso di errore.
~~~~

Se vuoi usare un errore semplice in più punti, dovresti dichiarare una variabile per l'errore invece di usare `errors.New` in linea.
Per convenzione, il nome della variabile dovrebbe iniziare con `Err` o `err` (a seconda che sia esportata o meno).
Queste variabili di errore sono spesso chiamate _errori sentinella_.

```go
import "errors"

var ErrNotFound = errors.New("resource was not found")

func DoSomething() error {
  // ...
  return ErrNotFound
}
```

Restituisci `nil` per l'errore per segnalare che non ci sono stati errori durante l'esecuzione della funzione:

```go
func Foo() (int, error) {
  return 10, nil
}
```

## Controllo degli errori

Se chiami una funzione che restituisce un errore, è comune memorizzare il valore dell'errore in una variabile chiamata `err`.
Prima di usare il risultato effettivo della funzione, devi controllare che non ci sia stato un errore.

Per evitare di annidare il «percorso felice» del codice, i casi di errore dovrebbero essere gestiti per primi.
Possiamo usare `==` e `!=` per confrontare l'errore con `nil` e sappiamo che c'è stato un errore quando `err` non è `nil`.

```go
func processUserFile() error {
	file, err := os.Open("./users.csv")
	if err != nil {
		return err
	}

	// do something with file
}
```

Il più delle volte, l'errore verrà restituito risalendo lo stack delle funzioni, come mostrato nell'esempio sopra.
Un altro modo per gestire l'errore potrebbe essere registrarlo nei log e continuare con un'altra operazione.
È buona pratica restituire o registrare l'errore, mai entrambe le cose.

Poiché la maggior parte delle funzioni in Go include un errore tra i valori restituiti, vedrai e userai il pattern `if err != nil` dappertutto nel codice Go.

## Tipi di errore personalizzati

Se vuoi che un errore includa più informazioni della sola stringa del messaggio di errore, puoi creare un tipo di errore personalizzato.
Come accennato prima, tutto ciò che implementa l'interfaccia error (ovvero ha un metodo `Error() string`) può fungere da errore in Go.

Di solito, si usa una struct per creare un tipo di errore personalizzato.
Per convenzione, i nomi dei tipi di errore personalizzati dovrebbero terminare con `Error`.
Inoltre, è meglio definire il metodo `Error() string` con un ricevitore puntatore; guarda questo [commento su Stack Overflow][stackoverflow-errors] per capire il motivo.
Nota che questo significa che devi restituire un puntatore al tipo di errore personalizzato, altrimenti non conterà come `error`, perché il valore non puntatore non fornisce il metodo `Error() string`.

```go
type MyCustomError struct {
  message string
  details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.message, e.details)
}

func someFunction() error {
  // ...
  return &MyCustomError{
    message: "...",
    details: "...",
  }
}
```

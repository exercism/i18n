# Informazioni sulla nullabilità

In un mondo ideale, potremmo contare sul fatto che tutto sia ben definito, con valori concreti e senza lacune.

Questo contrasta con la nostra esperienza quotidiana; per questo molti linguaggi di programmazione hanno un modo per rappresentare l'assenza di un valore: null o NULL, nil, None, nothing...

È stato facile da introdurre (risale al 1965), ma presto ha portato a dei rimpianti.
In seguito, il suo inventore lo ha definito il suo [«Billion Dollar Mistake»][web-mistake].

Negli ultimi decenni, i progettisti di linguaggi hanno esplorato molti modi per rendere i null disponibili ma (per lo più) sicuri.

Kotlin ha alcuni [principi generali][ref-null-safety], che [differiscono in modo significativo da Java][ref-java2kotlin].
_Le differenze fanno sì che Kotlin abbia funzionalità speciali per gestire l'interoperabilità con Java, ma i dettagli vanno oltre lo scopo di questo concetto._

- Kotlin ha uno speciale valore `null`.
- Tutti i tipi sono _per impostazione predefinita_ non-nullable (cioè non possono essere `null`) .
- Tutti i tipi possono essere _nullable_, ma questo va fatto in modo esplicito.
- Le funzioni che potrebbero fallire con un'eccezione hanno spesso una variante con un valore restituito nullable.
- Una sintassi speciale e molto concisa cerca di rendere il più semplice possibile verificare i null e reagire alla loro presenza.

## Creare variabili nullable

Un tipo può essere reso [nullable][ref-nullable-type] aggiungendo il suffisso `?` (ad esempio `String?` invece di `String`).

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operatori e funzioni utili

### L'[operatore di chiamata sicura][ref-safe-call] `?.`

Per una `String` non-nullable, possiamo ottenere la proprietà `.length`.

Una `String?` nullable fallisce con la stessa sintassi, ma usare `?.length` tiene conto della possibilità di un `null`.
Il tipo restituito è `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Come abbiamo visto nell'ultima riga qui sopra, `?.` funziona anche con i tipi non-nullable.

### L'[operatore Elvis][ref-elvis] `?:`

Estendendo l'idea dell'operatore di chiamata sicura, l'[operatore Elvis][wiki-elvis] ci permette di fornire un valore predefinito che sostituisca `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### L'[operatore di asserzione non-null][ref-not-null] `!!`

Con questo operatore, un tipo nullable viene forzato a essere trattato come non-null, quando chi programma ne è sicuro.
Forse a volte capiamo la logica del programma meglio di un compilatore troppo prudente?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

Ora la responsabilità è nostra: se `b` è ancora `null`, otteniamo una `NullPointerException`.

### La [funzione let][ref-let] `?.let`

Se passiamo un elemento nullable a un blocco di codice, potremmo fare controlli specifici sui null con `if (item != null) { do something }`.

Usare `item?.let { do something }` è più semplice e più idiomatico.
Il `do something` viene eseguito solo quando `item` non è null.

### Funzioni di tipo `somethingOrNone()`

Alcune funzioni possono fallire, per esempio quando si chiede un indice non valido in una stringa o in un array.

Anziché lanciare un'eccezione, potremmo usare la [variante `...OrNull`][ref-elem-at-or-null] della funzione, per ottenere (in questo caso) un valore restituito `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

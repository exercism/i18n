# Strategia di merge

I maintainer del track Rust [hanno deciso](https://github.com/exercism/v3/discussions/1725#discussion-7438) di mettere per iscritto la nostra strategia di merge, per comunicare le aspettative e incoraggiare contributi di qualità.

## Principi generali

- ci impegniamo ad accettare _tutti_ i contributi
  - Porteremo i contributi a un alto standard di qualità attraverso una revisione collaborativa e iterativa.
  - Adottiamo un approccio di merge pessimistico. Immagina le revisioni dei maintainer come il feedback del compilatore Rust. La quantità di feedback può sembrare opprimente e frustrante. Ma lavoreremo insieme a te per portarla fino al traguardo! Quindi continua così.
- Ogni pull request deve ricevere almeno un "Approval", e nessuna "Request Changes", da un maintainer del track prima che se ne possa fare il merge.
- Nessun maintainer può approvare la propria pull request.

## Flusso di lavoro delle pull request

### Definizioni

| Termine            |                                                                                               Significato |
| ------------------ | ----------------------------------------------------------------------------------------------------: |
| Contributore       |                                                                     Chiunque invii una pull request. |
| Maintainer         |         Chiunque faccia parte del [team @exercism/rust](https://github.com/orgs/exercism/teams/rust). |
| Branch di sviluppo | Il branch di sviluppo predefinito del repository [v3](https://github.com/exercism/v3). Attualmente `master`. |

### Il flusso di lavoro

1. I contributori iniziano aprendo una pull request [in bozza](https://github.blog/2019-02-14-introducing-draft-pull-requests/) o completa con le loro modifiche
   1. Usare la funzione bozza segnala che il lavoro è pronto per una revisione ad alto livello, ma che i dettagli potrebbero non essere ancora implementati, incompleti o sbagliati.
   1. Dopo un numero imprecisato di iterazioni dei passaggi 2-3, il contributore contrassegna la pull request come pronta per la revisione.
1. Un altro maintainer revisiona il contributo e fornisce un feedback.
1. Il contributore dà seguito a _tutti_ i feedback dei maintainer all'interno della pull request.
   1. I maintainer valutano di usare la funzione di suggerimento di GitHub per ritocchi minimi o modifiche banali.
   1. Il dissenso è incoraggiato quando un contributore ritiene di avere ragione e un maintainer di avere torto su un punto del feedback. «Dare seguito» a un feedback non è sinonimo di implementarlo ciecamente.
1. Il maintainer esamina il feedback e poi:
   1. approva
   1. richiede ulteriori modifiche. A questo punto, il processo torna al passaggio 3.
1. Dopo l'approvazione, un maintainer esegue il merge della pull request.
   1. I maintainer eseguono il merge delle proprie pull request. Dato che i contributori non sono necessariamente maintainer, questo passaggio deve essere eseguito da un maintainer.

## Merge ottimistico

I maintainer del track Rust hanno deciso di adottare temporaneamente il merge ottimistico per accelerare lo sviluppo del track v3.

- Questo vale solo per il repository v3
- Torneremo a una strategia di merge pessimistico quando rilasceremo la v3 in produzione.
- Approveremo ed eseguiremo il merge di lavori incompleti
  - Se compila, lo teniamo.
  - Preferiamo la velocità di iterazione ai dettagli più fini di un design del software corretto.
- Ogni pull request deve ricevere almeno un "Approval" da un maintainer del track prima che se ne possa fare il merge.

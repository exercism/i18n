# Informazioni

I thread di Factor sono *coroutine cooperative* su un singolo thread del sistema operativo. Un thread viene eseguito finché non cede esplicitamente il controllo o non esegue un'operazione di I/O bloccante: a quel punto lo scheduler sceglie un altro thread eseguibile. Due conseguenze:

- Tutto ciò che avviene tra un yield e l'altro è di fatto atomico.
- Il vero parallelismo multi-core richiede di uscire dal vocab `threads` standard (ad esempio `concurrency.distributed` per progettazioni multi-processo).

Le primitive di concorrenza standard sono disposte a livelli:

| Vocab                       | Fornisce                               |
|-----------------------------|----------------------------------------|
| [`threads`][threads]                   | `spawn`, `yield`, identità del thread  |
| [`concurrency.promises`][concurrency.promises]      | `<promise>`, `fulfill`, `?promise`     |
| [`concurrency.locks`][concurrency.locks]         | `<lock>`, `with-lock`                  |
| [`concurrency.combinators`][concurrency.combinators]   | `parallel-map`, `parallel-each`        |
| [`concurrency.semaphores`][concurrency.semaphores]    | `<semaphore>`, `acquire`, `release`    |
| [`concurrency.mailboxes`][concurrency.mailboxes]     | caselle di posta per thread, `send`, `receive` |
| [`concurrency.channels`][concurrency.channels]      | handle di rendezvous, `to`, `from`     |

```factor
USING: concurrency.combinators concurrency.locks
concurrency.promises kernel sequences threads ;

! parallel-map: fork-join, in order
{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }

! spawn + promise: hand-rolled fork-join
<promise> [
    [ "hello, world" swap fulfill ] curry "greeter" spawn drop
] keep ?promise .   ! => "hello, world"

! <lock> + with-lock: protect a shared mutable slot
<lock> :> guard
guard [ "do thing under lock" drop ] with-lock
```

`parallel-map` è l'API di alto livello, ed è quella a cui il Factor idiomatico ricorre per prima. Il trio `spawn` / `<promise>` / `?promise` è ciò su cui è costruito `parallel-map`: torna comodo quando la forma dell'iterazione non si adatta a map (ad esempio quando si generano worker che rispondono attraverso altri canali).

I lock proteggono lo *stato mutabile condiviso*: in genere uno slot di una tupla o una hashtable a cui più di un thread accede in lettura o in scrittura. Considera sia le letture sia le scritture come operazioni che richiedono il lock se esiste un aggiornamento composto non atomico: dimenticare il lock su uno dei due lati è la classica ricetta per una lettura parziale.

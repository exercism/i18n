# Sobre

## Tipos Compostos

Muitas vezes é útil definir tipos personalizados em nossos programas.

Criar novos tipos primitivos é possível, mas raramente se faz isso.
Os [tipos primitivos][primitive] embutidos não são uma escolha arbitrária: eles correspondem de perto aos tipos padrão do compilador LLVM que o Julia usa para compilação JIT.

Muito mais útil é a capacidade de definir [tipos compostos][composite-types], com campos nomeados.

Outras linguagens têm algo parecido, chamando-os de `structs` ou `records`.
A documentação do Julia se refere a eles como `composite types`, embora (com uma pequena discrepância) a sintaxe da linguagem os defina com a palavra-chave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale a pena destacar alguns pontos no exemplo acima:

- Nenhum tipo é especificado para `id`, então o compilador interpreta isso como `id::Any`.
  - **Observação:** na prática, é melhor ajudar o compilador especificando o tipo de um campo com um tipo concreto.
  - Veremos em um [Conceito futuro][parametric] que usar parâmetros é outra opção.
- O nome do tipo é usado como construtor, como em `Person(id, name, age)`, para criar uma instância do tipo `Person`.
- Campos individuais podem ser acessados com notação de ponto, assim como as [tuplas nomeadas][named-tuple].

Itens do tipo `Person` são imutáveis, então atualizações não são permitidas.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Se a mutabilidade for necessária, adicione `mutable` à definição.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Por padrão, o construtor exige que os campos apareçam na mesma ordem da definição. Isso se torna inconveniente para tipos mais complicados.

Usar a macro `@kwdef` permite dois novos recursos:

- O construtor usa argumentos nomeados, não a posição.
- Os campos podem ter valores padrão e, opcionalmente, podem ser omitidos do construtor.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarquias de Tipos Compostos

Até agora, criamos apenas tipos compostos concretos.
Se você verificar, todos são subtipos de `Any`.

Ao criar vários tipos relacionados, provavelmente faz mais sentido definir uma hierarquia para eles.
Isso é muito fácil de fazer.

Primeiro, crie um tipo abstrato:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Em seguida, inclua um operador `<:` na definição de um tipo, para mostrar a relação.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Repita conforme necessário, lembrando que não é permitido criar subtipos de tipos concretos.

Para uma hierarquia mais complexa, crie subtipos abstratos conforme necessário.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

O valor de uma hierarquia como essa ficará mais claro quando chegarmos ao Conceito `Multiple Dispatch` e virmos como as funções lidam com tipos de argumentos.


## Construtores Internos

Vimos no início deste Conceito que o nome do tipo é usado como construtor, para criar itens desse tipo:

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)
```

Aqui, `Person()` é conhecido como um `outer constructor`.
Os tipos dos campos serão verificados quanto à compatibilidade com a definição do tipo, e um erro será gerado se necessário.

E se quisermos restrições sobre os _valores_ passados, e não apenas sobre os _tipos_?

Então podemos incluir um `inner constructor` dentro da definição do tipo, para fazer as verificações apropriadas.

Por exemplo, temos um tipo abstrato `AbstractPoint`, destinado a receber coordenadas `(x, y)`, mas queremos um subtipo com a restrição `y > x`.

```julia-repl
julia> abstract type AbstractPoint end;

julia> struct Point <: AbstractPoint
           x::Integer
           y::Integer
       end;

julia> struct ConstrainedPoint <: AbstractPoint
           x::Integer
           y::Integer
           
           ConstrainedPoint(x, y) =
               y > x ? new(x, y) : @error("require y > x")
       end;
       
julia> Point(3, 2)
Point(3, 2)

julia> ConstrainedPoint(3, 2)
Error: require y > x

julia> ConstrainedPoint(3, 5)
ConstrainedPoint(3, 5)
```

A função `new()` pode ser usada _somente_ em construtores internos, e retorna o item desejado se as entradas forem consideradas válidas.

Para uma entrada inválida, poderíamos parar com uma mensagem de erro, como no exemplo.
Como alternativa, você pode preferir usar um placeholder como `nothing` ou `missing`.
Veja o Conceito [`Nothingness`][nothingness] para saber mais sobre isso.

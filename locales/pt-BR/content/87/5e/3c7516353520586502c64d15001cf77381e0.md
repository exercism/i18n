# Prepare-se para receber contribuições de código aberto de pessoas desconhecidas

Neste ponto, você já deve conseguir aceitar contribuições de pessoas desconhecidas.
Escreva uma [documentação de contribuição](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors) para ajudar essas pessoas a contribuir.

## Issues

Se houver exercícios que você queira incluir no track, mas ainda não implementou, abra issues para cada exercício.
Em geral, recomendamos abrir issues para as tarefas para as quais você aceitaria contribuições.

Temos uma seção especial no site que lista _tarefas_, que são issues com um ou mais labels especiais.
Ter suas issues listadas no site é uma ótima forma de conseguir mais contribuições.
Para saber mais sobre como fazer suas issues aparecerem no site, confira a [documentação de tarefas](/docs/building/product/tasks).

## Outras coisas a considerar

- Existe um guia de estilo para a sua linguagem de programação?
- Esses estilos são incentivados ou exigidos?
- Existem convenções que deveríamos adotar neste track por uma questão de consistência?
- Podemos exigir isso?
- Existe um linter? Existem muitos? Deveríamos usar um?
- Existe uma convenção comum para nomes de arquivos? Se não, qual deveria ser a nossa convenção?

Pode valer a pena abrir issues separadas para as coisas que você quiser resolver.

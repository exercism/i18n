# Introdução

## Adicionando contexto aos erros

Exploramos o tratamento básico de erros em Go no [conceito de erros][concept-errors].
Como você aprendeu lá, por padrão os erros não carregam stack traces.
Por isso, é fundamental garantir que o próprio erro contenha informações suficientes para identificar o problema.

Se quiséssemos adicionar informações a um erro existente com as ferramentas que já conhecemos, poderíamos escrever algo assim para criar um novo erro com o texto combinado do erro original e das informações adicionais:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Felizmente, o pacote `fmt` da biblioteca padrão tem uma versão abreviada disso na forma da função `Errorf`.
Isso permite, por exemplo, adicionar facilmente informações sobre o contexto em que o erro ocorreu.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Muitas vezes, essa forma de adicionar informações a um erro é suficiente, mas há casos em que você quer permitir que quem consome o seu erro verifique ou recupere o erro original subjacente.
Adicionar contexto de um jeito que permita isso é o que chamamos de "encapsular um erro" em Go.

## Encapsulando erros e verificando erros sentinela

O encapsulamento de erros pode ser feito com uma mudança bem pequena no código que vimos acima.
Para encapsular um erro, você precisa usar o verbo de formatação `%w` em vez de `%v`.
Nos bastidores, isso garante que o erro resultante implemente um método `Unwrap` que retorna o erro original.
Por causa disso, o `errors.Is` pode ser usado para verificar se um erro sentinela específico aparece em algum ponto da "cadeia de erros".
Ele faz isso chamando `Unwrap` repetidamente, nos bastidores, até que o erro em questão seja encontrado ou a cadeia termine.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

É uma boa prática usar `%v` por padrão e só usar `%w` se você quiser explicitamente permitir que quem consome o seu erro acesse um erro subjacente ([Google Go Styleguide][google-go-styleguide]).

Se você se deparar com uma situação em que quer verificar um erro sentinela mas não quer desencapsular explicitamente, pode usar `==` em vez de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Não há problema em trabalhar com `errors.Is` por padrão, mas você deve sempre ter em mente que isso significa que toda a cadeia de erros será percorrida.

## Verificando tipos de erro (personalizados)

Existe um equivalente ao `errors.Is` que permite verificar e recuperar um erro de um tipo específico na cadeia de erros.
A função para isso é `errors.As` e, assim como `errors.Is`, ela procura o tipo de erro informado ao longo de toda a cadeia.
O `errors.As` só então extrai o erro que encontrou e que corresponde ao tipo, para que você possa continuar trabalhando com ele, por exemplo, acessar campos específicos.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Cuidado com a sintaxe em relação aos ponteiros acima.
O código só vai funcionar e compilar corretamente se `customError` tiver exatamente o tipo que implementa a interface de erro.
No nosso caso, esse tipo é `*MyCustomError` (um [ponteiro][concept-pointers] para `MyCustomError`), e não o próprio `MyCustomError`.

Além disso, o segundo argumento precisa ser um ponteiro para a variável de erro.
Como o nosso erro já é um ponteiro, o que passamos para `errors.As` é um ponteiro para um ponteiro (para MyCustomError).
Só com isso configurado corretamente o Go consegue preencher a variável com o erro que encontrou.
~~~~

Como antes, o `errors.As` não teria encontrado o tipo de erro se `%v` tivesse sido usado na chamada de `Errorf`.

Se, por algum motivo, você não quiser desencapsular, pode usar uma asserção de tipo no lugar (equivalente ao `==` acima).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

A asserção de tipo não vai conseguir identificar o tipo de erro se o erro tiver sido encapsulado.

## Permitindo desencapsular erros de tipos personalizados

Às vezes, apenas encapsular um erro com um texto adicional não é o suficiente.
Você pode, em vez disso, criar um tipo de erro personalizado que guarda o erro original e os dados estruturados adicionais que você quer adicionar.
Se você quiser permitir o desencapsulamento do seu tipo de erro, a única coisa que precisa fazer é adicionar manualmente um método `Unwrap() error` para satisfazer a interface `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

# Sobre

`String` e `&str` são duas formas fundamentais de trabalhar com dados textuais em Rust.
Conhecer as características das duas e como elas funcionam juntas é muito útil.
Este documento mostra como elas se sobrepõem e traz alguns conselhos básicos.
`String` é um vetor de bytes `u8` com ownership.
`String` é mutável.
`&str` é uma referência emprestada a um slice de String.
`&str` é imutável.

A pronúncia correta de `&str` é "ref string".
`String` é uma representação codificada em UTF-8, potencialmente mutável, de uma sequência de code points Unicode.

`&str` é uma visão somente leitura de uma sequência UTF-8 bem formada.
Como é uma referência, ela é `Copy` e pode ser compartilhada.

Em Rust, não é possível indexar `String` e `&str` como você faria em outras linguagens.
Por exemplo, isto não funciona:

```rust,invalid
let hello = "Hello";
println!("First letter = {}", hello[0]);
```

Isso vem das seguintes propriedades:

- As strings são UTF-8, cuja unidade primitiva não é o byte, mas sim o code point Unicode: `char`.
- Os code points Unicode ocupam até 4 bytes, mas são codificados com largura variável.
- Por isso é impossível calcular a posição do `n`-ésimo code point sem iterar sobre os caracteres codificados de fato, porque, depois do primeiro caractere, a posição do próximo depende da largura dos anteriores.
- Por isso, os autores da biblioteca padrão do Rust optaram por não implementar o trait `Index` para strings: indexar um array de bytes leva tempo constante, mas indexar uma string pode levar bastante tempo. Isso viola o princípio da menor surpresa.

```rust
let example = "I'm not entirely ASCII! ❤";

let n_chars = example.chars().count();
let final_byte = example.as_bytes()[example.len()-1];

println!("n_chars = {}", n_chars);             // 25
println!("example.len() = {}", example.len()); // 27

println!("final char: {}", example.chars().nth(n_chars-1).unwrap()); // ❤
println!("final byte: {final_byte}");                                // 164
println!("char of final byte: {}", final_byte as char);              // ¤
```

## Convertendo uma `String` em um `&str`

`String` implementa `Deref<Target=str>`.
Esse trait tem um tratamento especial do compilador: ele significa que qualquer referência a uma `String` pode ser convertida automaticamente e de forma transparente em um `&str`.
Isso implica o seguinte:

- Qualquer código que espere, por exemplo, um argumento `&str` pode aceitar um `&String` no lugar.
- Qualquer método implementado para `&str` também pode ser chamado em uma `String`.

(Se você quisesse aceitar, de forma genérica, qualquer forma de referência a um `str`, poderia usar um argumento do tipo `impl AsRef<str>`, mas normalmente é comum tipar os argumentos como `&str`.)

## Convertendo um `&str` em uma `String`

Há muitas formas de criar uma `String` a partir de um `&str`:

- `String::from("my str")`
- `"my str".to_string()`
- `"my str".to_owned()`
- `let s: String = "my str".into();`

Todas as formas acima exigem alocar memória para a `String` (no heap).
É por isso que `&str` está disponível em no_std, mas `String` não.

(O crate [heapless](https://crates.io/crates/heapless) costuma ser usado para manipular
strings em no_std.)

## Usando String e `&str` em structs

Esta seção discute quando usar `String` ou `&str` em campos de struct.
É comum ver structs definidas com `String` em vez de `&str` nos campos.

```rust
struct Record {
    latitude: f64,
    longitude: f64,
    population: Option<u64>,
    city: String,
    state: String,
}
```

Ao usar `String`, os dados pertencem à struct.
Isso deixa o código mais fácil de ler e de ensinar para quem está começando.
Mas também significa que haverá alocações no heap para cada campo.
`&str` empresta os dados textuais, então tem um desempenho melhor, em troca de a sua struct precisar definir parâmetros de tempo de vida.
O [tutorial do crate csv][csv-tutorial] demonstra e explica essas ideias de forma bem prática.

## Notas sobre desempenho

As `String` são alocadas no heap, por isso podem ter um custo maior.
As `&str` são uma referência compartilhada, então não exigem realocação frequente.

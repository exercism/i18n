# Sobre

## Erros no `jq`

O `jq` reporta duas grandes categorias de erros:

1. **Erros de compilação**: o programa em si é inválido, com erros de sintaxe, referências a funções ou variáveis indefinidas e assim por diante.
   O `jq` se recusa a rodar o programa.

   ```sh
   $ jq -n '1 + $foo + 2'
   jq: error: $foo is not defined at <top-level>, line 1, column 5:
       1 + $foo + 2
           ^^^^
   jq: 1 compile error
   ```

2. **Erros de execução**: o programa é válido, mas algo dá errado enquanto um valor é processado: indexar um número com uma string, interpretar um texto JSON inválido com `fromjson`, chamar uma função com argumentos do tipo errado e assim por diante.

   ```sh
   $ echo '42' | jq '.foo'
   jq: error (at <stdin>:1): Cannot index number with "foo"
   ```

Este conceito trata de **erros de execução**: como lançá-los, como capturá-los e como interrompê-los.

Um erro de execução não capturado faz o `jq` imprimir uma mensagem na _saída de erro padrão_ e sair com status `5`.

## Lançando erros: `error` e `error(message)`

O filtro [`error`][man-error] lança um erro.

- `error` lança um erro cujo valor é o valor de **entrada**.
- `error(message)` lança um erro cujo valor é o resultado de `message`.

```jq
"bad input" | try error catch .
# => "bad input"

42 | try error("invalid value: \(.)") catch .
# => "invalid value: 42"
```

~~~~exercism/note
O valor do erro pode ser _qualquer_ valor JSON, não só uma string.
Lançar erros estruturados permite que um tratador de `catch` tome decisões com base no conteúdo do erro.

```jq
try error({kind: "range", msg: "age must be non-negative"})
catch (if type == "object" then "\(.kind) error: \(.msg)" else "unexpected: \(.)" end)
# => "range error: age must be non-negative"
```
~~~~

Se um valor de erro que não é string não for capturado, o `jq` o imprime como JSON, marcado com `(not a string)`.

```sh
$ jq -n 'error({code: 42, msg: "boom"})'
jq: error (at <unknown>) (not a string): {"code":42,"msg":"boom"}
```

## Capturando erros: `try` e `catch`

Erros podem ser capturados com [`try EXP catch HANDLER`][man-try-catch].
A primeira expressão é executada; se ela lançar um erro, a expressão `HANDLER` é executada **com o valor do erro como entrada**.
A saída do tratador é emitida como se fosse a saída da expressão que estava sendo tentada.

```jq
true | try .a catch "cannot index a \(type)"
# => "cannot index a boolean"

[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]

true | try error("some exception") catch .
# => "some exception"
```

A forma mais curta `try EXP` equivale a `try EXP catch empty`: o erro é descartado e nenhuma saída é produzida.

```jq
[{}, true, {"a": 1}] | [.[] | try .a]
# => [null, 1]
```

~~~~exercism/note
Um erro **aborta o resto do stream** dentro do `try`.
Os valores já produzidos são mantidos, mas nada depois do erro é avaliado.

```jq
jq -n 'try (1, error("x"), 3) catch "caught: \(.)"'
# outputs:
# 1
# "caught: x"
# (3 is never produced)
```
~~~~

Um tratador pode lançar um novo erro, ou relançar o original com um `error` simples. Como o valor do erro é a entrada do tratador, isso o propaga sem alterações.

```jq
try repeat(f) catch
  if . == "break" then empty else error end
```

## Suprimindo erros: o operador `?`

O [operador `?`][man-question-mark], usado como `EXP?`, é uma forma abreviada de `try EXP`.
Ele transforma uma expressão que falha em uma que simplesmente não produz saída.

```jq
["1", "invalid", "3", 4] | [.[] | tonumber?]
# => [1, 3, 4]

true | [.a?]
# => []
```

É comum vê-lo junto aos operadores de indexação:

- `.foo?` é `.["foo"]?`
- `.[]?` itera somente se a entrada for um array ou um objeto, e é vazio caso contrário

~~~~exercism/caution
O `?` suprime **todo** erro, inclusive os que você não previu.
`user.name?` silenciosamente não produz nada quando `user` não é um objeto, o que pode esconder problemas nos dados ou erros de digitação no seu programa.
Prefira `try ... catch` quando você precisa saber _que_ algo falhou, ou valide a entrada explicitamente.
~~~~

## O operador alternativo `//`

Às vezes as pessoas esperam que `a // b` produza `b` quando `a` falha.
Isso era verdade em versões antigas do `jq`, mas não desde o `jq` 1.6.
O operador `//` não suprime erros.
Ele só substitui `b` quando `a` não produz nenhum valor, produz `false` ou produz `null`; erros em `a` continuam propagando.

```sh
$ jq -n '(error("x")) // 42'
jq: error (at <unknown>): x
```

Use `try a catch b` se quiser uma alternativa para os erros.

## O operador alternativo de desestruturação `?//`

O [operador `?//`][man-question-mark-slash-slash] combina desestruturação com tratamento de erros.
Ele tenta cada padrão de vinculação, um de cada vez, até que um funcione, e as variáveis vinculadas pelas alternativas que falharam são definidas como `null`.

```jq
# input:
#   [
#     {"a": 1, "b": 2, "c": {"d": 3, "e": 4}},
#     {"a": 5, "b": 6, "c": [{"d": 7, "e": 8}]}
#   ]

.[] as {$a, $b, c: {$d, $e}} ?// {$a, $b, c: [{$d, $e}]}
| {$a, $b, $d, $e}

# outputs:
# {"a": 1, "b": 2, "d": 3, "e": 4}    # first element: c is an object, first pattern matched
# {"a": 5, "b": 6, "d": 7, "e": 8}    # second element: c is an array, second pattern matched
```

Aqui, o primeiro padrão espera que `c` seja um _objeto_ com as chaves `d` e `e`, enquanto o segundo espera que `c` seja um _array_ contendo um objeto assim.
O primeiro elemento da entrada se vincula ao primeiro padrão; o segundo elemento não satisfaz esse padrão, então o segundo padrão é tentado.

Isso permite que um único programa desestruture entradas que podem assumir uma entre várias formas, sem escrever cadeias explícitas de `if type == ...`.

## Interrompendo o programa: `halt` e `halt_error`

Às vezes a resposta certa para um erro é parar o processamento de vez.

- [`halt`][man-halt] interrompe o programa `jq` imediatamente, sem nenhuma outra saída; o status de saída é `0`.
- [`halt_error`][man-halt-error] interrompe o programa, imprime sua **entrada** na _saída de erro padrão_ como texto bruto (sem decoração, nem mesmo uma quebra de linha) e sai com o status informado, que é `5` por padrão.

```sh
$ echo '"Error: something went wrong"' | jq 'halt_error(1)'
Error: something went wrong    # printed on stderr, exit status 1
```

Repare que esses filtros interrompem o programa imediatamente, mesmo que ainda haja mais entradas para ler.

### Status de saída

Para referência, o `jq` usa estes status de saída:

| Status | Significado                                      |
| :----: | ------------------------------------------------ |
| `0`    | sucesso                                          |
| `2`    | erro de uso (opções de linha de comando inválidas) |
| `3`    | erro de compilação                               |
| `5`    | erro de execução (ou `halt_error` sem argumento) |

Com a opção `--exit-status` / `-e`, o status passa a refletir o último valor de saída: `0` para `true` ou números, `1` para `false` ou `null`, `4` quando não há saída.

## Auxiliares de depuração

Quando você está tentando descobrir de onde vem um erro, estes filtros ajudam:

- [`debug`][man-debug] repassa sua entrada sem alterações, mas imprime `["DEBUG:", <input>]` na saída de erro padrão.
  `debug(msgs)` também imprime `msgs` como mensagens de depuração.
- [`stderr`][man-stderr] imprime sua entrada, bruta e compacta, na saída de erro padrão.
- [`input_line_number`][man-input-line-number] gera o número da linha da entrada que está sendo filtrada no momento. É inestimável quando um arquivo contém muitos textos JSON e um deles está com problema.
- [`$__loc__`][man-loc] gera um objeto com as chaves `file` e `line` descrevendo onde no programa ele aparece, o que pode ser embutido em mensagens de erro.

```jq
def checked_div($d):
  if $d == 0
  then error("\($__loc__): division by zero")
  else . / $d end;

try (10 | checked_div(0)) catch .
# => "{\"file\":\"<top-level>\",\"line\":3}: division by zero"
```

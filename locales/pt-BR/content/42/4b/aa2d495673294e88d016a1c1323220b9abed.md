# Sobre

Em conceitos anteriores, foi mencionado que a diretiva `global` torna uma função ou variável definida em um arquivo-fonte visível para outros arquivos.
De forma semelhante, a diretiva `extern` informa ao montador que uma função ou variável usada no arquivo-fonte atual está definida em outro.

Essas duas diretivas são a principal forma de o código assembly interagir com outros arquivos-fonte para alcançar a modularização.

Para os propósitos dessas diretivas, é indiferente se o código externo é definido ou usado em assembly ou em uma linguagem de alto nível.
Assim, por exemplo, até mesmo uma função definida em uma linguagem de alto nível pode ser usada em código x86-64 se for declarada `extern`.

Da mesma forma, a convenção de chamada é compartilhada entre todas essas funções, definidas em assembly ou em linguagens de alto nível, e até com o Sistema Operacional (SO).

No entanto, como em assembly os dados são apenas uma sequência de bytes, é importante estar atento a como a linguagem de alto nível que faz a interface gerencia a memória.

## Tipos em C

A linguagem C é uma escolha comum como linguagem de alto nível para fazer interface com código assembly.
Ela facilita a tarefa de interagir com o SO, oferecendo wrappers de alto nível para muitas tarefas importantes, como imprimir na tela, ler do teclado ou alocar memória dinâmica.

Nesta trilha, os testes são escritos em C, por isso é importante oferecer uma visão geral da linguagem.

### Tipos primitivos

Existem muitos tipos primitivos em C, e o tamanho deles, em bytes, pode variar.
Alguns deles estão resumidos na tabela a seguir, com o tamanho típico em um sistema x86-64:

| tipo      | número de bytes | inteiro/ponto flutuante |
|-----------|-----------------|------------------------|
| _Bool     | 1               | inteiro                |
| char      | 1               | inteiro                |
| short     | 2               | inteiro                |
| int       | 4               | inteiro                |
| long      | 4 ou 8          | inteiro                |
| long long | 8               | inteiro                |
| float     | 4               | ponto flutuante        |
| double    | 8               | ponto flutuante        |

Cada um desses tipos integrais pode ser com sinal (o padrão) ou sem sinal.
Caso sejam sem sinal, isso precisa ser especificado, por exemplo: `unsigned int`.

Existem aliases para os tipos integrais, definidos para oferecer controle preciso sobre o tamanho deles:

| alias   | número de bytes |
|---------|-----------------|
| int8_t  | 1               |
| int16_t | 2               |
| int32_t | 4               |
| int64_t | 8               |

Esses aliases podem ter o prefixo `u` para indicar um tipo sem sinal, por exemplo: `uint64_t`.

Outros aliases dignos de nota são:

| alias  | tipo                                          |
|--------|-----------------------------------------------|
| bool   | _Bool                                         |
| size_t | geralmente um inteiro sem sinal de 8 bytes    |

Um `_Bool`, ou seu alias `bool`, é único no sentido de que, embora ocupe 1 byte inteiro, só pode assumir um de dois valores: `true` (`1`) e `false` (`0`).

Valores desses tipos primitivos são passados para as funções e retornados por elas de acordo com as regras usuais para inteiros e valores de ponto flutuante.

### Enums

Um [enum][enum] é um tipo que pode assumir um entre vários elementos indicados explicitamente:

```c
enum example {
    example_1,
    example_2,
    example_3,
    example_4
};
```

Em C, os enums são convertidos implicitamente para um tipo inteiro, que normalmente é um `int`, ou seja, um inteiro de 4 bytes.

Por padrão, o primeiro elemento possível de um enum é convertido para `0` e todos os elementos seguintes são convertidos para o próximo inteiro.
Assim, no `enum example` definido acima, `example_1` teria o valor `0`, `example_2` teria o valor `1` e assim por diante.

É possível indicar o valor de qualquer elemento de um enum e, então, por padrão, o próximo elemento teria o próximo inteiro como valor:

```c
enum example_2 {
    example_1 = 4,
    example_2 = 8,
    example_3
}; // example_3 is equal to 9
```

### Endereços de memória

Em C, um endereço de memória é referenciado por um [ponteiro][pointer] para um tipo e denotado com o operador `*`.
Então, por exemplo, `int64_t *` se refere a um local de memória para um ou mais `int64_t`.

Os endereços são tratados como inteiros de 8 bytes, como de costume.

### Arrays

Arrays são passados para as funções e retornados por elas como ponteiros para o primeiro elemento.

```c
int64_t example_arr[] = {1, 2, 3}; // this is an array of 3 signed 8-byte integers
fn(example_arr); // this is a function that passes a pointer (int64_t *) to the beginning of the array as argument
```

Cada elemento de um array tem o tamanho do tipo de elemento do array.
O `example_arr` definido acima, por exemplo, tem 3 elementos de 8 bytes cada, o que dá 24 bytes no total.

Como os arrays não armazenam o próprio comprimento, normalmente é necessário um valor separado para indicar o número de elementos, a menos que um valor sentinela marque o fim.

### Strings

Strings em C são um array de `char`, que é um tipo de 1 byte.
A maioria das strings é de caracteres ASCII e terminada em NUL, então elas acabam quando um byte com o valor `0` é encontrado.
Isso significa que o comprimento de uma string normalmente não precisa ser passado como um argumento separado.

## Chamando funções da biblioteca C

A diretiva `extern` apenas declara que um símbolo está definido em outro arquivo.
Como uma chamada a ele é feita de fato depende de como esse código externo é linkado.

Para funções comuns linkadas junto com o seu código, o linker consegue encontrar uma função externa diretamente, então um simples `call` basta.

No entanto, funções da biblioteca padrão do C como `malloc`, `free` e `printf` geralmente são resolvidas em tempo de execução a partir de uma biblioteca compartilhada, cujo endereço não é conhecido quando o seu código é montado.
A chamada, portanto, passa por um stub em uma [Tabela de Ligação de Procedimentos (PLT)][plt], posicionada em um deslocamento conhecido.
Sempre que chamar uma função externa de biblioteca a partir do assembly, o NASM exige uma indicação de que essa chamada deve ser resolvida a partir da PLT.

No `elf64` (formato de saída usado por programas Linux), essa indicação é feita adicionando `wrt ..plt` ("com referência à plt") depois da chamada.
Por exemplo, `call printf wrt ..plt`.

Em programas `macho64` (formato de saída usado por programas macOS), por outro lado, um sublinhado antes do nome da função basta.
Por exemplo, `extern _printf`, depois `call _printf`.
No entanto, como esta trilha monta código `macho64` com a flag `--prefix _`, esse sublinhado é adicionado automaticamente pelo montador nas duas situações, por exemplo, `extern printf`, depois `call printf`.

Repare que o test-runner do Exercism roda em uma imagem Linux, então qualquer solução enviada que chame funções da biblioteca C deve usar `wrt ..plt`.
É possível usar uma guarda em tempo de montagem para despachar corretamente entre os formatos de saída:

```x86asm
extern malloc

%ifidn __OUTPUT_FORMAT__,elf64
    call malloc wrt ..plt       ; elf64: reach the function through the PLT
%else
    call malloc                 ; macho64: the linker generates the call stub
                                ; the underscore is added automatically by an assembler flag
%endif
```

## Chamadas de sistema

Existem muitas operações que programas em nível de usuário, como os que rodam nesta trilha, não podem realizar diretamente.
Ler de `stdin`, escrever em `stdout`, solicitar memória dinâmica, interagir com periféricos etc., tudo isso é tratado pelo Sistema Operacional (SO).

Um programa em nível de usuário precisa pedir explicitamente ao SO que realize essas operações, quando necessário.
Isso é feito com a instrução [`syscall`][syscall].
Conceitualmente, essa instrução pode ser vista como uma chamada a algum procedimento predefinido do SO (uma chamada "de sistema").

Qualquer argumento para a chamada de sistema deve ser passado ao SO em GPRs: `rdi`, `rsi`, `rdx`, `r10`, `r8` e `r9`.

Repare que a sequência é quase a mesma usada em uma chamada de função, mas `rcx` é substituído por `r10`.
Isso acontece porque `rcx` e `r11` são usados pelo `syscall` para salvar o endereço de retorno e as flags (que são restauradas antes de devolver o controle à função que fez a chamada).
Os dois registradores devem ser tratados como sobrescritos a cada `syscall`.

Diferentemente de `call`, não há rótulos indicando as "funções" do sistema.
Em vez disso, elas são acessadas por meio de números específicos colocados em `rax` antes da chamada.
Qualquer valor retornado, se houver, também é colocado em `rax`.

As convenções acima são descritas [em um apêndice da ABI do System V][linux-convention] que trata especificamente do Linux, e está marcado como apenas informativo.
Na prática, as chamadas de sistema disponíveis, seu número e como os erros são reportados são detalhes do nível do SO que variam muito entre SOs e até entre versões diferentes do mesmo SO.

Muitas funções da biblioteca C, e outras funções de fato definidas pelo SO, são wrappers de nível mais alto sobre uma chamada de sistema.
A ABI recomenda que esses wrappers sejam preferidos a um `syscall` puro, e a Apple [não garante compatibilidade][mac-qa1118] na interface de chamadas de sistema do kernel.

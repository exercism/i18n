# Introdução

Muitas vezes é útil definir tipos personalizados nos nossos programas.

Criar novos tipos primitivos é possível, mas raramente acontece.
Os tipos primitivos embutidos não são uma escolha arbitrária: eles correspondem de perto aos tipos padrão do compilador LLVM que a Julia usa para a compilação JIT.

Muito mais útil é a possibilidade de definir tipos compostos, com campos nomeados.

Outras linguagens têm algo parecido e os chamam de `structs` ou `records`.
A documentação da Julia se refere a eles como `composite types`, embora (numa pequena inconsistência) a sintaxe da linguagem os defina com a palavra-chave `struct`.

```julia-repl
julia> struct Person
           id
           name::String
           age::Integer
       end

julia> fred = Person(23, "Fred Smith", 46)
Person(23, "Fred Smith", 46)

julia> typeof(fred)
Person

julia> isstructtype(Person)
true

julia> isconcretetype(Person)
true

julia> fred.age
46
```

Vale a pena observar alguns pontos no exemplo acima:

- Nenhum tipo é especificado para `id`, então o compilador interpreta isso como `id::Any`.
  - Na prática, é melhor ajudar o compilador especificando o tipo de um campo com um tipo concreto
- O nome do tipo é usado como construtor, como em `Person(id, name, age)`, para gerar uma instância do tipo `Person`.
- Campos individuais podem ser acessados com a notação de ponto, assim como nas tuplas nomeadas.

Itens do tipo `Person` são imutáveis, então não é permitido atualizá-los.

```julia-repl
julia> fred.age += 1
ERROR: setfield!: immutable struct of type Person cannot be changed
```

Se a mutabilidade for necessária, adicione `mutable` à definição.

```julia-repl
julia> mutable struct MutPerson
           name
           age
       end

julia> shaila = MutPerson("Shaila", 23)
MutPerson("Shaila", 23)

julia> shaila.age += 1
24

julia> shaila
MutPerson("Shaila", 24)
```

Por padrão, o construtor exige que os campos apareçam na mesma ordem da definição, o que se torna inconveniente em tipos mais complicados.

Usar a macro `@kwdef` traz duas novas possibilidades:

- O construtor usa palavras-chave, não posição.
- Os campos podem ter valores padrão e, opcionalmente, podem ser omitidos do construtor.

```julia-repl
julia> @kwdef struct KwPerson
           name
           age = 42
       end
KwPerson

julia> suki = KwPerson(age=29, name="Suki")
KwPerson("Suki", 29)

julia> qi = KwPerson(name="Qi")
KwPerson("Qi", 42)

# create a Vector{KwPerson}

julia> friends = [suki, qi]
2-element Vector{KwPerson}:
 KwPerson("Suki", 29)
 KwPerson("Qi", 42)
```

## Hierarquias de tipos compostos

Até agora, só criamos tipos compostos concretos.
Se você verificar, todos são subtipos de `Any`.

Quando criamos vários tipos relacionados, provavelmente faz mais sentido definir uma hierarquia para eles.
Isso é muito fácil de fazer.

Primeiro, crie um tipo abstrato:

```julia-repl
julia> abstract type AbstractPerson end

julia> supertype(AbstractPerson)
Any
```

Em seguida, inclua um operador `<:` numa definição de tipo, para mostrar a relação.

```julia-repl
julia> struct ConcretePerson <: AbstractPerson
            id
            name::String
            age::Integer
        end

julia> supertype(ConcretePerson)
AbstractPerson

julia> ConcretePerson(15, "Luis", 8)
ConcretePerson(15, "Luis", 8)
```

Repita conforme necessário, lembrando que não é permitido criar subtipos de tipos concretos.

Para uma hierarquia mais complexa, crie subtipos abstratos conforme a necessidade.

```julia-repl
julia> abstract type AdultPerson <: AbstractPerson end

julia> supertype(AdultPerson)
AbstractPerson
```

O valor de uma hierarquia assim ficará mais claro quando chegarmos ao Conceito `Multiple Dispatch` e virmos como as funções lidam com tipos de argumento.

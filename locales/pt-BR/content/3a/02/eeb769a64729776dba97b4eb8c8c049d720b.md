# About

Em aplicações C#, a aleatoriedade em geral é implementada com a classe `System.Random`.

Este [artigo][system-random] é uma excelente introdução ao assunto.

Ao se familiarizar com uma classe de biblioteca, vale sempre estudar a [documentação][system-random] das propriedades, dos métodos e de suas sobrecargas.

O exercício destacou uma série de pontos:

- O gerador de números aleatórios não precisa de uma [semente][random-seedless].
- `Random.Next()` pode gerar uma faixa de números inteiros
- `Random.Double()` pode gerar um número de ponto flutuante entre 0 e 1
- Os limites superiores em `Next...()`, `Double()` e `Sample()` são **exclusivos**, então `Random.Next(1,19)` produz valores de 1 a 18, mas não 19.
- Depois de obter o número aleatório, você pode fazer o que quiser com ele

Existem 3 padrões para implementar o último ponto:

- Você pode obter o número aleatório e manipulá-lo. No caso do exercício, isso consistiria em chamar `Random.NextDouble()` e multiplicar por 100. Este [trecho][random-use-case-array] discute como fazer seleções aleatórias a partir de um array.
- Você pode herdar de `System.Random` e sobrescrever o método `Sample()`.
- Você pode encapsular uma instância de `System.Random` como membro de uma classe sua, por exemplo, [para gerar Boolean][random-use-cases].

Os números gerados por `Random` não têm garantia de ser únicos.

É [recomendado][random-thread-safety] que você instancie `System.Random` como membro estático. Mas note que ele não é thread safe.

Você pode encontrar documentação que desaconselha o uso de construtores sem semente. Isso vale principalmente para o .NET Framework, e não para o .NET Core (que é o que o _Exercism_ usa). Para a história completa, leia [isto][random-multiple-instantiations].

Recomenda-se não usar `System.Random` para criptografia ou segurança. Veja este [provedor][crypto-provider] e este [gerador de números][crypto-rng].

## Segurança de threads

Quando aplicado no contexto de APIs de bibliotecas, "não é thread safe" é apenas uma forma abreviada de dizer que, se você provavelmente vai acessar instâncias da classe por meio de várias [threads][threading] concorrentes, deve fornecer seus próprios mecanismos de sincronização de threads ou, no caso de coleções, considerar a possibilidade de usar uma versão concorrente da classe. Sem essas precauções, é provável que ocorram [condições de corrida][so-race-conditions]. Se sua base de código não usa múltiplas threads, nem é provável que venha a usar, esse aviso não é motivo de grande preocupação.

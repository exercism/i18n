# Sobre

## Adicionando contexto aos erros

Exploramos o tratamento básico de erros em Go no [conceito de erros][concept-errors].
Como você aprendeu lá, por padrão os erros não carregam rastreamentos de pilha.
Por isso, é fundamental garantir que o próprio erro contenha informação suficiente para identificar o problema.

Se quiséssemos adicionar informação a um erro existente com as ferramentas que já conhecemos, poderíamos escrever algo assim para criar um novo erro com o texto combinado do erro original e da informação adicional:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Felizmente, o pacote `fmt` da biblioteca padrão trazem uma versão abreviada disso na forma da função `Errorf`.
Isso permite, por exemplo, adicionar facilmente informação sobre o contexto em que o erro ocorreu.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

A menos que você tenha certeza de que o erro já traz informação suficiente, procure criar o hábito de sempre adicionar contexto a um erro antes de retorná-lo de uma função.
Isso significa que seu padrão habitual de tratamento de erros deve se parecer com isto:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Como mostram os exemplos, a convenção é separar o erro da mensagem adicionada com dois-pontos.
Assim como a mensagem do erro original, a mensagem de contexto também não deve começar com letra maiúscula nem terminar com ponto-final.

~~~~exercism/note
Ao adicionar contexto a um erro, é tentador começar a mensagem com "failed to ..." ou algo parecido.
No entanto, como um erro pode acumular bastante contexto adicional à medida que sobe pela cadeia de funções, isso pode deixar a mensagem final, que será registrada no log ou mostrada para a pessoa, mais difícil de ler e cheia de repetições.

Veja um exemplo para ilustrar:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Então tenha esse resultado final em mente ao escrever as mensagens de contexto e evite adicionar texto sobre o fato de que algo não saiu como o esperado.
Isso geralmente fica claro pelo contexto (por exemplo, o nível de log "ERROR") e pela mensagem do erro original.
~~~~

Muitas vezes, essa forma de adicionar informação a um erro é suficiente, mas há casos em que você quer permitir que quem consome o seu erro verifique ou recupere o erro original subjacente.
Adicionar contexto de uma forma que permita isso é chamado de "encapsular um erro" em Go.

## Encapsulando erros e verificando erros sentinela

O encapsulamento de erros pode ser feito com uma mudança bem pequena no código que vimos acima.
Para encapsular um erro, você precisa usar o verbo de formatação `%w` em vez de `%v`.
Nos bastidores, isso garante que o erro resultante implemente um método `Unwrap` que retorna o erro original.
Por causa disso, `errors.Is` pode ser usado para verificar se um erro sentinela específico aparece em algum ponto da "cadeia de erros".
Ele faz isso chamando `Unwrap` repetidamente, nos bastidores, até encontrar o erro em questão ou até a cadeia acabar.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Verificar o erro original com `errors.Is` não funcionaria com o verbo de formatação comum `%v`.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Por isso, é uma boa prática usar `%v` por padrão e só usar `%w` se você quiser explicitamente permitir que quem consome o seu erro acesse um erro subjacente ([Guia de estilo do Google para Go][google-go-styleguide]).

Se você se encontrar numa situação em que quer verificar um erro sentinela mas não quer desencapsular explicitamente, pode usar `==` em vez de `errors.Is`.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Em contrapartida, `==` não identificaria o erro se ele estivesse encapsulado.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Tudo bem trabalhar com `errors.Is` por padrão, mas você deve sempre ter em mente que isso significa que toda a cadeia de erros será percorrida.

## Verificando tipos de erro (personalizados)

Existe um equivalente ao `errors.Is` que permite verificar e recuperar da cadeia de erros um erro de um tipo específico.
A função para isso é `errors.As` e, assim como `errors.Is`, ela procura o tipo de erro informado por toda a cadeia.
`errors.As` só então extrai o erro que encontrou e que corresponde ao tipo, para que você possa trabalhar mais com ele, por exemplo, recuperar campos específicos.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Cuidado com a sintaxe em relação aos ponteiros acima.
O código só vai funcionar e compilar corretamente se `customError` tiver exatamente o tipo que implementa a interface de erro.
No nosso caso, esse tipo é `*MyCustomError` (um [ponteiro][concept-pointers] para `MyCustomError`), e não o próprio `MyCustomError`.

Além disso, o segundo argumento precisa ser um ponteiro para a variável de erro.
Como o nosso erro já é um ponteiro, o que passamos para `errors.As` é um ponteiro para um ponteiro (para MyCustomError).
Só com essa configuração correta o Go consegue preencher a variável com o erro que encontrou.
~~~~

Como antes, `errors.As` não teria encontrado o tipo de erro se `%v` tivesse sido usado na chamada de `Errorf`.

Se, por algum motivo, você não quiser desencapsular, pode usar em vez disso uma asserção de tipo (equivalente ao `==` acima).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

A asserção de tipo não conseguirá identificar o tipo do erro se o erro estiver encapsulado.

## Permitindo desencapsular erros de tipos personalizados

Às vezes, apenas encapsular um erro com um texto adicional não é suficiente.
Você pode, em vez disso, criar um tipo de erro personalizado que guarda o erro original e os dados estruturados adicionais que você quer acrescentar.
Se você quer permitir o desencapsulamento do seu tipo de erro, a única coisa que precisa fazer é adicionar manualmente um método `Unwrap() error` para satisfazer a interface `Unwrap`.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Combinando vários erros

No Go 1.20, uma nova função `Join` foi adicionada ao pacote `errors`, que é embutido na linguagem.
`Join` permite combinar vários erros de uma forma que ainda permite o desencapsulamento, ou seja, verificar um erro ou tipo de erro específico ao longo da cadeia.
Com isso, a cadeia de erros pode, na verdade, ser uma árvore de erros.
Você encontra mais informação nas [notas de lançamento][release-notes] e na [documentação][doc-join].

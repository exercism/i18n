# Sobre

O código escalar depende de flags definidas por várias instruções para desviar em resposta a uma determinada condição.
Os valores empacotados, porém, representam não um, mas muitos valores em paralelo.
Uma mesma condição pode falhar em uma lane e ser satisfeita em outra.

É por isso que o código SIMD é [sem desvios][branchless-code] por padrão.

Em vez de depender de flags, as comparações empacotadas normalmente produzem uma **máscara** no operando de destino.
Para cada lane, a comparação preenche a lane inteira com uns quando a condição é verdadeira e com zeros quando é falsa.
Lida como inteiro com sinal, uma lane verdadeira vale `-1` e uma lane falsa vale `0`.

Essa máscara pode então ser combinada com [operações bit a bit][simd-bitwise] para filtrar lanes específicas.

## Comparações empacotadas

Um `cmp` escalar é genérico no sentido de que é usado para definir várias flags ao mesmo tempo.
Outra instrução pode então consumir essas flags para desviar ou realizar cálculos.

No entanto, como uma comparação empacotada ao mesmo tempo verifica uma condição e calcula uma máscara, ela não é genérica.
É preciso informar à comparação a condição exata que está sendo testada.

Há duas formas de fazer isso:

- As comparações de inteiros recebem a condição como sufixo: `eq` para igualdade e `gt` para maior que.
  As outras variantes são construídas combinando o resultado de uma dessas.
- As comparações de ponto flutuante recebem a condição codificada em um imediato.
  Valores diferentes desse imediato correspondem a condições diferentes sendo testadas.

Fora o uso de um sufixo condicional específico nas comparações de inteiros, a sintaxe segue a mesma estrutura que já vimos:

- Para inteiros, `p` + `cmp` + condição + tamanho (`b`, `w`, `d` ou `q`).
- Para ponto flutuante, `cmp` + `p` + tamanho (`s` ou `d`).
  A condição é passada em um imediato como operando extra.

### Comparações de inteiros

Como mencionado, só existem comparações de inteiros para igualdade e maior que:

| instrução                                  | descrição                          |
|--------------------------------------------|------------------------------------|
| `pcmpeqb`, `pcmpeqw`, `pcmpeqd`, `pcmpeqq` | igualdade por lane                 |
| `pcmpgtb`, `pcmpgtw`, `pcmpgtd`, `pcmpgtq` | maior que **com sinal** por lane   |

```x86asm
movdqa  xmm0, [rel scores]
pcmpgtd xmm0, [rel threshold] ; lane i = 0xFFFFFFFF (-1) if scores[i] > threshold[i], else 0
```

Para criar uma comparação de menor que, use `gt` com os operandos trocados: `a < b` == `b > a`.

Repare que a comparação é **com sinal**.
Para fazer uma comparação sem sinal, inverta o bit mais alto dos dois operandos.
Isso pode ser feito com um XOR com uma máscara em que só o bit mais alto está definido.

~~~~exercism/note
Dois truques úteis são:

1. Fazer XOR de um registrador com ele mesmo para produzir todos os bits em zero.
2. Comparar um registrador com ele mesmo para produzir todos os bits em um.

Por exemplo:

```x86asm
pxor    xmm4, xmm4 ; xmm4 = all zeros
pcmpeqd xmm7, xmm7 ; xmm7 = all ones
```

Máscaras de todos os bits em zero e de todos os bits em um são comuns para codificar "tudo falso" e "tudo verdadeiro", respectivamente.
Elas também podem ser usadas para representar o `0` empacotado ou o `-1` empacotado, que são valores sentinela comuns.
Por exemplo, o NUL que marca o fim de uma string é um `0`.
~~~~

### Comparações de ponto flutuante

As lanes de ponto flutuante usam um formato diferente: uma única instrução, `cmpps` (e `cmppd` para lanes de 64 bits), com a condição como um imediato:

```x86asm
movaps xmm0, [rel readings]
cmpps  xmm0, [rel limits], 1 ; condition 1 is "less than": lane i = all ones if readings[i] < limits[i]
```

O NASM também tem pseudo-ops que correspondem ao imediato correto e são mais fáceis de lembrar.
Em todos os casos a seguir, o `x` em `px` pode ser `s` (números de ponto flutuante de 32 bits) ou `d` (números de ponto flutuante de 64 bits):

| pseudo-op    | imediato | comparação             |
|--------------|----------|------------------------|
| `cmpeqpx`    | 0        | a == b                 |
| `cmpltpx`    | 1        | a <  b                 |
| `cmplepx`    | 2        | a <= b                 |
| `cmpunordpx` | 3        | a é NaN ou b é NaN     |
| `cmpneqpx`   | 4        | a != b                 |
| `cmpnltpx`   | 5        | a >= b                 |
| `cmpnlepx`   | 6        | a >  b                 |
| `cmpordpx`   | 7        | nem a nem b é NaN      |

~~~~exercism/caution
O NaN é comparado como não ordenado: ele não é menor, nem igual, nem maior que nada, incluindo ele mesmo.
Os predicados ordenados, como `cmpltps`, dão resultado falso quando um dos operandos é NaN, enquanto os predicados não ordenados dão resultado verdadeiro.
É por isso que `cmpordps` e `cmpunordps` existem, para testar explicitamente se há NaN.
~~~~

## Selecionando com uma máscara

Uma máscara codifica o resultado de uma condição.
Ela pode então ser usada para escolher, lane por lane, entre dois conjuntos de valores de acordo com essa condição.
Pegamos a lane de um valor onde a máscara é verdadeira e de outro onde ela é falsa:

```x86asm
; result = (a AND mask) OR (b AND NOT mask)
movdqa xmm2, xmm0  ; xmm0 holds the mask, keep a copy
pand   xmm2, xmm3  ; xmm2 = a AND mask: lanes of a where mask is true
pandn  xmm0, xmm4  ; xmm0 = NOT mask AND b: lanes of b where mask is false
por    xmm2, xmm0  ; combine the two halves
```

Esse padrão é a forma empacotada da seleção sem desvios.
Todas as lanes são calculadas, e só a máscara decide qual valor sobrevive, sem nenhum `jcc` em lugar algum.

## Blends dedicados

Existem instruções que fazem essa mesma seleção diretamente, lendo um bit por elemento de um registrador de máscara.
Elas são chamadas de instruções **blend**:

| instrução  | elemento    | origem da máscara |
|------------|-------------|-------------------|
| `pblendvb` | byte        | `xmm0` implícito  |
| `blendvps` | lane de 32 bits | `xmm0` implícito |
| `blendvpd` | lane de 64 bits | `xmm0` implícito |

Repare que a primeira instrução segue a sintaxe de inteiros, enquanto as outras duas seguem a sintaxe de ponto flutuante.
No entanto, como essas instruções apenas selecionam bytes brutos, qualquer uma delas pode ser usada tanto com inteiros quanto com ponto flutuante.

Para cada elemento, o blend mantém o destino quando o bit mais alto do elemento correspondente da máscara está zerado, e pega a origem quando ele está definido.
Só esse **bit mais alto** é consultado, e uma máscara de comparação satisfaz isso, já que suas lanes têm todos os bits em um ou todos os bits em zero.
O registrador de máscara é sempre o `xmm0`, que é implícito:

```x86asm
movaps   xmm0, [rel mask]  ; the selecting mask must be in xmm0
movaps   xmm1, [rel b]     ; destination: kept where the mask bit is clear
blendvps xmm1, [rel a]     ; source: taken where the mask bit is set
```

Também é possível usar `pblendvb` para selecionar lanes de uma máscara de comparação de qualquer outro tamanho.
Como todos os bytes de uma lane verdadeira têm todos os bits em um, `pblendvb` seleciona todos eles.

~~~~exercism/note
Todas essas instruções acrescentam um `v` depois da operação que realizam (`blend`).
Esse `v` vem de _variable_, porque a seleção não é estática: ela depende de um registrador.

Existem também variantes sem o `v`, que selecionam de acordo com um imediato.
Elas seguem o mesmo padrão, selecionando uma lane `i` se o bit `i` do imediato estiver definido.
~~~~

## Da máscara de volta ao escalar

Apesar de poderoso, o código SIMD não tem boa parte da flexibilidade do código escalar.
Em muitas situações, é preciso sair de um registrador empacotado e voltar ao mundo das instruções escalares.

A família de instruções `movmsk` serve de ponte entre os dois mundos.
Essas instruções extraem o **bit mais alto** de cada lane para um registrador de uso geral:

| instrução  | coleta                          | largura do resultado |
|------------|---------------------------------|----------------------|
| `pmovmskb` | o bit mais alto de cada um dos 16 bytes | 16 bits      |
| `movmskps` | o bit mais alto de cada um dos 4 dwords | 4 bits       |
| `movmskpd` | o bit mais alto de cada um dos 2 qwords | 2 bits       |

Se usadas depois de uma comparação, cada bit definido representa uma lane "verdadeira" e cada bit zerado, uma lane "falsa".
Esse resultado pode então ser manipulado como de costume com instruções escalares.
Por exemplo, um `popcnt` conta o número de correspondências, e `tzcnt` encontra a primeira.

O registrador de uso geral pode ter 32 ou 64 bits de largura.

## Testando um vetor inteiro

Existe também uma variante empacotada da instrução escalar `test`: `ptest`.

Ela é parecida com a sua equivalente escalar: realiza uma operação AND entre dois operandos, sem modificá-los.
Diferente de `test`, `ptest` também realiza uma operação ANDN, negando o primeiro operando.

Assim, dá para pensar no `ptest` como uma versão não destrutiva de `pand` e `pandn` que define flags de acordo com o resultado.
Mais ou menos como essas duas instruções, `ptest` trata todo o registrador SIMD como uma única lane e, por isso, não leva prefixo de tamanho.

Se o resultado de uma operação AND for `0`, o `ZF` é definido, e se a operação ANDN resultar em `0`, é o `CF` que é definido.
Isso significa que dá para usar `ptest` para verificar tanto uma máscara de todos os bits em um quanto uma de todos os bits em zero:

1. Usar `ptest` com um registrador ele mesmo define o `ZF` só se o registrador tiver todos os bits em zero.
   Isso imita o truque escalar comum de usar `test` com um registrador ele mesmo para verificar se ele é `0`.
2. Usar `ptest` com um registrador e uma máscara de todos os bits em um define o `CF` só se o registrador tiver todos os bits em um.
   Além disso, define o `ZF` só se o registrador tiver todos os bits em zero, o que permite verificar as duas máscaras de uma vez.

```x86asm
pxor  xmm0, xmm0   ; xmm0 = all zeros
ptest xmm0, xmm0   ; xmm0 AND xmm0 == 0 => ZF is set
                   ; (NOT xmm0) AND xmm0 == 0 => CF is set

; Using ptest on a register with itself makes ZF set only if the register is all zeros

pcmpeqb xmm1, xmm1 ; xmm1 = all ones
ptest   xmm0, xmm1 ; xmm0 AND xmm1 == 0 => ZF is set
                   ; (NOT xmm0) AND xmm1 != 0 => CF is cleared

pcmpeqb xmm3, xmm3 ; xmm3 = all ones
ptest   xmm3, xmm1 ; xmm3 AND xmm1 != 0 => ZF is cleared
                   ; (NOT xmm3) AND xmm1 == 0 => CF is set

mov eax, -1
movd  xmm2, eax    ; xmm2 = {-1, 0, 0, 0}
ptest xmm2, xmm1   ; xmm2 AND xmm1 != 0 => ZF is cleared
                   ; (NOT xmm2) AND xmm1 != 0 => CF is cleared

; After using ptest on a register with an all-ones mask, ZF is only set if the register is all zeros.
; CF may be:
; 1. cleared, if the register is all zeros or is partially set
; 2. set, if the register is all ones
```

O resultado de um `ptest` pode ser usado para desviar ou em instruções sem desvios como `setcc` ou `cmovcc`, como de costume.

## AVX e além

O AVX dá às comparações, aos blends e ao `ptest` uma forma com prefixo `v` em registradores mais largos.

O blend variável muda de forma.
A máscara já não é o `xmm0` implícito, mas um quarto operando explícito:

```x86asm
vpcmpgtd  ymm0, ymm1, ymm2       ; eight 32-bit lanes compared at once
vblendvps ymm0, ymm1, ymm2, ymm3 ; ymm3 is the mask, named explicitly
vptest    ymm0, ymm0
```

As extensões AVX-512 mudam o modelo de forma mais profunda.

Primeiro, elas acrescentam uma nova classe de registradores SIMD de 64 bytes, chamados `zmm`.
Eles expandem os registradores `ymm` correspondentes, do mesmo jeito que os registradores `ymm` expandem os registradores `xmm`.

Segundo, essas extensões também criam toda uma nova classe de **registradores opmask**, de `k0` a `k7`, cujo principal propósito é servir de máscara para instruções SIMD.
As comparações já não escrevem em vetores, mas em um desses novos registradores.
Eles também podem ser usados diretamente em muitas instruções como predicados, com uma máscara de escrita `{k}`, selecionando lanes _diretamente_:

```x86asm
vpcmpgtd  k1, zmm0, zmm1         ; k1 gets one bit per lane
vmovdqa32 zmm2{k1}, zmm3         ; copy only the lanes whose bits are set in k1
```

Por fim, há novas instruções para operar sobre esses novos registradores, incluindo copiá-los para registradores de uso geral.
Isso torna as instruções `movmsk` desnecessárias, e não há suporte para instruções `movmsk` em registradores `zmm`.

Essas extensões são mencionadas por uma questão de completude.
Os exercícios desta trilha usam as formas SSE.

# Sobre

Assembly escrito à mão é cheio de repetição.
A mesma sequência curta de instruções aparece de novo e de novo, com pouca variação, e há poucas abstrações para reduzir o código repetitivo.
Além disso, programar em assembly exige gerenciar valores sem semântica óbvia.
Não existem parâmetros nomeados, e a maior parte dos detalhes da máquina por trás disso precisa ser tratada manualmente por quem programa.

O NASM, o montador usado pela trilha, oferece algumas ferramentas que podem ajudar quem programa com esses dois problemas.
Essas ferramentas rodam em _tempo de montagem_, antes de qualquer instrução chegar ao processador.
Elas orientam o montador sobre como reescrever o texto-fonte antes mesmo de ele ser traduzido para código de máquina.

A mais importante dessas ferramentas são as **macros**, que podem ser vistas como uma receita para o montador.
Elas são expandidas no local onde são usadas, como se o código tivesse sido escrito ali à mão.

[Macros][macro] podem receber uma série de tokens literais como parâmetros, o que as torna reutilizáveis em contextos diferentes.
No entanto, elas não são funções: não há `call`, nem `ret`, nem transferência de controle para outro ponto do código.

## Macros de uma linha

A definição mais simples dá um nome a um valor ou a uma expressão curta com `%define`:

```x86asm
%define WIDTH 8
%define BUFFER_SIZE (WIDTH * 16)
```

Toda ocorrência posterior de `WIDTH` é substituída por `8` antes da montagem.
A substituição é textual, então o nome é trocado em qualquer lugar em que apareça, seja em um operando, seja dentro de outra definição.

~~~~exercism/note
Para _constantes_ numéricas, prefira `equ` em vez de `%define`.

Uma macro de uma linha declarada com `%define` só é expandida quando usada, e pode ser reatribuída ou indefinida.
Já uma constante `equ` é avaliada no ponto da definição e nunca é modificada.
~~~~

Um `%define` também pode receber parâmetros _nomeados_, comportando-se como uma pequena função inline:

```x86asm
%define double(x) ((x) + (x))

    mov eax, double(WIDTH)   ; assembled as mov eax, ((8) + (8))
```

~~~~exercism/caution
Coloque entre parênteses tanto o corpo inteiro quanto cada parâmetro.
Com `%define square(x) x*x`, a chamada `square(1+1)` expande para `1+1*1+1`, que é `3`.
Escrito como `%define square(x) ((x)*(x))`, a mesma chamada expande para `((1+1)*(1+1))`, que é `4`.
~~~~

Nomes definidos com `%define` diferenciam maiúsculas de minúsculas.
A variante `%idefine` torna o nome insensível a maiúsculas e minúsculas, caso isso seja desejado.

Macros de uma linha são úteis para dar significado a várias partes do código.
Se usadas com cuidado, elas melhoram a legibilidade e reduzem a chance de erros de digitação.
Por exemplo, um registrador que tem um propósito específico dentro de uma função pode ser definido pelo seu propósito:

```x86asm
%define COUNTER rcx
    ...
.loop:
    ...
    dec COUNTER
    jnz .loop
    ...
```

## Macros de várias linhas

Uma sequência inteira de código, com qualquer número de linhas, é capturada com `%macro` e fechada por `%endmacro`.
Um número depois do nome indica quantos argumentos a macro recebe, e pode ser zero.
Quando argumentos são passados, eles são separados por vírgula (`,`):

```x86asm
%macro example_macro 0
...
%endmacro
```

Os argumentos em macros de várias linhas não têm nome.
Eles são referenciados como `%1`, `%2` e assim por diante, na ordem em que são passados:

```x86asm
; Multiplies two values, returning the result in the first argument
%macro mult_two 2        ; %1 = accumulator, %2 = value
    imul %1, %2
%endmacro

    mult_two eax, ecx    ; multiplies eax and ecx and returns the result into eax
    mult_two r8, r9      ; multiplies r8 and r9 and returns the result into r8
```

Repare que os argumentos precisam ser sintaxe válida para as operações feitas no corpo da macro.
Aqui, `mult_two eax, ecx` e `mult_two r8, r9` montam, mas `mult_two eax, cl` não montaria, já que `imul eax, cl` não é definido.

As macros também podem receber um número arbitrário de argumentos.
Isso é feito com a notação `n-*`, em que `n` é o número mínimo de argumentos:

```x86asm
%macro multi_args 4-*
    ; this macro may take 4, 5, 6, ... arguments but not just 1 or 2 or 3
%endmacro
```

Em uma macro de várias linhas, `%0` indica o _número_ de argumentos da macro.
Isso é especialmente útil em macros que podem receber um número arbitrário de argumentos.

### Rótulos dentro de uma macro

Uma macro que define um rótulo comum quebra no momento em que é usada duas vezes, porque o rótulo também seria definido duas vezes.
Para usar rótulos dentro de uma macro que pode ser chamada mais de uma vez, é preciso prefixar esse rótulo com `%%`.
Isso instrui o montador a dar a esse rótulo um nome diferente e único a cada expansão:

```x86asm
; clobbers rcx
%macro clear_n 2         ; %1 = base address, %2 = count of dwords to clear
    xor ecx, ecx
%%loop:
    mov dword [%1 + rcx*4], 0
    inc ecx
    cmp ecx, %2          ; %2 is compared with ecx: it is an immediate or a 32-bit operand
    jb %%loop
%endmacro

    clear_n rdi, 4       ; gets its own %%loop
    clear_n rsi, 8       ; a different %%loop, no clash
```

## Repetição em tempo de montagem

É possível repetir um bloco de código de uma linha usando [`times`][times].
Isso é especialmente útil ao declarar valores repetidos na memória:

```x86asm
section .data
negative_block: times 16 db -1
; this assembles to 16 db -1 in sequence, i.e., an array of 16 bytes, all equal to -1
```

Para repetir código de várias linhas, podemos usar `%rep`:

```x86asm
%rep 2          ; number of repetitions: 2
    add rcx, 32
    mov dword [rsi + rcx], 0
%endrep
```

Repare que o número de repetições é indicado logo depois de `%rep`, e há um `%endrep` para fechar o bloco repetido.

É comum usar um contador de tempo de montagem dentro de um bloco `%rep`, assim como um laço em tempo de execução usa um contador.
Embora uma constante inteira de tempo de montagem possa ser declarada com `equ`, como já vimos, para _variáveis_ inteiras de tempo de montagem usamos `%assign`.
Diferente de `%define`, o `%assign` é avaliado imediatamente para um número e pode ser reatribuído:

```x86asm
    xor eax, eax
%assign i 0
%rep 4
    add eax, i           ; add 0, then 1, then 2, then 3
%assign i i + 1
%endrep
```

Depois que o pré-processador roda, o laço desaparece e restam quatro instruções `add`, com os imediatos `0`, `1`, `2` e `3` já embutidos.
Isso é o desenrolar de laço feito pelo montador: nenhum registrador contador, nenhum desvio, apenas código em linha reta.

Outro uso comum de `%rep` é lidar com os argumentos de uma macro que pode receber qualquer número deles.
Nesse caso, `%rep` costuma vir acompanhado de `%rotate`, que rotaciona os argumentos de uma macro, de modo que o segundo argumento se torne o primeiro.
Aplicações repetidas de `%rotate` fazem o terceiro argumento, depois o quarto, e assim por diante, virar o primeiro, garantindo que cada argumento seja tratado na sua vez:

```x86asm
%macro may_args 1-*
    %rep %0 ; repeats for as many times as the number of arguments
        ... ; do something
    %rotate 1
    %endrep
%endmacro
```

## Montagem condicional

Há vários condicionais disponíveis para o [pré-processador][preprocessor].
Eles selecionam entre vários caminhos diferentes, expandindo seu corpo no lugar, mas só quando a condição é verdadeira.

`%if` ... `%elif` ... `%else` ... `%endif` selecionam um ramo a partir de um teste numérico:

```x86asm
%if WIDTH > 4
    mov eax, 2
%elif WIDTH > 2
    mov eax, 1
%else
    mov eax, 0
%endif
```

`%ifdef` e `%ifndef` são parecidos, mas testam se um nome foi definido.
Por exemplo, eles podem ser usados para garantir que o conteúdo de um arquivo seja incluído apenas uma vez, mesmo quando mais de um arquivo-fonte o puxa:

```x86asm
%ifndef MY_FILE
%define MY_FILE
... ; whole file here
%endif
```

Você pode ter reparado que, no fim de todo arquivo `.asm` desta trilha, existe este trecho de código:

```x86asm
%ifidn __OUTPUT_FORMAT__,elf64
section .note.GNU-stack noalloc noexec nowrite progbits
%endif
```

`%ifidn` compara dois trechos de texto buscando uma correspondência exata.
O `__OUTPUT_FORMAT__`, embutido, expande para o formato de saída atual, então esse código verifica se o formato de saída é `elf64`, que é o formato usado por sistemas Linux.
Se for, uma nota é adicionada ao arquivo-objeto declarando as permissões que a pilha deve ter, uma medida de segurança comum.
Se não for, nada muda.

## Estruturas

Acessar um campo de um registro na memória significa somar o deslocamento em bytes do campo a um endereço-base.
Escrever esses deslocamentos como números crus é propenso a erros e esconde o significado deles.
[`struc`][struc] e `endstruc` nomeiam um layout, transformando cada campo em um deslocamento simbólico calculado em tempo de montagem.

Dentro do bloco, as diretivas de reserva `resb`, `resw`, `resd` e `resq` reservam um ou mais bytes, words, doublewords ou quadwords.
Colocar um `.` no início de cada campo mantém o nome dele restrito à estrutura:

```x86asm
struc thread
    .color:   resd 1     ; offset 0
    .tension: resq 1     ; offset 4 : 0 + 4 (the size of a dword)
    .name:    resb 16    ; offset 12: 4 + 8 (the size of a qword)
endstruc
```

Agora cada nome de campo representa seu deslocamento, então `thread.color` é `0`, `thread.tension` é `4` e `thread.name` é `12`.
O NASM também define `<struc>_size` como o total, em que `<struc>` é o nome do `struc`.
Por exemplo, aqui `thread_size` seria `4 + 8 + 16 = 28`.

Um campo é acessado somando seu deslocamento a um registrador-base, e `thread_size` é o passo de um registro para o próximo:

```x86asm
    mov [rdi + thread.color], eax        ; write the color field
    mov ecx, [rdi + thread.tension]      ; read the tension field
    add rdi, thread_size                 ; advance to the next record
```

Um `struc` só descreve um formato, não aloca memória por conta própria.
Para criar uma instância inicializada, você pode usar `istruc ... iend` depois de algum rótulo.
Dentro de uma instância, `at` coloca um valor em um campo nomeado:

```x86asm
warp_thread:
istruc thread
    at thread.color,   dd 0x00FF00
    at thread.tension, dq 7
    at thread.name,    db "warp", 0
iend
```

Repare que `thread.name` é inicializado com `"warp", 0`, que ocupa apenas 5 bytes.
Os outros 11 bytes reservados para ele no `struc` são preenchidos automaticamente com zeros pelo `iend`, que completa a instância até `thread_size` com `0`.

Um `struc` é apenas açúcar sintático para memória que também podemos declarar manualmente.
Por exemplo, o código acima é equivalente ao seguinte, em que `times 11 db 0` garante que 16 bytes sejam alocados no fim:

```x86asm
warp_thread:
    dd 0x00FF00
    dq 7
    db "warp", 0
    times 11 db 0
```

## Dividindo em arquivos

As macros costumam ficar em um arquivo próprio e são puxadas para cada código-fonte que precisa delas com `%include`:

```x86asm
%include "patterns.mac"
```

O arquivo indicado é inserido literalmente nesse ponto, antes da montagem, exatamente como se o conteúdo dele tivesse sido digitado ali.
Isso mantém as definições em um só lugar e permite que vários arquivos-fonte as compartilhem.

Se o arquivo de macros puder ser montado de forma independente, ele deve ter a extensão `.asm`.
Repare que as macros não têm linkage.
Mesmo que o arquivo de macros seja montado, suas macros só são visíveis para outro arquivo que o inclua com `%include`.

Caso contrário, um arquivo apenas de `%include` pode ter qualquer extensão.
Usar `.asm` ou `.mac` é uma convenção comum.

# Estratégia de merge

Os mantenedores da trilha de Rust [decidiram](https://github.com/exercism/v3/discussions/1725#discussion-7438) registrar nossa estratégia de merge para comunicar expectativas e incentivar contribuições de qualidade.

## Princípios gerais

- nos esforçamos para aceitar _todas_ as contribuições
  - Vamos levar as contribuições a um alto padrão de qualidade por meio de revisões colaborativas e iterativas.
  - Adotamos uma abordagem de merge pessimista. Pense nas revisões dos mantenedores como o feedback do compilador Rust. A quantidade de feedback pode parecer esmagadora e frustrante. Mas vamos trabalhar com você para levar tudo até a linha de chegada! Então continue com o bom trabalho.
- Todo pull request precisa ter ao menos uma "Aprovação", e nenhuma "Solicitação de alterações", de um mantenedor da trilha antes de poder receber merge.
- Nenhum mantenedor pode aprovar o próprio pull request.

## Fluxo de trabalho de pull request

### Definições

| Termo               |                                                                                               Significado |
| ------------------ | ----------------------------------------------------------------------------------------------------: |
| Contribuidor        |                                                                     Qualquer pessoa que envie um pull request. |
| Mantenedor          |         Qualquer pessoa que pertença à [equipe @exercism/rust](https://github.com/orgs/exercism/teams/rust). |
| branch de desenvolvimento | O branch de desenvolvimento padrão do repositório [v3](https://github.com/exercism/v3). Atualmente `master`. |

### O fluxo de trabalho

1. Os contribuidores começam abrindo um [rascunho](https://github.blog/2019-02-14-introducing-draft-pull-requests/) ou um pull request completo com suas alterações
   1. Usar o recurso de rascunho sinaliza que o trabalho está pronto para uma revisão de alto nível, mas que os detalhes podem ainda estar não implementados, incompletos ou errados.
   1. Depois de um número indeterminado de iterações dos passos 2 e 3, o contribuidor marca o pull request como pronto para revisão.
1. Outro mantenedor deve revisar a contribuição e fornecer feedback.
1. O contribuidor deve tratar _todo_ o feedback dos mantenedores como parte do pull request.
   1. Os mantenedores devem considerar usar o recurso de sugestões do GitHub para mudanças pequenas ou simples e diretas.
   1. Discordar é bem-vindo quando um contribuidor acredita que está certo e um mantenedor está errado sobre um item do feedback. "Tratar" um feedback não é sinônimo de implementá-lo cegamente.
1. O mantenedor deve revisar o feedback e então:
   1. aprovar
   1. solicitar mudanças adicionais. Neste ponto, o processo volta ao passo 3.
1. Após a aprovação, um mantenedor deve fazer o merge do pull request.
   1. Os mantenedores devem fazer o merge dos próprios pull requests. Como os contribuidores não são necessariamente mantenedores, um mantenedor precisa realizar esta etapa.

## Merge otimista

Os mantenedores da trilha de Rust decidiram adotar o merge otimista temporariamente para acelerar o desenvolvimento da trilha v3.

- Isso se aplica apenas ao repositório v3
- Voltaremos a uma estratégia de merge pessimista quando lançarmos a v3 em produção.
- Vamos aprovar e fazer merge de trabalhos incompletos
  - Se compilar, mantemos.
  - Preferimos a velocidade de iteração aos detalhes mais finos de um design de software correto.
- Todo pull request precisa ter ao menos uma "Aprovação" de um mantenedor da trilha antes de poder receber merge.

# Geradores de testes

Os geradores de testes permitem que as trilhas gerem testes automaticamente, sem que precisemos escrevê-los à mão. Cada gerador de testes lê os `canonical data` do exercício, que definem o nome do teste, suas entradas e suas saídas. Você pode ler mais sobre a abordagem do Exercism para suítes de testes [aqui](https://github.com/exercism/docs/blob/master/language-tracks/exercises/anatomy/test-suites.md).

Gerar testes automaticamente elimina qualquer tipo de erro humano na hora de criar testes. Queremos que os testes estejam corretos em relação aos seus dados canônicos. A geração de testes também torna muito mais fácil manter os testes atualizados. Conforme os dados canônicos mudam, os testes são atualizados automaticamente quando o gerador daquele teste é executado.

Um exemplo de arquivo de dados canônicos pode ser encontrado [aqui](https://github.com/exercism/problem-specifications/blob/master/exercises/bob/canonical-data.json)

## Termos comuns

Ao examinar os dados canônicos e o código-fonte do gerador, usamos bastante terminologia comum. Esta lista esclarece o que cada item representa.

* Dados canônicos - Representam toda a suíte de testes.
* Caso de dados canônicos - A representação de um único caso de teste.
* Descrição - O nome do teste.
* Propriedade - O método a ser chamado ao executar o teste.
* Entrada - A entrada do caso de teste.
* Esperado - O valor esperado ao executar o caso de teste.

## Adicionando um gerador simples

Adicionar um gerador de testes é simples. Basta adicionar uma classe ao arquivo `Generators.fs`, na pasta `generators`, com o nome do exercício (em PascalCase), e estender a classe abstrata `GeneratorExercise`.

Um exemplo de gerador simples é o exercício Bob. O código-fonte está abaixo, mas você também pode vê-lo no repositório [aqui](https://github.com/exercism/fsharp/blob/master/generators/Generators.fs#L174).

```fsharp
type Bob() =
    inherit GeneratorExercise()
```

Este é um gerador totalmente funcional: nenhum outro código precisa ser escrito. No entanto, essa simplicidade vem do fato de que a suíte de testes e o próprio programa são relativamente triviais.

## Adicionando um gerador complexo

Para muitos geradores, o comportamento padrão da classe `GeneratorExercise` já basta. No entanto, para geradores mais _complexos_, é possível sobrescrever um ou mais de seus métodos virtuais:

### Método: RenderInput

Renderiza a entrada de um método de teste.

#### Exemplo

O gerador `Gigasecond` renderiza o valor de entrada como um valor `DateTime` (entre parênteses):

```fsharp
override __.RenderInput (_, _, value) =
    DateTime.Parse(string value, CultureInfo.InvariantCulture)
    |> DateTime.renderParenthesized
```

Vale notar que você pode usar o campo `key` para personalizar a saída apenas de campos de entrada específicos. O gerador `Yacht` faz isso:

```fsharp
override __.RenderInput (canonicalDataCase, key, value) =
    match key with
    | "category" -> Obj.renderEnum "Category" value
    | _ -> base.RenderInput (canonicalDataCase, key, value)
```

### Método: RenderExpected

Renderiza o valor esperado de um método de teste.

#### Exemplo

O gerador `Connect` renderiza o valor esperado como um valor `Option<T>`:

```fsharp
override __.RenderExpected (canonicalDataCase, key, value) =
    match string value with
    | "O" -> "(Some White)"
    | "X" -> "(Some Black)"
    | _   -> "None"
```

### Método: RenderSut

Renderiza o System Under Test (SUT). Esse é o valor real que é verificado em relação ao valor esperado.

#### Exemplo

O gerador `RunLengthEncoding` tem um caso de teste em que verifica que codificar e depois decodificar a entrada resulta no mesmo valor. O método `RenderSut` é sobrescrito para converter o que seria uma única chamada a uma função `consistency` inexistente em uma cadeia de chamadas `encode |> decode`:

```fsharp
override this.RenderSut canonicalDataCase =
    match canonicalDataCase.Property with
    | "consistency" ->
        let parameters = this.RenderSutParameters canonicalDataCase |> String.concat " "
        sprintf "%s |> encode |> decode" parameters
    | _ ->
        base.RenderSut canonicalDataCase
```

### Método: RenderArrange

Renderiza a parte arrange do método de teste. Nessa parte, o SUT é criado.

O comportamento padrão geralmente é o que você quer. Só em circunstâncias muito especiais você vai querer mudar isso.

Observação: esse método retorna um `string list`, em que cada `string` corresponde a uma única linha renderizada no arquivo de teste.

### Método: RenderAssert

Renderiza a parte assert do método de teste. Nessa parte, a asserção é feita para verificar o SUT em relação ao valor esperado.

O comportamento padrão geralmente é o que você quer. Só em circunstâncias muito especiais você vai querer mudar isso.

Observação: esse método retorna um `string list`, em que cada `string` corresponde a uma única linha renderizada no arquivo de teste.

### Método: RenderSetup

Renderiza quaisquer métodos utilitários/de setup adicionais. Isso pode ser usado para definir métodos auxiliares que podem ser usados nos métodos de teste.

O código de setup é adicionado _antes_ dos métodos de teste, para permitir que os métodos de setup sejam usados nos métodos de teste.

Observação: esse método retorna um `string list`, em que cada `string` corresponde a uma única linha renderizada no arquivo de teste.

#### Exemplo

O gerador `Zipper` adiciona dois métodos auxiliares que são usados nos métodos de teste para remover um pouco do código tedioso e repetitivo:

```fsharp
override __.RenderSetup _ =
    [ "let subTree value left right = Some (tree value left right)"
      "let leaf value = subTree value None None" ]
    |> String.concat "\n"
```

### Método: RenderValue

Renderiza um único valor (que é usado para renderizar parâmetros de entrada, o valor esperado e o SUT).

### Exemplo

O gerador `ComplexNumbers` renderiza valores diferentes com base no tipo do valor:

```fsharp
override __.PropertiesWithIdentifier canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Array -> ["sut"]
    | _ -> base.PropertiesWithIdentifier canonicalDataCase
```

### Método: MapCanonicalDataCase

Mapeia o caso de dados canônicos. Isso pode ser útil se você quiser adicionar ou remover propriedades.

O comportamento padrão geralmente é o que você quer. Só em circunstâncias muito especiais você vai querer mudar isso.

#### Exemplo

O gerador `ScaleGenerator` usa o mapeamento do caso de dados canônicos para adicionar uma propriedade ausente como um valor `null` (o que facilita o processamento mais adiante):

```fsharp
override __.MapCanonicalDataCase canonicalDataCase =
    let input = canonicalDataCase.Input
    match Map.tryFind "intervals" input with
    | Some _ -> canonicalDataCase
    | None   -> { canonicalDataCase with Input = Map.add "intervals" null input }
```

### Método: PropertiesUsedAsSutParameter

Especifica quais propriedades devem ser usadas como parâmetros do SUT.

O comportamento padrão geralmente é o que você quer. Só em circunstâncias muito especiais você vai querer mudar isso.

#### Exemplo

O `RailFenceCipher` define explicitamente as propriedades usadas como parâmetros do SUT para mudar a ordem em que elas são passadas:

```fsharp
override __.PropertiesUsedAsSutParameter _ = ["rails"; "msg"]
```

### Método: PropertiesWithIdentifier

Especifica quais propriedades devem ter um identificador atribuído a elas. Se uma propriedade estiver nessa lista, seu valor será atribuído em uma linha separada, ao seu próprio identificador.

#### Exemplo

O gerador `Transpose` optou por usar identificadores para todas as propriedades:

```fsharp
override this.PropertiesWithIdentifier canonicalDataCase = this.Properties canonicalDataCase
```

### Método: IdentifierTypeAnnotation

Em alguns casos, você quer que um identificador tenha um tipo explícito. Um caso de uso comum é quando um valor é uma lista vazia. Nesses casos, o FsUnit precisa de uma anotação de tipo para executar a asserção com sucesso.

#### Exemplo

O gerador `Minesweeper` adiciona uma anotação de tipo `string list` para valores vazios:

```fsharp
override __.IdentifierTypeAnnotation (_, _, value) =
    match Seq.isEmpty value with
    | true  -> Some "string list"
    | false -> None
```

### Método: AdditionalNamespaces

Retorna uma lista de namespaces adicionais a serem abertos no arquivo de teste.

#### Exemplo

O gerador `Gigasecond` trabalha com instâncias de `DateTime` e, por isso, adiciona seu namespace à lista de namespaces adicionais:

```fsharp
override __.AdditionalNamespaces = [typeof<DateTime>.Namespace]
```

### Método: AssertTemplate

O template de asserção a ser usado. Você encontra a lista completa de templates de asserção em `generators/Templates/_Assert*.liquid`

#### Exemplo

O gerador `RationalNumbers` usa o template `"AssertEqualWithin"` para permitir verificar a igualdade de doubles com uma tolerância específica:

```fsharp
override __.AssertTemplate canonicalDataCase =
    match canonicalDataCase.Expected.Type with
    | JTokenType.Float -> "AssertEqualWithin"
    | _ -> base.AssertTemplate(canonicalDataCase)
```

### Método: TestFileFormat

O formato do arquivo de teste: um módulo ou uma classe.

O comportamento padrão é praticamente sempre o que você quer. Só em casos extremamente raros você vai querer mudar isso.

#### Exemplo

O gerador `Grep` se define como uma classe de teste para permitir o uso de métodos de setup e teardown:

```fsharp
override __.TestFileFormat = TestFileFormat.Class
```

### Método: TestMethodName

Especifica o nome do método de teste.

O comportamento padrão geralmente é o que você quer. Só em circunstâncias muito especiais você vai querer mudar isso.

#### Exemplo

O gerador `Zipper` faz uma pequena limpeza no nome do método de teste:

```fsharp
override __.RenderTestMethodName canonicalDataCase =
    let testMethodName = base.RenderTestMethodName canonicalDataCase
    testMethodName.Replace("Set_", "Set ")
```

### Método: UseFullMethodName

Indica se o nome do método de teste usado deve usar o caminho completo, o que significa que, para casos de teste aninhados, ele adiciona a descrição do(s) caso(s) pai(s) antes do nome do método de teste.

O comportamento padrão geralmente é o que você quer. Só em casos em que, de outra forma, haveria vários métodos de teste com o mesmo nome você vai querer mudar isso.

#### Método: Signature

O gerador `KindergartenGarden` usa nomes completos de métodos para evitar conflitos entre nomes de métodos de teste:

```fsharp
override __.UseFullMethodName _ = true
```

### Método: SkipTestMethod

Indica se o método de teste deve ser marcado com a propriedade `Skip = true`.

O comportamento padrão é praticamente sempre o que você quer. Só em casos extremamente raros você vai querer mudar isso.

#### Método: Signature

O exercício `Markdown` é um exercício de refatoração e, como tal, todos os seus testes já devem estar em um estado válido. Por isso, ele não adiciona a propriedade `Skip` a nenhum de seus métodos de teste:

```fsharp
override __.SkipTestMethod (_, _) = false
```

## Atualizando arquivos existentes

É possível que um exercício existente não corresponda aos dados canônicos. Não tem problema atualizar o stub do exercício e/ou o exemplo do exercício para seguir os dados canônicos!

Além disso, se você encontrar um problema em um dos geradores ou suítes de testes existentes, basta abrir o gerador que você quer atualizar, fazer suas mudanças e depois executar os geradores.

## Executando os geradores

Este repositório é codificado com [.NET Core 2.x](https://www.microsoft.com/net/core). Para executar os geradores, tudo o que você precisa fazer é rodar o seguinte comando no diretório generators:

`dotnet run`

Esse comando pega todos os geradores de exercícios que estão definidos e gera todos os casos de teste de cada exercício. Usamos reflexão para obter todos os exercícios, então, se você estiver adicionando um teste novo, ele será incluído automaticamente ao executar o gerador.

Se você só precisa executar um único gerador, pode fazer isso com o seguinte comando:

`dotnet run -e <exercise>`

Depois que o gerador for executado, você pode ver a saída da sua geração navegando até o arquivo de teste daquele exercício. Como exemplo, a suíte de testes do exercício Bob pode ser encontrada em:

`exercises/bob/BobTests.fs`

## Enviando um gerador

Se você estiver satisfeito com a saída do seu gerador, adoraríamos que você enviasse um pull request! Inclua seu gerador, a suíte de testes atualizada e quaisquer outros arquivos correspondentes que você tenha mudado.

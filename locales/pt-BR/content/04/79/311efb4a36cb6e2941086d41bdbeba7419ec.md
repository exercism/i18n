# Introdução

## A interface de erro

O tratamento de erros **não** é feito com exceções em Go.
Em vez disso, erros são _valores_ comuns de tipos que implementam a interface `error` embutida.
A interface `error` é bastante enxuta.
Ela contém apenas um método, `Error()`, que retorna a mensagem de erro como uma string.

```go
type error interface {
  Error() string
}
```

Sempre que você define uma função em que um erro pode acontecer durante a execução e precisa chegar até quem chamou, você precisa incluir `error` como um dos tipos de retorno.
Se a função tem vários valores de retorno, por convenção `error` é sempre o último.

```go
func DoSomething() (int, error) {
  // ...
}
```

## Criando e retornando um erro simples

Você não precisa implementar a interface de erro por conta própria o tempo todo.
Para criar um erro simples, você pode usar a função `errors.New()`, que faz parte do pacote `errors` da biblioteca padrão.
A única coisa que você precisa passar é a mensagem de erro como uma string, e `errors.New()` se encarrega de criar um valor que contém a sua mensagem e implementa a interface `error`.

Se a função retorna um erro, é uma boa prática retornar o valor zero para todos os outros parâmetros de retorno:

```go
func DoSomething() (SomeStruct, int, error) {
  // ...
  return SomeStruct{}, 0, errors.New("failed to calculate result")
}
```

~~~~exercism/caution
Você não deve presumir que todas as funções retornam valores zero para os outros valores de retorno quando há um erro.
A melhor prática é presumir que não é seguro usar nenhum dos outros valores de retorno se ocorreu um erro.
As únicas exceções são os casos em que a documentação afirma claramente que os outros valores de retorno fazem sentido em caso de erro.
~~~~

Se você quiser usar um erro simples como esse em vários lugares, declare uma variável para o erro em vez de usar `errors.New` na própria linha.
Por convenção, o nome da variável deve começar com `Err` ou `err` (dependendo se ela é exportada ou não).
Essas variáveis de erro costumam ser chamadas de _erros sentinela_.

```go
import "errors"

var ErrNotFound = errors.New("resource was not found")

func DoSomething() error {
  // ...
  return ErrNotFound
}
```

Retorne `nil` para o erro para sinalizar que não houve erros durante a execução da função:

```go
func Foo() (int, error) {
  return 10, nil
}
```

## Verificação de erros

Se você chama uma função que retorna um erro, é comum guardar o valor do erro em uma variável chamada `err`.
Antes de usar o resultado de fato da função, você precisa verificar que não houve erro.

Para evitar aninhar o "caminho feliz" do seu código, os casos de erro devem ser tratados primeiro.
Podemos usar `==` e `!=` para comparar o erro com `nil`, e sabemos que houve um erro quando `err` não é `nil`.

```go
func processUserFile() error {
	file, err := os.Open("./users.csv")
	if err != nil {
		return err
	}

	// do something with file
}
```

Na maioria das vezes, o erro será retornado para cima na pilha de funções, como mostra o exemplo acima.
Outra forma de tratar o erro é registrá-lo em log e continuar com alguma outra operação.
É uma boa prática retornar ou registrar o erro em log, nunca os dois.

Como a maioria das funções em Go inclui um erro como um dos valores de retorno, você vai ver e usar o padrão `if err != nil` em todo lugar no código Go.

## Tipos de erro personalizados

Se você quer que o seu erro inclua mais informações do que apenas a string da mensagem de erro, você pode criar um tipo de erro personalizado.
Como mencionado antes, tudo que implementa a interface `error` (ou seja, tem um método `Error() string`) pode servir como um erro em Go.

Normalmente, uma struct é usada para criar um tipo de erro personalizado.
Por convenção, os nomes de tipos de erro personalizados devem terminar com `Error`.
Além disso, é melhor definir o método `Error() string` com um receptor de ponteiro; veja este [comentário no Stackoverflow][stackoverflow-errors] para entender o motivo.
Note que isso significa que você precisa retornar um ponteiro para o seu erro personalizado, caso contrário ele não conta como `error`, porque o valor não-ponteiro não fornece o método `Error() string`.

```go
type MyCustomError struct {
  message string
  details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.message, e.details)
}

func someFunction() error {
  // ...
  return &MyCustomError{
    message: "...",
    details: "...",
  }
}
```

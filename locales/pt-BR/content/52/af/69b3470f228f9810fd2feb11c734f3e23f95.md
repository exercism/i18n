# Como contribuir com a trilha Rust do Exercism

No momento, issues e pull requests estão sendo fechados automaticamente.
Publique uma mensagem no [fórum do Exercism][the Exercism forum] para propor mudanças.
Contribuições são muito bem-vindas, desde que sejam coordenadas no fórum.

[the Exercism forum]: https://forum.exercism.org/

## Políticas gerais

- [Código de Conduta](https://exercism.org/code-of-conduct)
- [Diretrizes de PR do Exercism](https://exercism.org/docs/community/being-a-good-community-member/pull-requests).

## Ferramentas

Parte das ferramentas está em scripts bash em `bin/`.
Muito mais está em `rust-tooling/`,
que deve ser a opção preferida para qualquer coisa não trivial.

Há também uma configuração do [`mise`](https://mise.jdx.dev/)
com alguns comandos úteis para interagir com o repositório.
Fique à vontade para ampliá-la.

Se você quiser rodar os testes de CI localmente, `mise run test` já resolve boa parte.

## Excluir testes e adicionar testes personalizados

Ao criar ou atualizar um exercício, você pode decidir excluir determinados testes da geração.
Para isso, defina `include = false` em `.meta/tests.toml`.
Inclua um comentário explicando o motivo da exclusão.

Se você quiser adicionar testes extras específicos da trilha, pode fazer isso em um arquivo `.meta/additional-tests.json`.
Só faça isso se tiver um bom motivo para não enviar esses testes para o upstream.
Um comentário no teste adicional deve responder a estas perguntas:
- Por que o teste não é enviado para o `problem-specifications`, ou seja, por que ele não é útil de modo geral para outras linguagens?
- Por que o teste é válido para a trilha Rust, mesmo assim?

## Criar um novo exercício

Familiarize-se com a [documentação do Exercism sobre exercícios de prática][Exercism documentation about practice exercises].

[Exercism documentation about practice exercises]: https://exercism.org/docs/building/tracks/practice-exercises

Rode `mise run add-exercise` e o sistema vai pedir as informações mínimas
necessárias para gerar o stub do exercício para você.
Depois disso, entre no exercício gerado e preencha todos os placeholders que encontrar.
Isso inclui, principalmente:

- escrever o stub do exercício em `src/lib.rs`
- adicionar uma solução de exemplo em `.meta/example.rs`
- ajustar o `.meta/test_template.tera`

Os testes são gerados usando o motor de templates [Tera].
O template recebe como entrada os dados canônicos do [`problem-specifications`].

Encontre algumas dicas sobre como escrever templates Tera [aqui](#tera-templates).

[Tera]: https://keats.github.io/tera/docs/
[`problem-specifications`]: https://github.com/exercism/problem-specifications/

Muitos aspectos de um exercício implementado corretamente são verificados na CI.
Eu recomendo que, em vez de passar muito tempo estudando e escrevendo
documentação sobre o processo, você _simplesmente faça_.
Se algo quebrar, conserte e adicione um teste ou uma automação
para que isso não aconteça de novo.

Se você estiver criando um exercício de prática do zero,
que não existe no `problem-specifications`,
vai precisar escrever os testes manualmente.
Os testes devem ser ordenados por complexidade crescente,
para que os estudantes possam ativá-los um por um e resolver o exercício com TDD.
Veja [a documentação do Exercism](https://github.com/exercism/legacy-docs/blob/main/language-tracks/exercises/anatomy/test-suites.md)
para mais reflexões sobre como escrever bons testes.

Exceto em circunstâncias extraordinárias,
o arquivo stub deve compilar com `cargo test --no-run`.
Isso nos permite verificar se as assinaturas no arquivo stub
correspondem às assinaturas esperadas pelos testes.
Para isso, use `todo!()` como corpo de cada função.
Se houver um motivo justificado para isso não ser possível,
inclua uma chave `.custom."allowed-to-not-compile"`
no `.meta/config.json` do exercício, com o motivo.

## Atualizar um exercício

Muitos exercícios são derivados do [`problem-specifications`].
Isso inclui a suíte de testes e a documentação voltada ao usuário.
Antes de propor mudanças aqui,
verifique se elas deveriam ser feitas no `problem-specifications`.

Rode `mise run update-exercise` para atualizar um exercício.
Isso delega a maior parte do trabalho ao `configlet sync --update`
e roda o gerador de testes de novo.

Ao atualizar um exercício que ainda não tem um template Tera,
um novo será gerado para você.
Provavelmente você vai precisar ajustá-lo em algum grau.

Encontre algumas dicas sobre como escrever templates Tera [na próxima seção](#tera-templates).

## Templates Tera

A documentação completa dos templates Tera está [aqui][tera-docs].
A seguir estão algumas abordagens que funcionaram para as nossas necessidades específicas.

Provavelmente você vai querer olhar o `canonical-data.json` do exercício para ver como são os seus dados de entrada.
Você pode usar `bin/symlink_problem_specifications.sh` para criar um link simbólico desses dados
no diretório do exercício de verdade. Muito útil!

O nome da propriedade de entrada é diferente em cada exercício.
O template padrão será algo assim:

```txt
let input = {{ test.input | json_encode() }};
```

Você vai precisar adicionar o campo específico de entrada desse exercício, por exemplo:

```txt
let input = {{ test.input.integers | json_encode() }};
```

Alguns exercícios podem ter valores de retorno de erro.
Você pode usar um if-else para renderizar algo diferente,
dependendo da estrutura dos dados:

```txt
let expected = {% if test.expected is object -%}
    None
{%- else -%}
    Some({{ test.expected }})
{%- endif %};
```

Alguns exercícios têm várias funções que precisam ser implementadas
pelo estudante e, portanto, testadas.
Nesse caso, os dados canônicos contêm um campo `property`.
Você pode montar cadeias de if-else com base em `test.property` e renderizar uma função diferente a partir disso.

Alguns exercícios têm os casos de teste organizados em _grupos de teste_.
Seu template vai precisar levar isso em conta.
Em muitos casos, você pode simplesmente achatar a estrutura. (exemplo: [`affine-cipher`](/exercises/practice/affine-cipher/.meta/test_template.tera))
No entanto, às vezes os testes têm a mesma descrição em grupos diferentes, o que gera conflitos de nomes quando a estrutura é achatada.
Nesse caso, você pode usar a descrição do grupo para organizar os testes em módulos. (exemplo: [`forth`](/exercises/practice/forth/.meta/test_template.tera))

Existem alguns filtros Tera personalizados em [`rust-tooling`](/rust-tooling/generate/src/custom_filters.rs).
Aqui está a lista, que espero estar atualizada:
- `to_hex` formata inteiros em hexadecimal
- `make_ident` transforma uma string arbitrária em um identificador Rust decente.
   Muito útil para gerar nomes de funções a partir das descrições dos testes.
- `fmt_num` formata literais numéricos (insere `_` a cada três dígitos)

Fique à vontade para adicionar os seus na crate `rust-tooling`.
Espero que você lembre de atualizar a lista aqui também. 🙂

Para um exemplo bem mais complicado, dê uma olhada no template de teste do `triangle`.
Ele organiza os casos de teste em módulos e detecta dinamicamente quais testes colocar atrás de feature gates.
Esse exercício também reimplementa alguns casos de teste do upstream em `additional-tests.json`, para acrescentar a eles mais informações necessárias para gerar bons testes.

[tera-docs]: https://keats.github.io/tera/docs/#templates

## Syllabus

O syllabus está desativado no momento por causa da baixa qualidade.
veja [este post no fórum](https://forum.exercism.org/t/feeling-lost-and-frustrated-in-rust/4882)
para entender um pouco do contexto dessa decisão.

Criar um syllabus melhor seria muito benéfico,
mas dá muito trabalho e exige boa comunicação e coordenação.
Certifique-se de discutir no fórum quaisquer planos que você tenha
com pessoas que já têm experiência criando syllabi.

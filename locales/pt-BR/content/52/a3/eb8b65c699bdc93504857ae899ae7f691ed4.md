# Sobre

_"Datas e horários são algo que ensinamos para crianças pequenas. Quão difícil pode ser?"_

Muitos programadores já cometeram esse erro, e o que vem depois costuma ter um efeito ruim sobre a saúde e a felicidade deles.

Quem faz programação não trivial com datas e horários deveria, no mínimo, estar preparado para entender e mitigar possíveis problemas.

Este documento pretende dar uma visão geral de como o R lida com datas e horários, mas será necessário consultar a documentação completa para mais detalhes.

No R, uma linguagem de ciência de dados, datas e horários têm uma importância especial.
Boa parte dos dados chega na forma de séries temporais: número diário de pacientes durante um surto de doença, números mensais de emprego divulgados por governos, populações de aves em uma colônia de nidificação, PIB anual das principais economias, e incontáveis outros exemplos.

_Isso significa que o R torna o tratamento de datas e horários simples?_

Infelizmente, não!

A funcionalidade de datas e horários no R base tem má reputação, e hoje a maior parte dela raramente é usada.

O pacote [`lubridate`][web-lubridate] é uma grande melhoria, mas prepare-se para uma biblioteca grande e complicada, projetada para lidar com uma gama grande e complicada de problemas.

Originalmente independente, o `lubridate` hoje vem incluído na coleção `tidyverse`.
Carregue-o com `library(lubridate)` ou `library(tidyverse)`.

Recursos que ajudam você a trabalhar com o `lubridate` incluem:

- Uma [página de referência][ref-lubridate].
- Uma [cheatsheet][cheat-lubridate] em formato PDF.
- Um [capítulo][book-dates-times] do R for Data Science.

## Datas e datetimes

Uma `date` é apenas um dia, sem informação de horário.

Internamente, as datas são armazenadas como o número (com sinal) de dias desde `1970-01-01`.

```R
today()
#> [1] "2026-04-22"
typeof(today())  # just a number
#> [1] "double"
class(today())  # the class understands how to interpret the raw number
#> [1] "Date"
```

Um `datetime` combina informação de data, horário e fuso horário.

Internamente, ele é armazenado como o número de segundos desde o início de 1970 no fuso horário UTC.

```R
now()
#> [1] "2026-04-22 15:37:11 MST"  # mid-afternoon in Arizona
typeof(now())
#> [1] "double"  # again, just a number
# POSIX datetimes are built into most operating systems as standard
class(now())
#> [1] "POSIXct" "POSIXt"
```

Talvez surpreendentemente, o R não tem representação interna para valores que contêm apenas horário.
Quem precisar dessa funcionalidade (fora do Exercism) pode instalar o pacote [`hms`][ref-hms].

## Trabalhando com valores `date` e `datetime`

Talvez as necessidades mais frequentes envolvendo datas e horários sejam:

- Interpretar algum formato de entrada adequado para construir uma data ou um datetime.
- Obter o formato numérico ou de string necessário a partir de uma data ou um datetime.
- Aplicar um deslocamento a um valor de data ou datetime.
- Calcular o intervalo de tempo entre dois desses valores.
- Obter a data atual (com `today()`) e/ou o datetime atual (com `now()`).

### Interpretando a partir de strings

Existem muitas formas de escrever datas e horários, e elas costumam variar conforme a cultura.
Datas só com números, como "7/6/23", são ambíguas, confundem e já causaram muitos erros caros em organizações multinacionais (_o autor diz isso por experiência própria e amarga_).

O padrão internacional (a-m-d) é definido na [`ISO 8601`][wiki-ISO8601] e tem duas vantagens principais:

- A interpretação é rápida e sem ambiguidade.
- A ordenação é fácil, pois o datetime pode ser tratado como texto normal e ordenado alfabeticamente.

No entanto, ciência de dados é trabalhar com os dados que você consegue encontrar, e muitas vezes não adianta reclamar de como outras pessoas os formatam.

O R base tem funções de conversão que recebem uma string de formato (com ISO 8601 como padrão).

```R
as.Date("2026-04-22")
#> [1] "2026-04-22"
as.Date("4/22/26", format = "%m/%d/%y")
#> [1] "2026-04-22"
as.POSIXct("2026-04-22 15:30:09 MST")
#> [1] "2026-04-22 15:30:09 MST"
```

As strings de formato lembram a função `strptime()`, que existe há décadas e está presente em _muitas_ linguagens.
Quem já conhece essa sintaxe pode, opcionalmente, usar a função [`fast_strptime()`][ref-parse_dt] do lubridate.

De forma mais útil, o `lubridate` oferece uma ampla variedade de [funções auxiliares][ref-parsing], com nomes que representam a ordem dos campos.
Quando as funções sabem quais valores procurar e em que ordem, a interpretação é impressionantemente flexível.

```R
mdy("4/22/26")
#> [1] "2026-04-22"
mdy("April 22nd 26")
#> [1] "2026-04-22"
mdy("Wednesday, April 22nd 2026")
#> [1] "2026-04-22"
mdy_hm("Wednesday, April 22nd 2026, 4:14 pm")
#> [1] "2026-04-22 16:14:00 UTC"  # defaults to your OS timezone
```

Essas funções auxiliares são casos especiais da função [`parse_date_time()`][ref-parse_dt], que recebe uma string de formato como `"mdy_hm"` como segundo argumento.

### Construindo a partir de valores numéricos

Quando seu programa tem os componentes de uma data/datetime como números separados, eles podem ser montados com [`make_date()` ou `make_datetime()`][ref-make_datetime].

Estes são os componentes que podem ser fornecidos, mostrando sua ordem e seus valores padrão:

```R
make_datetime(
  year = 1970L,
  month = 1L,
  day = 1L,
  hour = 0L,
  min = 0L,
  sec = 0,
  tz = "UTC"
)
#> [1] "1970-01-01 UTC"

make_datetime(2026, 4, 22, 17)
#> [1] "2026-04-22 17:00:00 UTC"
```

Naturalmente, `make_date()` aceita apenas os argumentos de ano, mês e dia.

### Gerando saída legível para humanos

O console do R exibe datas/datetimes automaticamente como uma representação em string.
Isso geralmente é prático, mas às vezes engana.

Internamente, datas e datetimes são números (mais alguns atributos), não strings.
Retornar uma data (ou datetime) quando se espera uma string vai causar problemas, então precisamos saber como fazer a conversão.

Uma abordagem simples é usar [`as.character()`][ref-ascharacter] do R base, que gera uma string no formato ISO 8601.

Também existe a função [`format_ISO8601()`][ref-iso8601] para datetimes, com opções para arredondar para a precisão desejada.

```R
today() |> as.character()  # a date
#> [1] "2026-04-23"
now() |> as.character()  # a datetime
#> [1] "2026-04-23 09:07:09.779319"
now() |> format_ISO8601() # defaults to nearest second
#> [1] "2026-04-23T09:07:38"
```

Poucas pessoas fora da programação querem ver a saída em ISO 8601, então lidar com formatos de data e hora específicos de cada cultura é essencial.

O R base oferece a função [`format()`][ref-format], que usa strings de formato parecidas com as veneráveis funções `strftime()` presentes em muitas outras linguagens.

```R
format(today(), "%A, %d %B %Y")
#> [1] "Thursday, 23 April 2026"
```

Essa abordagem do R base é feia, mas confiável.
Estes são alguns dos códigos mais comuns:

Código | Resultado
-- | --
%d | Número do dia do mês (5, 17, 28, etc.)
%a | Dia da semana abreviado (Mon, Tue, Wed, etc.)
%A | Dia da semana completo (Monday, Tuesday, etc.)
%w | Número do dia da semana (0-6, domingo é 0)
%u | Número do dia da semana (1-7, segunda-feira é 1)
%b | Mês abreviado (Jan, Feb, etc.)
%B | Mês completo (January, February, etc.)
%y | Ano com 2 dígitos (ex.: 89)
%Y | Ano com 4 dígitos (ex.: 1989)
%h | horas (relógio de 24 horas)
%m | minutos
%s | segundos
%z | deslocamento em relação ao UTC
%Z | Fuso horário (caractere)

O lubridate busca oferecer uma alternativa mais amigável com a função [`stamp()`][ref-stamp], e as mais específicas `stamp_date()` e `stamp_time()`.

Elas recebem uma string de modelo que é um exemplo da saída desejada e criam uma função personalizada para gerar esse formato.

O lubridate tenta adivinhar o formato, mas muitas vezes esbarra em ambiguidades e produz o resultado errado.
Prepare-se para fornecer strings de formato (como `"dmy"`) quando for preciso desfazer a ambiguidade.

No Exercism, também pode ser útil especificar `locale = "C"`, para ignorar o locale do seu sistema e trabalhar em inglês (como os testes esperam).
Locales são complicados!

```R
sf <- stamp("Saturday, June 27, 2026 at 14:45", locale = "C")
#> Multiple formats matched: "%A, %B %d, %Y at %H:%M"(1), "Saturday, %Om %d, %Y at %H:%M"(1), "Saturday, %B %d, %Y at %H:%M"(1), "%A, %Om %d, %Y at %H:%M"(0)
#> Using: "%A, %B %d, %Y at %H:%M"

sf(make_datetime(2023, 3, 29, 15, 0, 0))
#> [1] "Wednesday, March 29, 2023 at 15:00"
```

### Definindo ou extraindo componentes

O lubridate oferece [muitas funções][ref-set-get] para obter ou definir elementos de uma data ou datetime: as óbvias, como `year()` e `second()`, mas também outras mais específicas, como `quarter()` e `epiweek()`.

Todas essas funções podem ser usadas para obter um valor, e a maioria também pode definir o valor.

```R
dt <- now()
dt
#> [1] "2026-04-23 15:47:11 MST"

# get
month(dt)
#> [1] 4

# set
month(dt) <- 11
dt
#> [1] "2026-11-23 15:47:11 MST"
```

Para `wday()` (dia da semana) e `month()`, o padrão é a saída como número inteiro, mas:

- Definir `labels = TRUE` retorna uma string abreviada correspondente ao locale atual.
- Definir também `abbr = FALSE` retorna o nome completo.

```R
d <- today()
d
#> [1] "2026-04-23"
wday(d)
#> [1] 5
wday(d, label = TRUE)
#> [1] Thu
#> Levels: Sun < Mon < Tue < Wed < Thu < Fri < Sat
wday(d, label = TRUE, abbr = FALSE)
#> [1] Thursday
#> Levels: Sunday < Monday < Tuesday < Wednesday < Thursday < Friday < Saturday
```

Os rótulos são `categorical variables`, que serão tema de outro Conceito.
Os valores ficam restritos aos `Levels` listados, que também mostram a ordem de classificação.

Por padrão, a semana começa no domingo, mas isso pode ser alterado com o argumento `week_start` (use `1` para segunda-feira).

```R
dt <- make_datetime(2026, 4, 23)

# default behavior
wday(dt)
#> [1] 5
wday(dt, label = T)
#> [1] Thu

# set week_start to Monday
wday(dt, week_start = 1)
#> [1] 4
```

Algumas funções utilitárias retornam valores `TRUE`/`FALSE`, como `leap_year()` e `dst()` (o horário de verão está ativo?).

Os meses variam de tamanho, então `days_in_month()` dá o valor como número inteiro.

### Arredondamento

Números podem ser arredondados com [funções][ref-round] como `round()`, `floor()` e `ceiling()`.

Por extensão, datas e datetimes têm as [funções][ref-round_date] `round_date()`, `floor_date()` e `ceiling_date()`.

Por padrão, o arredondamento é para o segundo, mas há muitas outras opções disponíveis no argumento `unit`.
Veja a [documentação][ref-round_date] para detalhes e fartos exemplos.

## Intervalos de tempo

Tanto valores `date` quanto `datetime` representam um instante ao longo da linha do tempo.

Como lidamos com conceitos como "esta mesma hora de ontem" ou "daqui a uma semana"?

Quem conhece outras linguagens voltadas à ciência talvez já tenha visto `datetime.timedelta` em Python ou o tipo `Period` em Julia.

Em contraste, o R tem nada menos que três formas de representar intervalos de tempo, com pontos fortes e limitações diferentes.
Como sempre, escolha a que melhor se adequa ao seu contexto.

Os vários intervalos podem ser convertidos facilmente entre si, com `as.period()`, `as_duration()` e `as.interval()`.

Os tipos de intervalo podem ser verificados com `is.period()`, etc.

### Períodos

Um `period`, como `hours(3)`, pode ser usado para avançar um horário em 3 horas.

Irregularidades como o horário de verão (DST) são em grande parte ignoradas.

Todos os períodos são o nome de uma unidade no plural: `years`, `weeks`, etc.

```R
d <- today()
d
#> [1] "2026-04-25"

d + weeks(2)
#> [1] "2026-05-09"

# dates are coerced to datetimes at midnight if necessary
d - hours(20)
#> [1] "2026-04-24 04:00:00 UTC"

hours(3)
#> [1] "3H 0M 0S"
```

### Durações

Uma `duration`, como `dhours(3)`, avança o tempo físico em 3 horas, respeitando irregularidades como o horário de verão que fazem o horário de relógio se desviar do tempo físico.

Todas as durações acrescentam um prefixo `d` ao período correspondente: `dyears`, `dweeks`, etc.

```R
dhours(3)
#> [1] "10800s (~3 hours)"
```

### Intervalos

Um `interval` é uma combinação de um horário de início e um de fim, criado com a função [`interval()`][ref-interval] ou com o operador infixo `%--%`.

```R
# the next 2 lines were run about 33s apart, so now() is different
dt1 <- now()
dt2 <- now() + hours(1)

# interval(0 function)
ivl <- interval(dt1, dt2)
ivl
#> [1] 2026-04-24 16:24:54 MST--2026-04-24 17:25:27 MST
class(ivl)
#> [1] "Interval"
attr(,"package")
#> [1] "lubridate"

# infix operator
iv2 <- dt1 %--% dt2
iv2 == iv1
#> [1] TRUE

# conversions
as.period(ivl)
#> [1] "1H 0M 32.738214969635S"
as.duration(ivl)
#> [1] "3632.73821496964s (~1.01 hours)"

# components
int_start(ivl)
#> [1] "2026-04-24 16:24:54 MST"

# is datetime within the interval?
(now() - minutes(20)) %within% ivl
#> [1] TRUE
```

## Fusos horários

Lidar com fusos horários pode ser desafiador.
A citação abaixo é da documentação do Python, mas é igualmente relevante para o R:

> "As regras de ajuste de horário pelo mundo são mais políticas do que racionais, mudam com frequência, e não há padrão adequado a toda aplicação além do UTC."

Alguns pontos gerais sobre fusos horários:

- Um `datetime` sempre inclui um fuso horário (`tz`); um `date` não considera fuso horário.
- Os construtores de datetime geralmente usam [UTC][wiki-UTC] como padrão.
- A função [`now()`][ref-now] é uma exceção: ela pega o horário local do relógio do sistema, incluindo o `tz`.
  O `tz` local é usado por padrão, mas outros podem ser especificados, como em `now("UTC")`.

```R
# timezone defaults to UTC
local <- ymd_hm("2026-04-25 10:32")
local
#> [1] "2026-04-25 10:32:00 UTC"

# timezone can be specified
AZ <- ymd_hm("2026-04-25 10:32", tz = "America/Phoenix")
AZ
#> [1] "2026-04-25 10:32:00 MST"

# same clocktime, different tz
local - AZ
#> Time difference of -7 hours
```

A aritmética com fusos horários usando durações é mais confiável do que com períodos.

```R
dt <- make_datetime(2020, 10, 31, 12, tz = "Europe/Helsinki")

# EET is 2h ahead of UTC
dt
#> [1] "2020-10-31 12:00:00 EET"

# A week earler, EEST (summer time) is 3h ahead of UTC

# a 7-day period => midday
dt - days(7)
#> [1] "2020-10-24 12:00:00 EEST"

# a 7-day duration => 1 pm
dt - ddays(7)
#> [1] "2020-10-24 13:00:00 EEST"
```

Tanto no cálculo com período quanto no cálculo com duração, o lubridate reconhece a mudança do Horário da Europa Oriental para o Horário de Verão da Europa Oriental, mas apenas a duração ajusta a mudança de 1 hora.

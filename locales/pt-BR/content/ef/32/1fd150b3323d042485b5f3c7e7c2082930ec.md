# Introdução

As threads do Factor são *corrotinas cooperativas*: elas compartilham uma única thread do sistema operacional, passam o controle umas para as outras nas operações de E/S e nos pontos de yield explícitos, e nunca rodam de verdade ao mesmo tempo. Tudo o que você faz *entre* um yield e outro acontece como um único passo ininterrupto. Mas se uma operação composta (ler-modificar-escrever) faz yield no meio do caminho, outra thread pode se intrometer e mudar o mundo antes de você terminar. E isso é uma condição de corrida.

Este exercício aborda quatro primitivas que aparecem o tempo todo:

## `parallel-map`: fork/join sobre uma sequência

```
parallel-map ( seq quot: ( elt -- newelt ) -- newseq )
```

Em [`concurrency.combinators`][combinators]. Cria uma thread por elemento, roda a quotation e recolhe os resultados de volta em uma nova sequência, na mesma ordem:

```factor
USING: concurrency.combinators sequences ;

{ "alpha" "beta" "gamma" } [ length ] parallel-map .
! => { 5 4 5 }
```

## `spawn`: iniciar uma thread

```
spawn ( quot name -- thread )
```

Em [`threads`][threads]. A quotation roda de forma concorrente; `name` é um rótulo para depuração. O handle de thread retornado é praticamente irrelevante nesse nível: simplesmente dê `drop` nele.

## Promises: passagem única de valor

```
<promise>           ( -- promise )
fulfill             ( value promise -- )
?promise            ( promise -- value )
```

Em [`concurrency.promises`][promises]. Uma promise é uma caixa de correio de disparo único: uma thread a cumpre, as outras a leem. `?promise` bloqueia até a promise ser cumprida e então retorna o valor.

```factor
USING: concurrency.promises kernel threads ;

<promise> [
    [ 42 swap fulfill ] curry "answer" spawn drop
] keep ?promise .
! => 42
```

`spawn` + `<promise>` é a base de que `parallel-map` é construído; montar isso à mão é útil quando cada tarefa faz algo diferente de "calcular um único elemento".

O formato típico de fan-out/join sobre uma sequência é: para cada entrada, crie uma promise nova, crie uma thread que faz o trabalho e chama `fulfill` na promise, recolha todas as promises em uma sequência e então chame `?promise` em cada uma para esperar a conclusão. Locals tornam isso legível: vincule a promise a um nome com `:>` dentro de uma lambda `[| | ]`, para que a quotation criada possa capturá-lo:

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
inputs [| x |
    <promise> :> p
    [ x do-work t p fulfill ] "worker" spawn drop
    p
] map [ ?promise drop ] each
```

## Locks: exclusão mútua

```
<lock>     ( -- lock )
with-lock  ( lock quot -- )
```

Em [`concurrency.locks`][locks]. Só uma thread pode deter um determinado lock por vez. `with-lock` adquire, roda a quotation e libera, mesmo que a quotation lance uma exceção.

```factor
! DOCTEST: SKIP   (`:>` only works inside [let, [|, or :: forms)
USING: concurrency.locks kernel locals ;

[let <lock> :> guard
    guard [ ! exclusive section ! ] with-lock
]
```

Use um lock sempre que um valor for *lido ou escrito por mais de uma thread* e as operações sobre ele não forem naturalmente atômicas. Tanto as leituras quanto as escritas precisam do lock: uma leitura que faz yield no meio do caminho pode enxergar um estado inconsistente.

# Introdução

Uma função é **recursiva** quando chama a si mesma.

Uma diferença fundamental entre uma chamada de função e um laço é que chamar uma função empilha o endereço de retorno na pilha.
Por isso, uma função recursiva geralmente exige mais espaço na pilha do que um laço equivalente.

Como consequência, uma função que fica chamando a si mesma pode acabar esgotando todo o espaço da pilha.
Isso se chama **estouro de pilha**.

Por isso, toda função recursiva precisa ter pelo menos um caso base, ou seja, uma situação em que a função retorna sem chamar a si mesma.
Qualquer chamada recursiva precisa chegar a um caso base em algum momento.

Por exemplo, a função fatorial `n! = n * (n - 1) * ... * 1` pode ser definida recursivamente com `1` como caso base:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Repare que `factorial` precisa fazer `push rdi` antes da chamada recursiva e `pop rdi` depois.
Isso porque ela ainda precisa de `n` quando a chamada recursiva retorna, para calcular `n * (n-1)!`.

Repare também que usar um registrador salvo pela função chamada não resolveria esse problema.

Mesmo que uma função recursiva seja uma possível chamadora de si mesma, ela também é chamada por alguma outra função.
Isso quer dizer que ela precisa preservar os registradores salvos pela função chamada antes de usá-los e restaurar seus valores depois de usá-los.
Normalmente isso é feito com uma sequência de `push`/`pop`, como vimos em um conceito anterior.

Como cada frame de uma função recursiva, com exceção do caso base, também é um chamador que precisa preservar suas próprias variáveis locais, essa sequência de `push`/`pop` precisa se repetir a cada frame.
Mesmo guardar a variável direto na pilha, sem usar registradores, ainda custaria os mesmos `8` bytes por frame.

Isso quer dizer que cada chamada recursiva acrescenta `8` bytes à pilha pelo endereço de retorno empilhado pelo `call`, mais `8` bytes para cada variável local que ela precisa salvar.
A função vai continuar acrescentando esses bytes à pilha a cada frame até chegar ao caso base.
Só então ela começa a desenrolar na ordem inversa: cada chamada recursiva usa quantos `pop` forem necessários e depois um `ret`.

Por exemplo, se `factorial` fosse chamada com o argumento `10`, ela chamaria a si mesma nove vezes antes de chegar ao caso base `1`.
Nesse momento, `144` bytes teriam sido usados para guardar o `n` (`8` bytes) e o endereço de retorno (`8` bytes) de cada frame anterior.

## Chamada de cauda

Em algumas situações, uma função não realiza mais nenhum trabalho depois de chamar outra e antes de retornar.

Considere, por exemplo:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

A função `triple_of_square`:

- multiplica o argumento recebido (em `rdi`) por ele mesmo, obtendo o quadrado;
- depois chama `times_three`, que retorna três multiplicado pelo argumento recebido.

Como resultado, `triple_of_square` retorna `3*x²`, em que `x` é seu argumento, passado em `rdi`.

Repare que nenhum trabalho é feito em `triple_of_square` depois de chamar `times_three`: a função simplesmente retorna.
Numa situação como essa, em vez de usar `call`, a função pode usar `jmp` e transferir a execução para a função chamada:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

Isso se chama **chamada de cauda**.

A principal vantagem de uma chamada de cauda é evitar o custo extra do `call`.
Um `call` empilha um endereço de retorno na pilha, e para que o controle volte a esse ponto precisa haver um `ret` correspondente.

Uma chamada de cauda dispensa os dois: não há endereço de retorno para empilhar nem um `ret` extra para combinar com ela, apenas o `ret` da própria função chamada.

## Recursão de cauda

Uma chamada de cauda é especialmente útil para funções recursivas que podem chamar a si mesmas muitas vezes antes de retornar.

No entanto, nem toda chamada recursiva pode ser convertida diretamente em uma chamada de cauda.
Como um `jmp` transfere o controle para a função chamada, o chamador não pode realizar mais nenhum trabalho depois da chamada de cauda.

Por exemplo, a função `factorial` anterior **não** é recursiva de cauda.
Depois da chamada recursiva, ela ainda precisa multiplicar o resultado pelo `n` atual, usando `imul rax, rdi`.

Em situações como essa, às vezes é possível usar um acumulador que vai reunir os cálculos parciais e ser retornado no final.
Por exemplo, podemos definir uma `factorial_helper` que faz a maior parte do trabalho, e então `factorial` prepara um acumulador e transfere o controle para `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Como não há mais nenhum trabalho depois da chamada recursiva, também não precisamos mais salvar o `rdi`.
Não existe `call` nem `push rdi`, então cada iteração recursiva acrescenta `0` bytes à pilha: nenhum espaço extra de pilha é usado.
Essa versão consegue lidar com qualquer `n`, por maior que seja, sem estourar a pilha.
Ela é ao mesmo tempo mais eficiente e mais segura.

Em alguns casos, mexendo na ordem das funções, dá até para evitar o `jmp` para a função auxiliar.
Por exemplo, `factorial` e `triple_of_square` podem ser reescritas assim:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

No trecho acima, a execução de `factorial` continua direto para `factorial_helper`.
O mesmo acontece com `triple_of_square` e `times_three`.
Nos dois casos, a execução continua em sequência, e parece que a função de cauda é apenas um rótulo local dentro da função "principal".

Na verdade, não há diferença essencial entre qualquer rótulo local e uma função.
O assembly x86-64 não dá tratamento especial a nenhum deles: são apenas endereços em uma seção de código executável, como `section .text`.

Dessa forma, uma função recursiva de cauda pode ser pensada essencialmente como um laço em que a chamada recursiva salta de volta para o início e o caso base é a condição que encerra o laço.

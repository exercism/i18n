# Introdução

No assembly, qualquer dado é uma sequência de bytes.
Isso significa que qualquer dado pode ser visto como um **array** desses bytes subjacentes.

## Como acessar elementos de um array

Para acessar qualquer valor na memória, é preciso calcular seu **endereço efetivo**.
Um endereço efetivo é uma expressão que pode ser composta por:

- um _endereço base_, por exemplo, o indicado pelo rótulo de uma variável.
- um _registrador de índice_, possivelmente escalonado por `1`, `2`, `4` ou `8`.
- um _deslocamento_ de 32 bits com sinal, que é um número somado ao endereço base (ou subtraído dele).

Repare que esse endereço é _indexado a partir de zero_, então um endereço base, sem nenhum deslocamento, aponta para o primeiro byte de uma variável.
É por isso que desreferenciar a memória usando apenas um rótulo, sem nenhum deslocamento, como fizemos em conceitos anteriores, produz um valor que começa em seu primeiro byte:

```x86asm
section .data
    example dq 10 ; example is a 8-byte variable
                  ; so it can be viewed as an array of those 8 bytes
                  ; which can be accessed from index 0 to index 7

section .text
fn:
    mov al, byte [example] ; this accesses the first byte
    mov r8b, byte [example + 2] ; this accesses the third byte
    mov edx, dword [example + 1] ; this accesses 4 bytes starting at the second
```

~~~~exercism/note
O x86-64 é [little endian][endianness].
Isso significa que o byte menos significativo de um valor com vários bytes fica armazenado no menor endereço de memória.

Por consequência, ao acessar os bytes individuais de um valor com vários bytes, é preciso somar um deslocamento positivo ao endereço base para alcançar os bytes mais significativos.

[endianness]: https://en.wikipedia.org/wiki/Endianness
~~~~

Uma variável inicializada declarada com uma lista de valores é um array desses valores, em que cada elemento tem o tamanho especificado.
No entanto, os deslocamentos são sempre em **_bytes_**, mesmo quando cada elemento do array tem um tamanho maior:

```x86asm
section .data
    arr dq 4, 8, 15, 23, 42 ; this defines an array of 5 qwords (8-byte elements)
                            ; the first qword has value 4 and can be accessed at [arr] (offset 0)
                            ; any subsequent qword can be accessed at offsets increasing by the size in bytes of each element (8)

section .text
fn:
    mov rdx, 2
    lea rcx, [rel arr]
    mov rax, qword [rcx + 8*rdx + 8]  ; rdx is an index register scaled by 8
                                      ; 8 is a signed 32-bit displacement
                                      ; rax now holds 8-bytes stored in 'arr' starting at offset:
                                      ; 8*rdx(2) + 8 = 16 + 8 = 24
                                      ; this is the fourth element of the array, i.e., the element 23
```

Repare que, como os endereços são contados em bytes, é possível acessar diretamente um byte individual de qualquer elemento de um array:

```x86asm
section .data
    arr dq 4, 8, 15, 16   ; this defines an array of 4 qwords (8-byte elements)

section .text
fn:
    mov r8, 3
    lea r9, [rel arr]
    mov r10b, byte [r9 + 2*r8 + 1] ; this accesses the byte in 'arr' at offset: 2*r8(3) + 1 = 7
                                   ; this byte is part of the first qword and has value 0 (the fist byte is the least significant one)
```

Pelo mesmo motivo, é possível acessar mais do que o tamanho de um elemento em uma única instrução:

```x86asm
section .data
    arr db 1, 2, 3, 4 ; this defines an array of 4 bytes

section .text
fn:
    mov r11d, dword [rel arr] ; this accesses all bytes in arr as a 32-bit value with bytes
                              ; the least significant byte is 1, the next is 2 and so on
                              ; the resulting number is 0x04030201 or 67305985 in decimal
```

~~~~exercism/caution
O assembly não faz verificação de limites nos acessos a arrays.
Um índice além do fim de um array lê ou escreve em memória fora dele.
Isso pode levar a resultados incorretos sem aviso, à corrupção de outros dados e, se a memória acessada não estiver mapeada, a uma falha em tempo de execução.
Cabe a quem programa manter todo endereço efetivo dentro do array.
~~~~

## Como calcular o tamanho de um array inicializado

O NASM (The Netwide Assembler, o montador usado nesta trilha) tem um símbolo especial (`$`) que indica a posição atual na memória.
Esse símbolo oferece uma forma prática de calcular o tamanho total na memória ocupado por um array:

```x86asm
section .data
    example dd 4, 5, 6
    example_length dq $ - example  ; this is a qword variable with the size of the array, in bytes
```

Quando usado logo depois de `example`, o `$` contém o endereço na memória do fim do array.
Isso significa que `$ - example` é a diferença entre esse endereço e o apontado pelo rótulo `example`.
Esse é exatamente o tamanho total, em bytes, ocupado pelo array apontado por `example`.

Assim, ao definir `example_length` com esse valor, criamos uma variável de 8 bytes que guarda o tamanho, ou comprimento, do array, em bytes.

## A seção .bss

Os dados não inicializados são declarados na **section .bss**.
Na maioria das plataformas, o sistema operacional preenche esses dados com zeros no início do programa.

No NASM, uma variável não inicializada tem um nome, uma diretiva que indica o tamanho dos dados e o número de elementos a reservar.
Cada um desses itens é separado dos demais por um espaço.

As principais diretivas e os tamanhos de dados correspondentes são:

| diretiva | tamanho |
| :-------: | :------ |
|   resb    | 1 byte  |
|   resw    | 2 bytes |
|   resd    | 4 bytes |
|   resq    | 8 bytes |

Por exemplo, isto reserva espaço não inicializado para `3` bytes em uma variável chamada `example`:

```x86asm
section .bss
    example resb 3
```

E isto reserva espaço não inicializado para `10` vezes `8` bytes (ou seja, `80` bytes) em uma variável chamada `arr`:

```x86asm
section .bss
    arr resq 10
```

As variáveis em `section .bss` são mutáveis, ou seja, podem ser lidas e escritas.

Os dados não inicializados podem ser acessados da mesma forma que os dados inicializados, usando seu endereço efetivo.
Da mesma forma, eles também têm duração de armazenamento estática e são acessíveis a partir de qualquer função no mesmo arquivo-fonte (e, se declarados `global`, também em outros arquivos-fonte).

## Como acessar endereços de array com a instrução Lea

Como vimos em um conceito anterior, a instrução `lea` calcula um endereço de memória efetivo.
Ela pode ser usada para calcular o endereço de qualquer elemento de um array, seguindo a mesma semântica.

Repare que, no endereçamento relativo, muitas vezes é preciso carregar o endereço da variável em um registrador antes de montar um endereço mais complexo:

```x86asm
lea rax, [rel arr]
lea rdx, [rax + 8*r10 - 20] ; accessing 'arr' directly instead of loading it into rax first may yield an error
```

~~~~exercism/note
Uma das vantagens de `lea` é que ela usa aritmética de cálculo de endereços para computar um valor sem de fato acessar a memória nesse endereço.
Isso a torna útil para fazer cálculos aritméticos mesmo quando nenhum dos registradores contém um endereço de memória:

```x86asm
mov rcx, 3
mov rdx, 5
lea rax, [rcx + 8*rdx + 10] ; rax = rcx(3) + 8*rdx(5) + 10 = 3 + 40 + 10 = 53
```

# Sobre

Uma função é [recursiva][recursion] quando chama a si mesma.

Uma diferença importante entre uma chamada de função e um laço é que chamar uma função empilha o endereço de retorno na pilha.
Isso significa que uma função recursiva normalmente exige mais espaço de pilha do que um laço equivalente.

Como consequência, uma função que fica chamando a si mesma pode acabar esgotando todo o espaço da pilha.
Isso é chamado de [estouro de pilha][stack-overflow].

É por isso que toda função recursiva precisa ter pelo menos um caso base, que é uma situação em que a função retorna sem chamar a si mesma.
Toda chamada recursiva precisa acabar chegando a um caso base.

Por exemplo, a função fatorial `n! = n * (n - 1) * ... * 1` pode ser definida recursivamente com `1` como caso base:

```x86asm
factorial:
    ; the argument `n` is passed on `rdi`
    ; the factorial will be returned on `rax`

    cmp rdi, 1
    jle .base_case     ; base case -> if rdi <= 1, return 1

    push rdi           ; save n
    dec rdi            ; rdi = n - 1
    call factorial     ; recursive call, rax = (n - 1)!
    pop rdi            ; restore n
    imul rax, rdi      ; rax = n * (n - 1)! = n!
    ret
.base_case:
    mov rax, 1
    ret
```

Repare que `factorial` precisa fazer `push rdi` antes de se chamar recursivamente e `pop rdi` depois.
Isso acontece porque ela ainda precisa de `n` depois que a chamada recursiva retorna, para calcular `n * (n-1)!`.

Repare também que usar um registrador preservado pela função chamada não resolveria esse problema.

Embora uma função recursiva seja uma possível chamadora de si mesma, ela também é a função chamada por alguma outra função.
Isso quer dizer que a função também precisa salvar os registradores preservados pela função chamada antes de usá-los e restaurar seus valores depois.
Isso normalmente é feito com uma sequência de `push`/`pop`, como vimos em um conceito anterior.

Como cada quadro de uma função recursiva, com exceção do caso base, também é uma chamadora que precisa preservar as próprias variáveis locais, essa sequência de `push`/`pop` precisa se repetir a cada quadro.
Mesmo guardar a variável diretamente na pilha, sem usar registradores, ainda custaria os mesmos `8` bytes por quadro.

Isso significa que cada chamada recursiva adiciona `8` bytes à pilha para o endereço de retorno empilhado pelo `call`, mais `8` bytes para cada variável local que precise salvar.
A função vai continuar adicionando esses bytes à pilha a cada quadro até chegar ao caso base.
Só então ela começa a se desenrolar em ordem inversa, com cada chamada recursiva usando tantos `pop` quantos forem necessários e depois um `ret`.

Por exemplo, se `factorial` fosse chamada com o argumento `10`, ela chamaria a si mesma nove vezes antes de chegar ao caso base de `1`.
Nesse ponto, `144` bytes teriam sido usados para guardar o `n` (`8` bytes) e o endereço de retorno (`8` bytes) de cada quadro anterior.

## Chamada de cauda

Em algumas situações, uma função não realiza mais nenhum trabalho depois de chamar outra e antes de retornar.

Considere, por exemplo:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    call times_three
    ret
```

A função `triple_of_square`:

- multiplica o argumento recebido (em `rdi`) por ele mesmo, obtendo o seu quadrado;
- em seguida, chama `times_three`, que retorna o argumento recebido multiplicado por três.

Como resultado, `triple_of_square` retorna `3*x²`, em que `x` é o seu argumento, passado em `rdi`.

Repare que nenhum trabalho é feito em `triple_of_square` depois de chamar `times_three`: a função simplesmente retorna.
Em uma situação como essa, em vez de usar `call`, uma função pode usar `jmp` e transferir a execução para a função chamada:

```x86asm
times_three:
    imul rax, rdi, 3
    ret

triple_of_square:
    imul rdi, rdi
    jmp times_three
```

Isso é chamado de [chamada de cauda][tail].

A principal vantagem de uma chamada de cauda é evitar o custo extra do `call`.
Um `call` empilha um endereço de retorno na pilha, e para que o controle volte a esse ponto precisa haver um `ret` correspondente.

Uma chamada de cauda pula os dois: não há endereço de retorno para empilhar nem um `ret` extra para fazer par, apenas o `ret` da própria função chamada.

## Recursão em cauda

Uma chamada de cauda é especialmente útil para funções recursivas que podem se chamar muitas vezes antes de retornar.

No entanto, nem toda chamada recursiva pode ser convertida diretamente em uma chamada de cauda.
Como um `jmp` transfere o controle para a função chamada, a função chamadora não pode realizar mais nenhum trabalho depois da chamada de cauda.

Por exemplo, a função `factorial` anterior **não** é recursiva em cauda.
Depois da chamada recursiva, ela ainda precisa multiplicar o resultado pelo `n` atual, usando `imul rax, rdi`.

Em situações como essa, às vezes é possível usar um acumulador que vai reunir os cálculos parciais e ser retornado no final.
Por exemplo, podemos definir uma `factorial_helper` que faz a maior parte do trabalho, e então `factorial` prepara um acumulador e transfere o controle para `factorial_helper`:

```x86asm
factorial_helper:
    ; the argument `n` is passed on `rdi`
    ; `rax` is used as an accumulator and will be returned at the end

    cmp rdi, 1
    jle .base_case

    imul rax, rdi        ; we accumulate the partial result on `rax`
    dec rdi              ; rdi = n - 1
    jmp factorial_helper ; tail call to accumulate (n - 1)!
.base_case:
    ret                  ; returns the factorial already accumulated on `rax`

factorial:
    mov rax, 1           ; initial value for the accumulator
    jmp factorial_helper ; tail call
```

Como nenhum trabalho é feito depois da chamada recursiva, também não precisamos mais salvar o `rdi`.
Não há `call` nem `push rdi`, então cada iteração recursiva adiciona `0` bytes à pilha: nenhum espaço adicional de pilha é usado.
Essa versão consegue lidar com qualquer `n` arbitrariamente grande sem estourar a pilha.
Ela é ao mesmo tempo mais eficiente e mais segura.

Em alguns casos, manipulando a ordem das funções, é possível até evitar o `jmp` para a função auxiliar.
Por exemplo, `factorial` e `triple_of_square` podem ser reescritas assim:

```x86asm
factorial:
    mov rax, 1
factorial_helper:
    cmp rdi, 1
    jle .base_case

    imul rax, rdi
    dec rdi
    jmp factorial_helper
.base_case:
    ret

triple_of_square:
    imul rdi, rdi
times_three:
    imul rax, rdi, 3
    ret
```

No trecho acima, a execução de `factorial` continua direto para `factorial_helper`.
O mesmo acontece com `triple_of_square` e `times_three`.
Nos dois casos, a execução continua de forma sequencial e parece que a função de cauda é apenas um rótulo local dentro da função "principal".

Na verdade, não há nenhuma diferença essencial entre um rótulo local qualquer e uma função.
O assembly x86-64 não dá tratamento especial a nenhum deles: são apenas endereços em uma seção com código executável, como `section .text`.

Dessa forma, uma função recursiva em cauda pode ser pensada essencialmente como um laço em que a chamada recursiva salta de volta para o início, e o caso base é a condição que encerra o laço.

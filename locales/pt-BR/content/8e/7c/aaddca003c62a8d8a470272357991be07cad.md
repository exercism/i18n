# Guia de estilo de C

Este guia descreve o estilo previsto para uso com os arquivos de exemplo e de teste dos exercícios da trilha de C.

As regras deste guia complementam, ou destacam, as definidas pelo arquivo [.clang-format][].

## Padrão C

O código deve estar em conformidade com o padrão C99, formalmente conhecido como ISO/IEC 9899:1999.
Não se deve usar POSIX nem quaisquer outras funções de biblioteca, tipos ou referências que sejam não padrão e externos à implementação.

## Nomes

De modo geral, os nomes de tipos, variáveis, estruturas e arquivos devem usar snake case, com todas as letras em minúsculas, usando underscores `_` para separar os componentes do nome.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Enums

Os nomes de enum geralmente devem estar no singular, não no plural.

Os rótulos de enum devem usar snake case com todas as letras em maiúsculas.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Macros

Macros que definem constantes são nomeadas em snake case com todas as letras em maiúsculas.

```c
#define CONSTANT 0x4000
```

Prefere-se snake case em maiúsculas para nomes de macros, mas macros que se assemelham a funções podem ser nomeadas em snake case minúsculo.

### Tipos

Os tipos de largura fixa padrão (em `stdint.h`) são preferíveis aos tipos inteiros básicos.

O tipo `bool` (de `stdbool.h`) é preferível a `_Bool`.

Do mesmo modo, `size_t` e `ptrdiff_t` (de `stddef.h`) são preferíveis para representar quantidades relacionadas à memória.

Tipos definidos por um programa com `typedef` devem ter o sufixo `_t`.
Embora estejamos cientes de que o POSIX reserva o sufixo `_t`, a trilha atualmente não utiliza POSIX.

## Guardas de inclusão

Deve-se usar guardas de inclusão em todos os arquivos de cabeçalho.

Em geral, um conjunto de guardas de inclusão deve envolver todo o conteúdo do cabeçalho.

As guardas na implementação de exemplo (`.meta/example.h`) e no esqueleto do exercício (`exercise_name.h`) devem usar nomes de macro que sigam o nome do exercício.
Os nomes das macros de guarda devem seguir a regra de maiúsculas e minúsculas acima para macros.

Por exemplo, para o exercício `hello-world`, use:

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Parâmetros

Os parâmetros de função devem ser nomeados tanto na declaração quanto na definição de todas as funções.
Isso vale tanto para arquivos `.c` quanto `.h`.
Os nomes usados devem ser iguais em todas as ocorrências.
Ou seja, embora o protótipo de função a seguir seja C válido, o estilo está incorreto porque o parâmetro não tem nome: `void foo(int);`.
O protótipo correto, desde que todas as outras declarações e a definição também usem o nome de parâmetro `bar`, seria `void foo(int bar);`.

Quando for mais simples ou mais apropriado, prefira parâmetros que exijam passar argumentos por valor em vez de por ponteiro.
Observe em especial que isso inclui parâmetros do tipo `struct`.

Caso não se espere que o estudante altere os valores de um parâmetro do tipo ponteiro dentro da implementação dele, esse parâmetro deve ser qualificado como `const`.

## Formatação

O repositório usa a ferramenta `clang-format`, conforme descrito no [guia de contribuição][contributing guide].

## Estrutura do arquivo de teste

O arquivo de teste de cada exercício segue uma estrutura específica.
A estrutura serve tanto para ajudar quem contribui a identificar as partes do arquivo quanto para ajudar quem está aprendendo a entender como os testes funcionam.

Como a maioria dos arquivos-fonte em C, um arquivo de teste começa com os includes.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

Depois dos includes vêm as funções `setUp()` e `tearDown()`.
Até agora, nenhum exercício usa essas funções (os corpos delas estão vazios), mas elas precisam continuar no lugar para que os arquivos de teste compilem corretamente em todas as plataformas.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

Em seguida vêm as funções auxiliares usadas pelas funções de teste.
Os nomes dessas funções auxiliares não devem usar o prefixo `test_`.

Depois vêm as próprias funções de teste.
Os nomes dessas funções usam o prefixo `test_`.
Com exceção da primeira, cada função de teste deve ter `TEST_IGNORE();` como sua primeira instrução.
A primeira ocorrência disso deve ser seguida pelo comentário de linha `// delete this line to run test`.

Por exemplo:

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Por último no arquivo vem a função `main()`.
O corpo da função main segue uma estrutura específica.
Primeiro, uma chamada a `UNITY_BEGIN()` seguida de uma linha vazia, depois os testes.
Depois do último teste vem outra linha vazia, antes de retornar o resultado de `UNITY_END()`.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

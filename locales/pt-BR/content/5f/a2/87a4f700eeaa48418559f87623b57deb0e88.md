# Especificação de Markdown

A seguir, veja como todos os arquivos Markdown do Exercism devem ser estruturados.

Algumas das regras deste documento ainda não foram implementadas em todo o Exercism.
Agradecemos PRs para corrigi-las.
Todas as regras estão sendo adicionadas à nossa CI e às nossas ferramentas de lint, e devem ser seguidas em novas alterações.

## Cabeçalhos

- Todos os arquivos devem começar com um cabeçalho de nível 1 (`# Some heading text`).
- Cabeçalhos de nível 1 existem apenas para serem consumidos no GitHub ou equivalente.
- Se o arquivo for renderizado pelo Exercism (por exemplo, exibido no site, renderizado pela CLI), esse cabeçalho será removido, e um cabeçalho contextual será inserido.
- Nenhum cabeçalho pode descer mais de um nível em relação ao anterior (por exemplo, `##` só pode ser seguido por `###`, nunca por `####`).
- Além do único cabeçalho de nível 1 (`#`), só podem ser usados cabeçalhos de nível 2 (`##`), nível 3 (`###`) e nível 4 (`####`).

## Links

Use [links de referência][reference-links], que são definidos no final do arquivo Markdown, mapeados para um slug de referência e referenciados por esse slug no texto.

Esse método facilita a manutenção, já que os links precisam ser atualizados em um único lugar.

Exemplo:

```
I have a paragraph of text that links to the same page twice.

The [first link][indirect-reference] in one sentence.

Then, another sentence with the [link repeated][indirect-reference].

[indirect-reference]: https://example.com/link-to-page
```

Os links devem sempre ter texto âncora, em vez de colocar a própria URL no texto. Por exemplo, o seguinte não usa texto âncora e é mais difícil de ler.

```
If you want some more information, please visit https://google.com.
```

Usar texto âncora e vinculá-lo é mais fácil de entender e contextualizar.

```
If you want some more information, [Google][google-link] is a useful resource.

[google-link]: https://google.com
```

O que é renderizado como: "Se você quiser mais informações, [Google][google-link] é um recurso útil."

## Código

Sempre que se referir a elementos de código (por exemplo, funções ou palavras-chave), o código deve ser envolto em crases:

```
- The `printf()` function writes to the console.
```

O que é renderizado como:

- A função `printf()` escreve no console.

Código mais complexo (por exemplo, código com várias linhas) deve ser envolto em três crases. Um [identificador de linguagem][language-identifier] deve ser especificado depois das três crases de abertura para habilitar o realce de sintaxe:

````python
```python
# Define a variable
album = "Abbey Road"
```
````

Quando possível, formate o código da maneira mais relevante para o ambiente em que ele está sendo apresentado. Se houver, consulte a documentação da sua linguagem.

Por exemplo, o Python tem o REPL (read-eval-print loop, ou laço ler-avaliar-imprimir), que permite a um programador digitar código diretamente em um terminal. Se uma pessoa estivesse depurando um código ou rodando uma função localmente para testar/observar como ela funciona, é mais provável que usasse um REPL para isso, já que é mais conveniente digitar interativamente ali. Nessa situação, preferimos formatar o código de exemplo como se estivesse sendo digitado no REPL, com um `>>>` no início:

```python
# This is the expected output a student would see while testing a function they wrote.
>>> print(extract_message("[INFO] Logline message"))
'Logline message'
```

Em outros casos, faz mais sentido deixar o código formatado como se estivesse em um arquivo `.py`. Aqui, o estudante se beneficia ao ver algo que imita como ele mesmo escreveria o código.

```python
# presenting how functions are defined in Python:
def sample_func(argument1):
    pass
```

Uma maneira rápida de distinguir entre os dois casos quando estiver em dúvida: se for código que o estudante pode rodar em um terminal, formate-o assim. Se for código que o Exercism pode rodar (em testes, código de biblioteca que o estudante vai escrever etc.), prefira formatá-lo como código executável.

## Blocos especiais (às vezes chamados de admonições)

Oferecemos suporte a tipos especiais de blocos que podem ser adicionados a documentos para destacar comentários que não se encaixam no corpo principal do texto.

<img width="500" alt="Bloco de nota do Markdown" src="https://user-images.githubusercontent.com/20866761/139531109-0c0f3ea5-b589-44ff-93ab-d901a45edc56.png">

<img width="500" alt="Bloco de aviso do Markdown" src="https://user-images.githubusercontent.com/20866761/139531234-9b58b9ab-524b-44fd-bbcb-4e10f2927d27.png">

<img width="500" alt="Bloco avançado do Markdown" src="https://user-images.githubusercontent.com/20866761/139531236-72259046-68a9-4934-9440-a730befde155.png">

Oferecemos suporte a três tipos de blocos:

- **exercism/note:** Blocos que destacam algumas informações extras especiais
- **exercism/caution:** Coisas que as pessoas devem saber ou tratar com cuidado
- **exercism/advanced:** Informações relevantes apenas para pessoas que querem se aprofundar em algo ou que já têm conhecimentos mais avançados.

Todos os blocos são escritos usando 4 tis, no formato:

````
~~~~exercism/note
Content goes here

You can include code:
```ruby
str = "Hello, World"
```

A [reference link][forum-link] must have the link definition inside the block.

[forum-link]: https://forum.exercism.org/t/link-references-in-special-blocks-admonitions-are-not-rendered/3803
~~~~
````

(Observação: você também pode usar crases ou outros níveis de tis em circunstâncias excepcionais)

## Layout

### Uma frase por linha

Os parágrafos devem ser organizados usando uma frase por linha. A [documentação do Ascii Doctor][asciidoctor] explica a lógica disso com clareza.

Por exemplo, um único parágrafo deve ser organizado da seguinte forma:

```
Exercism has been designed, engineered and built by thousands of very talented individuals.
Nearly everything with Exercism has been debated, discussed and rewritten many times.
Exercism is a very intentional product - things are there because they've been designed to be there, and things are often left out because they've been designed to be left out.
```

## Listas

Use o caractere hífen (`-`) como marcador de item de lista para listas não ordenadas.

## Comentários

- Prefira comentários Markdown em vez de comentários HTML (por exemplo, use `[comment]: # (Actual comment...)` em vez de `<!-- Actual comment -->`

Você pode testar se seu comentário Markdown é removido verificando como ele fica ao ser renderizado via commonmark em [babelmark3].

## HTML embutido

- HTML embutido é permitido, mas deve ser usado com moderação
- Sempre use alternativas nativas de Markdown quando disponíveis (por exemplo, use `# ...` em vez de `<h1>...</h1>`)

## Imagens

Como o site tem suporte a temas claro e escuro, imagens enviadas pela comunidade precisam ser renderizadas bem nos dois temas.
A solução para isso é adicionar um sufixo ao nome da sua imagem (antes da extensão do arquivo):

1. Faça o nome da imagem terminar em `-invertible` (por exemplo, `graph-invertible.svg`). A imagem será invertida automaticamente quando exibida no tema escuro (via `filter: invert(100%)`).
1. Faça o nome da imagem terminar em `-light` (por exemplo, `graph-light.png`) e também crie uma versão compatível com o tema escuro que termine em `-dark` (que seria `graph-dark.png`). Vamos renderizar automaticamente a imagem correta dependendo do tema da pessoa usuária.

Imagens sem nenhum dos sufixos serão usadas sem modificações nos dois temas.
Isso significa que, se você quiser criar imagens em escala de cinza, em geral pode fazê-las ficar boas no tema claro e depois defini-las como invertíveis.
Mas, se você estiver usando uma imagem com muitas cores, pode ser interessante criar duas variantes.

O nome completo da imagem (incluindo `-invertible`) deve ser adicionado ao Markdown onde a imagem é renderizada.
Para as de tema claro/escuro, inclua **APENAS** a variante `-light`.
Essa lógica é seguida em todos os documentos Markdown.

## Formatação automática

Alguns repositórios usam o [prettier][prettier] para garantir que todo Markdown seja formatado de forma consistente. Isso pode trazer os seguintes benefícios:

- Sem discussões sobre formatação.
- Ótima integração com editores/IDEs, para que os arquivos possam ser formatados ao salvar.
- Fácil adicionar verificações de CI para formatação.
- Fácil formatar arquivos automaticamente usando um script.

Tudo isso pode ajudar bastante a reduzir o retrabalho nas revisões, o que é frustrante tanto para quem revisa quanto para quem é revisado.

# Migrando do Travis

Aqui está um exemplo de `.travis.yml` (extraído da track `elm`):

```yml
sudo: false
language: node_js
node_js:
  - lts/*
script:
  - bin/fetch-configlet
  - bin/configlet lint
  - bin/build.sh
```

Para converter isso rapidamente em GitHub Actions, siga estes passos:

## Determine as variáveis do template

| variável                    | valor                                |
| --------------------------- | ------------------------------------ |
| `<track>`                   | `elm`                                |
| `<image-name>`              | `ubuntu-latest`                      |
| `<action to setup tooling>` | `actions/setup-node@v1`              |
| `<install dependencies>`    | `npm ci` (acontece dentro de `build.sh`) |
| `<code-extensions>`         | `.elm`                               |

> Encontrei a action de setup por meio de [esta busca](https://github.com/actions/?q=setup+node&type=&language=).
> Encontrei o nome da imagem olhando a [distribuição padrão do Travis](https://blog.travis-ci.com/2019-04-15-xenial-default-build-environment).

## Determine os passos

- `bin/fetch-configlet`: você não precisa mais disso ao usar o fluxo de trabalho [`configlet.yml`][workflow-template-configlet-yml]
- `bin/configlet lint`: você não precisa mais disso ao usar o fluxo de trabalho [`configlet.yml`][workflow-template-configlet-yml]
- `bin/build.sh`: um único script que faz tudo

## Prepare os "scripts"

Esta track usa a pasta `bin`, então dentro da pasta `bin`, crie os seguintes arquivos:

```bash
# bin/pr
bin/build.sh
```

```bash
# bin/pr-check
echo "No checks yet"
```

```bash
# bin/ci
bin/build.sh
```

```bash
# bin/ci-check
echo "No checks yet"
```

Criar esses arquivos como binários _separados_ vai permitir otimizações mais tarde. Não é preciso embutir nada agora.

## Agora deve funcionar

Isso é suficiente para converter para GitHub Actions, com a possibilidade de otimizar seus scripts.

1. No `build.sh`, remova os passos que devem rodar apenas uma vez e extraia-os para os arquivos `ci-check.sh` e `pre-check.sh` (dica: você pode criar `lint.sh` e chamá-lo a partir dos dois "scripts")
2. Em `pr.sh` e `pr-check.sh`, adicione otimizações que usam os argumentos de entrada para determinar quais arquivos ou exercícios verificar.
3. Adicione verificações adicionais
4. Adicione documentação sobre como rodar as verificações localmente e o que cada uma tenta alcançar.

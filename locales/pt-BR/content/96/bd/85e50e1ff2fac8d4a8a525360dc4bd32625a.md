# Introdução

Em um mundo ideal, poderíamos contar com tudo bem definido, com valores concretos e sem lacunas.

Isso entra em conflito com a nossa experiência cotidiana e, por isso, muitas linguagens de programação têm uma forma de representar a ausência de um valor: null ou NULL, nil, None, nothing...

Isso foi fácil de introduzir (lá em 1965), mas logo gerou arrependimentos.
Mais tarde, o inventor chamou isso de seu "Billion Dollar Mistake".

Nas últimas décadas, os projetistas de linguagens exploraram muitas formas de deixar os nulls disponíveis, mas (em geral) seguros.

O Kotlin tem alguns [princípios gerais][ref-null-safety], que diferem bastante do Java.


- O Kotlin tem um valor `null` especial.
- Todos os tipos são, _por padrão_, não anuláveis.
- A maioria dos tipos pode ser _tornada_ anulável, mas o programador precisa pedir isso explicitamente.
- Funções que podem falhar com uma exceção provavelmente têm uma variante com valor de retorno anulável.
- Uma sintaxe especial e bem concisa busca facilitar ao máximo testar nulls e responder a eles.

## Criando variáveis anuláveis

Os tipos padrão geralmente têm um equivalente anulável, com o sufixo `?`: por exemplo, `String?` em vez de `String`.

```kotlin
var a = "Kotlin"  // inferred type is String
a = null          // => Error: Null can not be a value of a non-null type String

var b: String? = "Kotlin"  // nullable type
b = null                   // => b is now null
b == null                  // => true
```

## Operadores e funções úteis

### O operador de chamada segura `?.`

Para uma `String` não anulável, podemos obter a propriedade `.length`.

Uma `String?` anulável falha com a mesma sintaxe, mas usar `?.length` permite a possibilidade de um `null`.
O tipo de retorno é `Int?`.

```kotlin
var a = "Kotlin"
a.length  // => 6

// b is still null
b.length  // => Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type String?
b?.length // => null
a?.length // => 6
```

Como vimos na última linha acima, `?.` também funciona com tipos não anuláveis.

### O operador Elvis `?:`

Ampliando a ideia do operador de chamada segura, o [operador Elvis][wiki-elvis] permite fornecer um valor padrão para substituir o `null`.

```kotlin
// b is still null
b?.length ?: -1  // => -1, in place of null
a?.length ?: -1  // => 6, as before
```

### O operador de asserção de não nulo `!!`

Com esse operador, um tipo anulável é forçado a ser tratado como não nulo, quando o programador tem certeza disso.
Talvez às vezes entendamos a lógica do programa melhor do que um compilador cauteloso demais?

```kotlin
// b is still a String?
b = "Kotlin?"
b!!.length  // => 7
```

A responsabilidade agora é nossa: se `b` ainda for `null`, recebemos uma `NullPointerException`.

### A função `let` e o `?.let`

Se formos passar um item anulável para um bloco de código, poderíamos fazer verificações de null específicas com `if (item != null) { do something }`.

É mais simples e mais idiomático usar `item?.let { do something }`,
O `do something` só será executado quando `item` não for null.

### Funções do tipo `somethingOrNone()`

Algumas funções podem falhar, por exemplo, ao pedir um índice inválido em uma string ou lista.

Em vez de lançar uma exceção, poderíamos usar a variante `...OrNull` da função, para obter (nesse caso) um valor de retorno `Int?`.

```kotlin
val str = "Kotlin"
str.elementAtOrNull(10)  // => null
str.elementAt(10)  // => StringIndexOutOfBoundsException: String index out of range: 10
```

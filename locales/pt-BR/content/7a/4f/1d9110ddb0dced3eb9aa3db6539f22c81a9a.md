# Contribuindo com o track C

Agradecemos o seu interesse em contribuir com o track de linguagem C do Exercism!
Todas as contribuições são bem-vindas: um novo exercício, uma mudança nas ferramentas ou na documentação, uma issue aberta ou até mesmo um comentário em uma issue ou PR existente.
Este arquivo traz informações para ajudar você a começar.

Primeiro, leia a [documentação do Exercism][Exercism docs], em especial as informações sobre [como contribuir com um track de linguagem][contributing to a language track], porque esses documentos cobrem boa parte do básico.

Depois, repare que há algumas coisas específicas deste repositório, explicadas a seguir.

Incentivamos contribuições que tragam correções e melhorias para exercícios existentes.
Vale lembrar que os exercícios deste track precisam seguir os padrões definidos no repositório [problem-specifications][].
Mudanças nos testes ou na documentação de um exercício comum geralmente exigem um pull request naquele repositório antes de poderem ser incorporadas aos exercícios deste track.
Se estiver em dúvida, abra uma [issue][] no GitHub e vamos conversar sobre a mudança.

## Código de Conduta

Ajude a manter o Exercism acolhedor.
Leia e siga o [Código de Conduta][Code of Conduct].

## Fluxo de trabalho com Git

1. Fazer um fork e clonar.
2. Adicionar este repositório como um novo remote ao seu clone: `git remote add upstream https://github.com/exercism/c.git`
3. Criar uma nova branch: `git checkout -b name-of-branch`
4. Fazer commit e push como de costume na sua nova branch
5. Quando estiver pronto para enviar um pull request, fazer rebase da sua branch sobre a main do upstream, para poder resolver os conflitos: `git fetch upstream && git rebase upstream/main`. Talvez você precise fazer push para a sua branch com `--force` depois de resolver os conflitos.
6. Quando tudo estiver pronto, fazer push para a sua branch e criar o pull request como descrito abaixo.

## Issues

Acompanhamos bugs, melhorias e pedidos de suporte no repositório usando as [issues][] do GitHub.

Para discussões de nível mais alto sobre o projeto como um todo, veja as issues do repositório [discussions][].

### Good First Patch

Estamos tentando marcar as issues com "good first patch" quando achamos que elas podem ser resolvidas sem muito contexto sobre a base de código ou o funcionamento do Exercism. Para encontrá-las, faça uma busca por [good-first-patch][].

## Pull Requests

Seria ótimo se você seguisse estas [diretrizes simples para pull requests][pull request guidelines] ao criar o seu PR, mas isso não é obrigatório.

Os pull requests devem ter foco em uma única issue ou mudança.
Acolhemos bem mudanças no estilo do código e na redação, mas, se possível, abra um PR separado para essas mudanças.
Abra uma issue antes de criar um PR que faça mudanças significativas (que quebram compatibilidade) em um exercício existente ou mudanças em muitos exercícios. O melhor é discutir essas mudanças antes de fazer o trabalho.

Se a sua mudança for em um exercício, você pode rodar os scripts de CI antes de enviar o pull request; caso contrário, eles rodarão automaticamente depois, como descrito em [integração contínua][Continuous Integration].

Ao enviar um pull request, às vezes vamos pedir que você faça mudanças antes de aceitarmos o patch.

Não feche o primeiro pull request para abrir um segundo com essas mudanças.
Se você fizer mais commits em uma branch para a qual já abriu um pull request, ele é atualizado automaticamente.

Se você quiser criar um PR com mudanças que ainda não estão prontas para serem mescladas na main (talvez você queira discutir algum ponto específico, por exemplo), crie o PR normalmente, mas use a interface do site do GitHub para [converter o PR para rascunho][convert the PR to a draft], para que os mantenedores saibam que ele ainda não está pronto para ser mesclado.

Assim como ao adicionar mais commits, você não precisa fechar o seu pull request e abrir outro se mudar o histórico (rebase, squash, amend) e usar git push --force para atualizar a branch no seu fork.
O pull request aponta para essa branch, não para commits específicos.

## Estilo de código

O estilo de código esperado nas contribuições de mudança de código está explicado no [guia de estilo][style guide].

O código dos exercícios é verificado durante a [CI][Continuous Integration] quanto à conformidade com as regras de espaçamento e indentação.
A verificação usa a ferramenta de CLI [`clang-format`][clang-format].
Ao adicionar um exercício ou fazer uma mudança nele, você pode verificar se a sua mudança segue essas regras rodando a ferramenta localmente antes de fazer o commit.

No Linux, o `clang-format` deve estar disponível para instalação pelo gerenciador de pacotes da sua distribuição.
No Mac, você pode instalar o pacote `clang-format` usando o [Homebrew][].

O clang-format pode ser rodado em todos os arquivos executando `format.sh`.
Para rodá-lo manualmente em um único arquivo, execute o seguinte:

```bash
clang-format -i $(file)
```

## Anatomia de um exercício

Cada exercício deve ficar em um diretório `c/exercises/practice/{exercise-name}`.
Veja [implement-an-exercise-from-specification][] para detalhes aprofundados sobre como implementar um exercício que corresponda à especificação

A estrutura de um diretório de exercício é a seguinte (repare no uso diferente de hífen e sublinhado para nomes de diretórios e de arquivos, respectivamente):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - Este arquivo contém todos os testes do exercício.  
`test-framework` - diretório que contém o harness de testes [Unity][] do [ThrowTheSwitch][].  
  O ThrowTheSwitch tem um guia decente de [primeiros passos com o Unity][getting started with Unity], caso você queira um tutorial.  
  A versão do Unity usada é indicada em [versões][versions]. O layout do arquivo de teste é descrito no [guia de estilo][test-file-layout].  
  Os testes devem ser escritos para satisfazer o arquivo `canonical-data.json` do exercício no repositório [problem-specifications][]  
`{exercise-name}.c` / `{exercise-name}.h` - Os arquivos-fonte do exercício.  
  Use [guardas de inclusão][include guards] nos seus arquivos de cabeçalho.
  Os testes do exercício podem ser rodados com `make test` a partir da raiz do repositório.
* `makefile` - é o makefile do exercício como ele seria compilado.  
Duas regras são obrigatórias,  
test: compila test_{exercise-name}.c e o executa.
memcheck: compila test_{exercise-name} com as flags -fsanitize=address, -fno-common, -fno-omit-frame-pointer e o executa
Espera-se que os makefiles mudem muito pouco entre exercícios, então deve ser fácil copiar um de outro exercício.

**Não esqueça** de adicionar o exercício ao `config.json` do track. Para isso, você vai precisar determinar o melhor lugar para adicionar o exercício na ordem de todos os outros exercícios do track. Você também vai precisar gerar um UUID para colocar aqui. Para as duas tarefas, você pode usar a ferramenta [configlet][]; ela ainda faz lint e formata o `config.json` para você depois que você fizer essas mudanças!

A propósito: para obter o artefato de instalação da ferramenta configlet, acesse a [página de releases do configlet][].

## Integração contínua

Este repositório usa fluxos de trabalho do GitHub para rodar algumas ferramentas a cada commit em um pull request.
A forma mais simples de rodar esses fluxos de trabalho na sua própria contribuição é abrir um PR neste repositório com as suas mudanças, marcar o PR como rascunho e deixar que a configuração de CI deste repositório cuide de tudo automaticamente para você.

### Ambiente de CI

O GitHub roda a CI em máquinas virtuais que ele chama de [runners hospedados][hosted runners].
Os fluxos de trabalho podem configurar alguns aspectos dos runners em que querem rodar.

Os fluxos de trabalho deste repositório especificam apenas que cada um deve rodar no Ubuntu 24.04. Eles são fixados em versões específicas, em vez de usar `latest`, porque algumas ferramentas usadas podem se comportar de forma diferente em versões diferentes.

### Rodar a CI no seu próprio fork

Se você quiser, também é possível rodar a CI no seu próprio fork: basta clonar este repositório normalmente no GitHub.
Os arquivos YAML que ficam em [`./.github/workflows/`][workflows] devem funcionar da mesma forma.
Se você quiser que a ação automatizada [`/format`][format-workflow] funcione corretamente, vai precisar adicionar uma chave de deploy ao repositório clonado.

### Os fluxos de trabalho

* O `checks.yml` roda o `shellcheck` nos scripts das ferramentas e, em seguida, roda as seguintes dessas ferramentas:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * a ação do [verificador de links Lychee][lychee]
* O `configlet.yml` busca a versão mais recente do configlet e então roda o comando `lint` no track
* O `format-code.yml` procura a string `/format` em qualquer comentário de um PR; se a encontrar, o `format.sh` é rodado nos exercícios e todas as mudanças resultantes são commitadas. É preciso uma chave de deploy para que o commit consiga disparar a CI de novo. A chave de deploy é administrada diretamente pelo Exercism.
* O `test.yml` roda o `make` na raiz do repositório para testar todos os exercícios

### As ferramentas

Você pode ver pelos [fluxos de trabalho][workflows] que o GitHub é instruído a rodar ferramentas do diretório [`./bin`][bin].
O trabalho que as ferramentas deste diretório fazem é descrito a seguir:

* `check-unitybegin` garante que todo arquivo de teste adiciona corretamente a linha `UNITY_BEGIN()` no início da sua função `main()`.
* `fetch-configlet` busca a ferramenta `configlet` do seu [repositório][configlet].
* `verify-unity-version` confere a versão do framework de testes Unity usada por cada exercício. A versão que este arquivo deve verificar está especificada em [`./docs/VERSIONS.md`][versions]
* `check-include-guards` confere se as guardas de inclusão usadas no stub e no cabeçalho de exemplo de cada exercício estão no formato correto, que é este:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* `fetch-configlet` busca a ferramenta `configlet` do seu [repositório][configlet].

### Rodar as ferramentas localmente

Você também pode rodar ferramentas individuais na sua própria máquina antes de fazer o commit.
Primeiro, verifique se você tem os aplicativos necessários instalados (como `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] e um compilador C) e, depois, rode a ferramenta desejada a partir da raiz do repositório. Por exemplo:

```bash
~/git/c$ make
```

Se você quiser rodar apenas alguns dos testes para conferir o seu trabalho, pode especificá-los como alvos do make.

```bash
~/git/c$ make acronym all-your-base allergies
```

## Runner de testes

Este track tem um runner de testes para o Exercism v3!
Você pode conferir [aqui][c-test-runner].

Os runners de teste oferecem um método dockerizado para rodar os testes de um exercício contra o código de um estudante no Exercism v3.
Essa abordagem com Docker ajuda a permitir que os estudantes programem direto no navegador.

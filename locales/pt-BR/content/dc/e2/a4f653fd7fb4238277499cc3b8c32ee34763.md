# Anexo das instruções

## A tarefa

Implemente dois procedimentos.

- `custom_error_message message` gera um erro, e `message` é a mensagem de erro.
- `handle_error script` roda o script dado e retorna uma string que descreve o que aconteceu:

  | Quando o script…                  | retorno                |
  | --------------------------------- | ---------------------- |
  | divide por zero                   | `"division by zero"`    |
  | abre um arquivo que não existe    | `"file does not exist"` |
  | chama um proc que não existe      | `"proc does not exist"` |
  | gera qualquer outro erro          | `"unknown error"`       |
  | termina com sucesso               | `"success"`             |

## Gerando erros

O Tcl tem dois comandos para gerar um erro.

```tcl
error "something went wrong"
throw {MYAPP BADTHING} "something went wrong"
```

`throw` exige um _código de erro_ como primeiro argumento.
O código de erro é uma lista que diz ao tratador que tipo de erro aconteceu, para que ele possa responder sem analisar o texto da mensagem.
O conteúdo fica a seu critério: `{MYAPP BADTHING}` é só um exemplo, e qualquer lista não vazia serve.
Por convenção, ele vai do geral para o específico.
Um tratador o captura com um padrão `try ... trap` correspondente (descrito abaixo), como `trap {MYAPP BADTHING}`, ou `trap {MYAPP}` para capturar todo erro `MYAPP`.
`error` aceita um código de erro opcional como terceiro argumento: `error message ?info? ?code?`.

## Tratando erros com `catch`

[`catch`][catch] roda um script e retorna um número inteiro, o _código de conclusão_, em vez de gerar o erro:

| código | significado |
| ------ | ----------- |
| 0      | `ok`        |
| 1      | `error`     |
| 2      | `return`    |
| 3      | `break`     |
| 4      | `continue`  |

```tcl
if {[catch {expr {1 / 0}} result options] == 1} {
    puts "error message: $result"
    puts "error code:    [dict get $options -errorcode]"
}
```
```none
error message: divide by zero
error code:    ARITH DIVZERO {divide by zero}
```

O segundo argumento opcional recebe o resultado (ou a mensagem de erro).
O terceiro argumento opcional recebe um _dicionário de opções_, que tem o `-errorcode` e o `-errorinfo` (o rastreamento da pilha).

Prós:

- É pequeno e flexível.
- É curto para casos simples, como `if {[catch {open $f} fh]} {...}`.

Contras:

- Você precisa verificar o código de conclusão por conta própria.
  Um `if {[catch ...] != 0} { handle error }` descuidado trata `return`, `break` e `continue` como erros também.
- Erros que você não trata são engolidos, a menos que você mesmo os relance.
- Não há um jeito nativo de rodar código de limpeza, tenha o script falhado ou não.

## Tratando erros com `try`

[`try`][try] roda um script e envia o resultado ao primeiro tratador correspondente.
Uma cláusula `finally` opcional sempre roda, o que faz dela um bom lugar para liberar recursos como canais de arquivo.

```tcl
set fh [open $filename r]
try {
    set data [read $fh]
} on error {msg options} {
    puts "could not read $filename: $msg"
} finally {
    close $fh
}
```

Prós:

- A estrutura é clara: um tratador para cada tipo de resultado.
- `finally` sempre roda.
- Resultados que nenhum tratador corresponde são repassados a quem chamou sem alteração.

Contras:

- É um pouco mais verboso que `catch` para casos simples.

### `try ... on` versus `try ... trap`

Existem dois tipos de tratador.

`on code {msgVar optionsVar}` corresponde ao _código de conclusão_: `ok`, `error`, `return`, `break` ou `continue`.
Todo erro tem o código de conclusão `error`, então `on error` não distingue uma divisão por zero de um arquivo que não existe.
Você teria que olhar o texto da mensagem, o que é frágil: mensagens são feitas para humanos e podem mudar entre versões do Tcl.

```tcl
try {
    expr {$a / $b}
} on error {msg} {
    if {[string match "*divide by zero*" $msg]} { ... }
}
```

`trap pattern {msgVar optionsVar}` corresponde ao _código de erro_.
O tratador corresponde quando o padrão é um prefixo da lista `-errorcode`.
Isso identifica o tipo de erro de forma confiável.

```tcl
try {
    expr {$a / $b}
} trap {ARITH DIVZERO} {} {
    puts "division by zero"
} trap {} {msg} {
    puts "some other error: $msg"
}
```

Um padrão vazio, `trap {}`, corresponde a qualquer erro.
Os tratadores são verificados em ordem, então deixe o que pega tudo por último.

## Encontrando o código de erro

Onde `ARITH DIVZERO` está documentado?
Na maior parte das vezes, só no código-fonte, mas o Tcl mostra para você.
Depois de um erro, a variável global `errorCode` guarda o código de erro do erro mais recente:

```none
$ tclsh
% set a 1; set b 0
% expr {$a / $b}
divide by zero
% set errorInfo     ;# this is the stack trace
divide by zero
    while executing
"expr {$a / $b}"
% set errorCode     ;# this is what we're after
ARITH DIVZERO {divide by zero}
```

Dentro de um programa, pegue-o do dicionário de opções:

```tcl
try {
    expr {$a / $b}
} on error {msg options} {
    puts [dict get $options -errorcode]
}
```

O último elemento de um código de erro costuma ser uma mensagem legível para humanos, ou o nome da coisa que causou o erro.
Deixe-o de fora do seu padrão `trap`: use `{ARITH DIVZERO}`, não `{ARITH DIVZERO {divide by zero}}`.

### Alguns códigos de erro comuns

Esta tabela não é completa.
Use a técnica acima para descobrir o código de qualquer outro erro.

| Situação                   | Exemplo                  | Código de erro                |
| -------------------------- | ------------------------ | ----------------------------- |
| Divisão por zero           | `expr {1 / 0}`           | `ARITH DIVZERO ...`           |
| Erro de domínio matemático | `expr {sqrt(-1)}`        | `ARITH DOMAIN ...`            |
| Arquivo não encontrado     | `open nosuchfile r`      | `POSIX ENOENT ...`            |
| Permissão negada           | `open /root/x w`         | `POSIX EACCES ...`            |
| Comando desconhecido       | `no::such::proc`         | `TCL LOOKUP COMMAND name`     |
| Variável desconhecida      | `set nosuchvar`          | `TCL LOOKUP VARNAME name`     |
| Número de argumentos errado | `string length a b`     | `TCL WRONGARGS`               |
| Dicionário inválido        | `dict size {1 2 3}`      | `TCL VALUE DICTIONARY`        |
| Lista inválida             | `llength "a \{b"`        | `TCL VALUE LIST ...`          |

Os códigos de erro `POSIX` usam os nomes de `errno` do sistema operacional, como `ENOENT`, `EACCES` e `EEXIST`.

## Dica: onde o script roda

`handle_error` recebe um script de quem a chamou.
Se você rodá-lo com `try $script`, ele é avaliado no escopo de `handle_error`, não no de quem chamou.
Para avaliá-lo onde ele foi escrito, use [`uplevel`][uplevel]: `try {uplevel 1 $script} ...`.

# Introdução

## SIMD: Bit a bit

Existem variantes empacotadas para a maioria das operações bit a bit escalares.
Elas seguem a mesma sintaxe geral das operações inteiras SIMD, mas não têm sufixo de tamanho:

| instrução | descrição                       |
|-------------|-----------------------------------|
| `pand`      | AND bit a bit de dois valores de 128 bits |
| `por`       | OR bit a bit de dois valores de 128 bits  |
| `pxor`      | XOR bit a bit de dois valores de 128 bits |

Repare que não existe um `NOT` empacotado.
No entanto, existe uma operação ANDN, que complementa (inverte todos os bits de) o operando de **destino** e depois calcula o AND entre os dois operandos.
Ela pode ser pensada como um NOT combinado com um AND:

| instrução | descrição                                                     |
|-------------|-----------------------------------------------------------------|
| `pandn`     | AND bit a bit do destino **complementado** com a origem |

Repare que uma operação bit a bit combina bits na mesma posição em dois operandos diferentes, então os limites das vias não podem mudar o resultado.
É por isso que essas instruções não têm sufixo de tamanho: o registrador se comporta como uma única via de 128 bits:

```x86asm
pand xmm0, xmm1   ; xmm0 = xmm0 AND xmm1
por  xmm2, xmm3   ; xmm2 = xmm2 OR xmm3
pxor xmm4, xmm5   ; xmm4 = xmm4 XOR xmm5
pandn xmm6, xmm7  ; xmm6 = (NOT xmm6) AND xmm7
```

~~~~exercism/note
Todas as instruções neste conceito calculam bits, mas não definem flags.
Um conceito posterior abordará condicionais com valores empacotados.
~~~~

### Deslocamentos por Via

Os deslocamentos, ao contrário das operações bit a bit puras, movem bits entre posições, então precisam de um tamanho de via para definir um limite.
Dentro de cada via, eles se comportam como seus equivalentes escalares, e os bits nunca passam de uma via para a vizinha:

| instrução               | descrição                         |
|---------------------------|-------------------------------------|
| `psllw`, `pslld`, `psllq` | deslocamento lógico para a esquerda, por via        |
| `psrlw`, `psrld`, `psrlq` | deslocamento lógico para a direita, por via       |
| `psraw`, `psrad`          | deslocamento aritmético para a direita, por via    |

Repare que essas instruções seguem a sintaxe das operações inteiras empacotadas, incluindo um sufixo de tamanho.
Não existe deslocamento de via de byte; apenas word, dword e, com exceção do deslocamento aritmético para a direita, qword.

Uma diferença entre os deslocamentos empacotados e seus equivalentes escalares está no nome da operação:

- Em vez de `shl` e `shr`, temos `sll` e `srl`, para **s**hift **l**eft (**r**ight) **l**ogical.
- Em vez de `sar`, temos `sra`, para **s**hift **r**ight **a**rithmetic.

Embora o nome seja diferente, a operação é a mesma:

- Um deslocamento lógico para a direita preenche os bits mais altos com zero.
  É equivalente a uma divisão sem sinal por uma potência de dois.
- Um deslocamento aritmético para a direita preenche os bits mais altos com o valor do bit de sinal.
  É equivalente a uma divisão com sinal por uma potência de dois, arredondando em direção ao infinito negativo.
- Um deslocamento para a esquerda sempre preenche com zero (é por isso que não há necessidade de um deslocamento aritmético para a esquerda).

A contagem de deslocamento é a mesma para todas as vias.
Ela pode ser um valor imediato, ou os 64 bits inferiores de um registrador `xmm`:

```x86asm
pslld xmm0, 4      ; each 32-bit lane shifted left by 4
psrlw xmm1, 1      ; each 16-bit lane shifted right by 1, zero-filled
psrad xmm2, xmm3   ; each 32-bit lane shifted right by the count in xmm3, sign-filled
```

~~~~exercism/note
Uma contagem de deslocamento maior que a largura da via não dá a volta como a família escalar `shl`/`shr`.
Ela simplesmente produz zero (ou todos os bits de sinal, no caso do deslocamento aritmético para a direita).
~~~~

### Operações Bit a Bit de Ponto Flutuante

Cada instrução bit a bit também tem versões gêmeas com nomes de ponto flutuante, seguindo a mesma sintaxe que vimos para operações empacotadas de ponto flutuante:

| nome da versão inteira | nomes da versão de ponto flutuante          |
|--------------|----------------------|
| `pand`       | `andps`, `andpd`     |
| `pandn`      | `andnps`, `andnpd`   |
| `por`        | `orps`, `orpd`       |
| `pxor`       | `xorps`, `xorpd`     |

Como as operações bit a bit atuam sobre bits, na prática as operações inteiras e de ponto flutuante calculam o mesmo resultado.
Os nomes diferentes existem por dois motivos:

1. Documentar a intenção, da mesma forma que preferiríamos `movdqa`, `movaps` ou `movapd` de acordo com a natureza dos bytes copiados.
2. Operações inteiras e de ponto flutuante costumam ter domínios de execução diferentes.
   Operações dentro do mesmo domínio de execução geralmente podem ser sequenciadas mais rapidamente.

Não há operação de deslocamento para valores de ponto flutuante.

### Representação em Bits de Ponto Flutuante

Um número de ponto flutuante IEEE tem uma representação em bits muito diferente da de um inteiro.

Em um inteiro sem sinal, cada bit tem um significado uniforme: ele representa uma potência de dois correspondente ao índice do bit.
O inteiro é a soma das potências de dois correspondentes aos bits definidos.
É por isso que deslocar os bits pode multiplicar ou dividir o número por uma potência de dois: estamos apenas mudando o índice de cada bit definido.

Em um inteiro com sinal, a maioria dos bits é interpretada da mesma forma que em um inteiro sem sinal.
No entanto, o bit mais alto é especial.
Se ele estiver definido, em vez de ser somado aos outros, precisamos subtrair a potência de dois correspondente, o que resulta em um número negativo.
Na prática, para mudar o sinal de um número, conceitualmente precisaríamos de dois passos: inverter todos os bits (um `not`) e depois somar 1 ao resultado (um `inc`).

Os bits em números de ponto flutuante não têm um significado uniforme e precisam ser interpretados de maneiras muito diferentes de acordo com sua posição:

| campo    | índices (32 bits) | índices (64 bits) |
|----------|------------------|------------------|
| sinal     | 31               | 63               |
| expoente | 30-23            | 62-52            |
| fração | 22-0             | 51-0             |

O número resultante é calculado por `(-1)^sign * 1.fraction * 2^(exponent - bias)`.
O bias depende da precisão:

| tamanho   | bias |
|--------|------|
| 32 bits | 127  |
| 64 bits | 1023 |

Em ambos os formatos, o sinal do número é determinado exclusivamente pelo bit de sinal.
Mudar o sinal de um número de ponto flutuante é feito apenas invertendo esse bit (uma operação XOR).
Obter o valor absoluto é feito apenas zerando esse bit (um AND no qual o bit é zerado):

```x86asm
section .rodata
align 16
abs_mask:  dd 0b0_11111111_11111111111111111111111, 0x7FFFFFFF, 0x7FFFFFFF, 0x7FFFFFFF ; same number in binary and hexadecimal
sign_mask: dd 0b1_00000000_00000000000000000000000, 0x80000000, 0x80000000, 0x80000000 ; same number in binary and hexadecimal

section .text
fn:
  andps xmm0, [rel abs_mask]  ; absolute value: clear the sign bit of all 4 floats
  xorps xmm1, [rel sign_mask] ; negation: flip the sign bit of all 4 floats
  ...
```

Repare que, nessa representação em bits, deslocar os bits não tem um resultado previsível e uniforme.
A fração pode "transbordar" para o expoente e o expoente, para o sinal.

No entanto, às vezes é conveniente isolar as diferentes partes da representação para operar sobre elas.

Por exemplo, os bits no expoente devem primeiro ser interpretados como um número sem sinal, antes que o bias seja subtraído dele.
Isso significa que podemos produzir um inteiro de 32 ou 64 bits cuja representação em bits subjacente corresponde a alguma potência de dois no formato de ponto flutuante correspondente.
Então essa representação bruta em bits pode ser usada para multiplicar ou dividir algum outro número de ponto flutuante.

Por exemplo:

```x86asm
mov eax, 210             ; in the exponent position, this would be 2^(210 - 127) = 2^83 in a 32-bit floating-point number
shl eax, 23              ; the bits are now in the correct position for the exponent of a 32-bit floating-point number
movd xmm0, eax           ; we move the raw bits to xmm0
mulss xmm1, xmm0         ; we are multiplying a 32-bit floating-point number in xmm1 by 2^83
```

Por outro lado, poderíamos extrair os expoentes de números de ponto flutuante empacotados realizando um AND com uma máscara em que os bits do expoente estão definidos e todos os outros estão zerados.
Combinado com um deslocamento e uma subtração, isso produz o expoente sem bias de cada via como um inteiro com sinal:

```x86asm
section .rodata
align 16
exp_mask: dd 0b0_11111111_00000000000000000000000, 0x7F800000, 0x7F800000, 0x7F800000 ; same number in binary and hexadecimal
bias: dd 127, 127, 127, 127

section .text
fn:
  movdqa xmm0, [rel values]   ; 4 packed 32-bit floating-point numbers
  pand   xmm0, [rel exp_mask] ; keep bits 30-23
  psrld  xmm0, 23             ; slide the exponent field to the bottom of each lane
  psubd  xmm0, [rel bias]     ; remove the bias
  ...
```

~~~~exercism/caution
Operar sobre os bits brutos de números de ponto flutuante, embora seja útil em algumas situações, deve ser feito com cautela.
Somar ou subtrair do campo do expoente só é seguro se não houver overflow nem underflow e se o número de entrada for normal.
Além disso, somar um `x` válido ao campo do expoente de `0.0` resulta em `2^(x - bias)`, não em `0.0 * 2^x`.
~~~~

# Sobre

A [pilha de chamadas][stack], ou simplesmente **pilha**, é uma estrutura de dados especial que começa no ponto mais alto da memória e cresce para baixo.

## Push e Pop

A pilha oferece suporte a pelo menos duas operações, com instruções de mesmo nome:

| Instrução | Operação realizada                                       |
| ----------- | --------------------------------------------------- |
| `push`      | adiciona um elemento à pilha                        |
| `pop`       | remove e retorna o elemento adicionado mais recentemente |

Isso significa que a pilha é uma estrutura de dados **último a entrar, primeiro a sair (LIFO)**.

Para acompanhar o ponto atual da pilha, onde está o elemento mais recente, usa-se o registro `rsp`.

Assim, uma instrução [push][push] recebe um operando e armazena o conteúdo desse operando na pilha.
Como a pilha cresce para baixo, o valor em `rsp` é reduzido pelo tamanho do valor armazenado.

De forma semelhante, uma instrução [pop][pop] recebe um operando e armazena nele o valor mais recente da pilha (aquele apontado por `rsp`).
O valor em `rsp` é então aumentado pelo tamanho do valor recuperado.

## Variáveis Locais

Também é possível manipular o valor de `rsp` diretamente.
Isso costuma ser usado para criar variáveis locais para uma função.

```x86asm
sub rsp, 24 ; this reserves 24 bytes of space in the stack
add rsp, 24 ; this restores the previous value of rsp, "reducing" the stack by 24 bytes
```

Repare que, no momento em que o espaço é reservado na pilha, o valor armazenado nesse espaço é _indefinido_.

~~~~exercism/note
Nem `pop` nem a manipulação direta de `rsp` removem de fato o conteúdo armazenado na memória.
A "remoção" da pilha é abstraída a partir do novo endereço em `rsp`.

Em alguns contextos, isso pode causar problemas de segurança ao expor valores internos a fontes externas.
Uma forma de lidar com isso é zerar o conteúdo de qualquer espaço da pilha usado pela função.
~~~~

## Call e Ret

O principal objetivo da pilha é acompanhar o endereço de retorno das funções chamadas.

Como mencionado em um conceito anterior, existe um registro especial chamado `rip` que aponta para a próxima instrução a ser executada.
Esse registro é usado para controlar o fluxo de um programa, sendo modificado por instruções como `jmp` e `call`.

Sempre que uma instrução `call` é usada, o valor atual em `rip` é inserido implicitamente na pilha.
Em seguida, o operando da instrução é movido para `rip`, de modo que a execução continua na função chamada.

Uma instrução `ret` faz a operação oposta.
Ela remove um valor da pilha e o coloca em `rip`, de modo que a execução retorna para a função chamadora.

No ponto de entrada, `rsp` aponta para o endereço a ser retornado.
Esse é o endereço que `ret` deve remover da pilha.

Portanto, qualquer mudança no valor de `rsp` dentro de uma função, seja diretamente ou com `push`, deve ser revertida antes que a função retorne.

## Registradores preservados pela função chamada e pela função chamadora

Além de `rsp`, existem outros registradores que devem ser preservados entre chamadas de função: `rbp`, `rbx`, `r12`, `r13`, `r14` e `r15`.
Em geral, a função chamadora espera poder usar esses registradores sem que eles sejam alterados por uma função chamada.

Isso significa que a função _chamada_ deve salvar os valores desses registradores antes de usá-los e restaurá-los aos valores originais antes de retornar.
É por isso que eles são chamados de **registradores preservados pela função chamada**.

Outros registradores de uso geral ficam diretamente disponíveis para uso pela função chamada.

Isso significa que a função _chamadora_ deve salvar os valores desses registradores antes de chamar qualquer função, caso eles sejam modificados pela função chamada.
É por isso que eles são chamados de **registradores preservados pela função chamadora**.

_A forma mais comum de salvar o conteúdo de um registro é armazená-lo na pilha._

## Prólogo e Epílogo

Em alguns casos, a pilha pode ser bastante usada, com muitas modificações antes de a função retornar.
Assim, acompanhar todas essas mudanças para revertê-las pode ser complexo.

Nesses casos, uma estratégia comum é salvar o endereço de `rsp` em outro registro que, fora isso, permaneça inalterado dentro da função.
E então, o valor de `rsp` pode ser restaurado com uma simples instrução `mov` no final, antes que a função retorne.

Embora qualquer registro possa ser usado para esse propósito, é convencional usar `rbp` como ponteiro de base.
Como `rbp` também é um registrador preservado pela função chamada, isso geralmente é precedido por um `push rbp`.
Essa sequência costuma ser chamada de **prólogo**.

No final, a restauração de `rsp` é feita com um `mov rsp, rbp` e então `rbp` também é restaurado com um `pop` da pilha.
Essa sequência costuma ser chamada de **epílogo**.

```x86asm
section .text
fn:
    ; prologue
    push rbp
    mov rbp, rsp
    ...
    ; epilogue
    mov rsp, rbp
    pop rbp
    ret
```

~~~~exercism/note
O principal objetivo das sequências de prólogo/epílogo é ajudar o programador a acompanhar as mudanças em `rsp`.
Isso é, é claro, muito mais fácil para um compilador fazer.

É por isso que muitos compiladores aplicam uma otimização para omitir o ponteiro de frame e remover prólogos/epílogos sempre que possível.
~~~~

## Passando Argumentos pela Pilha

Na convenção de chamada [System V ABI][SystemV], os argumentos geralmente são passados às funções em registradores.
Porém, quando há argumentos demais, ou quando eles precisam de mais espaço do que o tamanho de um registro, a pilha pode ser usada.

Nesses casos, os valores são adicionados à pilha em ordem inversa, de modo que o primeiro argumento fica mais próximo de `rsp`.
Como, no ponto de entrada, `rsp` aponta para o endereço de retorno, que é um valor de 8 bytes em x86-64, o primeiro argumento na pilha, se houver, pode ser acessado em `rsp + 8`:

```x86asm
mov rdi, 4   ; first argument
mov rsi, 8   ; second argument
mov rdx, 15  ; third argument
mov rcx, 16  ; fourth argument
mov r8, 23   ; fifth argument
mov r9, 42   ; sixth argument

; any remaining integer argument goes on the stack in reversed order
sub rsp, 16
mov qword [rsp], 100      ; seventh argument
mov qword [rsp + 8], 300  ; eighth argument

call many_arguments_fn ; call implicitly pushes `rip` to the stack
; so, at point of entry, 'many_arguments_fn' finds the first six integer arguments in the usual registers
; the seventh argument is found in rsp + 8
; and the eighth argument is found in rsp + 16
```

## Alinhamento da Pilha

A System V ABI determina que a pilha precisa estar alinhada a 16 bytes imediatamente _antes_ de a instrução call ser executada.
Como `call` insere `rip` na pilha, no ponto de entrada a pilha da função chamada **não** está alinhada a 16 bytes.

Isso significa que uma função que chama outra (e, em especial, funções externas) precisa alinhar a pilha antes de usar `call`.

Isso pode ser feito subtraindo um valor adequado de `rsp`.
No ponto de entrada, esse valor deve ser 8 a mais que um múltiplo de 16: 8, 24, 40, etc.
Como uma instrução `push` subtrai de `rsp`, um número ímpar de `push` pode ser usado para o mesmo efeito:

```x86asm
fn_a:
    sub rsp, 24 ; subtracting 8 more than a multiple of 16: this aligns the stack
    call fn_b
    add rsp, 24
    ret

fn_b:
    push rbx    ; odd number of pushes: this aligns the stack
    call fn_c
    pop rbx
    ret
```

## Zona Vermelha

A System V ABI reserva um espaço de 128 bytes logo abaixo de `rsp` que pode ser usado sem nenhum ajuste de `rsp`.
Esse espaço é conhecido como [zona vermelha][red-zone]:

```x86asm
fn:
    mov [rsp - 8], rax ; this is safe to use because it is in the red zone
    ret                ; no need to restore rsp
```

A zona vermelha só é segura para uso por uma função folha, ou seja, uma que não chama outra.

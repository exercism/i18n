# Bevezetés

Eddig a tanterv nem sokat mondott a típusokról, de a Julia nyelvben nyilvánvalóan léteznek:

```julia-repl
julia> vals = (42, 4.3, π, "hello", 'Q')
(42, 4.3, π, "hello", 'Q')

julia> typeof(vals)
Tuple{Int64, Float64, Irrational{:π}, String, Char}
```

Sosem adtuk meg a típusokat, a Julia mégis hozzárendelte őket.

1. A Juliában vannak `types`, és ezek központi szerepet játszanak a nyelv felépítésében.
2. A Julia általában „ki tudja találni” a típust, a `Type Inference` segítségével.

A JIT-fordító átnézi az (összes) kódot, megnézi, hogyan használjuk a változót, és _következtet_ egy olyan alkalmas alapértelmezett típusra, amely kompatibilis ezzel a használattal.

## Típuspromóció

A korábbi fogalmakban számos példa akadt arra, hogy a numerikus típusok egységesítésre kerülnek, a legegyszerűbb aritmetikától kezdve.

```julia-repl
julia> 2 + 1.3
3.3
```

Összeadtunk egy egész számot (Int64) és egy lebegőpontos számot (Float64), és az eredmény Float64 lett.
Hasonlóképpen:

```julia-repl
julia> nums = (3, 4.1, 1//4)
(3, 4.1, 1//4)

julia> typeof(nums)
Tuple{Int64, Float64, Rational{Int64}}

julia> [nums...]
3-element Vector{Float64}:
 3.0
 4.1
 0.25
```

A fenti esetben a tuple megőrizte az egyes elemek típusát, de a vektorrá alakítás mindegyiket egységes Float64 típusúvá változtatta.

A Julia-fordító érti, hogy mely típuskonverziók lehetségesek: egész számból lebegőpontosba nincs gond, lebegőpontosból egész számba viszont pontosságvesztés történik, ezért `InexactError` keletkezik.
A típuspromóció a kifejezés összes értékét egy közös típusra alakítja, amely elég rugalmas ahhoz, hogy minden bemenettel kompatibilis legyen.

## Típus-hozzárendelés

Az egyszerű tanulófeladatok megoldásához elég, ha a típuskövetkeztetésre hagyatkozunk, de nagyobb programoknál valószínűleg pontosabb vezérlésre lesz szükséged.

A legtöbb modern processzoron az egész szám alapértelmezésben `Int64`.
A [`Numbers`][numbers] fogalomban láttuk, hogy egy érték átalakítható egy adott, nem alapértelmezett típusra.

```julia-repl
julia> x = Int16(42)
42

julia> typeof(x)
Int16
```

Az `x` változó azonban továbbra is hozzárendelhető egy másik típushoz:

```julia-repl
julia> x = "changed"
"changed"

julia> typeof(x)
String
```

Ez a `type instability`, ami:

- Kis szkripteknél nagyon kényelmes.
- Nagyobb programoknál árt a teljesítménynek és a megbízhatóságnak.

Ehelyett a `::` operátorral megadhatjuk `x` típusát:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> y = "changed"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Int16
The function `convert` exists, but no method is defined for this combination of argument types.
```

Mostantól `y` `Int16` típusú, és az is marad.
Így a fordító tudja, hány bájtot kell lefoglalnia számára, és a kód többi részét is optimalizálhatja arra alapozva, hogy a típus stabil.
Ebben a tekintetben a változó többé-kevésbé olyan, mint egy statikusan típusos nyelvben, például C-ben.

## Típusállítás

A fent leírt típus-hozzárendelés egy változó-hozzárendelés bal oldalán használható arra, hogy korlátozza a változó típusát.

Ha a `::` operátort egy értékkel, vagy valamivel, ami értékké értékelődik ki, használjuk, az általában egy _állítás_ arra vonatkozóan, hogy az értéknek ilyen típusúnak kell lennie, különben hibát kell dobni.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Gyakran egy függvény visszatérési értékével használják, egyszerű utolsó ellenőrzésként arra, hogy a függvény a várt módon viselkedett.

## A típushierarchia

`Int64`, `Int16`, `String`, `Char`: honnan _„származnak”_ ezek a típusok?

Sok objektumorientált (OO) nyelvben minden típus egy osztály, az alosztályozás osztályhierarchiába rendezi őket, az osztálymetódusok pedig meghatározzák a viselkedést.

A Java és a Ruby nyilvánvaló példa erre a mintára, de belül a Python is hasonló.

***A Juliában nincsenek osztályok.***

A dokumentált indoklás szerint az OO-szolgáltatások zavarják a JIT-fordítót, és rontják a futásidejű teljesítményt.

És mégis, nézd meg ezt a kódot:

```julia-repl
julia> y::Int16 = 42
42

julia> typeof(y)
Int16

julia> supertype(Int16)
Signed

julia> supertypes(Int16)
(Int16, Signed, Integer, Real, Number, Any)
```

Néhány részlet kiegészítéseként:

- Az `Int16` egy típus, és létrehozhatunk ilyen típusú változókat.
- Az `Int16` a `Signed` altípusa, amit a `supertype()` függvény meg is mutat.
- Létezik a típusoknak egy hierarchiája, amely az `Integer`, a `Real` és a `Number` szinteken át fel egészen a legfelső `Any`-ig tart, és a `subtypes()` felsorolja nekünk a hierarchia ezen ágát.

Minden ág az `Any`-ban végződik, amely egyedülálló abban, hogy a saját szupertípusa.

```julia-repl
julia> supertypes(String)
(String, AbstractString, Any)

julia> supertype(Any)
Any
```

A Juliában tehát nincs `class`-hierarchia, de `type`-hierarchia _van_.

Egyszer majd megpróbáljuk kibogozni, hogyan is működik ez, de előbb még sok mindent fel kell fedeznünk.

## Típusok vizsgálata

A `typeof()` segítségével a szokásos módon vizsgálhatjuk az egyenlőséget.

```julia-repl
julia> typeof(11)
Int64

julia> typeof(11) == Int64
true

julia> typeof(11) == Number
false
```

A típusegyenlőségnek pontosnak kell lennie, mert ez az összehasonlítási forma nem érti a típushierarchiát.

Rugalmasabban az `isa` megmondja, hogy egy érték típusa megegyezik-e az összehasonlítóéval, vagy annak altípusa-e.
Használható függvény formában és infix formában is.

```julia-repl
julia> 12 isa Int64
true

julia> 12 isa Number
true

julia> isa(12, Number)
true

julia> 12 isa String
false
```

Vedd észre, hogy az `isa` a bal oldalon egy `value`-t vár, nem egy `type`-ot.

Ha így próbálunk két _típust_ összehasonlítani, váratlan eredményt kapunk.
A helyes operátor a `<:`, amivel a későbbi fogalmakban még sokat fogunk találkozni.

```julia-repl
julia> Int64 isa Number  ## Don't do this!
false

julia> Int64 <: Number
true
```

## Absztrakt és konkrét típusok

Láttuk, hogy a típushierarchia fastruktúrát alkot (informatikai értelemben, a gyökérrel a tetején).

A fában minden elem egy `node`, és ezeket kategóriákba sorolhatjuk:

1. Az altípusokkal rendelkező csomópontokat `abstract`-nak nevezzük.
2. A levélcsomópontokat, amelyeknek nincs altípusuk, `concrete`-nak nevezzük.

```julia-repl
julia> subtypes(Integer)  # an abstract type
3-element Vector{Any}:
 Bool
 Signed
 Unsigned

julia> subtypes(Int64)  # a concrete type
Type[]
```

Ez fontos megkülönböztetés, mert változóként csak a konkrét típusokat lehet `instantiated`-ként létrehozni.


```julia-repl
julia> a::Int16 = 42
42

julia> typeof(a)
Int16

julia> b::Integer = 42
42

julia> typeof(b)
Int64
```

Vedd észre, hogy ha absztrakt típust próbálunk használni, az (ebben az esetben) nem ad hibaüzenetet, hanem a fordító létrehoz egy megfelelő konkrét típust: `Int64`-et `Integer` helyett.
Legalább megakadályozza, hogy a változóhoz nem egész számot rendeljünk:

```julia-repl
julia> f::Integer = "hello"
ERROR: MethodError: Cannot `convert` an object of type String to an object of type Integer
The function `convert` exists, but no method is defined for this combination of argument types.
```

Az absztrakt típussal végzett típus-hozzárendelés tehát egy _megkötés_ a változó típusára nézve: a (fenti esetben) `Integer` bármely altípusa lehet.
Ez szokatlan dolog a programozási nyelvek világában: gyengébb, mint egy típus-hozzárendelés C-ben, de erősebb, mint egy típusannotáció a Python újabb verzióiban.

Az `isabstracttype()` és az `isconcretetype()` függvénnyel tesztelhetünk.
Vedd észre, hogy ezek nem csupán egymás tagadásai: egy későbbi fogalomban látni fogjuk, hogy egyes típusok sem nem absztraktak, sem nem konkrétak.


```julia-repl
julia> isconcretetype(Integer), isabstracttype(Integer)
(false, true)

julia> isconcretetype(Int64), isabstracttype(Int64)
(true, false)

# Vector is neither
julia> isconcretetype(Vector), isabstracttype(Vector)
(false, false)
```

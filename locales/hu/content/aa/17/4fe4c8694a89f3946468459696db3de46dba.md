# Bemutatás

## Kontextus hozzáadása a hibákhoz

A Go alapvető hibakezelését a [hibák][concept-errors] fogalomban jártuk körbe.
Ahogy ott megtanultad, a hibák alapértelmezés szerint nem hordoznak magukkal stack trace-t.
Ezért kulcsfontosságú, hogy maga a hiba elegendő információt tartalmazzon a probléma azonosításához.

Ha a már ismert eszközökkel szeretnénk információt hozzáadni egy meglévő hibához, valami ilyesmit írhatnánk, hogy létrehozzunk egy új hibát az eredeti hiba és a kiegészítő információ összefűzött szövegével:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Szerencsére a standard könyvtár `fmt` csomagja tartalmaz erre egy rövidebb változatot az `Errorf` függvény formájában.
Ez például lehetővé teszi, hogy könnyedén hozzáadj információt arról a kontextusról, amelyben a hiba bekövetkezett.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Hacsak nem vagy biztos benne, hogy a hiba már elegendő információt tartalmaz, próbáld megszokni, hogy mindig kontextust adsz a hibához, mielőtt visszaadod egy függvényből.
Ez azt jelenti, hogy a szokásos hibakezelési mintádnak így kell kinéznie:

```go
result, err := calculateSomething()
if err != nil {
  return 0, fmt.Errorf("calculating something: %v", err)
}
```

Ahogy a példákban is látszik, a konvenció az, hogy kettősponttal választjuk el a hibát a hozzáadott üzenettől.
Ahogy az eredeti hiba üzenetét, úgy a kontextusüzenetet sem kezdjük nagybetűvel, és a végére sem teszünk pontot.

~~~~exercism/note
Amikor kontextust adsz egy hibához, csábító, hogy az üzenetet a „failed to ...” fordulattal vagy hasonlóval kezdd.
Mivel azonban a hiba a függvényláncon felfelé haladva rengeteg további kontextust gyűjthet össze, ez megnehezítheti annak a végső üzenetnek az olvasását, amely naplóba kerül vagy amelyet a felhasználó lát, és tele lehet ismétlődésekkel.

Íme egy példa szemléltetésképpen:

```text
failed to validate request: failed to parse path parameter: failed to convert number: invalid input "abc"
vs.
validating request: parsing path parameter: converting to number: invalid input "abc"
```

Tartsd hát szem előtt ezt a végeredményt a kontextusüzenetek írásakor, és tartózkodj attól, hogy arról írj, hogy valami nem a várt módon alakult.
Ez általában kiderül a kontextusból (pl. a naplószint „ERROR”) és az eredeti hibaüzenetből.
~~~~

Ez az információszerzési mód gyakran elég jó, de vannak esetek, amikor szeretnéd megengedni a hibád fogyasztójának, hogy ellenőrizze vagy lekérje az eredeti, mögöttes hibát.
Az ilyen módon hozzáadott kontextus neve Go-ban a hiba becsomagolása.

## Hibák becsomagolása és sentinel hibák keresése

A hibák becsomagolását a fent látott kód nagyon apró módosításával érhetjük el.
Egy hiba becsomagolásához a `%v` helyett a `%w` formázási igét kell használnod.
A színfalak mögött ez biztosítja, hogy a keletkező hiba rendelkezzen egy `Unwrap` metódussal, amely visszaadja az eredeti hibát.
Emiatt aztán az `errors.Is` használható annak ellenőrzésére, hogy egy adott sentinel hiba előfordul-e valahol a „hibaláncban”.
Ezt úgy éri el, hogy titokban ismételten meghívja az `Unwrap`-ot, amíg meg nem találja a kérdéses hibát, vagy véget nem ér a lánc.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Az eredeti hiba `errors.Is`-szel való keresése nem működne a szokásos `%v` formázási igével.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %v", originalError)
errors.Is(err, originalError)
// => false
```

Ennek eredményeként jó gyakorlat alapértelmezés szerint a `%v`-t használni, és csak akkor használni a `%w`-t, ha kifejezetten szeretnéd megengedni a fogyasztódnak, hogy hozzáférjen egy mögöttes hibához ([Google Go stílusútmutató][google-go-styleguide]).

Ha olyan helyzetbe kerülsz, amikor egy sentinel hibát szeretnél ellenőrizni, de kifejezetten nem akarod kicsomagolni, az `errors.Is` helyett használhatod a `==`-t.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Ezzel szemben a `==` nem azonosítaná a hibát, ha az be volt csomagolva.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return fmt.Errorf("parsing age: %v", originalError)
}

err := someFunc()
err == originalError 
// => false
```

Alapértelmezés szerint rendben van az `errors.Is`-szel dolgozni, de mindig legyél tudatában annak, hogy ez azt jelenti: a teljes hibaláncot át fogja kutatni.

## (Egyedi) hibatípusok keresése

Létezik az `errors.Is` megfelelője, amellyel egy adott típusú hibát lehet keresni és lekérni a hibaláncból.
Erre az `errors.As` függvény szolgál, és az `errors.Is`-hez hasonlóan a teljes lánc mentén keresi az adott hibatípust.
Az `errors.As` csak akkor nyeri ki a megtalált, a típusnak megfelelő hibát, hogy azzal tovább dolgozhass, például le tudj kérni bizonyos mezőket.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Figyelj a fenti pointerekkel kapcsolatos szintaxisra.
A kód csak akkor működik és fordul le helyesen, ha a `customError` pontosan azzal a típussal rendelkezik, amely megvalósítja az error interfészt.
A mi esetünkben ez a `*MyCustomError` (egy [pointer][concept-pointers] a `MyCustomError`-ra), nem pedig maga a `MyCustomError`.

Ráadásul a második argumentumnak a hibaváltozóra mutató pointernek kell lennie.
Mivel a hibánk már eleve egy pointer, amit az `errors.As`-nak átadunk, az egy pointerre mutató pointer (a MyCustomError-ra).
Csak így, helyesen beállítva tudja a Go feltölteni a változót a megtalált hibával.
~~~~

Ahogy korábban, az `errors.As` sem találta volna meg a hibatípust, ha az `Errorf` hívásakor a `%v`-t használtad volna.

Ha valamiért nem akarsz kicsomagolni, helyette type assertiont használhatsz (ami a fenti `==`-vel egyenértékű).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

A type assertion nem lesz képes azonosítani a hibatípust, ha a hibát becsomagolták volna.

## Egyedi típusú hibák kicsomagolásának engedélyezése

Néha nem elég, ha egy hibát csupán némi kiegészítő szöveggel csomagolunk be.
Helyette létrehozhatsz egy egyedi hibatípust, amely tárolja az eredeti hibát és a hozzáadni kívánt kiegészítő strukturált adatokat.
Ha engedélyezni szeretnéd a hibatípusod kicsomagolását, mindössze annyit kell tenned, hogy manuálisan hozzáadsz egy `Unwrap() error` metódust, amely teljesíti az `Unwrap` interfészt.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

## Több hiba egyesítése

A Go 1.20-ban egy új `Join` függvény került a beépített `errors` csomagba.
A `Join` lehetővé teszi több hiba egyesítését úgy, hogy közben a kicsomagolás is lehetséges marad, azaz egy adott hiba vagy hibatípus keresése a lánc mentén.
Ezzel a hibalánc a valóságban akár hibafa is lehet.
További információt a [kiadási megjegyzésekben][release-notes] és a [dokumentációban][doc-join] találsz.

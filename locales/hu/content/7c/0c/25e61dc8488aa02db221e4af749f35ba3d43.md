# Bevezetés

## Kontextus hozzáadása a hibákhoz

A Go alapvető hibakezelését a [hibák][concept-errors] fogalomnál vettük át.
Ahogy ott megtanultad, a hibák alapértelmezés szerint nem hordoznak magukkal stack trace-t.
Ezért kulcsfontosságú, hogy maga a hiba elegendő információt tartalmazzon a probléma azonosításához.

Ha a már ismert eszközökkel szeretnénk információt hozzáadni egy meglévő hibához, valahogy így írhatnánk egy új hibát, amely az eredeti hiba és a kiegészítő információ egyesített szövegét tartalmazza:

```go
err := errors.New(fmt.Sprintf("parsing age for user %d: %v", userID, originalError))
```

Szerencsére a standard könyvtár `fmt` csomagja kínál erre egy rövidített változatot az `Errorf` függvény formájában.
Ez például lehetővé teszi, hogy könnyedén hozzáadd azt a kontextust, amelyben a hiba keletkezett.

```go
originalError := errors.New("unexpected negative number")
userID := 123
err := fmt.Errorf("parsing age for user %d: %v", userID, originalError)
err.Error()
// => "parsing age for user 123: unexpected negative number"
```

Gyakran ez az információgazdagítás elég jó, de van, amikor szeretnéd, hogy a hibát feldolgozó kód ellenőrizni tudja vagy le tudja kérdezni az eredeti, mögöttes hibát.
A kontextus ilyen módon való hozzáadását a Go-ban „hiba becsomagolásának” nevezik.

## Hibák becsomagolása és sentinel hibák ellenőrzése

A hibák becsomagolását egészen kis változtatással elérheted a fenti kódon.
Egy hiba becsomagolásához a `%v` helyett a `%w` formázási verbet kell használnod.
A háttérben ez gondoskodik arról, hogy a keletkező hiba rendelkezzen egy `Unwrap` metódussal, amely az eredeti hibát adja vissza.
Emiatt aztán az `errors.Is` segítségével ellenőrizheted, hogy egy adott sentinel hiba megjelenik-e valahol a „hibaláncban”.
Ezt úgy teszi, hogy a háttérben ismételten meghívja az `Unwrap` metódust, amíg meg nem találja a kérdéses hibát, vagy véget nem ér a lánc.

```go
originalError := errors.New("unexpected negative number")
err := fmt.Errorf("parsing age: %w", originalError)
errors.Is(err, originalError)
// => true
```

Jó gyakorlat alapértelmezés szerint a `%v`-t használni, és csak akkor a `%w`-t, ha kifejezetten szeretnéd, hogy a hibát feldolgozó kód hozzáférjen a mögöttes hibához ([Google Go stílusútmutató][google-go-styleguide]).

Ha olyan helyzetbe kerülsz, hogy ellenőrizni szeretnél egy sentinel hibát, de kifejezetten nem szeretnéd kicsomagolni, az `errors.Is` helyett használhatod a `==` operátort.

```go
var originalError = errors.New("unexpected negative number")
func someFunc() error {
  return originalError
}

err := someFunc()
err == originalError 
// => true
```

Alapértelmezés szerint rendben van az `errors.Is` használata, de mindig legyél tisztában azzal, hogy ez a teljes hibalánc átkutatását jelenti.

## (Egyedi) hibatípusok ellenőrzése

Az `errors.Is`-nek van egy megfelelője, amellyel egy adott típusú hibát kereshetsz meg és kérdezhetsz le a hibaláncból.
Erre az `errors.As` függvény szolgál, és az `errors.Is`-hez hasonlóan a teljes láncban keresi a megadott hibatípust.
Az `errors.As` csak akkor emeli ki a megtalált, a típusnak megfelelő hibát, hogy tovább dolgozhass vele, például lekérdezhess bizonyos mezőket.

```go
type MyCustomError struct {
  Message string
  Details string
}

func (e *MyCustomError) Error() string {
  return fmt.Sprintf("%s, details: %s", e.Message, e.Details)
}

func someFunc() error {
  originalError := &MyCustomError{
    Message: "some message",
    Details: "some details",
  }

  return fmt.Errorf("doing something: %w", originalError)
}

err := someFunc()
var customError *MyCustomError
errors.As(err, &customError)
// => true

// customError now contains the error that was found in the error chain.
customError.Details
// => "some details"
```

~~~~exercism/caution
Figyelj a fenti mutatókhoz tartozó szintaxisra.
A kód csak akkor működik és fordul le helyesen, ha a `customError` pontosan az a típus, amely megvalósítja az error interfészt.
Esetünkben ez a `*MyCustomError` (egy [mutató][concept-pointers] a `MyCustomError`-ra), nem pedig maga a `MyCustomError`.

Ráadásul a második argumentumnak a hibaváltozóra mutató mutatónak kell lennie.
Mivel a hibánk már önmagában egy mutató, amit az `errors.As`-nek átadunk, az egy mutató mutatóra (a MyCustomError-ra).
Csak ha ez így van beállítva, akkor tudja a Go a változót a megtalált hibával feltölteni.
~~~~

Ahogy korábban is, az `errors.As` nem találta volna meg a hibatípust, ha az `Errorf` hívásakor a `%v`-t használtad volna.

Ha valamiért nem szeretnél kicsomagolni, helyette típus-állítást is használhatsz (ez a fenti `==` megfelelője).

```go
// MyCustomError defined as above.

func someFunc() error {
  return &MyCustomError{
    Message: "some message",
    Details: "some details",
  }
}

err := someFunc()
customError, ok := err.(*CustomError)
// "ok" is now true
customError.Details
// => "some details"
```

A típus-állítás nem tudja azonosítani a hibatípust, ha a hiba be volt csomagolva.

## Egyedi típusú hibák kicsomagolásának engedélyezése

Néha nem elég egy hibát némi kiegészítő szöveggel becsomagolni.
Ilyenkor létrehozhatsz egy egyedi hibatípust, amely az eredeti hibát és a hozzáadni kívánt strukturált adatokat tárolja.
Ha engedélyezni szeretnéd a hibatípusod kicsomagolását, mindössze annyit kell tenned, hogy kézzel hozzáadsz egy `Unwrap() error` metódust, így teljesül az `Unwrap` interfész.

```go
type SpecialError struct {
  originalError error
  metadata string
}

func (e *SpecialError) Error() string {
  // The usual serialization code goes here.
}

func (e *SpecialError) Unwrap() error {
  return e.originalError
}
```

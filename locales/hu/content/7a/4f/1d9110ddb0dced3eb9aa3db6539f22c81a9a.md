# Hozzájárulás a C kurzushoz

Köszönjük, hogy érdeklődsz, hogy hozzájárulj az Exercism C nyelvi kurzusához!
Minden hozzájárulást szívesen fogadunk, legyen az egy új feladat, a tooling vagy a dokumentáció módosítása, egy beküldött issue, vagy akár csak egy hozzászólás egy meglévő issue-hoz vagy PR-hoz.
Ez a fájl információkkal segít, hogy elkezdhesd.

Először is olvasd el az [Exercism dokumentációját][Exercism docs], különösen a [nyelvi kurzushoz való hozzájárulásról][contributing to a language track] szóló részt, mert ezek a dokumentumok sok alapvető információt lefednek.

Ezután vedd figyelembe, hogy néhány dolog kifejezetten erre a repositoryra jellemző, és ezeket az alábbiakban magyarázzuk el.

Bátorítjuk azokat a hozzájárulásokat, amelyek javításokat és fejlesztéseket hoznak a meglévő feladatokhoz.
Ne feledd, hogy ennek a kurzusnak a feladatainak meg kell felelniük a [problem-specifications][] repositoryban meghatározott szabványoknak.
Egy közös feladat tesztjeinek vagy dokumentációjának módosítása gyakran megköveteli, hogy először pull requestet nyiss abban a repositoryban, mielőtt bekerülhetne ennek a kurzusnak a feladataiba.
Ha bizonytalan vagy, nyugodtan nyiss egy GitHub [issue-t][issue], és megbeszéljük a változtatást.

## Magatartási kódex

Segíts abban, hogy az Exercism barátságos hely maradjon.
Kérjük, olvasd el és tartsd be a [Magatartási kódexet][Code of Conduct].

## Git-munkafolyamat

1. Forkold és klónozd.
2. Add hozzá ezt a repositoryt új remote-ként a klónodhoz: `git remote add upstream https://github.com/exercism/c.git`
3. Hozz létre egy új branch-et: `git checkout -b name-of-branch`
4. Committelj és pusholj a szokásos módon az új branch-eden
5. Amikor készen állsz egy pull request beküldésére, rebase-eld a branch-edet az upstream main-re, hogy feloldhasd az esetleges ütközéseket: `git fetch upstream && git rebase upstream/main` Előfordulhat, hogy az ütközések feloldása után `--force` kapcsolóval kell felpusholnod a branch-edre.
6. Amikor minden készen áll, pushold fel a branch-edre, és hozd létre a pull requestet az alábbiak szerint.

## Issue-k

A repositoryban GitHub [issue-k][issues] segítségével tartjuk nyilván a hibákat, fejlesztéseket és támogatási kéréseket.

A projektről mint egészről szóló magasabb szintű beszélgetésekhez nézd meg a [discussions][] repository issue-jait.

### Jó első patch

Igyekszünk „good first patch” címkével ellátni azokat az issue-kat, amelyekről úgy gondoljuk, hogy túl sok kontextus nélkül is megoldhatók az Exercism kódbázisával vagy működésével kapcsolatban. Hogy megtaláld őket, kereshetsz a [good-first-patch][] címkére.

## Pull requestek

Nagyon jó lenne, ha követnéd ezeket az egyszerű [pull request irányelveket][pull request guidelines] a PR létrehozása során, de nem kötelező.

A pull requestek egyetlen issue-ra vagy változtatásra összpontosítsanak.
Örömmel fogadunk változtatásokat a kódstílusban és a szövegezésben, de lehetőség szerint ezekhez külön PR-t nyiss.
Kérünk, hogy nyiss issue-t, mielőtt olyan PR-t hoznál létre, amely jelentős (törő) változtatásokat eszközöl egy meglévő feladaton, vagy egyszerre sok feladatot érint. A legjobb, ha a munka megkezdése előtt megbeszéljük ezeket a változtatásokat.

Ha a változtatásod egy feladatot érint, a pull request beküldése előtt lefuttathatod a CI-szkripteket, vagy azok automatikusan lefutnak utána, ahogy azt a [Folyamatos integráció][Continuous Integration] leírja.

Egy pull request beküldésekor néha arra kérünk, hogy változtass rajta, mielőtt elfogadjuk.

Kérünk, ne zárd be az első pull requestet, és ne nyiss egy másodikat ezekkel a változtatásokkal.
Ha további commitokat pusholsz arra a branch-re, amelyre pull requestet nyitottál, az automatikusan frissíti a pull requestet.

Ha olyan változtatásokkal szeretnél PR-t létrehozni, amelyek még nem állnak készen arra, hogy a main branch-be kerüljenek (például mert meg szeretnél vitatni valamit), hozd létre a PR-t a szokásos módon, de a GitHub webes felületén [alakítsd a PR-t piszkozattá][convert the PR to a draft], hogy a karbantartók tudják, még nem áll készen az egyesítésre.

Ahogy a további commitok hozzáadásakor, úgy akkor sem kell bezárnod a pull requestet és újat nyitnod, ha megváltoztatod a történetet (rebase, squash, amend), és a git push --force használatával frissíted a branch-et a forkodon.
A pull request arra a branch-re mutat, nem konkrét commitokra.

## Kódstílus

A kódváltoztatásokhoz elvárt kódstílust a [stílusútmutató][style guide] ismerteti.

A feladatok kódját a [CI][Continuous Integration] során ellenőrzik, hogy megfelel-e a térközökre és behúzásra vonatkozó stílusszabályoknak.
Az ellenőrzés a [`clang-format`][clang-format] parancssori felület eszközt használja.
Amikor új feladatot adsz hozzá vagy módosítasz egyet, a commitolás előtt helyben futtatva az eszközt ellenőrizheted, hogy a változtatásod megfelel-e ezeknek a szabályoknak.

Linuxon a `clang-format` általában telepíthető a disztribúciód csomagkezelőjével.
Macon a `clang-format` csomagot a [Homebrew][] segítségével telepítheted.

A clang-format az összes fájlon futtatható a `format.sh` végrehajtásával.
Ha egyetlen fájlon szeretnéd kézzel futtatni, a következőt hajthatod végre:

```bash
clang-format -i $(file)
```

## Egy feladat felépítése

Minden feladatnak a `c/exercises/practice/{exercise-name}` könyvtárban kell lennie.
A specifikációnak megfelelő feladat megvalósításának részletes leírását lásd: [feladat megvalósítása a specifikáció alapján][implement-an-exercise-from-specification].

Egy feladat könyvtárának szerkezete a következő (figyeld meg, hogy a könyvtárnevekben kötőjel, a fájlnevekben pedig alulvonás szerepel):

```text
+-- {exercise-name}
    +-- makefile
    +-- {exercise-name}.c
    +-- {exercise-name}.h
    +-- test_{exercise-name}.c
    +-- test-framework
    |   +-- unity.c
    |   +-- unity.h
    |   +-- unity_internals.h
```

`test_{exercise_name}.c` - Ez a fájl tartalmazza a feladat összes tesztjét.  
`test-framework` - a [ThrowTheSwitch][]-től származó [Unity][] tesztkeretrendszert tartalmazó könyvtár.  
  A ThrowTheSwitch-nek van egy jó útmutatója az [Unity használatának első lépéseihez][getting started with unity], ha szeretnél egy bevezetőt.  
  A használt Unity verziója a [verziók][versions] fájlban van megadva. A tesztfájl felépítését a [stílusútmutató][test-file-layout] ismerteti.  
  A teszteket úgy kell megírni, hogy megfeleljenek a feladat `canonical-data.json` fájljának a [problem-specifications][] repositoryban  
`{exercise-name}.c` / `{exercise-name}.h` - A feladat forrásfájljai.  
  Kérünk, használj [include guards][include guards] elemeket a fejlécfájljaidban.
  A feladat tesztjeit a repository gyökeréből a `make test` parancs futtatásával indíthatod el.
* `makefile` - a feladat makefile-ja, ahogy fordítódna.  
Két szabály szükséges:  
test: lefordítja a test_{exercise-name}.c fájlt és lefuttatja.
memcheck: lefordítja a test_{exercise-name} fájlt a -fsanitize=address, -fno-common, -fno-omit-frame-pointer kapcsolókkal és lefuttatja
A makefile-ok feladatonként várhatóan nagyon keveset változnak, így könnyű az egyiket egy másik feladatéból lemásolni.

**Ne felejtsd el** hozzáadni a feladatot a kurzus `config.json` fájljához. Ehhez meg kell határoznod, hova illik legjobban a feladat az összes többi kurzushoz tartozó feladat sorrendjében. Emellett egy UUID-t is generálnod kell, hogy ide beírd. Mindkét feladathoz használhatod a [configlet][configlet] eszközt; az eszköz a változtatások elvégzése után még ellenőrzi és formázza is neked a `config.json` fájlt!

Mellékesen: a configlet eszköz telepítőcsomagjáért nézd meg a [configlet kiadási oldalát][configlet releases page].

## Folyamatos integráció

Ez a repository GitHub munkafolyamatokat használ, hogy bizonyos eszközöket futtasson egy pull request minden commitjánál.
A legegyszerűbb módja, hogy ezeket a munkafolyamatokat a saját hozzájárulásodon futtasd, ha nyitsz egy PR-t ebben a repositoryban a változtatásaiddal, a PR-t piszkozatnak állítod, majd hagyod, hogy a repository CI-beállítása automatikusan elintézze a dolgokat helyetted.

### CI-környezet

A GitHub azokat a virtuális gépeket, amelyeken a CI-t futtatja, [üzemeltetett futtatóknak][hosted runners] nevezi.
A munkafolyamatok némely tulajdonságát beállíthatják azoknak a futtatóknak, amelyeken futni szeretnének.

A repositoryban található munkafolyamatok csak azt írják elő, hogy mindegyikük Ubuntu 24.04-en fusson. A munkafolyamatok konkrét verziókhoz vannak rögzítve ahelyett, hogy a `latest`-re hivatkoznának, mert néhány használt eszköz eltérően viselkedhet a különböző verziókon.

### Futtasd a CI-t a saját forkodon

Ha szeretnéd, a CI-t a saját forkodon is futtathatod; egyszerűen klónozd le ezt a repositoryt a szokásos módon a GitHubon.
A [`./.github/workflows/`][workflows] mappában található YAML-fájloknak ugyanígy működniük kell.
Ha szeretnéd, hogy a [`/format`][format-workflow] automatikus művelet megfelelően működjön, hozzá kell adnod egy deploy key-t a klónozott repositoryhoz.

### A munkafolyamatok

* A `checks.yml` lefuttatja a `shellcheck`-et az eszköz szkriptjein, majd ezen eszközök közül a következőket futtatja:
  * `./bin/check-unitybegin`
  * `./bin/verify-unity-version`
  * `./bin/check-include-guards`
  * [Lychee linkellenőrző][lychee] művelet
* A `configlet.yml` letölti a configlet legújabb verzióját, majd azzal lefuttatja a `lint` parancsot a kurzuson
* A `format-code.yml` megkeresi a `/format` szöveget egy PR bármely hozzászólásában; ha megtalálja, akkor lefut a `format.sh` a feladatokon, és az abból eredő változtatásokat commitolja. Ahhoz, hogy a commit újra tudja indítani a CI-t, deploy key szükséges. A deploy key-t közvetlenül az Exercism kezeli.
* A `test.yml` a repository gyökerében lefuttatja a `make`-et, hogy letesztelje az összes feladatot

### Az eszközök

A [workflows][workflows] alapján láthatod, hogy a GitHub utasítást kap arra, hogy a [`./bin`][bin] könyvtárból futtasson eszközöket.
Az ebben a könyvtárban található eszközök munkája a következő:

* A `check-unitybegin` biztosítja, hogy minden tesztfájl helyesen adja hozzá a `UNITY_BEGIN()` sort a `main()` függvénye elején.
* A `fetch-configlet` letölti a `configlet` eszközt a [repositoryából][configlet].
* A `verify-unity-version` ellenőrzi az egyes feladatok által használt Unity tesztkeretrendszer verzióját. Azt a verziót, amelyre ennek a fájlnak ellenőriznie kell, a [`./docs/VERSIONS.md`][versions] adja meg.
* A `check-include-guards` ellenőrzi, hogy az egyes feladatok stub- és példa-fejlécfájljaiban használt include guards a helyes formátumot használja-e, a következőképpen:

    ```c
    #ifndef {EXERCISE_NAME}_H
    #define {EXERCISE_NAME}_H
    ```

* A `fetch-configlet` letölti a `configlet` eszközt a [repositoryából][configlet].

### Futtasd az eszközöket helyben

Az egyes eszközöket a saját gépeden is futtathatod commitolás előtt.
Először győződj meg róla, hogy telepítve vannak a szükséges alkalmazások (például `clang-format`, [`git`][git], [`sed`][sed], [`make`][make] és egy C-fordító), majd futtasd a kívánt eszközt a repository gyökeréből. Például:

```bash
~/git/c$ make
```

Ha csak néhány tesztet szeretnél lefuttatni a munkád ellenőrzéséhez, azokat célként adhatod meg a make számára.

```bash
~/git/c$ make acronym all-your-base allergies
```

Ennek a kurzusnak van egy tesztfuttatója az Exercism v3-hoz!
Megnézheted [itt][c-test-runner].

A tesztfuttatók egy dockerizált módot kínálnak arra, hogy egy feladat tesztjeit a tanuló kódján futtassák az Exercism v3-ban.
Ez a Docker-alapú megközelítés segít lehetővé tenni, hogy a tanulók a böngészőben programozhassanak.
Tudj meg többet a [tesztfuttatókról][test runners].

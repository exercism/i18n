# C stílusútmutató

Ez az útmutató azt a stílust írja le, amelyet a C kurzus feladatainak példa- és tesztfájljaiban érdemes követni.

Az itt leírt szabályok a [.clang-format][] fájlban megadottakon felül érvényesek, illetve felhívják rájuk a figyelmet.

## C szabvány

A kód feleljen meg a C99 szabványnak, amelynek hivatalos neve ISO/IEC 9899:1999. Ne használj POSIX-ot vagy más nem szabványos könyvtári függvényt, típust, illetve egyéb, az implementáción kívüli hivatkozást.

## Nevek

Általában a típusok, változók, struktúrák és fájlok nevét snake case írásmóddal adjuk meg: minden betű kisbetű, a névelemeket pedig `_` választja el egymástól.

```c
void some_foo_function(char * input_string, int input_string_length);
```

### Enumok

Az enum neve általában egyes számban álljon, ne többes számban.

Az enum címkéi csupa nagybetűvel, snake case írásmóddal készüljenek.

```c
enum heading {
    HEADING_NORTH,
    HEADING_EAST,
    HEADING_SOUTH,
    HEADING_WEST
}
```

### Makrók

A konstansokat definiáló makrók neve csupa nagybetűs snake case írásmóddal készül.

```c
#define CONSTANT 0x4000
```

A makróneveknél a nagybetűs snake case ajánlott, de a függvényekre hasonlító makrók kaphatnak kisbetűs snake case nevet is.

### Típusok

A szabványos, fix szélességű típusokat (a `stdint.h`-ban) előnyben részesítjük az alapvető egész típusokkal szemben.

A `bool` típust (a `stdbool.h`-ból) előnyben részesítjük a `_Bool`-lal szemben.

Ugyanígy a `size_t` és a `ptrdiff_t` (a `stddef.h`-ból) előnyösebb a memóriával kapcsolatos mennyiségek ábrázolására.

A programban `typedef`-fel definiált típusok nevét lássuk el `_t` utótaggal.
Bár tudjuk, hogy a POSIX lefoglalja a `_t` utótagot, a kurzus jelenleg nem használ POSIX-ot.

## Include guardok

Minden fejlécfájlban használj include guardot.

Általában egy include guard pár fogja közre a fejléc teljes tartalmát.

A példaimplementációban (`.meta/example.h`) és a feladat vázában (`exercise_name.h`) a guardok makrónevei kövessék a feladat nevét.
A guard makróneveinek írásmódjára a makróknál fentebb leírt szabály vonatkozik.

Például a `hello-world` feladatnál ezt írd:

```c
#ifndef HELLO_WORLD_H
#define HELLO_WORLD_H

//...

#endif
```

## Paraméterek

A függvényparamétereket minden függvény deklarációjában és definíciójában is nevezd el.
Ez a `.c` és a `.h` fájlokra egyaránt vonatkozik.
A használt nevek minden előfordulásban egyezzenek meg.
Vagyis bár az alábbi függvényprototípus érvényes C, a stílus hibás, mert a paraméter névtelen: `void foo(int);`.
A helyes prototípus, feltéve, hogy minden más deklaráció és a definíció is a `bar` paraméternevet használja, ez lenne: `void foo(int bar);`.

Ahol egyszerűbb vagy célszerűbb, ott azokat a paramétereket részesítsd előnyben, amelyeknél az argumentumot érték szerint kell átadni pointer helyett.
Különösen figyelj rá, hogy ez a `struct` típusú paraméterekre is vonatkozik.

Ha a tanulótól nem várható el, hogy az implementációjában megváltoztassa egy pointer típusú paraméter értékét, akkor azt a paramétert `const` minősítéssel kell ellátni.

## A tesztfájl felépítése

Minden feladat tesztfájlja egy meghatározott felépítést követ.
A felépítés célja, hogy segítse a közreműködőket a fájl részeinek azonosításában, és hogy segítsen a tanulóknak megérteni, hogyan működnek a tesztek.

A legtöbb C forrásfájlhoz hasonlóan a tesztfájl is include-okkal kezdődik.

```c
#include "vendor/unity.h"
#include "../src/file_under_test.h"
// any other includes here
```

Az include-okat a `setUp()` és a `tearDown()` függvények követik.
Eddig egyetlen feladat sem használja ezeket (a függvénytörzsek üresek), mégis a helyükön kell maradniuk, hogy a tesztfájlok minden platformon helyesen forduljanak.

```c
void setUp(void)
{
}

void tearDown(void)
{
}
```

Ezután a tesztfüggvények által használt segédfüggvények következnek.
Az ilyen segédfüggvények neve nem kezdődhet `test_` előtaggal.

Ezután maguk a tesztfüggvények következnek.
Ezeknek a függvényeknek a neve `test_` előtaggal kezdődik.
Az első kivételével minden tesztfüggvény első utasítása `TEST_IGNORE();` legyen.
Ennek első előfordulását kövesse a `// delete this line to run test` sorkomment.

Például:

```c
static void test_the_first(void)
{
   test_first_foo();
}

static void test_the_second(void)
{
   TEST_IGNORE();               // delete this line to run test
   test_second_foo();
}

static void test_the_third(void)
{
   TEST_IGNORE();
   char grade = 'A';
   test_third_foo(grade);
}
```

Utolsóként a fájlban a `main()` függvény áll.
A main függvénytörzse maga is egy meghatározott felépítést követ.
Először a `UNITY_BEGIN()` hívása, majd egy üres sor, aztán a tesztek.
Az utolsó tesztet egy újabb üres sor követi, mielőtt visszaadnánk a `UNITY_END()` eredményét.

```c
int main(void)
{
    UNITY_BEGIN();

    RUN_TEST(test_foo);
    RUN_TEST(test_bar);

    return UNITY_END();
}
```

# Részletesen

A programozók általában igyekeznek tökéletes szoftvert írni, és általában nem sikerül nekik.

A dolgok elromlanak, méghozzá váratlanul, és kezelnünk kell tudni ezt.

A nyelvtervezők egy része úgy gondolja, hogy a legfontosabb a hiba mielőbbi felismerése, majd a végrehajtás leállítása egy informatív üzenettel, ami megkönnyíti a debugot.

Az adattudományi nyelvek árnyaltabb megközelítést szoktak alkalmazni.
Egyes hibák annyira súlyosak, hogy azonnal le kell állni miattuk, de gyakran jobb, ha egy problémát később kezelendőként jelölünk meg, majd folytatjuk a végrehajtást.

A [Semmisség][nothingness] fogalomban láttuk, hogy a Julia különféle helyőrzőket kínál a problémás értékekhez: [`missing`][nothing], [`NaN`][NaN] és `Inf`.
Hogy ezek egy adott helyzetben jobb megközelítést jelentenek-e, mint a program leállítása, a programozó mérlegelésének kérdése.

_Egy megjegyzés a szóhasználatról_, mielőtt belevágunk a részletekbe: a Julia dokumentációja az „error” és az „exception” szavakat nagyrészt felcserélhetőnek tekinti.
Lehet, hogy az alábbi tartalom ugyanilyen következetlen lesz.

## Szabványos hibatípusok

Ha idáig eljutottál a tantervben, már biztosan láttál sok hibaüzenetet a Juliától.
Például:

```julia-repl
julia> Int(3.14)
ERROR: InexactError: Int64(3.14)
```

Egy tizedes tört egésszé alakítása pontosságvesztéssel jár, ezért `InexactError`-t kapunk.

Az `InexactError` egy típus, egyike a Juliába szabványosan beépített számos típusnak ([jelenleg 25][errors]).
Mindegyikük az `Exception` altípusa:

```julia-repl
julia> supertype(InexactError)
Exception
```

## `throw()`

A szabványos hibatípusok egy része hasznos lehet, ha a saját kódodban szeretnéd előállítani.

Mint minden konkrét típusnak, a hibáknak is van konstruktoruk.
Különféle argumentumokat várnak, ezért nézd meg a [dokumentációt][errors] ahhoz, amelyiket használni szeretnéd.

```julia-repl
julia> DomainError(42, "out of range")
DomainError(42, "out of range")
```

Ahhoz, hogy használd a hibát, csomagold a konstruktort egy [`throw()`][throw] függvénybe:

```julia-repl
julia> throw(DomainError(42, "out of range"))
ERROR: DomainError with 42:
out of range
```

## `error()`

Egy gyors, kevésbé elegáns megoldáshoz kényelmes lehet az [`error()`][error] függvény.
Egy stringet (vagy egy string alkotórészeit) vesz át argumentumként:

```julia-repl
julia> happy = false;
julia> happy || error("😞 something went wrong")
ERROR: 😞 something went wrong
```

## Egyéni hibák

Új hibatípusok létrehozása elvileg nagyon egyszerű.
Egyszerűen adj hozzá egy újabb `Exception`-altípust:

```julia-repl
julia> struct MyError <: Exception end

julia> throw(MyError)
ERROR: MyError
```

A fenti példának azonban nincsenek mezői, és a konstruktor nem vár argumentumot, így nincs befolyásunk a hibaüzenetre.
Felvehetünk egy üzenetmezőt:

```julia-repl
julia> struct AnotherError <: Exception
           msg::String
       end

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError("Wrong!")
```

Ha egyszerűen csak kiíratjuk a konstruktort, az még nem egészen az igazi.
Hasonlítsd össze a korábbi példával, ahol `DomainError`-t dobtunk.

Ahhoz, hogy egy egyéni hibát ugyanúgy kezeljenek, mint a beépített hibákat, hozzá kell adnunk egy [`showerror()`][showerror] metódust:

```julia-repl
julia> Base.showerror(io::IO, e::AnotherError) =
           print(io, "AnotherError: ", e.msg)

julia> throw(AnotherError("Wrong!"))
ERROR: AnotherError: Wrong!
```

Ez a meglehetősen gyengén dokumentált funkció lényegében beköti az egyéni hibatípusunkat a Julia szabványos hibakezelő rendszerébe.

## Állítások

Az állítás alapgondolata ez: „ennek az állításnak igaznak kell lennie, ezért panaszkodj hangosan, ha hamis.”
Ennek főként a debug során van értéke, mivel az éles kódnak soha nem szabad elbuknia egy állításon.

A [Típusok][types] fogalomban láttuk, hogy típusállításokat adhatunk hozzá, például egy függvény visszatérési típusának ellenőrzésére.

```julia-repl
julia> 42::Number
42

julia> "two"::Number
ERROR: TypeError: in typeassert, expected Number, got a value of type String
```

Általánosabban az [`@assert`][assert] makróval bármilyen Boolean értékké kiértékelődő kifejezést tesztelhetünk:

```julia-repl
julia> n = 22;
julia> @assert isodd(n) "n must be odd"
ERROR: AssertionError: n must be odd
```

## `try`...`catch`

Egyes hibák szükségszerűen végzetesek, de gyakran elvárjuk, hogy a program elegánsan helyreálljon.

Alapértelmezés szerint egy hiba azonnal leállítja az aktuális függvényt, és a hiba (a hozzá tartozó informatív üzenettel együtt) átkerül a hívó függvényhez.

Ez felfelé halad a hívási veremen, amíg a legfelső szintű kód le nem áll egy hibaüzenettel.

Bármelyik szinten elkapható a hiba egy [`try...catch`][try-catch] blokkal, amely megpróbálja kezelni.

```julia-repl
julia> n = -1;
julia> try
           log_n = log(n)
       catch problem
           if problem isa DomainError # number out of range
               # See next section for more on @warn and @info
               @warn "you may have supplied a negative real number: $n"
               @info "trying with complex argument"
               log_n = log(Complex(n))  # fallback calculation

           elseif problem isa MethodError # no idea what n is
               @error "please supply a valid argument"
 
           else
              rethrow() # the error could be anything else
           end
      end
┌ Warning: you may have supplied a negative real number: -1
└ @ Main REPL[3]:5
[ Info: trying with complex argument
0.0 + 3.141592653589793im  # success
```

A fenti példában a `log(n)`-hez `n`-nek vagy pozitív valós értéknek, vagy bármilyen komplex értéknek kell lennie.
A `try ... catch` elkapja a negatív valós értékekkel kapcsolatos problémákat, és visszaadja a helyes komplex eredményt, `iπ`-t, matematikai jelöléssel.

Ha például egy string argumentumot adsz meg, nincs mód a helyreállításra, csak annyi, hogy megkéred a felhasználót a javításra.

Végső mentőhálóként hozzáadtuk a [`rethrow()`][rethrow] hívást minden olyan esetre, ami se nem `DomainError`, se nem `MethodError`.

Vannak további opcionális ágak is:

- [`else`][else], amely akkor fut le, ha a `try` ág sikeres;
- [`finally`][finally], amely külső erőforrások felszabadítására használható, függetlenül attól, hogy a `try` sikeres vagy sikertelen: fájlok bezárása, adatbázis-kapcsolatok bontása...

***Megjegyzés:*** Néha valóban egy `try...catch` az, amire szükséged van, de kérünk, ne ess túlzásba vele.
Ha helyette egy `if...else` blokk is használható, az sokkal jobb teljesítményt nyújt, mint a kivételek elkapása.

## Naplózás

Figyelj rá, hogy a fentebb tárgyalt `error()` függvényt ne keverd össze az [`@error`][error_macro] makróval.

A függvény kivételt kelt, amely elkapás híján felfelé halad a hívási veremen.

Az `@error` makró a [`@debug`][debug_macro], [`@info`][info_macro] és [`@warn`][warn_macro] társaival együtt a [`Logging`][logging] modul része, és arra szolgál, hogy informatív üzeneteket állítson elő anélkül, hogy megváltoztatná a program menetét.

A kimenet alapértelmezés szerint a terminálra kerül (súlyosság szerint színezve), bár egy valódi alkalmazásban sok más lehetőség is kínálkozik.

```julia-repl
julia> @warn "Something looks not quite right"
┌ Warning: Something looks not quite right
└ @ Main REPL[55]:1

julia> @error "Panic!"
┌ Error: Panic!
└ @ Main REPL[56]:1
```
